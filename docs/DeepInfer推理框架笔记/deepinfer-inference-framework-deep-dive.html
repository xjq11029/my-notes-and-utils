1定位与全景：一个给 V4.1-Flash 用的「后厨运营系统」

一、这一章要解决的问题

打开 DeepInfer 的 README，第一眼看到的是三个关键词：高性能、大规模、DeepSeek 模型。但对第一次接触的人来说，真正要回答的是四个问题：

  • 模型已经能回答问题了，为什么还需要一个「推理框架」？
  • 既然 vLLM 已经开源且生态成熟，DeepSeek 为什么还要自己做一个？它和 vLLM 是什么关系？
  • 官方反复提到的 E/P/D、Wide-EP、KV 存储、四类负载均衡器，分别在解决什么瓶颈？
  • 这个开源仓库到底给了什么、没给什么？拿到它能不能直接上线一个服务？

这一章先建立全景，后续十章再逐个拆开。

二、机制与原理

2.1 推理框架到底在管什么

模型本身只做一件事：给定 token 序列，输出下一个 token 的概率分布。但要把这件事变成「同时服务成千上万个用户、还要便宜」，框架必须接管五类工作：

层次要解决的问题DeepInfer 的答案
调度多个请求如何共享一次 GPU 前向？谁先算、谁后算？显存不够时怎么办？C++ 连续批处理调度器、chunked prefill、抢占/重算、DP 步型投票
缓存每个请求的历史 KV 放哪？如何复用？显存不够时如何换出？分页 KV block + 每序列 state 槽位 + SWA 环 + 落盘布局
通信权重和专家分散在几十上百张卡上，token 如何搬运？DP / CP / EP 进程组、DeepEP 的 dispatch/combine、EPLB、userbuffer
算子每一步的计算如何在特定硬件上跑满？FlashMLA、DeepGEMM、DeepSelect、TileLang 自定义 kernel、Mega MoE
输出如何采样、如何保证格式合法、如何复现？融合采样器、MTP 验证、xgrammar 结构化输出、确定性采样

一句话：模型决定「能不能答」，框架决定「答得起不起、答得快不快、能同时答多少人」。

2.2 三个设计目标（官方）

官方 Q&A 把 V4.1 Flash 推理系统的目标归纳为三条来源：官方：

  1. 支持多厂商加速器：同一套框架既跑 NVIDIA，也跑华为昇腾，并尽量吃满各自硬件的性能。
  2. 围绕 commodity hardware 组织 P 与 D：Prefill 用普通 8 卡机，Decode 用 64–128 卡的超节点；两阶段的计算/通信/调度按各自负载特征设计，而不是一套配置硬套两个阶段。
  3. KV cache 保留超过 72 小时：给上下文复用留出长窗口，命中时直接跳过重复 prefill；代价是要承担容量与管理开销。

这三条目标直接解释了后面所有设计：为什么有 Wide-EP、为什么有独立的 state cache、为什么有 KV 落盘布局、为什么调度器要把 prefill 和 decode 当成两种「步型」。

2.3 生产架构：E/P/D + Wide-EP + 专用存储 + 四类 LB

官方给出的参考架构是 E/P/D 三阶段分离 + 专用存储节点来源：官方：

各部分的职责与官方口径：

组件作用关键配置 / 数据
VE（Vision Encoder）把图片编码成 embedding，与语言模型解耦一般单 GPU 一个实例，推荐便宜卡
PE（Prefill Engine）读完整 prompt、建立 KV cache、产出首 tokenEP2–8 / DP2–8，取 HBM 允许的最小并行度
CE（Decode Engine）逐 token 解码EP64–128 / DP64–128，取 GPU 允许的最大并行度
KV 存储跨请求、跨机器复用 block KV3FS，约 100 PiB SSD；TTL 3 天 / 7 天
四类 LBP / D / VE / 专家四个维度的负载均衡详见第 11 章

几个容易误解的点：

  • P 与 D 分离后，TTFT（首 token 延迟）与 TBT（相邻 token 间隔）可以分别优化：P 端决定首 token 何时出来，D 端决定后续 token 的节奏；这也是生产要把两阶段拆开的核心原因之一来源：官方。
  • Wide-EP 是 Decode 的核心：把专家摊到 64–128 张卡上，单步解码时每张卡只需搬运很少的专家权重，MoE 部分的访存压力大幅下降；再配合 EPLB，吞吐才能上去来源：官方。
  • 生产当前不用 TP，也不用 CP来源：官方。开源代码支持 --cp，示例里也有 CP8 的跑法，但生产部署走的是 DP + EP；第 5、10 章会讲 CP 在代码里如何实现。
  • 最小高效部署单元是 64P + 64D，因为推荐的 Decode 配置本身就要 64 卡以上；官方也说 1P + 1D 可以部署，但效率不在一个量级来源：官方。
  • P/D 可以跨数据中心：V4.1 的 KV 压缩得足够狠，跨机房传输在技术上可行，代价是可靠性；官方给的经验带宽是每 8 卡约 400 Gbps来源：官方。

2.4 开源版与生产版的差距

README 里有一句非常关键的话来源：官方：

说明

Required for a complete inference service (not included in this release):

- A KV cache system

- VE/Prefill/Decode disaggregation (most required engine functionality is already implemented)

- Load balancing across data-parallel replicas for both prefill and decode

翻译成工程语言：

能力状态影响
核心引擎（调度 / cache / 模型 / 采样）有可以跑离线批量推理
EngineType.PROMPT / COMPLETION有为 P/D 分离留了钩子与虚函数
P/D 的部署编排、请求路由无需要自己写服务层把两端接起来
KV cache 跨机存储 / 前缀匹配无开源版只有单机显存 + 单机 state cache
四类负载均衡器（P / D / VE / 服务层专家调度）无需要自己在服务层做路由；引擎内的 EPLB 除外
在线 HTTP / gRPC / 流式 API无LLMEngine 明确「本版本不含在线服务封装」

所以正确的预期是：这是一个「引擎内核 + 离线推理 + 研究样本」的开源，而不是一个开箱即用的在线推理平台。它的价值在于：核心调度、KV 布局、MoE 并行、投机解码、异步调度这些最难的部分，代码是完整可读的。

2.5 与 vLLM 的关系：骨架相同，器官大改

几乎每个核心文件头都写着 Derived from vLLM; modified by DeepSeek.，README 的致谢也说明它「最初主要基于 vLLM 构建」，并参考了 SGLang 与 TensorRT-LLM来源：官方 / 一手。

维度保留自 vLLM 的部分DeepSeek 改动 / 新增
入口LLM / LLMEngine / Worker 的分层离线入口保留，在线封装移除
调度Scheduler / BlockManager / Sequence 的概念调度器整体改为 C++；新增 DP 步型投票、MTP 变长预算、ZOS
缓存PagedAttention 式的 block table新增 state cache、SWA 环、压缩 KV、YoCo dropped region
模型nn.Module + 权重加载V4.1 专用模块（MLA 变体、Indexer、YoCo、Engram、HC）
采样SamplingParams / Sampler融合采样、DFlash 验证、结构化输出 mask、确定性采样
并行DP / CP / EP 概念EPLB、Wide-EP、Mega MoE、昇腾适配

因此，不要指望它兼容 vLLM 的 API 或配置：EngineArgs 的字段不同，没有 OpenAI Server，模型也只支持 V4.1-Flash。把它理解成「vLLM 的骨架 + DeepSeek 的器官」更准确。

四、常见坑与边界条件

  1. 「开源了就能部署在线服务」：不能。没有 HTTP Server、没有请求队列、没有 P/D 编排、没有 KV 存储与负载均衡。你要自己写服务层，或者只用离线批量推理。
  2. 「能不能跑别的模型」：基本不能。模型加载、注意力、MoE、MTP 都按 V4.1 的字段写死；换个模型需要改 model_executor/models/，不是改个配置就行。
  3. 「开源版有没有前缀缓存」：调度器支持 fork 子序列共享父序列的 block，但自动前缀匹配在官方生产架构里由 Entrypoint + kvcache-store 完成，这部分没开源；不要以为 prefix_caching_hit 变量就代表有完整的 prefix cache 服务。
  4. 把官方生产数字当成本地 benchmark：155 万亿 token/天、$38/GPU-hour、AIME 99.9% 都是官方口径，依赖完整生产栈与 V4.1-Flash 权重，开源仓库本身复现不了。
  5. Windows 开发机：不支持。代码里有 posix_ipc、fcntl、mmap、NUMA 绑定、C++ 扩展，Windows 上连构建都过不去。
  6. 消费级 GPU：不支持。SM100 是数据中心卡；capability 检测与 kernel 选择都按目标硬件写死。
  7. 许可证：主仓库 Apache-2.0，但 vendor/ 子模块各自有许可证，商用前逐个核对。

五、关键结论

  1. DeepInfer 是推理引擎，不是推理平台：核心引擎完整，服务化组件缺失。
  2. 它只为 DeepSeek-V4.1-Flash 服务：不是通用模型运行时。
  3. 生产架构是 E/P/D + Wide-EP + 专用 KV 存储 + 四类 LB，开源版只覆盖其中的引擎部分。
  4. 它与 vLLM 同源但已大幅分叉：调度器改 C++、加 ZOS、加 V4 模型、加 EPLB、加 state cache。
  5. 三条设计目标（多厂商、commodity P/D、长 KV 保留）解释了后面几乎所有工程取舍。
  6. 硬件门槛极高：Linux + GCC 13 + Python 3.12 + CUDA 13 / CANN 9.2 + SM100 / Ascend 950。
  7. 它的最大价值是设计样本：即使跑不起来，调度、缓存、并行、投机解码的实现也值得逐章读。

本章要点回顾

  • 推理框架管五件事：调度、缓存、通信、算子、采样/输出；模型只管「下一个 token 的概率」。
  • 官方三目标：多厂商加速器、commodity P/D、KV 保留 >72 小时。
  • 生产架构：E/P/D 分离 + Wide-EP（Decode EP64–128）+ 3FS KV 存储 + 四类 LB。
  • 开源版：引擎 + 离线推理 + 多模态 + 投机 + SO + 评测；缺 在线服务、KV 存储、P/D 编排、LB。
  • 与 vLLM：同源分叉，API 与配置不兼容。
  • 门槛：Linux / GCC 13 / Python 3.12 / CUDA 13 或 CANN 9.2 / SM100 或 Ascend 950。
  • 正确预期：当设计样本读，不要当开箱即用的服务平台。

2代码地图与启动链路：从 LLM.generate() 到一次 GPU step

一、这一章要解决的问题

第一次读 DeepInfer，最容易迷路的地方不是算法，而是对象太多：LLM、LLMEngine、Worker、ModelRunner、CacheEngine、Scheduler、DeepseekForCausalLM、V4Attention、Sampler……它们分别在哪个进程、什么时候创建、谁调用谁？

这一章沿一条最短路径走完：

文本 / 输出
LLM.generate()
  → EngineArgs / 四类 Config
  → LLMEngine 初始化（worker、模型、KV、调度器、CUDA Graph）
  → step() 循环（调度 → 执行 → 后处理）
  → RequestOutput

把这条链路走通，后面每章都只是在这条链路上放大某一段。

二、机制与原理

2.1 入口：LLM 只是一个薄壳

deepinfer/entrypoints/llm.py 的 LLM 做三件事：

  1. 补默认值：disable_log_stats=True、stop_preempted_request=False，并设置 TOKENIZERS_PARALLELISM=false。
  2. 构造 EngineArgs：把 model / tokenizer / expert_parallel_size / gpu_memory_utilization / seed / ... 转成引擎参数，并标记 offline_inference=True。
  3. 驱动引擎：generate() 逐个 add_request()，然后 _run_engine() 循环调用 llm_engine.step()，直到没有未完成请求；最后按 request_id 排序、反分词输出。

注意两个与在线服务不同的点来源：一手：

  • LLM 默认 stop_preempted_request=False：显存不足时优先重算被抢占的请求，而不是直接终止；EngineArgs 本身的默认值反而是 True。
  • LLM 默认 disable_log_stats=True：离线批量推理不打印每步统计；需要观测时显式打开。

2.2 第一层配置：EngineArgs → 四类 Config

deepinfer/engine/arg_utils.py 的 EngineArgs 是唯一入口参数对象，create_engine_configs() 把它拆成四个配置：

配置文件负责什么关键默认值
ModelConfigdeepinfer/config.py模型路径、tokenizer、最大长度、dtype、是否多模态max_model_len=4096（未指定时）

2.4 第三层：显存 profile 与 KV 分配

_init_cache() 先让每个 worker 跑 profile_num_available_blocks()，再做三件事：

  1. 模拟一次满负载 step：用 max_num_seqs 条虚拟序列、总 token 数等于 max_num_batched_tokens，跑完整的 forward + sample + post-process；MoE 还会强制 1.8 倍不均衡，把最坏情况的显存峰值算进去。
  2. 算可用 KV 显存：总显存 × gpu_memory_utilization − 峰值显存 − 2 × state cache；除以每个 block 的字节数得到 block 数。
  3. 全局对齐 block 数：所有 rank 做 all-reduce，按 SUM / world_size 取平均后向下取偶；这样得到的是全局统一值，但不保证每张卡都放得下——docstring 写的是「取最小值」，实现是平均值，显存不对称时要按最小卡估算（详见第 4 章）。

得到 num_gpu_blocks 后，CacheEngine.allocate_gpu_cache() 一次性分配：

  • gpu_blocks：分页 KV 的主缓冲区（所有层共享一段大 buffer，按层切 view）。
  • gpu_states：每序列一个 state 槽位（SWA / 压缩状态）。
  • 同时把布局信息写回 CacheConfig（bytes_per_block、num_state_seqs、bytes_of_state_per_seqs）。

接着 init_cache_engine() 构造 GPUCacheInterface，再 warm_up_model() 捕获 CUDA Graph。CUDA Graph 捕获失败的常见原因之一是显存不够：LLM 的文档字符串专门提示，遇到 illegal memory access 可以调低 gpu_memory_utilization 再试来源：一手。

四、常见坑与边界条件

  1. LLM 与 EngineArgs 默认值不一致：LLM 把 stop_preempted_request 设为 False，EngineArgs 默认 True。离线跑长请求时，前者会重算而不是终止；在线语义下通常反过来。
  2. max_model_len 不传就是 4096：不是「模型支持多少就多少」。长上下文实验必须显式设置，并同时保证 max_num_batched_tokens 足够。
  3. max_num_batched_tokens 有下限：至少 max_num_seqs × (1 + nextn)；不开 chunked prefill 时还必须 >= max_model_len，否则启动直接报错。
  4. CUDA_VISIBLE_DEVICES 必须设置：LLMEngine.__init__ 第一行就读取它，没设会 KeyError；昇腾下要求与 ASCEND_RT_VISIBLE_DEVICES 一致。
  5. driver worker 不是独立进程：它在引擎进程内，因此引擎里的 Python 代码与模型执行共享 GIL；真正的并行来自 GPU 流与 CP 子进程。
  6. CUDA Graph 捕获可能 OOM：调低 gpu_memory_utilization 或关掉 graph（DEEPINFER_ENFORCE_EAGER=1）再试。
  7. RequestOutput 会被下一步释放：不要在异步代码里裸存指针，先 clone。
  8. 离线结束要 flush：ZOS 下最后一步的 post-process 可能还在途，LLM._run_engine() 在 unfinished=False 时会调用 flush_inflight_reqs()，自定义调用方也要做。
  9. LLM.close() 不是可选的：它会停 worker、关 SO 线程池、释放共享内存；只靠 GC 可能在退出时留下资源泄漏告警。

五、关键结论

  1. LLM 是薄壳，真正的中枢是 LLMEngine；EngineArgs 是唯一参数入口。
  2. 配置推导有两个隐藏项：runtime_max_model_len 要加投机/ZOS 余量，max_num_batched_tokens 有下限。
  3. 初始化顺序是：worker → 模型 → 显存 profile → KV/state 分配 → 调度器 → CUDA Graph；顺序不能换。
  4. 进程模型是 driver + CP 子进程；driver 在引擎进程内，CP 通过共享内存广播方法调用。
  5. 一次 step() = 调度 → 执行（forward/sample）→ 后处理；ZOS 把后处理推迟一轮，与下一次 forward 重叠。
  6. 输出对象有池化生命周期，跨步使用必须 clone。

本章要点回顾

  • LLM.generate() → EngineArgs → 四类 Config → LLMEngine。
  • 初始化八步：tokenizer、模型类、worker、load_model、profile、init_cache、scheduler、stats。
  • driver worker 在引擎进程内；CP 其余 rank 是子进程，通过 cp_broadcast_object 同步方法调用。
  • 显存 profile 用「满负载模拟 + 强制 MoE 不均衡」算峰值，再全局取最小 block 数。
  • 一次 step：C++ 调度 → Worker.execute_model_step 四阶段 → scheduler.process_outputs → RequestOutput。
  • ZOS decode 步的 post-process 留到下一步；离线结束时必须 flush。
  • 常见坑集中在默认值、长度下限、CUDA_VISIBLE_DEVICES、CUDA Graph OOM 与输出对象生命周期。

3调度器：连续批处理、chunked prefill 与抢占

一、这一章要解决的问题

一个推理服务同时收到 200 个请求：有的 prompt 只有 100 token，有的 10 万 token；有的刚进来，有的已经生成到一半。GPU 每一刻只能执行一批计算，调度器必须回答：

  • 这一步做 prefill 还是 decode？两者能混在一起吗？
  • 哪些请求进这一批？超长 prompt 怎么切？
  • KV 显存块不够时，抢占谁、被抢占的请求怎么办？
  • 多张数据并行卡之间，如何保证同一步做同一类工作，不让某些卡空转陪跑？

DeepInfer 的调度器在 csrc/engine/scheduler.hpp，整体是 C++ 实现、Python 通过 pybind 调用。这一章按「选步型 → 选请求 → 分配块 → 生成元数据」的顺序拆开。

二、机制与原理

3.1 三种引擎类型

  • running：正在 decode 的请求。
  • prompted：P 端做完 prefill、等待 D 端接收的请求（P/D 分离用；单机 NORMAL 通常为空）。

3.3 NORMAL 引擎：先投票决定「这一步做 P 还是 D」

NORMAL 引擎不能简单地在每个 rank 上独立决定做 prefill 还是 decode，否则 DP 组里会出现「一半卡做 P、一半卡做 D」的集体通信错位。DeepInfer 的做法是全组投票（_schedule）：

文本 / 输出
每 prefill_attempt_interval（默认 70）个 decode step → ALL 点
  （刚做完 prompt step 的下一步 decode_step=0，也落在 ALL 点）
每 prefill_any_attempt_interval（默认 100）个 decode step → ANY 点
其余 step → 直接 decode
  • ALL 点：所有 rank 都有 prefill 活，才全组切到 prefill，避免「一个 rank 干活、其余陪跑空 prompt step」。
  • ANY 点：任一 rank 有活就全组切 prefill，给孤立 rank 兜底，防止它饿死。
  • 两类点重合时按 ANY 算。
  • 做 prefill 前还要看 GPU cache 使用率 ≤ 0.9（GPU_CACHE_PREFILL_WATERMARK），否则继续 decode，先消化显存。
  • 预填充后还有第二次投票：确认至少一个 rank 真的排出了 prefill；如果全组都空手（slot 满、KV 块不够），就转 decode，避免「空 prompt step 把 decode_step 清零 → 下一步又投票 → 又空手」的死循环。

这里的 decode_step 是全组同步的计数器：每次 decode +1，每次 prompt step 清零。投票次数与语义在全组一致，不会卡在 all-reduce。

3.4 Prefill 调度：FIFO + chunked + 多重上限

_schedule_prefill 从 waiting 队头开始，逐个尝试：

prompt_limit 的取值：

文本 / 输出
chunked_prefill = true  → max_model_len

也就是说，不开 chunked prefill 时，单条 prompt 不能超过一步的 token 预算；超过就直接被忽略。

chunked prefill 如何切

如果当前 prompt 放不进剩余预算，就切一段：

文本 / 输出
new_workload = min(seq_workload,
                   floor((max_num_batched_tokens - num_batched_tokens) / cp_align) × cp_align)

cp_align = cp_size × 2（CP > 1 时），保证每张 CP rank 分到的 token 数是偶数、可均分。切出来的这一段就是 seqlen_q，剩下的部分留在 waiting，下一步继续。

还有三个细节：

  1. chunk checkpoint：chunk_checkpoints 允许调用方指定必须停下的位置（例如多模态的图片边界）。
  2. 图片不能被切开：_adjust_chunk_size 检查切点是否落在 IMAGE + IMAGE_PAD × N 的图片单元内部；如果是，往前收缩或往后扩展，整个图片单元留到下一个 chunk。
  3. NORMAL 引擎一次只切一条：切完当前 prompt 就 break，避免一个超长请求把整步预算吃光。
fork 子序列与前缀共享

如果 block_table 非空、且 branch_id 以 _ 开头，说明这是从父请求 fork 出来的子序列：

  • 保留父序列已有的 block（pin 住），只为新增部分分配新 block；
  • 如果 cache.num_tokens 不是 block 的整数倍，把最后一个半满 block 复制一份（clone_blocks），避免子序列写脏父序列；
  • 克隆 state（clone_states），子序列从父序列的 state 快照继续。

这套机制用于 benchmark 里的「共享前缀、不同后缀」场景，不是完整的前缀缓存服务。

注意

⚠️ 变量名 prefix_caching_hit 有误导性：新建请求（block_table 为空）也会被置为 true。它实际控制的是「是否跳过 lookahead_tokens 的前置检查」，而不是「命中了前缀缓存」。

3.5 Decode 调度：先 admit，再按输出长度排序

_schedule_decode 分两段：

  1. admit：把 prompted 队列里的请求转入 running，直到 max_num_seqs；fork 请求要先克隆 state 和最后一个半满 block。
  2. 选批与抢占：
    • 按 get_output_len() 降序排序；
    • 从输出最短的一端开始调度（running[r-1]）；
    • 每调度一条，_append_slot 检查是否需要新 block；没有空闲 block 时，从输出最长的一端抢占（running[l]），直到腾出一块；
    • 如果腾不出来，当前这条也被抢占。

这实际上是一个 最短输出优先 + 最长输出先被抢占 的策略：短请求尽快完成，长请求在显存紧张时让位。官方注释把它称为 LCFS，但从代码行为看，更准确的描述是「按输出长度排序的短作业优先」。

被抢占的请求有两条路（_preempt）：

条件行为
stop_preempted_request == true标记 FINISHED_PREEMPTED，释放 block，直接结束
stop_preempted_request == falsereset_for_recompute()，放回 waiting 队头，释放 block；下次重新 prefill
请求带结构化输出（so_status != 0）且允许重算不支持重算，直接结束（SO 状态无法回滚）

3.6 MTP 变长调度：这一步验证几个草稿？

decode 调度最后会调用 _mtp_varlen.schedule(scheduled, seqlens_q)，为每个请求决定本步的 seqlen_q（1 个 golden token + 验证几个 draft）。它综合两类信息（csrc/engine/mtp_varlen.hpp）：

  • 接受率：用 N−2 轮的置信度估计选「最佳 batch 大小」，用 N−1 轮的值给每个请求分配验证名额；
  • 耗时模型：用 profile_decode_perf() 得到的 (batch_size, forward_ms) 曲线，加上运行时拟合的斜率与 sampler 耗时，估算每个 batch size 的吞吐，取最大者。

结果是「把验证名额优先给最可能被接受的请求」，这也是第 7 章的主题。不开 DEEPINFER_ENABLE_MTP_VARLEN 时，每个请求固定验证 nextn 个（默认 5）。

3.7 BlockManager：一个带引用计数的空闲链表

csrc/engine/block_manager.hpp 的 BlockManager 很简单，但有几个关键设计：

  • block 0 保留：Blocks 构造函数把 0 当作「空/占位」，从 1 开始分配。CUDA Graph 的 padding 行就落在 dummy slot 0。
  • 引用计数：allocate 加 1，free 减 1，归零才回到空闲链表；因此 fork 子序列可以共享父序列的 block（pin_blocks）。
  • 空闲链表：侵入式双向链表，_pop_front O(1)，适合每步高频分配/释放。
  • state 与 block 联合分配：BlockManagerMutexAcquire::try_allocate_seq 同时检查 block 与 state，任一不足就返回失败；state 不够时，block 也不会被占用。

3.2 一次调度的决策流

3.3 SequenceMetadata 里有什么

schedule() 为每个被选中的序列构造元数据，关键字段：

  • seqlen_q：本步 query 长度（prefill 是 chunk 长度；decode 是 1 + 验证的 draft 数）。
  • seqlen_k：本步 key 总长度 = cache.num_tokens + total_inflight_tokens + seqlen_q；异步调度下要加上在途 token。
  • block_table：KV block 列表（decode 时使用）。
  • position_end 校验：保证不超过 runtime_max_model_len，否则 RoPE cache 等按位置索引的 buffer 会越界。
  • start_inflight_step(max_seqlen_q)：把本步的在途 token 记到序列状态里，供下一步的 seqlen_k 使用。

这也是 ZOS 下 CPU 侧元数据会「滞后一步」的根源：本轮调度时，上一轮的采样结果还没回到 CPU，只能用估计值；第 8 章会讲如何在 GPU 上修正。

四、常见坑与边界条件

  1. COMPLETION 引擎必须 stop_preempted_request=true：否则构造函数直接 TORCH_CHECK 失败。
  2. 不开 chunked prefill 时，prompt 不能超过一步预算：超过会被标记 FINISHED_IGNORED，而不是报错或自动切分，排查时容易误以为「请求丢了」。
  3. prefill_max_sum_seqlen_k 默认 2^30：看起来无限，但它限制的是所有 prompt 的 seqlen_k 之和，长上下文高并发时会先撞上这个上限，表现为「有请求但调度不动」。
  4. CP 对齐会浪费预算：cp_align = cp_size × 2，chunk 会被向上取整到该倍数；CP 越大，尾部 padding 越多。
  5. 抢占带 SO 的请求会直接终止：结构化输出的 matcher 状态无法重算，stop_preempted_request=false 也救不回来。
  6. prefix_caching_hit 不是前缀缓存命中：见 3.4 的说明；真正的跨请求前缀匹配不在开源调度器里。
  7. NORMAL 的「陪跑空步」是设计行为：某个 rank 没有 prefill 活、但组内其他 rank 有活时，它会返回空 prompt step 以保持步型一致；这不是 bug，但会让该 rank 的有效吞吐下降。
  8. decode 排序不是严格 LCFS：代码按输出长度降序排序后从最短端调度、从最长端抢占；理解成「短作业优先 + 长请求先让位」更准确。

五、关键结论

  1. 调度器在 C++ 里，Python 只负责把 SequenceMetadata 转成输入张量。
  2. NORMAL 引擎用 ALL / ANY 两档投票决定全组做 P 还是 D；COMPLETION 只能 decode，PROMPT 只能 prefill。
  3. Prefill 是 FIFO + chunked + 多重上限；decode 是 短输出优先 + 长输出先被抢占。
  4. BlockManager 用 引用计数 + 侵入式空闲链表支持 fork 共享与前缀复用。
  5. 显存不足时，请求要么被重算（回 waiting），要么被终止；带结构化输出的请求不能重算。
  6. MTP 变长调度把「验证几个草稿」也纳入调度决策，目标是最大化每步有效吞吐。

本章要点回顾

  • 三种引擎类型：NORMAL / PROMPT / COMPLETION；COMPLETION 必须开 stop_preempted_request。
  • NORMAL 用 70 步 ALL 点 + 100 步 ANY 点投票，避免 DP 组步型不一致。
  • Prefill：FIFO、chunked、prompt_limit、prefill_max_sum_seqlen_k、图片边界对齐、fork 共享。
  • Decode：admit → 按输出长度排序 → 短输出先调度、长输出先抢占。
  • 抢占两种结局：重算（回 waiting）或 终止（FINISHED_PREEMPTED）；SO 请求只能终止。
  • BlockManager：block 0 保留、引用计数、O(1) 空闲链表、block/state 联合分配。
  • MTP 变长调度：用置信度与耗时曲线决定每步验证多少草稿。

4KV cache 与状态缓存：分页块、StateBlock 与 SWA 环

一、这一章要解决的问题

推理框架里最贵的资源不是算力，是显存里的历史状态。每个请求的每一层、每个 token 都要留下 KV；上下文越长、并发越高，KV 越大。DeepInfer 的 KV 管理不是「一个 tensor 存所有层」，而是三套结构叠在一起：

  1. 分页 block KV：主 KV、压缩 KV、Indexer KV，按 128 token 一块分配；
  2. 每序列 state 槽位：SWA 环、压缩状态，按序列独占；
  3. 落盘 / 跨机布局：哪些字节需要写盘、哪些只在本机、P 端如何交给 D 端。

这一章回答：这三套结构分别存什么、怎么对齐、显存怎么算、哪些状态会丢、丢了怎么恢复。

二、机制与原理

4.1 先分清五类缓存张量

V4.1 的注意力不是单一 KV，cache_engine.py 的 KVCache 数据类把每层的缓存分成五类来源：一手：

字段存什么布局是否分页
ca_cache压缩 KV（compressed attention），每 N 个 token 压成一个[num_blocks, block_size/N, 1, bytes_per_token]是
ica_cacheIndexer KV（稀疏索引器的 K）[num_blocks, block_size/N, 1, index_bytes]是

几个常量：

  • block_size = 128：ModelMetadata.resolved_tokens_per_block 直接返回 128，不是 vLLM 常见的 16。
  • KVSTORE_GRAIN = 128：落盘粒度也是 128 token，只在 128 的整数倍位置写。
  • 对齐 128 B：kvcache_align_to = 128，MXFP8 / 稀疏 FP4 的 scale 需要块对齐。
  • 主 KV 每 token 288 B 或 528 B：per-16 FP4 为 288 B；MXFP8 为 528 B（512 B 数据 + 16 B scale）。Indexer KV 是 per-32 UE8M0 的 FP4。

4.2 分页 block KV：所有层共享一段大 buffer

CacheEngine.allocate_gpu_cache() 一次性分配两块大显存：

文本 / 输出
gpu_blocks : [total_kv_bytes]        # 所有层的分页 KV 拼在一起，按层切 view
gpu_states : [num_state_seqs, total_state_bytes]  # 每序列一个 state 槽

GPUCacheInterface._kvcache_layout() 负责「切 view」：遍历运行时注意力层，算出每层的 (layer_id, kv_offset, kv_length)，再把 gpu_blocks 的对应区间包装成该层的 KVCache。这样做的原因有三：

  • 一次分配，避免每层单独分配造成碎片；
  • 统一 block id 空间：block table 里存的是全局 block id，所有层用同一套 ID；
  • 共享 KV：layer_kv_map / layer_index_module_map / layer_index_k_map 允许后面的层复用前面层的 cache，不重复占空间（share-kv / share-index）。

block 的分配与回收由 BlockManager 负责（第 3 章）：block 0 是保留的 dummy，CUDA Graph 的 padding 行写到这里；其余 block 用引用计数支持 fork 共享。

4.3 StateBlock：每序列一个「固定大小的抽屉」

分页 block 只解决「按 token 增长」的 KV；SWA 与压缩状态是每序列固定大小的，放进 state cache 更合适。

StateBlock 把一个 state 槽分成两段（cache_engine.py:221）：

文本 / 输出
[ stored region: SWA ] [ dropped region: YOCO consumer SWA | compression state ]
区域内容是否落盘跨机传输
stored region需要跨请求保留的 SWA 窗口（V4.1 前 20 层）✅✅
dropped region — YOCO consumer SWAconsumer 层的 SWA，恢复靠 prefill 重算❌✅（P→D 传完整 state）
dropped region — compression stateca_state / ica_state 等压缩边界累加器❌✅

state_size_to_disk 只包含 stored region：V4.1 是 20 层 × 134 token × 528 B = 1,415,040 B/序列来源：官方 Q&A。134 = 128 的 SWA 窗口 + 6 个投机回退位置；多出来的 6 个位置由 ring buffer 的额外槽位吸收。

说明

为什么 consumer SWA 可以丢？因为 YoCo 的 consumer 层在 prefill 时可以重算；而 compression state 的窗口边界天然对齐到 128 token 的落盘粒度，没有跨边界依赖，所以也可以不落盘来源：官方 Q&A。

4.4 SWA 环：窗口 + 回退余量

SWA（Sliding Window Attention）只保留最近 window_size 个 token 的 KV。swa_cache 是每序列一个环形缓冲区，大小是：

文本 / 输出
swa_block_size_inference = window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS

DEEPINFER_MAX_BACKTRACKING_TOKENS 默认取 max(env, nextn + 1)；nextn=5 时是 6。多出来的位置用于投机解码被拒绝时的回退：验证失败要回到之前的 token，窗口必须还能覆盖它。

这里有两个容易混淆的点：

  • SWA 只存窗口，不存全量；全量历史在压缩 KV 里（每 N 个 token 一个 key）。
  • SWA 槽位是按序列固定分配的，不是按 token 分页；所以它不进入 block table，而是通过 state_id 索引。

4.5 落盘：为什么是 128 的整数倍

KVSTORE_GRAIN = 128 是落盘粒度。具体规则来源：官方 Q&A：

  • Prefill 后：在序列末尾保留 1 个 token，再向下取整到 128 的倍数；如果不足一个完整的 128 单元，本轮不落盘。
  • Chunked prefill 中间：不落盘，只有最后一个 chunk 落。
  • Decode 期间：显存里另有一份 replica 区域；每跨过一个 128 边界，就把当前窗口复制到 replica；请求结束时从最近一次完整副本取数，落点向下取整到 128。
  • 最多溢出 5 个 token：复制位置可能越过边界最多 5 个 token，由 ring buffer 多出的 6 个位置吸收。

DEEPINFER_PREFILL_STORE_EXTRA_STATE（默认关）会为每个 SWA 层额外保留 DEEPINFER_PREFILL_STORE_EXTRA_SIZE（默认 128）个 token，目的是让多轮对话更容易命中——因为落盘只在 128 倍数处发生，prefill 结束时可能刚好差一点。

4.6 显存怎么算：profile + 2 倍 state + 全局平均

WorkerBase.profile_num_available_blocks()（worker/base.py:212）：

文本 / 输出
available = total_gpu_memory × gpu_memory_utilization − peak_allocated
available -= 2 × state_cache_size        # state store & copy buffer
num_gpu_blocks = available // cache_block_size
  • peak_allocated 来自一次满负载 profile run（含 MoE 强制 1.8 倍不均衡）。
  • state cache 乘 2：一份是正常 state，一份是 copy buffer（落盘 / P→D 传输要复制）。
  • 最后跨 rank 做 all-reduce，取平均后向下取偶（代码是 SUM / world_size / 2 * 2）。

得到的 block 数还要过一道校验（llm_engine.py:_init_cache）：

文本 / 输出
max_seq_len = block_size × num_gpu_blocks × 0.8
require runtime_max_model_len <= max_seq_len

不满足就直接报错，提示你提高 gpu_memory_utilization 或降低 max_model_len。

4.7 生产环境的三级存储

官方 Q&A 给出的生产分层来源：官方：

内容介质副本管理者

关键设计是把 block KV 放到独立存储集群，而不是本地分层存储：

  • 任何 prefill 机器都能命中任意前缀，不需要「前缀亲和」路由；
  • 存储扩缩容与计算节点解耦；
  • 计算节点故障不影响 KV（计算节点故障率比存储节点高一个数量级以上）。

这套存储系统没有随开源仓库发布；开源版只有单机 HBM + 单机 state cache，以及为 P→D 搬运预留的布局字段（state_size_to_disk、TO_CE 视图等）。

4.3 share-kv 是怎么省空间的

_get_kv_mapped_layer_id / _get_index_mapped_layer_id 会读取模型配置里的 layer_info_shared_cfg：

  • layer_kv_map[layer_id] = source_layer_id：本层复用 source 层的 KV，不再单独占空间；
  • layer_index_module_map / layer_index_k_map：Indexer 的 K 也可以共享；
  • 只允许指向前面已经处理过的层（mapped <= layer_id），否则断言失败。

所以 KVCache 的布局是「按需分配」的，不是每层都占一份；模型配置里共享得越多，block 能装下的 token 越多。

四、常见坑与边界条件

  1. 文档说取最小值，代码取平均值：_init_cache 的 docstring 写「take the minimum number of blocks across all workers」，但实际是 all-reduce SUM 后除以 world size。各 rank 显存不对称时，平均值可能让某些卡放不下；排查 OOM 时以代码为准。
  2. state cache 要按 2 倍预留：profile 时减去了 2 × state_size；如果手动估算显存，漏掉 copy buffer 会高估可用 block 数。
  3. DEEPINFER_MAX_BACKTRACKING_TOKENS 不能小于 nextn + 1：环境变量定义里用 max(v, nextn+1) 兜底；关掉投机后它也不会自动变小，仍按配置值占空间。
  4. SWA 只在 128 倍数落盘：多轮对话如果每轮长度不是 128 的倍数，命中率会低于预期；DEEPINFER_PREFILL_STORE_EXTRA_STATE 就是为这个场景准备的。
  5. chunked prefill 中间不落盘：只有最后一个 chunk 落；如果请求被 abort，之前 chunk 的 KV 不会进入持久化。
  6. YoCo consumer SWA 不落盘：依赖 prefill 重算恢复；如果关闭截断（DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=off）但模型仍有 consumer 层，load_state_from_store_to_prefill_cache 会断言失败。
  7. block 0 不可用：它是 dummy / padding 槽；任何「为什么 block 数比预期少 1」的疑问都来自这里。
  8. 共享层不占新空间，但要求顺序：share-kv 只能复用前面的层；配置写反会在启动时断言。

五、关键结论

  1. V4.1 的 KV 是三套结构：分页 block KV、每序列 state 槽、落盘/跨机布局。
  2. block_size = 128、KVSTORE_GRAIN = 128、对齐 128 B，是整套布局的三个基准数。
  3. StateBlock 把 state 分成 stored（需落盘） 与 dropped（可重算） 两段；V4.1 每序列落盘量约 1.4 MB。
  4. SWA 是环形窗口 + 6 token 回退余量；只在 128 倍数处落盘，chunked prefill 中间不落。
  5. 显存按「profile 峰值 + 2× state」计算，block 数跨 rank 取平均后取偶。
  6. 开源版只有单机 cache；生产的三级存储（HBM / host / 3FS）与跨机命中未开源。

本章要点回顾

  • 五类 cache：ca_cache、ica_cache、swa_cache、ca_state、ica_state。
  • block_size=128、KVSTORE_GRAIN=128、kvcache_align_to=128。
  • StateBlock = stored SWA + dropped（YoCo consumer SWA + compression state）。
  • V4.1 落盘量：20 层 × 134 token × 528 B ≈ 1.4 MB/序列。
  • SWA 窗口 + MAX_BACKTRACKING_TOKENS（默认 6）组成环形槽。
  • 显存公式：总显存 × utilization − profile 峰值 − 2×state。
  • 生产三级存储：HBM（在途）/ host（SWA）/ 3FS（分页 block KV），未开源。
  • 共享层（share-kv / share-index）只复用前面的层，不重复占空间。

5注意力栈：MLA、压缩 KV、稀疏索引与 SWA

一、这一章要解决的问题

V4.1 的注意力不是「一次标准 scaled dot-product attention」，而是几条分支拼起来的复合结构：

  • Q/KV 先做低秩投影（MLA），KV 不存完整矩阵，只存低秩潜向量；
  • 长上下文再按比例压缩（每 N 个 token 一个压缩 key）；
  • 稀疏注意力用一个 Indexer 选出 TopK 个压缩 key，只在这些 key 上算；
  • 每个 query 还额外看一个滑动窗口（SWA）；
  • 前若干层与后若干层还分 producer / consumer（YoCo），consumer 的 SWA 从共享 hidden 投影。

这一章按数据流拆开：Q 怎么来 → KV 怎么来 → 索引怎么选 → 注意力怎么算 → 输出怎么投。

二、机制与原理

5.1 MLA：KV 不存完整矩阵，只存低秩潜向量

标准多头注意力每个 token 每层要存 2 × num_heads × head_dim 个 KV 元素；上下文一长，KV cache 就爆炸。MLA（Multi-head Latent Attention）的做法是：

文本 / 输出
Q:  hidden → Wq.A（降到 q_lora_rank）→ RMSNorm → Wq.B（升到 num_heads × head_dim）
KV: hidden → Wkv.A（降到 kv_lora_rank + qk_rope_head_dim）→ 只缓存这个潜向量
    其中 qk_rope_head_dim 是解耦的 RoPE 部分，不参与压缩

代码里的对应字段（V4AttentionBase.__init__）：

字段含义
q_lora_rankQ 的低秩维度
kv_lora_rankKV 潜向量维度
qk_head_dim / head_dim每个 head 的维度
qk_rope_head_dim其中走 RoPE 的尾部维度
o_groups / o_lora_rank输出投影的分组数与低秩维度

num_key_value_heads == 1 是硬断言：V4.1 的 KV 是单头共享的（MQA 式），所有 query head 共用同一份潜向量。每个 token 的缓存量是 kv_lora_rank + qk_rope_head_dim，再按精度打包：

  • per-16 FP4：288 B/token；
  • MXFP8：528 B/token（512 B 数据 + 16 B scale）。

5.2 压缩 KV：每 N 个 token 一个 key

MLA 已经压了一次，V4.1 又加了一层时间维压缩：kv_compress_ratio = N，每 N 个 token 只产生一个压缩 key，写到 ca_cache：

文本 / 输出
ca_cache: [num_blocks, block_size / N, 1, bytes_per_token]
  • N = 1 表示不压缩（is_c1），走 dense 路径；
  • N > 1 时，前向要维护一个压缩器状态（ca_state），把窗口内的 token 累加/池化成新的 key；
  • 压缩窗口的边界天然对齐到 128 token 的落盘粒度，所以 ca_state 不需要跨边界持久化（第 4 章）。

每层的 PackedWkv 负责 KV 投影与压缩；如果某层只做 SWA、不做压缩，ca_cache 可以为空，block_size 也从 ca_cache.shape[1] × N 推导。

5.3 Indexer / DSA：先选 TopK，再算注意力

长上下文下，即使压缩了 KV，key 的数量仍然很大。V4.1 用稀疏索引器（DeepSeek Sparse Attention）进一步裁剪：

文本 / 输出
对每个 query：
  1. indexer 计算每个压缩 key 的分数：logits = relu(q_index @ k_index) * weights
  2. 取 TopK（topk_tokens）个压缩 key
  3. 核心注意力只在这 TopK 个 key 上计算（delegate 给 FlashMLA 的 sparse 路径）

index_attn.py 的 MQA 是这部分的实现：

组件作用
index_k_module（KProject）从主压缩 KV 投影出 Indexer 的 K
weights_proj给每个 index head 学一个权重
topk_tokens每个 query 保留多少个 key
candidate_topk_blocks先按 block 粒度粗筛，再在候选块内 fine-grained TopK
FP4_INDEX_KV_FORMATIndexer 的 Q/K 都用 FP4（E2M1 + UE8M0 scale）
deep_select.interface.topk实际的 TopK 算子（vendor/DeepSelect）

Indexer 的内存是单独核算的：compute_chunk_size = min(8192, DEEPINFER_INDEX_ATTN_MEMORY_LIMIT // row_bytes // 8 * 8)，默认上限 10 GiB（DEEPINFER_INDEX_ATTN_MEMORY_LIMIT）。行太宽时会分 chunk 计算，避免一次 materialize 全部 logits。

5.4 SWA：每个 query 额外看一个窗口

除了压缩 KV + TopK，每个 query 还要看最近的 window_size 个 token。这部分走独立的 swa_cache：

文本 / 输出
swa_cache: [num_state_seqs, swa_block_size, 1, 528]
swa_block_size = window_size + MAX_BACKTRACKING_TOKENS

为什么单独存？

  • 压缩 KV 的粒度是 N 个 token，最近窗口内的细节（尤其是 draft 回退需要的 token）用压缩 key 表达不了；
  • SWA 是每序列固定大小的环形结构，放 state cache 比放分页 block 更省管理开销。

Prefill 时，kv_swa_full_index 为每个 query 行列出窗口内可见的 key（从 swa_cache 历史 + 本轮新 KV 拼成的大 buffer 中取）；decode 时 kv_swa_index 从环形槽位直接取。最后，核心注意力把 SWA 分支的 key 与 压缩 KV 的 TopK key 拼在一起算（kv_index_cat）。

5.5 一次 forward 的完整数据流

对应的代码路径（V4Attention.forward，attn.py:752）：

  1. compute_attn_info()：把紧凑的索引字段展开成 kernel 可消费的完整索引（幂等）。
  2. _project_current_hidden_inputs()：把当前 hidden（以及 shared hidden）投影成 KV 与 index weights。
  3. _project_q_and_swa()：融合投影出 Q 低秩与 SWA KV。
  4. _prepare_swa_kv()：norm + RoPE + Hadamard + cast + 写 swa_cache；prefill 时同时准备 CP all-gather。
  5. _project_q_b()：Q 升维，拆出 Indexer Q。
  6. _compute_kv_ca_index()：调用 Indexer 选 TopK，得到 kv_ca_index；同时把压缩 KV 写入 ca_cache。
  7. Prefill：把 [SWA cache | 当前 SWA KV | 压缩 cache] 拼成一个连续 buffer，调用 prefill_attn_varlen_sparse。
  8. Decode：调用 decode_mla_mqa_sparse，主 key 用 swa_cache，额外 key 用 ca_cache + kv_ca_index。
  9. _wv_and_o_proj()：Wv 分组投影（deep_gemm.fp8_einsum）+ out_proj。

5.7 CP：prefill 时把上下文切给多张卡

CP > 1 时，模型层在 prefill 开头调用 input_metadata.prepare_for_mirror_cp()，按 CP rank 把 token 重排成镜像布局，再 gather hidden states。注意力内部对压缩器的输入与 SWA KV 做 all_gather，保证每个 rank 都能看到完整 KV；输出后再按反向索引还原顺序。

注意三个边界：

  • CP 只用于 prefill：decode 时 use_cp = is_prompt and cp > 1，为假；
  • COMPLETION 引擎不允许 CP > 1：LLMEngine.__init__ 里有断言；
  • 官方生产当前不使用 CP来源：官方 Q&A，开源代码的 CP 是给离线/实验场景准备的。

5.8 YoCo：前 producer、后 consumer

YoCo（You Only Cache Once）把模型按 n_prefill_layer 切成两段：

  • layer < n_prefill_layer：producer，正常算 KV；
  • layer >= n_prefill_layer：consumer，SWA 从第一层 consumer 的共享 hidden 投影，不重复算。

Prefill 截断有三种模式（DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE）：

模式行为代价
off不截断，consumer 层也跑全量 query最慢，但最准
mask保留全部 query，只收窄 SWA 可见域计算量仍大，索引被 mask
compact真正移除截断区的 query最快，但需要边界 gather / KV 全量写入

compact 模式下，_store_yoco_full_kv() 会用完整 hidden 更新主 KV/Index KV，保证 KV 覆盖完整上下文；但 query 只保留末尾 KEEP_TOKENS 个。官方要求 KEEP_TOKENS 覆盖 window_size + MAX_BACKTRACKING_TOKENS，且开启截断时必须显式设置（默认 0）。注意：代码只在 ModelMetadata 里断言 > 0，并不校验这个下界；配小了不会启动失败，但可能让回放/回退覆盖不到完整窗口。

5.1 为什么 KV 要「拼成一个大 buffer」再算 prefill

Prefill 的注意力需要同时看三类 key：

文本 / 输出
[ 历史 SWA 窗口（swa_cache） | 本轮新 SWA KV | 压缩 KV（ca_cache） ]

FlashMLA 的 sparse prefill 接收的是一个连续的 KV buffer + 索引，而不是多个 cache 指针。所以 _prepare_prefill_kv() 先算总长度、分配/复用一个 buffer，再用 load_paged_kv_cache 把 swa_cache 与 ca_cache 的块拷进去，最后用 kv_index_cat 把两段索引拼起来。共享 KV 的层会复用同一个 buffer（cross_layer_runtime.loaded_prefill_kv），只换索引。

5.2 融合 kernel 省了什么

fused_norm_rope_hadamard_cast_store_kvcache 把五件事合成一个 kernel：

文本 / 输出
RMSNorm → RoPE → Hadamard 变换 → 量化（FP8/FP4）→ 写 KV cache

对 Q 也有一条融合路径（fused_norm_rope_attn_rope_cast），把 Q 的 norm + RoPE + 注意力 + 输出 RoPE + cast 串起来。这减少的不只是 kernel 启动开销，更重要的是减少中间张量的显存读写——decode 每步都要走一遍，省下来的带宽直接变成吞吐。

四、常见坑与边界条件

  1. head 数不是 64/128 会被补零：_pad_attention_heads 会补到下一个支持值；超过 128 直接 ValueError。补零会浪费算力，但保证 kernel 可用。
  2. sparse attention 只支持非 causal：decode_mla_mqa_sparse 里 causal=False；可见性完全由索引表达，不要指望 mask 参数。
  3. use_swa=False 必须搭配 packed KV：V4AttentionBase 有断言；纯 SWA 层与 packed-KV 层的索引语义不同。
  4. 所有层都断言 sink_mode == "swa"：这是 V4.1 的配置约束，改模型配置时要先满足。
  5. Indexer 内存上限太小会启动失败：compute_chunk_size 必须 > 0；默认 10 GiB，调小要确保至少能放 8 行。
  6. YoCo 的 KEEP_TOKENS 有下限，但代码不校验：官方要求覆盖 SWA 窗口 + 最大回退；代码只断言 > 0，配小了不会启动失败，可能在回放/回退时覆盖不到完整窗口。开启截断时必须显式设置，不能依赖默认 0。
  7. YoCo 截断会关闭 prompt_logprobs：add_request() 里会强制置 False 并打 warning；需要 prompt logprobs 的实验不要开截断。
  8. CP 只在 prefill 生效：decode 不做 CP；COMPLETION 引擎配 CP > 1 会断言失败。
  9. batch invariant 会关掉部分融合路径：use_fused_norm_rope_attn_rope_cast 的条件里包含 not DEEPINFER_BATCH_INVARIANT（dense packed-KV decode 场景），确定性优先于峰值性能。

五、关键结论

  1. V4.1 的注意力是 MLA + 时间压缩 + 稀疏 TopK + SWA 的复合结构，不是单一 attention。
  2. MLA 只缓存低秩潜向量；压缩 KV 每 N 个 token 一个 key；SWA 单独存环形窗口。
  3. Indexer 用 relu(q@k)·weights 打分，TopK 后只算少量 key；Indexer Q/K 是 FP4。
  4. Prefill 把三类 key 拼成一个连续 buffer，交给 FlashMLA sparse；decode 用 paged cache + 索引。
  5. YoCo 让后半模型复用共享 hidden；compact 模式真正减少 query，但 KV 仍按全量写入。
  6. CP 在 prefill 时重排 token 并 all-gather KV；生产当前不用 CP。

本章要点回顾

  • MLA：Q 低秩 q_lora_rank，KV 只存 kv_lora_rank + qk_rope_head_dim。
  • 压缩 KV：每 N 个 token 一个 key，ca_cache 按 block 分页。
  • Indexer：relu(q@k)·weights → TopK → 只算 TopK 个 key。
  • SWA：独立环形缓存，window_size + 回退余量。
  • Prefill 拼 [SWA 历史 | 新 SWA | 压缩 KV]；decode 用 paged cache。
  • YoCo：n_prefill_layer 切分 producer / consumer；mask 与 compact 两种截断。
  • 常见坑：head 数、非 causal、use_swa=False 的 packed KV 前提、YoCo keep tokens、CP 仅 prefill。

6MoE、专家并行与 EPLB：热专家为什么要复制

一、这一章要解决的问题

稠密模型每个 token 都要走一遍全部参数；MoE 把 FFN 换成 N 个「专家」，每个 token 只选其中少数几个。好处是总参数可以很大、激活参数很小；代价是工程复杂度：

  • 专家分散在多张 GPU 上，token 要跨卡搬运（dispatch / combine）；
  • 不同专家的热度差异很大，热门专家会成为瓶颈；
  • 训练时要防塌缩，推理时要防负载倾斜。

DeepInfer 的答案是：EP（专家并行）+ EPLB（专家负载均衡）+ Mega MoE（通信计算融合）。这一章拆开这三件事。

二、机制与原理

6.1 结构：一个 MoE 层里有什么

model_executor/models/v4_modules/moe.py 定义三个容器：

组件作用
TopKGate给每个 token 打分，选出 TopK 个专家，输出权重
FusedExperts路由专家的权重容器（linear1 / linear2），加载时重排成运行时布局
ReplicatedSharedExpert所有 token 都走的共享专家（不参与路由）

V4.1 的门控配置（DeepseekMoE.__init__ 的断言）：

  • topk_method == "noaux_tc"：不做辅助损失，用 bias 校正负载；
  • norm_topk_prob == true：TopK 权重归一化；
  • scoring_func == "sqrtsoftplus"：打分函数是 sqrt(softplus(x))；
  • activation_type == "swiglu"：专家内部是 SwiGLU；
  • routed_scaling_factor：路由输出缩放。

多模态模型还有一个 e_score_correction_bias_vl，只对图像 token 生效（images_seq_mask）。

6.2 逻辑专家与物理槽位

这是理解 EPLB 的关键区分：

文本 / 输出
逻辑专家（logical expert）  = 模型定义的专家，编号 0..R-1
物理槽位（physical expert）  = GPU 上实际存放的副本，编号 0..P-1
P = R + E                        （E = 冗余副本数）
每个 rank 放 P / ep_size 个物理槽位
  • Gate 只认识逻辑专家。
  • EPLB 维护两张映射：
    • logical_to_physical_map[logical, replica] = physical；
    • physical_to_logical_map[physical] = logical。
  • Dispatch 使用物理槽位：token 被送到目标物理槽位所在的 rank。

为什么要多出 E 个副本？因为热专家可能被很多 token 选中；如果它只有一个副本、且所在 rank 的带宽/算力有限，就会成为长尾。复制热专家后，token 可以分散到多个副本上，用显存换负载均衡。

resolve_num_extra_experts() 会把冗余数向上补齐，使 R + E 能被 ep_size 整除；benchmark 默认从 32 个冗余专家起（DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS），实际值以补齐后为准。

6.3 MoE forward：三条路径

DeepseekMoE.forward() 根据硬件与精度选路径：

三条路径的差别：

路径条件特点
Mega MoEEP 组在 scale-up 域内（GPU 走 NVLink，NPU 视为单域），且精度组合支持；NPU 上仅 fp8×fp4 路径把 dispatch / GEMM / combine 融成更少的 kernel，减少中间张量访存
DeepEP dispatch/combine跨节点 / 非 NVL 域标准 EP 通信，异步与计算流重叠
共享专家n_shared_experts > 0复制到每个 rank，不走 EP；Mega 路径可融合进同一次 GEMM

routed_experts_forward() 是标准的「两次 grouped GEMM + SwiGLU」：

文本 / 输出
gate_up_proj: [num_expanded_tokens, 2 × intermediate]
  → SwiGLU + per-token cast
  → down_proj: [num_expanded_tokens, hidden]

权重支持 bf16 × bf16、fp8 × fp8、fp8 × fp4 三种组合（mma_type）；FP4 权重要求 checkpoint 是 QAT 产物，代码里有位模式断言。

6.4 Dispatch 与 combine：token 怎么跨卡

以 DeepEP 路径为例（DeepInferMoE.dispatch/combine）：

  • dispatch：按 topk_idx 把 token 的 hidden 发到目标物理槽位所在 rank；同时把 topk_weights 带过去；expert_count 顺便累加，供 EPLB 统计。
  • combine：把各专家算完的结果按原 token 收回，乘上路由权重；共享专家的输出可以作为 bias 一起加回来。
  • 通信与计算重叠：async_with_compute_stream=True、previous_event / EventHandle 让 dispatch/combine 与 GEMM 在不同流上重叠；DEEPINFER_USERBUFFER_COMM_SMS 控制通信占用的 SM 数。
  • 缓冲区：userbuffer.allocate_ep() 或 allocate_sym_buffer() 预分配，避免每步临时申请；max_num_tokens 在 prefill 与 decode 下不同（max_num_prefilling_tokens vs max_num_decoding_tokens）。

dispatch 里还有一个值得注意的开关：do_cpu_sync 在 prefill 且非 compact 模式时为真，在 compact 模式下关闭，因为「YoCo compaction 下 CPU 同步会成为瓶颈」（代码注释）。

6.5 EPLB：统计 → 决策 → 搬运

EPLB 的运行时状态在 eplb/__init__.py 的 ExpertLoadBalancer，分三步：

1）统计
  • 每个 step 在 dispatch 时累加 expert_count[physical]；
  • 每 DEEPINFER_EXPERT_COUNT_WINDOW_SIZE（默认 100）个 step 形成一个窗口；
  • 每 DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL 个 step 触发一次重排（默认 0，即关闭）；
  • 首次重排提前到 1/4 周期后，尽早纠正冷启动不均衡。
2）决策

policy.py:rebalance_experts_global()：

文本 / 输出
1. 先复制热专家：
   每轮选「加一个副本后，最大每副本负载下降最多」的逻辑专家，
   给它分配一个冗余物理槽位；共 E 轮。
2. 再把物理槽位均衡到各 rank：
   按「每副本历史负载」降序，逐个 expert 贪心放到当前
   「各 step 峰值负载之和」最小的 rank，直到每个 rank 放满 capacity 个。

目标函数是 sum_steps max_rank(load)，也就是最小化历史窗口内的最坏 rank 负载，而不是平均负载。这比简单的 round-robin 更贴近尾延迟。

3）搬运

shuffle.py 提供两种：

  • 节点内：用 torch.distributed._symmetric_memory 建镜像 buffer，走 IPC/NVLink，避免走网络；
  • 跨节点：expert_model_parallel_shuffle_inplace 用 P2P 传输。

搬运是原地的：把所有 rank 的权重按新映射重排，不需要额外的全量副本（节点内镜像是逐层复用的一层大小 buffer）。

统计指标

_log_rearrangement_metrics 输出：

  • rank_balance：平均 rank 负载 / 峰值 rank 负载；
  • logical_balance：平均逻辑专家负载 / 最大逻辑专家负载；
  • rank_peak、physical_peak；
  • 官方 Q&A 用的 moe_lb = slowest rank / mean，取值越接近 1 越好。

6.6 生产配置：Prefill 与 Decode 不同

官方 Q&A 给出两套 EPLB 参数来源：官方：

阶段冗余专家起点统计窗口重排间隔实测 moe_lb
Prefill每 GPU 4 个100 step1000 step1.074（EP4DP4）/ 1.045（EP2DP2）
Decode每 GPU 1 个（EP64 补齐后每 GPU 7 个）1000 step10000 step1.090

为什么 Decode 的窗口更长、重排更稀疏？因为 Decode 的 batch 小、每步统计噪声大，频繁重排得不偿失；而 Prefill 的 batch 大、统计更稳定，可以更快响应。

这也解释了 Wide-EP 的收益：Decode 用 EP64–128，把专家摊薄到更多卡上，单步每卡只需搬运很少的专家权重；再配合 EPLB 把热专家复制到空闲卡，MoE 部分的访存压力显著下降来源：官方。

6.7 EP 的拓扑约束

DeepseekMoE.__init__ 里几条硬约束：

  • num_physical_experts % ep_size == 0；
  • num_local_physical_experts = num_physical_experts // ep_size；
  • use_mega_moe 要求 EP 组在 scale-up 域内（GPU 的 NVLink / NPU 单域）；NPU 上只有 fp8×fp4 组合会走 Mega MoE；
  • 共享专家是 replicated，不参与 EP；
  • num_physical_topk = num_topk：每个 token 仍然选 K 个物理槽位（副本算不同槽位）。

parallel_state.py 的 EP 组是连续 rank（(edp, ep) reshape），所以一个 EP 组内的 GPU 通常在同一节点/NVLink 域；跨节点的大 EP 需要底层网络支持（生产用 400G 互联）。

physical:  [0, 1, ..., R-1, 0, 1, ..., E-1]
logical:   [0, 1, ..., R-1]

即「原始专家 + 前面几个专家的副本」。之后每次重排，policy.py 可能改变副本归属与物理顺序；logical_to_physical_map 的每一行最多有 E+1 个槽位（1 个原始 + 若干副本），无效位是 -1。

6.2 为什么 Gate 要读 logical_count

同一个逻辑专家可能有多个物理副本。Gate 选完逻辑专家后，需要把它们均匀分配到副本上，否则复制了也没用。gate_kwargs 里的 to_physical_map 与 logical_count 就是给 moe_topk_gate / bf16_mega_gate 做这件事的。

6.3 MTP 层也参与 EPLB

DeepseekForCausalLM._init_eplb 把主模型层与 DFlash 的 MoE 层一起分组：

Python
moe_layers = [*self.model.layers, *(self.MTP_module.moe_layer_list() if self.load_nextn else [])]

所以投机头的专家也会被统计与重排；如果只调主模型，MTP 层可能成为新的热点。

四、常见坑与边界条件

  1. EPLB 默认是关的：DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL 默认 0；不显式设置，永远不会重排。examples/offline_inference.py 默认打开（--disable_eplb 可关）；examples/benchmark.py 需要显式 --enable_eplb。
  2. 冗余专家数会被补齐：DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS 只是下限；实际 num_physical_experts 会向上补到 ep_size 的倍数，日志与图表用补齐后的值。
  3. num_physical_experts % ep_size != 0 直接断言失败：EP 大小与专家数必须整除。
  4. Mega MoE 只限 scale-up 域：跨节点会退回 DeepEP dispatch/combine，性能特征完全不同；不要拿单机 benchmark 推跨机。NPU 上只有 fp8×fp4 会走 Mega 路径。
  5. FP4 权重要求 QAT checkpoint：process_moe_weight 里有位模式断言；普通 FP8 checkpoint 转 FP4 会在加载时报错。
  6. 共享专家不走 EP：它是 replicated 的，每个 rank 都有一份；显存估算时不要把它算进 EP 分摊。
  7. EPLB 重排有同步成本：节点内用 symm_mem IPC，跨节点走 P2P；重排间隔太短会拖慢 decode。
  8. batch invariant 与 EPLB 的交互：userbuffer.py 在 DEEPINFER_BATCH_INVARIANT=1 且重排开启时关闭 multiple reduction，避免结果随专家重排变化；两者同时开要接受额外开销。
  9. DEEPINFER_FORCE_IMBALANCE_RATIO 是 profile 专用：它用随机路由模拟不均衡，把显存峰值算高；正常推理不要设。

五、关键结论

  1. MoE 的核心区分是 逻辑专家（模型定义）与 物理槽位（GPU 副本）；EPLB 维护两者映射。
  2. 热专家复制 + 贪心放置，目标是最小化历史窗口内的最坏 rank 负载，不是平均负载。
  3. 三条执行路径：Mega MoE（NVL 域内融合）、DeepEP dispatch/combine（跨节点）、共享专家（replicated）。
  4. EPLB 的统计窗口与重排间隔在 Prefill / Decode 上不同；默认关闭，需要显式开启。
  5. Wide-EP 的收益来自「把专家摊薄 + EPLB 复制热专家」，两者缺一不可。
  6. 关键约束：专家数能被 EP 整除、FP4 需要 QAT、Mega 需要 NVL 域。

本章要点回顾

  • 逻辑专家 vs 物理槽位；P = R + E，每 rank P / ep_size。
  • Gate 选逻辑专家，EPLB 映射到物理副本；logical_count 决定副本分配。
  • MoE forward：gate → dispatch → grouped GEMM ×2 + SwiGLU → combine。
  • Mega MoE 把通信与计算融合，只在 scale-up 域内启用（NPU 仅 fp8×fp4）。
  • EPLB 三步：统计（窗口）→ 决策（复制热专家 + 贪心放置）→ 搬运（symm_mem / P2P）。
  • 生产参数：Prefill 4 冗余/100/1000；Decode 1 冗余/1000/10000。
  • 坑：默认关闭、整除约束、QAT、NVL 域、共享专家不参与 EP。

7投机解码：DFlash、置信度头与变长验证

一、这一章要解决的问题

Decode 每生成一个 token 都要把主模型完整跑一遍；如果一次能"猜"出后面 5 个 token，再让主模型一次批量验证，猜对的部分就白赚了。这就是投机解码（speculative decoding）。

但「固定猜 5 个」不是最优：

  • 有的请求下一个 token 很确定，5 个草稿全中；
  • 有的请求很发散，5 个草稿可能只中 1 个，剩下 4 个的验证算力纯属浪费；
  • 不同请求、不同位置的接受率差别很大。

DeepInfer 的方案是 DFlash 草稿头 + Confidence Head 预测接受率 + 变长验证调度。官方文档把这组能力称为 DSpark and confidence-scheduled verification，配置项也以 dspark_* 命名；代码里的投机头实现在 deepinfer/model_executor/models/mtp/dflash.py。这一章拆开：草稿怎么来、怎么验证、怎么决定验证几个。

二、机制与原理

7.1 一次投机解码的时序

文本 / 输出
第 N 步（decode）：
  主模型 forward → 采样 golden token
  → DFlash 以 golden token 为起点，生成 max_MTP_value（默认 5）个草稿
  → 草稿写入 MTPInfoPool
第 N+1 步：
  主模型 forward（输入 = 上一步 golden token + 5 个草稿）
  → 得到 6 个位置的 logits
  → 逐个比较草稿 token 在主模型分布下的概率：
      接受 → 输出该 token
      拒绝 → 在第一个拒绝位置用残差分布重采样，停止验证
  → 统计 accepted / verified 数量
  → 用最后一个被接受的 token 再生成下一轮草稿

几个术语：

术语含义
golden token主模型自己采样出的 token，作为草稿的起点
draft tokenDFlash 猜出来的后续 token
verify用主模型分布逐个校验 draft
accepted length本轮最终被接受的连续 token 数（含 golden）
verified length本轮实际送进主模型验证的 token 数（含 golden）

7.2 DFlash 的结构

DFlash 是一个独立的 nn.Module，由 checkpoint 里的 MTP 层构造（models/mtp/dflash.py:82）：

组件作用
layersDFlashDecoderLayer 列表，每层有自己的 draft KV
main_kv_proj把目标层特征投影成每个 draft 层的主 KV
projection / projection_norm把多个目标层的 hidden 拼起来，投到 hidden_size
embed_tokens / lm_head与主模型共享词嵌入与输出头
markov_w1 / markov_w2（可选）Markov 头：把上一个 token 的 embedding 加到 logits 上，增强局部连贯性
confidence_head线性层，预测每个 draft token 的接受概率
mtp_info_pool跨 step 保存草稿、logprobs、置信度
decode_graph_runnerDFlash 专用的 CUDA Graph 捕获器

几个关键设计：

  • 主 KV 来自目标层特征：update_main_cache() 在主模型 forward 内部执行，把 dspark_target_layer_ids 这些层的 hidden 投影成 draft 层的 main-token K，写进 draft KV。这样 prefill 时不需要额外跑一遍 draft 模型。
  • 草稿层是固定步长的：_embed_draft_init_tokens() 把 draft_init_tokens 填成 [golden, noise, noise, noise, noise]，一次 forward 处理整个块；sample_drafts() 再逐步采样。
  • 主 KV 与 draft KV 分离：DFlashAttention 有独立的 draft KV；main_kv_proj 会复制一份 KV 权重，显存略增（代码注释明确说明）。
  • 窗口必须与主模型一致：DFlash.window_size == cfg.window_size[0]，否则 SWA 布局对不上。

7.3 草稿是怎么生成的

DFlash.run_drafts() 是 decode 的完整路径：

文本 / 输出
1. driver 广播 last_valid_offset 与 golden_tokens 给 CP follower
2. build_dflash_input()：按固定步长构造 draft 的 InputMetadata
3. forward_drafts()：跑完所有 draft 层，得到每个位置的 hidden
4. sample_drafts()：
   - post_norm + lm_head → logits
   - 可选 Markov 头修正 logits
   - 逐位置采样 draft token
   - Confidence Head 输出每个位置的接受概率
   - 写入 MTPInfoPool（草稿、logprobs、置信度）

sample_drafts() 的循环里，step_i 从 0 到 max_MTP_value-1，每一步：

  • 取该位置的 logits；
  • 有 Markov 头时，用上一步 draft token 的 embedding 修正；
  • 用与主采样器相同的 process_sampling（温度、top-k/p、种子）；
  • 置信度头用 hidden + markov_emb 预测接受率；
  • 结果按位置写入 pool。

草稿层数与草稿个数是解耦的：checkpoint 里的 MTP 层数由 num_nextn_predict_layers 决定，而每步生成几个草稿由 DEEPINFER_USE_NEXTN_DECODE（默认 5）决定。deepseek.py 里有注释明确这一点。

7.4 验证：接受、拒绝与重采样

Sampler._verification()（layers/sampler.py:410）在 decode 步执行：

  1. prepare_verification_metadata() 把 total_q 行映射到 (request, local_step, is_verify)：哪些行是待验证的 draft，哪些是普通 token。
  2. process_sampling() 同时处理「采样本轮 token」与「验证上一轮草稿」：
    • 对 draft 行，读取 MTPInfoPool 里上一轮的 logprobs 与 token；
    • 计算接受概率（accept_probs）与接受结果（accept_result_verify）。
  3. get_accept_result() 找出每个请求的接受前缀与最终行：
    • 第一个被拒绝的位置用残差分布重采样；
    • 全部接受时，在最后一个 draft 之后正常采样。
  4. finalize_verification() 打包 sampled_tokens 与 verified_tokens，统计 num_generated_tokens、num_verified_tokens。

类文档字符串把规则写得很清楚来源：一手：

说明

验证上一轮 MTP 预测的 draft tokens：逐步比较 draft token 在新旧分布下的 logprob，按 speculative decoding 的接受/拒绝规则决定是否接受；被接受的 draft tokens 作为 accepted tokens 输出；第一个被拒绝的位置用 residual probability 重采样作为 output token；全部接受则在最后一个 draft token 之后正常采样。

一个细节：如果本轮遇到 EOS，sample_drafts() 会把该请求下一轮所有草稿的置信度置 0，避免继续猜（sampler.py 里 emitted_stop_token 的处理）。

7.5 为什么需要「变长验证」

假设每个请求都固定验证 5 个草稿：

  • 接受率高的请求，5 个都能用上，赚；
  • 接受率低的请求，后几个草稿大概率被拒，验证它们的算力浪费；
  • 不同请求混在一批里，浪费会被放大。

变长验证的思路是：按每个草稿的预期接受率排序，把验证预算分配给边际收益最高的前缀。

官方 Q&A 的生产数据来源：官方：

配置平均验证长度平均接受长度相对固定 5 的吞吐
固定 55.003.29基准
变长（60 并发/rank）3.583.21+5.4%
变长（72 并发/rank）3.243.12+6.7%
变长（96 并发/rank）3.243.15+11.0%
变长（16 并发/rank）4.443.24−1.5%

结论：低并发时变长验证可能亏（调度开销大于省下的验证），高并发时收益明显；官方在生产工作点（约 60 并发/rank）给出的收益是 +4–7%，表中最高的 96 并发达到 +11%。

7.6 变长调度：MTPVarlen

csrc/engine/mtp_varlen.hpp 的 MTPVarlen::schedule() 在每步 decode 调度时执行：

文本 / 输出
1. 收集每个请求的 draft 数与接受率（来自 Confidence Head）
2. 用 N−2 轮的接受率计算「最佳 batch 大小」：
   从全 1 token 开始，按接受率从高到低逐个加入，
   用 (batch_size, forward_ms) 曲线 + 拟合斜率 + sampler 耗时估算吞吐，
   取吞吐最大的 batch 大小
3. 用 N−1 轮的接受率给每个请求分配 seqlen_q：
   每个请求先 1 个 golden token，剩余名额按接受率从高到低分配
4. 返回每个请求的 seqlen_q 给调度器

为什么用 N−2 与 N−1 两轮？因为 ZOS 下本轮调度时，上一轮的接受率可能还没回到 CPU（第 8 章）；用更早一轮的统计做 batch 决策，用最近一轮做请求内分配，是一个折中。代码注释明确写了这个约束。

7.7 ZOS 下的 GPU 修正

ZOS 开启时，CPU 侧调度用的是滞后的接受率；GPU 在 forward 前要按最新结果修正：

Worker._correct_seqlens_qk()（worker/worker.py:191）：

文本 / 输出
1. prepare_zos_inputs()：对比上一步与本步的 seq 交集，生成 remap / seqlens_q / seqlens_k
2. 若开启 MTP varlen：
   compute_seqlens_q_by_confidence_rates(total_q, remap, prev_confidence, seqlens_q)
3. compute_seqlens_k_zos()：用上一轮 num_accepted_tokens 修正 seqlen_k
4. 若 varlen，把修正后的 seqlens_q 拷回 pinned CPU buffer（D2H），
   供 sampler 前的 CPU 元数据更新使用

这就是官方 Q&A 说的「CPU 只固定总预算，per-request 长度在 GPU 上用 TileLang kernel 重算（累积乘积、全局排序 TopK、融合 remap scatter），结果写回 pinned buffer」。

7.8 CUDA Graph：把整段草稿路径录成图

DFlash 的 decode 路径形状固定（每请求 1 + nextn 行），非常适合 CUDA Graph：

  • capture_dflash_model() 在主模型 graph 之后捕获；
  • graph 里包含：driver 广播、固定步长 metadata、draft 层 forward、采样、MTPInfoPool 写入；
  • replay 时一次调用完成，省去逐 kernel 的 CPU 发射开销；
  • 与主模型共享 graph memory pool 与 stream。

7.2 一次验证的输入布局

每请求：[golden token, draft_1, draft_2, ..., draft_k]

四、常见坑与边界条件

  1. DEEPINFER_USE_NEXTN_DECODE 默认 5：显式设 0 才关闭投机；不设不是"自适应"，而是固定 5。
  2. 草稿层数 ≠ 草稿个数：MTP_num_layers 由 checkpoint 的 num_nextn_predict_layers 决定，草稿个数由环境变量决定；两者解耦。
  3. DFlash 的 window 必须与主模型一致：assert self.window_size == cfg.window_size[0]，否则 SWA cache 布局对不上。
  4. 主 KV 权重会复制一份：main_kv_proj 从主注意力 KV 权重克隆，显存略增；估算显存时别漏。
  5. 低并发下变长验证可能负收益：官方数据在 16 并发/rank 时是 −1.5%；不要无脑开，先看你的并发区间。
  6. 确定性采样必须关掉 varlen：README 给的组合是 DEEPINFER_BATCH_INVARIANT=1、DEEPINFER_ENABLE_MTP_VARLEN=0，并传固定 seq_seed；变长验证会改变每步验证的长度，破坏可复现性。
  7. ZOS 下 CPU 的接受率是滞后的：MTPVarlen 用 N−2/N−1 两轮历史；如果手动改调度逻辑，要保留这个约束。
  8. EOS 后置信度会被清零：不要指望请求结束后还能读到最后一步的 confidence。
  9. PROMPT 引擎的 DFlash 是 prefill_only：只加载 main-cache 路径参数；P/D 分离时 P 端不生成草稿。

五、关键结论

  1. 投机解码 = 草稿 + 批量验证；DFlash 是代码里的草稿头实现，DSpark 是官方对这套投机解码与置信度调度能力的称呼（配置项以 dspark_* 命名）。
  2. 主 KV 来自目标层特征，prefill 不额外跑 draft 模型；draft KV 独立存放。
  3. 验证规则是标准的 speculative sampling：接受前缀、首个拒绝位置用残差分布重采样。
  4. Confidence Head 预测每个草稿的接受率，MTPVarlen 用它分配变长验证预算。
  5. 变长验证在高并发下 +4–7%，低并发可能负收益；官方生产按并发区间权衡。
  6. ZOS 下 per-request 长度在 GPU 上修正，CPU 只负责总预算。

本章要点回顾

  • 一次 decode：主模型采样 golden → DFlash 猜 5 个 → 下一步批量验证。
  • 验证：接受前缀 + 首个拒绝位置残差重采样；全接受则再采一个。
  • Confidence Head：输入 hidden（+ Markov embedding），输出每个 draft 的接受概率。
  • MTPVarlen：N−2 轮定 batch，N−1 轮分配每请求验证长度。
  • 生产收益：验证长度 5.00 → 3.2–4.4，接受长度基本不变，吞吐 +4–7%。
  • 坑：nextn 默认 5、varlen 与确定性互斥、低并发负收益、window 必须一致。

8零开销异步调度与批不变性：消气泡与可复现

一、这一章要解决的问题

Decode 的每一步看起来只有「算」和「采样」，但真正拖慢 GPU 的往往是两步之间的 CPU 工作：

文本 / 输出
schedule(N) → forward(N) → sample(N) → post-process(N) → schedule(N+1) → ...

schedule 与 post-process 都是纯 CPU 逻辑，而 post-process(N) 必须先等 sample(N) 的结果从 GPU 回来。于是 GPU 在 post-process(N) 与 schedule(N+1) 期间空转。请求越多、每步越短，这个气泡占比越大。

另一件看似矛盾的事：推理框架为了性能会按 batch 形状选不同 kernel、不同归约顺序；结果同一个请求单独跑和拼批跑，输出可能不一样。评测、调试、Agent 回放都需要批不变性（batch invariance）。

这一章讲 DeepInfer 的两个答案：ZOS（零开销调度） 与 batch invariant / 确定性采样。

二、机制与原理

8.1 气泡从哪来

LLMEngine.step() 的正常顺序是：

文本 / 输出
1. scheduler.schedule()           CPU
2. worker.execute_model_step()
   ├── forward(N)                 GPU
   ├── sample(N)                  GPU
   └── post-process(N)            CPU（需要先 sample_end_evt.synchronize()）
3. 返回 RequestOutput

第 2 步的 post-process 里有 sample_end_evt.synchronize()（worker/worker.py:_post_process_step），这是 CPU 等 GPU 的同步点。同步之后才能：

  • 把采样结果写回序列状态；
  • 判断哪些请求结束、释放 block；
  • 为下一步调度准备 seqlen_k / seqlen_q。

如果每步都同步，GPU 就会在 CPU 做这些事时闲着。

8.2 ZOS 的核心：把「上一轮的后处理」塞进「这一轮的计算」

ZOS 把流水线改成：

文本 / 输出
GPU:  forward(N) → sample(N) ──────────────→ forward(N+1) → sample(N+1)
CPU:  schedule(N+1) → launch(N+1) → post-process(N-1) → launch sample(N+1)

具体到 Worker.execute_model_step() 的四步：

步骤做什么ZOS 下的差异
1forward 当前 step不变；但 CPU 侧 seqlens_q/k 可能滞后，需要 GPU 修正
2post-process 上一 stepZOS 下这是主要的重叠点
3sample 当前 step不变
4post-process 当前 stepdecode 时推迟到下一步；prefill 或非 ZOS 时当场做

WorkerStepState 保存了当前步的 seq_metadata_list、scheduler_outputs、sampler_output、sample_end_evt、graph_size 等，作为「上一 step」传给下一次调用。prev_step_state 就是这条流水线的传送带。

pre_sampler_sync 回调在采样前执行，做四件事：

  1. DeferredRelease.release()：释放上一轮缓存的 SequenceMetadata、RequestOutput、clone 的 block/state；
  2. 保存 KV cache（如果是 prompt 步，调用 pe_do_save_kvcache 等钩子）；
  3. so_matcher_builder.pump()：把已编译好的结构化输出 matcher 挂到请求上；
  4. 对 COMPLETION / NORMAL 引擎，finalize 已完成的请求。

这些工作都发生在 GPU 执行 forward/sample 的同时，不再占用 GPU 的空闲时间。

8.3 滞后的元数据如何在 GPU 上修正

ZOS 下 CPU 调度第 N+1 步时，第 N 步的采样结果还没回来。于是 CPU 只能用上一轮的信息估算 seqlen_q/k，GPU 在执行 forward 前再修正。

Worker._correct_seqlens_qk()（worker/worker.py:191）：

文本 / 输出
1. prepare_zos_inputs(seq_metadata_list, prev.seq_metadata_list, ...)
   → 找出两步 batch 的交集，生成 remap / seqlens_q / seqlens_k / has_overlap
2. 若开启 MTP varlen：
   compute_seqlens_q_by_confidence_rates(
       total_q, remap, prev.sampler_output.confidence_rates_gpu, seqlens_q)
3. 若 nextn > 0：
   compute_seqlens_k_zos(
       seqlens_k, seqlens_q, remap,
       prev.sampler_output.num_accepted_tokens_gpu, nextn)
4. 若 varlen：把修正后的 seqlens_q D2H 到 pinned buffer，
   供 sampler 前的 CPU 元数据更新

这里的关键是 remap：上一步的 batch 与这一步的 batch 不一定相同（有请求完成、有新请求加入），要用映射把「上一轮的接受结果」对应到本轮的行。MetadataZOS 里保存了 prev_sampled_token_ids、prev_predict_token_ids、prev_num_accepted_tokens，供 kernel 使用。

8.4 空批与收尾

ZOS 下还有两个边角情况：

  • placeholder step：如果调度器这一步没有选中任何序列（例如 DP 投票后本 rank 陪跑），Worker 会构造一个假的 SequenceMetadata（_placeholder_seq_metadata），让流水线继续运转；它的 mtp_info_write_slot 是 0（dummy slot），store kernel 会跳过。
  • 收尾 flush：最后一步的 post-process 还在 prev_step_state 里，LLM._run_engine() 在 unfinished=False 时调用 flush_inflight_reqs()，把在途结果全部处理完。

8.5 ZOS 的代价与边界

ZOS 不是免费的：

  • prev_step_state 要持有上一步的 sampler 输出与 metadata，显存/内存占用增加；
  • 调度器必须容忍「滞后的状态」，逻辑更复杂；
  • 某些操作不能放进 forward/sample 的 launch 路径（会引入同步），代码用 forbid_cuda_sync() 守卫；
  • 最后一步必须 flush，否则会丢输出。

默认行为（EngineType.default_zero_overhead_scheduling）：

  • NORMAL：开
  • COMPLETION：开
  • PROMPT：关（P 端只做 prefill，没有 decode 流水线）

8.6 批不变性：为什么同一请求会因拼批而变

即使输入 token、采样参数、随机种子都相同，下面这些因素也会让输出漂移：

来源机制
归约顺序矩阵乘 / attention 的 split-K、分块大小随 batch 形状变化，浮点加法不满足结合律
kernel 选择不同 batch size 走不同 kernel（例如是否 fused、是否走 CUDA Graph）
MoE 路由TopK 平票时的 tie-break、专家重排、副本选择
投机验证长度变长验证改变每步实际验证的 draft 数
随机数采样种子相同，但采样位置 / 分布形状可能变
paddingCUDA Graph 把 batch 补齐，如果 mask 没处理好，padding 会污染结果

8.7 DeepInfer 的 batch invariant 开关

DEEPINFER_BATCH_INVARIANT=1 主要做三件事来源：一手：

  1. runtime_config.configure_worker_kernels()： ``python deep_gemm.use_deterministic_algorithms(True) tile_kernels.use_deterministic_algorithms(True) `` 让底层算子走确定性实现（固定归约顺序）。
  2. attention_backend.decode_mla_mqa_sparse(..., enable_batch_invariant=True)：FlashMLA 的 decode 路径按批不变模式执行。
  3. userbuffer.py：当 batch invariant 与 EPLB 重排同时开启时，关闭 multiple reduction，避免专家重排改变归约结果。

此外，CUDA Graph 的 padding 行通过 valid_token_mask 标记为无效；MoE 的 gate_force_random 对 padding 也置 False，避免 padding token 参与路由。

平台限制：昇腾路径直接断言 not DEEPINFER_BATCH_INVARIANT（runtime_config.py），目前只支持 NVIDIA。

8.8 确定性采样：三个条件缺一不可

README 给出的确定性采样组合来源：官方：

Shell
DEEPINFER_BATCH_INVARIANT=1
DEEPINFER_ENABLE_MTP_VARLEN=0
# 并在 SamplingParams 里传固定的 seq_seed

为什么三个都要？

  • BATCH_INVARIANT=1：保证 logits 不随拼批变化；
  • MTP_VARLEN=0：固定每步验证的草稿数，避免验证长度变化；
  • 固定 seq_seed：采样 kernel 用 seq_seed + sample_position 生成随机数；种子固定，随机序列才固定。

对应的测试是 tests/models/test_batch_invariant.py：同一批 prompt 先以 64 条并发跑一遍，再逐条单跑，逐 token 比较 token_ids、logprobs、top_token_ids、top_logprobs，要求完全相等。

8.9 性能代价

Batch invariant 与 ZOS 都是「用一点性能换正确性/流水线效率」：

  • batch invariant 会禁用部分融合路径（例如 dense packed-KV decode 的 fused_norm_rope_attn_rope_cast 在 batch invariant 下不启用），并让 GEMM 走确定性实现；
  • 离线示例在 NVIDIA 上默认打开 DEEPINFER_BATCH_INVARIANT=1（examples/offline_inference.py），目的是让 PPL 基线可复现，而不是追求峰值吞吐；
  • benchmark 默认不设置它（除非外部环境变量显式打开），测的是性能上限。

8.2 为什么同步点不能随便加

ModelRunner.execute_main_model() 与 execute_sample() 都包在 forbid_cuda_sync() 里：

只要在 forward/sample 的 launch 路径里出现 .item()、.cpu()、torch.cuda.synchronize()，守卫就会抛错（可通过 DEEPINFER_DISABLE_SYNC_GUARD=1 临时关掉，仅用于 debug）。这条约束是 ZOS 能成立的前提：launch 必须纯异步。

8.3 输出为什么"晚一步"

step() 返回的 RequestOutput 对应的是上一步的采样结果，因为当前步的 post-process 被推迟了。离线 LLM._run_engine() 在循环结束时 flush，所以用户看到的是完整结果；如果你自己驱动 LLMEngine.step()，要记得在 has_unfinished_requests() 为假时调用 flush_inflight_reqs()。

四、常见坑与边界条件

  1. ZOS 默认开，但 PROMPT 引擎默认关：P 端没有 decode 流水线，开了反而增加复杂度。
  2. 不要在 forward/sample 里加同步：forbid_cuda_sync 会直接报错；DEEPINFER_DISABLE_SYNC_GUARD 只用于定位问题，不要在生产打开。
  3. 最后必须 flush：自定义驱动循环如果只调 step()，会丢掉最后一步的在途输出。
  4. batch invariant 只在 NVIDIA 支持：NPU 路径断言失败；跨平台比较输出时不要假设一致。
  5. batch invariant 不等于「跨硬件/跨版本一致」：它只保证同一套软硬件下，不同 batch 组合的结果一致；换 GPU 型号、换 kernel 版本仍可能变。
  6. 确定性采样必须同时关 varlen：只开 BATCH_INVARIANT=1 而保留变长验证，验证长度仍会变，输出不可复现。
  7. DEEPINFER_BATCH_INVARIANT=1 会牺牲性能：benchmark 通常不开，离线 PPL 回归通常开；先明确你要「快」还是「可复现」。
  8. EPLB 重排与 batch invariant 的交互：重排会改变专家放置，代码在两者同时开启时关闭 multiple reduction；但这不等于零成本，重排本身仍有同步开销。
  9. prev_step_state 会延长对象生命周期：长序列、大 batch 下要留意显存/内存峰值。

五、关键结论

  1. ZOS 的核心是把上一轮 post-process 与下一轮 schedule 塞进当前轮 GPU 计算期间，消除 CPU-GPU 气泡。
  2. 代价是元数据滞后：CPU 用历史信息估算 seqlen_q/k，GPU 用 remap + 接受结果 修正。
  3. 收尾必须 flush_inflight_reqs()；placeholder step 用来保持流水线运转。
  4. 批不变性来自确定性算子 + FlashMLA 专用模式 + 固定归约 + padding mask，只在 NVIDIA 支持。
  5. 确定性采样 = BATCH_INVARIANT=1 + MTP_VARLEN=0 + 固定 seq_seed，三者缺一不可。
  6. 两者都是性能与正确性的权衡：benchmark 追性能，评测/回归追可复现。

本章要点回顾

  • Decode 气泡：schedule / post-process 是 CPU 工作，GPU 等它们。
  • ZOS 流水线：GPU 算 N，CPU 同时做 schedule(N+1) 与 post-process(N-1)。
  • prev_step_state 传递上一轮状态；decode 的 post-process 推迟一轮。
  • 滞后修正：prepare_zos_inputs + compute_seqlens_* + remap + D2H。
  • 收尾：flush_inflight_reqs；空批：placeholder step。
  • 批不变性：确定性 kernel + FlashMLA flag + 固定归约 + mask；NVIDIA only。
  • 确定性采样三条件：BATCH_INVARIANT=1、MTP_VARLEN=0、固定 seq_seed。

一、这一章要解决的问题

  • 温度、top-k、top-p 怎么作用？

  • 要求输出 JSON / 正则 / EBNF 时，如何保证每一个 token 都合法，而不是事后校验？

9.2 采样器的执行路径

Sampler.forward()（layers/sampler.py:114）：

文本 / 输出
1. 从 hidden_states 里 gather 出需要采样的行（每个 prompt 的最后一行 / decode 的每行）
2. logits = hidden @ lm_head.weight        （bf16 GEMM）
3. 可选：blacklist token 置 -inf
4. 结构化输出 mask（若有 SO 请求）
5. fused_sample：
   - temperature 缩放
   - top-k / top-p 截断

7. 返回 SampledInfo（token、logprob、topk 信息）

几个工程细节：

  • force_topk（DEEPINFER_SAMPLER_FORCE_TOPK）：只在 top-k 个 token 上做 softmax / 采样，减少大片 logits 的读写；代价是要额外维护 token_index 映射。离线示例默认传 4096。
  • sum_smaller_probs（DEEPINFER_COMPUTE_SUM_SMALLER_PROBS）：统计「比采样 token 概率更小的所有 token 的概率和」，用于某些评测/校准场景；默认关。
  • prompt logprobs 分块计算：_PROMPT_LOGPROB_CHUNK_SIZE = 8192，避免一次 materialize 整个 prompt 的 logits；只有 CP rank 0 产出结果。
  • 验证路径共用：decode 时 fused_sample 同时完成「本轮采样」与「上一轮 draft 验证」；is_verify、last_nextn_token_logprobs 等参数把两条逻辑融合在一个 kernel 里（第 7 章）。

9.3 随机数与可复现

采样 kernel 的随机源是 seq_seed + sample_position：

  • seq_seed 是每序列一个 uint64，SamplingParams 不传时用 random.getrandbits(64) 生成；
  • sample_position 是该 token 在序列中的位置，保证同一种子下不同位置用不同随机数；
  • tag（default / mtp）区分主采样与草稿采样的 RNG 命名空间。

所以「固定 seq_seed」是确定性采样的必要条件，但不是充分条件：还要 batch invariant（logits 一致）与固定验证长度（MTP_VARLEN=0），见第 8 章。

9.4 结构化输出：编译期与运行期分离

so_args 的格式（SamplingParams 文档）：

Python
so_args = {
    "schema_type": "json" | "regex" | "ebnf",
    "schema": "...",                      # JSON Schema / 正则 / EBNF 文本
    "trigger_token_ids": [ ... ],         # 可选：完整出现后才开始约束
    "bound_token_id": 123,                # 可选：触发后先强制走完 trigger 序列
}

整个流程分两段来源：官方 Q&A + 一手代码：

编译期

structure_output/compiler.py 的 XGrammarCompiler 包装 xgrammar 的 GrammarCompiler：

  • json → compile_json_schema(schema, strict_mode=True)；
  • regex → compile_regex；
  • ebnf → compile_grammar；
  • 编译结果缓存，默认上限 10 GiB（DEEPINFER_XGRAMMAR_CACHE_LIMIT_BYTES）；
  • DEEPINFER_XGRAMMAR_DISABLE_CACHE 是 kill switch；如果上限 <= 0，代码会警告缓存无界增长，并提到 CVE-2025-32381。

SOMatcherBuilder 用线程池异步编译（max_workers 来自空闲 CPU，DEEPINFER_SO_BUILDER_CPUS 默认 4）。请求在 add_request() 时先 submit()，编译完成后由 pump() 挂到 seq.so_matcher 并真正入调度。这样编译不阻塞主线程，但请求的首 token 会多等一次编译（通常远小于一次 prefill）。

运行期

XGrammarMatcher（matcher.py:58）包住 xgrammar 的 GrammarMatcher，额外处理三件事：

  1. trigger tokens：在触发序列完整出现前，不施加约束；用 KMP 匹配，支持重叠/回退。
  2. bound token：触发后先强制逐 token 走完 trigger 序列，再进入 grammar；防止模型跳过触发词。
  3. 回滚：投机解码被拒时，rollback(steps) 把 matcher 状态退回；MAX_ROLLBACK_TOKENS = nextn + 2，回滚步数超过保留历史会抛错。

每个 decode step，Sampler._get_so_mask()：

  • 用上一轮被接受的 token（last_accepted_token + last_output_token）推进 matcher；
  • 对每个 draft token 预演 accept_token，记录能连续接受几步；
  • 为第 0 步（正常采样）与第 1..nextn 步（draft 验证）分别填 bitmask；
  • 把 bitmask 从 pinned CPU 拷到 GPU（独立 stream，record_stream 防复用）；
  • apply_token_bitmask_by_step_inplace 在对应 logits 行上把非法 token 置 -inf。

9.5 失败策略：只失败一个请求

结构化输出的错误处理原则是「只判死本请求，不带崩引擎」（代码注释）：

  • 编译超时（默认 20 s）→ aborted_matcher，请求标记 FINISHED_SO_FAILED；
  • matcher 运行时异常 → set_aborted，请求失败；
  • 日志里会打印 request_id，方便定位；
  • 主采样路径不 raise，避免连坐整个 batch 与 NCCL 超时。

9.6 SO 与投机解码的交互

投机解码会一次验证多个 draft，每个 draft 位置都需要自己的 mask：

  • _get_so_mask() 返回 max_MTP_value + 1 组 bitmask；
  • 第 k 组对应「假设前 k 个 draft 都被接受」时的合法 token 集；
  • 验证时如果第 k 个 draft 被拒，matcher 回滚到实际接受步数；
  • 请求遇到 EOS 后，后续 draft 的置信度被置 0（第 7 章）。

这也是 MAX_ROLLBACK_TOKENS = nextn + 2 的由来：最多回滚一轮验证的所有 draft，再加两个余量。

9.1 SO 的状态码

so_status 在代码里有四个值（按代码使用方式归纳）：

llm_engine.step() 在 prefill 最后一个 chunk 后把 0 改成 1；_get_so_mask() 在第一个 decode 步把 1 改成 2，并开始 accept_token。如果最后一个 prefill chunk 的 so_status 不是 0 或 matcher 为空，会直接把请求判死（代码里有错误日志），避免后续 mask 逻辑踩空。

9.2 为什么 mask 在 CPU 上填

xgrammar 的 matcher 是 CPU 库，状态推进、bitmask 填充都在 CPU 上完成；GPU 只负责把 bitmask 应用到 logits。DeepInfer 用 pinned memory + 独立 stream 把这次拷贝与主计算重叠：

  • bitmasks_cpu 预分配 max_MTP_value + 1 组；
  • so_copy_stream 等待当前流的一个 event，再异步 H2D；
  • 主采样流等待 so_mask_ready event 后再使用；
  • record_stream 防止 allocator 提前复用。

所以结构化输出不是「免费的」：每个 SO 请求每步都有一次 CPU matcher 推进 + H2D 拷贝；请求多时这部分会成为 CPU 瓶颈。

四、常见坑与边界条件

  1. temperature < 1e-5 会被改成贪心：同时把 top_p 设 1、top_k 设 -1；你以为在调低温，实际是直接 argmax。
  2. logprobs 布尔参数被忽略：要 logprob 请用 top_logprobs / prompt_logprobs。
  3. max_tokens=0 会被改成 1：不能用来「只做 prefill 不生成」。
  4. seq_seed 不传就是随机：想复现必须显式传；且还要满足 batch invariant + 固定验证长度。
  5. so_args 不接受 serialized：离线接口只接受 schema_type + schema；bound_token_ids（复数）也已废弃，只能传单个 bound_token_id。
  6. xgrammar 缓存无上限会 OOM：DEEPINFER_XGRAMMAR_CACHE_LIMIT_BYTES <= 0 时只有警告，不阻止运行；生产必须设正数。
  7. SO 编译超时 20 s：复杂 schema 可能超时，请求会失败；可以调 DEEPINFER_XGRAMMAR_TIMEOUT，但要权衡首 token 延迟。
  8. SO 请求被抢占后不能重算：matcher 状态无法回滚到任意历史，调度器会直接终止该请求（第 3 章）。
  9. YoCo 截断会关闭 prompt logprobs：add_request() 强制置 False 并打 warning；要 prompt logprobs 就别开截断。
  10. force_topk 与 draft 验证要 remap：开启后 draft 的 logprob 空间与主采样空间不同，代码用 remap_draft_topk 对齐；自己改采样逻辑时别漏。

五、关键结论

  1. 采样是「logits → 温度 → top-k/p → log-softmax → 带种子采样」；fused_sample 把主采样与投机验证融合在一个 kernel。
  2. 可复现需要三件事：固定 seq_seed、batch invariant、固定验证长度。
  3. 结构化输出是编译期 + 运行期分离：xgrammar 异步编译成自动机，运行期每步推进 matcher、填 bitmask、在 GPU 上屏蔽非法 token。
  4. trigger / bound tokens 允许「先自由生成，出现触发词后再约束」；matcher 支持回滚以配合投机解码。
  5. SO 失败只影响单个请求，不会拖垮引擎。
  6. 每个 SO 请求每步都有 CPU 推进 + H2D 成本；高并发下要评估这部分开销。

本章要点回顾

  • SamplingParams：温度、top-k/p、seq_seed、so_args、golden_token_ids。
  • 采样路径：gather → logits → blacklist → SO mask → fused_sample → 输出。
  • force_topk 省带宽但增加映射；sum_smaller_probs 默认关。
  • SO 编译：JSON strict / regex / EBNF；缓存默认 10 GiB；异步线程池。
  • SO 运行：matcher 推进 → 每步 bitmask → H2D → 屏蔽 logits；draft 被拒则回滚。
  • 状态码 0/1/2/-1；失败只终止本请求。
  • 坑：温度贪心化、logprobs 被忽略、max_tokens=0、种子、缓存上限、抢占后不能重算。

10多模态与并行组：图片怎么变 token，DP/CP/EP 怎么切

一、这一章要解决的问题

前面九章默认输入是纯文本。真实服务里还有两类复杂性：

  1. 多模态：一张图要经过视觉编码器变成一串 token/embedding，再与文本拼在一起；图片不能像普通 token 那样随便切 chunk。
  2. 并行拓扑：模型放不进一张卡，就要拆成 DP / CP / EP / ENP 多个进程组；不同组解决不同维度的切分，rank 的排列方式决定了通信是否高效。

这一章先讲图片如何进入引擎，再讲进程组如何组织，最后把开源版的「同引擎 VE」与生产版的「E/P/D 分离」对上。

二、机制与原理

10.1 图片进入引擎的五个步骤

以 ve/multimodal_processor.py 为例：

1）校验 image token

模型 config 里的 image_token_id 必须与 tokenizer 里的图像占位 token ID 一致，否则直接断言失败：

Python
assert self.mm_config.image_token_id == image_token_id

这是防止「图片 token 静默落到错误 ID」的关键校验（代码注释明确说明）。

2）展开占位符

overwrite_prompt() 把每个图像占位符替换成：

文本 / 输出
MM_IMAGE + MM_IMAGE_PAD × (N - 1)

其中 N = image_processor.estimate_num_tokens(image_input)，由图像尺寸与 patch size 决定。引擎侧的 MM_IMAGE / MM_IMAGE_PAD 不是词表里的 ID，而是：

Python
mm_image_token     = vocab_size + ImageTokenOffset.IMAGE
mm_image_pad_token = vocab_size + ImageTokenOffset.IMAGE_PAD

ImageTokenOffset 一共 5 个特殊图像 token（IMAGE、IMAGE_PAD、IMAGE_START、IMAGE_NEW_LINE、IMAGE_END），它们在词表之外单独编号，避免与真实 token 冲突。

3）记录 segment

展开的同时，multi_modal_data["segment_input"] 会记录：

  • 文本段：只记长度（TextLengthInput）；
  • 图像段：宽高、编码后的字节、该图在展开序列中的 (start, count)。

这样后续的 processor worker 不需要重新解析整条 prompt，只要按 segment 处理。

4）预处理 worker

_start_workers() 用 fork 启动多个 MultimodalProcessor 子进程：

  • 输入队列 / 输出队列，缓冲区默认 512（DEEPINFER_MULTI_MODAL_BUFFER_SIZE）；
  • 默认 8 GB/rank 的 pinned host 共享池（DEEPINFER_MULTIMODAL_POOL_SIZE_GB）；
  • worker 超时默认 1800 s（DEEPINFER_MULTI_MODAL_WORKER_TIMEOUT）；
  • 每个 worker 绑定到引擎 GPU 所在 NUMA（bind_numa(which_numa(0))）。

图像预处理（解码、缩放、归一化）是 CPU 工作，放在独立进程里，避免阻塞引擎主线程。

5）前向时的消费

LLMEngine.step() 每步调用 multi_modal_processor.fetch()，把已处理好的 segment 取回；如果某张图处理失败（损坏/超时），会把对应请求 abort，并打印错误。真正的视觉编码在模型 forward 里：models/vision_encoder/vit.py + vl_aligner.py + mlp_projector.py，输出与文本 embedding 拼在一起，交给 LLM。

10.2 图片为什么不能随便切 chunk

Chunked prefill 按 token 数切分，但一张图在序列里是 MM_IMAGE + N × MM_IMAGE_PAD 的连续单元；如果切在中间，视觉编码器会拿到半张图。调度器的 _adjust_chunk_size() 会检查切点：

  • 如果切点落在 IMAGE_PAD 区域内，且往前能找到 IMAGE，就把整个图片单元往前收缩或往后扩展；
  • 允许在两张图片之间（MM_IMAGE 边界）切开。

这条逻辑在 C++ 调度器里（第 3 章），不在多模态处理器里；因为切分决策发生在调度时。

10.3 视觉编码器在开源版里是「同引擎」的

开源示例的 --prompt_mode image 把原始图片直接喂给引擎，ViT 与 LLM 在同一个 engine 进程里：

文本 / 输出
prompt + image → ViT → aligner → LLM tokens → decode

生产架构则是 E/P/D 分离：VE 单独部署（一般单 GPU 一个实例，推荐便宜卡），PE 只做语言模型 prefill，CE 只做 decode。开源版没有 VE 的独立服务编排，但代码里已经按「VE 可分离」的方式组织：

  • ve/ 独立目录；
  • MultimodalProcessor 可以在 COMPLETION 引擎里关闭（engine_type != COMPLETION 才构造）；
  • EngineType.PROMPT / COMPLETION 为 P/D 分离留了钩子。

所以第 1 章说「P/D 编排未开源」：部件在，编排不在。

10.4 并行组：四类切分，五套进程组（含派生组）

deepinfer/model_executor/parallel_utils/parallel_state.py 的 ParallelProcessGroup.create_process_groups() 一次性建好：

组切分维度rank 排列用途
DP数据并行(replica, dp, cp) → 每组 dp 个 rank不同请求分到不同副本；attention 走 DP
CP上下文并行(dp, cp) → 每组 cp 个 rank一条长上下文切给多卡做 prefill
EP专家并行连续 ep_size 个 rankMoE 专家分布
ENPEngram 并行(replica, enp)Engram 模块的并行组
ep_in_dpDP 内的 EP连续 ep_size 个 rankDP 组内部的专家通信

关键公式（config.py:ParallelConfig）：

文本 / 输出
data_parallel_size = max(1, expert_parallel_size // context_parallel_size)  # 未显式指定时
model_parallel_size = context_parallel_size
world_size = max(cp_size × dp_size, engram_parallel_size)
data_parallel_rank = engine_rank % data_parallel_size

约束：

  • (cp × dp) % ep == 0：EP 必须整除总副本数；
  • world_size % (cp × dp) == 0、world_size % enp == 0；
  • ep_size 的组是连续 rank，所以一个 EP 组通常落在同一节点/NVLink 域；
  • ENP 默认等于 cp × dp，也可以单独指定。

10.5 进程组是怎么建出来的

create_process_groups() 用 torch.distributed.new_group() 按 rank 列表切分：

  • world：所有 rank；
  • local：每个 rank 单独一组（用于本地操作）；
  • DP / CP / EP / ENP：按上面的 reshape 规则；
  • CPU 组：DP / CP / EP-in-DP 各建一份 gloo 后端，用于 CPU 侧的广播与同步（ZOS 下尤其重要）。

CP 组还会创建一个 共享内存 MessageQueue（distributed/shm_broadcast.py），用于 cp_broadcast_object：driver 把方法名/参数写进共享内存，CP follower 读取并执行同名方法。这比 pickle + NCCL broadcast 更轻，适合每步高频调用。

init_device_groups() 会对每个 NCCL/HCCL 组做一次空的 all_reduce，强制建立通信；因为 PyTorch 默认进程组改成 gloo 后，NCCL 子组是懒初始化的，不先跑一次 collective 会拿到空指针。

10.6 CP 的实现：prefill 时重排 token

CP 只在 prefill 生效（第 5 章）：

  1. input_metadata.prepare_for_mirror_cp() 按 CP rank 重排 token，生成 mirror_cp_index / mirror_cp_reverse_index；
  2. 模型开头 gather(hidden_states, mirror_cp_index)，让每张卡拿到自己负责的 token；
  3. 注意力内部对压缩器输入、SWA KV 做 all_gather，保证每张卡都能看到完整 KV；
  4. 输出后 gather(..., mirror_cp_reverse_index) 还原原始顺序。

CP 的收益是「长 prompt 的 prefill 算力分摊」，代价是额外的 all-gather 与索引重排；所以生产当前不用 CP来源：官方 Q&A。

10.7 通信缓冲区：userbuffer

model_executor/parallel_utils/userbuffer.py 预分配三类缓冲区：

缓冲区用途
userbuffer.cpCP all-gather 的临时张量
userbuffer.allocate_ep()DeepEP dispatch/combine 的缓冲区
userbuffer.allocate_sym_buffer()Mega MoE 的对称内存缓冲区

好处是避免每步临时分配，并让通信与计算流可以精细重叠（async_with_compute_stream、EventHandle）。DEEPINFER_USERBUFFER_COMM_SMS 控制通信占用的 SM 数，limit_num_sms() 在共享专家计算时限制 SM，避免和通信抢资源。

10.2 并行组的拓扑示意

四、常见坑与边界条件

  1. image token ID 必须与 tokenizer 一致：assert self.mm_config.image_token_id == image_token_id，不一致直接启动失败。
  2. 图片不能被 chunk 切开：调度器会把切点移到图片边界；如果单张图片本身超过 max_num_batched_tokens，请求可能一直无法调度（而不是立刻报错）。
  3. 共享池按 rank 预留 8 GB：8 卡节点就是 64 GB pinned host memory；节点内存紧张时要调 DEEPINFER_MULTIMODAL_POOL_SIZE_GB。
  4. 多模态 worker 是 fork 出来的：父进程里不要在 fork 前创建 CUDA context 相关状态（代码用 ForkProcessWithCrashHeader 并做了 NPU 的 SIGTERM 处理）。
  5. CP 只在 prefill 生效：decode 不做 CP；COMPLETION + cp > 1 会断言失败。
  6. EP 组是连续 rank：跨节点大 EP 需要底层网络支持；不要假设任意 rank 组合都能高效通信。
  7. ep_size 必须整除 cp × dp：否则启动断言失败。
  8. 昇腾要求两个可见设备变量一致：CUDA_VISIBLE_DEVICES 与 ASCEND_RT_VISIBLE_DEVICES 不一致会直接 RuntimeError。
  9. 开源版没有 EPD 编排：VE 可以在同引擎跑，也可以关掉；但把 VE 拆成独立服务、做 E/P/D 路由，需要自己写。

五、关键结论

  1. 图片进入引擎要经过「校验 image token → 展开为 IMAGE + PAD → segment → worker 预处理 → ViT/aligner」。
  2. 图片是不可分割的 chunk 单元，调度器会在边界处调整切分。
  3. 开源版是「同引擎 VE」，生产是「E/P/D 分离」；部件在，编排不在。
  4. 并行有四套组：DP（请求）、CP（上下文）、EP（专家）、ENP（Engram）；world = max(cp×dp, enp)。
  5. CP 只在 prefill 生效，靠 token 重排 + all-gather 实现；生产当前不用。
  6. 平台差异被 Platform / deep_cluster / npu_ops 三层封装，NVIDIA 与昇腾走不同后端。

本章要点回顾

  • 图像 token：MM_IMAGE + N × MM_IMAGE_PAD，ID 在词表外单独编号。
  • 多模态 worker：fork 进程 + 共享内存池 + 超时/失败 abort。
  • chunk 切分不能切图片；调度器负责对齐。
  • 并行组：DP / CP / EP / ENP；EP 连续 rank；world_size 取最大值。
  • CP：prefill token 重排 + attention all-gather；decode 不用。
  • userbuffer：CP / EP / Mega MoE 三类预分配通信缓冲。
  • 平台：GPU（NCCL/CUDA）vs NPU（HCCL/CANN），环境变量必须一致。

一、这一章要解决的问题

  • 官方生产架构里，KV 存储、四类负载均衡、弹性容错是怎么做的？
  • 开源版能复现哪些数字，不能复现哪些？

  • 如果真要上线，还需要自己补哪些组件？

这一章的数据分两类：官方生产口径（不可由开源版直接复现）与仓库内可运行的基准/评测。正文会逐条标注。

二、机制与原理

11.1 生产拓扑：E/P/D + 专用存储 + 四类 LB

官方口径来源：官方 Q&A：

  • P/D 分离，VE 独立部署；生产不用 TP，也不用 CP。
  • Prefill 用最小的 EP/DP（HBM 允许范围内），Decode 用最大的 EP/DP（GPU 允许范围内）。
  • 最小高效部署单元是 64P + 64D；1P + 1D 也能部署，但效率不在一个量级。
  • 单集群日处理 155 万亿 token；GPU 小时收入 $38（低谷定价）。
  • P/D 可跨（相邻）数据中心，按每 8 GPU 约 400 Gbps 预留互联带宽。

11.2 KV 存储：为什么放到 3FS

第 4 章讲过三级存储，这里补生产细节来源：官方 Q&A：

内容介质副本管理者
在途 block KV + state KVGPU 显存—P / D 实例
SWA KV cache本地 host memory单副本；跨机命中走 400G VLANP / D 实例
分页 block KV（主 KV + Indexer K）专用 3FS 集群无应用层副本，依赖 3FS 冗余kvcache-store

为什么 block KV 不放在本地分层存储，而要单独一个存储集群？

  1. 任意前缀可命中：每台 prefill 机器都能查任意历史前缀，不需要「前缀亲和」路由，路由策略可以纯粹按负载来。
  2. 扩缩容解耦：存储节点与计算节点独立扩缩，不会因为计算节点扩缩而搬 KV。
  3. 故障隔离：计算节点故障率比存储节点高一个数量级以上；KV 放独立集群，计算节点挂了不影响缓存。

3FS 的工程参数来源：官方 Q&A：

  • 10+2 纠删码，一个 EC 组容忍两台节点同时故障；读时向 11 个节点同时发请求，任意 10 个返回即可解码。
  • 每个存储节点一个 GC Worker，按 LRU 回收过期 KV，把磁盘占用压在 watermark 以下。
  • 约 100 PiB SSD；TTL 3 天（Agent 流量）/ 7 天（Chatbot 流量）。
  • 经验值：TTL 从 7 天降到 3 天，Chatbot 的 KV 命中率损失约 0.5%–1%（长尾命中很重）。
  • 单存储服务器推荐 20 × 30.73 TB SSD，读 ≥ 40 GB/s、写 ≥ 5 GB/s，容量按 24 小时数据量规划。
  • 每 GPU 约 14.4 TB 逻辑容量（物理容量更大）。

11.3 四类负载均衡

Prefill LB：按上下文长度分桶 + 计算配额

官方做法来源：官方 Q&A：

  1. 分桶：按总上下文长度分 4 档——<16K / 16–64K / 64–256K / ≥256K。
  2. 动态分配引擎：每档分到多少 engine，按上一轮该档的「计算配额需求」比例重新分配；每档有自己的 per-batch 计算配额上限。
  3. 跨 DP 组：引擎按剩余计算配额主动拉取任务；因为任意引擎都能命中任意前缀，所以不做 prefix-affinity 路由。
  4. DP 组内：请求到达时，交给当前配额负载最低的 DP rank。
  5. 单 GPU 内：FIFO 出队；chunk 大小不是固定值，而是从预算里解出来：
    • 每个 prefill step 给一个时间预算 compute_quota_limit（纳秒）；
    • 用拟合的二次成本模型 cost(q, c) 预测耗时（q = 本步 query token 数，c = 已算前缀长度）；
    • 解二次方程，取「不超过 32768 token 预算、且刚好用完剩余时间」的最大 q；
    • 预算还要在 DP 组内做一次 all-reduce MIN，取最紧的那个。

这套调度的目标是按计算量而不是按请求数分配，避免长上下文请求把短请求饿死。

Decode LB：请求数 + KV 总长

Decode 的负载有两个维度：

  • 请求数决定每步 batch size；
  • KV 总长决定 attention 部分的成本。

官方策略是「短请求发给并发低但 KV 总长大的 GPU，长请求发给 KV 总长小的 GPU」，参考 DualPath 的组内调度算法来源：官方 Q&A。所有 decode 实例的 GPU 在一个统一池子里路由，不按前缀亲和。

VE LB：按机器 + patch 数

图片按机器粒度路由来源：官方 Q&A：

  1. prefill 机器随机选一台「每个 GPU 都挂了一个 VE」的机器；
  2. 在该机器上，把图片交给当前处理 patch 数最少的 GPU；
  3. patch 数直接按 (width / patch_size) × (height / patch_size) 估算。
EPLB

专家级负载均衡见第 6 章；官方四类 LB 里它单独算一类。

效果

官方说整体能达到「完美均衡离线基准」的约 80%来源：官方 Q&A。这是一个很有参考价值的数字：负载均衡做得再好，也会损失约 20% 的理想吞吐，因为真实路由有延迟、有状态、有尾部长请求。

11.4 弹性与容错

机制做法关键数字
Prefill 扩缩按「非缓存 token 数」决定机器数有速率限制与上下界
Decode 扩缩按「running 请求数」调整同上
缩容保护配额利用率 > 0.8 时禁止缩容0.8
CE 优雅退出收到 shutdown 后进入 1 分钟宽限期；未完成请求连同 KV 一次性转给其他 CE1 min
重启重启耗时分钟级；靠配额冗余 + 请求级重路由兜底，而不是缩短单机重启分钟级
EP failover大 EP 实例所有 GPU 是一个通信域，单卡故障整实例不可用；重启时按当前健康 GPU 重新确定 EP size重新定 EP

这条「重启分钟级 + 请求级重路由」的取舍很重要：它不追求单实例高可用，而是把可用性交给上层调度与冗余。

11.5 低精度与 kernel

官方口径来源：官方 Q&A：

内容格式
主 KVper-16、e4m3（类似 NVFP4，但没有 global scale）
Indexer KVper-32、ue8m0，MXFP4
MoE routed-expert 权重per-32、ue8m0，MXFP4

Kernel 方面：

  • Mega MoE：在 scale-up 域内，无论 EP 大小、batch 大小，都比非融合 MoE 明显更快，所以是通用方案。
  • FlashMLA：内部版本比开源版多一个手调 SASS 优化，decode kernel 快 5%–10%；端到端差距最多 5%。
  • 官方建议用 examples/benchmark.py 的 trace 看实际 kernel 使用情况。

11.6 Benchmark：仓库里怎么量

examples/benchmark.py 把 prefill 与 decode 解耦：

  • --prefill_batch_size / --non_cached_tokens 只影响 prefill 的 chunk 与后缀长度；
  • --decode_num_requests 只影响 decode 的 batch；
  • 默认：decode_num_requests=64、context_length=32768、non_cached_tokens=4096、prefill_batch_size=32768、nextn=5。

三个指标来源：一手 examples/README.md：

指标口径
prefill throughput（tokens/s/GPU）跳过 5 个 warmup chunk，取最后 11 个样本的 10 个稳态区间；token 数 / 总时长 / 设备数
decode avg_SPS（steps/s）跳过 50 个 warmup + 60 个带日志的 step，取最后 61 个样本的 60 个区间；与 MoE LB flush 冲突的区间丢弃
decode throughput（tokens/s/GPU）avg_SPS × decode_num_requests × (1 + nextn) / cp，按全接受记账

「全接受」意味着 decode throughput 是上限口径：不管真实接受率是多少，每步都按 1 + nextn 个 token 算。所以它适合比较硬件/配置，不适合预测线上真实吞吐。

其他细节：

  • PROFILE=1 时 prefill/decode 各跑一段 profiler，导出 head-to-tail 的 trace；trace 里的 step 时间包含 profiler 开销（bsz=1 时可能膨胀近 50%），不要用 trace 算 SPS。
  • sweep/run_sweep.sh 扫一个维度，plot_pareto.py 画吞吐-延迟曲线；一个 tag 一条曲线。
  • --result_jsonl 把完整配置与原始量写一行 JSON，便于复现。
  • ep_size = WORLD_SIZE × len(CUDA_VISIBLE_DEVICES)；--cp 必须整除 ep_size。
  • 冗余专家通过 DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS 传入，默认 32；引擎会向上补齐到 ep_size 的倍数。

11.9 开源边界：上线还缺什么

11.1 一次基准运行的读法

文本 / 输出
1. 构造一批共享前缀的请求（benchmark 自动 fork）
2. 跑 prefill：记录 10 个稳态区间 → prefill tokens/s/GPU
3. 跑 decode：记录 60 个稳态区间 → avg_SPS、max_step
4. 按全接受口径换算 decode tokens/s/GPU
5. 可选 PROFILE=1 导出 trace，看 kernel 组成
6. 可选 sweep 扫一个维度，画 Pareto

注意第 4 步的「全接受」是上限；真实吞吐 = 上限 × 实际接受率相关的系数。第 7 章给出的真实接受长度约 3.2，而全接受按 1 + 5 = 6 记账，所以不要拿 decode throughput 直接对线上 QPS。

四、常见坑与边界条件

  1. 把 decode throughput 当真实吞吐：它是全接受口径（每步 1 + nextn），真实接受长度通常更低。
  2. 用 trace 里的 step 时间算 SPS：profiler 会膨胀耗时（bsz=1 时可达近 50%），trace 只适合看 kernel 组成。
  3. 忽略 MoE LB flush 的干扰：benchmark 会丢弃与 flush 冲突的区间；自己写计时脚本时要处理。
  4. PPL 基线跨平台不通用：基线按平台/负载分组；换 GPU/NPU、换 workload 都要重测。
  5. AIME / HLE 数据要自己准备：仓库不下载数据集；HLE 是 gated，需要先在 Hugging Face 接受条款。
  6. HLE 不能用 rule judge：score.py 会直接拒绝；自由文本必须用 LLM judge。
  7. Pass@1 要先看 coverage_complete：为 false 时数字无效。
  8. 官方生产数字不是开源版 benchmark：155T tokens/day、$38/GPU-hour、AIME 99.9% 都依赖完整生产栈；开源版能复现的是引擎行为与相对趋势，不是绝对值。
  9. 开源版没有在线 API：LLMEngine 文档明确「本版本不含在线服务封装」；不要按 vLLM 的 OpenAI Server 预期来找入口。
  10. KV 存储 / LB / P/D 编排未开源：官方明确与内部基础设施耦合；需要自己实现或只用离线模式。

五、关键结论

  1. 生产是 E/P/D + 3FS KV 存储 + 四类 LB + 弹性容错 的完整系统；开源版只给引擎。
  2. KV block 放独立存储集群，是为了「任意前缀可命中 + 扩缩容解耦 + 故障隔离」；SWA 留在本机 host memory。
  3. Prefill LB 按上下文长度分桶、按计算配额拉取；Decode LB 同时平衡请求数与 KV 总长；整体约达完美均衡的 80%。
  4. 低精度是系统性的：主 KV FP4、Indexer MXFP4、MoE 权重 MXFP4；Mega MoE 是 NVL 域内的通用方案。
  5. Benchmark 的 decode throughput 是全接受上限口径；Eval 的 Pass@1 是能力参考值；两者都不能直接当线上 SLA。
  6. 上线还缺 API、Recipe、队列、P/D 路由、KV 存储、LB、弹性、可观测性八块。

本章要点回顾

  • 生产拓扑：E/P/D 分离 + 3FS + 四类 LB；最小高效单元 64P + 64D。
  • KV 存储：100 PiB、TTL 3/7 天、14.4 TB/GPU、400 Gbps/8 GPU。
  • Prefill LB：4 档上下文 + 计算配额 + 二次成本模型 + 32768 token 预算。
  • Decode LB：请求数 + KV 总长双维度；VE LB：按机器 + patch 数。
  • 弹性：按非缓存 token / running 请求扩缩；>0.8 禁止缩容；CE 1 分钟优雅退出。
  • Benchmark：prefill throughput、avg_SPS、decode throughput（全接受口径）。
  • Eval：AIME 99.9 / GPQA 93.4 / HLE 42.6；生成与打分分离；LLM judge。
  • 上线缺口：API、Recipe、队列、P/D 路由、KV 存储、LB、弹性、可观测性。
