说明

一、这一章要解决的问题

在框架线里，你在 LangChain 中写下 llm.invoke("你好")（框架线第 5 章），一行代码，回答就回来了。很方便，但也很难受：这行代码底下，网络上实际跑的是什么？

答案是：一份 JSON。准确地说，是 OpenAI Chat Completions 这个 HTTP 接口约定——请求长什么样、响应长什么样、出错时返回什么，全部写在一份公开的接口契约里。LangChain 的 invoke、stream，本质上都是在帮你拼这份 JSON、收这份 JSON。

本教程的手写线（S1–S10）全部建立在这份契约上。框架线用类和中间件把契约包起来，手写线反其道而行：把契约摊开在你面前，一行行自己拼。理由有两个：

  1. 契约是稳定的。它从 2023 年公布至今基本没变，所有主流厂商都兼容它。学会一次，处处能用。
  2. 契约是透明的。框架出问题时（比如响应里多了一个奇怪的字段），只有看得懂契约的人才排查得动。

读完本章，你应该能回答四个问题：请求 JSON 里有什么？响应 JSON 里有什么？流式响应和普通响应差在哪？以及——为什么本章的示例脚本不联网也能跑？

二、机制与原理

2.1 请求侧：三件套加一个开关

一次 Chat Completions 调用，请求体长这样：

json
{
  "model": "qwen3-vl",
  "messages": [
    {"role": "system", "content": "你是终端里的编码助手"},
    {"role": "user", "content": "帮我看看这个报错"}
  ],
  "tools": [],
  "stream": false
}

核心字段只有三个加一个开关：

字段必填作用
model是模型名，服务端靠它路由
messages是{role, content} 字典的数组，对话的全部上下文
tools否工具 Schema 列表（S4 展开）
stream否是否流式，默认 false（2.3 节）

messages 里每条消息必须带 role，契约定义了四种：

role谁在说话典型内容
system应用/开发者行为规则、环境信息（S2 整章都在讲它）
user用户提问、指令
assistant模型上一轮的回复；请求调工具时还带 tool_calls
tool工具执行方工具结果，回灌给模型（S4）

眼熟吗？框架线第 3 章的 SystemMessage / HumanMessage / AIMessage / ToolMessage 四个类，一一对应这四种 role。区别在于：框架线用类包装，手写线刻意只用 dict——没有任何中间层，你在 IDE 里打印一下，看到的就是网络上跑的东西。这不是偷懒，是教学设计：先见到裸契约，再回头看框架的抽象，才知道框架到底替你做了什么。

2.2 响应侧：choices、usage 和 finish_reason

响应也是一份 JSON，顶层结构和每个字段的作用如下（usage 数值随提问而变）：

字段作用
id本次调用的唯一 id，排障时用它对日志
object / model / created类型标识、模型名、时间戳
choices候选回复数组；默认只有一条，取 choices[0]
choices[].message正文所在：{role, content, …}
choices[].finish_reason停止原因：stop 或 tool_calls（2.4 节）
usagetoken 消耗：prompt_tokens / completion_tokens / total_tokens

下面是一个真实响应的结构摘录，来自《Agents底层逻辑》课程课件——Ollama 本地跑 qwen3-vl 的返回（取值有删节，字段结构原样）：

json
{
  "id": "chatcmpl-…",
  "object": "chat.completion",
  "model": "qwen3-vl",
  "choices": [
    {
      "index": 0,
      "finish_reason": "stop",
      "message": {
        "role": "assistant",
        "reasoning": "…思考过程…",
        "content": "…最终回答…"
      }
    }
  ],
  "usage": { "…": "…" }
}

注意 message 里多出来的 reasoning 字段——思考型模型（reasoning model）会把它推理时的"草稿"也返回给你。坑在这儿：不同厂商对思考字段的命名不统一：

厂商思考字段名
DeepSeek 系reasoning_content
qwen3 系部分端点（如课件中的 Ollama qwen3-vl）reasoning

手写线的 agent/model.py 在 _normalize_message 里两者都兼容，摘录如下：

Python
# agent/model.py
def _normalize_message(msg) -> dict:
    """把 SDK 的 message 对象归一化成纯 dict。

    兼容两种思考字段命名：reasoning_content（DeepSeek 等）与 reasoning（部分厂商）。
    """
    reasoning = getattr(msg, "reasoning_content", None) or getattr(msg, "reasoning", None)
    message: dict = {"role": "assistant", "content": getattr(msg, "content", None)}
    if reasoning:
        message["reasoning_content"] = reasoning
    …  # tool_calls 的处理见 S4
    return message

统一归一成 reasoning_content 之后，上层代码不用再关心厂商差异——这是"在边界处消化不一致"的典型做法。

归一化的效果与响应的原始形状，看 s01 的实测输出（s01_model_contract.py 第 1、2 节）：

文本 / 输出

{
  "role": "assistant",
  "content": "我是手写教程里的假模型，替你演示模型接口契约。",
  "reasoning_content": "用户在问我是谁，直接自我介绍即可。"
}

== 2. 响应的原始形状（顶层结构即契约）==
顶层字段     : ['choices', 'created', 'id', 'model', 'object', 'usage']
choices[0]   : ['finish_reason', 'index', 'message']
message 字段 : ['content', 'reasoning_content', 'role', 'tool_calls']

两个细节值得咀嚼：其一，message 字段里出现了 tool_calls——FakeClient 的 message 总是带这个属性（没有工具调用时为 None），_normalize_message 靠 getattr 判空，真 SDK 行为相同；其二，usage 数值是 FakeClient 的固定演示值（10/20/30），真实服务返回的数值随请求长度变化，但字段名与嵌套位置是契约的一部分，不会变。

2.3 流式：同一个契约的另一种响应形态

stream: true 时，响应不再是单个 JSON，而是被切成一串 chunk，逐个推给你。两个关键变化：

  1. 正文不再在 choices[].message，而是藏在每个 chunk 的 choices[].delta 里，一片一片到；
  2. finish_reason 不再每条都有，只在最后一个 chunk 出现，标志流结束。

s01 脚本手动迭代了一次 chunk 流，实测输出（s01_model_contract.py）：

文本 / 输出
== 3. 流式：逐 chunk 的 delta（手动迭代原始 chunk）==
chunk 0: delta.content='1、2' finish=None
chunk 1: delta.content='、3、' finish=None
chunk 2: delta.content='4、5' finish=None
chunk 3: delta.content='。' finish=None
chunk 4: delta.content=None finish='stop'

正文 '1、2'、'、3、'……一片片到达，最后一个 chunk 的 delta.content 是 None，只带来 finish='stop'。这和你平时在聊天界面看到的"打字机效果"是同一件事：前端逐片渲染 delta。

那谁来把这些碎片拼回完整消息？手写线的答案是 agent/model.py 里的 _StreamAssembler：三条通道（思考、正文、工具调用）各自累积，流结束后拼出一个与非流式完全同形的 message dict。看实测（s01_model_contract.py 第 4 节）：

文本 / 输出
== 4. 拼装后的 message（与非流式形状完全一致）==
{
  "role": "assistant",
  "content": "（假模型：没有匹配到脚本）"
}

形状确实一致（role + content），但内容是假模型的默认文案——原因是剧本规则默认 once=True，"从 1 数到 5" 这条响应在第 3 节手动迭代 chunk 时已经被消费掉了，第 4 节再调一次自然落到默认回复。形状一致性才是这节要验证的东西：上层代码拿到的 message 不需要区分它来自流式还是非流式。

2.4 client 可注入：离线也能跑的原理

手写线的 Model 有一个看似不起眼、实则贯穿全教程的设计：

Python
# agent/model.py
class Model(EventEmitter):
    """模型调用器。session 提供 messages（必需）与 tools（可选）。"""

    def __init__(self, client: Any | None = None) -> None:
        super().__init__()
        self.client = client if client is not None else make_default_client()

    def invoke(self, session, stream: bool = False) -> InvokeResult:
        kwargs: dict[str, Any] = {
            "model": settings.model,
            "messages": list(session.messages),
        }
        if session.tools:
            kwargs["tools"] = session.tools
        if stream:
            return self._invoke_stream(session, **kwargs)
        return self._invoke(session, **kwargs)

client 是注入的。不注入时按环境变量创建真的 OpenAI SDK client；注入时给什么都行——只要形状和 SDK 一样。_fake_llm.py 里的 FakeClient 就是这么造的：

真实 OpenAI SDKFakeClient形状
client.chat.completions.create(...)同名方法一致
返回带 .choices[0].message 属性的对象返回带同名属性的 SimpleNamespace一致
stream=True 时返回可迭代的 chunk同样返回 chunk 迭代器一致

这就是 duck-typing：走起来像鸭子、叫起来像鸭子，那就是鸭子。Model 只依赖形状，不依赖类型——所以 s01 不联网、不装 SDK 也能跑，而且恰好证明了契约的稳定性：只要响应形状符合契约，真模型和假模型对上层完全不可区分。

再看一眼请求侧实际发出了什么（s01_model_contract.py 第 5 节，FakeClient 会记录每次收到的请求）：

文本 / 输出

2.5 会用一份契约 = 会用几乎所有模型服务

OpenAI 公布这份契约后，生态里几乎所有人都选择了兼容它：Ollama 在 http://localhost:11434/v1 暴露同样端点，vLLM 自托管服务同样如此，各家云厂商则直接提供 OpenAI 兼容模式。切换服务商只需要改两个环境变量（见 agent/config.py）：OPENAI_BASE_URL 指向新地址、OPENAI_MODEL 换个模型名，代码一行不动。

所以"手写一遍 SDK 调用"的性价比极高：你写的不是"调用某个厂商的代码"，而是"调用几乎所有模型服务的代码"。

invoke 内部对非流式与流式分两条路径，但终点相同——一个归一化的 message dict：

Python
# agent/model.py（节选）
def _invoke(self, session, **kwargs) -> InvokeResult:
    resp = self.client.chat.completions.create(**kwargs)
    message = _normalize_message(resp.choices[0].message)
    session.add_message(message)      # 响应自动进会话历史（S3 详谈）
    return InvokeResult(message=message, raw=_to_plain(resp))

def _invoke_stream(self, session, **kwargs) -> InvokeResult:
    kwargs["stream"] = True
    chunks = self.client.chat.completions.create(**kwargs)
    message = _StreamAssembler(self).consume(chunks)
    session.add_message(message)
    return InvokeResult(message=message, raw=None)

两个值得注意的细节：

  1. raw=_to_plain(resp)：_to_plain 把 SDK 返回的对象递归转成纯 dict（优先走 pydantic 的 model_dump），否则你连 json.dumps 都做不了——原因见第四节的坑 4。
  2. 流式路径里 raw=None：chunk 流被消费后就不存在"原始响应"这个整体了，这是流式与非流式的本质差异。

四、常见坑与边界条件

坑 1：finish_reason 的两种值语义不同。 stop 表示模型直接给出了最终回答；tool_calls 表示模型想调工具，此时 message.content 往往是 None、tool_calls 字段才有内容。判断"这轮结束没有"不能看 content 是否为空，要看 finish_reason——手写线只处理 stop 和 tool_calls 两种值，遇到 length（达到 max_tokens 被截断）等其他值时应显式报错而不是静默继续。

坑 2：多候选被静默丢弃。 请求参数 n > 1 时响应会有多条 choices，但绝大多数应用（包括手写线）只取 choices[0]，其余候选直接消失。这不是 bug 而是取舍，但你要知道自己丢了什么。

坑 3：思考型模型默认"边想边说"。 qwen3 系等思考模型默认开启思考模式，响应里会多出思考字段（字段名见 2.2 节表格）；某些场景（追求低延迟）需要通过 extra_body 传厂商私有关闭思考的参数——具体字段名随厂商而异，参见《Agents底层逻辑》课件中 qwen3-vl 的示例。反过来，思考字段也是宝贵的：S3 会讲为什么必须把它留在上下文里。

坑 4：SDK 返回的不是 dict，是对象。 OpenAI SDK 用 pydantic 模型包装响应，resp["choices"] 会直接报 TypeError，json.dumps(resp) 也不行。要么按属性访问（resp.choices[0].message），要么先归一化——agent/model.py 的 _to_plain 用 model_dump() 递归转换， FakeClient 用 SimpleNamespace 模拟同样的属性访问形状。在边界处归一化，内层代码就只面对 dict。

顺带一个前瞻：流式下的 tool_calls 更阴险——arguments 是跨 chunk 的分片，必须按 index 累积拼接，流结束后才是完整 JSON。细节在 S4 展开。

五、关键结论

  1. 框架的 invoke 底层就是一份 JSON 契约：请求 {model, messages, tools?, stream?}，响应 {id, choices[].message, usage, finish_reason}。
  2. messages 是 {role, content} dict 数组，四种 role：system / user / assistant / tool。框架线第 3 章的四个 Message 类只是这四种 role 的类包装。
  3. 思考字段名不统一（reasoning_content vs reasoning），归一化要放在模型层边界（_normalize_message）。
  4. 流式只是把响应切碎：正文在 delta 里、finish_reason 在最后一个 chunk；Model 层负责把 chunk 拼回与非流式同形的 message。
  5. client 可注入 + duck-typing = 契约稳定性的直接红利：假模型与真 SDK 对上层不可区分，全教程得以离线运行。
  6. 一份契约兼容整个生态：改 OPENAI_BASE_URL 和 OPENAI_MODEL 就能切换 Ollama / vLLM / 云厂商。

本章要点回顾

  • 请求侧三件套：model 必填、messages 是对话的全部上下文、tools 留给 S4；stream 是响应形态的开关。
  • 响应侧取 choices[0]：正文在 .message.content，停止原因在 .finish_reason，消耗在 .usage。
  • 四种 role 与框架线第 3 章四个 Message 类一一对应；手写线只用 dict，契约透明。
  • 思考字段两套名字，_normalize_message 统一收编成 reasoning_content。
  • 流式 chunk 的正文在 delta、终点在最后一个 chunk 的 finish_reason；拼装后与非流式同形。
  • 下一步：messages[0] 位置上的 system 消息值得单独一章——S2 讲怎么写好它。

2系统提示词：模型的出厂设置由你决定

说明

一、这一章要解决的问题

同一个基座模型，在不同产品里的表现天差地别：有的严谨克制、有的满嘴胡话，有的精简利落、有的车轱辘话连篇。模型明明是同一个，差距从哪来？大部分时候，答案藏在一段你看不见的文本里——系统提示词（system prompt）。

系统提示词是 messages 数组里 role 为 system 的第一条消息（S1 讲过四种 role），它位于所有消息之前，而模型在训练时被重点对待"开头的指令"——把它理解成模型的出厂设置：用户没开口之前，它先定义了"你是谁、你在哪、你该怎么做"。

问题在于：系统提示词写得差，比不写还糟。废话太多稀释重点，规则自相矛盾让模型无所适从，把每分钟都在变的东西写进去则会在 S3 付出真金白银的代价。而且它藏得深：用户看到的是回答，看不到塑造回答的那段话，所以提示词的问题往往最后一个被发现。

改提示词也是 Agent 开发中性价比最高的优化——不用训练、不用改代码，一段文本就能改变行为。它也是你唯一能"用自然语言给模型下精确指令"的地方，手写线后续所有行为设计（S4 的工具规则、S8 的技能引导）最终都落在系统提示词或它携带的消息上。这也是它值得单独一章的原因。

本章解决三件事：

  1. 系统提示词该怎么写——五条可操作的原则，每条配反例和正例；
  2. 环境信息（工作目录、操作系统、是否 Git 仓库）怎么优雅地注入——模板与代码分离；
  3. 渲染结果最终去了哪——messages[0]，以及为什么渲染完就要"冻结"它。

二、机制与原理

2.1 位置决定地位：messages[0]

系统提示词的特殊性首先来自位置。每次调用模型（S3 会讲，每次都要重传完整历史），它都排在数组第一位，模型对开头的注意力权重天然更高。把两者放一起看：

system 消息user 消息
谁写的应用开发者最终用户
在历史里的位置永远是第一条逐条追加
内容性质规则、设定、环境信息具体请求
用户可见性通常不可见就是用户自己打的字
调试方式单独打印出来读（本章的做法）翻聊天记录

注意最后一行。系统提示词是"看不见的指挥棒"，出问题时人们习惯怀疑模型能力或参数设置，很少先把它打印出来通读一遍。调试提示词的第一步永远是：把它原样打印出来，以模型的视角读它。 s02 脚本的第一节输出就是为此准备的。

一点诚实的保留：「训练时被重点对待」是社区与课件的经验性总结，各厂商并未公开训练细节；但「开头的指令对行为影响最大」这一判断在实践中稳定成立，按此对待不会吃亏。

也正因为它是 messages[0]，S3 讲的 prompt cache 前缀命中才与它直接相关：它是最长的那段公共前缀，缓存收益最大；反过来，一旦它变了，后面的所有缓存全部作废。这条线索先记住，S2 末尾和 S3 都会回到它。

2.2 编写五原则：反例 vs 正例

以下五条整理自《Agents底层逻辑》课程课件，核心思想一句话：系统提示词是给模型读的配置文件，不是给人看的说明文。逐条对照：

原则反例正例
① 精简118 字废话："你现在要充当一名专业代码顾问，接下来我会向你提出各种各样和编程相关的问题。希望你认真仔细地阅读……"30 字："你是代码顾问。精准解答编程问题，不懂直接说明，禁止编造信息。"
② 自洽"回答要详尽、覆盖多个角度" + "答案控制在 30 字以内"删掉一个，或明确优先级："先给 30 字结论，需要时再展开"
③ 全局约束"如果用户问安全问题就拒绝，如果问代码就写，如果……"（条件式规则）"除了回答编程问题，其他话题一律说明超出范围"（无条件精简）
④ 保持静态"现在是 {当前时间}，欢迎回来，{用户名}！"时间、用户名等动态量不进提示词；环境信息在启动时渲染一次并冻结
⑤ 结构化一大段散文，规则混在描述里Markdown 分层：## 角色 / ## 运行环境 / ## 行为规则

五原则的一句话记忆版：对模型行为没有约束力的删掉；互相打架的删掉一句；条件句改写成无条件句；每轮都变的不放进去；每条规则都给一个标题。

几条原则背后的道理值得多说一句：

  • ① 精简：不是字数越少越好，而是删掉不携带信息的话。"希望你认真仔细地阅读我每一次发送过来的内容"翻来覆去只有一个意思——认真读题，对模型没有任何额外约束力。礼貌用语和铺垫在消耗上下文窗口和注意力。上面 118 字 vs 30 字是 s02 脚本实测的字数，实测输出：
文本 / 输出
== 2. 系统提示词的「精简」反例 vs 正例（同一意图）==
反例（118 字）: 你现在要充当一名专业代码顾问，接下来我会向你提出各种各样和编程相关的问题。希望你…
正例（30 字）: 你是代码顾问。精准解答编程问题，不懂直接说明，禁止编造信息。

同一意图压缩近 4 倍，且正例反而多了一条反例没有的硬约束（"禁止编造信息"）——精简的正确姿势是删废话、留规则，不是删内容。

废话黑名单里的常客："希望你认真仔细地阅读"、"充分理解我的诉求"、"回答清晰易懂方便我理解"、"如果遇到不清楚的内容千万不要随意编造"——最后这条其实是好约束，但"禁止编造"四个字就够了。

  • ② 自洽：模型遇到矛盾指令不会报错，它会随机偏向其中一边——这次听"详尽"、下次听"30 字以内"，你得到的输出不稳定，却找不到原因。矛盾也未必是数字上的：一句"覆盖所有可能的边界情况"配一句"回答保持极简"同样是打架。排查方法还是那条：把提示词打印出来，用人类的眼睛找矛盾。
  • ③ 全局约束：条件式规则（"如果……就……"）教模型学会了找例外、钻空子。举个具体的例子：把"涉及爬虫先提醒合规风险、涉及调试先要报错信息、涉及部署先问目标环境……"写成五条 if，模型的注意力花在"匹配哪条"上，规则夹缝里的需求它就开始自由发挥。改成一句无条件的"动手写代码前，先用一句话说明潜在风险与前提假设"，遵从度反而更高。全局约束的检验标准：这条规则对任何一条输入都应该生效。
  • ④ 保持静态：这是五条里唯一带"钱"味的，机制在 S3 展开；但注意它是原则不是铁律，本节末尾专门讨论。
  • ⑤ 结构化：模型对 Markdown 小节标题的遵从度显著高于散文段落——标题就是给规则的"名字"，模型引用和执行带名字的规则更稳定。手写线的模板只有三个小节（角色 / 运行环境 / 行为规则），够用就好，不必为了结构化而结构化。

2.3 环境感知：模板 + 环境变量，启动时渲染一次

手写线的编码助手需要知道三件事：当前工作目录、操作系统、是否在 Git 仓库内。这些信息每台机器、每个目录都不同，不能硬编码；但它们在一次运行的整个生命周期里不变。把"环境信息怎么进上下文"的三种方案摆在一起，取舍就清楚了：

方案做法问题
硬编码提示词里写死"你运行在 Windows"换台机器就错，文案与代码耦合
每轮动态渲染每次调用前取一次 cwd / 时间拼进提示词提示词每轮都变，缓存永远 miss（见坑 1）
启动时渲染一次（本教程）模板占位 + 启动时采集渲染，之后冻结长会话中值可能过期（如中途 cd），代价可接受

这张表还藏着一个规律：信息变化越频繁，就越该远离系统提示词——写死的 < 启动时注入 < 根本不进提示词。每轮都变的信息只属于 history（S3）。

第三种方案的实现：模板 agent/prompt/system.j2 留占位符，环境部分长这样：

- 操作系统：{{ os }}
- Git 仓库：{{ "是" if is_git else "否" }}

顺带回答一个必然的疑问：为什么用 Jinja2，f"…{cwd}…" 拼接不行吗？技术上完全可行，但拼接把文案埋进 Python 源码——文案不能被不懂代码的人改，diff 混在代码提交里，review 也不直观。模板文件让提示词成为一个可以被独立查看、独立评审、独立版本管理的"配置物"，这在提示词要反复迭代的 Agent 项目里是实打实的工程收益。

渲染器 agent/prompt.py 值得看的是环境变量的采集与注入方式：

Python
# agent/prompt.py（节选）
def get_cwd() -> str:
    return os.getcwd()

def get_os() -> str:
    return platform.system()

def get_is_git() -> bool:
    """判断当前目录是否在 Git 仓库内（沙箱/无 git 环境返回 False）。"""
    try:
        result = subprocess.run(
            ["git", "rev-parse", "--is-inside-work-tree"],
            capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0 and result.stdout.strip() == "true"
    except Exception:
        return False


def render_prompt(name: str = "system", **extra) -> str:
    """渲染模板。内置环境变量 + 任意额外变量（如技能清单 skills）。"""
    env = Environment(loader=FileSystemLoader(_TEMPLATE_DIR), keep_trailing_newline=True)
    template = env.get_template(f"{name}.j2")
    return template.render(
        cwd=get_cwd(),
        os=get_os(),
        is_git=get_is_git(),
        **extra,
    )

get_is_git 是个好例子：环境检测本身可能失败（没装 git、目录不可读），失败时降级为 False而不是让启动崩溃——提示词里少一行"Git 仓库：否"，远比 Agent 起不来强。**extra 则让调用方可以塞进任意附加变量（比如 S8 的技能清单），模板引擎的扩展点就此留好。

最后是消费端（s02_system_prompt.py 节选）：渲染一次，注入 Session，之后所有调用自动携带：

2.5 迭代提示词的最小工作流

提示词是"代码"，改它也要有流程。最小工作流三步：

  1. 渲染检查：改完模板跑一遍渲染，打印结果通读——查结构、查占位符、查矛盾；
  2. 对照测试：固定一组有代表性的测试问题，改前改后各跑一遍，对比回答变化；
  3. 一次只改一处：提示词没有"断点调试"，同时改三条规则后行为变了，你无法归因到任何一条——小步快改，每步验证。

再把提示词当"配置物"发布：改动走 review、与代码同一个 PR 提交，让任何人都能看到"这次行为变化对应哪段文案改动"。

第 2 步不必展开成正式的评测体系，但它能拦住八成的"改完之后模型开始胡说"。这个最小工作流的失效点就是评测的起点：测试问题攒到几十条、需要打分标准的时候，你就进入了 evaluation 的领域——超出本教程范围，但流程思想不变。

所有这些动作背后的态度只有一句话：把提示词当代码对待——代码要测试、要 review、要小步提交，提示词同样如此。

四、常见坑与边界条件

坑 1：动态内容进系统提示词 = 每轮缓存 miss。 最典型的反例是把 datetime.now() 或登录用户名渲染进提示词。每次请求提示词都不同，意味着 S3 要讲的 prompt cache 前缀永远命不中——最长的那段公共前缀被你自己毁掉了，等于主动放弃服务商给的折扣。收到"值得进提示词"的动态值时，先过三问：它一次运行内变不变？变了影响模型行为吗？从请求侧传行不行？三问之后大多会发现它根本不该进提示词。正确做法：要么不进提示词（用户身份从请求侧传），要么接受"启动时渲染一次、运行期间冻结"的折中（如本章的环境信息）。

坑 2：提示词膨胀。 规则一条条往上加，三个月后系统提示词上万 token：每轮请求都在为它付费，模型开始"选择性失聪"（规则太多反而都不遵守），改一条规则的副作用也难以预估。膨胀通常不是一次发生的，而是每次线上出问题就"加一条规则堵漏"——只加不减的提示词必然膨胀。出路是渐进式披露：通用规则留在系统提示词，领域知识按需加载——手写线 S8 的技能机制（skills 变量 + load_skill 工具）就是为此预留的口子；框架线第 16 章讲的也是同一件事。

坑 3："保持静态"是原则，不是铁律。 环境信息（cwd、os）严格说也是"运行时的动态值"，但它一次运行内不变、且对 Agent 的每轮决策都有用（"在哪个目录执行命令"是行为依据），注入的收益大于缓存代价。判断标准是变化的频率：一次运行内不变的可以进；每轮都变的（时间戳、随机数、对话内容）坚决不进。原则服务于目标（省缓存、保稳定），不是服务于它自己。

坑 4：模板是代码，要按代码的标准对待。 {% if %} 写错、变量名拼错，Jinja2 默认渲染成空字符串而不是报错——提示词悄悄缺一块，你却毫无知觉。上线前三项快速自检：

  • 占位符与渲染调用逐一对应（模板里的每个 {{ x }} 都有实参）；
  • 每个 {% if %} 的两个分支都跑过一遍（有 skills / 无 skills）；
  • 渲染产物里搜一遍 {{ 和 {%，确认没有没被替换的残渣。

渲染结果要在启动时打印或断言检查（s02 的第 1 节输出就是干这个的），不要等到模型行为怪异了再回头查模板。

坑 5：system 消息只放一条，永远放在 messages[0]。 契约不禁止多条 system 消息，但不同服务对"多条 system"的处理并不一致（有的合并、有的只认第一条），行为不可移植。约定俗成的做法：一条 system、排在第一位。真需要"多层级指令"时，用一条 system 内部的 Markdown 小节分层，而不是多条消息。

五、关键结论

  1. 系统提示词是模型的出厂设置：messages[0] 的 system 消息，训练时被重点对待，决定模型行为的基线。
  2. 五原则：精简、自洽、全局约束、保持静态、结构化——反例的共同点是"对模型没有约束力或互相打架"。
  3. 环境感知的标准做法：模板留占位符（system.j2），启动时采集环境变量渲染一次（prompt.py），渲染结果作为 messages[0] 冻结。
  4. 模板与代码分离：改提示词不动代码，改环境采集不动模板；渲染结果启动时打印检查。
  5. 静态性的判断标准是变化频率：一次运行内不变的可注入，每轮都变的不进提示词。
  6. 提示词膨胀的解药是渐进式披露：通用规则常驻，领域知识按需加载（S8、框架线第 16 章）。
  7. 提示词是迭代出来的：渲染检查 → 对照测试 → 一次只改一处，和写代码一样讲流程。

本章要点回顾

  • 同一模型表现不同，第一嫌疑人是系统提示词；它在 messages[0]，每次请求重传，与 S3 的 prompt cache 直接相关。
  • 调试提示词第一步：把它原样打印出来，以模型的视角通读。
  • 精简：删掉对模型没有约束力的礼貌与铺垫（实测 118 字 → 30 字，语义不减且多出硬约束）。
  • 自洽：矛盾指令不会报错，只会让输出不稳定；全局约束：规则写成无条件短句，不给模型留例外空间。
  • 结构化：Markdown 小节（## 角色 / ## 运行环境 / ## 行为规则）优于散文。
  • 环境信息走 Jinja2 模板 + 启动时渲染一次；Deep Agents 的 base_system_prompt（框架线第 13 章）是同一骨架的加长版。
  • 三种环境注入方案里选"启动时渲染一次"：硬编码换机器就错，每轮渲染打穿缓存。
  • 信息变化越频繁，越该远离系统提示词：写死的 < 启动时注入 < 只进 history。
  • 迭代提示词三步：渲染检查 → 对照测试 → 一次只改一处。
  • 下一章 S3：渲染好的提示词要靠 Session 带着走——模型"失忆"的真相与两条会话纪律。

3会话：无状态模型上的记忆工程

说明

手写线第 3 章｜配套代码：code/s03_session.py｜配图：assets/h03_session_compare.svg

一、这一章要解决的问题

先做一个思想实验：你问模型"uv 是什么？"，它答了；紧接着你问"如何安装？"——模型回你一句"抱歉，你说的『如何安装』是指什么？"。

模型不是装的，它是真的不记得。HTTP 请求一发一收即告结束，服务端不为任何"对话"保留状态——你上一轮发过什么、它上一轮答过什么，模型服务一概不知。所谓"对话"，只是客户端把历史消息每次都重新塞进 messages 数组发过去，模型每次都是"第一次读到全文"。

这一点框架线第 3 章 2.1 节讲过原理（LangChain 的 memory / checkpointer 替你做了重传），但手写线的原则是自己实现一遍。理由与前两章一致：只有亲手维护过"每轮重传"这件事，你才能真正理解 token 账单的构成、prompt cache 为什么值钱、上下文窗口为什么会溢出——这些在框架里都被 MemorySaver 之类的名字遮住了。

顺带校准一个预期：这一章的代码量是三章里最小的（Session 类不过几十行），但它是唯一一处"写错了会直接烧钱"的地方——历史管理的每一条纪律都对应真金白银，值得慢读。

它也是手写线真正的分水岭：S1 的契约是"每次调用"的规则，本章的会话是"跨调用"的规则——从这里开始，我们写的东西才有了时间维度。

本章解决四件事：

  1. 用对照实验亲眼看到"失忆"与"续答"的差别；
  2. 理解每次调用重传完整历史——这就是 token 费用随轮次增长的原因；
  3. 写一个最小的 Session 类：消息历史 + JSON 持久化 + 行车记录仪；
  4. 记住两条会话纪律——它们直接决定你的账单和推理模型的质量。

这就是你的 token 账单随轮次线性增长的原因：每轮的输入 token ≈ 之前所有轮次的总量 + 本轮新增。对话内容越多、工具输出越长（S4 之后每个工具结果都是一大段），增速越猛。

粗算一下量级：假设一轮问答新增 500 token，到第 10 轮时，单次请求的输入已包含前 9 轮约 4500 token——同样的内容，你为它付了 10 次钱（命中缓存的前缀打折，未命中的全价）。

对短对话无所谓，对长对话很快变得昂贵。服务商为此提供 prompt cache：请求的前缀若与近期请求完全相同，命中部分按大幅折扣计价。而"前缀完全相同"这个条件，直接引出本章最重要的纪律（2.4 节）。

顺带解开一个常见的错觉：模型"越聊越进入状态"，不是它在学习，而是你的历史越来越长，它的"人设"越来越被 system 提示词和历史锁定——锁定它的材料，正是你每次重传的那些内容。

还有一件事你无法直接观测：缓存命中是服务商端计算的，你看不到命中率，只能从计费面板的平均单价间接推断。单价没有随轮次下降，多半是纪律①被违反了——这是 2.4 节的伏笔。

设计上有两点值得说。其一，直接用契约形状存消息：不定义 Message 类、不做序列化层，存进 messages 的 dict 与发给模型的 dict 是同一个东西，save 落盘的就是网络上传的 JSON——所见即所传，跨语言、跨进程读取零转换，省掉一整层转换 bug 的可能。其二，不引入持久化依赖：JSON 文件 + 系统临时目录，load 时用 cls.__new__ 跳过 __init__ 原样恢复——对教程而言"能存能取"就是持久化的全部需求；生产项目可以升级 SQLite / Redis，接口不变。

持久化方案也要知道边界：临时目录 + JSON 文件是单进程方案——两个进程同时写同一个会话文件会互相覆盖，且没有任何锁。个人 Agent 够用；多人或多进程场景请升级到数据库。

2.4 两条纪律（本章重点）

会话怎么管理历史，决定你的账单和模型质量。前两条写在 agent/session.py 的模块 docstring 里，是纪律不是建议。

纪律①：历史只追加、不修改。

服务商端 prompt cache 的命中逻辑是前缀匹配：本次请求的 messages 与缓存里的历史逐条比对，公共前缀命中折扣——匹配精确到 token，少一个字节都算 miss。把三种历史操作放在一起看后果：

历史操作前缀命中计费后果
末尾追加新消息旧前缀原封不动，命中正常折扣
中间插入/删除一条从改动处起全部错位后续轮次全价
修改某条消息内容同上后续轮次全价

手写线把 add_message 写成只 append，就是从接口层面杜绝误操作。框架线第 9 章的上下文工程（裁剪历史、压缩摘要）看似在"修改"历史——其实那些框架都把裁剪当成一次重建来处理，重建后的新序列从头重新累积缓存，代价要有意识地付。

常见的"我就是要改"场景——用户发现上一句话打错了：正确姿势不是回去改那条 user 消息，而是追加一条更正消息。历史是档案，不是草稿。

纪律②：上下文里保留思维链（reasoning_content）。

S1 讲过，思考模型的响应里带思考字段，_normalize_message 把它归一成 reasoning_content 存进历史。为什么不在回传历史时把它删掉、省点 token？因为对推理模型而言，上一轮的思考过程是本轮推理的上下文锚点——课件明确给出的最佳实践：丢了它，模型在后续轮次里的推理质量会下降。省一点输入 token，换来的是更差的回答，得不偿失。

边界说明：如果应用天然只有单轮请求（每问独立、无追问），reasoning 留不留影响不大；两条纪律都是为多轮 Agent 服务的。

质量下降的具体机制（模型把上一轮思考当"自己的记忆"来锚定推理方向）各厂商仍在探索，但工程结论已被课件与实践收敛：存下来，传回去——至于为什么有效，可以留给读者当课后问题。

两条纪律合起来就是 S2"保持静态"的会话版：系统提示词启动时冻结（S2），历史只追加（本章），共同保住那条最长可命中的缓存前缀。

2.5 前瞻：工具循环里的会话

S4 之后，"一轮对话"不再是一问一答：模型可能请求调工具，工具结果回灌后模型再答——一次用户输入对应多组追加（assistant(tool_calls) → tool → assistant）。会话层对此毫无感知：还是只追加。两条纪律在工具循环里同样成立，而且更关键——工具结果回灌的位置错一点，就是第四节坑 2 的 400 报错。

换句话说，S3 的抽象在 S4 之后不换血、只增量：会话层从今天起不再变化，后面所有章（工具、ReAct、Agent、MCP、子代理）都是往这份只追加的历史里放形状合法的新消息——Session 的 API 到此定型，再没改过。

            json.dump(
                {"id": self.id, "tools": self.tools, "messages": self.messages},
                f, ensure_ascii=False, indent=2,
            )
        return path

    @classmethod
    def load(cls, path: str) -> "Session":
        data = json.load(open(path, encoding="utf-8"))
        session = cls.__new__(cls)
        session.id = data["id"]
        session.tools = data.get("tools", [])
        session.messages = data.get("messages", [])
        return session

行车记录仪 print_friendly——排障时最常用的方法：

Python
# agent/session.py（节选）
    def print_friendly(self) -> None:
        """人类可读的会话概览（截断长文本）。"""
        print(f"=== 会话 {self.id[:8]}…（{len(self.messages)} 条消息）===")
        for m in self.messages:
            role = m.get("role", "?")
            head = {"system": "[系统]", "user": "[用户]", "tool": "[工具]"}.get(role, "[助手]")
            if m.get("tool_calls"):
                calls = ", ".join(tc["function"]["name"] for tc in m["tool_calls"])
                print(f"{head} 请求调用工具: {calls}")
                continue
            text = m.get("content")
            if role == "tool":
                text = (text or "").replace("\n", " ")
                print(f"{head}({m.get('name', '')}) {text[:80]}{'…' if len(text) > 80 else ''}")
            elif text:
                text = str(text).replace("\n", " ")
                print(f"{head} {text[:80]}{'…' if len(text) > 80 else ''}")
            else:
                print(f"{head}（无文本内容）")

注意它对四类消息的区别处理：带 tool_calls 的 assistant 消息只打印工具名（参数往往一大坨），tool 消息标注来源工具名并截断到 80 字符——截断是为了"概览"，完整内容永远在 messages 里。

load 用 cls.__new__ 跳过 __init__ 是刻意的：走构造函数会重新生成 id、重新注入 system_prompt，与文件里的状态冲突。反序列化的黄金法则——从数据重建，不重新初始化。

示例脚本 s03_session.py 的对照组部分——两个独立 Session 与同一 Session，各调两次：

Python
# s03_session.py（节选）
# 对照组 A：两个独立 Session
model = Model(client=make_client())

a.add_message({"role": "user", "content": "uv 是什么？"})

# 对照组 B：同一 Session
model2 = Model(client=make_client())

model2.invoke(s, stream=True)

注意 Model.invoke（S1 见过）会自动把响应 message add_message 进 session——调用即追加，历史因此始终是完整的，调用方无须手工维护 assistant 回复。

还有一个容易忽略的实验设计：对照组 A 和 B 各自 make_client() 造了一个剧本完全相同的新 client，保证两组实验除了"历史有无"之外一切相同——控制变量，结论才干净。

四、常见坑与边界条件

坑 1：在历史中间插入/删除消息。 比如想"悄悄修正"用户的某句口误、删掉一段不想要的对话再继续——缓存前缀从改动处起全部失效，之后每一轮都付全价。另外服务商缓存还有 TTL（分钟级），间隔太久本来也会 miss，改历史只是让 miss 从"偶发"变"必然"。确需裁剪历史时，按"一次重建"处理并接受缓存重建成本（框架线第 9 章）。

坑 2：tool 消息必须紧跟对应的 assistant(tool_calls) 消息。 这是契约的硬性校验：模型请求调工具（finish_reason="tool_calls"），下一个 message 必须是带匹配 tool_call_id 的 tool 消息，否则 API 直接报 400。中间隔了别的消息、或把 tool 消息发给了别的会话，都会触发。遇到 400 先数消息顺序：tool 消息前面是不是紧挨着带 tool_calls 的 assistant。这也是为什么工具循环里"回灌"必须发生在下一次 invoke 之前——S4 的循环骨架会反复用到这一点。

坑 3：会话文件比想象的大。 save 把 tools Schema 也一起存了——工具定义动辄几 KB，工具多了会话文件体积可观。更隐蔽的是 messages 里长文本（大段代码、工具输出）会原样落盘，reasoning_content（模型的内部草稿）也一并随消息落盘。会话文件含完整对话与 Schema，不要把它当日志分享——里面可能有敏感信息。

坑 4：上下文窗口溢出。 只追加不删除 + 每次全量重传，历史迟早超过模型的上下文窗口上限，API 直接拒绝请求。这不是"万一"，是只追加策略的必然终点——区别只是来得早还是来得晚（工具输出会大幅加速）。应对手段（截断、摘要压缩、把长内容外置到文件）属于上下文工程，框架线第 9 章有系统讨论，原理篇 docs/harness/ 有对应实现细节；S8 的渐进式披露也是同一问题域的解法。手写线在这一章只负责"诚实地溢出"，让你先见到问题。

五、关键结论

  1. 模型服务无状态：所有"记忆"都是客户端重传历史制造的假象；失忆 = messages 里没带历史。
  2. 每次调用重传完整历史（实测 1 条 → 3 条），token 费用随轮次线性增长，prompt cache 是服务商给的折扣机制。
  3. Session = messages + tools + 持久化：JSON 直存契约形状，load 原样恢复；print_friendly 用来核对模型实际看到的历史。
  4. 纪律①：历史只追加、不修改——修改破坏前缀命中，让后续所有轮次全价计费。
  5. 纪律②：保留 reasoning_content——思维链是推理模型后续轮次的上下文锚点，删了省小钱、亏大质量。
  6. 调用即追加：Model.invoke 自动把响应写回 session，历史完整性由模型层保证。
  7. 历史是档案不是草稿：发现打错话，追加更正消息，不要回头修改。
  8. 会话文件是契约的镜像：里面就是发给模型的 JSON，看它 = 看模型看到的。

本章要点回顾

  • 模型每次都是"第一次读到全文"：会话状态完全由客户端的 messages 数组承载。
  • 对照实验：两个独立 Session 第二问失忆，同一 Session 第二问续答——唯一变量是历史。
  • token 账单随轮次增长是重传机制的直接后果；S2 的静态系统提示词 + 本章的只追加历史，共同保住最长可命中前缀。
  • Session.add_message 只追加；save/load 用系统临时目录存取 JSON（路径与 id 随运行变化）；print_friendly 是排障第一入口。
  • tool 消息必须紧跟对应的 assistant(tool_calls)，顺序错位 API 报 400。
  • 上下文溢出是只追加策略的必然终点，解法见框架线第 9 章与 docs/harness/。
  • 工具循环是"多组追加"，会话层与两条纪律原样适用（S4）。
  • 命中率不可见，只能从计费单价间接推断；单价异常先查是否违反纪律①。
  • 下一章 S4：历史里出现 tool_calls 之后该干什么——工具调用与回灌循环。

4tools：让模型「点菜」，你来「做菜」

一、这一章要解决的问题

前三章里，模型已经能稳定地「说话」了：我们调它，它回一段文本。但把目光从聊天框挪到你真正的开发需求上，问题立刻暴露——

模型只会输出文本。让它读一个文件？它做不到。执行一条命令？它做不到。联网搜索、查数据库、调用你公司内部 API？统统做不到。它唯一的能力是把 token 排列成文字。你遇到的是一个天堑：语言能力在云上，执行能力在你机器上，中间没有任何通道。

tool calling（工具调用）就是这座唯一的桥。它的思想朴素得惊人：模型说不出结果没关系，它可以请求结果——「如果有人能帮我执行 write_file，参数是这些……」。而执行这件事，由你的代码完成。

这一章把这座桥拆开给你看：不封装、不抽象，用最裸的方式手拼一次完整的 tool calling。看清楚裸流程之后，S5 的封装才不是魔法，S6 的循环才不是黑盒。

一句话先剧透整个机制：模型只「点菜」，从不下厨——它返回的只是一张写着菜名和配料的订单，真正把菜做出来的始终是你的代码。

二、机制与原理

2.1 裸流程五步

tool calling 的完整流程只有五步，一步都省不掉：

步骤谁来做做什么
① 定义函数你写普通的 Python 函数，模型看不见函数体，只看得见 Schema
② 上报 Schema你把工具的 JSON Schema 放进请求的 tools 字段
③ 返回 tool_calls模型「点菜」：返回工具名 + JSON 参数字符串，不执行
④ 执行你客户端（你的代码）按名字找到函数、校验参数、真正调用
⑤ 回填你结果以 role=tool 消息追加进上下文，再调一次模型

图 h4 画的就是这五步的流转：

为什么模型不直接执行？不是厂商偷懒，而是职责边界：模型在云端，你的函数、文件系统、数据库在你机器上。云端进程根本摸不到你的磁盘。这个「分工」是刻意的——它同时意味着：执行与否、怎么执行、执行失败怎么办，决定权全部在你手里。理解了这一点，后面所有设计（校验、异常兜底、权限确认）才有位置可放。

2.2 JSON Schema：模型选工具的唯一依据

第 ② 步里塞进 tools 字段的东西，长这样（摘自 s04_tools.py）：

Python
tools = [
    {
        "type": "function",
        "function": {
            "name": "write_file",
            "description": "写入文件",
            "parameters": {
                "type": "object",
                "properties": {
                    "filepath": {"type": "string",
                                 "description": "文件的绝对路径，或相对于cwd的路径"},
                    "content": {"type": "string",
                                "description": "要写入的内容，该内容会完全覆盖文件原本内容"},
                },
                "required": ["filepath", "content"],
            },
        },
    },
]

逐字段拆解：

字段作用备注
type: "function"工具类型当前 OpenAI 契约基本只有这一种
function.name工具名模型「点菜」时报的菜名，必须唯一
function.description工具描述模型决定选不选它的唯一依据
parameters.type参数容器固定 object
parameters.properties各参数的类型与说明描述写得越清楚，模型填参越准
parameters.required必填参数列表缺了这些参数的调用可直接拒绝

要特别强调 description 的分量。模型看不到你的函数体，看不到 with open(...) 那几行代码，它对工具的全部认知就是 Schema 里的文字。description 写「写入文件」和写「要写入的内容会完全覆盖文件原本内容」，模型的行为差异是实实在在的——前者模型可能以为追加，后者模型知道要重写。对模型来说，Schema 不是接口文档，它就是工具本身。

2.3 模型侧视角：tools 变成了「追加在系统提示词里的类型签名」

「点菜」这个比喻还有一层更底层的解释。厂商收到带 tools 的请求后，并不是把 JSON Schema 原样塞给底层模型——而是把它转成 TypeScript 风格的类型签名，追加在系统提示词的末尾。以 Qwen 系列为例，翻译之后大致长这样：

文本 / 输出
<|im_start|>system
...系统提示词...

    # Tools

    namespace functions {

    // 写入文件
    type write_file = (_: {
    // 要写入的内容，该内容会完全覆盖文件原本内容
    content: string,
    }) => any;

    } // namespace functions
<|im_end|>

所以从模型自己的视角看，它并没有调用什么「工具接口」——它只是在一段很长的提示词里读到了一些「可用函数的签名」，然后在生成文本时写出了类似 {"name": "write_file", "arguments": {...}} 的标记。厂商的推理服务解析出这个标记，包装成响应里的 tool_calls 字段返回给你。

「点菜」由此而来：模型读到菜单（Schema），写下一张订单（tool_calls）。订单是文本，菜没人做。下厨永远是客户端的事。

2.4 回填：role=tool 消息的格式

第 ⑤ 步的回填消息是契约里约定死的形状，四个字段一个不能少：

Python
session.messages.append({
    "role": "tool",            # 消息角色：工具结果
    "tool_call_id": tc["id"],  # 与请求配对的凭据
    "name": tc["function"]["name"],  # 工具名（冗余，便于排查）
    "content": "已写入文件",    # 结果正文——必须是字符串
})

注意两点：tool_call_id 是模型发出的调用与你的执行结果之间的配对凭据，对不上号直接 API 报错（2.4 节的坑里细说）；content 必须是字符串——就算你的工具返回 dict、返回数字，也要先转成字符串再回填。

3.3 手动执行：原始做法及其四个问题

从消息里抠出菜名和参数，用 globals().get 找到函数（agent-core 课件里的原始做法）：

if callable(func):
    arguments = json.loads(tc["function"]["arguments"])
    func(**arguments)

完整的消息链：user → assistant(tool_calls) → tool → assistant(content)。模型「说不出但能要到」的结果，就这样经由一张订单、一次执行、一条回填消息，最终融进了它的回答里。

四、常见坑与边界条件

坑一：arguments 忘了 json.loads。 模型返回的参数永远是 JSON 字符串。直接 tc["function"]["arguments"]["filepath"] 会得到 TypeError: string indices must be integers。同理，自己构造响应的测试代码（如本教程的 FakeClient）也要记得 json.dumps 回去，保持形状一致。

坑二：tool_call_id 配不上，直接 API 报错。 每条 role=tool 消息必须携带上一条 assistant 消息里对应调用的 id。如果手动构造消息时 id 写错、写丢，或者回填了两个 tool 消息却只对应一个调用，下一次请求会被服务端以 4xx 拒绝。id 是契约级的配对凭据，不是可有可无的备注。

坑三：执行了工具却忘了回填，再调模型 → 报错。 只要上一条 assistant 消息带 tool_calls，服务端就要求接下来紧跟配对的 role=tool 消息。执行完函数直接 model.invoke()，等于告诉服务端「我点了菜但没上菜」——请求直接被拒。反过来，「没有 tool_calls 却塞了 tool 消息」同样是非法序列。

坑四：一次 tool_calls 可以包含多个调用——每个都要有对应的 tool 消息。 模型可以并行点菜：一条 assistant 消息里同时出现 read_file 和 get_time 两个调用（id 分别是 call_1、call_2）。执行端必须逐个执行、逐条回填，两条 role=tool 消息各带各的 tool_call_id。漏掉任何一条，下一次请求报错。这也是 S5 里 registry.invoke 返回列表而不是单个结果的原因。

边界：content 必须是字符串。 你的工具返回 dict？返回 None？回填前一律 str() 或序列化。json.dumps(result, ensure_ascii=False) 是最常用的选择——既保住结构信息，又满足契约。

边界：模型可能「先说后点」。 content 与 tool_calls 可以在同一条 assistant 消息里并存——模型先解释一句「我需要先读一下文件」，再点菜。不要假设二者互斥。

五、关键结论

  1. tool calling 是模型连接真实世界的唯一桥梁，它的分工原则是：模型只「点菜」（返回 tool_calls），执行永远是客户端的事。
  2. 裸流程五步：定义函数 → 上报 Schema → 模型返回 tool_calls → 客户端执行 → role=tool 回填再调。五步缺一不可，顺序不可乱。
  3. Schema 就是模型的全部工具认知。description 不是注释，是模型选工具的唯一依据，值得认真写。
  4. 模型侧的实现真相：tools 被厂商转成类型签名追加进系统提示词，tool_calls 本质是模型生成的文本标记。
  5. finish_reason=tool_calls 与 role=tool 回填、tool_call_id 配对、arguments 为 JSON 字符串——这四件事构成了 tool calling 的契约骨架，记牢它们，后面所有框架的工具机制都能一眼看穿。
  6. globals().get 的原始做法暴露了四个问题（查找范围受限、静默失败、无校验、异常炸），每一个都指向同一个方向：这层苦力活该封装。

本章要点回顾

  • 模型只能输出文本，tool calling 是它「请求执行」的唯一通道：模型点菜，你来做菜。
  • 请求侧：tools 字段携带 JSON Schema，name/description/parameters 各司其职，description 决定模型选不选。
  • 响应侧：finish_reason=tool_calls + tool_calls[]（id + name + arguments 字符串）。
  • 执行侧：json.loads 参数 → 调函数 → 以 role=tool（tool_call_id 配对、content 为字符串）回填 → 再调模型。
  • 一次可能多个调用并行，回填必须一一对应、一条不缺。
  • globals().get 原始做法的四个雷，是 S5 封装（@tool 装饰器 + Pydantic 校验 + 注册表）的全部动机。下一章，把苦力活全部自动化。

5封装 tools：把苦力活交给 inspect + Pydantic

一、这一章要解决的问题

上一章我们手拼了一次完整的 tool calling，五步流程每一步都是手动档：Schema 一行一行写、函数按名字在 globals() 里捞、参数不校验、异常直接炸。跑通一次没问题，但它离「能用的工程代码」差得远——

把 S4 的四个雷换算成日常成本：每加一个工具，你要同步维护两份东西（函数 + Schema），人肉保证名字、参数、类型一致；模型点错菜（传错参数、点了不存在的工具），你要么静默吞掉要么程序爆炸；错误信息回不到模型那里，Agent 永远学不会自我修正。

这一章的目标是用一个装饰器把全部苦力活自动化。先看最终形态——定义一个工具的全部工作量：

    with open(filepath, "r", encoding="utf-8") as f:

2.1 核心机制一：create_params_model

这是整个封装里最「巧」的一步（摘自 agent/tool/core.py）：

Python
def create_params_model(func, param_descriptions=None) -> type[BaseModel]:
    param_descriptions = param_descriptions or {}
    fields: dict[str, tuple] = {}
    for name, param in inspect.signature(func).parameters.items():
        py_type = param.annotation if param.annotation is not inspect.Parameter.empty else Any
        desc = param_descriptions.get(name, "")
        if param.default is inspect.Parameter.empty:
            fields[name] = (py_type, Field(description=desc))          # 必填
        else:
            fields[name] = (py_type, Field(default=param.default, description=desc))  # 可选
    return create_model(f"{func.__name__}_params", **fields)

信息来源一共有三处，全部来自你已经写过的东西：

Schema 里的字段信息来源
参数类型 type: string函数签名的类型注解（filepath: str）
必填 / 可选（required）有没有默认值（encoding="utf-8" → 可选）
参数 description装饰器关键字参数（@tool(filepath="...")）

inspect.signature 把函数签名解析成参数列表；pydantic.create_model 按这些信息现场造一个 Pydantic 模型类。Pydantic 模型天生自带 model_json_schema()，JSON Schema 就白送了——不需要任何手写。

2.2 核心机制二：Tool 类——校验、执行、异常兜底

Tool 把函数包起来，提供两个行为（摘自 agent/tool/core.py）：

Python
def schema(self) -> dict:
    param_schema = self.param_model.model_json_schema()
    # ...组装成 OpenAI function calling 格式...
    return {
        "type": "function",
        "function": {
            "name": self.name,
            "description": self.description,      # 来自 docstring
            "parameters": { "type": "object", "properties": properties,
                            "required": param_schema.get("required", []) },
        },
    }

def __call__(self, **kwargs) -> str:
    try:
        validated = self.param_model(**kwargs)    # 校验 + 类型转换
        kwargs = validated.model_dump()
        return str(self.func(**kwargs))           # 统一返回字符串
    except Exception:
        return "".join(traceback.format_exception(*sys.exc_info())).rstrip()

三处设计值得停下来想：

  1. schema() 的产出与 S4 手写的形状完全一致。type/description/parameters/required 一个不缺——封装没有改变契约，只是自动化了契约的生产。
  2. __call__ 先校验再执行。模型传来的参数先过 Pydantic 模型这一关，类型不对、缺必填项，在真正的函数被调用之前就拦下来。
  3. 异常不外抛，返回完整堆栈文本。这是最反直觉也最关键的一条：工具出错时，Tool.__call__ 把整个 traceback 格式化成字符串返回。为什么？因为模型看得见错误，才能自我修正——它传错了路径，下一轮看到 FileNotFoundError: no such file: xxx，就会换个路径重试。S4 里「异常直接炸」和「静默失败」的两难，被这第三条路化解了。这是 Agent 容错体系的基石。

2.3 核心机制三：ToolRegistry——调度中心

注册表只有三个方法（摘自 agent/tool/__init__.py）：

Python
class ToolRegistry:
    def register(self, tool: Tool) -> Tool:
        self._tools[tool.name] = tool
        return tool

    def schemas(self) -> list[dict]:
        return [t.schema() for t in self._tools.values()]   # 出：给 session.tools

    def invoke(self, message: dict) -> list[dict] | None:
        tool_calls = message.get("tool_calls") or []
        if not tool_calls:
            return None                                    # ← 没有点菜
        # ...逐个查表、json.loads、执行、包装成 role=tool 消息...

invoke 内置了 S4 手动执行的所有兜底，逐个 tool_call 处理的完整逻辑（摘自 agent/tool/__init__.py）：

Python
def invoke(self, message: dict) -> list[dict] | None:
    tool_calls = message.get("tool_calls") or []
    if not tool_calls:
        return None                                    # ← 没有点菜
    results = []
    for tc in tool_calls:
        name = tc["function"]["name"]
        try:
            args = json.loads(tc["function"]["arguments"] or "{}")
        except json.JSONDecodeError:
            args = None
        tool = self._tools.get(name)
        if args is None:
            result = f"错误：arguments 不是合法 JSON：{...!r}"
        elif tool is None:
            result = f"错误：没有名为 {name} 的工具，请检查工具名拼写"
        else:
            result = tool(**args)                      # 走 Tool.__call__
        results.append({"role": "tool", "tool_call_id": tc["id"],
                        "name": name, "content": result})
    return results

invoke 把 S4 的四个雷逐一排掉：查表不限于 globals()（雷 1）；工具不存在返回错误文本而非静默跳过（雷 2）；参数先过 Tool.__call__ 的 Pydantic 校验（雷 3）；任何异常都被 Tool.__call__ 兜住转成文本（雷 4）。

特别注意 invoke 的返回值设计：没有 tool_calls 时返回 None。这个 None 不是边角处理，它是 S6 ReAct 循环的终止信号——「模型不再点菜 = 任务完成」。这里是伏笔，下一章兑现。

2.4 对照框架线第 7 章

这套封装思想在 LangChain 里有工业化版本。框架线第 7 章讲过：@tool 装饰器同样从函数名、docstring、类型注解自动推断 Schema，并提供覆盖口（自定义名字、描述、args_schema）；底层是 StructuredTool，执行时通过 ToolRuntime 注入运行时上下文。差别只在工程化程度：我们的手写版少了覆盖口和运行时注入，但「函数即工具、注解即 Schema、装饰器收集元信息」的核心思想一模一样。

四、常见坑与边界条件

坑一：忘写 docstring → description 为空 → 模型不选它。 Tool.__init__ 里 inspect.getdoc(func) or ""，没有 docstring 就得到空描述。Schema 里 description 为空的工具，模型几乎无法判断它是干嘛的，表现通常是永远不选它，或者乱选。定义工具时把 docstring 当作必需品。

坑二：参数没写类型注解 → Any → Schema 弱化。 create_params_model 对没有注解的参数回退到 Any，生成的 Schema 里没有 type 字段。模型失去类型约束，传参自由发挥，校验也拦不住（Pydantic 对 Any 什么都放行）。给每个参数写注解，是工具质量的下限。

坑三：Pydantic 默认 lax 模式的类型转换边界。 Pydantic v2 默认模式是宽容的："123" 能转成 int，123 能转成 str 吗？实测不能（见 3.2 节的 string_type 错误）。数组和自定义类型的转换规则更复杂。不要依赖隐式转换——模型传什么就是什么，类型声明写准才是正道。

坑四：返回值统一 str()，dict 返回值要先序列化。 Tool.__call__ 最后一行是 str(self.func(**kwargs))。如果你的工具返回 dict，str() 会得到 Python 字面量（单引号、True/False 大写），模型勉强能读但不规范；更好的做法是在函数内部就 json.dumps(result, ensure_ascii=False) 再返回。工具返回值永远面向模型阅读，字符串化是最后防线。

坑五：registry 是全局单例。 整个进程共享一个注册表（agent/tool/__init__.py 末尾 registry = ToolRegistry()）。两个含义：注册顺序影响 schemas() 的顺序（dict 保持插入序，实测 ['read_file', 'write_file'] 就是注册顺序），后注册的同名工具直接覆盖先注册的（self._tools[tool.name] = tool，无警告）。多次 import 或测试中重复注册时要心里有数；需要隔离时，另建一个 ToolRegistry() 实例即可。

坑六：注册顺序与 Schema 顺序会影响模型选择。 schemas() 按注册序输出，工具越多、越相似，排在前面的越容易被模型优先考虑。把最核心的工具先 register，是零成本的引导手段。

边界：MCP 工具不走 Pydantic。 Tool.from_mcp 直接采用服务器返回的 inputSchema，跳过本地建模（工具名规范为 server__tool 防冲突）。这条路径在 S9 展开，此处只需知道：schema() 和 __call__ 对两种来源一视同仁。

五、关键结论

  1. 封装目标：定义工具 = 写一个带 docstring 和类型注解的普通函数 + 装饰器注明参数含义，其余全自动。
  2. create_params_model：inspect.signature 提取签名，pydantic.create_model 动态建模——类型来自注解、必填/可选来自默认值、描述来自装饰器，JSON Schema 白送。
  3. Tool 类：schema() 产出 OpenAI 格式（契约不变，只是自动化）；__call__ 先校验再执行；异常不外抛而是返回堆栈文本——模型看得见错误才能自我修正，这是 Agent 容错的关键设计。
  4. ToolRegistry：register/schemas/invoke 三方法；invoke 把「非法 JSON、未知工具」都转成错误文本进上下文；没有 tool_calls 返回 None——这是 S6 循环的终止信号。
  5. 与框架线第 7 章 LangChain 的 @tool 同源同构：函数即工具、注解即 Schema，工业版只是多了覆盖口和运行时注入。
  6. 定义工具的三条纪律：docstring 必写、类型注解必写、返回值必字符串化。

本章要点回顾

  • 目标 API 形态：@tool(参数描述...) + docstring = 完整工具定义。
  • 流水线三件套：create_params_model（签名 → Pydantic → Schema）、Tool（校验 + 异常兜底）、ToolRegistry（注册 + 调度）。
  • 异常转文本是设计而非妥协：错误回给模型，模型自我修正，进程不炸。
  • registry.invoke 返回值语义：有调用 → role=tool 消息列表；没调用 → None（记住这个 None）。
  • 三个坑对应三条纪律：docstring、类型注解、返回值序列化。
  • Schema 自动化的思想与框架线第 7 章 LangChain @tool 一脉相承。
  • 单次工具调用已经封装完毕，但「读文件 → 加工 → 写回」这种多步任务怎么办？下一章 S6，把五步流程跑成一个循环。

6ReAct：把五步流程跑成循环，Agent 的心脏

一、这一章要解决的问题

S4、S5 已经把一次工具调用打磨得足够好了：模型点菜，registry.invoke 做菜并回填。但很多任务一次调用根本做不完——「读这个文件，总结要点，把摘要写回去」至少要三步：读文件 →（模型加工）→ 写文件 →（模型汇报）。每一步执行完，都得把结果交给模型看一眼、再决定下一步。手动写五步流程写三轮？代码会膨胀成一坨复制粘贴。

答案是显而易见的：循环。执行完工具就再调一次模型，模型还要点菜就再做，直到它不再点菜为止。这个「思考 → 行动 → 观察 → 再思考」的交替结构，就是 2022 年论文《ReAct: Synergizing Reasoning and Acting in Language Models》提出的模式，也是今天几乎所有 Agent 框架（LangChain、LangGraph、DeepAgents）的内核。

对照一下两个规模的任务，差距一目了然：

任务需要几次模型调用靠什么完成
「新建一个 uv.md 写入教程」2 次（点菜、汇报）S4 的五步手动流程
「读 notes.txt、总结、把摘要写回 summary.txt」3 次起步，每次之间夹工具执行循环
「排查这个报错并修复」不可预知，可能十几次循环 + 护栏

任务一在 S4 里是写死的两段代码：第一次 invoke、手动执行、回填、第二次 invoke。任务二如果把这套流程手写三遍，代码就是复制粘贴；任务三根本没法手写——你不知道要几轮，只有模型每次看完结果才知道。所以唯一的出路是把「调模型 → 执行 → 回填」包进循环，把「什么时候停」交给一个判断条件。

这一章做三件事：先把事件系统竖起来（模型调用过程的实时广播），再手写一个最小 ReAct 循环（你会发现全部秘密就几行 while True），最后跑一个真实的多步任务看完整轨迹。

二、机制与原理

2.1 ReAct 循环：全部秘密就这么几行

先给结论。图 h6 是 ReAct 循环的完整形状：

循环本体（摘自 s06_react.py）：

Python
rounds = 0
while True:
    rounds += 1
    model2.invoke(session, stream=True)          # 调模型
    call_msg = registry.invoke(session.messages[-1])  # 有 tool_calls 就执行
    if call_msg is None:
        break                                    # 模型不再点菜：任务完成
    session.messages.extend(call_msg)            # 回填 tool 消息
    print(f"第 {rounds} 轮：执行 {', '.join(m['name'] for m in call_msg)}")

print(f"循环共 {rounds} 轮结束")

值得留意的是循环之外还有什么：循环前只有两行准备——session.tools = registry.schemas()（把工具 Schema 交给 session，S5 的产出）和一条用户消息；循环后没有任何收尾代码，因为每一轮里 invoke 和 extend 已经把上下文维护完整了。循环没有自己的状态，全部状态都在 session.messages 里——这是上下文即状态的最直接体现。

对照 S4 的五步流程：① 定义函数（S5 已完成）和 ② 上报 Schema（session.tools 已绑定）是循环外的准备；③④⑤ ——调模型、执行、回填——就是循环体内的三行。Agent 的「智能」全部来自模型，循环只负责把「点菜-做菜-上菜」自动化地转下去，直到模型不再点菜。

终止条件只有一个：registry.invoke 返回 None（S5 埋的伏笔在这里兑现）。这个 None 语义极其干净——它不是超时、不是出错，而是模型用行为表明「我不需要工具了」。

2.2 事件系统：三通道广播

循环要能观察、能调试、能接 UI，就得看见模型调用过程的每一步。agent/events.py 用一个极简的发布-订阅实现（摘自 agent/events.py）：

Python
class Event:
    REASONING_START = "reasoning_start"; REASONING = "reasoning"; REASONING_END = "reasoning_end"
    CONTENT_START = "content_start";     CONTENT   = "content";    CONTENT_END   = "content_end"
    TOOL_CALL_START = "tool_call_start"; TOOL_CALL = "tool_call";  TOOL_CALL_END = "tool_call_end"
    COMPLETE = "complete"

class EventEmitter:
    def on(self, event: str, callback: Callable) -> None:
        self._handlers[event].append(callback)

    def emit(self, event: str, **data) -> None:
        for callback in list(self._handlers[event]):
            callback(event, **data)

事件按三条通道组织，各配 START / 正文 / END 三个阶段，外加一个总的 COMPLETE：

通道事件对应内容
思考reasoning_start / reasoning / reasoning_end思考型模型的思维链
正文content_start / content / content_end面向用户的回答文本
工具tool_call_start / tool_call / tool_call_end工具调用的名字与参数
收尾complete本次调用结束，携带拼装完成的完整 message

前三组各管一条流式通道，COMPLETE 则是总收尾——无论走了哪条通道，它都最后触发，并把归一化后的 message 一并带出。

Model 继承 EventEmitter，调用过程中把三条通道的内容以事件广播出去。为什么模型层要发事件？ 三个理由：

  1. 展示逻辑与调用逻辑解耦。Model 不需要知道有谁在听：打印器、日志、UI、计费统计，任何组件 model.on(...) 接入即可，模型层一行代码不用改。
  2. 可观测性的地基。S3 的 print_friendly 只能看静态消息序列；事件流能看到过程——模型什么时候在思考、思考了多久、什么时候切到点菜。没有事件，流式调用的内部就是黑盒。
  3. 一次实现，处处受益。事件在装配器解析 chunk 时发出，监听器拿到的是实时片段：做「打字机效果」的 UI 只需要监听 content 事件，做工具调用提醒只需要监听 tool_call 事件。

EventEmitter 本体只有十行，但它划出的边界很重要：事件是广播，不是回调地狱——发布者不知道订阅者存在，这正是发布-订阅模式的价值。S7 的 Agent 打印器就挂在这套事件上。

流结束时 _finalize 收口：未关闭的通道补发 END 事件，三条通道各自累积的内容拼成与非流式 message 完全一致的归一化 dict（摘自 agent/model.py）：

Python
def _finalize(self) -> dict:
    # ...补发 reasoning/content/tool 通道的 END 事件...
    message: dict = {"role": "assistant", "content": "".join(self.content) or None}
    if self.reasoning:
        message["reasoning_content"] = "".join(self.reasoning)
    if self.tool_calls:
        message["tool_calls"] = [self.tool_calls[i] for i in sorted(self.tool_calls)]
    self._emit(Event.COMPLETE, message=message)
    return message

两个关键设计：

思考通道结束的判定。流式响应不会显式告诉你「思考完了」，装配器用两条启发式规则：同一个 chunk 里既出现 reasoning 又出现 content/tool_calls（混合）；或后续 chunk 出现了 content/tool_calls（更常见）。此时立即补发 reasoning_end，切换通道。

tool_calls 的 arguments 跨 chunk 分片拼接。这是流式 tool calling 最容易踩的坑：arguments 不是一次给全的，它被拆成若干片（甚至工具名一片、参数前半一片、后半一片），分散在多个 chunk 里，靠 index 标识归属、靠字符串拼接复原。consume() 结束后拼出来的 message，与非流式响应的形状完全一致——上层代码（包括 ReAct 循环）感知不到流式与非流式的差别。

3.3 事件与循环的关系

把 3.1 的事件视角和 3.2 的循环视角叠起来看：循环的每一轮 = 一次 model.invoke = 一串事件。三轮任务里两种轮型的对比：

轮型事件序列循环里的走向
点菜轮（第 1、2 轮）reasoning_start → … → tool_call_endinvoke 返回 tool_calls → 执行 → 回填 → 下一轮
收工轮（第 3 轮）content_start → content × n → content_end → completeregistry.invoke 返回 None → break

第 1 轮的事件序列是「思考 + 点菜」型（如 3.1 实测），第 3 轮则是纯 content 通道。事件系统让每轮内部纤毫毕现，循环让轮与轮之间自动衔接——两层视图合起来，才是 Agent 运行时的完整图景。

这也是为什么事件系统要做成与循环解耦的旁路：循环代码三行，事件监听可有可无、想接就接——打印、日志、计费、UI 各自独立演进，谁也不影响谁。

还有一层实用价值：事件流是活体的，轨迹是事后的。调试「Agent 卡住了」这类问题时，看事件流能立刻分辨是模型在长思考、还是在等工具执行、还是循环本身出了 bug——三种情况的处理路径完全不同。

四、常见坑与边界条件

坑一：没有 max_turns 的死循环。 终止条件「模型不再点菜」依赖模型行为，而模型可能陷入怪圈：反复读同一个文件、反复用同样的错误参数调用工具、或者永远「再确认一下」。真跑一次就知道这种事不罕见——工具返回的错误文本没有给出模型能理解的修正线索时，模型常常原样重试。本教程的循环是教学极简版，生产实现必须加 max_turns 轮数上限——超过就强制退出并告知模型。S7 会把这个护栏加进 Agent 类。

坑二：模型先「说」后「点菜」，content 与 tool_calls 并存。 一条 assistant 消息里可以同时有 content（「我先读一下这个文件」）和 tool_calls。两个推论：处理消息时不要假设二者互斥；展示层要明白这个 content 是给用户看的说明，不是最终回答——最终回答是后续某轮不再点菜时的 content。对应到事件上，就是一次调用里 content 通道和工具通道先后都有事件。

坑三：多工具并行调用，id 一一对应。 一轮里模型可能同时点两道菜（tool_calls 数组里有多个调用，id 各不相同），执行后必须每个调用回填一条 role=tool 消息，tool_call_id 一一对应。S5 的 registry.invoke 返回列表、循环里用 extend 而不是 append，都是这个原因；漏回填一条，下一次请求直接 4xx。

坑四：工具结果不回填就退出循环 → 上下文残缺。 常见于初学者提前 break：模型刚点完菜（assistant 消息带 tool_calls）就退出循环或保存会话。这份上下文里有一条「悬空的订单」——下次继续对话时，服务端会要求紧跟配对的 tool 消息，直接报错。要么执行并回填，要么在退出前把这条调用标记为已取消并补一条说明性的 tool 消息。 正确的退出时机只有 registry.invoke 返回 None 之后——那时最后一条消息是纯 content，上下文是自洽的。

边界：流式与非流式的 arguments 形状一致。 只要装配器把分片拼对了，循环代码不需要感知 stream 开关。反过来，如果你自己手写流式解析，忘了按 index 拼接 arguments，拿到的就是半截 JSON，json.loads 必炸——这是 S4 坑一在流式场景下的进阶版。FakeClient 的流式模拟特意把 arguments 拆成「id+name → 参数前半 → 参数后半」三片，就是为了在离线环境复现这个坑。

边界：思考通道不是所有模型都有。 非思考型模型的响应里没有 reasoning_content，事件序列里整条思考通道不会出现——第一件事就是 content_start 而不是 reasoning_start。监听器不要假设思考事件一定先到。

五、关键结论

  1. ReAct = Reasoning + Acting：模型在循环里交替思考、调工具、看结果，直到不再请求工具；一次工具调用解决不了的多步任务，循环补齐。
  2. 循环的全部秘密就几行 while True：调模型 → 执行 tool_calls → 回填 → 再调。智能在模型，循环只是自动化的「点菜-做菜-上菜」传送带。
  3. 终止条件唯一：registry.invoke 返回 None = 模型不再点菜 = 任务完成。但裸循环没有护栏，死循环风险真实存在，max_turns 必不可少（S7 兑现）。
  4. 事件系统是可观测性的地基：三通道（reasoning/content/tool_call）× START/正文/END + COMPLETE，EventEmitter 极简发布-订阅，展示逻辑与调用逻辑解耦。
  5. 流式装配器逐 chunk 消费：三通道各自累积、边解析边发事件；思考通道结束靠「同 chunk 混合或后续 chunk 出现 content/tool_calls」判定；arguments 跨 chunk 分片按 index 拼接——流式 tool calling 最容易踩的坑。
  6. 实测轨迹验证了整个闭环：三轮循环、六条消息、文件真实落盘——Agent 没有任何超出「模型 + 循环 + 工具」之外的魔法。
  7. 上下文即状态：循环没有私有记忆，历史只追加、思维链保留两条纪律在循环里自然成立；轨迹回放是调试 Agent 的第一手段。

本章要点回顾

  • 多步任务需要循环；ReAct 就是「思考 → 行动 → 观察」交替到模型不再点菜为止。
  • 循环三行核心：invoke → registry.invoke → 回填；None 即终点。
  • 事件三通道 × 三阶段 + COMPLETE；on/emit 十行实现，价值在于解耦与可观测。
  • _StreamAssembler：通道切换判定 + arguments 按 index 分片拼接，最终 message 与非流式形状一致。
  • 事件序列实测：reasoning_start → reasoning ×2 → reasoning_end → tool_call_start → tool_call → tool_call_end，无 content 事件（只点菜不说话）。
  • 实测轨迹：3 轮循环、6 条消息、summary.txt 真实落盘——第 3 轮模型不再点菜，registry.invoke 返回 None，循环收工。
  • 四个坑：死循环要 max_turns、content 与 tool_calls 可并存、并行调用 id 一一对应、退出前别留悬空订单。
  • 两条边界：流式与非流式的 message 形状一致（分片拼接是前提）；思考通道并非所有模型都有，监听器别假设它先到。
  • 至此，模型契约（S1）、系统提示词（S2）、会话（S3）、工具（S4/S5）、循环（S6）全部就位——下一章 S7 把它们装配成一个真正的 Agent 类。

7Agent：把循环装进盒子，让过程可观测

一、这一章要解决的问题

S6 里我们已经把 ReAct 循环跑通了：调模型 → 请求工具 → 执行 → 回灌 → 再调模型，直到模型给出最终回答。但回头审视那段代码，它是一个脚本，不是组件——

  • 不可复用：换一个模型客户端、换一组工具，就得复制粘贴整个循环再改一遍；
  • 不可配置：系统提示词、会话状态、工具清单全部硬编码在脚本里，组装方式没有收敛到一个入口；
  • 不可观测：过程信息靠散落的 print 输出，想换成写日志、渲染到 UI、按 token 计费，就得改动循环本身。

一句话概括这一章要做的事：把模型、会话、工具、监听器组装成一个可直接对话、可复用、可观测的东西。这个东西就是 Agent。

先给一个结论定调：Agent 不是新协议、不是新算法，它就是一个装进盒子里的 while 循环。盒子的价值不在循环本身（S6 已经证明循环只有几行），而在于：

维度S6 的手写脚本S7 的 Agent 组件
组装方式代码里逐个拼Agent(...) 一个构造入口
复用复制粘贴一个类，任意实例化
过程观测散落的 print监听器订阅事件流
死循环防护没有max_turns 安全阀
工具注册手工罗列registry 统一管理

那么什么时候该把脚本升级成 Agent？一个实用的判断表：

现状判断
循环只跑一次、场景单一脚本够用，别急着抽象
需要在多个入口（CLI / 服务 / 测试）复用同一套对话逻辑该封装了
需要观测过程（调试、计费、审计）该封装了——先竖事件通道
模型可能陷入工具调用循环该封装了——安全阀放进组件里，别靠人盯着

2.3 invoke：与 S6 手写版逐行对照

再看循环本体（摘自 agent/agent.py）：

Python
def invoke(self, query: str) -> list[InvokeResult]:
    self.session.add_message({"role": "user", "content": query})
    results: list[InvokeResult] = []
    for _ in range(self.max_turns):
        resp = self.model.invoke(self.session, stream=True)
        results.append(resp)
        tool_results = registry.invoke(self.session.messages[-1])
        if tool_results is None:
            return results          # 模型不再请求工具：任务完成
        self.session.messages.extend(tool_results)
    print(f"[Agent] 已达最大轮次 {self.max_turns}，强制停止。", file=sys.stderr)
    return results

与 S6 的手写循环对照，逻辑完全同构，只有两处差异：

差异点S6 手写版S7 Agent
循环上限while True 靠人眼盯着for _ in range(self.max_turns)
超限行为不存在打 stderr 警告，返回已得结果

max_turns 为什么返回而不抛异常？因为超限不等于失败：模型可能已经完成了大部分工作，只是没来得及收尾。把已产出的消息和结果还给调用方，调用方可以自行决定是续跑、换提示词还是报错；抛异常则会把这些中间状态全部丢掉。这也是为什么警告走 stderr——它是一条运维信号，不是任务结果的一部分，不应该污染正常输出流。

再把 3.1 节那次实测任务放进循环里逐轮追踪，看清状态如何流转（与 3.2 节的五条消息一一对应）：

轮次循环动作会话状态变化
进入前add_message(user)系统提示词 + 用户消息（2 条）
第 1 轮model.invoke → 请求 web_search追加助手消息（3 条）
第 1 轮registry.invoke → 执行工具追加 tool 消息（4 条）

每一轮的分支只有两个：模型点菜（继续）或模型答复（终止）。所谓编排，就是维护这张状态表不出错。

2.4 监听器模式：可观测性的地基

观测能力来自三层极简机制。先是事件总线（摘自 agent/events.py）：

Python
class EventEmitter:
    def on(self, event: str, callback: Callable) -> None:
        self._handlers[event].append(callback)

    def emit(self, event: str, **data) -> None:
        for callback in list(self._handlers[event]):
            callback(event, **data)

模型层在流式调用中沿三条通道（思考 / 正文 / 工具调用）发事件，外加一个 complete 收尾事件。监听器基类则一次性订阅全部事件（摘自 agent/listener.py）：

Python
class ModelListener:
    def listen(self, model) -> None:
        for event in ALL_EVENTS:
            model.on(event, self._handler)

    def _handler(self, event: str, **data) -> None:
        raise NotImplementedError

子类只需要实现 _handler。ModelPrinterListener（agent/printer.py）就是一个约 40 行的实现：把 content 事件翻译成流式正文打印，把 tool_call_end 翻译成 调用工具: xxx 一行。事件全集在 S6 的 2.2 节已列成表——三条通道（思考/正文/工具调用）各配 START/正文/END，外加 complete，共十个事件名；ModelListener.listen 把它们一次性全部订阅，子类在 _handler 里按事件名分发即可。

解耦的价值在这里具象化：打印、日志、UI 渲染、token 计费，全都是不同的 ModelListener 子类；给 Agent 换一种观测方式，模型层零改动。反过来，模型层只在「发事件」这一个动作上付出成本，不知道也不关心谁在听。

几个典型的监听器形态，感受一下同一个接口能长出多少种东西：

监听器_handler 里做什么
ModelPrinterListener流式打印思考/正文，工具调用打一行
日志监听器把事件序列化写进日志文件/日志服务
UI 监听器推送到前端（WebSocket / SSE），渲染打字机效果
计费监听器在 complete 事件里累计 usage token
审计监听器记录每次工具调用的参数与返回，供事后回放

这也是 S9 MCP 要做的事：把这个「可替换」标准化成协议。

四、常见坑与边界条件

四个坑都来自实测代码本身，按「症状 → 根因 → 解法」整理。

坑 1：监听器回调异常会沿 emit 传播，中断整个模型调用。

  • 症状：某个监听器抛异常，整个 invoke 直接崩掉，报错栈里却找不到模型层的错。
  • 根因：EventEmitter.emit 对回调没有任何保护（见 2.4 节代码），异常沿 emit → 模型层 → invoke 循环一路穿透。本教学实现刻意未隔离，让你看清事件链路。
  • 解法：生产实现必须在 emit 里对每个回调 try/except——观测组件的故障不应该杀死业务调用。最少要打日志并继续调用下一个监听器。

坑 2：全局 registry 的注册顺序影响 schemas 顺序。

  • 症状：同样的问题，两次运行模型选了不同的工具。
  • 根因：Agent.__init__ 里工具清单来自 registry.schemas()，而 schema 列表的顺序就是注册顺序。模型看到的工具顺序受此影响（先看到的工具在概率上更容易被选中）。
  • 解法：先注册高频核心工具，再做批量注册；保持注册顺序确定，行为才可复现。

坑 3：auto_builtin 的重复注册是覆盖语义。

  • 症状：你自定义的 read_file 行为悄悄变了。
  • 根因：registry 的 register 对同名工具是覆盖而非报错。创建两个 Agent、或先手动注册再让 Agent 自动注册同名内置工具，后者会无声顶掉前者。
  • 解法：给自定义工具起不同的名字；或传 auto_builtin=False 关掉自动注册，显式控制工具集。排查「我的工具怎么行为变了」时先查注册顺序。

坑 4：system_prompt 缺省渲染依赖 cwd。

  • 症状：模型拿着错误的路径调 read_file，返回「文件不存在」。
  • 根因：缺省系统提示词会把创建 Agent 时的当前工作目录注入「运行环境」节（见 3.2 实测输出）。如果脚本先 os.chdir() 再创建 Agent，注入的就是 chdir 后的目录——工具的工作路径与提示词声明不一致。
  • 解法：要么显式传 system_prompt，要么保证创建 Agent 之后再 chdir。

五、关键结论

  1. Agent = 装进盒子的 while 循环。循环本体只有十行（2.3 节），组件化的收益全部来自组装入口、配置面与事件旁路。
  2. 可观测性靠监听器，不靠 print。事件总线 + ModelListener 让打印/日志/UI/计费成为可插拔的外围组件，模型层零改动。
  3. max_turns 返回而非抛异常：超限时保住中间状态，把「下一步怎么办」的决定权交给调用方。
  4. 这个约 200 行的 Agent 与框架线第 5 章 create_agent 的循环是同一件事——框架的价值在中间件与持久化，不在循环本身。理解了这一章，框架线第 15 章的架构图对你就是「换了名字的旧相识」。
  5. 循环里唯一的新钩子是 skills 参数——它通向 S8 的渐进式披露，下一章展开。

本章要点回顾

  • Agent 解决的是 S6 遗留的三个问题：不可复用、不可配置、不可观测。
  • 分层架构：编排层（Agent）→ 模型层（Model）/ 会话层（Session）/ 工具层（registry）→ 监听层（listener），底座是 EventEmitter 事件总线，分层与《Agents底层逻辑》课件第 21 章同构。
  • __init__ 四步组装：建模型挂监听 → 注册内置工具 → 可选注册 load_skill → 渲染提示词建 Session。
  • invoke 与 S6 同构，新增 max_turns 安全阀；超限返回结果并打 stderr，不抛异常。
  • 监听器模式：ModelListener 订阅全部事件，ModelPrinterListener 把事件流翻译成终端输出；解耦让观测方式可插拔。
  • 实测确认三件事：两行终端输出对应两次模型调用；print_friendly 回放完整五消息轨迹；max_turns=3 在模型死循环时以消息数 8 强制收场。

8Skill：提示词按需加载，没命中几乎零成本

一、这一章要解决的问题

写过大一点的 Agent 系统你就会发现提示词膨胀（prompt bloat）：

  • 智能客服要把产品手册、退换货规则写进系统提示词；
  • 数据分析 Agent 要把指标口径、SQL 规范写进系统提示词；
  • 天气播报 Agent 要把播报格式、着装建议规范写进系统提示词……

这些内容有个共同特征：只在特定场景才用得上。用户十次提问里九次不问天气，可天气播报规范每一轮都躺在系统提示词里——每一轮都在为它付费，占上下文窗口，还稀释模型对真正相关指令的注意力。

直观的解法是「需要时再给」：模型用到时才把指引读进上下文。问题是，模型怎么知道「存在这份指引」？又怎么「读」它？

S8 的答案叫 Skill（技能），核心机制叫渐进式披露（progressive disclosure）：

阶段时机注入内容代价
一启动时每个技能的 name + description（几十 token）几乎为零
二模型判断需要时该技能的 SKILL.md 全文才付全文代价

没命中几乎零成本，命中才付全文价格——这就是 Skill 相对「全塞进系统提示词」的本质优势。

把三种候选解法摆在一起，Skill 的位置就清楚了：

解法思路问题
全塞进系统提示词一劳永逸，模型永远「知道」每轮付费、稀释注意力（本节的问题）
运行时检索（RAG）按相似度检索片段注入引入向量库与切分工程；指引类内容短小完整，检索收益低
Skill（本节）清单常驻，全文按需只多一个工具往返；机制零新意

指引类内容的特点是短小、完整、触发条件明确（「用户问天气时」）——恰好不适合检索、恰好适合「清单 + 按名加载」。

二、机制与原理

2.1 渐进式披露的两阶段

阶段一：启动时只交「目录」。SkillRegistry 扫描技能目录下的每个 <name>/SKILL.md，只解析头部 frontmatter，把 name + description 交给 Agent 渲染进系统提示词的「可用技能」节。每个技能在上下文里只占几十 token，模型由此知道「有哪些技能、分别在什么场景用」。

阶段二：命中才读「全文」。模型判断用户需求与某个技能相关时，调用 load_skill 工具（Agent 在组装时自动注册，见 S7 的 2.2 节），工具返回 SKILL.md 全文。此时技能的操作指引才进入上下文，模型按指引执行任务。

两个阶段的接力点是一个普通的工具调用——没有任何新机制，Skill 是用「工具 + 提示词」这两个旧零件拼出来的新能力。

有人会问：为什么不让模型「自己读文件」？因为模型不能主动发起任何动作（S4 的核心事实）：它只能发出工具调用请求，由宿主执行后把结果回灌。所以「需要时才读」必须落成一个工具——load_skill 就是为此而生的。同时，模型必须先知道「有哪些文件可读」，这只能靠启动时注入清单——两阶段机制是被模型的被动性逼出来的，不是拍脑袋的设计。

2.2 SKILL.md 格式与 frontmatter 解析

先看技能目录的组织形式——一个技能 = 一个目录 + 一个 SKILL.md：

文本 / 输出
skills/
├── text-summary/
│   └── SKILL.md
└── weather-report/
    └── SKILL.md

一个技能就是一个目录加一个文件。看实测用的天气技能（skills/weather-report/SKILL.md）：

markdown
---
name: weather-report
description: 天气查询场景的工作指引：如何调用天气工具、如何组织回答
---

# 天气查询技能

## 步骤
1. 从用户消息中提取城市名；没有城市时先反问。
2. 调用 get_weather 工具（参数 city），获取天气数据。
3. 用一句话播报：城市 + 温度 + 天气现象 + 一条着装建议。

## 规则
- 工具返回的数据不得修改；查不到的城市明确说查不到，禁止编造。
- 回答不超过两句话。

头部是 YAML frontmatter（name / description 两行），正文是给模型看的操作指引。解析器是手写的（摘自 agent/skill.py）：

Python
def parse_frontmatter(text: str) -> dict:
    """只支持简单的 key: value 行（够 SKILL.md 用），不引入 PyYAML。"""
    meta: dict[str, str] = {}
    if not text.startswith("---"):
        return meta
    for line in text.split("\n")[1:]:
        if line.strip() == "---":
            break
        if ":" in line:
            key, _, value = line.partition(":")
            meta[key.strip()] = value.strip()
    return meta

不引 PyYAML 的取舍：frontmatter 只需要两个标量字段，13 行手写解析就够了；省一个依赖，也让「披露的入口只有几十 token」这件事看得见摸得着。代价是脆弱性——缩进、多行值、引号转义都不支持，见第四节坑 1。

2.3 技能注册表与 load_skill 工具

SkillRegistry 的三个方法正好对应三个角色：

方法角色返回内容
scan()启动时扫描目录解析每个 SKILL.md 的 frontmatter
list_skills()供系统提示词渲染只有 name + description 的清单
load(name)供 load_skill 工具调用SKILL.md 全文

load_skill 工具本身由工厂函数生成（摘自 agent/skill.py）：

Python
def make_load_skill_tool(skills: SkillRegistry):
    @tool(name="要加载的技能名，来自系统提示词中的可用技能清单")
    def load_skill(name: str) -> str:
        """读取一个技能的完整说明（SKILL.md 全文），按说明执行该领域的任务"""
        return skills.load(name)
    return load_skill

工具描述里明确写了「按说明执行该领域的任务」——这句话是在告诉模型：拿到的不是数据，是操作规程。与 S7 对照：Agent 的 __init__ 只要发现 skills 参数非空，就自动把这个工具注册进 registry，再让 render_prompt 把 list_skills() 的结果写进「可用技能」节。组装逻辑在 S7 已经讲过，这里看到的是它的第一次实战。

还有一个容易被忽略的细节——load 对不存在的技能名的容错（摘自 agent/skill.py）：

Python
def load(self, name: str) -> str:
    skill = self._skills.get(name)
    if skill is None:
        return f"错误：没有名为 {name} 的技能。可用技能：{', '.join(self._skills) or '无'}"
    with open(skill["path"], encoding="utf-8") as f:
        return f.read()

返回的是一段错误提示文本（列出可用技能），而不是抛异常。为什么？因为这条错误会作为 tool 消息回灌给模型——模型读到「可用技能：text-summary, weather-report」后可以自己纠正重试。把错误设计成模型可读、可行动的文本，是工具设计的基本功（S4 的 isError 思路在这里的延续）。

2.4 与框架线的对照

框架线第 16 章的 SkillsMiddleware 是同一机制的工程化版本，逐项对照：

全塞系统提示词全文几百 token × 每轮0几万 token
Skill清单几十 token × 每轮命中轮付一次全文清单总账 + 5 次全文

差距随「非命中轮占比」放大——指引越专业、场景越窄，Skill 省得越多。反过来，如果一个指引几乎每轮都会命中，Skill 的两段式反而多付清单钱，直接写进系统提示词更划算。机制没有优劣，只有与使用频率的匹配度。

四、常见坑与边界条件

坑 1：手写 frontmatter 解析的脆弱性。2.2 节的解析器只认 key: value 单行：缩进、多行值（YAML 的 | 块）、引号转义一概不支持。如果 description 里写冒号后跟复杂结构，解析结果会静默出错（不报错，但字段内容不对）。症状很隐蔽：技能扫描得到但 description 缺胳膊少腿，模型命中率莫名下降。解法：技能字段保持「一行一个简单值」，需要复杂结构时放正文而不是 frontmatter；对格式要求高的团队直接上 PyYAML，代价只是多一个依赖。

坑 2：description 写不好 → 模型永不命中。description 是模型决定是否 load_skill 的唯一依据。写得含糊（「处理一些事情」）或与用户的措辞不重叠（用户说「退货」而描述写「售后流程」），模型就可能永远不触发加载——而且不会有任何报错，技能安静地躺在这里，仿佛不存在。解法：写 description 时问自己，用户会用什么词提出这个场景的请求？ 把这些词写进去；上线后用真实问法做回归测试。

坑 3：技能指引引用了不存在的工具。SKILL.md 里写「调用 get_weather 工具」，但组装 Agent 时忘了注册 get_weather——模型会忠实地尝试调用，然后收到「未知工具」错误，整个流程卡死或退化成编造。技能与工具要配套交付：技能目录与工具注册属于同一个功能包，拆开发布就会踩这个坑。解法：在 SKILL.md 开头列出本技能依赖的工具，组装时逐项核对；测试技能时故意断开工具，确认失败路径可控。

坑 4：技能全文加载后常驻上下文。load_skill 返回的全文会作为 tool 消息留在会话历史里，没有卸载机制——长会话中多个技能全文累积，膨胀问题会换个形式回来：单轮省的钱，被长会话慢慢吃回去。这是本实现的刻意取舍（保持机制简单）。解法：生产系统可以用会话裁剪（框架线第 16 章的中间件有相关钩子）定期清理过期的技能消息；或在技能指引末尾提示模型「任务完成后无需再参考本指引」，为裁剪创造语义空间。

五、关键结论

  1. Skill 解决提示词膨胀：特定场景才需要的指引，不该让所有轮次买单。
  2. 渐进式披露两阶段：启动时注入 name + description（几十 token），命中时才经 load_skill 加载全文——没命中几乎零成本。
  3. 机制零新意：技能 = 目录约定（SKILL.md）+ 清单注入（提示词）+ 按需加载（工具），全是 S1–S7 的旧零件；两阶段设计是被「模型不能主动发起动作」逼出来的。
  4. 错误要设计成模型可读的文本：load 不存在的技能返回「错误 + 可用技能清单」，模型能自己纠正重试。
  5. description 是命中率的一切，技能引用的工具必须配套注册，全文常驻上下文是本实现的已知取舍。
  6. 机制没有优劣，只有与使用频率的匹配度：几乎每轮命中的指引直接写进系统提示词，场景越窄 Skill 越划算。
  7. 与框架线第 16 章 SkillsMiddleware 同机制；SKILL.md 格式是公共技能生态（skills.sh 等）的通用货币。S9 会看到另一条工具来源——MCP，届时两者定位之别会非常清晰。

本章要点回顾

  • 问题：提示词膨胀——场景性指引每轮付费；解法：渐进式披露，没命中几乎零成本，命中才付全文代价。
  • 阶段一：SkillRegistry.scan() 解析 frontmatter，list_skills() 注入系统提示词「可用技能」节；阶段二：模型调 load_skill 工具拿 SKILL.md 全文。
  • 两阶段设计是被模型的被动性逼出来的：模型不能主动读文件，只能通过工具往返；也必须先有清单才知道该调哪个工具。
  • SKILL.md = YAML frontmatter（name/description）+ 正文指引；parse_frontmatter 手写 13 行解析，不引 PyYAML。
  • 实测走通三轮往返：load_skill → get_weather → 按技能规范播报（-8°C，晴，西北风3级，着装建议）；对照组无技能无工具，模型只能空泛或编造。
  • Agent 侧零新增机制：S7 的 skills 参数自动注册 load_skill 并渲染清单。
  • load 对不存在的技能返回「错误 + 可用技能清单」，模型可自纠——错误要设计成模型可读的文本。
  • 四个坑：frontmatter 解析脆弱、description 决定命中率、技能与工具必须配套、全文常驻无卸载。
  • 一句话带走：清单解决「知道有」，全文解决「知道怎么做」，而命中与否，取决于 description 里有没有用户的词。

9MCP：把工具来源标准化，一次实现两头复用

一、这一章要解决的问题

S7 的工具跑在自己进程里，S8 的技能写在本地目录里——它们都只在「我这个 Agent」里可用。设想一个更大的图景：

  • M 个应用（编码助手、客服机器人、数据分析平台……）都想接工具；
  • N 个工具提供者（搜索服务、文件系统、日历、数据库……）都想被接入。

没有标准时，这是 M×N 集成问题：每一对「应用 × 提供者」都要单独写接入代码，M=10、N=10 就是一百份胶水代码，且各自漂移、无人维护。

MCP（Model Context Protocol，模型上下文协议）的解法是把「Agent 与工具提供者」的通信标准化：

  • 提供者实现一次 Server，任何 MCP 客户端都能用它；
  • 应用实现一次 Client，任何 MCP 服务器都能接入；

M×N 塌缩成 M + N。一次实现，两头复用。

什么信号说明你需要 MCP 了？对照这张表：

现状判断
工具全在自己进程里，一个 Agent 用S7 的 registry 够用，别上协议
想用别人写好的工具服务器（搜索、数据库、浏览器……）需要 Client
想让自己的工具被任意 Agent 使用需要 Server
两种都要（多数平台的终态）两端都实现——本章正好两端都手写

这一章我们手写协议的两端：一个约 130 行的 stdio 服务器、一个同步的客户端封装，再把 MCP 工具注册进 S7 的 Agent——目标是让你看到：协议内核小到可以徒手实现。

二、机制与原理

2.1 协议内核：角色、传输、消息

概念内容本教程的实现
角色Client = Agent 侧；Server = 工具提供者agent/mcp/client.py / mcp_servers/time_server.py
传输stdio（本地子进程）或 HTTP（远程）手写 stdio 版；HTTP 留作练习
消息格式JSON-RPC 2.0：{jsonrpc, id, method, params}一行一条 JSON，无帧头、无魔法

JSON-RPC 2.0 请求长这样：

json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "add", "arguments": {"a": 123, "b": 456}}}

id 有值的是请求（需要响应），没有 id 的是通知（不需要响应）。stdio 传输下每个消息就是一行文本——stdout 是协议通道，stderr 才是日志通道，这条纪律后面会反复出现。

JSON-RPC 2.0 的消息一共四种形态，MCP 全用得上：

形态识别特征例子
请求有 id + method{"jsonrpc":"2.0","id":1,"method":"tools/list"}
成功响应有 id + result{"jsonrpc":"2.0","id":1,"result":{"tools":[…]}}
错误响应有 id + error{"jsonrpc":"2.0","id":9,"error":{"code":-32601,"message":"未知方法 …"}}
通知有 method、无 id{"jsonrpc":"2.0","method":"notifications/initialized"}

双方靠 id 配对请求与响应：客户端发出带 id 的请求后，读到 id 相同的行才算收到答案。理解了这张表，后面服务端与客户端的每一行代码都只是在实现它。

2.2 三步协议

MCP 服务器的全部协议义务只有三步（握手 → 发现 → 调用）：

  1. initialize 握手：客户端声明自己的 protocolVersion、capabilities、clientInfo；服务器回应自己支持的版本、能力与 serverInfo。双方由此确认「我们说的是同一种方言」。
  2. notifications/initialized：客户端发一条通知（无 id、无响应），宣告初始化完成。
  3. tools/list 与 tools/call：客户端拉取工具清单（每项含 name / description / inputSchema），随后按名调用，取回 content 文本。

注意 inputSchema 是服务器给的——客户端不需要知道工具的参数怎么定义，照单转述给模型即可。工具的「自我描述」集中在服务器一端，这正是标准化带来的分工。

为什么三步就够、不能再省？握手解决「方言对不对」（版本协商），发现解决「有什么可调」（模型需要 schema 才能点菜，这是 S4 定下的契约），调用解决「怎么调」。三步各对应一个不可省略的问题——协议设计的下限不是「越少越好」，而是「每个字段都有存在的理由」。

2.3 手写服务器走读

mcp_servers/time_server.py 全文约 130 行，主干三段。主循环（摘自 time_server.py）：

Python
def main() -> None:
    print(f"[{SERVER_INFO['name']}] 已启动，等待请求", file=sys.stderr)
    for line in sys.stdin:                       # stdin 逐行读
        line = line.strip()
        if not line:
            continue
        try:
            request = json.loads(line)
        except json.JSONDecodeError:
            print(f"[{SERVER_INFO['name']}] 非法 JSON 行已忽略", file=sys.stderr)
            continue
        response = handle(request)               # 分发处理
        if response is not None:
            sys.stdout.write(json.dumps(response, ensure_ascii=False) + "\n")
            sys.stdout.flush()                   # stdout 逐行写，记得 flush

分发函数 handle() 是一个 if 链：initialize 返回版本与能力；tools/list 返回 TOOLS 表；tools/call 按名执行并包成 {"content": [{"type": "text", "text": ...}]}；未知方法返回 JSON-RPC 错误码 -32601。TOOLS 表里 add 工具的声明长这样（摘自 time_server.py）：

Python
{
    "name": "add",
    "description": "计算两个整数的和（确定性工具，用于验证协议）",
    "inputSchema": {
        "type": "object",
        "properties": {
            "a": {"type": "integer", "description": "第一个整数"},
            "b": {"type": "integer", "description": "第二个整数"},
        },
        "required": ["a", "b"],
    },
}

这份 inputSchema 与 S5 里 @tool 装饰器生成的 schema 形状完全一致（JSON Schema 的 type: object）——所以它才能被 Tool.from_mcp 原样转发给模型。工具调用这条契约从 S4 一路贯穿到 S9，没有变过。

tools/call 的执行分支也值得看一眼——错误被包成带 isError 的正常响应而不是 JSON-RPC error：

Python
try:
    ...
    return _result(req_id, {"content": [{"type": "text", "text": text}]})
except TypeError as e:
    return _result(req_id, {
        "content": [{"type": "text", "text": f"参数错误：{e}"}],
        "isError": True,
    })

区分两级错误：协议错误（方法不存在、JSON 不合法）走 JSON-RPC error；业务错误（参数不对、工具执行失败）走 isError 标记的正常响应。前者是「我们没说同一种话」，后者是「话说明白了，但事情没办成」——模型的参数填错了该重试，通道坏了该重连，不能混为一谈。

日志纪律：所有运行信息（启动提示、非法行警告）一律走 stderr——如果混进 stdout，客户端会把日志当协议消息解析，JSON 解析立刻失败，整个通道错乱。json.JSONDecodeError 时选择「忽略脏行继续」而不是崩溃，也是对脏环境的容忍。

两个工具的设计意图：get_current_time 返回动态结果（时间随运行变化），add 返回确定性结果（123 + 456 = 579 永远不变）。一个验证「协议活着」，一个可精确复现——写协议示例时，确定性工具是验证的金标准。

2.4 传输层走读：StdioRpc 与 id 配对

客户端传输层 agent/mcp/jsonrpc.py 的核心是 request() 的读循环（摘自 jsonrpc.py）：

Python
def request(self, method: str, params: dict | None = None) -> dict:
    req_id = uuid.uuid4().hex[:8]
    self._send({"jsonrpc": "2.0", "id": req_id, "method": method, ...})
    while True:
        line = self.proc.stdout.readline()
        if not line:
            raise RpcError(-32000, "服务器提前退出（stdout 已关闭）")
        line = line.strip()
        if not line:
            continue
        try:
            msg = json.loads(line)
        except json.JSONDecodeError:
            continue                      # 不是 JSON 的行（脏输出）忽略
        if msg.get("id") == req_id:
            if "error" in msg:
                raise RpcError(...)       # JSON-RPC 错误 → 异常
            return msg.get("result", {})
        # 其他消息（服务器主动通知等）忽略

三处防御性设计，每处对应一种真实世界里的脏情况：

设计防的是什么
脏行 continue 忽略服务器日志/调试输出混进 stdout
id 不匹配的行忽略服务器主动通知、迟到的旧响应
readline 返回空 → 报错子进程崩溃，stdout 关闭，避免死等

也要看到这个教学实现的边界：readline 是阻塞读、没有超时——服务器卡死时客户端会永远等下去。生产实现必须加超时与并发读（官方 SDK 用 asyncio 解决，见第四节坑 3）。子进程生命周期也很朴素：close() 关掉 stdin，服务器以 stdin EOF 为退出信号——「写完关灯」，协议之外的第三个约定。

2.5 Agent 接入：协议抹平工具来源

客户端封装 MCPClient（摘自 agent/mcp/client.py）把三步协议打包：

def register_tools(self, registry) -> list[Tool]:
    tools: list[Tool] = []
    for server_name, infos in self.list_tools().items():
        for info in infos:
            call_fn = self._make_call_fn(server_name, info["name"])
            tools.append(registry.register(
                Tool.from_mcp(server_name, info, call_fn)))
    return tools

配套的 Tool.from_mcp（摘自 agent/tool/core.py）做了两件关键的事：

Python
tool.name = f"{server_name}__{info['name']}"   # time__add：防跨服务器同名冲突
tool._external_schema = {
    "type": "function",
    "function": {
        "name": tool.name,
        "parameters": info.get("input_schema") or {...},  # 直接用服务器给的

}
  • 命名规范 server__tool：两个服务器都有 search 工具时不会互相覆盖；

注册完成后，Agent 眼里的 time__add 与本地 @tool 装饰器注册的 web_search 没有任何区别：同样的 schema 导出、同样的按名调用。模型层、编排层对「工具来自本进程还是子进程」零感知——这就是协议抹平工具来源的价值。

3.4 Skill vs MCP：谁来做，与怎么做

确定性高：同一输入同一输出低：模型按指引自由发挥
越权风险有：工具真执行，需权限管控无：只有文字，不落地

最佳实践：用 MCP 定义底层工具（文件、命令、搜索、接口调用），用 Skill 定义业务流程（怎么订票、怎么退货——流程里可以引用 MCP 工具）。两者叠加才是完整形态：Skill 指挥，MCP 落地。以「帮用户订一张明天的机票」为例，两者在同一个循环里的分工：

步骤由谁驱动内容
1Skill（flight-booking 全文）指引：先问出发地，再查航班，最后确认价格才能下单
2MCP 工具（flight__search）真正查询航班数据
3MCP 工具（flight__book）真正下单（权限管控在这层做）
4Skill指引：按公司模板生成订票确认话术

抽掉 Skill，模型有工具却不知道流程顺序与确认红线；抽掉 MCP，模型背得出台词却办不成一件实事。

四、常见坑与边界条件

坑 1：子进程 stdout 混入日志 → JSON 解析失败。手写 server 最大的坑。任何 print() 默认走 stdout，而 stdout 是协议通道——一行日志混进去，客户端按 JSON 解析立刻失败。两条防线：日志纪律（一律 file=sys.stderr，见 2.3 节）+ 客户端容忍脏行（2.4 节的读循环里，解析失败的行忽略而不是崩溃，服务端主循环同样如此）。第三库尤其危险：import 时顺带打印 banner、依赖库往 stdout 写警告，都可能炸掉通道——接别人的 MCP server 前先跑一遍裸协议确认 stdout 干净。

坑 2：Windows 上 zoneinfo 缺 tzdata。get_current_time 用的 zoneinfo 是标准库，但在 Windows 上没有系统时区数据库，ZoneInfo("Asia/Shanghai") 会抛异常。实测环境踩过这个坑：requirements.txt 里已加 tzdata 包。跨平台分发 MCP 服务器时，别假设「标准库就一定开箱能用」——标准库也可能依赖平台数据。

坑 3：官方 SDK 是 asyncio 的，Jupyter / 同步代码里不能直接跑。官方 Python SDK 基于 asyncio + ClientSession，在 Jupyter 或纯同步代码里直接 await 会遇到「事件循环已在运行」或「无法嵌套」。课件的做法是起一个独立线程跑事件循环再桥接。本教程的同步手写实现天然规避了这个问题——教学场景下这是手写版的真实优势，不只是「为了教学而教学」。代价是 2.4 节说的：没有超时、没有并发读。

坑 4：HTTP 传输未实现，但协议是同一套。client.py 遇到非 stdio 类型会显式报错（「手写客户端只实现了 stdio 传输」），留作练习。动手前先明确：传输换 HTTP 时三步协议的消息一个字节都不用变——变的只是「一行 JSON」变成「一个 HTTP 请求体」。协议与传输解耦，是 MCP 设计里最值得体会的一笔。

边界：每次调用重连子进程。MCPClient 的 list_tools / call_tool 都是「连接 → 三步 → 关闭」，不复用连接。对教学演示无所谓，高频调用下进程启动开销会主导延迟。框架线第 7 章 MCPAdapter 管理连接生命周期（长连接、复用、异常重连），正是补上这一块。

五、关键结论

  1. MCP 解决 M×N 集成问题：Server 实现一次、Client 实现一次，M×N 塌缩成 M + N。
  2. 协议内核极小：JSON-RPC 2.0 + 三步消息（initialize → tools/list → tools/call），stdio 传输就是「一行一条 JSON」，约 130 行可徒手实现。
  3. stdout 是协议通道：日志必须走 stderr；客户端对脏行要有容忍。
  4. 注册即抹平：Tool.from_mcp 用 server__tool 命名 + 转发 inputSchema，Agent 对本进程工具与 MCP 远程工具零感知（3.3 节实测为证）。
  5. Skill 与 MCP 互补：MCP 管「谁来做」，Skill 管「怎么做」；底层工具走 MCP，业务流程走 Skill。
  6. 与框架线第 7 章 MCPAdapter 对照：框架帮你管连接生命周期（长连接、复用、重连），手写版每次调用重连子进程——这是教学取舍，不是协议要求。

本章要点回顾

  • 问题：M 个应用 × N 个工具的两两接入不可维护；MCP 把「Agent 与工具提供者」通信标准化，一次实现两头复用。
  • 内核：Client/Server 两角色、stdio/HTTP 两传输、JSON-RPC 2.0 消息（有 id 是请求，无 id 是通知）。
  • 三步协议：initialize 握手（交换 protocolVersion/capabilities/serverInfo）→ notifications/initialized → tools/list 发现 → tools/call 调用（实测 add(123,456) 稳定返回 579）。
  • 手写 server 主循环：stdin 逐行读 → handle 分发 → stdout 逐行写 + flush；日志一律 stderr；get_current_time 动态、add 确定性，一个验活一个复现。
  • Agent 接入：MCPClient.register_tools + Tool.from_mcp（server__tool 命名、直接转发 inputSchema）；实测注册表出现 time__get_current_time、time__add，对话循环与 S7 完全同构。
  • 四个坑：stdout 污染、Windows tzdata 缺失、官方 SDK 的 asyncio 与同步环境冲突、HTTP 传输留作练习（协议与传输解耦）。
  • 最佳实践：MCP 定义「谁来做」，Skill 定义「怎么做」——下一章 S10 会看到，多 Agent 协作不过是把这个循环再套一层。

10子代理：给每个子任务一个干净的上下文

说明

手写线走到第十章，我们的 Agent 已经有了工具（S4）、ReAct 循环（S6）、事件系统与安全阀（S7）、技能（S8）和 MCP（S9）。但它始终只有一个会话——所有任务的细节都挤在同一条上下文里。这一章我们要给系统加上最后一层结构能力：子代理（Sub Agent）。

一、这一章要解决的问题

设想一个真实场景：用户说「给业务系统加一个订单导出功能」。如果把它整个塞进单个 ReAct 循环，会发生什么？

  • 需求分析：读代码、读文档，十几次 read_file，每次的文件内容都整段进入上下文；
  • 建 ORM 模型：写声明式模型、跑迁移，中间夹着报错与重试，每次报错的堆栈又是一大段；
  • 写 DTO 与接口：Pydantic 分层、路由注册，又是一轮读写往返；
  • 写测试、修错误：bash_command 反复执行，每条命令的输出——包括失败的——全部留在历史里。

几十次工具往返下来，会出现三个典型症状。

症状一：注意力被稀释。 模型的注意力要在全部上下文上分配。当上下文里有几十条工具输出时，最初那条用户需求只占其中很小一行——模型开始「忘记」最初的目标，后期决策质量肉眼可见地下降。

症状二：费用滚雪球。 ReAct 循环每轮都把全部历史重新发给模型。上下文越长，单轮成本越高；轮次越多，历史越长——总费用随轮次接近平方级增长。S3 里我们说过会话只追加不删减，这在短任务里是纪律，在大任务里就成了负担。

症状三：错误上下文污染。 一次失败尝试的报错和废案会永久留在历史里。模型是有「惯性」的：它会被自己过去的失败经验带偏，后续步骤反复绕开本可用的方案，甚至为了「避开」根本不存在的坑而选择更差的路径。

《Agents底层逻辑》课件第 29 章把这个场景称为「单循环陷阱」。用一张表收拢三个症状：

二、机制与原理

解法出人意料地简单：主代理只做宏观规划，把每个子任务派给一个拥有独立会话的子代理。

子代理在自己的上下文里消化全部细节——读文件、试错、比对、汇总——最后只把一段最终结论回传给主代理。这层结构就像一道上下文防火墙：

防火墙的规则只有三条：

  1. 向下：只传任务。主代理给子代理的只是一段任务描述（query），不附带自己的消息历史——子代理看不到、也不需要看到主代理聊过什么；
  2. 向上：只回结论。子代理返回的是最终报告，几十轮工具往返的细节全部留在防火墙另一侧；
  3. 横向：互不可见。两个子代理并行调研时，彼此的上下文完全隔离。
说明

心智模型一句话：主上下文是「会议室」，子代理是「外勤组」——外勤组在外面跑断腿，回到会议室时只带一页纸的结论。会议记录（主会话）永远干净。

用一张表对比「不拆」与「拆」：

维度单 ReAct 循环硬扛主代理 + 子代理

防火墙不是唯一选项，它和上下文治理的另外两手值得放在一起看：

手段做的是什么细节去了哪
压缩 / 摘要（框架线第 9 章）把细节变成更短的细节仍在本会话，只是变小了
裁剪删掉旧细节丢失，不可恢复
子代理（本章）细节从未进入主会话在子会话里完整保留

压缩与裁剪是「事后止损」，子代理是「事前分流」。后者有个常被忽视的好处：细节在子会话里完整无损——如果调研方向错了，子代理的全部过程仍可回溯，主上下文却没有为之付出一分注意力。

实现上，子代理不需要任何新协议、新类、新循环——create_agent 就是一个普通工具。它的三个关键性质：

  • 独立会话：每次派发都通过 agent_factory 闭包产出一个全新 Agent，拥有自己的 Session；
  • 共享工具注册表：子代理能用的工具与主代理相同（同一个全局 registry）；
  • 不继承历史：新 Agent 从零开始，主代理的消息一条都不带。

「是普通工具」这一点值得停下来想一想。它意味着：模型不需要学任何新东西——工具调用是它本来就会的动作；框架不需要改一行循环代码——子代理的运行复用同一个 ReAct 循环。整个子代理体系只靠「工厂 + 工具」两个既有概念组合而成。这是好设计的典型味道：新能力从旧概念里长出来，而不是另起炉灶。

顺带回答一个常见疑问：为什么不做一个「自动拆解」机制，让框架自己决定何时派子代理？ 因为任务拆解本质上依赖对业务的理解，这正是模型在主上下文里擅长做的决策；框架如果把拆解规则写死，要么太僵（拆不出业务需要的粒度），要么太玄（黑盒魔法难以调试）。把拆解权交给模型、把派发能力交给工具——决策与机制分离，两边各做擅长的事。S10 之后的框架线会看到，成熟的实现（第 15 章）也是沿着这条边界走的。

返回值有结构化约定：每个子代理的报告以这样的前缀开头——

文本 / 输出
【子代理名字】（N 轮调用，M 条消息，上下文独立）
<结论正文>

这个约定不是装饰，而是主子代理之间的微型协议：主代理要靠它把多份报告「对号入座」后汇总；N 轮 / M 条消息 给主代理提供了「这次调研花了多大代价」的可读信号。如果回传的是无结构自由文本，汇总就从「抄写题」退化成「理解题」——坑 2 会展开这一点。

这个前缀还有第二重价值：它对代码同样可解析。一个正则就能把报告拆成结构化条目，喂给监控面板、测试断言或费用归集——主代理读到的是文本，外围系统读到的是数据。接口设计成「人机双读」，是子代理系统的实用小技巧。

与 docs/harness/ 原理篇的分工一句话：原理篇讲清「为什么必须做上下文隔离」（Agent = Model + Harness 中的记忆边界问题、五个必然问题里的「上下文从哪来到哪去」），本章给出「隔离的最小实现」——核心逻辑不到 30 行。

三、代码：Python

完整实现只有 39 行，核心是 make_create_agent_tool 这个工厂函数（代码摘自 agent/subagent.py，节选）：

Python
def make_create_agent_tool(agent_factory) -> object:
    """工厂：生成 create_agent 工具（闭包持有 agent_factory）。"""

    @tool(agents="子代理配置数组，每项包含 name（子代理名字）和 query（交给它的任务描述）")
    def create_agent(agents: list[dict]) -> str:
        """启动一个或多个子代理分别执行任务，返回每个子代理的最终结论"""
        reports = []
        for spec in agents:
            sub = agent_factory()          # 每个子代理都是全新 Agent
            results = sub.invoke(spec.get("query", ""))
            turns = len(results)
            final = results[-1].message.get("content") if results else ""
            reports.append(
                f"【{spec.get('name', 'sub-agent')}】（{turns} 轮调用，"
                f"{len(sub.session.messages)} 条消息，上下文独立）\n{final}"
            )
        return "\n\n".join(reports)

    return create_agent

逐个拆解关键点：

  • agent_factory 闭包：create_agent 不直接 Agent()，而是调用外部传入的工厂。这让子代理的模型客户端、监听器等配置完全由组装方决定，工具本身保持无状态——同一个工具，装配出测试环境或生产环境的子代理；
  • sub.invoke(...)：子代理内部跑的是和主代理一模一样的 ReAct 循环（见 agent/agent.py 的 invoke）。子代理不是新物种，只是又一个普通 Agent；
  • 报告拼装：turns 是 ReAct 轮数，len(sub.session.messages) 是子代理会话的消息总数；results[-1] 取的是最后一次模型输出——也就是子代理自己的「最终回答」；
  • 参数 schema：@tool(agents=...) 的描述字符串直接进入工具 schema，模型靠它理解「传一个数组、每项有 name 和 query」。工具描述质量就是子代理系统的 Prompt Engineering（下一章的五维之一）。

顺带回看子代理跑的循环本身（代码摘自 agent/agent.py，节选）：

Python
def invoke(self, query: str) -> list[InvokeResult]:
    """处理一条用户输入：跑完整个 ReAct 循环，返回每轮的调用结果。"""
    self.session.add_message({"role": "user", "content": query})
    results: list[InvokeResult] = []
    for _ in range(self.max_turns):
        resp = self.model.invoke(self.session, stream=True)
        results.append(resp)
        tool_results = registry.invoke(self.session.messages[-1])
        if tool_results is None:
            return results  # 模型不再请求工具：任务完成
        self.session.messages.extend(tool_results)
    print(f"[Agent] 已达最大轮次 {self.max_turns}，强制停止。", file=sys.stderr)
    return results

主代理调用它、子代理也调用它——同一个函数，两份独立的 Session，这就是「独立会话」的全部秘密。

把一次 create_agent 调用的完整时序摆出来：

  1. 主代理模型输出工具调用：create_agent({agents: [sub-orm, sub-dto]})；
  2. registry.invoke 执行工具体，进入 for 循环；
  3. agent_factory() 产出 sub-orm 的全新 Agent——全新 Session，从零开始；
  4. sub.invoke(query) 跑 3 轮 ReAct：读 orm.md、读 migration.md、给结论；
  5. 拼装 sub-orm 的报告字符串；对 sub-dto 重复 3–5 步；
  6. 两份报告 join 后作为一条 tool 消息回到主上下文，主代理汇总收尾。

注意第 4 步里发生的所有 read_file 都记在子会话的账上——主会话的账本里只有第 1、2、6 步。

主上下文只收到一段汇总文本——这就是子代理的价值。

把实测数字逐项读一遍：

观测点实测值含义
主上下文消息数5系统 + 用户 + 助手调用 + 工具结果 + 汇总，一个不多
主代理工具调用次数1只有一次 create_agent，两个子任务在同一参数里派发
工具结果内容两份报告拼接【sub-orm】…【sub-dto】…，结构化前缀清晰可辨
sub-orm 报告头3 轮调用，7 条消息读 orm.md、读 migration.md、给结论；1 用户 + 3 助手 + 3 工具
sub-dto 报告头同样 7 条消息读 dto.md、读 api.md、给结论
子代理消息是否进主会话否主上下文的 5 条里没有一条是 read_file 的结果

做个反事实推演：假如不用子代理，把两个子代理各自的 7 条消息直接搬进主会话，主上下文将变成 5 − 1 + 14 = 18 条——看似不多，但其中 12 条是 read_file 的文件内容，是纯粹的「干细节」。主代理后续每一轮都要为这 12 条付注意力与费用，而它们对「汇总结论」这个目标的边际价值是零。子任务再复杂一点（每个子代理 20 条消息），差距就是数量级的。

并发说明：教学实现里两个子代理串行执行——好处是输出确定、剧本匹配简单、便于对照理解。生产实现完全可以用线程池或异步并发，在一轮 create_agent 调用里同时发出多个子任务，报告拼装逻辑不变。两个子任务本就相互独立，串行纯属教学取舍。

与框架线第 15 章 Deep Agents 的 task 工具对照，派发有两种模式：

模式子代理起点适用场景
isolated（本实现）全新空上下文子任务自包含，不依赖主代理的现场
fork复制当前代理的上下文再分叉子任务需要「继承现场」（已读文件、已定方案）

选哪种，取决于子任务是否依赖主代理已有的背景——不是越「干净」越好。

四、常见坑与边界条件

坑 1：防火墙只隔离上下文，不隔离世界。

子代理与主代理共享同一个工具注册表，也就共享同一个真实世界。子代理写文件、执行命令，后果是真实发生的：主上下文看不到写文件的过程，但文件系统已经变了。把子代理当「沙箱」是危险的——它是视野隔离，不是权限隔离。

要限制子代理的能力，应当在工厂里给它装配更少的工具（比如只读、不写），而不是指望防火墙兜底：

Python
agent_factory=lambda: Agent(client=client, auto_builtin=False)  # 只读子代理：不装配写文件 / 执行命令

一个具体的翻车案例：你派两个子代理「分别调研 A、B 两个方案」，它们共享的 bash_command 都会真实执行——子代理 A 的试验脚本删了子代理 B 正要读的缓存文件，而两者的主代理对此一无所知。防火墙挡住了信息，挡不住副作用。

坑 2：报告格式不约定，汇总变成猜谜。

如果 create_agent 返回的是各子代理的自由文本，主代理拿到的就是一坨无结构信息：哪段属于哪个任务？调研了几轮？哪份结论更可信？全部要靠模型脑补。子代理一多、报告一长，脑补就会出错——而且错得悄无声息。

【名字】（N 轮调用，M 条消息） 这个前缀约定成本几乎为零，却让汇总从「理解题」变成「抄写题」。设计子代理系统时，回传格式与任务描述同样重要——前者是子代理对主代理的接口，后者是主代理对子代理的接口，两个方向都要设计。

一个最小的好实践：在 query 里就写明「最后给结论，结论里包含 X、Y、Z」。回传接口在派发时就被约定，而不是事后祈祷子代理自觉。

坑 3：深度嵌套的上下文成本与失控风险。

子代理还能再派子代理吗？技术上完全可以——子代理的注册表里同样有 create_agent。但要警惕三重代价：

  • 规划精度：每深一层，任务描述必须更精确，否则最底层拿到的是传了两次的「传话游戏」；
  • 信息损耗：每层回传都只保留结论，跨层传递时细节丢失不可逆；
  • 费用相乘：父代理一轮 + 子代理 N 轮 + 孙代理 M 轮，总调用量是乘积关系。

经验法则是：两层（主 → 子）覆盖绝大多数场景；三层以上应先怀疑任务拆分方式不对，而不是继续嵌套。

一个粗算：主代理 1 轮派发、两个子代理各 5 轮、某个孙代理再 5 轮——最坏路径上是 1 + 5 + 5 = 11 次模型调用，而每层报告回传都只保留结论。第三层看到的任务描述，已经经过两次「压缩转述」，偏差会被逐层放大。

坑 4：父代理的 max_turns 不覆盖子代理。

S7 里的安全阀 max_turns 是每个 Agent 各自独立计数的：父代理 10 轮的上限，管不了子代理在自己的循环里跑多少轮——子代理有自己的 max_turns（agent/agent.py 中各自的构造参数）。

后果：一个子任务死循环时，父代理会同步等它撞上自己的安全阀才罢休。串行实现下这会放大成整体阻塞；并发实现下则表现为某个分支悄悄吞掉预算。给不同层级的代理显式配置轮次上限，是子代理系统的基本卫生：

Python
agent_factory=lambda: Agent(
    client=client, auto_builtin=True,
    max_turns=6,   # 子代理轮次独立设小：调研类任务不该跑太深
)

要点只有一句：子代理的 max_turns 在工厂里显式给，别吃默认值。

边界条件：结论里必须自带主代理所需的事实。

本实现里子代理的结果只以文本形式回传，不回传它读过的文件内容。如果子任务发现的信息需要主代理亲自处置（比如「这个文件必须改第 3 行」），结论里必须把必要细节写清楚——防火墙挡掉的是过程，不是主代理后续行动所需的事实。一句话：派发前想清楚「我最后要拿什么」，结论里就要求子代理写什么。

五、关键结论

  1. 子代理 = 上下文防火墙：主上下文只保留任务与结论（实测 5 条消息、仅 1 次工具调用），全部细节消化在子代理的独立会话里（各 7 条消息，从未进主会话）；
  2. create_agent 是普通工具：以 @tool 装饰、参数为配置数组、经 agent_factory 闭包产出全新 Agent——独立会话、共享工具注册表、不继承历史；新能力从旧概念里长出来，不另起炉灶；
  3. 它不是权限隔离：子代理写文件、跑命令的后果真实存在，限权要在工厂里做；
  4. 报告格式是协议：【名字】（N 轮调用，M 条消息）+ 结论 的约定让汇总可依赖，回传接口与派发接口同等重要；
  5. 两层为宜：isolated 与 fork（框架线第 15 章）对应「从零开始」与「继承现场」两种拆分需求；深度嵌套前先怀疑拆分方式。

从工程视角看，S10 一次性落了两个维度：Loop Engineering（把一个长循环拆成多个短循环，让每个循环都可靠收敛）和 Graph Engineering（主代理与子代理构成一张显式的任务拓扑）。这正是下一章的主题——把这十章里散落的工程实践，收拢成五个维度。

本章要点回顾

  • 为什么：单 ReAct 循环扛大任务，会遭遇注意力稀释、费用滚雪球、错误上下文污染三大症状——细节 ≠ 结论；
  • 是什么：主代理只做规划，每个子任务派给拥有独立会话的子代理，只回传结论——上下文防火墙，规则三条：向下只传任务、向上只回结论、横向互不可见；
  • 怎么实现：create_agent 是普通工具，agent_factory 闭包每次产出全新 Agent（见 agent/subagent.py）；子代理复用同一个 ReAct 循环（见 agent/agent.py）；
  • 实测：主上下文 5 条消息、仅 1 次工具调用；子代理各 3 轮调用、7 条消息，全部留在防火墙内侧；
  • 坑：防火墙不隔离世界、报告格式要约定、嵌套宜浅、max_turns 各自独立计数、结论里要自带主代理所需事实；
  • 延伸：并发执行与 isolated / fork 两种派发模式，见框架线第 15 章；上下文隔离的原理推导见 docs/harness/。

11五大 Engineering：从会写到写好

说明

S1–S10 回答的是「怎么实现」——从模型契约一路写到子代理，我们的 Agent 跑起来了。但「跑起来」和「跑得好」之间隔着一条经验的鸿沟。这一章不写代码，而是把前面散落各章的实践收拢成五个工程维度，回答最后一个问题：怎么做好。

一、这一章要解决的问题

先交代两个背景事实。

第一，Harness 这个词并非本书生造。Mitchell Hashimoto 在记录自己的 AI 采纳历程时，把「围绕模型搭建的那圈脚手架」称为 harness——从马具「挽具」引申而来：模型是马，挽具决定这匹马能拉什么车、拉得稳不稳。OpenAI 随后的 Harness Engineering 博文让这个提法在业界流行开来（以上为《Agents底层逻辑》课件引用来源，一句话带过）。

第二，一个拼写勘误：课件原文将 Engineering 误拼为 Engeering，本教程统一使用正确拼写 Engineering——错字无伤大雅，但这五个名字会反复出现在你的工程文档与检索关键词里，值得写对。

现在看问题本身。S1–S10 的每一章都解决了一个「有没有」的问题：

「有没有」问题（前十章已解决）「好不好」问题（本章）
提示词写进系统提示了吗？（S2）提示词是不是精简、自洽、结构化的？
会话保存历史了吗？（S3）历史在 50 轮后还能撑住吗？
工具注册进 registry 了吗？（S4）危险操作有护栏吗？出问题能观测吗？
ReAct 循环能转了吗？（S6）循环保证收敛吗？死循环有安全阀吗？
子代理能派发了吗？（S10）任务拓扑是刻意设计的，还是随机长出来的？

左边一列问的是存在性，右边一列问的是质量。让系统从「存在」走向「高质量存在」，靠的不是更多代码，而是方法论。

这五个「好不好」也不是本书的私人发明，而是业界在 Agent 实践中沉淀下来的方法论分层——《Agents底层逻辑》课程第 30–34 章将它们命名为五个 Engineering：Prompt、Context、Harness、Loop、Graph。本章逐一拆解，并把每一维映射回本书手写线的章节与框架线章节。

它们的出场方式也很能说明问题：课程把五维安排在全部实现性内容（1–29 章）之后讲——方法论的命名总是晚于方法的实践，就像「面向对象」这个词出现在大量面向对象代码之后。本教程的手写线也是同样的顺序：先写出来，再回头看写的是什么。

为什么值得专门用一章做这件事？因为不收拢就会遗忘。学完 S1–S10 你手里有十几块积木，但如果没有一张全景图，下次遇到「我的 Agent 效果不好」时，你不会知道该从哪块积木查起。五个维度就是那张全景图：任何 Agent 问题，都能定位到其中一维或几维的缺口。

还有一个自然的追问：为什么恰好是五个，不是三个或八个？ 因为五个维度各自对应一类独立失效模式，两两之间既不可互相替代、也无法合并：Prompt 错了 Context 救不了（指令自相矛盾，历史再多也没用）；Loop 不可收敛时 Harness 再稳也白搭（工具再好，循环停不下来就等于零）；而 Graph 解决的「多任务编排」在单任务系统里根本不会出现。五个问题彼此正交，又恰好覆盖「从一句话到一套系统」的全部层级——这大概就是它被业界普遍接受的原因。

二、机制与原理

五个维度可以排成一条抽象阶梯：越靠前越贴近模型本身，越靠后越贴近系统结构。

阶梯的读法有三层。

第一层：自下而上是依赖关系。

  • Prompt 是模型直接的输入面——写什么，模型就按什么理解任务；
  • Context 决定除 prompt 外还有什么进入模型视野——历史、检索结果、技能正文；
  • Harness 提供工具与护栏等「模型之外的一切」——没有它，模型只会说话不会做事；
  • Loop 把前三层装进一个可靠收敛的循环——让「说」变成「做、看结果、再做」；
  • Graph 在循环之上编排多个循环——子代理拓扑、任务规划、显式状态机。

第二层：每个维度回答一个核心问题。 模型听懂了吗？上下文够用且不膨胀吗？模型之外的一切齐了吗？循环可靠收敛吗？复杂任务有序编排吗？——五个问题依次对应五维。漏掉任何一问，系统都会在对应层面失控，而且失控的表现恰好暴露缺的是哪一维：答非所问是 Prompt 缺口、越聊越糊涂是 Context 缺口、有手无脚是 Harness 缺口、停不下来是 Loop 缺口、一团乱麻是 Graph 缺口。

第三层：五个维度不是五个技术栈。 它们是同一套系统的五个质量维度。你写的每一行 Agent 代码都同时处于这五个维度上——一个 @tool 装饰器既是 Harness（工具供给），其描述质量又影响模型要不要调它（Prompt 面），好不好用还决定循环几轮收敛（Loop 面）。

先用一句话定义给五维各立一块牌子：

维度一句话定义类比
Prompt Engineering把任务说明写到模型能听懂把话说明白
Context Engineering把该看见的给模型，不该占位的挡在外面整理桌面
Harness Engineering供给做事的工具，管住做事的边界装备与保险
Loop Engineering保证「做—看—再做」能稳定走到终点刹车与油门
Graph Engineering多个循环之间的分工与协作组织架构图

维度之间还存在放大与抵消关系，这是「逐项对照」比「依次专精」更有效的原因：

  • Context 放大 Loop：历史失控让每轮输入变长变脏，模型更容易在噪声里做出错误工具调用，循环被拖向死循环——反过来，干净的历史让每一轮决策更果断，轮数下降；
  • Harness 放大 Prompt：工具描述写得好，模型对「什么时候用什么工具」的理解就准，系统提示里的任务描述压力也随之减轻——工具 schema 本身就是提示词的一部分；
  • Graph 抵消 Context 压力：S10 的防火墙本质上是 Graph 结构（主 + 子拓扑）替 Context 维度扛住了膨胀；
  • Loop 抵消 Graph 风险：每个子循环各自带安全阀，才敢放心把任务拆成拓扑——没有 Loop 兜底的 Graph 是把风险乘以节点数。

两个容易误解的地方需要提前澄清。

误解一：维度之间是学习顺序。 并非「先学好 Prompt 再学 Graph」——它们更像体检指标，应当逐项对照、整体改善。实践中最常见的组合拳是 Context 治理（裁剪历史）与 Loop 收敛（安全阀）同时做，因为两者互相放大：历史失控会把循环拖向死循环，循环失控又让历史疯长。

误解二：维度与代码量正相关。 Graph Engineering 听起来最「高级」，但它的最小实现（S10 的子代理）只有 30 行；Prompt Engineering 听起来最「基础」，做好它需要的迭代次数往往最多。维度的高度衡量的是抽象层级，不是难度或工作量。

误解三：五维只属于「大系统」。 恰恰相反，小项目从五维获益更直接——大厂有平台组兜底 Harness、有评测体系兜底 Loop，而独立开发者身兼数职时，五维总表就是你的外包清单：哪一维没人管，哪一维迟早爆雷。S1–S10 每章几十行代码就是证明：质量维度的落实从来不取决于团队规模，只取决于有没有人记得它。

三、五个维度逐一拆解

每个维度按统一结构展开：回答什么问题 → 核心手段 → 本书哪里实践了它 → 框架线哪里对应，末尾附一条反模式与三问自查清单——读完可以直接拿去对照自己的项目。

1. Prompt Engineering——让模型听懂

  • 回答什么问题：模型听懂了吗？同样的底层能力，指令写法不同，表现可以差出一个量级。
  • 核心手段：
    • 精简——删掉不产生行为差异的话，每一句都在争夺模型的注意力预算；
    • 自洽——指令之间不互相打架（「要详细」与「要简短」同时出现，模型只能掷硬币）；
    • 全局约束——放系统提示一次生效，而不是每轮对话里重复叮嘱；
    • 静态——用模板渲染，运行时只换变量，提示词主体不随对话漂移；
    • 结构化——角色 / 环境 / 规则 / 输出格式分节，让模型的「阅读理解」有路标。
  • 本书哪里实践了它：S2 提炼的系统提示词五原则正是这套手段的落地；S7 的默认提示词模板（agent/prompt.py 渲染角色与工具清单）是「静态 + 结构化」的实例；S4 的工具描述字符串也在这个维度里——工具 schema 就是写给模型看的「提示词」。
  • 框架线哪里对应：框架线第 3 章的 ChatPromptTemplate 把「模板 + 变量注入」工业化，支持 few-shot 槽位、消息列表拼装与角色模板。
  • 反模式：提示词越写越长、互相矛盾、把示例和规则混在一起——典型症状是「改一句、坏三处」。
  • 上手自查：
    • 系统提示里有没有互相打架的指令？删掉一遍再读一遍；
    • 工具描述是否说清了「什么时候该用、什么时候不该用」；
    • 每轮对话里是否在重复系统提示已有的话？

2. Context Engineering——让上下文够用且不膨胀

  • 回答什么问题：上下文够用吗？够用之后，会不会无限膨胀？
  • 核心手段：
    • 会话历史管理——记什么、记多久、什么时候压缩；
    • 两条纪律——只追加（消息一经写入不改写，保证工具调用与结果配对完整）与保思维链（assistant 的推理过程不丢，它是后续决策的依据）；
    • 渐进式披露——先给目录，需要时再加载全文，别把整本书塞进第一轮；
    • 压缩与卸载——摘要、裁剪、缓存前缀，给历史降温而不丢关键事实。
  • 本书哪里实践了它：S3 的 Session 落实了只追加与思维链保全；S8 的 Skill 用「清单进提示词、正文按需 load_skill」实现了渐进式披露；S10 的子代理是最激进的上下文治理——细节整体不出防火墙。
  • 框架线哪里对应：框架线第 9 章给出摘要压缩、历史裁剪、缓存前缀三条生产级路线。
  • 反模式：历史只进不出、把大文件全文塞上下文、压缩时把思维链一起压掉——模型在后续轮次会重复犯已修正过的错。
  • 上手自查：
    • 长会话的第 50 轮，最初的任务目标还「够得着」吗；
    • 有没有渐进式披露的机会——哪些大块内容可以先给目录；
    • 压缩 / 裁剪前，是否先划出了不可丢弃区（系统提示、思维链、关键结论）。

3. Harness Engineering——模型之外的一切

  • 回答什么问题：模型之外还缺什么？裸模型只会生成文本，让它「做事」的一切都在 harness 里。
  • 核心手段：
    • 工具供给——schema 设计与描述质量决定模型会不会用、用得对不对；
    • 权限护栏——危险操作的白名单、确认机制与最小权限装配；
    • 可观测——事件流让每一次模型调用与工具执行有迹可循，出问题能回放。
  • 本书哪里实践了它：S4 的工具包与 registry 是工具供给；S7 的事件系统与监听器是可观测的最小实现；registry.invoke 对未授权工具返回 None 是最朴素的护栏；S9 的 MCP 把工具供给扩展成生态接入。
  • 框架线哪里对应：框架线第 6 章的中间件是它的工业化形态——六个钩子把「模型之外的一切」变成可插拔的切面。原理篇 docs/harness/ 与本维度全面呼应：Agent = Model + Harness，以及 harness 必须回答的五个必然问题。
  • 反模式：只有工具、没有护栏与可观测——等于给模型发了枪却不装保险、不留弹道记录，出事时连是哪次调用闯的祸都查不到。
  • 上手自查：
    • 每个工具的副作用等级标注了吗？写类 / 执行类工具有没有确认机制；
    • 一次失败的工具调用，能否从事件流里回放出「当时模型看到了什么」；
    • 子代理（如 S10 的工厂）装配的工具集是否按需最小化。

4. Loop Engineering——让循环可靠收敛

  • 回答什么问题：循环可靠收敛吗？ReAct 循环默认没有出口，收敛性必须被设计。
  • 核心手段：
    • 终止条件设计——registry.invoke 返回 None（模型不再请求工具）是唯一自然出口，工具集合的「可完成性」决定了出口是否存在；
    • max_turns 安全阀——防死循环的强制止损，S10 的坑 4 提醒我们它按代理独立计数；
    • 工具异常回喂——报错作为 tool 消息还给模型让它自己修正，而不是让循环崩溃；
    • 多步任务拆解——一个大循环拆成多个短循环，每个都容易收敛（S10 的防火墙一石二鸟）。
  • 本书哪里实践了它：S5 的错误回喂、S7 的 max_turns 安全阀、S10 的子代理拆解，正好覆盖这四条手段。
  • 框架线哪里对应：框架线第 12 章的 interrupt / resume 是人在回路对循环的接管——把「何时继续、何时停下」的决定权部分交还给人类。
  • 反模式：只设安全阀不管终止条件（每单都烧满 max_turns 才停）、异常直接抛出杀掉循环、把多步任务硬塞进单循环硬扛。
  • 上手自查：
    • 每个工具集合是否存在「模型永远无法给出最终回答」的死局；
    • max_turns 触发时有告警或日志吗，还是静默吞掉（S7 里它只打到 stderr）；
    • 工具抛异常时，错误信息是否以 tool 消息形态回喂（S5），且模型拿到的报错足以自我修正。

5. Graph Engineering——复杂任务的结构化编排

  • 回答什么问题：复杂任务有序编排吗？单循环再可靠，也扛不住任务内在的分支、并行与依赖。
  • 核心手段：
    • 子代理拓扑——主代理规划、子代理执行的星型结构，天然带上下文隔离；
    • 任务规划——先拆解再派发，派发即编排，拓扑是设计出来的不是长出来的；
    • 显式状态机——把「下一步干什么」从模型的即兴发挥变成图上的确定路径。
  • 本书哪里实践了它：S10 的主代理 + 子代理就是最小拓扑——一个中心节点向两个叶子节点派发并回收结论。
  • 框架线哪里对应：框架线第 10 章 LangGraph 的 State / Reducer / Send 是这个维度的全套基础设施；第 15 章 Deep Agents 的 task 工具与 isolated / fork 两种派发模式是它的成品形态。
  • 反模式：图锤子病——看什么任务都想建图，忘了编排结构本身有成本（见坑 2）。
  • 上手自查：
    • 当前任务的分支 / 并行 / 依赖，单循环加安全阀真的扛不住吗；
    • 每条回传边的「接口约定」（如 S10 的报告前缀）写清了吗；
    • 拓扑层级是否控制在两层以内，第三层的理由经得起推敲吗。

四、常见坑与边界条件

坑 1：把五个维度当成五门课依次修。

最常见的误读是「我先把 Prompt 学透，再学 Context……」。五维是同一系统的五个切面，不是五层技术栈。一个典型的反例：团队花两周打磨提示词，却任由会话历史无限增长——第 60 轮时，再好的提示词也被淹没在垃圾上下文里。正确姿势是像体检一样逐项对照，优先补最短的那块板。

判别「短板」有个实用信号：去看失效现场。用户抱怨「答非所问」，先别急着改提示词——把会话轨迹拉出来（S7 的事件系统正是干这个的），看模型当时看见了什么：如果关键信息压根不在上下文里，那是 Context 的锅；信息在但被淹没，还是 Context 的锅；信息清晰完整而模型仍理解偏了，才轮到 Prompt。先诊断后开方，五维是诊断框架，不是开发排期表。

坑 2：Graph Engineering 万能论。

学会了子代理与状态图之后，容易患上「图锤子病」——看什么任务都想建一张图。但编排结构本身有成本：拓扑越复杂，调试越难、回传损耗越大、费用越高。判断标准很简单：单循环能在安全阀内收敛的任务，不该上 Graph。S10 的两层拓扑覆盖绝大多数场景；需要三层以上时，先怀疑任务拆分方式（见 S10 坑 3）。

一个自查动作：动手建图前，先写清楚这张图省掉了哪次失败的重试、哪段重复的上下文。写不出来的图，就是为图而图的图。

坑 3：把 Harness 等同于「工具多」。

工具供给只是 Harness 的三分之一。只有工具、没有护栏与可观测的 Agent，等于给模型发了枪却不装保险、不留弹道记录——出事时你甚至不知道是哪次调用闯的祸。护栏（权限确认）与可观测（事件流）必须与工具同步建设，S7 的事件系统就是为此存在的。接入 MCP（S9）后这条尤其重要：外部工具来自第三方服务，副作用面更大、更不可控，更需要护栏先行、可观测殿后。

坑 4：Context 治理只做减法。

裁剪和压缩是手段，不是目的。保思维链这条纪律提醒我们：有些「占地方」的内容恰恰是最值钱的——assistant 的推理过程一旦被裁掉，模型在后续轮次会重复犯错。做上下文治理时，先划「不可丢弃区」（系统提示、思维链、任务关键结论），再在剩余空间里做减法。一个可操作的比例感：不可丢弃区通常只占上下文的两三成，真正的膨胀都来自工具输出——治理对象要找对。

坑 5：术语漂移。

Harness、Context、Orchestration 这些词在不同社区所指不同：有人用 Harness 指评测脚手架（evals harness），有人指运行时外壳。本书及《Agents底层逻辑》课件取「模型之外的一切运行时支撑」这一含义；引用外部资料时先对齐词义，再讨论问题。举个真实的混淆场景：你读到一篇「Harness 工程实践」的文章，前半篇讲工具注册（与本书同义），后半篇讲评测集管理（不同义）——不作区分地照搬两半的建议，会发现它们对同一个系统提出了矛盾的要求。顺带再提一次：课件原文的「Engeering」系误拼，检索资料时请用正确拼写 Engineering，否则可能漏掉关键文献。

边界条件：五维框架本身的适用边界。

五个维度是为「用循环干活的 Agent」总结的。纯生成类应用（一次性问答、无工具调用）只有 Prompt 与 Context 两维生效；重度结构化流水线可能整个系统都活在 Graph 维。框架是地图，不是疆域——用五维定位问题，但别为了「凑齐五维」而给简单系统加装它不需要的层。

一个判断「该覆盖几维」的粗略方法：数一数你的系统里 registry.invoke 返回过几次非 None。一次都没有（纯问答），前两维就是全部；有返回但没有分支派发，Loop 就是天花板；开始派子任务，才真正进入 Graph 的领地。

五、关键结论

  1. 五个维度不是五个技术栈，而是同一套系统的五个质量维度：Prompt、Context、Harness、Loop、Graph 分别回答「听懂、够用、齐备、收敛、有序」五个问题；
  2. S1–S10 其实一直在五个维度上做工：S2 是 Prompt、S3/S8 是 Context、S4/S7 是 Harness、S5/S7 是 Loop、S10 是 Graph——本章只是把它们显式命名；
  3. 手写线让你看见它们的最小实现，框架线让你看见它们的生产形态：模板之于五原则、中间件之于 Harness、LangGraph 之于 Graph，都是「同维升级」而非「另起炉灶」；
  4. 实践顺序按短板来，不按清单来：逐项对照总表，先补最弱的维度；
  5. Harness 一词源自 Mitchell Hashimoto 的 AI 采纳历程与 OpenAI 的 Harness Engineering 博文——记住词源（挽具），就记住了它的立场：模型是马，工程是挽具。
