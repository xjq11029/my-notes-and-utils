# S2 系统提示词：模型的出厂设置由你决定

> 手写线第 2 章｜配套代码：`code/s02_system_prompt.py`｜配图：`assets/h02_prompt_render.png`

## 一、这一章要解决的问题

同一个基座模型，在不同产品里的表现天差地别：有的严谨克制、有的满嘴胡话，有的精简利落、有的车轱辘话连篇。模型明明是同一个，差距从哪来？大部分时候，答案藏在一段你看不见的文本里——**系统提示词（system prompt）**。

系统提示词是 `messages` 数组里 `role` 为 `system` 的第一条消息（S1 讲过四种 role），它位于所有消息之前，而模型在训练时被重点对待"开头的指令"——把它理解成模型的**出厂设置**：用户没开口之前，它先定义了"你是谁、你在哪、你该怎么做"。

问题在于：系统提示词写得差，比不写还糟。废话太多稀释重点，规则自相矛盾让模型无所适从，把每分钟都在变的东西写进去则会在 S3 付出真金白银的代价。而且它藏得深：用户看到的是回答，看不到塑造回答的那段话，所以提示词的问题往往最后一个被发现。

改提示词也是 Agent 开发中性价比最高的优化——不用训练、不用改代码，一段文本就能改变行为。它也是你唯一能"用自然语言给模型下精确指令"的地方，手写线后续所有行为设计（S4 的工具规则、S8 的技能引导）最终都落在系统提示词或它携带的消息上。这也是它值得单独一章的原因。

本章解决三件事：

1. 系统提示词该怎么写——五条可操作的原则，每条配反例和正例；
2. 环境信息（工作目录、操作系统、是否 Git 仓库）怎么优雅地注入——模板与代码分离；
3. 渲染结果最终去了哪——`messages[0]`，以及为什么渲染完就要"冻结"它。

## 二、机制与原理

### 2.1 位置决定地位：messages[0]

系统提示词的特殊性首先来自**位置**。每次调用模型（S3 会讲，每次都要重传完整历史），它都排在数组第一位，模型对开头的注意力权重天然更高。把两者放一起看：

| | system 消息 | user 消息 |
| --- | --- | --- |
| 谁写的 | 应用开发者 | 最终用户 |
| 在历史里的位置 | 永远是第一条 | 逐条追加 |
| 内容性质 | 规则、设定、环境信息 | 具体请求 |
| 用户可见性 | 通常不可见 | 就是用户自己打的字 |
| 调试方式 | 单独打印出来读（本章的做法） | 翻聊天记录 |

注意最后一行。系统提示词是"看不见的指挥棒"，出问题时人们习惯怀疑模型能力或参数设置，很少先把它打印出来通读一遍。**调试提示词的第一步永远是：把它原样打印出来，以模型的视角读它。** s02 脚本的第一节输出就是为此准备的。

一点诚实的保留：「训练时被重点对待」是社区与课件的经验性总结，各厂商并未公开训练细节；但「开头的指令对行为影响最大」这一判断在实践中稳定成立，按此对待不会吃亏。

也正因为它是 `messages[0]`，S3 讲的 **prompt cache 前缀命中**才与它直接相关：它是最长的那段公共前缀，缓存收益最大；反过来，一旦它变了，后面的所有缓存全部作废。这条线索先记住，S2 末尾和 S3 都会回到它。

### 2.2 编写五原则：反例 vs 正例

以下五条整理自《Agents底层逻辑》课程课件，核心思想一句话：**系统提示词是给模型读的配置文件，不是给人看的说明文**。逐条对照：

| 原则 | 反例 | 正例 |
| --- | --- | --- |
| ① 精简 | 118 字废话："你现在要充当一名专业代码顾问，接下来我会向你提出各种各样和编程相关的问题。希望你认真仔细地阅读……" | 30 字："你是代码顾问。精准解答编程问题，不懂直接说明，禁止编造信息。" |
| ② 自洽 | "回答要详尽、覆盖多个角度" + "答案控制在 30 字以内" | 删掉一个，或明确优先级："先给 30 字结论，需要时再展开" |
| ③ 全局约束 | "如果用户问安全问题就拒绝，如果问代码就写，如果……"（条件式规则） | "除了回答编程问题，其他话题一律说明超出范围"（无条件精简） |
| ④ 保持静态 | "现在是 {当前时间}，欢迎回来，{用户名}！" | 时间、用户名等动态量不进提示词；环境信息在启动时渲染一次并冻结 |
| ⑤ 结构化 | 一大段散文，规则混在描述里 | Markdown 分层：`## 角色` / `## 运行环境` / `## 行为规则` |

五原则的一句话记忆版：**对模型行为没有约束力的删掉；互相打架的删掉一句；条件句改写成无条件句；每轮都变的不放进去；每条规则都给一个标题。**

几条原则背后的道理值得多说一句：

- **① 精简**：不是字数越少越好，而是删掉不携带信息的话。"希望你认真仔细地阅读我每一次发送过来的内容"翻来覆去只有一个意思——认真读题，对模型没有任何额外约束力。礼貌用语和铺垫在消耗上下文窗口和注意力。上面 118 字 vs 30 字是 s02 脚本实测的字数，实测输出：

```text
== 2. 系统提示词的「精简」反例 vs 正例（同一意图）==
反例（118 字）: 你现在要充当一名专业代码顾问，接下来我会向你提出各种各样和编程相关的问题。希望你…
正例（30 字）: 你是代码顾问。精准解答编程问题，不懂直接说明，禁止编造信息。
```

  同一意图压缩近 4 倍，且正例反而多了一条反例没有的**硬约束**（"禁止编造信息"）——精简的正确姿势是删废话、留规则，不是删内容。

  废话黑名单里的常客："希望你认真仔细地阅读"、"充分理解我的诉求"、"回答清晰易懂方便我理解"、"如果遇到不清楚的内容千万不要随意编造"——最后这条其实是好约束，但"禁止编造"四个字就够了。

- **② 自洽**：模型遇到矛盾指令不会报错，它会**随机偏向其中一边**——这次听"详尽"、下次听"30 字以内"，你得到的输出不稳定，却找不到原因。矛盾也未必是数字上的：一句"覆盖所有可能的边界情况"配一句"回答保持极简"同样是打架。排查方法还是那条：把提示词打印出来，用人类的眼睛找矛盾。

- **③ 全局约束**：条件式规则（"如果……就……"）教模型学会了找例外、钻空子。举个具体的例子：把"涉及爬虫先提醒合规风险、涉及调试先要报错信息、涉及部署先问目标环境……"写成五条 if，模型的注意力花在"匹配哪条"上，规则夹缝里的需求它就开始自由发挥。改成一句无条件的"动手写代码前，先用一句话说明潜在风险与前提假设"，遵从度反而更高。全局约束的检验标准：这条规则**对任何一条输入都应该生效**。

- **④ 保持静态**：这是五条里唯一带"钱"味的，机制在 S3 展开；但注意它是原则不是铁律，本节末尾专门讨论。

- **⑤ 结构化**：模型对 Markdown 小节标题的遵从度显著高于散文段落——标题就是给规则的"名字"，模型引用和执行带名字的规则更稳定。手写线的模板只有三个小节（角色 / 运行环境 / 行为规则），够用就好，不必为了结构化而结构化。

### 2.3 环境感知：模板 + 环境变量，启动时渲染一次

手写线的编码助手需要知道三件事：当前工作目录、操作系统、是否在 Git 仓库内。这些信息**每台机器、每个目录都不同**，不能硬编码；但它们在**一次运行的整个生命周期里不变**。把"环境信息怎么进上下文"的三种方案摆在一起，取舍就清楚了：

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 硬编码 | 提示词里写死"你运行在 Windows" | 换台机器就错，文案与代码耦合 |
| 每轮动态渲染 | 每次调用前取一次 cwd / 时间拼进提示词 | 提示词每轮都变，缓存永远 miss（见坑 1） |
| 启动时渲染一次（本教程） | 模板占位 + 启动时采集渲染，之后冻结 | 长会话中值可能过期（如中途 cd），代价可接受 |

这张表还藏着一个规律：**信息变化越频繁，就越该远离系统提示词**——写死的 < 启动时注入 < 根本不进提示词。每轮都变的信息只属于 history（S3）。

第三种方案的实现：模板 `agent/prompt/system.j2` 留占位符，环境部分长这样：

```jinja
## 运行环境
- 工作目录：{{ cwd }}
- 操作系统：{{ os }}
- Git 仓库：{{ "是" if is_git else "否" }}
```

负责渲染的是 `agent/prompt.py` 的 `render_prompt()`：Jinja2 加载模板，注入四个变量——`cwd`（当前目录）、`os`（操作系统）、`is_git`（是否 Git 仓库，启动时真的执行一次 `git rev-parse`）、以及可选的 `skills`（技能清单，S8 的伏笔）。四个变量一览：

| 变量 | 来源 | 本机实测值 |
| --- | --- | --- |
| `cwd` | `os.getcwd()` | `D:\…\handwritten\code` |
| `os` | `platform.system()` | `Windows` |
| `is_git` | `git rev-parse --is-inside-work-tree` | `True`（仓库内运行） |
| `skills` | 启动时注册，可选 | 无（S8 启用） |

s02 脚本第一步就把渲染结果打了出来，实测输出（`s02_system_prompt.py`，在代码目录下运行）：

```text
== 1. 渲染后的系统提示词 ==
# 角色
你是运行在用户终端里的编码助手，通过工具完成实际操作。

## 运行环境
- 工作目录：D:\ProjectCode\my-notes-and-utils\docs\agent开发教程\handwritten\code
- 操作系统：Windows
- Git 仓库：是

## 行为规则
1. 需要读写文件或执行命令时，直接调用工具完成，不要只描述做法。
2. 回答精简；信息不足时明确说明，禁止编造。
3. 执行写操作前，与用户确认目标路径。
```

两个细节：`Git 仓库：是` 是因为脚本恰好在 Git 仓库内运行（`is_git` 检测为 `True`，换到仓库外运行这里就是"否"）；工作目录的值取决于你在哪里启动脚本。工作目录每次运行都一样吗？不一定——**但它只在启动时渲染这一次**，运行期间不会变，这就是"静态"。

第三个细节藏在输出末尾：「行为规则」之后有两个空行——来自模板条件块 `{% if skills %}` 前后的换行符，Jinja2 默认不会删掉它们。无害，但它解释了为什么渲染产物和模板原文"看着不太一样"，也提醒你：提示词里的空白字符也是内容的一部分。

渲染完的系统提示词去哪了？看 s02 的检视输出：

```text
== 3. 检视：系统提示词在 messages 里的位置 ==
{"role": "system", "content": "# 角色\n你是运行在用户终端里的编码助手，通过工具完成实际操作。\n\n## 运行环境\n- 工作目录：D:\\ProjectCode\\my-notes-and-utils\…
```

就是 `messages[0]`——一条普通的 system 消息。`Session(system_prompt=...)` 在构造时把它 `add_message` 进历史（S3 详谈 Session），之后每次调用原样重传。第二次调用"你好"时，模型看到的 messages 是 `[system, user("目前在哪个目录？"), assistant(…), user("你好")]`——出厂设置全程在场。

**模板与代码分离的价值**在此时显现：调整提示词措辞只需要改 `.j2` 文件，不碰任何 Python 代码；反过来，环境变量的采集逻辑（怎么拿 cwd、怎么判断 Git）也独立在 `prompt.py` 里，各改各的。

顺带回答一个必然的疑问：为什么用 Jinja2，`f"…{cwd}…"` 拼接不行吗？技术上完全可行，但拼接把文案埋进 Python 源码——文案不能被不懂代码的人改，diff 混在代码提交里，review 也不直观。模板文件让提示词成为一个可以被独立查看、独立评审、独立版本管理的"配置物"，这在提示词要反复迭代的 Agent 项目里是实打实的工程收益。

（另一个小开关：`render_prompt` 里 `keep_trailing_newline=True`。Jinja2 默认吞掉模板文件末尾的换行符，这个开关让渲染产物与模板逐字节对齐，diff 友好。）

### 2.4 往上多看一层

框架线第 14 章介绍过 Deep Agents 的 `base_system_prompt`——那是一份长得多的系统提示词（含文件系统使用守则、规划工具说明、任务委托规则等）。骨架与本章完全同款：角色、环境、规则，只是规则条目更多、更细：

| | 手写线 `system.j2` | Deep Agents `base_system_prompt`（框架线第 14 章） |
| --- | --- | --- |
| 篇幅 | 十几行 | 上百行 |
| 环境感知 | 三个变量，启动时渲染 | 更丰富的环境与工具说明 |
| 技能/扩展 | `skills` 变量按需注入（S8） | 文件系统 + 子代理的完整使用守则 |
| 骨架 | 角色 → 环境 → 规则 | 相同 |

**写系统提示词的能力是随 Agent 复杂度线性增长的**，但五原则不变：再长的提示词，也要精简、自洽、全局、静态、结构化。两者的差别不在"写法"，在"规模带来的管理成本"——十几行可以靠手感，上百行就必须走 2.5 节的迭代流程。

## 三、代码：Python

先看模板全文——它本身就是"五原则落地"的示范：结构化（三个小节）、精简、全局约束、内容静态（只有启动时确定的环境变量）。先读模板还有个额外好处：它是这个 Agent 行为的最短完整说明，给新人讲系统提示词往往比讲代码更快：

```jinja
{# agent/prompt/system.j2 全文 #}
# 角色
你是运行在用户终端里的编码助手，通过工具完成实际操作。

## 运行环境
- 工作目录：{{ cwd }}
- 操作系统：{{ os }}
- Git 仓库：{{ "是" if is_git else "否" }}

## 行为规则
1. 需要读写文件或执行命令时，直接调用工具完成，不要只描述做法。
2. 回答精简；信息不足时明确说明，禁止编造。
3. 执行写操作前，与用户确认目标路径。
{% if skills %}

## 可用技能
以下技能提供特定领域的完整工作指引。当用户需求与某个技能相关时：
先调用 load_skill 工具读取该技能的完整说明，再按说明执行。
{% for s in skills %}
- {{ s.name }}：{{ s.description }}
{% endfor %}
{% endif %}
```

注意 `{% if skills %}` 的用法：没有技能注册时，整个"可用技能"小节**从提示词里消失**，而不是留下一个空标题——条件块让一份模板适配多种运行形态。四个变量里 `skills` 是唯一的"内容变量"：它不是环境事实，而是注册进来的能力清单，启动时注入哪些技能直接决定模型"知道自己会什么"——这根线在 S8 收获。

渲染器 `agent/prompt.py` 值得看的是环境变量的采集与注入方式：

```python
# agent/prompt.py（节选）
def get_cwd() -> str:
    return os.getcwd()

def get_os() -> str:
    return platform.system()

def get_is_git() -> bool:
    """判断当前目录是否在 Git 仓库内（沙箱/无 git 环境返回 False）。"""
    try:
        result = subprocess.run(
            ["git", "rev-parse", "--is-inside-work-tree"],
            capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0 and result.stdout.strip() == "true"
    except Exception:
        return False


def render_prompt(name: str = "system", **extra) -> str:
    """渲染模板。内置环境变量 + 任意额外变量（如技能清单 skills）。"""
    env = Environment(loader=FileSystemLoader(_TEMPLATE_DIR), keep_trailing_newline=True)
    template = env.get_template(f"{name}.j2")
    return template.render(
        cwd=get_cwd(),
        os=get_os(),
        is_git=get_is_git(),
        **extra,
    )
```

`get_is_git` 是个好例子：环境检测本身可能失败（没装 git、目录不可读），失败时**降级为 False**而不是让启动崩溃——提示词里少一行"Git 仓库：否"，远比 Agent 起不来强。`**extra` 则让调用方可以塞进任意附加变量（比如 S8 的技能清单），模板引擎的扩展点就此留好。

最后是消费端（`s02_system_prompt.py` 节选）：渲染一次，注入 Session，之后所有调用自动携带：

```python
# s02_system_prompt.py（节选）
system_prompt = render_prompt()               # 启动时渲染一次

client = FakeClient([...])
model = Model(client=client)

session = Session(system_prompt=system_prompt)  # 成为 messages[0]
session.add_message({"role": "user", "content": "目前在哪个目录？"})
resp = model.invoke(session, stream=True)

session.add_message({"role": "user", "content": "你好"})
resp = model.invoke(session, stream=True)       # 第二次调用：system 仍在 messages[0]
```

FakeClient 的两条例子（"目前在哪个目录"→ 回目录、"你好"→ 回你好）在这里只为验证管线通不通：第二次调用后用 `model.client.calls[0]["messages"][0]` 检视，确认 system 确实排在第一位——s02 第 3 节的输出就是干这个的。

### 2.5 迭代提示词的最小工作流

提示词是"代码"，改它也要有流程。最小工作流三步：

1. **渲染检查**：改完模板跑一遍渲染，打印结果通读——查结构、查占位符、查矛盾；
2. **对照测试**：固定一组有代表性的测试问题，改前改后各跑一遍，对比回答变化；
3. **一次只改一处**：提示词没有"断点调试"，同时改三条规则后行为变了，你无法归因到任何一条——小步快改，每步验证。

再把提示词当"配置物"发布：改动走 review、与代码同一个 PR 提交，让任何人都能看到"这次行为变化对应哪段文案改动"。

第 2 步不必展开成正式的评测体系，但它能拦住八成的"改完之后模型开始胡说"。这个最小工作流的失效点就是评测的起点：测试问题攒到几十条、需要打分标准的时候，你就进入了 evaluation 的领域——超出本教程范围，但流程思想不变。

所有这些动作背后的态度只有一句话：**把提示词当代码对待**——代码要测试、要 review、要小步提交，提示词同样如此。

## 四、常见坑与边界条件

**坑 1：动态内容进系统提示词 = 每轮缓存 miss。** 最典型的反例是把 `datetime.now()` 或登录用户名渲染进提示词。每次请求提示词都不同，意味着 S3 要讲的 **prompt cache 前缀永远命不中**——最长的那段公共前缀被你自己毁掉了，等于主动放弃服务商给的折扣。收到"值得进提示词"的动态值时，先过三问：它一次运行内变不变？变了影响模型行为吗？从请求侧传行不行？三问之后大多会发现它根本不该进提示词。正确做法：要么不进提示词（用户身份从请求侧传），要么接受"启动时渲染一次、运行期间冻结"的折中（如本章的环境信息）。

**坑 2：提示词膨胀。** 规则一条条往上加，三个月后系统提示词上万 token：每轮请求都在为它付费，模型开始"选择性失聪"（规则太多反而都不遵守），改一条规则的副作用也难以预估。膨胀通常不是一次发生的，而是每次线上出问题就"加一条规则堵漏"——只加不减的提示词必然膨胀。出路是**渐进式披露**：通用规则留在系统提示词，领域知识按需加载——手写线 S8 的技能机制（`skills` 变量 + `load_skill` 工具）就是为此预留的口子；框架线第 17 章讲的也是同一件事。

**坑 3："保持静态"是原则，不是铁律。** 环境信息（cwd、os）严格说也是"运行时的动态值"，但它一次运行内不变、且对 Agent 的每轮决策都有用（"在哪个目录执行命令"是行为依据），注入的收益大于缓存代价。判断标准是**变化的频率**：一次运行内不变的可以进；每轮都变的（时间戳、随机数、对话内容）坚决不进。原则服务于目标（省缓存、保稳定），不是服务于它自己。

**坑 4：模板是代码，要按代码的标准对待。** `{% if %}` 写错、变量名拼错，Jinja2 默认渲染成空字符串而不是报错——提示词悄悄缺一块，你却毫无知觉。上线前三项快速自检：

- 占位符与渲染调用逐一对应（模板里的每个 `{{ x }}` 都有实参）；
- 每个 `{% if %}` 的两个分支都跑过一遍（有 skills / 无 skills）；
- 渲染产物里搜一遍 `{{` 和 `{%`，确认没有没被替换的残渣。

渲染结果要**在启动时打印或断言检查**（s02 的第 1 节输出就是干这个的），不要等到模型行为怪异了再回头查模板。

**坑 5：system 消息只放一条，永远放在 messages[0]。** 契约不禁止多条 system 消息，但不同服务对"多条 system"的处理并不一致（有的合并、有的只认第一条），行为不可移植。约定俗成的做法：一条 system、排在第一位。真需要"多层级指令"时，用一条 system 内部的 Markdown 小节分层，而不是多条消息。

## 五、关键结论

1. **系统提示词是模型的出厂设置**：`messages[0]` 的 system 消息，训练时被重点对待，决定模型行为的基线。
2. **五原则**：精简、自洽、全局约束、保持静态、结构化——反例的共同点是"对模型没有约束力或互相打架"。
3. **环境感知的标准做法**：模板留占位符（`system.j2`），启动时采集环境变量渲染一次（`prompt.py`），渲染结果作为 `messages[0]` 冻结。
4. **模板与代码分离**：改提示词不动代码，改环境采集不动模板；渲染结果启动时打印检查。
5. **静态性的判断标准是变化频率**：一次运行内不变的可注入，每轮都变的不进提示词。
6. **提示词膨胀的解药是渐进式披露**：通用规则常驻，领域知识按需加载（S8、框架线第 17 章）。
7. **提示词是迭代出来的**：渲染检查 → 对照测试 → 一次只改一处，和写代码一样讲流程。

## 本章要点回顾

- 同一模型表现不同，第一嫌疑人是系统提示词；它在 `messages[0]`，每次请求重传，与 S3 的 prompt cache 直接相关。
- 调试提示词第一步：把它原样打印出来，以模型的视角通读。
- 精简：删掉对模型没有约束力的礼貌与铺垫（实测 118 字 → 30 字，语义不减且多出硬约束）。
- 自洽：矛盾指令不会报错，只会让输出不稳定；全局约束：规则写成无条件短句，不给模型留例外空间。
- 结构化：Markdown 小节（`## 角色` / `## 运行环境` / `## 行为规则`）优于散文。
- 环境信息走 Jinja2 模板 + 启动时渲染一次；Deep Agents 的 `base_system_prompt`（框架线第 14 章）是同一骨架的加长版。
- 三种环境注入方案里选"启动时渲染一次"：硬编码换机器就错，每轮渲染打穿缓存。
- 信息变化越频繁，越该远离系统提示词：写死的 < 启动时注入 < 只进 history。
- 迭代提示词三步：渲染检查 → 对照测试 → 一次只改一处。
- 下一章 S3：渲染好的提示词要靠 Session 带着走——模型"失忆"的真相与两条会话纪律。
