## 二、需要调整的部分

### A. 两个真实缺陷（文档和代码都该记，优先级最高）

**A1. 手写模型层拿不到 token 账——而 ch_s07 把「计费监听器」写成现成能力。**

实测：`message` dict 里没有 `usage` 键；流式路径 `InvokeResult.raw` 被 `model.py:82` 显式置为 `None`；`_normalize_message` 与 `_StreamAssembler` **都不读 usage**。非流式的 `raw.usage` 倒是有值（`{'completion_tokens':2,'prompt_tokens':18,...}`），但没人消费它。

而 `ch_s07_agent.md:187` 的监听器表格写着：

> | 计费监听器 | 在 `complete` 事件里累计 usage token |

`complete` 事件只携带 `message`（`model.py:225`），**当前结构下这条实现不了**。`ch_s06_react.md:88`、`ch_s07_agent.md:9` 有同类暗示。要么补一处把 usage 透出来，要么把这条改成「需要自己补」并说明补在哪。

**A2. 流式装配器扛不住 `stream_options={"include_usage": true}`。**

`model.py:155` 是 `self._feed(chunk.choices[0].delta)`，对**空 `choices`** 无防护。实测构造 OpenAI 该模式下的 usage-only 尾块（`choices: []`）→ **`IndexError: list index out of range`**（见 `stream_robustness_probe.txt`）。

这条与 A1 是同一个洞的两面：**「流式 + 计费」这条路当前完全走不通**，而 include_usage 恰恰是流式下拿 token 账的唯一途径。修法是一行的守卫。

> 注：`choices` 在 SDK 类型里是 required 的 list，空数组是合法取值；「OpenAI 在 include_usage 下会发空 choices 尾块」是官方文档行为，本机未对真 OpenAI 验证。

### B. 标注纪律：同一套教程内部标准不齐

**B1. S4 / S5 把假模型的写死剧本当成模型行为叙述，且没有就地标注。**

- `ch_s04_tools.md:176-199`「模型返回的原始响应」「`content` 是 null，**模型这次一个字的正文都没说**，全部输出花在了点菜上」——真实来源是 `s04_tools.py:82-92` 硬编码的 `tool_calls=[...]`，`filepath` 由脚本自己 `mkdtemp` 后回填。**模型没有「选」过工具、也没填过参数。**
- S4 全章唯一一处提到 `FakeClient` 在 `:274` 的「坑一」里，**没有贴在 §3 的叙事上**；**S5 一处都没有**（计数 0）。
- 对照：S6 / S7 / S8 各有 4 / 4 / 3 处「假模型 / 剧本」标注。

**B2. 两个 README 承诺的标注并不存在。**

`handwritten/README.md:85` 与 `code/README.md:86-88` 都写「正文**逐处**标注『需 API Key，未实测』」——实测 `ch_s01`～`ch_s05` 的「未实测」计数**全为 0**。承诺与交付不符。

## 三、判断

**需要调整，但性质和框架线不同。**

框架线的问题是**代码结论被写歪**（单边当双边、读源码当实测），改动面 27 个文件。
手写线的问题是**文档没跟上代码**：代码本身在真实模型下零逻辑错误，配图、骨架、依赖、协议实现、HTML 生成链全部合规。

按投入产出排序：

1. **A1 / A2 两个真缺陷**——只有 2 处，但一个是「把做不到的事写成现成能力」，一个是实测崩溃。必须改。
2. **B1 / B2 标注纪律**——S4、S5 补就地标注 + 两个 README 的失实承诺。这是手写线的教学可信度问题，且与框架线刚立的四级口径正好对齐。
3. **C 过期声明 4 处**——机械修改。
4. **D 事实错误 12 条**——逐条订正，都是小改动。
5. **E 留证缺口**——可选：把探针脚本入库，比改措辞更值钱。

**总计约 30 处，集中在 2 个 README + 6 个章节（S1/S4/S5/S6/S7/S8/S10）**，比框架线小一个量级。
