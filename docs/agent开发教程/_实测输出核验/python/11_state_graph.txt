② 同一线程再次 invoke：输入值按各字段自己的 reducer 合并
==============================================================================
  第 1 次，输入 {'n': 0, 'trail': ['起点']}  → n=1    trail=['起点', '→1']
  第 2 次，输入 None                       → n=1    trail=['起点', '→1']
  第 3 次，输入 {}                         → n=2    trail=['起点', '→1', '→2']
  第 4 次，输入 {'n': 100}                 → n=101  trail=['起点', '→1', '→2', '→101']
  第 5 次，输入 {'trail': ['插一条']}         → n=102  trail=['起点', '→1', '→2', '→101', '插一条', '→102']

  逐行读：
  · 第 1 次：给了 n=0 和 trail，节点 +1 得 n=1
  · 第 2 次：输入是 None —— **空操作**！已跑完的线程没有待执行任务，
            直接返回当前状态，什么都没发生（n 仍是 1）
  · 第 3 次：输入是 {} —— 和 None **不一样**：图会从检查点状态重新执行，
            节点读到检查点里的 n=1，+1 得 2
  · 第 4 次：输入里给了 n=100，按默认 reducer（覆盖）冲掉检查点的 2，再 +1 得 101
  · 第 5 次：输入里只有 trail，n 沿用检查点的 101，节点 +1 得 102；
            trail 有 operator.add，输入值被**追加**而不是替换

  结论（实测口径）：
  ① 输入字典里**出现**的字段 → 按该字段自己的 reducer 合并进检查点状态
  ② 输入字典里**没出现**的字段 → 保留检查点里的值
  ③ `invoke(None, cfg)` 是空操作；`invoke({}, cfg)` 才是「从检查点续跑」
  ⚠️ 第 ①②条很容易踩：以为「同一线程会累积」，结果标量字段被输入悄悄重置。

④ Send：map-reduce 式的并行派发
==============================================================================
  items   = ['a', 'b', 'c']
  results = ['a 处理完毕', 'b 处理完毕', 'c 处理完毕']
  → 三个 worker 在**同一个 super-step** 里并行执行；
    结果靠 results 字段的 operator.add reducer 汇总——这就是 map-reduce。

⑤ Overwrite：想清空合并型字段时怎么办
==============================================================================
  不包 Overwrite：log = ['旧值'] + [] = ['旧值']  ← 清不掉
  包了 Overwrite：log = []
  → Overwrite 是绕过 reducer 的显式指令，专门用来「我就是要覆盖」。

⑥ add_sequence 与静态扇入：顺序、并行汇合
==============================================================================
  add_sequence([a, b]) → ['a', 'b']
  静态扇入 START→left/right→join → ['left', 'right', 'join<-left,right']
  → add_edge([a, b], 'join') 的含义是「等 a、b 都完成后再跑 join」；
    Python 侧一次传 list 即可，TS 侧同样是 addEdge(['left','right'], 'join')。

⑦ 循环与 recursion_limit：本机默认 10007
==============================================================================
  循环到 n>=3 自动退出 → {'n': 3}
  recursion_limit=3 → GraphRecursionError: Recursion limit of 3 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key.
  → 本机 langgraph 1.2.12 的默认上限是 10007（源码核对）；
    讲义/旧文档里的 25、1000、10000 都随版本变化，生产代码请显式传值。
  节点看到的 remaining_steps = 4
  recursion_limit=5 时 → {'n': 1}
  → RemainingSteps 是 LangGraph 注入的 managed 值：进入节点时还剩几步；
    Python 侧从 langgraph.managed 导入；JS 1.4.17 没有同名导出（差异已登记）。

⑧ RetryPolicy / async timeout / CachePolicy
==============================================================================
  RetryPolicy(max_attempts=3) → {'n': 1}，实际尝试 3 次
  async 节点 timeout=0.05s → NodeTimeoutError: Node 'slow' exceeded its run timeout of 0.050s
  ⚠️ 同步节点不能设 timeout：compile() 会直接抛 ValueError（Python 无法安全取消同步执行），
     所以示例用 async 节点；这条不是配置问题，是运行时限制。
  同一输入调用两次 CachePolicy(ttl=60) → 节点实际执行 1 次
  → 只缓存「纯节点」；有副作用（写库、发消息、扣款）的节点不要开缓存。

⑨ Functional API：@entrypoint / @task
==============================================================================
  @entrypoint 串行：3 → add_one → triple = 12
  两个 @task 并行后汇总：(3+1) + (3×3) = 13
  → Graph API 用节点/边描述形状；Functional API 用普通函数调用描述同一件事。
    需要可视化、中断、子图时优先 Graph API；逻辑本身就是一条函数链时 Functional 更直接。
