① 一次 agent 调用产生的 trace 树
==============================================================================
├─ [chain] price_lookup  (4.0 ms)
  ├─ [chain] model  (1.1 ms)
    ├─ [llm  ] ScriptedChatModel  (0.4 ms)
  ├─ [chain] tools  (1.3 ms)
    ├─ [tool ] get_price  (0.3 ms)
  ├─ [chain] model  (0.3 ms)
    ├─ [llm  ] ScriptedChatModel  (0.1 ms)

  共 7 个 run，根节点 1 个

  结构读法：
    chain  ── 整次 agent 调用（对应 LangSmith 里的一个 trace）
      └ chain ── 图里的 model 节点
          └ llm ── 真正那次模型请求
      └ chain ── 图里的 tools 节点
          └ tool ── 真正那次工具执行

  ⚠️ 每个 run 都有自己的 input / output，所以「第几次模型调用说了什么」
     是可以逐层下钻看到的——这就是能查清「agent 为什么走了这一步」的原因。
     没有 trace 的话，你只能看到最终答案，中间过程是个黑盒。

==============================================================================
② 离线评测的最小骨架
==============================================================================
  #   用例             调用的工具          判定
  ----------------------------------------------------
  1   A-1 多少钱？       get_price      ✅ 通过
  2   B-2 多少钱？       get_price      ✅ 通过
  3   你好             None           ✅ 通过

  结果：3/3 通过

  评测的两个层次（别只做第一层）：
    ① 结果对不对 —— 最终答案是否满足预期（本例做的就是这层）
    ② 过程对不对 —— 工具选得对不对、调了几次、有没有绕路
       第二层才是 agent 评测和普通 LLM 评测的分水岭：
       答案碰对了但过程全错，换个输入就会崩。

  ⚠️ 本示例的「判定」是字符串匹配，只是骨架。真实项目里判定器本身也要评测——
     用 LLM 当裁判会引入位置偏差、冗长偏差、自我偏好、风格偏差四类系统性问题。

③ 该盯哪几个数
==============================================================================
  ┌────────────────┬──────────────────────────────────────────────┐
  │ 指标           │ 为什么盯它                                    │
  ├────────────────┼──────────────────────────────────────────────┤
  │ 模型调用次数   │ agent 的成本基本正比于它；失控循环也看这个    │
  │ 输入 token     │ 每轮都要重发完整历史，涨得比你想的快          │
  │ 缓存命中率     │ 命中与否，单价可能差一个数量级                │
  │ 工具调用次数   │ 工具选错 / 反复重试，看这里最直观             │
  │ 端到端 P95     │ 平均延迟掩盖长尾，而用户体验由长尾决定        │
  └────────────────┴──────────────────────────────────────────────┘

  ⚠️ 本示例的 trace 是离线回调，只记了耗时；token 与成本字段需要真实模型
     返回的 usage 元数据，本机无 API Key，未实测——以官方文档为准。
