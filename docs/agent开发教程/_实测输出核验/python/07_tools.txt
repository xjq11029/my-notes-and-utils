========================================================================
① 工具的 schema 从哪来
========================================================================
  工具名（取自函数名）: search_orders
  工具描述（取自 docstring）: '按关键词搜索订单。\n\nArgs:\n    query: 搜索关键词\n    limit: 最多返回多少条'
  参数 schema: dict_keys(['query', 'limit'])
  → 模型看到的就只有这三样东西；docstring 写得含糊，模型就会选错工具。

========================================================================
② ToolRuntime：工具里读取 state / context / store
========================================================================
  工具返回值: 历史 2 条 | tenant=t-7 | store 回读={'tenant': 't-7'}
  → runtime 参数对模型不可见：模型只看到工具名和描述，不会看到 user_id 之类的东西。
  → 旧写法 InjectedState / InjectedStore / get_runtime() 在 v1 已由 runtime 统一取代。

========================================================================
③ 工具返回 Command：直接修改状态
========================================================================
  最终 state['user_name'] = '小明'
  → 工具不再只能返回字符串：返回 Command 就能顺手改状态，省掉一轮模型调用。

========================================================================
④ 工具出错怎么办：wrap_tool_call 把异常变成 ToolMessage
========================================================================
  [中间件] 捕获到异常：ZeroDivisionError，转成 ToolMessage
  1. [HumanMessage] '1 除以 0'
  2. [AIMessage] ''  tool_calls=[('divide', {'a': 1, 'b': 0})]
  3. [ToolMessage] '工具执行失败：division by zero。请换一个参数再试。'
  4. [AIMessage] '除数不能为 0，我换个数再算。'

  对比一下两种做法的后果：
  · 让异常直接抛出去 → 整个 agent 调用崩掉，用户看到 500；
  · 转成 ToolMessage    → 模型读到「失败了，换个参数」，自己纠错继续。

  ⚠️ 注意：v1 已经**不再**使用 ToolException / handle_tool_error 这套旧 API。
     要么像上面这样自己写 wrap_tool_call，要么直接用内置的 ToolErrorMiddleware。
