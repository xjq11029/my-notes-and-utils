==============================================================================
① supervisor 拓扑：agent 当节点
==============================================================================
  输入 '帮我查一下数据库'       → route=end   最终回复='查到 3 行。'
    supervisor 决策序列 = ['db', 'end']   ← 派出去 → 收回来 → 结束
  输入 '帮我发个邮件'         → route=end   最终回复='邮件已发。'
    supervisor 决策序列 = ['mail', 'end']   ← 派出去 → 收回来 → 结束

  ⚠️ create_agent 返回的就是**已编译的图**，所以可以直接 add_node。
     副作用：它变成了子图，流式输出需要 subgraphs=True（见第 13 章示例）。
     记得给每个 agent 起 name=，否则 trace 里分不清是谁在跑。

==============================================================================
② handoff 拓扑：用 Command 交棒
==============================================================================
  输入 '我要问账单'        → owner=billing  回复='[账单组] 已处理'
  输入 '系统报错了'        → owner=tech     回复='[技术组] 已处理'

  supervisor vs handoff 的区别：
    supervisor  有一个「调度者」节点反复决定下一步交给谁，交完还能收回来；
    handoff     交棒后**不回来**，接手的 agent 负责到底——更像「转人工」。
    前者适合需要多轮协调的任务，后者适合一次分流就结束的场景。

==============================================================================
③ 从旧版迁移到 v1
==============================================================================
  能力           旧版写法                                   v1 写法
  --------------------------------------------------------------------------------------------
  建 agent      AgentExecutor(agent=..., tools=...)    create_agent(model, tools)
  调用           executor.invoke({'input': '...'})      agent.invoke({'messages': [...]})
  输入形态         字符串 input                              消息列表 messages
  输出形态         {'output': '...'}                      {'messages': [...]}，取 messages[-1]
  提示词          prompt 模板字符串                           system_prompt= + middleware
  记忆           memory=ConversationBufferMemory()      checkpointer + thread_id
  工具错误         handle_tool_error / ToolException      @wrap_tool_call 或 ToolErrorMiddleware
  运行时注入        InjectedState / InjectedStore          runtime: ToolRuntime
  链式拼装         LCEL 的 `|` 管道                          StateGraph 的 add_node / add_edge
  扩展点          自定义 Agent / 继承                         middleware 的六个钩子

  迁移的心智转变（比记 API 更重要）：
    · 旧版：agent 是一个**组件**，你用 LCEL 把它串进链里；
    · v1 ：agent 是一张**图**，你用节点和边定义控制流，用中间件扩展行为。
    所以「迁移」不是换函数名，而是把控制流从链式表达改成图表达。

  建议顺序：① 先把 AgentExecutor 换成 create_agent（接口迁移，非行为等价）；
            ② 再把 LCEL 的编排改成 StateGraph（这一步才真正动结构）；
            ③ 最后把自定义逻辑收进 middleware。
            一次全改，出了问题分不清是哪一步引入的。

==============================================================================
④ 部署形态
==============================================================================
  托管（Agent Server）
    · 持久化（checkpointer / store）由服务端自动提供，不用自己配
    · 自带 trace、评测、人工审批的 UI
    · 代价：绑定平台，本地调试与线上环境的差异要自己盯

  自托管
    · 自己接 Postgres 做检查点与 Store，自己接观测后端
    · 自由度最高，但「持久化」这件事必须一开始就做对——
      中途从 InMemorySaver 换到 PostgresSaver，历史数据是搬不过去的

  ⚠️ 无论哪种形态，上线前都该确认三件事：
     ① 检查点有没有持久化（进程重启会不会丢会话）
     ② 有没有调用次数上限（模型调用 / 工具调用都要限）
     ③ 高风险操作有没有人在回路（扣款、发邮件、删文件）
