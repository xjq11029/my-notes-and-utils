========================================================================
① 一次工具调用的完整往返
========================================================================
  1. [HumanMessage] "上海天气怎么样？"
  2. [AIMessage] ""  tool_calls=[["get_weather",{"city":"上海"}]]
  3. [ToolMessage] "上海: 22C sunny"
  4. [AIMessage] "上海 22°C，晴。"

  模型从没执行过工具——它只输出「请调用 get_weather」；
  真正执行并把结果写回上下文的是框架的 tools 节点。

========================================================================
② messages 只追加（append-only）
========================================================================
  第 1 轮后，历史里有 2 条消息
  第 2 轮后，历史里有 4 条消息（不是 2 条）
  1. [HumanMessage] "你好，我叫小明。"
  2. [AIMessage] "你好，我是脚本模型。"
  3. [HumanMessage] "我叫什么？"
  4. [AIMessage] "你刚才说你叫小明。"

  第二次 invoke 传进去的那条消息是被**追加**进去的，而不是替换掉旧历史——
  这就是 messages 字段的 addMessages reducer 在起作用。

========================================================================
③ thread_id（对话作用域）与 context（单次运行作用域）
========================================================================
  工具看到的 context：user_id=u-42
  → thread_id 决定「这段历史属于哪次对话」，会被写进检查点；
  → context 是「这一次运行」的随身数据，不写进检查点，也不进消息历史。

========================================================================
④ 结构化输出：responseFormat
========================================================================
  result.structuredResponse = {"city":"上海","tempC":22}
  → 与 Python 一样拿到按 schema 解析的对象，不用自己 JSON.parse。
  → 参数不合法时框架走「校验失败写回 ToolMessage → 模型重试」（见 04 示例第 ⑥ 节）。

  ⚠️ 假模型回普通文本而不回工具调用时，structuredResponse 是 undefined——
     策略没被命中，框架不报错；真实模型下由模型自己决定调不调这个工具。
  ⚠️ 「JS 默认走 provider 原生 JSON schema」只对 provider 子类成立（未实测）；
     裸 schema 与纯 BaseChatModel 子类的默认策略都是工具调用（源码可证）。
