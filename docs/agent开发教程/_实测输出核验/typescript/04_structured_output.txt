========================================================================
① 手动链路 vs withStructuredOutput
========================================================================
  JSON.parse 成功，拿到对象：{"name":"张三","age":"三十","occupation":"软件工程师"}
  手动校验 typeof data.age === "number" → false
  → 少写一个 if，这个「三十」就会一路流到下游数据库里。
  withStructuredOutput(Person) → {"name":"张三","age":30,"occupation":"软件工程师"}
  直接点属性：person.name="张三" person.age=30
  → zod 的 .describe() 会被转成 JSON Schema 交给模型，字段约束与解析一次配好。
  默认策略把 schema 绑成的工具名 = [["extract"]]

========================================================================
② schema 形态：zod 与 JSON Schema dict
========================================================================
  zod          → {"name":"张三","age":30,"occupation":"软件工程师"}   绑定工具名=[["extract"]]
  JSON Schema  → {"name":"张三","age":30,"occupation":"软件工程师"}   绑定工具名=[["extract"]]
  → 两种形态在基类实现里都落到「工具名 extract」这一个工具上，只能用 name 选项改名。
     与 Python 不同：Python 那边工具名取类名（Person / PersonDict / PersonDC / title）。

  ⚠️ JS 只有两种可运行时使用的形态。Python 的 TypedDict 与 @dataclass 在 JS 侧**没有等价物**：
     TS 的 interface / type 编译后就被擦除，运行时拿不到字段信息，传进去只会报错。
     实测：withStructuredOutput(undefined) → TypeError: Cannot use 'in' operator to search for 'description' in unde

========================================================================
③ 两种策略：method 参数
========================================================================
  不传 config（默认） → {"name":"张三","age":30,"occupation":"软件工程师"}
  method=functionCalling → {"name":"张三","age":30,"occupation":"软件工程师"}
  method=jsonSchema → {"name":"张三","age":30,"occupation":"软件工程师"}
  method=jsonMode → Error: Base withStructuredOutput implementation only supports "functionCalling" as a me
  name=Person → {"name":"张三","age":30,"occupation":"软件工程师"}
  → 实测（@langchain/core 1.2.12）：基类只认 function calling——`jsonMode` 直接抛错，
     其余 method 值被忽略；默认工具名是 `extract`（可用 name 覆盖）。
     「JS 默认走 json_schema」说的是 **provider 子类**（如 ChatOpenAI）；
     在纯 BaseChatModel 子类上，默认就是工具调用。**真实 provider 的请求体已实测（见 code/README B）。**

========================================================================
④ 类型校验：JS 基类不校验
========================================================================
  age 传中文 → {"name":"张三","age":"三十","occupation":"工程师"}
  漏填 age/occupation → {"name":"张三"}
  → 基类实现里解析器只做「找到这条 tool_call 就返回它的 args」，**没有一步校验**。
     同一个 schema 在 Python 侧会抛 ValidationError——这是双语言最容易踩空的一处。
     想要校验，走 agent 侧的工具策略（第 ⑥ 节），那条路径会用 zod 校验。

========================================================================
⑤ includeRaw：拿到原始响应
========================================================================
  keys = ["raw","parsed"]
  parsed = {"name":"张三","age":30,"occupation":"软件工程师"}
  raw 类型 = AIMessageChunk
  → JS 只有 { raw, parsed }；Python 多一个 parsing_error，且解析失败时 parsed 为 null。

⑥ 与 agent 侧 responseFormat 的关系
========================================================================
  toolStrategy(Person) 的策略工具名 = "Person"
  state.structuredResponse = {"name":"张三","age":30,"occupation":"软件工程师"}
  1. [HumanMessage] "张三是一名 30 岁的软件工程师"
  2. [AIMessageChunk] ""  tool_calls=[["Person",{"name":"张三","age":"三十","occupation":"工程师"}]]
  3. [ToolMessage] "Failed to parse structured output for tool 'Person':\n  - ..."
  4. [AIMessageChunk] ""  tool_calls=[["Person",{"name":"张三","age":30,"occupation":"软件工程师"}]]
  5. [ToolMessage] "{\"name\":\"张三\",\"age\":30,\"occupation\":\"软件工程师\"}"
  6. [AIMessage] "Returning structured response: {\"name\":\"张三\",\"age\":30,\"occ..."
  模型被调用 2 次：第一次参数非法，框架把错误写回 ToolMessage，模型自己改对了。
  providerStrategy(Person) → {"name":"张三","age":30,"occupation":"软件工程师"}
  → 分工：模型侧由 withStructuredOutput 决定怎么绑，agent 侧由 responseFormat 决定用哪种策略，
     且工具策略多一步「校验失败自动重试」。这是第 5 章的主题。
