② 同一线程再次 invoke：输入值按各字段自己的 reducer 合并
==============================================================================
  第 1 次，输入 {"n":0,"trail":["起点"]}     → n=1    trail=["起点","→1"]
  第 2 次，输入 null                       → n=1    trail=["起点","→1"]
  第 3 次，输入 {}                         → n=2    trail=["起点","→1","→2"]
  第 4 次，输入 {"n":100}                  → n=101  trail=["起点","→1","→2","→101"]
  第 5 次，输入 {"trail":["插一条"]}          → n=102  trail=["起点","→1","→2","→101","插一条","→102"]

  逐行读：
  · 第 1 次：给了 n=0 和 trail，节点 +1 得 n=1
  · 第 2 次：输入是 null —— **空操作**！已跑完的线程没有待执行任务，
            直接返回当前状态（n 仍是 1）
  · 第 3 次：输入是 {} —— 和 null **不一样**：图会从检查点状态重新执行，
            节点读到检查点里的 n=1，+1 得 2
  · 第 4 次：输入里给了 n=100，按默认 reducer（覆盖）冲掉检查点的 2，再 +1 得 101
  · 第 5 次：输入里只有 trail，n 沿用检查点的 101，节点 +1 得 102；
            trail 有 concat reducer，输入值被**追加**而不是替换

  结论（实测口径，Python / JS 一致）：
  ① 输入字典里**出现**的字段 → 按该字段自己的 reducer 合并进检查点状态
  ② 输入字典里**没出现**的字段 → 保留检查点里的值
  ③ `invoke(null, cfg)` 是空操作；`invoke({}, cfg)` 才是「从检查点续跑」

④ Send：map-reduce 式的并行派发
==============================================================================
  items   = ["a","b","c"]
  results = ["a 处理完毕","b 处理完毕","c 处理完毕"]
  → 三个 worker 在**同一个 super-step** 里并行执行；
    结果靠 results 字段的 concat reducer 汇总——这就是 map-reduce。

⑤ Overwrite：想清空合并型字段时怎么办
==============================================================================
  log = []
  → 直接返回 [] 是**没用的**（concat 会把 [] 拼上去，旧值还在）；
    包一层 new Overwrite([]) 才是「我就是要覆盖」的显式指令。
