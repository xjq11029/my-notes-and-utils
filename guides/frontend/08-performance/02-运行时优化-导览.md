## 一、核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | 运行时优化关注页面加载完成后用户操作过程中的性能表现，核心在于避免 JavaScript 主线程阻塞 |
| 能做什么 | 保持 60fps 流畅帧率（每帧约 16.6ms），避免主线程长任务（Long Task > 50ms），确保用户交互即时响应 |
| 怎么用 | 通过防抖节流控制高频事件、减少回流重绘、虚拟列表渲染大数据、Web Worker 处理 CPU 密集计算、框架级优化避免不必要渲染 |
| 原理和工作流程 | 浏览器主线程同时负责 JS 执行、样式计算、布局、绘制和合成，任何长时间占用主线程的操作都会导致页面卡顿和响应延迟。运行时优化的核心策略包括：控制事件触发频率（防抖节流）、减少 DOM 操作开销（回流重绘优化）、减少 DOM 节点数量（虚拟列表）、将计算移出主线程（Web Worker）、框架级跳过不必要渲染（React.memo/useMemo、Vue v-once/v-memo） |
| 缺点 | 运行时优化需要理解浏览器渲染原理，门槛较高；过度优化可能导致代码可读性下降 |

## 二、底层原理

### 防抖与节流

| 维度 | 内容 |
|------|------|
| 是什么 | 防抖在事件连续触发时只执行最后一次（每次重置计时器）；节流在固定时间间隔内只执行一次（记录上次执行时间） |
| 能做什么 | 控制高频事件（输入、滚动、resize、鼠标移动）的触发频率，减少不必要的计算和 DOM 操作 |
| 怎么用 | 防抖：`searchInput.addEventListener('input', debounce(fetchSearchResults, 300))`；节流：`window.addEventListener('scroll', throttle(updateScrollProgress, 100))` |
| 原理和工作流程 | 防抖：每次触发重置计时器，停止触发后延迟 N 毫秒才执行，适用搜索输入、窗口 resize、按钮防重复提交。节流：记录上次执行时间，间隔不足 N 毫秒则跳过，适用滚动事件、鼠标移动、无限滚动加载。防抖关注"最后一次"，节流关注"均匀分布" |
| 缺点 | 防抖在持续触发期间完全不执行，可能导致用户看不到中间反馈；节流在快速操作时可能丢失关键事件 |

### 回流与重绘优化

| 维度 | 内容 |
|------|------|
| 是什么 | 回流是元素几何属性变化导致重新布局（开销大），重绘是外观属性变化不影响布局（开销较小），回流一定触发重绘 |
| 能做什么 | 通过批量修改 DOM、使用 DocumentFragment、离线 DOM、transform 动画、读写分离、requestAnimationFrame 等策略减少回流次数 |
| 怎么用 | 批量修改：`el.className = 'new-style'` 替代逐条修改 style；transform：`transform: translateY(100px)` 替代 `top: 100px`；读写分离：先批量读取属性再批量写入 |
| 原理和工作流程 | 触发回流的操作：添加/删除 DOM、修改宽高/边距/定位、读取 offsetTop/scrollTop/clientWidth/getComputedStyle 等属性（触发强制同步布局）、修改字体大小。优化策略：批量修改 DOM 用 className 一次性应用、DocumentFragment 在内存中构建后一次性插入、离线 DOM 先 display:none 操作后恢复、transform 和 opacity 只触发合成不触发回流、读写分离避免 Layout Thrashing、requestAnimationFrame 在下一帧批量更新 |
| 缺点 | 读写分离增加代码复杂度；transform 不能替代所有动画场景 |

### 虚拟列表

| 维度 | 内容 |
|------|------|
| 是什么 | 只渲染可视区域内的 DOM 节点，根据 scrollTop 动态计算 startIndex 和 endIndex，通过 padding 或 transform 模拟完整滚动高度 |
| 能做什么 | 解决大数据量列表（1000+ 条）直接渲染导致的内存占用高、渲染卡顿问题 |
| 怎么用 | React：`<FixedSizeList height={600} itemCount={items.length} itemSize={50}>{({ index, style }) => <div style={style}>{items[index]}</div>}</FixedSizeList>`；Vue：`<RecycleScroller :items="list" :item-size="50" key-field="id" v-slot="{ item }">` |
| 原理和工作流程 | 核心变量：startIndex = Math.floor(scrollTop / itemHeight)、endIndex = startIndex + visibleCount + bufferSize（bufferSize 避免快速滚动白屏）、offsetY 通过 padding-top 或 transform: translateY 模拟滚动偏移。常用库：react-window（轻量 < 3KB）、react-virtuoso（分组/粘性头部）、vue-virtual-scroller（Vue 官方推荐）、vxe-table（表格内置虚拟滚动） |
| 缺点 | 每项高度不固定的场景（动态高度）实现复杂；需要设置 overscan 缓冲区避免快速滚动白屏；虚拟列表内无法使用锚点定位 |

### 大文件分片上传

| 维度 | 内容 |
|------|------|
| 是什么 | 利用 Blob.slice() 将大文件切分为多个小块（如 5MB/片），分片上传，支持断点续传和秒传 |
| 能做什么 | 解决大文件上传超时、失败后需重传整个文件的问题，提升上传可靠性和用户体验 |
| 怎么用 | `const chunk = file.slice(i * chunkSize, (i + 1) * chunkSize)`；spark-md5 计算文件哈希；`Promise.all(pendingChunks)` 并发上传 |
| 原理和工作流程 | 文件分片：Blob.slice(start, end) 切分为固定大小分片。文件哈希：spark-md5 增量计算 MD5 作为文件唯一标识。并发上传：控制同时上传的分片数量（3-5 个）。断点续传：上传前查询服务端已上传分片列表，跳过已上传分片。秒传：根据文件哈希查询服务端是否已有相同文件，有则直接返回。所有分片上传完成后通知服务端合并分片 |
| 缺点 | 需要服务端配合实现分片接收、合并和去重；大文件哈希计算可能阻塞主线程，需用 Web Worker |

### 内存泄漏排查

| 维度 | 内容 |
|------|------|
| 是什么 | 常见内存泄漏场景包括全局变量、未清除定时器、闭包引用、DOM 引用、未解绑事件监听、WebSocket 未关闭，通过 Chrome DevTools 的堆快照和时间轴录制排查 |
| 能做什么 | 识别和修复内存泄漏，避免页面长时间运行后越来越卡顿甚至崩溃 |
| 怎么用 | Performance 面板勾选 Memory 录制 → 观察 JS Heap 是否持续上升 → 手动 GC 后是否回落 → Memory 面板堆快照对比 Delta → 搜索 "Detached" 查找分离 DOM 节点 |
| 原理和工作流程 | 排查步骤：录制 Performance（勾选 Memory）→ 执行可疑操作 → 观察 JS Heap 蓝色线是否持续上升 → 手动触发 GC（垃圾桶图标）→ 内存未回落则存在泄漏 → 切换到 Memory 面板拍摄两次堆快照对比 Delta → 搜索 "Detached" 查找已从 DOM 树移除但 JS 仍引用的节点。常见泄漏修复：组件卸载时 clearTimeout/clearInterval、removeEventListener、断开 WebSocket、使用 WeakMap/WeakSet 存储 DOM 引用 |
| 缺点 | 堆快照分析需要经验，大型应用快照体积大难以分析；某些泄漏只在特定操作序列下触发 |

### Web Worker 提升性能

| 维度 | 内容 |
|------|------|
| 是什么 | Web Worker 在独立后台线程中执行 JavaScript，不阻塞主线程，通过 postMessage 与主线程通信 |
| 能做什么 | 处理 CPU 密集型计算（大数据排序/过滤、图像处理、加密解密、大规模 JSON 解析、实时数据流处理），保持主线程响应 |
| 怎么用 | 使用 Comlink 简化通信：worker.js 中 `expose({ heavyCalculation })`，主线程中 `const worker = wrap(new Worker('./worker.js'))`；`const result = await worker.heavyCalculation(largeData)` |
| 原理和工作流程 | Worker 在独立线程中运行，无法访问 DOM/window/document，通过 postMessage 通信（结构化克隆传递数据）。Comlink 库将 postMessage 包装为 Promise 风格的 RPC 调用。对于大数据传递，使用 Transferable Objects（如 ArrayBuffer）转移数据所有权而非复制，避免内存开销。SharedArrayBuffer 允许主线程和 Worker 共享内存 |
| 缺点 | 无法操作 DOM；postMessage 大数据复制开销大（需用 Transferable Objects）；Worker 创建和通信有开销，简单任务不适合 |

### SSR SSG ISR 对比

| 维度 | 内容 |
|------|------|
| 是什么 | SSR 每次请求服务端渲染（实时），SSG 构建时预渲染静态页面（最快），ISR 首次请求时生成后续复用（可配置 revalidate 间隔） |
| 能做什么 | 根据页面数据新鲜度需求和服务器成本选择合适的渲染模式，平衡 SEO、首屏速度和服务器压力 |
| 怎么用 | Next.js：SSR 用 `getServerSideProps`、SSG 用 `getStaticProps`、ISR 用 `getStaticProps` + `revalidate: 60` |
| 原理和工作流程 | SSR：每次请求在服务端渲染完整 HTML，数据实时，首屏快，SEO 友好，但服务器压力大。SSG：构建时预渲染为静态 HTML，数据新鲜度低，首屏最快，服务器压力最低。ISR：首次请求时生成静态页面并缓存，revalidate 秒后下次请求触发后台重新生成，结合 SSR 实时性和 SSG 性能。框架支持：Next.js（React）、Nuxt.js（Vue） |
| 缺点 | SSR 服务器压力大需缓存策略；SSG 构建时间长（大型站点）；ISR 首次访问仍可能较慢 |

### React Vue 层面的性能优化

| 维度 | 内容 |
|------|------|
| 是什么 | React 通过 React.memo/useMemo/useCallback 避免不必要重渲染；Vue 通过 v-once/v-memo/shallowRef/computed 缓存跳过更新 |
| 能做什么 | 在框架层面减少不必要的组件渲染和计算，提升运行时性能 |
| 怎么用 | React：`React.memo` 包裹组件 props 浅比较、`useMemo` 缓存计算结果、`useCallback` 缓存函数引用、避免内联对象/函数、稳定唯一的 key。Vue：`v-once` 渲染一次后冻结、`v-memo` 缓存子树、`shallowRef/shallowReactive` 只跟踪第一层属性、`computed` 自动缓存 |
| 原理和工作流程 | React.memo：对 props 做浅比较，相同则跳过渲染。useMemo：依赖不变时返回缓存值。useCallback：依赖不变时返回同一函数引用。Vue 的响应式系统自动追踪依赖，但 v-once 跳过依赖追踪，v-memo 手动指定依赖数组，shallowRef 只追踪 .value 的引用变化。computed 在依赖不变时直接返回缓存值 |
| 缺点 | useMemo/useCallback 滥用增加代码复杂度且缓存开销超过收益；React.memo 浅比较可能漏掉深层变化 |

## 三、实战应用

### 防抖节流在业务中的实际应用

| 维度 | 内容 |
|------|------|
| 是什么 | 三类典型业务场景：搜索输入防抖 300ms、滚动加载节流 200ms、按钮防重复提交（leading 模式首次立即执行） |
| 能做什么 | 减少不必要的 API 请求和 DOM 操作，提升用户体验 |
| 怎么用 | 搜索防抖：`searchInput.addEventListener('input', debounce(async (e) => { fetch(`/api/search?q=${e.target.value}`) }, 300))`；滚动节流：`window.addEventListener('scroll', throttle(loadMoreData, 200))`；按钮防重复：leading 模式首次立即执行，后续 N 毫秒内忽略 |
| 原理和工作流程 | 搜索防抖：用户停止输入 300ms 后才发送请求，避免每次按键都触发 API 调用。滚动节流：每 200ms 最多触发一次加载更多判断。按钮防重复：leading 模式首次立即执行，设置定时器在 N 毫秒后清除标记，期间再次点击直接忽略 |
| 缺点 | 防抖延迟过长影响交互体验；leading 模式下无法取消已触发的操作 |

### 虚拟列表集成示例

| 维度 | 内容 |
|------|------|
| 是什么 | Vue 3 中集成 vue-virtual-scroller 的 RecycleScroller 组件，实现固定高度虚拟列表 |
| 能做什么 | 渲染 10000+ 条数据只创建约 20-30 个 DOM 节点，保持页面流畅 |
| 怎么用 | `<RecycleScroller class="scroller" :items="list" :item-size="50" key-field="id" v-slot="{ item }"><div class="item">{{ item.name }}</div></RecycleScroller>` |
| 原理和工作流程 | RecycleScroller 根据容器高度和 itemSize 计算 visibleCount，根据 scrollTop 计算 startIndex，只渲染可视范围内的数据。key-field 用于 DOM 复用追踪。滚动时回收离开可视区的 DOM 节点并重新绑定新数据 |
| 缺点 | 需要每项高度固定或预先计算；内部元素不能使用复杂的 CSS 定位 |

### 内存泄漏避免 Checklist

| 维度 | 内容 |
|------|------|
| 是什么 | 组件卸载时的清理清单：定时器、事件监听、WebSocket、全局大对象、DOM 引用、大列表 DOM 节点 |
| 能做什么 | 在开发阶段预防内存泄漏，避免线上运行时内存持续增长 |
| 怎么用 | 组件卸载时：`clearTimeout/clearInterval`、`removeEventListener`、WebSocket.close()、`WeakMap/WeakSet` 存储 DOM 引用、虚拟列表减少 DOM 节点数 |
| 原理和工作流程 | 定时器未清除：回调函数持续引用组件闭包变量，阻止 GC。事件监听未解绑：元素被事件监听器引用，即使从 DOM 移除也无法回收。WebSocket 未关闭：连接对象持续占用内存。全局变量：window 上的属性永远不会被 GC。WeakMap/WeakSet：键为对象时，对象被回收后对应条目自动移除 |
| 缺点 | 需要在每个组件卸载时手动清理，容易遗漏；第三方库的隐式引用难以排查 |

## 四、常见面试题

### 防抖和节流的区别及适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | 防抖连续触发只执行最后一次（搜索输入、窗口 resize、按钮防重复），节流固定间隔执行一次（滚动事件、鼠标移动、无限滚动） |
| 能做什么 | 验证候选人是否能准确区分两种高频事件控制策略及各自适用场景 |
| 怎么用 | 防抖：`debounce(fn, 300)` 每次重置定时器；节流：`throttle(fn, 100)` 记录上次执行时间 |
| 原理和工作流程 | 防抖核心是每次触发重置定时器，停止触发后延迟执行，适合"最终结果"场景。节流核心是固定时间窗口，每 N 毫秒最多执行一次，适合"持续反馈"场景。防抖关注最后一次，节流关注均匀分布 |
| 缺点 | 两种策略选错场景会导致用户体验问题（如搜索用节流会有多余请求，滚动用防抖会没反馈） |

### 什么是回流和重绘如何减少回流

| 维度 | 内容 |
|------|------|
| 是什么 | 回流是元素几何属性变化导致重新布局（开销大），重绘是外观变化不影响布局（开销较小），回流一定触发重绘 |
| 能做什么 | 回答时需列举 6 种减少回流的具体策略 |
| 怎么用 | 批量修改 DOM（className 一次性）、DocumentFragment 内存构建、离线 DOM（display:none 操作后恢复）、transform 动画替代 top/left、读写分离、requestAnimationFrame |
| 原理和工作流程 | 每次回流浏览器需要重新计算元素几何属性、构建布局树、绘制，开销巨大。批量和离线操作将多次回流合并为一次；transform 和 opacity 在合成线程处理，不触发主线程回流；读写分离避免强制同步布局（Layout Thrashing）；requestAnimationFrame 将更新集中在下一帧之前 |
| 缺点 | 读写分离增加代码复杂度；transform 不能替代所有动画（如需要改变布局的动画） |

### 虚拟列表的实现原理

| 维度 | 内容 |
|------|------|
| 是什么 | 只渲染可视区域 DOM 节点，根据 scrollTop 计算 startIndex/endIndex，通过 padding 或 transform 模拟滚动位置 |
| 能做什么 | 验证候选人是否理解虚拟列表的核心变量和实现步骤 |
| 怎么用 | startIndex = Math.floor(scrollTop / itemHeight)；endIndex = startIndex + visibleCount + bufferSize；offsetY 通过 paddingTop 模拟 |
| 原理和工作流程 | 监听滚动事件获取 scrollTop → 计算 startIndex 和 endIndex → 只渲染 [startIndex, endIndex] 范围内数据 → 设置容器总高度 itemHeight x totalCount 保证滚动条正确 → 通过 padding-top 或 transform 模拟偏移。需设置缓冲区（overscan）避免快速滚动时白屏。动态高度场景需维护每项高度缓存 |
| 缺点 | 动态高度实现复杂；快速滚动可能导致短暂白屏 |

### SSR SSG ISR 的区别和适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | SSR 每次请求服务端渲染（个性化内容），SSG 构建时预渲染（文档/博客），ISR 按需重新生成（商品详情/新闻列表） |
| 能做什么 | 验证候选人是否能根据数据新鲜度要求和服务器成本选择合适的渲染模式 |
| 怎么用 | Next.js：`getServerSideProps`（SSR）、`getStaticProps`（SSG）、`getStaticProps` + `revalidate`（ISR） |
| 原理和工作流程 | SSR 适合个性化内容、实时数据，服务器压力大；SSG 适合内容不常变页面，性能最优，构建时数据新鲜度低；ISR 结合二者优点，首次请求生成静态页面，revalidate 秒后后台重新生成。框架支持：Next.js 全支持，Nuxt.js 支持 SSR/SSG，Gatsby 专注 SSG |
| 缺点 | 选择不当会导致服务器成本过高或内容更新不及时 |

### React 中如何避免不必要的重渲染

| 维度 | 内容 |
|------|------|
| 是什么 | React.memo 包裹组件 props 浅比较、useMemo 缓存计算结果、useCallback 缓存函数引用、避免内联对象/函数、稳定唯一 key |
| 能做什么 | 验证候选人对 React 性能优化手段的掌握程度 |
| 怎么用 | `const MemoComp = React.memo(ExpensiveComponent)`；`const sorted = useMemo(() => data.sort(), [data])`；`const handleClick = useCallback(() => doSomething(id), [id])` |
| 原理和工作流程 | React.memo 对 props 做浅比较，相同则跳过渲染（返回上次结果）。useMemo 在依赖不变时返回缓存值，避免重复计算。useCallback 返回稳定的函数引用，避免子组件因 props 引用变化而重渲染。内联对象/函数每次渲染都创建新引用，导致子组件即使 props 值相同也会重渲染 |
| 缺点 | useMemo/useCallback 本身有开销，简单计算不需要缓存；过度使用降低代码可读性 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 运行时优化中常见的实践错误：防抖闭包旧值、大量 DOM 直接渲染、Layout Thrashing、组件卸载后副作用、Worker 大数据传递、SSR 滥用、useMemo 滥用、虚拟列表无缓冲区 |
| 能做什么 | 帮助开发者提前识别运行时性能陷阱，避免优化不足或过度优化 |
| 怎么用 | 对照排查：防抖闭包问题用 useRef 存最新值；列表卡顿用虚拟列表；layout thrashing 用读写分离；组件卸载清理用 useEffect cleanup 或 AbortController；Worker 大数据用 Transferable Objects |
| 原理和工作流程 | 常见错误根源：防抖函数闭包捕获过时变量引用（用 useRef 或 useCallback+useRef 解决）、1000+ 条数据直接渲染导致大量 DOM 节点（用虚拟列表）、频繁读写布局属性交替触发强制同步布局（读写分离）、异步操作完成时组件已卸载（cleanup 函数或 AbortController）、postMessage 结构化克隆大数据复制开销大（Transferable Objects 转移所有权）、所有页面都用 SSR 拉高服务器成本（按页面特性选择）、对简单计算使用 useMemo 反而增加开销、虚拟列表无 overscan 导致快速滚动白屏 |
| 缺点 | 运行时优化需要性能监控数据支撑，不能凭感觉优化 |

## 补充内容1：INP 深度优化

### INP 测量口径与三段耗时

| 维度 | 内容 |
|------|------|
| 是什么 | INP（Interaction to Next Paint）是 2024 年 3 月取代 FID 的响应性指标，测量整个页面生命周期内所有交互从输入到"下一次绘制完成"的端到端耗时，取接近最差的高百分位值 |
| 能做什么 | 反映真实的交互流畅度，而不只是"首次交互的输入延迟"；通过三段拆分定位瓶颈所在环节 |
| 怎么用 | `import { onINP } from 'web-vitals'`，在回调中读取 `metric.value` 与 `metric.attribution`（含 `interactionType` / `interactionTarget` / `loadState` / `longestScript`）；也可用 `PerformanceObserver` 监听 `type: 'event'` 条目 |
| 原理和工作流程 | 三段耗时：输入延迟（`processingStart - startTime`，主线程被长任务占用）、处理时间（`processingEnd - processingStart`，事件回调执行）、呈现延迟（`startTime + duration - processingEnd`，框架调度 + 样式计算 + 布局 + 绘制 + 合成）。阈值：≤ 200ms 良好，200-500ms 需改进，> 500ms 差 |
| 缺点 | 只在真实用户环境采集才准确；三段耗时只能靠 DevTools 面板做进一步归因；单次交互的 INP 受设备性能影响大 |

### 长任务识别与主线程让出

| 维度 | 内容 |
|------|------|
| 是什么 | 长任务指主线程连续执行超过 50ms 的任务；让出主线程指在片段之间把控制权交还事件循环，让浏览器处理输入与渲染 |
| 能做什么 | 降低输入延迟与呈现延迟；在保持吞吐的同时维持交互响应 |
| 怎么用 | 用 `PerformanceObserver` 监听 `type: 'longtask'` 定位长任务；用 `scheduler.yield()` 让出并优先恢复；用 `scheduler.postTask(fn, { priority })` 按 `user-blocking` / `user-visible` / `background` 排序；用 `TaskController` 中止任务；降级方案为 `setTimeout(0)` |
| 原理和工作流程 | 50ms 是"用户输入到达时主线程最多能拖多久仍被感知为即时"的经验上限，因此单次任务控制在 50ms 以内（实践中按 40ms 预算分片）。`scheduler.yield()` 按任务优先级重新排队，续体优先恢复；`setTimeout(0)` 则追加到队列末尾，且受最小 1ms 与嵌套超时钳制（可达 4ms 以上）影响，恢复更晚且会被插队 |
| 缺点 | `scheduler.yield()` 需要 Chrome 129+，必须有降级；分片本身有调度开销，分片过细反而更慢；`requestIdleCallback` 触发时机不确定、单帧预算仅几毫秒、不参与优先级体系、Safari 支持较晚，只适合明确可无限期延后的任务 |

### React 并发特性与 INP

| 维度 | 内容 |
|------|------|
| 是什么 | React 18 的并发特性（`startTransition` / `useTransition` / `useDeferredValue`）把一次大渲染拆成可中断的片段，片段之间检查是否有更高优先级更新 |
| 能做什么 | 让紧急更新（输入框）立即响应、非紧急更新（列表结果）延后渲染，从而改善呈现延迟 |
| 怎么用 | `const [isPending, startTransition] = useTransition()`，在 `startTransition(() => setList(compute(value)))` 中标记非紧急更新；非组件环境用全局 `startTransition`；不改变状态本身时用 `useDeferredValue(keyword)` |
| 原理和工作流程 | 并发渲染使渲染过程可中断，片段之间优先处理新的输入更新，因此输入延迟与呈现延迟同时下降；`isPending` 用于给用户"加载中"反馈，避免"点了没反应"的感知 |
| 缺点 | 只让渲染可中断，**不会切碎回调内的同步计算**——300ms 的同步计算仍需移到 Web Worker 或手动分片；并发特性引入额外的调度复杂度，过度使用会降低可读性 |

### INP 归因流程

| 维度 | 内容 |
|------|------|
| 是什么 | 从监控数据到 Performance 面板定位、再到验证的完整排查路径 |
| 能做什么 | 快速判断瓶颈落在输入延迟、处理时间还是呈现延迟，避免"盲优化" |
| 怎么用 | ① 用 `onINP` 的 `attribution` 确定交互类型 / 元素 / 加载阶段；② Performance 面板录制并复现交互；③ 在 `Interactions` 分组看三段耗时；④ 在 Call Tree / Bottom-Up 按自耗时排序定位函数；⑤ 开启 CPU 节流（4x-6x）复现移动端表现；⑥ 改后重新录制并看 P75 是否下降 |
| 原理和工作流程 | 输入延迟大 → 查该交互之前的长任务（首屏未完成的 JS、大列表渲染、第三方脚本）；处理时间长 → 查 Call Tree 中自耗时最高的函数（同步计算、DOM 读写、Layout Thrashing）；呈现延迟大 → 查样式计算 / 布局 / 绘制 / 合成（组件树过大、CSS 选择器复杂、大面积重排、动画未走合成层） |
| 缺点 | 依赖 DevTools 的录制能力，移动端真机录制受限；归因结论需要结合业务代码人工判断，无法全自动 |

## 补充内容2：移动端性能优化

### 移动端与桌面端的性能差异根源

| 维度 | 内容 |
|------|------|
| 是什么 | 移动端与桌面端在 CPU、GPU、内存、网络、屏幕 DPR、交互方式六个维度上的系统性差异 |
| 能做什么 | 建立"同样的代码在移动端要贵好几倍"的认知，从而优先减少总工作量而非微调单行代码 |
| 怎么用 | 用 `navigator.hardwareConcurrency` / `navigator.deviceMemory` / `navigator.connection.effectiveType` 做设备分级，按档位下发不同策略（是否启用动效、图片质量档位、是否预取） |
| 原理和工作流程 | CPU 主频低、核心少、散热受限易降频导致 JS 与样式计算慢 3-10 倍；集成 GPU 填充率有限导致合成、滤镜、模糊开销高；内存容量小且单页可用更少导致易 OOM；网络 RTT 与丢包波动大导致加载不可预测；DPR 2-3 使同等 CSS 尺寸下像素量是桌面端的 2-4 倍，解码与绘制压力更大 |
| 缺点 | `deviceMemory` 仅 Chromium 系支持，`connection` 是估算值，设备分级只能作为"提示"而非精确测量；降级策略需要额外的代码分支与测试成本 |

### `will-change` 与合成层开销

| 维度 | 内容 |
|------|------|
| 是什么 | `will-change` 提示浏览器把元素提升为独立合成层，使 `transform` / `opacity` 动画在合成线程完成，不触发主线程的样式计算与布局 |
| 能做什么 | 让动画走合成路径，避免回流重绘；在移动端提升动画流畅度 |
| 怎么用 | 只对即将做动画的元素临时加：`.card:hover { will-change: transform }`；动画结束后在 `transitionend` 中设 `willChange = 'auto'`；需要强制提升层时用 `transform: translateZ(0)` |
| 原理和工作流程 | 每个合成层都要分配独立内存缓冲（DPR 3 手机上一个全屏层可能占用数 MB），层数过多导致内存暴涨与合成阶段"层管理"开销上升；`will-change` 是长期提示，加上后浏览器长期保留该层 |
| 缺点 | 滥用等于永久增加内存占用，低端机容易触发页面回收或 OOM；`will-change: all` 或全局给 `*` 加 `will-change` 会直接让内存失控；移动端大面积 `backdrop-filter` / `filter: blur()` / `box-shadow` 会显著拉高填充率开销 |

### 触摸事件与滚动性能

| 维度 | 内容 |
|------|------|
| 是什么 | `passive` 选项声明监听器不会调用 `preventDefault()`；`touch-action` 用 CSS 声明手势行为；两者共同解决滚动迟滞与 300ms 点击延迟 |
| 能做什么 | 让浏览器不必等待 JS 执行就能开始滚动；让 `click` 立即派发而非等待双击缩放判定；避免"滚到底带动整个页面" |
| 怎么用 | `addEventListener('touchmove', fn, { passive: true })`；`.btn { touch-action: manipulation }`；`.scroll-area { touch-action: pan-y pinch-zoom; overscroll-behavior: contain; -webkit-overflow-scrolling: touch }`；正确的视口声明 `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` |
| 原理和工作流程 | 浏览器无法预知监听器是否 `preventDefault()`，因此必须等监听器执行完才能滚动；`passive: true` 解除这一等待。300ms 延迟源于早期浏览器在 `touchend` 后等待约 300ms 判断是否双击缩放，现代浏览器在正确视口声明下移除该延迟，`touch-action: manipulation` 进一步明确不需要双击缩放。`document` / `window` / `body` 上的 `touchstart` / `touchmove` 默认已 passive，`wheel` 在 Chrome 73+ 也默认 passive，其他元素需显式声明 |
| 缺点 | `passive: true` 与 `preventDefault()` 冲突时控制台警告且阻止不生效；需要精细手势控制时仍需 Pointer Events（`pointerdown` / `pointerup` / `pointercancel`），并自行处理与滚动手势的区分，容易误触 |

### WebView 差异与移动端首屏优化

| 维度 | 内容 |
|------|------|
| 是什么 | WebView 与浏览器在内核版本、缓存机制、调试能力、能力注入上的差异；以及移动端首屏的优化要点集合 |
| 能做什么 | 明确最低支持内核版本并据此决定构建目标与 API 使用范围；压缩"从请求到首屏绘制"的关键路径长度 |
| 怎么用 | 首屏：骨架屏 / SSR、首屏 CSS 内联（≤ 14KB）、首屏图片直出配 `fetchpriority="high"`、路由级代码分割、延后非关键脚本、避免首屏同步布局读取、长列表用虚拟列表、`viewport-fit=cover` + `env(safe-area-inset-bottom)` 适配安全区；调试：Chrome Remote Debugging（`chrome://inspect`）、Safari Web Inspector、vConsole / Eruda、`adb shell dumpsys gfxinfo` |
| 原理和工作流程 | WebView 内核跟随宿主 App 打包版本（可能显著落后），缓存常被离线包 / 请求拦截替代，首屏可用离线包从"网络往返"变为"本地读取"，JSBridge 调用为异步且可能失败需超时降级，App 可能注入全局变量或拦截 `fetch` / `XMLHttpRequest`；真机性能特征与模拟器差异巨大，性能结论必须以真机为准 |
| 缺点 | 线上包通常无法开启 WebView 调试，只能依赖 vConsole 或远程日志；离线包需要额外的版本校验与增量更新机制；移动端真机录制性能数据成本较高 |
