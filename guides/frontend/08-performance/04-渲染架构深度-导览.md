# 04-渲染架构深度 - 导览

---

## 1.1 四种渲染策略总览（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 四种渲染策略分别为 SSG（静态生成，构建时预渲染）、ISR（增量静态再生成，首次请求+定时重建）、SSR（服务端渲染，每次请求生成）、CSR（客户端渲染，浏览器端渲染）。用报纸类比：SSG 是提前印好的报纸，ISR 是定时更新的报纸，SSR 是有人要看才印，CSR 是给白纸让读者自己写 |
| 能做什么 | 根据页面数据新鲜度需求、SEO 要求、服务器成本、访问量等因素选择最合适的渲染策略，平衡首屏速度与数据实时性 |
| 怎么用 | Next.js Pages Router：SSG 用 `getStaticProps`、ISR 用 `getStaticProps` + `revalidate`、SSR 用 `getServerSideProps`；App Router：SSG 默认行为、ISR 用 `export const revalidate`、SSR 用 `export const dynamic = 'force-dynamic'`、CSR 用 `useEffect` + `useState` |
| 原理和工作流程 | SSG 构建时渲染为静态 HTML 直接部署到 CDN；ISR 基于 stale-while-revalidate 策略，首次请求返回缓存并在后台重新生成；SSR 每次请求在服务端渲染完整 HTML；CSR 浏览器下载 JS 后在客户端渲染 DOM |
| 缺点 | SSG 构建时间长（大型站点）、数据不实时；ISR 首次访问可能较慢；SSR 服务器压力大需缓存策略；CSR 首屏白屏时间长、SEO 不友好 |

## 1.2 React Server Components（RSC）核心理念（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | RSC 是 React 18 引入的架构范式转变，核心理念是"默认服务端渲染，按需客户端交互"。服务端组件运行在服务端，可直接访问数据库和文件系统；客户端组件（`'use client'`）运行在浏览器，可使用交互 API |
| 能做什么 | 减少客户端 JavaScript 体积（服务端组件代码不发送到浏览器）、直接访问后端资源无需 API 端点、缩小客户端组件边界 |
| 怎么用 | 默认导出为服务端组件；需要交互的组件在文件顶部添加 `'use client'`；服务端组件可导入客户端组件，客户端组件不能直接导入服务端组件（可通过 props.children 传递） |
| 原理和工作流程 | 服务端渲染服务端组件树 → 生成 RSC Payload（序列化的 React 元素树）→ 流式传输到客户端 → 客户端 React 解析 Payload 重建组件树 → 客户端组件执行 Hydration 绑定事件 |
| 缺点 | 服务端组件不能使用 `useState`/`useEffect`/事件处理；`'use client'` 边界需要仔细设计；调试和错误定位比纯 CSR 复杂 |

## 1.3 PPR 部分预渲染（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | PPR（Partial Prerendering）是 Next.js 14+ 引入的混合渲染策略，核心思想是"静态外壳 + 流式动态内容"。构建时预渲染静态部分（导航栏、页脚），请求时动态内容通过 Suspense 边界流式填充 |
| 能做什么 | 结合 SSG 的极速首屏和 SSR 的动态能力，用户立即看到静态外壳，动态内容逐步填充，无需等待整个页面渲染完成 |
| 怎么用 | `next.config.ts` 中启用 `experimental.ppr = true`；用 Suspense 包裹动态组件，静态组件直接渲染 |
| 原理和工作流程 | 构建时：静态组件预渲染为 HTML → 动态组件标记为 Suspense 占位符 → 请求时：静态外壳立即发送 → 动态组件在服务端渲染 → 流式传输替换占位符 |
| 缺点 | 目前仍为实验性功能；需要合理设计 Suspense 边界；静态/动态边界划分不当可能影响性能收益 |

## 2.1 Next.js App Router 渲染流程（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Next.js App Router 的完整渲染流程分为三个阶段：RSC Payload 生成（服务端渲染组件树）、流式传输（HTTP chunked 传输）、客户端 Hydration（绑定事件监听器） |
| 能做什么 | 理解渲染流程有助于排查渲染问题、优化首屏性能、设计 Suspense 边界 |
| 怎么用 | 通过 `layout.tsx` 定义静态外壳，`page.tsx` 定义页面内容，Suspense 包裹异步组件控制流式传输 |
| 原理和工作流程 | 服务端接收请求 → 匹配路由 → 渲染服务端组件树 → 生成 RSC Payload（序列化格式）→ 流式传输 RSC Payload + HTML → 客户端 React 解析 Payload → 调和组件树 → Hydration 绑定事件 → 页面可交互 |
| 缺点 | RSC Payload 格式不透明，调试困难；Hydration 阶段仍有性能开销；复杂交互场景需要精细的客户端组件边界设计 |

## 2.2 ISR 的 revalidate 机制（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | ISR 基于 stale-while-revalidate（SWR）策略：先返回缓存（stale）内容，同时在后台异步重新生成（revalidate）新内容，下次请求返回新内容 |
| 能做什么 | 在性能和数据新鲜度之间取得平衡，避免每次请求都重新渲染，同时保证内容不会长期过时 |
| 怎么用 | App Router：`export const revalidate = 3600` 或 `fetch(url, { next: { revalidate: 60 } })`；On-Demand Revalidation：`revalidatePath('/path')` 或 `revalidateTag('tag')` |
| 原理和工作流程 | 构建时生成静态页面 v1 → 用户请求返回 v1 → revalidate 时间后触发后台重新生成 → 后台生成 v2 成功则更新缓存 → 后续请求返回 v2；若后台生成失败则继续使用 v1 |
| 缺点 | revalidate 间隔过短可能导致频繁构建队列堆积；On-Demand Revalidation 需要安全的 API 端点设计；首次请求冷启动可能较慢 |

## 2.3 Streaming SSR 原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Streaming SSR 允许服务端将 HTML 分块发送到浏览器，而不是等待整个页面渲染完成。React 18 的 `renderToPipeableStream` 配合 Suspense 边界实现 |
| 能做什么 | 解决传统 SSR 中"最慢组件拖慢整个页面"的问题，用户先看到静态外壳，动态内容按优先级逐步填充 |
| 怎么用 | 服务端：`renderToPipeableStream` 的 `onShellReady` 回调中 `pipe(res)`；客户端：用 Suspense 包裹每个异步组件，为每个边界设置 fallback（骨架屏） |
| 原理和工作流程 | 服务端渲染静态外壳 → onShellReady 触发 → 立即通过 HTTP chunked 发送 Shell HTML → 异步组件渲染完成后发送替换脚本 → 浏览器逐步替换 fallback 为真实内容 |
| 缺点 | 未设置 Suspense 边界时整个页面仍需等待最慢组件；骨架屏设计需要额外工作；流式传输中的错误处理较复杂 |

## 2.4 Edge Runtime 与 Serverless 差异（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Edge Runtime 基于 V8 Isolates 在边缘节点运行，冷启动极快（~0ms）但 API 受限；Serverless 基于容器化 Node.js，冷启动较慢（50-200ms）但支持完整 Node.js API |
| 能做什么 | Edge 适合轻量级 API 网关、A/B 测试、地理位置路由、简单认证；Serverless 适合数据库查询、ORM 操作、复杂计算 |
| 怎么用 | Edge：`export const config = { runtime: 'edge' }`；Serverless：Next.js 默认部署方式 |
| 原理和工作流程 | Edge 在全球边缘节点运行 V8 Isolate，每个请求在独立 Isolate 中执行，无状态；Serverless 在容器中运行完整 Node.js，首次请求触发冷启动，后续请求可复用容器 |
| 缺点 | Edge 不支持 fs/net/child_process 等 Node.js 原生 API，最大执行时间 30 秒，响应体 4MB 限制；Serverless 冷启动延迟明显，长连接场景需额外处理 |

## 3.1 Next.js 15 渲染模式实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 在同一页面中混合使用 SSG（静态 Header）、ISR（热门文章，revalidate=300）、SSR（实时动态，cache: 'no-store'）三种渲染策略的完整实现 |
| 能做什么 | 展示如何根据内容特性选择最佳渲染策略，实现"物尽其用"的渲染架构 |
| 怎么用 | SSG 部分：纯静态组件直接渲染；ISR 部分：`export const revalidate = 300`；SSR 部分：`fetch(url, { cache: 'no-store' })` 并用 Suspense 包裹 |
| 原理和工作流程 | 构建时静态 Header 预渲染 → 请求时 ISR 热门文章检查缓存 → 如果过期则后台重新生成 → SSR 实时动态每次请求实时获取 → 组合返回完整页面 |
| 缺点 | 混合渲染增加页面复杂度；不同策略的缓存策略需要协调；调试时需要关注各部分的渲染时机 |

## 3.2 Server Actions 表单处理（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Server Actions 是 Next.js 14+ 引入的特性，允许在服务端组件中直接定义可被客户端调用的异步函数，配合 `useActionState` 和 `useOptimistic` 实现完整的表单处理 |
| 能做什么 | 简化表单处理流程：无需创建 API 端点、自动类型安全、内置 CSRF 保护、支持渐进增强和乐观更新 |
| 怎么用 | 定义 `'use server'` 函数处理表单数据 → 客户端用 `useActionState(serverAction, initialState)` 管理提交状态 → 用 `useOptimistic` 实现乐观更新 |
| 原理和工作流程 | 客户端提交表单 → Server Action 在服务端执行 → 验证数据（zod）→ 写入数据库 → revalidatePath 清除缓存 → redirect 跳转；useOptimistic 在服务端响应前立即更新 UI，确认后自动同步 |
| 缺点 | 复杂表单（多步骤、文件上传）需要额外处理；错误处理比传统 API 调用更隐晦；与第三方表单库（React Hook Form）集成需要适配 |

## 3.3 流式渲染实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 设计优雅的 Suspense 边界，实现骨架屏（Skeleton）与内容逐步填充的完整流式渲染页面 |
| 能做什么 | 提升大页面（商品列表 + 用户评价）的首屏体验，用户先看到完整布局结构，内容按优先级逐步到达 |
| 怎么用 | 为每个异步组件设计对应的骨架屏组件 → 用 Suspense 包裹异步组件，传入骨架屏作为 fallback → 静态内容直接渲染 |
| 原理和工作流程 | 静态 Header 立即渲染 → 商品列表 Suspense 先显示 ProductGridSkeleton（2 秒后替换为真实数据）→ 用户评价 Suspense 先显示 ReviewSkeleton（3 秒后替换为真实数据）→ 静态 Footer 立即渲染 |
| 缺点 | 骨架屏设计与真实内容布局需要保持匹配；过度使用 Suspense 会导致页面碎片化；骨架屏的闪烁（flicker）需要动画过渡 |

## 3.4 渲染策略选择决策树（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 一套基于页面特征的渲染策略选择决策流程，通过 Mermaid 流程图直观展示从"数据是否需要实时更新"到最终策略的完整决策路径 |
| 能做什么 | 帮助开发者在项目初期快速确定每个页面的渲染策略，避免后期返工和性能问题 |
| 怎么用 | 从"页面数据是否需要实时更新"开始，依次回答决策节点的问题（SEO 需求、个性化内容、访问量、数据变化频率），最终到达推荐的策略 |
| 原理和工作流程 | 决策树遍历：实时数据 → 需要 SEO → 个性化内容 → SSR；实时数据 → 不需要 SEO → CSR；非实时数据 → 几乎不变 → SSG；非实时数据 → 中等变化 → ISR；非实时数据 → 频繁变化 → 再判断访问量 |
| 缺点 | 实际决策还需考虑团队技术栈熟悉度、基础设施成本、运维复杂度等非技术因素 |
