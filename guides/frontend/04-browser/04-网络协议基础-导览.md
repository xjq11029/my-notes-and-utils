## 二、底层原理

### 2.1 网络分层模型

| 维度 | 内容 |
|------|------|
| 是什么 | 将网络通信拆分为功能独立的层次，OSI 七层模型是理论参考（应用层、表示层、会话层、传输层、网络层、数据链路层、物理层），TCP/IP 四层模型是工业事实标准（应用层、传输层、网络层、网络接口层），每一层有独立的职责和协议。 |
| 能做什么 | 解耦网络协议设计，让各层独立演进；理解数据封装过程（应用层消息→传输层段→网络层包→链路层帧）；定位网络问题时可快速确定故障所在层次。 |
| 怎么用 | 网络调试时按层次排查：应用层检查 HTTP 状态码和请求参数；传输层用 `netstat` 查看 TCP 连接状态；网络层用 `ping`/`traceroute` 检查连通性；链路层检查网卡和交换机。 |
| 原理和工作流程 | 发送端从上到下逐层封装：应用层生成原始数据→传输层添加 TCP/UDP 头部→网络层添加 IP 头部→链路层添加帧头和帧尾；接收端从下到上逐层解封装，每层只关心自己的协议头部信息。 |
| 缺点 | OSI 七层模型过于理论化，表示层和会话层在实际中很少独立实现；TCP/IP 四层模型的网络接口层过于宽泛，合并了物理层和数据链路层两个职责不同的层次。 |

### 2.2 DNS 解析过程

| 维度 | 内容 |
|------|------|
| 是什么 | DNS（Domain Name System）是互联网的电话簿，将人类可读的域名（如 `www.example.com`）解析为机器可读的 IP 地址（如 `93.184.216.34`），是每次网络请求的第一步。 |
| 能做什么 | 实现域名到 IP 的映射，用户无需记忆 IP 地址；支持多种记录类型（A/AAAA/CNAME/MX/NS/TXT）；通过 TTL 机制控制各级缓存时间，平衡解析速度和灵活性。 |
| 怎么用 | 开发者可通过 Chrome `chrome://net-internals/#dns` 查看浏览器 DNS 缓存；Windows 上 `ipconfig /displaydns` 查看系统 DNS 缓存；修改 `hosts` 文件可实现本地域名劫持，用于开发环境将域名指向本地服务器。 |
| 原理和工作流程 | 浏览器 DNS 缓存→操作系统 DNS 缓存（hosts 文件优先）→本地 DNS 服务器→根 DNS 服务器（返回顶级 DNS 地址）→顶级 DNS 服务器（返回权威 DNS 地址）→权威 DNS 服务器（返回 IP 地址）；客户端到本地 DNS 是递归查询，本地 DNS 到各级 DNS 是迭代查询；解析结果按 TTL 在各层缓存。 |
| 缺点 | DNS 解析有延迟，首次访问需要多次往返；DNS 劫持和污染是常见安全威胁；DNS 缓存可能导致 IP 变更后用户仍访问旧地址（需等 TTL 过期）。 |

### 2.3 TCP 三次握手

| 维度 | 内容 |
|------|------|
| 是什么 | TCP 连接的建立过程，需要三次报文交互：客户端发送 SYN（请求连接）→服务器回复 SYN-ACK（同意连接）→客户端回复 ACK（确认连接），之后双方进入 ESTABLISHED 状态。 |
| 能做什么 | 在不可靠的 IP 网络上建立可靠的连接，双方确认彼此的收发能力都正常；同步初始序列号，为后续数据传输的可靠性做准备。 |
| 怎么用 | 开发者无需手动实现，TCP 协议栈由操作系统内核处理；后端开发可通过 `netstat -an` 查看 TCP 连接状态（SYN_SENT、SYN_RCVD、ESTABLISHED）；前端可以通过 Chrome DevTools Network 面板查看连接建立时间。 |
| 原理和工作流程 | 第一次握手：客户端发送 SYN=1, seq=x，进入 SYN_SENT 状态；第二次握手：服务器收到后回复 SYN=1, ACK=1, seq=y, ack=x+1，进入 SYN_RCVD 状态；第三次握手：客户端回复 ACK=1, ack=y+1，双方进入 ESTABLISHED 状态。三次握手本质上完成了"双方确认对方收发能力正常"这一目标。 |
| 缺点 | 三次握手增加了连接建立的延迟（1 个 RTT），对短连接场景（如 HTTP/1.0 每次请求新建连接）影响较大；SYN 洪水攻击利用三次握手缺陷，发送大量 SYN 但不回复 ACK，耗尽服务器资源。 |

### 2.4 TCP 四次挥手

| 维度 | 内容 |
|------|------|
| 是什么 | TCP 连接的断开过程，需要四次报文交互：主动方发送 FIN→被动方回复 ACK→被动方发送 FIN→主动方回复 ACK 并进入 TIME_WAIT 状态等待 2MSL。 |
| 能做什么 | 双方分别关闭自己的发送通道，确保全双工连接的两个方向都能正常关闭；TIME_WAIT 状态确保最后的 ACK 能到达对方，并让旧连接的所有报文从网络中消失。 |
| 怎么用 | 开发者无需手动实现，但需要理解 TIME_WAIT 状态的产生原因（主动关闭方会进入 TIME_WAIT）；后端高并发场景下大量 TIME_WAIT 可能导致端口耗尽，可通过调整内核参数优化。 |
| 原理和工作流程 | 第一次挥手：主动方发送 FIN，进入 FIN_WAIT_1；第二次挥手：被动方回复 ACK，进入 CLOSE_WAIT，主动方进入 FIN_WAIT_2；第三次挥手：被动方发送 FIN，进入 LAST_ACK；第四次挥手：主动方回复 ACK，进入 TIME_WAIT（等 2MSL），被动方收到 ACK 后进入 CLOSED。四次挥手是因为 TCP 是全双工，ACK 和 FIN 不能合并（被动方可能还有数据要发）。 |
| 缺点 | TIME_WAIT 状态持续 2MSL（通常 60 秒），高并发短连接场景下大量 TIME_WAIT 连接占用端口；CLOSE_WAIT 状态如果长期不消失，说明应用程序没有正确关闭连接（socket 泄漏）。 |

### 2.5 UDP vs TCP

| 维度 | 内容 |
|------|------|
| 是什么 | UDP 和 TCP 是传输层两种核心协议。TCP 是面向连接的可靠协议，通过三次握手建立连接、确认重传机制保证数据可靠送达；UDP 是无连接的不可靠协议，直接发送数据不保证送达，但速度快、开销小。 |
| 能做什么 | TCP 适合需要可靠传输的场景（网页浏览、文件下载、邮件、数据库）；UDP 适合实时性要求高的场景（视频直播、VoIP 通话、在线游戏、DNS 查询）。 |
| 怎么用 | 前端开发中 TCP 体现在 HTTP 请求（fetch/axios），UDP 体现在 WebRTC 音视频传输；`new RTCPeerConnection()` 建立 WebRTC 连接时底层使用 UDP 传输音视频数据。 |
| 原理和工作流程 | TCP 有拥塞控制（慢启动、拥塞避免、快速重传、快速恢复）和流量控制（滑动窗口），头部 20 字节；UDP 没有拥塞控制和流量控制，头部仅 8 字节，支持多播和广播。TCP 面向字节流无消息边界，UDP 面向报文保留消息边界。 |
| 缺点 | TCP 的可靠性和拥塞控制导致延迟较高，不适合实时音视频；UDP 不保证送达，需要应用层自行实现可靠性机制（如 WebRTC 在 UDP 之上实现了丢包重传和 FEC 前向纠错）。 |

### 2.6 IP 地址与端口

| 维度 | 内容 |
|------|------|
| 是什么 | IP 地址是网络层地址，用于标识网络中的主机（IPv4 32 位约 43 亿个地址，IPv6 128 位几乎无限）；端口号是传输层标识，用于区分同一主机上的不同网络服务（0-65535）。 |
| 能做什么 | IP 地址实现跨网络路由寻址；端口号让一台服务器可以同时运行多个网络服务；私有 IP 地址（192.168.x.x、10.x.x.x）用于局域网，通过 NAT 访问公网。 |
| 怎么用 | 前端开发中常见的本地开发地址 `127.0.0.1:3000`（localhost）；Vite 配置 `server.port` 指定开发服务器端口；Nginx 反向代理配置 `proxy_pass http://localhost:3001` 转发到后端端口。 |
| 原理和工作流程 | IPv4 地址为点分十进制（`192.168.1.1`），IPv6 为冒号分隔十六进制（`2001:db8::1`）；知名端口 0-1023 由 IANA 分配需管理员权限，注册端口 1024-49151 由应用注册，动态端口 49152-65535 由客户端临时使用；常见端口：80(HTTP)、443(HTTPS)、3000(Node.js 开发)、8080(代理/开发)。 |
| 缺点 | IPv4 地址已耗尽，NAT 是临时解决方案但增加了网络复杂性；端口号有限，大量并发连接可能耗尽临时端口；私有 IP 地址使端到端通信变得困难。 |

### 2.7 URL 组成与编码

| 维度 | 内容 |
|------|------|
| 是什么 | URL（Uniform Resource Locator）由 `scheme://host:port/path?query#fragment` 六部分组成，用于定位网络资源；URL 编码用于将非 ASCII 字符和特殊字符转换为 `%XX` 格式，确保 URL 只包含合法字符。 |
| 能做什么 | 使用 `URL` API 解析 URL 各部分；`encodeURIComponent` 编码参数值防止特殊字符被误解析；`encodeURI` 编码完整 URL 保留结构字符。 |
| 怎么用 | `new URL('https://example.com/path?key=值')` 解析 URL；`url.searchParams.get('key')` 获取查询参数；参数值用 `encodeURIComponent(value)` 编码；完整 URL 用 `encodeURI(url)` 编码；解码分别用 `decodeURIComponent` 和 `decodeURI`。 |
| 原理和工作流程 | `encodeURIComponent` 编码除 `A-Z a-z 0-9 - _ . ! ~ * ' ( )` 外的所有字符，包括 `&`、`=`、`?`、`#` 等 URL 特殊字符，确保参数值中的特殊字符不会被误解析为 URL 结构字符；`encodeURI` 只编码非 ASCII 字符和部分特殊字符，保留 `; , / ? : @ & = + $ #` 等 URL 结构字符，用于编码完整 URL。 |
| 缺点 | 混淆 `encodeURI` 和 `encodeURIComponent` 是常见错误，用 `encodeURI` 编码参数值会导致 `&` `=` 等未编码，服务器解析参数时出错；`fragment`（`#` 之后）不会发送到服务器，前端路由需要额外处理。 |

### 2.8 HTTP 请求方法

| 维度 | 内容 |
|------|------|
| 是什么 | HTTP 定义了一组请求方法表明对资源的操作意图：GET 获取、POST 创建、PUT 完整替换、PATCH 部分更新、DELETE 删除、HEAD 获取头部、OPTIONS 查询支持的方法。 |
| 能做什么 | 通过 HTTP 方法语义清晰表达 API 意图；GET 和 HEAD 是安全且幂等的；PUT 和 DELETE 是幂等的；POST 和 PATCH 既不安全也不幂等。 |
| 怎么用 | `fetch(url, { method: 'POST', body: JSON.stringify(data) })` 指定请求方法；GET 请求参数通过 URL 查询字符串传递；POST/PUT/PATCH 请求参数通过请求体传递；DELETE 请求通常无请求体。 |
| 原理和工作流程 | 幂等性指同一操作执行多次结果与一次相同（GET 多次读取结果不变，PUT 多次提交相同数据资源状态不变，DELETE 多次删除第一次成功后续返回 404 但服务器状态不变）；安全性指操作不修改服务器资源（GET、HEAD 安全，POST/PUT/DELETE/PATCH 不安全）。 |
| 缺点 | 部分代理和防火墙不支持 DELETE/PATCH 方法；GET 请求参数暴露在 URL 中，不适合传输敏感数据；POST 请求参数在请求体中，不能被浏览器缓存和收藏。 |

### 2.9 HTTP 状态码

| 维度 | 内容 |
|------|------|
| 是什么 | HTTP 状态码由三位数字组成，第一位表示类别：1xx 信息（请求已接收继续处理）、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误。 |
| 能做什么 | 根据状态码判断请求结果并采取相应处理：200 正常解析响应、201 获取新建资源位置、301/302 处理重定向、304 使用缓存、401 跳转登录、403 提示权限不足、404 显示 404 页面、500 提示服务器错误。 |
| 怎么用 | `fetch` 后检查 `response.ok` 判断 2xx；`response.status` 获取具体状态码；204 响应不解析响应体；201 响应从 `Location` 头获取新资源 URL；429 响应从 `Retry-After` 头获取等待时间。 |
| 原理和工作流程 | 浏览器自动处理 301/302 重定向，默认用 GET 方法重新请求；304 响应时浏览器自动使用本地缓存；`fetch` API 不会自动处理重定向，但 `response.redirected` 可判断是否发生了重定向。 |
| 缺点 | 不同后端框架对相同状态码的使用可能不一致（如 422 vs 400 表示参数错误）；`fetch` 在 HTTP 4xx/5xx 时不会 reject，需要手动检查 `response.ok`，这是前端开发中常见的错误处理遗漏。 |

### 2.10 HTTP 请求头与响应头

| 维度 | 内容 |
|------|------|
| 是什么 | HTTP 头部是请求和响应中的元数据，请求头包含 Content-Type、Authorization、Cache-Control、Cookie 等；响应头包含 Content-Type、ETag、Cache-Control、CORS 头部等。 |
| 能做什么 | Content-Type 指定请求/响应体格式；Authorization 传递认证凭据；Cache-Control 和 ETag/Last-Modified 控制缓存策略；CORS 头部（Access-Control-Allow-*）控制跨域访问权限。 |
| 怎么用 | 请求头通过 `fetch(url, { headers: { 'Content-Type': 'application/json' } })` 设置；响应头通过 `response.headers.get('Content-Type')` 读取；CORS 头部在服务器端配置，前端通过代理（Vite proxy）解决开发环境跨域。 |
| 原理和工作流程 | 强缓存（Cache-Control: max-age）直接使用本地缓存不发请求；协商缓存（ETag/If-None-Match）发送请求但服务器返回 304 时使用本地缓存；CORS 非简单请求先发送 OPTIONS 预检请求，服务器返回允许的来源和方法后，浏览器才发送真实请求。 |
| 缺点 | 手动设置 `Content-Type: multipart/form-data` 会缺少 boundary 参数导致上传失败；CORS 配置复杂，预检请求增加了额外延迟；Cookie 头部可能过大导致请求头超出服务器限制。 |

### 2.11 HTTPS 与 TLS 握手

| 维度 | 内容 |
|------|------|
| 是什么 | HTTPS 在 HTTP 和 TCP 之间插入 TLS 层，通过加密和证书机制实现三大安全目标：机密性（对称加密 AES）、完整性（消息认证码 MAC）、身份认证（CA 证书链）。 |
| 能做什么 | 防止通信内容被窃听（对称加密）；防止数据被篡改（完整性校验）；防止中间人攻击（证书链验证服务器身份）；混合加密结合了非对称加密的安全性和对称加密的高效性。 |
| 怎么用 | 前端无需特殊处理，使用 HTTPS 协议的 URL 即可（`https://`）；Service Worker 和部分 Web API 必须在 HTTPS 环境下使用；开发环境可通过 `mkcert` 生成本地证书。 |
| 原理和工作流程 | TLS 握手：ClientHello（支持的加密套件）→ServerHello+Certificate+ServerHelloDone（选定加密套件、证书、公钥）→客户端验证证书→ClientKeyExchange（用公钥加密预主密钥）→双方用随机数+预主密钥生成会话密钥→ChangeCipherSpec+Finished→后续通信对称加密。证书链验证：根 CA 证书（操作系统内置）→中间 CA 证书→服务器证书。 |
| 缺点 | TLS 握手增加 1-2 个 RTT 延迟；证书需要购买和定期更新（免费的有 Let's Encrypt）；HTTPS 不能防止所有攻击（如 XSS、SQL 注入等应用层攻击仍需开发者自行防范）。 |

### 2.12 HTTP/1.1 vs HTTP/2 vs HTTP/3

| 维度 | 内容 |
|------|------|
| 是什么 | 三代 HTTP 协议的演进：HTTP/1.1（1997，文本协议，TCP）→HTTP/2（2015，二进制帧+多路复用+头部压缩，TCP）→HTTP/3（2022，基于 QUIC/UDP，0-RTT+无队头阻塞+连接迁移）。 |
| 能做什么 | HTTP/2 多路复用一个连接并行传输多个请求/响应，消除 HTTP 层队头阻塞；HTTP/3 消除 TCP 层队头阻塞（单流丢包不影响其他流），支持网络切换无缝连接迁移，0-RTT 实现零延迟连接恢复。 |
| 怎么用 | 前端无需修改代码，HTTP/2 和 HTTP/3 由服务器和浏览器自动协商；需要注意 HTTP/1.1 时代的优化手段（域名分片、雪碧图、资源合并）在 HTTP/2 下反而降低性能，应移除这些优化。 |
| 原理和工作流程 | HTTP/2 将 HTTP 报文拆分为二进制帧，多个 Stream 的帧可以交错发送，接收端根据 Stream ID 重组；HPACK 使用静态表和动态表压缩头部，减少重复头部传输；HTTP/3 的 QUIC 协议在 UDP 之上实现了可靠传输+内置 TLS 1.3，使用连接 ID 标识连接而非 IP+端口。 |
| 缺点 | HTTP/2 仍有 TCP 层队头阻塞（一个 TCP 包丢失导致所有流等待重传）；HTTP/3 的 QUIC 协议基于 UDP，部分网络环境可能限制 UDP 流量；HTTP/3 的服务器推送功能实际使用率不高，部分浏览器已考虑移除。 |

### 2.13 RESTful API 设计原则

| 维度 | 内容 |
|------|------|
| 是什么 | REST（Representational State Transfer）是基于 HTTP 协议的 API 设计风格，核心原则包括：资源导向（名词复数表示资源）、HTTP 方法语义化、状态码语义化、无状态通信、统一接口。 |
| 能做什么 | 设计清晰、一致、可预测的 API；前端通过约定好的 URL 结构和方法语义即可推断 API 功能；标准的错误响应格式方便前端统一处理错误。 |
| 怎么用 | 资源 URL 用名词复数：`GET /users`、`POST /users`、`GET /users/123`、`PATCH /users/123`、`DELETE /users/123`；版本控制用 URL 路径：`/api/v1/users`；分页过滤排序用查询参数：`?page=1&limit=20&sort=-created_at`。 |
| 原理和工作流程 | 每个 URL 代表一个资源（名词），HTTP 方法表示操作（动词），状态码表示结果；无状态意味着每个请求包含所有必要信息，服务器不保存客户端会话状态；统一接口通过标准 HTTP 方法、状态码、头部实现。 |
| 缺点 | 复杂的业务操作（如"下单"、"转账"）难以用简单的 CRUD 表达，可能需要引入 RPC 风格接口；REST 是设计风格而非标准，不同团队实现差异大；查询参数过多时 URL 可能很长。 |

### 2.14 分页模式对比

| 维度 | 内容 |
|------|------|
| 是什么 | 两种常见的 API 分页实现方式：Offset-based（偏移分页，`?page=1&limit=20`）通过偏移量和限制数量分页，支持跳页；Cursor-based（游标分页，`?cursor=xxx&limit=20`）通过游标定位下一条数据，只支持顺序翻页。 |
| 能做什么 | Offset-based 适合后台管理系统，数据量不大（万级以下），需要跳页和显示总页数；Cursor-based 适合移动端信息流无限滚动和实时数据流，数据量大时性能始终高效，且分页期间数据变化不会导致重复或遗漏。 |
| 怎么用 | Offset-based：前端维护 `page` 和 `limit` 参数，根据 `totalPages` 渲染分页组件；Cursor-based：前端维护 `cursor` 变量，首次请求不传 cursor，每次请求后用返回的 `nextCursor` 更新，用 IntersectionObserver 实现滚动自动加载。 |
| 原理和工作流程 | Offset-based SQL 实现：`SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 20`，大偏移量时需扫描前 N 行再丢弃，性能差；Cursor-based SQL 实现：`SELECT * FROM users WHERE id > 123 ORDER BY id LIMIT 20`，利用索引直接定位，始终高效。 |
| 缺点 | Offset-based 大偏移量性能差，分页期间数据变化导致重复或遗漏；Cursor-based 无法跳页，无法计算总页数，只能判断是否还有下一页；Cursor 值需要是唯一且可排序的（通常用自增 ID 或时间戳）。 |

## 三、实战应用

### 3.1 封装 HTTP 请求模块

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 `fetch` API 封装的一个企业级 HTTP 客户端，包含超时控制（AbortController）、请求/响应拦截器、统一错误处理、便捷方法（get/post/put/patch/delete）。 |
| 能做什么 | 自动添加 Token（请求拦截器）；自动处理 401 跳转登录（响应拦截器）；超时控制防止请求挂起；统一错误处理格式；链式调用 `http.get('/users', { page: 1 })`、`http.post('/users', data)`。 |
| 怎么用 | `const http = new HttpClient('/api', { timeout: 5000 })` 创建实例；`http.useRequestInterceptor(config => { ... })` 添加拦截器；`http.useResponseInterceptor(response => { ... })` 添加响应拦截器。 |
| 原理和工作流程 | 请求拦截器在发送前依次执行，可修改 URL 和请求选项；`AbortController` + `setTimeout` 实现超时控制；响应拦截器在解析响应后依次执行；`response.ok` 判断 HTTP 2xx，非 2xx 抛出包含状态码和错误数据的 Error 对象。 |
| 缺点 | 基于 `fetch` 封装，不支持上传/下载进度监控（需用 XMLHttpRequest）；拦截器是同步/异步函数，需注意执行顺序；错误处理依赖后端返回格式一致。 |

### 3.2 文件上传

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 `FormData` API 和 `multipart/form-data` 格式实现文件上传，支持单文件、多文件和附加字段。 |
| 能做什么 | `FormData` 自动设置正确的 `Content-Type`（含 boundary）；`XMLHttpRequest.upload.onprogress` 监听上传进度；支持多文件批量上传和附加元数据。 |
| 怎么用 | `formData.append('file', file)` 添加文件；`formData.append('folder', 'images')` 添加附加字段；上传时不要手动设置 `Content-Type`；进度用 `xhr.upload.addEventListener('progress', callback)` 实现。 |
| 原理和工作流程 | `FormData` 生成的 `Content-Type` 为 `multipart/form-data; boundary=----WebKitFormBoundary...`，boundary 是随机字符串用于分隔多个表单字段；每个字段以 boundary 开头，包含字段名和内容，文件字段额外包含文件名和 Content-Type。 |
| 缺点 | `fetch` 不支持原生上传进度回调，需降级为 `XMLHttpRequest`；大文件上传需额外实现分片上传和断点续传；手动设置 `Content-Type` 会丢失 boundary 导致上传失败。 |

### 3.3 SSE 服务端推送

| 维度 | 内容 |
|------|------|
| 是什么 | SSE（Server-Sent Events）是 HTTP 协议原生支持的服务器单向推送技术，客户端通过 `EventSource` API 建立持久连接，服务器持续推送文本事件。 |
| 能做什么 | 实现服务端主动推送消息（如通知、实时数据更新）；浏览器自动重连（无需手动处理）；支持自定义事件类型（`eventSource.addEventListener('notification', callback)`）。 |
| 怎么用 | `const es = new EventSource('/api/events')` 建立连接；`es.onmessage` 监听默认消息；`es.addEventListener('customEvent', fn)` 监听自定义事件；`es.close()` 关闭连接。 |
| 原理和工作流程 | 浏览器向服务器发送 GET 请求，`Accept: text/event-stream`；服务器保持连接不关闭，持续发送 `data: {json}\n\n` 格式的文本流；浏览器根据 `id:` 字段追踪最后接收的事件 ID，重连时通过 `Last-Event-ID` 头部告知服务器。 |
| 缺点 | 只支持服务器到客户端的单向推送（与 WebSocket 的双向通信不同）；只能传输文本数据；浏览器对同一域名的 SSE 连接数有限制（HTTP/1.1 下 6 个）；IE 不支持。 |

## 四、常见面试题

### Q1：从输入 URL 到页面展示经历了哪些步骤（网络协议部分）

| 维度 | 内容 |
|------|------|
| 是什么 | 前端面试中最经典的综合题，网络协议部分涵盖 DNS 解析、TCP 三次握手、TLS 握手（HTTPS）、HTTP 请求/响应、TCP 四次挥手共六个关键步骤。 |
| 能做什么 | 综合考察对网络协议全链路的理解，从 DNS 到 TCP 到 HTTP 到 TLS 的完整知识体系。 |
| 怎么用 | DNS 解析：浏览器缓存→OS 缓存→hosts→本地 DNS→根 DNS→顶级 DNS→权威 DNS；TCP 三次握手：SYN→SYN-ACK→ACK；TLS 握手：ClientHello→ServerHello+Certificate→密钥交换；HTTP 请求/响应；TCP 四次挥手。 |
| 原理和工作流程 | 整个流程可以按时间线串联：DNS 解析获取 IP→TCP 建立可靠连接→TLS 建立安全通道→HTTP 传输应用数据→TCP 断开连接。 |
| 缺点 | 题目范围太广，回答时容易遗漏某个环节；面试官可能追问每个环节的细节，需要全面准备。 |

### Q2：TCP 为什么是三次握手，不是两次或四次

| 维度 | 内容 |
|------|------|
| 是什么 | TCP 采用三次握手建立连接而非两次或四次，是为了在不可靠网络上实现双向确认，同时兼顾效率。 |
| 能做什么 | 三次握手让双方都确认了对方的收发能力正常；防止已失效的连接请求到达服务器导致错误（两次握手无法解决）；效率最优（四次握手多余的确认没有额外收益）。 |
| 怎么用 | 理解后可以回答：二次握手只能确认客户端发送正常+服务器接收正常，无法确认客户端接收能力，且无法防止历史连接问题；四次握手第三次 ACK 可以和第二次 SYN-ACK 合并，多余的确认没意义。 |
| 原理和工作流程 | 第一次握手：客户端证明自己发送正常；第二次握手：服务器证明自己接收正常+发送正常；第三次握手：客户端证明自己接收正常。至此双方都确认对方收发正常。已失效连接问题：旧 SYN 延迟到达，三次握手下客户端不回复 ACK，服务器不会建立连接。 |
| 缺点 | 三次握手增加了 1 个 RTT 的延迟；SYN 洪水攻击利用三次握手缺陷，服务器在 SYN_RCVD 状态分配资源等待 ACK。 |

### Q3：HTTP/1.1、HTTP/2、HTTP/3 的核心区别

| 维度 | 内容 |
|------|------|
| 是什么 | 三代 HTTP 协议的核心区别：HTTP/1.1 文本协议+串行请求；HTTP/2 二进制帧+多路复用+头部压缩；HTTP/3 基于 QUIC/UDP+0-RTT+无队头阻塞。 |
| 能做什么 | HTTP/2 解决 HTTP/1.1 的队头阻塞和头部冗余问题；HTTP/3 解决 HTTP/2 的 TCP 层队头阻塞和连接建立延迟问题。 |
| 怎么用 | 前端无需修改代码，协议由浏览器和服务器协商；HTTP/1.1 时代的优化手段（域名分片、雪碧图、资源合并）在 HTTP/2 下应移除。 |
| 原理和工作流程 | HTTP/2 多路复用：一个 TCP 连接上多个 Stream 并行传输，帧交错发送按 Stream ID 重组；HPACK 头部压缩：静态表+动态表+哈夫曼编码；HTTP/3 QUIC：在 UDP 上实现可靠传输+TLS 1.3，使用连接 ID 标识连接。 |
| 缺点 | HTTP/2 TCP 层队头阻塞仍存在；HTTP/3 UDP 可能被防火墙限制；HTTP/3 服务器推送功能实际使用率低。 |

### Q4：HTTPS 为什么是安全的？TLS 握手做了什么

| 维度 | 内容 |
|------|------|
| 是什么 | HTTPS 通过 TLS 层实现三大安全目标：机密性（对称加密）、完整性（MAC）、身份认证（CA 证书链），采用混合加密策略（非对称加密交换密钥+对称加密传输数据）。 |
| 能做什么 | 防止窃听（加密通信内容）、防止篡改（完整性校验）、防止冒充（证书链验证服务器身份）。 |
| 怎么用 | 前端使用 HTTPS 协议的 URL 即可；Service Worker 和部分 Web API 必须 HTTPS 环境；开发环境用 `mkcert` 生成本地证书。 |
| 原理和工作流程 | TLS 握手：ClientHello→ServerHello+Certificate→客户端验证证书→ClientKeyExchange（密钥交换）→双方生成会话密钥→加密通信；证书链：根 CA→中间 CA→服务器证书，浏览器逐级验证签名。 |
| 缺点 | TLS 握手增加延迟；证书需购买和更新；HTTPS 不能防 XSS/SQL 注入等应用层攻击。 |

### Q5：HTTP 状态码 301 vs 302、401 vs 403 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | 301 永久重定向（浏览器缓存重定向，下次直接访问新地址）；302 临时重定向（不缓存，每次访问原地址）；401 未认证（需要登录）；403 已认证但无权限（禁止访问）。 |
| 能做什么 | 301 用于域名变更、HTTP 迁移 HTTPS；302 用于临时维护、A/B 测试；401 触发登录流程；403 提示权限不足。 |
| 怎么用 | 后端返回 301 时设置 `Location` 头指向新地址；前端 401 响应时跳转登录页；前端 403 响应时显示"权限不足"提示。 |
| 原理和工作流程 | 浏览器收到 301 后缓存重定向规则，下次访问原 URL 时直接请求新地址；302 不缓存，每次请求原 URL 都走重定向流程；401 响应可包含 `WWW-Authenticate` 头提示认证方式；403 表示服务器理解请求但拒绝执行。 |
| 缺点 | 301 缓存后很难撤销（浏览器缓存可能持续很久）；302 每次额外请求增加延迟；混淆 401 和 403 导致用户体验问题（已登录用户被要求重新登录）。 |

### Q6：RESTful API 设计有哪些核心原则

| 维度 | 内容 |
|------|------|
| 是什么 | RESTful API 有六大核心原则：资源导向（名词复数）、HTTP 方法语义化、状态码语义化、无状态通信、统一接口、版本控制。 |
| 能做什么 | 设计可预测的 API 结构；前端能通过 URL 推断资源和操作；标准错误格式方便统一处理。 |
| 怎么用 | `GET /users` 获取列表，`POST /users` 创建，`GET /users/:id` 获取单个，`PATCH /users/:id` 更新，`DELETE /users/:id` 删除；`/api/v1/users` 版本控制；`?page=1&limit=20&sort=-created_at` 分页排序。 |
| 原理和工作流程 | 每个 URL 代表资源（名词），HTTP 方法表示操作（动词），状态码表示结果；无状态：每个请求包含所有必要信息；统一接口：标准 HTTP 方法、状态码、头部。 |
| 缺点 | 复杂业务操作难以用 CRUD 表达；REST 是风格非标准，团队实现差异大；查询参数过多时 URL 可能很长。 |

### Q7：Offset-based 和 Cursor-based 分页各自适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | Offset-based 通过偏移量分页（`?page=1&limit=20`），支持跳页；Cursor-based 通过游标分页（`?cursor=xxx&limit=20`），只支持顺序翻页。 |
| 能做什么 | Offset-based 适合后台管理系统（数据量万级以下、需要跳页）；Cursor-based 适合移动端无限滚动和实时数据流（数据量大、需要一致性）。 |
| 怎么用 | Offset-based：前端维护 `page`/`limit`，根据 `totalPages` 渲染分页组件；Cursor-based：前端维护 `cursor` 变量，用 IntersectionObserver 实现滚动自动加载，每次请求用返回的 `nextCursor` 更新。 |
| 原理和工作流程 | Offset-based：`SELECT * FROM users LIMIT 20 OFFSET 20`，OFFSET 越大需扫描的行越多；Cursor-based：`SELECT * FROM users WHERE id > 123 ORDER BY id LIMIT 20`，利用索引直接定位始终高效。 |
| 缺点 | Offset-based 大偏移量性能差，分页期间数据变化导致重复/遗漏；Cursor-based 无法跳页，无法计算总页数，游标值需唯一可排序。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 聚合了网络协议开发中十个常见错误、原因分析和解决方案的综合参考，涵盖 URL 编码、文件上传、CORS、混合内容、fetch 错误处理、超时控制、分页一致性、缓存策略、上传进度、限流重试。 |
| 能做什么 | 快速对照排查：`encodeURI` 编码参数值导致 `&` `=` 未编码；手动设置 `Content-Type: multipart/form-data` 缺少 boundary 导致上传失败；CORS 非简单请求忘记处理 OPTIONS 预检；HTTPS 页面加载 HTTP 资源被阻止；`fetch` 不检查 `response.ok` 导致错误处理遗漏；不设置超时请求挂起；offset 分页期间数据变化导致重复；强缓存导致用户看不到新版本；大文件上传不显示进度；429 限流后不等待 `Retry-After` 就重试。 |
| 怎么用 | 参数值用 `encodeURIComponent`；`FormData` 上传不手动设置 `Content-Type`；后端配置 CORS 头部包括 OPTIONS；所有资源用 HTTPS；`fetch` 后检查 `response.ok`；`AbortController` 实现超时；改用 cursor-based 分页；文件名 hash + HTML 不缓存；`XMLHttpRequest.upload.onprogress`；读取 `Retry-After` 头等待后重试。 |
| 原理和工作流程 | 每个错误都有明确的技术原因：`encodeURI` 保留 URL 结构字符的编码规则导致参数值中的特殊字符泄露；`FormData` 的 boundary 需要浏览器自动生成，手动设置会覆盖；CORS 预检请求是浏览器的安全机制，非简单请求必须先预检；混合内容策略是浏览器的安全策略；`fetch` 设计上只在网络错误时 reject；分页期间数据变化导致 offset 偏移量语义失效。 |
| 缺点 | 需要开发者在日常编码中持续注意，部分错误（如混合内容、CORS）在开发环境可能不暴露，到生产环境才出现；`fetch` 的错误处理设计容易让习惯 axios 的开发者踩坑。 |
