## 一、核心概念

网络协议是浏览器与服务器通信的基石。前端开发中几乎每一个功能--从页面加载、API 调用到资源缓存、安全传输--都建立在网络协议之上。理解网络协议的工作原理，能帮助我们写出更高效、更健壮的前端代码。

**核心概念要点：**

1. **网络分层模型**：将复杂的网络通信过程拆分为多个层次，每一层有独立的职责，层与层之间通过接口交互。分层的目的是解耦，让每一层的实现可以独立演进。
2. **DNS 解析**：将人类可读的域名（如 `www.example.com`）转换为机器可读的 IP 地址（如 `93.184.216.34`），是每次网络请求的第一步。
3. **TCP 协议**：面向连接的、可靠的传输层协议，通过三次握手建立连接、四次挥手断开连接，保证数据有序、完整地送达。
4. **HTTP 协议**：应用层协议，定义客户端与服务器之间请求和响应的格式。从 HTTP/1.1 到 HTTP/3，协议不断演进以提升性能。
5. **HTTPS**：HTTP 的安全版本，在 HTTP 和 TCP 之间插入 TLS 层，通过加密和证书机制保证通信的机密性、完整性和身份认证。
6. **RESTful API**：基于 HTTP 协议的 API 设计规范，强调资源导向、无状态通信和统一接口。

## 二、底层原理

### 2.1 网络分层模型

网络分层是理解网络协议最重要的基础概念。将网络通信拆分为功能独立的层次，每一层只关心自己的职责，不关心其他层的实现细节。

#### 2.1.1 OSI 七层模型 vs TCP/IP 四层模型

| 对比维度 | OSI 七层模型 | TCP/IP 四层模型 |
|---------|-------------|----------------|
| 层数 | 7 层 | 4 层 |
| 提出者 | ISO（国际标准化组织） | 美国国防部 |
| 定位 | 理论模型，教学参考 | 事实标准，工业实现 |
| 上层 | 应用层、表示层、会话层 | 应用层（合并了表示层和会话层） |
| 中间层 | 传输层 | 传输层 |
| 网络层 | 网络层 | 网络层（因特网层） |
| 下层 | 数据链路层、物理层 | 网络接口层（合并了数据链路层和物理层） |

**OSI 七层模型详解：**

```
┌─────────────────┐
│  7. 应用层       │  ← 为用户提供网络服务接口（HTTP、FTP、SMTP、DNS）
├─────────────────┤
│  6. 表示层       │  ← 数据格式化、加密解密、压缩（TLS/SSL、JPEG、ASCII）
├─────────────────┤
│  5. 会话层       │  ← 建立、管理、终止会话（NetBIOS、RPC）
├─────────────────┤
│  4. 传输层       │  ← 端到端可靠传输（TCP、UDP）
├─────────────────┤
│  3. 网络层       │  ← 路由选择、逻辑寻址（IP、ICMP、ARP）
├─────────────────┤
│  2. 数据链路层   │  ← 帧同步、差错控制、MAC 寻址（以太网、Wi-Fi）
├─────────────────┤
│  1. 物理层       │  ← 比特流传输、物理介质（光纤、网线、无线电波）
└─────────────────┘
```

**TCP/IP 四层模型与协议对应：**

| 层次 | 名称 | 核心协议 | 数据单元 | 关键设备 |
|------|------|---------|---------|---------|
| 第 4 层 | 应用层 | HTTP、HTTPS、DNS、FTP、SMTP、WebSocket | 消息（Message） | - |
| 第 3 层 | 传输层 | TCP、UDP | 段（Segment）/ 数据报（Datagram） | - |
| 第 2 层 | 网络层 | IP、ICMP、ARP | 包（Packet） | 路由器 |
| 第 1 层 | 网络接口层 | 以太网、Wi-Fi、PPP | 帧（Frame） | 交换机、网桥 |

**数据封装过程（发送端从上到下逐层封装）：**

```
应用层：   [HTTP 请求数据]                              ← 原始数据
传输层：   [TCP 头部 | HTTP 请求数据]                    ← TCP 段
网络层：   [IP 头部 | TCP 头部 | HTTP 请求数据]           ← IP 包
链路层：   [帧头 | IP 头部 | TCP 头部 | HTTP 请求数据 | 帧尾] ← 以太网帧
```

> 把网络分层想象成**国际快递**：应用层是你写的内容（信件），传输层是快递公司打包并给包裹编号确保不丢件（TCP），网络层是填写收件地址和选择运输路线（IP），链路层是卡车司机把包裹从一个中转站送到下一个中转站（以太网）。每一层只关心自己的活儿，收货人拆包裹时从外到内一层层拆，最后读到你的信。

#### 2.1.2 各层协议速查

| 层次 | 协议 | 全称 | 作用 |
|------|------|------|------|
| 应用层 | HTTP | HyperText Transfer Protocol | Web 页面传输 |
| 应用层 | HTTPS | HTTP Secure | 加密的 HTTP |
| 应用层 | DNS | Domain Name System | 域名解析为 IP |
| 应用层 | WebSocket | WebSocket | 全双工实时通信 |
| 应用层 | FTP | File Transfer Protocol | 文件传输 |
| 应用层 | SMTP | Simple Mail Transfer Protocol | 邮件发送 |
| 传输层 | TCP | Transmission Control Protocol | 可靠、面向连接传输 |
| 传输层 | UDP | User Datagram Protocol | 不可靠、无连接传输 |
| 网络层 | IP | Internet Protocol | 逻辑寻址与路由 |
| 网络层 | ICMP | Internet Control Message Protocol | 网络诊断（ping） |
| 网络层 | ARP | Address Resolution Protocol | IP 地址 → MAC 地址 |

### 2.2 DNS 解析过程

DNS（Domain Name System）是互联网的电话簿，负责将域名转换为 IP 地址。每次你在浏览器输入一个 URL，DNS 解析是第一步。

#### 2.2.1 DNS 解析完整流程

```
用户输入 example.com
        ↓
① 浏览器 DNS 缓存  → 命中？ → 返回 IP
        ↓ 未命中
② 操作系统 DNS 缓存（/etc/hosts 优先） → 命中？ → 返回 IP
        ↓ 未命中
③ 本地 DNS 服务器（路由器/ISP 提供） → 命中？ → 返回 IP
        ↓ 未命中
④ 根 DNS 服务器  → 返回 .com 顶级 DNS 服务器地址
        ↓
⑤ .com 顶级 DNS 服务器  → 返回 example.com 权威 DNS 服务器地址
        ↓
⑥ 权威 DNS 服务器  → 返回 example.com 的 IP 地址
        ↓
⑦ 本地 DNS 服务器缓存结果，返回 IP 给浏览器
```

**各级缓存 TTL 说明：**

| 缓存位置 | 说明 | 典型 TTL |
|---------|------|---------|
| 浏览器 DNS 缓存 | Chrome 内置 DNS 缓存，chrome://net-internals/#dns 可查看 | 约 1 分钟 |
| 操作系统 DNS 缓存 | 系统级 DNS 缓存，`ipconfig /displaydns`（Windows）可查看 | 由 DNS 响应 TTL 决定 |
| hosts 文件 | 本地域名映射，优先级最高 | 永久有效 |
| 本地 DNS 服务器 | ISP 提供的 DNS 服务器缓存 | 由权威 DNS 的 TTL 决定 |

#### 2.2.2 递归查询 vs 迭代查询

| 对比维度 | 递归查询 | 迭代查询 |
|---------|---------|---------|
| 查询方式 | 客户端发起一次请求，DNS 服务器负责完成全部查询并返回最终结果 | 客户端（或本地 DNS 服务器）逐级向各级 DNS 服务器查询，每次获取下一级 DNS 地址 |
| 客户端负担 | 低，只需发起一次请求 | 较高，需要多次发起请求 |
| 服务器负担 | 高，服务器需要代理完成全部查询 | 低，服务器只返回自己知道的信息 |
| 典型场景 | 客户端 → 本地 DNS 服务器（递归） | 本地 DNS 服务器 → 根/顶级/权威 DNS 服务器（迭代） |

**图示：**

```
递归查询：                         迭代查询：
客户端                               本地 DNS
  │                                    │
  ├─ 请求 example.com ──→ 本地 DNS      ├─ 请求 → 根 DNS（返回 .com 地址）
  │                          │         │
  │                          ├→ 根 DNS  ├─ 请求 → .com DNS（返回权威 DNS 地址）
  │                          ├→ .com DNS│
  │                          ├→ 权威 DNS ├─ 请求 → 权威 DNS（返回 IP）
  │                          │         │
  ├── 返回 IP ──────────────┘         └── 返回 IP 给客户端
```

**实际解析过程是混合模式：** 客户端到本地 DNS 服务器是递归查询，本地 DNS 服务器到根/顶级/权威 DNS 是迭代查询。

#### 2.2.3 DNS 记录类型

| 记录类型 | 含义 | 示例 |
|---------|------|------|
| A | 域名 → IPv4 地址 | `example.com → 93.184.216.34` |
| AAAA | 域名 → IPv6 地址 | `example.com → 2606:2800:220:1:248:1893:25c8:1946` |
| CNAME | 域名别名 → 规范域名 | `www.example.com → example.com` |
| MX | 邮件服务器地址 | `example.com → mail.example.com` |
| NS | 该域名的权威 DNS 服务器 | `example.com → ns1.example.com` |
| TXT | 文本记录（常用于域名验证、SPF 等） | `example.com → "v=spf1 ..."` |

### 2.3 TCP 三次握手

TCP 是面向连接的传输协议，在传输数据之前必须先建立连接，这个过程称为"三次握手"。

#### 2.3.1 三次握手过程

```
客户端                                    服务器
   │                                        │
   │  ──── SYN (seq=x) ────────────────→   │  ① 第一次握手
   │      "我要连接你，我的序列号是 x"       │
   │                                        │
   │  ←── SYN-ACK (seq=y, ack=x+1) ────    │  ② 第二次握手
   │      "收到，我同意连接。我的序列号是 y，  │
   │       我期待你的下一个序列号是 x+1"      │
   │                                        │
   │  ──── ACK (ack=y+1) ──────────────→   │  ③ 第三次握手
   │      "收到，连接已建立"                  │
   │                                        │
   │  ====== TCP 连接已建立 ============    │
   │  ====== 开始传输数据 ==============    │
```

**三次握手详细说明：**

| 握手 | 方向 | 标志位 | 作用 |
|------|------|--------|------|
| 第一次 | 客户端 → 服务器 | SYN=1, seq=x | 客户端请求建立连接，告知初始序列号 |
| 第二次 | 服务器 → 客户端 | SYN=1, ACK=1, seq=y, ack=x+1 | 服务器确认收到请求，告知自己的序列号 |
| 第三次 | 客户端 → 服务器 | ACK=1, ack=y+1 | 客户端确认收到服务器的确认，连接建立 |

#### 2.3.2 为什么是三次握手，而不是两次或四次？

这是面试中的高频问题。核心原因：**三次握手是为了在不可靠的信道上建立可靠的连接，双方都需要确认自己和对方的收发能力正常。**

| 握手次数 | 方案 | 能确认什么 | 问题 |
|---------|------|-----------|------|
| 两次握手 | 客户端 SYN → 服务器 SYN-ACK，连接建立 | 客户端确认自己发送正常、服务器确认自己接收正常 | 服务器无法确认客户端的接收能力；更重要的是，无法防止**已失效的连接请求**到达服务器导致错误 |
| 三次握手 | 客户端 SYN → 服务器 SYN-ACK → 客户端 ACK | 双方都确认了对方的收发能力正常，且能防止历史连接 | 满足需求，效率最高 |
| 四次握手 | 再多一次确认 | 没有额外收益 | 多余的往返，浪费资源 |

**已失效连接请求问题（两次握手无法解决）：**

```
场景：客户端发送了第一个 SYN 请求，但由于网络拥堵，这个请求在路上滞留了很久。
客户端以为请求丢失，重新发送了一个新的 SYN。
滞留的旧 SYN 后来到达服务器。

两次握手：服务器收到旧 SYN → 回复 SYN-ACK → 直接建立连接。
           但客户端已经不需要这个连接了，服务器却一直在等待数据，浪费资源。

三次握手：服务器收到旧 SYN → 回复 SYN-ACK → 客户端收到后发现这不是自己想要的连接，
           不发送 ACK，服务器收不到 ACK 就不会建立连接，资源不会浪费。
```

> 把三次握手想象成**打电话**：你拨号（SYN），对方接起说"喂，哪位？"（SYN-ACK），你说"是我，老王"（ACK）。至此双方都确认对方能听见自己，通话正式开始。如果只有两次握手（你拨号 + 对方接起），你无法确认对方是不是真的接起了，可能只是语音信箱；对方也无法确认你是不是拨错了号。
>
> **为什么必须三次？** 如果只有两次握手，就像你昨天打的电话因为信号不好延迟到今天才接通——对方接起来说"喂"，但你早已挂断。对方却以为你还在线，一直等着你说话，白白浪费资源。三次握手需要你最后回一句"是我"，昨天的延迟电话就不会被误接。这正是 TCP 防止已失效连接请求（old duplicate SYN）的核心机制。

### 2.4 TCP 四次挥手

TCP 连接是全双工的，双方都可以发送和接收数据。断开连接时，双方需要分别关闭自己的发送通道，因此需要四次挥手。

#### 2.4.1 四次挥手过程

```
客户端                                    服务器
   │                                        │
   │  ──── FIN (seq=u) ────────────────→   │  ① 第一次挥手
   │      "我没有数据要发了，想关闭连接"      │
   │                                        │
   │  ←── ACK (ack=u+1) ───────────────    │  ② 第二次挥手
   │      "收到，我知道你发完了"              │
   │                                        │
   │  (客户端进入 FIN_WAIT_2 状态)           │  (服务器可能还有数据要发)
   │                                        │
   │  ←── FIN (seq=v, ack=u+1) ────────    │  ③ 第三次挥手
   │      "我也没有数据要发了，想关闭连接"    │
   │                                        │
   │  ──── ACK (ack=v+1) ──────────────→   │  ④ 第四次挥手
   │      "收到，连接关闭"                    │
   │                                        │
   │  (客户端进入 TIME_WAIT 状态，等待 2MSL)  │  (服务器收到 ACK 后立即关闭)
```

#### 2.4.2 TIME_WAIT 状态

**为什么客户端最后要等待 2MSL（Maximum Segment Lifetime，最长报文段寿命）？**

| 原因 | 说明 |
|------|------|
| 确保最后的 ACK 能到达服务器 | 如果 ACK 丢失，服务器会重发 FIN，客户端需要在此状态下重新发送 ACK。2MSL = 一个 FIN 从发送到超时重传的最长时间 + 一个 ACK 从发送到送达的最长时间。 |
| 让旧连接的所有报文从网络中消失 | 防止旧连接的延迟报文被新连接误接收。经过 2MSL 后，该连接期间产生的所有报文都已从网络中消失。 |

**TCP 状态转换速查：**

| 状态 | 说明 | 所属方 |
|------|------|--------|
| SYN_SENT | 已发送 SYN，等待对方确认 | 客户端 |
| SYN_RCVD | 收到 SYN，已发送 SYN-ACK，等待 ACK | 服务器 |
| ESTABLISHED | 连接已建立，可以传输数据 | 双方 |
| FIN_WAIT_1 | 已发送 FIN，等待对方 ACK | 主动关闭方 |
| FIN_WAIT_2 | 已收到 ACK，等待对方 FIN | 主动关闭方 |
| TIME_WAIT | 等待 2MSL，确保对方收到最后的 ACK | 主动关闭方 |
| CLOSE_WAIT | 收到对方 FIN，已发送 ACK，等待应用程序关闭 | 被动关闭方 |
| LAST_ACK | 应用程序已关闭，已发送 FIN，等待 ACK | 被动关闭方 |
| CLOSED | 连接已关闭 | 双方 |

#### 2.4.3 为什么挥手需要四次，而握手只需三次？

因为 TCP 是全双工的：
- **握手时**：服务器收到 SYN 后，可以**同时**发送 SYN 和 ACK（SYN-ACK 合并），因为此时还没有数据传输。
- **挥手时**：客户端发送 FIN 后，服务器可能还有数据没发完。服务器先回复 ACK 表示"我知道你发完了"，等自己的数据也发完后，再发送 FIN。ACK 和 FIN 不能合并，所以需要四次。

### 2.5 UDP vs TCP

UDP 是另一种传输层协议，与 TCP 形成鲜明对比。

| 对比维度 | TCP | UDP |
|---------|-----|-----|
| 连接方式 | 面向连接（三次握手建立连接） | 无连接（直接发送数据，不需要建立连接） |
| 可靠性 | 可靠传输（确认机制、重传机制、序号保证顺序） | 不可靠传输（不保证送达、不保证顺序） |
| 传输速度 | 较慢（有拥塞控制、流量控制） | 快（无额外控制开销） |
| 数据边界 | 面向字节流（无消息边界） | 面向报文（保留消息边界） |
| 头部开销 | 20 字节 | 8 字节 |
| 适用场景 | 文件传输、网页浏览、邮件、数据库 | 视频直播、VoIP 语音通话、在线游戏、DNS 查询 |
| 多播/广播 | 不支持 | 支持 |
| 拥塞控制 | 有（慢启动、拥塞避免、快速重传、快速恢复） | 无 |

**代码示例：TCP 和 UDP 在前端的体现**

```javascript
// TCP 在前端的体现：HTTP 请求基于 TCP
// 浏览器自动处理 TCP 连接，开发者无需关心底层细节
fetch('https://api.example.com/data')
  .then(res => res.json())
  .then(data => console.log(data));

// UDP 在前端的体现：WebRTC 使用 UDP 传输音视频数据
// WebRTC 在 UDP 之上实现了自己的可靠性机制
const pc = new RTCPeerConnection();
// 音视频流通过 UDP 传输，低延迟优先
navigator.mediaDevices.getUserMedia({ video: true, audio: true })
  .then(stream => {
    stream.getTracks().forEach(track => pc.addTrack(track, stream));
  });
```

> 把 TCP 和 UDP 的区别类比成**快递 vs 广播**：TCP 是顺丰快递，每件包裹都有单号，寄丢了会补发，签收要确认，确保包裹按顺序送达。UDP 是学校的广播喇叭，只管喊话，不管你有没有听到，也不管你听没听清，但优点是快--全校同时听到，没有快递的延迟。

### 2.6 IP 地址与端口

#### 2.6.1 IPv4 与 IPv6

| 对比维度 | IPv4 | IPv6 |
|---------|------|------|
| 地址长度 | 32 位（4 字节） | 128 位（16 字节） |
| 地址数量 | 约 43 亿个 | 约 3.4×10³⁸ 个 |
| 表示方式 | 点分十进制：`192.168.1.1` | 冒号分隔十六进制：`2001:db8::1` |
| 报头格式 | 可变长度（20-60 字节） | 固定 40 字节 |
| NAT 需求 | 需要 NAT 解决地址不足 | 理论上不需要 NAT |
| 安全性 | IPsec 可选 | IPsec 内置支持 |
| 广播 | 支持 | 不支持（用组播替代） |

**特殊 IP 地址：**

| 地址 | 说明 |
|------|------|
| `127.0.0.1` | 本地回环地址（localhost） |
| `0.0.0.0` | 表示本机所有 IPv4 地址（监听时） |
| `::1` | IPv6 本地回环地址 |
| `192.168.x.x` | 私有地址（局域网） |
| `10.x.x.x` | 私有地址（企业内网） |
| `172.16.x.x - 172.31.x.x` | 私有地址 |

### 2.7 URL 组成与编码

#### 2.7.1 URL 结构解析

一个完整的 URL 由以下部分组成：

```
https://www.example.com:443/path/to/page?key1=value1&key2=value2#section1
└─┬─┘ └──────┬──────┘└┬┘└─────┬──────┘└───────────┬──────────┘└───┬───┘
 scheme    host      port   path               query            fragment
 协议      主机名    端口   路径              查询参数           片段标识符
```

| 组成 | 名称 | 说明 | 是否必须 |
|------|------|------|---------|
| `scheme` | 协议 | 指定使用的协议，如 `http`、`https`、`ftp`、`ws` | 是 |
| `host` | 主机名 | 域名或 IP 地址，如 `www.example.com` 或 `192.168.1.1` | 是 |
| `port` | 端口号 | 服务端口，HTTP 默认 80，HTTPS 默认 443（默认端口可省略） | 否 |
| `path` | 路径 | 服务器上的资源路径，如 `/api/users` | 是 |
| `query` | 查询参数 | 以 `?` 开头，`key=value` 格式，多个参数用 `&` 分隔 | 否 |
| `fragment` | 片段标识符 | 以 `#` 开头，指向页面内的某个位置（不会发送到服务器） | 否 |

```javascript
// 使用 URL API 解析 URL
const url = new URL('https://www.example.com:8080/api/users?id=123&sort=desc#profile');

console.log(url.protocol);  // 'https:'
console.log(url.hostname);  // 'www.example.com'
console.log(url.port);      // '8080'
console.log(url.pathname);  // '/api/users'
console.log(url.search);    // '?id=123&sort=desc'
console.log(url.hash);      // '#profile'

// 获取查询参数
console.log(url.searchParams.get('id'));    // '123'
console.log(url.searchParams.get('sort'));  // 'desc'

// 遍历所有查询参数
url.searchParams.forEach((value, key) => {
  console.log(`${key}: ${value}`);
});
```

#### 2.7.2 URL 编码 / 解码

URL 中只能使用 ASCII 字符集中的部分字符，非 ASCII 字符和特殊字符需要进行编码。

| 函数 | 编码范围 | 不编码的字符 | 适用场景 |
|------|---------|-------------|---------|
| `encodeURIComponent()` | 编码除 `A-Z a-z 0-9 - _ . ! ~ * ' ( )` 之外的所有字符 | 极少 | 编码 URL 参数值、路径段 |
| `encodeURI()` | 编码除 `A-Z a-z 0-9 - _ . ! ~ * ' ( ) ; , / ? : @ & = + $ #` 之外的字符 | 保留 URL 结构字符 | 编码完整 URL |
| `decodeURIComponent()` | 解码 `encodeURIComponent` 的结果 | - | 解码 URL 参数值 |
| `decodeURI()` | 解码 `encodeURI` 的结果 | - | 解码完整 URL |

```javascript
// encodeURIComponent：编码 URL 参数值（推荐使用）
const name = '张三';
const query = 'name=' + encodeURIComponent(name);
// name=%E5%BC%A0%E4%B8%89

// encodeURI：编码完整 URL（保留 URL 结构字符）
const url = 'https://example.com/搜索?q=前端';
const encoded = encodeURI(url);
// https://example.com/%E6%90%9C%E7%B4%A2?q=%E5%89%8D%E7%AB%AF

// 常见错误：用 encodeURI 编码参数值
const wrong = 'https://example.com?q=' + encodeURI('a&b=c');
// https://example.com?q=a&b=c  ← & 没有被编码，服务器会解析出两个参数！

// 正确做法：用 encodeURIComponent
const correct = 'https://example.com?q=' + encodeURIComponent('a&b=c');
// https://example.com?q=a%26b%3Dc  ← 正确，& 和 = 被编码了

// 解码
const decoded = decodeURIComponent('%E5%BC%A0%E4%B8%89');
console.log(decoded); // '张三'
```

**常见需要编码的字符：**

| 字符 | 编码后 | 说明 |
|------|--------|------|
| 空格 | `%20` | 空格在 URL 中必须编码 |
| `&` | `%26` | 参数分隔符，出现在值中必须编码 |
| `=` | `%3D` | 键值分隔符，出现在值中必须编码 |
| `?` | `%3F` | 查询字符串起始符，出现在值中必须编码 |
| `#` | `%23` | 片段标识符，出现在值中必须编码 |
| `/` | `%2F` | 路径分隔符，出现在参数值中由 `encodeURIComponent` 编码 |
| 中文 | `%E5%BC%A0` 等 | 非 ASCII 字符必须编码 |

### 2.8 HTTP 请求方法

HTTP 定义了一组请求方法，用于表明对资源的操作意图。

#### 2.8.1 常用请求方法

| 方法 | 含义 | 幂等性 | 安全性 | 请求体 | 缓存 |
|------|------|--------|--------|--------|------|
| GET | 获取资源 | 是 | 是 | 无 | 可缓存 |
| POST | 创建资源 | 否 | 否 | 有 | 一般不缓存 |
| PUT | 完整替换资源 | 是 | 否 | 有 | 不可缓存 |
| DELETE | 删除资源 | 是 | 否 | 可有 | 不可缓存 |
| PATCH | 部分更新资源 | 否 | 否 | 有 | 不可缓存 |
| HEAD | 获取响应头（无响应体） | 是 | 是 | 无 | 可缓存 |
| OPTIONS | 获取服务器支持的请求方法 | 是 | 是 | 无 | 不可缓存 |

**术语解释：**

| 术语 | 定义 | 举例 |
|------|------|------|
| 幂等性 | 同一操作执行多次，结果与执行一次相同 | GET 多次读取同一资源，结果不变；PUT 多次提交相同数据，资源状态不变；DELETE 多次删除同一资源，第一次成功，后续返回 404，但服务器状态不变 |
| 安全性 | 操作不会修改服务器上的资源 | GET 只读取不修改；HEAD 只获取头部不修改；POST/PUT/DELETE/PATCH 都会修改资源 |

#### 2.8.2 各方法使用场景

```javascript
// GET：获取资源列表
fetch('/api/users?page=1&limit=20')
  .then(res => res.json())
  .then(data => console.log(data));

// POST：创建新资源
fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: '张三', email: 'zhangsan@example.com' })
});

// PUT：完整替换资源（需要提供所有字段）
fetch('/api/users/123', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: '张三', email: 'newemail@example.com' })
});

// PATCH：部分更新资源（只提供需要修改的字段）
fetch('/api/users/123', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email: 'newemail@example.com' })
});

// DELETE：删除资源
fetch('/api/users/123', {
  method: 'DELETE'
});

// HEAD：检查资源是否存在（不下载响应体）
fetch('/api/users/123', { method: 'HEAD' })
  .then(res => {
    if (res.ok) console.log('资源存在');
    else console.log('资源不存在');
  });

// OPTIONS：预检请求（CORS 场景）
// 浏览器在跨域非简单请求前自动发送 OPTIONS 请求
```

#### 2.8.3 GET 和 POST 深入对比

| 对比维度 | GET | POST |
|---------|-----|------|
| 参数位置 | URL 查询字符串中 | 请求体中 |
| 参数长度 | 受 URL 长度限制（浏览器通常限制约 2KB-8KB） | 理论上无限制（受服务器配置限制） |
| 安全性 | 参数暴露在 URL 中，浏览器历史、服务器日志中可见 | 参数在请求体中，不暴露在 URL |
| 书签 | 可收藏 | 不可收藏 |
| 缓存 | 浏览器可缓存 | 一般不缓存 |
| 后退/刷新 | 无害 | 浏览器会提示"是否重新提交表单" |
| 编码类型 | `application/x-www-form-urlencoded` | `application/x-www-form-urlencoded` 或 `multipart/form-data` |

### 2.9 HTTP 状态码

HTTP 状态码由三位数字组成，第一位表示响应类别。

#### 2.9.1 状态码分类

| 类别 | 范围 | 含义 | 说明 |
|------|------|------|------|
| 1xx | 100-199 | 信息响应 | 请求已接收，继续处理 |
| 2xx | 200-299 | 成功 | 请求已成功处理 |
| 3xx | 300-399 | 重定向 | 需要进一步操作才能完成请求 |
| 4xx | 400-499 | 客户端错误 | 请求有语法错误或无法完成 |
| 5xx | 500-599 | 服务器错误 | 服务器处理请求时出错 |

#### 2.9.2 常见状态码详解

| 状态码 | 短语 | 说明 | 前端处理 |
|--------|------|------|---------|
| 200 | OK | 请求成功，GET 返回资源，POST 返回处理结果 | 正常处理响应数据 |
| 201 | Created | 资源创建成功（POST 请求成功后常见） | 获取新资源的位置（Location 头） |
| 204 | No Content | 请求成功但无响应体（DELETE 成功后常见） | 不解析响应体 |
| 301 | Moved Permanently | 永久重定向，浏览器会缓存重定向 | 更新书签/API 地址 |
| 302 | Found | 临时重定向 | 不做永久缓存 |
| 304 | Not Modified | 资源未修改（协商缓存命中） | 使用本地缓存，不重新下载 |
| 400 | Bad Request | 请求参数错误 | 提示用户检查输入 |
| 401 | Unauthorized | 未认证，需要登录 | 跳转到登录页 |
| 403 | Forbidden | 已认证但无权限访问 | 提示权限不足 |
| 404 | Not Found | 资源不存在 | 显示 404 页面或提示 |
| 405 | Method Not Allowed | 请求方法不被允许 | 检查 API 文档 |
| 408 | Request Timeout | 请求超时 | 提示用户重试 |
| 409 | Conflict | 资源冲突（如重复创建） | 提示冲突信息 |
| 422 | Unprocessable Entity | 请求格式正确但语义错误（验证失败） | 显示字段验证错误信息 |
| 429 | Too Many Requests | 请求频率超限 | 等待后重试（根据 Retry-After 头） |
| 500 | Internal Server Error | 服务器内部错误 | 显示通用错误提示 |
| 502 | Bad Gateway | 网关错误（上游服务器无响应） | 提示服务暂时不可用 |
| 503 | Service Unavailable | 服务器暂时不可用（过载或维护） | 提示稍后重试 |
| 504 | Gateway Timeout | 网关超时（上游服务器响应超时） | 提示请求超时，重试 |

```javascript
// 前端统一处理 HTTP 状态码
async function request(url, options = {}) {
  const response = await fetch(url, options);

  if (response.ok) {
    // 2xx 状态码
    if (response.status === 204) return null; // 无响应体
    return response.json();
  }

  // 根据状态码分类处理
  switch (response.status) {
    case 401:
      // 未登录，跳转登录页
      window.location.href = '/login';
      throw new Error('请先登录');
    case 403:
      throw new Error('没有权限执行此操作');
    case 404:
      throw new Error('请求的资源不存在');
    case 422: {
      const errors = await response.json();
      throw new ValidationError(errors);
    }
    case 429: {
      const retryAfter = response.headers.get('Retry-After');
      throw new RateLimitError(retryAfter);
    }
    case 500:
    case 502:
    case 503:
      throw new Error('服务器繁忙，请稍后重试');
    default:
      throw new Error(`请求失败: ${response.status}`);
  }
}

// 304 状态码是浏览器自动处理的，fetch 会返回 200 并从缓存中读取
// 所以在代码中一般不需要特殊处理 304
```

### 2.10 HTTP 请求头与响应头

#### 2.10.1 常用请求头

| 请求头 | 说明 | 示例 |
|--------|------|------|
| `Content-Type` | 请求体的媒体类型 | `application/json`、`multipart/form-data` |
| `Authorization` | 认证凭据 | `Bearer eyJhbGciOi...` |
| `Accept` | 客户端能接受的响应内容类型 | `application/json` |
| `Accept-Encoding` | 客户端能接受的内容编码（压缩） | `gzip, deflate, br` |
| `Accept-Language` | 客户端偏好的语言 | `zh-CN,zh;q=0.9` |
| `Cache-Control` | 缓存控制指令 | `no-cache`、`max-age=0` |
| `Cookie` | 发送给服务器的 Cookie | `sessionId=abc123` |
| `User-Agent` | 客户端标识 | `Mozilla/5.0 ...` |
| `Origin` | 请求来源（协议+域名+端口） | `https://www.example.com` |
| `Referer` | 请求来源的完整 URL | `https://www.example.com/page` |
| `If-None-Match` | 协商缓存（配合 ETag） | `"abc123"` |
| `If-Modified-Since` | 协商缓存（配合 Last-Modified） | `Wed, 21 Oct 2023 07:28:00 GMT` |

#### 2.10.2 常用响应头

| 响应头 | 说明 | 示例 |
|--------|------|------|
| `Content-Type` | 响应体的媒体类型 | `application/json; charset=utf-8` |
| `Content-Length` | 响应体大小（字节） | `1024` |
| `Content-Encoding` | 响应体的内容编码 | `gzip`、`br` |
| `Cache-Control` | 缓存控制指令 | `max-age=3600`、`no-store` |
| `ETag` | 资源版本标识（协商缓存） | `"abc123"` |
| `Last-Modified` | 资源最后修改时间 | `Wed, 21 Oct 2023 07:28:00 GMT` |
| `Set-Cookie` | 设置 Cookie | `sessionId=abc123; HttpOnly; Secure` |
| `Access-Control-Allow-Origin` | CORS 允许的来源 | `*` 或 `https://www.example.com` |
| `Access-Control-Allow-Methods` | CORS 允许的方法 | `GET, POST, PUT, DELETE` |
| `Access-Control-Allow-Headers` | CORS 允许的请求头 | `Content-Type, Authorization` |
| `Access-Control-Max-Age` | 预检请求缓存时间（秒） | `86400`（24 小时） |
| `Location` | 重定向目标地址 | `https://www.example.com/new` |
| `Retry-After` | 重试等待时间 | `120`（秒）或 `Wed, 21 Oct 2023 07:30:00 GMT` |

#### 2.10.3 Content-Type 常见值

| Content-Type | 说明 | 使用场景 |
|-------------|------|---------|
| `application/json` | JSON 数据 | RESTful API 请求/响应 |
| `application/x-www-form-urlencoded` | 表单数据（URL 编码） | 简单表单提交 |
| `multipart/form-data` | 多部分表单数据 | 文件上传 |
| `text/html` | HTML 文档 | 页面响应 |
| `text/css` | CSS 样式表 | 样式文件 |
| `application/javascript` | JavaScript 代码 | 脚本文件 |
| `image/png`、`image/jpeg` | 图片 | 图片资源 |
| `application/octet-stream` | 二进制流 | 文件下载 |

#### 2.10.4 CORS 相关头部详解

```javascript
// CORS 是前端面试中最高频的网络协议问题之一

// 简单请求：同时满足以下条件
// 1. 方法为 GET、HEAD、POST 之一
// 2. 仅使用 Accept、Accept-Language、Content-Language、Content-Type
// 3. Content-Type 仅限 application/x-www-form-urlencoded、multipart/form-data、text/plain

// 简单请求：浏览器直接发送请求，检查响应头中的 CORS 头部
// 响应头需要包含：Access-Control-Allow-Origin

// 非简单请求（如 Content-Type: application/json 的 POST 请求）：
// 浏览器先发送 OPTIONS 预检请求，询问服务器是否允许跨域
// 预检请求的请求头：
//   Origin: https://www.example.com
//   Access-Control-Request-Method: POST
//   Access-Control-Request-Headers: Content-Type

// 预检请求的响应头：
//   Access-Control-Allow-Origin: https://www.example.com
//   Access-Control-Allow-Methods: GET, POST, PUT, DELETE
//   Access-Control-Allow-Headers: Content-Type, Authorization
//   Access-Control-Max-Age: 86400  （预检结果缓存 24 小时）

// 前端处理跨域的常见方案
// 方案一：开发环境代理（Vite 配置）
// vite.config.js
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://backend-server:3000',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
};
```

#### 2.10.5 缓存相关头部

| 缓存策略 | 相关头部 | 说明 |
|---------|---------|------|
| 强缓存（本地缓存） | `Cache-Control: max-age=3600` | 在 3600 秒内直接使用缓存，不发请求 |
| 强缓存 | `Cache-Control: no-cache` | 每次都向服务器验证（使用协商缓存） |
| 强缓存 | `Cache-Control: no-store` | 完全不缓存 |
| 协商缓存 | `ETag` / `If-None-Match` | 服务器返回资源版本号，下次请求带上，服务器比较后返回 304 或 200 |
| 协商缓存 | `Last-Modified` / `If-Modified-Since` | 服务器返回修改时间，下次请求带上，服务器比较后返回 304 或 200 |

```javascript
// 强缓存 vs 协商缓存流程
// 强缓存：浏览器检查本地缓存是否过期 → 未过期则直接使用，不发请求
// 协商缓存：浏览器发送请求 → 服务器检查资源是否修改 → 未修改返回 304 → 浏览器使用本地缓存

// ETag 优先级高于 Last-Modified
// ETag 更精确：Last-Modified 只能精确到秒，同一秒内多次修改无法区分
```

### 2.11 HTTPS 与 TLS 握手

HTTPS 在 HTTP 和 TCP 之间插入 TLS（Transport Layer Security）层，通过加密和证书机制保证通信安全。

#### 2.11.1 HTTPS 的三大安全目标

| 目标 | 说明 | 实现方式 |
|------|------|---------|
| 机密性（Confidentiality） | 通信内容只有收发双方可见，中间人无法窃听 | 对称加密（AES） |
| 完整性（Integrity） | 通信内容在传输过程中没有被篡改 | 消息认证码（MAC） |
| 身份认证（Authentication） | 确认通信对象是真实的服务器，而非冒充者 | 数字证书（CA 证书链） |

#### 2.11.2 对称加密 vs 非对称加密

| 对比维度 | 对称加密 | 非对称加密 |
|---------|---------|-----------|
| 密钥数量 | 1 个密钥（加密和解密用同一个密钥） | 2 个密钥（公钥加密，私钥解密） |
| 加密速度 | 快 | 慢（比对称加密慢 100-1000 倍） |
| 密钥分发 | 困难（如何安全传递密钥？） | 简单（公钥可以公开分发） |
| 典型算法 | AES、DES、ChaCha20 | RSA、ECC、ECDHE |
| 使用场景 | 大量数据传输的加密 | 密钥交换、数字签名、身份认证 |

**HTTPS 的加密策略：混合加密**

HTTPS 结合了两种加密方式的优点：
- **非对称加密**用于 TLS 握手阶段，交换对称加密的密钥
- **对称加密**用于数据传输阶段，高效加密大量数据

> 把 HTTPS 混合加密类比成**送一个带锁的箱子**：你想让朋友把机密文件放进去寄给你。非对称加密是：你先把一个打开的锁（公钥）寄给朋友，朋友把文件放进去后用你的锁锁上，只有你有钥匙（私钥）能打开。对称加密是：你们俩事先约定了一把相同的钥匙，但问题是--怎么安全地把这把钥匙交给对方呢？HTTPS 的做法是：先用非对称加密（锁+钥匙）安全地传递对称加密的钥匙，然后后续的所有通信都用这把对称钥匙加密，又快又安全。

#### 2.11.3 TLS 握手过程（简化版）

```
客户端                                    服务器
   │                                        │
   │  ── ClientHello ──────────────────→   │
   │  (支持的 TLS 版本、加密套件列表、随机数1) │
   │                                        │
   │  ←── ServerHello ──────────────────    │
   │  (选定的 TLS 版本、加密套件、随机数2)     │
   │  ←── Certificate ────────────────      │
   │  (服务器证书，包含公钥和 CA 签名)        │
   │  ←── ServerHelloDone ─────────────     │
   │                                        │
   │  (客户端验证证书：检查 CA 签名、有效期、  │
   │   域名是否匹配)                          │
   │                                        │
   │  ── ClientKeyExchange ────────────→   │
   │  (用服务器公钥加密的预主密钥)             │
   │                                        │
   │  (双方用随机数1+随机数2+预主密钥         │
   │   生成对称加密的会话密钥)                │
   │                                        │
   │  ── ChangeCipherSpec ─────────────→   │
   │  (通知服务器：后续通信将使用会话密钥加密)   │
   │  ── Finished ──────────────────────→   │
   │                                        │
   │  ←── ChangeCipherSpec ─────────────    │
   │  ←── Finished ─────────────────────    │
   │                                        │
   │  ====== 加密通信开始 ===============    │
```

#### 2.11.4 证书链验证

```
根 CA 证书（自签名，操作系统/浏览器内置信任）
   │
   └── 签名 → 中间 CA 证书
                 │
                 └── 签名 → 服务器证书（包含域名和公钥）
```

浏览器验证证书的过程：
1. 检查服务器证书是否由信任的中间 CA 签发
2. 检查中间 CA 证书是否由信任的根 CA 签发
3. 检查证书是否在有效期内
4. 检查证书的域名是否与访问的域名一致
5. 检查证书是否被吊销（CRL 或 OCSP）

### 2.12 HTTP/1.1 vs HTTP/2 vs HTTP/3

#### 2.12.1 三代 HTTP 协议对比

| 对比维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---------|----------|--------|--------|
| 发布年份 | 1997 | 2015 | 2022 |
| 传输层协议 | TCP | TCP | QUIC（基于 UDP） |
| 连接复用 | 支持（Keep-Alive），但串行请求 | 多路复用（一个连接上并行传输多个请求/响应） | 多路复用（无队头阻塞） |
| 头部压缩 | 无（每次请求携带完整头部） | HPACK 头部压缩 | QPACK 头部压缩 |
| 服务器推送 | 不支持 | 支持（Server Push）[^1] | 支持（Server Push）[^1] |
| 队头阻塞 | 有（HTTP 层队头阻塞） | 有（TCP 层队头阻塞--丢包影响所有流） | 无（QUIC 基于 UDP，单流丢包不影响其他流） |
| 连接建立 | TCP 三次握手 + TLS 握手 | TCP 三次握手 + TLS 握手 | 0-RTT（首次连接 1-RTT） |
| 二进制协议 | 否（文本协议） | 是（二进制帧） | 是（二进制帧） |
| 优先级 | 无 | 流优先级 | 流优先级 |

#### 2.12.2 HTTP/2 多路复用详解

```javascript
// HTTP/1.1：每个请求需要单独的 TCP 连接（或串行排队）
// 浏览器对同一域名有并发连接数限制（通常 6 个）
// 优化手段：域名分片、雪碧图、资源合并

// HTTP/2：一个 TCP 连接上可以同时传输多个请求和响应
// 通过二进制帧（Frame）和流（Stream）实现
// 每个请求/响应对应一个 Stream，Stream 之间互相独立
// 帧可以交错发送，接收端根据帧头中的 Stream ID 重新组装

// 前端不需要做任何代码修改，HTTP/2 的优化由服务器和浏览器自动处理
// 但需要注意：HTTP/1.1 时代的优化手段（域名分片、雪碧图、资源合并）
// 在 HTTP/2 下反而可能降低性能
```

#### 2.12.3 HTTP/3 与 QUIC 协议

```
HTTP/1.1 和 HTTP/2：
┌─────────────┐
│    HTTP     │  应用层
├─────────────┤
│    TLS      │  安全层
├─────────────┤
│    TCP      │  传输层
├─────────────┤
│     IP      │  网络层
└─────────────┘

HTTP/3：
┌─────────────┐
│  HTTP/3     │  应用层
├─────────────┤
│    QUIC     │  传输层 + 安全层（内置 TLS 1.3）
├─────────────┤
│    UDP      │  传输层
├─────────────┤
│     IP      │  网络层
└─────────────┘
```

**HTTP/3 的核心优势：**

| 特性 | 说明 |
|------|------|
| 0-RTT 连接建立 | 已访问过的网站，再次连接时无需握手，直接发送数据 |
| 无 TCP 队头阻塞 | QUIC 基于 UDP，单个流的数据包丢失不会阻塞其他流 |
| 连接迁移 | 即使网络切换（Wi-Fi → 4G），连接也能无缝保持，因为 QUIC 使用连接 ID 而非 IP+端口标识连接 |
| 内置加密 | QUIC 内置 TLS 1.3，无需额外 TLS 握手 |

### 2.13 RESTful API 设计原则

REST（Representational State Transfer）是一种基于 HTTP 协议的 API 设计风格。

#### 2.13.1 核心设计原则

**1. 资源导向，使用名词复数**

| 错误 | 正确 | 说明 |
|------|------|------|
| `GET /getUsers` | `GET /users` | 用名词表示资源，不用动词 |
| `POST /createUser` | `POST /users` | 创建用 POST 方法表达 |
| `GET /getUserById?id=123` | `GET /users/123` | 用路径表示资源标识 |
| `POST /deleteUser` | `DELETE /users/123` | 用 HTTP 方法表达操作 |

**2. HTTP 方法语义**

| 方法 | 路径 | 含义 | 示例 |
|------|------|------|------|
| GET | `/users` | 获取用户列表 | `GET /users?page=1&limit=20` |
| GET | `/users/:id` | 获取单个用户 | `GET /users/123` |
| POST | `/users` | 创建用户 | `POST /users` |
| PUT | `/users/:id` | 完整替换用户 | `PUT /users/123` |
| PATCH | `/users/:id` | 部分更新用户 | `PATCH /users/123` |
| DELETE | `/users/:id` | 删除用户 | `DELETE /users/123` |

**3. 状态码语义**

| 操作 | 成功状态码 | 说明 |
|------|-----------|------|
| GET 列表 | 200 OK | 返回资源列表 |
| GET 单个 | 200 OK | 返回单个资源 |
| POST 创建 | 201 Created | 返回新资源（含 Location 头） |
| PUT 替换 | 200 OK | 返回更新后的资源 |
| PATCH 更新 | 200 OK | 返回更新后的资源 |
| DELETE 删除 | 204 No Content | 无响应体 |

**4. API 版本控制**

```javascript
// 方案一：URL 路径版本（最常见）
GET /api/v1/users
GET /api/v2/users

// 方案二：请求头版本
GET /api/users
Accept: application/vnd.example.v1+json

// 方案三：查询参数版本（不推荐）
GET /api/users?version=1
```

**5. 分页、过滤、排序**

```javascript
// 分页
GET /api/users?page=1&limit=20

// 过滤
GET /api/users?status=active&role=admin

// 排序

GET /api/users?sort=name,-age      // 按 name 升序，age 降序

// 字段筛选

// 搜索

```

### 2.14 分页模式对比

分页是 API 设计中最常见的需求之一，主要有两种实现方式。

#### 2.14.1 Offset-based 分页 vs Cursor-based 分页

| 对比维度 | Offset-based（偏移分页） | Cursor-based（游标分页） |
|---------|------------------------|------------------------|
| 实现方式 | `?page=1&limit=20` 或 `?offset=0&limit=20` | `?cursor=xxx&limit=20` |
| SQL 实现 | `SELECT * FROM users LIMIT 20 OFFSET 0` | `SELECT * FROM users WHERE id > ? LIMIT 20` |
| 性能 | 大偏移量时性能差（OFFSET 100000 需要扫描前 100000 行） | 始终高效（利用索引直接定位） |
| 数据一致性 | 分页期间新增/删除数据会导致重复/遗漏 | 基于游标值，不会遗漏或重复 |
| 总页数 | 可以计算总页数 | 无法计算总页数（只能判断是否还有下一页） |
| 跳页 | 支持（可直接跳到第 N 页） | 不支持（只能顺序翻页） |
| 适用场景 | 后台管理系统、数据总量不大、需要跳页 | 移动端无限滚动、实时数据流、数据量大 |

#### 2.14.2 代码实现对比

```javascript
// Cursor-based 分页
// 请求：GET /api/users?cursor=123&limit=20
// 后端 SQL：SELECT * FROM users WHERE id > 123 ORDER BY id LIMIT 20

// 前端实现
let cursor = null; // 第一页 cursor 为 null
let hasMore = true;

  const params = new URLSearchParams({ limit });
  if (cursor) params.append('cursor', cursor);

  const res = await fetch(`/api/users?${params}`);
  const { data } = await res.json();

  // 更新游标和状态
  cursor = data.nextCursor ?? null;
  hasMore = data.nextCursor !== null;

  return data.items;
}

// 无限滚动组件
function InfiniteScroll({ onLoadMore }) {
  const loaderRef = useRef(null);

  useEffect(() => {
    const observer = new IntersectionObserver((entries) => {
      if (entries[0].isIntersecting) {
        onLoadMore();
      }
    });
    if (loaderRef.current) observer.observe(loaderRef.current);
    return () => observer.disconnect();
```

#### 2.14.3 分页模式选择指南

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 后台管理列表（数据量万级以下） | Offset-based | 需要跳页功能，数据量不大 |
| 移动端信息流（无限滚动） | Cursor-based | 不需要跳页，数据量大，实时性强 |
| 搜索列表 | Offset-based | 需要显示总页数，用户可能跳页 |
| 实时数据流（如消息列表） | Cursor-based | 避免新增数据导致重复，保证一致性 |
| 数据导出 | Cursor-based | 数据量大，逐页处理效率高 |

### 3.1 封装一个健壮的 HTTP 请求模块

```javascript
// request.js - 基于 fetch 的封装，包含错误处理、超时、重试、拦截器
class HttpClient {
  constructor(baseURL = '', defaultOptions = {}) {
    this.baseURL = baseURL;
    this.defaultOptions = {
      headers: { 'Content-Type': 'application/json' },
      timeout: 10000,
      ...defaultOptions
    };
    this.interceptors = {
      request: [],
      response: []
    };
  }

  // 请求拦截器
  useRequestInterceptor(fn) {
    this.interceptors.request.push(fn);
  }

  // 响应拦截器
  useResponseInterceptor(fn) {
    this.interceptors.response.push(fn);
  }

  // 核心请求方法
  async request(url, options = {}) {
    const mergedOptions = {
      ...this.defaultOptions,
      ...options,
      headers: { ...this.defaultOptions.headers, ...options.headers }
    };

    // 构建完整 URL
    const fullURL = url.startsWith('http') ? url : `${this.baseURL}${url}`;

    // 执行请求拦截器
    let requestConfig = { url: fullURL, options: mergedOptions };
    for (const interceptor of this.interceptors.request) {
      requestConfig = await interceptor(requestConfig);
    }

    // 超时控制
    const controller = new AbortController();
    const timeoutId = setTimeout(() => controller.abort(), mergedOptions.timeout);
    requestConfig.options.signal = controller.signal;

    try {
      let response = await fetch(requestConfig.url, requestConfig.options);
      clearTimeout(timeoutId);

      // 执行响应拦截器
      for (const interceptor of this.interceptors.response) {
        response = await interceptor(response);
      }

      // 处理 HTTP 错误
      if (!response.ok) {
        throw await this.handleError(response);
      }

      // 204 无内容
      if (response.status === 204) return null;

      return await response.json();
    } catch (error) {
      clearTimeout(timeoutId);
      if (error.name === 'AbortError') {
        throw new Error('请求超时');
      }
      throw error;
    }
  }

  // 错误处理
  async handleError(response) {
    let errorData;
    try {
      errorData = await response.json();
    } catch {
      errorData = { message: '未知错误' };
    }

    const error = new Error(errorData.message || `请求失败: ${response.status}`);
    error.status = response.status;
    error.data = errorData;
    return error;
  }

  // 便捷方法
  get(url, params, options) {
    const query = params ? '?' + new URLSearchParams(params).toString() : '';
    return this.request(url + query, { ...options, method: 'GET' });
  }

  post(url, data, options) {
    return this.request(url, {
      ...options,
      method: 'POST',
      body: JSON.stringify(data)
    });
  }

  put(url, data, options) {
    return this.request(url, {
      ...options,
      method: 'PUT',
      body: JSON.stringify(data)
    });
  }

  patch(url, data, options) {
    return this.request(url, {
      ...options,
      method: 'PATCH',
      body: JSON.stringify(data)
    });
  }

  delete(url, options) {
    return this.request(url, { ...options, method: 'DELETE' });
  }
}

// 使用示例
const http = new HttpClient('/api', { timeout: 5000 });

// 添加请求拦截器：自动添加 Token
http.useRequestInterceptor((config) => {
  const token = localStorage.getItem('token');
  if (token) {
    config.options.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 添加响应拦截器：统一处理 401
http.useResponseInterceptor((response) => {
  if (response.status === 401) {
    localStorage.removeItem('token');
    window.location.href = '/login';
  }
  return response;
});

// 使用
const users = await http.get('/users', { page: 1, limit: 20 });
const newUser = await http.post('/users', { name: '张三', email: 'zhangsan@example.com' });
```

### 3.2 文件上传（multipart/form-data）

```javascript
// 上传进度（使用 XMLHttpRequest，fetch 暂不支持原生进度）
function uploadWithProgress(file, onProgress) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    const formData = new FormData();
    formData.append('file', file);

    xhr.upload.addEventListener('progress', (e) => {
      if (e.lengthComputable) {
        const percent = Math.round((e.loaded / e.total) * 100);
        onProgress(percent);
      }
    });

    xhr.addEventListener('load', () => {
      if (xhr.status >= 200 && xhr.status < 300) {
        resolve(JSON.parse(xhr.responseText));
      } else {
        reject(new Error('上传失败'));
      }
    });

    xhr.open('POST', '/api/upload');
    xhr.send(formData);
  });
}
```

## 四、常见面试题

**Q1：从输入 URL 到页面展示，经历了哪些步骤？（结合网络协议部分）**

A：这是前端面试中最经典的综合题，网络协议相关步骤包括：
1. **DNS 解析**：浏览器缓存 → OS 缓存 → hosts 文件 → 本地 DNS 服务器 → 根 DNS → 顶级 DNS → 权威 DNS，最终获取服务器 IP 地址
2. **TCP 三次握手**：客户端 SYN → 服务器 SYN-ACK → 客户端 ACK，建立 TCP 连接
3. **TLS 握手**（HTTPS）：ClientHello → ServerHello + Certificate → ClientKeyExchange → 双方生成会话密钥 → 加密通信开始
4. **发送 HTTP 请求**：浏览器构造 HTTP 请求报文，发送给服务器
5. **服务器处理请求**：服务器解析请求，生成响应
6. **接收 HTTP 响应**：浏览器接收响应，解析状态码和响应头
7. **TCP 四次挥手**：数据传输完毕后断开连接（或保持连接复用）
8. 之后进入浏览器渲染流程（HTML 解析、CSS 解析、渲染树构建、布局、绘制、合成）

**Q2：TCP 为什么是三次握手，不是两次或四次？**

A：三次握手是为了在不可靠的网络上建立可靠的连接，做到"双方确认对方的收发能力都正常"。两次握手时，服务器无法确认客户端的接收能力，且无法防止已失效的连接请求到达服务器导致错误（服务器收到旧 SYN 后直接建立连接，但客户端不需要这个连接，浪费服务器资源）。四次握手没有必要，因为第二次握手时服务器可以同时发送 SYN 和 ACK（SYN-ACK 合并），多一次是多余的往返，三次已经能完成双向确认。

**Q3：HTTP/1.1、HTTP/2、HTTP/3 的核心区别是什么？**

A：
- HTTP/1.1：文本协议，串行请求，有队头阻塞，不支持头部压缩。每次请求需要携带完整头部，同一域名下浏览器限制并发连接数（通常 6 个）。
- HTTP/2：二进制协议，多路复用（一个连接并行多个请求），HPACK 头部压缩，服务器推送[^1]。但 TCP 层的队头阻塞仍然存在（一个 TCP 包丢失，整个连接的所有流都等待重传）。
- HTTP/3：基于 QUIC 协议（UDP），0-RTT 建立连接，无 TCP 队头阻塞（单流丢包不影响其他流），连接迁移（网络切换不断连）。是目前最新、最快的 HTTP 版本。

**Q4：HTTPS 为什么是安全的？TLS 握手做了什么？**

A：HTTPS 通过 TLS 层实现三大安全目标：
1. 机密性：通过对称加密（AES）保护通信内容，密钥通过非对称加密（RSA/ECDHE）在握手阶段安全交换
2. 完整性：通过消息认证码（MAC）确保数据未被篡改
3. 身份认证：通过 CA 证书链验证服务器身份，防止中间人攻击

TLS 握手过程：客户端发送 ClientHello（支持的加密套件）→ 服务器返回 ServerHello + 证书 + 公钥 → 客户端验证证书 → 双方协商生成会话密钥 → 后续通信使用对称加密。

**Q5：HTTP 状态码 301 和 302 有什么区别？401 和 403 有什么区别？**

A：
- 301（永久重定向）：资源永久迁移到新地址，浏览器会缓存重定向，下次直接访问新地址。适用于域名变更等场景。
- 302（临时重定向）：资源临时迁移，浏览器不会缓存，每次都会先访问原地址再跳转。适用于临时维护等场景。
- 401（未认证）：用户没有提供认证凭据或凭据无效，需要登录。浏览器会弹出登录框或前端跳转到登录页。
- 403（已认证但无权限）：用户已登录但没有访问该资源的权限。前端应提示"权限不足"而非跳转登录页。

**Q6：RESTful API 设计有哪些核心原则？**

A：
1. 资源导向：URL 使用名词复数表示资源（如 `/users`），不用动词
2. HTTP 方法语义：GET 读取、POST 创建、PUT 完整替换、PATCH 部分更新、DELETE 删除
3. 状态码语义：200 成功、201 创建成功、204 无内容、400 参数错误、404 不存在、422 验证失败、500 服务器错误
4. 无状态：每个请求包含所有必要信息，服务器不保存客户端状态
5. 版本控制：通过 URL 路径（`/v1/`）或请求头进行版本管理
6. 分页/过滤/排序：通过查询参数实现

**Q7：Offset-based 分页和 Cursor-based 分页各自适用什么场景？**

A：
- Offset-based：适合数据量不大（万级以下）、需要跳页功能的场景，如后台管理系统。缺点是偏移量越大性能越差（`OFFSET 100000` 需要扫描前 10 万行），且分页期间数据变化会导致重复或遗漏。
- Cursor-based：适合数据量大、实时性强、无限滚动（移动端信息流）的场景。利用索引定位，性能始终高效，且分页期间数据变化不会导致重复或遗漏。缺点是无法跳页，无法计算总页数。

## 五、避坑指南

| 常见错误 | 现象 | 原因 | 解决方案 |
|---------|------|------|---------|
| `encodeURI` 编码 URL 参数值 | 参数值中的 `&`、`=` 未编码，服务器解析错误 | `encodeURI` 保留了 URL 结构字符，不会编码 `&`、`=` 等 | 参数值使用 `encodeURIComponent` 编码 |
| POST 请求手动设置 `Content-Type: multipart/form-data` | 文件上传失败或服务器无法解析 | 缺少 `boundary` 参数，浏览器需要自动生成 | 使用 `FormData` 时不要手动设置 `Content-Type` |
| 跨域请求忘记处理预检请求 | CORS 错误，请求被浏览器拦截 | 非简单请求（如 `Content-Type: application/json`）会触发 OPTIONS 预检 | 后端配置 `Access-Control-Allow-*` 头部，包括 OPTIONS 方法的处理 |
| 混合内容（HTTPS 页面加载 HTTP 资源） | 资源加载失败，浏览器控制台警告 | 浏览器安全策略禁止 HTTPS 页面加载 HTTP 资源 | 所有资源使用 HTTPS，或使用 `//` 协议相对 URL |
| `fetch` 不处理 HTTP 错误状态码 | 请求失败但代码进入成功分支 | `fetch` 只在网络错误时 reject，HTTP 4xx/5xx 不会 reject | 检查 `response.ok` 或 `response.status` |
| 不设置请求超时 | 请求一直挂起，页面无响应 | `fetch` 默认没有超时时间 | 使用 `AbortController` + `setTimeout` 实现超时控制 |
| 分页期间数据变化导致重复 | 使用 offset 分页时，列表出现重复数据 | 在分页期间新增了数据，导致后续页中包含了之前页的数据 | 改用 cursor-based 分页，或使用 snapshot 机制 |
| 强缓存导致用户看不到最新内容 | 发布了新版本，用户看到旧页面 | 静态资源设置了过长的 `max-age` | 文件名使用 hash（如 `app.abc123.js`），HTML 文件不缓存 |
| 大文件上传不显示进度 | 用户不知道上传进度，等待体验差 | `fetch` 不支持上传进度监听 | 使用 `XMLHttpRequest.upload.onprogress` 实现进度回调 |
| 忘记处理 `Retry-After` 头 | 触发限流后立即重试，导致被持续封禁 | 未按照服务器建议的等待时间重试 | 429 响应时读取 `Retry-After` 头，等待后再重试 |
