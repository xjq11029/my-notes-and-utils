## 一、核心概念

### 1.1 CSP 策略体系

CSP（Content Security Policy）是一种**声明式安全策略**，通过 HTTP 响应头或 `<meta>` 标签告诉浏览器哪些资源可以加载、哪些行为可以执行。把它想象成**大楼安保**：不同的指令控制不同"入口"的访问权限，未授权的行为一律拦截。

**核心指令分类**：

| 指令 | 控制范围 | 大楼安保类比 |
|---|---|---|
| `default-src` | 所有资源类型的默认策略 | 大楼所有入口的默认安保规则 |
| `script-src` | JavaScript 脚本来源 | 控制谁能进入机房（最危险的入口） |
| `style-src` | CSS 样式来源 | 控制谁能装修墙面 |
| `img-src` | 图片来源 | 控制谁能往墙上挂画 |
| `connect-src` | XHR / fetch / WebSocket 请求目标 | 控制谁能打电话出去 |
| `font-src` | 字体来源 | 控制谁能带字体文件进来 |
| `frame-src` / `frame-ancestors` | iframe 嵌套的来源/谁能嵌套当前页面 | 控制谁能在楼里搭临时棚屋 |
| `form-action` | 表单提交目标 | 控制表单数据能寄到哪里 |
| `object-src` | `<object>` / `<embed>` / `<applet>` 来源 | 控制谁能带插件设备进来 |
| `base-uri` | `<base>` 标签的 URL | 控制谁能改地址簿 |

```nginx
# Nginx 基础 CSP 配置
add_header Content-Security-Policy "
  default-src 'self';
  script-src 'self' 'nonce-random123' https://cdn.example.com;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  img-src 'self' data: https://images.example.com;
  connect-src 'self' https://api.example.com;
  font-src 'self' https://fonts.gstatic.com;
  frame-ancestors 'none';
  form-action 'self';
  base-uri 'self';
";
```

**CSP 中的特殊值**：

| 值 | 含义 | 风险 |
|---|---|---|
| `'self'` | 同源资源 | 低风险 |
| `'none'` | 禁止任何来源 | 最安全 |
| `'unsafe-inline'` | 允许内联脚本/样式 | 高风险，削弱 XSS 防护 |
| `'unsafe-eval'` | 允许 `eval()` 等动态代码执行 | 高风险 |
| `'nonce-xxx'` | 允许带有匹配 nonce 属性的脚本 | 中等风险（需服务端支持） |
| `'strict-dynamic'` | 允许已授权脚本动态加载的其他脚本 | 中等风险（需配合 nonce/hash） |
| `data:` | 允许 data: URI | 中等风险 |
| `https:` | 允许 HTTPS 来源 | 低风险 |

### 1.2 依赖安全扫描

现代前端项目依赖数百个第三方包，每个包都可能引入安全漏洞。依赖安全扫描通过自动化工具定期检查项目依赖中是否存在已知漏洞。

**三类主流工具**：

| 工具 | 类型 | 特点 | 适用场景 |

| Renovate / Dependabot | 自动更新 | 自动检测依赖更新并创建 PR，降低滞后风险 | 依赖维护自动化 |

### 1.3 安全头配置

除了 CSP，现代 Web 应用还需要配置多个 HTTP 安全头，每个头负责防御不同类别的攻击。

| 安全头 | 作用 | 典型配置 |
|---|---|---|
| `Strict-Transport-Security` (HSTS) | 强制浏览器使用 HTTPS 访问 | `max-age=31536000; includeSubDomains; preload` |
| `X-Content-Type-Options` | 禁止浏览器 MIME 嗅探 | `nosniff` |
| `X-Frame-Options` | 控制页面是否能被 iframe 嵌套 | `DENY` 或 `SAMEORIGIN` |
| `Referrer-Policy` | 控制 Referer 头的发送策略 | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | 控制浏览器功能 API 的使用权限 | `camera=(), microphone=(), geolocation=(self)` |
| `Cross-Origin-Opener-Policy` (COOP) | 控制跨域窗口的隔离 | `same-origin` |
| `Cross-Origin-Embedder-Policy` (COEP) | 控制跨域资源加载 | `require-corp` |
| `Cross-Origin-Resource-Policy` (CORP) | 控制资源是否可被跨域加载 | `same-origin` |

## 二、底层原理

### 2.1 CSP nonce 工作流程

CSP nonce（number used once）是一种**基于随机值的脚本授权机制**，服务端每次请求生成一个随机 nonce 值，同时注入到 HTML 脚本标签和 CSP 响应头中，浏览器验证两者匹配后才允许执行。

```
用户请求页面
    |
    v
服务端生成随机 nonce（如 "r4nd0m-n0nc3-v4lu3"）
    |
    ├──→ 注入到 HTML：<script nonce="r4nd0m-n0nc3-v4lu3">...</script>
    └──→ 注入到 CSP 头：script-src 'nonce-r4nd0m-n0nc3-v4lu3'
    |
    v
浏览器接收 HTML 和 CSP 头
    |
    v
执行脚本前：检查 script 标签的 nonce 属性是否匹配 CSP 头中的 nonce 值
    |
    ├── 匹配 → 允许执行
    └── 不匹配 → 拒绝执行（控制台报告 CSP 违规）
```

```typescript
// Next.js 中间件实现 CSP nonce
// middleware.ts
import { NextRequest, NextResponse } from 'next/server';
import crypto from 'crypto';

export function middleware(request: NextRequest) {
  // 生成随机 nonce
  const nonce = crypto.randomBytes(16).toString('base64');

  // 构建 CSP 策略
  const cspHeader = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic';
    style-src 'self' 'unsafe-inline';
    img-src 'self' data:;
    connect-src 'self' https://api.example.com;
    frame-ancestors 'none';
  `.replace(/\s{2,}/g, ' ').trim();

  const requestHeaders = new Headers(request.headers);
  // 将 nonce 传递给下游组件
  requestHeaders.set('x-nonce', nonce);

  const response = NextResponse.next({
    request: { headers: requestHeaders },
  });

  // 设置 CSP 响应头
  response.headers.set('Content-Security-Policy', cspHeader);

  return response;
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
};
```

```typescript
// app/layout.tsx —— 使用 nonce 渲染脚本
import { headers } from 'next/headers';
import Script from 'next/script';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  const nonce = headers().get('x-nonce') ?? '';

  return (
    <html lang="zh-CN">
      <body>
        {children}
        {/* 内联脚本使用 nonce */}
        <Script id="inline-config" nonce={nonce}>
          {`window.__CONFIG__ = ${JSON.stringify({ env: 'production' })}`}
        </Script>
      </body>
    </html>
  );
}
```

### 2.2 Trusted Types

Trusted Types 是浏览器级别的安全机制，**强制开发者使用安全的 DOM API**，从根本上防止 DOM XSS 攻击。它要求所有可能执行脚本的 DOM API（如 `innerHTML`、`document.write`）只能接受 TrustedHTML 类型的对象，而不能接受普通字符串。

```typescript
// 启用 Trusted Types（CSP 头）
// Content-Security-Policy: require-trusted-types-for 'script'; trusted-types default

// 创建 Trusted Types 策略
// trusted-types-policy.ts
if (typeof window !== 'undefined' && window.trustedTypes) {
  // 创建默认策略
  window.trustedTypes.createPolicy('default', {
    // 创建 TrustedHTML：只允许已知安全的 HTML
    createHTML: (input: string) => {
      // 这里可以实现 HTML 清洗逻辑
      const sanitized = input.replace(/<script\b[^<]*(?:(?!<\/script>)<[^<]*)*<\/script>/gi, '');
      return sanitized;
    },
    // 创建 TrustedScriptURL：只允许白名单域名
    createScriptURL: (input: string) => {
      const url = new URL(input);
      const allowedHosts = ['cdn.example.com', 'cdnjs.cloudflare.com'];
      if (!allowedHosts.includes(url.hostname)) {
        throw new Error(`不允许的脚本来源: ${url.hostname}`);
      }
      return input;
    },
  });
}

// 使用 Trusted Types
function safeSetInnerHTML(element: HTMLElement, html: string) {
  if (window.trustedTypes?.defaultPolicy) {
    // 通过 Trusted Types 策略创建安全的 HTML
    element.innerHTML = window.trustedTypes.defaultPolicy.createHTML(html) as unknown as string;
  } else {
    // 降级处理：使用 DOMPurify 等第三方库清洗
    element.innerHTML = html;
  }
}
```

```typescript
// DOMPurify 集成 Trusted Types
import DOMPurify from 'dompurify';

// 配置 DOMPurify 返回 TrustedHTML
const sanitizedHTML = DOMPurify.sanitize(userInput, {
  RETURN_TRUSTED_TYPE: true, // 返回 TrustedHTML 对象
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'br'],
  ALLOWED_ATTR: ['href', 'title', 'target'],
});

// 直接赋值给 innerHTML，符合 Trusted Types 要求
document.getElementById('content')!.innerHTML = sanitizedHTML as unknown as string;
```

### 2.3 Subresource Integrity（SRI）

SRI 通过**对资源内容计算哈希值**，确保从 CDN 加载的脚本或样式没有被篡改。浏览器下载资源后计算哈希值，与 `integrity` 属性中声明的哈希值对比，不匹配则拒绝加载。

```html
<!-- SRI 使用示例 -->
<!-- 在 script 标签上添加 integrity 属性 -->
<script
  src="https://cdn.example.com/library@3.0.0/dist/bundle.js"
  integrity="sha384-abc123def456ghi789jkl012mno345pqr678stu901vwx234yz"
  crossorigin="anonymous"
></script>

<!-- 在 link 标签上添加 integrity 属性 -->
<link
  rel="stylesheet"
  href="https://cdn.example.com/library@3.0.0/dist/styles.css"
  integrity="sha384-xyz789abc012def345ghi678jkl901mno234pqr567stu890vwx"
  crossorigin="anonymous"
/>
```

```bash
# 生成 SRI 哈希值的命令行工具
# 使用 openssl 计算 SHA-384
cat bundle.js | openssl dgst -sha384 -binary | openssl base64 -A

# 或使用 Node.js 脚本
node -e "
const crypto = require('crypto');
const fs = require('fs');
const content = fs.readFileSync('bundle.js');
const hash = crypto.createHash('sha384').update(content).digest('base64');
console.log('sha384-' + hash);
"
```

```typescript
// Webpack 插件自动生成 SRI
// webpack.config.ts
import type { Configuration } from 'webpack';
import SriPlugin from 'webpack-subresource-integrity';

const config: Configuration = {
  output: {
    crossOriginLoading: 'anonymous',
  },
  plugins: [
    new SriPlugin({
      hashFuncNames: ['sha384', 'sha512'],
      enabled: true,
    }),
  ],
};

export default config;
```

### 2.4 依赖检测原理

`npm audit` / `pnpm audit` 的核心工作流程：读取 lock 文件（package-lock.json / pnpm-lock.yaml）中记录的每个依赖的精确版本号，与 GitHub Advisory Database 等漏洞数据库进行匹配。

```
开发者执行 pnpm audit
    |
    v
读取 package-lock.json / pnpm-lock.yaml
    |
    v
提取所有依赖的 name@version 列表
    |
    v
向漏洞数据库（GitHub Advisory Database）查询每个依赖
    |
    ├── 匹配到漏洞 → 返回漏洞详情（CVE 编号、严重程度、修复版本、攻击向量）
    └── 未匹配 → 安全
    |
    v
汇总结果：按严重程度排序（Critical > High > Moderate > Low）
    |
    v
输出报告：列出漏洞路径（依赖链）、建议修复方案
```

### 3.1 CSP 策略从零到一

实施 CSP 的推荐路径：**Report-Only 模式 → 收集违规报告 → 逐步收紧策略 → 强制执行**。

```nginx
# Nginx 完整 CSP 配置（渐进式实施）
server {
    listen 443 ssl;
    server_name example.com;

    # ============ 第一阶段：Report-Only 模式 ============
    # 暂时不拦截，只收集违规报告
    # add_header Content-Security-Policy-Report-Only "
    #   default-src 'self';
    #   script-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.example.com;
    #   style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
    #   img-src 'self' data: https:;
    #   connect-src 'self' https://api.example.com https://*.example.com;
    #   font-src 'self' https://fonts.gstatic.com;
    #   frame-ancestors 'self';
    #   report-uri /csp-report-endpoint;
    # ";

    # ============ 第二阶段：收紧策略 ============
    # 根据收集的违规报告，逐步收紧
    add_header Content-Security-Policy "
        default-src 'self';
        script-src 'self' 'nonce-$csp_nonce' 'strict-dynamic' https:;
        style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
        img-src 'self' data: https:;
        connect-src 'self' https://api.example.com;
        font-src 'self' https://fonts.gstatic.com;
        frame-ancestors 'self';
        form-action 'self';
        base-uri 'self';
        object-src 'none';
        report-uri /csp-report-endpoint;
    ";

    # ============ 其他安全头 ============
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=(self), payment=()" always;
}
```

```typescript
// CSP 违规报告收集端点
// app/api/csp-report/route.ts
import { NextRequest } from 'next/server';

export async function POST(request: NextRequest) {
  const report = await request.json();

  // 提取关键信息
  const {
    'blocked-uri': blockedUri,
    'violated-directive': violatedDirective,
    'document-uri': documentUri,
    'script-sample': scriptSample,
  } = report['csp-report'] ?? {};

  // 记录到监控系统
  console.warn('[CSP Violation]', {
    blockedUri,
    violatedDirective,
    documentUri,
    scriptSample,
    timestamp: new Date().toISOString(),
  });

  // 也可以发送到 Sentry、Grafana 等监控平台
  // sentry.captureMessage('CSP Violation', { extra: report });

  return new Response(null, { status: 204 });
}
```

### 3.2 依赖安全扫描实战

将 `pnpm audit` 集成到 CI 流水线中，阻断高危漏洞进入生产环境。

```yaml
# .github/workflows/security-audit.yml
name: Security Audit

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    # 每天凌晨 2 点自动运行
    - cron: '0 2 * * *'

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Run security audit
        # 当存在 high 或 critical 级别漏洞时失败
        run: pnpm audit --audit-level high
        continue-on-error: false

      - name: Run Snyk security scan
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: --severity-threshold=high

      - name: Check for outdated dependencies
        run: pnpm outdated --format json > outdated.json
        continue-on-error: true

      - name: Upload audit results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: security-audit-results
          path: outdated.json
```

```nginx
# Nginx 完整安全头配置
# /etc/nginx/conf.d/security-headers.conf

# 1. HSTS：强制 HTTPS（仅生产环境启用）
```

## 四、常见面试题

**Q1：请解释 CSP 的工作原理，以及 nonce 和 hash 两种授权方式的区别。**

**答案要点**：
- CSP 通过 HTTP 响应头或 `<meta>` 标签声明资源加载白名单，浏览器拦截违规的资源加载和执行
- nonce（number used once）：服务端每次请求生成随机值，同时注入 HTML 属性（`<script nonce="xxx">`）和 CSP 头（`script-src 'nonce-xxx'`），浏览器验证两者匹配
- hash：对脚本内容计算 SHA-256/384/512 哈希值，在 CSP 头中声明 `script-src 'sha256-xxx'`，浏览器验证脚本内容哈希匹配
- nonce 适合动态内容，hash 适合静态内联脚本；`'strict-dynamic'` 允许已授权脚本动态加载其他脚本

**Q2：Trusted Types 解决什么问题？它是如何工作的？**

**答案要点**：
- 解决 DOM XSS 问题：强制所有可能执行脚本的 DOM API（如 `innerHTML`、`document.write`）只能接受 TrustedHTML 对象
- 通过 CSP 头启用：`require-trusted-types-for 'script'`
- 开发者注册 Trusted Types 策略（createPolicy），在策略中实现清洗逻辑
- 普通字符串赋值给 `innerHTML` 会抛出 TypeError，必须通过策略创建 TrustedHTML
- 配合 DOMPurify 等库可以实现自动清洗并返回 TrustedHTML

**Q3：什么是 Subresource Integrity（SRI）？如何生成和使用？**

**答案要点**：
- SRI 通过 `integrity` 属性验证 CDN 资源未被篡改
- 浏览器下载资源后计算哈希值，与 `integrity` 属性中的哈希值对比
- 生成方式：`openssl dgst -sha384 -binary | openssl base64 -A`
- 使用方式：`<script src="..." integrity="sha384-xxx" crossorigin="anonymous"></script>`
- 需要配合 `crossorigin="anonymous"` 属性（CORS 请求）
- Webpack 可用 `webpack-subresource-integrity` 插件自动生成

**Q4：pnpm audit 的工作机制是什么？如何与 CI 集成？**

**答案要点**：
- 读取 `pnpm-lock.yaml` 中的依赖版本，与 GitHub Advisory Database 匹配
- 返回漏洞详情（CVE 编号、严重程度、修复版本、依赖路径）
- CI 集成：`pnpm audit --audit-level high` 在有高危漏洞时返回非零退出码
- 配合 GitHub Actions 的 schedule 定时执行，确保持续监控
- 结合 Renovate/Dependabot 自动创建修复 PR

**Q5：防御供应链攻击有哪些关键措施？**

**答案要点**：
- 锁定依赖版本：使用精确版本号（不使用 ^ 或 ~）+ lockfile
- 定期审计：`pnpm audit` + Snyk 等商业工具
- 自动更新：Renovate/Dependabot 自动创建安全更新 PR
- CI 验证：`pnpm install --frozen-lockfile` 确保依赖一致性
- Lockfile 审查：在 PR 中审查 `pnpm-lock.yaml` 变更
- 最小权限原则：减少依赖数量，优先选择社区活跃的包

## 五、避坑指南

| 坑点 | 现象 | 原因 | 解决方案 |
|---|---|---|---|
| CSP 配置 `script-src 'unsafe-inline'` 导致 XSS 防护失效 | 攻击者仍可通过注入内联脚本执行恶意代码 | `'unsafe-inline'` 允许所有内联脚本，完全绕过了 CSP 的脚本控制 | 使用 nonce 或 hash 替代 `'unsafe-inline'`；配合 `'strict-dynamic'` 允许已授权脚本动态加载 |
| CSP Report-Only 模式长期不切换为强制执行 | 收集了大量违规报告但从未实际拦截，安全防护形同虚设 | 团队担心 CSP 拦截导致功能异常，迟迟不敢切换 | 分阶段收紧：先分析 Report-Only 报告修复违规点 → 按页面/路径逐步启用强制执行 → 保留 report-uri 端点持续监控 |
| `pnpm audit` 忽略后未修复漏洞 | 依赖漏洞持续存在，可能被攻击者利用 | `pnpm audit` 的修复建议可能涉及 breaking change 或依赖版本冲突 | 建立漏洞修复 SLA（Critical 24h / High 7d）；使用 Renovate 自动创建更新 PR；对无法修复的漏洞做风险评估 |
