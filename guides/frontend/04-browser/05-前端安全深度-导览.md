# 05-前端安全深度 - 导览

## 1.1 CSP 策略体系（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | CSP（Content Security Policy）是一种声明式安全策略，通过 HTTP 响应头或 `<meta>` 标签告诉浏览器哪些资源可以加载、哪些行为可以执行。用大楼安保类比：不同指令控制不同"入口"（default-src 控制默认规则，script-src 控制脚本入口，style-src 控制样式入口，img-src 控制图片入口，connect-src 控制网络请求入口，frame-ancestors 控制嵌套入口） |
| 能做什么 | 防御 XSS 攻击（限制脚本来源）、防止数据注入、控制资源加载来源、报告违规行为 |
| 怎么用 | Nginx 配置 `add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'nonce-xxx'; ...";`；或通过 `<meta http-equiv="Content-Security-Policy" content="...">` 设置 |
| 原理和工作流程 | 浏览器解析 CSP 策略 → 加载资源时检查是否匹配策略 → 匹配则允许加载 → 不匹配则拦截并报告（如果配置了 report-uri） |
| 缺点 | 配置复杂，容易遗漏；过于严格的策略可能导致正常功能异常；`'unsafe-inline'` 会削弱 XSS 防护；legacy 浏览器不支持 |

## 1.2 依赖安全扫描（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 三类工具：`pnpm audit`（内置 CLI，免费）、Snyk（商业 SaaS，更全面）、Renovate/Dependabot（自动更新），通过检查 `pnpm-lock.yaml` 与漏洞数据库匹配识别已知漏洞 |
| 能做什么 | 识别项目依赖中的已知安全漏洞（CVE）、输出修复建议和依赖路径、自动化修复和更新 |
| 怎么用 | `pnpm audit` 检查漏洞；`pnpm audit --audit-level high` 仅关注高危漏洞；Snyk 通过 `snyk/actions/node@master` GitHub Action 集成；Dependabot 通过 `.github/dependabot.yml` 配置 |
| 原理和工作流程 | 读取 lockfile 中所有依赖的精确版本 → 向 GitHub Advisory Database 查询 → 匹配到漏洞则返回详情（CVE 编号、严重程度、修复版本、依赖路径）→ 按严重程度排序输出 |
| 缺点 | `pnpm audit` 漏洞数据库不如 Snyk 全面；自动修复可能引入 breaking change；误报和漏报需要人工甄别 |

## 1.3 安全头配置（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 除 CSP 外的多个 HTTP 安全头，各自防御不同类别攻击：HSTS（强制 HTTPS）、X-Content-Type-Options（禁止 MIME 嗅探）、X-Frame-Options（控制 iframe 嵌套）、Referrer-Policy（控制 Referer 发送）、Permissions-Policy（控制浏览器 API 权限） |
| 能做什么 | 构建纵深防御体系，每个安全头覆盖一个攻击面，组合使用提供全面防护 |
| 怎么用 | Nginx 中通过 `add_header` 指令逐个配置，`always` 参数确保在所有响应中生效 |
| 原理和工作流程 | HSTS：浏览器首次访问后记录 HTTPS 强制要求，后续自动升级 HTTP 为 HTTPS；X-Content-Type-Options：阻止浏览器根据内容猜测 MIME 类型；X-Frame-Options：阻止页面被其他网站 iframe 嵌套；Referrer-Policy：控制跨域请求中 Referer 头的发送级别 |
| 缺点 | HSTS 首次访问前仍可能被中间人攻击（需 HSTS Preload）；X-Frame-Options 已被 CSP frame-ancestors 取代；Permissions-Policy 配置复杂且浏览器支持不一致 |

## 2.1 CSP nonce 工作流程（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | CSP nonce（number used once）是一种基于随机值的脚本授权机制，服务端每次请求生成随机 nonce，同时注入到 HTML 脚本标签（`<script nonce="xxx">`）和 CSP 响应头（`script-src 'nonce-xxx'`），浏览器验证匹配后允许执行 |
| 能做什么 | 安全地允许内联脚本执行，替代 `'unsafe-inline'`，即使用户输入注入 `<script>` 标签也无法执行（因为没有匹配的 nonce） |
| 怎么用 | 服务端生成 `crypto.randomBytes(16).toString('base64')` → 注入到 CSP 头 `script-src 'nonce-xxx'` → 注入到 HTML 标签 `nonce="xxx"` → 浏览器自动验证 |
| 原理和工作流程 | 用户请求 → 服务端生成随机 nonce → 同时注入 CSP 头和 HTML 属性 → 浏览器解析时提取 CSP 策略中的 nonce 白名单 → 对比脚本标签的 nonce 属性 → 匹配则执行，不匹配则拦截 |
| 缺点 | 需要服务端动态生成，不能用于纯静态页面；nonce 需要每次请求都不同，缓存策略需调整；配合 `'strict-dynamic'` 才能让已授权脚本动态加载其他脚本 |

## 2.2 Trusted Types（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Trusted Types 是浏览器级别的安全机制，强制所有可能执行脚本的 DOM API（`innerHTML`、`document.write`、`eval`）只能接受 TrustedHTML 对象，从根源上防止 DOM XSS |
| 能做什么 | 从根本上消除 DOM XSS 攻击面，即使攻击者能控制 DOM 操作的内容，也无法直接将恶意字符串写入 `innerHTML` |
| 怎么用 | 通过 CSP 头启用：`require-trusted-types-for 'script'`；注册策略：`window.trustedTypes.createPolicy('default', { createHTML: sanitizeFn })`；配合 DOMPurify 的 `RETURN_TRUSTED_TYPE: true` 选项 |
| 原理和工作流程 | 浏览器拦截所有向危险 DOM API 传入字符串的操作 → 检查是否通过 Trusted Types 策略创建 → 策略中执行清洗逻辑 → 返回 TrustedHTML 对象 → 浏览器允许赋值 |
| 缺点 | 浏览器兼容性有限（Chrome/Edge 支持，Firefox/Safari 不支持）；需要改造所有 `innerHTML` 调用点；第三方库可能不兼容 |

## 2.3 Subresource Integrity SRI（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | SRI 通过对资源内容计算哈希值（SHA-256/384/512），在 `integrity` 属性中声明，浏览器下载资源后计算哈希值对比，不匹配则拒绝加载，确保 CDN 资源未被篡改 |
| 能做什么 | 防止 CDN 被劫持后注入恶意代码、确保第三方资源完整性、提供资源加载的安全保障 |
| 怎么用 | 生成哈希：`openssl dgst -sha384 -binary | openssl base64 -A`；使用：`<script src="..." integrity="sha384-xxx" crossorigin="anonymous"></script>`；Webpack 插件 `webpack-subresource-integrity` 自动生成 |
| 原理和工作流程 | 构建时计算资源哈希 → 写入 HTML 的 integrity 属性 → 浏览器下载资源 → 重新计算哈希 → 对比两者 → 匹配则执行，不匹配则拒绝并报错 |
| 缺点 | 资源更新后需重新生成哈希；资源内容即使微小的变化也会导致哈希不匹配；需要 `crossorigin="anonymous"` 属性配合 |

## 2.4 依赖检测原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | `pnpm audit` 读取 `pnpm-lock.yaml` 中记录的精确版本号，与 GitHub Advisory Database 等漏洞数据库进行匹配，输出漏洞详情（CVE 编号、严重程度、修复版本、依赖路径） |
| 能做什么 | 自动识别项目依赖中是否存在已知安全漏洞，提供修复建议和依赖路径追踪 |
| 怎么用 | 命令行：`pnpm audit`；CI 集成：`pnpm audit --audit-level high`（高危漏洞时返回非零退出码）；查看详情：`pnpm audit --json` |
| 原理和工作流程 | 读取 lockfile → 提取所有依赖 name@version → 向漏洞数据库查询 → 匹配到漏洞 → 返回漏洞详情（CVE 编号、严重程度、修复版本、攻击向量、依赖路径）→ 按严重程度排序 → 输出报告 |
| 缺点 | 只检查已知漏洞，零日漏洞无法检测；漏洞数据库可能存在延迟；修复建议可能涉及 breaking change |

## 3.1 CSP 策略从零到一（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的分阶段 CSP 实施流程：第一阶段 Report-Only 模式收集违规报告 → 第二阶段分析报告逐步收紧策略 → 第三阶段强制执行，配合 Nginx 完整配置 |
| 能做什么 | 安全的 CSP 实施路径，避免"一刀切"导致功能异常，通过渐进式收紧确保平滑过渡 |
| 怎么用 | 第一阶段：`Content-Security-Policy-Report-Only` + `report-uri` 端点；第二阶段：根据报告移除 `'unsafe-inline'`/`'unsafe-eval'`；第三阶段：切换为 `Content-Security-Policy` 强制执行 |
| 原理和工作流程 | Report-Only 模式下浏览器只报告不拦截 → 收集违规报告到后端端点 → 分析哪些页面/功能触发了违规 → 修复违规点（用 nonce 替代 inline、用 Trusted Types 替代 eval）→ 确认无违规后切换为强制执行 |
| 缺点 | Report-Only 阶段需要收集充足数据，周期较长；违规报告端点本身需要安全防护；复杂应用中完全消除 inline 脚本可能困难 |

## 3.2 依赖安全扫描实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 将 `pnpm audit` 和 Snyk 集成到 GitHub Actions 中，实现每次 PR 和定时任务自动检查依赖漏洞，高危漏洞阻断合并 |
| 能做什么 | 自动化依赖安全检查，防止高危漏洞进入生产环境，定时任务确保持续监控 |
| 怎么用 | GitHub Actions workflow：`pnpm audit --audit-level high` + `snyk/actions/node@master`；schedule cron 定时执行；artifact 上传审计结果 |
| 原理和工作流程 | PR 触发 workflow → `pnpm install --frozen-lockfile` → `pnpm audit` 检查 → 高危漏洞返回非零退出码 → workflow 失败阻断合并；schedule 定时执行确保持续监控 |
| 缺点 | `pnpm audit` 可能误报；Snyk 需要 token 配置；CI 运行时间增加 |

## 3.3 安全头完整配置（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 Nginx 安全头配置，包括 HSTS（强制 HTTPS）、X-Content-Type-Options（禁止 MIME 嗅探）、X-Frame-Options（控制 iframe 嵌套）、Referrer-Policy（控制 Referer）、Permissions-Policy（控制浏览器 API）、CSP |
| 能做什么 | 构建纵深防御体系，每个安全头覆盖一个攻击面，组合使用提供全面防护 |
| 怎么用 | 在 Nginx server 块中通过 `add_header` 指令配置，使用 `always` 参数确保所有响应（包括错误响应）都包含安全头 |
| 原理和工作流程 | HSTS 通过 `Strict-Transport-Security` 头告知浏览器只能通过 HTTPS 访问；X-Content-Type-Options 阻止浏览器根据内容猜测 MIME 类型；X-Frame-Options 阻止页面被 iframe 嵌套；Permissions-Policy 默认关闭所有敏感 API |
| 缺点 | 配置项多容易遗漏；Permissions-Policy 各浏览器支持不一致；HSTS 首次访问前仍可能被中间人攻击 |

## 3.4 供应链攻击防御（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 多层次供应链攻击防御策略：锁定依赖版本（精确版本号 + lockfile）、定期审计（pnpm audit + Snyk）、自动更新（Renovate/Dependabot）、CI 验证（frozen-lockfile）、lockfile 审查 |
| 能做什么 | 防止恶意依赖混入项目、及时发现和修复已知漏洞、自动化依赖更新减轻维护负担 |
| 怎么用 | 使用精确版本号锁定依赖；`pnpm audit` 定期检查；Renovate 配置自动创建更新 PR；CI 中 `pnpm install --frozen-lockfile` 确保一致性；PR 审查中检查 lockfile 变更 |
| 原理和工作流程 | 精确版本号 + lockfile 确保依赖版本一致 → `pnpm audit` 检查已知漏洞 → Renovate 自动检测更新并创建 PR → CI 验证 lockfile 未被篡改 → 人工审查 lockfile 变更确认无恶意依赖 |
| 缺点 | 精确版本号锁定可能导致错过安全补丁；Renovate PR 频繁需要人工审查成本；完全杜绝供应链攻击不现实，只能降低风险 |
