# 06-国际化与多端同构

## 一、核心概念

### 1.1 国际化、本地化与全球化

| 缩写 | 全称 | 中文 | 关注点 | 谁负责 |
|---|---|---|---|---|
| **i18n** | internationalization | 国际化 | 让产品**具备**适配多种语言与地区的能力（架构与工程） | 研发 |
| **l10n** | localization | 本地化 | 把产品**实际适配**到某个具体地区（内容与体验） | 本地化 / 运营 |
| **g11n** | globalization | 全球化 | 包含 i18n + l10n + 商业与合规的整体战略 | 业务 |

**i18n 是架构能力，l10n 是内容交付**。架构师要保证的是：**新增一种语言时不需要改代码**，只需新增一份语言包与配置。这是判断 i18n 架构是否合格的核心标准。

**国际化必须覆盖的七个维度**（只做文案翻译是最常见的认知缺口）：

| 维度 | 示例 | 常见错误 |
|---|---|---|
| 文案 | 按钮、提示、错误信息 | 把文案硬编码在组件里 |
| 日期时间 | `2026/09/17` vs `09/17/2026` | 用 `YYYY-MM-DD` 字符串硬格式化 |
| 时区 | 用户看到自己的当地时间 | 后端返回无时区信息的本地时间 |
| 数字 | `1,234.56` vs `1.234,56` | 手写千分位正则 |
| 货币 | `¥1,234` vs `€1.234` | 手写 `'¥' + price` |
| 复数与性别 | 俄语 4 种复数形式；阿拉伯语 6 种 | 只写 `one` / `other` 两种 |
| 书写方向 | 阿拉伯语、希伯来语从右到左 | 用 `margin-left` 硬编码 |

### 1.2 文案管理方案

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **JSON 文件** | 语言包以 JSON 存放在仓库，随代码发布 | 零外部依赖，与代码同版本，回滚简单 | 文案改动要发版；翻译人员需接触代码仓库 | 单语言团队、文案变更低频 |
| **平台化（自建后台）** | 自建文案管理后台 + 数据库 + 发布接口 | 运营可自助改文案，支持灰度与回滚 | 建设与维护成本高，需多语言数据模型 | 文案变更频繁、有独立运营团队 |
| **TMS 翻译平台** | 接入 Crowdin / Lokalise / Phrase / Transifex，CI 拉取产物 | 专业翻译工作流、翻译记忆库、术语库、质量校验 | 按量付费，与 CI 集成需额外工程 | 多语言、多市场、需专业翻译 |

**推荐演进路径**：JSON 文件起步 → 语言数超过 3 种或翻译团队介入后接入 TMS → 运营需要自助改文案时再考虑自建平台。

**TMS 与 CI 的集成**：

```
源码语言包（zh-CN.json）──push──▶ TMS 平台 ──翻译──▶ 各语言产物
                                     │
CI 构建时 ◀────────── pull ──────────┘
   │
   └─▶ 校验（key 一致性 / 占位符一致性 / 空值检测）→ 构建产物
```

**必须在 CI 中做的三项校验**：
1. **key 一致性**：所有语言的 key 集合必须相同，缺失 key 会导致运行期回退到 fallback 语言（用户看到中英混杂）
2. **占位符一致性**：`{count}` 翻译后不能变成 `{Count}` 或丢失，否则运行期抛错或显示原始占位符
3. **空值检测**：空字符串会静默覆盖 fallback，比缺失 key 更隐蔽

### 1.3 key 命名规范与分层

**核心原则：key 描述语义，不描述位置或文案本身。**

```json
// ❌ 反例一：用文案本身当 key —— 改一次文案，全项目 key 失效
{ "提交订单": "Submit Order" }

// ❌ 反例二：用 UI 位置当 key —— 位置调整后 key 全部失去意义
{ "header": { "leftTopButton": "Submit" } }

// ✅ 正例：语义化 + 分层 + 命名空间
{
  "common": { "confirm": "确定", "cancel": "取消", "loading": "加载中…" },
  "order": {
    "list": { "title": "订单列表", "empty": "暂无订单" },
    "detail": { "status": { "pending": "待付款", "paid": "已付款" } },
    "action": { "submit": "提交订单" }
  },
  "validation": {
    "required": "{field} 不能为空",
    "maxLength": "{field} 长度不能超过 {max} 个字符"
  }
}
```

| 层级 | 示例 | 说明 |
|---|---|---|
| 命名空间（namespace） | `common` / `order` / `user` | 与业务模块对齐，也是按需加载的分包单位 |
| 页面 / 场景 | `order.list` | 二级定位 |
| 语义 | `title` / `empty` / `status.pending` | 描述含义，而非"第几个按钮" |
| 变体（可选） | `action.submit.short` | 文案过长时的短版本，用于小屏 |

**key 设计的五条约定**：
1. **全部小写 + 点分层**，层级控制在 3-4 层，过深会让 JSON 解析与 IDE 提示变慢
2. **动词用统一词表**：`submit` / `cancel` / `delete` / `create` / `edit` / `export`，避免 `add` / `create` / `new` 混用
3. **同一语义只保留一个 key**。同时存在 `order.submit` 与 `order.action.submitOrder` 时立即合并 —— 重复 key 是翻译成本失控的主因
4. **不要把业务数据当文案**。订单状态来自后端枚举时，key 约定为 `order.status.${status}`，由后端返回枚举值、前端拼 key 查文案
5. **key 一旦发布就不要改名**。改名等同于删除 + 新增，会让已有翻译全部丢失；如需重构，保留旧 key 作为别名至少一个版本

### 1.4 多端同构的定义与价值

**同构（Isomorphic / Universal）**：同一套代码能够在**不同的运行环境**（服务端 / 浏览器 / 小程序 / App / 桌面端）中运行并产出结果。

```
                    ┌──────────────────┐
                    │   共享业务代码    │
                    │  领域模型 / 校验   │
                    │  状态管理 / 请求   │
                    └────────┬─────────┘
        ┌──────────┬─────────┼─────────┬──────────┐
        ▼          ▼         ▼         ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │  浏览器 │ │ 服务端  │ │ 小程序  │ │  App   │ │ 桌面端  │
   └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
```

**"同构"有两层常见语境**，学习时必须区分：

| 语境 | 含义 | 典型技术 |
|---|---|---|
| **SSR 同构** | 同一套组件代码在服务端和浏览器都能执行（服务端产出 HTML，浏览器注水接管） | Next.js / Nuxt / Vue SSR / React SSR |
| **多端同构** | 同一套代码编译或运行到多个客户端平台 | Taro / uni-app / React Native / Flutter |

**核心价值**：

| 价值 | 说明 | 量化参考 |
|---|---|---|
| 开发成本 | 一套代码覆盖 N 端，避免 N 倍重复开发 | 端数量 ≥ 3 时收益明显 |
| 一致性 | 业务规则、校验逻辑、交互流程天然一致 | 消除"Web 修了小程序没修"的 bug |
| 团队效率 | 团队技能栈统一，人力可灵活调度 | 无需为每端配专职人员 |
| 迭代速度 | 需求一次实现、一次评审、一次测试 | 减少 N-1 次沟通成本 |

### 1.5 同构的三个层次

同构不是"要么全同构、要么全不同构"的二元选择，而是三个可独立选择的层次：

| 层次 | 复用内容 | 复用方式 | 跨端可行性 | 示例 |
|---|---|---|---|---|
| **代码复用** | 工具函数、常量、类型定义、正则 | 抽成独立 npm 包 | 极高（几乎无差异） | `isValidPhone()`、`OrderStatus` 枚举、TS 类型 |
| **逻辑同构** | 业务规则、数据转换、状态管理、请求封装 | 抽成与框架无关的纯函数 / 类 | 高（需抹平平台 API） | 订单金额计算、购物车状态机、API 客户端 |
| **渲染同构** | UI 组件、布局、交互 | 依赖跨端框架或条件编译 | 中（平台差异最大） | 商品卡片组件、表单、弹窗 |

**架构建议**：**自下而上逐层同构** —— 先做代码复用（零风险、收益立竿见影），再做逻辑同构（需要设计适配层），最后才考虑渲染同构（成本最高、平台差异最大）。

```
┌─────────────────────────────────────┐
│  渲染同构（成本最高，收益不确定）      │  ← 最后做
├─────────────────────────────────────┤
│  逻辑同构（需要适配层设计）           │  ← 重点投入
├─────────────────────────────────────┤
│  代码复用（零风险，立刻做）           │  ← 优先做
└─────────────────────────────────────┘
```

> **与 03 模块的呼应**：03-前端分层架构中"业务逻辑层不依赖 UI 框架"正是逻辑同构的前提。若业务逻辑写在组件里，就永远无法跨端复用。

## 二、底层原理

### 2.1 ICU MessageFormat

**ICU MessageFormat** 是 Unicode 联盟定义的国际化消息格式规范，也是现代 i18n 库的通用语法基础（`intl-messageformat`、vue-i18n 消息编译器、`i18next-icu` 均实现该规范）。

**四种语法能力**：

```
① 简单插值
{name} 邀请你加入 {team}

② 复数（plural）—— 按 CLDR 复数规则选择分支
{count, plural,
  =0 {暂无消息}
  one {# 条新消息}
  other {# 条新消息}
}

③ 性别 / 分类选择（select）
{gender, select,
  male {他邀请了你}
  female {她邀请了你}
  other {TA 邀请了你}
}

④ 序数（selectordinal）
{position, selectordinal, one {第 # 名} other {第 # 名}}
```

| 语法元素 | 含义 |
|---|---|
| `=0` | **精确匹配**，优先级最高，任何语言下都命中 |
| `one` / `other` | **复数类别（plural category）**，由 CLDR 按语言定义 |
| `#` | 占位符，自动替换为 `count` 的**本地化格式**数字（含千分位） |

**关键认知：不同语言的复数类别数量差异极大**，只写 `one` / `other` 是错误的：

| 语言 | 复数类别 | 说明 |
|---|---|---|
| 中文 / 日语 / 韩语 | `other` | 只有一种形式，`one` 分支不会命中 |
| 英语 / 德语 / 西班牙语 | `one`, `other` | 两种 |
| 法语 | `one`, `many`, `other` | 三种 |
| 俄语 / 乌克兰语 | `one`, `few`, `many`, `other` | 四种 |
| 阿拉伯语 | `zero`, `one`, `two`, `few`, `many`, `other` | 六种 |

因此**复数分支必须由翻译人员或平台按目标语言补全**，前端不能假设只有 `one` / `other`。

**嵌套**（`plural` 与 `select` 可嵌套，实现"数量 + 性别"的组合）：

```
{count, plural,
  =0 {没有{gender, select, male {他} female {她} other {TA}}}人报名}
  other {# 人报名，其中{gender, select, male {他} female {她} other {TA}}是发起人}
}
```

**类型化格式（skeleton）**：`{price, number, ::currency/CNY}` → `¥1,234.56`；`{ts, date, ::yyyyMMdd}` → `20260917`。

```javascript
// 以 @formatjs/intl-messageformat 为例（规范的标准实现之一）
import { IntlMessageFormat } from 'intl-messageformat';

const msg = new IntlMessageFormat('{count, plural, =0 {暂无消息} other {# 条新消息}}', 'zh-CN');
msg.format({ count: 0 });  // "暂无消息"
msg.format({ count: 5 });  // "5 条新消息"

// 按目标语言自动选择正确的复数类别
const enMsg = new IntlMessageFormat('{count, plural, one {# item} other {# items}}', 'en-US');
enMsg.format({ count: 1 });  // "1 item"
enMsg.format({ count: 2 });  // "2 items"

// 直接查询某语言的复数类别
new Intl.PluralRules('en-US').select(1);   // 'one'
new Intl.PluralRules('en-US').select(2);   // 'other'
new Intl.PluralRules('ar-EG').select(3);   // 'few'（阿拉伯语有 6 个类别）
new Intl.PluralRules('zh-CN').select(1);   // 'other'（中文只有 other）
```

> **`Intl.MessageFormat` 目前还不是浏览器原生 API**，需要由库提供实现。选择库时务必确认其符合 ICU MessageFormat 规范，否则复数与嵌套语法行为会不一致。

**易错点**：**不要把可变的句子片段拼接起来**。

```javascript
// ❌ 拼接会导致其他语言语序错乱（"你有 3 条消息"在日语/德语中语序不同）
const text = '你有 ' + count + ' 条消息';

// ✅ 整句作为消息模板，把变量交给 MessageFormat 处理
t('message.count', { count });
```

### 2.2 日期时间与时区处理

**时区问题的根源**：`Date` 对象内部是 UTC 时间戳，但大量 API（`getFullYear`、`getHours`、`toLocaleDateString`）默认使用**运行环境的本地时区**。服务端时区通常是 UTC、客户端是用户本地时区，于是同一时间戳在两端格式化出不同结果 —— 这既是显示 bug，也是 SSR 水合不匹配的经典原因。

**架构约定（必须写入团队规范）**：

| 环节 | 约定 | 理由 |
|---|---|---|
| 存储 | 数据库存 UTC（`timestamp with time zone`） | 避免夏令时与跨时区歧义 |
| 传输 | 接口返回 **ISO 8601**，带 `Z` 或时区偏移（`2026-09-17T10:00:00Z`） | 无歧义、可被 `new Date()` 直接解析 |
| 展示 | 前端按**用户时区**或**业务时区**格式化 | 用户看到当地时间 |
| 禁止 | 接口返回 `2026-09-17 10:00:00`（无时区信息） | 无法判断是哪个时区的 10 点 |

```javascript
// ========== Intl API（浏览器原生，无需依赖库）==========
const date = new Date('2026-09-17T10:00:00Z');

// 日期时间格式化：按 locale 自动选择格式
new Intl.DateTimeFormat('zh-CN', { dateStyle: 'long' }).format(date);      // "2026年9月17日"
new Intl.DateTimeFormat('en-US', { dateStyle: 'short' }).format(date);     // "9/17/26"
new Intl.DateTimeFormat('de-DE', { dateStyle: 'medium', timeStyle: 'short' }).format(date);
// → "17.09.2026, 12:00"（德国用点号分隔、24 小时制）

// 显式指定时区（关键：不依赖运行环境时区）
new Intl.DateTimeFormat('zh-CN', {
  dateStyle: 'medium', timeStyle: 'short', timeZone: 'Asia/Shanghai',
}).format(date);  // → "2026年9月17日 18:00"

// 获取用户时区
const userTimeZone = Intl.DateTimeFormat().resolvedOptions().timeZone;  // "Asia/Shanghai"

// 相对时间："3 天前""昨天"
const rtf = new Intl.RelativeTimeFormat('zh-CN', { numeric: 'auto' });
rtf.format(-1, 'day');   // "昨天"
rtf.format(-3, 'day');   // "3天前"

// 列表连接："苹果、香蕉和橙子"
new Intl.ListFormat('zh-CN', { style: 'long', type: 'conjunction' }).format(['苹果', '香蕉', '橙子']);

// 语言名称本地化
new Intl.DisplayNames(['zh-CN'], { type: 'language' }).of('en');  // "英语"
```

```javascript
// ========== Day.js（轻量替代方案，需插件）==========
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc';
import timezone from 'dayjs/plugin/timezone';
import relativeTime from 'dayjs/plugin/relativeTime';
import localizedFormat from 'dayjs/plugin/localizedFormat';
import 'dayjs/locale/zh-cn';  // 引入中文语言包

dayjs.extend(utc);
dayjs.extend(timezone);
dayjs.extend(relativeTime);
dayjs.extend(localizedFormat);
dayjs.locale('zh-cn');

// 把"某个时区的墙上时间"转成正确的时刻
dayjs.tz('2026-09-17 10:00:00', 'Asia/Shanghai').toISOString();
// → "2026-09-17T02:00:00.000Z"

// 把 UTC 时刻按目标时区展示
dayjs.utc('2026-09-17T02:00:00Z').tz('Asia/Shanghai').format('YYYY-MM-DD HH:mm');
// → "2026-09-17 10:00"

dayjs('2026-09-14').fromNow();  // "3 天前"
```

> **Day.js 时区插件依赖 `Intl.DateTimeFormat`**，在缺少完整 ICU 数据的环境（部分旧版 Node、部分小程序运行时）中会退化或报错，需实测确认。

**Temporal API（未来标准，TC39 Stage 3）**：`Date` 的设计缺陷（可变、时区语义混乱、无独立日期类型）催生了 `Temporal`，其核心价值是**把"时刻（Instant）"与"墙上时间（PlainDate / PlainDateTime）"明确分离**，从类型层面杜绝时区误用。

```javascript
// Temporal 为 TC39 Stage 3 提案，需引入 polyfill（@js-temporal/polyfill）
// 原生支持仍在推进中，生产环境请以 polyfill 为主

// 时刻（带时区的确定时间点）
const zdt = Temporal.ZonedDateTime.from('2026-09-17T10:00:00+08:00[Asia/Shanghai]');
zdt.hour;                                    // 10
zdt.withTimeZone('America/New_York').hour;   // 22（前一天）

// 墙上时间（不带时区，适用于"生日""节假日"这类概念）
const birthday = Temporal.PlainDate.from('1995-06-15');
birthday.add({ years: 30 });

// 时长运算与本地化格式化（与 Intl 选项完全兼容）
const duration = Temporal.Duration.from({ days: 3, hours: 5 });
Temporal.Now.zonedDateTimeISO().add(duration);
zdt.toLocaleString('zh-CN', { dateStyle: 'full', timeStyle: 'short' });
```

**业务时区 vs 用户时区（架构决策）**：

| 场景 | 用哪个 | 理由 |
|---|---|---|
| 消息时间、日志时间 | 用户时区 | 用户关心"我这边几点" |
| 订单日期、财务报表、营业日 | **业务时区**（固定，如 `Asia/Shanghai`） | 避免同一订单在不同时区被算作不同日期，导致对账差异 |
| 活动开始时间 | 业务时区（并在 UI 明确标注） | "10 点开始"必须明确是哪个时区的 10 点 |
| 倒计时 | UTC 时间戳计算差值 | 与时区无关 |

```javascript
// 判断"今天"必须显式指定时区，不能用本地 Date
// ❌ 错误：服务端（UTC）与客户端（+08:00）会得到不同的"今天"
const today = new Date().getDate();

// ✅ 正确：显式指定业务时区
function getBusinessDate(date = new Date(), timeZone = 'Asia/Shanghai') {
  // en-CA 的日期格式恰好是 YYYY-MM-DD，可直接用于比较
  return new Intl.DateTimeFormat('en-CA', {
    timeZone, year: 'numeric', month: '2-digit', day: '2-digit',
  }).format(date);  // → "2026-09-17"
}
```

### 2.3 数字与货币格式化

```javascript
// 数字：千分位、小数位、百分比
new Intl.NumberFormat('en-US').format(1234567.891);   // "1,234,567.891"
new Intl.NumberFormat('de-DE').format(1234567.891);   // "1.234.567,891"（点号千分位、逗号小数）
new Intl.NumberFormat('zh-CN', { style: 'percent', maximumFractionDigits: 1 }).format(0.1234);
// → "12.3%"

// 货币：符号位置、小数位、分组方式全部由 locale 决定
new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(1234.5);
// → "¥1,234.50"
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5);
// → "1.234,50 €"（符号在后、逗号小数、点号分组）
new Intl.NumberFormat('en-US', { style: 'currency', currency: 'JPY' }).format(1234.5);
// → "¥1,235"（日元无小数位，自动四舍五入）

// 大数缩写与单位
new Intl.NumberFormat('zh-CN', { notation: 'compact', compactDisplay: 'short' }).format(1234567);
// → "123万"
new Intl.NumberFormat('zh-CN', { style: 'unit', unit: 'kilometer', unitDisplay: 'short' }).format(5);
// → "5公里"
```

**四条货币格式化的架构原则**：
1. **金额永远以最小货币单位的整数传输**（分 / cents），避免浮点误差。`0.1 + 0.2 !== 0.3` 在金额场景不可接受。
2. **货币符号与格式由 locale 决定，不要手写 `'¥' + amount`**。同一个 `¥` 在 CNY 与 JPY 下含义不同。
3. **后端返回 `{ amount: 123450, currency: 'CNY' }`**，前端用 `Intl.NumberFormat` 按用户 locale 渲染。不要把已格式化的字符串从后端返回（无法适配多语言）。
4. **币种与 locale 是两件事**。中国用户看美元金额时，格式应按 `zh-CN` 排版、符号应为 `US$`，而不是 `$`。

```javascript
// 金额展示的正确封装
function formatMoney(amountInMinorUnits, currency, locale = 'zh-CN') {
  // 从最小货币单位还原主单位（不同币种的最小单位可能不是 1/100）
  const digits = new Intl.NumberFormat(locale, { style: 'currency', currency })
    .resolvedOptions().maximumFractionDigits;
  return new Intl.NumberFormat(locale, { style: 'currency', currency })
    .format(amountInMinorUnits / 10 ** digits);
}

formatMoney(123450, 'CNY');  // "¥1,234.50"
formatMoney(123450, 'JPY');  // "¥123,450"（日元 0 位小数）
```

> **易错点**：不存在 `Intl.NumberFormat.parse`，从本地化字符串还原数值需自行实现或使用专用库。

### 2.4 语言包按需加载与体积优化

**体积问题的来源**：语言数 × 文案条数。10 种语言 × 5000 条文案 × 平均 60 字节 ≈ 3MB（未压缩），全量打包会让首屏体积失控。

| 优化手段 | 做法 | 收益 | 代价 |
|---|---|---|---|
| **按命名空间分包** | 每个业务模块一个语言包文件，路由级动态 `import()` | 首屏只加载当前页面需要的文案 | 需要维护命名空间边界 |
| **只内联 fallback 语言** | 主包只含 `zh-CN`，其他语言懒加载 | 首屏体积与语言数解耦 | 切换语言时有一次加载延迟 |
| **按语言异步加载** | `import(`./locales/${locale}.json`)` | 首屏只加载当前语言 | 需处理加载态与失败回退 |
| **预编译消息** | 构建期把 ICU 字符串编译为 AST / 函数 | 去掉运行时消息编译器（vue-i18n 可减约 20-30KB） | 构建配置复杂度上升 |
| **key 压缩** | 构建期把长 key 映射为短 id（`order.list.title` → `a.b.c`） | 减少 30-50% 体积 | 可读性下降，需保留 sourcemap 映射 |
| **未使用 key 清理** | 静态扫描代码，删除无引用的 key | 持续控制体积 | 动态拼接的 key 易误删 |
| **服务端按需内联** | SSR 时按 `Accept-Language` 只内联当前语言 | 消除 FOUC 与额外请求 | 需要 SSR 能力 |
| **CDN 长缓存** | 语言包文件名带内容哈希 | 语言包更新不影响其他资源缓存 | — |

```typescript
// 语言包按需加载：按 locale + namespace 双重懒加载
const localeLoaders = import.meta.glob('./locales/*/*.json');

async function loadMessages(locale: string, namespaces: string[]) {
  const results = await Promise.all(
    namespaces.map(async (ns) => {
      const loader = localeLoaders[`./locales/${locale}/${ns}.json`];
      if (!loader) {
        // 该语言缺少此命名空间 → 回退到 fallback 语言，并上报缺失
        reportMissing(locale, ns);
        const fallback = await localeLoaders[`./locales/zh-CN/${ns}.json`]?.();
        return [ns, fallback?.default ?? {}] as const;
      }
      const mod = await loader();
      return [ns, (mod as { default: Record<string, unknown> }).default] as const;
    })
  );
  return Object.fromEntries(results);
}
```

```typescript
// vite.config.ts —— 使用 @intlify/unplugin-vue-i18n 在构建期预编译消息
import VueI18nPlugin from '@intlify/unplugin-vue-i18n/vite';

export default defineConfig({
  plugins: [
    VueI18nPlugin({
      // 只包含语言包目录，避免把其他 JSON 也编译
      include: resolve(__dirname, './src/locales/**'),
      // 关闭运行时消息编译器，强制预编译（体积更小）
```

### 2.5 动态切换语言的实现

**切换语言需要同步更新的五处状态**：

| 状态 | 更新方式 | 遗漏后果 |
|---|---|---|
| i18n 实例的 locale | `i18n.global.locale.value = 'en-US'` | 文案不切换 |
| `<html lang>` | `document.documentElement.lang = 'en-US'` | 无障碍朗读语言错误、SEO 信号错误 |
| `<html dir>` | RTL 语言时设为 `rtl` | 阿拉伯语布局不镜像 |
| 持久化存储 | `localStorage` / Cookie | 刷新后回到默认语言 |
| 服务端数据 | 重新拉取带语言参数的接口 | 后端返回的枚举文案仍是旧语言 |

```typescript
// i18n/index.ts —— 语言切换的统一入口
import { createI18n } from 'vue-i18n';

export const SUPPORTED_LOCALES = ['zh-CN', 'en-US', 'ja-JP', 'ar-EG'] as const;
export type AppLocale = (typeof SUPPORTED_LOCALES)[number];
const RTL_LOCALES = new Set(['ar-EG', 'he-IL', 'fa-IR']);

export const i18n = createI18n({
  legacy: false,             // 组合式 API 模式
  globalInjection: true,     // 模板中可直接用 $t
  locale: 'zh-CN',
  fallbackLocale: 'zh-CN',   // 缺失 key 时的兜底语言
  messages: {},              // 初始为空，由 loadMessages 填充
});

export async function setLocale(locale: AppLocale) {
  // 1. 加载语言包（若已加载会命中缓存）
  i18n.global.setLocaleMessage(locale, await loadMessages(locale, ['common', 'order']));

  // 2. 切换 locale
  i18n.global.locale.value = locale;

  // 3. 同步 DOM 属性
  document.documentElement.lang = locale;
  document.documentElement.dir = RTL_LOCALES.has(locale) ? 'rtl' : 'ltr';

  // 4. 持久化（用 Cookie 便于 SSR 端读取，避免服务端渲染出错误语言）
  document.cookie = `locale=${locale}; path=/; max-age=31536000; samesite=lax`;

  // 5. 通知需要重新拉取数据的模块（如后端返回的枚举文案）
  await refreshServerProvidedText(locale);
}

// 初始化：Cookie > 浏览器语言 > 默认语言
export function detectLocale(): AppLocale {
  const fromCookie = document.cookie.match(/(?:^|;\s*)locale=([^;]+)/)?.[1];
  if (fromCookie && SUPPORTED_LOCALES.includes(fromCookie as AppLocale)) {
    return fromCookie as AppLocale;
  }
  const fromNavigator = navigator.languages?.find((l) =>
    SUPPORTED_LOCALES.includes(l as AppLocale)
  );
  return (fromNavigator as AppLocale) ?? 'zh-CN';
}
```

**必须注意的三点**：

```typescript
// ① 不要缓存 t() 的返回值到模块级变量（切换语言后不会更新）
const TITLE = i18n.global.t('order.list.title');                      // ❌
const title = computed(() => i18n.global.t('order.list.title'));      // ✅ 建立响应式依赖
```

② **`fallbackLocale` 不是万能的**。缺失 key 时回退会让界面出现中英混杂。生产环境应通过 CI 校验 key 完整性，而不是依赖 fallback 兜底。

③ **语言切换与路由要联动**（使用路由前缀策略时）。切换语言需同时更新 URL 中的语言前缀，否则刷新后语言与 URL 不一致。

### 2.6 SEO 与多语言

| 策略 | 示例 | SEO 效果 | 运维成本 | 适用 |
|---|---|---|---|---|
| **子目录** | `example.com/zh-CN/` | 好（继承主域权重，易集中管理） | 低 | **推荐，绝大多数场景** |
| **子域名** | `zh.example.com` | 中（权重独立，需分别维护） | 中 | 需要独立部署 / 独立团队 |
| **国家顶级域** | `example.cn` / `example.de` | 最好（本地化信号最强） | 最高（需注册与备案） | 强本地化诉求、有本地实体 |
| **URL 参数** | `example.com?lang=zh` | 差（不被视为独立页面） | 最低 | **不推荐用于 SEO 场景** |

```html
<!-- hreflang 标注：每个语言版本都要声明全部语言版本，包括自己（自引用） -->
<link rel="alternate" hreflang="zh-CN" href="https://example.com/zh-CN/product/1001" />
<link rel="alternate" hreflang="zh-Hant-TW" href="https://example.com/zh-TW/product/1001" />
<link rel="alternate" hreflang="en-US" href="https://example.com/en-US/product/1001" />
<link rel="alternate" hreflang="ja-JP" href="https://example.com/ja-JP/product/1001" />
<!-- x-default 指向"未匹配到任何语言"时的兜底版本 -->
<link rel="alternate" hreflang="x-default" href="https://example.com/en-US/product/1001" />

<html lang="zh-CN">
```

**hreflang 的三条硬性规则**（违反会被搜索引擎忽略整组标注）：

| 规则 | 说明 |
|---|---|
| **自引用** | 每个页面必须包含指向自己的 hreflang |
| **双向指向** | A 页面标注了 B，B 页面也必须标注 A，否则标注无效 |
| **语言码规范** | 使用 ISO 639-1 语言码 + 可选 ISO 3166-1 地区码（`zh-CN`、`pt-BR`、`zh-Hant`） |

```http
# 响应头声明内容语言（与 html lang 保持一致）
Content-Language: zh-CN
```

```xml
<!-- sitemap.xml：用 xhtml:link 标注每个 URL 的所有语言版本 -->
<url>
  <loc>https://example.com/zh-CN/product/1001</loc>
  <xhtml:link rel="alternate" hreflang="en-US" href="https://example.com/en-US/product/1001" />
  <xhtml:link rel="alternate" hreflang="ja-JP" href="https://example.com/ja-JP/product/1001" />
</url>
```

**必须避免的四种做法**：

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 客户端 JS 跳转语言 | 爬虫执行 JS 不可靠，可能只抓到默认语言 | 服务端按 URL 前缀渲染对应语言 |
| 按 `navigator.language` 自动跳转 | 爬虫 UA 语言不确定，抓取结果随机 | 用 `Accept-Language` 做**服务端 302**，且允许 `?lang=` 覆盖 |
| 按 Cookie 决定语言 | 爬虫无 Cookie，只能看到默认语言 | 语言体现在 URL 中 |
| 各语言版本内容完全相同 | 被判为重复内容，权重分散 | 每个语言版本有独立 URL + 独立内容 + hreflang 标注 |

### 2.7 RTL（从右到左）适配

RTL 语言包括阿拉伯语（`ar`）、希伯来语（`he`）、波斯语（`fa`）、乌尔都语（`ur`）。适配的核心是**从"物理方向"思维切换到"逻辑方向"思维**。

**① 逻辑属性（Logical Properties）—— 最重要的一条**

CSS 逻辑属性用"起始 / 结束"替代"左 / 右"，随 `direction` 自动映射，**一份样式同时适配 LTR 与 RTL**。

| 物理属性（不推荐） | 逻辑属性（推荐） | RTL 下的行为 |
|---|---|---|
| `margin-left` | `margin-inline-start` | 自动变为右侧外边距 |
| `margin-right` | `margin-inline-end` | 自动变为左侧外边距 |
| `padding-left` | `padding-inline-start` | 自动映射 |
| `border-left` | `border-inline-start` | 自动映射 |
| `left: 0` | `inset-inline-start: 0` | 自动变为 `right: 0` |
| `text-align: left` | `text-align: start` | 自动变为右对齐 |
| `float: left` | `float: inline-start` | 自动映射 |
| `width` / `height` | `inline-size` / `block-size` | 随书写模式映射 |

```css
/* ❌ 物理属性：RTL 下布局错乱 */
.card {
  margin-left: 16px;
  padding-right: 8px;
  border-left: 3px solid var(--color-primary);
  text-align: left;
}

/* ✅ 逻辑属性：一份代码适配两种方向 */
.card {
  margin-inline-start: 16px;
  padding-inline-end: 8px;
  border-inline-start: 3px solid var(--color-primary);
  text-align: start;
}
```

**② 方向来源与设置**

```typescript
// 方式一：Intl.Locale.prototype.textInfo（较新 API，需确认目标浏览器支持）
// 注意：旧版浏览器不支持，必须提供兜底
function getDirection(locale: string): 'ltr' | 'rtl' {
  try {
    // textInfo 为 Intl.Locale 的属性，返回 { direction: 'ltr' | 'rtl' }
    return new Intl.Locale(locale).textInfo.direction;
  } catch {
    // 兜底：维护一份 RTL 语言前缀清单
    const RTL_PREFIXES = ['ar', 'he', 'fa', 'ur', 'yi', 'dv', 'ps', 'sd'];
    return RTL_PREFIXES.some((p) => locale.startsWith(p)) ? 'rtl' : 'ltr';
  }
}

// 设置到根元素，全站生效
document.documentElement.dir = getDirection(locale);
```

```css
/* 方式二：:dir() 伪类（新特性，语义更准确，能匹配继承的 direction） */
/* 兼容写法 [dir='rtl'] 覆盖面更广，推荐优先使用 */
[dir='rtl'] .sidebar { /* RTL 下的特定调整 */ }
:dir(rtl) .sidebar { }
```

**③ 图标镜像：哪些要翻转，哪些不能翻**

| 类别 | 是否翻转 | 示例 |
|---|---|---|
| **方向性图标** | ✅ 翻转 | 箭头（`→`）、返回/前进、chevron、折叠展开、进度条方向、滑块 |
| **文字相关** | ✅ 翻转 | 列表项目符号（若为图形）、引号样式 |
| **时间相关** | ❌ 不翻转 | 时钟、日历、播放/暂停按钮 |
| **媒体与品牌** | ❌ 不翻转 | 品牌 logo、播放三角、媒体控制条 |
| **状态符号** | ❌ 不翻转 | 勾选、叉号、警告三角、加号 |
| **数字与图表** | ❌ 不翻转 | 数字、坐标轴、饼图、地图 |

```css
/* 只对方向性图标做镜像，不要全局翻转 */
[dir='rtl'] .icon-directional {
  transform: scaleX(-1);
}
```

**④ 混排文本：用 `bdi` 与 `dir="auto"` 隔离**

```html
<!-- 问题：RTL 文本中嵌入 LTR 内容（数字、URL、英文名）会导致标点跑到错误的一侧 -->
<p dir="rtl">تم إنشاء الطلب رقم 1001A بسعر $99.00</p>

<!-- 方案一：dir="auto" 让浏览器按首个强方向字符自动判断 -->
<p dir="rtl">تم إنشاء الطلب <span dir="auto">1001A</span> بسعر <span dir="auto">$99.00</span></p>

<!-- 方案二（推荐）：<bdi> 元素天然隔离双向文本，不影响周围文本顺序 -->
<p dir="rtl">تم إنشاء الطلب <bdi>1001A</bdi> بسعر <bdi>$99.00</bdi></p>
```

**⑤ 第三方 UI 库的 RTL 支持**

| 库 | RTL 支持方式 |
|---|---|
| Ant Design | `<ConfigProvider direction="rtl">` |
| Element Plus | 引入 RTL 样式文件（`element-plus/dist/index.css` + RTL 版本） |
| Tailwind CSS | 用 `ms-*` / `me-*`（逻辑属性）替代 `ml-*` / `mr-*`；`rtl:` 变体做特定调整 |
| Vuetify | `$vuetify.rtl` + RTL 配置 |

> **易错点**：只切换 `dir="rtl"` 而不引入组件库的 RTL 样式，会导致组件内部（弹窗、下拉、分页器）方向仍然错误。

### 2.8 SSR 同构中的状态序列化与注水

**SSR 的完整链路**：

```
1. 请求到达服务端
2. 服务端创建应用实例 → 执行组件代码 → 预取数据 → 渲染为 HTML 字符串
3. 把"服务端已经取到的数据"序列化后内联到 HTML
4. 浏览器直接展示 HTML（首屏可见，无需等 JS）
5. 客户端加载 JS → 用同一份数据"注水"（hydrate）→ 复用 DOM，绑定事件
6. 之后由客户端接管路由与交互
```

**为什么必须序列化状态**：若客户端不拿到服务端已取的数据，注水时会重新请求接口，导致首屏数据闪烁（服务端渲染了内容、注水时变空白再填充）、重复请求、**注水不匹配**。

```typescript
// ========== 服务端 ==========
import { createSSRApp } from 'vue';
import { renderToString } from 'vue/server-renderer';
import serialize from 'serialize-javascript';

async function handleRequest(url: string, locale: string) {
  const app = createSSRApp(App);
  const router = createRouter({ history: createMemoryHistory(), routes });
  const store = createStore();

  app.use(router);
  app.use(store);

  // 让路由解析到目标地址
  await router.push(url);
  await router.isReady();

  // 关键：收集需要序列化的状态（含路由地址、locale 与预取数据）
  const state = { route: router.currentRoute.value.fullPath, locale, ...store.state };
  const html = await renderToString(app);

  // ⚠️ 安全关键：必须转义，否则数据中的 </script> 会造成 XSS
  // serialize-javascript 会转义 <、>、\u2028、\u2029 等危险字符
  const serialized = serialize(state, { isJSON: true });

  return `<!DOCTYPE html>
    <html lang="${locale}">
      <body>
        <div id="app">${html}</div>
        <script>window.__INITIAL_STATE__ = ${serialized}</script>
        <script type="module" src="/entry-client.js"></script>
      </body>
    </html>`;
}

// ========== 客户端 ==========
const app = createSSRApp(App);
// 用服务端序列化的状态初始化 store，保证首次渲染结果与服务端一致
const initialState = window.__INITIAL_STATE__;
const store = createStore(initialState);

app.mount('#app'); // 注水：复用服务端 DOM，绑定事件监听
```

> **XSS 风险说明**：直接 `JSON.stringify(state)` 内联到 `<script>` 是**高危漏洞**。若数据中含有 `</script>`，脚本标签会被提前闭合，攻击者可注入任意脚本。必须使用 `serialize-javascript`，或至少执行 `JSON.stringify(x).replace(/</g, '\\u003c')`。

**注水不匹配（Hydration Mismatch）的六种成因**：

| 成因 | 示例 | 修复 |
|---|---|---|
| **时间相关** | 服务端渲染时 `Date.now()` 与客户端不同 | 把时间渲染推迟到 `onMounted` 后，或由服务端把时间作为 props 传入 |
| **随机数** | `Math.random()` 生成 id 或文案 | 用 `useId()`（React / Vue 3.5+）生成稳定 id |
| **时区差异** | 服务端 UTC、客户端 +08:00，`toLocaleString()` 结果不同 | **服务端与客户端显式指定同一 `timeZone`**（国际化场景的经典坑） |
| **locale 差异** | 服务端按 `Accept-Language` 用 `zh-CN`，客户端 `detectLocale()` 得到 `en-US` | 服务端把 locale 序列化传给客户端，客户端初始化时直接使用，不再自行探测 |
| **浏览器 API 分支** | 服务端 `typeof window === 'undefined'` 走了不同分支 | 用 `<ClientOnly>` 包裹仅客户端内容，或统一在 `onMounted` 后渲染 |
| **HTML 结构非法** | `<div>` 嵌在 `<p>` 内，浏览器自动纠正导致 DOM 与虚拟 DOM 不一致 | 修正非法嵌套；避免在 `<p>` 内放块级元素 |

**注水失败的后果**：React 会丢弃服务端 HTML 并在客户端重新渲染（白屏 + 性能损失 + 丢失服务端渲染收益）；Vue 会输出警告并尝试修补，可能出现短暂的视觉跳动。

### 2.9 路由同构设计

**核心思路**：**同一份路由表 + 不同的 history 实现**。

| 框架 | 服务端 | 客户端 |
|---|---|---|
| Vue Router 4 | `createMemoryHistory()` | `createWebHistory()` / `createWebHashHistory()` |
| React Router 6 | `<StaticRouter location={req.url}>` | `<BrowserRouter>` |
| Next.js / Nuxt | 框架内建，无需手工配置 | 框架内建 |

```typescript
// 同一份路由表，两个入口各自传入 history
import { createRouter, createMemoryHistory, createWebHistory } from 'vue-router';
import type { RouterHistory } from 'vue-router';

export function createAppRouter(history: RouterHistory) {
  return createRouter({ history, routes });
}

// entry-server.ts
const router = createAppRouter(createMemoryHistory());
// entry-client.ts
const router = createAppRouter(createWebHistory());
```

**数据预取的同构抽象**：把"路由级数据获取"从组件生命周期中抽出来，做成与渲染环境无关的接口。

| 框架 | 服务端预取方式 | 客户端复用方式 |
|---|---|---|
| Vue 3 | `onServerPrefetch` + `useSSRContext` | 注水后检查 store 是否已有数据，避免重复请求 |
| Nuxt 3 | `useAsyncData` / `useFetch`（自动序列化到 payload） | 自动从 payload 读取，不重复请求 |
| React Router 6 | `loader` 函数（`createStaticHandler` 服务端执行） | 路由切换时自动调用同一 `loader` |
| Next.js App Router | Server Component 直接 `await` | 数据作为 props 传入 Client Component |

```typescript
// Vue 3：路由级数据预取的通用写法
// 关键：服务端预取的数据要写入 store，客户端注水后直接复用，避免重复请求
export function useOrderList() {
  const store = useOrderStore();

  // 服务端预取：仅在 SSR 阶段执行
  onServerPrefetch(async () => {
    store.orders = await fetchOrders();
  });

  // 客户端：若 store 已有数据（来自服务端序列化），则跳过请求
  onMounted(async () => {
    if (store.orders.length === 0) store.orders = await fetchOrders();
  });

  return store;
}
```

**路由守卫的同构注意点**：

| 注意点 | 说明 |
|---|---|
| 守卫中不能访问 `window` / `document` | 服务端会执行守卫，访问浏览器 API 会直接抛错 |
| 重定向必须在服务端完成 | 服务端返回 302 而非渲染一个"正在跳转"的页面，避免闪烁与 SEO 问题 |
| 守卫必须是幂等的 | 服务端与客户端都会执行，不能有副作用（如重复上报埋点） |
| 权限校验不能只靠守卫 | 服务端守卫可防住未登录访问，但数据权限仍须后端接口保证（见 05 模块） |

### 2.10 平台差异抹平

多端同构的最大工程挑战不是"写一套代码"，而是"处理差异"。三种手段按优先级使用：

| 手段 | 生效时机 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **适配层（Adapter）** | 运行时 | 可测试、可 mock、接口稳定、差异集中 | 需要抽象设计；多一层间接调用 | **首选**：存储、请求、导航、UI 反馈 |
| **条件编译** | 编译期 | 零运行时开销；代码被真正剔除 | 代码可读性下降；IDE 提示差 | 平台专有 API、平台专有组件 |
| **运行时探测** | 运行时 | 无需构建配置 | 有运行时开销；难以静态分析；容易漏分支 | 兜底手段，尽量少用 |

**① 适配层：把平台差异收敛到一处**

```typescript

  name: 'web' | 'weapp' | 'alipay' | 'app' | 'harmony';

  getSystemLocale(): string;
}

// platform/web.ts —— Web 实现
export const webPlatform: IPlatform = {
  name: 'web',

    async set(key, value) { localStorage.setItem(key, value); },
    async remove(key) { localStorage.removeItem(key); },
  },
  navigator: {
    push(url) { history.pushState(null, '', url); },
    replace(url) { history.replaceState(null, '', url); },
    back() { history.back(); },
  },
  toast: { show(message, duration = 2000) { /* 自定义 Toast 实现 */ } },
  request: (url, options) => fetch(url, options).then((r) => r.json()),

// platform/weapp.ts —— 小程序实现
export const weappPlatform: IPlatform = {

      return res?.data ?? null;

    back() { Taro.navigateBack(); },

  // 小程序无法读取 Accept-Language，需通过系统信息获取并归一化格式
  getSystemLocale: () => normalizeLocale(Taro.getSystemInfoSync().language ?? 'zh_CN'),
```


### 2.11 Taro / uni-app 的架构实现思路

两者都采用"**编译时 + 运行时**"的混合方案，但侧重不同。

| 维度 | Taro | uni-app |
|---|---|---|
| 出品方 | 京东 | DCloud |
| 语法基础 | React / Vue（可自由选择） | Vue（2 / 3） |
| 编译产物 | 各端小程序 DSL、H5、React Native、鸿蒙 | 各端小程序、H5、App（原生渲染）、鸿蒙 |
| 条件编译 | `process.env.TARO_ENV` | `#ifdef` / `#ifndef` 注释指令 |
| 运行时方案 | `@tarojs/runtime` 提供 DOM / BOM 模拟层 | 各端 runtime + 统一 API 层（`uni.*`） |
| 差异化能力 | React 生态完整可用（Hooks / Context） | 更贴近 Vue 生态，App 端支持原生渲染 |
| 原生能力扩展 | 插件化 + 原生模块 | 原生插件 + UTS（uni-app x） |

**Taro 的架构思路（"重运行时"方案）**：

```
业务代码（React 组件）
      │
      ▼
@tarojs/runtime 提供 DOM / BOM 模拟层（Taro DOM Tree）
      │
      ▼
React 在模拟环境中运行 → 产出 Taro DOM Tree
      │
      ▼
运行时 diff Taro DOM Tree → 通过 setData 同步到小程序视图层
```

**核心洞察**：Taro 3 之后不再把 React 组件**编译**为小程序模板（Taro 1/2 的做法），而是**让 React 直接运行在小程序的 JS 环境中**，用模拟 DOM 承接渲染结果，再通过 `setData` 把差异同步到视图层。

**这带来一个关键的性能约束**：小程序逻辑层与视图层是**两个线程**，通过 `setData` 跨线程通信，数据量越大、调用越频繁，性能越差。

```typescript
// ❌ 反模式：每次 setData 都传大对象，跨线程序列化开销巨大
setState({ list: hugeList });  // hugeList 有 5000 条

// ✅ 正例：只传变更的最小数据
// 1. 列表分页，单页不超过 20 条
// 2. 用不可变更新，让运行时能精确 diff
// 3. 避免在高频事件（滚动、输入）中直接 setState
```

**uni-app 的架构思路（"编译器 + 统一 API"方案）**：

```
Vue SFC（含 #ifdef 条件编译）
      │
      ▼
@dcloudio/uni-cli-shared 编译器
（解析 SFC → 按平台条件编译剔除代码 → 生成各端产物）
      │
      ├──▶ 小程序：WXML / WXSS / JS
      ├──▶ H5：标准 Web 产物
      └──▶ App：原生渲染层（或 uni-app x 编译为各端原生代码）
```

**统一 API 层**：`uni.request` / `uni.setStorage` / `uni.navigateTo` 等 API 在各端有不同实现，由 runtime 按平台分发到对应的原生 API。这与 2.10 节的"适配层"思路一致，只是由框架统一提供。

**两者的共同架构启示**：

| 启示 | 说明 |
|---|---|
| 差异处理应尽量前移到编译期 | 编译期剔除的代码不占运行时体积、无分支开销 |
| 运行时适配必须有性能预算 | 跨线程通信（`setData`）与桥接调用是主要成本来源 |
| 抽象层要稳定且窄 | 适配层接口越多，各端实现成本越高，越容易不一致 |
| 框架无法消除平台差异 | 只能收敛差异，无法让"小程序有的能力"在 Web 上出现 |

### 2.12 多端同构的成本与收益评估

**收益侧**：

| 收益 | 量化参考 | 前提条件 |
|---|---|---|
| 减少重复开发 | 端数 N ≥ 3 时可减少 50-70% 的前端工作量 | 业务逻辑占比高 |
| 一致性提升 | 消除"Web 修了小程序没修"类 bug | 逻辑同构做得好 |
| 迭代速度 | 需求一次实现、一次评审、一次测试 | 渲染差异小 |
| 人力弹性 | 团队技能栈统一，人员可灵活调度 | 团队接受统一技术栈 |

**成本侧**：

| 成本 | 说明 | 缓解手段 |
|---|---|---|
| 学习成本 | 需要掌握跨端框架 + 各端差异 + 各端调试工具 | 先做小项目试点；建立内部最佳实践文档 |
| 性能损耗 | 跨端运行时（模拟 DOM、跨线程通信、桥接调用）带来额外开销 | 关键路径用平台原生实现；性能敏感页面单独开发 |
| 调试成本 | 需要各端开发者工具，问题可能出现在框架层 | 保留框架源码调试能力；关注框架 issue |
| 生态兼容 | 第三方库可能依赖浏览器 API 或原生能力 | 建立"跨端可用库清单"；优先选无副作用的纯函数库 |
| 框架绑定 | 框架升级受制于框架方，框架停止维护时迁移成本高 | 用适配层隔离框架 API；核心业务逻辑保持框架无关 |
| 平台能力缺口 | 各端 API 覆盖不一致，某些能力只有个别平台有 | 用能力探测 + 降级方案；条件编译处理专有能力 |

| 场景特征 | 建议 |
|---|---|
| 端数 ≥ 3，业务逻辑占比高，交互复杂度中等 | **适合多端同构** |
| 端数 = 2（如 Web + 小程序），交互复杂（动画、手势、富文本编辑） | 分别开发可能更划算 |
| 性能敏感（长列表、高频交互、音视频编辑） | 关键页面用平台原生实现 |
| 已有成熟的多端独立代码库 | 逐步抽取逻辑同构层，不做整体重写 |
| 团队无跨端经验、项目周期紧张 | 不要在同构上做技术冒险 |

> **核心判断标准**：**同构的收益来自"逻辑复用"，成本来自"渲染差异"。** 若业务逻辑占比高（如订单、审批、表单类应用），同构收益显著；若交互与视觉效果是核心竞争力（如内容创作、游戏化应用），渲染差异会吃掉全部收益。

```typescript
export const SUPPORTED_LOCALES = ['zh-CN', 'en-US', 'ja-JP', 'ar-EG'] as const;
export type AppLocale = (typeof SUPPORTED_LOCALES)[number];
const RTL_LOCALES = new Set<AppLocale>(['ar-EG']);

export const i18n = createI18n({
  legacy: false,
  globalInjection: true,
  locale: 'zh-CN',
  fallbackLocale: 'zh-CN',
  // 主包只内联 fallback 语言，其余语言按需加载
  messages: { 'zh-CN': zhCN },
  // 缺失 key 由 CI 校验保证，生产环境关闭告警刷屏
  missingWarn: import.meta.env.DEV,
  fallbackWarn: import.meta.env.DEV,
});

// 语言包懒加载缓存
const loadedNamespaces = new Map<string, Set<string>>();

export async function loadMessages(locale: AppLocale, namespaces: string[]) {
  const loaded = loadedNamespaces.get(locale) ?? new Set<string>();
  const pending = namespaces.filter((ns) => !loaded.has(ns));
  if (pending.length === 0) return;

  const results = await Promise.all(
    pending.map(async (ns) => {
      const mod = await import(`@/locales/${locale}/${ns}.json`);
      return [ns, mod.default] as const;
    })
  );

  // 合并到已有语言包，避免覆盖其他命名空间
  const current = (i18n.global.getLocaleMessage(locale) ?? {}) as Record<string, unknown>;
  const merged = { ...current };
  for (const [ns, messages] of results) {
    merged[ns] = { ...(merged[ns] as object), ...messages };
    loaded.add(ns);
  }
  i18n.global.setLocaleMessage(locale, merged);
  loadedNamespaces.set(locale, loaded);
}

export async function setLocale(locale: AppLocale) {
  await loadMessages(locale, ['common']);
  i18n.global.locale.value = locale;
  document.documentElement.lang = locale;
  document.documentElement.dir = RTL_LOCALES.has(locale) ? 'rtl' : 'ltr';
  document.cookie = `locale=${locale}; path=/; max-age=31536000; samesite=lax`;
}
```

```typescript
function flatten(obj: Record<string, unknown>, prefix = ''): string[] {
  return Object.entries(obj).flatMap(([key, value]) => {
    const path = prefix ? `${prefix}.${key}` : key;
    return value && typeof value === 'object' && !Array.isArray(value)
      ? flatten(value as Record<string, unknown>, path)
      : [path];
  });
}

/** 提取 ICU 占位符（{name}、{count, plural, ...} 等）中的变量名 */
function extractPlaceholders(message: string): string[] {
  const names = new Set<string>();
  // 简化实现：匹配 { 开头到第一个 , 或 } 之间的标识符
  const regex = /\{\s*([a-zA-Z_$][\w$]*)\s*[,}]/g;
  let match: RegExpExecArray | null;
  while ((match = regex.exec(message)) !== null) names.add(match[1]);
  return [...names].sort();
}

const namespaces = readdirSync(join(LOCALES_DIR, BASE_LOCALE)).map((f) => f.replace('.json', ''));
const locales = readdirSync(LOCALES_DIR);
const errors: string[] = [];

for (const ns of namespaces) {
  const baseMessages = JSON.parse(readFileSync(join(LOCALES_DIR, BASE_LOCALE, `${ns}.json`), 'utf8'));
  const baseKeys = new Set(flatten(baseMessages));

  for (const locale of locales) {
    if (locale === BASE_LOCALE) continue;

    let messages: Record<string, unknown>;
    try {
      messages = JSON.parse(readFileSync(join(LOCALES_DIR, locale, `${ns}.json`), 'utf8'));
    } catch {
      errors.push(`[${locale}/${ns}] 文件缺失或 JSON 解析失败`);
      continue;
    }

    const keys = new Set(flatten(messages));
    const pick = (source: unknown, key: string) =>
      key.split('.').reduce<unknown>((acc, k) => (acc as any)?.[k], source);

    for (const key of baseKeys) {
      // 校验一：key 一致性（缺失会导致运行期回退，界面中英混杂）
      if (!keys.has(key)) {
        errors.push(`[${locale}/${ns}] 缺失 key: ${key}`);
        continue;
      }
      const baseValue = pick(baseMessages, key);
      const targetValue = pick(messages, key);

      // 校验二：空值检测（空字符串会静默覆盖 fallback，比缺失更隐蔽）
      if (typeof targetValue === 'string' && targetValue.trim() === '') {
        errors.push(`[${locale}/${ns}] 空文案: ${key}`);
      }

      // 校验三：占位符一致性（改名或丢失会导致运行期报错）
      if (typeof baseValue !== 'string' || typeof targetValue !== 'string') continue;
      const basePh = extractPlaceholders(baseValue).join(',');
      const targetPh = extractPlaceholders(targetValue).join(',');
      if (basePh !== targetPh) {
        errors.push(`[${locale}/${ns}] 占位符不一致: ${key}（期望 ${basePh}，实际 ${targetPh}）`);
      }
    }
  }
}

if (errors.length > 0) {
  console.error(`国际化校验失败，共 ${errors.length} 个问题：`);
  errors.forEach((e) => console.error(`  - ${e}`));
  process.exit(1);
}
console.log('国际化校验通过');
```

```typescript
// domain/order.ts —— 纯函数，可在任意端运行，可在 Node 中单元测试
export interface OrderItem { skuId: string; price: number; quantity: number }

export function calculateOrderTotal(items: OrderItem[], discountRate = 0): number {
  const subtotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  // 用整数运算避免浮点误差：折扣也以"万分比"表示
  return Math.round(subtotal * (1 - discountRate));
}
```

### 3.6 国际化与多端同构的结合

| 问题 | 原因 | 方案 |
|---|---|---|
| 语言包体积 | 小程序主包有体积上限（如微信主包 2MB） | 按分包拆分语言包；只把当前语言打进主包 |
| 语言分发 | 各端产物格式不同（Web JSON / 小程序 JSON / App 原生资源） | TMS 平台配置多端导出；CI 按端拉取对应格式 |
| 语言判定 | 小程序无法读取 `Accept-Language` 请求头；App 有系统语言 API | 统一收敛到适配层的 `getSystemLocale()`（见 2.10 节 `IPlatform` 定义） |

**语言包在服务端与客户端的加载策略**：

| 端 / 阶段 | 策略 | 理由 |
|---|---|---|
| SSR 首屏 | 服务端按 `Accept-Language` 协商语言，**只把当前语言包内联到 HTML** | 避免 FOUC（先渲染默认语言再闪成目标语言）；省一次网络请求 |
| 浏览器客户端 | 首屏语言已内联；切换语言时动态 `import()` 对应语言包 | 首屏体积与语言数解耦 |
| 小程序 | 按分包拆分语言包；只把当前系统语言打进主包，其他语言放分包 | 主包体积受限 |
| App | 语言包随版本内置（覆盖常用语言）+ 支持热更新（覆盖新增语言） | 避免首次启动时无网络导致文案缺失 |
| 所有端 | 语言包文件名带内容哈希，CDN 长缓存 | 语言包更新不影响其他资源缓存 |

```typescript
// 服务端语言协商（Node 侧，基于 Accept-Language 请求头）
import { match } from '@formatjs/intl-localematcher';
import Negotiator from 'negotiator';

const SUPPORTED = ['zh-CN', 'en-US', 'ja-JP', 'ar-EG'];

export function negotiateLocale(acceptLanguage: string | undefined, fallback = 'zh-CN') {
  if (!acceptLanguage) return fallback;
  // 把 "zh-CN,zh;q=0.9,en;q=0.8" 解析为按权重排序的语言列表
  const languages = new Negotiator({ headers: { 'accept-language': acceptLanguage } }).languages();
  // match 会处理 "zh" → "zh-CN" 这类近似匹配
  return match(languages, SUPPORTED, fallback);
}

// SSR 内联语言包：避免客户端再发一次请求
const messages = await loadMessages(locale, ['common', 'order']);

const html = `<!DOCTYPE html>
  <html lang="${locale}" dir="${getDirection(locale)}">
    <body>
      <div id="app">${appHtml}</div>
      <script>window.__I18N__ = ${serialize({ locale, messages }, { isJSON: true })}</script>
      <script type="module" src="/entry-client.js"></script>
    </body>
  </html>`;

// 客户端直接使用内联语言包，不再发起语言包请求
const { locale: l, messages: m } = window.__I18N__;
i18n.global.setLocaleMessage(l, m);
i18n.global.locale.value = l;
document.documentElement.dir = getDirection(l);
```

> **注意**：内联语言包会增大 HTML 体积（约等于语言包大小）。若语言包较大（> 100KB），应改为"内联首屏关键命名空间 + 其余懒加载"的混合策略，并给 HTML 设置 `no-cache` 或短缓存（否则语言包更新后用户拿到旧 HTML）。

## 四、常见面试题

**Q1：i18n 架构需要覆盖哪些维度？只做文案翻译有什么问题？**

**答案要点**：七个维度 —— 文案、日期时间、时区、数字、货币、复数与性别、书写方向（RTL）。只做文案翻译会导致日期格式不符合当地习惯、金额符号与小数位错误、复数形式错误（阿拉伯语有 6 种复数类别）、RTL 语言布局错乱。i18n 是架构能力（新增语言不改代码），l10n 是内容交付（实际翻译与本地化）。判断标准：新增一种语言时只需新增语言包与配置，不需要改业务代码。

**Q2：ICU MessageFormat 的复数为什么要区分 `one` / `other` 之外的类别？**

**答案要点**：复数类别由 CLDR 按语言定义，不同语言数量差异极大 —— 中文只有 `other`，英语有 `one`/`other`，法语 3 种，俄语 4 种，阿拉伯语 6 种。只写 `one`/`other` 会导致俄语、阿拉伯语等语言的复数形式错误。`=0` 是精确匹配、优先级最高；`#` 会自动替换为本地化格式的数字。复数分支必须由翻译人员或 TMS 平台按目标语言补全，前端不能假设只有两种。可用 `Intl.PluralRules` 查询某语言某个数字对应的复数类别。

**Q3：跨时区的时间应该如何处理？**

**答案要点**：存储统一 UTC；传输统一 ISO 8601（带 `Z` 或时区偏移）；展示按用户时区或业务时区。用 `Intl.DateTimeFormat` 的 `timeZone` 选项显式指定时区，不要依赖运行环境默认时区。区分"用户时区"（消息、日志）与"业务时区"（订单日期、财务报表、营业日）。判断"今天"必须显式指定时区，用 `new Date().getDate()` 会在服务端与客户端得到不同结果。严禁接口返回无时区信息的字符串。未来可关注 `Temporal` API（TC39 Stage 3），它从类型层面分离"时刻"与"墙上时间"。

**Q4：语言包体积如何优化？**

**答案要点**：按命名空间分包 + 路由级动态 `import()`；主包只内联 fallback 语言；构建期预编译消息（vue-i18n 关闭运行时编译器可减约 20-30KB）；key 压缩（长 key 映射为短 id，减 30-50% 体积，代价是可读性）；静态扫描清理未使用 key；SSR 时按 `Accept-Language` 只内联当前语言包；语言包文件名带内容哈希走 CDN 长缓存。

**Q5：多语言站点如何做 SEO？**

**答案要点**：路由策略优先级 —— 子目录 > 子域名 > 国家顶级域 > URL 参数（参数方式不推荐）。hreflang 三条硬性规则：自引用、双向指向、语言码符合 ISO 639-1 + ISO 3166-1；必须有 `x-default`。同步设置 `<html lang>` 与 `Content-Language`。禁止客户端 JS 跳转语言、按 Cookie 决定语言、按 `navigator.language` 自动跳转（爬虫都看不到）。各语言版本必须有独立 URL 和独立内容，否则被判重复内容。

**Q6：RTL 适配的核心要点是什么？**

**答案要点**：核心是**用逻辑属性替代物理属性** —— `margin-inline-start` 替代 `margin-left`、`inset-inline-start` 替代 `left`、`text-align: start` 替代 `text-align: left`，一份样式适配两种方向。`dir` 设置在 `<html>` 上，通过 `Intl.Locale.prototype.textInfo.direction` 或 RTL 语言清单判定（需兜底）。图标镜像要分类：方向性图标翻转，时间/媒体/品牌/状态符号不翻转。混排文本用 `<bdi>` 或 `dir="auto"` 隔离。第三方组件库必须显式启用 RTL。图表不要整体 `scaleX(-1)` 翻转，应逐项配置 `inverse` / `position`。

**Q7：SSR 为什么需要序列化状态？注水不匹配的常见原因有哪些？**

**答案要点**：不序列化会导致注水时重新请求接口，出现首屏数据闪烁、重复请求、注水不匹配。序列化必须转义：`JSON.stringify` 后直接内联到 `<script>` 是 XSS 高危漏洞（数据含 `</script>` 会提前闭合标签），必须用 `serialize-javascript` 或替换 `<` 为 `\u003c`。六种注水不匹配成因：时间相关、随机数、**时区差异**、**locale 差异**、浏览器 API 分支、HTML 结构非法。国际化场景的经典坑是服务端按 `Accept-Language` 用 `zh-CN`、客户端 `detectLocale()` 得到 `en-US`。原则：依赖 locale / timeZone 的格式化要么在服务端完成并传结果字符串，要么两端显式使用同一套配置。

**Q8：多端同构的三种平台差异抹平手段，优先级如何？**

**答案要点**：优先级 —— 适配层（Adapter）> 条件编译 > 运行时探测。适配层接口稳定、差异集中、可测试可 mock，是逻辑同构的基础；条件编译编译期剔除、零运行时开销，适合平台专有 API，但降低可读性且被剔除分支不做类型检查；运行时探测无需构建配置，但有运行时开销、难以静态分析，只作兜底。关键实践：业务代码只依赖 `IPlatform` 接口，差异全部收敛在 `platform/*` 实现中。

**Q9：多端同构的收益与成本如何评估？什么场景不适合？**

**答案要点**：收益来自"逻辑复用"（端数 ≥ 3 时可减少 50-70% 前端工作量），成本来自"渲染差异"。成本项包括学习成本、跨端运行时性能损耗（跨线程通信、桥接调用）、各端调试成本、第三方库兼容性不确定、框架绑定风险、平台能力缺口。不适合：端数只有 2 且交互复杂（动画、手势、富文本编辑）；性能敏感场景（长列表、音视频编辑）。分层策略：`domain/` 100% 复用、`services/` 90%+、`platform/` 0%（本身即差异）、`pages/` 50-80%。

## 五、避坑指南

| 坑点 | 现象 | 原因 | 解决方案 |
|---|---|---|---|
| 用文案本身当 i18n key | 改一次文案，全项目 key 失效，所有翻译丢失 | key 直接使用源语言文案 | key 用语义化命名空间（`order.action.submit`）；key 一旦发布不改名，重构时保留旧 key 作别名 |
| 只写 `one` / `other` 复数分支 | 俄语、阿拉伯语等语言复数形式错误 | 假设所有语言只有两种复数类别 | 按 CLDR 规则补全分支；用 `Intl.PluralRules` 验证 |
| 字符串拼接代替消息模板 | 其他语言语序错乱 | `'你有 ' + count + ' 条消息'` | 整句作为 ICU 消息模板，变量交给 MessageFormat 处理 |
| 手写货币符号与千分位 | `€1.234,56` 被写成 `€1234.56` | `'¥' + amount` 或手写正则 | 用 `Intl.NumberFormat` 的 `style: 'currency'` |
| 金额用浮点数传输 | 金额出现 `0.30000000000000004`，对账差异 | 用 `Number` 表示元 | 以最小货币单位（分）的整数传输；后端返回 `{ amount, currency }` |
| 接口返回无时区的时间字符串 | 跨时区用户看到的时间相差数小时 | 后端返回 `2026-09-17 10:00:00` | 统一返回 ISO 8601（带 `Z` 或偏移）；前端用 `Intl` 的 `timeZone` 显式格式化 |
| 用 `new Date().getDate()` 判断"今天" | 服务端（UTC）与客户端（+08:00）得到不同日期，统计口径不一致 | 未显式指定时区 | 用 `Intl.DateTimeFormat` 指定业务时区后比较日期字符串 |
| 服务端与客户端 locale 不一致 | SSR 页面出现注水不匹配警告，内容短暂闪烁 | 服务端按 `Accept-Language` 定语言，客户端自行 `detectLocale()` | 服务端把 locale 序列化传给客户端，客户端初始化时直接使用 |
| `JSON.stringify` 直接内联到 `<script>` | XSS 漏洞，数据含 `</script>` 时被提前闭合 | 未转义危险字符 | 用 `serialize-javascript` 的 `isJSON: true`，或 `replace(/</g, '\\u003c')` |
| 语言包缺失 key 依赖 fallback 兜底 | 界面出现中英混杂 | 未做 key 完整性校验 | CI 中校验 key 一致性、占位符一致性、空值；不依赖 `fallbackLocale` |
| 缓存 `t()` 的返回值 | 切换语言后部分文案不更新 | `const TITLE = t('...')` 在模块加载时执行一次 | 在渲染时调用 `t()`，或用 `computed(() => t('...'))` |
| 只用 `margin-left` 等物理属性 | RTL 语言下布局错乱（间距在错误一侧） | 未使用逻辑属性 | 全面改用 `margin-inline-start`、`inset-inline-start`、`text-align: start` |
| 整体 `scaleX(-1)` 翻转图标或图表 | 文字镜像不可读、数字反向 | 未区分方向性图标与不可翻转元素 | 只翻转方向性图标；图表逐项配置 `inverse` / `position` |
| 未启用组件库的 RTL 模式 | 弹窗、下拉、分页器方向仍为 LTR | 只设置 `dir="rtl"`，未引入组件库 RTL 样式 | Ant Design 用 `direction="rtl"`；Element Plus 引入 RTL 样式文件 |
| 客户端 JS 跳转语言 | 搜索引擎只抓到默认语言，多语言页面不被索引 | 用 `navigator.language` 或 Cookie 在客户端重定向 | 语言体现在 URL 中，服务端按 URL 前缀渲染；`Accept-Language` 只用于 302 |
| hreflang 缺少自引用或非双向 | 搜索引擎忽略整组 hreflang 标注 | 只在部分页面标注，或 A 标注 B 但 B 未标注 A | 每个页面标注全部语言版本（含自己）；确保双向指向；补充 `x-default` |
| 语言包全量打进主包 | 小程序主包超限；Web 首屏体积随语言数线性增长 | 未做分包与按需加载 | 按命名空间分包 + 按 locale 懒加载；小程序把非当前语言放分包；SSR 只内联当前语言 |
| 业务代码直接调用平台 API | 同一段逻辑需要写 N 份，改一处漏 N-1 处 | 未建立适配层，`wx.request` 与 `fetch` 混用 | 定义 `IPlatform` 接口，业务代码只依赖接口；差异全部收敛在 `platform/*` |
| 条件编译块内写业务逻辑 | 被剔除的分支不做类型检查，运行期才发现错误 | 把大段逻辑放进 `#ifdef` | 条件编译块只放平台 API 调用（保持极短），逻辑走适配层 |
| 小程序中频繁 `setData` 大对象 | 页面卡顿，输入延迟明显 | 逻辑层与视图层跨线程通信，数据量越大开销越大 | 列表分页（单页 ≤ 20 条）；只传变更的最小数据；避免在滚动/输入等高频事件中直接 `setData` |
| 多端同构未做成本评估就全面推行 | 项目延期，性能不达标，团队学习成本被低估 | 只看"一套代码"的收益，忽略渲染差异与运行时开销 | 先做分层复用（`domain/` 优先），渲染层按端评估；端数 ≥ 3 且逻辑占比高时才全面同构 |
