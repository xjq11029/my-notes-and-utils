# 06-国际化与多端同构 - 导览

---

## 1.1 国际化、本地化与全球化（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | i18n（国际化，让产品具备适配多语言地区的能力）、l10n（本地化，实际适配到某个地区）、g11n（全球化，含商业与合规的整体战略）三个不同职责的概念 |
| 能做什么 | 明确"研发负责 i18n 架构、本地化团队负责 l10n 内容"的分工；避免把国际化等同于"文案翻译" |
| 怎么用 | 架构师保证"新增一种语言时不改代码"，只需新增语言包与配置；国际化必须覆盖文案、日期时间、时区、数字、货币、复数与性别、书写方向七个维度 |
| 原理和工作流程 | i18n 提供机制（消息模板、格式化 API、RTL 布局），l10n 填充内容（翻译、地区习惯） |
| 缺点 | 只做文案翻译是最常见的认知缺口，会导致日期格式不符当地习惯、金额符号错误、复数形式错误、RTL 布局错乱 |

---

## 1.2 文案管理方案（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 三种文案管理方案：JSON 文件（随代码发布）、平台化（自建文案后台）、TMS 翻译平台（Crowdin / Lokalise / Phrase / Transifex） |
| 能做什么 | JSON 文件零外部依赖、与代码同版本、回滚简单；自建平台让运营自助改文案并支持灰度；TMS 提供专业翻译工作流、翻译记忆库、术语库与质量校验 |
| 怎么用 | 演进路径：JSON 文件起步 → 语言数超过 3 种或翻译团队介入后接入 TMS → 运营需要自助改文案时再自建平台；TMS 与 CI 集成做 push/pull |
| 原理和工作流程 | 源码语言包 push 到 TMS → 翻译 → CI 构建时 pull 各语言产物 → 校验 → 构建 |
| 缺点 | JSON 文件改文案要发版且翻译人员需接触仓库；自建平台建设维护成本高；TMS 按量付费且集成需额外工程；**CI 中必须做 key 一致性、占位符一致性、空值检测三项校验** |

## 1.3 key 命名规范与分层（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | i18n key 的命名规范：语义化 + 命名空间分层（`common` / `order` / `validation`），层级 3-4 层，动词用统一词表 |
| 能做什么 | 避免"改一次文案全项目 key 失效"与"位置调整后 key 失去意义"；同一语义只保留一个 key，控制翻译成本 |
| 怎么用 | 用 `order.action.submit` 而非 `{"提交订单": "Submit"}` 或 `header.leftTopButton`；业务枚举文案约定为 `order.status.${status}`；key 一旦发布不改名，重构时保留旧 key 作别名 |
| 原理和工作流程 | 命名空间与业务模块对齐，同时作为按需加载的分包单位；页面/场景定位到二级；语义层描述含义而非"第几个按钮" |
| 缺点 | 严格规范增加初期设计成本；命名空间边界需团队共识；重复 key 与业务数据当文案是成本失控的主因 |

## 1.4 多端同构的定义与价值（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 同构（Isomorphic / Universal）指同一套代码能在不同运行环境中运行并产出结果；分 SSR 同构（服务端与浏览器）与多端同构（编译或运行到多个客户端平台）两种语境 |
| 能做什么 | 一套代码覆盖 N 端减少重复开发；业务规则与交互流程天然一致（消除"Web 修了小程序没修"）；团队技能栈统一、人力可灵活调度 |
| 怎么用 | SSR 同构用 Next.js / Nuxt / Vue SSR；多端同构用 Taro / uni-app / React Native |
| 原理和工作流程 | 共享业务代码（领域模型、校验、状态管理、请求封装）→ 各端渲染层分别实现；服务端产出 HTML + 序列化状态，浏览器注水接管 |
| 缺点 | 端数量少（= 2）时收益不明显；跨端运行时带来性能损耗；调试链路变长；框架绑定风险 |

---

## 1.5 同构的三个层次（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 同构的三个可独立选择的层次：代码复用（工具函数、常量、类型）、逻辑同构（业务规则、数据转换、状态管理）、渲染同构（UI 组件、布局、交互） |
| 能做什么 | 代码复用跨端可行性极高；逻辑同构可行性高（需抹平平台 API）；渲染同构可行性中（平台差异最大） |
| 怎么用 | **自下而上逐层推进**：先做代码复用（零风险、收益立竿见影）→ 再做逻辑同构（需设计适配层）→ 最后才考虑渲染同构 |
| 原理和工作流程 | 代码复用抽成独立 npm 包；逻辑同构抽成与框架无关的纯函数/类；渲染同构依赖跨端框架或条件编译 |
| 缺点 | 若业务逻辑写在组件里就永远无法跨端复用（呼应 03 模块"业务逻辑层不依赖 UI 框架"是逻辑同构的前提） |

## 2.1 ICU MessageFormat（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Unicode 联盟定义的国际化消息格式规范，是现代 i18n 库的通用语法基础（`intl-messageformat`、vue-i18n 消息编译器、`i18next-icu` 均实现该规范） |
| 能做什么 | 简单插值（`{name}`）、复数（`plural` + CLDR 复数类别 + `#` 占位符）、性别/分类选择（`select`）、序数（`selectordinal`）、类型化格式（skeleton），且支持嵌套 |
| 怎么用 | `{count, plural, =0 {暂无消息} other {# 条新消息}}`；`{gender, select, male {他} female {她} other {TA}}`；`{price, number, ::currency/CNY}`；用 `Intl.PluralRules` 查询某语言的复数类别 |
| 原理和工作流程 | `=0` 精确匹配优先级最高；`one`/`other` 等类别由 CLDR 按语言定义；`#` 自动替换为本地化格式的数字（含千分位） |
| 缺点 | **不同语言复数类别数量差异极大**（中文只有 `other`，英语 2 种，法语 3 种，俄语 4 种，阿拉伯语 6 种），只写 `one`/`other` 会出错；`Intl.MessageFormat` 尚非浏览器原生 API，需库提供实现 |

## 2.2 日期时间与时区处理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 时区问题的根源是 `Date` 内部为 UTC 时间戳、但多数 API 默认使用运行环境本地时区；配套 `Intl` API、Day.js、Temporal 三套方案 |
| 能做什么 | `Intl.DateTimeFormat` 按 locale 自动选格式并显式指定 `timeZone`；`Intl.RelativeTimeFormat` 输出"昨天""3天前"；`Intl.ListFormat` 做列表连接；`Intl.DisplayNames` 本地化语言名；Temporal 从类型层面分离"时刻"与"墙上时间" |
| 怎么用 | 存储 UTC → 传输 ISO 8601（带 `Z` 或偏移）→ 展示按用户时区或业务时区；Day.js 用 `utc` + `timezone` + `relativeTime` + `localizedFormat` 插件；Temporal 需 polyfill（Stage 3） |
| 原理和工作流程 | 用户时区（消息、日志）vs 业务时区（订单日期、财务报表、营业日）；判断"今天"必须用 `Intl.DateTimeFormat` 显式指定时区，`new Date().getDate()` 会在服务端与客户端得到不同结果 |
| 缺点 | Day.js 时区插件依赖 `Intl.DateTimeFormat`，在缺少完整 ICU 数据的环境（旧版 Node、部分小程序运行时）会退化或报错；严禁接口返回无时区信息的字符串 |

## 2.3 数字与货币格式化（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 用 `Intl.NumberFormat` 完成数字、百分比、货币、大数缩写、单位的本地化格式化 |
| 能做什么 | `de-DE` 下千分位是点号、小数是逗号（`1.234,56`）；货币符号位置与小数位由 locale 决定（`¥1,234.50` vs `1.234,50 €`）；日元自动 0 位小数；`notation: 'compact'` 输出"123万"或"1.2M" |
| 怎么用 | 后端返回 `{ amount: 123450, currency: 'CNY' }`，前端用 `Intl.NumberFormat` 按用户 locale 渲染；金额以最小货币单位整数传输 |
| 原理和工作流程 | 用 `resolvedOptions().maximumFractionDigits` 取得该币种的小数位，再从最小单位还原主单位，避免硬编码 `/100` |
| 缺点 | **不存在 `Intl.NumberFormat.parse`**，从本地化字符串还原数值需自行实现；金额用浮点传输会出现 `0.1 + 0.2 !== 0.3` 的对账差异；币种与 locale 是两件事（中国用户看美元应用 `zh-CN` 排版 + `US$` 符号） |

## 2.4 语言包按需加载与体积优化（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 语言包体积 = 语言数 × 文案条数（10 种语言 × 5000 条 × 60 字节 ≈ 3MB），需通过分包、懒加载、预编译等手段控制 |
| 能做什么 | 按命名空间分包（路由级 `import()`）；只内联 fallback 语言；按语言异步加载；构建期预编译消息（vue-i18n 关闭运行时编译器可减约 20-30KB）；key 压缩（减 30-50% 体积）；未使用 key 清理；SSR 按需内联；CDN 长缓存 |
| 怎么用 | `import.meta.glob('./locales/*/*.json')` 按 locale + namespace 双重懒加载；`@intlify/unplugin-vue-i18n` 配 `runtimeOnly: true` 预编译；语言包文件名带内容哈希 |
| 原理和工作流程 | 缺失命名空间时回退到 fallback 语言并上报缺失；`setLocaleMessage` 合并而非覆盖，避免丢失其他命名空间 |
| 缺点 | `runtimeOnly: true` 后无法对运行期动态拼接的字符串调用 `t()`（如后端返回消息模板）；key 压缩牺牲可读性；未使用 key 扫描易误删动态拼接的 key |

## 2.5 动态切换语言的实现（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 切换语言需要同步更新五处状态：i18n 实例的 locale、`<html lang>`、`<html dir>`、持久化存储（localStorage / Cookie）、服务端提供的文案数据 |
| 能做什么 | 无需刷新页面完成语言切换；RTL 语言自动切换布局方向；刷新后保持语言选择；后端返回的枚举文案同步更新 |
| 怎么用 | `i18n.global.locale.value = locale` → `document.documentElement.lang/dir` → Cookie 持久化（便于 SSR 读取）→ `refreshServerProvidedText()`；初始化优先级 Cookie > 浏览器语言 > 默认 |
| 原理和工作流程 | `setLocaleMessage` 加载语言包 → 切换 locale → 同步 DOM 属性 → 通知需要重拉数据的模块 |
| 缺点 | **不能缓存 `t()` 的返回值到模块级变量**（切换语言后不更新），需在渲染时调用或用 `computed`；`fallbackLocale` 兜底会导致中英混杂，应靠 CI 校验而非 fallback；路由前缀策略下切换语言需同步更新 URL |

## 2.6 SEO 与多语言（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 多语言站点的 SEO 核心是路由策略选择 + hreflang 标注 + 语言信号一致性（`html lang`、`Content-Language`） |
| 能做什么 | 子目录（`/zh-CN/`）继承主域权重、运维简单，是绝大多数场景的推荐；子域名权重独立；国家顶级域本地化信号最强但成本最高；URL 参数方式 SEO 效果最差 |
| 怎么用 | 每个页面标注全部语言版本（含自引用）+ `x-default`；sitemap 用 `xhtml:link` 标注；语言切换链接用 `<a href>` 保证可爬取 |
| 原理和工作流程 | hreflang 三条硬性规则：自引用、双向指向、语言码符合 ISO 639-1 + ISO 3166-1；违反会被忽略整组标注 |
| 缺点 | 四种必须避免的反模式：客户端 JS 跳转语言、按 `navigator.language` 自动跳转、按 Cookie 决定语言、各语言版本内容完全相同（判重复内容分散权重） |

## 2.7 RTL（从右到左）适配（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 阿拉伯语、希伯来语、波斯语、乌尔都语等从右到左书写语言的适配，核心是从"物理方向"思维切换到"逻辑方向"思维 |
| 能做什么 | 逻辑属性（`margin-inline-start`、`inset-inline-start`、`text-align: start`）让一份样式同时适配 LTR 与 RTL；`<bdi>` / `dir="auto"` 隔离混排文本 |
| 怎么用 | `document.documentElement.dir = getDirection(locale)`，方向判定用 `new Intl.Locale(locale).textInfo.direction` 并准备 RTL 语言前缀清单兜底；图标镜像用 `[dir='rtl'] .icon-directional { transform: scaleX(-1) }` |
| 原理和工作流程 | 逻辑属性随 `direction` 自动映射（`inline-start` 在 RTL 下变为右侧）；图标需分类处理 |
| 缺点 | `Intl.Locale.prototype.textInfo` 是较新 API，旧浏览器不支持必须兜底；**图标镜像要分类**（方向性图标翻转，时间/媒体/品牌/状态符号不翻转）；图表整体 `scaleX(-1)` 会导致文字镜像不可读；第三方组件库必须显式启用 RTL（Ant Design `direction="rtl"`、Element Plus 引入 RTL 样式） |

## 2.8 SSR 同构中的状态序列化与注水（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | SSR 链路：服务端渲染 HTML + 序列化已取到的数据 → 浏览器直接展示 → 加载 JS 后"注水"复用 DOM 并绑定事件 |
| 能做什么 | 避免注水时重新请求接口导致的首屏数据闪烁、重复请求、注水不匹配；首屏无需等 JS 即可见 |
| 怎么用 | 服务端 `renderToString` 后 `serialize(state, { isJSON: true })` 内联为 `window.__INITIAL_STATE__`；客户端用它初始化 store 再 `app.mount('#app')` |
| 原理和工作流程 | 服务端 `createMemoryHistory` + `router.push(url)` + `router.isReady()` → 收集状态（路由、locale、store）→ 渲染 → 序列化；客户端用同一份状态保证首次渲染结果一致 |
| 缺点 | **`JSON.stringify` 直接内联是 XSS 高危漏洞**（数据含 `</script>` 会提前闭合标签），必须用 `serialize-javascript` 或替换 `<` 为 `\u003c`；六种注水不匹配成因：时间相关、随机数、**时区差异**、**locale 差异**、浏览器 API 分支、HTML 结构非法；注水失败会丢弃服务端 HTML 重新渲染 |

## 2.9 路由同构设计（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 同一份路由表 + 不同的 history 实现：Vue 用 `createMemoryHistory()`（服务端）/ `createWebHistory()`（客户端）；React 用 `<StaticRouter>` / `<BrowserRouter>` |
| 能做什么 | 路由定义只维护一份；路由级数据预取抽象为与渲染环境无关的接口，服务端预取的数据写入 store 后客户端直接复用 |
| 怎么用 | `createAppRouter(history)` 工厂函数供两个入口调用；Vue 用 `onServerPrefetch` + `onMounted` 判断"store 是否已有数据"；React Router 6 用 `loader`；Nuxt 3 用 `useAsyncData` |
| 原理和工作流程 | 服务端 `router.push(url)` → `await router.isReady()` → 等待异步路由解析 → 渲染；客户端注水后接管路由 |
| 缺点 | 守卫中不能访问 `window` / `document`（服务端会执行）；守卫必须幂等（两端都执行，不能有重复上报等副作用）；重定向必须在服务端完成（返回 302 而非渲染跳转页）；权限校验不能只靠守卫，数据权限仍须后端保证 |

## 2.10 平台差异抹平（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 三种手段：适配层（Adapter，运行时）、条件编译（编译期）、运行时探测（运行时兜底） |
| 能做什么 | 适配层让业务代码只依赖 `IPlatform` 接口，差异全部收敛在 `platform/*` 实现中；条件编译零运行时开销；运行时探测无需构建配置 |
| 怎么用 | 适配层抽象 `IStorage` / `INavigator` / `IToast` / `IPlatform`；Taro 用 `process.env.TARO_ENV`，uni-app 用 `#ifdef` / `#ifndef` / `#endif` 注释指令；运行时探测用 `typeof wx !== 'undefined'` |
| 原理和工作流程 | **优先级：适配层 > 条件编译 > 运行时探测**；差异应尽量前移到编译期（不占运行时体积、无分支开销） |
| 缺点 | 适配层需抽象设计且多一层间接调用；条件编译降低可读性且被剔除分支不做类型检查（建议块内只放平台 API 调用）；运行时探测有开销且难以静态分析、无法 tree-shaking，只作兜底 |

## 2.11 Taro / uni-app 的架构实现思路（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 两者都采用"编译时 + 运行时"混合方案：Taro（京东，React/Vue 可选）与 uni-app（DCloud，Vue 基础） |
| 能做什么 | Taro 用 `@tarojs/runtime` 提供 DOM/BOM 模拟层，让 React 直接运行在小程序 JS 环境中，产出 Taro DOM Tree 后 diff 并通过 `setData` 同步到视图层；uni-app 用编译器按平台条件编译剔除代码，配 `uni.*` 统一 API 层 |
| 怎么用 | Taro 3 之后不再把 React 组件编译为小程序模板（Taro 1/2 的做法），而是"重运行时"方案；uni-app 用 `@dcloudio/uni-cli-shared` 编译到各端，App 端支持原生渲染，uni-app x 用 UTS 编译为原生代码 |
| 原理和工作流程 | 编译期剔除代码 → 运行时承接渲染结果 → 跨线程通信同步差异；框架只能收敛差异，无法让"小程序有的能力"在 Web 上出现 |
| 缺点 | 小程序逻辑层与视图层是两个线程，`setData` 跨线程通信数据量越大越慢（需列表分页、只传最小变更、避免高频事件中直接 `setData`）；框架升级受制于框架方；平台 API 覆盖不一致 |

## 2.12 多端同构的成本与收益评估（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 从收益与成本两侧评估多端同构是否适合当前项目 |
| 能做什么 | 收益：端数 ≥ 3 时可减少 50-70% 前端工作量、一致性提升、迭代速度加快、人力弹性；成本：学习成本、跨端运行时性能损耗、各端调试成本、生态兼容不确定、框架绑定、平台能力缺口 |
| 怎么用 | 决策矩阵：端数 ≥ 3 且逻辑占比高 → 适合；端数 = 2 且交互复杂（动画/手势/富文本编辑）→ 分别开发更划算；性能敏感（长列表、音视频编辑）→ 关键页面用原生实现；已有成熟多端代码库 → 逐步抽取逻辑同构层不做整体重写 |
| 原理和工作流程 | **核心判断标准：收益来自"逻辑复用"，成本来自"渲染差异"**；业务逻辑占比高（订单、审批、表单类）收益显著；交互与视觉是核心竞争力（内容创作、游戏化）时收益被渲染差异吃掉 |
| 缺点 | 成本项容易被低估（尤其调试成本与生态兼容）；团队无跨端经验且周期紧张时不应在同构上做技术冒险 |

## 3.1 国际化完整配置（vue-i18n + Vite）（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 `createI18n` + Vite 的完整国际化配置：语言包懒加载、命名空间合并、`setLocale` 统一切换入口、组件内 `Intl` 格式化 |
| 能做什么 | 主包只内联 fallback 语言；按 locale + namespace 双重懒加载并缓存已加载命名空间；切换语言同步更新 `html lang` / `dir` / Cookie |
| 怎么用 | `createI18n({ legacy: false, globalInjection: true, fallbackLocale: 'zh-CN', messages: { 'zh-CN': zhCN } })`；`loadMessages` 用 `setLocaleMessage` 合并；组件内用 `computed` 包裹 `Intl.DateTimeFormat` / `Intl.NumberFormat` 以响应 locale 变化 |
| 原理和工作流程 | `legacy: false` 启用组合式 API 模式；`loadedNamespaces` Map 避免重复加载；日期与金额格式化显式指定 `timeZone: 'Asia/Shanghai'` |
| 缺点 | 需处理语言包加载失败的回退；`missingWarn` / `fallbackWarn` 需按环境开关，生产环境应关闭以避免告警刷屏 |

## 3.2 CI 中的语言包校验（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 在 CI 中运行的 Node 脚本，校验所有语言的 key 一致性、空值、ICU 占位符一致性 |
| 能做什么 | 拦截"缺失 key 导致中英混杂""空文案静默覆盖 fallback""占位符改名导致运行期报错"三类问题 |
| 怎么用 | `flatten()` 把嵌套 JSON 扁平化为 `a.b.c` key 集合；`extractPlaceholders()` 用正则提取 ICU 变量名；对比基准语言（`zh-CN`）与目标语言的差异，发现问题 `process.exit(1)` |
| 原理和工作流程 | 遍历 `src/locales/*/` 下所有命名空间 → 与基准语言对比 key 集合、值是否为空、占位符集合是否一致 → 汇总错误并阻断构建 |
| 缺点 | 正则提取占位符是简化实现，复杂嵌套消息可能有误判；动态拼接的 key（如 `order.status.${status}`）无法静态校验，需额外维护枚举清单 |

## 3.4 SSR 状态序列化与注水（Nuxt / Next.js 对照）（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Vue 3 SSR 完整数据流（`entry-server` + `entry-client`）与 React 18 / Next.js App Router 的对照实现 |
| 能做什么 | 服务端按 `Accept-Language` 确定 locale 并写入序列化状态；客户端直接使用服务端的 locale 而非自行探测，消除注水不匹配 |
| 怎么用 | 服务端 `render(url, locale)` 返回 `{ html, state }`，state 含 `route` / `locale` / `pinia`；客户端 `pinia.state.value = state.pinia`、`i18n.global.locale.value = state.locale` 后再 `mount` |
| 原理和工作流程 | Next.js 侧：Server Component 在服务端完成时间格式化并把结果字符串传给 Client Component，客户端不再做时间格式化 |
| 缺点 | **国际化 + SSR 的核心原则**：所有依赖 locale / timeZone 的格式化，要么在服务端完成并传结果字符串，要么两端显式使用同一套配置；让两端各自"自动探测"是注水不匹配的首要原因 |

## 3.5 多端同构实战（Taro + 适配层）（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 分层目录结构（`platform/` 适配层、`domain/` 领域逻辑、`services/` 业务服务、`pages/` 页面）+ 条件编译处理平台专有能力 |
| 能做什么 | `domain/` 纯函数可在任意端运行并可在 Node 中单元测试；`services/` 只依赖 `IPlatform` 接口；`pages/` 用条件编译处理订阅消息等平台专有能力 |
| 怎么用 | `platform/*.ts` 各端实现 `IStorage` / `INavigator` / `IToast`；小程序 Storage 同步 API 包装为 Promise 统一接口；条件编译块保持极短，只放平台 API 调用 |
| 原理和工作流程 | 分层复用比例（经验值）：`domain/` 100%、`services/` 90%+、`platform/` 0%（本身即差异）、`pages/` 50-80% |
| 缺点 | 适配层接口越多各端实现成本越高、越容易不一致；小程序与 Web 的组件能力差异仍需在页面层用条件编译处理 |

## 3.6 国际化与多端同构的结合（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 多端场景下的三个特殊问题：语言包体积（小程序主包上限）、语言分发（各端产物格式不同）、语言判定（小程序无法读 `Accept-Language`，App 用系统语言 API） |
| 能做什么 | 语言判定统一收敛到适配层的 `getSystemLocale()`；TMS 平台配置多端导出、CI 按端拉取；SSR 首屏只内联当前语言包避免 FOUC |
| 怎么用 | 小程序用 `Taro.getSystemInfoSync().language` 并归一化格式；服务端用 `Negotiator` 解析 `Accept-Language` + `@formatjs/intl-localematcher` 的 `match` 做近似匹配；客户端用内联的 `window.__I18N__` 直接初始化 |
| 原理和工作流程 | 加载策略：SSR 首屏只内联当前语言 → 浏览器切换语言时动态 `import()` → 小程序按分包拆分语言包 → App 语言包随版本内置 + 热更新 → 所有端语言包文件名带内容哈希走 CDN 长缓存 |
| 缺点 | 内联语言包会增大 HTML 体积（若 > 100KB 应改为"内联首屏关键命名空间 + 其余懒加载"）；HTML 需设 `no-cache` 或短缓存，否则语言包更新后用户拿到旧 HTML |
