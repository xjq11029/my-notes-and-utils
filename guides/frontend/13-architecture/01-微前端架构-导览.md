# 01-微前端架构 - 导览

---

## 1.1 什么是微前端（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 微前端是一种将单一前端应用拆分为多个独立子应用、由主应用统一管理的架构模式，借鉴了后端微服务思想 |
| 能做什么 | 解决巨石应用难以维护、构建缓慢、多团队协作冲突、技术栈锁定等问题；支持多技术栈共存、独立部署、增量升级 |
| 怎么用 | 引入 qiankun / Module Federation / wujie / micro-app 等方案，主应用负责路由分发，子应用暴露生命周期函数 |
| 原理和工作流程 | 主应用注册子应用配置（name、entry、container、activeRule）→ 路由匹配时加载子应用资源 → 子应用执行 bootstrap → mount → 沙箱隔离 → 卸载时执行 unmount |
| 缺点 | 架构复杂度增加；首屏加载可能变慢；子应用间通信比单体应用复杂；调试和排错难度上升 |

---

## 1.2 四种主流方案对比（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | qiankun（阿里）、Module Federation（Webpack 5）、wujie（腾讯）、micro-app（京东）是当前最主流的四种微前端实现方案，各有侧重 |
| 能做什么 | qiankun 适合存量系统改造和多技术栈共存；Module Federation 适合全新项目追求极致性能；wujie 适合快速接入和强隔离场景；micro-app 适合对 WebComponent 规范的轻量接入 |
| 怎么用 | qiankun 通过 registerMicroApps + start 接入；MF 通过 ModuleFederationPlugin 配置；wujie 通过 setupApp + preloadApp 接入；micro-app 通过 `<micro-app>` 标签式声明接入 |
| 原理和工作流程 | qiankun 基于 JS Proxy 沙箱 + CSS 隔离；MF 基于 Webpack 运行时共享模块；wujie 基于 iframe + WebComponent 双保险；micro-app 基于 CustomElement + Shadow DOM 隔离 |
| 缺点 | qiankun 沙箱有性能开销且 CSS 隔离不完美；MF 无内置沙箱隔离需团队规范约束；wujie 的 iframe 内存开销较大；micro-app 的 Shadow DOM 兼容性有限且对复杂样式穿透要求高 |

---

## 1.3 核心术语（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 微前端架构中的核心术语包括：主应用、子应用、沙箱隔离、应用间通信、生命周期（bootstrap / mount / unmount） |
| 能做什么 | 主应用管理路由和生命周期；子应用承载独立业务；沙箱保障隔离安全；通信实现跨应用数据流转 |
| 怎么用 | 主应用调用 registerMicroApps 注册子应用；子应用导出 bootstrap/mount/unmount 函数；沙箱通过 start 配置开启 |
| 原理和工作流程 | 主应用根据 activeRule 路由分发 → 子应用在沙箱中挂载到指定容器 → 通过 props 或 eventBus 通信 → 卸载时清理资源 |
| 缺点 | 生命周期约定增加了子应用改造成本；通信机制与框架耦合；沙箱可能影响部分第三方库的正常运行 |

## 2.1 qiankun 的 JS Proxy 沙箱与 CSS 隔离原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | qiankun 通过 Proxy 创建 window 对象的代理，拦截子应用对全局变量的读写；CSS 隔离通过 Shadow DOM 或样式前缀实现 |
| 能做什么 | 阻止子应用对全局 window 变量的污染（如修改 document.title、添加全局事件监听），避免子应用间样式冲突 |
| 怎么用 | 在 start() 中配置 sandbox 选项；子应用在沙箱环境下执行，修改的是 fakeWindow 而非真实 window |
| 原理和工作流程 | ProxySandbox 创建 fakeWindow → 子应用代码在 fakeWindow 中执行 → 激活时将修改同步到 window → 失活时恢复 window 原值 |
| 缺点 | ProxySandbox 无法拦截直接对 window 属性的赋值（需配合 with 语句）；strictStyleIsolation 会导致弹窗组件挂载到 body 时失效 |

---

## 2.2 Module Federation 的 shared 依赖共享与 singleton 机制（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Module Federation 是 Webpack 5 内置的模块联邦功能，通过 shared 配置实现多应用间的依赖共享，singleton 确保全局唯一点 |
| 能做什么 | 避免重复加载相同依赖（如 react、react-dom）；通过 singleton 解决多实例冲突（hooks 错误、context 断裂） |
| 怎么用 | 在 ModuleFederationPlugin 的 shared 中配置 `{ singleton: true, requiredVersion: '^18.0.0' }` |
| 原理和工作流程 | 主应用初始化共享依赖 → 子应用 remoteEntry.js 加载时检测共享作用域 → 若已存在则直接复用，否则按需加载 → 版本协商取最高版本 |
| 缺点 | 无 JS/CSS 沙箱隔离，依赖团队规范；版本不匹配时仅警告不阻止；配置复杂度随子应用数量增加 |

---

## 2.3 wujie 的 iframe + WebComponent 双保险隔离原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | wujie 将子应用 JS 放在隐藏 iframe 中执行（利用 iframe 的天然隔离），DOM 渲染通过劫持操作同步到主应用的 WebComponent 容器中 |
| 能做什么 | 提供比 qiankun Proxy 沙箱更彻底的 JS 隔离（iframe 独立 window 上下文），同时保留 DOM 在主应用中的灵活性 |
| 怎么用 | 调用 setupApp 配置全局参数 → preloadApp 预加载子应用 → 使用 WujieVue 组件挂载子应用 |
| 原理和工作流程 | 创建隐藏 iframe 加载子应用 → 获取 iframe 的 contentWindow 作为沙箱 → 劫持 appendChild 等 DOM 操作 → 将渲染结果同步到主应用容器 |
| 缺点 | iframe 内存开销较大；DOM 操作劫持可能有兼容性问题；白屏时间比纯 JS 方案略长 |

---

## 2.4 micro-app 的类 WebComponent 隔离原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | micro-app（京东）借鉴 WebComponent 思想，通过 CustomElement 将子应用封装为 `<micro-app>` 标签，利用 Shadow DOM 实现样式隔离和 DOM 隔离 |
| 能做什么 | 提供类 `<iframe>` 的隔离体验但无 `<iframe>` 的性能问题；支持标签式声明接入（`<micro-app name='app1' url='//xxx.com'></micro-app>`）；兼容多种框架（Vue/React/Angular/JQuery） |
| 怎么用 | 安装 `@micro-zoe/micro-app` → 主应用引入 → 使用 `<micro-app>` 标签声明子应用 → 配置 url、baseroute 等属性 |
| 原理和工作流程 | 子应用资源加载 → 在 CustomElement 内创建隔离的 DOM 环境 → 通过 Shadow DOM 隔离样式 → 通过 Proxy 沙箱隔离 JS 全局变量 → 路由同步通过 baseroute 与主应用协作 |
| 缺点 | Shadow DOM 兼容性有限（不支持 IE 11）；样式穿透需要 `::part()` 或 CSS 变量；复杂样式（如全局 CSS 框架）需要额外处理；生态相对较新（历史兼容场景，2026 年新项目按现代浏览器基线） |

---

## 2.5 应用间通信机制对比（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 主子应用之间通过 globalState（qiankun 发布-订阅）、Custom Events（浏览器原生事件）、共享模块（EventBus / zustand）三种方式通信 |
| 能做什么 | 实现登录态同步、主题切换、购物车数据共享、跨应用事件通知等跨应用数据流转 |
| 怎么用 | globalState 通过 initGlobalState + onGlobalStateChange；Custom Events 通过 dispatchEvent + addEventListener；共享模块通过 window.eventBus |
| 原理和工作流程 | globalState 基于内部状态池 + 订阅回调；Custom Events 基于浏览器事件循环；共享模块基于单例挂载到全局作用域 |
| 缺点 | globalState 耦合 qiankun；Custom Events 类型不安全、调试困难；共享模块需注意命名冲突和内存泄漏 |

## 3.1 qiankun 接入实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 qiankun 主应用（Vue 3）+ 子应用（Vue 2）接入流程，包含注册、生命周期、样式隔离、异常处理 |
| 能做什么 | 快速将现有 Vue 2 项目改造为 qiankun 子应用，接入 Vue 3 主应用，实现微前端架构 |
| 怎么用 | 主应用：registerMicroApps 注册 → start 启动；子应用：暴露 bootstrap/mount/unmount → 配置 webpack output.library |
| 原理和工作流程 | 主应用路由匹配 activeRule → 加载子应用 entry 资源 → 子应用在沙箱中执行 bootstrap → mount 到 container → 卸载时执行 unmount 清理 |
| 缺点 | 子应用需要改造 webpack 配置（output.library/libraryTarget）；CORS 配置必不可少；publicPath 需要动态设置 |

## 3.2 Module Federation 实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 Rspack 的 Module Federation 完整配置，包含 Host 主应用和 Remote 子应用的 shared 依赖共享 |
| 能做什么 | 实现多个独立构建的 React 应用共享依赖，减少重复加载，提升性能 |
| 怎么用 | Host 配置 remotes 指向子应用 remoteEntry.js；Remote 配置 exposes 暴露模块；shared 配置 singleton 依赖 |
| 原理和工作流程 | Host 构建时记录 remote 地址 → 运行时按需加载 remoteEntry.js → 检测 shared 依赖版本 → 复用或降级加载 |
| 缺点 | 需要同技术栈（React/React 或 Vue/Vue）；类型声明需手动维护；远程模块加载失败需要降级处理 |

## 3.3 wujie 接入实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 wujie 和 wujie-vue3 的完整接入流程，包含保活模式、预加载、应用间通信 |
| 能做什么 | 零改造接入现有子应用，支持保活模式保持子应用状态，实现跨域子应用加载 |
| 怎么用 | setupApp 全局配置 → preloadApp 预加载 → WujieVue 组件挂载 → bus 通信 |
| 原理和工作流程 | 预加载时创建 iframe 加载子应用 → 路由匹配时激活子应用 → 劫持 DOM 操作同步到容器 → 保活模式下隐藏而非销毁 |
| 缺点 | 保活模式消耗更多内存；iframe 跨域限制可能影响某些功能；生态较新文档不够完善 |

## 3.4 micro-app 接入实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 micro-app 的完整接入流程，包含 Vue 3 主应用 + React 子应用的标签式声明接入 |
| 能做什么 | 通过 `<micro-app>` 标签零改造接入 React 子应用，支持数据通信、路由同步和生命周期管理 |
| 怎么用 | 安装 `@micro-zoe/micro-app` → 主应用 `import microApp from '@micro-zoe/micro-app'` → `microApp.start()` 启动 → 使用 `<micro-app name='react-app' url='http://localhost:3001/'></micro-app>` 声明子应用 |
| 原理和工作流程 | 主应用启动时初始化 micro-app → 渲染 `<micro-app>` 标签时加载子应用 → 通过 fetch 获取子应用 HTML → 在 Shadow DOM 中渲染 → 通过 `microApp.setData()` 和 `@DataChange` 事件通信 |
| 缺点 | 子应用需确保资源路径正确（使用相对路径或配置 publicPath）；Shadow DOM 样式隔离可能影响第三方 UI 库；复杂场景下需要处理样式穿透 |
