## 1.1 BFF 的定义与解决的问题（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | BFF（Backend For Frontend）是为每一种前端客户端提供专属的后端服务层，位于客户端与后端微服务之间，由 Sam Newman 系统化提出、源自 SoundCloud 实践 |
| 能做什么 | 解决多端数据聚合（多次 RTT 合并为一次）、接口裁剪（只返回前端需要的字段）、协议转换（gRPC/SOAP → REST/GraphQL）、变更隔离（后端升级不阻塞客户端发版） |
| 怎么用 | 前端团队为每个端（Web / App / 小程序）维护一个 Node 服务，聚合下游微服务数据后按端形态返回 |
| 原理和工作流程 | 客户端请求 → BFF 并行调用多个下游 → 聚合并裁剪字段 → 返回客户端专属结构；BFF 属于客户端，遵循客户端发布节奏 |
| 缺点 | 多一层服务增加运维与排查成本；服务数量随端数增长；团队若缺乏 Node 运维能力会引入新的稳定性风险 |

---

## 1.2 BFF 与 API Gateway 的职责边界（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | API Gateway 负责南北向流量的安全与治理，BFF 负责面向特定客户端的数据编排，两者关注点完全不同、通常同时存在 |
| 能做什么 | Gateway 提供统一鉴权、限流熔断、灰度路由、TLS 终止、IP 黑白名单；BFF 提供数据聚合、字段裁剪、协议转换、客户端专属缓存 |
| 怎么用 | 链路为 `客户端 → CDN/边缘 → API Gateway → BFF → 微服务`；Gateway 做身份认证，BFF 做数据权限收敛 |
| 原理和工作流程 | Gateway 做通用横切（不懂业务、低频变更、归基础设施团队）；BFF 做业务编排（懂业务、高频变更、归前端团队） |
| 缺点 | 边界容易被侵蚀：限流、黑白名单等能力若搬进 BFF，BFF 会退化成"第二个网关"，职责失控 |

---

## 1.3 BFF 的部署形态与粒度（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | BFF 的三种粒度：按端拆分（纵向）、按业务域拆分（横向）、端 × 域 二维矩阵 |
| 能做什么 | 按端拆分适合端间数据形态差异大的场景；按域拆分与后端微服务边界对齐；矩阵形态满足大型组织双重诉求 |
| 怎么用 | 按团队规模选型：< 10 人前端可用单个 BFF 甚至不引入；10-30 人按端拆；30-100 人按端为主 + 域内聚合；100+ 人用矩阵 + 统一脚手架 |
| 原理和工作流程 | 服务数量 = 端数 × 域数（矩阵形态），实践中常用 `X-Client-Type` 请求头让一个服务承载多端来降本，代价是内部维护多套响应适配 |
| 缺点 | 端数量增长时服务线性增长，登录/埋点等公共逻辑容易复制多份；矩阵形态运维成本最高 |

## 1.4 前端网关与流量治理（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | "前端网关"是 BFF 再往前的流量入口，由 CDN + Nginx / 边缘运行时共同承担，负责路由分发、灰度、鉴权前置、限流、静态加速、A/B 实验 |
| 能做什么 | 按路径/域名/请求头分流；按用户或设备哈希做灰度；边缘校验 Token 减少回源；按 IP/UID/租户限流 |
| 怎么用 | Nginx 用 `location` 路由、`map` 映射后端、`split_clients` 灰度；边缘用 Cloudflare Workers / Vercel Edge / Next.js Middleware 写路由重写与个性化注入 |
| 原理和工作流程 | 请求到达边缘 → 识别语言/租户/灰度分组 → 重写路由或注入信息 → 回源到 BFF；灰度按稳定标识哈希取模保证用户粘性 |
| 缺点 | 边缘运行时是 V8 Isolate 而非完整 Node.js，不支持 `fs`、原生 `net` 与多数原生模块，能力受平台限制且各平台不一致 |

## 1.5 权限模型：RBAC / ABAC / ReBAC（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 三种主流权限模型：RBAC（用户→角色→权限，分 RBAC0/1/2/3 四级）、ABAC（主体/资源/操作/环境属性 + 策略表达式）、ReBAC（关系元组 `资源#关系@主体`） |
| 能做什么 | RBAC 简单直观，适合绝大多数后台管理系统；ABAC 表达能力强，支持时间/地域/密级等维度且策略可动态下发；ReBAC 天然支持共享、继承与嵌套 |
| 怎么用 | 后台管理选 RBAC；强合规场景用 ABAC（OPA/Rego、AWS Cedar、CASL）；协作类产品用 ReBAC（Zanzibar 论文、OpenFGA、SpiceDB）；混合场景 RBAC 管"能不能进"、ABAC/ReBAC 管"能看哪些数据" |
| 原理和工作流程 | RBAC 靠角色-权限两张关联表；ABAC 靠策略引擎对属性组合求值；ReBAC 靠关系图查询回答"谁能访问这个资源" |
| 缺点 | RBAC 易角色爆炸（组合需求增多时角色数指数增长）；ABAC 策略编写调试门槛高、判定成本高且难反查；ReBAC 需引入图存储与关系查询，架构复杂度显著上升 |

## 1.6 前端权限的四个层次（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端权限的四个层次：路由级（页面能否进入）、菜单级（导航项是否展示）、按钮级（操作是否可用）、数据级（能看到哪些数据） |
| 能做什么 | 无权限页面直接跳 403 而非"能进去但报错"；不展示点了就失败的入口；敏感字段不渲染 |
| 怎么用 | 路由级用动态路由 + 全局前置守卫；菜单级由过滤后的路由表派生；按钮级用指令/组件/Hook；数据级用后端字段脱敏 + 行级过滤 |
| 原理和工作流程 | 登录 → 拉取权限码集合 → 过滤路由表 → 动态注册 → 生成菜单 → 按钮/数据层按权限码判定 |
| 缺点 | 四个层次全部可被绕过（改内存、改 DOM、重放请求），只能作为用户体验优化，不能作为安全边界 |

## 1.7 前端权限不可信原则（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 任何来自客户端的权限声明都不可信，越权防护必须由后端在每个数据接口上完成；前端权限只是"建议"而非"边界" |
| 能做什么 | 唯一可信的是后端签发并验签的 Token；前端权限的作用是降低用户困惑与减少无效请求 |
| 怎么用 | userId 只从 Token 取，绝不信任 query/body/URL；单资源查询把归属条件合并进 `where`；资源不存在与无权访问统一返回 404 |
| 原理和工作流程 | 篡改 JWT Payload 会因签名校验失败被拒（前端能防住）；但改内存权限数组、删 DOM、用 curl 重放请求前端无法防（必须后端防） |
| 缺点 | 越权漏洞的两种类型：水平越权（同角色访问他人数据，典型形态 IDOR）与垂直越权（低权限执行高权限操作），两者都只能靠后端拦截 |

---

## 1.8 权限与多租户（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | SaaS 场景下租户隔离是比用户权限更前置的一层约束，三种模式：独立数据库、共享库独立 Schema、共享库共享表 + `tenant_id` |
| 能做什么 | 保证 A 租户用户无法访问 B 租户数据；隔离强度从高到低、成本从高到低 |
| 怎么用 | 租户 ID 由边缘按域名映射推导并覆盖客户端传入的同名头；ORM 中间件或数据库 RLS 强制注入租户条件；缓存 Key 统一格式 `tenant:{tid}:...` |
| 原理和工作流程 | 客户端传路由信息（子域名）→ 边缘映射出租户 ID 并注入 `X-Tenant-Id` → 网关校验 → BFF 透传 → 数据访问层自动叠加租户条件 |
| 缺点 | 共享表模式最省成本但最依赖代码正确性，任一查询漏写 `tenant_id` 即造成跨租户泄露；`AsyncLocalStorage` 等上下文透传机制增加调试难度 |

## 2.1 BFF 数据聚合的并行编排与部分失败（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | BFF 用 `Promise.all` 将串行累加的耗时压缩为最大值，并按数据重要程度区分"关键数据"与"非关键数据"做分级降级 |
| 能做什么 | 5 个下游各 200ms 的聚合从 1000ms 降到 200ms；避免"优惠券服务抖动导致整个首页白屏" |
| 怎么用 | 关键数据用 `await` 或 `Promise.all`（失败即整体失败）；非关键数据用 `Promise.allSettled` 各自兜底；响应中显式返回 `degraded: ['coupons']` 标记 |
| 原理和工作流程 | 并行发起请求 → `allSettled` 收集每个 Promise 的 `fulfilled`/`rejected` 状态 → 失败字段返回默认值并记录降级标记 → 前端据标记区分"暂无数据"与"加载失败" |
| 缺点 | `allSettled` 会掩盖下游异常，需配合监控告警；`Promise.race` 实现的超时只是"放弃等待"，被放弃的请求仍在进行，必须用 `AbortSignal.timeout` 真正取消 |

## 2.2 BFF 的缓存与降级策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | BFF 是缓存的最佳落点（既了解客户端诉求又贴近下游），支持"缓存聚合结果"与"缓存下游单点结果"两种粒度，并配套四级降级策略 |
| 能做什么 | `stale-while-revalidate` 消除缓存过期瞬间的延迟尖峰；`stale-if-error` 让下游故障时页面仍可用；分片缓存避免"最易变字段拖累整体缓存" |
| 怎么用 | 公共数据 `public, max-age=60, s-maxage=300, stale-while-revalidate=600`；用户私有数据 `private, max-age=30`；敏感数据 `no-store` |
| 原理和工作流程 | 四级降级：L1 局部降级（字段兜底）→ L2 缓存降级（返回过期缓存）→ L3 静态降级（预生成兜底 JSON）→ L4 熔断（快速失败避免雪崩）；熔断器状态机 CLOSED → OPEN → HALF_OPEN |
| 缺点 | 分片缓存实现复杂度高；用户私有接口若漏设 `private` 且 CDN 忽略 Cookie 缓存，会导致跨用户数据泄露（上线最常见的高危问题） |

## 2.3 GraphQL 作为 BFF 的实践与取舍（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | GraphQL 让客户端精确声明所需数据、服务端一次返回，定位与 BFF 高度重合，因此"GraphQL 即 BFF"是常见架构 |
| 能做什么 | 客户端自由选择字段（BFF 无需改动）、同一 Schema 适配多端、单次请求拿到整棵数据树、Schema 即契约可自动生成 TS 类型 |
| 怎么用 | 用 DataLoader 解决 N+1；用 `graphql-depth-limit` + `graphql-validation-complexity` 限制深度与复杂度；用 APQ 把 POST 转成可缓存的 GET；前端显式检查 `errors` 数组 |
| 原理和工作流程 | DataLoader 在同一 tick 内合并多个 `load` 为一次批量调用并做请求级缓存；APQ 首次发完整查询换 hash、后续只发 hash，服务端按 hash 查缓存并形成白名单 |
| 缺点 | 学习成本高（Schema 设计、Resolver、性能治理）；单一 POST 端点使 HTTP 缓存基本失效；恒返回 200 使错误语义藏在 `errors` 中；无性能治理能力时不应选用 |

## 2.4 动态路由与权限路由的实现原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 把"路由表"从静态常量变为运行时按权限计算出的结果：登录 → 拉权限 → 过滤路由表 → 动态注册 → 生成菜单 |
| 能做什么 | 无权限页面地址直接跳 403；菜单自动只展示可访问项；三种形态可选（后端返回路由表 / 前端全量路由 + 权限码过滤 / 混合模式） |
| 怎么用 | Vue 用 `router.addRoute()` + 全局守卫；React Router 6 无 `addRoute`，改用状态驱动路由表（权限拉取完成后 `setRoutes` 让 `<Routes>` 重新渲染） |
| 原理和工作流程 | 守卫中判断"已登录但未初始化权限"→ 拉权限码 → 递归过滤 `asyncRoutes`（父路由无权限则整棵子树丢弃）→ `addRoute` 注册 → 返回 `{ ...to, replace: true }` 重新导航 |
| 缺点 | `addRoute` 后必须重新导航否则命中 404；登出必须移除动态路由否则切号残留；刷新页面丢失动态路由需重走守卫；404 通配路由必须最后注册 |

## 2.5 权限指令与权限组件的封装原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 按钮级权限的三种封装形态：指令（Vue `v-permission`）、组件（`<Auth code="...">`）、Hook/Composable（`usePermission`），本质都是"读权限码 → 判定 → 决定渲染/禁用" |
| 能做什么 | 指令写法最简但无法参与条件渲染表达式；组件可组合、可传 fallback（无权限时展示禁用按钮而非隐藏）；Hook 可在逻辑中使用并参与计算 |
| 怎么用 | Vue 3 指令在 `mounted` 钩子中 `el.parentNode.removeChild(el)`；组件用 `<slot>` / `<slot name="fallback">`；React 用 `useAuthStore` + 条件渲染；权限码统一 `{域}:{资源}:{操作}` 三段式 |
| 原理和工作流程 | 权限码集合（`Set`）→ 支持 `all`/`any` 两种判定模式 → 指令做破坏性 DOM 移除、组件做条件渲染、Hook 返回布尔值供逻辑使用 |
| 缺点 | 指令的 `removeChild` 是破坏性操作，权限动态变化时元素无法恢复，仅适合会话内权限不变的场景；权限码命名若不统一会前后端漂移 |

## 2.6 前端权限数据的获取与缓存策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 权限数据的四种获取方式：登录响应内联、独立权限接口、Token 内嵌权限码、Token 内嵌版本号 |
| 能做什么 | 内联方式少一次 RTT；独立接口职责清晰；内嵌权限码服务端无状态；内嵌版本号让 Token 体积小且权限可即时失效 |
| 怎么用 | 推荐组合：Token 只放 `userId` + `tenantId` + `permVersion`；权限清单由 `GET /api/me/permissions` 返回并缓存在 Redis，权限变更时递增版本号让缓存失效 |
| 原理和工作流程 | 启动时比对 `permVersion` → 不一致则重新拉取 → 权限清单以 `{ userId, permissions }` 形式存入内存（Pinia/Redux）→ 403 响应视为"权限过期"信号触发重拉 |
| 缺点 | 权限码全塞进 JWT 会让 Token 超过 8KB 被网关拒绝且变更需等过期；持久化到 localStorage 后长期不刷新会让被回收权限的用户仍看到入口 |

## 3.1 BFF 聚合接口完整实现（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 Fastify 的完整聚合接口：关键数据直取、非关键数据并行兜底、降级标记暴露、缓存头设置、健康检查 |
| 能做什么 | 首页一次请求拿到用户、订单、优惠券、运营位；下游部分故障时页面仍可渲染并提示具体模块失败 |
| 怎么用 | `request.user.userId` 取身份（绝不从 query 取）→ `await` 关键数据 → `Promise.allSettled` 非关键数据 → 收集 `degraded` 数组 → `Cache-Control: private, max-age=30` |
| 原理和工作流程 | 身份从已验签 Token 提取 → 并行调用下游 → 按端裁剪字段（去掉 phone/email）→ 标记降级 → 返回固定结构 |
| 缺点 | 需为每个聚合接口单独设计降级策略；`degraded` 标记需前端配合处理，否则形同虚设 |

## 3.2 BFF 请求合并与缓存（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 用 DataLoader 在同一请求内合并重复的下游调用（如首页 5 个卡片都要作者昵称） |
| 能做什么 | 10 次单点用户查询合并为 1 次批量查询，并附赠请求级缓存 |
| 怎么用 | 写 `createLoaders(clients)` 工厂函数，在 `onRequest` 钩子中挂到请求上下文，请求结束随上下文回收 |
| 原理和工作流程 | 同一事件循环 tick 内的多个 `load(key)` 被合并 → 批量调用下游 → 返回数组顺序必须与入参严格一致，缺失位置补 `null` |
| 缺点 | **绝不能做成模块级单例**：单例的请求级缓存跨请求存活会导致 A 用户拿到 B 用户数据（跨用户数据泄露） |

## 3.3 Vue 3 完整权限体系实现（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 Pinia + Vue Router 4 的完整权限体系：权限码集合、`hasPermission` 判定、动态路由注册、登出清理、401/403 拦截 |
| 能做什么 | 登录后按权限注册动态路由并生成菜单；按钮级权限复用同一判定逻辑；登出后彻底清理防止切号残留；403 触发权限自愈重拉 |
| 怎么用 | `useAuthStore` 提供 `token`/`permissions`/`routesLoaded`/`hasPermission`/`registerRoutes`/`reset`；守卫中"首次"拉权限并注册路由；响应拦截器处理 401（登出）与 403（重拉权限） |
| 原理和工作流程 | 守卫检查 token → 未初始化则 `fetchPermissions` + `filterRoutes` + `addRoute` → `return { ...to, replace: true }` 重新导航；保存 `addRoute` 返回的移除函数供 `reset` 调用 |
| 缺点 | 动态路由仅存在于内存，刷新需重走守卫流程；`routesLoaded` 若持久化需同步持久化路由表并恢复，实现复杂度上升 |

## 3.4 前端网关配置（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Nginx 配置示例：`map` 按租户子域名映射后端集群、`split_clients` 按设备 ID 哈希做灰度分流、边缘注入租户标识、静态资源与 HTML 差异化缓存 |
| 能做什么 | 租户路由到独立 BFF 集群；同一用户稳定命中灰度版本；静态资源长缓存 + HTML 不缓存保证发版即时生效 |
| 怎么用 | `map $host $tenant_backend`；`split_clients "${http_x_device_id}${remote_addr}" $api_version { 10% "v2"; * "v1"; }`；`proxy_set_header X-Tenant-Id $tenant` 覆盖客户端同名头 |
| 原理和工作流程 | 请求到达 → 按 `$host` 解析租户 → 按设备 ID 哈希确定灰度版本 → 覆盖租户头防止伪造 → 转发到对应 BFF 集群 |
| 缺点 | Nginx 配置为静态文件，灰度规则调整需 reload；同名 header 若不显式覆盖（`proxy_set_header`）客户端可伪造 `X-Tenant-Id` 实现跨租户访问 |

## 3.5 数据级权限：字段脱敏与行级过滤（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 数据级权限的三个层次：字段可见性（无权限字段直接不返回）、行可见性（数据范围：本人/本部门/本部门及下级/全部）、聚合可见性 |
| 能做什么 | 无 `user:field:phone` 权限时响应体中不含 phone 字段；数据范围权限按部门树 path 前缀匹配避免递归查询 |
| 怎么用 | 用 `FIELD_PERMISSION` 映射表遍历删除无权限字段（删除而非置空）；用 `buildScopeCondition(scope, user)` 生成行级过滤条件 |
| 原理和工作流程 | 后端按权限码决定字段是否出现在响应体中 → 按数据范围生成 `where` 条件 → 部门层级用 path 前缀匹配替代递归查询 |
| 缺点 | **必须由后端实现**：前端脱敏（`138****8888`）只是展示层处理，原始值若出现在响应体中，打开 Network 面板即可拿到；字段删除而非置空是防止泄露"该字段存在"的关键细节 |
