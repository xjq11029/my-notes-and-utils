### 微前端（3 题）

**1. ★★ 以下关于 qiankun 的 JS 沙箱，描述正确的是？**

A. qiankun 使用 iframe 实现 JS 隔离
B. ProxySandbox 为每个子应用创建独立的 fakeWindow，支持多子应用同时运行
C. SnapshotSandbox 支持多个子应用同时激活
D. qiankun 的沙箱可以拦截所有对 window 的修改，包括直接赋值

**答案：B**

**解析**：
- A 错误：qiankun 使用 Proxy 实现 JS 沙箱，而非 iframe（wujie 使用 iframe）
- B 正确：ProxySandbox 是多例沙箱，每个子应用有独立的 fakeWindow
- C 错误：SnapshotSandbox 是单例沙箱，同一时间只能激活一个子应用
- D 错误：Proxy 沙箱在某些场景下无法完全拦截（如直接对 window 属性的赋值需要配合 with 语句）

---

**2. ★★ Module Federation 中 `shared` 配置 `singleton: true` 的主要作用是？**

A. 让子应用可以独立运行
B. 确保全局只有一个该依赖的实例，避免多实例冲突
C. 提升构建速度
D. 实现 CSS 样式隔离

**答案：B**

**解析**：`singleton: true` 确保全局只有一个该依赖的实例（如 React），避免因多个 React 实例导致的 hooks 报错"Invalid hook call"、Context 断裂等问题。A 是子应用独立运行的能力，与 singleton 无关；C 和 D 都不是 singleton 的作用。

---

**3. ★★ wujie 相比 qiankun 的核心优势不包括？**

A. 子应用几乎零改造
B. 更强的 JS 隔离能力
C. 更小的运行时体积
D. 原生跨域支持

**答案：C**

**解析**：wujie 使用 iframe + WebComponent 实现隔离，iframe 本身有内存开销，运行时体积并不比 qiankun 更小。A、B、D 都是 wujie 的优势：零改造接入、iframe 天然 JS 隔离、原生跨域支持。

### 设计系统（3 题）

**4. ★★ W3C DTCG 三层令牌体系中，以下哪项属于语义令牌（Semantic Tokens）？**

A. `blue-500: #3B82F6`
B. `color-brand-primary: {value: '{blue.500}'}`
C. `button-bg-primary: {value: '{color.brand.primary}'}`
D. `--blue-500: #3B82F6;`

**答案：B**

**解析**：
- A 是原始令牌（Raw Token），直接定义颜色值
- B 是语义令牌（Semantic Token），将原始值与业务语义绑定
- C 是组件令牌（Component Token），应用到具体组件
- D 是 CSS 变量形式，属于实现层面

**5. ★★ 以下哪种组件库模式最适合"有自己的设计系统、需要完全控制样式"的团队？**

A. 传统 npm 包（如 Ant Design）
B. Headless UI（如 Radix UI）
C. Copy-in 模式（如 shadcn/ui）
D. 以上都可以

**答案：B**

**解析**：Headless UI 只提供逻辑和行为，不提供样式，最适合需要完全控制样式的团队。传统 npm 包样式定制受限；Copy-in 模式可以直接修改源码，适合需要深度定制的场景。两种模式各有适用场景，选择取决于团队对样式控制的需求程度。

**6. ★★★ CSS @layer 的优先级规则中，以下说法正确的是？**

A. 声明越靠前的 layer 优先级越高
B. 未分层（unlayered）的样式优先级低于所有分层样式
C. `!important` 会反转层级优先级
D. @layer 中的样式始终优先于内联样式

**答案：C**

**解析**：
- A 错误：声明越靠后的 layer 优先级越高（`@layer A, B, C;` 中 C 最高）
- B 错误：未分层样式优先级高于所有分层样式
- C 正确：`!important` 反转层级优先级，分层中的 `!important` 高于未分层的 `!important`
- D 错误：内联样式优先级机制独立于 @layer，内联样式优先级始终最高

**9. ★ 技术债分级中，L1（关键债）的定义是？**

A. 影响代码可读性，但不影响功能
B. 影响开发效率，每次迭代都产生额外成本
C. 影响系统稳定性和安全性，存在线上故障风险

- B 是 L2（高优债）

**10. ★★ 依赖倒置原则（DIP）在前端分层架构中的核心思想是？**

A. 高层模块依赖低层模块
B. 抽象依赖具体实现
C. 高层模块和低层模块都依赖抽象
D. 视图层直接调用 API

**答案：C**

**解析**：依赖倒置原则的核心是：高层模块不应依赖低层模块，两者都应依赖抽象。在前端分层中，业务逻辑层（高层）通过接口（抽象）依赖数据层（低层），而非直接依赖具体实现。

### 补充：微前端与渲染架构（2 题）

**11. ★★ qiankun 的两种 CSS 隔离模式，以下说法正确的是？**

A. `strictStyleIsolation` 通过给子应用样式规则加前缀实现隔离
B. `experimentalStyleIsolation` 基于 Shadow DOM 实现隔离
C. `strictStyleIsolation` 基于 Shadow DOM，子应用 DOM 被包裹进 shadowRoot
D. 两种模式默认都开启

**答案：C**

**解析**：
- A、B 说反了：`strictStyleIsolation` 基于 Shadow DOM，`experimentalStyleIsolation` 基于样式前缀（`div[data-qiankun="xxx"]`）
- C 正确：`strictStyleIsolation` 用 Shadow DOM 包裹子应用容器，隔离彻底，但会带来 `document.querySelector` 查不到外部元素、弹窗挂载到 `body` 失效等副作用，需要子应用改造
- D 错误：qiankun 默认不做 CSS 隔离，需显式配置；`experimentalStyleIsolation` 兼容性好但隔离不彻底（`body` / `html` 上的全局样式仍会泄漏）

**12. ★★★ 关于 Island Architecture（孤岛架构）与 Partial Hydration（局部注水），描述正确的是？**

A. Island Architecture 会注水整个页面，Partial Hydration 只注水局部
B. Island Architecture 让页面主体保持静态 HTML，只对交互"孤岛"注水；Partial Hydration 按优先级 / 可见性 / 交互触发逐步注水
C. 两者都是"零 JS"方案，页面完全不注水
D. Resumability（Qwik）与 Partial Hydration 是同一概念的不同叫法

**答案：B**

**解析**：
- A 说反：Island Architecture 的静态区域零 JS，只有孤岛注水
- B 正确：Astro 是 Island Architecture 的代表（孤岛之间互不依赖、可各自使用不同框架）；React 18 的 Selective Hydration、由 `<Suspense>` 驱动的按需注水属于 Partial Hydration
- C 错误：两者都仍有 JS，区别在注水的范围与时机
- D 错误：Resumability 不重新执行组件代码，而是把状态与事件序列化后在客户端"恢复"，省去重放组件逻辑的开销，思路与 Partial Hydration（仍需执行并注水）不同

### BFF 与权限架构（5 题）

**13. ★★ 关于 BFF 与 API Gateway 的职责边界，以下说法错误的是？**

A. API Gateway 面向所有外部流量（含第三方 OpenAPI），BFF 面向特定客户端
B. API Gateway 做身份认证，BFF 做数据权限收敛
C. 全局限流应放在 BFF，因为 BFF 更懂业务
D. BFF 不应维护 IP 黑白名单、证书和路由规则表

**答案：C**

**解析**：
- C 错误：限流应放在 Gateway。BFF 实例数少、扩缩容慢，做全局限流成本高；BFF 只做面向单用户的下游保护（如对某微服务的并发上限）
- A、B、D 正确。边界三原则：鉴权两层都做但语义不同（Gateway 认证 / BFF 数据权限收敛）；限流放 Gateway；不把 Gateway 能力搬进 BFF，否则 BFF 会退化成"第二个网关"
- 一句话区分：**Gateway 关心"这个请求能不能进来"，BFF 关心"这个请求要返回什么数据"**

**14. ★★ BFF 聚合首页数据（用户服务 + 优惠券服务并行调用），以下做法最合理的是？**

A. 全部用 `Promise.all`，任一失败则整个接口报错
B. 全部用 `Promise.allSettled`，失败的一律返回 `null`
C. 关键数据用 `Promise.all`，非关键数据用 `Promise.allSettled` + 兜底值，并返回 `degraded` 标记
D. 改为串行调用，保证顺序可控

**答案：C**

**解析**：
- A 会让"优惠券服务抖动"放大为"整个首页白屏"，是典型的故障放大
- B 的问题是无法区分"真的没有数据"与"拉取失败"，前端只能盲猜
- C 正确：区分关键与非关键数据，非关键降级为兜底值并显式返回 `degraded`，前端据此展示占位或提示
- D 错误：串行会叠加 RTT，首屏变慢

**15. ★★★ 以下哪种场景最适合使用 ABAC（而非 RBAC）？**

A. 后台管理系统，权限由管理员按角色配置
B. 要求"同部门可编辑、资源密级不高于自身密级、且仅限工作时间操作"
C. 在线文档中用户可把文档分享给他人，且文件夹权限向子文档继承
D. 简单的菜单可见性控制

**答案：B**

**解析**：
- B 是多属性组合判定（主体属性 + 资源属性 + 环境属性），用 RBAC 表达会导致"角色爆炸"
- A 是 RBAC 的经典场景（用户 → 角色 → 权限）
- C 是 ReBAC（关系元组 `资源#关系@主体`，天然支持共享与继承，代表实现 Zanzibar / OpenFGA / SpiceDB）
- D 用权限码过滤即可
- 补充：ABAC 表达能力强、策略可动态下发，但判定成本高、难以反查"谁能访问 X"，适合强合规场景；工程实现有 OPA(Rego)、AWS Cedar、CASL

**16. ★★ 前端权限的四个层次，从粗到细依次是？**

A. 按钮级 → 菜单级 → 路由级 → 数据级
B. 路由级 → 菜单级 → 按钮级 → 数据级
C. 数据级 → 按钮级 → 菜单级 → 路由级
D. 路由级 → 按钮级 → 菜单级 → 数据级

**答案：B**

**解析**：B 正确——路由级（页面能否进入）、菜单级（导航项是否展示）、按钮级（操作是否可用）、数据级（同页面内能看到哪些数据）。
关键认知：四个层次**全部可以被绕过**（改内存、改 DOM、重放请求），前端权限的作用是降低用户困惑与减少无效请求，安全边界必须由后端保证。其中数据级权限必须由后端做字段脱敏与行级过滤，只在前端做 `138****8888` 展示处理会被 Network 面板直接看穿。

**17. ★★★ 关于水平越权（IDOR）的防护，以下做法正确的是？**

A. 前端把 `userId` 放进请求参数，后端按该参数查询
B. 后端从已验签的 Token 中取 `userId` 作为查询条件
C. 单资源查询先按 `id` 查出记录，再判断归属，不匹配返回 403
D. 无权访问返回 403、资源不存在返回 404，便于前端区分

**答案：B**

**解析**：
- A 是典型的 IDOR 漏洞：信任客户端传入的 `userId`，攻击者可传任意值
- B 正确：`userId` 只从可信来源（Token）取；单资源查询应把归属条件合并进 `where`（如 `where: { id: params.id, userId: req.auth.userId }`），而不是"先查后判"
- C 有两个问题："先查后判"存在竞态窗口；返回 403 泄露了"资源存在"这一信息
- D 错误：资源不存在与无权访问应**统一返回 404**，否则攻击者可据状态码枚举有效 ID 区间
- 对比：水平越权是同角色访问他人数据；垂直越权是低权限用户执行高权限操作（防护靠每个接口做权限校验）

### 国际化与多端同构（3 题）

**18. ★★ ICU MessageFormat 中，关于复数（plural）的说法正确的是？**

A. 所有语言都只有 `one` 和 `other` 两种复数类别
B. 中文（`zh-CN`）在 `count = 1` 时会命中 `one` 分支
C. `=0` 是精确匹配且优先级最高；`one` / `other` 是 CLDR 按语言定义的复数类别
D. 用字符串拼接 `'你有 ' + count + ' 条消息'` 可以替代消息模板

**答案：C**

**解析**：
- A 错误：复数类别数量差异极大——中文只有 `other`，英语 `one` / `other`，法语 3 种，俄语 4 种，阿拉伯语 6 种
- B 错误：中文只有 `other` 类别，`one` 分支永远不会命中
- C 正确：`=0` 为精确匹配、优先级最高；`#` 占位符会自动替换为 `count` 的本地化格式数字（含千分位）；可用 `Intl.PluralRules('zh-CN').select(1)` 验证
- D 错误：拼接会导致其他语言语序错乱，必须把整句作为 ICU 消息模板，变量交给 MessageFormat 处理

**19. ★★ 关于 SSR 状态序列化与注水（hydration），以下做法错误的是？**

A. 服务端把预取数据序列化后内联到 HTML，客户端用同一份数据初始化 store
B. 服务端与客户端显式指定同一个 `timeZone`，避免格式化结果不同
C. 直接用 `JSON.stringify(state)` 内联到 `<script>` 中，性能最好
D. 服务端把 `locale` 序列化传给客户端，客户端初始化时直接使用，不再自行探测

**答案：C**

**解析**：
- C 错误且是**高危 XSS 漏洞**：若数据中含有 `</script>`，脚本标签会被提前闭合，攻击者可注入任意脚本。必须用 `serialize-javascript`（`isJSON: true`），或至少 `JSON.stringify(x).replace(/</g, '\\u003c')`
- A、B、D 都是避免注水不匹配（Hydration Mismatch）的正确做法
- 注水不匹配的六种成因：时间相关（`Date.now()`）、随机数（`Math.random()`）、时区差异、`locale` 差异、浏览器 API 分支、HTML 结构非法
- 注水失败后果：React 会丢弃服务端 HTML 重新渲染（白屏 + 丢失 SSR 收益），Vue 输出警告并尝试修补（可能出现视觉跳动）

**20. ★★ RTL 适配中，以下做法正确的是？**

A. 把 `margin-left` 改成 `margin-right` 即可适配 RTL
B. 用 `margin-inline-start` 替代 `margin-left`，一份样式同时适配 LTR 与 RTL
C. 对所有图标统一 `transform: scaleX(-1)` 翻转
D. 只需在 `<html>` 上设置 `dir="rtl"`，组件库会自动适配

**答案：B**

**解析**：
- A 错误：物理属性在 RTL 下不会自动映射，间距会留在错误一侧
- B 正确：逻辑属性映射——`margin-inline-start` ← `margin-left`、`inset-inline-start` ← `left`、`text-align: start` ← `text-align: left`、`inline-size` ← `width`
- C 错误：只有方向性图标（箭头、返回 / 前进、chevron、折叠展开）需要翻转；时间（时钟 / 日历 / 播放）、媒体与品牌、状态符号（勾选 / 叉号 / 警告）、数字与图表都不应翻转，整体翻转会导致文字镜像、数字反向
- D 错误：只设 `dir` 而不引入组件库 RTL 样式，弹窗、下拉、分页器方向仍会错误（Ant Design 需 `<ConfigProvider direction="rtl">`，Element Plus 需引入 RTL 样式文件）

## 第二部分：简答题（共 15 题）

**Q1（★★）：请简述微前端架构的核心价值，并说明在什么场景下不适合使用微前端。**

**答案**：
微前端的核心价值包括：
- 技术栈无关：主应用不限制子应用的技术栈，Vue 2/3、React 可共存
- 独立开发部署：各子应用仓库独立，CI/CD 独立，互不影响
- 增量升级：逐步迁移老项目，避免全量重写
- 团队自治：不同团队负责不同业务模块，解耦组织架构

不适合使用微前端的场景：
- 团队规模小（< 10 人），没有多团队并行开发的需求
- 项目规模小，单体应用完全可以满足需求
- 对首屏加载性能有极致要求（微前端会增加初始化开销）
- 团队缺乏微前端相关经验，强行引入会增加维护成本

**Q2（★★）：请对比 qiankun 和 Module Federation 的隔离机制的差异，并说明各自的适用场景。**

**答案**：
隔离机制差异：
- qiankun：使用 JS Proxy 沙箱（ProxySandbox）实现 JS 变量隔离，通过 experimentalStyleIsolation（CSS 前缀）或 strictStyleIsolation（Shadow DOM）实现 CSS 隔离
- Module Federation：没有内置的 JS/CSS 隔离机制，依赖 shared 配置共享依赖，依赖团队规范保证代码隔离

适用场景：
- qiankun：适合存量系统改造，需要多技术栈共存（Vue 2 + Vue 3 + React），子应用之间需要强隔离
- Module Federation：适合全新项目，同技术栈（如全部 React），追求极致性能和构建速度，团队有良好的代码规范

**Q3（★★）：解释 Design Tokens 的三层架构，并说明为什么需要语义令牌这一层。**

**答案**：
三层架构：
1. 原始令牌（Raw Tokens）：定义最基础的视觉值，如 `blue-500: #3B82F6`
2. 语义令牌（Semantic Tokens）：将原始值与业务语义绑定，如 `color-brand-primary: {blue.500}`
3. 组件令牌（Component Tokens）：将语义令牌应用到具体组件，如 `button-bg-primary: {color.brand.primary}`

需要语义令牌的原因：
- **解耦值和用途**：如果品牌色从蓝色变为绿色，只需修改语义令牌的引用（`blue.500` → `green.500`），不需要修改所有使用了品牌色的组件
- **语义化命名**：`color-brand-primary` 比 `blue-500` 更直观，设计师和开发者都能理解
- **多主题支持**：暗色模式下，语义令牌可以映射到不同的原始值，组件令牌无需感知

**Q4（★★）：Headless UI 组件库（如 Radix UI）相比传统组件库（如 Ant Design）的优势和劣势是什么？**

**答案**：
优势：
- 样式完全可控：不提供任何默认样式，团队可以完全自定义外观
- 更小的体积：只提供逻辑和行为，不包含样式代码
- 更好的可访问性：Radix UI 等 Headless 库通常对 WAI-ARIA 有很好的支持
- 与设计系统解耦：可以与任何样式方案（Tailwind、CSS Modules、styled-components）配合

劣势：
- 开发效率较低：需要自己写所有样式，不像 Ant Design 开箱即用
- 缺乏统一的设计语言：如果团队没有成熟的设计系统，容易导致风格不一致
- 需要额外学习成本：需要同时掌握 Headless 库和样式方案
- 组件数量有限：Headless 库通常只覆盖基础组件，高级组件（如 Table、Tree）需要自行实现

**Q5（★★）：请描述前端分层架构中依赖倒置的具体实现方式，并给出代码示例。**

**答案**：
依赖倒置在前端分层中的实现方式：

1. 定义 Repository 接口（抽象层）
2. 数据层实现接口（具体实现）
3. 业务逻辑层通过构造函数注入依赖接口
4. 视图层通过 DI 机制获取 Service 实例

```typescript
// 1. 定义抽象接口
interface IUserRepository {
  getUser(id: string): Promise<User>;
}

// 2. 数据层实现
class HttpUserRepository implements IUserRepository {
  async getUser(id: string) {
    return fetch(`/api/users/${id}`).then(r => r.json());
  }
}

// 3. 业务逻辑层依赖抽象
class UserService {
  constructor(private repo: IUserRepository) {}
  async getProfile(id: string) {
    const user = await this.repo.getUser(id);
    return { ...user, displayName: user.nickname || user.name };
  }
}

// 4. 依赖注入
const repo = new HttpUserRepository();
const userService = new UserService(repo);
```

**Q6（★）：什么是技术债？如何对它进行分级管理？**

**答案**：
技术债是指为了快速交付而做出的次优技术决策，需要在未来偿还的"利息"。

分级管理：
- **L1 关键债**：影响系统稳定性、安全性，存在线上故障风险。策略：立即偿还，可暂停当前迭代
- **L2 高优债**：影响开发效率，每次迭代都产生额外成本。策略：本迭代内偿还
- **L3 中优债**：影响代码可读性，但不影响功能。策略：下个迭代偿还
- **L4 低优债**：代码风格不一致，有优化空间但不紧急。策略：纳入 backlog，逐步偿还

管理方法：
- 建立技术债登记表，记录编号、描述、级别、影响范围、预估工时
- 每个迭代预留 20% 时间用于技术债偿还
- 遵循童子军规则：每次修改代码时让代码比之前更干净

**Q7（★★）：在进行技术选型时，如何平衡"技术先进性"和"团队熟悉度"？**

**答案**：
平衡策略：
1. **使用五维度评估矩阵**：将"技术先进性"拆解为"性能"和"生态社区"，将"团队熟悉度"设为独立维度，根据项目实际情况分配权重
2. **新技术的引入原则**：新技术先在非核心模块或小型项目中试点，验证可行后再推广；核心业务模块优先使用团队熟悉的技术
3. **风险矩阵评估**：新技术带来高收益的同时也伴随高风险，评估失败的成本和影响范围
4. **团队能力匹配**：如果团队有较强的学习能力，可以适当提高新技术权重；如果项目时间紧，优先选择团队熟悉的技术
5. **编写 ADR**：详细记录选型理由和风险评估，方便后续回顾和修正

权重分配示例（稳定型项目）：
- 团队熟悉度：30%
- 生态成熟度：20%
- 性能：20%
- 学习成本：15%
- 社区活跃度：15%

**Q8（★★★）：请描述大型项目从单体架构迁移到微前端架构的渐进式迁移策略。**

**答案**：
渐进式迁移策略分为五个阶段：

**阶段一：评估与准备**
- 分析现有代码，识别可拆分的业务模块边界
- 确定微前端方案（qiankun / MF / wujie）
- 搭建主应用骨架（路由、权限、公共组件）

**阶段二：基础设施搭建**
- 建立公共依赖管理（shared dependencies）
- 抽取公共组件和工具函数为独立包
- 建立应用间通信机制

**阶段三：垂直拆分**
- 选择一个低风险、独立的业务模块作为试点
- 将其从主应用中剥离为独立子应用
- 通过主应用路由接入，验证架构可行性

**阶段四：逐步迁移**
- 按照业务优先级，逐个迁移其他模块
- 每次迁移一个模块，灰度发布验证
- 保留回退能力（主应用保留原始路由兜底）

**阶段五：收尾与优化**
- 迁移最后一个模块
- 清理主应用中的冗余代码
- 性能优化、监控完善、文档沉淀

**Q9（★★）：BFF 与 API Gateway 的职责边界是什么？边界设计有哪三条原则？**

**答案**：

职责对比：

| 维度 | API Gateway | BFF |
|---|---|---|
| 服务对象 | 所有外部流量（含第三方 OpenAPI） | 特定客户端（Web / App / 小程序各一个） |
| 核心关注点 | 安全、流量治理、协议接入 | 业务数据编排、面向端的接口形态 |
| 典型能力 | 统一鉴权、限流熔断、灰度路由、TLS 终止、IP 黑白名单 | 数据聚合、字段裁剪、协议转换、客户端专属缓存 |
| 是否懂业务 | 不懂业务，只做通用横切 | 懂业务，知道"首页需要哪几块数据" |
| 归属团队 | 基础设施 / 中台团队 | 前端团队 |
| 变更频率 | 低（改一次影响全站） | 高（跟随客户端迭代） |
| 故障影响面 | 全站不可用 | 单个端不可用 |

边界设计三条原则：

1. **鉴权两层都做，但语义不同**：Gateway 做身份认证（你是谁、Token 是否有效），BFF 做数据权限收敛（这个用户能看到哪些数据）；绝不能只在 BFF 做认证，因为 Gateway 是更靠前、更统一的可信边界
2. **限流放在 Gateway**：BFF 实例数少、扩缩容慢，做全局限流成本高；BFF 只做面向单用户的下游保护
3. **不要把 Gateway 的能力搬进 BFF**：一旦 BFF 开始维护 IP 黑白名单、证书、路由规则表，它就会退化成"第二个网关"，职责失控

一句话区分：**Gateway 关心"请求能不能进来"，BFF 关心"要返回什么数据"**。

**Q10（★★）：BFF 的粒度应如何划分？四种常见反模式是什么？**

**答案**：

三种粒度形态：

- **按端拆分（纵向）**：`BFF-Web`（接口胖、字段全）/ `BFF-App`（字段瘦）/ `BFF-MP`（最瘦、包体积敏感）。优点是各端独立演进；缺点是服务数随端数线性增长、公共逻辑易复制。适用端间数据形态差异大的场景
- **按业务域拆分（横向）**：`BFF-Trade` / `BFF-User`，与后端微服务边界对齐。缺点是单页面跨域聚合时客户端仍需多次请求。适用域多、团队多的场景
- **端 × 域矩阵**：能同时满足两种诉求，但服务数 = 端数 × 域数，运维成本最高；实践中常用 `X-Client-Type` 请求头让一个 BFF 承载多端来降本

选型依据：团队规模、端数量、域数量、端间数据形态差异度。核心原则：**BFF 属于客户端，应由前端团队维护并遵循客户端的发布节奏**。

四种反模式：

| 反模式 | 表现 | 修正 |
|---|---|---|
| 变成新的巨石 | BFF 代码量超过前端主应用，改一处要全量回归 | 只做聚合 / 裁剪 / 协议转换，业务逻辑归下游领域服务 |
| 逻辑下沉混乱 | 同一校验在前端 / BFF / 后端各写一遍，三处不一致 | 格式校验在前端，业务校验在领域服务，BFF 只透传 |
| 暴露内部接口 | 客户端能调到下游内部管理接口 | 显式路由白名单，禁止 `app.use('*', proxy)` 通配转发 |
| 职责越界 | BFF 维护 IP 黑白名单、证书、路由规则表 | 明确边界，BFF 只管"返回什么数据" |

**Q11（★★）：RBAC、ABAC、ReBAC 的区别与选型依据？**

**答案**：

| 模型 | 判定依据 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| RBAC | 用户 → 角色 → 权限 | 模型简单，两张关联表即可实现 | **角色爆炸**（"华南区-家电类目-审核员"这类组合增多时角色数指数增长） | 绝大多数企业后台管理系统 |
| ABAC | 主体 / 资源 / 操作 / 环境属性 + 策略表达式 | 表达能力强、策略与代码解耦、可动态下发 | 策略编写调试门槛高、判定需拿到资源属性成本高、难反查"谁能访问 X" | 强合规、规则维度多（金融 / 医疗 / 多租户 SaaS） |
| ReBAC | 关系元组 `资源#关系@主体` | 天然支持共享、继承、嵌套，可反查访问者 | 需引入图存储与关系查询，架构复杂度显著上升 | 协作类产品（在线文档、网盘、项目管理） |

RBAC 的四个层级：RBAC0（核心，用户-角色 + 角色-权限两个多对多关系）、RBAC1（角色继承）、RBAC2（角色约束，如互斥角色）、RBAC3（RBAC1 + RBAC2）。

工程实现：ABAC → OPA(Rego) / AWS Cedar / CASL；ReBAC → Google Zanzibar 论文 / OpenFGA / SpiceDB。

选型建议：**混合使用** —— RBAC 管"能不能进系统"，ABAC / ReBAC 管"能看哪些数据"。权限维度少但要求灵活时，用"RBAC + 少量 ABAC 策略"。

**Q12（★★★）：前端权限的四个层次是什么？为什么说前端权限不可信？如何防护越权？**

**答案**：

四个层次（从粗到细）：

| 层次 | 控制对象 | 实现方式 | 用户体验目标 |
|---|---|---|---|
| 路由级 | 页面能否进入 | 动态路由 + 全局前置守卫 | 无权限地址直接跳 403，不出现"能进去但报错" |
| 菜单级 | 导航项是否展示 | 路由表过滤后生成菜单 | 不展示点了就 403 的入口 |
| 按钮级 | 操作按钮是否可用 | 指令 / 组件 / Hook 判定 | 不展示点了就失败的操作 |
| 数据级 | 同页面内能看到哪些数据 | 后端字段脱敏 + 行级过滤 | 敏感字段不渲染，而非渲染后隐藏 |

**不可信的原因**：

| 绕过手段 | 具体操作 | 前端能防住吗 |
|---|---|---|
| 修改内存状态 | DevTools 改 Pinia / Redux 中的 `permissions` 数组 | 不能 |
| 篡改 DOM | 删除按钮上的 `v-if`，或直接改 `display` | 不能 |
| 重放请求 | 从 Network 面板复制请求，用 curl 重放 | 不能 |
| 改 Token Payload | 修改 JWT Payload 中的 `role` 字段 | **能防住**（签名校验失败） |

**越权防护**：

- **水平越权（IDOR）**：`userId` 只从 Token 取，绝不信任 URL / query / body；单资源查询把归属条件合并进 `where`，避免"先查后判"的竞态
- **垂直越权**：每个接口做权限校验（中间件 + 权限码注解），不能只依赖前端隐藏入口
- 资源不存在与无权访问**统一返回 404**，避免攻击者用状态码枚举有效 ID
- 数据级权限必须由后端做脱敏 / 行级过滤，前端展示层的 `138****8888` 不是安全措施

**Q13（★★★）：动态路由（权限路由）的实现原理是什么？`addRoute` 之后有哪四个必须注意的点？**

**答案**：

实现流程：

```
登录 → 拉取用户权限 → 权限码集合 → 过滤静态路由表 → 得到可访问路由
     → router.addRoute() 动态注册 → 生成菜单 → 渲染页面
```

三种形态对比：

| 形态 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 后端返回路由表 | 后端下发菜单 / 路由 JSON，前端动态注册 | 权限变更即时生效，前端无需发版 | 前端路由结构被后端耦合，组件路径需约定 |
| 前端全量路由 + 权限码过滤 | 前端定义全部路由（含 `meta.permission`），按权限码过滤 | 前端掌控路由结构，组件映射简单 | 新增页面需前端发版 |
| 混合模式 | 路由结构前端定，可访问性由后端权限码决定 | 兼顾两者 | 需约定权限码规范 |

`addRoute` 之后四个必须注意的点：

1. **必须重新导航**：守卫中 `return { ...to, replace: true }`，否则本次导航仍按旧路由表解析，会命中 404
2. **登出必须移除动态路由**：保存 `addRoute` 返回的移除函数并逐个调用（或用 `removeRoute`），否则切换账号后旧权限路由残留
3. **刷新会丢失动态路由**：路由表在内存中，刷新后需重新走守卫流程；`routesLoaded` 不能简单持久化
4. **404 通配路由必须最后注册**：`{ path: '/:pathMatch(.*)*' }` 若早于动态路由注册，动态路由将永远无法匹配

React Router 6 没有 `addRoute`，做法是用状态驱动路由表：权限拉取完成后 `setRoutes(filtered)`，`<Routes>` 重新渲染即完成"动态路由"。

按钮级权限的三种封装：指令（Vue，写法最简 `v-permission="'user:add'"`，但 `removeChild` 是破坏性操作、权限变化后无法恢复）、组件（`<Auth code="user:add">`，可传 fallback，如"无权限时展示禁用按钮"）、Hook / Composable（`usePermission('user:add')`，可参与计算与禁用态判断）。

权限码规范：`{域}:{资源}:{操作}`（如 `system:user:create`），全小写、冒号分隔、三段固定，操作动词用统一词表（list / detail / create / update / delete / export / import / approve），禁止出现 UI 概念（如 `button:red:click`）。

**Q14（★★★）：多租户系统如何保证租户隔离？三条必须遵守的规则是什么？**

**答案**：

三种隔离模式：

| 隔离模式 | 数据层实现 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|---|
| 独立数据库 | 每租户一个 DB 实例 | 最高 | 最高 | 金融、政企、强合规 |
| 共享库独立 Schema | 每租户一个 Schema | 高 | 中 | 中大型 SaaS |
| 共享库共享表 + 租户字段 | 每行带 `tenant_id` | 中（依赖代码正确性） | 最低 | 中小型 SaaS、快速迭代 |

链路传递：

```
客户端 → 边缘（识别租户，注入 X-Tenant-Id）→ Gateway（校验租户合法性）
       → BFF（透传）→ 微服务（写入查询条件）
```

三条必须遵守的规则：

1. **租户 ID 必须由服务端推导**：客户端只传"子域名 / 登录域名"这类路由信息，租户 ID 由边缘或网关按域名映射得出，防止 A 租户用户把 `X-Tenant-Id` 改成 B 租户（注意 Nginx 同名 header 是覆盖语义）
2. **租户 ID 必须进入数据访问层**：用 ORM 中间件或数据库行级安全（RLS）强制注入 `tenant_id`，而不是靠开发者自觉，避免某个查询漏写造成跨租户泄露
3. **缓存 Key 必须包含租户 ID**：`user:123:profile` 在多租户下会串数据，必须是 `tenant:{tid}:user:{uid}:profile`

补充：请求级上下文的自动透传用 `AsyncLocalStorage`（Node.js）读取当前请求的隔离存储，无需逐层传参。

**Q15（★★）：i18n 架构需要覆盖哪些维度？ICU MessageFormat 的复数与字符串拼接有哪些坑？**

**答案**：

**i18n 需要覆盖的七个维度**：文案、日期时间、时区、数字、货币、复数与性别、书写方向（RTL）。只做文案翻译会导致日期格式不符合当地习惯、金额符号与小数位错误、复数形式错误、RTL 语言布局错乱。

判断标准：**新增一种语言时只需新增语言包与配置，不需要改业务代码** —— 这是 i18n 架构能力；实际翻译与本地化交付属于 l10n。

**ICU MessageFormat 的四种语法能力**：简单插值 `{name}`、复数 `{count, plural, ...}`、分类选择 `{gender, select, ...}`、序数 `{position, selectordinal, ...}`。

**复数的坑**：

- 复数类别由 CLDR 按语言定义，数量差异极大：中文只有 `other`、英语 `one` / `other`、法语 3 种、俄语 4 种、阿拉伯语 6 种
- 只写 `one` / `other` 会导致俄语、阿拉伯语等语言的复数形式错误；复数分支必须由翻译人员或 TMS 平台按目标语言补全
- `=0` 是精确匹配、优先级最高；`#` 会自动替换为本地化格式的数字（含千分位）
- 可用 `Intl.PluralRules('ar-EG').select(3)` → `'few'` 验证

**拼接的坑**：

```javascript
// ❌ 拼接导致其他语言语序错乱（"你有 3 条消息"在日语/德语中语序不同）
const text = '你有 ' + count + ' 条消息';
// ✅ 整句作为消息模板，变量交给 MessageFormat
t('message.count', { count });
```

其他关键约定：时间统一"存储 UTC / 传输 ISO 8601（带 `Z` 或偏移）/ 展示按用户时区或业务时区"；金额用最小货币单位的整数传输（避免 `0.30000000000000004` 这类浮点误差）；用 `Intl.NumberFormat` 的 `style: 'currency'` 而非手写货币符号。

- BFF 变成新的巨石（代码量超过前端主应用）
- 逻辑下沉混乱（同一校验在前端 / BFF / 后端各写一遍）

- 把 IP 黑白名单 / 证书 / 路由表搬进 BFF（职责越界）
- DataLoader 做成全局单例，导致跨用户缓存泄露

- 平台差异抹平优先级：适配层（Adapter）> 条件编译 > 运行时探测
- 复用比例参考：`domain/` 100%、`services/` 90%+、`platform/` 0%、`pages/` 50-80%

- 服务端把预取数据序列化后内联（必须用 `serialize-javascript` 转义，防 `</script>` 造成 XSS）
- 服务端把 `locale` 序列化传给客户端，客户端不再自行 `detectLocale()`，避免注水不匹配
- 两端显式指定同一 `timeZone`，避免时间格式化结果不同

**五、成本与收益评估**
- 端数 ≥ 3 且逻辑占比高时全面同构收益明显（可减少 50-70% 前端工作量）
- 不适合：端数只有 2 且交互复杂（动画 / 手势 / 富文本编辑）、性能敏感场景（长列表 / 音视频编辑）
- 需计入学习成本、跨端运行时损耗（跨线程通信 / 桥接调用）、各端调试成本、第三方库兼容性风险

## 第四部分：高频追问速答（共 23 题）

> 面试中答完主问题后，面试官常沿同一条线索继续追问。以下 23 组"追问 + 速答"覆盖本模块最容易被打穿的细节，用于临场查漏。

**追问 1（★★）：BFF 和 Node 中间层是一回事吗？**

不完全等价。Node 中间层是**技术实现形态**，BFF 是**架构角色定位**。一个 Node 中间层如果只做静态资源托管或简单代理，它不是 BFF；BFF 的核心特征是"面向特定客户端做数据编排"。判断标准：它是否在解决客户端与微服务之间的**阻抗失配**（多端聚合、字段裁剪、协议转换、变更隔离）。

**追问 2（★★）：BFF 为什么强调"属于客户端"？**

因为它必须跟随客户端发布节奏（可一天发多次），而它的价值（字段裁剪、接口形态）取决于客户端的 UI 需求。若归后端团队维护，就会被后端发布窗口与评审流程约束，灵活性优势消失。这是 BFF 能否真正发挥价值的**组织前提**。

**追问 3（★★★）：BFF 用 GraphQL 有什么坑？**

四个：**N+1 查询**（DataLoader 批量化 + 请求级缓存，且必须按请求创建，单例会串用户数据）；**查询复杂度攻击**（深度限制 + 复杂度评分 + 持久化查询白名单）；**HTTP 缓存失效**（单一 POST 端点无法按 URL 缓存，用 APQ 转成 GET）；**错误语义**（GraphQL 恒返回 200，前端必须显式检查 `errors` 数组）。

**追问 4（★★）：前端权限能不能做到"安全"？**

不能。前端权限是 **UX 优化**：降低用户困惑（不展示点了就 403 的入口）、减少无效请求。唯一可信的是后端签发并验签的 Token，越权防护必须在后端每个数据接口上完成。

**追问 5（★★★）：Token 里放权限码还是放版本号？**

推荐 Token 只放 `userId` + `tenantId` + `permVersion`。权限码放 Payload 会导致 Token 体积膨胀（可能超过网关 8KB 限制）、权限变更需等 Token 过期；版本号方案 Token 小、权限可即时失效，代价是需维护版本号与权限的映射缓存。

**追问 6（★★）：为什么"资源不存在"和"无权访问"都要返回 404？**

若分别返回 404 和 403，攻击者可用状态码区分"资源存在但无权"与"资源不存在"，进而枚举有效 ID 区间。统一返回 404 后，真实原因记在服务端日志里供排查。

**追问 7（★★★）：动态路由为什么刷新后会丢？**

`addRoute` 注册的路由在**内存中**，页面刷新后应用重新初始化，路由表回到静态定义的状态，因此必须重新走守卫流程拉取权限并注册。`routesLoaded` 标记也不能简单持久化——持久化了就会跳过注册，导致动态路由缺失。

**追问 8（★★★）：多端同构是不是"一套代码跑所有端"？**

不是。同构分三个**可独立选择**的层次：代码复用（工具函数 / 类型，跨端可行性极高）、逻辑同构（业务规则 / 状态机 / 请求封装，需抹平平台 API）、渲染同构（UI 组件，平台差异最大）。架构建议**自下而上**推进，不要一上来就做渲染同构。

**追问 9（★★）：SSR 为什么必须序列化状态？**

若客户端不拿到服务端已取的数据，注水时会重新请求接口，导致首屏数据闪烁（服务端渲染了内容、注水时变空白再填充）、重复请求、注水不匹配。序列化时**必须转义**，否则数据含 `</script>` 会造成 XSS。

**追问 10（★★★）：i18n 场景下 SSR 最容易踩什么坑？**

服务端与客户端的 `locale` / `timeZone` 不一致导致注水不匹配。服务端按 `Accept-Language` 用 `zh-CN`，客户端 `detectLocale()` 得到 `en-US`，两边渲染结果不同。修复：服务端把 `locale` 序列化传给客户端，客户端初始化时直接使用；时区两端显式指定同一个 `timeZone`。

**追问 11（★★★）：qiankun 的沙箱能完全隔离吗？**

不能。Proxy 沙箱只能拦截通过 `window.xxx` 的访问（配合 `with` 语句改写作用域），无法拦截 `Function('return this')()`、部分 DOM API，也无法隔离 CSS 的全局副作用（`experimentalStyleIsolation` 只是加前缀）。真正的强隔离只有 iframe 路线（wujie 的 iframe + WebComponent）。

**追问 12（★★）：Module Federation 为什么需要 `singleton`？**

避免同一个依赖（如 React）被加载多份实例，否则会出现 "Invalid hook call"、Context 断裂、状态不共享等问题。配套还要设置 `requiredVersion` 与 `eager`，并明确版本不满足时的降级行为。

**追问 13（★★）：Design Tokens 为什么必须分三层？**

原始令牌（值）→ 语义令牌（用途）→ 组件令牌（应用）。语义层是解耦的关键：品牌色从蓝变绿时只改语义令牌的引用，所有组件令牌自动跟随；同时语义层让暗色模式可以映射到不同的原始值，组件无需感知主题。

**追问 14（★★）：技术债怎么量化才不被当成"借口"？**

用可度量的指标：构建时长、CI 时长、缺陷密度、变更前置时间、技术债条目数与级别分布。把偿还计划写进迭代（如每迭代预留 20% 时间），并在 ADR / 技术债登记表中记录影响范围与预估工时，让偿还成为可排期的工作项而非口号。

**追问 15（★★）：ADR 的价值是什么？**

记录"当时为什么这么决策"的上下文，避免后人重复讨论或误改。五要素：标题、状态、上下文、决策、后果。关键是把"后果"（含负面影响与缓解措施）写清楚 —— 只写优点的 ADR 没有价值。

**追问 16（★★）：为什么 BFF 的聚合接口必须给下游设超时？**

BFF 是单进程 Node 服务，事件循环是**共享资源**。一个慢下游会让大量请求挂起、连接池与内存被占满，最终所有接口一起变慢（雪崩）。因此所有下游调用必须设超时（`AbortSignal.timeout`），并配合熔断器与并发上限。

**追问 17（★★★）：分层正交为什么能提升流量利用率？**

单个实验只用 10% 流量，剩余 90% 会闲置。分层正交把流量池按"层"划分：**层内互斥**（同一用户在同层最多命中一个实验，避免同层实验互相污染），**层间正交**（不同层用不同 salt，分桶结果独立）。这样用户可同时进入多个层的实验，在总流量 100% 的前提下并行跑多个实验。

**追问 18（★★★）：权限指令用 `removeChild` 有什么风险？**

`removeChild` 是**破坏性操作**，元素从 DOM 中移除后若权限发生变化（如管理员在会话内授予了权限），元素无法恢复，必须重新渲染整个组件。因此指令方案只适合"权限在会话内不变"的场景；权限会动态变化时应改用权限组件或 `v-if`。

**追问 19（★★）：RTL 下为什么不能整体翻转图标？**

整体 `scaleX(-1)` 会把时间类（时钟、日历、播放 / 暂停）、媒体与品牌（logo、播放三角）、状态符号（勾选、叉号、警告三角）、数字与图表一起镜像，导致文字不可读、数字反向、坐标轴错位。正确做法是只翻转方向性图标，图表逐项配置 `inverse` / `position`。

**追问 20（★★★）：同构项目里第三方库不兼容某个平台怎么办？**

三层处理：优先选有跨端适配的库；其次在适配层做条件实现（`platform/*` 下按平台给出不同实现，业务只依赖 `IPlatform` 接口）；最后才是条件编译兜底。切忌在业务代码里散落 `#ifdef` 或 `typeof wx !== 'undefined'` 判断 —— 那会让逻辑同构退化为"每个端各写一份"。

**追问 21（★★）：CSS 变量与 `@layer` 如何配合做主题切换？**

`@layer` 只负责**优先级**（声明越靠后的层优先级越高；未分层样式高于所有分层样式；`!important` 反转层级优先级），不负责主题切换。主题切换靠 **CSS 变量**：在 `:root` / `[data-theme="dark"]` 上重定义同一批变量，组件样式只引用变量，切换时改属性即可。两者结合：把基础样式放低优先级层、组件样式放高层、覆盖层（utilities）放最高层，避免主题覆盖被组件样式压住。

**追问 22（★★）：微前端选型决策树怎么用？**

从三个问题入手：① 是否需要多技术栈共存（Vue 2 + Vue 3 + React）→ 是则选 qiankun / wujie；② 是否追求构建期共享依赖与极致性能、且全站同技术栈 → 选 Module Federation；③ 子应用能否接受改造、是否需要强 JS 隔离 → 不能接受改造选 wujie，需要强隔离选 wujie / micro-app。补充判据：存量系统改造优先 qiankun（中文社区与文档成熟），全新项目优先 MF，需要 iframe 级隔离优先 wujie。

**追问 23（★★★）：前端分层架构中的数据流模式怎么选？**

按"状态归属"判断：① 组件内部状态 → 本地 `ref` / `useState`；② 跨组件共享的客户端状态 → 轻量 Store（Pinia / Zustand，精准订阅、避免不必要渲染）；③ 服务端状态（缓存、重试、失效）→ 交给数据请求库（TanStack Query / SWR），不要手写进全局 Store；④ 复杂表单 / 状态机 → 状态机库（XState）。常见错误是把服务端数据也塞进全局 Store，导致缓存、失效、并发请求都要自己实现。
