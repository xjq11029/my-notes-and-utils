# 02-设计系统与组件库架构 - 导览

---

## 1.1 什么是设计系统（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 设计系统是由 Design Tokens（设计令牌）、组件库（Component Library）、文档规范（Documentation）三者构成的三角体系，是前端工程化在视觉一致性层面的核心实践 |
| 能做什么 | 保证多产品多平台视觉一致性；提升设计到开发的协作效率；降低维护成本（改一处 Token 全局生效）；加速新功能开发 |
| 怎么用 | 定义 Design Tokens → 基于 Tokens 构建组件库 → 编写组件文档和使用规范 → 在项目中统一引用 |
| 原理和工作流程 | 原始令牌（raw values）→ 语义令牌（semantic mapping）→ 组件令牌（component-specific）→ CSS 变量 → 组件消费 → 主题切换 |
| 缺点 | 建设初期成本高；需要设计师和前端工程师持续维护；团队规模小的时候 ROI 可能不明显 |

---

## 1.2 W3C DTCG 三层令牌体系（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | W3C DTCG 提出的三层令牌体系：原始令牌（Raw Tokens）→ 语义令牌（Semantic Tokens）→ 组件令牌（Component Tokens），用调色板→品牌色→按钮背景色类比 |
| 能做什么 | 实现设计值与业务语义的解耦，修改原始值即可全局更新，语义层保持稳定 |
| 怎么用 | 定义 JSON 格式的令牌文件 → 使用工具（Style Dictionary）编译为 CSS 变量 / Tailwind 配置 / JS 常量 |
| 原理和工作流程 | 原始令牌定义所有可用值 → 语义令牌将原始值与业务含义绑定 → 组件令牌应用到具体 UI 组件 |
| 缺点 | 三层抽象增加了初期设计成本；需要团队对命名规范达成共识；令牌过多时管理复杂 |

## 1.3 组件库的三种模式（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Headless UI（无头组件，如 Radix UI）、Copy-in（复制即用，如 shadcn/ui）、传统 npm 包（如 Ant Design）三种组件库模式 |
| 能做什么 | Headless UI 提供逻辑和行为不限制样式；Copy-in 代码归属项目可自由修改；传统 npm 包开箱即用 |
| 怎么用 | Headless UI：`pnpm add @radix-ui/react-dialog` 后自定义样式；Copy-in：`pnpm dlx shadcn-ui add button`；传统 npm 包：`pnpm add antd` |
| 原理和工作流程 | Headless UI 通过 render props / slots 提供状态和行为；Copy-in 将源码复制到项目中；传统 npm 包通过 ConfigProvider 定制主题 |
| 缺点 | Headless UI 需要自己写样式；Copy-in 更新需要手动同步；传统 npm 包样式定制受限、体积大 |

## 2.1 CSS 变量的级联与主题切换原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 利用 CSS 自定义属性的级联特性，通过切换根元素的 `data-theme` 属性，实现全局主题的无缝切换 |
| 能做什么 | 实现亮色/暗色主题切换，无需 JavaScript 操作 DOM 样式，性能极高 |
| 怎么用 | 在 `:root` 和 `[data-theme='dark']` 中分别定义变量值 → 组件使用 `var(--xxx)` 引用 → JavaScript 切换 `data-theme` 属性 |
| 原理和工作流程 | 浏览器维护 CSS 变量继承链 → 切换 `data-theme` 时触发样式重计算 → 所有使用 `var()` 的元素自动更新 |
| 缺点 | 不支持 IE 11；变量值只能是字符串；大量变量可能影响初始渲染性能（微乎其微）（历史兼容场景，2026 年新项目按现代浏览器基线） |

## 2.2 @layer 优先级管理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | CSS `@layer` 规则允许开发者显式声明样式层级的优先级顺序，解决组件库样式与业务样式冲突的问题 |
| 能做什么 | 将组件库样式放在低优先级层，确保业务代码可以覆盖；将 reset 放在最低优先级层 |
| 怎么用 | `@layer reset, base, components, utilities;` 声明层级顺序 → 各层内编写样式 → 业务代码不写 @layer 获得最高优先级 |
| 原理和工作流程 | 声明顺序决定优先级 → 未分层样式优先级高于所有分层样式 → `!important` 反转层级优先级 |
| 缺点 | 较新的 CSS 特性，老项目可能不兼容；需要团队统一约定层级命名 |

## 2.3 Figma-to-Code 管道（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 从 Figma 设计稿自动提取 Design Tokens，转换为代码（CSS 变量 / Tailwind 配置）的自动化管道 |
| 能做什么 | 减少设计师与前端之间的手动同步工作；确保设计稿与代码中的 Token 值一致 |
| 怎么用 | Figma Tokens 插件导出 JSON → 编写转换脚本 → 生成 CSS 变量 / Tailwind 配置 |
| 原理和工作流程 | Figma 设计稿定义 Token → 插件导出标准化 JSON → Node.js 脚本解析并转换为目标格式 → 集成到构建流程 |
| 缺点 | 依赖 Figma 插件生态；需要设计师遵循规范使用 Token；复杂组件（如动画）难以用 Token 描述 |

## 2.4 零运行时 CSS 方案对比（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Tailwind CSS v4、Panda CSS、StyleX、vanilla-extract、CSS Modules 五种零运行时 CSS 方案的对比 |
| 能做什么 | 在构建时生成静态 CSS，运行时零开销，兼顾开发体验和性能 |
| 怎么用 | Tailwind：工具类在 HTML 中直接使用；Panda CSS：`css({})` 函数；vanilla-extract：`style()` 函数生成 `.css.ts` 文件 |
| 原理和工作流程 | 构建时扫描源码 → 提取使用的样式 → 生成最小化的 CSS 文件 → 运行时直接使用生成的 CSS 类 |
| 缺点 | 各有学习曲线；Tailwind 类名冗长；Panda/StyleX 需要特定构建工具链；CSS Modules 类型安全弱 |

## 3.1 从零搭建 Design Tokens 体系（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 从原始颜色值开始，逐步构建语义令牌，最终生成 CSS 变量的完整流程 |
| 能做什么 | 建立项目的设计语言基础，确保所有组件使用统一的视觉变量 |
| 怎么用 | 定义原始令牌（颜色、间距、圆角等）→ 映射语义令牌 → 编写生成脚本 → 输出 CSS 变量文件 |
| 原理和工作流程 | JavaScript 对象定义 Token 层级 → 递归遍历生成 CSS 变量 → 写入 CSS 文件 → 全局引入 |
| 缺点 | 初期设计工作量较大；Token 命名需要与设计师达成一致；后期扩展需要保持向后兼容 |

## 3.2 基于 Radix UI + Tailwind 构建组件库（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 Radix UI 提供无障碍和交互逻辑，Tailwind 提供样式，CVA 管理变体，构建高质量的组件库 |
| 能做什么 | 构建完全自定义样式、满足无障碍标准、类型安全的组件库 |
| 怎么用 | 安装 Radix UI 组件 → 使用 CVA 定义变体样式 → 结合 Tailwind 类名 → 导出组件 |
| 原理和工作流程 | Radix UI 处理状态管理和键盘交互 → CVA 根据 variant/size 生成对应类名 → Tailwind 提供原子化样式 |
| 缺点 | 需要同时学习 Radix UI、CVA、Tailwind 三个工具；初期组件开发效率低于直接用 Ant Design |

## 3.3 暗色模式完整实现（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 支持亮色/暗色/跟随系统三种模式的主题切换方案，包含 CSS 变量定义、React Hook 封装、系统偏好监听、闪烁防止 |
| 能做什么 | 实现无缝的主题切换体验，支持 localStorage 持久化和系统偏好自动跟随 |
| 怎么用 | 定义 `:root` 和 `.dark` 的 CSS 变量 → 使用 useTheme Hook 管理主题状态 → 在 `<head>` 中内联初始化脚本防止闪烁 |
| 原理和工作流程 | 初始化读取 localStorage 或系统偏好 → 设置 `class` 或 `data-theme` → CSS 变量自动更新 → 监听系统偏好变化 |
| 缺点 | 需要为所有组件定义暗色样式；内联脚本增加了 HTML 体积；第三方组件可能不支持暗色模式 |

## 3.4 组件 API 设计原则（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 组件 API 设计的五条核心原则：一致性、可组合性、受控/非受控双模式、asChild 模式、正向布尔属性 |
| 能做什么 | 提升组件库的易用性和一致性，降低使用者的学习成本 |
| 怎么用 | 统一命名规范（size: sm/md/lg）→ 支持受控和非受控 → 使用 asChild 支持多态 → 用 disabled 而非 enabled=false |
| 原理和工作流程 | 设计阶段制定 API 规范 → 组件开发时遵循规范 → Code Review 时检查一致性 |
| 缺点 | 严格遵循规范可能增加开发时间；需要在灵活性和一致性之间权衡 |
