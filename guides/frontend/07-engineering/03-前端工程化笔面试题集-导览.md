### 1. Webpack 中 Loader 的作用是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Loader 是 Webpack 的文件转换器，将非 JavaScript 文件（CSS、TypeScript、图片等）转换为 Webpack 能处理的模块 |
| 能做什么 | 实现不同资源类型的统一模块化管理，使得 Webpack 能处理 JS 之外的任何文件类型 |
| 怎么用 | `module.rules: [{ test: /\.js$/, use: 'babel-loader' }]` |
| 原理和工作流程 | Loader 本质是函数，接收源文件内容，返回转换后的结果。在 Webpack 打包流程中，每个 Module 根据 rules 匹配对应 Loader 链，从右向左依次执行转换。与 Plugin 的区别在于 Loader 只处理单个文件，Plugin 介入整个打包生命周期 |
| 缺点 | 不能做跨模块操作；配置顺序错误会导致构建失败 |

### 2. Webpack 中 Plugin 的作用是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Plugin 是 Webpack 的功能扩展器，通过 hooks 机制在打包生命周期的各个阶段执行自定义任务 |
| 能做什么 | 实现生成 HTML 文件、提取 CSS 为独立文件、压缩代码、定义环境变量、分析打包体积等 Loader 无法完成的全局功能 |
| 怎么用 | `plugins: [new HtmlWebpackPlugin({ template: './public/index.html' })]` |
| 原理和工作流程 | Plugin 是一个包含 `apply(compiler)` 方法的类，接收 Compiler 对象后通过 `compiler.hooks` 注册到特定生命周期阶段（如 emit 修改输出资源、done 输出构建报告）。与 Loader 的核心区别在于处理对象是整个打包流程而非单个文件 |
| 缺点 | 编写 Plugin 需要深入理解 Webpack 内部钩子机制和 Compilation 对象 |

### 3. Vite 开发环境启动快的主要原因是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Vite 利用浏览器原生 ES Module 能力，开发时按需编译，无需像 Webpack 那样先打包整个应用 |
| 能做什么 | 实现秒级冷启动，解决 Webpack 大型项目启动慢（几十秒到几分钟）的痛点 |
| 怎么用 | `pnpm create vite my-app --template vue-ts` 创建项目，`pnpm dev` 启动 |
| 原理和工作流程 | 浏览器请求模块 → Vite Dev Server 拦截 → esbuild（Go 语言）预构建 node_modules 依赖 → 按需编译源码为 ES Module → 返回。只编译浏览器当前请求的模块，而非一次性编译所有文件。esbuild 比 Webpack 的 JS 实现快 10-100 倍 |
| 缺点 | 依赖浏览器支持 ESM；首次加载时模块请求数量可能较多 |

### 4. 以下关于 Tree Shaking 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | Tree Shaking 基于 ES Module 的静态导入（import/export）特性，在编译时分析依赖关系并移除未使用代码 |
| 能做什么 | 减少打包体积，剔除未被引用的函数、类、变量，尤其对大型第三方库效果显著 |
| 怎么用 | `package.json` 中设置 `"sideEffects": false`；使用 ES Module 语法；production 模式构建 |
| 原理和工作流程 | ES Module 的 import/export 在编译时即可确定引用关系（静态分析），构建工具标记所有未被引用的导出为 dead code，Terser 在打包阶段移除标记代码。CommonJS 的 require 是动态的，无法在编译时做静态分析，因此不支持 Tree Shaking |
| 缺点 | 仅支持 ES Module；sideEffects: false 误用会移除全局 CSS 等有副作用的模块 |

### 5. Webpack 的 HMR 热模块替换原理是什么

| 维度 | 内容 |
|------|------|
| 是什么 | HMR 通过 WebSocket 在浏览器和 Dev Server 之间建立长连接，文件变更后只推送变更模块进行热替换，不刷新整个页面 |
| 能做什么 | 修改代码后保持应用状态不丢失，大幅提升开发效率 |
| 怎么用 | 配置 `devServer: { hot: true }`；模块中通过 `module.hot.accept()` 接收更新 |
| 原理和工作流程 | 文件变更 → Webpack 重新编译变更模块 → WebSocket 推送 hash 事件和更新清单（manifest.json）→ 浏览器 HMR Runtime 请求变更模块的增量更新 → 执行 module.hot.accept() 完成热替换。若模块未定义 accept 则向上冒泡，直到被处理或整页刷新 |
| 缺点 | 复杂状态（如 Vuex/Pinia store）可能无法热替换；某些场景需手动编写 accept 和 dispose 逻辑 |

### 6. 以下哪个不是 Webpack 的内置性能优化手段

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Webpack 内置优化手段（Tree Shaking、Code Splitting、Scope Hoisting）与 Vite 特性（Lazy Compilation）的区分 |
| 能做什么 | 验证候选人对不同构建工具核心优化特性的准确认知 |
| 怎么用 | Tree Shaking：production 模式自动启用；Code Splitting：splitChunks 配置；Scope Hoisting：production 模式自动启用 |
| 原理和工作流程 | Tree Shaking 移除未使用代码，Code Splitting 将代码拆分为多个 chunk 按需加载，Scope Hoisting 将多个模块合并到一个函数作用域减少闭包开销。Lazy Compilation（惰性编译/按需编译）是 Vite 的核心特性而非 Webpack 内置优化 |
| 缺点 | Webpack 5 有实验性的 lazy compilation 特性，可能导致混淆 |

### 7. ESLint 和 Prettier 的区别是什么

| 维度 | 内容 |
|------|------|
| 是什么 | ESLint 检查代码质量和潜在错误（逻辑问题、最佳实践），Prettier 格式化代码风格（缩进、引号、分号等纯格式问题） |
| 能做什么 | ESLint 发现未使用变量、可能的空指针等逻辑问题；Prettier 统一团队代码风格，消除格式差异 |
| 怎么用 | 配合使用：安装 `eslint-config-prettier` 在 ESLint 的 extends 末尾添加 `'prettier'`，关闭冲突规则 |
| 原理和工作流程 | ESLint 将源码解析为 AST，遍历节点匹配规则，报告逻辑错误；Prettier 解析为自己的 AST 后按固定规则重新输出，完全忽略原有格式。两者分工明确：ESLint 管"对不对"，Prettier 管"好不好看" |
| 缺点 | 两者配合不当会导致规则冲突（格式化后 ESLint 报错）；部分团队可能觉得 Prettier 的"有主见"风格不够灵活 |

### 8. 以下关于 pnpm 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | pnpm 使用硬链接（hard link）和符号链接（symlink）管理依赖，所有项目共享同一份依赖文件，大幅节省磁盘空间 |
| 能做什么 | 实现非扁平化的 node_modules 结构（严格依赖访问）、更快的安装速度、原生 Monorepo 支持 |
| 怎么用 | `pnpm add express` 安装依赖；`pnpm-workspace.yaml` 配置 Monorepo |
| 原理和工作流程 | pnpm 将依赖存储在全局 store（内容寻址存储），项目 node_modules 通过硬链接指向 store 中的文件，通过符号链接构建依赖树。与 npm 的扁平化结构不同，pnpm 的非扁平化结构确保包只能访问自身声明的依赖（严格模式），避免幽灵依赖问题 |
| 缺点 | 与某些依赖幽灵依赖的旧项目可能存在兼容性问题 |

### 9. Vite 生产环境使用什么工具进行打包

| 维度 | 内容 |
|------|------|
| 是什么 | Vite 生产环境使用 Rollup 进行打包，esbuild 仅用于代码压缩（minify） |
| 能做什么 | Rollup 在打包 ES Module 代码方面有天然优势，输出代码更干净、体积更小，天然支持 Tree Shaking |
| 怎么用 | `vite.config.ts` 中通过 `build.rollupOptions` 配置 Rollup 选项 |
| 原理和工作流程 | 开发环境：Vite 利用浏览器原生 ESM 按需编译，esbuild 预构建依赖。生产环境：Vite 委托 Rollup 打包（保证兼容性和优化效果），esbuild 仅做代码压缩。Rollup 的 Tree Shaking 比 Webpack 更彻底，输出更简洁 |
| 缺点 | Rollup 生态插件不如 Webpack 丰富；部分 Webpack 特有的功能（如 require.context）在 Rollup 中无法直接使用 |

### 10. Webpack 中 chunk 和 bundle 的区别是什么

| 维度 | 内容 |
|------|------|
| 是什么 | chunk 是 Webpack 内部处理时的代码块（中间产物），bundle 是最终输出到文件系统的文件（最终产物），Module 是源码中的每个文件（最小单位） |
| 能做什么 | 理解三者关系有助于配置代码分割、分析打包产物、优化构建性能 |
| 怎么用 | 通过 SplitChunksPlugin 控制 chunk 拆分策略，通过 output.filename 控制 bundle 命名 |
| 原理和工作流程 | Module（源码文件）→ 经 Loader 转换 → 多个 Module 组成 Chunk（Webpack 内部概念）→ Chunk 经过压缩优化 → 输出为 Bundle（最终文件）。一个 Chunk 可对应一个 Bundle，也可多个 Chunk 合并为一个 Bundle。入口文件和动态 import 各自产生 Chunk |
| 缺点 | 概念抽象，初学者容易混淆；Chunk 是 Webpack 内部概念，不直接暴露给用户 |

### 1. Webpack 的打包流程是什么

| 维度 | 内容 |

### 2. Loader 和 Plugin 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | Loader 是文件转换器（处理单个文件），Plugin 是功能扩展器（介入整个打包生命周期），这是 Webpack 面试中最核心的问题之一 |
| 能做什么 | 验证候选人对 Webpack 两大扩展机制职责、执行时机、调用方式、编写方式的完整理解 |
| 怎么用 | Loader：配置 module.rules 匹配文件后链式转换；Plugin：在 plugins 数组中实例化 |
| 原理和工作流程 | Loader 是函数 `source => transformedSource`，链式从右向左执行，只在模块加载时对单个文件进行转换。Plugin 是包含 `apply(compiler)` 方法的类，通过 compiler.hooks 在生命周期各阶段执行全局任务。关键区别：Loader 做"翻译"工作，Plugin 做"扩展"工作 |
| 缺点 | 两者职责边界有时模糊（如 MiniCssExtractPlugin 的 loader 部分），初学者容易混淆 |

### 3. Vite 的原理和优势

| 维度 | 内容 |
|------|------|
| 是什么 | Vite 开发环境利用浏览器原生 ESM + esbuild 预构建 + 按需编译实现零打包；生产环境使用 Rollup 打包 |
| 能做什么 | 实现秒级冷启动、毫秒级 HMR、开箱即用的 TypeScript/CSS 预处理器支持，配置简洁 |
| 怎么用 | `pnpm create vite my-app --template vue-ts` 创建项目，vite.config.ts 配置 plugins、resolve.alias、server.proxy |
| 原理和工作流程 | 开发环境：浏览器请求 → Vite Dev Server 拦截 → esbuild 预构建 node_modules 依赖 → 按需编译源码为 ES Module → 返回。HMR：chokidar 监听文件变化 → WebSocket 推送变更路径 → 浏览器请求变更模块。生产环境委托 Rollup 打包，esbuild 压缩 |
| 缺点 | 开发环境需浏览器支持 ESM；生产构建依赖 Rollup 生态，与 Webpack 插件不兼容 |

### 4. Tree Shaking 的原理和实现条件

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 ES Module 静态导入特性在编译时分析依赖关系，移除未被引用的导出代码（dead code） |
| 能做什么 | 减少打包体积，对大型第三方库（如 lodash）效果显著 |
| 怎么用 | 使用 ES Module 语法；package.json 设置 "sideEffects": false；production 模式构建；确保 Babel 不将 ES Module 转为 CommonJS |
| 原理和工作流程 | ES Module 的 import/export 在编译时即可确定引用关系，构建工具标记所有未被引用的导出为 dead code，Terser 在打包阶段移除标记代码。CommonJS 的 require 是动态的（运行时确定），无法在编译时进行静态分析 |
| 缺点 | 仅支持 ES Module；sideEffects 配置不当会误删全局 CSS 等有副作用模块；对使用原型链扩展的库可能误删 |

### 6. CI/CD 流程是什么

| 维度 | 内容 |
|------|------|
| 是什么 | CI（持续集成）是代码合并后自动构建测试的实践，CD（持续部署）是自动将构建产物部署到环境的流程 |
| 能做什么 | 减少手动操作避免人为失误，快速发现集成问题，提高发布频率和质量，统一构建环境 |
| 怎么用 | GitHub Actions 配置 YAML 流水线：代码提交 → 依赖安装 → lint → 测试 → 构建 → 部署 |
| 原理和工作流程 | CI 阶段：push 触发 → 拉取代码 → pnpm install --frozen-lockfile → lint 检查 → 单元测试 → 构建产物。CD 阶段：构建产物部署到测试/预发布环境 → 自动化测试 → 审批或自动发布到生产。常用工具：GitHub Actions、GitLab CI/CD、Jenkins、Vercel、Netlify |
| 缺点 | 流水线配置需要 DevOps 知识；构建时间较长可能影响开发效率 |

### 7. Monorepo 的优缺点和 pnpm workspaces 配置

| 维度 | 内容 |
|------|------|
| 是什么 | Monorepo 是将多个项目/包放在单一仓库中管理的策略，通过 pnpm workspaces 实现 |
| 能做什么 | 统一配置、代码共享、原子提交、依赖管理统一，适合多应用/多包的大型项目 |
| 怎么用 | pnpm-workspace.yaml：`packages: ['packages/*', 'apps/*']`；子包通过 `"@my-app/shared": "workspace:*"` 引用本地包 |
| 原理和工作流程 | 优点：一份 ESLint/Prettier/TypeScript 配置所有包共享、公共代码放在 packages/shared 直接引用、一次提交修改多个包。缺点：仓库体积大克隆慢、构建时间可能较长需 Turborepo 优化、权限管理困难、对工具链要求高。pnpm 通过符号链接管理 workspace 内包依赖 |
| 缺点 | 不适合小团队或独立项目；需要 Turborepo/Nx 等工具管理构建顺序和缓存 |

### 8. 前端部署方案有哪些 SPA 的 Nginx 配置要点是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 四种部署方案（静态托管/Nginx 自建/Docker 容器化/CDN+OSS）及 Nginx 的 SPA 五大配置要点 |
| 能做什么 | 根据项目规模和需求选择合适的部署方案，确保前端路由正常工作、资源高效传输 |
| 怎么用 | Nginx：`try_files $uri $uri/ /index.html`（SPA fallback）、`gzip on`（压缩）、`location /api/ { proxy_pass ... }`（反向代理）、静态资源 `expires 1y`、HTTPS 强制跳转 |
| 原理和工作流程 | 路由 fallback 确保 Vue/React Router 的 history 模式下刷新不 404；gzip 减少传输体积 70% 以上；反向代理将 /api/ 请求转发到后端服务解决跨域；带哈希的静态资源设置长期缓存（immutable）；HTTP 301 强制跳转 HTTPS |
| 缺点 | 自建 Nginx 需要运维知识；静态托管平台有流量和构建次数限制 |

### 4. 设计一个前端错误监控和日志上报方案

| 维度 | 内容 |
|------|------|
| 是什么 | 一套包含错误捕获（JS 运行时/Promise/资源加载/框架组件）、批量上报、Source Map 还原的前端错误监控方案 |
| 能做什么 | 实时发现线上错误，定位问题根源，减少用户影响范围 |
| 怎么用 | 封装 ErrorMonitor 类，初始化时注册 window.onerror、unhandledrejection、资源 error 等全局监听器 |
| 原理和工作流程 | 错误捕获层：window.onerror 捕获 JS 运行时错误、unhandledrejection 捕获 Promise 未处理拒绝、捕获阶段 error 事件捕获资源加载失败、框架错误边界（Vue errorHandler/React ErrorBoundary）。上报层：队列缓存 + 批量上报（maxBatchSize 阈值 + flushInterval 定时），使用 sendBeacon 确保页面关闭时也能上报。Source Map 还原：构建时生成 hidden-source-map，服务端通过 source-map 库解析错误堆栈 |
| 缺点 | 错误监控本身也会消耗资源，需要控制采样率和上报频率；Source Map 管理需要额外基础设施 |

### 5. 设计一个前端灰度发布方案

| 维度 | 内容 |
|------|------|
| 是什么 | 支持按用户比例、白名单、地域等多维度进行灰度分流的前端发布方案，含 Nginx 层和前端代码层两种实现 |
| 能做什么 | 实现新功能小流量验证，降低发布风险，发现问题后快速回滚 |
| 怎么用 | Nginx 层：基于 Cookie 的 map 分流；前端代码层：基于用户 ID 哈希判断是否进入灰度，配合远程配置中心动态调整灰度策略 |
| 原理和工作流程 | 灰度判断：用户 ID 哈希取模 `hashCode(userId) % 100 < percentage` 确保同一用户始终进入同一版本（一致性哈希）。白名单优先：白名单用户直接进入灰度。强制版本：调试用参数覆盖。配置动态下发：从远程配置中心获取灰度比例和白名单，无需重新部署即可调整。发布流程：功能开发 → 灰度分支构建 → 部署灰度环境 → 小流量验证 → 监控指标 → 逐步放量（10% → 30% → 50% → 100%）→ 全量 → 清理灰度环境 |
| 缺点 | 需要额外的基础设施（配置中心、灰度环境）；哈希取模在用户量少时可能分布不均 |
