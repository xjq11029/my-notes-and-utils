## 一、核心概念

### 1.1 质量门禁定义

**质量门禁**（Quality Gate）是代码合并前必须通过的自动化检查关卡。用**机场安检**来类比：

| 机场安检 | 质量门禁 | 作用 |
|---|---|---|
| 行李检查（X 光机） | Lint 检查 | 扫描代码格式和潜在问题 |
| 身份验证（身份证） | 类型检查 | 验证类型系统完整性 |
| 安检扫描（金属探测） | 单元测试 | 验证功能逻辑正确性 |
| 登机确认（登机牌） | 构建验证 | 确保项目可以成功构建 |
| 危险品排查 | 依赖安全扫描 | 检查依赖漏洞 |

**质量门禁的核心价值**：将"人肉审查"转变为"自动化检查"，确保每次代码合并都经过标准化的质量验证，避免人为疏忽导致的线上问题。

```typescript
// 质量门禁的伪代码抽象
interface QualityGate {
  name: string;
  description: string;
  run: () => Promise<QualityGateResult>;
  blocking: boolean; // 失败是否阻断合并
}

interface QualityGateResult {
  passed: boolean;
  errors: string[];
  warnings: string[];
  duration: number; // 毫秒
}

// 理想的质量门禁流水线
const pipeline: QualityGate[] = [
  { name: 'Lint', blocking: true, run: runLint },
  { name: 'TypeCheck', blocking: true, run: runTypeCheck },
  { name: 'UnitTest', blocking: true, run: runUnitTest },
  { name: 'Build', blocking: true, run: runBuild },
  { name: 'SecurityAudit', blocking: true, run: runAudit },
  { name: 'BundleSize', blocking: false, run: runBundleAnalyze }, // 非阻断，仅告警
];
```

### 1.2 门禁体系

完整的质量门禁体系分为五个层级，从快到慢、从浅到深逐层递进：

| 层级 | 检查内容 | 执行速度 | 阻断级别 | 工具 |
|---|---|---|---|---|
| 1. Lint 检查 | 代码风格、潜在错误、最佳实践 | 极快（秒级） | 阻断 | ESLint + Prettier |
| 2. 类型检查 | TypeScript 类型正确性 | 快（十秒级） | 阻断 | `tsc --noEmit` |
| 3. 单元测试 | 逻辑正确性、边界条件 | 中等（分钟级） | 阻断 | Vitest / Jest |
| 4. 构建验证 | 项目可构建性 | 中（分钟级） | 阻断 | `next build` / `vite build` |
| 5. 依赖安全扫描 | 已知漏洞检测 | 慢（分钟级） | 阻断 | `pnpm audit` / Snyk |

```typescript
// 门禁体系的设计原则
// 1. 快速失败：越快的检查越靠前，让开发者快速获得反馈
// 2. 阻断优先：失败的检查立即阻断后续流程
// 3. 并行执行：同一层级的检查可以并行运行
// 4. 结果可见：所有检查结果汇总到一个报告中

const qualityGatePipeline = {
  stage1: ['lint', 'format-check'],           // 并行，秒级
  stage2: ['type-check'],                      // 依赖 stage1，十秒级
  stage3: ['unit-test', 'integration-test'],   // 依赖 stage2，分钟级
  stage4: ['build'],                           // 依赖 stage3，分钟级
  stage5: ['security-audit', 'bundle-analyze'], // 依赖 stage4，分钟级
};
```

### 1.3 CI/CD 流水线中的质量门禁

在 GitHub Actions 或 GitLab CI 中，质量门禁通过 **stage/job 设计** 实现，每个 stage 包含一组并行 job，stage 之间串行依赖。

```yaml
# 质量门禁的 CI Stage 设计
# GitHub Actions 实现
name: Quality Gate

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  # ============ Stage 1: 快速检查（并行） ============
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint

  type-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
      - run: pnpm install --frozen-lockfile
      - run: pnpm type-check

  # ============ Stage 2: 测试（依赖 Stage 1） ============
  test:
    needs: [lint, type-check]  # 必须等 lint 和 type-check 通过
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3]  # 测试分片，并行执行
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
      - run: pnpm install --frozen-lockfile
      - run: pnpm test -- --shard=${{ matrix.shard }}/${{ strategy.job-total }}

  # ============ Stage 3: 构建（依赖 Stage 2） ============
  build:
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: .next/

  # ============ Stage 4: 安全与审计（依赖 Stage 3） ============
  security:
    needs: [build]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
      - run: pnpm install --frozen-lockfile
      # 注意：pnpm 10.x 中 audit 命令参数可能已变更，请参考 pnpm audit --help 确认
      - run: pnpm audit --audit-level high
```

## 二、底层原理

### 2.1 Husky + lint-staged 原理

**Husky** 利用 Git Hooks 机制，在 Git 操作（如 commit、push）的特定时机执行自定义脚本。**lint-staged** 进一步优化：只检查 `git add` 暂存区的文件，而不是整个项目。

```
开发者执行 git commit
    |
    v
Git 触发 pre-commit hook
    |
    v
Husky 拦截 hook → 执行 .husky/pre-commit 脚本
    |
    v
lint-staged 读取暂存区文件列表
    |
    v
对匹配的文件执行配置的检查命令（lint-staged.config.js）
    |
    ├── *.ts → eslint --fix
    ├── *.ts → prettier --write
    └── *.css → stylelint --fix
    |
    ├── 全部通过 → git commit 继续执行
    └── 任一失败 → git commit 被中断
```

```bash
# 安装 Husky 和 lint-staged
pnpm add -D husky lint-staged

# 初始化 Husky
pnpm exec husky init
```

```bash
# .husky/pre-commit —— Git pre-commit 钩子
#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

pnpm lint-staged
```

```bash
# .husky/commit-msg —— Git commit-msg 钩子
#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

pnpm exec commitlint --edit $1
```


### 2.2 CI 中的并行执行策略

CI 流水线的执行效率直接影响开发体验。核心优化策略包括：依赖缓存、并行 job、矩阵构建。

```yaml
# .github/workflows/ci.yml —— 并行执行策略
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  # ============ 策略 1: 依赖缓存 ============
  # 使用 pnpm 的缓存机制，避免每次重新下载依赖
  install:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v5
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'  # 自动缓存 ~/.pnpm-store

      - name: Cache node_modules
        uses: actions/cache@v4
        with:
          path: node_modules
          key: ${{ runner.os }}-pnpm-${{ hashFiles('pnpm-lock.yaml') }}
          restore-keys: |
            ${{ runner.os }}-pnpm-

      - run: pnpm install --frozen-lockfile

  # ============ 策略 2: 并行 job ============
  # 多个独立检查同时运行，互不阻塞
  lint:
    needs: [install]
    runs-on: ubuntu-latest
    # ... lint 配置

  type-check:
    needs: [install]
    runs-on: ubuntu-latest
    # ... type-check 配置

  # ============ 策略 3: 矩阵构建 ============
  # 在不同 Node.js 版本和操作系统上并行测试
  test:
    needs: [install]
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false  # 一个失败不影响其他继续运行
      matrix:
        os: [ubuntu-latest, windows-latest]
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v5
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'pnpm'

      - run: pnpm install --frozen-lockfile
      - run: pnpm test
```

### 2.3 覆盖率报告与质量门禁

测试覆盖率是衡量测试质量的重要指标，但覆盖率不等于质量。需要设置合理的阈值，并通过 CI 强制执行。

```typescript
// vitest.config.ts —— 覆盖率配置
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    globals: true,
    // 覆盖率配置
    coverage: {
      provider: 'v8',           // 使用 V8 原生覆盖率（更快）
      reporter: ['text', 'json', 'html', 'lcov'],
      reportsDirectory: './coverage',
      // 覆盖率阈值：低于阈值则测试失败
      thresholds: {
        // 全局阈值
        lines: 80,
        functions: 80,
        branches: 75,
        statements: 80,
        // 按文件路径设置不同阈值
        // 'src/components/**': {
        //   lines: 90,
        //   branches: 85,
        // },
      },
      include: ['src/**/*.{ts,tsx}'],
      exclude: [
        'src/**/*.test.{ts,tsx}',
        'src/**/*.spec.{ts,tsx}',
        'src/**/*.d.ts',
        'src/types/**',
      ],
    },
  },
});
```

### 2.4 构建产物验证

构建产物验证确保每次构建的输出质量，包括 Bundle 体积分析和 Chunk 大小监控。

```typescript

const withBundleAnalyzer = bundleAnalyzer({
  enabled: process.env.ANALYZE === 'true',
});

  // 构建输出配置

  // 禁止生产环境 sourcemap（减小体积）
  productionBrowserSourceMaps: false,
  // 压缩配置
  compress: true,
};

```

```javascript
// scripts/check-bundle-size.js —— 体积预算检查
import { readFileSync, existsSync, readdirSync } from 'fs';
import { join, dirname } from 'path';

const BUILD_DIR = '.next';

// 体积预算（单位：KB）—— 使用路径前缀匹配实际文件
const BUDGET = {
  'static/chunks/framework': 50,    // 框架核心代码
  'static/chunks/main': 200,         // 应用主 bundle
  'static/chunks/pages/_app': 100,   // _app 页面
  'static/css': 100,                  // CSS 总大小
};

function getBundleSize(pattern) {
  const dir = join(BUILD_DIR, dirname(pattern));
  const prefix = pattern.split('/').pop();
  if (!existsSync(dir)) return 0;
  // 匹配含有哈希后缀的文件名（如 framework-abc123.js）
  const files = readdirSync(dir).filter(f => f.startsWith(prefix));
  if (files.length === 0) return 0;
  return files.reduce((total, file) => {
    const stat = readFileSync(join(dir, file));
    return total + stat.length / 1024;
  }, 0);
}

function checkBudget() {
  let hasViolation = false;

  for (const [pattern, maxSize] of Object.entries(BUDGET)) {
    const size = getBundleSize(pattern);
    if (size > maxSize) {
      console.error(`[Bundle Budget] ${pattern}: ${size.toFixed(1)}KB > ${maxSize}KB`);
      hasViolation = true;
    } else {
      console.log(`[Bundle Budget] ${pattern}: ${size.toFixed(1)}KB (OK)`);
    }
  }

  if (hasViolation) {
    console.error('\nBundle size exceeds budget!');
    process.exit(1);
  }
}

checkBudget();
```

### 3.2 CI 流水线设计

完整的 GitHub Actions 五阶段质量门禁流水线。

```yaml
# .github/workflows/quality-gate.yml
name: Quality Gate

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  NODE_VERSION: 20
  PNPM_VERSION: 9

jobs:
  # ============ Stage 1: Lint 检查 ============
  lint:
    name: 🔍 Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with: { version: ${{ env.PNPM_VERSION }} }
      - uses: actions/setup-node@v4
        with: { node-version: ${{ env.NODE_VERSION }}, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm format:check

  # ============ Stage 2: 类型检查 ============
  type-check:
    name: 🔷 Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with: { version: ${{ env.PNPM_VERSION }} }
      - uses: actions/setup-node@v4
        with: { node-version: ${{ env.NODE_VERSION }}, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm type-check

  # ============ Stage 3: 测试（带覆盖率） ============
  test:
    name: 🧪 Test
    needs: [lint, type-check]
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3]
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with: { version: ${{ env.PNPM_VERSION }} }
      - uses: actions/setup-node@v4
        with: { node-version: ${{ env.NODE_VERSION }}, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - name: Run tests with coverage
        run: pnpm test -- --coverage --shard=${{ matrix.shard }}/${{ strategy.job-total }}

      - name: Upload coverage
        uses: actions/upload-artifact@v4
        with:
          name: coverage-${{ matrix.shard }}
          path: coverage/

  # 汇总覆盖率报告
  coverage-report:
    name: 📊 Coverage Report
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { pattern: 'coverage-*', path: coverage/ }
      - name: Merge coverage reports
        run: pnpm dlx istanbul-merge --out coverage/coverage-final.json coverage/**/coverage-final.json
      - name: Check coverage thresholds
        run: pnpm dlx istanbul-threshold --file coverage/coverage-final.json --lines 80 --functions 80 --branches 75 --statements 80

  # ============ Stage 4: 构建验证 ============
  build:
    name: 🏗️ Build
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with: { version: ${{ env.PNPM_VERSION }} }
      - uses: actions/setup-node@v4
        with: { node-version: ${{ env.NODE_VERSION }}, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - name: Check bundle size
        run: node scripts/check-bundle-size.js
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: .next/

  # ============ Stage 5: 安全审计 ============
  security-audit:
    name: 🔒 Security Audit
    needs: [build]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with: { version: ${{ env.PNPM_VERSION }} }
      - uses: actions/setup-node@v4
        with: { node-version: ${{ env.NODE_VERSION }}, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm audit --audit-level high
```

### 3.4 Bundle 体积监控

配置 Bundle Analyzer 和体积预算，确保每次构建不会意外增大产物。

```typescript
// next.config.ts —— 完整配置
import type { NextConfig } from 'next';
import bundleAnalyzer from '@next/bundle-analyzer';

const withBundleAnalyzer = bundleAnalyzer({
  enabled: process.env.ANALYZE === 'true',
  openAnalyzer: false,
});

const nextConfig: NextConfig = {
  productionBrowserSourceMaps: false,
  compress: true,
  // 实验性配置
  experimental: {
    optimizePackageImports: [
      'lodash',
      'date-fns',
      '@radix-ui/react-dialog',
      '@radix-ui/react-dropdown-menu',
    ],
  },
  // 配置 webpack 用于体积优化
  webpack: (config, { isServer }) => {
    if (!isServer) {
      // 客户端体积优化
      config.optimization.splitChunks = {
        chunks: 'all',
        maxInitialRequests: 25,
        minSize: 20000,
        cacheGroups: {
          // 框架核心：React 等
          framework: {
            test: /[\\/]node_modules[\\/](react|react-dom|next)[\\/]/,
            name: 'framework',
            priority: 40,
          },
          // UI 组件库
          ui: {
            test: /[\\/]node_modules[\\/](@radix-ui|@headlessui)[\\/]/,
            name: 'ui',
            priority: 30,
          },
          // 通用工具库
          lib: {
            test: /[\\/]node_modules[\\/](lodash|date-fns|zod)[\\/]/,
            name: 'lib',
            priority: 20,
          },
          // 其余 vendor
          vendor: {
            test: /[\\/]node_modules[\\/]/,
            name: 'vendor',
            priority: 10,
          },
        },
      };
    }
    return config;
  },
};

export default withBundleAnalyzer(nextConfig);
```

## 四、常见面试题

**Q1：什么是质量门禁？它的核心价值是什么？**

**答案要点**：
- 质量门禁是代码合并前必须通过的自动化检查关卡
- 用机场安检类比：Lint 是行李检查，类型检查是身份验证，测试是安检扫描，构建是登机确认
- 核心价值：将"人肉审查"转变为"自动化检查"，标准化质量验证，避免人为疏忽
- 五层体系：Lint 检查 → 类型检查 → 单元测试 → 构建验证 → 依赖安全扫描

**Q2：Husky + lint-staged 的工作原理是什么？**

**答案要点**：
- Husky 利用 Git Hooks 机制，在 Git 操作（commit、push）的特定时机执行自定义脚本
- lint-staged 只检查 `git add` 暂存区的文件，避免全量检查
- 工作流程：`git commit` → Git 触发 pre-commit hook → Husky 拦截 → lint-staged 读取暂存文件 → 对匹配文件执行 ESLint/Prettier/Stylelint → 通过则继续，失败则中断
- commitlint 在 commit-msg hook 中验证提交信息格式（如 Conventional Commits 规范）

**Q3：如何在 CI 中实现并行执行优化？**

**答案要点**：
- 依赖缓存：使用 `actions/cache` 缓存 node_modules 和 pnpm store
- 并行 job：同一 stage 的 job 默认并行执行，互不依赖
- 矩阵构建：`strategy.matrix` 在不同 Node.js 版本和操作系统上并行测试
- 测试分片：`vitest --shard=1/3` 将测试分片到多个 job 并行运行
- 并发控制：`concurrency.group` 取消同一 PR 的旧运行

**Q4：测试覆盖率是什么？如何设置合理的阈值？**

**答案要点**：
- 覆盖率指标：行覆盖率（lines）、函数覆盖率（functions）、分支覆盖率（branches）、语句覆盖率（statements）
- 阈值设置原则：核心逻辑（utils/hooks）要求高（85-95%），UI 组件要求低（70-80%），配置文件不需要
- Vitest 配置：`coverage.thresholds` 设置全局和按目录的阈值
- 覆盖率不等于质量，100% 覆盖率不代表没有 Bug
- 需要关注的是关键路径的覆盖，而非盲目追求数字

**Q5：Bundle 体积监控的作用是什么？如何配置？**

**答案要点**：
- 作用：防止引入大型依赖导致包体积膨胀、监控 chunk 拆分策略是否合理、提前发现性能回归
- 工具：`@next/bundle-analyzer` 可视化分析、`webpack-bundle-analyzer` 交互式分析
- 体积预算：为不同 chunk 设置最大体积限制，超出则 CI 失败
- 优化策略：`splitChunks` 合理拆分、`optimizePackageImports` 优化命名导入、tree-shaking 移除无用代码

## 五、避坑指南

| 坑点 | 现象 | 原因 | 解决方案 |
|---|---|---|---|
| Husky 钩子不触发 | `git commit` 后 Husky 脚本没有执行，lint-staged 检查被跳过 | `.husky/` 目录权限不正确，或 Git hooks 路径配置错误（`core.hooksPath`） | 执行 `pnpm exec husky init` 重新初始化；检查 `git config core.hooksPath` 是否指向 `.husky`；确保 `.husky/pre-commit` 文件有执行权限 |
| CI 覆盖率阈值设置过高导致频繁失败 | 测试覆盖率 79% 接近 80% 阈值，每次开发新功能都因覆盖率不足失败 | 覆盖率阈值设置不合理，未区分核心逻辑和 UI 组件的不同要求 | 按目录设置不同阈值：核心逻辑（utils/hooks）85-95%，UI 组件 70-80%；使用 watermarks 替代硬阈值，给出警告而非直接失败 |
| 并行构建时缓存冲突 | 多个 CI job 同时写入缓存，导致不确定性的构建失败 | `actions/cache` 的 restore-keys 命中旧缓存，不同 job 的依赖版本不一致 | 使用 `hashFiles('pnpm-lock.yaml')` 作为缓存 key 确保一致性；不同 job 使用独立的缓存 key；构建前执行 `pnpm install --frozen-lockfile` 验证 |
