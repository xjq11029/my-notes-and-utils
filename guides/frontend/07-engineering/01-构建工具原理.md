# 构建工具原理

> 模块：07-engineering（第7周 前端工程化）
> 定位：核心基础原理篇

---

## 一、核心概念

前端构建工具是前端工程化的核心基础设施，它解决了现代前端开发中"源码无法直接在浏览器中运行"的问题。随着前端项目规模从几 KB 增长到几百 MB，构建工具也从简单的文件合并演化为复杂的编译流水线。

### 前端构建工具演进

| 阶段 | 代表工具 | 解决的问题 | 局限性 |
|------|---------|-----------|--------|
| 无构建时代 | 无 | 直接编写 HTML/CSS/JS | 模块化用全局变量，文件依赖靠手动排序，无压缩混淆 |
| 任务流时代 | Grunt / Gulp | 自动化执行重复任务（压缩、合并、检查） | 只是任务编排，不具备模块打包能力，配置繁琐 |
| 打包时代 | Webpack / Rollup / Parcel | 模块化打包，资源统一管理，Tree Shaking，代码分割 | 配置复杂，大型项目构建慢 |
| 原生 ESM 时代 | Vite / Snowpack | 开发时零打包，按需编译，极速启动和 HMR | 浏览器兼容性要求高，生态不如 Webpack 成熟 |

**各阶段详细说明**：

1. **无构建时代**：使用 `<script>` 标签引入 JS 文件，依赖顺序靠手动维护，全局变量污染严重，代码无法压缩和混淆
2. **Grunt/Gulp 时代**：通过配置文件定义任务流水线，自动化执行压缩、合并、检查等操作。Gulp 基于 Node.js Stream，比 Grunt 基于文件 I/O 更快，但它们本质上只是任务编排器，不具备模块打包能力
3. **Webpack 时代**：以模块为核心理念，将一切资源（JS、CSS、图片、字体）都视为模块，通过 Loader 和 Plugin 构建出完整的依赖图，最终输出优化后的静态资源
4. **Vite 时代**：利用浏览器原生 ES Module 能力，开发时无需打包，按需编译，生产环境使用 Rollup 打包，实现了极致的开发体验

## 二、底层原理

### Webpack 核心概念

```javascript
// webpack.config.js 基础结构
const path = require('path')
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  // 入口：打包的起点，Webpack 从这里开始构建依赖图
  entry: './src/index.js',

  // 输出：打包后的文件输出位置
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'js/[name].[contenthash:8].js',
    clean: true // 每次构建前清空 dist 目录
  },

  // 模式：development(开发) / production(生产) / none
  mode: 'production',

  // Loader：转换非 JavaScript 文件
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: 'babel-loader'
      }
    ]
  },

  // Plugin：扩展 Webpack 功能
  plugins: [
    new HtmlWebpackPlugin({
      template: './public/index.html'
    })
  ],

  // 解析配置
  resolve: {
    extensions: ['.js', '.jsx', '.ts', '.tsx', '.json'],
    alias: {
      // 注意：Vite 配置文件内部支持 __dirname，但 ESM 中默认不可用
      '@': path.resolve(__dirname, 'src')
    }
  }
}
```

**核心概念解析**：

| 概念 | 说明 | 示例 |
|------|------|------|
| Entry（入口） | Webpack 打包的起点，可以是一个或多个文件 | `entry: './src/index.js'` |
| Output（输出） | 打包后的文件放在哪里，如何命名 | `output: { path: 'dist', filename: '[name].js' }` |
| Loader（转换器） | 将非 JS 文件转换为 Webpack 能识别的模块 | `babel-loader` 转换 ES6+ → ES5 |
| Plugin（插件） | 扩展 Webpack 功能，在打包生命周期中执行各种任务 | `HtmlWebpackPlugin` 生成 HTML |
| Mode（模式） | 设置 `development` / `production` / `none`，启用对应内置优化 | production 模式下自动启用压缩 |
| Chunk | 代码块，Webpack 打包过程中的中间产物，由多个 Module 组成 | 一个入口文件对应一个 Chunk |
| Bundle | 最终输出的文件，是 Chunk 经过处理和优化后的产物 | `dist/main.js` |
| Module（模块） | Webpack 中的最小单位，每个文件都是一个 Module | `./src/utils.js` |

**Chunk、Bundle、Module 的区别**：
- **Module**：源码中的每个文件都是 Module，包括 JS、CSS、图片等
- **Chunk**：Webpack 内部处理时的代码块，由多个 Module 组成。一个 Chunk 可能对应一个 Bundle，也可能多个 Chunk 合并为一个 Bundle（通过 SplitChunksPlugin）
- **Bundle**：最终构建输出的文件，是用户可以引入的、经过压缩优化的最终产物

### Webpack 打包流程

Webpack 的完整打包流程分为以下几个阶段：

```
初始化参数 → 开始编译 → 确定入口 → 编译模块 → 完成编译 → 输出资源 → 输出完成
```

**详细步骤**：

1. **初始化参数**：从 `webpack.config.js` 和命令行参数中读取配置，合并为最终配置对象
2. **创建 Compiler**：用合并后的配置初始化 Compiler 对象，它是 Webpack 的核心引擎，负责控制整个编译流程
3. **加载插件**：依次调用所有 Plugin 的 `apply` 方法，将 Compiler 对象传入，让 Plugin 注册到编译生命周期钩子上
4. **run 开始编译**：调用 Compiler 的 `run` 方法，正式启动编译
5. **从 Entry 开始递归构建依赖图**：从入口文件开始，通过 Loader 转换模块，解析模块依赖（`import` / `require`），递归处理所有依赖的模块，形成依赖图（Module Graph）
6. **Loader 转换模块**：对于每个 Module，按照配置的 rules 匹配对应 Loader，从右向左（或从下向上）链式调用 Loader 进行转换
7. **生成 Chunk**：将 Module 按照入口和代码分割策略，组合成不同的 Chunk
8. **输出文件**：将 Chunk 写入文件系统，生成最终 Bundle

> **生活化类比**：搬家打包——把所有东西（模块）分门别类打包进箱子（bundle），贴上标签（hash），搬到新家（部署）。Loader 是把非标准物品（图片、CSS）变成标准包装，Plugin 是搬家公司的项目经理——Loader 负责打包每个物品（文件转换），Plugin 负责统筹全局：决定什么时候开始打包、打包完要不要贴标签（hash）、要不要生成物品清单（HTML 文件）、要不要把重物分开放（代码分割）。没有项目经理，搬家照样能进行，但效率和质量会大打折扣。

**Webpack 打包完整流程图**：

> Webpack 的打包流程以**入口文件**为起点，通过 import/require 递归构建模块依赖图。每个模块经过 Resolve 解析和 Loader 链式转换后，最终被组合为 Chunk 并通过 Plugin 优化输出。Loader 负责"翻译"不同类型的文件，Plugin 则在整个生命周期中通过钩子机制介入，二者协作完成从源码到部署包的完整构建。

```javascript
// 简化版的 Webpack 打包流程伪代码
class Compiler {
  constructor(config) {
    this.config = config
    this.hooks = {
      run: new SyncHook(),
      compile: new SyncHook(),
      emit: new AsyncSeriesHook(),
      done: new SyncHook()
    }
  }

  run() {
    this.hooks.run.call()
    this.compile()
  }

  compile() {
    this.hooks.compile.call()
    // 1. 从 entry 开始解析
    const entryModule = this.parseModule(this.config.entry)
    // 2. 递归构建依赖图
    const moduleGraph = this.buildModuleGraph(entryModule)
    // 3. 生成 Chunk
    const chunks = this.emitChunks(moduleGraph)
    // 4. 输出文件
    this.emitAssets(chunks)
    this.hooks.done.call()
  }

  parseModule(filePath) {
    // 读取文件内容
    const source = fs.readFileSync(filePath, 'utf-8')
    // 通过 Loader 链转换
    const transformed = this.applyLoaders(filePath, source)
    // 解析 AST，提取依赖
    const dependencies = this.parseDependencies(transformed)
    return { filePath, source: transformed, dependencies }
  }
}
```

### Loader 和 Plugin 的区别

这是 Webpack 面试中最核心的问题之一。

| 维度 | Loader | Plugin |
|------|--------|--------|
| 作用 | 文件转换器，将非 JS 文件转换为 Webpack 能处理的模块 | 扩展 Webpack 功能，在打包生命周期中执行各种任务 |
| 处理对象 | 单个文件（模块） | 整个打包流程 |
| 执行时机 | 在模块加载时，对模块源码进行转换 | 在 Webpack 生命周期的各个钩子中执行 |
| 调用方式 | 链式调用，从右向左（或从下向上） | 通过 hooks 注册，按照 tap 的顺序执行 |
| 典型示例 | `babel-loader`、`css-loader`、`style-loader` | `HtmlWebpackPlugin`、`MiniCssExtractPlugin` |
| 编写方式 | 导出一个函数，接收 source，返回转换后的内容 | 导出一个类，包含 `apply` 方法，接收 Compiler 对象 |

**Loader 链式调用原理**：

```javascript
// 配置：use: ['style-loader', 'css-loader', 'sass-loader']
// 执行顺序：sass-loader → css-loader → style-loader（从右向左）

// 简化版 Loader 实现
function myLoader(source) {
  // source 是上一个 loader 处理后的结果（或原始文件内容）
  const result = transform(source)
  return result
}

// 每个 Loader 就是一个函数：source => transformedSource
```

**Plugin 钩子机制**：

```javascript
// 简化版 Plugin 实现
class MyPlugin {
  apply(compiler) {
    // 在 emit 阶段（输出资源之前）执行
    compiler.hooks.emit.tap('MyPlugin', (compilation) => {
      // compilation 包含所有模块和资源信息
      console.log('即将输出资源...')
    })
  }
}
```

### 常用 Loader

| Loader | 作用 | 使用场景 |
|--------|------|----------|
| `babel-loader` | 将 ES6+ 代码转换为 ES5，兼容旧浏览器 | 处理 JS/JSX 文件 |
| `ts-loader` | 编译 TypeScript 为 JavaScript | TypeScript 项目 |
| `css-loader` | 解析 CSS 中的 `@import` 和 `url()` | 处理 CSS 文件 |
| `style-loader` | 将 CSS 以 `<style>` 标签注入 DOM | 开发环境 |
| `sass-loader` / `less-loader` | 编译 Sass/Less 为 CSS | 使用预处理器 |
| `postcss-loader` | 通过 PostCSS 插件处理 CSS（如 autoprefixer） | 自动添加浏览器前缀 |
| `file-loader` | 将文件复制到输出目录，返回文件路径 | 处理图片、字体等静态资源 |
| `url-loader` | 类似 file-loader，但小于阈值时转为 base64 内联 | 减少小文件 HTTP 请求 |
| `vue-loader` | 解析 `.vue` 单文件组件 | Vue 项目 |
| `eslint-webpack-plugin` | 在构建时执行 ESLint 检查（替代已废弃的 eslint-loader） | 代码质量检查 |

```javascript
// Webpack 5 中，file-loader 和 url-loader 已被内置 Asset Modules 替代
module.exports = {
  module: {
    rules: [
      {
        test: /\.(png|jpg|gif|svg)$/,
        type: 'asset', // asset/resource(file-loader) / asset/inline(url-loader)
        parser: {
          dataUrlCondition: {
            maxSize: 8 * 1024 // 8KB 以下转为 base64
          }
        }
      }
    ]
  }
}
```

### Vite 原理

Vite（法语"快"的意思）由 Vue.js 作者尤雨溪开发，利用浏览器原生 ES Module 能力，实现了开发环境下的零打包。

**开发环境原理**：

```
浏览器请求 → Vite Dev Server → 拦截请求 → 按需编译 → 返回 ES Module
```

1. **利用浏览器原生 ESM**：Vite 在开发环境下直接将源码作为 ES Module 提供给浏览器，不需要打包整个应用
2. **esbuild 预构建依赖**：使用 Go 语言编写的 esbuild 对 `node_modules` 中的依赖进行预构建，速度比 Webpack 快 10-100 倍
3. **按需编译**：只编译浏览器当前请求的模块，而不是一次性编译所有文件
4. **热更新（HMR）**：基于 ES Module 的 HMR 实现，只更新变更的模块，不需要重新打包

**生产环境原理**：

Vite 生产环境使用 Rollup 打包（Vite 7-）/ Rolldown 打包（Vite 8+），保证兼容性和优化效果。esbuild 用于代码压缩。

```javascript
// vite.config.js 示例
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  },
  server: {
    port: 3000,
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true
      }
    }
  },
  build: {
    // 生产环境 Rollup 配置
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ['vue', 'vue-router', 'pinia']
        }
      }
    }
  }
})
```

### Vite 热更新（HMR）原理

Vite 的 HMR 基于 WebSocket 和原生 ESM 实现，流程如下：

```
文件变更 → chokidar 文件监听 → 模块图更新 → WebSocket 推送 → 浏览器接收更新 → 请求更新模块 → HMR 热替换
```

**详细步骤**：

1. **文件监听**：Vite 使用 `chokidar` 监听文件系统的变化
2. **模块图更新**：当文件发生变化时，Vite 在模块图中标记该模块及其所有依赖方为"已失效"
3. **WebSocket 推送**：Vite Dev Server 通过 WebSocket 连接向浏览器发送更新消息，消息包含变更模块的路径
4. **浏览器接收更新**：浏览器中的 HMR Runtime 接收 WebSocket 消息
5. **请求更新模块**：浏览器向 Dev Server 重新请求变更的模块，同时在请求 URL 上添加时间戳避免缓存
6. **HMR 热替换**：HMR Runtime 调用对应框架的 HMR API（如 `import.meta.hot.accept()`），执行热替换逻辑

```javascript
// 在模块中使用 HMR API
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // 接受自身更新，执行热替换
    console.log('模块热更新完成', newModule)
  })

  import.meta.hot.dispose(() => {
    // 在模块被替换前清理副作用
    clearInterval(timer)
  })
}
```

> **生活类比**：
> - **Webpack vs Vite 开发模式**：传统自助餐（Webpack）是一次性把所有菜端上来，你吃不吃都摆着（全量打包）；Vite 是你点什么菜后厨现做（按需编译），所以启动极快。等正式上菜（生产构建）时大家菜单都一样，再用 Rollup 统一打包。
> - **esbuild 预构建**：就像预制菜——把常用依赖（React、Vue、Lodash）提前处理成半成品放冰箱，用时直接加热（ESM 导入），不用每次从头洗菜切菜（CommonJS 转 ESM）。
> - **HMR 热更新**：就像换灯泡——只换坏的那个灯泡（修改的模块），不需要重新装修整个房间（全量刷新页面）。Vite 只重新请求修改过的模块，其他模块保持原样。

### Webpack vs Vite 对比

| 维度 | Webpack | Vite |
|------|---------|------|
| 开发启动速度 | 几十秒到几分钟（大型项目），需要先打包整个应用 | 秒级启动，利用原生 ESM 按需编译 |
| HMR 速度 | 秒级，随着项目增大而变慢 | 毫秒级，只更新变更模块 |
| 构建速度 | 较慢，但生态成熟，优化手段丰富 | 开发阶段极快，生产构建使用 Rollup |
| 生态成熟度 | 成熟，插件和 Loader 极其丰富 | 快速成长，基本覆盖主流场景 |
| 浏览器兼容性 | 通过配置可支持所有浏览器，包括 IE11（需 Babel 转译）（历史兼容场景，2026 年新项目按现代浏览器基线） | 开发环境需要支持 ESM 的现代浏览器 |
| 生产构建 | 成熟的代码分割和 Tree Shaking | 基于 Rollup，输出优化好 |
| 配置复杂度 | 较复杂，但有大量文档和社区支持 | 简洁，开箱即用 |
| TypeScript 支持 | 需要配置 ts-loader 或 babel | 内置支持，esbuild 直接编译 |
| CSS 处理 | 需要配置 css-loader + style-loader | 内置支持 CSS、Less、Sass |

### Vite 6：Environment API 与 Rolldown（2024 年 11 月发布）

Vite 6 于 2024 年 11 月 26 日正式发布，引入了 Environment API 这一重大架构变化。Environment API 允许为不同的运行环境（客户端、SSR、Workers 等）创建独立的构建配置和插件管道。同时，Vite 团队正在开发 **Rolldown**——一个用 Rust 编写的高性能打包器，计划在未来替代 Vite 生产构建中的 Rollup 和 esbuild。

**Rolldown 简介**：

Rolldown 由 Vite 团队（尤雨溪主导）开发，是用 Rust 编写的新一代 JavaScript 打包器，目标是兼容 Rollup 的插件 API 和配置方式，同时利用 Rust 的性能优势。Rolldown 在 Vite 6 中以 `rolldown-vite` 包形式提供实验性预览，Vite 7 进一步集成，Vite 8（2025 年 12 月 Beta）起作为默认生产构建引擎，全面替代 Rollup 和 esbuild。

| 维度 | Rollup（旧） | Rolldown（当前） |
|------|-------------|---------------|
| 开发语言 | JavaScript | Rust |
| 构建速度 | 中等 | 接近 esbuild 级别 |
| 插件兼容性 | 原生 Rollup 插件 | 兼容 Rollup 插件 API |
| 与 Vite 关系 | Vite 5 生产构建引擎 | Vite 8+ 默认生产构建引擎 |
| 状态 | 成熟稳定 | Beta（Vite 8，2025-12） |

**核心变化**：

| 维度 | Vite 5 | Vite 6 |
|------|--------|--------|
| 环境抽象 | 隐式的客户端 + SSR 双环境 | 显式的多环境 API（Environment API） |
| 插件兼容性 | 插件需判断环境 | 插件可声明目标环境 |
| 构建配置 | 统一配置 | 按环境独立配置 |
| HMR | 仅客户端 | 可为任意环境启用 HMR |
| Node.js 要求 | 18+ | 18+（推荐 20+） |

```javascript
// vite.config.js - Vite 6 Environment API 示例
import { defineConfig } from 'vite'

export default defineConfig({
  environments: {
    client: {
      // 浏览器环境配置
      build: {
        outDir: 'dist/client',
        rollupOptions: {
          input: 'src/client-entry.js'
        }
      },
      dev: {
        hmr: true
      }
    },
    server: {
      // SSR 环境配置
      build: {
        outDir: 'dist/server',
        rollupOptions: {
          input: 'src/server-entry.js'
        }
      },
      resolve: {
        // 服务端专用条件导出
        conditions: ['node']
      }
    },
    worker: {
      // Web Worker 环境配置
      build: {
        outDir: 'dist/worker',
        target: 'esnext'
      }
    }
  }
})
```

**Vite 5 → Vite 6 迁移要点**：
- Environment API 为可选特性，Vite 5 配置仍可正常工作
- 废弃了部分旧 API（如 `server.ssr` 配置，改用 `environments.server`）
- CSS 处理引擎升级，支持更快的 CSS 编译
- 内置支持 `@import` 中 `url()` 的自动重写

## 三、新一代构建工具

随着前端项目规模持续增长，传统的 JavaScript 构建工具在性能上逐渐遇到瓶颈。新一代构建工具利用 Rust、Go 等高性能语言重写核心模块，大幅提升了构建速度。

### 1. Rspack 核心原理

Rspack 是由字节跳动团队开发的高性能 JavaScript 打包工具，核心用 Rust 语言编写，设计目标是与 Webpack 保持高度兼容。

**核心特性**：

- **Rust 实现**：核心模块（解析、转换、代码生成）全部用 Rust 编写，利用 Rust 的零成本抽象和内存安全特性，实现比 JavaScript 快 5-10 倍的构建性能
- **Webpack 兼容性**：API 和配置项与 Webpack 高度一致，支持绝大多数 Webpack Loader 和 Plugin，迁移成本极低
- **并行编译**：利用 Rust 的并发模型，在模块解析、代码生成阶段实现真正的并行处理

```javascript
// rspack.config.js —— 与 Webpack 配置几乎一致
const rspack = require('@rspack/core');

module.exports = {
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash:8].js',
  },
  module: {
    rules: [
      {
        test: /\.jsx?$/,
        use: 'builtin:swc-loader', // Rspack 内置的 SWC loader
      },
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader'],
      },
    ],
  },
  plugins: [
    new rspack.HtmlRspackPlugin({
      template: './public/index.html',
    }),
  ],
  resolve: {
    extensions: ['.js', '.jsx', '.ts', '.tsx'],
    alias: { '@': path.resolve(__dirname, 'src') },
  },
};
```

**性能对比**（大型项目约 1000 个模块基准测试）：

| 指标 | Webpack 5 | Rspack |
|------|-----------|--------|
| 冷启动 | ~25s | ~2s |
| 热启动 | ~10s | ~0.8s |
| HMR | ~2s | ~0.1s |
| 生产构建 | ~45s | ~5s |
| 内存占用 | ~1.2GB | ~400MB |

### 2. Turbopack 核心原理

Turbopack 是 Vercel 团队开发的增量打包工具，由 Webpack 作者 Tobias Koppers 主导设计，使用 Rust 编写，是 Next.js 的默认开发构建工具。

**核心特性**：

- **增量计算**：Turbopack 核心创新在于函数级别的缓存和增量计算。当文件发生变化时，只有受影响的部分重新计算，而非整个模块
- **请求级编译**：开发模式下只编译浏览器请求的页面所需模块，而非一次性编译整个应用
- **内存缓存**：在内存中维护模块依赖图，避免重复的文件 I/O 操作

```javascript
// next.config.js —— Turbopack 通过 Next.js 配置
module.exports = {
  // Next.js 14+ 使用 --turbo 标志启用 Turbopack
  // pnpm dev --turbo
  experimental: {
    turbo: {
      rules: {
        // 自定义 Turbopack 规则
        // 注意：Turbopack 使用独立 loader 系统，Webpack loader 不直接兼容
        '*.svg': {
          loaders: ['@svgr/webpack'],
          as: '*.js',
        },
      },
      resolveAlias: {
        '@': './src',
      },
    },
  },
};
```

**Turbopack 的增量计算机制**：

```
文件变更 → 定位受影响模块 → 仅重新计算这些模块 → 更新模块图 → 推送变更
```

传统打包工具需要重新构建整个依赖图或大量模块，而 Turbopack 通过函数级缓存，只重新计算变更模块及其直接依赖，做到了 O(变更模块数) 的复杂度。

### 4. 选型建议

**场景一：存量 Webpack 项目优化**

如果你的项目已经使用 Webpack，且构建速度成为瓶颈，推荐迁移到 **Rspack**。Rspack 与 Webpack 的配置高度兼容，迁移成本极低，通常只需将 `webpack.config.js` 重命名为 `rspack.config.js` 并微调少量配置即可。

```javascript
// 迁移示例：Webpack → Rspack
// 1. 安装依赖
// pnpm add @rspack/core @rspack/cli -D
// 2. 将 webpack.config.js 重命名为 rspack.config.js
// 3. 调整 loader 配置（使用 Rspack 内置 loader）
// 4. 替换 Webpack 专属 Plugin 为 Rspack 版本
```

**场景二：新项目选型**

| 项目类型 | 推荐工具 | 理由 |
|---------|---------|------|
| React/Vue 单页应用 | Vite | 开发体验极致，生态成熟，社区活跃 |
| Next.js 项目 | Turbopack（内置） | 深度集成，增量计算优势明显 |
| 大型企业级项目 | Rspack | Webpack 兼容，迁移成本低，性能优秀 |
| 工具库 / 组件库 | esbuild 或 Rollup | 轻量快速，输出干净 |
| 追求极致性能 | Rspack 或 Farm | Rust 底层，大型项目优势明显 |

**场景三：从 Webpack 迁移到 Vite**

如果选择 Vite，需要注意：
- 开发环境依赖浏览器 ESM 支持，生产环境使用 Rollup
- Webpack 的 `require.context` 等特性不支持
- 环境变量使用 `import.meta.env.VITE_*` 而非 `process.env`
- CSS Modules 的文件名需改为 `*.module.css`
- 静态资源引用方式不同（`new URL('./img.png', import.meta.url)`）

**总结建议**：

1. **新项目优先考虑 Vite**：开发体验最好，社区最活跃，插件生态完善
2. **Webpack 项目迁移首选 Rspack**：几乎零成本获得 5-10 倍性能提升
3. **Next.js 项目使用 Turbopack**：官方集成，无需额外配置
4. **构建性能极致追求者**：关注 Rspack 和 Farm 的发展，两者都在快速迭代
5. **esbuild 适合工具链中的特定环节**：如 Vite 的预构建和代码压缩，而非完整打包方案

```css
@import "tailwindcss";
```

```javascript
// vite.config.js - Vite 中使用 Tailwind CSS v4
import { defineConfig } from 'vite'
```

## 六、常见面试题

### 1. Webpack 的打包流程是什么？

**回答要点**：初始化参数（合并配置）→ 创建 Compiler → 加载 Plugin → run 开始编译 → 从 Entry 入口递归构建依赖图 → Loader 转换每个 Module → 生成 Chunk → 输出文件到 dist。要强调 Loader 是从右向左链式执行，Plugin 是在生命周期钩子中执行。

### 2. Loader 和 Plugin 有什么区别？

**回答要点**：Loader 是文件转换器，处理单个文件，将非 JS 文件转换为 Webpack 能识别的模块，链式调用从右向左。Plugin 是功能扩展器，在 Webpack 整个打包生命周期中执行，通过 hooks 机制介入打包流程，可以做 Loader 做不到的事情（如生成 HTML、提取 CSS、压缩代码）。

### 3. Vite 为什么快？

**回答要点**：开发环境利用浏览器原生 ESM 能力，不需要打包整个应用，按需编译；使用 esbuild 预构建依赖（Go 语言编写，速度极快）；HMR 基于 ES Module，只更新变更的模块；生产环境使用 Rollup 打包（Vite 7-）/ Rolldown 打包（Vite 8+），保证兼容性和优化效果。

### 4. Tree Shaking 的原理和实现条件？

> **本主题权威章节**（其他模块的同主题内容均指向此处）。

**回答要点**：Tree Shaking 基于 ES Module 的静态导入特性（`import` 和 `export`），在编译时分析模块之间的依赖关系，移除未被引用的代码（dead code）。实现条件：必须使用 ES Module（不能是 CommonJS），在 `package.json` 中设置 `"sideEffects": false` 或指定副作用文件，生产模式下 Webpack 会自动开启。

> 📖 **参考链接**：
> - [Webpack官方文档 - Tree Shaking](https://webpack.docschina.org/guides/tree-shaking/)

### 5. Webpack 的热更新（HMR）原理是什么？

**回答要点**：Webpack 通过 WebSocket 在浏览器和 Dev Server 之间建立连接。文件变更时，Webpack 重新编译变更模块，通过 WebSocket 推送 hash 事件和更新清单到浏览器，浏览器请求变更模块的增量更新，HMR Runtime 执行 `module.hot.accept()` 完成热替换。

## 七、避坑指南

| 常见错误 | 现象 | 原因 | 解决方案 |
|---------|------|------|----------|
| 开发环境使用 style-loader 生产环境未提取 CSS | 生产环境 CSS 通过 JS 注入，闪屏 | style-loader 将 CSS 注入 DOM，不是独立文件 | 生产环境使用 MiniCssExtractPlugin 提取 CSS |
| Loader 配置顺序错误 | 构建报错或样式不生效 | Loader 从右向左执行，顺序错误导致转换失败 | 确保 use 数组顺序正确，如 `['style-loader', 'css-loader', 'sass-loader']` |
| 开发环境正常，生产环境报错 | 构建产物在浏览器中运行报错 | 生产构建时某些 polyfill 或配置缺失 | 检查 babel 配置和 browserslist，确保兼容目标浏览器 |
| Vite 项目中 import 图片路径报错 | 页面无法加载图片 | Vite 的静态资源处理方式与 Webpack 不同 | 使用 `new URL('./img.png', import.meta.url).href` 或直接 import |
| Webpack 打包后文件过大 | 首屏加载慢，bundle 超过 1MB | 未启用代码分割和 Tree Shaking | 配置 splitChunks，使用动态 import，启用 BundleAnalyzerPlugin 分析 |
| Vite 项目兼容性问题 | 老浏览器无法运行 | Vite 默认不处理 ES6+ 语法和 API polyfill | 使用 @vitejs/plugin-legacy 插件 |
| 开发环境 proxy 配置不当 | 接口请求 404 或跨域 | 代理配置路径或目标地址不正确 | 检查 proxy 配置的 path 和 target，注意路径重写 |
| 忽略 .gitignore 中的 dist 目录 | dist 被提交到 Git 仓库 | 未在 .gitignore 中忽略构建产物 | 在 .gitignore 中添加 `/dist` 或 `/build` |

## 补充内容1：编译链对比（Babel / SWC / esbuild）

构建工具负责"把多个模块打成一个包"，编译器负责"把一份源码翻译成另一份源码"。前者解决依赖图与产物组织，后者解决语法兼容与语法扩展。日常说的"构建慢"，很多时候瓶颈并不在打包，而在编译链——也就是 Babel、SWC、esbuild 这三个角色。

### 1. 三者定位与差异

| 维度 | Babel | SWC | esbuild |
|------|-------|-----|---------|
| 实现语言 | JavaScript | Rust | Go |
| 定位 | 编译器 / 转译器（生态型，靠插件扩展） | Babel 的 Rust 重写（编译器 + 压缩器） | 打包器 + 转译器（一体化） |
| 输入粒度 | 单个文件源码字符串 | 单个文件源码字符串 | 模块图（也可单文件） |
| 插件系统 | 极丰富，插件 / preset 生态成熟 | 有（WASM 插件），生态较小 | 极简（`onResolve` / `onLoad`），无法操作 AST |
| 是否内置打包 | 否（依赖 Webpack / Rollup） | 否 | 是 |
| 类型检查 | 不负责 | 不负责 | 不负责 |
| polyfill 注入 | 支持（`core-js` + `useBuiltIns`） | 支持（`env` 模式 + `coreJs`） | 不支持（只降级语法） |
| 典型宿主 | Webpack + `babel-loader`、Jest、`@vitejs/plugin-react` | Next.js、Rspack、`@vitejs/plugin-react-swc` | Vite 预构建与压缩、tsx、Vitest |

**一句话概括**：Babel 是"转译器生态"（能力最全、最慢）；SWC 是"用 Rust 重写 Babel"（能力接近 Babel、快得多）；esbuild 是"用 Go 写的打包 + 转译器"（最快，但能力边界最窄）。

### 2. 底层原理：为什么 SWC / esbuild 快这么多

**（1）语言层面的差距**。Babel 的所有工作都在 V8 里执行：解析、AST 对象创建、遍历、字符串拼接，每一步都要分配 JS 对象并承受 GC 压力。Rust / Go 编译为机器码直接运行，没有 JIT 预热，内存布局紧凑，GC 开销极低。这是最根本的一层差距，单线程下就能拉开 10 倍以上。

**（2）并行化能力**。Babel 单进程单线程，同一时刻只能处理一个文件；要并行只能借助 `thread-loader`、`jest-worker` 这类方案，跨进程通信与 AST 序列化会吃掉大部分收益。SWC / esbuild 在进程内使用线程池，多个文件真正并行处理。

**（3）AST 复用与遍历次数**。Babel 的流水线是 `字符串 → 解析成 AST → 各插件依次 traverse → 生成字符串`，每个插件都要完整遍历一次 AST，插件越多遍历次数越多；而且 loader 之间会反复做"字符串 → AST → 字符串"的往返。esbuild 解析一次后在自己的 AST 上把所有工作（TS 类型擦除、JSX 转换、语法降级、依赖收集、代码生成）在尽量少的遍历里做完，不做跨进程 AST 序列化。

**性能量级参考**（官方基准，具体倍数随场景与机器差异很大）：

| 工具 | 相对速度 | 说明 |
|------|---------|------|
| Babel | 1x | 基准 |
| SWC | 约 20x（单线程）/ 约 70x（4 核） | SWC 官方 benchmark |
| esbuild | 约 10-100x | esbuild 官方 benchmark，取决于是否含打包 |

> **注意**：三者都不做类型检查。SWC / esbuild 只是把 TypeScript 的类型标注"擦掉"，类型错误不会被发现。这也是为什么 Vite 项目在 `build` 脚本里仍然要跑一次 `vue-tsc --noEmit` 或 `tsc --noEmit`。

### 3. 各自在 Vite / Webpack / Next.js 中的角色

| 工具链 | 编译链角色 |
|--------|-----------|
| Vite（开发） | esbuild 预构建 `node_modules` 依赖；源码的 TS / JSX 由 esbuild 转译 |
| Vite（React 插件） | `@vitejs/plugin-react` 默认用 Babel（支持 Fast Refresh 与 Babel 插件）；`@vitejs/plugin-react-swc` 用 SWC |
| Vite（生产） | 打包由 Rollup 负责（Vite 8+ 为 Rolldown），JS 压缩默认交给 esbuild |
| Webpack | 转译由 loader 决定：`babel-loader`（默认）/ `swc-loader` / `esbuild-loader`；类型检查交给 `fork-ts-checker-webpack-plugin` 并行执行 |
| Next.js | 12+ 默认编译器是 SWC；一旦项目根目录存在 `babel.config.js`，会退回 Babel 编译；Turbopack 内部同样使用 SWC |
| Rspack | 内置 `builtin:swc-loader`，不需要额外安装 Babel |
| 测试工具 | Vitest 用 esbuild 转译；Jest 用 `babel-jest`（可换 `@swc/jest`）；tsx 用 esbuild |

```javascript
// webpack.config.js —— 用 esbuild-loader 替换 babel-loader

module.exports = {
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,

  },

    new ForkTsCheckerWebpackPlugin()
  ]
}
```

```javascript
// vite.config.js —— 用 SWC 版 React 插件替代 Babel 版
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react-swc'

export default defineConfig({
  plugins: [react()]
})
```

### 4. `@babel/preset-env` 与 browserslist 的关系

`@babel/preset-env` 本身不包含任何转换逻辑，它是一个**调度器**：读取目标浏览器范围，反推出"哪些语法需要降级、哪些可以原样保留"，然后按需启用对应的 transform 插件。

- **targets 的来源优先级**：`preset-env` 的 `targets` 选项 > `browserslist` 配置（`package.json` 的 `browserslist` 字段或 `.browserslistrc` 文件）。
- **browserslist 是共享的兼容目标声明**：`autoprefixer`、`postcss-preset-env`、SWC 的 `env` 模式、Next.js 都读同一份配置，所以改一处即可全链路生效。环境选择由 `BROWSERSLIST_ENV` / `NODE_ENV` 决定。
- **必须区分"语法降级"与"API polyfill"**：`const`、箭头函数、可选链、类字段属于**语法**，靠 transform 插件降级；`Promise`、`Array.prototype.flat`、`fetch`、`Object.entries` 属于**运行时 API**，老浏览器上根本不存在，必须靠 `core-js` 注入。只配 browserslist 而不开 `useBuiltIns`，结果是语法能跑但 API 报 `undefined is not a function`。

```json
// package.json —— browserslist 支持按环境分段
{
  "browserslist": {
    "production": ["> 0.5%", "last 2 versions", "not dead"],
    "development": ["last 1 chrome version", "last 1 firefox version"]
  }
}
```

```javascript
// babel.config.js
module.exports = {
  presets: [
    [
      '@babel/preset-env',
      {
        // 未显式写 targets 时，preset-env 会读取 package.json / .browserslistrc 的 browserslist
        useBuiltIns: 'usage', // 按代码中实际用到的 API 按需注入 core-js（需同时安装 core-js）
        corejs: '3.37', // 必须与安装的 core-js 主版本一致
        bugfixes: true, // 只对目标浏览器中确实有 bug 的语法做额外降级，产物更小
        modules: false // 保留 ESM，交给打包器处理，才能让 Tree Shaking 生效
      }
    ]
  ],
  plugins: [
    // preset-env 覆盖不到的补充转换，例如装饰器提案
    ['@babel/plugin-proposal-decorators', { version: 'legacy' }]
  ]
}
```

### 5. 什么场景还需要 Babel

SWC / esbuild 能覆盖 90% 的日常转译需求，但以下场景仍然离不开 Babel：

1. **自定义 Babel 插件**：项目里手写的 AST 转换（按需引入、埋点自动注入、国际化 key 提取、代码规范约束）。SWC 的 WASM 插件开发门槛高、生态薄，迁移成本远超收益。
2. **依赖 Babel 生态的特定转换**：`babel-plugin-styled-components`（生成稳定类名、保证 SSR 样式一致）、`babel-plugin-import`（组件库按需加载）、`babel-plugin-lodash`、`babel-plugin-transform-remove-console` 等。
3. **必须完整降级到 ES5**：esbuild 对部分语法的 ES5 降级并不完整，遇到不支持的特性会直接报错 `Transforming ... to the configured target environment ("es5") is not supported yet`（例如 async generator）。需要兼容 IE11 这类环境时只能回到 Babel（历史兼容场景，2026 年新项目按现代浏览器基线）。
4. **装饰器元数据（`emitDecoratorMetadata`）**：NestJS + TypeORM 这类依赖运行时类型元数据的场景，esbuild 不支持该选项（SWC 支持）。
5. **Jest 生态**：`babel-jest` 与 `babel.config.js` 深度绑定，Babel 插件形式的 mock / transform 更成熟（可用 `@swc/jest` 替代，但要评估插件兼容性）。
6. **以 Babel 插件形式发布的实验性方案**：例如 React Compiler（`babel-plugin-react-compiler`）目前只提供 Babel 插件。

### 6. SWC / esbuild 的能力边界

| 能力 | Babel | SWC | esbuild |
|------|-------|-----|---------|
| 类型检查 | 不支持 | 不支持 | 不支持 |
| 完整降级到 ES5 | 支持 | 支持 | 部分（个别语法直接报错） |
| core-js polyfill 注入 | 支持 | 支持（`env` 模式） | 不支持 |
| 自定义 AST 插件 | 支持 | 有限（WASM 插件） | 不支持（仅 `onResolve` / `onLoad`） |
| `emitDecoratorMetadata` | 支持 | 支持 | 不支持 |
| 代码分割 | 不涉及 | 不涉及 | 支持（仅 ESM 输出格式） |
| 内置压缩 | 不支持 | 支持 | 支持 |
| CSS 处理 | 不支持 | 不支持 | 基础支持（可打包 CSS） |
| 内置 HMR | 不支持 | 不支持 | 不支持（由宿主实现） |

### 7. 面试常见问法

**Q1：Babel、SWC、esbuild 三者的定位区别？**
回答要点：Babel 是 JS 生态的编译器 / 转译器，能力最全、插件生态最强、速度最慢；SWC 用 Rust 重写 Babel，能力接近 Babel，速度提升约 20-70 倍，被 Next.js / Rspack 采用；esbuild 用 Go 编写，是打包器与转译器的一体化工具，速度最快，但插件能力、polyfill 注入、ES5 降级都有边界。

**Q2：esbuild 为什么比 Babel 快？**
回答要点：三点——语言层面（Go 机器码 vs JS 在 V8 中执行，无 JIT 预热、GC 压力小）；并行化（进程内线程池 vs 单线程，Babel 多线程要靠跨进程方案）；架构层面（解析一次、在自有 AST 上一次性完成所有转换、不做 AST 序列化，而 Babel 每个插件都要完整遍历一次 AST，loader 之间还有字符串往返）。

**Q3：`@babel/preset-env` 和 browserslist 是什么关系？**
回答要点：preset-env 是调度器，它读取 targets（显式 `targets` 选项优先，否则读 `browserslist` 配置）来推导需要哪些语法降级插件；browserslist 是跨工具共享的兼容目标声明，autoprefixer、postcss-preset-env、SWC、Next.js 都复用它。要注意语法降级与 API polyfill 是两件事，后者还需要 `useBuiltIns` + `core-js`。

**Q4：项目从 Babel 换到 SWC 要注意什么？**
回答要点：先盘点用到的 Babel 插件能否找到对应实现（自定义插件、`styled-components`、按需引入类插件是主要风险点）；确认装饰器元数据需求（SWC 支持 `emitDecoratorMetadata`）；保留类型检查环节（`tsc --noEmit`）；注意 Next.js 项目残留 `babel.config.js` 会静默退回 Babel；最后对比产物体积与浏览器兼容范围。

**Q5：有了 esbuild 还需要 Babel 吗？**
回答要点：需要。esbuild 不做类型检查、不注入 polyfill、插件无法操作 AST、ES5 降级不完整。常见组合是"esbuild 负责转译 + Babel 只跑少数必要插件"，或者用 `esbuild-loader` 替换 `babel-loader` 并把类型检查交给独立进程。

### 8. 易错点

| 易错点 | 现象 | 原因 | 解决方案 |
|--------|------|------|----------|
| 把语法降级当成 API polyfill | 老浏览器报 `Promise is not defined` | esbuild 只降级语法，不做 core-js 注入 | 开启 SWC 的 `env` 模式，或保留 Babel 的 `useBuiltIns` |
| 以为 SWC / esbuild 会做类型检查 | 类型错误带到生产环境 | 它们只擦除类型标注，不做类型分析 | 保留 `tsc --noEmit` 或 `fork-ts-checker-webpack-plugin` |
| Next.js 项目残留 `babel.config.js` | 编译变慢，部分优化失效 | 存在 Babel 配置时 Next.js 会退回 Babel | 确认无 Babel 插件需求后删除该文件 |
| `useBuiltIns: 'usage'` 与 `corejs` 版本不匹配 | 构建报错或注入了错误的 core-js 路径 | `corejs` 必须与安装的 core-js 主版本一致 | 统一 `corejs: '3.x'` 与 `core-js@3` |
| 以为 esbuild 会读 browserslist | 兼容范围与预期不符 | esbuild 只认显式的 `target` | 手动设置 `target`，并与 browserslist 声明保持同步 |
| 把 Babel 插件直接搬到 SWC | 配置报错，插件不生效 | `@swc/core` 不识别 `@babel/plugin-*` | 寻找对应的 SWC 实现，或改用 WASM 插件 |
| 用 `thread-loader` 包 `babel-loader` 后变量丢失 | loader 之间无法共享状态 | 多进程模式下 loader 上下文被隔离 | 改用 SWC / esbuild 获得原生并行，而非叠加进程方案 |

## 补充内容2：环境变量与多环境构建

同一份源码要跑在开发、预发布、生产三套环境，差异集中在 API 域名、CDN 地址、埋点开关、日志级别、第三方公钥上。把这些差异从代码里抽出来、按环境注入，就是"多环境构建"要解决的问题。

### 1. 两类注入时机

| 维度 | 构建时注入 | 运行时配置 |
|------|-----------|-----------|
| 载体 | `import.meta.env` / `process.env` / `DefinePlugin` | `window.__CONFIG__` / `/config.json` / 远程配置中心 |
| 生效时机 | 编译期静态替换，产物里是字面量 | 页面启动时读取 |
| 是否需要重新构建 | 需要（每个环境一份产物） | 不需要（同一份产物可部署到多环境） |
| 是否公开 | 明文写在 bundle 中，任何人可见 | 同样是明文，但可配合接口鉴权与下发生效 |
| 适用场景 | 与构建强相关的常量（版本号、构建时间、feature flag 默认值） | 部署后才确定的地址、灰度开关、租户配置 |

**铁律**：任何注入到前端的变量都是公开信息。无论用哪种方式，都不能承载密钥。

### 2. `.env` 文件分级与 Vite 的 `import.meta.env`

Vite 使用 `dotenv` + `dotenv-expand` 加载环境文件，**后加载的覆盖先加载的**，优先级从低到高为：

`.env` → `.env.local` → `.env.[mode]` → `.env.[mode].local`

| 文件 | 何时加载 | 是否提交 Git |
|------|---------|-------------|
| `.env` | 所有模式 | 是 |
| `.env.local` | 所有模式 | 否（加入 `.gitignore`） |
| `.env.development` | `mode=development` | 是 |
| `.env.staging` | `mode=staging` | 是 |
| `.env.production` | `mode=production` | 是 |
| `.env.[mode].local` | 对应模式 | 否 |
| `.env.example` | 不自动加载，仅作模板 | 是 |

```bash
# .env —— 所有环境共享的公开配置
VITE_APP_TITLE=My App

# .env.development —— pnpm dev 时生效
VITE_API_BASE=/api
VITE_ENABLE_MOCK=true

# .env.staging —— pnpm build --mode staging 时生效
VITE_API_BASE=https://api-staging.example.com
VITE_ENABLE_MOCK=false

# .env.production —— pnpm build（默认 mode=production）时生效
VITE_API_BASE=https://api.example.com
VITE_ENABLE_MOCK=false
```

**`VITE_` 前缀的作用**：只有带 `VITE_` 前缀的变量才会被暴露给客户端代码，其余变量仅在 `vite.config.js` 等 Node 侧可用。这是防止"把服务端密钥误暴露给浏览器"的安全阀，**但它不是保护机制**——一旦加了前缀，值就会明文进入产物。前缀可通过 `envPrefix` 配置修改。

```javascript
// vite.config.js —— 自定义前缀（一般不建议改）
import { defineConfig } from 'vite'

export default defineConfig({
  envPrefix: ['VITE_', 'APP_']
})
```

```javascript
// src/config/env.js —— 集中收口，避免 import.meta.env 散落在业务代码里
export const env = {
  mode: import.meta.env.MODE, // 'development' | 'staging' | 'production'
  isDev: import.meta.env.DEV,
  isProd: import.meta.env.PROD,
  baseUrl: import.meta.env.BASE_URL,
  apiBase: import.meta.env.VITE_API_BASE, // 静态写法，构建时被替换为字面量
  enableMock: import.meta.env.VITE_ENABLE_MOCK === 'true',
  appTitle: import.meta.env.VITE_APP_TITLE
}

// 注意：环境变量在构建时被静态替换，不能用动态 key 访问
// const key = 'VITE_API_BASE'
// import.meta.env[key] // 取不到值
```

```typescript

  readonly VITE_API_BASE: string
  readonly VITE_ENABLE_MOCK: string
  readonly VITE_APP_TITLE: string

  readonly env: ImportMetaEnv
}
```

### 3. Webpack 的 `DefinePlugin`

`DefinePlugin` 的原理是**编译期的标识符文本替换**：把源码中出现的指定标识符，整体替换成配置里给定的值。因此字符串值必须用 `JSON.stringify` 包裹，否则 `https://api.example.com` 会被当成代码片段解析，产物直接报语法错误。

- `optimization.nodeEnv` 默认取 `mode`，等价于自动定义了 `process.env.NODE_ENV`。
- `webpack.EnvironmentPlugin` 是 `DefinePlugin` 的语法糖，从 `process.env` 读取值。
- Webpack 没有 `VITE_` 这样的前缀约定（前缀是 CRA / Vite / Next.js 各自加的安全阀），任何被 define 的变量都会进入产物。
- 只做字面量替换，`process.env[key]` 这种动态取值不会被替换。

```javascript
// webpack.config.js
const webpack = require('webpack')

module.exports = (env, argv) => {
  const isProd = argv.mode === 'production'
  // 环境名由 CLI 显式传入：webpack --env appEnv=staging
  const appEnv = (env && env.appEnv) || (isProd ? 'production' : 'development')

  const configs = {
    development: { API_BASE: '/api', ENABLE_MOCK: true },
    staging: { API_BASE: 'https://api-staging.example.com', ENABLE_MOCK: false },
    production: { API_BASE: 'https://api.example.com', ENABLE_MOCK: false }
  }

  const current = configs[appEnv]

  return {
    mode: isProd ? 'production' : 'development',
    plugins: [
      new webpack.DefinePlugin({
        // 字符串值必须 JSON.stringify，否则会被当作代码片段解析
        'process.env.API_BASE': JSON.stringify(current.API_BASE),
        'process.env.ENABLE_MOCK': JSON.stringify(current.ENABLE_MOCK),
        __APP_ENV__: JSON.stringify(appEnv),
        __BUILD_TIME__: JSON.stringify(new Date().toISOString())
      })
    ]
  }
}
```

```javascript
// 另一种写法：EnvironmentPlugin 直接从 process.env 读取，第二个参数是缺失时的默认值
new webpack.EnvironmentPlugin({
  NODE_ENV: 'development',
  API_BASE: '/api'
})
```

### 4. 构建时注入 vs 运行时配置（`window.__CONFIG__` / 远程配置）

当"同一个镜像要部署到多套环境"时，构建时注入就不够用了——每换一个环境都要重新构建一次。这时改用运行时配置。

**方案一：`window.__CONFIG__`（同步可用，实现最简单）**

```html
<!-- public/config.js —— 不参与打包，部署时由运维/启动脚本替换 -->
<!-- 必须设置 Cache-Control: no-cache，否则改了配置不生效 -->
<script>
  window.__CONFIG__ = {
    API_BASE: 'https://api.example.com',
    SENTRY_DSN: '',
    FEATURE_FLAGS: { newDashboard: false }
  }
</script>
```

```html
<!-- index.html —— 必须排在应用入口之前，保证启动时已就绪 -->
<script src="/config.js"></script>
<script type="module" src="/src/main.ts"></script>
```

```javascript
// src/config/runtime.js —— 读取运行时配置，带兜底与校验
const runtime = window.__CONFIG__ || {}

export const config = {
  apiBase: runtime.API_BASE || import.meta.env.VITE_API_BASE,
  featureFlags: runtime.FEATURE_FLAGS || {}
}

if (!config.apiBase) {
  throw new Error('缺少运行时配置 API_BASE')
}
```

**方案二：`config.json`（可远程托管、可带鉴权，但有一次网络往返）**

```javascript
// src/main.js —— 先取远程配置，再挂载应用
async function bootstrap() {
  let remoteConfig = {}
  try {
    // 加时间戳绕过 CDN 与浏览器缓存，保证拿到最新配置
    const res = await fetch(`/config.json?t=${Date.now()}`, { cache: 'no-store' })
    if (!res.ok) throw new Error(`HTTP ${res.status}`)
    remoteConfig = await res.json()
  } catch (err) {
    // 配置拉取失败不能白屏，退回构建时默认值
    console.warn('远程配置加载失败，使用构建时默认值', err)
  }

  const { createApp } = await import('./app.js')
  createApp({ ...import.meta.env, ...remoteConfig }).mount('#app')
}

bootstrap()
```

**取舍**：`window.__CONFIG__` 同步可用、无额外等待，但需要多一个脚本请求（可内联进 HTML 省掉）；`config.json` 更灵活，可以放到 CDN 或配置中心并做权限控制，但引入一次网络往返，必须做超时与兜底，且要避免被强缓存。

### 5. 多环境（dev / staging / prod）的 CI 注入实践

三条原则：

1. **产物只构建一次，配置在部署时注入**——如果团队接受"每环境构建一次"，用构建时注入更简单；否则走运行时配置。
2. **敏感值走 CI Secret，不进仓库**——仓库里只保留 `.env.example` 模板（只列 key 与示例值）。
3. **环境名必须显式入参**——禁止"本地默认值悄悄生效"导致 staging 误连生产接口。

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        # 一条流水线并行构建两个环境
        app_env: [staging, production]
    environment: ${{ matrix.app_env }} # 关联 GitHub Environment 级别的 Secret
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - run: pnpm install --frozen-lockfile
      - name: Build
        run: pnpm build --mode ${{ matrix.app_env }}
        env:
          # Secret 通过环境变量注入，Vite 在构建时读取并静态替换
          VITE_API_BASE: ${{ vars.API_BASE }}
          VITE_SENTRY_DSN: ${{ secrets.SENTRY_DSN }}
```

**Docker 方案：一次构建，多环境运行**

```dockerfile
# Dockerfile —— 构建产物不含环境差异，配置在容器启动时注入
FROM node:20-alpine AS builder
WORKDIR /app
COPY . .
RUN corepack enable && pnpm install --frozen-lockfile && pnpm build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
# 用启动脚本 + envsubst 把容器环境变量渲染成 config.js
COPY docker/config.template.js /etc/nginx/template/config.template.js
COPY docker/entrypoint.sh /docker-entrypoint.d/40-render-config.sh
RUN chmod +x /docker-entrypoint.d/40-render-config.sh
```

```bash
# docker/entrypoint.sh —— 用运行时环境变量渲染配置文件
#!/bin/sh
set -e
envsubst < /etc/nginx/template/config.template.js > /usr/share/nginx/html/config.js
```

```bash
# 同一个镜像部署到不同环境，无需重新构建
docker run -e API_BASE=https://api-staging.example.com my-app:1.0.0
docker run -e API_BASE=https://api.example.com my-app:1.0.0
```

```javascript
// scripts/check-env.mjs —— 放在 build 脚本前置执行，缺配置直接失败
const required = ['VITE_API_BASE']
const missing = required.filter((key) => !process.env[key])

if (missing.length > 0) {
```

### 6. 敏感信息不能放前端的原理

- **前端产物是公开代码**。任何被注入的变量都会以字符串字面量出现在 `.js` 文件里，用户在 DevTools 的 Sources / Network 面板中就能看到。压缩、混淆、Base64 编码、拆包都只是提高阅读成本，不构成任何保护。
- **判断标准**：这个值被人看到会不会造成损失？API 密钥、数据库连接串、JWT 签名密钥、云厂商 AK/SK、内部服务地址、支付私钥——一律不能进前端。
- **正确做法**：密钥留在服务端（BFF / API 网关 / 边缘函数），前端只调用自家接口；第三方能力（地图、短信、支付）用后端代理 + 域名白名单 + 配额限制，或使用服务商明确设计为公开的 key（如地图浏览器的 Web 端 key，需要配置 Referer 白名单）。
- **常见误区**：把 `VITE_` 前缀当成"只有我能用"的开关；把 `NODE_ENV=production` 当作安全边界（它只是构建开关）；以为生产构建会自动加密环境变量。
- **补充**：`.env.local` 与 `.env.[mode].local` 必须加入 `.gitignore`；一旦密钥被提交过，即使删除历史记录也可能已经泄露，必须立即轮换。

### 7. 面试常见问法

**Q1：Vite 的环境变量加载顺序？为什么必须加 `VITE_` 前缀？**
回答要点：加载顺序为 `.env` → `.env.local` → `.env.[mode]` → `.env.[mode].local`，后者覆盖前者；`VITE_` 前缀是"暴露给客户端"的开关，防止服务端专用变量被误打进 bundle，但它不是安全机制——加了前缀就等于公开。只有 `import.meta.env.VITE_X` 这种静态写法会被构建时替换，动态 key 取不到值。

**Q2：Webpack 的 `DefinePlugin` 原理是什么？为什么值要 `JSON.stringify`？**
回答要点：`DefinePlugin` 在编译期做标识符的文本替换，把源码中的标识符整体替换为配置值。值会被当作代码片段插入，所以字符串必须 `JSON.stringify` 成带引号的字面量，否则 `https://api.example.com` 里的 `//` 会被当成注释，直接导致产物语法错误。

**Q3：构建时注入和运行时配置怎么选？**
回答要点：看是否需要"一份产物多环境部署"。需要就用运行时配置（`window.__CONFIG__` 或 `config.json`），代价是引入运行时读取与兜底逻辑；不需要就用构建时注入，实现简单、无运行时开销。两者可以叠加：构建时给默认值，运行时覆盖。

**Q4：同一份产物如何部署到多个环境？**
回答要点：产物只构建一次，把环境差异抽成运行时配置。常见做法是 Docker 多阶段构建出镜像，容器启动时用 `envsubst` 把环境变量渲染进 `public/config.js`（或 `config.json`），前端在启动前读取。同时给该配置文件设置 `Cache-Control: no-cache`，避免配置被缓存。

**Q5：前端能不能放 API 密钥？为什么？**
回答要点：不能。前端产物是公开的，任何注入的变量都以明文出现在 bundle 中，混淆不构成保护。密钥必须留在服务端，前端通过自家 BFF 代理调用第三方服务；服务商公开设计的浏览器端 key 除外，但也必须配置域名 / Referer 白名单。

### 8. 易错点

| 易错点 | 现象 | 原因 | 解决方案 |
|--------|------|------|----------|
| 用动态 key 读环境变量 | `import.meta.env[key]` 为 `undefined` | 构建时只做静态字面量替换 | 用固定写法，或集中收口到一个 config 模块 |
| 敏感变量加了 `VITE_` 前缀 | 密钥出现在产物中 | 前缀只是"暴露给客户端"的开关，不是保护机制 | 密钥只留在服务端，前端走 BFF 代理 |
| `DefinePlugin` 的值未 `JSON.stringify` | 产物报语法错误或变量未定义 | 值被当作代码片段解析 | 字符串一律 `JSON.stringify(value)` |
| `.env` 被提交到 Git | 密钥泄露 | 未加入 `.gitignore` | 只提交 `.env.example`，忽略 `.env.local` 与真实 `.env` |
| 运行时配置文件被 CDN 强缓存 | 改了配置不生效 | `config.js` / `config.json` 命中长缓存 | 对该文件设置 `Cache-Control: no-cache`，或加时间戳参数 |
| 用 `NODE_ENV` 区分环境 | staging 被当成 production | `NODE_ENV` 只有 development / production 两种语义 | 用 `mode`（Vite）或 `--env`（Webpack）显式声明环境名 |
| 以为环境变量运行时可改 | 改了 `.env` 不重新构建无效 | 构建时静态替换，产物里已是字面量 | 需要运行时可变就改用 `window.__CONFIG__` 或远程配置 |
| 缺少必填配置直接上线 | 生产环境接口地址为空 | 构建时未做校验，空值被静默打进产物 | 构建前置校验脚本，缺配置直接 `exit 1` |
