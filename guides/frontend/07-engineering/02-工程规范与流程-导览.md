## 核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | 前端工程规范体系涵盖代码规范、Git 工作流、CI/CD 流水线、Monorepo 架构和部署方案，是团队协作和项目长期维护的基础设施 |
| 能做什么 | 统一代码风格降低 Code Review 成本、自动化质量保障在提交前拦截问题、规范化协作流程提升效率、持续集成与部署减少人工失误、保障代码库长期可维护性 |
| 怎么用 | `pnpm add -D eslint prettier husky lint-staged @commitlint/cli` 搭建基础工具链 |
| 原理和工作流程 | 五大核心目标：统一代码风格（ESLint + Prettier）、自动化质量保障（Husky + lint-staged 在 pre-commit 阶段检查暂存文件）、规范化协作（Git Flow 或 GitHub Flow + Conventional Commits）、持续集成部署（GitHub Actions 等 CI/CD 工具自动 lint/test/build/deploy）、可维护性（Monorepo 统一配置和依赖管理） |
| 缺点 | 工具链搭建和维护有一定成本；过度规范可能降低开发灵活性；团队需要统一认知和培训 |

## 底层原理

### 代码规范工具

| 维度 | 内容 |
|------|------|
| 是什么 | ESLint 负责代码质量检查（逻辑错误、潜在 bug、最佳实践），Prettier 负责代码格式化（缩进、引号、分号等纯格式问题），两者分工明确 |
| 能做什么 | ESLint 通过静态分析发现潜在错误和不符合规范的代码；Prettier 按统一规则重新格式化，消除因个人习惯导致的代码差异 |
| 怎么用 | ESLint 配置 `eslint.config.mjs`（Flat Config）；Prettier 配置 `.prettierrc.js`：`{ singleQuote: true, semi: false, tabWidth: 2 }` |
| 原理和工作流程 | ESLint 使用 parser（如 @typescript-eslint/parser）将源码解析为 AST，遍历 AST 节点匹配规则，不符合则生成错误/警告。Prettier 将源码解析为自己的 AST 后按固定规则重新输出，不关心原有格式。两者配合通过 eslint-config-prettier 关闭 ESLint 中与 Prettier 冲突的格式规则，让各司其职 |
| 缺点 | 配置不当会导致规则冲突（格式化后 ESLint 报错）；Prettier 的"有主见"风格可能不符合所有团队偏好 |

### Husky + lint-staged

| 维度 | 内容 |
|------|------|
| 是什么 | Husky 管理 Git Hooks 在 Git 操作时自动触发脚本，lint-staged 只对 Git 暂存区文件执行检查，两者结合实现提交前自动检查 |
| 能做什么 | 在 git commit 前自动运行 ESLint 和 Prettier，避免不符合规范的代码进入仓库，提升代码质量一致性 |
| 怎么用 | `pnpm add -D husky lint-staged`；`pnpm exec husky init`；`.husky/pre-commit` 写入 `pnpm lint-staged`；package.json 配置 lint-staged 匹配规则 |
| 原理和工作流程 | Husky 在 .git/hooks 目录创建钩子脚本，拦截 Git 操作。lint-staged 读取 Git 暂存区文件列表，只对匹配的文件执行 ESLint --fix 和 Prettier --write，避免全量检查，大幅提升速度。检查通过后允许提交，失败则阻止提交 |
| 缺点 | 需正确配置 lint-staged 命令格式，否则可能检查所有文件而非暂存文件；Husky 钩子文件需确保可执行 |

### commitlint

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Conventional Commits 规范的 Git 提交信息校验工具，确保提交信息符合团队约定的格式 |
| 能做什么 | 强制统一的 Commit Message 格式 `type(scope): subject`，便于生成 Changelog、定位问题、代码审查 |
| 怎么用 | `pnpm add -D @commitlint/cli @commitlint/config-conventional`；`.husky/commit-msg` 写入 `pnpm exec commitlint --edit $1` |
| 原理和工作流程 | commitlint 在 commit-msg 钩子中拦截提交信息，按配置的规则校验 type（feat/fix/docs/refactor/perf/test/chore/ci/revert）、scope、subject 等字段。type-enum 规则定义允许的 type 列表，subject-case 规则控制标题格式 |
| 缺点 | 常规提交类型较少，特殊场景可能需要自定义 type；团队成员需要学习成本 |

### Git 工作流

| 维度 | 内容 |
|------|------|
| 是什么 | Git Flow 是多分支模型（master/develop/feature/release/hotfix），适合有明确版本发布周期的项目；GitHub Flow 是单分支模型（main + feature），适合持续部署项目 |
| 能做什么 | 规范团队协作的分支管理策略，减少合并冲突，保障代码质量，支持并行开发和紧急修复 |
| 怎么用 | Git Flow：feature 分支从 develop 拉出，完成后合并回 develop；release 分支冻结后修 bug 打 tag，合并到 master 和 develop。GitHub Flow：从 main 拉 feature 分支，PR 合并后立即部署 |
| 原理和工作流程 | Git Flow 核心流程：develop 作为开发主线，feature 从 develop 拉出并在完成后合并回 develop，release 分支从 develop 拉出进行版本冻结和 bug 修复，完成后合并到 master（打 tag 发布）和 develop，hotfix 从 master 拉出紧急修复后合并到 master 和 develop。GitHub Flow 保持 main 始终可部署，feature 分支通过 PR 合并 |
| 缺点 | Git Flow 分支模型复杂，小团队维护成本高；GitHub Flow 不适合有多个并行版本的项目 |

### Commit Message 规范

| 维度 | 内容 |
|------|------|
| 是什么 | Conventional Commits 是标准化提交信息格式，结构为 `type(scope): subject` + 可选的 body 和 footer |
| 能做什么 | 实现自动化 Changelog 生成、语义化版本管理、提交历史可追溯，提升团队协作效率 |
| 怎么用 | `feat(auth): 添加 JWT 登录功能`；`fix(table): 修复分页参数错误`；`refactor(api): 提取公共请求拦截器` |
| 原理和工作流程 | type 标识变更类型（feat 新功能、fix 修复、docs 文档、style 格式、refactor 重构、perf 性能、test 测试、chore 构建工具、ci 配置、revert 回滚），scope 标识影响范围，subject 简明描述变更内容。遵循此规范可配合 standard-version 等工具自动生成版本号和 Changelog |
| 缺点 | 小型个人项目可能显得过于繁琐；scope 粒度需要团队协商统一 |

### CI/CD 流程

| 维度 | 内容 |
|------|------|
| 是什么 | CI（持续集成）是代码合并后自动构建测试的实践，CD（持续部署/持续交付）是自动将构建产物部署到环境的流程 |
| 能做什么 | 减少手动操作避免人为失误，快速发现和修复集成问题，提高发布频率和质量，统一构建环境消除环境差异 |
| 怎么用 | GitHub Actions 配置 `.github/workflows/ci-cd.yml`：push 触发 lint → test → build → deploy 流水线 |
| 原理和工作流程 | CI 阶段：代码推送 → 触发流水线 → 安装依赖（pnpm install --frozen-lockfile）→ lint 检查 → 单元测试 → 构建产物。CD 阶段：构建产物部署到测试/预发布环境 → 自动化端到端测试 → 审批或自动发布到生产环境。通过 --frozen-lockfile 锁定依赖版本，确保一致性 |
| 缺点 | 流水线配置和维护需要 DevOps 知识；构建时间较长可能影响开发效率；敏感信息（SSH 密钥）需通过 Secrets 管理 |

### Monorepo 架构

| 维度 | 内容 |
|------|------|
| 是什么 | 将多个相关项目/包放在同一个 Git 仓库中管理的策略，共享配置、依赖和工具链 |
| 能做什么 | 统一 ESLint/Prettier/TypeScript 配置、代码共享（packages/shared）、原子提交（一次提交修改多个包）、统一依赖管理 |
| 怎么用 | pnpm-workspace.yaml 配置 `packages: ['packages/*', 'apps/*']`；根 package.json 脚本 `"dev:web": "pnpm --filter @my-app/web dev"` |
| 原理和工作流程 | pnpm workspaces 通过符号链接将 workspace 内的包链接到 node_modules，本地包引用使用 `workspace:*` 协议。Turborepo 提供增量构建（只构建变更包及依赖方）、远程缓存（团队共享构建缓存）、并行执行（自动分析依赖关系并行执行无依赖任务）。Nx 提供依赖图分析和只构建受影响项目的优化 |
| 缺点 | 仓库体积大导致克隆慢；构建时间可能较长需工具优化；权限管理困难（所有开发者能看所有代码）；对工具链要求高 |

### 部署方案

| 维度 | 内容 |
|------|------|
| 是什么 | 前端部署方案包括静态托管（Vercel/Netlify/GitHub Pages）、Nginx 自建服务器、Docker 容器化部署和 CDN+OSS 四种主要方式 |
| 能做什么 | 静态托管零运维成本适合个人/小型项目；Nginx 灵活高性能适合中大型项目；Docker 可移植隔离性好；CDN+OSS 适合大流量纯静态资源 |
| 怎么用 | Nginx 核心配置：`try_files $uri $uri/ /index.html`（SPA 路由 fallback）、`gzip on`（压缩）、`location /api/ { proxy_pass http://localhost:8080/ }`（反向代理）、静态资源 `expires 1y` + `Cache-Control "public, immutable"` |
| 原理和工作流程 | Nginx 作为 Web 服务器和反向代理：接收 HTTP 请求 → 检查静态资源缓存 → 匹配 location 规则 → 静态资源直接返回文件，API 请求代理到后端服务 → SPA 路由 fallback 将非文件请求返回 index.html。Docker 多阶段构建：第一阶段用 node 镜像编译，第二阶段用 nginx 镜像只复制 dist 产物，减小镜像体积 |
| 缺点 | 静态托管平台有流量和构建次数限制；Nginx 自建需要运维知识；Docker 构建产物可能过大需优化 |

## 实战应用

### 从零搭建前端工程规范

| 维度 | 内容 |
|------|------|
| 是什么 | 一套完整的初始化脚本，包含 ESLint、Prettier、Husky、lint-staged、commitlint 的安装和配置 |
| 能做什么 | 一键为新项目建立完整的代码规范和提交检查体系，确保团队代码质量从第一天起受控 |
| 怎么用 | `pnpm init` → `pnpm add -D eslint prettier eslint-config-prettier husky lint-staged @commitlint/cli @commitlint/config-conventional` → `pnpm exec husky init` → 配置 .husky/pre-commit 和 .husky/commit-msg |
| 原理和工作流程 | 按顺序安装依赖、初始化 Husky（创建 .husky 目录和 Git 钩子）、配置 lint-staged 匹配规则、配置 commitlint 校验规则、编写 ESLint 和 Prettier 配置文件。pre-commit 钩子触发 lint-staged 对暂存文件执行 ESLint --fix 和 Prettier --write；commit-msg 钩子触发 commitlint 校验提交信息 |
| 缺点 | 初始化步骤较多，可能需要脚本化；TypeScript 项目还需额外安装 @typescript-eslint/parser 等依赖 |

### Monorepo 项目搭建

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 pnpm workspaces 搭建包含共享工具库、公共 UI 组件、多应用（Web + Admin）的 Monorepo 项目结构 |
| 能做什么 | 实现多项目统一配置管理、代码共享、原子提交，提升大型项目的开发效率 |
| 怎么用 | 创建 `pnpm-workspace.yaml`：`packages: ['packages/*', 'apps/*']`；在各子包中通过 `"@my-app/shared": "workspace:*"` 引用本地包 |
| 原理和工作流程 | pnpm 通过 workspace 协议管理本地包依赖，使用符号链接而非复制，共享 node_modules 中相同版本的依赖，节省磁盘空间。根 package.json 通过 `pnpm --filter` 脚本按包名筛选执行命令，`pnpm -r` 递归执行所有子包命令 |
| 缺点 | 需要合理规划包边界和依赖关系，避免循环依赖；构建顺序需通过 Turborepo 等工具管理 |

### 完整的 CI/CD 流水线配置

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 GitHub Actions 的自动化部署流水线，包含依赖安装、lint 检查、单元测试、构建和 SSH 部署 |
| 能做什么 | 实现代码推送后自动完成质量检查、测试和部署，减少人工操作，确保部署一致性 |
| 怎么用 | 创建 `.github/workflows/deploy.yml`，配置 on.push.branches 触发条件，jobs 按 lint → test → build → deploy 串行执行 |
| 原理和工作流程 | push 到 main 分支触发 → checkout 代码 → 安装 pnpm → 安装依赖（--frozen-lockfile）→ lint → test → build → SSH 部署到服务器。使用 --frozen-lockfile 确保依赖版本与 lockfile 一致，避免"在我机器上能跑"的问题 |
| 缺点 | 需配置 GitHub Secrets 存储服务器 SSH 密钥等敏感信息；部署步骤失败时需手动回滚 |

## 常见面试题

### ESLint 和 Prettier 的区别是什么如何配合使用

| 维度 | 内容 |
|------|------|
| 是什么 | 考察代码质量工具和代码格式化工具的分工与协作方式 |
| 能做什么 | 验证候选人是否理解 ESLint 关注逻辑质量（潜在 bug、最佳实践）和 Prettier 关注纯格式（缩进、引号、分号）的职责划分 |
| 怎么用 | 安装 `eslint-config-prettier` 并在 extends 末尾添加 `'prettier'`，关闭 ESLint 中与 Prettier 冲突的规则 |
| 原理和工作流程 | ESLint 通过 AST 分析发现代码质量问题（如未使用变量、可能的空指针），Prettier 重新格式化不考虑原风格。eslint-config-prettier 禁用所有与 Prettier 冲突的 ESLint 规则，让各司其职 |
| 缺点 | 初学者容易混淆两者职责；配置不当仍可能出现规则冲突 |

### Husky 和 lint-staged 的作用是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Husky 管理 Git Hooks 触发自动化脚本，lint-staged 限定检查范围仅对暂存文件执行，两者结合实现提交前自动检查 |
| 能做什么 | 在 git commit 前自动运行 ESLint 和 Prettier，阻止不符合规范的代码进入仓库 |
| 怎么用 | `pnpm add -D husky lint-staged`；`pnpm exec husky init`；.husky/pre-commit 写入 `pnpm lint-staged` |
| 原理和工作流程 | Husky 在 .git/hooks 中创建 pre-commit 钩子脚本，Git 在提交前执行该脚本。lint-staged 读取暂存区文件列表，只对匹配的文件执行检查命令（如 eslint --fix），避免全量检查耗时过长 |
| 缺点 | lint-staged 配置中命令格式不正确会导致检查所有文件；Husky 钩子文件需确保可执行 |

### Git Flow 和 GitHub Flow 有什么区别

| 维度 | 内容 |
|------|------|
| 是什么 | Git Flow 是多分支模型（master/develop/feature/release/hotfix），GitHub Flow 是单分支模型（main + feature 分支），分别适合不同发布节奏的项目 |
| 能做什么 | 根据项目类型选择合适的分支管理策略：有明确版本发布周期的项目用 Git Flow，持续部署的项目用 GitHub Flow |
| 怎么用 | Git Flow：feature 从 develop 拉出合并回 develop；release 从 develop 拉出合并到 master 和 develop。GitHub Flow：feature 从 main 拉出通过 PR 合并回 main，合并后立即部署 |
| 原理和工作流程 | Git Flow 的核心是 develop 分支作为开发主线，只通过 release 分支向 master 发布，hotfix 紧急修复线上的 bug。GitHub Flow 的核心是 main 分支始终保持可部署状态，所有开发通过 feature 分支 + PR 进行 |
| 缺点 | Git Flow 分支模型复杂，小团队维护成本高；GitHub Flow 不适合有多个并行版本的项目 |

### Conventional Commits 规范是什么有哪些 type 类型

| 维度 | 内容 |
|------|------|
| 是什么 | 标准化 Git 提交信息格式 `type(scope): subject`，type 标识变更类型，scope 标识影响范围 |
| 能做什么 | 实现自动化 Changelog 生成、语义化版本管理，提升提交历史可读性 |
| 怎么用 | `feat(auth): 添加 JWT 登录`；`fix(table): 修复分页参数错误`；`chore(deps): 升级 Vue 到 3.4` |
| 原理和工作流程 | 定义 10 种标准 type：feat（新功能）、fix（修复）、docs（文档）、style（格式）、refactor（重构）、perf（性能）、test（测试）、chore（构建工具）、ci（CI/CD）、revert（回滚）。配合 commitlint 在提交时自动校验 |
| 缺点 | 小型个人项目可能显得过于繁琐；scope 粒度需团队协商统一 |

### Monorepo 的优缺点是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Monorepo 是将多个项目/包放在单一仓库中管理的策略，通过 pnpm workspaces 等工具实现 |
| 能做什么 | 统一配置管理、代码共享、原子提交、依赖版本统一，提升大型项目协作效率 |
| 怎么用 | pnpm-workspace.yaml 配置包路径，子包通过 `workspace:*` 协议引用本地包，Turborepo 管理构建流水线 |
| 原理和工作流程 | 优点：一份 ESLint/Prettier/TypeScript 配置所有包共享；公共代码放在 packages/shared 直接引用；一次提交可修改多个包保持一致性；统一依赖管理避免版本冲突。缺点：仓库体积大克隆慢；构建时间可能较长；权限管理困难；对工具链要求高 |
| 缺点 | 不适合小团队或独立项目；需要 Turborepo/Nx 等工具管理构建；权限粒度难以控制 |

## 避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 工程规范实践中常见的配置冲突、工具失效、性能问题和架构陷阱 |
| 能做什么 | 帮助开发者提前识别 ESLint/Prettier 冲突、lint-staged 配置错误、commitlint 不生效、Monorepo 循环依赖、Nginx SPA 404、Docker 镜像过大、CI/CD 依赖版本不一致等问题 |
| 怎么用 | 对照排查：ESLint/Prettier 冲突 → 安装 eslint-config-prettier 并在 extends 最后加 'prettier'；SPA 刷新 404 → 添加 try_files 配置；CI/CD 构建不一致 → 使用 --frozen-lockfile |
| 原理和工作流程 | 常见错误根源：ESLint 和 Prettier 规则重叠互相覆盖（需 eslint-config-prettier 协调）、lint-staged 命令不含文件参数导致全量检查、Husky 钩子未正确安装、Monorepo 包间循环依赖、Nginx 缺少 SPA fallback 配置、Docker 多阶段构建未清理、CI/CD 中使用 pnpm install 而非 --frozen-lockfile 导致版本漂移 |
| 缺点 | 排查这些坑需要同时对多个工具链有深入理解；某些问题（如循环依赖）需要重构代码才能解决 |
