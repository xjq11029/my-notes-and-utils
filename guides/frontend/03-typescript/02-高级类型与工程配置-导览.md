## 一、核心概念

### 1.1 泛型基础

| 维度 | 内容 |
|------|------|
| 是什么 | 在定义函数、接口或类时不指定具体类型，而是使用类型变量（T），使用时再传入具体类型，实现类型安全的代码复用。 |
| 能做什么 | 创建可复用的类型安全组件（如 `Array<T>`）；函数返回类型与参数类型关联（如恒等函数返回与输入相同类型）；避免使用 any 导致类型信息丢失。 |
| 怎么用 | `function identity<T>(arg: T): T { return arg; }`、`const result = identity<string>('hello');`（类型推断可省略 `<string>`） |
| 原理和工作流程 | 泛型在编译时进行类型实例化，每个不同的类型参数组合生成一次类型检查，类型信息在运行时被擦除。泛型约束（extends）限制类型参数必须满足特定条件。 |
| 缺点 | 泛型过度使用导致类型签名过于复杂；泛型嵌套过深时错误信息难以阅读；泛型擦除后运行时无法获取类型信息。 |

### 1.2 泛型约束（extends）

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 `extends` 关键字限制泛型类型参数必须满足特定接口或类型，从而在泛型函数内部安全访问类型的特定属性。 |
| 能做什么 | 约束泛型参数必须具有某些属性或方法，在函数内部使用这些属性时不会报错；实现泛型参数的限定。 |
| 怎么用 | `function getLength<T extends { length: number }>(arg: T): number { return arg.length; }`、`function getProperty<T, K extends keyof T>(obj: T, key: K) { return obj[key]; }` |
| 原理和工作流程 | extends 约束确保 T 类型至少包含指定属性，编译器在泛型内部使用这些属性时不会报错。`K extends keyof T` 表示 K 必须是 T 的键名类型之一。 |
| 缺点 | 约束过多导致泛型失去灵活性，过多约束的泛型不如直接指定具体类型。 |

### 1.3 泛型工具类型

| 维度 | 内容 |
|------|------|
| 是什么 | TypeScript 内置的泛型工具类型，用于类型变换：Partial（可选）、Required（必选）、Readonly（只读）、Pick（选取）、Omit（排除）、Record（记录）、Exclude/Extract（提取）。 |
| 能做什么 | 基于已有类型快速生成新类型，减少重复代码；Partial 将属性变为可选；Pick 从类型中选取部分属性；Omit 从类型中排除部分属性；Record 创建键值对映射类型。 |
| 怎么用 | `Partial<T>`、`Required<T>`、`Readonly<T>`、`Pick<T, K>`、`Omit<T, K>`、`Record<K, T>`、`Exclude<T, U>`、`Extract<T, U>` |
| 原理和工作流程 | 这些工具类型本身是泛型类型，通过映射类型和条件类型实现。Partial 通过 `[P in keyof T]?: T[P]` 将所有属性变为可选；Pick 通过 `[P in K]: T[P]` 选取指定属性。 |
| 缺点 | 嵌套工具类型语法复杂，可读性下降；不了解工具类型会重复手动定义类型。 |

## 二、底层原理

### 2.1 联合类型与交叉类型

| 维度 | 内容 |
|------|------|
| 是什么 | 联合类型（`|`）表示值可以是多种类型之一；交叉类型（`&`）表示合并多个类型的所有属性。 |
| 能做什么 | 联合类型用于函数参数支持多种类型、状态值枚举、类型收窄；交叉类型用于 mixin 模式、组合多个接口。 |
| 怎么用 | 联合：`type Status = 'pending' | 'active' | 'done';`；交叉：`type User = { name: string } & { age: number };` |
| 原理和工作流程 | 联合类型是"或"关系，只能访问共有属性；交叉类型是"且"关系，可以访问所有属性。类型收窄通过 typeof、instanceof、in、自定义类型守卫将联合类型缩小到具体类型。 |
| 缺点 | 交叉类型合并同名属性时，值类型变交叉可能导致 never 类型；联合类型未收窄前只能访问共有属性。 |

### 2.2 类型守卫与类型收窄

| 维度 | 内容 |
|------|------|
| 是什么 | 通过条件判断将联合类型缩小到具体类型的技术，包括 typeof、instanceof、in、自定义类型守卫（is 关键字）。 |
| 能做什么 | 在函数内部针对不同具体类型执行不同逻辑，同时保证类型安全；让 TypeScript 编译器理解条件分支后变量的具体类型。 |
| 怎么用 | `if (typeof x === 'string') { ... }`、`if (x instanceof Date) { ... }`、`if ('length' in x) { ... }`、`function isString(x: unknown): x is string { return typeof x === 'string'; }` |
| 原理和工作流程 | 编译器分析控制流，在条件分支中根据类型守卫将变量类型缩小。`is` 关键字定义自定义类型守卫，返回 true 后编译器将变量视为指定类型。 |
| 缺点 | 自定义类型守卫实现错误会导致类型推断错误，运行时可能异常。 |

### 2.3 映射类型

| 维度 | 内容 |
|------|------|
| 是什么 | 基于已有类型通过 `[P in keyof T]` 遍历属性并生成新类型的语法，内置工具类型 Partial、Required、Readonly 等都是映射类型。 |
| 能做什么 | 批量修改类型属性（如全部变为可选、只读）；根据属性名生成新类型；配合模板字面量类型创建新属性名。 |
| 怎么用 | `type Readonly<T> = { readonly [P in keyof T]: T[P]; };`、`type Nullable<T> = { [P in keyof T]: T[P] | null; };` |
| 原理和工作流程 | `keyof T` 获取 T 的所有属性名联合类型，`[P in keyof T]` 遍历每个属性名，通过 `T[P]` 获取原属性类型。映射类型在编译时展开，生成具体类型。 |
| 缺点 | 映射类型嵌套过深时类型展开后的类型信息量过大，IDE 提示可能不够友好。 |

### 2.4 条件类型

| 维度 | 内容 |
|------|------|
| 是什么 | 根据类型关系进行类型选择的类型级三元表达式：`T extends U ? X : Y`，if 条件成立返回 X 类型，否则返回 Y 类型。 |
| 能做什么 | 实现类型级别条件判断，根据输入类型返回不同输出类型；配合 infer 关键字提取类型中的部分信息；实现递归类型处理。 |
| 怎么用 | `type IsString<T> = T extends string ? true : false;`、`type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;` |
| 原理和工作流程 | 条件类型在编译时求值，根据类型关系选择分支。联合类型作为条件类型输入时自动分发（distributive），每个类型独立判断然后重新联合。infer 关键字在条件类型中声明临时类型变量，从匹配类型中提取信息。 |
| 缺点 | 条件类型分发规则容易遗忘；复杂条件类型嵌套难以调试；infer 使用场景有限。 |

### 2.5 TypeScript 4.9+ 新特性

#### 2.5.1 `satisfies` 关键字（TS 4.9+）

| 维度 | 内容 |
|------|------|
| 是什么 | `satisfies` 关键字用于验证表达式的类型是否匹配某个类型，同时保留表达式更精确的推断类型。与 `as` 类型断言不同，`satisfies` 不会丢失类型信息。 |
| 能做什么 | 类型检查 + 类型推断保留：在确保对象满足某个类型约束的同时，保留每个属性的精确字面量类型；替代 `as` 断言，避免类型信息丢失。 |
| 怎么用 | `const palette = { red: [255, 0, 0], green: '#00ff00' } satisfies Record<Color, RGB \| string>;` 调用 `palette.red[0]` 时类型为 `255`（精确），而非 `number \| string`。 |
| 原理和工作流程 | `satisfies` 在编译时进行双向类型检查：先验证表达式类型是否满足约束，再保留表达式的原始精确类型。`as` 是单向强制转换，`satisfies` 是"验证+保留"。 |
| 缺点 | 仅 TS 4.9+ 可用；与 `as const` 配合使用时需注意类型行为差异。 |

#### 2.5.2 `const` 类型参数（TS 5.0+）

| 维度 | 内容 |
|------|------|
| 是什么 | 在泛型函数中声明 `const` 修饰的类型参数，使得传入的字面量参数被推断为最窄（const）的类型，无需调用方手动添加 `as const`。 |
| 能做什么 | 简化 `as const` 断言的使用，在函数层面控制类型推断的宽度；保留字面量类型，避免类型拓宽为 `string` 或 `number`。 |
| 怎么用 | `function getValues<const T>(items: T[]): T[] { return items; }` 调用 `getValues(['a', 'b', 'c'])` 返回类型为 `readonly ['a', 'b', 'c']`，无需手动 `as const`。 |
| 原理和工作流程 | 编译器在泛型实例化时，将 `const` 修饰的类型参数推断为最窄类型（类似 `as const`），但由函数声明控制而非调用方控制。 |
| 缺点 | 仅 TS 5.0+ 可用；所有调用方都会受到 const 推断影响，无法按调用场景选择是否拓宽。 |

#### 2.5.3 `noInfer<T>` 工具类型（TS 5.4+）

| 维度 | 内容 |
|------|------|
| 是什么 | `noInfer<T>` 用于阻止 TypeScript 从泛型参数中推断类型，让某个参数的类型由其他参数或显式注解决定，而非从当前参数推断。 |
| 能做什么 | 控制泛型推断的"方向"，防止意外推断导致类型变宽或变窄；确保回调参数类型由外部声明决定。 |
| 怎么用 | `function createLogger<T>(levels: T[], defaultLevel: noInfer<T>) { ... }` 调用时 `T` 仅从 `levels` 推断，`defaultLevel` 只被检查是否满足 `T`。 |
| 原理和工作流程 | `noInfer<T>` 在类型推断阶段标记该参数为"非推断源"，编译器跳过该参数进行类型推断，但仍对该参数进行类型检查。 |
| 缺点 | 仅 TS 5.4+ 可用；过度使用可能导致类型推断不完整，需要手动注解。 |

#### 2.5.4 `using` 声明（TS 5.2+）

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 TC39 Explicit Resource Management 提案的显式资源管理语法，声明在作用域结束时自动清理的资源，支持同步（`using`）和异步（`await using`）两种模式。 |
| 能做什么 | 替代 try-finally 模板代码，自动管理文件句柄、数据库连接等资源；通过 `DisposableStack` 组合管理多个资源，按 LIFO 顺序自动清理。 |
| 怎么用 | `using file = new MyFileHandle('data.txt');` 离开作用域时自动调用 `file[Symbol.dispose]()`；异步：`await using db = new DatabaseConnection();`。 |
| 原理和工作流程 | 类实现 `Disposable`（`Symbol.dispose`）或 `AsyncDisposable`（`Symbol.asyncDispose`）接口；编译器在 `using` 声明的作用域结束时自动插入清理代码；`DisposableStack` 内部维护资源栈，按 LIFO 逆序释放。 |
| 缺点 | 需要目标环境支持 `Symbol.dispose`/`Symbol.asyncDispose`（或 polyfill）；目前仍是 Stage 3 提案，API 可能微调。 |

## 三、实战应用

### 3.1 模块（ESM / CJS）

| 维度 | 内容 |
|------|------|
| 是什么 | TypeScript 支持 ES Module 和 CommonJS 两种模块系统，通过 import/export 或 require/module.exports 实现代码分割。 |
| 能做什么 | 按功能拆分代码为独立模块，控制作用域和导出；import type 仅导入类型不产生运行时代码；ESM 支持 Tree Shaking。 |
| 怎么用 | ESM：`export const x = 1; import { x } from './module';`；CJS：`export = ...; import x = require('./module');`；仅类型导入：`import type { User } from './types';` |
| 原理和工作流程 | tsconfig.json 中 module 配置决定编译后的模块格式。moduleResolution 决定模块查找策略（node 或 classic）。import type 在编译时被完全移除，不产生运行时代码。 |
| 缺点 | ESM 和 CJS 混用容易出现兼容问题；require 导入的类型信息不如 import 完整。 |

### 3.2 命名空间（Namespace）

| 维度 | 内容 |
|------|------|
| 是什么 | TypeScript 内部模块机制，使用 namespace 关键字将相关代码组织在一起，编译为 IIFE（立即执行函数表达式）。 |
| 能做什么 | 在单个文件中组织相关代码，防止全局命名冲突；将多个文件编译为一个文件时使用。 |
| 怎么用 | `namespace Util { export function fn() {} }`、`Util.fn();`、`/// <reference path="..." />` 三斜杠指令引用命名空间 |
| 原理和工作流程 | namespace 在编译时生成 IIFE，内部代码闭包隔离，export 暴露到命名空间对象上。编译后通过对象属性访问。 |
| 缺点 | ES Module 成为标准后不推荐使用 namespace；三斜杠指令已过时，推荐使用 import/export。 |

### 3.3 声明文件（.d.ts）

| 维度 | 内容 |
|------|------|
| 是什么 | 以 `.d.ts` 结尾的类型声明文件，包含类型定义但不包含实现代码，为 JavaScript 库提供类型信息。 |
| 能做什么 | 为第三方 JavaScript 库提供类型支持（DefinitelyTyped）；为全局变量或模块声明类型；声明全局类型扩展。 |
| 怎么用 | `declare module 'lodash' { ... }`、`declare const process: { env: ... };`、`declare global { ... }`、`pnpm install @types/lodash` |
| 原理和工作流程 | 声明文件只有类型信息，编译器读取后获得类型知识，运行时不受影响。`@types` 是 DefinitelyTyped 社区维护的类型定义库，npm 安装后自动获得类型支持。`declare global` 扩展全局作用域类型。 |
| 缺点 | 声明文件版本与库版本不匹配时类型错误；编写声明文件需要理解库的 API，工作量较大。 |

### 3.4 tsconfig.json 详解

| 维度 | 内容 |
|------|------|
| 是什么 | TypeScript 项目配置文件，控制编译选项、文件包含范围、项目引用等。 |
| 能做什么 | 配置编译目标、模块系统、严格模式、输出目录、路径别名、项目引用等。 |
| 怎么用 | `tsc --init` 生成配置文件；关键配置：compilerOptions（编译选项）、include（包含文件）、exclude（排除文件）、extends（继承配置）、references（项目引用） |
| 原理和工作流程 | 编译器读取 tsconfig.json 确定编译范围和行为。strict 选项组合开启所有严格检查；baseUrl 和 paths 配置路径别名，需要配合构建工具使用。 |
| 缺点 | 配置选项过多，需要理解每个选项的含义；错误配置可能导致编译失败或类型检查不完整。 |

### 3.5 严格模式详解

| 维度 | 内容 |
|------|------|
| 是什么 | tsconfig.json 中 strict: true 开启的一组严格类型检查选项，包括 strictNullChecks、strictFunctionTypes、noImplicitAny 等。 |
| 能做什么 | 提升类型安全等级，避免常见类型错误；strictNullChecks 防止 null/undefined 赋值给其他类型；noImplicitAny 禁止隐式 any 类型。 |
| 怎么用 | `"strict": true` 一键开启所有严格检查；`"strictNullChecks": true` 防止 null/undefined 错误；`"noImplicitAny": true` 禁止隐式 any；`"strictFunctionTypes": true` 严格函数类型检查。 |
| 原理和工作流程 | 每个子选项针对特定类型安全问题：strictNullChecks 将 null 和 undefined 从其他类型中排除，访问前必须类型守卫；noImplicitAny 强制所有变量必须显式声明类型。 |
| 缺点 | 严格模式增加开发工作量，需要更多类型注解；从非严格模式迁移需要大量修改。 |

### 3.6 路径别名配置

| 维度 | 内容 |
|------|------|
| 是什么 | 在 tsconfig.json 中配置 baseUrl 和 paths，将 `@/components/Button` 等别名映射到文件系统路径，配合构建工具使用。 |
| 能做什么 | 简化 import 路径，避免深层相对路径 `../../../../`；方便重构时移动文件只需修改配置。 |
| 怎么用 | `"baseUrl": "./src", "paths": { "@/*": ["./*"] }`，需要配合 Webpack resolve.alias 或 Vite resolve.alias 同步配置。 |
| 原理和工作流程 | TypeScript 编译器在解析模块时使用 paths 映射，将别名路径转换为实际文件路径。构建工具需要同步配置，否则编译通过但打包失败。 |
| 缺点 | 需要 TypeScript 和构建工具同步配置，不一致时出现编译通过打包失败。 |

## 四、常见面试题

### 1. 泛型的作用和使用场景

| 维度 | 内容 |
|------|------|
| 是什么 | 考查泛型概念、作用、使用场景和泛型约束。 |
| 能做什么 | 检验对 TypeScript 泛型核心特性的理解。 |
| 怎么用 | 泛型用于创建可复用类型安全的组件，保留类型信息；常见的 `Array<T>`、`Promise<T>` 就是泛型；泛型约束限制类型参数需满足条件。 |
| 原理和工作流程 | 泛型在编译时进行类型实例化，不同参数类型生成不同检查，运行时擦除。工具类型如 Partial、Pick 等底层都是泛型。 |
| 缺点 | 复制粘贴时遗漏泛型参数导致类型错误；错误信息难阅读。 |

### 2. 类型守卫是什么，有哪些实现方式

| 维度 | 内容 |
|------|------|
| 是什么 | 考查类型守卫概念和四种实现方式：typeof、instanceof、in、自定义 is 类型守卫。 |
| 能做什么 | 检验对类型收窄的理解，能否正确处理联合类型。 |
| 怎么用 | typeof 判断基本类型；instanceof 判断实例类型；in 判断属性存在；自定义 is 类型守卫实现判断逻辑。 |
| 原理和工作流程 | 编译器分析控制流，在条件分支中根据类型守卫将变量类型收窄。自定义类型守卫通过 is 关键字告诉编译器判断结果与类型的关系。 |
| 缺点 | 不熟悉自定义 is 类型守卫语法是常见问题。 |

### 3. tsconfig.json 中 strict 模式的作用

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 strict 模式包含的子选项及其作用。 |
| 能做什么 | 检验对 TypeScript 工程配置的理解。 |
| 怎么用 | strict: true 包含 strictNullChecks、strictFunctionTypes、noImplicitAny 等所有严格检查选项，推荐开启。 |
| 原理和工作流程 | 严格模式是 TypeScript 官方推荐的配置，能在编译阶段捕获更多类型错误，提升代码质量。项目从创建就应该开启。 |
| 缺点 | 不知道严格模式开启哪些子选项是常见问题。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总 TypeScript 高级类型和工程配置中 5 个高频错误：泛型过度使用、类型守卫 missing、strict 模式未开启、路径别名未同步、声明文件冲突。 |
| 能做什么 | 帮助开发者避免高级类型和配置中的常见陷阱。 |
| 怎么用 | 泛型保持简洁，非必要不引入；联合类型函数内部使用类型守卫；创建项目立即开启 strict: true；路径别名在 TypeScript 和构建工具同步配置；检查 @types 版本与库版本匹配。 |
| 原理和工作流程 | 每个错误对应一个工程实践问题：泛型过度增加复杂度；未类型守卫导致联合类型只能访问共有属性；strict 未开启让类型安全退化；路径别名不一致导致编译通过打包失败。 |
| 缺点 | 严格模式和路径别名配置需要了解全部选项，学习成本较高。 |

## 补充：.d.ts 声明文件系统

### 补1 三种类型来源与 declare 语法

| 维度 | 内容 |
|------|------|
| 是什么 | 声明文件（`.d.ts`）只描述类型、不含实现。项目类型来源有三处：TS 内置 `lib.*.d.ts`、第三方 `node_modules/@types/*`、项目自写的 `*.d.ts`（或在 `.ts` 里用 `declare`）。 |
| 能做什么 | 为无类型的第三方库补类型；为全局变量、环境变量、构建期注入常量声明类型；扩展已有全局类型（如给 `Window` 加字段）。 |
| 怎么用 | `declare const __BUILD_VERSION__: string`；`declare function gtag(cmd: string, ...args: unknown[]): void`；`declare class LegacySDK { init(token: string): void }`；`declare namespace MyLib { interface Options { debug?: boolean } }`；库项目用 `"declaration": true` 生成 `.d.ts`。 |
| 原理和工作流程 | `.d.ts` 中的顶层声明都是环境声明（隐式 `declare`），只提供类型、不生成运行时代码。内置声明由 `target` + `lib` 决定加载哪些（如 `lib.dom.d.ts`）；`@types` 默认从 `typeRoots`（`node_modules/@types`）自动加载，可用 `types` 白名单收窄。类型查找顺序：`package.json` 的 `types`/`typings` → `exports` 的 `types` 条件 → `@types/<pkg>`。 |
| 缺点 | 声明文件与库版本不匹配会报错；手写声明需要理解库的 API，维护成本高；`@types` 全量自动加载会拖慢编译并污染全局类型。 |

### 补2 全局声明与模块声明

| 维度 | 内容 |
|------|------|
| 是什么 | 含顶层 `import`/`export` 的文件是模块（声明仅模块内可见），否则是全局脚本（声明注入全局）。`declare global {}` 用于在模块中做全局增强，`declare module 'x'` 既可以是环境模块声明，也可以是模块增强。 |
| 能做什么 | 在模块化项目里安全地扩展 `Window`、`ImportMeta` 等全局接口；为无类型的包补类型；用通配符声明让 TS 接受非 JS 资源导入。 |
| 怎么用 | `export {};` 后写 `declare global { interface Window { __APP_CONFIG__: { apiBase: string } } }`；补类型用独立 `.d.ts`：`declare module "legacy-chart" { export interface ChartOptions { width: number }; export default class Chart { render(data: number[]): void } }`；CommonJS 用 `export = format`；资源用 `declare module "*.css" { const classes: { readonly [key: string]: string }; export default classes }`。 |
| 原理和工作流程 | 模块判定只看有没有顶层 `import`/`export`，这决定了声明是全局还是模块作用域，也是 `declare global` 必须先 `export {}` 的原因。`declare module 'x'` 写在全局脚本里是「环境模块声明」（不要求模块存在），写在模块文件里是「模块增强」（要求能解析到目标模块，否则报 `Invalid module name in augmentation`）。`*.vue` 这类 shim 只对纯 tsc 项目必要，使用 vue-tsc / Volar 时反而会让组件 props 类型退化为 `any`。 |
| 缺点 | 全局声明容易造成命名冲突与全局污染；`declare module` 的两种语义差异隐蔽，容易写错位置；通配符声明会让所有匹配文件都拿到同一类型，丢失精确性。 |

## 补充：paths 路径别名实战

### 补1 baseUrl / paths 配置与构建工具配合

| 维度 | 内容 |
|------|------|
| 是什么 | `baseUrl` 指定非相对导入的解析基准目录，`paths` 在其上建立「别名 → 实际路径」映射。**它只影响类型解析，不改写生成的 import 语句。** |
| 能做什么 | 消除 `../../../` 深层相对路径；集中管理模块路径，移动文件只需改配置；让编辑器跳转与自动导入更稳定。 |
| 怎么用 | `"baseUrl": ".", "paths": { "@/*": ["src/*"], "@components/*": ["src/components/*"] }`；Vite：`resolve.alias: { "@": fileURLToPath(new URL("./src", import.meta.url)) }`；Webpack：`resolve.alias: { "@": path.resolve(__dirname, "src") }`；Jest：`moduleNameMapper: { "^@/(.*)$": "<rootDir>/src/$1" }`。 |
| 原理和工作流程 | TS 4.1 起 `paths` 可脱离 `baseUrl` 使用，此时取值相对于声明它的 tsconfig 所在目录解析。运行时/打包时的解析由构建工具负责，所以必须同步配置，否则会出现「编辑器不报错、`vite build` 失败」。发布库时 tsc 不会改写 import 路径，`@/xxx` 会原样写入产物与 `.d.ts`，需用 `tsc-alias` / `tsup` / `vite-plugin-dts` 处理。 |
| 缺点 | TS 与构建工具双份配置容易漂移；继承配置中的相对路径基准不同，易出错；发布 npm 包时必须额外处理路径改写。 |

### 补2 tsconfig 继承与多环境配置

| 维度 | 内容 |
|------|------|
| 是什么 | 用 `extends` 把公共编译选项抽到 `tsconfig.base.json`，再由 `tsconfig.app.json`（浏览器）与 `tsconfig.node.json`（Node）分别覆盖，形成多环境配置。 |
| 能做什么 | 避免在浏览器代码里误用 Node 全局类型（`process`、`Buffer`），反之亦然；让不同运行环境使用各自合适的 `lib` 与 `types`；统一严格性规则，减少重复配置。 |
| 怎么用 | `"extends": "./tsconfig.base.json"`；浏览器侧 `"lib": ["ES2022", "DOM", "DOM.Iterable"], "types": ["vite/client"]`；Node 侧 `"lib": ["ES2023"], "types": ["node"]`；TS 5.0+ 支持 `"extends": ["./base.json", "./strict.json"]`（后写者覆盖前者）；官方模板用根 `tsconfig.json` 的 `"files": []` + `references` 组织子项目（被引用子项目需开 `composite`）。 |
| 原理和工作流程 | `extends` 继承时，`compilerOptions` 里的相对路径（含 `paths`）相对于**被继承的配置文件**解析，而 `files` / `include` / `exclude` 相对于**当前子配置文件**解析——这是继承出错的高频原因。若只想按环境分别检查而不产出文件，直接用 `tsc -p tsconfig.app.json --noEmit` 即可，不必引入 `references`。 |
| 缺点 | 配置文件数量变多，排查问题需要先确认「当前生效的是哪一份」；`extends` 的路径基准规则不直观；`references` 要求 `composite`，与「只检查不产出」的目标存在张力。 |

## 补充：与 Vue / React 的类型集成

### 补1 Vue：vue-tsc 与 defineProps / withDefaults

| 维度 | 内容 |
|------|------|
| 是什么 | `.vue` 单文件组件不是标准 TS 文件，需要 `vue-tsc`（Volar 的 CLI 封装）做类型检查；`defineProps` / `defineEmits` / `defineSlots` / `defineExpose` 是无需 import 的编译宏。 |
| 能做什么 | 在 `<script setup>` 中声明类型安全的 props、emits、插槽与暴露接口；`withDefaults` 为可选 props 提供默认值并让类型不再包含 `undefined`；`PropType<T>` 处理运行时 props 声明中的复杂类型；`InjectionKey<T>` 让 provide/inject 类型一致。 |
| 怎么用 | `withDefaults(defineProps<Props>(), { count: 0, tags: () => [] })`；`defineEmits<{ change: [id: number] }>()`（Vue 3.3+）或 `defineEmits<{ (e: "change", id: number): void }>()`；泛型组件 `<script setup lang="ts" generic="T extends { id: number }">`；CI 中执行 `vue-tsc --noEmit`。 |
| 原理和工作流程 | Vite 只做转译不做类型检查，`<script setup>` 里的类型在构建时被擦除，类型错误不会让构建失败，因此必须单独跑 `vue-tsc`。`defineProps<Props>()` 的类型参数会被编译器静态分析以生成运行时 props 声明，所以必须是类型字面量或可静态解析的类型引用（Vue 3.3 起支持引用导入的类型，之前必须写在同文件）。`withDefaults` 会让带默认值的 props 在结果类型中变为「一定有值」。 |
| 缺点 | 只跑 `vite build` 会漏掉类型错误；`defineProps` 对类型写法有静态分析限制；数组/对象默认值必须写成工厂函数，否则所有实例共享同一对象。 |

### 补2 React：ComponentProps / FC / 事件与泛型组件

| 维度 | 内容 |
|------|------|
| 是什么 | React 组件就是普通函数，类型集成的核心是精确描述 props、children、ref、事件与泛型；`ComponentProps` / `ComponentPropsWithRef` / `ComponentPropsWithoutRef` 用于从组件或内置元素提取 props 类型。 |
| 能做什么 | 组合原生元素属性（如给自定义按钮加上 `button` 的全部属性）；从已有组件提取 props；用泛型组件表达「items 与 renderItem 同类型」；用 `React.ChangeEvent<T>` 等类型描述事件；用 `forwardRef` + `useImperativeHandle` 暴露命令式方法。 |
| 怎么用 | `type ButtonProps = ComponentPropsWithoutRef<"button"> & { variant?: "primary" \| "ghost" }`；`function List<T>({ items, renderItem }: ListProps<T>) {}`；JSX 中显式指定 `<List<string> ... />`；`(e: ChangeEvent<HTMLInputElement>) => setKeyword(e.target.value)`；`useRef<HTMLInputElement>(null)`。 |
| 原理和工作流程 | 组合原生元素属性时用 `ComponentPropsWithoutRef` 可避免与自己的 ref 转发冲突（`ComponentProps` 含原生 ref 类型）。`React.FC<P>` 会带上 `displayName`、`defaultProps` 等静态属性；`@types/react` 18 之前它还隐含 `children?: ReactNode`，18 起移除，因此需要 children 时应显式写 `PropsWithChildren<P>`。泛型组件在 React 中就是泛型函数，TS 2.9+ 支持在 JSX 里显式传入类型实参。事件对象类型由 JSX 属性自动推断，抽出处理函数时才需要 `React.ChangeEventHandler<T>` 这类现成类型。React 19 中 `ref` 已成为普通 prop，可不再使用 `forwardRef`。 |
| 缺点 | 依赖 `@types/react` 版本差异（隐式 children 的移除、`useRef` 返回类型的变化）容易造成升级阵痛；`FC` 与普通函数组件写法混用会让风格不统一；`ComponentProps` 系列与 ref 转发组合时需要仔细选择变体。 |

## 补充：TS 编译性能

### 补1 isolatedModules / verbatimModuleSyntax / importsNotUsedAsValues

| 维度 | 内容 |
|------|------|
| 是什么 | 三个与「单文件转译」相关的选项：`isolatedModules` 报出逐文件转译会出错的写法；`verbatimModuleSyntax`（TS 5.0+）让导入导出写法与产物一一对应；`importsNotUsedAsValues` 已被前者取代（5.0 废弃、5.5 移除）。 |
| 能做什么 | 保证 tsc 与 esbuild / swc / Babel 的行为一致，避免「本地检查通过、打包后运行报错」；让类型导入在产物中被确定地删除，减少无效导入与副作用误删。 |
| 怎么用 | `"isolatedModules": true`；类型再导出写 `export type { User } from "./types"` 或行内 `export { type User, createUser }`；`"verbatimModuleSyntax": true` 时类型导入必须写 `import type`，纯副作用导入写 `import "./polyfill"`。 |
| 原理和工作流程 | 打包器逐文件转译，无法判断导入是类型还是值，也无法跨文件内联 `const enum`，`isolatedModules` 因此把这些写法报成错误。`verbatimModuleSyntax` 取消了两类隐式改写：不再猜测类型导入、不再自动删除未使用的值导入；它与输出格式强绑定——文件被判定为 CommonJS（`.cts` 或 `package.json` 的 `"type": "commonjs"`）时使用 ESM 语法会报 `ESM syntax is not allowed in a CommonJS module`，需改用 `import x = require("x")`。 |
| 缺点 | 开启后存量代码需要批量改造导入写法；`verbatimModuleSyntax` 与 `module` 格式强耦合，配置不当会大面积报错；`const enum` 在单文件转译下无法跨文件内联，建议改用 `as const` 对象。 |

### 补2 项目引用、增量构建与 skipLibCheck

| 维度 | 内容 |
|------|------|
| 是什么 | `references` + `composite` 是项目级拆分（`tsc -b` 按依赖图增量构建）；`incremental` 是单项目增量编译（靠 `.tsbuildinfo`）；`skipLibCheck` 跳过所有 `.d.ts` 内部的类型检查。 |
| 能做什么 | monorepo 中只重建受影响的子项目，引用方只读被引用项目的 `.d.ts`；单项目跳过未变更文件的检查；用 `skipLibCheck` 省掉大量第三方声明检查时间。 |
| 怎么用 | 被引用项目：`"composite": true` + `"tsBuildInfoFile": "./node_modules/.tmp/x.tsbuildinfo"` + `"outDir"`；引用方：`"references": [{ "path": "../utils" }]`；构建：`tsc -b packages/app`、`tsc -b --watch`、`tsc -b --clean`；`"skipLibCheck": true`。 |
| 原理和工作流程 | `composite` 要求项目能产出声明文件（隐式开启 `declaration`），`tsc -b` 据此建立依赖图并复用 `.tsbuildinfo`，只重新检查受影响的子项目。`skipLibCheck` 跳过的是**声明文件内部**的检查，业务代码对这些类型的使用仍会检查；因此它能掩盖自己手写 `.d.ts` 里的错误，以及库之间类型冲突（问题会推迟到业务代码暴露）。 |
| 缺点 | `composite` 与「只检查不产出」的目标存在张力（子项目需要能产出 `.d.ts`）；`.tsbuildinfo` 未持久化会导致每次全量检查；`skipLibCheck` 牺牲了声明文件的正确性校验。 |

### 补3 编译慢的排查与常见提速手段

| 维度 | 内容 |
|------|------|
| 是什么 | 一套定位「TS 为什么慢」的方法：用 `--extendedDiagnostics` 看统计、用 `--generateTrace` 定位昂贵类型，再针对 `include` 范围、`types` 白名单、复杂条件类型等做优化。 |
| 能做什么 | 快速区分是「文件太多」「类型太多」还是「类型实例化爆炸」；定位到具体是哪个类型/哪个文件最耗时；把 CI 的类型检查时间控制在可接受范围。 |
| 怎么用 | `pnpm exec tsc --noEmit --extendedDiagnostics` 关注 `Files` / `Types` / `Instantiations` / 各阶段耗时；`tsc --noEmit --generateTrace ./trace` 后用 `@typescript/analyze-trace` 分析；配置侧：`"incremental": true`、`"skipLibCheck": true`、`"types": ["node", "vite/client"]`、精确的 `include` / `exclude`。 |
| 原理和工作流程 | 类型检查的主要成本是**类型实例化**：递归映射类型、深层条件类型、超大联合类型会产生指数级实例化，表现为编译慢、编辑器卡顿，甚至报 `Type instantiation is excessively deep and possibly infinite`。此外，`include` 范围过大、`@types` 全量自动加载（`types` 未收窄）也会显著增加文件数与检查量。 |
| 缺点 | `--extendedDiagnostics` 只给总量、不指向具体类型，需要配合 trace 工具才能定位；拆解复杂类型会牺牲一定的类型精度；增量缓存需要在 CI 中额外配置持久化。 |
