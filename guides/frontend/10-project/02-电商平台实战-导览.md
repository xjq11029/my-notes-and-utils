## 一、核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | 电商全栈平台是以 Vue 3 + TypeScript + Node.js BFF + MySQL/Redis + Prisma ORM 为核心技术栈，涵盖商品管理、订单系统、购物车、支付集成和用户中心的全栈实战项目 |
| 能做什么 | 构建功能完整的电商平台，包含商品搜索与筛选、购物车状态管理、订单状态机、支付回调处理、库存防超卖等高并发场景解决方案 |
| 怎么用 | 前端 `pnpm create vite` 创建项目；BFF 层 `pnpm init` 初始化 Node.js 项目，`pnpm dlx prisma init` 初始化 ORM；Docker Compose 一键部署 MySQL、Redis、ES、BFF 和 Nginx |
| 原理和工作流程 | 前端 Vue 3 通过 Axios 请求 BFF 层（Node.js Express/Koa），BFF 层负责接口聚合、数据裁剪、鉴权校验和缓存加速，通过 Prisma ORM 操作 MySQL，Redis 做热点缓存和分布式锁，ES 提供商品全文搜索，支付通过回调异步处理 |
| 缺点 | 全栈项目涉及技术栈较多，学习曲线陡峭；BFF 层增加了系统复杂度 |

## 二、底层原理

### 需求分析与架构设计

| 维度 | 内容 |
|------|------|
| 是什么 | 覆盖五大核心模块（商品管理、订单系统、购物车、支付集成、用户中心）的电商全栈平台，采用前端 Vue 3 + BFF 层 Node.js + 数据层 MySQL/Redis/ES 的三层架构 |
| 能做什么 | 提供商品搜索筛选、购物车合并、订单状态机、支付回调幂等、库存防超卖等企业级电商解决方案 |
| 怎么用 | 三层架构：客户端（PC/Mobile/小程序）→ 网关层（Nginx 负载均衡、SSL 终止）→ BFF 层（Express/Koa 路由 + 中间件 + Service）→ 数据层（MySQL 主从、Redis Cluster、Elasticsearch、OSS） |
| 原理和工作流程 | BFF 层作为前后端中间层，负责接口聚合（商品详情 = 商品信息 + 评价 + 推荐）、数据裁剪（PC/Mobile 返回不同字段）、鉴权统一（JWT 中间件）和缓存加速（Redis 中间件）。Service 层封装业务逻辑，通过 Prisma ORM 访问数据库 |
| 缺点 | 三层架构增加了请求链路，需要做好超时控制和降级策略 |

### 数据库设计

| 维度 | 内容 |
|------|------|
| 是什么 | 以 MySQL 为核心的关系型数据库设计，包含用户表、商品表、SKU 表、购物车表、订单表、订单项表、支付记录表等核心表，通过 Prisma ORM 管理 Schema 和迁移 |
| 能做什么 | 支撑电商核心业务数据存储，通过索引优化查询性能，支持事务保证数据一致性 |
| 怎么用 | Prisma Schema 定义模型 → `prisma migrate dev` 生成迁移 → `prisma generate` 生成类型安全的 Client；订单项使用快照存储（下单时保存商品名称、价格、规格），避免后续商品变更影响历史订单 |
| 原理和工作流程 | 核心 ER 关系：用户 1:N 订单/购物车/地址，商品 1:N SKU/图片，订单 1:N 订单项，订单项 N:1 SKU。订单项存快照保证历史数据完整性。DECIMAL 存储金额避免浮点精度问题 |
| 缺点 | 外键约束在高并发下有性能开销；需要进行合理的索引设计和慢查询优化 |

### 商品搜索与筛选

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Elasticsearch 的商品全文搜索引擎，支持关键词匹配、多条件筛选、排序和分页；无 ES 时降级为 MySQL + Redis 多级缓存方案 |
| 能做什么 | 实现商品名称/描述的高亮搜索、分类筛选、价格区间筛选、销量/价格/新品排序 |
| 怎么用 | ES 方案：`multi_match` 查询（name^3、description^1、category_name^2），`bool` 组合查询（must + filter），`highlight` 高亮返回；前端用 `useDebounceFn` 防抖 300ms 触发搜索 |
| 原理和工作流程 | ES 通过倒排索引实现快速全文搜索，分词器（如 IK）支持中文分词；MySQL 方案使用 FULLTEXT 索引 + LIKE 模糊查询，Redis 缓存搜索结果（key: `product:search:{hash}`，TTL 5分钟） |
| 缺点 | ES 需要额外部署和维护；MySQL 全文搜索不支持分词，中文搜索效果差 |

### 购物车状态管理

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Pinia 的购物车全局状态管理，支持未登录（localStorage）和已登录（服务端 MySQL）两种状态，登录后自动合并 |
| 能做什么 | 管理购物车商品的增删改查、选中/取消选中、全选/取消全选、数量变更、总价计算，以及未登录与登录状态的购物车合并 |
| 怎么用 | `useCartStore` 定义状态和方法：`fetchCart()` 获取列表、`addItem(skuId, quantity)` 添加、`updateQuantity(cartId, quantity)` 修改数量、`toggleItem(cartId)` 切换选中、`mergeCart()` 合并本地购物车 |
| 原理和工作流程 | 未登录时购物车数据存在 `localStorage`（`guest_cart`）；登录后调用 `mergeCart()` 将本地数据同步到服务端，相同 SKU 取最大数量。数量变更采用乐观更新（先更新本地 UI，再异步同步后端），提升操作响应速度 |
| 缺点 | 合并逻辑需要处理冲突（如相同 SKU 取大还是累加）；乐观更新失败需要回滚 UI |

### 订单状态机

| 维度 | 内容 |
|------|------|
| 是什么 | 基于状态转移表（transitions）的订单状态机，定义 7 种状态（待支付/已支付/已发货/已完成/已取消/退款中/已退款）和合法转移规则，通过乐观锁保证并发安全 |
| 能做什么 | 控制订单生命周期的合法流转，防止状态跳跃（如直接从待支付跳到已发货），处理状态变更的副作用（扣库存、发通知、写日志） |
| 怎么用 | `transitionOrder(orderId, action)` 函数，传入订单 ID 和操作类型（pay/cancel/ship/confirm/refund/approve/reject），自动校验状态转移合法性并执行副作用 |
| 原理和工作流程 | `transitions` 映射表定义每个状态可转移到的目标状态列表，`transitionActions` 定义触发动作。使用 Prisma 事务 + `updateMany` 乐观锁（`WHERE status = currentStatus`）更新状态，防止并发修改。副作用处理独立于状态转移 |
| 缺点 | 状态机复杂度随业务场景增长；需要仔细设计转移规则避免死循环 |

### 库存扣减与防超卖

| 维度 | 内容 |
|------|------|
| 是什么 | 多层防护的库存扣减方案：Redis 预减库存（Lua 脚本原子操作）→ 数据库乐观锁（`WHERE stock >= quantity`）→ 消息队列异步下单，确保高并发下不超卖 |
| 能做什么 | 处理秒杀、抢购等高并发场景下的库存扣减，防止同一库存被多次扣减 |
| 怎么用 | `deductStockInRedis(skuId, quantity)` 用 Lua 脚本原子扣减；`deductStockInDB(skuId, quantity)` 用 `updateMany({ where: { stock: { gte: quantity } } })` 乐观锁扣减；失败时回滚 Redis 库存 |
| 原理和工作流程 | 下单流程：Redis 预减库存 → 创建订单 → 数据库真实扣减。Redis 预减失败直接返回库存不足；数据库扣减失败回滚 Redis 库存。Lua 脚本保证 Redis 操作的原子性（先 GET 检查库存，再 DECRBY 扣减） |
| 缺点 | Redis 和数据库库存可能短暂不一致；极端情况下需要手动对账修复 |

### 支付集成

| 维度 | 内容 |
|------|------|
| 是什么 | 集成支付宝/微信支付的支付流程：前端发起支付 → 第三方支付 → 异步回调通知 → BFF 层验签 → 更新订单状态，核心关注幂等性处理和签名验证 |
| 能做什么 | 实现完整的支付闭环，保证支付回调的幂等性（不重复处理），验签防止伪造回调 |
| 怎么用 | `handleAlipayCallback(params)` 处理支付宝回调：验签 → 幂等检查（trade_no 去重）→ 分布式锁（`payment:lock:{orderId}`）→ 事务更新订单和支付记录 |
| 原理和工作流程 | 回调处理三步：1. RSA 验签确保请求来自支付宝；2. 根据 `trade_no` 判断是否已处理（幂等）；3. Redis 分布式锁防止并发重复处理。使用 Prisma 事务 + `upsert` 保证支付记录和订单状态原子更新 |
| 缺点 | 支付回调可能因网络问题延迟或丢失，需要主动查询接口兜底；验签需要正确配置支付宝公钥 |

### 性能优化

| 维度 | 内容 |
|------|------|
| 是什么 | 全面的性能优化方案：Redis 多级缓存策略（商品详情/分类/推荐/购物车）、缓存穿透/击穿/雪崩防护、数据库索引优化、前端图片懒加载 + 路由懒加载 + 虚拟列表 |
| 能做什么 | 将商品详情接口从 200ms 优化到 20ms，支持 10000+ 商品列表流畅滚动 |
| 怎么用 | Redis 缓存：`cacheMiddleware(ttl)` 中间件自动缓存接口响应；防穿透：布隆过滤器；防击穿：互斥锁；防雪崩：TTL 加随机值。数据库索引：复合索引 `(category_id, status)`、覆盖索引 `(user_id, status, created_at)`。前端：`v-lazy` 图片懒加载 + `() => import()` 路由懒加载 + `useVirtualList` 虚拟列表 |
| 原理和工作流程 | 请求 → Redis 缓存命中（直接返回）→ 未命中（查询数据库 + 写入缓存）。缓存穿透：布隆过滤器判断 key 是否存在；缓存击穿：互斥锁保证只有一个线程查询数据库；缓存雪崩：TTL 加随机值避免同时过期 |
| 缺点 | 缓存策略增加了系统复杂度；缓存一致性需要额外处理 |

### 部署方案

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Docker Compose 的容器化部署方案，包含 Nginx（反向代理 + 静态资源 + SSL）、BFF（Node.js）、MySQL、Redis、Elasticsearch 五个服务，配合 GitHub Actions 实现 CI/CD 自动化 |
| 能做什么 | 一键部署完整电商平台，支持灰度发布和自动回滚 |
| 怎么用 | `docker-compose up -d` 启动所有服务；GitHub Actions 监听 `main` 分支 push → 构建前端和 BFF → 构建 Docker 镜像 → 推送到镜像仓库 → SSH 远程部署 |
| 原理和工作流程 | Nginx 作为入口，80 端口重定向到 443，SSL 终止后转发到 BFF 层（`/api/`）或静态资源（前端 SPA）。BFF 连接 MySQL、Redis、ES。限流通过 `limit_req` 控制。CI/CD 通过 GitHub Actions 的 `ssh-action` 远程执行 `docker-compose up -d` |
| 缺点 | Docker Compose 适合单机部署，大规模集群需要 Kubernetes；CI/CD 配置需要保护敏感信息 |

## 三、实战应用

### 商品搜索与筛选

| 维度 | 内容 |
|------|------|
| 是什么 | 前端商品搜索筛选组件 + 后端 ES/MySQL 搜索服务，支持关键词搜索、分类筛选、价格区间、排序和分页 |
| 能做什么 | 实现类似淘宝的商品搜索体验，包含搜索高亮、筛选联动、防抖搜索 |

| 原理和工作流程 | 前端筛选条件变化 → emit `filter` 事件 → 父组件调用 API → BFF 层转发到 ES → 返回结果 + 高亮片段 → 前端渲染商品列表。ES 搜索权重：name^3 > category_name^2 > description^1 |
| 缺点 | 筛选条件过多时 URL 参数冗长；ES 集群维护成本高 |

### 购物车管理

| 维度 | 内容 |
|------|------|
| 是什么 | 购物车全流程管理：添加商品、修改数量、删除、选中/取消选中、全选、总价计算，以及未登录 localStorage 和登录后服务端数据的合并 |
| 能做什么 | 提供流畅的购物车操作体验，支持跨设备同步（登录后） |
| 怎么用 | `useCartStore` 提供 `addItem`、`updateQuantity`、`removeItem`、`toggleItem`、`toggleAll`、`mergeCart` 等方法；`selectedItems`、`totalAmount`、`isAllSelected` 等计算属性 |
| 原理和工作流程 | 未登录：localStorage 存储 `guest_cart`。登录后：调用 `mergeCart()` 将本地数据同步到服务端 MySQL，相同 SKU 取最大数量。数量变更采用乐观更新，先更新本地 UI 再异步同步后端，失败时回滚 |
| 缺点 | 合并冲突需要明确规则；乐观更新失败需要提示用户 |

### 订单创建与支付

| 维度 | 内容 |
|------|------|
| 是什么 | 从购物车结算到支付完成的完整订单流程：创建订单（Redis 预减库存 + 数据库扣减）→ 跳转支付（支付宝/微信）→ 支付回调（验签 + 幂等 + 更新状态） |
| 能做什么 | 实现从下单到支付完成的全链路闭环 |
| 怎么用 | 前端：`/checkout` 确认订单页面 → 提交订单 → 跳转支付页面。后端：`createOrderWithStock()` 创建订单 + 扣库存 → `handleAlipayCallback()` 处理支付回调 |
| 原理和工作流程 | 下单：Redis Lua 脚本预减库存 → Prisma 事务创建订单 + 订单项 + 真实扣库存 → 清除购物车已选商品。支付：前端调用支付接口获取支付参数 → 跳转支付宝/微信 → 支付完成后异步回调 → BFF 验签 → 幂等检查 → 更新订单状态 |
| 缺点 | 支付回调可能丢失，需要定时任务主动查询；超时未支付订单需要自动取消 |

### 订单状态管理

| 维度 | 内容 |
|------|------|
| 是什么 | 订单全生命周期状态管理：待支付 → 已支付 → 已发货 → 已完成，以及取消和退款流程 |
| 能做什么 | 管理订单从创建到完结的完整状态流转，支持用户操作（支付、取消、确认收货、申请退款）和商家操作（发货、退款审核） |
| 怎么用 | 前端根据订单状态展示不同操作按钮（待支付显示"去支付"和"取消"，已发货显示"确认收货"）；后端 `transitionOrder(orderId, action)` 控制状态流转 |
| 原理和工作流程 | 状态机定义合法转移路径，乐观锁保证并发安全。每次状态变更都在事务中完成，并触发副作用（支付成功扣库存、取消恢复库存、确认收货更新销量） |
| 缺点 | 状态机扩展需要修改转移规则表；复杂状态流转需要仔细测试 |

### 库存管理

| 维度 | 内容 |
|------|------|
| 是什么 | 商品 SKU 级别的库存管理，包含商品上架时同步库存到 Redis、下单时 Redis 预减库存、支付成功后数据库真实扣减、取消订单时恢复库存 |
| 能做什么 | 确保高并发场景下库存数据准确，防止超卖 |
| 怎么用 | `syncStockToRedis(skuId, stock)` 上架时同步；`deductStockInRedis(skuId, quantity)` 下单时预减；`deductStockInDB(skuId, quantity)` 支付后真实扣减；`restoreStockInRedis(skuId, quantity)` 取消时恢复 |
| 原理和工作流程 | Redis 作为高性能库存计数器，利用 Lua 脚本保证原子性。数据库作为最终一致性保证，通过乐观锁防止并发修改。定时任务对账 Redis 和数据库库存差异 |
| 缺点 | 极端情况下 Redis 和数据库库存可能不一致，需要定时对账 |

## 四、常见面试题

### 电商项目中如何防止超卖

| 维度 | 内容 |
|------|------|
| 是什么 | 考察多层防护的库存防超卖方案：Redis 预减库存（Lua 原子操作）+ 数据库乐观锁 + 分布式锁 + 消息队列异步下单 |
| 能做什么 | 验证候选人是否掌握高并发库存扣减的核心技术方案 |
| 怎么用 | Redis Lua 脚本 `GET + DECRBY` 原子操作；数据库 `UPDATE ... WHERE stock >= quantity` 乐观锁；`SET key value NX EX` 分布式锁 |
| 原理和工作流程 | 下单时先在 Redis 用 Lua 脚本原子扣减库存，扣减成功才进入下单流程；数据库层面用乐观锁保证最终一致性；消息队列削峰填谷避免数据库压力过大 |
| 缺点 | Redis 预减后如果订单超时取消，需要恢复库存 |

### 如何设计一个高并发秒杀系统

| 维度 | 内容 |
|------|------|
| 是什么 | 考察从客户端到数据层的全链路秒杀系统设计：前端防重复 + 网关限流 + Redis 预减库存 + 消息队列异步下单 + 数据库读写分离 |
| 能做什么 | 验证候选人全链路高并发系统设计能力 |
| 怎么用 | 前端：按钮置灰 + 倒计时；网关：Nginx `limit_req` + 验证码；BFF：Redis 预减库存；消息队列：削峰异步下单；数据库：读写分离 + 分库分表 |
| 原理和工作流程 | 层层过滤：前端和网关过滤掉 99% 无效请求，BFF 层 Redis 原子扣减库存，消息队列异步处理下单，数据库只承受最终成功的订单写入 |
| 缺点 | 系统复杂度高，需要仔细设计降级方案 |

### 购物车在未登录和登录状态下如何处理

| 维度 | 内容 |
|------|------|
| 是什么 | 考察购物车跨登录状态的管理方案：未登录用 localStorage，登录后合并到服务端 MySQL/Redis |
| 能做什么 | 验证候选人处理跨状态数据同步和合并冲突的能力 |
| 怎么用 | 未登录：`localStorage.setItem('guest_cart', JSON.stringify(items))`；登录后：`mergeCart()` 将本地数据同步到服务端，相同 SKU 取最大数量 |
| 原理和工作流程 | 用户操作购物车时，未登录状态写入 localStorage；登录后调用合并接口，服务端按规则合并（相同 SKU 取最大数量），清除本地数据 |
| 缺点 | 合并规则需要明确（取大还是累加）；localStorage 有容量限制（5MB） |

### 订单状态机如何设计

| 维度 | 内容 |
|------|------|
| 是什么 | 考察基于状态转移表（transitions）的订单状态机设计：7 种状态 + 合法转移规则 + 乐观锁 + 副作用处理 |
| 能做什么 | 验证候选人设计复杂状态流转系统的能力 |
| 怎么用 | `transitions` 映射表定义合法状态转移；`transitionOrder(orderId, action)` 执行状态转移；`handleTransitionSideEffect` 处理副作用 |
| 原理和工作流程 | 状态机通过转移规则表控制合法流转，使用乐观锁防止并发修改。每次状态变更在事务中完成，并触发副作用（扣库存、发通知、写日志） |
| 缺点 | 状态机扩展需要修改转移规则表；副作用处理需要确保幂等 |

### BFF 层的作用和为什么需要

| 维度 | 内容 |
|------|------|
| 是什么 | BFF（Backend For Frontend）是位于前端和后端微服务之间的中间层，负责接口聚合、数据裁剪、鉴权统一和缓存加速 |
| 能做什么 | 减少前端请求次数，降低前后端耦合，统一鉴权和缓存策略 |
| 怎么用 | Express/Koa 路由定义 API 接口，中间件处理鉴权和缓存，Service 层封装业务逻辑 |
| 原理和工作流程 | 前端请求 BFF 接口 → BFF 聚合多个后端服务数据 → 按前端需要裁剪格式 → 返回统一响应。鉴权中间件在 BFF 层统一处理 JWT 校验 |
| 缺点 | 增加系统复杂度；需要额外维护 BFF 层代码 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 电商全栈开发中的常见错误：库存超卖、支付回调幂等、订单状态并发修改、购物车未合并、大事务长连接、缓存不一致、图片未做缩略图、SQL 注入、XSS 攻击、接口未限流、BFF 超时未控制、订单超时未取消 |
| 能做什么 | 帮助开发者提前识别并避免电商全栈开发中的典型陷阱 |
| 怎么用 | 对照排查：库存扣减用 Redis Lua 脚本 + 数据库乐观锁；支付回调用 trade_no 去重 + 分布式锁；订单状态用乐观锁 WHERE status = oldStatus；购物车登录后先合并再清除本地数据 |
| 原理和工作流程 | 常见错误根源：库存扣减非原子操作（用 Lua 脚本解决）、支付回调重复处理（用幂等 key 去重）、订单状态并发修改（用乐观锁）、购物车数据丢失（登录先合并）、大事务内调外部 API（拆分为小事务）、缓存删除失败（用 binlog 异步更新）、原图加载（用多尺寸缩略图）、SQL 拼接（用参数化查询）、富文本 XSS（用 DOMPurify 过滤）、接口无限制（用 Nginx 限流 + BFF 令牌桶）、BFF 无超时（设置 5s 超时 + 降级数据）、超时订单未取消（用定时任务扫描） |
| 缺点 | 这些坑需要在实践中积累经验才能识别；部分问题（如缓存不一致）需要监控告警发现 |
