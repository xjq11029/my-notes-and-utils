## 一、核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | 高频项目类型实战是四类"技术设施型"项目的架构设计与讲法总结：组件库 / 设计系统、低代码平台、数据可视化大屏、IM 即时通讯前端。它们本身不是业务系统，而是被业务系统使用的技术设施 |
| 能做什么 | 掌握四类项目的技术选型理由、架构分层、关键难点方案，并能用 STAR 结构在面试中讲清项目背景、目标、动作与量化结果 |
| 怎么用 | 先理解四类项目的共性技术主线（用配置描述意图、用渲染器实现渲染），再按「项目背景与技术选型 → 核心架构设计 → 关键技术难点与解决方案 → 面试怎么讲」四段逐类深入 |
| 原理和工作流程 | 四类项目共享同一条主线：组件库用 Props / Slots 描述意图，低代码用 JSON Schema 描述意图，大屏用 ECharts Option 描述意图，IM 用消息协议描述意图——都是"数据驱动视图"在不同抽象层级上的应用 |
| 缺点 | 四类项目对抽象能力与工程化能力要求高，尤其低代码平台难度最高（★★★★★）；若无真实项目经验，只靠背诵方案容易在追问中露馅 |

## 二、底层原理

### 组件库：Monorepo 与 pnpm workspace

| 维度 | 内容 |
|------|------|
| 是什么 | 组件库采用 Monorepo 组织"一仓库、多包、相互依赖"的结构，用 pnpm workspace 管理包间依赖 |
| 能做什么 | 让 `components` / `hooks` / `icons` / `theme` 等包相互引用；开发时改源码立即生效，发布时自动替换为真实版本号 |
| 怎么用 | `pnpm-workspace.yaml` 声明 `packages: ['packages/*']`；包间依赖写 `"@my/hooks": "workspace:*"`；用 Turborepo 的 `dependsOn: ["^build"]` 编排构建顺序 |
| 原理和工作流程 | `workspace:*` 协议在开发时把依赖软链到本地源码（无需 `npm link`），发布时被 pnpm 替换为真实版本号。Turborepo 通过任务依赖图保证"先构建上游依赖包，再构建当前包"，并复用命中缓存的产物 |
| 缺点 | Monorepo 增加了仓库复杂度与 CI 配置成本；包数量多时版本管理需依赖 Changesets 等工具，否则容易出现版本错配 |

### 组件库：构建产物与 Tree Shaking

| 维度 | 内容 |
|------|------|
| 是什么 | 组件库的构建产物决定使用方的打包体积，核心是让未使用的组件能被 Tree Shaking 消除 |
| 能做什么 | 让使用方只打包用到的组件，而不是引入整个组件库；同时保证类型提示与老工具链兼容 |
| 怎么用 | `package.json` 中声明 `module` / `exports` / `sideEffects`；Vite 库模式配置 `formats: ['es', 'cjs']`、`external: ['vue']`、`preserveModules: true` |
| 原理和工作流程 | Tree Shaking 生效需要三个前提：① 产物是 ESM 格式（`import` / `export` 是静态语法，可静态分析；CJS 的 `require` 是运行时行为无法消除）；② 包声明 `"sideEffects": false`；③ 使用方也走 ESM 且开启生产模式。`preserveModules` 保留模块结构以细化摇树粒度，`external` 防止 Vue 被打进产物 |
| 缺点 | `"sideEffects": false` 会把 CSS 一起摇掉，含样式的包必须写成 `["**/*.css"]`；不 external `vue` 会导致使用方加载两份 Vue，`provide/inject` 失效、体积翻倍 |

### 组件库：按需引入与版本发布

| 维度 | 内容 |
|------|------|
| 是什么 | 按需引入让使用方只加载用到的组件；语义化版本与 Changesets 管理多包发布流程 |
| 能做什么 | 三种按需引入方式：手动按路径引入、编译期自动转换、原生 ESM 摇树；版本号按 MAJOR / MINOR / PATCH 规则递增，支持预发布 |
| 怎么用 | 手动方式 `import Button from '@my/ui/button'`；自动方式配置 `unplugin-vue-components` + `ElementPlusResolver`；发布流程 `pnpm changeset` → `pnpm changeset version` → `pnpm changeset publish` |
| 原理和工作流程 | 编译期自动转换由构建插件把 `import { Button }` 重写为按路径导入；语义化版本中 MAJOR 对应不兼容变更、MINOR 对应向下兼容的新功能、PATCH 对应向下兼容的缺陷修复；Changesets 在 PR 阶段收集变更描述，合并后统一升级版本并生成 CHANGELOG |
| 缺点 | 自动转换依赖构建插件（插件升级可能带来兼容问题）；antd 5.x 已支持原生 ESM 摇树，无需 `babel-plugin-import`，方案选择需按库的版本区分 |

### 低代码：Schema 驱动与渲染器

| 维度 | 内容 |
|------|------|
| 是什么 | Schema 驱动是"页面即数据"的思想：用一棵 JSON 树（`componentName` + `props` + `children`）描述页面，渲染器把它映射为组件树 |
| 能做什么 | 让页面结构可序列化、可服务端下发、可持久化保存、可编译出码；是低代码平台的核心机制 |
| 怎么用 | 定义 `SchemaNode` 接口；渲染器通过 `materialMap[componentName]` 查找组件并递归渲染子节点；未知物料渲染占位提示而非抛错 |
| 原理和工作流程 | 渲染器有三个职责：物料查找（`componentName` → 组件实现）、递归渲染（深度优先遍历 Schema 树）、上下文注入（数据源与事件回调通过 Context 下传）。Schema 与虚拟 DOM 结构同构，但虚拟 DOM 是运行时临时产物、每次渲染重建，Schema 是持久化数据、可跨进程传输 |
| 缺点 | 递归渲染深度过大时有性能风险；Schema 表达能力有限，复杂交互需要额外的表达式求值与事件引擎支撑 |

### 低代码：物料协议与 Setter

| 维度 | 内容 |
|------|------|
| 是什么 | 物料 = 组件实现 + 元信息，元信息即物料协议（`componentName` / `title` / `category` / `schema` / `configure` / `snippets`）；Setter 是"属性 → 编辑器组件"的映射机制 |
| 能做什么 | 让组件实现与元信息分离，元信息可序列化、可服务端下发、可跨平台共享；属性配置面板通过遍历协议自动渲染 |
| 怎么用 | 维护 `materialMap`（组件实现）与 `materialProtocols`（元信息）两张表；用 `registerSetter(name, component)` 注册 Setter，面板遍历 `configure.props` 为每个属性找到对应 Setter |
| 原理和工作流程 | 面板渲染逻辑是"遍历协议声明 → 查 Setter 注册表 → 渲染编辑器"，并做兜底（找不到 Setter 时用 `FallbackSetter`）。关键收益是新增物料只需写组件 + 协议，**不需要修改面板代码** |
| 缺点 | 协议字段设计不当会导致扩展困难；Setter 之间的联动（某属性变化影响其他 Setter 选项）需要额外机制支撑 |

### 低代码：拖拽与撤销重做

| 维度 | 内容 |
|------|------|
| 是什么 | 拖拽实现有 HTML5 DnD 与 Pointer Events 两套方案；撤销重做有快照栈、命令模式、补丁三种方案 |
| 能做什么 | 拖拽实现物料从面板到画布的放置与落点计算；撤销重做支持用户回退任意操作 |
| 怎么用 | HTML5 DnD：`draggable` + `dragstart` / `dragover`（必须 `preventDefault`）/ `drop`；Pointer Events：`setPointerCapture` + `pointermove` / `pointerup`。命令模式：`execute` 时 `do()` 并入栈，`undo()` 执行逆操作 |
| 原理和工作流程 | 落点计算遍历容器节点的 `getBoundingClientRect()`，与子节点垂直中线比较得出插入 index，取面积最小的容器（层级最深）。命令模式的内存占用只与操作数量成正比，而快照栈与 Schema 大小成正比；`maxSize` 限制栈深，新操作清空重做栈 |
| 缺点 | HTML5 DnD 的 `dragImage` 样式难定制、`dragover` 坐标精度受限、移动端支持差；命令模式需为每种操作实现正确的逆操作，且一次拖拽涉及"删旧 + 插新"必须用复合命令合并，否则用户要按两次撤销 |

### 低代码：出码方案与适用边界

| 维度 | 内容 |
|------|------|
| 是什么 | 出码是把 Schema 编译为可独立运行源码的过程；同时需要明确低代码平台的适用边界 |
| 能做什么 | 出码支持模板字符串拼接与 AST 生成两种实现；平台边界界定哪些场景该用低代码、哪些不该用 |
| 怎么用 | AST 方式用 `@babel/types` 构造节点、`@babel/generator` 输出代码，再接 Prettier 格式化；边界判断标准是"复杂度来自字段数量还是交互逻辑" |
| 原理和工作流程 | 模板拼接在嵌套复杂时容易生成非法代码，AST 生成输出规范且可格式化。主流选择是运行时渲染而非出码——出码一旦导出，Schema 的后续修改无法同步到已导出代码，形成双份维护；出码更适合"平台下线时导出资产"或"作为二次开发起点" |
| 缺点 | 适合场景：中后台 CRUD 页面、营销落地页、内部工具、表单流程类应用；不适合场景：强交互（富文本 / 图形编辑器 / 地图）、动画要求高的 C 端页面、性能敏感的复杂列表 |

### 大屏：ECharts 集成与按需引入

| 维度 | 内容 |
|------|------|
| 是什么 | ECharts 是 Option 驱动的渲染管线：Option → 数据处理 → 布局计算 → 图元生成 → 渲染 → 交互层 |
| 能做什么 | 通过按需引入把体积从约 1MB 降到 300KB 以内；通过 `shallowRef` + `dispose()` 保证 Vue 集成下的性能与内存安全 |
| 怎么用 | 从 `echarts/core` 引入并用 `echarts.use([...])` 注册所需图表与组件；实例用 `shallowRef` 包裹；`onMounted` 中 `init` + `ResizeObserver`，`onBeforeUnmount` 中 `disconnect()` + `dispose()` |
| 原理和工作流程 | ECharts 按 series 生成图元并渲染到 Canvas 或 SVG。实例内部属性极多，若被 Vue 深度响应式代理会产生巨大的依赖收集开销导致掉帧，因此必须用 `shallowRef`；`dispose()` 释放 Canvas 与事件监听，`ResizeObserver` 比 `window.resize` 更精准 |
| 缺点 | 按需引入需手工维护注册清单，漏注册会导致图表不渲染；`dispose()` 与 `ResizeObserver` 清理容易被遗漏，造成内存泄漏 |

### 大屏：自适应适配与性能优化

| 维度 | 内容 |
|------|------|
| 是什么 | 大屏适配有 `transform: scale`、`rem` + 动态根字号、`vw/vh` 三种方案；性能优化围绕大数据量渲染与实时更新展开 |
| 能做什么 | 在 1080P / 2K / 4K 等不同分辨率下完整还原设计稿；十万级数据点图表流畅渲染；实时刷新不闪烁 |
| 怎么用 | `scale` 方案按 `min(宽/1920, 高/1080)` 算缩放比再算居中偏移；性能优化配置 `sampling: 'lttb'`、`large: true`、`showSymbol: false`、`animation: false`；实时曲线用 `chart.appendData()` |
| 原理和工作流程 | `scale` 是 contain 语义（内容完整可见）而非 cover（裁切）；`large` 是渲染路径优化（跳过逐点样式计算），`sampling` 是数据量优化（降采样），两者可叠加；`appendData` 只追加增量，不重建整个 series |
| 缺点 | `scale` 在非整数缩放下 `1px` 边框渲染成亚像素而模糊（改用 `box-shadow` 模拟）；`getBoundingClientRect()` 返回缩放后的值，坐标换算需除以 `scale`；`appendData` 只能追加不能修改删除，需滚动窗口时必须改用 `setOption` |

### 大屏：定时刷新与部署投屏

| 维度 | 内容 |
|------|------|
| 是什么 | 大屏的定时刷新机制与投屏部署要点，包括定时器清理、全屏模式、防止长时间运行卡死 |
| 能做什么 | 保证大屏 7×24 常亮、数据持续刷新、长时间运行不卡死 |
| 怎么用 | `setInterval` 中调 `setOption(option, { notMerge: false })` 合并更新；`onBeforeUnmount` 清理定时器；部署用 Chrome `--kiosk` + 锁定 100% 缩放 + 关闭休眠 + 凌晨低峰期定时 `location.reload()` |
| 原理和工作流程 | `notMerge: false` 表示合并更新，保留用户已设置的缩放等交互状态；定时器不清理会导致内存泄漏与后台持续请求；`--kiosk` 提供无地址栏的全屏体验；定时重载规避长时间运行的内存碎片 |
| 缺点 | 定时重载会造成短暂白屏（需选择低峰期）；不同投屏设备的 DPI 缩放可能影响字体渲染，需逐设备验证 |

### IM：WebSocket 连接管理与重连

| 维度 | 内容 |
|------|------|
| 是什么 | WebSocket 提供全双工通信但不提供可靠性保证，需要在其之上补齐心跳、重连与消息可靠性 |
| 能做什么 | 通过应用层心跳发现"假死连接"；通过指数退避 + 随机抖动实现稳定重连；通过待发队列补发断线期间的消息 |
| 怎么用 | `onopen` 中重置重试计数、启动心跳、补发队列；`onmessage` 中过滤 `pong`；`onclose` 中停止心跳并调度重连；`delay = min(1000 * 2 ** retryCount, 30000) + random(0, 1000)` |
| 原理和工作流程 | TCP 存在"假死"状态（拔网线、NAT 表项超时、代理静默断开），此时浏览器不触发 `onclose`，前端会误以为连接正常；WebSocket 协议层虽有 ping/pong 帧但浏览器 JS API 不暴露发送能力，因此需应用层心跳：定时发 `ping`，超时未收到 `pong` 就主动断开重连。`onerror` 之后必定触发 `onclose`，所以重连逻辑统一放 `onclose` |
| 缺点 | 心跳增加了一定的流量与耗电；指数退避在极端情况下会延迟恢复时间；重连期间的消息需入队，队列积压过多时需考虑降级或限流 |

### IM：消息可靠性与已读回执

| 维度 | 内容 |
|------|------|
| 是什么 | 消息可靠性由 ACK 确认、`msgId` 去重、`seq` 排序三者共同保证；已读回执通过会话级 `readSeq` 上报实现 |
| 能做什么 | 实现"不丢、不重、不乱序"的消息体验；正确计算会话未读数；支持离线消息增量同步 |
| 怎么用 | 发送时生成 `msgId` 并乐观更新，启动 5s ACK 超时定时器，超时重发最多 3 次，仍失败标记 `failed`；服务端回 ACK 带 `seq` 后状态转 `sent`；客户端按 `seq` 排序，未 ACK 的排最前；已读用 `socket.send({ type: 'read', conversationId, readSeq })` |
| 原理和工作流程 | 状态机 `sending → sent → failed` 驱动 UI 表现；去重在服务端按 `msgId` 幂等、在客户端按 `msgId` 只更新状态不重复插入；排序依赖服务端分配的单调递增 `seq`（客户端时钟不可信）；未读数 = 会话最新 `seq` − 我读到的 `seq`。离线同步靠本地 `lastSyncSeq` 拉取增量 |
| 缺点 | 已读回执在群聊场景需维护每个成员的 `readSeq`，存储量大，通常只对"重要消息"（如 @ 我）开启；重试机制在极端弱网下会持续占用请求；IndexedDB 存储需要处理版本迁移 |

### IM：富文本渲染、虚拟滚动与降级

| 维度 | 内容 |
|------|------|
| 是什么 | 富文本消息的 Markdown 渲染与 XSS 防护；大消息列表的虚拟滚动；连接状态与降级策略 |
| 能做什么 | 安全渲染 Markdown / 表情 / 链接消息；万条消息下保持滚动流畅；弱网与断网场景下仍可用 |
| 怎么用 | 渲染链路 `marked.parse()` → `DOMPurify.sanitize()`，配 `ALLOWED_TAGS` / `ALLOWED_URI_REGEXP` 白名单；虚拟滚动用动态高度方案 + `scrollHeight` 差值补偿 `scrollTop`；降级按 WS → SSE → 长轮询 → 本地队列 |
| 原理和工作流程 | XSS 防护是纵深防御：消毒 + 协议白名单（只允许 `http/https/mailto`）+ 外链 `rel="noopener noreferrer"` + 图片走服务端代理防 IP 泄露。虚拟滚动的两个关键细节：向上加载历史时补偿 `scrollTop` 保持视觉位置；新消息只在"距底部 < 80px"时自动滚动，否则显示浮标不打断阅读 |
| 缺点 | DOMPurify 需要维护白名单，过严会丢失合法格式、过松会有风险；虚拟滚动对动态行高支持需要测量缓存，实现复杂度高；降级方案牺牲实时性 |

## 三、实战应用

### 组件库 / 设计系统项目

| 维度 | 内容 |
|------|------|
| 是什么 | 从 0 到 1 搭建组件库：pnpm workspace 组织 Monorepo，设计令牌作为地基，API 规范统一，质量体系覆盖单测与视觉回归 |
| 能做什么 | 统一多个系统的视觉规范；让新项目接入成本从 5 天降到 1 天；让交互规范调整从改 8 个仓库变成改 1 个文件 |
| 怎么用 | 技术栈 pnpm workspace + Vite 库模式 + Turborepo + Changesets + VitePress（文档）+ Storybook（调试）+ Vitest + Chromatic（视觉回归）；目录拆为 `theme` / `hooks` / `icons` / `components` / `docs` |
| 原理和工作流程 | 设计令牌是单一数据源，组件只引用令牌不写死颜色值，令牌通过 CSS 变量支持主题切换。API 规范统一 Props 命名（`size` / `type` / `disabled` / `loading`），支持受控与非受控双模式，`inheritAttrs: false` + `$attrs` 透传原生属性，内置 `aria-*` 无障碍属性 |
| 缺点 | 组件库需长期维护，破坏性变更要按 SemVer 升 MAJOR 并提供迁移指南；视觉回归需要固定字体、时区、DPR 等测试环境因素，否则误报率高 |

### 低代码平台

| 维度 | 内容 |
|------|------|
| 是什么 | 面向运营的低代码平台，把"页面开发"变成"页面配置"，架构分为编辑器层、引擎层、运行时层、产物层四层 |
| 能做什么 | 让运营自助完成 80% 常规页面；把常规页面交付周期从 2-3 天降到 2 小时；沉淀业务物料库 |
| 怎么用 | 技术栈 React 18 + Zustand + Immer（状态）+ Pointer Events（拖拽）+ 命令模式（撤销）+ `@babel/generator`（出码）+ iframe 沙箱（预览）；SchemaStore 作为单一数据源，所有操作通过命令对象修改 |
| 原理和工作流程 | 编辑器层由物料面板、画布、属性配置面板、大纲树组成；引擎层包含 SchemaStore、CommandManager、DragEngine、MaterialRegistry；运行时层由 Renderer、数据源引擎、事件引擎组成；产物层负责预览、出码、发布。拖拽落点靠 `getBoundingClientRect()` 与子节点中线比较；属性面板靠 Setter 注册表自动渲染 |
| 缺点 | 平台有明确边界：只支持"字段多但交互简单"的场景，富文本编辑、图形编辑等强交互需求不纳入；节点超 500 后需要节点级订阅与拖拽期间的 `transform` 优化，否则明显卡顿 |

### 数据可视化大屏

| 维度 | 内容 |
|------|------|
| 是什么 | 面向指挥中心的 4K 大屏项目，需要多分辨率还原、十万级数据点流畅渲染、7×24 常亮稳定 |
| 能做什么 | 在 1080P / 2K / 4K 下完整还原设计稿；十万点折线图首帧从 3.2 秒降到 400 毫秒内；连续运行 30 天无重启 |
| 怎么用 | 技术栈 Vue 3 + ECharts 5（按需引入）+ `transform: scale` 适配 + WebSocket 推送 + 轮询兜底 + Chrome `--kiosk` 部署；用 `useChart` 统一封装 init / resize / dispose |
| 原理和工作流程 | 适配按 `min(宽/1920, 高/1080)` 算缩放比并居中（contain 语义）；性能优化分渲染层面（`sampling` / `large` / `showSymbol: false` / `animation: false`）与更新层面（`appendData` 追加、`notMerge: false` 合并）；稳定性靠 `dispose()` + 清理 `ResizeObserver` 与定时器 + WS 断线降级轮询 + 凌晨定时重载 |
| 缺点 | `scale` 在非整数缩放下细边框模糊；`appendData` 不能修改删除已有数据；`dispose` 遗漏会导致内存持续增长 |

### IM 即时通讯前端

| 维度 | 内容 |
|------|------|
| 是什么 | SaaS 客服系统的 IM 模块，要求消息不丢、不重、不乱序，弱网下可用 |
| 能做什么 | 消息送达率从 99.2% 提升到 99.98%；乱序问题清零；万条消息滚动帧率从 20 FPS 提升到 55 FPS 以上；弱网发送成功率从 87% 提升到 99.5% |

## 四、常见面试题

### 组件库如何做到按需引入？Tree Shaking 生效的前提是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 考察按需引入的三种实现方式，以及 Tree Shaking 生效的三个前提条件 |
| 能做什么 | 验证候选人是否理解 ESM 静态分析与打包器的摇树机制，而非只知道"配置插件就行" |
| 怎么用 | 手动按路径引入 `import Button from '@my/ui/button'`；编译期自动转换配 `unplugin-vue-components`；原生 ESM 摇树（antd 5.x）；前提是 ESM 产物 + `sideEffects: false` + 生产模式 |
| 原理和工作流程 | `import` / `export` 是静态语法，打包器可在编译期做静态分析并消除未引用模块；CJS 的 `require` 是运行时行为无法静态消除。`sideEffects` 声明模块是否有副作用，含 CSS 的包必须写 `["**/*.css"]`，否则样式会被一起摇掉。`preserveModules` 保留模块结构以细化摇树粒度 |
| 缺点 | `sideEffects` 配置错误会导致样式丢失或摇树失效；`preserveModules` 会增加产物文件数量 |

### 低代码平台的 Schema 驱动渲染原理是什么？如何设计渲染器

| 维度 | 内容 |
|------|------|
| 是什么 | 考察"页面即数据"的核心思想与渲染器的三个职责 |
| 能做什么 | 验证候选人是否理解 Schema 与虚拟 DOM 的异同，以及渲染器的容错与性能设计 |
| 怎么用 | 定义 `SchemaNode`（`componentName` / `props` / `children`）；渲染器用 `materialMap[componentName]` 查组件并递归渲染；未知物料渲染占位提示 |
| 原理和工作流程 | 渲染器职责为物料查找、递归渲染、上下文注入。设计要点包括未知物料容错（避免白屏）、容器与叶子区分（`isContainer`）、条件与循环渲染、节点级订阅（避免一个属性变化触发全树重渲染）。Schema 与虚拟 DOM 结构同构但本质不同：前者是可序列化的持久化数据，可服务端下发与出码；后者是运行时临时产物 |
| 缺点 | 递归渲染深度大时有性能风险；表达式求值与事件引擎需要额外实现 |

### 低代码的撤销重做怎么实现？命令模式和快照有什么区别

| 维度 | 内容 |
|------|------|
| 是什么 | 考察撤销重做的三种方案（快照栈、命令模式、补丁）及其取舍 |
| 能做什么 | 验证候选人是否理解内存占用与实现复杂度的权衡，以及复合命令的必要性 |
| 怎么用 | 命令模式：`execute` 时 `do()` 并入栈、清空重做栈、超 `maxSize` 时 `shift()`；`undo()` 执行逆操作并把命令推入重做栈 |
| 原理和工作流程 | 快照栈每次操作深拷贝完整 Schema，内存占用与 Schema 大小成正比；命令模式只记录操作本身，内存与操作数量成正比，但需为每种操作实现正确的逆操作。三个工程要点：`undo()` 幂等、复合命令合并一次拖拽的"删旧 + 插新"、栈深度限制。新操作必须清空重做栈，否则重做会与当前状态冲突 |
| 缺点 | 命令模式在操作类型多时实现成本高；补丁方案依赖 Immer 或 JSON Patch 等库 |

### 大屏自适应适配方案怎么选？transform: scale 有什么坑

| 维度 | 内容 |
|------|------|
| 是什么 | 考察 `transform: scale` / `rem` / `vw-vh` 三种适配方案的适用场景与 `scale` 的两个典型问题 |
| 能做什么 | 验证候选人是否能根据"是否需 1:1 还原设计稿"做出正确的方案选择 |
| 怎么用 | 定尺寸投屏用 `scale`（按 `min(宽/1920, 高/1080)` 缩放 + 居中）；需流式重排用 `rem` + PostCSS 转换；简单响应式用 `vw/vh` |
| 原理和工作流程 | `min` 是 contain 语义（内容完整可见），`max` 是 cover 语义（会裁切），大屏要求信息完整所以用 `min`。两个坑：① 非整数缩放下 `1px` 边框渲染成亚像素而模糊或缺失，改用 `box-shadow: 0 0 0 1px color` 模拟；② `getBoundingClientRect()` 返回缩放后的尺寸，坐标换算需除以 `scale`，ECharts 场景可直接用 `convertFromPixel` |
| 缺点 | `rem` 方案下 Canvas 内容（图表）不跟随缩放；`vw/vh` 在极端宽高比下布局变形 |

### ECharts 大数据量渲染有哪些优化手段

| 维度 | 内容 |
|------|------|
| 是什么 | 考察 ECharts 大数据量优化的多个层级：数据量优化、渲染路径优化、更新优化 |
| 能做什么 | 让十万级数据点的图表首帧渲染从数秒降到数百毫秒，并保持交互流畅 |
| 怎么用 | `showSymbol: false` 关闭数据点标记；`large: true` + `largeThreshold` 走批量渲染；`sampling: 'lttb'` 降采样；`progressive` 分帧渲染；`appendData` 增量追加；`dataZoom` + `weakFilter` 只渲染可视区域；`animation: false` 关动画 |
| 原理和工作流程 | `large` 是渲染路径优化（跳过逐点样式计算），`sampling` 是数据量优化（保留趋势特征的降采样），两者可叠加。`appendData` 只追加增量不重建 series。ECharts 实例必须用 `shallowRef` 包裹，否则深度响应式代理超大对象会造成巨大依赖收集开销而掉帧 |
| 缺点 | `appendData` 不能修改或删除已有数据，需滚动窗口时必须改用 `setOption`；`sampling` 会损失部分细节，不适合需要精确数值的场景 |

### WebSocket 为什么要心跳？重连策略怎么设计

| 维度 | 内容 |
|------|------|
| 是什么 | 考察 TCP 假死问题、应用层心跳的必要性，以及重连策略的五个设计点 |
| 能做什么 | 让前端能发现"物理断开但未触发 onclose"的连接，并稳定恢复 |
| 怎么用 | 定时（30s）发 `ping`，超时未收 `pong` 主动 `close()` 重连；重连用 `min(1000 * 2 ** retryCount, 30000) + random(0, 1000)`；`onopen` 中重置计数并补发队列 |
| 原理和工作流程 | TCP 假死（拔网线、NAT 表项超时、代理静默断开）不触发 `onclose`，前端会误以为连接正常；WebSocket 协议层虽有 ping/pong 帧但浏览器 JS API 不暴露发送能力，所以需要应用层心跳。重连的五个设计点：指数退避、封顶 30s、随机抖动防惊群、连接成功重置计数、`offline` 时停止重连。`onerror` 后必定触发 `onclose`，重连逻辑统一放 `onclose` |
| 缺点 | 心跳带来额外流量与耗电；退避封顶过大时恢复慢，过小时易造成服务端压力 |

### IM 消息如何保证不丢、不重、不乱序

| 维度 | 内容 |
|------|------|
| 是什么 | 考察消息可靠性的三件套：ACK 确认、`msgId` 去重、`seq` 排序 |
| 能做什么 | 实现"不丢、不重、不乱序"的消息体验，并在弱网与断网下保持可用 |
| 怎么用 | 发送时生成唯一 `msgId` 并乐观更新 UI，启动 5s ACK 超时定时器，超时重发最多 3 次，仍失败标记 `failed` 提供手动重发；服务端回 ACK 带 `seq` 后状态转 `sent`；客户端按 `seq` 排序，未 ACK 的排最前 |
| 原理和工作流程 | 不丢靠 ACK + 超时重发 + 断线待发队列；不重靠服务端按 `msgId` 幂等 + 客户端按 `msgId` 只更新状态不重复插入；不乱序靠服务端分配的会话内单调递增 `seq`（客户端时钟不可信，不能用 `Date.now()` 排序） |
| 缺点 | 重试机制在极端弱网下会持续占用请求；待发队列积压过多时需要限流或降级 |

### IM 大消息列表的虚拟滚动有什么特殊难点

| 维度 | 内容 |
|------|------|
| 是什么 | 考察 IM 虚拟滚动区别于普通列表的四个特殊需求 |
| 能做什么 | 在万条消息下保持滚动流畅，同时不破坏用户的阅读位置与习惯 |
| 怎么用 | 动态行高渲染后测量缓存；向上加载历史时记录插入前后 `scrollHeight` 差值补偿 `scrollTop`；新消息只在"距底部 < 80px"时自动滚动，否则显示"有新消息"浮标；图片消息用宽高比容器预留占位高度 |
| 原理和工作流程 | 普通虚拟列表假设固定行高，IM 消息长度不一必须动态测量。向上加载时顶部插入数据会改变 `scrollHeight` 导致视觉跳变，必须补偿。新消息无条件滚到底部会打断用户看历史，需要判断当前位置。消息量大时用 IndexedDB 而非 localStorage（后者 5MB 上限且同步读写阻塞主线程） |
| 缺点 | 动态测量在快速滚动时可能出现高度估算误差导致跳动；占位高度与实际高度不符时会累积偏差 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 四类项目开发中的典型陷阱：组件库的 `sideEffects` 配置与 `external` 遗漏、低代码的撤销粒度与拖拽落点、大屏的 `dispose` 遗漏与定时器泄漏、IM 的假死连接与消息去重 |
| 能做什么 | 帮助开发者提前识别并避免四类项目的典型陷阱，减少线上问题 |
| 怎么用 | 对照排查：`sideEffects` 写成 `["**/*.css"]`；`rollupOptions.external` 排除 `vue`；拖拽用复合命令合并操作；落点遍历子节点 `getBoundingClientRect()` 与中线比较；图表 `onBeforeUnmount` 中 `dispose()`；WebSocket 实现应用层心跳；消息用 `msgId` 去重、`seq` 排序；已读回执按会话上报 `readSeq` |
| 原理和工作流程 | 常见错误根源：`sideEffects: false` 会把 CSS 一起摇掉导致样式丢失；不 external `vue` 会让使用方加载两份 Vue 使 `provide/inject` 失效；低代码拖拽被拆成两条命令导致撤销粒度错误；ECharts 实例未 `dispose` 与 `ResizeObserver` 未断开导致内存持续增长；`setInterval` 未清理导致卸载后仍请求接口；WebSocket 只依赖 `onclose` 判断断线会漏掉 TCP 假死；用本地时间排序会因客户端时钟不可信而错乱；消息内容直接 `v-html` 会导致 XSS；虚拟列表向上加载不补偿 `scrollTop` 会跳变；新消息强制滚到底部会打断阅读 |
| 缺点 | 这些坑需要实践积累才能识别；内存泄漏与连接假死类问题需要监控工具才能发现；部分问题（如视觉回归误报）需要长期调优测试环境 |
