## 一、核心概念

### 1.1 服务端状态 vs 客户端状态

| 维度 | 内容 |
|------|------|
| 是什么 | 客户端状态是本端产生、本端消费的同步状态（表单输入、弹窗开关、主题）；服务端状态是远端数据库的一份本地缓存，异步获取且随时可能过期（stale）。 |
| 能做什么 | 明确状态归属，避免用 `useState` / Redux 硬扛缓存问题，也避免用数据请求层存纯 UI 状态；为选型提供判断依据。 |
| 怎么用 | 客户端状态用 `useState` / Zustand / Redux；服务端状态用 TanStack Query / SWR / RTK Query。 |
| 原理和工作流程 | 服务端状态天然需要「缓存 + 失效 + 重新验证 + 去重 + 重试 + 竞态处理」六件事；把它塞进 Redux / Zustand 等于自己手写一套缓存系统，因此应交给专门的数据请求层。 |
| 缺点 | 两类状态边界在实践中容易模糊（如「未提交的筛选条件」属于客户端状态，提交后的结果列表属于服务端状态），需要团队约定；引入数据请求层会增加一个依赖与一层心智模型。 |

### 1.2 手写 `useEffect` + `fetch` 的六大问题

| 维度 | 内容 |
|------|------|
| 是什么 | 指直接在组件里用 `useEffect` + `fetch` + `useState` 完成取数时必然踩到的六个问题：竞态条件、重复请求、无缓存、无重试、loading / error 手写、瀑布式请求。 |
| 能做什么 | 作为「为什么需要数据请求层」的论证依据，也是面试中回答该问题的标准清单。 |
| 怎么用 | 对照六大问题逐项检查现有代码：是否手写了 `cancelled` 标记、是否多个组件重复请求同一接口、是否切页必白屏、是否失败即终态。 |
| 原理和工作流程 | 竞态：先发请求后返回会覆盖新数据；重复请求：组件之间不共享请求与结果；无缓存：组件卸载后数据即丢失；无重试：`fetch` reject 即进入错误态；样板代码：三态判断与 `cancelled` 标记要重复写；瀑布式：父请求完成才渲染子组件，子组件再发请求，串行等待（总耗时 = T1 + T2 + T3，而并行只需 max(T1, T2)）。 |
| 缺点 | 这段代码只覆盖「最简单的成功路径」，在真实项目中会随需求增长不断打补丁，最终演变成难以维护的临时缓存层。 |

### 1.3 数据请求层的职责

| 维度 | 内容 |
|------|------|
| 是什么 | 数据请求层是专门管理服务端状态的抽象层，提供请求去重、缓存复用、自动重新验证、统一状态机、重试退避、失效与更新、竞态取消、SSR 支持八项能力。 |
| 能做什么 | 让组件只关心「渲染什么」，不必关心「数据怎么来、何时过期、失败怎么办」；把缓存与失效策略收敛到一处统一维护。 |
| 怎么用 | 安装 `@tanstack/react-query`，用 `QueryClientProvider` 包裹应用，组件中调用 `useQuery` / `useMutation`。 |
| 原理和工作流程 | 以 `queryKey` 为索引维护缓存条目，相同键的并发请求共享同一个 Promise（去重）；组件挂载时先返回缓存再后台校验（stale-while-revalidate）；请求失败按 `retry` 配置指数退避；`queryFn` 接收 `signal` 用于取消；服务端 `prefetchQuery` + `dehydrate`，客户端 `hydrate` 复用。 |
| 缺点 | 引入了额外的概念与配置（`staleTime` / `gcTime` / `queryKey` 设计），配置不当会产生「数据不更新」或「请求过多」两类问题；调试时需要专门的 Devtools。 |

## 二、底层原理

### 2.1 TanStack Query 核心机制

| 维度 | 内容 |
|------|------|
| 是什么 | TanStack Query（原 React Query）是 React 生态事实标准的数据请求层，核心是 QueryClient + QueryCache + Query 三层模型，每个 `useQuery` 调用对应一个 Observer，组件即订阅者。 |
| 能做什么 | 以 `queryKey` 为索引管理缓存、请求去重、自动重新验证、重试、取消；提供 `useQuery`（读）与 `useMutation`（写）两套状态机。 |
| 怎么用 | `useQuery({ queryKey: ['users', { page: 1 }], queryFn: ({ signal }) => fetch(url, { signal }).then(r => r.json()), staleTime: 60_000, gcTime: 5 * 60_000, retry: 3 })`；写操作用 `useMutation({ mutationFn, onSuccess: () => queryClient.invalidateQueries({ queryKey }) })`。 |
| 原理和工作流程 | 调用 `useQuery` 后用 `queryKey` 序列化出 `queryHash`：缓存无该 Query 则创建并执行 `queryFn`；缓存有且新鲜则直接返回；缓存有但 stale 则先返回缓存渲染、同时后台重新请求。成功后写入缓存并通知所有订阅者，失败则按 `retry` 重试。所有观察者卸载后开始 `gcTime` 倒计时，超时回收缓存。 |
| 缺点 | v5 有破坏性变更（`cacheTime` → `gcTime`、移除 `useQuery` 回调、`isInitialLoading` → `isLoading`），升级需改代码；`queryFn` 返回 `undefined` 会被视为失败，需返回 `null`；`fetch` 不会因 HTTP 错误码抛错，必须手动检查 `res.ok`。 |

### 2.2 `queryKey` 设计原则

| 维度 | 内容 |
|------|------|
| 是什么 | `queryKey` 是查询的唯一身份标识，也是缓存索引与失效依据，是一个从泛到具体的数组。 |
| 能做什么 | 决定数据缓存到哪个条目、`invalidateQueries` 能失效哪些查询、预取能否命中；设计得当可避免「数据不更新」与「请求过多」。 |
| 怎么用 | 层级化：`['todos']` → `['todos', 'list', { status, page }]` → `['todos', 'detail', id]`；只放影响请求的参数；用 `queryOptions()` 集中管理键与配置，组件 / 预取 / 失效复用同一份定义。 |
| 原理和工作流程 | 前缀匹配：`invalidateQueries({ queryKey: ['todos'] })` 会失效所有以 `['todos']` 开头的查询；内部对 `queryKey` 做**确定性哈希**（对象键顺序不影响结果），但放入主题、语言等无关 UI 状态仍会导致无意义的失效与重新请求。 |
| 缺点 | 键设计错误不会报错，只会表现为「数据不更新」或「请求过多」，排查成本高；层级过深时字符串拼接容易出错，需要 `queryOptions` 约束。 |

### 2.3 `staleTime` 与 `gcTime` 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | `staleTime` 是数据被视为「新鲜」的时长（默认 `0`），`gcTime` 是查询没有任何观察者后缓存被回收前的保留时长（默认 5 分钟，v4 名为 `cacheTime`）。 |
| 能做什么 | `staleTime` 控制「要不要重新请求」；`gcTime` 控制「缓存还能不能读到」。二者配合可精细控制请求频率与内存占用。 |
| 怎么用 | 全局默认：`defaultOptions: { queries: { staleTime: 60_000, gcTime: 10 * 60_000 } }`；实时数据 `staleTime: 0`；几乎不变的数据 `staleTime: Infinity`。 |
| 原理和工作流程 | 时间线：挂载请求写入缓存 → `staleTime` 内其他组件直接读缓存不请求 → 超过 `staleTime` 变 stale → 新组件挂载时先渲染缓存、同时后台重新请求（stale-while-revalidate）→ 所有组件卸载后开始 `gcTime` 倒计时 → 超时缓存被回收。 |
| 缺点 | 常见误配是 `gcTime < staleTime`，导致数据刚变 stale 就被回收、缓存形同虚设；`staleTime` 不是「数据存活时间」，容易与 `gcTime` 混淆；默认 `staleTime: 0` 会让 SSR 预取在客户端水合后立即失效。 |

### 2.4 失效与乐观更新

| 维度 | 内容 |
|------|------|
| 是什么 | 失效（Invalidate）是把指定查询标记为 stale 并对活跃查询立即重新请求；乐观更新（Optimistic Update）是在请求返回前先把 UI 改成预期结果，失败时回滚。 |
| 能做什么 | 失效保证写操作后关联查询与服务端一致；乐观更新让点赞、收藏、发消息等操作获得零延迟反馈。 |
| 怎么用 | 失效：`invalidateQueries({ queryKey })` / 精确 `{ exact: true }` / 只标记 `{ refetchType: 'none' }` / 只请求 `refetchQueries()`。乐观更新：`onMutate`（`cancelQueries` + `getQueryData` 快照 + `setQueryData` 写入 + 返回 context）→ `onError`（用快照回滚）→ `onSettled`（`invalidateQueries` 最终同步）。 |
| 原理和工作流程 | `invalidateQueries` 把匹配前缀的查询标记为 stale，并对有观察者的查询立即重新请求；乐观更新的关键在于 `onMutate` 必须**先取消在途请求**，否则在途响应返回后会覆盖乐观数据；`onSettled` 无论成功失败都执行，是让服务端数据最终生效的兜底位置。 |
| 缺点 | 乐观更新需要手写「快照 + 回滚」，逻辑分散在三个回调中，容易漏写 `onSettled` 导致缓存与服务端长期不一致；React 19 的 `useOptimistic` 只能处理组件内乐观 UI，缓存一致性仍需数据层保证。 |

### 2.5 分页、无限滚动与预取

| 维度 | 内容 |
|------|------|
| 是什么 | 分页用 `useQuery` 把页码放进 `queryKey`；无限滚动用 `useInfiniteQuery` 配合 `getNextPageParam`；预取用 `prefetchQuery` / `ensureQueryData` 在用户真正需要前准备好数据。 |
| 能做什么 | 翻页时用 `placeholderData: keepPreviousData` 保留上一页数据避免白屏；无限滚动通过 `maxPages` 控制内存；预取在悬停、路由 loader 等时机提前加载，做到「点击即见」。 |
| 怎么用 | 分页：`useQuery({ queryKey: ['users', { page }], queryFn, placeholderData: keepPreviousData })`；无限：`useInfiniteQuery({ queryKey: ['feed'], queryFn: ({ pageParam }) => fetchFeed({ cursor: pageParam }), initialPageParam: 0, getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined, maxPages: 5 })`；预取：`queryClient.prefetchQuery(...)` / `queryClient.ensureQueryData(...)`。 |
| 原理和工作流程 | `useInfiniteQuery` 返回 `{ pages, pageParams }`，`getNextPageParam` 返回 `undefined` 表示没有下一页（`hasNextPage` 为 false）；触底加载通常用 `IntersectionObserver` 监听哨兵元素后调用 `fetchNextPage()`；`prefetchQuery` 只确保缓存里有数据、返回 `void`，`ensureQueryData` 会返回数据本身，适合在 loader 中直接使用。 |
| 缺点 | 无限滚动的所有页数据默认都留在缓存中，不设 `maxPages` 会导致内存持续增长；`keepPreviousData` 会让 `data` 与当前 `page` 短暂不一致，需用 `isPlaceholderData` 区分；预取过多会浪费带宽。 |

### 2.6 SWR 的定位与差异

| 维度 | 内容 |
|------|------|
| 是什么 | SWR 是 Vercel 出品的轻量数据请求库，名字来自 HTTP 缓存策略 stale-while-revalidate（先返回陈旧数据，同时后台重新验证），与 TanStack Query 共享同一心智模型。 |
| 能做什么 | 以极简 API 完成「取数 + 自动重新验证」：窗口聚焦、网络恢复、轮询自动触发；`dedupingInterval` 做请求去重；`useSWRMutation` 处理写操作。 |
| 怎么用 | `useSWR('/api/user', fetcher, { revalidateOnFocus: true, revalidateOnReconnect: true, dedupingInterval: 2000 })`，返回 `{ data, error, isLoading, isValidating, mutate }`。 |
| 原理和工作流程 | 以 key 为索引维护缓存，命中缓存时先返回旧数据并同时发起后台重新验证；`dedupingInterval` 内相同 key 的请求合并为一次；相比 TanStack Query 少了完整的状态机、`queryKey` 层级化与前缀失效、`queryOptions` 类型助手和官方 Devtools。 |
| 缺点 | 失效粒度较粗（字符串 key），复杂缓存失效与乐观更新需手动实现；无官方 Devtools，调试体验弱于 TanStack Query；中大型应用中缓存与变更管理能力不足。 |

## 三、实战应用

### 3.1 请求竞态的处理（`AbortController`）

| 维度 | 内容 |
|------|------|
| 是什么 | 请求竞态指「先发的请求后返回」，旧响应覆盖新数据；处理手段有 `AbortController`（真正取消请求）与 `ignore` / `cancelled` 标记（只丢弃结果）。 |
| 能做什么 | 保证快速切换 `userId`、连续输入搜索词时展示的始终是最新请求的结果；避免无意义的网络开销与服务端压力。 |
| 怎么用 | `const controller = new AbortController(); fetch(url, { signal: controller.signal }).catch((err) => { if (err.name !== 'AbortError') setError(err); }); return () => controller.abort();`；数据层中直接写成 `queryFn: ({ signal }) => fetch(url, { signal }).then(r => r.json())`。 |
| 原理和工作流程 | `useEffect` 的 cleanup 在依赖变化或组件卸载时执行 `controller.abort()`，中断在途请求并让 Promise 以 `AbortError` reject；TanStack Query 的 `queryFn` 会自动收到 `signal`，并在查询失效、组件卸载或 `cancelQueries` 被调用时 abort，无需手写 cleanup。 |
| 缺点 | 需要显式忽略 `AbortError`，否则取消会被当作业务错误弹提示；`ignore` 标记不节省网络开销；手写方案每个取数组件都要重复这套逻辑。 |

### 3.2 缓存失效策略

| 维度 | 内容 |
|------|------|
| 是什么 | 缓存失效策略回答「什么时候这份数据不再可信」，包含时间失效、主动失效、精确失效、直接写缓存、只标记不请求、全局重置等。 |
| 能做什么 | 写操作后让关联查询与服务端保持一致；退出登录 / 切换租户时彻底清空缓存；跨标签页同步失效事件。 |
| 怎么用 | 时间：`staleTime`；主动：`invalidateQueries({ queryKey })`；精确：`{ exact: true }`；只标记：`{ refetchType: 'none' }`；直写：`setQueryData(key, updater)`；重置：`queryClient.clear()`；跨标签页：`broadcastQueryClient({ queryClient, broadcastChannel })`。 |
| 原理和工作流程 | 写操作后三种更新方式代价从低到高：直接写缓存（省请求，要求服务端返回完整实体，列表需用 updater 局部替换）→ 精确失效（多一次请求但保证一致）→ 全局重置（用于登出 / 切换租户）。`invalidateQueries` 走前缀匹配并只对活跃查询立即重新请求。 |
| 缺点 | 直接写缓存要求前端完整复刻服务端的数据结构，服务端返回不完整时会写入脏数据；`broadcastQueryClient` 目前是实验性 API；失效策略分散在各 mutation 中，缺少集中约束容易遗漏。 |

### 3.3 SSR 场景下的数据预取（`dehydrate` / `hydrate`）

| 维度 | 内容 |
|------|------|
| 是什么 | SSR 预取指在服务端提前请求首屏数据、把缓存序列化后随 HTML 送到客户端，客户端直接命中缓存，避免「JS 加载 → 挂载 → 请求」的二次等待。 |
| 能做什么 | 首屏渲染即有数据，消除水合后的加载闪烁与二次请求；配合路由 loader 可做到「进入页面即见内容」。 |
| 怎么用 | 服务端：`const queryClient = new QueryClient(); await queryClient.prefetchQuery({ queryKey, queryFn, staleTime: 60_000 });` 再用 `<HydrationBoundary state={dehydrate(queryClient)}>` 包裹客户端组件；纯 CSR / Pages Router 场景用 `hydrate(queryClient, dehydratedState)`。 |
| 原理和工作流程 | `prefetchQuery` 在服务端把数据写入服务端缓存 → `dehydrate(queryClient)` 把缓存序列化成可传输的 `dehydratedState` → 客户端 `HydrationBoundary`（或 `hydrate`）灌入客户端 `QueryClient` → 客户端 `useQuery` 命中缓存，若数据仍新鲜则不重新请求。 |
| 缺点 | 三大坑：QueryClient 跨请求复用会导致用户数据泄露（必须每请求新建）；忘记设置 `staleTime` 会让水合后立即重新请求、预取白做；两端 `queryKey` 不一致则无法命中缓存。此外服务端预取会延长首字节时间，需权衡。 |

### 3.4 数据请求层与状态管理库的分工边界

| 维度 | 内容 |
|------|------|
| 是什么 | 明确「服务端状态归数据层（TanStack Query / SWR），客户端状态归状态管理库（Zustand / Redux）」的职责划分。 |
| 能做什么 | 避免用 Redux 手写 loading / error / 缓存 / 失效的重复样板；避免用 Query 缓存存纯 UI 状态；让状态归属清晰、调试路径明确。 |
| 怎么用 | 判断标准：数据来自远端接口、需要失效 / 重试 / 去重、会被其他端修改 → 数据层；本端用户操作产生、不会被其他端修改 → 状态管理库。组件中只调用 Hook，不直接 `fetch`；API 收敛到 `api/` / `services/`，查询配置收敛到 `queries/`。 |
| 原理和工作流程 | 数据层负责服务端状态的缓存生命周期（取数、去重、失效、重试、取消），状态管理库负责本端 UI 状态的同步流转。需要「一个 store 管全部」时可用 Redux 生态的 RTK Query（`createApi` 自动生成 Hook），把服务端状态也纳入 Redux store。 |
| 缺点 | 边界约定依赖团队自觉，缺少工具强制；跨层引用（组件直接 `fetch` 后写 store）会破坏约定；RTK Query 与 TanStack Query 各有生态绑定，迁移成本高。 |

| 能做什么 | 精炼回答高频面试问题，面试前快速回顾标准答案与关键术语。 |
| 怎么用 | 直接阅读原文 Q1-Q6 的参考答案作为面试素材，重点背诵「六大问题」「staleTime vs gcTime」「queryKey 三条原则」「onMutate / onError / onSettled 三步」。 |
| 原理和工作流程 | Q1：六大问题 + 数据层的系统性解决。Q2：`staleTime` 管「要不要重新请求」，`gcTime` 管「缓存还能不能读到」，默认 `0` / 5 分钟，且 `gcTime` ≥ `staleTime`。Q3：层级化数组、参数稳定且只放请求依赖、`queryOptions` 集中管理。Q4：`onMutate` 取消 + 快照 + 写入并返回 context，`onError` 回滚，`onSettled` 失效。Q5：`AbortController`、`ignore` 标记、数据层 `queryKey` 隔离三选一。Q6：`prefetchQuery` → `dehydrate` → `HydrationBoundary`，配合三大坑与状态归属边界。 |
| 缺点 | 未覆盖 SWR 与 TanStack Query 的详细对比、`useInfiniteQuery` 的参数细节、`broadcastQueryClient` 等进阶考点；面试追问时可能需要更深入的回答。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总数据请求层开发中十类高频错误：`queryKey` 设计问题、`gcTime` 与 `staleTime` 误配、SSR 的 QueryClient 复用与 `staleTime` 缺失、乐观更新前不取消在途请求、`onSettled` 不做失效、无限滚动不限制页数、`queryFn` 不检查 `res.ok`、未处理 `AbortError`、手动 `fetch` 与 Query 混用。 |
| 能做什么 | 快速对照排查：数据不更新先查 `queryKey` 是否遗漏参数、请求过多先查是否混入无关值；SSR 数据串味查 QueryClient 是否跨请求复用；水合后二次请求查 `staleTime`；乐观更新闪烁查 `onMutate` 是否先 `cancelQueries`。 |
| 怎么用 | `queryOptions` 统一管理键；`gcTime` 设为 `staleTime` 的 3~10 倍；每请求新建 `QueryClient`；`onMutate` 中 `await queryClient.cancelQueries({ queryKey })`；`maxPages` 限制保留页数；`if (!res.ok) throw new Error(...)`；catch 中判断 `err.name !== 'AbortError'`。 |
| 原理和工作流程 | `queryKey` 是缓存身份，遗漏或混入无关值都会破坏缓存语义；`gcTime < staleTime` 会让缓存刚过期即被回收；SSR 复用单例会让不同用户共享缓存；不取消在途请求则乐观写入会被响应覆盖；不检查 `res.ok` 会把 HTTP 错误当作成功；`AbortController` 取消时会抛 `AbortError`，不区分会误报错误。 |
| 缺点 | 这些坑大多不报错、只表现为「数据不对」，排查需要结合 Devtools 观察缓存状态；部分问题（如直接写缓存）在简单场景下不会暴露，容易长期潜伏。 |
