## 一、核心概念

### 1.1 服务端状态 vs 客户端状态

| 维度 | 客户端状态 | 服务端状态 |
|------|-----------|-----------|
| 数据归属 | 当前浏览器会话，只有本端知道 | 远端数据库，可能被其他用户 / 端修改 |
| 获取方式 | 同步产生（用户操作） | 异步获取（HTTP 请求） |
| 时效性 | 不会自行过期 | 随时可能过期（stale） |
| 典型内容 | 表单输入、弹窗开关、主题、当前 Tab | 用户列表、订单详情、商品库存、评论 |
| 管理工具 | `useState` / Zustand / Redux | TanStack Query / SWR / RTK Query |

服务端状态的本质是**一份远端数据的本地缓存**，天然需要「缓存 + 失效 + 重新验证 + 去重 + 重试 + 竞态处理」。把它塞进 Redux / Zustand，等于自己手写一套缓存系统。

### 1.2 手写 `useEffect` + `fetch` 的六大问题

```jsx
useEffect(() => {
  let cancelled = false; // 手写「忽略过期响应」的标记
  fetch(`/api/users/${userId}`)
    .then((res) => res.json())
    .then((data) => { if (!cancelled) setUsers(data); })
    .catch((err) => { if (!cancelled) setError(err); })
    .finally(() => { if (!cancelled) setLoading(false); });
  return () => { cancelled = true; };
}, [userId]);
```

这段代码能跑，但只覆盖了「最简单的成功路径」。六大问题：

| # | 问题 | 具体表现 |
|---|------|---------|
| 1 | **竞态条件** | 快速切换 `userId` 时，先发的请求可能后返回，用旧数据覆盖新数据 |
| 2 | **重复请求** | 5 个组件用同一份数据就发 5 次请求，互不共享、无法去重 |
| 3 | **无缓存** | 从 A 跳到 B 再回 A，重新白屏 loading，数据无法复用 |
| 4 | **无重试** | 一次网络抖动就进入错误态，需要用户手动刷新 |
| 5 | **loading / error 手写** | 每个组件重复三态样板代码，容易漏写 `cancelled` |
| 6 | **瀑布式请求** | 父组件拿到数据后才渲染子组件，子组件再发请求，请求串行等待 |

第 6 点最容易被忽视：

```
瀑布式（手写 useEffect）：父请求 ──等待──▶ 渲染子组件 ──等待──▶ 子请求 ──等待──▶ 渲染
并行（数据层统一预取 / 路由 loader 并行）：父请求 ─┐
                                          子请求 ─┼──等待 max(T1, T2) ──▶ 渲染
                                          孙请求 ─┘
```

### 1.3 数据请求层的职责

- **请求去重**：相同 `queryKey` 的并发请求只发一次，多个组件共享同一个 Promise。
- **缓存与复用**：以 `queryKey` 为索引，组件挂载时先渲染缓存数据，再后台校验。
- **自动重新验证**：窗口聚焦、网络恢复、组件重新挂载时按策略重新请求。
- **状态机**：统一提供 `data` / `error` / `isPending` / `isFetching` / `isSuccess`。
- **重试与退避**：失败自动重试（默认 3 次、指数退避），并区分可重试与不可重试错误。
- **失效与更新**：写操作后精确失效相关查询，支持乐观更新与回滚。
- **竞态处理**：查询失效或组件卸载时自动取消在途请求。
- **SSR 支持**：服务端预取并序列化缓存，客户端水合复用，避免首屏二次请求。

## 二、底层原理

### 2.1 TanStack Query 核心机制

TanStack Query（原 React Query）是当前 React 生态事实标准的数据请求层，核心是 **QueryClient + QueryCache + Query** 三层模型：QueryClient 持有默认配置与缓存容器，QueryCache 用 `queryHash`（由 `queryKey` 序列化得到）索引每条 Query，每个 `useQuery` 调用对应一个 Observer，组件就是订阅者。

一次查询的生命周期：

```
useQuery 调用 → 用 queryKey 算出 queryHash
  ├─ 缓存无该 Query     → 创建 Query（pending）→ 执行 queryFn
  ├─ 缓存有且数据新鲜    → 直接返回缓存，不请求
  └─ 缓存有但已 stale   → 先返回缓存渲染，同时后台重新请求
        ↓
     成功 → 写入缓存 → 通知所有订阅者重渲染；失败 → 重试，用完后置为 error
        ↓
     所有观察者卸载 → 开始 gcTime 倒计时 → 超时后缓存被回收
```

```jsx
import { useQuery } from '@tanstack/react-query';

function UserList() {
  const { data, error, isPending, isFetching, refetch } = useQuery({
    queryKey: ['users', { page: 1 }], // 缓存键，决定数据的身份
    queryFn: async ({ signal }) => {  // signal 用于取消请求
      const res = await fetch('/api/users?page=1', { signal });
      if (!res.ok) throw new Error(`请求失败：${res.status}`); // fetch 不会自动抛错
      return res.json();
    },
    staleTime: 60 * 1000,       // 1 分钟内视为新鲜，不自动重新请求
    gcTime: 5 * 60 * 1000,      // 无订阅者后缓存保留 5 分钟
    enabled: true,              // 为 false 时不自动请求（依赖前置数据时用）
    retry: 3,                   // 失败重试 3 次（指数退避）
    refetchOnWindowFocus: true, // 窗口重新聚焦时后台刷新
  });

  if (isPending) return <Spinner />; // 尚无数据且正在请求
  if (error) return <ErrorView error={error} />;
  return <ul>{data.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

> v5 变更：`cacheTime` 更名 `gcTime`；`useQuery` 的 `onSuccess` / `onError` / `onSettled` 回调被移除（改在 `QueryCache` 全局配置处理）；`isInitialLoading` 更名 `isLoading`；`useErrorBoundary` 更名 `throwOnError`。

写操作用 `useMutation`，通过 `mutation.mutate(data)` 触发，`isPending` 表示提交中，通常在 `onSuccess` 中调用 `invalidateQueries` 让相关查询失效（完整示例见 2.4 节）。

| 维度 | `useQuery` | `useMutation` |
|------|-----------|--------------|
| 触发方式 | 声明式，挂载 / 依赖变化时自动执行 | 命令式，调用 `mutate()` / `mutateAsync()` |
| 是否缓存 | 有缓存，按 `queryKey` 索引 | 不缓存，只保留最近一次的状态 |
| 重试 | 默认自动重试 3 次 | 默认不重试 |
| 生命周期回调 | v5 中移除，改在全局配置 | 保留 `onMutate` / `onSuccess` / `onError` / `onSettled` |
| 典型用途 | 读取数据 | 新增 / 修改 / 删除数据 |

### 2.2 `queryKey` 设计原则

`queryKey` 是查询的唯一身份标识，也是缓存索引与失效的依据。

**原则一：从泛到具体，用数组表达层级**

```jsx
['todos']                            // 所有 todo 相关查询
['todos', 'list', { status, page }]  // 带筛选与分页的列表
['todos', 'detail', id]              // 详情

['users', { theme: 'dark' }]     // ❌ 放入了不影响请求的 UI 状态，切换主题也会重新请求
['users', { page: 1, size: 10 }] // ✅ 只保留请求依赖
```

`invalidateQueries({ queryKey: ['todos'] })` 会**前缀匹配**失效所有 todo 查询，而 `['todos', 'detail', id]` 只失效单个详情。TanStack Query 内部对 `queryKey` 做**确定性哈希**（对象键顺序不影响结果），但放入无关值仍会导致无意义的失效与重新请求。

**原则二：用 `queryOptions` 集中管理，避免字符串硬编码**

```javascript
// queries/userQueries.js（queryOptions 由 @tanstack/react-query 提供）
export const userQueries = {
  all: () => ['users'],
  detail: (id) => queryOptions({
    queryKey: [...userQueries.all(), 'detail', id],
    queryFn: () => fetchUser(id),
    staleTime: 5 * 60 * 1000,
  }),
};
// 组件、预取、失效复用同一份定义，改一处即全局生效
const { data } = useQuery(userQueries.detail(userId));
queryClient.prefetchQuery(userQueries.detail(nextId));
queryClient.invalidateQueries({ queryKey: userQueries.all() });
```

### 2.3 `staleTime` 与 `gcTime` 的区别

最高频的面试题。一句话概括：**`staleTime` 决定「要不要重新请求」，`gcTime` 决定「缓存还能不能读到」**。

| 维度 | `staleTime` | `gcTime` |
|------|------------|----------|
| 含义 | 数据被视为「新鲜」的时长 | 查询没有任何观察者后，缓存被回收前的保留时长 |
| 默认值 | `0`（一拿到就视为过期） | `5 * 60 * 1000`（5 分钟） |
| 作用时机 | 有组件正在使用该查询时 | 所有使用该查询的组件都已卸载后 |
| 影响 | 新鲜期内不自动重新请求，但仍从缓存渲染 | 保留期内重新挂载可立即读到缓存；超时后缓存删除 |
| v4 名称 | `staleTime` | `cacheTime`（v5 更名） |

时间线（`staleTime: 30s`、`gcTime: 5min`）：

```
t=0s      组件挂载 → 请求 → 数据写入缓存
t=0~30s   数据新鲜：其他组件挂载直接读缓存，不请求
t=30~40s  数据 stale；t=40s 新组件挂载 → 先渲染缓存，同时后台重新请求
t=60s     所有组件卸载 → 开始 gcTime 倒计时；t=360s 缓存被回收
```

```javascript
const queryClient = new QueryClient({
  defaultOptions: { queries: { staleTime: 60 * 1000, gcTime: 10 * 60 * 1000, retry: 2 } },
});
useQuery({ queryKey: ['stock', code], queryFn: fetchStock, staleTime: 0 });                   // 实时性高：不缓存
useQuery({ queryKey: ['dict', 'countries'], queryFn: fetchCountries, staleTime: Infinity });  // 几乎不变
```

> **易错点**：`gcTime` 应 ≥ `staleTime`。若 `gcTime` 比 `staleTime` 还短，数据刚变 stale 就被回收，缓存形同虚设。另外 `staleTime` 不是「数据存活时间」——即使 stale，只要缓存未被 GC，组件依然会**先用缓存渲染**再后台刷新。

### 2.4 失效与乐观更新

**失效（Invalidate）**：把指定查询标记为 stale，并对活跃查询立即重新请求。

```javascript
queryClient.invalidateQueries({ queryKey: ['todos'] });                            // 前缀失效
queryClient.invalidateQueries({ queryKey: ['todos', 'detail', 1], exact: true });  // 精确失效
queryClient.invalidateQueries({ queryKey: ['todos'], refetchType: 'none' });       // 只标记，不请求
queryClient.refetchQueries({ queryKey: ['todos'] });                               // 只请求，不改 stale
```

**乐观更新（Optimistic Update）**：在请求返回前就把 UI 改成预期结果，失败再回滚，分三步：

```jsx
useMutation({
  mutationFn: updateTodoTitle,

  // 1. onMutate：请求发出前执行「取消 + 快照 + 写入」
  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ['todos', 'detail', newTodo.id] }); // 取消在途请求
    const previousTodo = queryClient.getQueryData(['todos', 'detail', newTodo.id]); // 快照缓存
    queryClient.setQueryData(['todos', 'detail', newTodo.id], newTodo);             // 写入乐观数据
    return { previousTodo }; // 返回值作为 context 传给 onError / onSettled
  },

  // 2. onError：失败时用快照回滚；3. onSettled：让服务端数据最终生效
  onError: (err, newTodo, context) =>
    queryClient.setQueryData(['todos', 'detail', newTodo.id], context.previousTodo),
  onSettled: (newTodo) =>
    queryClient.invalidateQueries({ queryKey: ['todos', 'detail', newTodo.id] }),
});
```

React 19 内置的 `useOptimistic` 适合纯组件内的乐观 UI；TanStack Query 的乐观更新把「缓存写入 + 回滚」也纳入数据层。两者可配合：`useOptimistic` 做瞬时反馈，`onMutate` / `onSettled` 保证缓存一致。

### 2.5 分页、无限滚动与预取

**分页**：页码作为 `queryKey` 的一部分，关键是保留上一页数据避免闪烁。

```jsx
const { data, isPending, isPlaceholderData } = useQuery({
  queryKey: ['users', { page }],
  queryFn: () => fetchUsers({ page }),
  placeholderData: keepPreviousData, // v5：翻页时保留上一页数据，不再白屏
});
// isPlaceholderData 为 true 表示当前展示的是上一页的占位数据
```

**无限滚动**：用 `useInfiniteQuery`，通过 `getNextPageParam` 告诉 Query 下一页的参数。

```jsx
const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
  queryKey: ['feed'],
  queryFn: ({ pageParam }) => fetchFeed({ cursor: pageParam }),
  initialPageParam: 0,                                              // v5 必填
  getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,  // undefined 表示没有下一页
  maxPages: 5,                                                       // 最多保留 5 页，控制内存
});
// 触底加载：用 IntersectionObserver 监听哨兵元素
useEffect(() => {
  const observer = new IntersectionObserver(([entry]) => {
    if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();
  });
  if (sentinelRef.current) observer.observe(sentinelRef.current);
  return () => observer.disconnect();
}, [hasNextPage, isFetchingNextPage, fetchNextPage]);

// data.pages 是页数组，需要 flatMap 展平
data.pages.flatMap((page) => page.items).map((item) => <li key={item.id}>{item.title}</li>);
```

**预取（Prefetch）**：在用户真正需要之前把数据准备好，常见三个时机：

```jsx
// 时机一：悬停列表项时预取详情
<tr onMouseEnter={() => queryClient.prefetchQuery(userQueries.detail(user.id))}>

// 时机二：拿到列表后预取前几条详情
data?.slice(0, 3).forEach((user) => queryClient.prefetchQuery(userQueries.detail(user.id)));

// 时机三：路由 loader 中预取（ensureQueryData 有缓存直接用，没有才请求，并返回数据本身）
await queryClient.ensureQueryData(userQueries.detail(params.id));
```

`prefetchQuery` 与 `ensureQueryData` 的区别：前者只确保「缓存里有」，返回 `void`；后者会**返回数据本身**，适合在 loader / 事件处理器中直接使用。

### 2.6 SWR 的定位与差异

SWR 是 Vercel 出品的轻量数据请求库，名字来自 HTTP 缓存策略 **stale-while-revalidate**（先返回陈旧数据，同时后台重新验证）——这正是它与 TanStack Query 共享的核心思想。

```jsx
const fetcher = (url) => fetch(url).then((res) => res.json());

const { data, error, isLoading } = useSWR('/api/user', fetcher, {
  revalidateOnFocus: true,     // 窗口聚焦时重新验证
  revalidateOnReconnect: true, // 网络恢复时重新验证
  dedupingInterval: 2000,      // 2 秒内相同 key 的请求去重（默认值）
});
```

| 维度 | TanStack Query | SWR |
|------|---------------|-----|
| 包体积 | 较大（约 13KB gzip） | 较小（约 5KB gzip） |
| API 风格 | 配置对象 + 完整状态机（`isPending` / `isFetching` / `isSuccess`） | 极简（`data` / `error` / `isLoading` / `isValidating`） |
| 缓存键 | `queryKey` 数组，层级化、支持前缀失效 | 字符串 key（或数组），失效粒度较粗 |
| 变更管理 | `useMutation` 完整生命周期与乐观更新 context | `useSWRMutation`，乐观更新需手动实现 |
| 无限加载 | `useInfiniteQuery`（内置 `maxPages` 等） | `useSWRInfinite` |
| 适用场景 | 中大型应用，缓存 / 失效 / 乐观更新需求复杂 | 轻量项目、Next.js 生态、只需「取数 + 自动重新验证」 |

选型建议：需要精细的缓存失效、乐观更新、无限滚动、SSR 预取时选 TanStack Query；追求极简 API、包体积敏感时选 SWR。两者的心智模型（以 key 为中心的缓存 + 后台重新验证）一致，迁移成本不高。

## 三、实战应用

### 3.1 请求竞态的处理（`AbortController`）

竞态的典型场景：搜索框连续输入，或快速点击不同用户详情。先发请求后返回时，就会**用旧数据覆盖新数据**。

```jsx
// ✅ 方案一：用 AbortController 真正取消上一次请求
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setUser)
    .catch((err) => {
      // 主动取消会抛 AbortError，需要忽略而不是当作业务错误
      if (err.name !== 'AbortError') setError(err);
    });
  return () => controller.abort(); // 依赖变化或组件卸载时取消
}, [userId]);

// ✅ 方案二：用「本次请求是否已过期」的标记（不取消请求，只丢弃结果）
useEffect(() => {
  let ignore = false;
  fetch(`/api/users/${userId}`).then((res) => res.json()).then((data) => { if (!ignore) setUser(data); });
  return () => { ignore = true; };
}, [userId]);
```

两者区别：`AbortController` 会真正**中断网络请求**（节省带宽与服务端资源），`ignore` 标记只**丢弃结果**（请求仍会完成）。

**TanStack Query 内置了这套机制**：`queryFn` 接收的 `signal` 会在查询失效、组件卸载或 `cancelQueries` 被调用时 abort，无需手写 cleanup——写成 `queryFn: ({ signal }) => fetch(url, { signal }).then((r) => r.json())` 即可；同时 `queryKey` 本身就是竞态的天然屏障——不同 `userId` 对应不同缓存条目，旧请求即使返回也只写入旧 key。

### 3.2 缓存失效策略

缓存失效要回答：**「什么时候这份数据不再可信？」**

| 策略 | 实现方式 | 适用场景 |
|------|---------|---------|
| 时间失效 | `staleTime` 到期后按触发条件重新请求 | 大多数列表、详情数据 |
| 主动失效 | 写操作后 `invalidateQueries({ queryKey })` | 增删改后的关联查询 |
| 精确失效 | `invalidateQueries({ queryKey, exact: true })` | 只需刷新单条详情 |
| 直接写缓存 | `setQueryData(key, updater)` | 已知服务端返回的新值，省一次请求 |
| 只标记不请求 | `invalidateQueries({ queryKey, refetchType: 'none' })` | 当前页面不展示，下次进入再请求 |
| 全局重置 | `queryClient.clear()` | 退出登录、切换租户 |

```javascript
// 方式一：直接写缓存（最省请求，要求服务端返回完整实体）
onSuccess: (updatedTodo) => {
  queryClient.setQueryData(['todos', 'detail', updatedTodo.id], updatedTodo);
  // 列表中的该条也要同步，用 updater 函数做局部替换
  queryClient.setQueryData(['todos', 'list'], (old) =>
    old?.map((t) => (t.id === updatedTodo.id ? updatedTodo : t)));
},
// 方式二：精确失效（多一次请求，但保证与服务端一致）
onSuccess: () => queryClient.invalidateQueries({ queryKey: ['todos', 'detail', todo.id] }),
// 方式三：全局重置（退出登录 / 切换租户）
function logout() { queryClient.clear(); }
```

**跨标签页同步**：多个标签页各持一份缓存可能不一致，TanStack Query 提供实验性的 `broadcastQueryClient`，通过 `BroadcastChannel` 同步失效事件：`broadcastQueryClient({ queryClient, broadcastChannel: 'my-app' })`。

### 3.3 SSR 场景下的数据预取（`dehydrate` / `hydrate`）

CSR 下首屏必须等 JS 加载 → 组件挂载 → 发请求才能看到数据；SSR 下可以在服务端就发起请求，把缓存随 HTML 一起送到客户端：

```
服务端：为本次请求创建独立 QueryClient → prefetchQuery 预取 → dehydrate 序列化成 dehydratedState
客户端：<HydrationBoundary state={...}>（或 hydrate(queryClient, state)）灌入缓存 → useQuery 直接命中
```

```tsx
// app/posts/page.tsx —— 服务端组件
export default async function Page() {
  const queryClient = new QueryClient(); // 每次请求创建新实例，避免用户数据串味
  // staleTime 是关键：避免客户端水合后立刻重新请求
  await queryClient.prefetchQuery({ queryKey: ['posts'], queryFn: fetchPosts, staleTime: 60 * 1000 });
  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <PostList /> {/* 客户端组件：useQuery 直接命中缓存，首屏渲染即有数据 */}
    </HydrationBoundary>
  );
}
```

**SSR 三大坑**：

1. **QueryClient 跨请求复用**：服务端若用模块级单例，A 用户的缓存可能被 B 用户读到，造成数据泄露，必须每个请求创建新实例。
2. **忘记设置 `staleTime`**：默认 `staleTime: 0`，客户端水合后数据立刻被视为过期，会马上再请求一次，SSR 预取白做。
3. **`queryKey` 不一致**：服务端与客户端的 `queryKey` 必须完全一致（含参数结构），否则无法命中缓存。

### 3.4 数据请求层与状态管理库的分工边界

一句话原则：**服务端状态归数据层，客户端状态归状态管理库，两者不互相搬运。**

```
组件（视图）：只负责渲染 + 触发事件，不关心数据从哪来
  ├── 服务端状态 → TanStack Query / SWR：用户列表、订单、库存（缓存 / 失效 / 重试）
  └── 客户端状态 → Zustand / Redux：弹窗开关、主题、表单草稿（跨组件 UI 状态）
                          ↓  HTTP API / 后端
```

| 判断标准 | 放数据层（Query / SWR） | 放状态管理库（Zustand / Redux） |
|---------|----------------------|------------------------------|
| 数据来源 | 远端接口 | 本端用户操作 |
| 是否需要失效 / 重试 / 去重 | 需要 | 不需要 |
| 是否会被其他端修改 | 会 | 不会 |
| 典型例子 | 商品列表、用户信息、通知数量 | 侧边栏折叠、表单草稿、未提交的筛选条件 |

```jsx
// ❌ 错误：把服务端数据放进 Redux，再手写 loading / error / 失效
dispatch(fetchUsersStart());
try { dispatch(fetchUsersSuccess(await api.getUsers())); }
catch (e) { dispatch(fetchUsersError(e)); }
// 问题：没有缓存、没有去重、没有自动重新验证，每个 slice 都要重复这套代码
// 正确做法：useQuery({ queryKey: ['users'], queryFn: api.getUsers })

// ❌ 错误：把纯 UI 状态塞进 Query 缓存（Query 是异步数据缓存，不应存同步 UI 状态）
queryClient.setQueryData(['sidebar-open'], true);
// 正确做法：用 useState 或 Zustand
```

**需要「一个 store 管全部」时**：Redux 生态的 RTK Query 把服务端状态也纳入 Redux store，用 `createApi` 定义端点并自动生成 `useGetUsersQuery` 等 Hook，缓存与失效由 RTK Query 管理，适合已在用 Redux Toolkit 且希望「单一 store、DevTools 全量可见」的团队；纯 React 项目直接用 TanStack Query 更轻。

**边界落地建议**：

- 组件中只调用 Hook（`useQuery` / `useMutation` / `useStore`），不直接 `fetch`。
- API 请求统一收敛到 `api/` 或 `services/` 目录，`queryKey` 与查询配置收敛到 `queries/` 目录（用 `queryOptions`）。
- 状态管理库只存「本端产生、本端消费」的数据；写操作后的状态同步优先「失效 + 重新请求」，乐观更新只在交互体验确实需要时使用。

## 四、常见面试题

**Q1：为什么不应该在 `useEffect` 里手写数据请求？**

手写 `useEffect` + `fetch` 存在六大问题：竞态条件（旧请求覆盖新数据）、重复请求（多组件不共享）、无缓存（切页重新加载）、无重试（网络抖动直接失败）、loading / error 样板代码重复、瀑布式请求（父子组件串行取数）。数据请求层通过 `queryKey` 索引的缓存、请求去重、自动重新验证、统一状态机、重试退避与取消信号，系统性地解决了这些问题。

**Q2：`staleTime` 和 `gcTime` 有什么区别？**

`staleTime` 是数据被视为「新鲜」的时长，决定**要不要重新请求**：新鲜期内不自动请求，过期后在有观察者且触发条件满足时后台重新请求。`gcTime` 是查询**没有任何观察者后**缓存被回收前的保留时长，决定**缓存还能不能读到**：保留期内重新挂载可立即读到缓存，超时后缓存被删除。默认值分别是 `0` 与 5 分钟，且 `gcTime` 应 ≥ `staleTime`。

**Q3：如何设计 `queryKey`？**

三条原则：(1) 从泛到具体、用数组表达层级，如 `['todos', 'list', { status, page }]`、`['todos', 'detail', id]`，这样 `invalidateQueries({ queryKey: ['todos'] })` 可前缀匹配失效整组查询；(2) 参数顺序稳定、只放影响请求的值，避免放入主题、语言等无关 UI 状态；(3) 用 `queryOptions` 集中管理键与配置，让预取、失效、组件调用复用同一份定义。

**Q4：什么是乐观更新？如何实现回滚？**

乐观更新是在服务端响应之前就把 UI 改成预期结果，失败时回滚。TanStack Query 分三步：`onMutate` 中先 `cancelQueries` 取消在途请求避免覆盖，再用 `getQueryData` 快照当前缓存，然后 `setQueryData` 写入乐观数据，并把快照作为 context 返回；`onError` 用 context 中的快照回滚；`onSettled` 中 `invalidateQueries` 让服务端真实数据最终生效。

**Q5：请求竞态是怎么产生的？如何解决？**

竞态产生于「先发的请求后返回」：快速切换 `userId` 或连续输入搜索词时，旧请求的响应可能在新请求之后到达并覆盖正确数据。三种方案：(1) `AbortController` 配合 `useEffect` cleanup 真正取消在途请求；(2) 用 `ignore` / `cancelled` 标记丢弃过期响应；(3) 使用数据层——`queryKey` 让不同参数对应不同缓存条目，旧响应只写入旧 key，TanStack Query 还会在 `queryKey` 变化时自动 abort 上一次请求。

**Q6：SSR 下如何做数据预取？数据层和状态管理库的边界又在哪里？**

SSR 预取：服务端为每个请求创建独立的 `QueryClient`，用 `prefetchQuery` 预取首屏数据，再 `dehydrate` 序列化缓存，通过 `<HydrationBoundary state={...}>` 传给客户端灌入，客户端 `useQuery` 直接命中。三个坑：QueryClient 不能跨请求复用（会造成用户数据泄露）；必须设置 `staleTime`，否则水合后立即重新请求；两端 `queryKey` 必须一致。边界：服务端状态（远端数据，会过期、需缓存 / 去重 / 重试）交给 TanStack Query / SWR；客户端状态（本端产生、本端消费的 UI 状态）交给 Zustand / Redux；不要把手写的服务端数据放进状态管理库，也不要用 Query 缓存存纯 UI 状态。

## 五、避坑指南

| 常见错误 | 现象 | 原因 | 解决方案 |
|---------|------|------|---------|
| `queryKey` 中遗漏参数或放入无关 UI 状态 | 参数变化后仍显示旧数据 / 切换主题也触发重新请求 | 缓存键未完整表达请求依赖，或混入了无关值 | 把影响请求的所有参数都放进 `queryKey`，无关值剔除，并用 `queryOptions` 统一管理 |
| `gcTime` 小于 `staleTime` | 数据刚过期就被回收，缓存几乎不起作用 | 配置参数矛盾 | 保证 `gcTime` ≥ `staleTime`，一般为 3~10 倍 |
| SSR 下复用同一个 `QueryClient` 或忘记设置 `staleTime` | 用户 A 看到用户 B 的数据 / 水合后立刻再请求一次 | 模块级单例在请求之间共享缓存；默认 `staleTime: 0`，灌入即 stale | 每个请求创建新的 `QueryClient` 实例，并在服务端与客户端统一设置合理的 `staleTime` |
| 乐观更新前不 `cancelQueries` | 在途请求返回后覆盖乐观数据，UI 闪烁 | 在途请求与乐观写入竞争同一缓存 | `onMutate` 中先 `await queryClient.cancelQueries({ queryKey })` |
| `onSettled` 中不做失效 | 乐观数据与服务端真实数据不一致 | 回滚只处理失败路径，成功路径缺少最终同步 | `onSettled` 中 `invalidateQueries`，让服务端数据最终生效 |
| 无限滚动不限制页数 | 长时间滚动后内存持续增长 | 所有页数据都保留在缓存中 | 设置 `maxPages` 限制保留页数 |
| `queryFn` 中不检查 `res.ok` | 接口返回 404 / 500 时被当作成功 | `fetch` 只在网络错误时 reject，HTTP 错误码不会抛错 | 手动 `if (!res.ok) throw new Error(...)` |
| 未处理 `AbortError` | 取消请求被当作业务错误弹出提示 | `AbortController` 取消时抛 `AbortError` | catch 中判断 `err.name !== 'AbortError'` 再处理 |
| 手动 `fetch` 与 Query 混用同一份数据 | 同一份数据出现两个真相，UI 不一致 | 绕过缓存直接请求 | 统一通过 `useQuery` / `setQueryData` 读写，保持单一数据源 |
