### useEffect vs useLayoutEffect

| 对比维度 | useEffect | useLayoutEffect |
|---------|-----------|-----------------|
| 核心定位 | 处理副作用，不阻塞浏览器渲染 | 在浏览器绘制前同步读取和修改 DOM |
| 执行时机 | 渲染完成后**异步**执行 | DOM 变更后**同步**执行 |
| 是否阻塞渲染 | 不阻塞，浏览器正常绘制 | 阻塞渲染，直到回调执行完毕 |
| 服务端渲染 | 不会执行 | 会触发警告 |
| 使用场景 | 数据请求、事件订阅、日志记录、定时器 | 读取 DOM 布局尺寸、避免视觉闪烁、同步调整位置 |
| 性能影响 | 对渲染性能影响小 | 滥用会导致页面响应变慢、长时间白屏 |
| 选择建议 | 默认使用 useEffect，大部分场景不需要阻塞渲染 | 仅在需要同步测量 DOM 并立即修改时使用 |

### useMemo vs useCallback vs React.memo

| 对比维度 | useMemo | useCallback | React.memo |
|---------|---------|-------------|------------|
| 核心定位 | 缓存**计算结果**，依赖不变返回缓存值 | 缓存**函数引用**，依赖不变返回同一个函数 | 缓存**组件渲染结果**，props 浅比较不变则跳过渲染 |
| 类型 | Hook（在组件内部调用） | Hook（在组件内部调用） | 高阶组件（包裹组件） |
| 缓存内容 | 任意值（对象、数组、计算结果） | 函数引用 | 组件渲染输出 |
| 返回值 | 缓存的值 | 缓存的函数 | 增强后的组件 |
| 语法糖关系 | `useMemo(() => fn, deps)` | `useCallback(fn, deps)` 等价于 `useMemo(() => fn, deps)` | 无关联 |
| 使用场景 | 昂贵的计算、缓存对象/数组避免子组件重渲染 | 传递给子组件的回调函数，配合 React.memo 使用 | 避免 props 不变的纯展示子组件重渲染 |
| 性能开销 | 依赖比较和缓存存储 | 依赖比较和缓存存储 | props 浅比较开销 |
| 选择建议 | 计算开销大且依赖不频繁变化时使用 | 回调传递给 React.memo 子组件时使用 | 子组件渲染开销大且 props 不频繁变化时使用 |

### Redux Toolkit vs Zustand

| 对比维度 | Redux Toolkit | Zustand |
|---------|---------------|---------|
| 核心定位 | 功能完备的企业级状态管理方案 | 极简轻量的状态管理库 |
| 包体积 | ~12KB | ~1KB |
| 学习曲线 | 陡峭（需理解 Store、Reducer、Action、Middleware） | 低（只需一个 `create` 函数） |
| 样板代码 | 较多（createSlice 减少但仍需定义 initialState、reducers） | 极少（直接在 create 中定义 state 和 actions） |
| 不可变数据 | 内置 immer，可直接修改 state | 需手动不可变更新，或使用 immer 中间件 |
| Provider 包裹 | 需要 `<Provider store={store}>` | 不需要，store 是模块级单例 |
| 中间件生态 | 丰富（redux-thunk、redux-saga、redux-persist 等） | 支持（persist、devtools、immer 等中间件） |
| DevTools | Redux DevTools 完善 | 支持 Redux DevTools（通过 devtools 中间件） |
| 异步处理 | createAsyncThunk 自动管理 pending/fulfilled/rejected 状态 | 直接在 store 中定义 async 函数 |
| 精确订阅 | useSelector + shallowEqual | selector 默认浅比较，天然精确订阅 |
| 适用场景 | 大型企业应用，需要严格单向数据流和可追溯性 | 中小型应用，追求简洁 API 和极小包体积 |
| 选择建议 | 团队熟悉 Redux 生态、项目规模大、需丰富中间件 | 新项目快速启动、追求简洁、团队规模小 |

### 受控组件 vs 非受控组件

| 对比维度 | 受控组件 | 非受控组件 |
|---------|---------|-----------|
| 核心定位 | 表单数据由 React state 管理，React 是"单一数据源" | 表单数据由 DOM 自身管理，通过 ref 获取值 |
| 数据流向 | React state -> input value -> onChange 更新 state | DOM -> ref.current.value 读取 |
| 值的来源 | `useState` 管理的 state | DOM 节点的原生 value 属性 |
| 实时校验 | 支持（每次输入都可触发校验） | 不支持（仅在提交时读取值） |
| 代码复杂度 | 需为每个表单字段维护 state 和 onChange | 代码简洁，无需 state 维护 |
| 灵活性 | 高（可动态格式化、条件禁用、联动校验） | 低（仅读取原始值） |
| 性能 | 每次输入触发重渲染 | 不触发重渲染 |
| 使用场景 | 需要实时校验、动态格式化、字段联动 | 简单表单、文件上传、集成非 React 库 |
| 选择建议 | 大多数表单场景使用受控组件 | 仅需提交时获取值且无需实时交互时使用 |
