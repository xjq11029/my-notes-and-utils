## 一、核心概念

### 1.1 前端路由的本质

| 维度 | 内容 |
|------|------|
| 是什么 | 在不刷新页面的前提下，根据 URL 变化切换显示不同页面内容的技术方案 |
| 能做什么 | 支撑单页应用（SPA）的多页面体验，通过监听 URL 变化并匹配路由规则来渲染对应组件，保持应用状态不丢失 |
| 怎么用 | `window.history.pushState(state, '', '/path')` 或 `window.addEventListener('hashchange', handler)` |
| 原理和工作流程 | 依赖两个关键能力：监听 URL 变化和匹配路由规则。**History API** 模式通过 `pushState`/`replaceState` 修改 URL 不触发刷新，`popstate` 事件监听前进后退；**Hash** 模式通过 `window.onhashchange` 监听 URL 中 `#` 之后部分的变化，兼容性更好 |
| 缺点 | **BrowserRouter** 模式刷新非首页路径会返回 404，需服务器配置 fallback 将所有路由指向 `index.html`；Hash 模式 URL 带有 `#` 符号，不够美观且 SEO 抓取受限 |

### 1.2 状态管理的必要性

| 维度 | 内容 |
|------|------|
| 是什么 | 应用规模增长时将组件间共享状态集中管理的架构方案 |
| 能做什么 | 提供单一数据源避免 **prop drilling**，通过明确的 action/reducer 控制状态变更路径，将业务逻辑与视图层解耦 |
| 怎么用 | `const store = createStore(rootReducer)` 或 `const useStore = create((set) => ({ ... }))` |
| 原理和工作流程 | 单一数据源：全局状态集中存储，任意组件可直接访问，无需层层传递 props。可预测的状态变化：所有状态变更通过 action 描述意图，由 reducer 纯函数计算新状态。状态与 UI 分离：业务逻辑在 store 中处理，组件只负责渲染和触发 action |
| 缺点 | 引入额外依赖和样板代码，小型应用可能过度设计；Redux 学习曲线陡峭；全局状态过多时数据流向追踪困难，调试成本上升 |

## 二、底层原理

### 2.1 React Router v6 核心变化

| 维度 | 内容 |
|------|------|
| 是什么 | **React Router v6** 相较 v5 的一次重大 API 重构，简化了路由配置方式 |
| 能做什么 | 用 `<Routes>` 替代 `<Switch>`，用 `element` 属性替代 `component`/`render`，通过 `<Outlet>` 实现嵌套路由渲染，`useNavigate` 替代 `useHistory` 进行编程式导航 |
| 怎么用 | `<Routes><Route path="/users/:id" element={<UserDetail />} /></Routes>` |
| 原理和工作流程 | v6 使用 `<Routes>` 进行智能路由匹配（默认匹配最佳路由而非首个匹配），嵌套路由通过 `<Outlet>` 占位符渲染子路由。`useRoutes` 支持配置式路由定义，路由守卫通过包装组件配合 `<Navigate>` 实现重定向。移除了 `<Redirect>`、`<Prompt>` 等组件，改用 `useBlocker` 等 Hook 替代 |
| 缺点 | 从 v5 迁移时 API 不兼容，需要逐一替换；`<Prompt>` 的移除导致路由拦截需自行实现；官方文档中部分高级用法示例不够充分 |

### 2.2 路由模式

| 维度 | 内容 |
|------|------|
| 是什么 | 前端路由的两种实现方式：**BrowserRouter**（HTML5 History API）和 **HashRouter**（hash 模式） |
| 能做什么 | BrowserRouter 提供干净美观的 URL 且有利于 SEO；HashRouter 无需服务器配置，兼容性极佳 |
| 怎么用 | `<BrowserRouter>` 或 `<HashRouter>` 包裹应用根组件 |
| 原理和工作流程 | BrowserRouter 基于 `history.pushState`/`replaceState` API，URL 形如 `/users/123`，需 Nginx 配置 `try_files $uri /index.html` 处理 fallback。HashRouter 基于 `window.onhashchange` 事件，URL 形如 `/#/users/123`，hash 部分不会发送到服务器，因此无需后端配置，但搜索引擎不抓取 hash 后的内容 |
| 缺点 | BrowserRouter 需要服务器端 fallback 配置，部署复杂度增加；HashRouter 的 URL 带有 `#` 符号，不美观，SEO 不友好 |

### 2.3 路由守卫实现

| 维度 | 内容 |
|------|------|
| 是什么 | 在路由跳转前根据权限或登录状态决定是否放行的一种访问控制机制 |
| 能做什么 | 保护需要认证的页面，未登录用户自动重定向到登录页；可实现基于角色的权限控制 |
| 怎么用 | `<Route path="/dashboard" element={<ProtectedRoute><Dashboard /></ProtectedRoute>} />` |
| 原理和工作流程 | 高阶组件方式：创建 `ProtectedRoute` 包装组件，内部调用 `useAuth()` 检查认证状态，未认证时返回 `<Navigate to="/login" replace />`，已认证则渲染 `children`。Hook 方式：在 `useEffect` 中监听认证状态，未认证时调用 `navigate('/login', { replace: true })` 进行重定向。需注意异步认证状态下初始值为 null 时的 loading 处理 |
| 缺点 | 异步检查登录状态时存在短暂闪烁（未登录时瞬间显示受保护页面）；权限逻辑分散在多处路由配置中，大规模应用维护成本高 |

### 2.4 Redux 工作流程

| 维度 | 内容 |
|------|------|
| 是什么 | 一种遵循严格单向数据流的可预测状态管理库，包含 Store、Action、Reducer 三大核心概念 |
| 能做什么 | 将应用状态集中存储在单一 Store 中，所有状态变更通过 dispatch action 触发，由纯函数 reducer 生成新状态 |
| 怎么用 | `store.dispatch({ type: 'ADD_TODO', payload: '学习' })` |
| 原理和工作流程 | 单向数据流：View 通过 `dispatch(action)` 发送 action 对象到 Store，Store 将当前 state 和 action 交给 Reducer 纯函数计算新 state，Store 更新后通过 subscribe 通知 View 重新渲染。三大原则：单一数据源（整个应用只有一个 Store）、State 只读（唯一改变方式是 dispatch action）、纯函数修改（Reducer 必须是无副作用的纯函数） |
| 缺点 | 样板代码多，一个简单的状态变更需要定义 action type、action creator、reducer 分支；学习曲线陡峭，新手难以理解中间件（如 **redux-thunk**）的工作原理 |

### 2.5 Redux Toolkit（RTK）

| 维度 | 内容 |
|------|------|
| 是什么 | Redux 官方推荐的工具集，通过 `createSlice`、`configureStore`、`createAsyncThunk` 大幅简化 Redux 开发 |
| 能做什么 | 用 `createSlice` 同时生成 action creator 和 reducer，内置 **immer** 允许直接修改 state；`createAsyncThunk` 简化异步请求的状态管理（pending/fulfilled/rejected） |
| 怎么用 | `const slice = createSlice({ name, initialState, reducers: { add(state) { state.value++ } } })` |
| 原理和工作流程 | `createSlice` 内部集成 immer，在 reducer 中可直接修改 state 而无需手动展开。`configureStore` 默认集成 **Redux DevTools** 和 **redux-thunk**。`createAsyncThunk` 自动生成三个 action（pending/fulfilled/rejected），通过 `extraReducers` 的 builder 模式处理异步状态流转。组件中通过 `useSelector` 读取状态，`useDispatch` 派发 action |
| 缺点 | 相较轻量方案（如 Zustand）仍有一定学习成本；`createAsyncThunk` 的错误处理需要在 `extraReducers` 中额外处理 `rejected` 分支，容易遗漏 |

### 2.6 Zustand 轻量状态管理

| 维度 | 内容 |
|------|------|
| 是什么 | 一个极简的 React 状态管理库，API 仅需一个 `create` 函数，无需 Provider 包裹 |
| 能做什么 | 快速创建全局 store，支持 selector 精确订阅避免不必要的重渲染，内置中间件支持持久化和 DevTools |
| 怎么用 | `const useStore = create((set) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) }))` |
| 原理和工作流程 | 基于发布订阅模式，`create` 函数返回一个自定义 Hook。组件调用 `useStore(selector)` 时，Zustand 内部维护订阅列表，当 `set` 触发状态更新时，仅通知那些 selector 返回值变化的订阅者。无需 Provider 包裹，因为 store 是模块级单例。支持 `persist` 中间件将状态同步到 **localStorage**，`devtools` 中间件连接 Redux DevTools |
| 缺点 | 缺乏 Redux 那样成熟的中间件生态；对于需要严格单向数据流和可追溯性的大型企业应用，调试和审计能力不如 Redux 完善 |

### 2.7 状态管理方案对比

| 维度 | 内容 |
|------|------|
| 是什么 | 对 **Redux Toolkit**、**MobX**、**Zustand**、**Jotai** 四种主流方案在包体积、学习曲线、适用场景等维度的横向对比 |
| 能做什么 | 帮助开发者根据项目规模、团队经验和业务特点选择最合适的状态管理方案 |
| 怎么用 | 大型企业应用选 Redux Toolkit；中小型应用选 Zustand；细粒度状态选 Jotai；数据密集型选 MobX |
| 原理和工作流程 | 对比维度包括：包体积（Zustand ~1KB 最小，Redux ~12KB）、学习曲线（Redux 陡峭，Zustand/Jotai 低）、样板代码量（Zustand 极少，Redux 较多）、数据可变性（Redux/Zustand 不可变，MobX 可变）、中间件生态（Redux 最丰富）、Provider 需求（Zustand 不需要，其余需要） |
| 缺点 | 各方案间 API 不兼容，迁移成本高；选型需权衡当前需求和未来扩展性，过早优化可能引入不必要的复杂度 |

## 三、实战应用

### 3.1 多层级路由配置

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 `useRoutes` 配置式定义嵌套多层级的路由结构，通过 `children` 数组描述路由层级关系 |
| 能做什么 | 实现 Dashboard 等复杂页面的多级导航，结合路由守卫保护子路由，支持 index 路由和通配路由 |
| 怎么用 | `{ path: 'dashboard', element: <ProtectedRoute><Dashboard /></ProtectedRoute>, children: [ ... ] }` |
| 原理和工作流程 | 通过 `useRoutes` 接收路由配置数组，每层路由通过 `children` 字段定义子路由。父组件使用 `<Outlet />` 渲染匹配的子路由。路由守卫包裹在 `element` 属性中，保护整个子树。`index: true` 定义默认子路由，`path: '*'` 匹配所有未匹配路径 |
| 缺点 | 层级过深时路由配置可读性下降；嵌套路由的权限控制粒度较粗，难以对单个子路由做精细化权限控制 |

### 3.2 全局 Loading 状态管理

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Redux Slice 管理全局 Loading 状态，支持多个并发请求的独立追踪 |
| 能做什么 | 追踪每个异步请求的加载状态，自动计算全局 loading 标识，驱动全局 Loading 组件显示 |
| 怎么用 | `dispatch(startLoading('requestKey'))` 开始加载，`dispatch(stopLoading('requestKey'))` 结束加载 |
| 原理和工作流程 | 在 `loadingSlice` 中维护 `requests` 对象（键为请求标识，值为布尔）和 `global` 布尔值。`startLoading` 将对应 key 设为 true，`stopLoading` 删除对应 key 并检查 `requests` 是否仍有进行中的请求来更新 `global`。这是一种基于计数的方案，允许并发请求独立追踪 |
| 缺点 | 需要手动管理每个请求的 key 命名，容易漏掉 `stopLoading` 调用导致 loading 永不消失；错误场景下需在 catch 块中额外调用 `stopLoading` |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总路由与状态管理开发中 7 个高频错误及其根因和解决方案 |
| 能做什么 | 帮助开发者快速定位和修复常见问题，避免在面试和实际开发中踩坑 |
| 怎么用 | 对照表格逐项排查：BrowserRouter 刷新 404 检查 Nginx fallback 配置；Redux state 直接修改改用不可变更新或 RTK immer |
| 原理和工作流程 | (1) BrowserRouter 刷新 404：服务器未配置 fallback，需 Nginx `try_files $uri /index.html`。(2) Redux state 直接修改：破坏不可变性导致 React 无法检测变化，需始终返回新对象或使用 RTK immer。(3) selector 返回整个 state：默认严格相等比较导致任何字段变化都触发重渲染，需精确选择字段或使用 `shallowEqual`。(4) 路由守卫异步闪烁：异步认证初始为 null，需添加 loading 判断。(5) Zustand selector 返回新引用：每次返回新对象导致浅比较判定变化，需选择基本类型值或使用 shallow 比较。(6) 嵌套路由忘记 `<Outlet />`：子路由无法渲染，需在父组件中放置 `<Outlet />`。(7) createAsyncThunk 未处理错误：thunk 内部异常未被捕获，需在 `extraReducers` 处理 rejected 状态 |
| 缺点 | 部分错误（如 Redux state 直接修改）在 RTK 中使用 immer 后不再常见，但理解底层原理仍有价值；表格未覆盖运行时性能排查方法 |
