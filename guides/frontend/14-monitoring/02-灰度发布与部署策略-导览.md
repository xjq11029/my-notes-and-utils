# 02-灰度发布与部署策略 - 导览

---

## 1.1 Feature Flags 四类模型（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Feature Flags 分为四类：Release Toggles（发布开关）、Experiment Toggles（实验开关）、Ops Toggles（运维开关）、Permission Toggles（权限开关），用汽车功能开关类比：未发布功能用开关隐藏、A/B 测试对比不同版本、紧急降级关闭非核心功能、VIP 用户专属功能 |
| 能做什么 | Release Toggles 控制未上线功能；Experiment Toggles 支持 A/B 测试；Ops Toggles 紧急降级；Permission Toggles 按用户级别控制功能可见性 |
| 怎么用 | 在代码中通过 `if (flag.isEnabled('feature-name'))` 控制功能分支；在 Flag 管理后台配置放量策略和用户分群 |
| 原理和工作流程 | 应用启动时拉取 Flag 配置 → 存入内存缓存 → 每次功能判断时查询本地缓存 → 监听 WebSocket 实时更新 → Flag 服务不可用时使用本地默认值降级 |
| 缺点 | Flag 代码长期不清理导致逻辑膨胀；Flag 嵌套导致组合爆炸；Flag 服务不可用时的降级策略需要精心设计 |

## 1.2 三种部署策略（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 三种部署策略分别是灰度发布（Canary，逐步放量）、蓝绿部署（Blue-Green，环境切换）、滚动更新（Rolling Update，逐个替换实例） |
| 能做什么 | 灰度发布降低上线风险、蓝绿部署实现秒级回滚、滚动更新实现零停机更新 |
| 怎么用 | 灰度发布通过 Nginx split_clients 按比例分流；蓝绿部署通过 K8s Service selector 切换；滚动更新通过 K8s RollingUpdate strategy |
| 原理和工作流程 | 灰度发布：新版本部署到少量实例 → 分配 10% 流量 → 观察 → 逐步放量至 100%；蓝绿部署：闲置环境部署新版本 → 切换流量 → 旧环境作为回滚备份；滚动更新：逐个替换实例 → 每个实例替换后验证健康 → 继续下一个 |
| 缺点 | 灰度发布观察期长；蓝绿部署资源成本翻倍；滚动更新回滚速度慢、短暂新旧版本混用 |

## 1.3 前端 Feature Flags 实现架构（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端 Feature Flags 实现架构包含四层：SDK 初始化（拉取配置）、本地缓存（减少网络请求）、实时更新（WebSocket 推送）、降级策略（本地默认值） |
| 能做什么 | 实现功能开关的前端侧完整方案；支持离线使用（localStorage 缓存）；支持实时更新（无需刷新页面） |
| 怎么用 | 应用入口初始化 SDK → 拉取 Flag 配置 → 存入 localStorage 缓存 + 内存 → 通过 Hook/组件获取 Flag 状态 → 监听 WebSocket 更新 |
| 原理和工作流程 | SDK 初始化 → 从 Flag 服务拉取配置 → 合并本地默认值 → 存入内存 + localStorage（TTL 5 分钟）→ 实时更新通过 WebSocket 推送 → 降级时使用 localStorage 缓存值或硬编码默认值 |
| 缺点 | 初始化时可能有短暂延迟（拉取配置）；WebSocket 连接需要额外维护；降级策略需要与后端协调 |

## 2.1 Nginx 层灰度（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Nginx 通过 `map` 指令根据 Cookie/Header 分流，通过 `split_clients` 指令按比例分流，将请求路由到不同版本的前端静态资源 |
| 能做什么 | 在不修改应用代码的情况下实现流量分流；支持精确用户控制（Cookie/Header）和随机比例分配（IP 哈希） |
| 怎么用 | 定义 `map $cookie_gray_version $app_version` 按 Cookie 分流 → 定义 `split_clients` 按比例分流 → 在不同 location 中根据版本变量选择 root 目录 |
| 原理和工作流程 | 用户请求到达 Nginx → map 指令检查 Cookie/Header → 无匹配则用 split_clients 按 IP 哈希分配 → 路由到对应版本的静态资源目录 → 返回不同版本的 index.html + JS/CSS |
| 缺点 | 仅能控制静态资源版本，无法控制应用内逻辑；配置变更需要 Nginx reload；Cookie 可能被用户手动修改 |

## 2.2 Feature Flags 灰度（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Feature Flags 在服务端通过规则引擎 + 用户分群（ID 哈希、地区、设备、套餐）实现精细化功能控制，支持按比例放量、A/B 测试变体分配 |
| 能做什么 | 实现比 Nginx 更精细的灰度控制（应用内功能级别）；支持多维度用户分群；支持 A/B 测试变体分配 |
| 怎么用 | 在 Flag 管理后台创建 Flag → 配置放量策略（比例、地区、设备、用户白名单）→ 前端通过 SDK 获取 Flag 状态 → 控制功能开关 |
| 原理和工作流程 | 用户请求 → 前端 SDK 携带用户上下文请求 Flag 服务 → 服务端规则引擎根据用户 ID 哈希 + 分群条件判断 → 返回 Flag 状态 → 前端缓存结果 |
| 缺点 | 依赖 Flag 服务的可用性；每次判断需要网络请求或依赖缓存；规则引擎复杂度随 Flags 数量增长 |

---

## 2.3 CDN 边缘灰度（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 利用 CDN 边缘计算节点（Cloudflare Workers、Vercel Edge Functions）在请求到达源站之前进行流量分流，可按地理位置、比例、Cookie、User-Agent 等维度灰度 |
| 能做什么 | 在 CDN 边缘就近分流，减少延迟；支持按地理位置灰度（仅特定国家/地区放量）；无需修改源站配置 |
| 怎么用 | 编写 Cloudflare Workers 或 Vercel Edge Function → 在 fetch 事件中判断请求属性 → 修改目标 hostname 路由到不同版本 |
| 原理和工作流程 | 用户请求到达 CDN 边缘节点 → Worker 拦截请求 → 根据 cf.country/hash/Cookie 判断 → 修改请求 URL 指向灰度版本 → 转发到源站 |
| 缺点 | 仅支持特定 CDN 平台（Cloudflare、Vercel）；Worker 有执行时间限制（10-50ms）；调试较困难 |

## 2.4 容器化部署原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端容器化部署的完整流程：Docker 多阶段构建前端镜像 → Nginx 反向代理静态资源 → K8s 滚动更新管理 Pod 生命周期 |
| 能做什么 | 实现前端应用的标准化交付（镜像）；支持弹性伸缩（K8s HPA）；支持零停机更新（滚动更新）；支持健康检查和自动恢复 |
| 怎么用 | 编写 Dockerfile（多阶段构建）→ 构建镜像推送到镜像仓库 → 编写 K8s Deployment/Service → 通过 kubectl apply 部署 |
| 原理和工作流程 | 代码提交 → CI 构建 Docker 镜像 → 推送镜像仓库 → K8s 拉取新镜像 → 按 RollingUpdate 策略逐步替换旧 Pod → 就绪探针通过后接收流量 → 旧 Pod 终止 |
| 缺点 | 学习曲线陡峭（Docker + K8s）；镜像构建和推送需要时间；K8s 集群运维成本高 |

## 3.1 Feature Flags 实战（Unleash 接入）（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 Unleash 接入流程，包括初始化 Unleash 客户端、创建 Flag、配置用户分群、渐进式放量、A/B 测试变体 |
| 能做什么 | 快速实现企业级 Feature Flags 管理；支持渐进式放量（10% → 25% → 50% → 100%）；支持 A/B 测试 |
| 怎么用 | 安装 `unleash-proxy-client` → 初始化 UnleashClient → 封装 `useFeatureFlag` Hook → 在组件中使用 → 在 Unleash 管理后台配置放量策略 |
| 原理和工作流程 | Unleash SDK 通过代理服务器与 Unleash 服务端通信 → 定期拉取 Flag 配置 → 本地缓存 → 组件通过 Hook 获取 Flag 状态 → 变更通过 WebSocket 实时推送 |
| 缺点 | 需要部署 Unleash 服务端或使用云服务；代理服务器增加额外延迟；免费版功能有限 |

## 3.2 Nginx 灰度部署配置（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 Nginx 灰度部署配置，支持 Cookie 分流、Header 分流、比例分流三种方式，优先级 Cookie > Header > 比例 |
| 能做什么 | 在不修改应用代码的情况下实现多版本前端静态资源分流；支持精确用户控制和随机比例分配 |
| 怎么用 | 编写 Nginx 配置文件 → 定义 map 和 split_clients 规则 → 在不同 location 中根据版本变量选择 root 目录 → 配置 HTML 不缓存（确保灰度切换即时生效） |
| 原理和工作流程 | 三种分流方式组合 → 优先级判断 → 确定最终版本 → 路由到对应目录 → 返回 HTML → 浏览器加载对应版本的 JS/CSS |
| 缺点 | 分流逻辑在 Nginx 层，调试困难；配置变更需要 reload；不支持应用内功能级别的灰度 |

## 3.3 Docker + Nginx 前端部署（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 Docker 多阶段构建 + Nginx 配置模板 + 容器化部署方案，包含 Dockerfile、docker-entrypoint.sh、nginx.conf.template |
| 能做什么 | 实现前端应用的标准化构建和交付；支持运行时环境变量注入（API 地址等）；减小镜像体积 |

| 缺点 | 需要学习 Docker 基础知识；镜像构建时间较长；调试需要进入容器 |

## 3.4 Feature Flags 最佳实践（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Feature Flags 的最佳实践包括命名规范、过期清理机制、CI 检测、避免嵌套、依赖注入、测试覆盖 |
| 能做什么 | 避免 Flag 代码腐化；确保 Flag 可维护性；防止 Flag 组合爆炸导致的测试困难 |
| 怎么用 | 命名采用 `{domain}-{feature}-{action}` 格式 → 每个 Flag 设置过期时间 → CI 中检测过期 Flag → Flag 通过 props/context 传入组件 → 测试覆盖 Flag 的两种状态 |
| 原理和工作流程 | 创建 Flag 时设置 TTL → CI 流程中扫描过期 Flag → 过期 Flag 阻止合并 → 功能全量上线后清理 Flag 代码 → 测试确保 Flag 两种状态正常工作 |
| 缺点 | 需要团队严格执行规范；过期清理需要专人负责；CI 检测可能增加构建时间 |
