# 01-前端监控体系 - 导览

---

## 1.1 前端监控三大体系（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端监控分为错误监控（代码质量）、性能监控（用户体验）、业务监控（产品指标）三大体系，类比汽车仪表盘：故障灯、油耗表、导航地图 |
| 能做什么 | 错误监控发现和定位 JS 运行时错误、资源加载失败、Promise 异常；性能监控采集 LCP/INP/CLS 等 Core Web Vitals；业务监控统计 PV/UV、用户行为路径、API 成功率 |
| 怎么用 | 接入 Sentry 等第三方平台或自建 SDK，在应用入口初始化监控，配置错误捕获、性能观察、埋点追踪 |
| 原理和工作流程 | 数据采集层（ErrorCollector / PerfCollector / BusinessCollector）→ 数据处理层（清洗、去重、分组）→ 上报层（sendBeacon / fetch keepalive / img beacon）→ 可视化层（Dashboard） |
| 缺点 | 监控 SDK 引入额外性能开销；需要平衡采样率与数据完整性；跨域脚本错误信息不完整（Script error.） |

## 1.2 Sentry 核心能力（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Sentry 是开源错误监控平台，核心能力包括错误分组（fingerprint）、Sourcemap 还原、Breadcrumbs（面包屑）、Release 关联 |
| 能做什么 | 自动将相同根因的错误归为一组；还原压缩后的错误堆栈到源码位置；记录错误发生前的用户操作轨迹；关联错误与代码版本 |
| 怎么用 | 通过 `Sentry.init()` 初始化，配置 dsn、release、environment、sampleRate；通过 `captureException` 手动上报；通过 Webpack/Vite 插件自动上传 Sourcemap |
| 原理和工作流程 | SDK 初始化 → 注册全局错误监听 → 收集 Breadcrumbs → 错误发生时附加上下文 → 上报到 Sentry 服务端 → 服务端根据 Release 匹配 Sourcemap → 还原堆栈 → 按 fingerprint 分组 |
| 缺点 | 免费版有事件量限制；私有化部署运维成本高；Sourcemap 上传需要 CI/CD 集成；部分敏感数据需手动脱敏 |

| 维度 | 内容 |
|---|---|

## 2.1 错误采集原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端错误采集覆盖四种场景：JS 运行时错误（window.onerror）、Promise 未捕获异常（unhandledrejection）、console.error 劫持、资源加载错误（捕获阶段 error 事件） |
| 能做什么 | 全面捕获前端所有错误类型，附带 Breadcrumbs 还原用户操作轨迹，实现错误现场还原 |
| 怎么用 | 注册 `window.addEventListener('error', handler)` 捕获 JS 错误；注册 `window.addEventListener('unhandledrejection', handler)` 捕获 Promise 异常；劫持 `console.error` 记录控制台错误；在捕获阶段监听资源加载错误 |
| 原理和工作流程 | 注册全局事件监听 → 错误发生时触发回调 → 收集错误信息（message、stack、filename、lineno）→ 附加 Breadcrumbs → 调用上报器发送 |
| 缺点 | window.onerror 无法捕获语法错误和跨域脚本详细错误（需 crossorigin 属性）；资源加载错误不冒泡，必须在捕获阶段监听 |

## 2.2 性能采集原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 通过 PerformanceObserver API 监听 LCP（最大内容绘制）、INP（交互延迟）、CLS（布局偏移）等 Core Web Vitals；通过 performance.getEntriesByType 获取资源加载耗时 |
| 能做什么 | 量化用户体验（加载速度、交互响应、视觉稳定性）；识别性能瓶颈（慢资源、长任务）；建立性能基线和告警 |
| 怎么用 | 使用 `new PerformanceObserver(callback).observe({ type, buffered: true })` 监听各类性能指标；使用 `performance.getEntriesByType('resource')` 获取资源耗时分解 |
| 原理和工作流程 | 浏览器异步收集性能数据 → 放入 PerformanceObserver 缓冲区 → 回调函数被触发 → 提取指标值 → 与阈值对比 → 上报 |
| 缺点 | PerformanceObserver 需要浏览器支持（Chrome 52+）；INP 延迟计算需在页面卸载时进行；部分指标（如 TTI）需要 Lighthouse 等工具辅助 |

## 2.3 上报策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 上报策略包括三种上报方式（sendBeacon、fetch keepalive、img beacon）、采样率控制、本地 IndexedDB 缓冲、批量上报和重试机制 |
| 能做什么 | 确保监控数据可靠送达服务端；控制上报数据量避免服务端压力过大；网络不可用时数据不丢失 |
| 怎么用 | 页面卸载时使用 sendBeacon；正常运行时使用 fetch keepalive 批量上报；失败数据存入 IndexedDB 等待重试；通过采样率控制上报量 |
| 原理和工作流程 | 数据先入内存缓冲区 → 缓冲区满或定时触发 → 批量上报 → 失败则存入 IndexedDB → 恢复时重新上报 → 页面卸载时强制 flush |
| 缺点 | sendBeacon 不返回响应，无法确认服务端是否成功处理；fetch keepalive 有 64KB 限制；img beacon 受 URL 长度限制 |

## 2.4 Sourcemap 三步曲（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Sourcemap 三步曲：构建时生成 Sourcemap 文件 → 上传到监控平台 → 服务端根据错误堆栈自动还原源码位置 |
| 能做什么 | 将生产环境压缩混淆后的错误堆栈还原为可读的源码位置，实现精准的错误定位 |
| 怎么用 | 构建配置 `devtool: 'hidden-source-map'` → 通过 Sentry Webpack/Vite Plugin 自动上传 → 删除 .map 文件 → 错误发生时服务端自动匹配还原 |
| 原理和工作流程 | 构建工具根据源码生成映射关系 → 上传到 Sentry 等平台 → 收到错误时根据 release 版本查找对应 Sourcemap → 解析行列号映射 → 返回原始源码堆栈 |
| 缺点 | 构建时间略有增加；Sourcemap 泄露到生产环境是严重安全隐患；需要 CI/CD 集成上传流程 |

## 补充：埋点体系（数据采集）

### 补1 埋点的三种方式与选型

| 维度 | 内容 |
|------|------|
| 是什么 | 按"谁来定义采集点"分为三类：代码埋点（开发者在代码中显式调用）、可视化埋点（运营圈选元素生成配置，运行时按配置匹配）、无痕埋点（SDK 自动采集全部行为） |
| 能做什么 | 代码埋点保证核心链路语义精确、参数可控；可视化埋点让运营无需发版即可加埋点；无痕埋点零开发成本、支持历史行为回溯与探索性分析 |
| 怎么用 | 分层组合：核心转化链路（下单、支付）用代码埋点；运营活动页用可视化埋点；全局行为用无痕埋点做路径分析。三者共用同一套数据模型与上报通道 |
| 原理和工作流程 | 可视化埋点把"代码调用点"外置为配置：圈选态生成元素路径与稳定特征并保存，运行态用同一套算法匹配元素后绑定监听；无痕埋点用全局监听采集所有点击与 PV，由数据侧做元素路径到业务语义的映射 |
| 缺点 | 代码埋点响应慢、埋点散落在业务代码中；可视化埋点依赖元素路径稳定性（动态 class、列表索引、DOM 改版会导致配置静默失效）；无痕埋点数据量大且缺业务语义；三者用不同数据模型会导致无法统一分析 |

### 补2 埋点数据模型设计

| 维度 | 内容 |
|------|------|
| 是什么 | 事件模型遵循"1 个事件 + N 个业务属性 + 公共参数"：事件标识（`event_id` / `event` / `event_type`）、业务 `properties`、SDK 统一注入的 `common`、以及 `timestamp` 与时区 |
| 能做什么 | 保证所有事件口径一致、任意维度可切分；事件名枚举化后数据侧可稳定聚合；公共参数独立后可按版本、平台、实验分组做全局对比 |
| 怎么用 | 事件名用 `{对象}_{动作}` 蛇形命名并维护枚举；属性值只允许标量，嵌套对象与数组在 SDK 层扁平化；公共参数在每次构造事件时实时读取（不是初始化快照）；`event_id` 用 UUID 生成用于幂等 |
| 原理和工作流程 | 业务调用 `track` → EventBuilder 合并实时上下文（页面路径、视口、实验分组）与静态公共参数 → 扁平化并校验类型 → 采样 → 入队上报；数据侧按事件表或对象-动作表建模 |
| 缺点 | 事件表模型随属性增长会膨胀、查询需大量 `CASE WHEN`；对象-动作模型建模成本高、变更需评审；属性扁平化会丢失嵌套结构语义；公共参数实时读取带来少量运行时开销 |

### 补3 曝光埋点

| 维度 | 内容 |
|------|------|
| 是什么 | 采集元素在视口中"真实可见"的事件，是推荐、广告、列表、活动位等指标的分母；判定三要素为可见比例、停留时长、去重策略 |
| 能做什么 | 准确衡量内容消费（曝光量、曝光转化率）；避免"渲染即曝光"导致的分母虚高；首屏曝光由 IntersectionObserver 的初始回调自然覆盖 |
| 怎么用 | `new IntersectionObserver(cb, { threshold: [0, 0.5], rootMargin: '0px' })`；进入可见时启动 `setTimeout` 计时，离开时 `clearTimeout`；达到停留阈值后上报并 `unobserve` 去重 |
| 原理和工作流程 | 交叉状态由浏览器在合成阶段计算，回调异步触发；`threshold` 必须包含 0，否则元素离开视口时不回调、计时器无法清理；`once` 去重用 WeakSet + unobserve，虚拟列表场景需改用内容 ID 去重 |
| 缺点 | 不检测遮挡（被覆盖的元素仍可能报告相交）；ratio 阈值对"高于视口的列表项"不友好；虚拟滚动复用 DOM 节点会让基于节点的去重失效；rootMargin 设正的大值会造成曝光虚高 |

### 补4 点击埋点

| 维度 | 内容 |
|------|------|
| 是什么 | 采集用户点击行为，工程上用"事件委托 + 元素标识"实现：在 `document` 捕获阶段监听一次，通过 `closest('[data-track]')` 定位元素并上报 |
| 能做什么 | 一次监听覆盖全站（含动态渲染元素）；避免业务组件的 `stopPropagation` 导致漏埋；`data-track` 声明式标识让埋点与实现解耦，并支持自动化校验 |
| 怎么用 | 在 `document` 上 `addEventListener('click', handler, true)`；元素上写 `data-track="{模块}_{对象}_{动作}"`，参数用 `data-track-params` 传 JSON；解析失败时降级为无参数，不影响业务点击 |
| 原理和工作流程 | 捕获阶段回调早于业务冒泡阶段的 `stopPropagation`；`closest` 沿祖先链向上查找，支持"点图标但标识在按钮上"；A/B 实验需保证埋点携带分流信息（SDK 就绪后再放行上报） |
| 缺点 | 事件委托拿不到闭包变量，参数只能通过 `data-*` 传递；`data-track` 命名重复会导致数据侧无法区分来源；埋点回调若做同步耗时操作会影响点击响应；捕获阶段监听会先于业务逻辑执行，需避免副作用 |

### 补5 自定义埋点（PV/UV、停留时长、性能埋点）

| 维度 | 内容 |
|------|------|
| 是什么 | 业务语义驱动的采集：PV（页面浏览）、UV（访客去重）、页面停留时长、性能埋点（性能指标与业务转化联合上报） |
| 能做什么 | 量化流量与参与度；把性能指标与转化率关联，回答"慢 1 秒损失多少转化"；按会话切分统计口径 |
| 怎么用 | SPA 劫持 `pushState` + 监听 `popstate` / `hashchange` 统计 PV（`replaceState` 不计）；UV 用持久化 `anonymous_id` 由服务端去重；停留时长累加 `visibilitychange` 的可见时长并用 `pagehide` 兜底；性能埋点把 CWV 作为业务事件属性上报 |
| 原理和工作流程 | 路由变化触发 PV 上报并做同路径去重 → 可见时开始计时、隐藏时累加上报 → 匿名 ID 首访生成并持久化（cookie 365 天 / localStorage）→ 登录后回填 `user_id` 由服务端做 ID-Mapping |
| 缺点 | SPA 路由劫持需覆盖所有入口（漏掉 `popstate` 会低估流量）；墙钟时间算时长会被后台标签页污染；匿名 ID 存 `sessionStorage` 会导致 UV 高估；性能与业务联合上报会增加事件体积 |

### 补6 上报时机与批量上报策略

| 维度 | 内容 |
|------|------|
| 是什么 | 事件从产生到送达之间的缓冲策略：定量触发（队列满）、定时触发、关键事件立即触发、生命周期触发（页面隐藏/卸载） |
| 能做什么 | 用批量上报把请求数降到约"事件数 / batchSize"；关键事件不因缓冲丢失；页面离开时强制 flush 保证数据完整；公共参数上提到批次级可压缩 payload |
| 怎么用 | `batchSize` 约 10、`flushInterval` 约 5s、`maxQueueSize` 约 200；队列超限丢最旧并上报丢弃计数；`visibilitychange(hidden)` 与 `pagehide` 时用 `sendBeacon` 强制 flush；失败落 IndexedDB 重试 |
| 原理和工作流程 | 事件入内存队列 → 满足任一触发条件即 splice 出批次 → 卸载场景走 `sendBeacon`，运行期走 `fetch keepalive` → 失败进入重试（指数退避）或持久化；后台标签页定时器被节流，因此不能依赖定时器保证时效 |
| 缺点 | 批量上报引入 `flushInterval` 级延迟；整批失败影响面更大；队列无上限会内存泄漏；重试无上限会造成重试风暴；丢弃策略与"不丢关键数据"的目标存在冲突，需要分级队列 |

### 补7 埋点数据的质量保障

| 维度 | 内容 |
|------|------|
| 是什么 | 针对三类质量问题（漏埋、重复埋、参数错误）建立"开发期 → 测试期 → 线上期"的三层防线，并把埋点配置纳入版本管理形成闭环 |
| 能做什么 | 在开发阶段就拦住非法事件与参数；在测试阶段自动发现漏埋与配置漂移；在线上通过量级告警与业务对账快速发现数据异常 |
| 怎么用 | 开发期用 schema 校验（必填/类型/枚举）+ 单测断言；测试期在 E2E 中拦截上报请求断言事件已发出，并把代码中的 `data-track` 与配置表做 diff；线上期做同比环比突降告警、支付成功数与订单库对账、参数健康度（空值率、枚举分布）监控 |
| 原理和工作流程 | 漏埋靠"声明式标识 + 捕获阶段监听 + E2E 断言 + 配置 diff"；重复埋靠 `event_id` 幂等 + SDK 单例 + 路由去重；参数错误靠 schema 校验 + 公共参数实时读取 + 数据侧对账 |
| 缺点 | 埋点校验会增加开发与构建成本；配置 diff 对动态拼接的事件名无能为力；线上告警需要与业务指标交叉验证，否则会把"流量下降"误判为"埋点丢失"；治理依赖流程执行，缺乏强制力时容易退化 |

### 补8 埋点 SDK 的设计要点

| 维度 | 内容 |
|------|------|
| 是什么 | 运行在业务应用中的"数据采集中间件"，分四层：接入层 API、可插拔采集插件层、处理层（组装/校验/脱敏/去重）、传输层（队列/批量/离线补发） |
| 能做什么 | 对业务提供稳定的 `track` / `trackExposure` / `setUser` 接口；插件化采集（PV、点击、曝光、性能、错误）可按需启用并支持 Tree-shaking；SDK 内部异常不影响业务 |
| 怎么用 | `TrackSDK.init()` 单例初始化 → `use(plugin)` 注册采集插件 → 就绪队列放行初始化期间的事件 → 公共参数由 SDK 统一注入 → 采样、脱敏、校验后入队上报 |
| 原理和工作流程 | 初始化时同步注册监听、异步建连；未就绪事件先入队等就绪后 flush（保证首屏事件与实验分流信息对齐）；脱敏用白名单/黑名单过滤属性；`anonymous_id` 持久化 + 登录后回填 `user_id` 供服务端 ID-Mapping |
| 缺点 | SDK 体积与首屏性能存在张力（需插件化与空闲回调控制）；微前端多子应用各自初始化会导致重复上报，需主应用统一初始化；脱敏黑名单易漏（新增敏感字段忘记加名单）；SDK 自身也需要可观测性（丢弃数、失败数、队列长度） |
