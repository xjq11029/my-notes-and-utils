## 前端监控常见错误

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---|---|---|---|
| Sourcemap 文件泄露到生产环境 CDN，任何人都能查看源码 | 构建时未删除 .map 文件，或 CDN 部署脚本未过滤 .map 文件 | 使用 `hidden-source-map`；构建后删除 .map 文件；通过 Sentry CLI 或 Webpack 插件自动上传后删除 | [01-前端监控体系-导览 - 2.4](./01-前端监控体系-导览.md) |
| 监控 SDK 本身导致页面性能下降，出现卡顿、白屏 | SDK 同步加载阻塞渲染；采集逻辑在主线程执行大量计算；上报请求过多 | SDK 异步加载（async/defer）；使用 requestIdleCallback 执行非关键采集；控制采样率（性能 10%、行为 5%）；批量上报 | [01-前端监控体系-导览 - 3.2](./01-前端监控体系-导览.md) |
| 错误告警风暴，一个错误重复告警数百次 | 相同错误没有有效去重；告警阈值设置不合理；错误分组规则不完善 | Sentry 配置自定义 fingerprint 合并同类错误；设置告警冷却时间（如 5 分钟内同一错误不重复告警）；按影响用户数而非错误次数设置告警阈值 | [01-前端监控体系-导览 - 3.1](./01-前端监控体系-导览.md) |
| 跨域脚本错误仅显示 "Script error."，无法获取详细堆栈 | 第三方脚本未配置 CORS 头，且 script 标签未添加 crossorigin 属性 | 为 script 标签添加 `crossorigin="anonymous"`；CDN 配置 `Access-Control-Allow-Origin` 响应头 | [01-前端监控体系-导览 - 2.1](./01-前端监控体系-导览.md) |
| 白屏检测误报，正常页面被判为白屏 | 采样点阈值设置过高；未考虑 Canvas/WebGL 渲染的页面；SPA 异步加载阶段被判为白屏 | 三层判断机制（文本内容 + 媒体元素 + 采样点）；白屏检测延迟启动（等待异步加载完成）；Canvas 页面特殊处理 | [01-前端监控体系-导览 - 3.4](./01-前端监控体系-导览.md) |

## 埋点体系常见错误

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---|---|---|---|
| SPA 路由切换后 `page_path` 永远是首页 | 公共参数在 SDK 初始化时"快照"一次，没有随路由更新 | 每次构造事件时实时读取公共参数 | [01-前端监控体系-导览 - 2.5](./01-前端监控体系-导览.md) |
| 数据仓库聚合时出现"同值不同键" | 属性值类型不统一（有时 `sku_id: 123`，有时 `'123'`） | 在事件模型层统一字段类型，并在采集时做类型校验 | [01-前端监控体系-导览 - 2.5](./01-前端监控体系-导览.md) |
| 转化漏斗前半段数据缺失 | 用户标识只在登录后采集，未登录行为没有 `anonymous_id` | 首访即生成并持久化 `anonymous_id`，登录后再做 ID 关联 | [01-前端监控体系-导览 - 2.5](./01-前端监控体系-导览.md) |
| 埋点参数里带了手机号、token，合规风险与上报体膨胀 | 未对上报参数做脱敏与体积控制 | 白名单采集关键字段；敏感字段脱敏后再上报 | [01-前端监控体系-导览 - 2.5](./01-前端监控体系-导览.md) |
| 元素离开视口时不再回调，`setTimeout` 残留，用户滚回来重复计入停留时长 | `threshold: 0.5` 却没有在数组里加 `0` | threshold 数组补上 `0`，保证离开视口也能收到回调 | [01-前端监控体系-导览 - 3.4](./01-前端监控体系-导览.md) |
| 虚拟列表中元素被复用后新内容永远不曝光 | 用 `once = true` 的 `unobserve` 去重，但虚拟滚动复用 DOM 节点，`WeakSet` 里已有记录 | 去重键设为"内容 ID"而非 DOM 节点 | [01-前端监控体系-导览 - 3.4](./01-前端监控体系-导览.md) |
| 曝光量整体虚高 | `rootMargin` 给了正的大值（如 `2000px`），屏幕外元素也被判为曝光 | rootMargin 按业务口径设置，避免过度外扩 | [01-前端监控体系-导览 - 3.4](./01-前端监控体系-导览.md) |
| 被遮挡的元素仍被判为曝光 | `IntersectionObserver` 不检测遮挡 | 配合 `document.elementFromPoint` 或业务兜底校验 | [01-前端监控体系-导览 - 3.4](./01-前端监控体系-导览.md) |
| 业务组件的 `stopPropagation` 导致埋点静默丢失 | 在冒泡阶段监听 `document` | 用捕获阶段监听：`addEventListener('click', handler, true)` | [01-前端监控体系-导览 - 4.4](./01-前端监控体系-导览.md) |
| 点到按钮内的图标或文字节点时读不到 `data-track` | 直接用 `e.target` 读标识 | 用 `e.target.closest('[data-track]')` 向上查找 | [01-前端监控体系-导览 - 4.4](./01-前端监控体系-导览.md) |
| 点击密集的列表页出现掉帧 | 埋点回调里做同步耗时操作（大对象 JSON 序列化、写 localStorage） | 回调中只入队，序列化与上报放到 `requestIdleCallback` | [01-前端监控体系-导览 - 4.4](./01-前端监控体系-导览.md) |
| 数据侧无法区分 `data-track` 来源 | 多个模块用了同一个标识，命名重复 | 标识里带模块前缀并做唯一性校验 | [01-前端监控体系-导览 - 4.4](./01-前端监控体系-导览.md) |
| 浏览器前进/后退不产生 PV，流量数据偏低 | 只监听了 `pushState` 而漏掉 `popstate` | 同时监听 `pushState`、`replaceState`、`popstate`、`hashchange` | [01-前端监控体系-导览 - 5.4](./01-前端监控体系-导览.md) |
| 停留时长数据被严重污染 | 用墙钟时间计算停留时长，用户把页面挂在后台一整天 | 基于 `visibilitychange` 累计真实可见时长 | [01-前端监控体系-导览 - 5.4](./01-前端监控体系-导览.md) |
| UV 被严重高估 | 匿名 ID 存在 `sessionStorage` 里，关闭标签页即失效 | 匿名 ID 持久化到 Cookie 或 localStorage，设置合理有效期 | [01-前端监控体系-导览 - 5.4](./01-前端监控体系-导览.md) |
| 首屏 PV 丢失 | 首次 PV 在 SDK 初始化之前触发（路由框架先于 SDK 加载） | SDK 尽早同步执行，或由路由框架主动上报首屏 | [01-前端监控体系-导览 - 5.4](./01-前端监控体系-导览.md) |
| 移动端数据静默丢失 | 只在 `beforeunload`/`unload` 里 flush，移动端这两个事件经常不触发 | 改用 `visibilitychange(hidden)` + `pagehide` | [01-前端监控体系-导览 - 6.4](./01-前端监控体系-导览.md) |
| 卸载时上报的请求被浏览器取消 | 用 `fetch`（不带 `keepalive`）在卸载时上报 | 使用 `navigator.sendBeacon` 或 `fetch(url, { keepalive: true })` | [01-前端监控体系-导览 - 6.4](./01-前端监控体系-导览.md) |
| 后台上报延迟远超预期 | 后台标签页定时器被节流（Chrome 后台 `setInterval` 最低 1 分钟） | 后台依赖生命周期事件触发上报，而不是依赖定时器 | [01-前端监控体系-导览 - 6.4](./01-前端监控体系-导览.md) |
| 用户长时间离线后内存持续增长，最终 OOM 或卡死 | 上报队列无上限 | 设置队列条数上限与过期时间，超限丢最旧并上报丢弃计数 | [01-前端监控体系-导览 - 6.4](./01-前端监控体系-导览.md) |
| 服务端故障时客户端形成重试风暴，加剧故障 | 重试没有上限和退避 | 重试设置上限 + 指数退避 + 随机抖动 | [01-前端监控体系-导览 - 6.4](./01-前端监控体系-导览.md) |
| 只在数据侧做去重，前端仍上报大量重复数据 | 重复上报白白消耗流量与服务端资源 | 前端先做会话级/内容级去重，数据侧再做兜底幂等 | [01-前端监控体系-导览 - 7.4](./01-前端监控体系-导览.md) |
| 埋点问题在上线后才暴露 | 埋点校验只在开发环境开启，测试/预发环境未开 | 埋点校验在测试、预发、生产都开启，E2E 中断言埋点请求 | [01-前端监控体系-导览 - 7.4](./01-前端监控体系-导览.md) |
| 数据量下降时误判为"埋点丢失" | 实际是上游业务流量下降 | 同时看业务指标做交叉验证 | [01-前端监控体系-导览 - 7.4](./01-前端监控体系-导览.md) |
| 埋点配置漂移无人知晓 | 埋点配置散落在文档里而不进版本库 | 埋点配置进版本库，与代码一起评审和 diff 校验 | [01-前端监控体系-导览 - 7.4](./01-前端监控体系-导览.md) |
| SDK 同步执行耗时初始化阻塞首屏 | 初始化时同步读 cookie、建 IndexedDB 连接 | 拆分为同步注册 + 异步就绪，重初始化懒加载 | [01-前端监控体系-导览 - 8.4](./01-前端监控体系-导览.md) |
| 数据侧无法从采样数据还原真实量级 | 采样率只在前端生效且不上报 | 上报采样率，数据侧按采样率还原总量 | [01-前端监控体系-导览 - 8.4](./01-前端监控体系-导览.md) |
| 新增敏感字段时忘记加脱敏名单 | 脱敏只做黑名单 | 改为白名单采集关键字段，新增字段默认不上报 | [01-前端监控体系-导览 - 8.4](./01-前端监控体系-导览.md) |
| 埋点异常打断业务 | SDK 直接 `throw`，影响主流程 | 埋点必须"永远不打断业务"，所有异常在 SDK 内部捕获并降级 | [01-前端监控体系-导览 - 8.4](./01-前端监控体系-导览.md) |
| 微前端下同一行为被多次上报 | 多个子应用各自初始化 SDK | 主应用统一初始化，或做跨应用单例 | [01-前端监控体系-导览 - 8.4](./01-前端监控体系-导览.md) |

## 灰度发布与部署策略常见错误

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---|---|---|---|
| 灰度发布时新旧版本共享同一数据库，导致数据不一致或读写冲突 | 数据库 schema 变更未考虑向后兼容性；新旧版本 API 返回格式不一致 | 数据库 schema 变更必须向后兼容（新增字段而非修改/删除字段）；API 版本化（v1/v2）；灰度期间使用双写策略 | [02-灰度发布与部署策略-导览 - 1.2](./02-灰度发布与部署策略-导览.md) |
| Feature Flag 长期不清理，导致代码中遍布大量条件判断，逻辑难以维护 | 发布后未及时清理 Flag 代码；未设置 Flag 过期时间 | 每个 Flag 设置过期时间（如 30 天）；CI 流程中检测过期 Flag 并阻止合并；功能全量上线后立即清理 Flag 代码 | [02-灰度发布与部署策略-导览 - 3.4](./02-灰度发布与部署策略-导览.md) |
| 滚动更新时新旧版本混用，用户请求被路由到不同版本导致功能异常 | 未配置会话亲和性（Session Affinity）；静态资源版本不一致（旧 HTML 加载新 JS） | 配置 Nginx `ip_hash` 或使用 Cookie 会话保持；静态资源使用内容哈希命名（`app.a1b2c3d4.js`）；确保 HTML 和 JS/CSS 版本匹配 | [02-灰度发布与部署策略-导览 - 2.4](./02-灰度发布与部署策略-导览.md) |
| Docker 镜像体积过大（> 500MB），部署和拉取缓慢 | 构建阶段和运行时阶段未分离；node_modules 包含在运行时镜像中 | 使用多阶段构建（Node 构建 + Nginx 运行时）；仅保留 dist 构建产物；使用 Alpine 基础镜像 | [02-灰度发布与部署策略-导览 - 3.3](./02-灰度发布与部署策略-导览.md) |

## 可观测性与故障排查常见错误

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---|---|---|---|
| 告警太多导致"狼来了"效应，团队对告警不再敏感 | 告警阈值设置过低；告警无冷却时间；无分级告警 | 告警阈值基于统计学（如 P99 而非平均值）；每个规则设置冷却时间；分级告警（critical 即时通知，warning 仅发邮件，info 汇总日报） | [03-可观测性与故障排查-导览 - 2.4](./03-可观测性与故障排查-导览.md) |
| Session Replay 录制了敏感信息（密码、身份证号、银行卡号等），导致隐私合规风险 | 未开启脱敏配置；录制范围过大 | 配置 `maskAllText: true` 脱敏所有文本；`maskAllInputs: true` 脱敏所有输入框；`blockAllMedia: true` 阻止媒体录制；排除敏感页面（如支付页、个人信息页） | [03-可观测性与故障排查-导览 - 1.3](./03-可观测性与故障排查-导览.md) |
| 日志中包含了完整的用户 token 和密码，被泄露到第三方监控平台 | console 劫持时未脱敏；日志上报时未过滤敏感字段 | 实现数据脱敏函数，过滤 password、token、secret 等敏感字段；日志上报前进行脱敏检查；敏感数据使用 `***[REDACTED]***` 替换 | [03-可观测性与故障排查-导览 - 2.1](./03-可观测性与故障排查-导览.md) |
| 链路追踪数据量过大导致存储成本飙升 | 全量采样追踪数据；未设置合理的采样率 | 生产环境 tracesSampleRate 设置为 0.1（10%）；对错误请求 100% 采样；设置数据保留策略（如 7 天） | [03-可观测性与故障排查-导览 - 2.3](./03-可观测性与故障排查-导览.md) |

## A/B 实验与上报可靠性常见错误

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---|---|---|---|
| 把"灰度开关"当"实验平台"用，只能得到"没坏"得不到"更好" | 没有对照组与统计检验 | 明确对照组、主要指标与统计检验方法后再上线 | [05-AB实验与上报可靠性-导览 - 1.6](./05-AB实验与上报可靠性-导览.md) |
| 上线后在海量指标里挑显著的那个，得到假阳性结论 | 实验没有提前定义主要指标（OEC） | 启动前明确 OEC + 护栏指标 + 最小样本量；多指标做 Bonferroni / FDR 校正 | [05-AB实验与上报可靠性-导览 - 1.6](./05-AB实验与上报可靠性-导览.md) |
| 分流不稳定，实验数据完全不可信 | 用 `Math.random()` 或时间戳参与分桶 | 用纯函数哈希分桶：`hash(unit + salt) % BUCKET_TOTAL` | [05-AB实验与上报可靠性-导览 - 2.1.5](./05-AB实验与上报可靠性-导览.md) |
| 同一未登录用户被分到不同组 | 未登录用户没有稳定标识，每次访问生成新 ID | 首访即持久化 `anonymous_id` 作为分流单元 | [05-AB实验与上报可靠性-导览 - 2.1.5](./05-AB实验与上报可靠性-导览.md) |
| 实验中途改 salt 或桶总数后历史数据口径断裂 | 全量重分桶，历史数据与新增数据不可比 | 实验运行期间固定 salt 与桶总数，需要变更就新建实验 | [05-AB实验与上报可靠性-导览 - 2.1.5](./05-AB实验与上报可靠性-导览.md) |
| 两个改同一按钮的实验结论互相污染却无法察觉 | 把互相影响的实验放在了不同层 | 互相影响的实验放同一层做互斥，独立实验放不同层 | [05-AB实验与上报可靠性-导览 - 2.1.5](./05-AB实验与上报可靠性-导览.md) |
| 曝光重复上报（StrictMode 双渲染、并发渲染重放） | 在 React 组件体内调用曝光上报 | 曝光放在渲染提交后（`useEffect`），并做会话内去重 | [05-AB实验与上报可靠性-导览 - 2.2.4](./05-AB实验与上报可靠性-导览.md) |
| 出现"实验开关回跳" | 配置刷新后未比较版本号，旧响应覆盖了新配置 | 用版本号/时间戳比较，只接受更新的配置 | [05-AB实验与上报可靠性-导览 - 2.2.4](./05-AB实验与上报可靠性-导览.md) |
| 配置服务故障时全量用户看到未验证方案 | 兜底值用了 `treatment` 而非 `control` | 兜底必须回退到 `control`，保证故障时行为可控 | [05-AB实验与上报可靠性-导览 - 2.2.4](./05-AB实验与上报可靠性-导览.md) |
| 页面关闭后上报数据大量丢失 | 只用 `beforeunload` 上报且用普通 `fetch`，请求被取消 | 用 `visibilitychange(hidden)` + `pagehide`，配合 `sendBeacon` / `fetch keepalive`，失败落 IndexedDB 补发 | [05-AB实验与上报可靠性-导览 - 2.3.4](./05-AB实验与上报可靠性-导览.md) |
| 在 `hidden` 回调里做同步耗时操作，用户感知卡顿 | 大对象序列化、等待 IndexedDB 事务都在卸载回调里同步执行 | 卸载回调里只做轻量的入队与投递 | [05-AB实验与上报可靠性-导览 - 2.3.4](./05-AB实验与上报可靠性-导览.md) |
