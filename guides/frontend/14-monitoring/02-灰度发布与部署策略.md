## 一、核心概念

### 1.1 Feature Flags 四类模型

Feature Flags（功能开关/特性标志）是一种通过配置动态控制功能开启或关闭的机制，无需重新部署代码。它用汽车功能开关做类比最为直观：

| 开关类型 | 汽车类比 | 前端场景 | 典型生命周期 |
|---|---|---|---|
| **Release Toggles**（发布开关） | 未发布的新功能用开关隐藏，测试完成后打开 | 新功能开发完成但暂不上线，通过开关控制 | 数天到数周，功能上线后清理 |
| **Experiment Toggles**（实验开关） | A/B 测试对比不同版本的仪表盘设计 | 两套 UI 方案随机分配给不同用户组，对比转化率 | 数周到数月，实验结束后清理 |
| **Ops Toggles**（运维开关） | 紧急情况下关闭非核心功能（如空调）以保护引擎 | 大促期间关闭非核心功能（如动画、推荐）保障性能 | 短期，事件结束后恢复 |
| **Permission Toggles**（权限开关） | VIP 用户专属功能（如座椅加热） | 付费用户可见高级功能，免费用户隐藏 | 长期，需纳入产品设计 |

```typescript
// Feature Flags 四类模型示例
const featureFlags = {
  // Release Toggle：新功能已完成但暂不公开
  'new-payment-flow': {
    type: 'release',
    enabled: false,         // 默认为 false，功能验证通过后改为 true
    rollout: 0,             // 0% 放量
  },

  // Experiment Toggle：A/B 测试
  'new-checkout-ui': {
    type: 'experiment',
    enabled: true,
    // 50% 用户看到新 UI，50% 看到旧 UI
    variants: ['control', 'variant-b'],
    trafficAllocation: { control: 50, 'variant-b': 50 },
  },

  // Ops Toggle：运维开关
  'heavy-animations': {
    type: 'ops',
    enabled: true,          // 正常运行
    // 大促期间手动关闭此开关
  },

  // Permission Toggle：权限开关
  'export-excel': {
    type: 'permission',
    enabled: true,
    // 仅 VIP 用户可见
    requiredPlan: 'premium',
  },
};
```

### 1.2 三种部署策略

```
┌─────────────────────────────────────────────────────────────┐
│                      三种部署策略对比                         │
├──────────────┬──────────────────┬──────────────────────────┤
│  灰度发布     │    蓝绿部署       │     滚动更新              │
│  (Canary)    │  (Blue-Green)    │   (Rolling Update)       │
├──────────────┼──────────────────┼──────────────────────────┤
│              │                  │                          │
│  ┌─新版本─┐  │  ┌─蓝环境(旧)─┐  │  ┌实例1─┐ ┌实例1─┐      │
│  │ 10%流量 │  │  │ 100%流量   │  │  │旧版本│→│新版本│      │
│  └────────┘  │  └───────────┘  │  └──────┘ └──────┘      │
│  ┌─旧版本─┐  │        ↓切换     │  ┌实例2─┐ ┌实例2─┐      │
│  │ 90%流量 │  │  ┌─绿环境(新)─┐  │  │旧版本│→│新版本│      │
│  └────────┘  │  │ 100%流量   │  │  └──────┘ └──────┘      │
│              │  └───────────┘  │  ┌实例3─┐ ┌实例3─┐      │
│  逐步放量    │  瞬时切换        │  │旧版本│→│新版本│      │
│  风险可控    │  秒级回滚        │  └──────┘ └──────┘      │
│  观察期长    │  资源翻倍        │  逐个替换                │
└──────────────┴──────────────────┴──────────────────────────┘
```

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| **灰度发布** | 新版本先部署到少量实例，分配小比例流量，验证无问题后逐步放量 | 风险可控、可观测、逐步验证 | 需要流量路由能力、观察期长 | 重大功能上线、高风险变更 |
| **蓝绿部署** | 维护两套完全相同的环境（蓝/绿），新版本部署到闲置环境，切换流量瞬间完成 | 秒级回滚、无停机时间 | 资源成本翻倍、数据库兼容性挑战 | 对可用性要求极高的服务 |
| **滚动更新** | 逐个替换运行实例，每个实例替换后验证通过再替换下一个 | 资源利用率高、无需额外环境 | 回滚速度慢、短暂存在新旧版本混用 | 常规版本迭代、K8s 集群部署 |

## 二、底层原理

### 2.1 Nginx 层灰度

Nginx 通过 `map` 指令根据请求中的 Cookie、Header 等条件将流量分发到不同版本的前端静态资源。

```nginx
# ========== Nginx 灰度配置 ==========

# 第一步：定义灰度规则 map
# 根据 Cookie 中的 canary 字段决定路由到哪个版本
map $cookie_canary $app_version_cookie {
    default     "stable";       # 默认走稳定版
    "v2"        "canary";       # cookie canary=v2 走灰度版
    "beta"      "canary";       # cookie canary=beta 走灰度版
}

# 也可以根据 Header 分流
map $http_x_canary $app_version_header {
    default     "stable";
    "true"      "canary";
}

# 合并：Cookie 或 Header 任一匹配则走灰度
# 注意：Nginx 不允许两个 map 定义同一个变量名，需用中间变量合并
map "$app_version_cookie$app_version_header" $app_version {
    default         "stable";
    ~canary         "canary";
}

# 第二步：根据版本变量路由到不同的静态资源目录
server {
    listen 80;
    server_name example.com;

    # 灰度版静态资源
    location / {
        # 根据 $app_version 变量选择不同的 root
        # 注意：Nginx 中 if 在 location 块内是"evil"反模式，仅用于 set 指令是安全的。切勿在 if 块内使用 proxy_pass 等指令。
        set $root_path /usr/share/nginx/html/stable;
        if ($app_version = "canary") {
            set $root_path /usr/share/nginx/html/canary;
        }
        root $root_path;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # 灰度版 API 代理
    location /api/ {
        set $backend "stable-backend:3000";
        if ($app_version = "canary") {
            set $backend "canary-backend:3000";
        }
        proxy_pass http://$backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

# 第三步：按比例灰度（使用 split_clients）
# 将 10% 的流量路由到灰度版
split_clients "${remote_addr}${http_user_agent}" $canary_split {
    10%     "canary";    # 10% 流量走灰度版
    *       "stable";    # 其余走稳定版
}

# 按比例灰度的完整配置
server {
    listen 80;
    server_name example.com;

    # 使用 split_clients 按 IP + UA 哈希分配流量
    # 同一用户始终被分配到同一版本（一致性哈希）
    set $version "stable";
    if ($canary_split = "canary") {
        set $version "canary";
    }

    location / {
        root /usr/share/nginx/html/$version;
        index index.html;
        try_files $uri $uri/ /index.html;
    }
}
```

### 2.2 Feature Flags 灰度

Feature Flags 在服务端通过规则引擎和用户分群实现精细化的功能控制。

```typescript
// ========== Feature Flags 服务端规则引擎 ==========

// 用户分群策略
interface UserContext {
  userId: string;
  email?: string;
  region?: string;       // 地区：cn / us / eu
  device?: string;       // 设备：mobile / desktop / tablet
  plan?: string;         // 套餐：free / pro / enterprise
  customAttributes?: Record<string, string>;
}

// Flag 策略定义
interface FlagStrategy {
  name: string;
  // 放量策略
  rollout: {
    percentage: number;  // 放量比例 0-100
    // 用户分群条件
    constraints?: {
      regions?: string[];
      devices?: string[];
      plans?: string[];
      userIds?: string[];        // 白名单用户
      customRules?: ((user: UserContext) => boolean)[];
    };
  };
  // 变体（用于 A/B 测试）
  variants?: { name: string; weight: number }[];
}

// Feature Flag 引擎
class FeatureFlagEngine {
  private flags: Map<string, FlagStrategy> = new Map();

  registerFlag(name: string, strategy: FlagStrategy): void {
    this.flags.set(name, strategy);
  }

  // 核心算法：判断用户是否在放量范围内
  isEnabled(flagName: string, user: UserContext): boolean {
    const strategy = this.flags.get(flagName);
    if (!strategy) return false;

    const { rollout } = strategy;

    // 1. 检查白名单
    if (rollout.constraints?.userIds?.includes(user.userId)) {
      return true;
    }

    // 2. 检查用户分群条件
    if (rollout.constraints) {
      const { regions, devices, plans, customRules } = rollout.constraints;
      if (regions && !regions.includes(user.region || '')) return false;
      if (devices && !devices.includes(user.device || '')) return false;
      if (plans && !plans.includes(user.plan || '')) return false;
      if (customRules && !customRules.every(rule => rule(user))) return false;
    }

    // 3. 按比例放量（基于用户 ID 哈希，保证一致性）
    if (rollout.percentage < 100) {
      const hash = this.hashUserId(user.userId);
      // hash 值在 0-99 之间，小于 percentage 则在放量范围内
      return (hash % 100) < rollout.percentage;
    }

    return true;
  }

  // 获取 A/B 测试变体
  getVariant(flagName: string, user: UserContext): string {
    const strategy = this.flags.get(flagName);
    if (!strategy || !strategy.variants) return 'control';

    const hash = this.hashUserId(user.userId + flagName);
    let cumulative = 0;
    for (const variant of strategy.variants) {
      cumulative += variant.weight;
      if ((hash % 100) < cumulative) {
        return variant.name;
      }
    }
    return strategy.variants[0].name;
  }

  // 用户 ID 哈希（简单的一致性哈希）
  private hashUserId(userId: string): number {
    let hash = 0;
    for (let i = 0; i < userId.length; i++) {
      const char = userId.charCodeAt(i);
      hash = ((hash << 5) - hash) + char;
      hash = hash | 0; // 转为 32 位有符号整数
    }
    return Math.abs(hash);
  }
}

// 使用示例
const engine = new FeatureFlagEngine();

// 注册一个灰度发布 Flag
engine.registerFlag('new-dashboard', {
  name: 'new-dashboard',
  rollout: {
    percentage: 10, // 10% 用户放量
    constraints: {
      regions: ['cn'],        // 仅中国区用户
      devices: ['desktop'],   // 仅桌面端
      userIds: ['test-user-1', 'test-user-2'], // 白名单用户
    },
  },
});

// 注册一个 A/B 测试 Flag
engine.registerFlag('new-checkout-ui', {
  name: 'new-checkout-ui',
  rollout: {
    percentage: 50,
    constraints: {
      plans: ['pro', 'enterprise'], // 仅付费用户
    },
  },
  variants: [
    { name: 'control', weight: 50 },    // 对照组（旧 UI）
    { name: 'variant-b', weight: 50 },  // 实验组（新 UI）
  ],
});

// 判断用户是否启用新功能
const user: UserContext = {
  userId: 'user-123',
  region: 'cn',
  device: 'desktop',
  plan: 'pro',
};

console.log(engine.isEnabled('new-dashboard', user));  // 取决于哈希结果
console.log(engine.getVariant('new-checkout-ui', user)); // 'control' 或 'variant-b'
```

### 2.3 CDN 边缘灰度

CDN 边缘灰度利用边缘计算节点（Cloudflare Workers、Vercel Edge Functions）在请求到达源站之前进行流量分流。

```javascript
// ========== Cloudflare Workers 边缘灰度 ==========

// 在 CDN 边缘根据地理位置和比例分流的 Worker
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const country = request.cf?.country || 'US';  // Cloudflare 提供的国家信息

    // 策略一：按地理位置灰度
    // 仅在中国区放量新版本
    if (country === 'CN') {
      // 将请求路由到灰度版本
      url.hostname = 'canary.example.com';
    }

    // 策略二：按比例灰度
    // 10% 的流量路由到灰度版本
    const hash = await this.hashRequest(request);
    if (hash < 26) {
      url.hostname = 'canary.example.com';
    }

    // 策略三：按 Cookie 灰度
    const cookie = request.headers.get('Cookie') || '';
    if (cookie.includes('canary=true')) {
      url.hostname = 'canary.example.com';
    }

    // 策略四：按 User-Agent 灰度（仅移动端）
    const ua = request.headers.get('User-Agent') || '';
    if (/Mobile|Android|iPhone/.test(ua)) {
      url.hostname = 'canary.example.com';
    }

    return fetch(url.toString(), request).then(response => {
      // 区分 4xx 和 5xx 响应状态码，进行分级处理
      const status = response.status;
      if (status >= 500) {
        // 5xx：服务端错误 → 记录错误日志，返回友好提示
        console.error(`[Server Error] ${status} on ${url.toString()}`);
        return new Response('服务暂时不可用，请稍后重试', {
          status: status,
          headers: { 'Content-Type': 'text/plain;charset=UTF-8', 'Retry-After': '60' },
        });
      } else if (status >= 400) {
        // 4xx：客户端错误 → 记录警告日志，通常透传原始响应
        console.warn(`[Client Error] ${status} on ${url.toString()}`);
        if (status === 404) {
          return new Response('页面未找到', {
            status: 404,
            headers: { 'Content-Type': 'text/plain;charset=UTF-8' },
          });
        }
      }
      // 2xx / 3xx：正常响应，透传
      return response;
    });
  },

  async hashRequest(request) {
    const data = new TextEncoder().encode(
      request.headers.get('CF-Connecting-IP') || ''
    );
    const hashBuffer = await crypto.subtle.digest('SHA-256', data);
    const hashArray = new Uint8Array(hashBuffer);
    return hashArray[0]; // 0-255
  },
};
```

### 2.4 容器化部署原理

前端项目容器化部署的完整流程：Docker 构建镜像 → Nginx 反向代理 → K8s 滚动更新。

```dockerfile

# 阶段一：构建阶段
FROM node:20-alpine AS builder

WORKDIR /app

# 利用 Docker 层缓存：先复制依赖文件
COPY package.json pnpm-lock.yaml ./
# 使用 corepack 管理 pnpm 版本（推荐方式）
RUN corepack enable && corepack prepare pnpm@latest --activate && pnpm install --frozen-lockfile

# 复制源码并构建
COPY . .
RUN pnpm build

# 阶段二：运行时阶段（仅保留构建产物）
FROM nginx:alpine

# 复制构建产物到 Nginx 静态目录
COPY --from=builder /app/dist /usr/share/nginx/html

# 复制自定义 Nginx 配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 健康检查
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget --quiet --tries=1 --spider http://localhost:80/health || exit 1

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

```typescript
// src/hooks/useFeatureFlag.ts
import { useEffect, useState } from 'react';
import { unleashClient } from '../featureFlags/unleash';

export function useFeatureFlag(flagName: string, defaultValue = false): boolean {
  const [enabled, setEnabled] = useState(defaultValue);

  useEffect(() => {
    // 初始检查
    setEnabled(unleashClient.isEnabled(flagName));

    // 监听 Flag 变更
    const handler = () => {
      setEnabled(unleashClient.isEnabled(flagName));
    };
    unleashClient.on('update', handler);

    return () => {
      unleashClient.off('update', handler);
    };
  }, [flagName]);

  return enabled;
}

// 获取 A/B 测试变体

  const [variant, setVariant] = useState(() =>

  return variant;
}
```

### 3.2 Nginx 灰度部署配置

```nginx
# ========== Nginx 灰度部署完整配置 ==========
# /etc/nginx/conf.d/gray-release.conf

# 灰度规则定义
# -------- 方式一：按 Cookie 分流 --------
map $cookie_gray_version $static_version {
    default     "v1";       # 默认版本
    "v2"        "v2";       # 灰度版本
}

# -------- 方式二：按 Header 分流 --------
map $http_x_gray_release $static_version {
    default     "v1";
    "true"      "v2";
}

# -------- 方式三：按比例分流（IP 哈希）--------
split_clients "${remote_addr}${http_user_agent}${date_gmt}" $traffic_split {
    10%     "v2";    # 10% 流量
    *       "v1";    # 90% 流量
}

# 合并灰度规则：优先 Cookie > Header > 比例
map "$cookie_gray_version:$http_x_gray_release:$traffic_split" $final_version {
    "~^v2:"     "v2";  # Cookie 指定 v2
    "~^:true:"  "v2";  # Header 指定 v2
    "~^[^:]*:[^:]*:v2" "v2";  # 比例分配 v2
    default     "v1";
}

# 前端静态资源服务
server {
    listen 80;
    server_name app.example.com;

    # 健康检查端点（用于 K8s 探针）
    location /health {
        access_log off;
        return 200 "healthy\n";
        add_header Content-Type text/plain;
    }

    # 静态资源：根据版本路由到不同目录
    location / {
        # 使用 alias 而非 root，根据版本选择目录
        alias /usr/share/nginx/html/$final_version/;
        index index.html;
        try_files $uri $uri/ /index.html;

        # 添加版本标识头（方便调试）
        add_header X-App-Version $final_version;

        # 缓存策略
        # HTML 文件不缓存（确保灰度切换即时生效）
        location ~ /index.html$ {
            add_header Cache-Control "no-cache, no-store, must-revalidate";
            add_header Pragma "no-cache";
            add_header Expires "0";
        }

        # 静态资源（JS/CSS/图片）长期缓存
        location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
    }
}

# 灰度 API 路由
server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        # 根据灰度版本选择后端服务
        set $backend "backend-v1-service:3000";
        if ($final_version = "v2") {
            set $backend "backend-v2-service:3000";
        }

        proxy_pass http://$backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-App-Version $final_version;

        # 超时配置
        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
        proxy_send_timeout 30s;
    }
}
```

### 3.4 Feature Flags 最佳实践

```typescript
// ========== Feature Flags 最佳实践 ==========

// 1. 命名规范
// 推荐格式：{domain}-{feature}-{action}
const FLAG_NAMING = {
  // ✅ 好的命名
  'payment-new-flow': true,
  'dashboard-analytics-export': true,
  'search-ai-suggestions': true,

  // ❌ 不好的命名
  'flag1': false,           // 无意义
  'newFeature': false,      // 不明确
  'temp_toggle': false,     // 临时但变成永久
};

// 2. 过期清理机制
// 每个 Flag 必须设置过期时间，超期自动告警
interface FlagWithTTL {
  name: string;
  createdAt: Date;
  expiresAt: Date;         // 必填过期时间
  owner: string;           // 负责人
  ticket: string;          // 关联的需求/工单编号
}

// CI 检测脚本：检查是否有过期 Flag
// scripts/check-stale-flags.ts
const STALE_DAYS = 30; // Flag 超过 30 天未清理视为过期

async function checkStaleFlags() {
  const flags = await fetchFlagsFromUnleash();

  const staleFlags = flags.filter(flag => {
    const daysSinceCreation = (Date.now() - new Date(flag.createdAt).getTime()) / 86400000;
    return daysSinceCreation > STALE_DAYS;
  });

  if (staleFlags.length > 0) {
    console.error(`发现 ${staleFlags.length} 个过期 Feature Flag：`);
    staleFlags.forEach(f => console.error(`  - ${f.name} (创建于 ${f.createdAt})`));
    process.exit(1); // CI 失败
  }
}

// 3. 避免 Flag 嵌套
// ❌ 错误：Flag 嵌套导致组合爆炸
if (flagA && flagB && !flagC) {
  // 2^3 = 8 种组合，难以测试
  renderComponentX();
}

// ✅ 正确：每个 Flag 独立控制一个完整功能
if (flagA) {
  renderComponentA(); // 独立功能 A
}
if (flagB) {
  renderComponentB(); // 独立功能 B
}

// 4. Flag 隔离：通过依赖注入而非全局变量
// ✅ 好的做法：Flag 通过 props 或 context 传入
interface FeatureFlags {
  newDashboard: boolean;
  exportExcel: boolean;
}

function Component({ flags }: { flags: FeatureFlags }) {
  // 组件不直接依赖全局 Flag 服务
  return flags.newDashboard ? <NewDashboard /> : <OldDashboard />;
}

// 5. 测试覆盖：确保 Flag 的两种状态都经过测试
describe('Dashboard', () => {
  it('Flag 关闭时显示旧版仪表盘', () => {
    render(<Dashboard flags={{ newDashboard: false }} />);
    expect(screen.getByTestId('old-dashboard')).toBeInTheDocument();
  });

  it('Flag 开启时显示新版仪表盘', () => {
    render(<Dashboard flags={{ newDashboard: true }} />);
    expect(screen.getByTestId('new-dashboard')).toBeInTheDocument();
  });
});
```

## 四、常见面试题

### 面试题 1：什么是灰度发布？它和蓝绿部署、滚动更新的区别是什么？

**答案要点**：

- **灰度发布**：新版本先部署到少量实例，分配小比例流量，逐步放量至 100%。风险可控，但观察期长。
- **蓝绿部署**：维护两套完全相同的环境，切换瞬间完成。秒级回滚，但资源成本翻倍。
- **滚动更新**：逐个替换实例。资源利用率高，但回滚速度慢，短暂存在新旧版本混用。
- 核心区别：灰度发布关注流量比例控制，蓝绿部署关注环境切换，滚动更新关注实例替换顺序。

### 面试题 2：Feature Flags 有哪四种类型？分别适用什么场景？

**答案要点**：

- **Release Toggles**：控制未发布功能，短期存在，功能上线后清理
- **Experiment Toggles**：A/B 测试，对比不同版本效果，实验结束后清理
- **Ops Toggles**：运维开关，紧急情况下关闭非核心功能，短期使用
- **Permission Toggles**：权限开关，控制付费/高级功能可见性，长期存在

### 面试题 3：Nginx 如何实现灰度发布？有哪些分流方式？

**答案要点**：

Nginx 通过 `map` 指令和 `split_clients` 指令实现流量分流：
1. **Cookie 分流**：根据 `$cookie_xxx` 将特定用户路由到灰度版本
2. **Header 分流**：根据 `$http_x_xxx` 自定义头路由
3. **比例分流**：使用 `split_clients` 按 IP 哈希分配流量比例
4. **组合策略**：Cookie > Header > 比例，优先级依次降低

### 面试题 4：前端项目的 Docker 多阶段构建有什么优势？

**答案要点**：

1. **减小镜像体积**：构建阶段包含 Node.js 和所有依赖，运行时阶段仅保留 Nginx + 构建产物
2. **安全性更高**：运行时镜像不包含源代码和构建工具，减少攻击面
3. **构建缓存优化**：分层构建，依赖变化时才重新安装，源码变化时复用依赖层缓存
4. **构建参数灵活**：通过 ARG 在构建时注入环境变量

### 面试题 5：Feature Flags 有哪些最佳实践？

**答案要点**：

1. **命名规范**：`{domain}-{feature}-{action}` 格式
2. **过期清理**：每个 Flag 必须设置过期时间，CI 检测过期 Flag
3. **避免嵌套**：Flag 之间不要有依赖关系，组合爆炸导致测试困难
4. **依赖注入**：Flag 通过 props/context 传入，不直接依赖全局服务
5. **测试覆盖**：确保 Flag 开启和关闭两种状态都经过测试

## 五、避坑指南

| 常见错误 | 产生原因 | 正确做法 |
|---|---|---|
| 灰度发布时新旧版本共享同一数据库，导致数据不一致或读写冲突 | 数据库 schema 变更未考虑向后兼容性；新旧版本 API 返回格式不一致 | 数据库 schema 变更必须向后兼容（新增字段而非修改/删除字段）；API 版本化（v1/v2）；灰度期间使用双写策略 |
| Feature Flag 长期不清理，导致代码中遍布大量条件判断，逻辑难以维护 | 发布后未及时清理 Flag 代码；未设置 Flag 过期时间 | 每个 Flag 设置过期时间（如 30 天）；CI 流程中检测过期 Flag 并阻止合并；功能全量上线后立即清理 Flag 代码 |
| 滚动更新时新旧版本混用，用户请求被路由到不同版本导致功能异常 | 未配置会话亲和性（Session Affinity）；静态资源版本不一致（旧 HTML 加载新 JS） | 配置 Nginx `ip_hash` 或使用 Cookie 会话保持；静态资源使用内容哈希命名（`app.a1b2c3d4.js`）；确保 HTML 和 JS/CSS 版本匹配 |
