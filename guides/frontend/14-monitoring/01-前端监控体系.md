## 一、核心概念

### 1.1 前端监控三大体系

前端监控不仅仅是"报错"，它是一套完整的工程质量保障体系。类比汽车的仪表盘：错误监控是故障灯（告诉你哪里坏了），性能监控是油耗/速度表（告诉你运行得怎么样），业务监控是导航地图（告诉你用户走到哪了）。

```
┌──────────────────────────────────────────────────┐
│                  前端监控体系                       │
├──────────────┬──────────────┬────────────────────┤
│  错误监控     │  性能监控     │   业务监控          │
│  (Error)     │  (Perf)      │   (Business)       │
├──────────────┼──────────────┼────────────────────┤
│ JS 运行时错误 │  Core Web    │  PV/UV 统计         │
│ 资源加载错误  │  Vitals      │  页面停留时长        │
│ Promise 异常  │  资源加载耗时 │  用户行为路径        │
│ 接口请求错误  │  首屏渲染时间 │  转化率漏斗          │
│ 框架错误边界  │  长任务监控   │  API 调用成功率      │
└──────────────┴──────────────┴────────────────────┘
```

**三大体系的定位**：

| 监控类型 | 关注点 | 核心指标 | 典型工具 |
|---|---|---|---|
| 错误监控 | 代码质量、稳定性 | 错误率、错误量、影响用户数 | Sentry、Fundebug、自建 SDK |
| 性能监控 | 用户体验、加载速度 | LCP、INP、CLS、FCP、TTFB | Lighthouse、Web Vitals、Perfume.js |
| 业务监控 | 产品指标、用户行为 | PV、UV、转化率、留存率 | 百度统计、Google Analytics、自建埋点 |

### 1.2 Sentry 核心能力

Sentry 是当前最流行的开源错误监控平台，其核心能力包括四个关键机制。

**（1）错误分组（Fingerprint）**

Sentry 不会把每个错误都当作独立事件，而是通过计算错误堆栈的"指纹（fingerprint）"将相同根因的错误归为一组。默认指纹算法：取堆栈最顶层调用帧的 `函数名 + 文件名 + 行号` 组合。

```javascript
// 自定义指纹规则 - 将特定错误合并到同一组
Sentry.init({
  dsn: 'https://xxx@sentry.io/xxx',
  beforeSend(event, hint) {
    const error = hint.originalException;
    // 将同一接口的所有错误归为一组
    if (error && error.url) {
      event.fingerprint = ['api-error', error.url];
    }
    return event;
  },
});
```

**（2）Sourcemap 还原**

生产环境的 JS 代码经过压缩混淆后，错误堆栈中的行号和变量名毫无意义。Sentry 支持上传 Sourcemap 文件，在服务端自动将压缩后的堆栈还原为原始源码位置。

**（3）Breadcrumbs（面包屑）**

Breadcrumbs 记录了错误发生前用户的一系列操作（点击、导航、网络请求、控制台输出等），帮助还原错误现场。

```javascript
// 手动添加 Breadcrumb
Sentry.addBreadcrumb({
  category: 'auth',
  message: '用户点击了登录按钮',
  level: 'info',
  data: { userId: 12345 },
});
```

**（4）Release 关联**

通过 `release` 字段将错误与具体的代码版本关联，可以快速判断错误是在哪个版本引入的。

```javascript
Sentry.init({
  dsn: 'https://xxx@sentry.io/xxx',
  release: 'my-app@1.2.3',          // 或使用 process.env.RELEASE_VERSION
  environment: 'production',         // production / staging / development
});
```

## 二、底层原理

### 2.1 错误采集原理

前端错误采集需要覆盖四种场景：JS 运行时错误、Promise 未捕获异常、console.error 劫持、资源加载错误。

```typescript
// ========== 完整的错误采集器实现 ==========

interface ErrorReport {
  type: 'js' | 'promise' | 'resource' | 'console';
  message: string;
  stack?: string;
  filename?: string;
  lineno?: number;
  colno?: number;
  timestamp: number;
  breadcrumbs: Breadcrumb[];
}

interface Breadcrumb {
  type: 'click' | 'navigation' | 'http' | 'console';
  message: string;
  timestamp: number;
  data?: Record<string, unknown>;
}

class ErrorCollector {
  private breadcrumbs: Breadcrumb[] = [];
  private maxBreadcrumbs = 100;

  constructor() {
    this.initBreadcrumbs();
    this.initErrorListeners();
  }

  // ------ 面包屑收集（还原用户操作轨迹） ------
  private initBreadcrumbs(): void {
    // 1. 点击事件
    document.addEventListener('click', (e) => {
      const target = e.target as HTMLElement;
      this.addBreadcrumb({
        type: 'click',
        message: `点击 ${target.tagName.toLowerCase()}${target.id ? '#' + target.id : ''}${target.className ? ' .' + target.className.split(' ').slice(0, 2).join('.') : ''}`,
        timestamp: Date.now(),
      });
    }, true); // 捕获阶段，确保所有点击都被记录

    // 2. 路由变化
    const originalPushState = history.pushState;
    history.pushState = (...args) => {
      this.addBreadcrumb({
        type: 'navigation',
        message: `路由跳转: ${args[2]}`,
        timestamp: Date.now(),
      });
      return originalPushState.apply(history, args);
    };

    // 3. 网络请求（劫持 fetch）
    const originalFetch = window.fetch;
    window.fetch = (...args) => {
      const start = Date.now();
      const url = typeof args[0] === 'string' ? args[0] : args[0].url;
      return originalFetch(...args).then((res) => {
        this.addBreadcrumb({
          type: 'http',
          message: `fetch ${url} - ${res.status} (${Date.now() - start}ms)`,
          timestamp: Date.now(),
        });
        return res;
      });
    };

    // 4. console 输出（区分 error 和 warn 的处理）
    const levels = ['log', 'warn', 'error'] as const;
    levels.forEach((level) => {
      const original = console[level];
      console[level] = (...args: unknown[]) => {
        this.addBreadcrumb({
          type: 'console',
          message: `[${level}] ${args.map(String).join(' ')}`,
          timestamp: Date.now(),
          data: level === 'error' ? { stack: new Error().stack } : undefined,
        });
        // console.error 额外捕获堆栈信息用于错误定位
        if (level === 'error') {
          const errorStack = new Error().stack;
          // 可将堆栈信息附加到面包屑或触发独立的错误上报
          this.addBreadcrumb({
            type: 'console',
            message: `[error.stack] ${errorStack?.split('\n').slice(1, 4).join(' → ')}`,
            timestamp: Date.now(),
          });
        }
        original.apply(console, args);
      };
    });
  }

  private addBreadcrumb(breadcrumb: Breadcrumb): void {
    this.breadcrumbs.push(breadcrumb);
    if (this.breadcrumbs.length > this.maxBreadcrumbs) {
      this.breadcrumbs.shift();
    }
  }

  // ------ 错误监听 ------
  private initErrorListeners(): void {
    // 1. JS 运行时错误（window.onerror）
    // 注意：window.onerror 只能捕获"运行时错误"，
    // 无法捕获"语法错误"（需在同一个 script 标签内）和"资源加载错误"
    window.addEventListener('error', (event: ErrorEvent) => {
      // 过滤掉资源加载错误（资源加载错误没有 message 属性）
      if (!(event instanceof ErrorEvent) || !event.message) return;

      this.reportError({
        type: 'js',
        message: event.message,
        filename: event.filename,
        lineno: event.lineno,
        colno: event.colno,
        stack: event.error?.stack || '',
        timestamp: Date.now(),
        breadcrumbs: [...this.breadcrumbs],
      });
    });

    // 2. Promise 未捕获异常（unhandledrejection）
    // 当 Promise 被 reject 且没有 catch 处理时触发
    window.addEventListener('unhandledrejection', (event: PromiseRejectionEvent) => {
      const reason = event.reason;
      this.reportError({
        type: 'promise',
        message: reason instanceof Error ? reason.message : String(reason),
        stack: reason instanceof Error ? reason.stack : '',
        timestamp: Date.now(),
        breadcrumbs: [...this.breadcrumbs],
      });
      // 阻止默认行为（控制台打印错误），由 SDK 统一处理
      event.preventDefault();
    });

    // 3. 资源加载错误（捕获阶段监听）
    // 资源加载错误（如 <img> <script> <link> 加载失败）不会冒泡到 window，
    // 必须在捕获阶段监听
    window.addEventListener('error', (event: Event) => {
      const target = event.target as HTMLElement;
      const isResource =
        target instanceof HTMLScriptElement ||
        target instanceof HTMLLinkElement ||
        target instanceof HTMLImageElement ||
        target instanceof HTMLVideoElement;

      if (isResource) {
        const src =
          (target as HTMLScriptElement | HTMLImageElement).src ||
          (target as HTMLLinkElement).href || '';
        this.reportError({
          type: 'resource',
          message: `资源加载失败: ${target.tagName} ${src}`,
          filename: src,
          timestamp: Date.now(),
          breadcrumbs: [...this.breadcrumbs],
        });
      }
    }, true); // 第三个参数 true = 捕获阶段
  }

  // ------ 上报 ------
  private reportError(report: ErrorReport): void {
    console.log('[ErrorCollector] 捕获到错误:', report);
    // 交给 Reporter 上报（见 2.3 节）
  }
}

// 初始化
new ErrorCollector();
```

**关键原理总结**：

| 错误类型 | 捕获方式 | 注意事项 |
|---|---|---|
| JS 运行时错误 | `window.addEventListener('error', ...)` | 冒泡阶段（默认 false）：检查 `event instanceof ErrorEvent`。// false 表示冒泡阶段（默认），true 表示捕获阶段 |
| Promise 异常 | `window.addEventListener('unhandledrejection', ...)` | 调用 `event.preventDefault()` 阻止控制台输出 |
| 资源加载错误 | `window.addEventListener('error', ..., true)` | 必须在捕获阶段，因为资源加载错误不冒泡 |
| console.error | 劫持 `console.error` 方法 | 收集面包屑辅助调试，error 级别额外捕获堆栈信息；warn 级别仅记录消息，不单独触发错误上报（需保留原始方法） |
| 框架内错误 | React ErrorBoundary / Vue errorHandler | 框架的错误边界是组件级的，不会冒泡到 window |

**window.onerror 的局限性**：
- 无法捕获语法错误（SyntaxError），因为语法错误发生在代码解析阶段
- 无法捕获跨域脚本的详细错误信息（`Script error.`），需要添加 `crossorigin="anonymous"` 属性
- 无法捕获 Promise 异常（需用 `unhandledrejection` 事件）
- 无法捕获资源加载错误（需用捕获阶段的 `error` 事件）

### 2.2 性能采集原理

现代浏览器提供了 `PerformanceObserver` API 和 `performance.getEntriesByType()` 两种方式采集性能数据。

```typescript
// ========== 完整的性能采集器实现 ==========

interface PerfMetrics {
  // Core Web Vitals
  LCP?: number;  // Largest Contentful Paint - 最大内容绘制
  INP?: number;  // Interaction to Next Paint - 交互到下次绘制
  CLS?: number;  // Cumulative Layout Shift - 累积布局偏移
  FCP?: number;  // First Contentful Paint - 首次内容绘制
  TTFB?: number; // Time to First Byte - 首字节时间

  // 自定义指标
  FMP?: number;  // First Meaningful Paint - 首次有意义绘制
  TTI?: number;  // Time to Interactive - 可交互时间
  // 资源耗时
  resourceTimings?: ResourceTiming[];
}

interface ResourceTiming {
  name: string;
  type: string;
  duration: number;
  dns: number;
  tcp: number;
  request: number;
  response: number;
}

class PerfCollector {
  private metrics: PerfMetrics = {};

  constructor() {
    this.observeCoreWebVitals();
    this.observeResourceTimings();
    this.observeLongTasks();
  }

  // ------ Core Web Vitals 采集 ------
  private observeCoreWebVitals(): void {
    // 1. LCP（Largest Contentful Paint）- 最大内容绘制
    // 标识视口内最大的可见元素（图片/文本块）渲染完成的时间
    // 阈值：好 < 2.5s，需改进 2.5-4s，差 > 4s
    const lcpObserver = new PerformanceObserver((list) => {
      const entries = list.getEntries();
      const lastEntry = entries[entries.length - 1] as PerformanceEntry & { size: number };
      // LCP 会多次更新，取最后一次
      this.metrics.LCP = lastEntry.startTime;
      console.log(`[LCP] ${this.metrics.LCP.toFixed(0)}ms`);
    });
    lcpObserver.observe({ type: 'largest-contentful-paint', buffered: true });

    // 2. INP（Interaction to Next Paint）- 交互到下次绘制
    // 衡量用户交互（点击、按键等）到页面视觉反馈的延迟
    // 阈值：好 < 200ms，需改进 200-500ms，差 > 500ms
    // 注意：INP 需要在用户离开页面时计算，因为它是整个会话中最差的交互延迟
    let maxInteractionDelay = 0;
    const inpObserver = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        const evt = entry as PerformanceEventTiming;
        if (!evt.interactionId) continue;
        const delay = evt.processingStart - evt.startTime;
        maxInteractionDelay = Math.max(maxInteractionDelay, delay);
      }
    });
    inpObserver.observe({ type: 'event', buffered: true, durationThreshold: 16 });

    // 在页面卸载时上报 INP
    window.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        this.metrics.INP = maxInteractionDelay;
        console.log(`[INP] ${this.metrics.INP.toFixed(0)}ms`);
      }
    });

    // 3. CLS（Cumulative Layout Shift）- 累积布局偏移
    // 衡量页面视觉稳定性，所有意外布局偏移分数的总和
    // 阈值：好 < 0.1，需改进 0.1-0.25，差 > 0.25
    let clsValue = 0;
    const clsObserver = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        const layoutShift = entry as LayoutShift;
        // 只计算非用户交互导致的布局偏移
        if (!layoutShift.hadRecentInput) {
          clsValue += layoutShift.value;
        }
      }
    });
    clsObserver.observe({ type: 'layout-shift', buffered: true });

    window.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        this.metrics.CLS = clsValue;
        console.log(`[CLS] ${this.metrics.CLS.toFixed(4)}`);
      }
    });

    // 4. FCP（First Contentful Paint）- 首次内容绘制
    const fcpObserver = new PerformanceObserver((list) => {
      const fcpEntry = list.getEntries()[0];
      if (fcpEntry) {
        this.metrics.FCP = fcpEntry.startTime;
        console.log(`[FCP] ${this.metrics.FCP.toFixed(0)}ms`);
      }
    });
    fcpObserver.observe({ type: 'paint', buffered: true });

    // 5. TTFB（Time to First Byte）
    // 使用 Navigation Timing API
    const navEntry = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming;
    if (navEntry) {
      this.metrics.TTFB = navEntry.responseStart - navEntry.requestStart;
      console.log(`[TTFB] ${this.metrics.TTFB.toFixed(0)}ms`);
    }
  }

  // ------ 资源耗时采集 ------
  private observeResourceTimings(): void {
    // performance.getEntriesByType('resource') 返回所有资源的加载耗时
    const entries = performance.getEntriesByType('resource') as PerformanceResourceTiming[];

    this.metrics.resourceTimings = entries.map((entry) => ({
      name: entry.name,
      type: entry.initiatorType, // script / img / css / fetch / xmlhttprequest
      duration: entry.duration,
      // 分解各阶段耗时
      dns: entry.domainLookupEnd - entry.domainLookupStart,
      tcp: entry.connectEnd - entry.connectStart,
      request: entry.responseStart - entry.requestStart,
      response: entry.responseEnd - entry.responseStart,
    }));

    // 找出最慢的 5 个资源
    const slowest = [...this.metrics.resourceTimings]
      .sort((a, b) => b.duration - a.duration)
      .slice(0, 5);
    console.table(slowest);
  }

  // ------ 长任务监控 ------
  private observeLongTasks(): void {
    // 长任务（Long Task）指执行时间超过 50ms 的任务
    // 长任务会阻塞主线程，导致页面卡顿
    const longTaskObserver = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        console.warn(`[长任务] 耗时 ${entry.duration.toFixed(0)}ms:`, entry);
        // 长任务说明这里可能有不合理的同步计算、大量 DOM 操作等
      }
    });
    longTaskObserver.observe({ type: 'longtask', buffered: true });
  }
}

// 初始化
new PerfCollector();
```

**PerformanceObserver 的工作原理**：

```
执行流程：
1. 注册 Observer  →  指定监听的 performance entry type
2. 浏览器异步通知 →  将符合条件的 entry 放入 Observer 的缓冲区
3. 回调触发      →  PerformanceObserverCallback 被调用
4. 处理 entry    →  遍历 entries，提取指标数据

关键 API：
- PerformanceObserver.observe({ type, buffered }) 
  buffered: true  = 获取页面加载以来所有历史 entry（不仅限于注册后的）
- PerformanceObserver.disconnect() = 停止监听
- performance.getEntriesByType(type) = 一次性获取所有未消耗的 entry
```

**Core Web Vitals 指标速查**：

| 指标 | 全称 | 含义 | 好 | 需改进 | 差 |
|---|---|---|---|---|---|
| LCP | Largest Contentful Paint | 最大内容渲染时间 | < 2.5s | 2.5-4s | > 4s |
| INP | Interaction to Next Paint | 交互响应延迟 | < 200ms | 200-500ms | > 500ms |
| CLS | Cumulative Layout Shift | 累积布局偏移 | < 0.1 | 0.1-0.25 | > 0.25 |
| FCP | First Contentful Paint | 首次内容绘制 | < 1.8s | 1.8-3s | > 3s |
| TTFB | Time to First Byte | 首字节时间 | < 800ms | 800-1800ms | > 1800ms |

### 2.3 上报策略

上报策略决定了监控数据能否可靠地传送到服务端，直接影响监控的准确性。

```typescript
// ========== 完整的 Reporter 实现 ==========

interface ReportData {
  type: 'error' | 'perf' | 'business';
  data: Record<string, unknown>;
  timestamp: number;
  sampleRate: number; // 采样率
}

class Reporter {
  private endpoint: string;
  private buffer: ReportData[] = [];
  private bufferSize = 10;
  private flushInterval = 5000; // 5 秒批量上报
  private dbName = 'monitor-reports';
  private retryQueue: ReportData[] = [];

  constructor(endpoint: string) {
    this.endpoint = endpoint;
    this.initFlushTimer();
    this.initPageUnloadReport();
    this.recoverFailedReports();
  }

  // ------ 方式一：navigator.sendBeacon（页面卸载时使用） ------
  // sendBeacon 的优势：
  // 1. 异步发送，不阻塞页面卸载
  // 2. 浏览器保证在页面关闭后仍会发送请求
  // 3. 不受页面 unload 事件限制（某些浏览器限制 unload 中的异步操作）
  private sendByBeacon(data: ReportData): boolean {
    const blob = new Blob([JSON.stringify(data)], { type: 'application/json' });
    const sent = navigator.sendBeacon(this.endpoint, blob);
    if (!sent) {
      console.warn('[Reporter] sendBeacon 发送失败，数据过大');
    }
    return sent;
  }

  // ------ 方式二：fetch + keepalive（页面卸载时备选） ------
  // fetch keepalive 的特性：
  // 1. 允许请求在页面卸载后继续完成
  // 2. 单次请求 body 限制 64KB（Chrome）
  // 3. 同一页面最多允许 64KB 的 keepalive 请求总量
  private async sendByFetchKeepalive(data: ReportData): Promise<void> {
    try {
      await fetch(this.endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(data),
        keepalive: true,
      });
    } catch (err) {
      // fetch keepalive 失败时降级到 sendBeacon
      this.sendByBeacon(data);
    }
  }

  // ------ 方式三：img beacon（最简方案，用于跨域简单场景） ------
  // img beacon 的原理：
  // 1. 动态创建 Image 对象，将数据编码到 URL 参数中
  // 2. 天然支持跨域，无需 CORS 配置
  // 3. 缺点：仅支持 GET 请求，URL 长度有限制（~2048 字符）
  private sendByImgBeacon(data: ReportData): void {
    const params = new URLSearchParams({
      data: JSON.stringify(data).slice(0, 1800), // 截断防止超长
      t: Date.now().toString(),
    });
    const img = new Image();
    img.src = `${this.endpoint}?${params.toString()}`;
  }

  // ------ 采样率控制 ------
  // 采样策略：并非所有错误/性能数据都需要上报，根据采样率过滤
  private shouldSample(sampleRate: number): boolean {
    // 采样率 0-1，0 表示不上报，1 表示全量上报
    if (sampleRate >= 1) return true;
    if (sampleRate <= 0) return false;
    return Math.random() < sampleRate;
  }

  // ------ 本地 IndexedDB 缓冲 ------
  // 当网络不可用或上报失败时，将数据暂存到 IndexedDB，等待恢复后重试
  private async saveToIndexedDB(data: ReportData): Promise<void> {
    return new Promise((resolve, reject) => {
      const request = indexedDB.open(this.dbName, 1);

      request.onupgradeneeded = (event) => {
        const db = (event.target as IDBOpenDBRequest).result;
        if (!db.objectStoreNames.contains('reports')) {
          db.createObjectStore('reports', {
            keyPath: 'id',
            autoIncrement: true,
          });
        }
      };

      request.onsuccess = (event) => {
        const db = (event.target as IDBOpenDBRequest).result;
        const tx = db.transaction('reports', 'readwrite');
        const store = tx.objectStore('reports');
        store.add({ ...data, id: undefined });
        tx.oncomplete = () => {
          db.close();
          resolve();
        };
        tx.onerror = () => reject(tx.error);
      };

      request.onerror = () => reject(request.error);
    });
  }

  // ------ 恢复失败的上报 ------
  private async recoverFailedReports(): Promise<void> {
    return new Promise((resolve) => {
      const request = indexedDB.open(this.dbName, 1);

      request.onsuccess = (event) => {
        const db = (event.target as IDBOpenDBRequest).result;
        const tx = db.transaction('reports', 'readonly');
        const store = tx.objectStore('reports');
        const getAll = store.getAll();

        getAll.onsuccess = () => {
          const reports = getAll.result;
          if (reports.length > 0) {
            console.log(`[Reporter] 恢复 ${reports.length} 条失败上报`);
            // 尝试重新上报
            reports.forEach((r: ReportData) => this.send(r));
          }
          db.close();
          resolve();
        };
      };

      request.onerror = () => resolve();
    });
  }

  // ------ 页面卸载时保证送达 ------
  private initPageUnloadReport(): void {
    // visibilitychange 比 beforeunload/unload 更可靠
    // 移动端浏览器可能在 beforeunload 时不执行异步操作
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        // 刷新缓冲区中积压的数据
        this.flush(true);
      }
    });

    // 兜底：beforeunload 事件
    window.addEventListener('beforeunload', () => {
      this.flush(true);
    });
  }

  // ------ 批量上报 ------
  private initFlushTimer(): void {
    setInterval(() => this.flush(false), this.flushInterval);
  }

  private flush(useBeacon: boolean): void {
    if (this.buffer.length === 0) return;

    const batch = [...this.buffer];
    this.buffer = [];

    if (useBeacon) {
      // 页面卸载时使用 sendBeacon，确保送达
      this.sendByBeacon({ type: 'batch', data: { items: batch }, timestamp: Date.now(), sampleRate: 1 });
    } else {
      this.sendByFetchKeepalive({ type: 'batch', data: { items: batch }, timestamp: Date.now(), sampleRate: 1 });
    }
  }

  // ------ 公共上报接口 ------
  public send(data: ReportData): void {
    // 采样判断
    if (!this.shouldSample(data.sampleRate)) return;

    this.buffer.push(data);

    // 缓冲区满时立即上报
    if (this.buffer.length >= this.bufferSize) {
      this.flush(false);
    }
  }
}

// 使用示例
const reporter = new Reporter('https://monitor.example.com/api/report');
reporter.send({
  type: 'error',
  data: { message: '测试错误', stack: '...' },
  timestamp: Date.now(),
  sampleRate: 1, // 错误全量上报
});
```

**三种上报方式对比**：

| 方式 | 兼容性 | 数据量 | 跨域 | 可靠性 | 适用场景 |
|---|---|---|---|---|---|
| sendBeacon | Chrome 39+、不支持 IE | 无限制 | 需 CORS | 高 | 页面卸载、批量上报 |
| fetch keepalive | Chrome 66+ | 64KB | 需 CORS | 高 | 现代浏览器、POST 大数据 |
| img beacon | 全兼容 | ~2KB (URL 限制) | 天然支持 | 中 | 简单埋点、跨域场景 |

### 2.4 Sourcemap 三步曲

Sourcemap 是前端错误定位的关键技术，它包含了压缩后代码与原始源码之间的映射关系。

```
Sourcemap 三步曲：

第一步：生成 Sourcemap
  webpack/vite 构建时设置 devtool: 'source-map' 或 'hidden-source-map'
  ↓
第二步：上传 Sourcemap 到 Sentry / 监控平台
  - 通过 Sentry CLI: sentry-cli releases files <release> upload-sourcemaps ./dist
  - 通过 Webpack 插件: @sentry/webpack-plugin
  - 注意：不要把 Sourcemap 部署到生产环境 CDN
  ↓
第三步：服务端自动还原
  - 收到错误 → 根据 release 版本查找 Sourcemap
  - 解析压缩后的行列号 → 映射到原始源码位置
  - 返回带源码上下文的错误堆栈
```

### 3.3 自定义埋点 SDK

```typescript
// ========== 自定义埋点 SDK 实现 ==========

interface TrackEvent {
  eventName: string;
  eventType: 'pv' | 'click' | 'exposure' | 'duration' | 'api';
  properties: Record<string, unknown>;
  timestamp: number;
}

class TrackingSDK {
  private events: TrackEvent[] = [];
  private pageStartTime: number;
  private currentPage: string;
  private reporter: Reporter;

  constructor(reportUrl: string) {
    this.reporter = new Reporter(reportUrl);
    this.pageStartTime = Date.now();
    this.currentPage = window.location.pathname;
    this.init();
  }

  private init(): void {
    this.trackPV();
    this.trackPageLeave();
    this.trackBehavior();
    this.trackAPICalls();
  }

  // ------ PV/UV 统计 ------
  private trackPV(): void {
    const pvEvent: TrackEvent = {
      eventName: 'page_view',
      eventType: 'pv',
      properties: {
        page: this.currentPage,
        referrer: document.referrer,
        screenWidth: window.screen.width,
        screenHeight: window.screen.height,
        // UV 标识：通常使用服务端生成的唯一 ID 或 cookie
        visitorId: this.getVisitorId(),
      },
      timestamp: Date.now(),
    };
    this.send(pvEvent);

    // 监听路由变化（SPA 应用）
    window.addEventListener('popstate', () => {
      this.trackPV();
    });

    // 劫持 pushState / replaceState
    const originalPushState = history.pushState;
    history.pushState = (...args) => {
      originalPushState.apply(history, args);
      this.trackPV();
    };
  }

  // ------ 页面停留时长 ------
  private trackPageLeave(): void {
    const reportDuration = () => {
      const duration = Date.now() - this.pageStartTime;
      const durationEvent: TrackEvent = {
        eventName: 'page_duration',
        eventType: 'duration',
        properties: {
          page: this.currentPage,
          duration, // 毫秒
          durationSeconds: Math.round(duration / 1000),
        },
        timestamp: Date.now(),
      };
      this.send(durationEvent);
    };

    // 页面隐藏时上报
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        reportDuration();
      }
    });

    // 页面卸载时上报
    window.addEventListener('beforeunload', () => {
      reportDuration();
    });
  }

  // ------ 用户行为路径 ------
  private trackBehavior(): void {
    // 点击行为追踪
    document.addEventListener('click', (e) => {
      const target = e.target as HTMLElement;
      // 只追踪有 data-track 属性的元素
      const trackId = target.getAttribute('data-track');
      if (!trackId) return;

      const clickEvent: TrackEvent = {
        eventName: 'user_click',
        eventType: 'click',
        properties: {
          trackId,
          tagName: target.tagName,
          text: target.textContent?.slice(0, 50) || '',
          page: this.currentPage,
          // 用户行为路径：从进入页面到当前的所有事件序列
          path: this.getBehaviorPath(),
        },
        timestamp: Date.now(),
      };
      this.send(clickEvent);
    });

    // 曝光追踪（元素进入视口）
    this.trackExposure();
  }

  // 曝光追踪
  private trackExposure(): void {
    const observer = new IntersectionObserver(
      (entries) => {
        entries.forEach((entry) => {
          if (entry.isIntersecting) {
            const target = entry.target as HTMLElement;
            const trackId = target.getAttribute('data-track-exposure');
            if (trackId) {
              this.send({
                eventName: 'element_exposure',
                eventType: 'exposure',
                properties: {
                  trackId,
                  page: this.currentPage,
                },
                timestamp: Date.now(),
              });
              // 只曝光一次
              observer.unobserve(target);
            }
          }
        });
      },
      { threshold: 0.5 } // 元素 50% 可见时触发
    );

    // 监听所有带 data-track-exposure 属性的元素
    document.querySelectorAll('[data-track-exposure]').forEach((el) => {
      observer.observe(el);
    });
  }

  // ------ API 调用成功率 ------
  private trackAPICalls(): void {
    // 劫持 fetch
    const originalFetch = window.fetch;
    const requestMap = new Map<string, number>();

    window.fetch = (...args: Parameters<typeof fetch>) => {
      const url = typeof args[0] === 'string' ? args[0] : args[0].url;
      const start = Date.now();
      const requestId = `${url}_${start}`;
      requestMap.set(requestId, start);

      return originalFetch(...args)
        .then((response) => {
          const duration = Date.now() - start;
          this.send({
            eventName: 'api_call',
            eventType: 'api',
            properties: {
              url,
              status: response.status,
              duration,
              success: response.ok,
              page: this.currentPage,
            },
            timestamp: Date.now(),
          });
          requestMap.delete(requestId);
          return response;
        })
        .catch((error) => {
          const duration = Date.now() - start;
          this.send({
            eventName: 'api_call',
            eventType: 'api',
            properties: {
              url,
              status: 0,
              duration,
              success: false,
              error: error instanceof Error ? error.message : String(error),
              page: this.currentPage,
            },
            timestamp: Date.now(),
          });
          requestMap.delete(requestId);
          throw error;
        });
    };
  }

  // ------ 辅助方法 ------
  private getVisitorId(): string {
    // 从 cookie 或 localStorage 获取或生成唯一访客 ID
    let visitorId = localStorage.getItem('_visitor_id');
    if (!visitorId) {
      visitorId = `${Date.now()}_${Math.random().toString(36).slice(2, 11)}`;
      localStorage.setItem('_visitor_id', visitorId);
    }
    return visitorId;
  }

  private getBehaviorPath(): string[] {
    // 返回当前会话的用户行为路径
    return this.events
      .filter((e) => e.eventType === 'click')
      .map((e) => e.properties.trackId as string)
      .slice(-10); // 仅保留最近 10 步
  }

  private send(event: TrackEvent): void {
    this.events.push(event);
    this.reporter.send({
      type: 'business',
      data: event.properties,
      timestamp: event.timestamp,
      sampleRate: 1,
    });
  }
}

// 使用示例
```

### 3.4 白屏检测实现

```typescript
// ========== 白屏检测 SDK ==========

class WhiteScreenDetector {
  private readonly checkInterval = 3000; // 每 3 秒检测一次
  private readonly samplePoints = 18;    // 采样点数量（3x6 网格）
  private readonly whiteThreshold = 16;  // 白色阈值：至少 16 个采样点相同才判定为白屏
  private timer: number | null = null;

  constructor() {
    this.start();
  }

  // ------ 基于 MutationObserver + 采样点对比的白屏检测 ------
  start(): void {
    // 页面加载完成后开始检测
    if (document.readyState === 'complete') {
      this.scheduleCheck();
    } else {
      window.addEventListener('load', () => this.scheduleCheck());
    }
  }

  private scheduleCheck(): void {
    this.timer = window.setInterval(() => {
      this.detect();
    }, this.checkInterval);
  }

  private detect(): void {
    // 第一步：检查 DOM 是否有内容
    // 获取 body 中所有可见文本内容
    const rootElement = document.getElementById('root') || document.body;
    const textContent = rootElement.innerText?.trim() || '';

    // 如果文本内容超过阈值，说明页面正常
    if (textContent.length > 10) {
      return; // 页面正常，不是白屏
    }

    // 第二步：检查是否有可见的图片/Canvas 元素
    const hasVisibleMedia = this.hasVisibleMedia(rootElement);
    if (hasVisibleMedia) {
      return; // 有可见媒体内容，不是白屏
    }

    // 第三步：采样点对比
    // 在页面上取 18 个均匀分布的采样点
    const isWhiteScreen = this.checkSamplePoints();
    if (isWhiteScreen) {
      this.reportWhiteScreen();
    }
  }

  private hasVisibleMedia(element: Element): boolean {
    const images = element.querySelectorAll('img, canvas, video, svg');
    for (const img of images) {
      const rect = img.getBoundingClientRect();
      // 检查是否在视口内且有实际尺寸
      if (rect.width > 0 && rect.height > 0 &&
          rect.bottom > 0 && rect.right > 0 &&
          rect.top < window.innerHeight && rect.left < window.innerWidth) {
        return true;
      }
    }
    return false;
  }

  private checkSamplePoints(): boolean {
    const { innerWidth: w, innerHeight: h } = window;
    const cols = 3, rows = 6;
    const cellW = w / cols;
    const cellH = h / rows;

    let sameCount = 0;

    for (let row = 0; row < rows; row++) {
      for (let col = 0; col < cols; col++) {
        // 计算采样点坐标（每个格子的中心）
        const x = cellW * col + cellW / 2;
        const y = cellH * row + cellH / 2;

        // 使用 document.elementFromPoint 获取该点的元素
        const element = document.elementFromPoint(x, y);

        if (element) {
          // 检查该元素是否是根容器或其直接子元素
          // 如果是，说明该位置没有实际内容渲染
          if (element === document.body ||
              element === document.getElementById('root') ||
              element === document.documentElement) {
            sameCount++;
          }
        }
      }
    }

    // 如果超过 whiteThreshold 个采样点都在根节点上，判定为白屏
    return sameCount >= this.whiteThreshold;
  }

  private reportWhiteScreen(): void {
    const report = {
      type: 'white_screen',
      page: window.location.href,
      timestamp: Date.now(),
      ua: navigator.userAgent,
      viewport: `${window.innerWidth}x${window.innerHeight}`,
      domContent: document.getElementById('root')?.innerHTML?.slice(0, 500) || '',
    };

    console.error('[白屏检测] 检测到白屏:', report);

    // 使用 sendBeacon 上报
    navigator.sendBeacon(
      '/api/monitor/white-screen',
      new Blob([JSON.stringify(report)], { type: 'application/json' })
    );
  }

  stop(): void {
    if (this.timer) {
      clearInterval(this.timer);
      this.timer = null;
    }
  }
}

// 使用
new WhiteScreenDetector();
```

**白屏检测原理总结**：

```
白屏检测的三层判断：

第一层：文本内容判断
  检查 root 容器内是否有可见文本（innerText 长度 > 10）

第二层：媒体元素判断
  检查是否有可见的图片/Canvas/Video/SVG 元素

第三层：采样点对比
  在页面上取 18 个均匀采样点（3x6 网格）
  使用 elementFromPoint 获取每个点的元素
  如果超过 16 个点都落在根节点（body/html/root），判定为白屏
```

## 四、常见面试题

### 面试题 1：前端错误监控有哪些类型？分别如何捕获？

**答案要点**：

前端错误监控覆盖四种类型：
1. **JS 运行时错误**：通过 `window.addEventListener('error', handler)` 捕获，注意区分 `ErrorEvent` 和资源错误事件
2. **Promise 未捕获异常**：通过 `window.addEventListener('unhandledrejection', handler)` 捕获，建议调用 `event.preventDefault()` 阻止控制台输出
3. **资源加载错误**：通过 `window.addEventListener('error', handler, true)` 在捕获阶段监听（资源加载错误不冒泡）
4. **框架错误边界**：React 使用 `ErrorBoundary` 组件（`componentDidCatch` / `getDerivedStateFromError`），Vue 使用 `errorHandler` 全局配置

### 面试题 2：什么是 Sourcemap？如何安全地使用它？

**答案要点**：

Sourcemap 是压缩后代码与原始源码之间的映射文件，包含行列号、变量名等映射关系。

安全使用 Sourcemap 的关键原则：
- 生产环境使用 `hidden-source-map`（生成 sourcemap 但不添加 sourceMappingURL 注释）
- Sourcemap 文件上传到 Sentry 等监控平台，不部署到生产环境 CDN
- 构建完成后删除 dist 目录中的 .map 文件
- 通过 Sentry Webpack Plugin 或 Vite Plugin 自动上传

### 面试题 3：`navigator.sendBeacon` 和 `fetch` 有什么区别？什么场景用哪个？

**答案要点**：

| 对比维度 | sendBeacon | fetch |
|---|---|---|
| 页面卸载时可靠性 | 高（浏览器保证发送） | 中（需 keepalive 标志） |
| 数据量限制 | 无限制 | 64KB（keepalive） |
| 请求方法 | 仅 POST | GET/POST/PUT/DELETE |
| 响应处理 | 不关心响应 | 可获取响应 |
| 兼容性 | Chrome 39+、不支持 IE | Chrome 66+（keepalive） |

使用场景：页面卸载时使用 sendBeacon；正常运行时使用 fetch；跨域简单场景使用 img beacon。

### 面试题 4：如何设计一个前端监控 SDK？需要考虑哪些核心问题？

**答案要点**：

核心设计要点：
1. **数据采集层**：错误采集（window.onerror、unhandledrejection）、性能采集（PerformanceObserver）、行为采集（埋点、点击、路由）
2. **数据处理层**：数据清洗（去重、脱敏）、错误分组（fingerprint）、Sourcemap 还原
3. **上报层**：上报策略（sendBeacon + fetch keepalive）、采样率控制、本地缓冲（IndexedDB）、批量上报
4. **可视化层**：错误趋势图、性能分布图、用户行为漏斗

需要考虑的核心问题：
- 性能影响：SDK 本身不能影响页面性能（异步加载、采样率控制）
- 可靠性：网络不可用时数据不丢失（IndexedDB 缓冲）
- 安全性：敏感数据脱敏（密码、手机号等不采集）
- 兼容性：覆盖主流浏览器和移动端
- 数据量控制：采样率、数据截断、批量上报

### 面试题 5：Core Web Vitals 中的 LCP、INP、CLS 分别是什么？如何优化？

**答案要点**：

| 指标 | 含义 | 优化方向 |
|---|---|---|
| LCP | 最大内容绘制时间 | 优化首屏关键资源（图片预加载、CDN、SSR）；压缩资源大小；减少渲染阻塞 |
| INP | 交互到下次绘制延迟 | 拆分长任务（使用 scheduler.yield）；避免同步布局计算；使用 Web Worker 处理复杂计算 |
| CLS | 累积布局偏移 | 为图片/视频/广告预留尺寸（width/height）；避免在已有内容上方插入内容；使用 `font-display: optional` |

## 五、避坑指南

| 常见错误 | 产生原因 | 正确做法 |
|---|---|---|
| Sourcemap 文件泄露到生产环境 CDN，任何人都能查看源码 | 构建时未删除 .map 文件，或 CDN 部署脚本未过滤 .map 文件 | 使用 `hidden-source-map`；构建后删除 .map 文件；通过 Sentry CLI 或 Webpack 插件自动上传后删除 |
| 监控 SDK 本身导致页面性能下降，出现卡顿、白屏 | SDK 同步加载阻塞渲染；采集逻辑在主线程执行大量计算；上报请求过多 | SDK 异步加载（async/defer）；使用 requestIdleCallback 执行非关键采集；控制采样率（性能 10%、行为 5%）；批量上报 |
| 错误告警风暴，一个错误重复告警数百次 | 相同错误没有有效去重；告警阈值设置不合理；错误分组规则不完善 | Sentry 配置自定义 fingerprint 合并同类错误；设置告警冷却时间（如 5 分钟内同一错误不重复告警）；按影响用户数而非错误次数设置告警阈值 |

## 补充：埋点体系（数据采集）

> 本节补齐监控体系中的"业务监控"分支：埋点是数据采集的入口，决定了后续所有指标、漏斗、实验分析的数据质量。前三节讲了错误与性能的采集，本节讲"用户做了什么"这件事如何被准确地采集、上报和校验。

### 1. 埋点的三种方式与选型

#### 1.1 概念定义

埋点（Tracking / Instrumentation）是在代码中植入数据采集点的行为，把用户行为转换成结构化事件并上报。按"谁来定义采集点"划分，业界有三类实现：

| 方式 | 定义者 | 采集时机 | 典型代表 |
|---|---|---|---|
| 代码埋点（手动埋点） | 开发者在代码里显式调用 API | 代码执行到埋点调用处 | `track('click_buy', { skuId })` |
| 可视化埋点（圈选埋点） | 运营/产品在可视化工具中圈选元素 | 运行时按配置匹配元素并绑定事件 | 神策、GrowingIO 的可视化圈选 |
| 无痕埋点（全埋点/自动埋点） | SDK 自动采集所有行为 | SDK 监听全局事件，全量上报 | 全埋点 SDK、Google Analytics 增强衡量 |

#### 1.2 底层原理

**代码埋点**：本质是一次函数调用，SDK 把 `eventName + properties` 组装成事件对象入队。优点是语义精确、参数可控；缺点是每加一个埋点都要改代码 + 发版，运营需求响应慢。

**可视化埋点**：本质是"把代码埋点的调用点外置成配置"。工具分两部分：

1. **圈选态**：在页面中注入编辑器 SDK，拦截点击事件并阻止默认行为，根据被点元素生成一个**元素唯一路径**（DOM 层级路径 / XPath + 元素特征），连同事件类型、事件名、参数一起保存到配置中心。
2. **运行态**：业务页面加载 SDK 后拉取配置，用同一套路径生成算法在运行时匹配元素，命中后自动绑定监听并上报。

```
圈选态：运营点击「立即购买」按钮
  → 生成路径：div.product-card > div.actions > button:nth-child(1)
  → 补充稳定特征：text="立即购买"
  → 保存配置：{ event: 'click_buy', selector: '...', features: {...} }
运行态：SDK 拉取配置 → 按 selector 查询元素 → 命中则 addEventListener → 上报
```

它的最大难点是**元素路径不稳定**：动态 `class`、列表项索引变化、A/B 实验导致 DOM 结构差异，都会让路径失配。所以成熟的圈选工具都会把"路径 + 稳定特征（`id`、`data-*`、文本、相对位置）"组合打分，并支持手工修正。

**无痕埋点**：本质是"把代码埋点的语义推断交给数据侧"。SDK 只做通用的自动采集，例如全局监听 `click` 采集所有可点击元素、监听路由变化采集所有 PV。优点是零开发成本、历史数据可回溯；缺点是数据量大、缺少业务语义（不知道"这个按钮是购买还是收藏"），需要在数据侧用元素路径做二次映射。

#### 1.3 选型对比

| 维度 | 代码埋点 | 可视化埋点 | 无痕埋点 |
|---|---|---|---|
| 开发成本 | 高（每个点都要写） | 低（圈选即用） | 极低（一次接入） |
| 运营自主性 | 低（依赖开发排期） | 高（无需发版） | 中（需数据侧配置映射） |
| 业务语义 | 精确 | 精确（人工圈选） | 弱（需推断） |
| 参数灵活度 | 高（可带任意业务参数） | 中（受限于可提取的 DOM 信息） | 低（只能采集 DOM 可见信息） |
| 数据量 | 可控 | 可控 | 大（全量行为） |
| 元素稳定性要求 | 无（直接绑定） | 高（依赖路径匹配） | 高（依赖路径聚合） |
| 维护成本 | 中（散落在业务代码中） | 中（配置漂移、需定期巡检） | 低 |
| 适用场景 | 核心转化链路、需要业务参数的场景 | 运营活动页、频繁调整的页面 | 用户行为探索、路径分析、历史回溯 |

**选型建议**：不要三选一，而是**分层组合**。核心链路（支付、下单）用代码埋点保证准确；运营页面用可视化埋点保证效率；全局行为用无痕埋点做探索性分析。三者共用同一套数据模型和上报通道，才能在数据侧统一分析。

#### 1.4 面试常见问法

- "可视化埋点的原理是什么？为什么元素路径会失效？" → 答配置外置 + 路径匹配，失效源于动态 class / 列表索引 / DOM 结构变更。
- "全埋点能不能替代代码埋点？" → 不能，缺业务语义与业务参数，且数据量大、聚合成本高，只适合探索性分析。
- "如果让你为电商项目设计埋点方案，怎么选？" → 分层组合 + 统一数据模型 + 核心链路代码埋点。

#### 1.5 易错点

- 把"无痕埋点"理解成"不用埋点"：它仍然需要 SDK 采集与数据侧的元素映射，只是把定义工作后移。
- 可视化埋点的配置与页面版本强耦合：页面改版后旧配置静默失效，需要埋点配置巡检机制（定期跑一遍配置匹配率）。
- 三种方式用三套数据模型，导致数据侧无法统一分析——这是最常见的架构性错误。

### 2. 埋点数据模型设计

#### 2.1 概念定义

一个可分析的事件模型通常遵循"**1 个事件 + N 个属性 + 公共参数**"的结构，参考 Google Analytics 4 与 Snowplow 的设计：

```typescript
// 事件模型（Event Model）
interface TrackEvent {
  // ---------- 事件标识 ----------
  event_id: string;        // 事件唯一 ID（UUID），用于服务端幂等去重
  event: string;           // 事件名，如 'page_view' / 'click_buy' / 'item_exposure'
  event_type: EventType;   // 事件大类：pv / click / exposure / custom / perf

  // ---------- 业务属性（每个事件不同） ----------
  properties: Record<string, string | number | boolean | null>;

  // ---------- 公共参数（所有事件都带） ----------
  common: CommonParams;

  // ---------- 时间 ----------
  timestamp: number;       // 客户端发生时间（毫秒）
  timezone: string;        // 时区偏移，如 'Asia/Shanghai'，避免跨时区口径错乱
}

type EventType = 'pv' | 'click' | 'exposure' | 'custom' | 'perf';

interface CommonParams {
  app_id: string;          // 应用标识（多应用共用一套采集时必需）
  app_version: string;     // 应用版本，用于按版本对比
  sdk_version: string;     // SDK 版本，SDK 升级后的行为差异可追溯
  platform: 'web' | 'ios' | 'android';
  // 用户标识（见 2.3）
  anonymous_id: string;    // 匿名 ID，首访生成后持久化
  user_id: string | null;  // 登录 ID，未登录为 null
  // 页面上下文
  page_url: string;
  page_path: string;       // 去掉 query 的路径，便于聚合
  page_title: string;
  referrer: string;
  // 实验与渠道（见 05 章）
  experiment?: Record<string, string>;  // { exp_id: 'variant' }
  utm_source?: string;
  // 设备与环境
  screen: string;          // '1440x900'
  viewport: string;
  device_id: string;       // 设备指纹（谨慎使用，涉及隐私合规）
  network: string;         // '4g' / 'wifi'
}
```

#### 2.2 底层原理

**为什么必须把公共参数独立出来**：公共参数是"所有事件的维度基线"。如果把它混进 `properties`，会出现两个问题：

1. **口径不一致**：不同开发者漏带 `app_version`，导致版本对比时数据缺口。
2. **无法做全局切分**：分析侧需要在任意事件上按 `platform` / `experiment` 切分，公共参数必须由 SDK 统一注入，不依赖业务方手写。

**事件名的命名规范**：推荐 `{对象}_{动作}` 的蛇形命名（`item_exposure`、`button_click`、`order_submit`），对象与动作各自维护枚举。命名混乱是埋点治理中返工成本最高的部分——同一件事出现 `clickBuy`、`buy_click`、`click_buy_btn` 三种写法，数据侧就无法聚合。

**属性类型约束**：属性值只允许标量（字符串/数字/布尔/null）。嵌套对象和数组要扁平化（`{ sku: { id, price } }` → `sku_id`、`sku_price`），因为大多数数据仓库的宽表结构不擅长处理变长嵌套字段。

**事件模型的两种流派**：

| 流派 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| 事件表（Event） | 一行一个事件，属性打平 | 灵活、易扩展 | 属性膨胀、查询需大量 `CASE WHEN` |
| 对象-动作表（Object-Action） | 按业务对象建模（Order/Item/User） | 语义清晰、易治理 | 建模成本高、变更需评审 |

前端埋点通常从事件表起步，规模变大后按业务域收敛成对象-动作模型。

#### 2.3 代码示例：SDK 侧的统一事件构造

```typescript
// ========== 事件构造器：把业务参数与公共参数组装成标准事件 ==========

class EventBuilder {
  private commonParams: Partial<CommonParams> = {};
  private experimentContext: Record<string, string> = {};

  // 应用启动时由 SDK 注入一次，之后不再变化
  public setCommonParams(params: Partial<CommonParams>): void {
    this.commonParams = { ...this.commonParams, ...params };
  }

  // 登录/登出时更新用户标识（见 8.4 的 ID 打通）
  public setUserId(userId: string | null): void {
    this.commonParams.user_id = userId;
  }

  // 实验 SDK 分流后回写，保证每个事件都带上分流信息
  public setExperiment(experimentId: string, variant: string): void {
    this.experimentContext[experimentId] = variant;
  }

  public build(
    event: string,
    eventType: EventType,
    properties: Record<string, unknown> = {}
  ): TrackEvent {
    return {
      event_id: this.uuid(),              // 幂等去重的关键，见第 7 节
      event,
      event_type: eventType,
      // 业务属性必须扁平化为标量，嵌套对象在这里被拒绝（开发环境直接报错）
      properties: this.flatten(properties),
      common: {
        // 每次构造时读取实时上下文，而不是初始化时快照
        page_url: location.href,
        page_path: location.pathname,
        page_title: document.title,
        referrer: document.referrer,
        viewport: `${window.innerWidth}x${window.innerHeight}`,
        screen: `${window.screen.width}x${window.screen.height}`,
        experiment: Object.keys(this.experimentContext).length
          ? { ...this.experimentContext }
          : undefined,
        ...this.commonParams,
      } as CommonParams,
      timestamp: Date.now(),
      timezone: Intl.DateTimeFormat().resolvedOptions().timeZone,
    };
  }

  // 扁平化：{ sku: { id: 1 } } → { sku_id: 1 }
  private flatten(
    obj: Record<string, unknown>,
    prefix = ''
  ): Record<string, string | number | boolean | null> {
    const result: Record<string, string | number | boolean | null> = {};
    for (const [key, value] of Object.entries(obj)) {
      const fullKey = prefix ? `${prefix}_${key}` : key;
      if (value === null || ['string', 'number', 'boolean'].includes(typeof value)) {
        result[fullKey] = value as string | number | boolean | null;
      } else if (typeof value === 'object' && !Array.isArray(value)) {
        Object.assign(result, this.flatten(value as Record<string, unknown>, fullKey));
      } else if (Array.isArray(value)) {
        // 数组统一序列化为逗号分隔字符串，避免属性类型不一致
        result[fullKey] = value.join(',');
      } else if (value !== undefined) {
        // 开发环境暴露问题，生产环境降级为字符串，避免因埋点参数导致业务报错
        if (import.meta.env.DEV) {
          throw new TypeError(`[EventBuilder] 不支持的属性类型: ${fullKey}`);
        }
        result[fullKey] = String(value);
      }
    }
    return result;
  }

  private uuid(): string {
    // crypto.randomUUID 需要安全上下文（HTTPS / localhost）
    return typeof crypto.randomUUID === 'function'
      ? crypto.randomUUID()
      : `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
  }
}
```

#### 2.4 面试常见问法

- "埋点的数据模型怎么设计？" → 事件 + 属性 + 公共参数三层，强调公共参数由 SDK 统一注入、属性扁平化、事件名枚举化。
- "为什么公共参数不能放在 properties 里？" → 口径一致性 + 全局可切分。
- "事件名怎么规范？" → `{对象}_{动作}` 蛇形命名 + 枚举管理 + 评审。

#### 2.5 易错点

- 公共参数在 SDK 初始化时"快照"一次，导致 SPA 路由切换后 `page_path` 永远是首页——必须每次构造事件时实时读取。
- 属性值类型不统一（有时 `sku_id: 123`，有时 `'123'`），数据仓库做聚合时出现同值不同键。
- 用户标识只在登录后采集，未登录行为没有 `anonymous_id`，导致转化漏斗前半段数据缺失。
- 埋点参数里带敏感信息（手机号、身份证、token），既违反合规要求，也会让上报体积极速膨胀。

### 3. 曝光埋点

#### 3.1 概念定义

曝光（Exposure / Impression）指元素在用户视口中**真实可见**。它区别于"元素被渲染"：`<img>` 已经加载完成，但用户滚动到屏幕外时不算曝光。曝光埋点是推荐、广告、列表、活动位等"内容消费类"指标的分母，直接决定 CTR（点击率）口径是否可信。

#### 3.2 底层原理：IntersectionObserver

`IntersectionObserver` 异步监听目标元素与视口（或指定 `root`）的交叉状态，回调参数 `IntersectionObserverEntry` 提供：

| 属性 | 含义 |
|---|---|
| `isIntersecting` | 本次回调时是否与 root 相交 |
| `intersectionRatio` | 相交面积占目标元素面积的比例（0-1） |
| `boundingClientRect` | 目标元素相对视口的矩形 |
| `intersectionRect` | 相交区域矩形 |
| `rootBounds` | root 的矩形 |
| `time` | 交叉状态变化的时间戳 |
| `target` | 被观察的元素 |

它的优势是**不依赖滚动事件**：交叉计算由浏览器在合成阶段完成，避免在 `scroll` 回调里反复调用 `getBoundingClientRect()` 触发强制同步布局（layout thrashing）。

```typescript
// ========== 曝光采集：阈值 + 停留时长 + 去重 ==========

interface ExposureOptions {
  minRatio?: number;      // 最小可见比例，默认 0.5
  minDuration?: number;   // 最小停留时长（ms），默认 500
  once?: boolean;         // 同一元素是否只上报一次，默认 true
}

class ExposureTracker {
  private observer: IntersectionObserver;
  // 记录每个元素的"可见起始时间"，用于计算停留时长
  private visibleSince = new WeakMap<Element, number>();
  // 已上报过的元素（once = true 时用于去重）
  private reported = new WeakSet<Element>();
  private timers = new WeakMap<Element, number>();
  private options: Required<ExposureOptions>;

  constructor(
    private onExpose: (el: HTMLElement, ratio: number, duration: number) => void,
    options: ExposureOptions = {}
  ) {
    this.options = {
      minRatio: options.minRatio ?? 0.5,
      minDuration: options.minDuration ?? 500,
      once: options.once ?? true,
    };

    this.observer = new IntersectionObserver(
      (entries) => this.handleEntries(entries),
      {
        // threshold 传数组时，每次跨越任一阈值都会回调。
        // 必须包含 0，否则元素"从可见变为完全不可见"时不会回调，
        // 停留时长的计时器无法被清除。
        threshold: [0, this.options.minRatio],
        // rootMargin 可以理解为"视口的外扩/收缩"：
        // 正数 = 提前曝光（如提前 100px 就认为曝光），
        // 负数 = 延迟曝光（要求元素更深入视口才算曝光）。
        rootMargin: '0px',
      }
    );
  }

  private handleEntries(entries: IntersectionObserverEntry[]): void {
    for (const entry of entries) {
      const el = entry.target as HTMLElement;

      if (entry.isIntersecting && entry.intersectionRatio >= this.options.minRatio) {
        // ---- 进入可见状态：启动停留计时 ----
        this.visibleSince.set(el, entry.time);
        this.startDwellTimer(el, entry.intersectionRatio);
      } else {
        // ---- 离开可见状态：清理计时 ----
        this.visibleSince.delete(el);
        const timer = this.timers.get(el);
        if (timer !== undefined) {
          clearTimeout(timer);
          this.timers.delete(el);
        }
      }
    }
  }

  // 停留时长校验：可见后必须"连续"停留 minDuration 才算有效曝光
  private startDwellTimer(el: HTMLElement, ratio: number): void {
    if (this.timers.has(el)) return; // 已在计时，避免重复启动
    const timer = window.setTimeout(() => {
      this.timers.delete(el);
      this.commit(el, ratio);
    }, this.options.minDuration);
    this.timers.set(el, timer);
  }

  private commit(el: HTMLElement, ratio: number): void {
    if (this.options.once && this.reported.has(el)) return;
    const start = this.visibleSince.get(el);
    if (start === undefined) return; // 计时期间已离开视口

    this.reported.add(el);
    this.onExpose(el, ratio, performance.now() - start);

    // once = true 时立刻取消观察，避免同一个元素反复触发回调
    if (this.options.once) this.observer.unobserve(el);
  }

  // 首屏曝光：DOM 就绪后立即观察，IO 会在下一帧给出初始交叉状态
  public observeAll(selector: string): void {
    document.querySelectorAll<HTMLElement>(selector).forEach((el) => {
      if (this.reported.has(el)) return;
      this.observer.observe(el);
    });
  }

  public destroy(): void {
    this.observer.disconnect();
  }
}
```

**曝光埋点的三个判定要素**：

```
① 可见比例（ratio）：元素有多少面积进入了视口
   - ratio = 0.5 表示元素一半面积可见
   - 列表项高度远大于视口时，ratio 永远达不到 0.5，
     此时应改用「可见面积像素数」或降低阈值（如 0.1）

② 停留时长（dwell time）：可见状态持续多久
   - 快速划过（滚轮一划而过）不应算曝光，否则曝光量虚高
   - 实现要点：可见时 setTimeout，不可见时 clearTimeout
   - 必须保证 threshold 包含 0，否则离开视口时无法清理计时器

③ 去重策略：
   - 会话内一次（最常用）：WeakSet 记录 + unobserve
   - 每次进入视口都算一次：不 unobserve，但需要冷却时间
     （如 5 秒内重复进入不重复计数），否则抖动会产生海量曝光
```

**首屏曝光与常规曝光的差异**：首屏元素在页面加载时就已经处于视口内，不存在"从不可见变为可见"的过程。`IntersectionObserver` 在 `observe()` 后会在下一个渲染帧异步回调一次初始状态（`isIntersecting` 为 `true`），因此**不需要额外补一次首屏检测**。但如果元素在 `observe()` 之前就已经被渲染且 `once` 去重依赖回调顺序，则需要保证"先 observe 再上报"的顺序，否则首屏曝光会与列表数据渲染竞态。

**为什么不用 `scroll` 事件**：

| 方案 | 精度 | 性能 | 说明 |
|---|---|---|---|
| `scroll` + `getBoundingClientRect` | 高 | 差 | 每次滚动都触发强制同步布局，主线程压力大 |
| `scroll` + `requestAnimationFrame` 节流 | 中 | 中 | 需要自己实现节流与去重，滚动停止时可能漏判 |
| `IntersectionObserver` | 高 | 好 | 浏览器在合成阶段计算，主线程零开销，异步回调 |

#### 3.3 面试常见问法

- "曝光埋点怎么实现？" → IntersectionObserver + 可见比例阈值 + 停留时长 + 去重，说明为何不用 scroll。
- "为什么 threshold 里必须包含 0？" → 元素从可见变为不可见时才会回调，用于清理停留计时器。
- "曝光量虚高怎么排查？" → 检查是否缺少停留时长校验、是否未去重、是否 rootMargin 用了过大的正值。

#### 3.4 易错点

- `threshold: 0.5` 却没有在数组里加 `0`：元素离开视口时不再回调，`setTimeout` 残留，用户滚回来时重复计入停留时长。
- 用 `once = true` 的 `unobserve` 去重，但列表使用虚拟滚动复用 DOM 节点，元素被复用时 `WeakSet` 里已存在记录，导致新内容永远不曝光——虚拟列表必须把去重键设为"内容 ID"而非 DOM 节点。
- `rootMargin` 给正的大值（如 `2000px`）导致屏幕外的元素也被判为曝光，曝光量整体虚高。
- 元素被 `display: none` 或被其他元素遮挡时，`IntersectionObserver` 仍可能报告相交（它不检测遮挡），需要配合 `document.elementFromPoint` 或业务兜底。

### 4. 点击埋点

#### 4.1 概念定义

点击埋点采集用户的点击行为，是转化漏斗的核心数据源。工程上分为两种实现：**逐元素绑定**（在每个按钮上 `addEventListener`）与**事件委托统一采集**（在 `document` 上监听一次，按元素标识分发）。

#### 4.2 底层原理：事件委托 + 元素标识

**为什么用捕获阶段监听**：在 `document` 上用 `addEventListener('click', handler, true)` 注册捕获阶段监听，回调会在事件从 `window` 向目标元素传播的过程中触发，早于业务代码在冒泡阶段调用 `stopPropagation()`。这能避免"业务组件阻止了事件冒泡导致埋点丢失"这一最常见的漏埋原因。

```typescript
// ========== 点击采集：事件委托 + data-track 标识 ==========

// 元素标识规范（推荐）
// data-track="{模块}_{对象}_{动作}"，如：
// <button data-track="cart_submit_order">提交订单</button>
// <a data-track="nav_go_profile" href="/profile">个人中心</a>
// 需要额外参数时用 data-track-params 传 JSON：
// <button data-track="item_add_cart"
//         data-track-params='{"item_id":"p1","source":"list"}'>加入购物车</button>

class ClickTracker {
  constructor(
    private onTrack: (
      trackId: string,
      params: Record<string, unknown>,
      el: HTMLElement
    ) => void
  ) {
    // 捕获阶段监听，早于业务代码的 stopPropagation
    document.addEventListener('click', this.handleClick, true);
  }

  private handleClick = (e: MouseEvent): void => {
    const target = e.target as HTMLElement | null;
    if (!target) return;

    // closest 会沿祖先链向上查找，天然支持"点击图标但标识在按钮上"的场景
    const el = target.closest<HTMLElement>('[data-track]');
    if (!el) return;

    const trackId = el.dataset.track;
    if (!trackId) return;

    // 解析附加参数：解析失败不能影响业务点击，只降级为无参数
    let params: Record<string, unknown> = {};
    const rawParams = el.dataset.trackParams;
    if (rawParams) {
      try {
        params = JSON.parse(rawParams);
      } catch {
        params = { _parse_error: rawParams.slice(0, 100) };
      }
    }

    this.onTrack(trackId, params, el);
  };

  public destroy(): void {
    document.removeEventListener('click', this.handleClick, true);
  }
}
```

**data-track 方案的三个设计要点**：

1. **标识与实现解耦**：标识写在 HTML 属性上，而不是 JS 调用点。这样元素被重构、组件被替换时，只要属性保留，埋点就不丢；运营改文案也不会影响埋点。
2. **可被自动化校验**：构建期或 E2E 阶段可以扫描代码中的 `data-track` 与埋点配置表做 diff，实现"漏埋/多埋"的自动检测（见第 7 节）。
3. **就近携带参数**：`data-track-params` 让参数跟随元素，避免在回调里反查 DOM 或依赖闭包变量。

**事件委托 vs 逐元素绑定**：

| 维度 | 事件委托 | 逐元素绑定 |
|---|---|---|
| 监听器数量 | 1 个 | N 个 |
| 动态渲染元素 | 天然支持 | 需要在渲染后重新绑定 |
| 内存占用 | 低 | 高（列表场景下线性增长） |
| 参数传递 | 依赖 `data-*` 属性 | 可直接用闭包变量 |
| 捕获阶段支持 | 支持（可避免 `stopPropagation` 漏埋） | 需逐个元素指定 |
| 适用场景 | 全局统一采集 | 少量、参数复杂的元素 |

**A/B 实验与点击埋点的关系**：实验分析需要把"点击/转化"归因到分流分组，因此埋点事件必须携带分流信息（公共参数中的 `experiment` 字段，见 05 章）。如果埋点在分流完成前就上报（例如首屏点击先于实验配置拉取完成），该事件会缺失实验标识，只能被丢弃或落入"未分流"桶，造成样本流失。工程上的标准做法是：**实验 SDK 初始化完成后再放行埋点上报**，或让埋点在 SDK 未就绪时先入队、等分流信息补齐后统一 flush。

#### 4.3 面试常见问法

- "全站点击埋点怎么实现？" → `document` 捕获阶段 + `closest('[data-track]')` + `data-track-params`，说明为何用捕获阶段。
- "为什么不用每个按钮单独绑定？" → 监听器数量、动态元素、内存、漏埋风险。
- "埋点和 A/B 实验如何打通？" → 分流信息作为公共参数随事件上报，且保证上报发生在分流之后。

#### 4.4 易错点

- 在冒泡阶段监听 `document`：业务组件的 `stopPropagation` 会让埋点静默丢失。
- 用 `e.target` 直接读 `data-track`：点到按钮内的图标/文字节点时读不到，必须用 `closest` 向上查找。
- 埋点回调里做同步耗时操作（如 JSON 序列化大对象、写 localStorage），在点击密集的列表页造成掉帧——应只入队，序列化与上报放到 `requestIdleCallback`。
- `data-track` 命名重复（多个模块用了同一个标识），数据侧无法区分来源，必须在标识里带模块前缀并做唯一性校验。

### 5. 自定义埋点（PV/UV、停留时长、性能埋点）

#### 5.1 概念定义

自定义埋点指业务语义驱动的指标采集，最常见的三类是 PV/UV（流量）、页面停留时长（参与度）、性能埋点（体验与业务指标的关联分析）。

#### 5.2 底层原理

**PV（Page View）**：页面被浏览一次计一次。SPA 的难点在于路由切换不触发页面刷新，必须劫持路由 API：

```typescript
// ========== PV 采集：SPA 路由监听 ==========

class PVTracker {
  private lastPath = '';

  constructor(private onPV: (path: string, from: string) => void) {
    this.report(); // 首次进入页面
    this.patchHistory();
    window.addEventListener('popstate', () => this.report()); // 浏览器前进/后退
    window.addEventListener('hashchange', () => this.report()); // hash 路由
  }

  private patchHistory(): void {
    const originalPush = history.pushState;
    // pushState：新增历史记录，应计一次 PV
    history.pushState = (...args) => {
      const result = originalPush.apply(history, args);
      this.report();
      return result;
    };

    const originalReplace = history.replaceState;
    // replaceState：替换当前历史记录（常用于参数同步、重定向兜底），
    // 不产生新的浏览行为，因此不计 PV，否则会造成 PV 虚高
    history.replaceState = (...args) => {
      return originalReplace.apply(history, args);
    };
  }

  private report(): void {
    const path = location.pathname + location.search;
    if (path === this.lastPath) return; // 同路径重复触发时去重
    const from = this.lastPath;
    this.lastPath = path;
    this.onPV(path, from);
  }
}
```

**UV（Unique Visitor）**：按访客去重。前端只负责生成并持久化 `anonymous_id`，去重由服务端按时间窗口完成：

```typescript
// 匿名 ID 生成与持久化：优先 cookie（可与服务端共享），降级 localStorage
function getAnonymousId(): string {
  const KEY = '_an_id';
  const fromCookie = document.cookie
    .split('; ')
    .find((c) => c.startsWith(`${KEY}=`))
    ?.split('=')[1];
  if (fromCookie) return fromCookie;

  const id = `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
  // 365 天有效期；SameSite=Lax 兼顾跳转场景与 CSRF 防护
  document.cookie = `${KEY}=${id}; max-age=${365 * 24 * 3600}; path=/; SameSite=Lax`;
  return id;
}
```

**页面停留时长**：必须区分"页面打开时长"与"用户真正在看的时间"。后台标签页、锁屏、最小化都不应计入：

```typescript
// ========== 停留时长：累加"可见时长"而非墙钟时长 ==========

class DwellTimeTracker {
  private visibleStart = 0;
  private visibleTotal = 0; // 累计可见毫秒数

  constructor(private onLeave: (duration: number) => void) {
    this.visibleStart = performance.now();
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        this.accumulate();
        this.onLeave(this.visibleTotal); // 隐藏即上报，防止被直接杀掉时丢数据
      } else {
        this.visibleStart = performance.now(); // 回到前台继续累计
      }
    });

    // pagehide 作为兜底：移动端浏览器在关闭标签页时不一定触发 visibilitychange
    window.addEventListener('pagehide', () => {
      this.accumulate();
      this.onLeave(this.visibleTotal);
    });
  }

  private accumulate(): void {
    if (this.visibleStart === 0) return;
    this.visibleTotal += performance.now() - this.visibleStart;
    this.visibleStart = 0;
  }
}
```

> 会话（Session）口径：业界常用"30 分钟无操作即切分会话"（GA4 默认），前端需要维护"最后操作时间"，超过阈值时生成新的 `session_id`。停留时长与 PV/UV 都应按 `session_id` 维度聚合。

**性能埋点**：把性能指标与业务指标关联，回答"慢 1 秒损失多少转化"：

```typescript
// ========== 性能埋点：性能指标 + 业务转化 联合上报 ==========

// 思路：在关键业务节点（如支付成功）上，附带当前页面的性能快照，
// 数据侧即可按 LCP / INP 分桶计算转化率。
function trackConversionWithPerf(perf: PerfMetrics, orderId: string): void {
  track('order_submit_success', {
    order_id: orderId,
    // 性能快照（数值型，便于分桶聚合）
    lcp_ms: Math.round(perf.LCP ?? 0),
    inp_ms: Math.round(perf.INP ?? 0),
    cls_score: Number((perf.CLS ?? 0).toFixed(4)),
    ttfb_ms: Math.round(perf.TTFB ?? 0),
  });
}
```

#### 5.3 面试常见问法

- "SPA 的 PV 怎么统计？`replaceState` 要不要计 PV？" → 劫持 `pushState` + `popstate` + `hashchange`；`replaceState` 不产生新浏览行为，通常不计，否则 PV 虚高。
- "停留时长怎么算才准？" → 累加 `visibilitychange` 的可见时长，而不是 `Date.now() - startTime`；`pagehide` 兜底上报。
- "UV 怎么统计？" → 前端生成并持久化匿名 ID，服务端按窗口去重。
- "性能数据怎么和业务挂钩？" → 性能指标作为业务事件的属性上报，数据侧做分桶分析。

#### 5.4 易错点

- 只监听 `pushState` 而漏掉 `popstate`：浏览器前进/后退不产生 PV，导致流量数据偏低。
- 用墙钟时间算停留时长：用户把页面挂在后台一整天，时长数据被严重污染。
- 匿名 ID 存在 `sessionStorage` 里，关闭标签页即失效，UV 被严重高估。
- 首次 PV 在 SDK 初始化之前触发（路由框架先于 SDK 加载），首屏 PV 丢失——SDK 必须尽早同步执行或由路由框架主动上报首屏。

### 6. 上报时机与批量上报策略

#### 6.1 概念定义

埋点事件从产生到送达服务端之间有一个**缓冲队列**。上报策略决定何时把队列刷出，本质是在"实时性"、"请求数量"和"数据完整性"三者之间取舍。

#### 6.2 底层原理

**四种触发时机**：

| 触发时机 | 触发条件 | 目的 |
|---|---|---|
| 定量触发 | 队列长度 ≥ `batchSize`（如 10 条） | 控制单请求体积，避免队列无限增长 |
| 定时触发 | 每隔 `flushInterval`（如 5s） | 保证低流量场景下的数据实时性 |
| 关键事件触发 | 白名单事件（支付成功、错误） | 关键数据不因缓冲丢失，立即上报 |
| 生命周期触发 | `visibilitychange` → hidden、`pagehide` | 页面即将离开时强制 flush，防丢数据 |

**批量上报的三个关键设计**：

```typescript
// ========== 批量上报队列 ==========

interface QueuedEvent {
  event_id: string;
  payload: TrackEvent;
  retryCount: number;
  enqueuedAt: number;
}

class BatchReporter {
  private queue: QueuedEvent[] = [];
  private readonly maxQueueSize = 200;   // 内存上限，防止长时间离线导致内存泄漏
  private readonly batchSize = 10;
  private readonly flushInterval = 5000;
  private readonly maxRetry = 3;
  private timer: number | null = null;

  constructor(private endpoint: string) {
    this.timer = window.setInterval(() => this.flush('timer'), this.flushInterval);
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') this.flush('hidden');
    });
    // pagehide 覆盖移动端"直接关闭标签页"场景，此时 visibilitychange 可能不触发
    window.addEventListener('pagehide', () => this.flush('pagehide'));
  }

  public enqueue(event: TrackEvent, immediate = false): void {
    this.queue.push({
      event_id: event.event_id,
      payload: event,
      retryCount: 0,
      enqueuedAt: Date.now(),
    });

    // 队列超限：丢弃最旧的数据而不是最新的。
    // 原因是最新数据更可能属于当前会话，分析价值更高；
    // 但若业务要求"不丢关键事件"，则应改为丢弃非关键事件并上报丢弃计数。
    while (this.queue.length > this.maxQueueSize) {
      this.queue.shift();
      // 丢弃行为本身也要被观测，否则数据量下降无法归因
      this.countDropped();
    }

    if (immediate) {
      this.flush('immediate');
    } else if (this.queue.length >= this.batchSize) {
      this.flush('batch-full');
    }
  }

  private async flush(reason: string): Promise<void> {
    if (this.queue.length === 0) return;
    const batch = this.queue.splice(0, this.queue.length);

    // 页面卸载场景必须用 sendBeacon：它由浏览器保证发送，
    // 且不阻塞页面卸载（fetch 的 keepalive 也可，但有 64KB 总量限制）
    const useBeacon = reason === 'hidden' || reason === 'pagehide';
    const body = JSON.stringify({ events: batch.map((b) => b.payload) });

    if (useBeacon) {
      const ok = navigator.sendBeacon(
        this.endpoint,
        new Blob([body], { type: 'application/json' })
      );
      // sendBeacon 返回 false 表示浏览器无法入队（通常是总大小超限），
      // 此时只能退化为本地持久化，等下次会话补发
      if (!ok) await this.persistOffline(batch);
      return;
    }

    try {
      const res = await fetch(this.endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body,
        keepalive: true,
      });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
    } catch {
      await this.retryOrPersist(batch);
    }
  }

  // 指数退避重试：1s → 2s → 4s，超过上限则落盘等待下次会话补发
  private async retryOrPersist(batch: QueuedEvent[]): Promise<void> {
    const retryable = batch.filter((b) => ++b.retryCount <= this.maxRetry);
    if (retryable.length > 0) {
      this.queue.unshift(...retryable);
    }
    const failed = batch.filter((b) => b.retryCount > this.maxRetry);
    if (failed.length > 0) await this.persistOffline(failed);
  }

  private async persistOffline(batch: QueuedEvent[]): Promise<void> {
    // 见 05 章「离线补发」：写入 IndexedDB 队列，下次会话启动时补发
    await offlineStore.save(batch.map((b) => b.payload));
  }

  private countDropped(): void { /* 上报 dropped 计数指标 */ }
}
```

**批量上报的收益与代价**：

| 维度 | 单条实时上报 | 批量上报 |
|---|---|---|
| 请求数 | 事件数 1:1，QPS 高 | 约为事件数 / batchSize |
| 单请求体积 | 小（但含完整公共参数，冗余高） | 大（公共参数可提为批次级） |
| 数据实时性 | 高 | 有 `flushInterval` 级延迟 |
| 丢数据风险 | 低（单条失败影响面小） | 中（整批失败） |
| 页面卸载可靠性 | 差 | 好（一次 beacon 发完） |
| 服务端压力 | 高（连接数、限流风险） | 低 |

**优化技巧**：批次内把公共参数上提到批次级别，服务端再回填到每条事件，可显著压缩 payload：

```json

  { "event": "click_buy", "common": { "app_id": "shop", "app_version": "1.2.3", "page_path": "/p/1" } },
  { "event": "click_cart", "common": { "app_id": "shop", "app_version": "1.2.3", "page_path": "/p/1" } }
]}

// 优化后：公共参数只出现一次
{ "common": { "app_id": "shop", "app_version": "1.2.3", "page_path": "/p/1" },
  "events": [ { "event": "click_buy" }, { "event": "click_cart" } ] }
```

#### 6.3 面试常见问法

- "埋点数据什么时候上报？为什么不全量实时上报？" → 四种触发时机 + 请求数/服务端压力/卸载可靠性权衡。
- "页面关闭时怎么保证数据不丢？" → `visibilitychange`/`pagehide` + `sendBeacon`，说明 `unload` 不可靠（详见 05 章）。
- "队列满了丢哪一端的数据？" → 默认丢最旧，并上报丢弃计数指标使数据量下降可归因。
- "批量上报怎么压缩体积？" → 公共参数上提到批次级 + 属性扁平化 + 采样。

#### 6.4 易错点

- 只在 `beforeunload`/`unload` 里 flush：移动端这两个事件经常不触发，数据静默丢失。
- 用 `fetch`（不带 `keepalive`）在卸载时上报，请求会被浏览器直接取消。
- 定时器在后台标签页被节流（Chrome 后台 `setInterval` 最低 1 分钟），导致上报延迟远超预期——后台应依赖生命周期事件而非定时器。
- 队列无上限，用户长时间离线时内存持续增长，最终 OOM 或页面卡死。
- 重试没有上限和退避，服务端故障时客户端形成重试风暴，加剧故障。

### 7. 埋点数据的质量保障

#### 7.1 概念定义

埋点质量问题是数据可信度的最大杀手，可归为三类：**漏埋**（该采的没采到）、**重复埋**（同一行为被计多次）、**参数错误**（采到了但值不对）。

#### 7.2 底层原理与治理手段

| 问题类型 | 典型表现 | 根因 | 治理手段 |
|---|---|---|---|
| 漏埋 | 漏斗某一步骤数据为 0 或骤降 | 代码分支未覆盖、`stopPropagation` 阻断、组件重构丢失埋点、上报被卸载事件取消 | 埋点需求与 PRD 同步评审、`data-track` 声明式标识、捕获阶段监听、E2E 断言埋点请求、埋点配置与代码 diff 校验 |
| 重复埋 | 同一行为被计 2-3 次 | 路由事件重复触发（`pushState` + `popstate`）、组件多次挂载、SDK 被重复初始化、重试未幂等 | 事件唯一 `event_id` + 服务端幂等写入、SDK 单例保护、路由路径去重、重试前先查重 |
| 参数错误 | 维度值缺失、枚举值异常、类型不一致 | 属性未做 schema 校验、公共参数快照过期、大小写/空格不一致、时间戳单位混用 | 事件 schema 定义（必填 + 类型 + 枚举）、开发环境运行时断言、数据侧对账告警 |

**三层防线**：

```
第一层：开发期（成本最低，效果最好）
  - 事件 schema 集中定义（如 Zod / JSON Schema），SDK 在 DEV 环境对每个事件做校验
  - 属性值做枚举校验：'ios' | 'android' | 'web'，非法值直接报错而不是静默上报
  - 单测覆盖关键埋点：断言 track 被调用且参数正确（见 15-testing 模块）

第二层：测试期
  - E2E 中拦截上报请求，断言"点击购买后确实发出了 click_buy 事件"
  - 埋点配置与代码静态比对：扫描源码中的 data-track / track() 调用，
    与埋点配置表做 diff，输出"代码里有但配置表没有"（多埋/漏登记）
    和"配置表里有但代码里没有"（漏埋）
  - 埋点验收清单：按 PRD 的埋点文档逐条走查

第三层：线上期
  - 数据量突降告警：同比/环比跌幅超阈值（如 30%）触发告警
  - 关键指标兜底校验：支付成功数（数据侧）与业务库订单数对账
  - 埋点覆盖率看板：曝光量 / PV、点击量 / 曝光量等派生比例异常时告警
  - 参数健康度：枚举值分布、空值率、属性长度分布
```

#### 7.3 面试常见问法

- "怎么保证埋点数据的准确性？" → 三层防线（开发期 schema 校验、测试期 E2E 断言 + 配置 diff、线上期量级告警 + 对账）。
- "线上发现某个埋点数据为 0，怎么排查？" → 从"是否上报（Network）→ 是否触发（调试日志）→ 是否被采样/丢弃（队列丢弃计数）→ 是否服务端过滤"逐层排查。
- "重复埋点怎么根治？" → `event_id` 幂等 + SDK 单例 + 路由去重，服务端做幂等写入而非依赖前端"保证不重复"。

#### 7.4 易错点

- 只在数据侧做去重，前端仍上报大量重复数据，白白消耗流量与服务端资源。
- 埋点校验只在开发环境开启，测试/预发环境未开，问题在上线后才暴露。
- 数据量下降时先怀疑"埋点丢失"，实际是上游业务流量下降——必须同时看业务指标做交叉验证。
- 埋点配置散落在文档里而不进版本库，配置漂移无人知晓。

### 8. 埋点 SDK 的设计要点

#### 8.1 概念定义

埋点 SDK 是一个运行在业务应用中的"数据采集中间件"，对上提供稳定的采集 API，对下屏蔽数据组装、队列、上报、持久化的复杂度。

#### 8.2 架构与关键设计

```typescript
// ========== 埋点 SDK 的分层架构 ==========

// ┌──────────────────────────────────────────────┐
// │  接入层 API                                   │
// │  init / track / trackExposure / setUser       │
// │  setCommonParams / bindExperiment             │
// ├──────────────────────────────────────────────┤
// │  采集插件层（可插拔）                          │
// │  PvPlugin │ ClickPlugin │ ExposurePlugin      │
// │  PerfPlugin │ ErrorPlugin │ RoutePlugin       │
// ├──────────────────────────────────────────────┤
// │  处理层                                       │
// │  EventBuilder（组装）│ Validator（校验）        │
// │  Filter（脱敏/采样）│ Deduplicator（去重）      │
// ├──────────────────────────────────────────────┤
// │  传输层                                       │
// │  Queue → Batch → Transport                    │
// │  sendBeacon │ fetch keepalive │ img           │
// │  IndexedDB 离线队列 + 重试                     │
// └──────────────────────────────────────────────┘

interface TrackSDKConfig {
  appId: string;
  endpoint: string;
  appVersion: string;
  // 采样率：按事件类型分别配置，关键事件全量
  sampleRate?: Record<string, number>;
  // 立即上报的事件白名单（关键转化）
  immediateEvents?: string[];
  batchSize?: number;
  flushInterval?: number;
  maxQueueSize?: number;
  debug?: boolean;
  // 脱敏：命中则丢弃该属性
  sensitiveKeys?: string[];
}

class TrackSDK {
  private static instance: TrackSDK | null = null; // 单例，防止重复初始化
  private builder: EventBuilder;
  private reporter: BatchReporter;
  private plugins: Array<{ name: string; setup: (sdk: TrackSDK) => void }> = [];
  private ready = false;
  private pending: Array<() => void> = [];

  constructor(private config: TrackSDKConfig) {
    this.builder = new EventBuilder();
    this.reporter = new BatchReporter(config.endpoint);
    this.builder.setCommonParams({
      app_id: config.appId,
      app_version: config.appVersion,
      sdk_version: SDK_VERSION,
      anonymous_id: getAnonymousId(),
    });
  }

  public static init(config: TrackSDKConfig): TrackSDK {
    // 单例保护：SPA 中模块被多次 import 或热更新时不会重复挂监听
    if (TrackSDK.instance) return TrackSDK.instance;
    TrackSDK.instance = new TrackSDK(config);
    TrackSDK.instance.bootstrap();
    return TrackSDK.instance;
  }

  private bootstrap(): void {
    this.plugins.forEach((p) => p.setup(this));
    this.ready = true;
    // 放行初始化期间入队的事件（如首屏 PV）
    this.pending.splice(0).forEach((fn) => fn());
  }

  public use(plugin: { name: string; setup: (sdk: TrackSDK) => void }): this {
    this.plugins.push(plugin);
    return this;
  }

  // 对外唯一的上报入口：统一走校验 → 脱敏 → 采样 → 入队
  public track(
    event: string,
    properties: Record<string, unknown> = {},
    options: { immediate?: boolean } = {}
  ): void {
    const run = () => {
      const payload = this.builder.build(event, 'custom', properties);

      if (!this.validate(payload)) return;      // 校验失败：丢弃并计数
      this.sanitize(payload);                   // 脱敏
      if (!this.sample(event)) return;          // 采样

      const immediate =
        options.immediate ?? this.config.immediateEvents?.includes(event) ?? false;
      this.reporter.enqueue(payload, immediate);
    };

    // SDK 未就绪时入队，保证首屏事件不丢（见 4.2 的 A/B 归因问题）
    this.ready ? run() : this.pending.push(run);
  }

  public setUser(userId: string | null): void {
    // 登录/登出时更新，同时把 anonymous_id 一起上报，
    // 服务端据此把匿名阶段的行为与登录用户合并（ID-Mapping）
    this.builder.setUserId(userId);
  }

  private validate(payload: TrackEvent): boolean {
    if (!payload.event || typeof payload.event !== 'string') return false;
    if (payload.event.length > 64) return false;              // 事件名长度约束
    if (JSON.stringify(payload).length > 32 * 1024) return false; // 单事件体积约束
    return true;
  }

  private sanitize(payload: TrackEvent): void {
    const keys = this.config.sensitiveKeys ?? [];
    for (const key of Object.keys(payload.properties)) {
      if (keys.some((k) => key.toLowerCase().includes(k.toLowerCase()))) {
        payload.properties[key] = '[REDACTED]';
      }
    }
  }

  private sample(event: string): boolean {
    const rate = this.config.sampleRate?.[event] ?? 1;
    if (rate >= 1) return true;
    if (rate <= 0) return false;
    return Math.random() < rate;
  }
}
```

**设计要点清单**：

| 要点 | 说明 |
|---|---|
| 统一 API | 只暴露 `track` / `trackExposure` / `setUser` / `setCommonParams`，避免业务方直接操作队列 |
| 插件化采集 | PV、点击、曝光、性能、错误各自独立插件，可按需启用，便于 Tree-shaking 与分包 |
| 单例保护 | 防止多入口、微前端、热更新导致 SDK 被重复初始化、监听器重复注册 |
| 就绪队列 | 初始化完成前的事件先入队，就绪后统一 flush，解决首屏事件与分流信息竞态 |
| 公共参数集中管理 | 由 SDK 注入，业务不感知；页面切换时实时更新 |
| 用户标识打通 | `anonymous_id`（持久化）+ `user_id`（登录后回填），服务端做 ID-Mapping |
| 校验与脱敏前置 | 在 SDK 层拦截非法数据与敏感信息，不依赖服务端补救 |
| 采样分层 | 关键事件全量、高频事件低采样率，采样率作为公共参数上报以便还原真实量级 |
| 体积与性能 | gzip 后控制在 10KB 以内；序列化与上报放在 `requestIdleCallback`；避免同步 IO |
| 降级与兜底 | `sendBeacon` 不可用降级为 `fetch keepalive`，再降级为 img 打点；网络失败落 IndexedDB |
| 版本可追溯 | `sdk_version` 作为公共参数，SDK 升级带来的数据变化可解释 |
| 可观测性 | SDK 自身也要上报丢弃数、失败数、队列长度，否则数据量异常无法归因 |

#### 8.3 面试常见问法

- "如果让你设计一个埋点 SDK，你会怎么分层？" → 接入层 / 插件采集层 / 处理层 / 传输层，并说明每层职责与扩展点。
- "SDK 怎么保证不重复初始化？" → 单例 + 插件注册去重 + 监听器幂等。
- "用户登录前后的行为怎么打通？" → `anonymous_id` 持久化 + 登录后上报 `user_id`，服务端 ID-Mapping。
- "埋点 SDK 体积和性能怎么控制？" → 插件化 + Tree-shaking、空闲回调、批量上报、采样、体积门禁。

#### 8.4 易错点

- SDK 同步执行耗时初始化（读 cookie、建 IndexedDB 连接）阻塞首屏，应拆分为同步注册 + 异步就绪。
- 采样率只在前端生效且不上报，数据侧无法从采样数据还原真实量级。
- 脱敏只做黑名单：新增敏感字段时忘记加名单，应改为白名单采集关键字段。
- SDK 直接 `throw` 影响业务：埋点必须"永远不打断业务"，所有异常在 SDK 内部捕获并降级。
- 微前端场景下多个子应用各自初始化 SDK，导致同一行为被多次上报——需要主应用统一初始化或做跨应用单例。
