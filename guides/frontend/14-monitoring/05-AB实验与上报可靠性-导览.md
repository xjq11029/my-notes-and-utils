# 05-AB实验与上报可靠性 - 导览

---

## 1.1 A/B 实验平台的整体架构（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | A/B 实验是把流量随机分成对照组与实验组、通过指标对比判断改动是否有效的平台化能力，链路为"实验管理平台 → 配置服务 → 客户端 SDK → 数据链路" |
| 能做什么 | 统一管理实验的创建、层/域配置、流量分配、指标定义与启停归档；让前端、iOS、Android、服务端共用一套分流与归因能力 |
| 怎么用 | 平台侧创建实验并配置变体权重 → 配置服务版本化下发 → 客户端 SDK 拉取并缓存配置 → 业务读取变体渲染 → 曝光与转化事件上报 → 数据侧按 variant 聚合做统计检验 |
| 原理和工作流程 | 客户端负责三件事：稳定分流（哈希分桶）、曝光上报（变体真正渲染后）、事件归因（转化事件携带分流信息）；数据链路负责指标计算与显著性判定 |
| 缺点 | 平台建设成本高（分流引擎 + 指标计算 + 统计引擎）；前端埋点与分流不一致会直接导致结论错误；实验数量增长后层/域治理复杂 |

## 1.2 实验与灰度的区别（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 灰度发布是"逐步放量验证稳定性"，A/B 实验是"随机分组比较方案优劣"，两者都做流量切分但目的与判据不同 |
| 能做什么 | 灰度用于降低发布风险（错误率、崩溃率、性能）；实验用于验证业务假设（转化率、留存、GMV）并给出统计显著性结论 |
| 怎么用 | 灰度按 1% → 10% → 100% 逐步放量，异常则回滚；实验按 50/50 或指定比例随机分组，跑满样本量后看主要指标是否显著 |
| 原理和工作流程 | 灰度通常无对照组，判据是技术指标；实验必须有对照组，判据是业务指标 + 统计检验；实践中先用灰度下发实验配置做冒烟，再放量到实验所需样本量 |
| 缺点 | 灰度无法回答"哪个方案更好"；实验有周期长、结论依赖统计正确性的问题；两者混用（把开关当实验）会得到错误结论 |

## 1.3 数据上报可靠性的三个层次（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 上报可靠性分为三层：发送可靠性（能否发出）、送达可靠性（发出后是否丢）、口径可靠性（数据是否正确） |
| 能做什么 | 保证卸载场景不丢数据；网络异常时离线缓存并在恢复后补发；采样后仍能还原真实量级并与业务数据对账 |
| 怎么用 | 发送层选对方式（`fetch keepalive` / `sendBeacon` / img）与时机（`visibilitychange` + `pagehide`）；送达层用 IndexedDB 队列 + 重试 + `event_id` 幂等；口径层用一致性采样并随数据上报采样率 |
| 原理和工作流程 | 事件产生 → 内存缓冲 → 批量/定时/生命周期触发 flush → 失败落盘 → 启动 / `online` / 定时补发 → 服务端按 `event_id` 幂等写入 |
| 缺点 | 三层都需实现，工程成本高；离线队列需要容量与过期治理；服务端幂等需要额外存储与索引 |

## 1.4 SLO 与错误预算（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | SLI 是可测量指标，SLO 是内部目标，SLA 是对外合同承诺，错误预算 = `1 - SLO`（如 99.9% 对应每月约 43.2 分钟） |
| 能做什么 | 把"能否发布"从主观争论变为客观决策；用燃尽率提前发现预算快速消耗；通过预算消耗驱动发布节奏与技术改造排期 |
| 怎么用 | 定义 SLI（可用性 = 无致命错误的会话数 / 总会话数）→ 设定 SLO（如月度 ≥ 99.9%）→ 计算错误预算与燃尽率 → 联动告警与发布策略 |
| 原理和工作流程 | 采集会话级指标 → 计算实际错误率 → 与允许错误率对比得到燃尽率 → 多窗口多燃尽率触发分级告警 → 预算耗尽冻结功能发布 |
| 缺点 | SLO 定得过高会让团队无法发布；指标口径（会话/用户/请求）选错会导致预算失真；前端 SLI 依赖埋点质量，埋点丢失会掩盖真实问题 |

## 2.1 实验分流原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 分流是把分流单元稳定映射到桶号、再按区间决定变体的过程：`bucket = hash(unit + salt) % BUCKET_TOTAL` |
| 能做什么 | 保证同一用户每次访问进入同一变体；通过不同 `salt` 让多个实验分桶互相独立；通过分层正交让多实验并行跑在同一批流量上 |
| 怎么用 | 用 FNV-1a / MurmurHash3 等非加密哈希 + 固定桶总数（如 10000）+ 按权重划分区间；层内互斥、层间用不同 `salt` 保证正交 |
| 原理和工作流程 | 纯函数哈希保证稳定性，固定桶总数避免全量重分桶，层间独立 salt 保证正交；一致性哈希用于配置分片与流量路由，不用于实验分流 |
| 缺点 | 放量调整比例会引起部分用户重分桶；分层正交需要正确的域划分（互相影响的实验必须同层互斥）；哈希实现弱会导致分布不均与 SRM |

## 2.2 实验 SDK 设计（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 实验 SDK 负责配置拉取与缓存、分流决策、曝光上报，对外暴露 `getVariant` / `trackExposure` 等接口 |
| 能做什么 | 冷启动即可分流（本地缓存优先）；配置刷新不影响已决策用户；配置服务故障时用兜底值保证业务可用；曝光与分流解耦避免分母污染 |
| 怎么用 | 初始化时同步 `loadFromCache()` → 异步 `refresh()`（带版本号防回退）→ 业务 `getVariant(key, fallback)` → 渲染提交后 `trackExposure(key)` |
| 原理和工作流程 | 配置：缓存优先 + 异步刷新 + 版本比较；分流：纯函数哈希 + 会话内决策缓存 + 兜底 `control`；曝光：渲染提交后上报 + 会话内去重 |
| 缺点 | 缓存 TTL 内的配置变更不生效（紧急下线需 SSE 或短 TTL）；决策缓存导致会话内无法切换变体；未登录用户依赖持久化匿名 ID |

## 2.3 上报方式对比与页面卸载上报（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 四种上报方式（XHR / `fetch` + `keepalive` / `navigator.sendBeacon` / img 像素打点）与页面生命周期的上报时机选择 |
| 能做什么 | 正常运行期用 `fetch` 保证可读响应与重试；卸载期用 `sendBeacon` 保证送达；跨域极简场景用 img 打点；通过 `visibilitychange` + `pagehide` 覆盖移动端卸载场景 |
| 怎么用 | `document.addEventListener('visibilitychange', ...)` 判断 `hidden` 时 flush；`pagehide` 兜底并读取 `event.persisted` 区分 bfcache；`pageshow` 恢复状态；卸载时用 `sendBeacon`，返回 `false` 则落盘 |
| 原理和工作流程 | "页面不可见"比"页面卸载"更早更可靠；`unload` 移动端常不触发且注册监听器会使页面无法进入 bfcache；`sendBeacon` 异步入队、不阻塞卸载，但队列总量约 64KB；`fetch keepalive` 单页总量约 64KB |
| 缺点 | `sendBeacon` 无法设置自定义 header、不返回响应、超限返回 `false`；img 打点受 URL 长度限制且易被广告拦截插件拦截；`unload` 已不推荐使用 |

## 2.4 离线补发机制（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 上报失败时把数据持久化到本地队列，在合适时机重新发送的机制，由"队列 + 重试 + 去重"三部分组成 |
| 能做什么 | 网络不可用时数据不丢失；页面被强杀后下次启动仍能补发；通过 `event_id` 幂等避免补发造成的数据重复 |
| 怎么用 | 用 IndexedDB 建对象仓库（`event_id` 唯一索引 + `createdAt` 索引）→ 写入后裁剪（过期 + 条数上限）→ 启动 / `online` / 定时触发补发 → 成功后删除，失败重试并设上限 |
| 原理和工作流程 | 事件落盘（`store.add`，唯一索引冲突即天然去重）→ 补发调度（并发保护 + 分批发送）→ 服务端按 `event_id` 幂等写入 |
| 缺点 | 队列需容量与过期治理，否则无限增长；重试有风暴风险，需退避与上限；客户端去重无法完全消除重复，必须服务端幂等兜底 |

## 2.5 采样策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 采样是只上报部分数据的降本手段，分为全量、随机采样、一致性采样、分层采样、动态采样 |
| 能做什么 | 在数据量与成本之间取得平衡；一致性采样保证同一用户"全采或全不采"，使漏斗分析不被破坏；采样率随数据上报后可还原真实量级 |
| 怎么用 | 关键事件（错误、支付）全量；性能与行为数据用 `hash(unit) % 10000 < rate * 10000` 做一致性采样；按事件类型配置不同采样率；采样率写入公共参数 `sample_rate` |
| 原理和工作流程 | 采样判断发生在入队前 → 命中才上报 → 数据侧按 `sample_rate` 加权还原总量 → 关键事件单独走全量通道 |
| 缺点 | 随机采样会破坏漏斗（分子分母不匹配）；采样率变更需记录，否则历史数据无法还原；动态采样频繁变化增加数据侧处理复杂度 |

## 2.6 SLI / SLO / SLA 与错误预算（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端 SLO 的指标定义（可用性、加载性能达标率、接口错误率、白屏率、交互可用性）、错误预算与燃尽率的计算方法、多窗口多燃尽率告警与降噪手段 |
| 能做什么 | 量化用户体验目标；用燃尽率区分"快速燃烧"与"慢速消耗"；通过错误预算联动发布策略；通过六种降噪手段避免告警风暴 |
| 怎么用 | 按会话定义 SLI → 设 SLO → 计算 `consumed` 与 `burnRate` → 配置 P0/P1/P2 多窗口告警 → 预算消耗 ≥ 100% 时冻结功能发布 |
| 原理和工作流程 | 燃尽率 = 实际错误率 / 允许错误率；1h/5m 燃尽率 14.4 触发 P0（2 天耗尽月度预算），6h/30m 燃尽率 6 触发 P1，3d/6h 燃尽率 1 触发 P2；告警经聚合、抑制、冷却、分级后路由 |
| 缺点 | 前端指标依赖埋点质量；SLO 过高导致无法发布；多窗口阈值需要按业务调参；告警配置不当会产生噪音或被忽略 |

## 3.1 实验 SDK 接入实战（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 从初始化埋点 SDK 到业务组件读取变体的完整接入流程，含登录后匿名 ID 与用户 ID 的打通 |
| 能做什么 | 5 分钟内完成实验接入；保证曝光事件携带分流信息；保证转化事件通过公共参数自动归因到实验分组 |
| 怎么用 | `TrackSDK.init()` → `configManager.loadFromCache()` → `new ExperimentClient(...)` → `void configManager.refresh()` → 业务用 `useExperiment(key)` 读取变体并在 `useEffect` 中上报曝光 |
| 原理和工作流程 | 埋点 SDK 先初始化保证通道可用 → 实验客户端在曝光回调里写公共参数 → 后续所有转化事件自动携带 `experiment` 字段 → 数据侧按分组聚合 |
| 缺点 | 初始化顺序有强依赖（埋点先于实验）；登录后切换分流单元会导致重新分流；曝光上报漏调会使实验分母缺失 |

## 3.2 指标口径与实验分析（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 曝光转化率与留存指标的口径定义，以及实验结论的七步判定清单（样本量、SRM、显著性、多重比较、辛普森悖论、新奇效应、护栏指标） |
| 能做什么 | 统一用户口径与事件口径，避免转化率被稀释；按同期群正确计算留存；在得出结论前系统性排除统计陷阱 |
| 怎么用 | 曝光转化率用"转化用户数 / 曝光用户数"；留存按 cohort 计算 D1/D7；结论前依次检查样本量 → SRM → 显著性 → 多重比较校正 → 分层验证 → 周期完整性 → 护栏指标 |
| 原理和工作流程 | 事件上报（含分流信息）→ 数据侧按 `variant` 去重聚合 → 卡方检验查 SRM → 主要指标显著性检验 → 多重比较校正（Bonferroni / FDR）→ 输出结论 |
| 缺点 | 用户口径需要去重窗口定义；留存指标必须等窗口完整；统计检验依赖数据质量，SRM 未被发现时所有结论都不可信 |

## 3.3 前端 SLO 看板与错误预算告警（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 错误预算的计算实现（`consumed` / `burnRate` / `status`）与看板必备的五个面板（预算剩余、燃尽率、可用性趋势、性能达标率、关键路径成功率） |
| 能做什么 | 实时判断"当前能否发布"；按 app_version 定位引入问题的版本；把性能达标率与错误预算并列作为两条核心 SLI |
| 怎么用 | `computeBudget(config, goodCount, totalCount, windowFraction)` 计算预算状态 → 看板展示预算剩余与三窗口燃尽率 → 结合发布策略执行"正常 / 谨慎 / 冻结" |
| 原理和工作流程 | `consumed = 实际错误率 / 允许错误率 × 已过去时间占比`；`burnRate = 实际错误率 / 允许错误率`；`consumed ≥ 1` 判为 `frozen`，`≥ 0.5` 判为 `warning` |
| 缺点 | 前端侧计算只适合自检，正式告警应在数据侧实现；窗口占比参数需要与统计周期严格对齐；预算状态需与发布流程真正联动才有价值 |
