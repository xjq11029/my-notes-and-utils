**1. ★★ 以下关于 `window.onerror` 的说法，正确的是？**

A. `window.onerror` 可以捕获所有类型的 JS 错误，包括语法错误和 Promise 异常
B. `window.onerror` 无法捕获跨域脚本的详细错误信息，除非脚本添加了 `crossorigin` 属性
C. `window.onerror` 可以捕获资源加载错误（如 `<img>` 加载失败）
D. `window.onerror` 和 `window.addEventListener('error')` 的行为完全一致

**答案：B**

**解析**：
- A 错误：`window.onerror` 无法捕获语法错误（发生在解析阶段）和 Promise 异常（需用 `unhandledrejection`）
- B 正确：跨域脚本默认只返回 `"Script error."`，添加 `crossorigin="anonymous"` 并配置 CORS 头才能获取详细错误
- C 错误：资源加载错误不冒泡，无法被 `window.onerror` 捕获，需在捕获阶段监听
- D 错误：`window.onerror` 和 `addEventListener('error')` 的参数和行为有差异（前者参数是 message/source/lineno/colno/error，后者是 Event 对象）

**2. ★★ 以下关于 Core Web Vitals 的描述，错误的是？**

A. LCP（Largest Contentful Paint）衡量视口内最大可见元素的渲染时间
B. INP（Interaction to Next Paint）衡量用户交互到页面视觉反馈的延迟
C. CLS（Cumulative Layout Shift）衡量页面视觉稳定性，包含用户交互导致的布局偏移
D. TTFB（Time to First Byte）衡量浏览器从请求到接收第一个字节的时间

**答案：C**

**解析**：
- C 错误：CLS 只计算非用户交互导致的布局偏移（`hadRecentInput` 为 false 的 layout-shift），用户主动点击导致的布局变化不计入 CLS

**3. ★★ 关于 `navigator.sendBeacon` 的特性，以下说法错误的是？**

B. `sendBeacon` 支持 GET 和 POST 两种请求方法

- D 正确：这是 sendBeacon 的主要使用场景

**4. ★★ 以下哪种方式最适合捕获 Promise 中未被 catch 的异常？**

A. `window.onerror`
B. `try...catch` 包裹所有 Promise
C. `window.addEventListener('unhandledrejection')`
D. `console.error` 劫持

**答案：C**

### 补充：埋点体系（5 题）

**11. ★★ 关于埋点的三种方式（代码埋点 / 可视化埋点 / 无痕埋点），以下说法正确的是？**

A. 无痕埋点可以完全替代代码埋点，因为它零开发成本
B. 可视化埋点的本质是"把代码埋点的调用点外置成配置"，运行态按元素路径匹配元素
C. 代码埋点适合运营活动页等需要频繁调整的页面
D. 三种埋点方式应各自使用独立的数据模型，便于分别优化

**答案：B**

**解析**：
- A 错误：无痕埋点缺少业务语义（不知道"这个按钮是购买还是收藏"）与业务参数，数据量大、聚合成本高，只适合探索性分析
- B 正确：可视化埋点分**圈选态**（拦截点击、生成元素唯一路径 + 稳定特征，保存到配置中心）与**运行态**（拉配置、按同一套路径算法匹配元素、命中后绑定监听并上报）。最大难点是元素路径不稳定：动态 `class`、列表项索引变化、A/B 实验导致 DOM 结构差异都会让路径失配
- C 错误：代码埋点适合核心转化链路（支付、下单）等需要业务参数的场景；运营活动页适合可视化埋点
- D 错误：三种方式必须**共用同一套数据模型和上报通道**，否则数据侧无法统一分析 —— 这是最常见的架构性错误

**12. ★★ 关于曝光埋点，以下说法错误的是？**

A. 曝光指元素在视口中真实可见，区别于"元素已被渲染"
B. `IntersectionObserver` 相比 `scroll` 事件的优势是不依赖滚动回调，避免强制同步布局
C. `threshold` 数组不需要包含 0，因为元素可见时必然回调
D. 有效曝光通常需要同时满足"可见比例阈值"与"连续停留时长"

**答案：C**

**解析**：
- C 错误：`threshold` **必须包含 0**。否则元素"从可见变为完全不可见"时不会触发回调，停留时长的计时器无法被清除，残留计时器会导致误上报
- A 正确：`<img>` 已加载完成，但用户滚动到屏幕外不算曝光
- B 正确：交叉计算由浏览器在合成阶段完成，避免在 `scroll` 回调里反复调用 `getBoundingClientRect()` 触发 layout thrashing
- D 正确：典型实现是 `minRatio`（如 0.5）+ `minDuration`（如 500ms），并用 `WeakSet` 去重（`once`）

**13. ★★ 全站点击埋点为什么要在 `document` 的捕获阶段监听？**

A. 捕获阶段的事件对象包含更多信息
B. 捕获阶段性能更好，回调次数更少
C. 捕获阶段早于业务代码在冒泡阶段调用 `stopPropagation()`，避免漏埋
D. 只有捕获阶段才能读取 `data-*` 属性

**答案：C**

**解析**：C 正确 —— 这是避免"业务组件阻止事件冒泡导致埋点丢失"这一最常见漏埋原因的关键。A、B、D 均不成立。
补充要点：必须用 `e.target.closest('[data-track]')` 向上查找，直接读 `e.target` 在点到按钮内图标 / 文字节点时会读不到；`data-track` 命名需带模块前缀并做唯一性校验；回调里只入队，序列化与上报放到 `requestIdleCallback`，避免点击密集的列表页掉帧。

**14. ★★ 关于埋点数据模型中的"公共参数"（`common`），以下说法错误的是？**

A. 公共参数是所有事件的维度基线，如 `app_version`、`platform`、`anonymous_id`
B. 把公共参数混进 `properties` 会导致不同开发者漏带字段、口径不一致
C. 公共参数中的 `timezone` 用于避免跨时区口径错乱
D. 公共参数应在每个埋点调用处由业务代码手动传入，以保证灵活性

**答案：D**

**解析**：
- D 错误：公共参数应由 **SDK 统一注入**，而不是每次调用手动传 —— 手动传必然出现漏带与拼写不一致
- A、B、C 正确。事件模型为"1 个事件 + N 个属性 + 公共参数"：`event_id`（服务端幂等去重）、`event`、`event_type`、`properties`、`common`、`timestamp`、`timezone`
- `common` 典型字段：`app_id` / `app_version` / `sdk_version` / `platform` / `anonymous_id` / `user_id` / `page_url` / `page_path` / `experiment` / `utm_source` / `screen` / `network`

**15. ★★★ 线上发现某埋点数据量骤降，排查顺序最合理的是？**

A. 先怀疑上游业务流量下降，再看埋点链路
B. 依次排查：是否上报（Network）→ 是否触发（调试日志）→ 是否被采样 / 队列丢弃 → 是否被服务端过滤
C. 直接改代码加日志并重新发布
D. 先检查数据侧去重逻辑是否误删

**答案：B**

**解析**：
- B 正确：从上报链路末端向源头逐层排查，能最快收敛到根因
- A 部分正确但不完整：数据量下降确实可能是上游业务流量下降（必须同时看业务指标做交叉验证），但排查仍应从埋点链路本身开始
- C 错误：未定位根因就改代码重发，成本高且可能掩盖问题
- D 错误：服务端去重是幂等写入，不会导致量级骤降
- 补充：埋点质量三类问题（漏埋 / 重复埋 / 参数错误）与三层防线（开发期 schema 校验、测试期 E2E 断言 + 配置 diff、线上期量级告警 + 对账）

### A/B 实验与上报可靠性（5 题）

**16. ★★★ A/B 实验的分流实现中，以下做法错误的是？**

A. `bucket = hash(unit + salt) % BUCKET_TOTAL`，同一 `unit + salt` 永远得到同一结果
B. 用 MurmurHash3 / FNV-1a 等非加密哈希保证分布均匀
C. 用 `Math.random()` 分流，保证随机性与统计公平
D. 桶总数固定为 10000，放量时只调整变体区间

**答案：C**

**解析**：
- C 错误：`Math.random()` 不稳定，同一用户每次访问会命中不同变体，指标被稀释且体验受损
- 分流必须满足三个性质：**稳定性**（纯函数哈希）、**均匀性**（非加密哈希；`String.hashCode()` 这类弱哈希在大样本下分布明显不均）、**独立性**（不同实验 `salt` 不同，避免"总是同一批用户进实验组"）
- D 正确：桶总数固定，避免扩容导致全量重分桶、污染运行中的实验

**17. ★★★ 关于分层正交（Layered Experiments），以下说法正确的是？**

A. 层内实验互相独立，用户可同时命中同层的多个实验
B. 层内互斥（同层最多命中一个实验），层间正交（不同层用不同 `salt`，用户可同时进入多层实验）
C. 分层正交的目的是减少实验数量
D. 互相影响的实验（如都改同一个按钮）应放在不同层

**答案：B**

**解析**：
- A 说反：层内是**互斥**的，同层实验共享同一份流量池
- B 正确：层间正交让多个实验并行跑在同一批流量上，在总流量 100% 的前提下同时运行
- C 错误：目的是提升流量利用率（单个实验只用 10% 流量，剩余 90% 不再闲置），不是减少实验数量
- D 错误：互相影响的实验必须放**同层同域互斥**，否则结论互相污染却无法察觉；域的划分依据是"实验是否作用于同一用户旅程的同一环节"

**18. ★★★ 页面关闭时保证埋点不丢，以下方案最完整的是？**

A. 监听 `unload`，在回调里用 `fetch` 上报
B. 监听 `visibilitychange(hidden)` + `pagehide` 兜底，用 `sendBeacon` 上报，并配合离线队列
C. 监听 `beforeunload`，用同步 XHR 上报
D. 只在定时器里批量上报即可

**答案：B**

**解析**：
- A 错误：`unload` 在移动端（尤其 iOS Safari）常不触发；注册 `unload` 监听会使页面失去 bfcache 资格；`unload` 中发起的普通异步请求会被浏览器取消
- B 正确：`visibilitychange` → hidden 是最早、最可靠的信号（移动端切 App 一定触发）；`pagehide` 作为卸载兜底（`persisted === true` 表示进入 bfcache）；卸载期用 `sendBeacon`（浏览器保证排队发送）；离线队列（IndexedDB）保证彻底失败的数据可补发
- C 错误：同步 XHR 会阻塞页面卸载，体验差
- D 错误：定时批量上报无法覆盖"用户关闭页面"这一时刻

**19. ★★ 关于上报方式，以下说法错误的是？**

A. `sendBeacon` 仅支持 POST，不支持自定义请求头，也无法读取响应
B. `fetch` 配合 `keepalive: true` 可在页面卸载后继续发送
C. `sendBeacon` 队列总量约 64KB，超限时返回 `false`
D. img 像素打点支持自定义请求头，且不受 URL 长度限制

**答案：D**

**解析**：
- D 错误：img 打点只能通过赋值 `img.src` 发起 GET，**不支持自定义请求头**，且受 URL 长度限制（约 2KB）。优点是天然跨域（图片跨域加载无需 CORS）、兼容性最好，适合极简埋点与降级兜底，但易被广告拦截插件拦截
- A、B、C 正确。选型结论：运行期用 `fetch`（可读响应、可重试、体积无限制），卸载期用 `sendBeacon`，需要极简跨域时降级 img 打点，`XMLHttpRequest` 仅在需要兼容老浏览器时使用

**20. ★★★ 关于采样策略，以下做法正确的是？**

A. 对曝光与转化分别做独立的随机采样，以节省上报量
B. 用一致性采样（`hash(unit) % 10000 < rate * 10000`），保证同一用户在窗口内"全采或全不采"
C. 采样率无需随数据上报，数据侧自行估算即可
D. 对错误上报做随机采样并只保留采样数据，以降低成本

**答案：B**

**解析**：
- A 错误：独立随机采样会**破坏漏斗** —— 曝光采到、转化没采到，转化率算出来可能 > 100%
- B 正确：一致性采样基于稳定 `unit`（未登录依赖持久化的 `anonymous_id`），漏斗分子分母匹配
- C 错误：采样率必须随数据上报（如 `common.sample_rate`），否则数据侧无法还原真实量级（真实 PV ≈ 采样 PV / 0.1）
- D 错误：对错误随机采样却只保留采样数据会造成"错误量下降"的假象，应上报真实总量的估算值

### 简答题 7（★★）：如何设计一个合理的告警策略？

**答案要点**：

五项原则：
1. **基于影响用户数**：不以错误次数告警，以受影响用户数为准

### 简答题 9（★★）：埋点的三种方式（代码埋点 / 可视化埋点 / 无痕埋点）的原理与选型依据？

**答案要点**：

三种方式的定义：

| 方式 | 定义者 | 采集时机 | 典型代表 |
|---|---|---|---|
| 代码埋点（手动埋点） | 开发者在代码里显式调用 API | 代码执行到埋点调用处 | `track('click_buy', { skuId })` |
| 可视化埋点（圈选埋点） | 运营 / 产品在可视化工具中圈选元素 | 运行时按配置匹配元素并绑定事件 | 神策、GrowingIO 的可视化圈选 |
| 无痕埋点（全埋点） | SDK 自动采集所有行为 | SDK 监听全局事件，全量上报 | 全埋点 SDK、GA 增强衡量 |

**原理**：

- **代码埋点**：本质是一次函数调用，SDK 把 `eventName + properties` 组装成事件对象入队。优点是语义精确、参数可控；缺点是每加一个埋点都要改代码 + 发版
- **可视化埋点**：把代码埋点的调用点**外置成配置**。圈选态拦截点击并阻止默认行为，根据被点元素生成**元素唯一路径**（DOM 层级路径 / XPath + 元素特征）连同事件类型、事件名、参数保存到配置中心；运行态拉取配置，用同一套路径生成算法在运行时匹配元素，命中后自动绑定监听并上报。最大难点是**元素路径不稳定**：动态 `class`、列表项索引变化、A/B 实验导致 DOM 结构差异都会让路径失配，所以成熟工具会把"路径 + 稳定特征（`id`、`data-*`、文本、相对位置）"组合打分并支持手工修正
- **无痕埋点**：把语义推断交给数据侧。SDK 只做通用自动采集（全局监听 `click`、监听路由变化采 PV），数据侧用元素路径做二次映射

**选型对比**：

| 维度 | 代码埋点 | 可视化埋点 | 无痕埋点 |
|---|---|---|---|
| 开发成本 | 高 | 低 | 极低 |
| 运营自主性 | 低 | 高 | 中 |
| 业务语义 | 精确 | 精确 | 弱（需推断） |
| 参数灵活度 | 高 | 中 | 低 |
| 数据量 | 可控 | 可控 | 大 |
| 元素稳定性要求 | 无 | 高 | 高 |
| 适用场景 | 核心转化链路 | 运营活动页 | 行为探索、路径分析 |

**选型建议**：不要三选一，而是**分层组合** —— 核心链路（支付、下单）用代码埋点保证准确，运营页面用可视化埋点保证效率，全局行为用无痕埋点做探索性分析。三者必须**共用同一套数据模型与上报通道**，才能在数据侧统一分析。

### 简答题 10（★★）：曝光埋点的原理是什么？`IntersectionObserver` 相比 `scroll` 事件有哪些优势？

**答案要点**：

**定义**：曝光（Exposure / Impression）指元素在用户视口中**真实可见**，区别于"元素被渲染"。它是推荐、广告、列表、活动位等"内容消费类"指标的分母，直接决定 CTR（点击率）口径是否可信。

**`IntersectionObserver` 原理**：异步监听目标元素与视口（或指定 `root`）的交叉状态，回调参数 `IntersectionObserverEntry` 提供 `isIntersecting`、`intersectionRatio`、`boundingClientRect`、`intersectionRect`、`rootBounds`、`time`、`target`。

**相比 `scroll` 的优势**：不依赖滚动事件 —— 交叉计算由浏览器在**合成阶段**完成，避免在 `scroll` 回调里反复调用 `getBoundingClientRect()` 触发强制同步布局（layout thrashing）。

**有效曝光判定**：`minRatio`（最小可见比例，默认 0.5）+ `minDuration`（最小停留时长，默认 500ms）+ `once`（同一元素只上报一次，用 `WeakSet` 去重）。

**关键细节**：
- `threshold` **必须包含 0**，否则元素"从可见变为完全不可见"时不会回调，停留计时器无法清除
- `rootMargin` 语义：正数 = 提前曝光（如提前 100px），负数 = 延迟曝光
- 用 `WeakMap` 存"可见起始时间"与计时器句柄，元素被移除后自动回收，避免内存泄漏

### 简答题 11（★★）：全站点击埋点如何实现？为什么用捕获阶段和 `closest`？

**答案要点**：

**实现**：在 `document` 上注册捕获阶段监听（`addEventListener('click', handler, true)`），用 `e.target.closest('[data-track]')` 找到带标识的元素，读取 `dataset.track` 与 `dataset.trackParams`。

**为什么用捕获阶段**：业务组件常在冒泡阶段调用 `stopPropagation()`；捕获阶段在事件从 `window` 向目标元素传播时触发，早于业务代码的阻止冒泡，从根上避免漏埋。

**为什么用 `closest`**：点击按钮内的图标 / 文字节点时 `e.target` 是子节点，读不到 `data-track`，必须沿祖先链向上查找。

**`data-track` 命名规范**：`{模块}_{对象}_{动作}`（如 `cart_submit_order`），必须带模块前缀并做唯一性校验，否则数据侧无法区分来源。

**参数就近携带**：`data-track-params` 传 JSON，避免在回调里反查 DOM 或依赖闭包变量；解析失败降级为无参数，**不能影响业务点击**。

**事件委托 vs 逐元素绑定**：

| 维度 | 事件委托 | 逐元素绑定 |
|---|---|---|
| 监听器数量 | 1 个 | N 个 |
| 动态渲染元素 | 天然支持 | 需在渲染后重新绑定 |
| 内存占用 | 低 | 高（列表场景线性增长） |
| 参数传递 | 依赖 `data-*` | 可直接用闭包变量 |
| 捕获阶段支持 | 支持 | 需逐个指定 |

**性能**：回调里只入队，序列化与上报放到 `requestIdleCallback`，避免点击密集的列表页掉帧。

**与 A/B 实验打通**：埋点事件必须携带分流信息（`common.experiment`），且上报必须发生在分流之后；标准做法是**实验 SDK 初始化完成后再放行埋点上报**，或先入队、分流补齐后统一 flush。

### 简答题 12（★★★）：埋点数据的质量保障体系是什么？重复埋点如何根治？

**答案要点**：

**三类问题**：漏埋（该采的没采到）、重复埋（同一行为被计多次）、参数错误（采到了但值不对）。

**三层防线**：

```
第一层：开发期（成本最低，效果最好）
  - 事件 schema 集中定义（Zod / JSON Schema），DEV 环境对每个事件做校验
  - 属性值枚举校验，非法值直接报错而不是静默上报
  - 单测覆盖关键埋点：断言 track 被调用且参数正确

第二层：测试期
  - E2E 拦截上报请求，断言"点击购买后确实发出了 click_buy 事件"
  - 埋点配置与代码静态比对：扫描 data-track / track() 调用与配置表 diff，
    输出"代码有但配置没有"（多埋）与"配置有但代码没有"（漏埋）
  - 按 PRD 的埋点文档逐条走查验收

第三层：线上期
  - 数据量突降告警（同比 / 环比跌幅超阈值）
  - 关键指标兜底对账（支付成功数 vs 业务库订单数）
  - 埋点覆盖率看板（曝光量 / PV、点击量 / 曝光量等派生比例异常告警）
  - 参数健康度（枚举值分布、空值率、属性长度分布）
```

**重复埋点的根治**：
- 事件唯一 `event_id` + 服务端幂等写入（唯一索引 / Redis `SETNX`）
- SDK 单例保护，避免重复初始化
- 路由事件去重（`pushState` + `popstate` 重复触发）
- 重试前先查重

**组织手段**：建立"埋点需求文档（含事件名、属性、触发时机、责任人）→ 评审 → 开发 → 验收 → 监控"的闭环，并把埋点配置纳入版本管理（配置即代码），使变更可 review、可回滚。

### 简答题 13（★★★）：A/B 实验的分流如何实现？为什么不用随机数？分层正交是什么？

**答案要点**：

**分流公式**：

```
unit（分流单元）= userId（登录）或 deviceId / anonymousId（未登录）
salt（实验盐）  = experimentId 或 layerId
bucket  = hash(unit + salt) % BUCKET_TOTAL   // 通常 10000
variant = 按流量比例划分桶号区间
```

**三个必须满足的性质**：
1. **稳定性**：`hash` 是纯函数，同一 `unit + salt` 永远得到同一结果；排除 `Math.random()`、时间戳等不稳定输入
2. **均匀性**：用 MurmurHash3、FNV-1a、xxHash 等非加密哈希；`String.hashCode()` 这类弱哈希在大样本下分布明显不均
3. **独立性**：不同实验 `salt` 不同，分桶互相独立，避免"总是同一批用户进实验组"

**为什么不用随机数**：不稳定，同一用户看到不同变体，指标被稀释且体验受损。

**桶总数为什么固定为 10000**：若从 100 改成 200，`hash % 100` 与 `hash % 200` 结果不同，所有用户被重新分桶，运行中的实验被污染。固定足够大的桶空间后，放量只通过调整区间实现。

**放量时的重分桶问题**：从 50/50 调成 30/70 时，原本落在 `[0.5, 0.7)` 的用户会从 treatment 变 control，体验发生切换。工程做法：比例一经确定不再调整；需要调整时新建实验或新增变体（老变体区间不动）；必须调整则在报告中剔除切换期数据。

**分层正交**：
- **层内互斥**：同层实验共享同一份流量池，一个用户在同层最多命中一个实验，保证同层实验不互相污染
- **层间正交**：不同层用不同 `salt`，分桶结果独立，用户可同时进入多个层的实验，实现"总流量 100% 时并行跑多个实验"
- 域的划分依据是"实验是否作用于同一用户旅程的同一环节"

**一致性哈希**：实验分流不用（桶总数固定，不存在节点增减问题）；它在实验体系里用于"配置缓存分片"或"流量在多计算节点间的路由"。

**实验配置读取**：本地缓存优先 + 异步刷新 —— 冷启动同步读本地缓存保证首屏分流可用（不发网络请求），异步刷新失败时保留旧配置，绝不把用户打回未分流状态。

### 简答题 14（★★★）：什么是 SRM（样本比例失调）？如何排查和预防？

**答案要点**：

**定义**：SRM（Sample Ratio Mismatch）指实验实际进入各变体的样本比例与配置的流量比例显著不符（如配置 50/50，实际 48/52 且统计显著）。

**危害**：分流不随机，实验结论不可信 —— 此时任何指标差异都可能来自分流偏差而非实验干预。SRM 是"实验有效性"的前置门禁，**先过 SRM 再看指标**。

**常见成因**：
- 分流不稳定（用随机数 / 时间戳参与分桶）
- 分流单元不统一（同一实验里混用 `userId` 与 `deviceId`）
- 未登录用户没有稳定标识，每次访问生成新 ID（必须首访持久化 `anonymous_id`）
- 实验运行中修改 `salt` 或桶总数，导致全量重分桶
- 埋点上报晚于分流，事件缺失实验标识，落入"未分流"桶造成样本流失
- 数据侧过滤条件本身与分组相关（如只统计"完成下单"的用户，而某变体更容易下单）

**排查**：按分流单元与实验标识统计各变体样本量，做卡方检验（`p < 0.001` 通常视为 SRM）；检查分流日志与配置版本是否中途变更。

**预防**：
- 固定桶总数与 `salt`，比例一经确定不调整
- 首访持久化 `anonymous_id`

### 简答题 15（★★★）：页面关闭时如何保证埋点不丢？离线补发机制如何设计？

**答案要点**：

**上报时机**：

| 事件 | 触发时机 | 可靠性 | 是否影响 bfcache | 建议用途 |
|---|---|---|---|---|
| `visibilitychange` → hidden | 页面不可见（切后台 / 切标签 / 即将卸载） | 高 | 不影响 | **上报主时机** |
| `pagehide` | 页面卸载前 / 进入 bfcache 时 | 高 | 不影响 | 上报兜底、清理 |
| `unload` | 页面真正卸载时 | 低（移动端常不触发） | **会使页面无法进入 bfcache** | 不再使用 |
| `beforeunload` | 卸载前，可弹确认框 | 中 | 会影响 | 仅用于"离开前提示" |

关键认知：**"页面不可见"比"页面卸载"更早、更可靠**。移动端切到别的 App 时页面可能永远不触发卸载事件，但一定会触发 `visibilitychange`。另需监听 `pageshow`（`persisted === true`）在从 bfcache 返回时恢复状态。

**上报方式**：卸载期用 `sendBeacon`（浏览器保证排队发送，不阻塞卸载；队列总量约 64KB，超限返回 `false`，必须降级处理）；运行期用 `fetch`（可读响应、可重试、体积无限制）；需要极简跨域或兼容性兜底时用 img 打点。

**离线补发机制**：

```
存储：IndexedDB（异步不阻塞主线程、容量大、支持事务与索引、可存结构化数据）
     不用 localStorage（同步 API 写大 JSON 阻塞主线程，5MB 上限很快打满）
队列：event_id 唯一索引天然去重 + 条数上限（如 500）+ 过期丢弃（如 7 天）
重试：指数退避 + 最大重试次数（如 5 次），避免服务端故障时形成重试风暴
触发：启动补发 + online 事件 + 定时兜底（如 60s）
并发保护：flushing 标记，避免 online 与定时器同时触发导致同一批数据被发两次
```

**幂等**：客户端去重只能减少重复，不能消除（补发、多标签页、重试都会产生重复），服务端必须按 `event_id` 做幂等写入（唯一索引 / Redis `SETNX`）。

**队列满了怎么办**：丢最旧 + 上报丢弃计数（使数据量下降可归因）；关键事件走单独的高优先级队列。**安全**：队列长期保留敏感数据既有空间成本也有合规风险，需设置过期时间并脱敏。

> - [MDN - Beacon API](https://developer.mozilla.org/zh-CN/docs/Web/API/Beacon_API)
> - [web.dev - bfcache](https://web.dev/articles/bfcache)
> - [MDN - IntersectionObserver](https://developer.mozilla.org/zh-CN/docs/Web/API/IntersectionObserver)

### 场景设计题 7（★★★）：设计一个 A/B 实验平台

**题目**：设计一个支持多实验并行的 A/B 实验平台，包含分流 SDK、实验配置管理、SRM 监控与指标分析。请给出架构与关键设计。

**一、整体架构**

```
配置中心（实验配置 + 版本号）
      │ 拉取 / 推送

      │
      ▼

```

**二、分流设计**
- `unit`：登录用 `userId`，未登录用持久化的 `anonymousId` / `deviceId`
- `salt`：用 `experimentId` 或 `layerId`，保证实验间独立
- 桶总数固定 10000，`bucket = hash(unit + salt) % 10000`，`variant` 按区间划分
- 三性质：稳定性（纯函数哈希）、均匀性（MurmurHash3 / FNV-1a）、独立性（不同 salt）
- **禁止**用 `Math.random()`、时间戳、弱哈希

**三、分层正交**
- 层内互斥（共享流量池，同层最多命中一个实验）
- 层间正交（不同 salt，可同时进入多层实验）
- 域按"是否作用于同一用户旅程的同一环节"划分

**四、实验 SDK 设计**
- 冷启动同步读本地缓存（保证首屏分流可用，不发网络请求）
- 异步刷新配置，失败时保留旧配置（绝不把用户打回未分流状态）
- 配置带 `version` 字段，用于防回退与问题追溯
- 缓存损坏时静默降级为无配置并清理

**五、SRM 监控**
- 按分流单元与实验标识统计各变体样本量，做卡方检验
- `p < 0.001` 判定 SRM，实验直接标记无效
- 常见成因：分流不稳定、unit 不统一、`anonymous_id` 未持久化、中途改 salt / 桶总数、埋点早于分流

**六、指标口径与分析**
- 实验前做 AA 测试验证分流无偏
- 明确主指标 / 护栏指标，样本量按最小可检测效应（MDE）预估
- 比例中途调整时，剔除切换期数据
- 报告需标注置信区间与显著性，避免"看趋势下结论"

**七、避坑清单**
- 桶总数可变 → 全量重分桶
- 同层放互相影响的实验 → 结论污染
- 埋点早于分流 → 样本流失、SRM
- 配置缓存丢失 → 用户被打回未分流状态，指标口径断裂

### 场景设计题 8（★★★）：设计前端 SLO 与错误预算体系

**题目**：为某核心交易页面设计前端 SLO 体系，覆盖可用性、加载性能、接口错误率、白屏率，并给出错误预算告警与上报可靠性方案。

**答案要点**：

**一、SLI / SLO 定义**

| SLI | 定义（分子 / 分母） | 建议 SLO | 数据来源 |
|---|---|---|---|
| 可用性 | 无致命错误的会话数 / 总会话数 | ≥ 99.9% | 错误监控 SDK |
| 加载性能达标率 | P75 LCP < 2.5s 的会话数 / 总会话数 | ≥ 95% | 性能采集 / RUM |
| 接口错误率 | 失败请求数 / 总请求数 | ≤ 1% | 接口埋点 / 网关 |
| 白屏率 | 白屏会话数 / 总会话数 | ≤ 0.1% | 白屏检测 SDK |
| 交互可用性 | P75 INP < 200ms 的会话数 / 总会话数 | ≥ 95% | PerformanceObserver |

**二、三条设计原则**
1. **按会话 / 用户聚合，而非按请求**：一个用户 100 次请求失败与 1 次失败，对体验影响完全不同
2. **与用户可感知体验对齐**：SLO 要能被用户感知，避免"指标达标但用户仍在抱怨"
3. **SLO 数量要克制**：每增加一个 SLO 就增加一份维护与告警成本

**三、错误预算与告警**
- 错误预算 = 1 - SLO（如 99.9% → 每月约 43 分钟不可用额度）
- **快烧告警**（1 小时窗口烧掉 5% 预算）→ 立即通知，可能触发发布回滚
- **慢烧告警**（6 小时窗口烧掉 10% 预算）→ 工单跟进
- 预算耗尽 → 冻结非关键发布，优先修复稳定性

**四、上报可靠性（SLO 数据的可信前提）**
- 采样用**一致性采样**，采样率随数据上报，否则无法还原真实量级
- 页面卸载用 `sendBeacon` + `visibilitychange(hidden)`，配合 IndexedDB 离线补发
- 服务端按 `event_id` 幂等，避免补发造成重复计数污染 SLO

**五、看板与治理闭环**
- Grafana 大盘：SLI 趋势、错误预算剩余、错误 Top N、影响用户数
- 告警以**影响用户数**为主指标，不以错误次数为准
- 每周复盘错误预算消耗归因（发布引入 / 下游故障 / 客户端兼容性）
- 把 SLO 纳入发布门禁：预算不足时限制高风险变更的放量节奏

## 第四部分：高频追问速答（共 12 题）

> 面试官常在主问题后沿同一条链路继续追问。以下 12 组速答覆盖监控与运维最容易被追问的细节。

**追问 1（★★）：`sendBeacon` 返回 `false` 怎么办？**

说明浏览器无法把请求加入发送队列（通常是队列总量约 64KB 超限）。必须降级处理：先尝试写入 IndexedDB 离线队列等下次补发；若关键事件，可退回 `fetch` + `keepalive`。绝不能忽略返回值——否则数据静默丢失且无记录。

**追问 2（★★）：为什么不用 `beforeunload` 上报？**

`beforeunload` 用于弹出"确认离开"对话框，会影响页面进入 bfcache，且它并非为数据上报设计。上报应使用 `visibilitychange(hidden)` 与 `pagehide`，二者都不影响 bfcache。

**追问 3（★★）：曝光埋点如何避免同一元素重复上报？**

三个手段叠加：① `once: true` 时用 `WeakSet` 记录已上报元素，元素被移除后自动回收；② 用 `WeakMap` 记录"可见起始时间"与计时器句柄，重复回调时先判断是否已在计时；③ `minDuration` 要求"连续"停留，中途离开会清除计时器，短暂划过的元素不会计入。

**追问 4（★★）：全埋点能否替代代码埋点？**

不能。全埋点缺少业务语义与业务参数（不知道"这个按钮是购买还是收藏"），数据量大、聚合成本高，需要在数据侧用元素路径二次映射。它适合探索性分析与历史回溯，核心转化链路仍必须用代码埋点。

**追问 5（★★★）：为什么实验分流的桶总数必须固定？**

因为放量是通过调整变体区间实现的。若桶总数从 100 改成 200，`hash % 100` 与 `hash % 200` 结果不同，所有用户被重新分桶，运行中的实验被污染、历史数据与新增数据口径断裂。固定足够大的桶空间（如 10000）后，重分桶影响最小。

**追问 6（★★★）：实验运行中调整流量比例会怎样？**

从 50/50 调成 30/70 时，原本落在 `[0.5, 0.7)` 的用户会从 treatment 漂移到 control，体验发生切换，且这批用户在切换前后的数据口径不一致。工程做法：比例一经确定不再调整；需调整时新建实验或新增变体（老变体区间不动）；必须调整则在分析中剔除切换期数据。

**追问 7（★★）：采样率中途变化，历史数据怎么还原？**

采样率必须随每条数据上报（如 `common.sample_rate`）。若历史数据没有记录采样率，就无法按时间段加权还原，只能按"估算值"标注并说明口径变化，无法做精确同比。因此采样配置变更必须留档。

**追问 8（★★★）：错误上报要不要采样？**

关键错误不应采样，应全量上报；若量级实在过大，可用**分层采样**（高频错误 1%、新错误 100%），但必须上报真实总量的估算值，否则会出现"错误量下降"的假象，掩盖真实故障。

**追问 9（★★）：离线队列为什么必须设上限和过期时间？**

无上限会在长期断网或服务端持续故障时把磁盘配额打满，甚至影响同域名下的其他存储；无过期时间会让敏感数据长期驻留，既有空间成本也有合规风险。做法：条数上限 + 过期丢弃 + 丢弃计数上报（使数据量下降可归因）。

**追问 10（★★★）：白屏检测的 18 点采样法原理是什么？**

在页面上取 18 个均匀采样点（3×6 网格），用 `document.elementFromPoint` 获取每个点命中的元素；若超过 16 个点都落在根容器上，判定为白屏。辅助手段：先用"是否有可见文本（innerText 长度 > 10）"与"是否有可见图片 / Canvas / Video / SVG"做前置判断，再用 `MutationObserver` + 定时（3 秒间隔）检测。

**追问 11（★★）：为什么告警以影响用户数为主，而不是错误次数？**

次数会被单个用户的重复触发放大：10 个用户各报错 100 次（1000 次错误）远不如 100 个用户各报错 1 次（100 次错误）严重。以受影响用户数为主指标，才能对齐"真实业务影响"。

**追问 12（★★）：SLA、SLO、SLI 三者是什么关系？**

SLI 是**指标**（可测量的量，如可用性百分比），SLO 是**目标值**（对 SLI 的内部承诺，如 ≥ 99.9%），SLA 是**对外合同**（达不到时的赔偿条款）。顺序是：先定义 SLI，再设定 SLO，最后才可能对外承诺 SLA。SLO 通常严于 SLA，留出缓冲。
