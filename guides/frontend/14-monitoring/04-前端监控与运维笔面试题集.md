**1. 以下关于 `window.onerror` 的说法，正确的是？**

A. `window.onerror` 可以捕获所有类型的 JS 错误，包括语法错误和 Promise 异常
B. `window.onerror` 无法捕获跨域脚本的详细错误信息，除非脚本添加了 `crossorigin` 属性
C. `window.onerror` 可以捕获资源加载错误（如 `<img>` 加载失败）
D. `window.onerror` 和 `window.addEventListener('error')` 的行为完全一致

**答案：B**

**解析**：
- A 错误：`window.onerror` 无法捕获语法错误（发生在解析阶段）和 Promise 异常（需用 `unhandledrejection`）
- B 正确：跨域脚本默认只返回 `"Script error."`，添加 `crossorigin="anonymous"` 并配置 CORS 头才能获取详细错误
- C 错误：资源加载错误不冒泡，无法被 `window.onerror` 捕获，需在捕获阶段监听
- D 错误：`window.onerror` 和 `addEventListener('error')` 的参数和行为有差异（前者参数是 message/source/lineno/colno/error，后者是 Event 对象）

**2. 以下关于 Core Web Vitals 的描述，错误的是？**

A. LCP（Largest Contentful Paint）衡量视口内最大可见元素的渲染时间
B. INP（Interaction to Next Paint）衡量用户交互到页面视觉反馈的延迟
C. CLS（Cumulative Layout Shift）衡量页面视觉稳定性，包含用户交互导致的布局偏移
D. TTFB（Time to First Byte）衡量浏览器从请求到接收第一个字节的时间

**答案：C**

**解析**：
- C 错误：CLS 只计算非用户交互导致的布局偏移（`hadRecentInput` 为 false 的 layout-shift），用户主动点击导致的布局变化不计入 CLS
- A、B、D 均正确

**3. 关于 `navigator.sendBeacon` 的特性，以下说法错误的是？**

A. `sendBeacon` 异步发送数据，不阻塞页面卸载
B. `sendBeacon` 支持 GET 和 POST 两种请求方法
C. `sendBeacon` 浏览器保证在页面关闭后仍会完成请求发送
D. `sendBeacon` 适合在页面卸载时上报监控数据

**答案：B**

**解析**：
- B 错误：`sendBeacon` 仅支持 POST 请求，不支持 GET
- A 正确：sendBeacon 是异步的，不会阻塞 unload 事件
- C 正确：浏览器会保证在页面关闭后完成 sendBeacon 请求
- D 正确：这是 sendBeacon 的主要使用场景

**4. 以下哪种方式最适合捕获 Promise 中未被 catch 的异常？**

A. `window.onerror`
B. `try...catch` 包裹所有 Promise
C. `window.addEventListener('unhandledrejection')`
D. `console.error` 劫持

**答案：C**

**解析**：
- C 正确：`unhandledrejection` 事件专门用于捕获未被 catch 处理的 Promise rejection
- A 错误：`window.onerror` 无法捕获 Promise 异常
- B 错误：`try...catch` 无法捕获异步的 Promise 异常（除非使用 async/await）
- D 错误：`console.error` 劫持只能捕获开发者主动调用的 `console.error`，无法捕获未处理的 Promise rejection

C. 64 位
D. 128 位

**答案：B**

**10. 以下关于告警策略的说法，错误的是？**

A. 告警应以错误次数为唯一标准，次数越多越严重
B. 告警应设置冷却时间，避免告警风暴
C. 告警应分级（critical/warning/info），不同级别不同通知渠道
D. 新出现的错误类型应立即告警，即使量很少

**答案：A**

**解析**：

- B、C、D 都是正确的告警策略原则

## 第二部分：简答题（共 8 题）

### 简答题 1：请描述前端监控 SDK 的架构设计，包含哪些核心模块？

**答案要点**：

前端监控 SDK 采用四层架构：

1. **数据采集层（Collector）**：
   - ErrorCollector：捕获 JS 错误、Promise 异常、资源加载错误、console 劫持
   - PerfCollector：采集 LCP/INP/CLS/FCP/TTFB、资源耗时、长任务
   - BusinessCollector：PV/UV、用户行为、API 调用成功率

2. **数据处理层（Processor）**：
   - 数据清洗：去重、脱敏、截断
   - 错误分组：fingerprint 计算
   - 数据聚合：批量合并

3. **上报层（Reporter）**：
   - 上报策略：sendBeacon（页面卸载）/ fetch keepalive（正常运行时）
   - 采样率控制：错误 100% / 性能 10% / 行为 5%
   - 本地缓冲：IndexedDB 存储失败数据，恢复后重试

4. **可视化层（Dashboard）**：
   - 对接 Grafana/Kibana 展示错误趋势、性能分布、用户行为漏斗

### 简答题 2：什么是 Sourcemap？如何安全地使用它？

**答案要点**：

Sourcemap 是压缩后代码与原始源码之间的映射文件，记录了变量名、行列号的对应关系。

**安全使用原则**：
- 生产环境使用 `hidden-source-map`（不添加 sourceMappingURL 注释，浏览器无法加载）
- 通过 CI/CD 自动上传 Sourcemap 到 Sentry 等监控平台
- 构建完成后删除 dist 目录中的 .map 文件
- 禁止将 .map 文件部署到生产环境 CDN
- 通过 Sentry Webpack Plugin 或 Vite Plugin 自动化上述流程

**三步曲**：构建生成 Sourcemap → 上传到监控平台 → 服务端自动还原错误堆栈。

### 简答题 3：Feature Flags 有哪四种类型？分别适用什么场景？

**答案要点**：

| 类型 | 适用场景 | 生命周期 |
|---|---|---|
| Release Toggles | 新功能开发完成但暂不发布 | 数天到数周，上线后清理 |

### 简答题 5：前端如何进行白屏检测？有哪些检测手段？

**答案要点**：

白屏检测采用三层判断机制：

1. **文本内容判断**：检查 root 容器内是否有可见文本（innerText 长度 > 10）
2. **媒体元素判断**：检查是否有可见的图片/Canvas/Video/SVG 元素
3. **采样点对比**（核心）：在页面上取 18 个均匀采样点（3x6 网格），使用 `elementFromPoint` 获取每个点的元素，如果超过 16 个点落在根节点上，判定为白屏

辅助手段：MutationObserver 监听 DOM 变化，定时（3 秒间隔）检测。

### 简答题 6：什么是可观测性三支柱？它们之间如何协作？

**答案要点**：

可观测性三支柱：Logs（日志）、Metrics（指标）、Traces（链路追踪）。

**协作关系**：
- Metrics 发现问题："错误率从 0.1% 上升到 2.5%"
- Traces 定位范围："是 /api/user 接口超时导致的"
- Logs 定位根因："数据库连接池耗尽，错误信息：ECONNREFUSED"

类比医院：Metrics 是体检数据（发现异常指标），Traces 是诊断流程（追踪病因路径），Logs 是病历（详细记录症状）。

### 简答题 7：如何设计一个合理的告警策略？

**答案要点**：

五项原则：
1. **基于影响用户数**：不以错误次数告警，以受影响用户数为准
2. **冷却时间**：同一规则两次告警之间有最小间隔（如 5 分钟）
3. **分级告警**：critical（即时通知）> warning（邮件通知）> info（汇总日报）
4. **趋势告警**：不只看绝对值，也看环比变化（错误率从 0.1% → 0.5%，即使未超 1% 阈值也应告警）
5. **新错误告警**：新出现的错误类型即时告警，即使量少

### 简答题 8：前端如何实现链路追踪？traceId 如何在前后端之间传递？

**答案要点**：

基于 W3C Trace Context 标准实现：

1. **生成 TraceContext**：前端生成 traceId（32 位十六进制）和 spanId（16 位十六进制）
2. **注入 HTTP 头**：在 fetch/XHR 请求中设置 `traceparent: 00-{traceId}-{spanId}-01`
3. **后端接收**：后端从请求头中提取 traceId，继续创建子 Span
4. **全链路关联**：所有服务使用同一个 traceId，各自生成 spanId
5. **数据上报**：各服务的 Span 数据上报到 Jaeger/Zipkin/Sentry 等追踪系统，通过 traceId 关联展示

> - [MDN - Beacon API](https://developer.mozilla.org/zh-CN/docs/Web/API/Beacon_API)
> - [OpenTelemetry官方文档](https://opentelemetry.io/docs/)

### 场景设计题 1：设计一个完整的前端监控体系

### 场景设计题 2：设计一个灰度发布方案

**题目**：某产品需要上线一个重大改版，涉及前端 UI 重构和后端 API 变更。请设计灰度发布方案。

**答案要点**：

**一、方案选型**：灰度发布（Canary）+ Feature Flags 组合

**二、分层灰度策略**：

```
第一层：Nginx 层（流量入口）
  - 10% 用户 → 新版本静态资源
  - 90% 用户 → 旧版本
  - 分流方式：split_clients 按 IP 哈希

第二层：Feature Flags 层（应用内）
  - 新功能通过 Flag 控制
  - 灰度用户组通过 Unleash 管理
  - 支持按用户 ID / 地区 / 设备分群

第三层：API 层（后端）
  - Nginx 根据 version header 路由到不同后端服务
  - 灰度期间 API 版本化（/api/v1 和 /api/v2 共存）
```

**三、放量计划**：
- 第 1 天：内部测试用户（白名单）
- 第 2-3 天：1% 流量
- 第 4-5 天：10% 流量
- 第 6-7 天：50% 流量
- 第 8 天：100% 流量

**四、回滚策略**：
- Nginx 层：修改 split_clients 比例回退
- Feature Flags 层：关闭 Flag
- 紧急回滚：K8s 回滚到上一版本镜像

**五、监控指标**：错误率、P99 响应时间、转化率、用户反馈量

### 场景设计题 3：设计一个线上故障排查流程

**题目**：线上突然收到大量用户反馈"页面白屏"，同时监控平台收到大量 JS 错误告警。请设计完整的排查流程。

**答案要点**：

**一、故障发现**：
- 用户反馈：页面白屏，无法正常使用
- 监控告警：Sentry 错误率飙升到 5%，错误类型：`TypeError: Cannot read properties of undefined`
- 影响范围：约 5000 用户，Chrome 浏览器占比 95%

**二、故障定位**：
1. 查看 Sentry 错误详情，通过 Sourcemap 还原定位到源码位置
2. 查看 Breadcrumbs：用户访问页面 → 加载数据 → 错误发生
3. 查看 Release：最近一次发布 v1.2.3
4. 查看 Tags：特定浏览器版本 + 特定用户数据格式

**三、故障复现**：
- 本地模拟相同浏览器版本和用户数据
- 确认错误可稳定复现

**四、故障修复**：
- 修复代码（添加可选链/空值判断）
- 编写单元测试覆盖边界情况
- Code Review

**五、验证上线**：
- 灰度发布到 10% 用户
- 监控确认错误率下降
- 逐步放量至 100%

**六、复盘总结**：
- 根因分析：后端接口变更返回格式，前端未做兼容处理
- 改进措施：添加接口返回格式校验；增加端到端测试；完善 Code Review 清单

### 场景设计题 4：设计一个告警策略

**题目**：为前端监控系统设计一套完整的告警策略，覆盖错误、性能、可用性。

**答案要点**：

**一、错误告警**：

| 规则 | 条件 | 级别 | 冷却 | 通知 |
|---|---|---|---|---|
| 错误率飙升 | 5 分钟错误率 > 1% 且影响用户 > 50 | critical | 5 分钟 | 钉钉 + 飞书 + 电话 |

**二、性能告警**：

| 规则 | 条件 | 级别 | 冷却 | 通知 |
|---|---|---|---|---|
| P99 响应慢 | P99 > 3s | warning | 10 分钟 | 飞书 |
| LCP 超标 | P75 LCP > 4s | warning | 30 分钟 | 邮件 |
| CLS 超标 | P75 CLS > 0.25 | info | 60 分钟 | 邮件 |

**三、可用性告警**：

| 规则 | 条件 | 级别 | 冷却 | 通知 |
|---|---|---|---|---|
| 可用性下降 | 可用性 < 99.9% | critical | 5 分钟 | 钉钉 + 飞书 + 电话 |
| 白屏检测 | 检测到白屏 | critical | 5 分钟 | 钉钉 + 飞书 |

**四、降噪策略**：
- 同一错误 5 分钟内最多告警 1 次
- 同一类错误每天最多告警 10 次
- 非工作时间仅 critical 级别通知

### 场景设计题 5：设计一个前端容器化部署架构

**题目**：某前端项目需要实现容器化部署，支持滚动更新、健康检查、弹性伸缩。请设计部署架构。

**答案要点**：

**一、Docker 镜像设计**：

```
多阶段构建：
  Stage 1 (Node.js) → 构建静态资源
  Stage 2 (Nginx) → 仅保留构建产物 + Nginx 配置

镜像大小：< 50MB（Alpine Nginx + 静态资源）
```

**二、K8s 部署架构**：

```yaml
Deployment:
  replicas: 3
  strategy: RollingUpdate
    maxSurge: 1        # 更新时最多额外 1 个 Pod
    maxUnavailable: 0  # 保证零停机

Service:
  type: ClusterIP
  selector: app=frontend

Ingress:
  域名 → Service → Pod
```

**三、健康检查**：
- 就绪探针（readinessProbe）：HTTP GET /health
- 存活探针（livenessProbe）：HTTP GET /health
- 启动探针（startupProbe）：初始延迟 10s

**四、弹性伸缩**：
- HPA：CPU > 70% 或内存 > 80% 时自动扩容
- 最小副本数：3，最大副本数：10

**五、CI/CD 流程**：
1. 代码提交 → 触发 CI
2. 构建 Docker 镜像 → 推送镜像仓库
3. 更新 K8s Deployment 镜像版本
4. K8s 执行滚动更新
5. 健康检查通过 → 旧 Pod 终止

**六、灰度发布集成**：
- 通过 Nginx Ingress 的 canary 注解实现灰度
- 新版本服务用单独的 Deployment，逐步调整流量比例
