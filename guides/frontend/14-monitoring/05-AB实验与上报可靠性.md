# 05-AB实验与上报可靠性

> **推荐版本**：Node.js 20+、现代浏览器（Chromium 88+ / Safari 14+）

---

## 一、核心概念

### 1.1 A/B 实验平台的整体架构

A/B 实验（A/B Testing）是把流量随机分成对照组与实验组，通过指标对比判断改动是否有效的方法论。它不是"前端功能"，而是一套跨端平台：

```
┌──────────────────────────────────────────────────────┐
│  实验管理平台：实验创建 → 层/域配置 → 流量分配 → 指标定义 → 启停 │
└──────────────────────────────────────────────────────┘
                        ▲ 配置下发（版本化）
┌──────────────────────────────────────────────────────┐
│  配置服务：配置版本、按应用/环境隔离、缓存与 CDN 分发             │
└──────────────────────────────────────────────────────┘
                        ▲ 拉取配置（HTTP + 本地缓存）
┌──────────────────────────────────────────────────────┐
│  客户端 SDK：① 分流 hash(unit+salt) → bucket → variant │
│             ② 缓存 localStorage 持久化，冷启动可用      │
│             ③ 曝光：真正渲染变体后才上报 exposure        │
└──────────────────────────────────────────────────────┘
                        ▲ 曝光 / 转化事件
┌──────────────────────────────────────────────────────┐
│  数据链路：埋点 → 数仓 → 按 variant 聚合 → 统计检验 → 报告 │
└──────────────────────────────────────────────────────┘
```

前端只负责三件事，但每件都决定结论是否可信：

| 职责 | 关键问题 | 失效后果 |
|---|---|---|
| 稳定分流 | 同一用户每次访问进入同一变体 | 用户看到 A/B 交替闪烁，指标被稀释 |
| 曝光上报 | 只有"真正看到变体"才计入分母 | 分母虚高，实验灵敏度下降 |
| 事件归因 | 所有转化事件携带分流信息 | 转化无法归因，结论错误 |

### 1.2 实验与灰度的区别

| 维度 | 灰度发布 | A/B 实验 |
|---|---|---|
| 目的 | 降低发布风险，验证稳定性 | 验证假设，比较方案优劣 |
| 对照组 | 通常没有 | 必须有（control + treatment） |
| 流量分配 | 逐步放量 1% → 10% → 100% | 随机均匀分组（50/50 或按比例） |
| 判据 | 技术指标（错误率、崩溃率、性能） | 业务指标（转化率、留存）+ 统计显著性 |
| 生命周期 | 全量后消失 | 得出结论后关闭，可能全量也可能下线 |
| 失败处理 | 回滚版本 | 下线实验组，保留对照组 |
| 核心风险 | 新版本不稳定 | 结论不可信（SRM、样本偏差） |

**一句话区分**：灰度是"先让少数人用，确认不坏"；实验是"让两组人用不同方案，确认哪个更好"。实践中常组合：先用灰度把实验配置下发到 1% 流量冒烟，再放量到实验所需样本量。

### 1.3 数据上报可靠性的三个层次

```
第一层：发送可靠性（能不能发出去）
  - 方式选型：fetch keepalive / sendBeacon / img 打点
  - 卸载时机：visibilitychange(hidden) + pagehide，而非 unload
  - 失败降级：beacon 失败 → 本地持久化
第二层：送达可靠性（发出去会不会丢）
  - 离线队列：IndexedDB / localStorage 持久化
  - 重试：指数退避 + 抖动 + 上限 + 过期丢弃
  - 去重：客户端 event_id + 服务端幂等
第三层：口径可靠性（数据对不对）
  - 采样：一致性采样（按用户哈希）而非纯随机
  - 采样率随数据上报，便于数据侧还原真实量级
  - 对账：前端上报量与业务库数据交叉验证
```

### 1.4 SLO 与错误预算

| 概念 | 全称 | 定义 | 例子 |
|---|---|---|---|
| SLI | Service Level Indicator | 可测量的指标（分子/分母明确） | 可用性 = 无致命错误的会话数 / 总会话数 |
| SLO | Service Level Objective | 团队内部的指标目标 | 月度可用性 ≥ 99.9% |
| SLA | Service Level Agreement | 对外合同的承诺与违约条款 | 月度可用性 ≥ 99.5%，低于则赔付 |
| 错误预算 | Error Budget | `1 - SLO`，允许"犯错"的额度 | SLO 99.9% → 每月约 43.2 分钟 |

错误预算把"要不要发布"从主观争论变成客观决策：预算充足正常发布，耗尽则冻结功能发布、优先还技术债。

### 1.5 面试常见问法

- "A/B 实验和灰度发布有什么区别？" → 从目的、有无对照组、判据、生命周期四个维度对比。
- "前端在实验链路里负责什么？" → 稳定分流、曝光上报、事件归因。
- "SLO 和 SLA 有什么区别？" → SLO 是内部目标，SLA 是对外承诺，SLA 通常更宽松。

### 1.6 易错点

- 把"灰度开关"当"实验平台"用：没有对照组与统计检验，只能得到"新版本没坏"，得不到"新版本更好"。
- 实验没有明确的主要指标（OEC），上线后在海量指标里挑显著的那个，必然得到假阳性结论。
- SLO 定得过高（如 99.999%），错误预算几乎为 0，团队被迫停止一切变更。

## 二、底层原理

### 2.1 实验分流原理

#### 2.1.1 哈希分桶

```
unit（分流单元）= userId（登录）或 deviceId / anonymousId（未登录）
salt（实验盐）  = experimentId 或 layerId，保证不同实验分桶互相独立

bucket  = hash(unit + salt) % BUCKET_TOTAL   // 通常 10000
variant = 按流量比例划分桶号区间

例：BUCKET_TOTAL = 10000
  control   : bucket ∈ [0, 5000)
  treatment : bucket ∈ [5000, 10000)
  → 用户 U 的 bucket = 3721 → 命中 control
```

**三个必须满足的性质**：

1. **稳定性**：`hash` 是纯函数，同一 `unit + salt` 永远得到同一结果。排除 `Math.random()`、时间戳等不稳定输入。
2. **均匀性**：输出在桶空间均匀分布。用 MurmurHash3、FNV-1a、xxHash 等非加密哈希；`String.hashCode()` 这类弱哈希在大样本下分布明显不均。
3. **独立性**：不同实验 `salt` 不同，分桶互相独立，避免"总是同一批用户进实验组"。

```typescript
// ========== 分流核心实现 ==========

const BUCKET_TOTAL = 10000; // 桶总数固定，避免扩容导致全量重分桶

// FNV-1a 32 位哈希：实现简单、分布均匀、无依赖
function fnv1a(str: string): number {
  let hash = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    hash ^= str.charCodeAt(i);
    // 乘 FNV 素数 16777619，用移位加法避免 32 位溢出精度问题
    hash = (hash + ((hash << 1) + (hash << 4) + (hash << 7) + (hash << 8) + (hash << 24))) >>> 0;
  }
  return hash >>> 0;
}

function getBucket(unit: string, salt: string): number {
  return fnv1a(`${unit}::${salt}`) % BUCKET_TOTAL;
}

interface VariantRange { variant: string; start: number; end: number }

function pickVariant(bucket: number, ranges: VariantRange[]): string {
  const position = bucket / BUCKET_TOTAL; // 归一化到 [0, 1)
  for (const r of ranges) {
    if (position >= r.start && position < r.end) return r.variant;
  }
  return ranges[ranges.length - 1].variant; // 边界兜底
}

const bucket = getBucket('user_123', 'exp_home_ui');
const variant = pickVariant(bucket, [
  { variant: 'control', start: 0, end: 0.5 },
  { variant: 'treatment', start: 0.5, end: 1 },
]);
```

**为什么桶总数固定为 10000**：若从 100 改成 200，`hash % 100` 与 `hash % 200` 结果不同，所有用户被重新分桶——运行中的实验被污染，用户可能从对照组"漂移"到实验组。固定足够大的桶空间后，放量只通过调整区间实现，重分桶影响最小。

**放量时的重分桶**：从 50/50 调成 30/70 时，原本落在 `[0.5, 0.7)` 的用户会从 treatment 变 control，体验发生切换。工程做法：比例一经确定不再调整；需要调整时新建实验或新增变体（老变体区间不动）；必须调整则在报告中剔除切换期数据。

#### 2.1.2 一致性哈希

一致性哈希解决"节点增减时映射关系大面积失效"的问题，把节点与 key 都映射到哈希环上，key 顺时针找到第一个节点：

```
环上节点：nodeA(1000)、nodeB(3000)、nodeC(8000)
  key1 → 顺时针第一个节点 nodeB
  nodeB 下线后：key1 → nodeC
  → 只有原本属于 B 的 key 需要迁移，其他 key 不受影响
```

| 维度 | 普通取模 `hash % N` | 一致性哈希 |
|---|---|---|
| 节点增减影响 | 几乎所有 key 重新映射 | 只影响相邻节点的 key |
| 数据倾斜 | 无 | 有，需引入虚拟节点 |
| 实验分流适用性 | 适用（桶总数固定时等价） | 更适合"分片/路由"场景 |

> **实验分流不用一致性哈希**：实验桶总数固定为 10000，不存在节点增减问题。一致性哈希在实验体系里用于"配置缓存分片"或"流量在多计算节点间的路由"。

#### 2.1.3 分层正交（Layered Experiments）

单个实验只用 10% 流量，剩余 90% 若闲置就浪费了。分层正交让多个实验同时跑在同一批流量上而不互相干扰：

```
第 1 层 layer_ui   （salt = 'layer_ui'）
  ├── 域 domain_home   → exp_home_ui
  └── 域 domain_search → exp_search_rank
第 2 层 layer_algo （salt = 'layer_algo'）
  └── 域 domain_recommend → exp_rec_model

同一用户 U：
  hash(U + 'layer_ui')   → exp_home_ui 的 treatment
  hash(U + 'layer_algo') → exp_rec_model 的 control
  → 两个实验的命中结果互相独立（正交）
```

两条规则：

1. **层内互斥**：同层实验共享同一份流量池，一个用户在同层最多命中一个实验，保证同层实验不互相污染（如两个都在改首页 UI 的实验）。
2. **层间正交**：不同层用不同 `salt`，分桶结果独立，用户可同时进入多个层的实验，实现"总流量 100% 时并行跑多个实验"。

**域的划分依据**是"实验是否作用于同一用户旅程的同一环节"：首页 UI 实验 + 搜索排序实验不冲突，可放不同层；改按钮颜色的实验 + 改按钮文案的实验互相影响，必须放同层同域互斥。

#### 2.1.4 面试常见问法

- "实验分流怎么保证同一用户每次都进同一组？" → 纯函数哈希 + 固定桶总数 + 稳定的分流单元。
- "为什么不用随机数分流？" → 不稳定，同一用户看到不同变体，指标被稀释且体验受损。
- "分层正交的原理？" → 层内互斥（共享流量池）、层间独立 salt 保证正交，实现多实验并行。

#### 2.1.5 易错点

- 用 `Math.random()` 或时间戳参与分桶：分流不稳定，数据完全不可信。
- 未登录用户没有稳定标识，每次访问生成新 ID，同一人被分到不同组——必须首访持久化 `anonymous_id`。
- 实验运行中修改 `salt` 或桶总数：全量重分桶，历史数据与新增数据口径断裂。
- 把互相影响的实验放在不同层：两个实验都改同一个按钮，结论互相污染却无法察觉。

### 2.2 实验 SDK 设计

#### 2.2.1 配置拉取与缓存

实验配置的读取必须满足"**冷启动可用**"和"**不阻塞渲染**"，因此采用"本地缓存优先 + 异步刷新"：

```typescript
// ========== 实验配置管理：缓存优先 + 异步刷新 ==========

interface ExperimentConfig {
  key: string;
  variants: Array<{ name: string; weight: number }>; // 权重和为 1
  status: 'running' | 'paused' | 'stopped';
  targeting?: { platform?: string[]; appVersion?: string[] };
  version: number; // 配置版本，用于防回退与问题追溯
}

class ConfigManager {
  private static readonly CACHE_KEY = '_exp_config';
  private memory = new Map<string, ExperimentConfig>();
  private version = 0;

  constructor(private endpoint: string) {}

  // 冷启动：同步读本地缓存，保证首屏分流可用（不发网络请求）
  public loadFromCache(): void {
    try {
      const raw = localStorage.getItem(ConfigManager.CACHE_KEY);
      if (raw) this.apply(JSON.parse(raw));
    } catch {
      // 缓存损坏（被篡改 / JSON 截断）→ 静默降级为无配置
      localStorage.removeItem(ConfigManager.CACHE_KEY);
    }
  }

  // 异步刷新：不阻塞首屏；失败时保留旧配置，绝不把用户打回未分流状态
  public async refresh(): Promise<void> {
    try {
      const res = await fetch(`${this.endpoint}?version=${this.version}`, {
        credentials: 'include',
      });
      if (res.status === 304 || !res.ok) return; // 无更新或请求失败
      const data: { version: number; experiments: ExperimentConfig[] } = await res.json();
      if (data.version <= this.version) return; // 防止旧响应覆盖新配置
      this.apply(data);
      localStorage.setItem(ConfigManager.CACHE_KEY, JSON.stringify(data));
    } catch {
      // 网络失败：保持内存与缓存中的旧配置继续工作
    }
  }

  private apply(data: { version: number; experiments: ExperimentConfig[] }): void {
    this.version = data.version;
    this.memory = new Map(data.experiments.map((e) => [e.key, e]));
  }

  public get(key: string): ExperimentConfig | undefined {
    return this.memory.get(key);
  }
}
```

| 策略 | 冷启动可用 | 实时性 | 适用场景 |
|---|---|---|---|
| 仅内存 | 否（首屏无法分流） | 高 | 不推荐 |
| localStorage + 异步刷新 | 是 | 中（TTL 内） | **推荐默认方案** |
| localStorage + 轮询 | 是 | 中 | 需要较快生效的实验 |
| SSE / WebSocket 推送 | 是 | 高 | 秒级生效的紧急开关（Kill Switch） |

#### 2.2.2 分流结果的稳定性

```typescript
// ========== 实验客户端：分流 + 曝光 ==========

class ExperimentClient {
  private decisions = new Map<string, string>(); // 分流结果缓存
  private exposed = new Set<string>();           // 曝光去重

  constructor(
    private config: ConfigManager,
    private unit: () => string,                  // userId 或 anonymousId
    private onExposure: (key: string, variant: string) => void
  ) {}

  public getVariant(key: string, fallback = 'control'): string {
    // 1. 已决策过直接返回，避免重复计算导致结果漂移
    const cached = this.decisions.get(key);
    if (cached !== undefined) return cached;

    const exp = this.config.get(key);
    // 2. 配置缺失 / 实验已停止 / 定向不匹配 → 返回兜底值
    if (!exp || exp.status !== 'running' || !this.matchTargeting(exp)) return fallback;

    // 3. 哈希分桶：salt 用实验 key，保证实验间独立
    const variant = pickVariant(getBucket(this.unit(), key), this.toRanges(exp.variants));
    this.decisions.set(key, variant);
    return variant;
  }

  // 曝光上报：必须由业务在"变体真正渲染"后调用
  public trackExposure(key: string): void {
    const variant = this.getVariant(key);
    const exposureKey = `${key}::${variant}`;
    if (this.exposed.has(exposureKey)) return; // 会话内去重
    this.exposed.add(exposureKey);
    this.onExposure(key, variant);
  }

  private toRanges(variants: ExperimentConfig['variants']): VariantRange[] {
    let acc = 0;
    return variants.map((v) => {
      const start = acc;
      acc += v.weight;
      return { variant: v.name, start, end: acc };
    });
  }

  private matchTargeting(exp: ExperimentConfig): boolean {
    const t = exp.targeting;
    if (!t) return true;
    if (t.platform && !t.platform.includes(PLATFORM)) return false;      // PLATFORM = 'web'
    if (t.appVersion && !t.appVersion.includes(APP_VERSION)) return false; // 构建时注入
    return true;
  }
}
```

**稳定性的三个保护**：

1. **决策缓存**：会话内缓存分流结果，配置中途刷新也不会让用户切换变体。
2. **兜底值**：配置失败、实验停止、定向不匹配时返回 `control`，业务必须能容忍任意兜底值——这是"实验不影响可用性"的前提。
3. **曝光与分流解耦**：`getVariant` 只做决策，`trackExposure` 才上报，"读取了变体但没渲染"不会污染曝光分母。

**曝光时机选择**：

| 时机 | 问题 | 结论 |
|---|---|---|
| SDK 初始化时上报所有实验曝光 | 用户可能根本没看到 | 分母虚高 |
| `getVariant` 调用时上报 | 组件可能未被渲染 | 分母虚高 |
| 组件渲染提交后上报（React `useEffect`） | 与"用户看到"最接近 | **推荐** |
| 元素进入视口后上报 | 最严格 | 适合首屏外的实验位 |

#### 2.2.3 面试常见问法

- "实验配置怎么拉取？冷启动怎么办？" → 本地缓存优先 + 异步刷新 + 兜底值，强调不阻塞首屏。
- "分流结果怎么保证稳定？" → 纯函数哈希 + 决策缓存 + 配置版本号防回退。
- "曝光埋点什么时候上报？" → 变体真正渲染后；不要用"读取变体"或"SDK 初始化"作为时机。
- "配置拉取失败会怎样？" → 使用缓存或兜底 `control`，实验系统故障不应影响业务可用性。

#### 2.2.4 易错点

- 在 React 组件体内调用曝光上报：StrictMode 双渲染、并发渲染重放会导致重复曝光。
- 配置刷新后未比较版本号，旧响应覆盖新配置，出现"实验开关回跳"。
- 兜底值用了 `treatment` 而非 `control`：配置服务故障时全量用户看到未验证方案。

### 2.3 上报方式对比与页面卸载上报

#### 2.3.1 四种上报方式

| 维度 | XMLHttpRequest | fetch（`keepalive: true`） | `navigator.sendBeacon` | img 像素打点 |
|---|---|---|---|---|
| API 形态 | 事件回调 | Promise | 同步返回布尔值 | 赋值 `img.src` |
| 请求方法 | 任意 | 任意 | 仅 POST | 仅 GET |
| 自定义请求头 | 支持 | 支持 | **不支持** | 不支持 |
| 读取响应 | 支持 | 支持 | 不支持（只知是否入队） | 不支持 |
| 页面卸载后继续 | 不支持（请求会被取消） | 支持 | 支持（浏览器保证排队发送） | 支持 |
| 体积限制 | 无（受服务端限制） | 单页 keepalive 总量约 64KB | 队列总量约 64KB，超限返回 `false` | URL 长度限制（约 2KB） |
| 跨域 | 需 CORS | 需 CORS | 需 CORS | 天然允许（图片跨域加载无需 CORS） |
| 兼容性 | 最好（含 IE） | Chrome 66+ / Safari 13+ | Chrome 39+ / Safari 11.1+ | 全兼容 |
| 被拦截风险 | 中 | 中 | 中 | 高（广告拦截插件常拦像素域名） |
| 适用场景 | 需要响应结果的上报 | 常规批量上报 | **页面卸载时的关键上报** | 极简跨域埋点、兼容性兜底 |

**选型结论**：运行期用 `fetch`（可读响应、可重试、体积无限制）；卸载期用 `sendBeacon`；`sendBeacon` 不可用或需要极简跨域时降级 img 打点；`XMLHttpRequest` 仅在需要兼容老浏览器时使用。

#### 2.3.2 为什么 `visibilitychange` / `pagehide` 优于 `unload`

```typescript
// ========== 页面生命周期与上报时机 ==========

// ❌ 不推荐：unload 已废弃且不可靠
// window.addEventListener('unload', () => reporter.flush());
// 问题 1：移动端（尤其 iOS Safari）在切 App / 划掉标签页 / 系统回收时经常不触发
// 问题 2：注册 unload 监听器会使页面无法进入 bfcache，返回时重新加载
// 问题 3：unload 中发起的普通异步请求会被浏览器取消（除非用 sendBeacon / keepalive）

// ✅ 推荐：visibilitychange → hidden 是最早、最可靠的信号
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    // 可能只是切后台（并未卸载），也可能即将卸载；两种情况都应发出数据
    reporter.flush('hidden');
  }
});

// ✅ 推荐：pagehide 作为卸载兜底
window.addEventListener('pagehide', (event: PageTransitionEvent) => {
  // persisted === true 表示页面进入 bfcache（并未真正卸载）
  reporter.flush(event.persisted ? 'bfcache' : 'unload');
});

// ✅ 配套：从 bfcache 返回时恢复状态
window.addEventListener('pageshow', (event: PageTransitionEvent) => {
  if (event.persisted) reporter.resume(); // DOM 与内存都在，但定时器/连接可能已失效
});
```

| 事件 | 触发时机 | 可靠性 | 是否影响 bfcache | 建议用途 |
|---|---|---|---|---|
| `visibilitychange` → hidden | 页面不可见（切后台 / 切标签 / 即将卸载） | 高 | 不影响 | **上报主时机** |
| `pagehide` | 页面卸载前 / 进入 bfcache 时 | 高 | 不影响 | 上报兜底、清理 |
| `unload` | 页面真正卸载时 | 低（移动端常不触发） | **会使页面无法进入 bfcache** | 不再使用 |
| `beforeunload` | 卸载前，可弹确认框 | 中 | 会影响 | 仅用于"离开前提示" |

> 关键认知：**"页面不可见"比"页面卸载"更早、更可靠**。移动端切到别的 App 时页面可能永远不触发卸载事件，但一定会触发 `visibilitychange`。

#### 2.3.3 面试常见问法

- "页面关闭时怎么保证埋点不丢？" → `visibilitychange(hidden)` + `pagehide` + `sendBeacon`，并解释 `unload` 不可靠、破坏 bfcache。
- "`sendBeacon` 和 `fetch keepalive` 怎么选？" → 卸载场景优先 `sendBeacon`（不阻塞、无单请求 64KB 限制），需要读响应或自定义 header 时用 `fetch`；两者都有总量限制，需配合离线队列。
- "img 打点还有什么用？" → 天然跨域、兼容性最好，适合极简埋点与降级兜底，但受 URL 长度限制且易被拦截。
- "`sendBeacon` 返回 `false` 说明什么？" → 浏览器无法把请求加入发送队列（通常队列总量超限），必须降级处理。

#### 2.3.4 易错点

- 只用 `beforeunload` 上报且用普通 `fetch`：请求被取消，数据静默丢失。
- 在 `hidden` 回调里做同步耗时操作（大对象序列化、等待 IndexedDB 事务）：阻塞页面切换，用户感知卡顿。
- 忽略 `sendBeacon` 返回值：队列超限时数据直接丢失且无记录。
- 注册 `unload` 监听器：页面失去 bfcache 资格，返回时重新加载，性能与体验双输。

### 2.4 离线补发机制

#### 2.4.1 存储选型

| 维度 | localStorage | IndexedDB |
|---|---|---|
| API 形态 | 同步 | 异步（事件 / Promise 封装） |
| 容量 | 约 5MB | 通常为磁盘配额的较大比例（数百 MB 起） |
| 数据类型 | 仅字符串 | 结构化对象、Blob、ArrayBuffer |
| 事务与索引 | 无 | 支持 |
| 主线程阻塞 | 会 | 不会 |
| 适用场景 | 少量简单状态 | **上报队列（推荐）** |

#### 2.4.2 队列 + 重试 + 去重

```typescript
// ========== 离线队列：持久化 + 去重 + 上限裁剪 ==========

interface OfflineRecord {
  id?: number;      // 自增主键
  event_id: string; // 业务唯一 ID，服务端据此幂等
  payload: unknown;
  createdAt: number;
  retryCount: number;
}

class OfflineQueue {
  private static readonly DB = 'track-offline';
  private static readonly STORE = 'events';
  private static readonly MAX_ITEMS = 500;             // 条数上限
  private static readonly MAX_AGE = 7 * 24 * 3600_000; // 7 天后丢弃
  private dbPromise: Promise<IDBDatabase> | null = null;

  private open(): Promise<IDBDatabase> {
    // 复用连接，避免频繁 open 的开销与句柄泄漏
    this.dbPromise ??= new Promise((resolve, reject) => {
      const req = indexedDB.open(OfflineQueue.DB, 1);
      req.onupgradeneeded = () => {
        const store = req.result.createObjectStore(OfflineQueue.STORE, {
          keyPath: 'id',
          autoIncrement: true,
        });
        // event_id 唯一索引：重复写入直接失败，天然去重
        store.createIndex('event_id', 'event_id', { unique: true });
        store.createIndex('createdAt', 'createdAt');
      };
      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
    return this.dbPromise;
  }

  public async save(events: Array<{ event_id: string } & Record<string, unknown>>): Promise<void> {
    const db = await this.open();
    const tx = db.transaction(OfflineQueue.STORE, 'readwrite');
    const store = tx.objectStore(OfflineQueue.STORE);
    const now = Date.now();

    for (const e of events) {
      store.add({ event_id: e.event_id, payload: e, createdAt: now, retryCount: 0 });
    }
    this.trim(store, now); // 写入后裁剪：先删过期，再按上限删最旧
    await new Promise<void>((resolve) => { tx.oncomplete = () => resolve(); });
  }

  private trim(store: IDBObjectStore, now: number): void {
    const cutoff = now - OfflineQueue.MAX_AGE;
    // 过期清理
    store.index('createdAt').openCursor().onsuccess = (ev) => {
      const cursor = (ev.target as IDBRequest<IDBCursorWithValue | null>).result;
      if (!cursor) return;
      if ((cursor.value as OfflineRecord).createdAt < cutoff) cursor.delete();
      cursor.continue();
    };
    // 超限裁剪：从最旧的开始删，保证最近数据优先保留
    const countReq = store.count();
    countReq.onsuccess = () => {
      let overflow = countReq.result - OfflineQueue.MAX_ITEMS;
      if (overflow <= 0) return;
      store.index('createdAt').openCursor().onsuccess = (ev) => {
        const cursor = (ev.target as IDBRequest<IDBCursorWithValue | null>).result;
        if (!cursor || overflow-- <= 0) return;
        cursor.delete();
        cursor.continue();
      };
    };
  }

  public async drain(): Promise<OfflineRecord[]> {
    const db = await this.open();
    const req = db.transaction(OfflineQueue.STORE, 'readonly')
      .objectStore(OfflineQueue.STORE).getAll();
    return new Promise((resolve) => {
      req.onsuccess = () => resolve(req.result as OfflineRecord[]);
      req.onerror = () => resolve([]);
    });
  }

  public async remove(ids: number[]): Promise<void> {
    const db = await this.open();
    const tx = db.transaction(OfflineQueue.STORE, 'readwrite');
    const store = tx.objectStore(OfflineQueue.STORE);
    ids.forEach((id) => store.delete(id));
    await new Promise<void>((resolve) => { tx.oncomplete = () => resolve(); });
  }
}
```

```typescript
// ========== 补发调度：启动 / 网络恢复 / 定时 ==========

class OfflineResender {
  private static readonly MAX_RETRY = 5;
  private flushing = false;

  constructor(
    private queue: OfflineQueue,
    private send: (payloads: unknown[]) => Promise<boolean>
  ) {
    void this.flush();                                    // 1. 启动补发
    window.addEventListener('online', () => void this.flush()); // 2. 网络恢复
    window.setInterval(() => void this.flush(), 60_000);  // 3. 定时兜底
  }

  public async flush(): Promise<void> {
    // 并发保护：避免多个触发源同时补发导致重复上报
    if (this.flushing) return;
    this.flushing = true;
    try {
      const records = await this.queue.drain();
      const BATCH = 20;
      for (let i = 0; i < records.length; i += BATCH) {
        const batch = records.slice(i, i + BATCH);
        const ok = await this.send(batch.map((r) => r.payload));
        if (!ok) break; // 本批失败，暂停后续批次，等待下次触发
        // 服务端已按 event_id 幂等，重复发送也安全
        await this.queue.remove(batch.map((r) => r.id!));
      }
    } finally {
      this.flushing = false;
    }
  }
}
```

**去重必须在服务端兜底**：客户端去重只能减少重复，不能消除（补发、多标签页、重试都会产生重复）。服务端必须按 `event_id` 做幂等写入（唯一索引 / Redis `SETNX`），否则数据侧需额外去重，成本更高且容易漏。

#### 2.4.3 面试常见问法

- "离线数据怎么补发？" → IndexedDB 队列 + 指数退避重试 + 上限与过期丢弃 + 启动/`online`/定时三种触发 + 服务端幂等去重。
- "为什么用 IndexedDB 而不是 localStorage？" → 异步不阻塞主线程、容量大、支持事务与索引、可存结构化数据。
- "重试会不会造成重复数据？" → 会，所以必须有 `event_id` + 服务端幂等；客户端只做"减少重复"。
- "队列满了怎么办？" → 丢最旧 + 上报丢弃计数，使数据量下降可归因；关键事件走单独的高优先级队列。

#### 2.4.4 易错点

- 用 `localStorage` 存队列：同步 API 写入大 JSON 时阻塞主线程，且 5MB 上限很快被打满。
- 重试无上限、无退避：服务端故障时形成重试风暴。
- 补发没有并发保护：`online` 事件与定时器同时触发，同一批数据被发两次。
- 服务端没做幂等，却依赖"客户端保证不重复"——架构上的必败假设。
- 队列长期保留敏感数据：既占空间又带来合规风险，需设置过期时间并脱敏。

### 2.5 采样策略

| 策略 | 做法 | 适用 | 风险 |
|---|---|---|---|
| 全量上报 | 不过滤 | 错误、支付等关键事件 | 数据量大、成本高 |
| 随机采样 | `Math.random() < rate` | 性能指标（如 10%） | **破坏漏斗**：同一用户的 PV 采到、点击没采到 |
| 一致性采样 | `hash(unit) % 10000 < rate * 10000` | 行为埋点、性能指标 | 需稳定 `unit`，未登录依赖 `anonymous_id` |
| 分层采样 | 按事件/错误类型配不同采样率 | 高频错误 1%、新错误 100% | 需维护采样配置与统计口径 |
| 动态采样 | 按当日上报量自动调整 | 大促等流量尖峰 | 采样率变化频繁，数据侧需按时间段还原 |

```typescript
// ========== 一致性采样：同一用户在窗口内"全采或全不采" ==========

function shouldSampleByUnit(unit: string, salt: string, rate: number): boolean {
  if (rate >= 1) return true;
  if (rate <= 0) return false;
  // 复用分流的哈希能力：桶号落在前 rate 比例内则采样
  return getBucket(unit, `sample::${salt}`) < rate * BUCKET_TOTAL;
}
```

**采样率必须随数据上报**，否则数据侧无法还原真实量级：

```json
{ "event": "page_view", "common": { "sample_rate": 0.1 } }
// 数据侧还原：真实 PV ≈ 采样到的 PV / 0.1
```

#### 2.5.1 面试常见问法

- "上报采样怎么做？" → 一致性采样优于随机采样（漏斗不破裂）；采样率随数据上报；关键事件全量。
- "随机采样有什么问题？" → 同一用户部分事件被丢弃，漏斗分子分母不匹配，转化率被严重扭曲。
- "采样后怎么算总量？" → 按 `sample_rate` 加权还原，并注明是估算值。

#### 2.5.2 易错点

- 对曝光与转化用**独立**的随机采样：曝光采到、转化没采到，转化率算出来可能 > 100%。
- 采样率变了但历史数据没有记录采样率，数据侧无法还原。
- 对错误上报做随机采样却只保留采样数据，造成"错误量下降"的假象（应上报真实总量估算值）。

### 2.6 SLI / SLO / SLA 与错误预算

#### 2.6.1 前端 SLO 的设定

| SLI | 定义（分子/分母） | 建议 SLO | 数据来源 |
|---|---|---|---|
| 可用性 | 无致命错误的会话数 / 总会话数 | ≥ 99.9% | 错误监控 SDK |
| 加载性能达标率 | P75 LCP < 2.5s 的会话数 / 总会话数 | ≥ 95% | 性能采集 / RUM |
| 接口错误率 | 失败请求数 / 总请求数 | ≤ 1% | 接口埋点 / 网关 |
| 白屏率 | 白屏会话数 / 总会话数 | ≤ 0.1% | 白屏检测 SDK |
| 交互可用性 | P75 INP < 200ms 的会话数 / 总会话数 | ≥ 95% | PerformanceObserver |

**三条设计原则**：

1. **按会话/用户聚合，而非按请求**：一个用户的 100 次请求失败与 1 次失败，对体验影响完全不同。
2. **用分位数而非均值**：均值会被大量快速请求拉平，掩盖长尾用户的糟糕体验；P75 是 Core Web Vitals 的官方口径。
3. **指标必须可行动**：报警后没人知道该做什么的 SLI，不该作为 SLO。

#### 2.6.2 错误预算与燃尽率

```
SLO = 99.9%（月度）→ 错误预算 = 0.1%
月度总分钟数 ≈ 30 × 24 × 60 = 43,200 分钟 → 预算 ≈ 43.2 分钟

常见 SLO 对应的月度预算：
  99%    → 7.2 小时      99.9%  → 43.2 分钟
  99.95% → 21.6 分钟     99.99% → 4.32 分钟
```

**燃尽率（Burn Rate）** = 实际错误率 / 允许错误率，表示当前消耗速度是"恰好用完预算"的多少倍：

```
SLO 99.9% → 允许错误率 0.1%
过去 1 小时实际错误率 1.44% → 燃尽率 = 1.44% / 0.1% = 14.4
含义：按此速度，30 天的预算将在 30 / 14.4 ≈ 2 天内耗尽 → 立即告警
```

**多窗口多燃尽率告警**（Google SRE Workbook）：单一窗口要么太灵敏（噪音多）要么太迟钝（发现晚），因此用"长窗口 + 短窗口"组合：

| 级别 | 长窗口 | 短窗口 | 燃尽率阈值 | 预算消耗 | 含义 |
|---|---|---|---|---|---|
| P0 | 1 小时 | 5 分钟 | 14.4 | 2% | 快速烧钱，立即介入 |
| P1 | 6 小时 | 30 分钟 | 6 | 5% | 持续异常，当天处理 |
| P2 | 3 天 | 6 小时 | 1 | 10% | 慢速消耗，排期修复 |

**错误预算联动发布策略**：

| 预算消耗 | 策略 |
|---|---|
| < 50% | 正常发布，按常规节奏迭代 |
| 50% - 100% | 谨慎发布：需负责人审批，只允许小流量灰度 |
| ≥ 100% | **冻结功能发布**，只允许修复性发布，直到预算恢复 |

#### 2.6.3 告警分级与降噪

```yaml
# ========== 告警规则示例（Prometheus Alertmanager 风格）==========
groups:
  - name: frontend-slo
    rules:
      # P0：1 小时长窗口燃尽率 > 14.4，且 5 分钟短窗口确认
      - alert: FrontendErrorBudgetBurnFast
        expr: |
          (sum(rate(frontend_fatal_errors_total[1h])) / sum(rate(frontend_sessions_total[1h]))) > (14.4 * 0.001)
          and
          (sum(rate(frontend_fatal_errors_total[5m])) / sum(rate(frontend_sessions_total[5m]))) > (14.4 * 0.001)
        for: 2m
        labels:
          severity: P0
        annotations:
          summary: "前端错误预算快速燃烧，2 天内将耗尽月度预算"
          runbook: "https://wiki.example.com/runbook/frontend-errors"
```

| 降噪手段 | 做法 | 解决的问题 |
|---|---|---|
| 聚合 | 相同 fingerprint 的错误合并为一条告警 | 一个错误重复告警数百次 |
| 抑制（Inhibit） | 上游故障时抑制下游告警 | 一次故障引发全链路告警风暴 |
| 冷却（Cooldown） | 同一告警 N 分钟内不重复通知 | 通知轰炸 |
| 分级 | P0 电话 / P1 群消息 / P2 工单 | 所有告警同一渠道导致麻木 |
| 按影响面 | 按影响用户数/会话比例设阈值，而非错误次数 | 高频但无人受影响的错误误报 |
| 行动性审查 | 每条告警必须有明确处理动作与责任人 | 无法行动的告警应删除 |

#### 2.6.4 面试常见问法

- "SLI、SLO、SLA 有什么区别？" → 指标 / 内部目标 / 对外承诺；SLA 通常比 SLO 宽松。
- "什么是错误预算？怎么用？" → `1 - SLO`；预算消耗驱动发布决策（充足正常发布、耗尽冻结发布）。
- "燃尽率告警为什么用多窗口？" → 长窗口看趋势、短窗口看确认，兼顾灵敏度与降噪。
- "前端 SLO 怎么定？" → 可用性、加载性能达标率、接口错误率、白屏率；按会话聚合、用 P75、必须可行动。
- "告警太多怎么办？" → 聚合、抑制、冷却、分级、按影响面、行动性审查。

#### 2.6.5 易错点

- 把 SLA 当 SLO 用：对外承诺更宽松，用它做内部目标会让团队失去改进动力。
- SLO 覆盖率 100%：预算为 0，任何变更都会被"冻结"，实际无法执行。
- 用错误**次数**做阈值：一个用户循环报错 1000 次就触发 P0，实际影响面只有 1 人。
- 只设单窗口燃尽率告警：阈值低则噪音大、阈值高则发现晚，团队会逐渐忽略告警。

```typescript
    // 曝光事件必须携带分流信息，否则数据侧无法归因
    track.track('experiment_exposure', { experiment_key: key, variant });
    // 写入公共参数：后续所有转化事件都会带上该实验分组
    track.setCommonParams({ experiment: { [key]: variant } });
  }
);

// 第四步：异步刷新配置（不阻塞渲染）
void configManager.refresh();

// 第五步：登录后打通匿名 ID 与用户 ID
function onLogin(userId: string) {
  track.setUser(userId);
  void configManager.refresh(); // 分流单元从 anonymousId 切换为 userId
}
```

### 3.2 指标口径与实验分析

**曝光转化率**：

```
口径 A（用户口径，推荐）：
  曝光转化率 = 发生转化的用户数 / 曝光用户数
  例：1000 人看到实验位，50 人下单 → 5%
口径 B（事件口径）：
  转化率 = 转化事件数 / 曝光事件数
  例：曝光 3000 次（同一用户多次曝光），转化 60 次 → 2%
  问题：同一用户多次曝光被重复计入分母，口径被稀释
结论：统一用「用户口径」+ 去重，并明确去重窗口（实验期 / 每日 / 会话内）
```

**留存指标**：

```
次日留存（D1 Retention）：
  D1 留存率 = 第 D+1 日仍活跃的「第 D 日新增用户」数 / 第 D 日新增用户数
  → 必须按同期群（cohort）计算，而不是"今日活跃 / 昨日活跃"
要求：两组的新增定义一致（"首次访问"还是"首次下单"）；
      窗口必须完整（D7 要等 7 天）；实验跑满 1-2 个完整周期（含周末）
```

**实验结论判定清单**：

```
① 样本量是否达到预期？（未达最小样本量不要下结论）
② 是否有 SRM？（期望比例 vs 实际比例，卡方检验 p < 0.001 判为 SRM）
③ 主要指标是否显著？（预设 OEC，p < 0.05 且置信区间不含 0）
④ 是否有多重比较问题？（多指标/多变体需 Bonferroni 或 FDR 校正）
⑤ 是否出现辛普森悖论？（整体显著但分层不显著，或反之）
⑥ 是否存在新奇效应？（短期数据好、长期回落，需延长观察）
⑦ 护栏指标是否恶化？（转化率升但错误率/性能降 → 不可上线）
```

### 3.3 前端 SLO 看板与错误预算告警

```typescript
// ========== 错误预算计算（前端侧自检，也可在数据侧实现）==========

interface SloConfig { name: string; slo: number; windowDays: number }

interface BudgetState {
  consumed: number;   // 已消耗比例（0-1）
  burnRate: number;   // 燃尽率
  status: 'healthy' | 'warning' | 'frozen';
}

function computeBudget(
  config: SloConfig,
  goodCount: number,
  totalCount: number,
  windowFraction = 1 // 已过去的时间占统计窗口的比例
): BudgetState {
  const totalBudget = 1 - config.slo;                 // 允许的错误率
  const actualErrorRate = 1 - goodCount / totalCount; // 实际错误率
  // 已消耗预算 = 实际错误率 / 允许错误率 × 已过去时间占比
  const consumed = Math.min(1, (actualErrorRate / totalBudget) * windowFraction);
  return {
    consumed,
    burnRate: actualErrorRate / totalBudget,
    status: consumed >= 1 ? 'frozen' : consumed >= 0.5 ? 'warning' : 'healthy',
  };
}

// 可用性 SLO 99.9%，窗口 30 天，已过去 15 天
const state = computeBudget({ name: 'availability', slo: 0.999, windowDays: 30 }, 998_500, 1_000_000, 0.5);
// 实际错误率 0.15%，允许 0.1% → 燃尽率 1.5，已消耗 75% → warning
// 结论：剩余预算不足以支撑正常发布节奏，需谨慎发布并优先修复错误
```

| 看板面板 | 指标 | 作用 |
|---|---|---|
| 错误预算剩余 | `1 - consumed`，按日/周趋势 | 一眼看出能否发布 |
| 燃尽率 | 1h / 6h / 3d 三个窗口 | 区分快速燃烧与慢速消耗 |
| 可用性趋势 | 按会话的错误率，按 app_version 拆分 | 定位哪个版本引入的问题 |
| 性能达标率 | P75 LCP / INP / CLS 达标率 | 与错误预算并列的第二条 SLI |
| 关键路径成功率 | 登录 / 下单 / 支付的端到端成功率 | 业务视角的护栏指标 |

## 四、常见面试题

### 面试题 1：A/B 实验的分流是怎么实现的？如何保证稳定性？

**答案要点**：

分流本质是稳定的哈希映射：`bucket = hash(unit + salt) % BUCKET_TOTAL`，再按桶号区间决定变体。三个关键点：

1. **纯函数哈希**：用 MurmurHash3 / FNV-1a 等非加密哈希，输入只有稳定的分流单元（`userId` 或持久化的 `anonymousId`）与实验 `salt`，绝不用随机数或时间戳。
2. **固定桶总数**：通常取 10000，放量通过调整权重区间实现，避免桶总数变化导致全量重分桶。
3. **决策缓存**：会话内缓存 `getVariant` 结果，配置刷新也不会让用户中途切换变体。

稳定性失效的常见原因：未登录用户没有持久化匿名 ID、实验运行中修改 `salt`、用 `Math.random()` 分流、前后端分流算法不一致。

### 面试题 2：什么是分层正交？为什么需要它？

**答案要点**：

分层正交解决"多个实验如何共享同一批流量"。两条规则：**层内互斥**（同层实验共享流量池，一个用户在同层最多命中一个实验，用于隔离互相影响的实验）；**层间正交**（不同层用不同 `salt`，分桶独立，用户可同时进入多个层的实验，正交性可用卡方检验验证，p > 0.05 表示独立）。

价值：10% 流量跑一个实验会浪费 90% 流量；分层正交让多个实验并行运行在同一批用户上，大幅提升实验吞吐量，同时避免实验间互相污染。

### 面试题 3：实验数据为什么会出现样本比例失调（SRM）？怎么排查？

**答案要点**：

SRM 指实际观测到的分组比例与配置比例显著不符（卡方检验 p < 0.001）。常见原因与排查方向：

1. **分流不一致**：前后端分流算法 / `salt` / 桶总数不一致，边界用户被分到不同组。
2. **埋点丢失不对称**：某个变体的曝光上报被条件分支跳过（如实验组多一个弹窗拦截了渲染）。
3. **缓存问题**：配置缓存过期时间不同，部分用户用旧配置分流。
4. **实验互斥配置错误**：同层实验流量重叠，部分用户被"抢走"。
5. **定向条件过窄**：`targeting` 命中率在两组间不一致。
6. **机器人/爬虫流量**：不执行 JS 的流量不计入，且分布不均。

处理原则：**发现 SRM 应停止实验、修复后重跑**，而不是"凑合看数据"——SRM 意味着分流机制本身有 bug，结论不可信。

### 面试题 4：页面关闭时如何保证埋点数据不丢？

**答案要点**：

三层保障：

1. **选对时机**：`visibilitychange` → `hidden` 作为主上报时机，`pagehide` 兜底。不用 `unload`（移动端经常不触发，且注册 unload 监听器会让页面无法进入 bfcache）、不用 `beforeunload`（只适合做离开确认）。
2. **选对方式**：卸载场景用 `navigator.sendBeacon`（异步、不阻塞卸载、浏览器保证排队发送）；需要自定义 header 或读响应时用 `fetch` + `keepalive: true`（注意单页 keepalive 总量约 64KB）。`sendBeacon` 返回 `false` 说明队列超限，必须降级落盘。
3. **离线兜底**：失败时写入 IndexedDB 队列，在下次启动、`online` 事件、定时器触发时补发；重试用指数退避 + 上限；去重靠客户端 `event_id` + 服务端幂等。

补充：`hidden` 状态可能只是切后台而非卸载，因此"不可见就上报"比"卸载才上报"覆盖更全、更早。

### 面试题 5：什么是 SLO 和错误预算？前端如何设定？

**答案要点**：

- **SLI** 是可测量的指标（如"无致命错误的会话数 / 总会话数"）；**SLO** 是内部目标（如月度 ≥ 99.9%）；**SLA** 是对外合同承诺（如 ≥ 99.5%，违约赔付）。SLA 通常比 SLO 宽松。
- **错误预算 = 1 - SLO**，99.9% 对应每月约 43.2 分钟不可用。它把"能否发布"变成客观决策：预算充足正常发布，消耗过半谨慎发布，耗尽则冻结功能发布、只允许修复性发布。
- **燃尽率**衡量消耗速度，配合"多窗口多燃尽率"告警（1h/5m 燃尽率 14.4 → P0；6h/30m 燃尽率 6 → P1；3d/6h 燃尽率 1 → P2），兼顾灵敏度与降噪。
- **前端 SLO 设定**：选可用性、加载性能达标率（P75 LCP < 2.5s 的会话占比）、接口错误率、白屏率；按会话而非请求聚合，用分位数而非均值，且指标必须可行动。

### 面试题 6：Feature Flags 和 A/B 实验是什么关系？

**答案要点**：

Feature Flags 是"能力"，A/B 实验是"方法论"。Feature Flags 提供按规则开关功能的通用机制，四类模型分别是 Release（发布解耦）、Experiment（实验）、Ops（运维开关）、Permission（权限）。A/B 实验是 Experiment 型 Flag 的一种用法，但完整实验平台还需要额外能力：分流单元管理、层/域与互斥关系、曝光与指标口径、统计显著性计算、实验生命周期管理（启停、归档、结论沉淀）。

因此实践中的关系是：**实验平台的开关能力可以复用 Feature Flags 基础设施，但实验平台必须自带分流引擎与指标分析能力**，否则无法回答"哪个方案更好"。

## 五、避坑指南

| 常见错误 | 产生原因 | 正确做法 |
|---|---|---|
| 实验结论不可信，指标差异巨大但无法解释 | 分流不稳定（随机数 / 未持久化匿名 ID）、运行中改配置、SRM 未检测 | 纯函数哈希 + 固定桶总数 + 决策缓存；上线前做 SRM 检验（卡方检验 p < 0.001 即停止实验） |
| 曝光量远大于实际用户数，转化率被稀释 | 在 SDK 初始化或 `getVariant` 调用时上报曝光，而非变体真正渲染后 | 曝光放在渲染提交后（React `useEffect`）；会话内去重；首屏外实验位配合 IntersectionObserver |
| 页面关闭后数据大量丢失 | 用 `unload` + 普通 `fetch` 上报；或忽略 `sendBeacon` 返回值 | `visibilitychange(hidden)` + `pagehide`；`sendBeacon` / `fetch keepalive`；失败落 IndexedDB 补发 |
| 补发后数据重复，指标虚高 | 客户端重试 + 多触发源并发补发，服务端未做幂等 | 客户端 `event_id`（UUID）+ 补发并发保护；服务端按 `event_id` 唯一索引幂等写入 |
| 离线队列无限增长，页面卡顿甚至崩溃 | 队列无条数/字节上限，`localStorage` 同步写入大 JSON | 用 IndexedDB；条数上限（如 500）+ 过期时间（如 7 天）；超限丢最旧并上报丢弃计数 |
| 漏斗数据断裂，转化率算出来大于 100% | 对曝光与转化做独立的随机采样 | 改一致性采样（按 `unit` 哈希），同一用户全采或全不采；关键事件全量 |
| 告警风暴导致值班麻木，真正的 P0 被淹没 | 单窗口阈值告警、无聚合/抑制/冷却、按错误次数而非影响面 | 多窗口多燃尽率告警；聚合相同 fingerprint、抑制下游告警、设置冷却；按影响用户数设阈值 |
| SLO 定得过高导致团队无法发布 | 盲目追求"四个 9"，错误预算接近 0 | SLO 必须"可达且值得追求"；预算耗尽时冻结功能发布但保留修复性发布通道；定期评审调整 |
| 实验上线后才发现主要指标未定义，事后挑指标 | 缺少实验设计与评审流程 | 启动前明确 OEC（唯一主要指标）+ 护栏指标 + 最小样本量；多指标做 Bonferroni / FDR 校正 |
