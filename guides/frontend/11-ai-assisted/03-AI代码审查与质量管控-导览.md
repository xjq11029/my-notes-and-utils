## 核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | AI 代码审查是利用 AI 工具对代码进行自动化质量检查的方法体系。随着 AI 生成代码比例超过 50%，代码审查的焦点已从"检查语法错误"转向"拦截 AI 幻觉代码"。与传统代码审查相比，AI 审查能自动检测竞态条件、不存在的 API、过时模式等 AI 代码特有的深层次问题，而传统 ESLint 规则只能捕获表层问题。 |
| 能做什么 | 自动检测四类 AI 代码核心缺陷（占 AI 代码缺陷的 80%+）：胡编 API（不存在的属性名、错误的方法签名、虚构的配置项）、过时语法（Vue 2 语法混入 Vue 3 项目）、缺失错误处理（AI 默认生成"快乐路径"代码）、竞态条件遗漏（异步操作几乎总是缺少取消和清理）。同时支持安全漏洞扫描、性能回归检测、可访问性检查。 |
| 怎么用 | 建立"三层防线"审查体系：第一层 - 自动化检查（TypeScript 类型检查 + ESLint 规则 + 单元测试，每次提交自动执行）；第二层 - AI 辅助审查（竞态条件检测 + 安全漏洞扫描 + 性能回归检测，每次 PR 执行）；第三层 - 人工审查（架构合理性 + 业务逻辑正确性 + 代码可维护性，每次 PR 执行）。三层逐级递进，各司其职。 |
| 原理和工作流程 | AI 代码审查基于两个核心原理：AST 静态分析（将源码解析为抽象语法树，遍历节点匹配问题模式，在代码运行前发现问题）和 AI 语义理解（通过 Prompt 指定审查维度和检查清单，AI 基于语义理解发现静态规则难以覆盖的深层次问题）。两者结合形成完整的审查防线。 |
| 缺点 | 与传统审查的区别：AI 审查速度快但无法替代人工判断（架构合理性、业务逻辑正确性仍需人工）；AST 静态分析无法检测运行时行为；AI 审查可能产生误报需要人工确认；审查规则需要持续维护和更新；AI 审查无法感知团队特定的业务规范和历史约定。 |

## 竞态条件系统化检测

| 维度 | 内容 |
|------|------|
| 是什么 | 将 AI 生成代码中最常见的竞态条件分为四类（请求竞态、状态更新竞态、定时器竞态、事件处理竞态），并提供系统化检测清单和解决方案。 |
| 能做什么 | 请求竞态：AbortController 取消旧请求、请求序列化（队列）、版本号机制；状态更新竞态：useEffect cleanup / ignore 标记、Vue watchEffect onCleanup；定时器竞态：组件卸载时清理；事件处理竞态：防重复提交。 |
| 怎么用 | 使用竞态条件检测清单逐项检查 AI 生成的代码：异步请求是否有取消、useEffect 是否有 cleanup、定时器是否清理、表单提交是否有防重复。 |
| 原理和工作流程 | 竞态条件本质是"异步操作到达顺序不确定 + 状态更新基于过期值"——通过取消旧操作、版本号标记、cleanup 清理来保证顺序和一致性。 |
| 缺点 | AbortController 在某些旧浏览器中不支持（需 polyfill）；请求队列可能降低吞吐量；版本号方案需要额外维护计数器。 |

## AST 自动拦截 AI 幻觉代码

| 维度 | 内容 |
|------|------|
| 是什么 | 通过编写自定义 ESLint 规则，在 AST 层面自动检测 AI 生成的幻觉代码（不存在的 API、未处理的 Promise、过时的导入路径）。 |
| 能做什么 | 拦截不存在的 API 调用（CallExpression 检测）；拦截未处理的 Promise（no-floating-promises）；拦截过时的导入路径（ImportDeclaration 检测）；拦截危险代码模式（eval、new Function、debugger）。 |
| 怎么用 | 编写自定义 ESLint 插件 → 配置 blockedPatterns 黑名单 → 集成到 CI 流水线 → 提交时自动拦截。 |
| 原理和工作流程 | ESLint 将源码解析为 AST → 遍历 AST 节点 → 自定义规则匹配黑名单模式 → 报告错误。AST 是静态分析，可以在代码运行前发现问题。 |
| 缺点 | AST 静态分析无法检测运行时行为；规则维护需要持续更新黑名单；误报需要定期调整白名单。 |

## getter 防调试方案识别与重构

| 维度 | 内容 |
|------|------|
| 是什么 | 识别 AI 可能生成的三种防调试模式（无限 debugger 循环、Object.defineProperty DevTools 检测、console.log 劫持），并提供安全的重构方案。 |
| 能做什么 | 识别无限 debugger → 移除并用 ESLint no-debugger 拦截；识别 getter 陷阱 → 替换为安全的 Proxy 日志代理；识别 console 劫持 → 替换为统一的日志库（winston/pino）。 |
| 怎么用 | 使用防调试代码检查清单逐项排查：搜索 debugger 关键字、审查 Object.defineProperty 的 getter 函数体、审查 console. 赋值语句。 |
| 原理和工作流程 | 防调试代码通过劫持调试接口阻止正常开发工作——识别后移除陷阱逻辑，替换为不影响调试的安全替代方案（Proxy 日志代理、结构化日志库）。 |
| 缺点 | 人工审查工作量大；部分防调试代码可能伪装成正常业务逻辑；需要审查者具备一定的安全知识。 |

## AI 代码审查工作流

| 维度 | 内容 |
|------|------|
| 是什么 | 三级审查模型（自动化检查 → AI 辅助审查 → 人工复核）是 AI 代码审查的核心工作流。阶段一（自动化检查）由机器在每次提交时自动执行，覆盖类型检查、ESLint 规则、单元测试和构建验证；阶段二（AI 辅助审查）由 AI 在每次 PR 时执行，覆盖竞态条件检测、安全漏洞扫描、性能回归检测和审查报告生成；阶段三（人工复核）由开发者在每次 PR 时执行，覆盖架构合理性、业务逻辑正确性、代码可维护性和 AI 审查结果确认。 |
| 能做什么 | 阶段一拦截表层问题（类型错误、语法违规、测试失败），零人工成本；阶段二发现深层次问题（竞态条件、AI 幻觉 API、安全漏洞、内存泄漏、错误处理缺失、可访问性），按严重程度输出结构化报告；阶段三把关 AI 无法替代的决策（架构设计是否合理、业务逻辑是否正确、代码是否易于维护），确认 AI 审查结果是否准确。 |
| 怎么用 | 在 CI/CD 流水线中集成三级审查：阶段一配置 TypeScript strict 模式 + ESLint 自定义规则（含 AI 幻觉检测规则）+ Vitest 测试；阶段二使用 Claude Code 或 Copilot 的审查功能，配合标准化 Prompt 模板（指定六维检查：竞态条件、AI 幻觉 API、安全漏洞、内存泄漏、错误处理、可访问性）；阶段三通过 PR 评论和人工阅读代码完成，以 AI 审查报告为参考。 |
| 原理和工作流程 | 三级审查模型遵循"机器替代重复劳动，人工聚焦高价值决策"的原则。阶段一通过静态分析在代码运行前发现问题（零成本）；阶段二通过 AI 语义理解发现静态规则难以覆盖的问题（低成本）；阶段三通过人工经验判断 AI 无法替代的决策（高成本但高价值）。逐级递进减少人工审查负担。 |
| 缺点 | 三级审查增加了 CI/CD 流程的复杂度（需要维护多套配置）；AI 审查报告可能过于冗长（需限制输出格式，只报告严重和高优先级问题）；AI 审查结果可能产生误报（需要人工逐条确认，增加审查负担）；阶段三的人工审查仍然不可替代，AI 只能加速信息收集和分析，不能替代最终决策。 |

## 常见问题与避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | AI 代码审查中常见的五类问题：审查规则过于宽松（遗漏关键缺陷导致线上事故）、审查规则过于严格（误报过多导致开发者忽略审查报告）、误报处理不当（AI 标记的问题实际上不是问题，但开发者盲目信任而浪费修复时间）、审查覆盖度不足（只检查了语法和类型，遗漏了竞态条件和安全漏洞）、AI 审查报告过于冗长（信息过载导致开发者不愿阅读）。 |
| 能做什么 | 逐项解决：规则过松 → 持续迭代 ESLint 自定义规则和 AI 审查 Prompt，补充发现的新问题模式；规则过严 → 在 ESLint 规则中添加 `allowedAPIs` 白名单，在 AI Prompt 中调整严重程度阈值；误报处理 → 建立误报反馈机制，定期调整白名单和规则配置；覆盖度不足 → 使用六维审查清单（竞态条件、幻觉 API、安全、内存、错误处理、可访问性）；报告冗长 → 限制输出为"只报告严重和高优先级问题"。 |
| 怎么用 | 在项目中建立审查规则迭代流程：每周回顾 AI 审查的误报率 → 更新白名单/黑名单 → 每月回顾漏报的线上问题 → 补充新的检测规则 → 每季度审查整体审查效果 → 调整审查策略。同时结合 CI/CD 集成，将 AI 审查结果自动作为 PR 评论，降低人工审查的认知负担。 |
| 原理和工作流程 | AI 审查问题的根因有三：规则库不完整（黑名单/白名单未覆盖所有场景）→ 需要持续迭代；AI 模型理解偏差（对业务特定逻辑不了解）→ 需要人工复核；静态分析局限（无法检测运行时行为）→ 需要结合单元测试和 E2E 测试。解决方案是"规则迭代 + 人工复核 + 测试覆盖"三位一体。 |
| 缺点 | 审查规则迭代需要持续投入精力（不是一次性配置）；误报的调整过程可能引入新的漏报风险；AI 审查无法完全替代人工，最终决策仍需开发者判断；不同项目的审查需求差异大，无法直接复用其他项目的审查配置。 |
