### 1. Cursor 四种核心功能的描述

| 维度 | 内容 |
|------|------|
| 是什么 | Cursor 的四种核心功能构成从行级到项目级的完整能力层级：Tab 补全（行级/多行）、Cmd+K（精准修改选中区域）、Composer（多文件生成）、Agent（自主规划多步骤任务）。 |
| 能做什么 | Tab 补全支持多行同时补全，能感知上下文；Cmd+K 可对选中代码块执行自然语言指令修改；Composer 可一次性创建整个功能模块；Agent 需人工监控。 |
| 怎么用 | Tab 接受补全建议；Cmd+K 选中代码后输入指令；Cmd+I 打开 Composer；Composer 内切换 Agent 模式。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | Agent 模式需要人工监控，不可完全放任。 |

### 2. GitHub Copilot 独有优势

| 维度 | 内容 |
|------|------|
| 是什么 | Copilot 是 IDE 插件形式，独有优势包括：GitHub 生态深度集成（PR 审查、Issue 分类）、支持多种 IDE、企业级代码隐私保护。Copilot 没有独立的 CLI 模式。 |
| 能做什么 | PR 代码审查、Issue 自动分类、Workspace 代理跨文件修改。 |
| 怎么用 | 安装 VS Code / JetBrains 插件，使用 Copilot Chat 进行对话。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | 无独立 CLI 模式，Claude Code 在 CLI 原生场景中更占优势。 |

### 3. Claude Code 与 Cursor 的核心差异

| 维度 | 内容 |
|------|------|
| 是什么 | Claude Code 是 CLI 原生工具，启动时自动扫描项目文件建立全局上下文；Cursor 是 IDE 工具，需要手动 @ 引用文件。Claude Code 在 10+ 文件的大型重构中更稳定，Cursor 在日常编码中体验更流畅。 |
| 能做什么 | Claude Code 适合架构级重构、需要频繁测试验证的复杂任务；Cursor 适合日常编码、快速原型、需要边改边看 UI 效果的场景。 |
| 怎么用 | Claude Code 在终端中运行；Cursor 作为 IDE 使用。两者推荐组合使用。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | Claude Code 无实时 Tab 补全；Cursor 在超大型重构中多文件一致性不如 Claude Code。 |

### 4. Prompt 工程五要素

| 维度 | 内容 |
|------|------|
| 是什么 | 五要素包括：角色设定（AI 的专业身份）、任务描述（要完成的具体任务）、上下文信息（项目技术栈/文件路径）、输出格式（约束输出结构）、约束条件（技术选型/编码规范/边界条件）。"代码优化建议"不属于五要素。 |
| 能做什么 | 五要素齐全的 Prompt 可以让 AI 输出与需求高度匹配、格式规范、可直接使用的高质量代码。 |
| 怎么用 | 按五要素模板依次填写：角色设定 → 任务描述 → 上下文信息 → 输出格式 → 约束条件。 |
| 原理和工作流程 | 每个要素对应 AI 输出质量的一个维度，缺一不可。 |
| 缺点 | 五要素齐全的 Prompt 较长，编写成本较高。 |

### 5. AI 幻觉（Hallucination）的表现

| 维度 | 内容 |
|------|------|
| 是什么 | AI 幻觉是"可能"而非"一定"——AI 生成的代码不一定都存在运行时错误，但存在幻觉风险。四种典型表现：虚构 API、过时语法、虚构导入路径、逻辑错误。 |
| 能做什么 | 识别 AI 幻觉代码，建立多层防范防线。 |
| 怎么用 | Prompt 层约束 API 范围 + ESLint 规则拦截 + 自定义 AST 规则 + TypeScript 类型检查。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | 幻觉无法完全消除，必须配合自动化检查和人工审查。 |

### 6. Few-shot 示例的作用

| 维度 | 内容 |
|------|------|
| 是什么 | Few-shot 通过提供 1-3 个"输入-输出"示例，让 AI 模仿示例的格式、风格和质量标准，可将输出准确率提升 50% 以上。 |
| 能做什么 | 格式校准（明确输出格式）、风格对齐（代码风格统一）、质量基准（示例质量决定输出质量）。 |
| 怎么用 | 提供 1-3 个与任务同领域但不同内容的完整示例，覆盖边界情况。 |
| 原理和工作流程 | AI 通过示例学习期望的输出模式，模仿而非创新。 |
| 缺点 | 示例与任务过于相似会导致 AI 直接复制内容；超过 3 个示例收益递减。 |

### 7. AI 代码审查三级模型

| 维度 | 内容 |
|------|------|
| 是什么 | 三级模型：第一级自动化检查（TypeScript/ESLint/测试/构建，机器执行），第二级 AI 辅助审查（竞态条件/AI 幻觉/安全漏洞/内存泄漏，AI 执行），第三级人工审查（架构合理性/业务逻辑/可维护性，开发者执行）。 |
| 能做什么 | 分层拦截不同性质的问题，让机器做确定性检查，让人做架构判断和业务理解。 |
| 怎么用 | 第一级 CI 自动执行，任何失败阻止合入；第二级 PR 时自动审查，结果作为参考；第三级每次 PR 必须执行。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | 三级模型需要合理配置 CI 流水线，初期搭建成本较高。 |

### 8. 竞态条件检测与防范

| 维度 | 内容 |
|------|------|
| 是什么 | 竞态条件是 AI 生成代码中最常见的深层次缺陷。`Promise.all` 只是并发执行请求，并不解决竞态问题——返回顺序不确定时仍可能出现旧数据覆盖新数据。 |
| 能做什么 | 识别请求竞态、状态更新竞态、定时器竞态、事件处理竞态四类问题。 |
| 怎么用 | AbortController 取消旧请求、请求版本号机制、ignore 标记/cleanup 函数、防重复提交 loading 锁。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | 竞态条件检测需要深入理解异步执行模型，自动化检测难以覆盖所有场景。 |

### 9. AST 拦截 AI 幻觉代码

| 维度 | 内容 |
|------|------|
| 是什么 | 通过自定义 ESLint 规则，在 AST 层面检测 `CallExpression`（不存在的 API 调用）和 `ImportDeclaration`（虚构的导入路径）节点，自动拦截 AI 幻觉代码。 |
| 能做什么 | 在编译阶段自动拦截 AI 幻觉产生的虚假 API 调用、过时语法和虚构导入路径。 |
| 怎么用 | 编写 ESLint 插件，维护黑名单 API 列表和黑名单正则模式，配置白名单避免误报，集成到 CI 流水线。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | AST 是静态分析，不能检测运行时行为；黑名单需要持续维护更新。 |

### 10. 上下文管理策略

| 维度 | 内容 |
|------|------|
| 是什么 | 上下文不是越长越好——信息密度过高会导致 AI 抓不住重点。正确策略包括：规则文件持久化、精确引用、渐进式上下文、定期重置、上下文预算管理。 |
| 能做什么 | 在有限的上下文窗口内最大化 AI 输出质量，避免上下文溢出导致的生成质量下降。 |
| 怎么用 | 配置 `.cursorrules`/`CLAUDE.md` 持久化规范；使用 `@file` 精确引用；对话超过 20 轮开启新对话；采用"先概要后细节"的渐进策略。 |
| 原理和工作流程 | 详见原文。 |
| 缺点 | 上下文管理需要刻意练习，新手容易一次性提供过多信息导致 AI 抓不住重点。 |
