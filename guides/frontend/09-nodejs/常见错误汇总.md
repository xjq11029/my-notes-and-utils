# Node.js - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 在 for 循环中使用 require | require 有缓存机制，首次加载后缓存，循环中重复调用无实际效果 | 将 require 放在文件顶部，不要放在循环或函数内 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 混淆 process.nextTick 和 setImmediate 导致回调顺序异常 | 两者执行阶段不同：nextTick 在本阶段结束时执行，setImmediate 在 check 阶段执行 | 记住：nextTick 更早、优先级更高；setImmediate 在 poll 阶段之后 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 大文件使用 fs.readFile 导致内存溢出 | readFile 一次性将文件全部读入内存 | 使用 fs.createReadStream 配合 pipe 流式处理大文件 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| Buffer.allocUnsafe 未覆盖数据导致敏感信息泄露 | allocUnsafe 不初始化内存，原内存可能包含密码、密钥等 | 优先使用 Buffer.alloc；若用 allocUnsafe，确保立即覆盖全部数据 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 在 package.json 混用 CommonJS 和 ESM 导致模块加载失败 | "type": "module" 下 .js 文件被当作 ESM，不支持 require | 明确使用 .mjs（ESM）和 .cjs（CommonJS）扩展名 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 未处理流 error 事件导致进程崩溃 | 流默认会在 error 事件无监听器时抛出异常 | 始终为流绑定 error 事件监听器 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 在 poll 阶段递归调用 process.nextTick 导致事件循环饥饿 | nextTick 在当前阶段结束时执行，递归调用会无限循环 | 避免在 nextTick 中递归调用 nextTick；改用 setImmediate | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 线程池被 CPU 密集型任务占满导致 I/O 响应变慢 | 线程池默认只有 4 个线程，CPU 密集型任务会阻塞线程池 | 将 CPU 密集型任务交由 Worker Threads 处理，或增大 UV_THREADPOOL_SIZE | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 中间件不调用 next() 也不结束响应导致请求挂起 | 中间件链条中断，响应永远不会被发送 | 检查每个中间件是否正确调用 next() 或 res.send() | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| 在 Koa 中混用回调风格的中间件导致洋葱模型断裂 | Koa 中间件必须返回 Promise，回调风格无法被 await | 将回调风格中间件包装为 Promise，或使用 util.promisify | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| 生产环境使用内存存储 Session 导致服务重启后用户全部重新登录 | 内存存储不持久化，且多进程间不共享 | 使用 connect-redis 等持久化存储 | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| JWT Secret 硬编码在代码中导致密钥泄露 | 密钥暴露在代码仓库中，Token 可被伪造 | 使用环境变量或配置中心管理密钥 | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| 忘记设置 Cookie 的 httpOnly 属性导致 XSS 可窃取 Cookie | JavaScript 可通过 document.cookie 读取 Cookie | 始终设置 httpOnly: true | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| BFF 层串行请求多个微服务导致接口响应慢 | 串行请求累加延迟，延长了总体响应时间 | 使用 Promise.all 并行请求，无依赖关系的接口必须并行 | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| ctx.body 在 await next() 之后赋值导致不生效 | 响应已发送，HTTP 连接可能已关闭，后续修改无效 | 响应体数据在 await next() 之前准备好，或在 next() 之后利用流式响应 | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| 未设置 SameSite 属性导致 CSRF 攻击风险 | 跨站请求默认携带 Cookie | 设置 sameSite: 'strict' 或 sameSite: 'lax' | [Web框架与BFF层导览](./02-Web框架与BFF层-导览.md) |
| 在 Koa 中间件中忘记 await next() 导致后续中间件不执行 | 不加 await，next() 返回的 Promise 未被等待，洋葱模型断裂 | 始终使用 await next() 等待下游中间件 | [Node.js笔面试题集导览](./03-Node.js笔面试题集-导览.md) |
| 未处理 unhandledRejection 导致进程崩溃 | 未被 .catch() 处理的 Promise rejection 会触发 unhandledRejection 事件 | 始终为 Promise 添加 .catch() 或使用全局 unhandledRejection 处理器 | [Node.js笔面试题集导览](./03-Node.js笔面试题集-导览.md) |
| 忽略 body-parser 中间件的注册顺序导致 req.body 为 undefined | 请求体解析中间件必须在路由之前注册 | 确保 app.use(express.json()) 在路由定义之前 | [Node.js笔面试题集导览](./03-Node.js笔面试题集-导览.md) |
| 把 CPU 密集计算写成 `async` 就以为不阻塞，接口依然超时 | `async` 只改变写法，不改变执行线程，`await` 之前的同步计算仍占用主线程 | 用 `worker_threads` 真正把计算卸载到别的线程 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 为每个请求创建 Worker，响应变慢、内存暴涨 | 每个 Worker 都要初始化新的 V8 Isolate | 使用 Worker 池并复用线程 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| `postMessage` 传大对象导致主线程卡顿、内存翻倍 | 结构化克隆做深拷贝，开销随数据量线性增长 | 用 Transferable 转移所有权，或使用 `SharedArrayBuffer` | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 在 `SharedArrayBuffer` 上做普通读写，计数结果偏小、数据错乱 | 普通读写不是原子的，存在竞态 | 使用 `Atomics.add` / `Atomics.load` 等原子操作 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| Worker 内未捕获异常导致整个进程退出 | Worker 的未捕获异常触发 `error` 事件，未监听会拖垮进程 | Worker 内 `try/catch` 并回传错误，同时在主线程监听 `error` 事件 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 把 I/O 任务放进 Worker 后性能反而变差 | I/O 已由事件循环与 libuv 处理，放进 Worker 只增加通信开销 | I/O 用异步 API，Worker 只放 CPU 密集的纯 JS 计算 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 运行时修改 `UV_THREADPOOL_SIZE` 配置不生效 | 该环境变量在进程启动时读取，运行时修改无效 | 在启动命令前设置，如 `UV_THREADPOOL_SIZE=8 node app.js` | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| Worker 池容量按 CPU 核数满配后主线程被挤占 | 主线程也需要 CPU 时间 | 池大小设为 CPU 核数 - 1 或更小 | [Node运行时与核心API导览](./01-Node运行时与核心API-导览.md) |
| 请求频繁超时，数据库连接耗尽 | 未使用连接池或连接池过小，每次请求创建新连接开销巨大 | 配置合理连接池大小（`核心数*2+磁盘数`），并在启动时预热连接池 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 接口响应极慢，数据库 CPU 飙升（N+1 问题） | 循环中逐条查询导致 N+1 次数据库请求 | 用 ORM 的 `include`/`relations` 预加载关联数据，或 `findMany` 批量查询后代码组装 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 查询效率低、网络传输量大 | 使用 `SELECT *` 返回了不需要的字段，浪费 I/O 和内存 | 用 `select`（Prisma）/ `select` 列（TypeORM）/ `attributes`（Sequelize）只查需要的字段 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 查询从毫秒级变为秒级，出现全表扫描 | 忘记为查询条件列建索引 | 用 `EXPLAIN` 分析慢查询，为 WHERE/JOIN/ORDER BY 涉及的列创建索引 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| Emoji 等 4 字节字符插入失败或乱码 | MySQL 使用了 `utf8`（阉割版，最多 3 字节） | 始终使用 `utf8mb4` 字符集和 `utf8mb4_unicode_ci` 排序规则 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| Redis 缓存返回旧数据，与数据库不一致 | 更新数据库后未及时清除缓存，或缓存与数据库更新非原子 | 采用 Cache-Aside 模式（先更新数据库，再删除缓存），设置合理过期时间兜底 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 数据库连接卡死，其他请求排队等待 | 事务长时间未提交导致锁持有、连接不释放 | 为事务设置超时时间；避免在事务中执行外部 API 调用等耗时操作 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 生产数据库被意外重置或修改 | 生产环境使用了 `prisma migrate dev`，它会触发开发环境特有行为 | 生产环境使用 `prisma migrate deploy`，CI/CD 中集成迁移检查 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| MongoDB 聚合管道执行极慢 | 聚合管道中的 `$match`、`$sort` 缺少索引支持 | 为 `$match` 和 `$sort` 涉及的字段创建索引，用 `explain` 分析聚合管道 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 大表 `ALTER TABLE` 加字段时表被锁住，所有写入阻塞 | 旧版本 MySQL 的 `ALTER TABLE` 会锁表，大表可能执行数小时 | 使用 `pt-online-schema-change` 在线修改，或使用支持在线 DDL 的数据库版本 | [数据库与ORM导览](./04-数据库与ORM-导览.md) |
| 凭直觉优化后性能没变化甚至变差 | 没有 profiling 数据，改的不是真正的瓶颈 | 先用 `--cpu-prof` / `0x` 采样，按自耗时排序定位热点再动手 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| `heapUsed` 稳定但进程仍被 OOM 杀掉 | `Buffer` 的内存计入 `external` / `arrayBuffers`，不计入 `heapUsed` | 同时监控 `rss` / `heapUsed` / `external` / `arrayBuffers` 四个指标 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 误判正常缓存为内存泄漏 | 单张 Heap Snapshot 无法区分"应有的对象"与"泄漏的对象" | 用三快照法，重复同一操作观察增量是否线性增长 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 进程被 OOM Killer 静默杀掉，没有 JS 堆栈 | 只设了容器内存 limit，未设堆上限；V8 堆未达上限但 `rss` 超过 limit | 显式设置 `--max-old-space-size` 为容器上限的 70%-80% | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 生产环境暴露 `--inspect` 到公网 | 调试端口暴露了完整的代码执行能力 | 只在排查时开启，通过内网跳板机或 SSH 隧道访问 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 压测前几秒数据严重偏低，结论失真 | JIT 尚未达到稳定优化状态，没有预热 | 加 `-w` 预热参数，丢弃预热阶段数据 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 压测结果波动大且偏低 | 压测进程与被测进程抢 CPU 与网络 | 压测机独立部署，或用 cgroup 限制压测进程资源 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 平均延迟正常但用户抱怨卡顿 | 平均值掩盖了长尾 | 关注 P95 / P99，以及非 2xx 响应数与错误率 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| Serverless 中数据库连接数被打爆，大量连接被拒绝 | 总连接数 = 实例数 × 单实例池大小，实例数弹性放大 | 池大小设为 1，或用 PgBouncer / RDS Proxy 做外部连接池 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| Serverless 冷启动 P95 高达数秒 | 在 handler 内初始化重依赖，依赖加载与连接建立全部进入冷启动关键路径 | 客户端初始化提到模块作用域，重初始化改为懒加载 + 动态 `import()` | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 多实例下登录状态随机失效 | 用进程内变量存会话，Serverless 实例不固定且会回收 | 会话外置到 Redis / 数据库 / JWT，实例内只做可失效的缓存 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| 进程收到 `SIGTERM` 后不退出 | 定时器未 `unref()` 也未清理，活跃 handle 让事件循环无法清空 | 后台定时器加 `.unref()`，请求级定时器在生命周期结束时清理 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
| Lambda 中调用一直卡到超时 | keep-alive 连接让 Node.js 运行时一直等待事件循环清空 | 设置 `context.callbackWaitsForEmptyEventLoop = false`，或正确管理连接生命周期 | [Node性能调优与内存排查导览](./05-Node性能调优与内存排查-导览.md) |
