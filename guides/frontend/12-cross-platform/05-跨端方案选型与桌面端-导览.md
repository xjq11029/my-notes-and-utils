# 05-跨端方案选型与桌面端 - 导览

---

## 1.1 跨端方案的四大分类（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 按"谁来绘制像素"这一最本质维度，把主流跨端方案分为四类：WebView 容器类（uniapp、Cordova、Capacitor）、编译时转换类（Taro、uniapp 小程序端、Weex）、原生渲染类（React Native、Flutter）、桌面端类（Electron、Tauri） |
| 能做什么 | 帮助开发者建立统一的技术坐标系，避免把"编译时方案"和"运行时方案"混为一谈，从而在选型时快速缩小候选范围 |
| 怎么用 | 判断三个问题：谁负责绘制像素？跨端发生在编译期还是运行期？UI 与业务逻辑的边界在哪里？按答案对号入座 |
| 原理和工作流程 | WebView 容器类在运行期把 Web 页面装进系统 WebView；编译时转换类在构建阶段把一套源码翻译成各端代码；原生渲染类不依赖 WebView，RN 把 JS 组件映射为原生组件、Flutter 用自绘引擎直接绘制；桌面端类用 Web 技术栈开发桌面应用，差别在渲染引擎来自内置还是系统 |
| 缺点 | 分类之间并非互斥，真实框架常是混合体（如 uniapp 在 App 端同时用 WebView 与原生渲染），分类只是认知工具而非严格定义 |

## 1.2 主流跨端方案对比矩阵（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 对 uniapp、Taro、React Native、Flutter、Electron、Tauri 六个主流方案，从技术栈、渲染方式、性能、包体积、生态成熟度、学习成本、适用场景七个维度做横向对比 |
| 能做什么 | 让选型从"感觉哪个好"变成"按维度打分"；对 Java 后端转全栈的学习者，能清晰看出哪些方案可复用 Vue/React 技能、哪些需要新增 Dart 或 Rust 能力 |
| 怎么用 | 先按目标平台筛掉不适用的方案，再在剩下的方案里对比包体积与学习成本；"性能"一列看的是能否稳定跑满 60fps 复杂交互，"包体积"一列看的是增量成本而非业务代码大小 |
| 原理和工作流程 | 对比的底层差异只有三条：渲染引擎是自带的还是系统的、UI 是自绘的还是映射的、跨端发生在编译期还是运行期。Electron 的大体积来自内置 Chromium，Flutter 的强一致性来自自绘引擎，RN 的性能上限与瓶颈都来自"JS 驱动原生组件"这一机制 |
| 缺点 | 表格中的性能、体积等数值随版本迭代变化快，只能作为量级参考；生态成熟度的评价带有主观性，需结合自身业务的实际依赖做验证 |

## 1.3 选型决策树：四个维度（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 一套基于"目标平台 → 团队技术栈 → 性能要求 → 交付周期"四个维度依次收敛的选型方法，用决策树形式表达 |
| 能做什么 | 把模糊的"该选什么框架"转化为可执行的判断路径：仅桌面且体积敏感 → Tauri；仅桌面且要绝对一致性 → Electron；含小程序 → Taro / uniapp；愿意学 Dart 且要极致 UI 性能 → Flutter |
| 怎么用 | 从根节点"目标平台是"开始逐层判断；无完美方案时接受"移动端一套 + 桌面端一套"的组合，而不是强行用一套代码覆盖全平台 |
| 原理和工作流程 | 四个维度按"硬约束 → 软约束"排序：目标平台是不可协商的硬约束，先筛；团队技术栈决定学习成本上限；性能要求决定方案的天花板是否够用；交付周期决定能否承担新语言与新框架的双重学习成本 |
| 缺点 | 决策树只能给出方向性建议，无法量化权衡；当多个维度互相冲突（如周期紧但性能要求高）时，仍需要人工做取舍并承担对应风险 |

## 1.4 桌面端方案概览：Electron 与 Tauri（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 桌面端跨端的两大主流方案：Electron 用 Node.js 做后端 + 内置 Chromium 做渲染；Tauri 用 Rust 做后端 + 系统 WebView 做渲染 |
| 能做什么 | 用已有的 Web 技术栈开发 Windows / macOS / Linux 桌面应用；Electron 的代表应用有 VS Code、飞书、Slack、Discord；Tauri 阵营有 Pake、Spacedrive 等开源项目 |
| 怎么用 | Electron：`pnpm add -D electron` 后用 `main.js` 创建 `BrowserWindow`；Tauri：`pnpm create tauri-app` 生成前后端一体的工程，`pnpm tauri dev` 开发、`pnpm tauri build` 打包 |
| 原理和工作流程 | Electron 把 Chromium 与 Node.js 一起打包进安装包，进程间通过 IPC 通信，渲染进程默认无 Node 能力；Tauri 把前端产物嵌入 Rust 二进制，通过 `#[tauri::command]` 注册命令、前端用 `invoke` 调用，权限由 capability 声明式控制 |
| 缺点 | Electron 体积（80-150MB）与内存（100MB+）开销大；Tauri 依赖系统 WebView 导致渲染一致性风险，且需要 Rust 能力与更长的首次构建时间 |

## 2.1 Electron 的三进程模型（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Electron 应用由"一个 Node.js 主进程 + N 个 Chromium 渲染进程 + 预加载脚本"组成；预加载脚本在页面脚本之前执行，同时拥有 DOM 访问能力与受限的 Node 能力 |
| 能做什么 | 主进程负责创建窗口、管理应用生命周期、调用菜单/托盘/文件对话框等系统能力；渲染进程负责渲染页面与响应用户交互；预加载脚本负责把受限的系统能力安全地暴露给页面 |
| 怎么用 | 主进程：`new BrowserWindow({ webPreferences: { preload, contextIsolation: true, nodeIntegration: false, sandbox: true } })`；渲染进程：`window.desktopApi.xxx()`；预加载脚本：`contextBridge.exposeInMainWorld('desktopApi', { ... })` |
| 原理和工作流程 | `app.whenReady()` 后创建窗口 → 预加载脚本在页面脚本前执行并挂载受限 API → 页面脚本通过 `window` 上的桥接对象发起 IPC → 主进程处理并返回结果 → 窗口关闭触发 `closed`，全部窗口关闭后（非 macOS）调用 `app.quit()` |
| 缺点 | 每个窗口一个渲染进程，内存随窗口数线性增长；主进程是单例且被阻塞时会卡住整个应用；预加载脚本若暴露过宽会破坏安全边界 |

---

## 2.2 进程间通信：IPC 与 contextBridge（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Electron 的通信分两层：contextBridge 负责"开门"（在页面上挂载受限 API），IPC 负责"传话"（在主进程与渲染进程之间传递消息）。三种模式：请求-响应（`invoke`/`handle`）、单向通知（`send`/`on`）、主进程推送（`webContents.send`/`ipcRenderer.on`） |
| 能做什么 | 让渲染进程在不直接拥有 Node 能力的前提下，调用文件读写、系统对话框、原生菜单等主进程能力；也能让主进程把下载进度、更新通知等状态主动推送给 UI |
| 怎么用 | 主进程：`ipcMain.handle('config:read', async () => {...})`；预加载：`contextBridge.exposeInMainWorld('desktopApi', { readConfig: () => ipcRenderer.invoke('config:read') })`；渲染进程：`await window.desktopApi.readConfig()` |
| 原理和工作流程 | 页面调用桥接函数 → `ipcRenderer.invoke` 序列化参数并发送到主进程 → 主进程 `ipcMain.handle` 注册的回调执行 → 返回值序列化后通过 Promise 回传；订阅类通信中，预加载脚本需把 `(event, payload)` 包装为 `(payload)`，并返回取消订阅函数 |
| 缺点 | 所有数据都需要序列化，大对象传输有开销；若把 `ipcRenderer` 本体直接暴露给页面，等于把全部主进程能力交给前端；监听器忘记移除会导致内存泄漏与回调重复触发 |

## 2.3 Electron 安全实践（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 一套以"最小权限 + 显式授权"为核心的安全配置体系，关键项包括 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、`webSecurity: true`，配合 CSP、外链拦截与主进程参数校验 |
| 能做什么 | 即使渲染进程被 XSS 攻破，也无法直接执行系统命令、读取任意文件或跳转到钓鱼页面；把攻击面限制在"已暴露的受限函数"范围内 |
| 怎么用 | 主进程 `webPreferences` 中声明三项安全配置；用 `session.defaultSession.webRequest.onHeadersReceived` 注入 CSP；用 `setWindowOpenHandler` + `shell.openExternal` 处理外链并校验协议；IPC 处理器中对路径做白名单校验 |
| 原理和工作流程 | 上下文隔离让预加载脚本与页面运行在不同 JavaScript 上下文，页面无法篡改桥接对象 → Node 集成关闭后页面无 `require`/`process` → Chromium 沙箱提供 OS 级隔离 → CSP 禁止内联脚本与 `eval`，从源头抑制 XSS → 主进程校验是最后一道防线 |
| 缺点 | 默认值随 Electron 版本变化（`contextIsolation` 自 12 起默认 true、`sandbox` 自 20 起默认 true），旧项目升级时容易被历史配置绕过；过度收紧 CSP 可能影响正常功能，需要逐个指令调试 |

## 2.4 Electron 打包与自动更新（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | electron-builder 负责把源码、Chromium 与 Node.js 运行时组装成各平台安装包；electron-updater 负责在应用启动后检查、下载并安装新版本 |
| 能做什么 | 一次配置产出 Windows（nsis）、macOS（dmg/zip）、Linux（AppImage/deb）多平台安装包；支持增量更新、后台静默下载、下载完成后再提示用户重启 |
| 怎么用 | `package.json` 中配置 `build` 字段（`appId`、`files`、各平台 `target`、`publish` 更新源）；主进程 `app.isPackaged` 为真时调用 `autoUpdater.checkForUpdatesAndNotify()`，并监听 `update-available`、`download-progress`、`update-downloaded`、`error` 事件 |
| 原理和工作流程 | 构建时 electron-builder 收集 `files` 指定的产物并绑定平台运行时 → 生成安装包与更新元数据（如 `latest.yml`）→ 应用启动后向 `publish` 配置的地址请求元数据 → 版本号更高则下载差量/全量包 → 下载完成后调用 `quitAndInstall()` 退出并安装 |
| 缺点 | 体积无法通过打包配置显著削减（Chromium 是预编译二进制，不可 tree-shaking）；macOS 需要代码签名与公证，否则用户无法正常安装；更新源需要自行搭建或使用第三方托管 |

## 2.5 Tauri 的架构与体积优势（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Tauri 把 Electron 的"内置 Chromium + Node.js"替换为"系统 WebView + Rust 后端"，形成两层架构：渲染层用系统 WebView（Windows 用 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK），后端层是 Rust 编译出的单一静态二进制 |
| 能做什么 | 把桌面应用安装包从 80-150MB 压到 3-10MB，启动更快，且因为不打包浏览器内核而显著降低分发成本 |
| 怎么用 | `pnpm create tauri-app` 生成工程 → `src-tauri/` 放 Rust 代码与配置 → `pnpm tauri dev` 开发 → `pnpm tauri build` 打包，产物在 `src-tauri/target/release/bundle/` |
| 原理和工作流程 | 体积优势有三个成因：一是不打包浏览器内核，Chromium 这个体积大头直接归零；二是 Rust 编译为单一静态二进制，无运行时解释器与 JIT，还能通过 LTO 与 strip 进一步压缩；三是前端 HTML/CSS/JS 作为静态资源嵌入二进制，体积只取决于业务代码 |
| 缺点 | Windows 依赖 WebView2 Runtime（老系统需引导安装）；各平台 WebView 内核版本不同，存在渲染一致性与 CSS 兼容风险，Linux WebKitGTK 碎片化最严重；需要 Rust 能力且首次构建耗时较长 |

---

## 2.6 Tauri 的命令系统与 IPC（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Tauri 用 `#[tauri::command]` 宏定义后端命令、用 `generate_handler![]` 注册、前端用 `invoke` 调用；异步事件则通过 `emit` / `listen` 双向传递 |
| 能做什么 | 让前端调用 Rust 侧的文件、网络、数据库等能力；让 Rust 侧把下载进度、后台任务状态等主动推送给前端；命令返回值支持 `Result<T, E>`，错误可通过 `Err` 传到前端 Promise 的 reject |
| 怎么用 | Rust：`#[tauri::command] async fn save_user(user: User) -> Result<String, String> { ... }`，并在 `tauri::Builder::default().invoke_handler(tauri::generate_handler![greet, save_user])` 中注册；前端：`import { invoke } from '@tauri-apps/api/core'` 后 `await invoke<string>('greet', { name: '世界' })` |
| 原理和工作流程 | 前端 `invoke('命令名', 参数对象)` → 参数序列化后经 IPC 送到 Rust 侧 → 匹配已注册命令并执行 → `Ok` 值或 `Err` 值序列化回传 → 前端 Promise resolve 或 reject。事件通道则由 Rust 侧 `emit` 触发，前端 `listen` 收到 `event.payload` |
| 缺点 | 命令必须在 `generate_handler![]` 中显式注册，漏注册会在运行时报 `command not found`；耗时操作若写成同步命令会阻塞，需使用 `async`；参数与返回值需要 `Serialize`/`Deserialize`，复杂类型要额外处理 |

## 2.7 Tauri 的安全模型与权限配置（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Tauri 2 的三层权限模型：Permission 是单个 API 的最小权限单元（如 `fs:allow-read-text-file`），Capability 是一组权限的集合并绑定到具体窗口，Scope 规定权限的生效范围（如允许访问的目录白名单） |
| 能做什么 | 实现"默认拒绝"（deny by default）：未在 capability 中声明的 API，前端根本无法调用；即使前端被 XSS 控制，能造成的破坏也被权限范围限制住 |
| 怎么用 | 在 `src-tauri/capabilities/default.json` 中声明 `identifier`、`windows` 与 `permissions` 数组，权限项可带 `allow` 配置 scope，例如 `{ "identifier": "fs:allow-read-text-file", "allow": [{ "path": "$APPDATA/config/**" }] }` |
| 原理和工作流程 | 构建时 Tauri 读取 capabilities 生成权限清单 → 前端调用某个 API 时先校验该窗口是否拥有对应 capability → 再校验参数是否落在 scope 范围内 → 全部通过才转发到 Rust 侧执行 |
| 缺点 | 权限配置写在 JSON 中，与业务代码分离，排查"为什么调用被拒"时需要同时看配置与前端代码；插件权限标识符较多，初次配置需要查文档；相比 Electron 的"代码中手写校验"，灵活性略低但边界更清晰 |

---

## 2.8 Electron vs Tauri 逐项对比（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 从包体积、内存占用、渲染一致性、性能、生态、学习成本、原生能力、安全性、移动端支持、更新机制、构建时间、适用场景十二个维度对两者做逐项对比 |
| 能做什么 | 给出有依据的选型结论：需要渲染一致性、成熟生态、低学习成本 → Electron；需要极小体积、更清晰的安全模型、移动端延伸 → Tauri |
| 怎么用 | 把"渲染一致性"和"团队是否有 Rust 能力"作为两个关键分水岭：若应用 UI 复杂且要求三端完全一致，或团队无 Rust 能力且周期紧张，选 Electron；若体积是第一约束且团队愿意投入 Rust，选 Tauri |
| 原理和工作流程 | 所有差异最终收敛到两个根因：一是渲染引擎来自内置还是系统（决定体积、一致性与性能表现），二是后端语言是 Node.js 还是 Rust（决定生态、学习成本与构建时间）。包体积与一致性其实是同一个取舍的两面 |
| 缺点 | 对比结论具有时效性，Tauri 2 发布后生态与移动端支持改善明显；"内存占用更低"并非数量级差异，因为系统 WebView 本身仍占内存，容易被过度宣传误导 |

## 3.1 Electron 最小可用工程结构（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 一个可直接运行的 Electron 工程骨架：`main.js`（主进程）、`preload.js`（安全桥）、`renderer/`（前端产物）、`package.json`、`build/`（图标等打包资源） |
| 能做什么 | 完成窗口创建、白屏消除、外链拦截、系统文件对话框调用与 IPC 注册，作为真实桌面应用的起点 |
| 怎么用 | `new BrowserWindow({ show: false, webPreferences: { preload, contextIsolation: true, nodeIntegration: false, sandbox: true } })` → `loadFile` 加载页面 → `once('ready-to-show', () => win.show())` 消除白屏 → `ipcMain.handle('dialog:pickFile', ...)` 注册系统能力 → `setWindowOpenHandler` 拦截外链 |
| 原理和工作流程 | 应用就绪后创建窗口并隐藏 → 预加载脚本注入受限 API → 页面渲染完成后显示窗口 → 用户触发操作时页面调用桥接函数 → 主进程执行 `dialog.showOpenDialog` 与 `fs.readFile` → 结果回传渲染进程展示 |
| 缺点 | 仍需自行处理多平台差异（macOS 的 `activate` / `window-all-closed` 行为与 Windows 不同）；生产环境还需补充自动更新、崩溃上报与日志收集 |

## 3.2 Tauri 最小可用工程结构（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 一个标准的 Tauri 2 工程骨架：`src/`（前端工程）、`src-tauri/src/main.rs`（二进制入口）、`src-tauri/src/lib.rs`（业务逻辑与命令）、`src-tauri/capabilities/default.json`（权限配置）、`src-tauri/tauri.conf.json`（主配置） |
| 能做什么 | 用前端技术栈写 UI、用 Rust 写后端逻辑，产出多平台安装包；`main.rs` 保持极薄以便同一份逻辑复用到移动端 |
| 怎么用 | `pnpm create tauri-app` 创建 → `pnpm tauri dev` 开发（启动前端 dev server + 编译 Rust + 热重载）→ `pnpm tauri build` 打包，产物在 `src-tauri/target/release/bundle/` |
| 原理和工作流程 | 开发时前端跑在 Vite dev server（由 `devUrl` 指定），Tauri 窗口加载该地址；构建时执行 `beforeBuildCommand` 产出前端资源到 `frontendDist` 目录，再由 Rust 侧嵌入二进制并生成各平台安装包 |
| 缺点 | 首次 `cargo build` 需要编译大量 Rust 依赖，耗时明显长于 Electron；`main.rs` 与 `lib.rs` 的拆分对新手容易造成困惑；Windows 需确认目标机器具备 WebView2 Runtime |
