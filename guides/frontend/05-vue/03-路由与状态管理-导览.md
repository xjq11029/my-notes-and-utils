## 二、底层原理

### Vue Router 路由模式

| 维度 | 内容 |
|------|------|
| 是什么 | Vue Router 支持两种路由模式：Hash 模式（URL 使用 `#` 分隔，通过 `hashchange` 事件监听）和 History 模式（使用 HTML5 History API 的 `pushState`/`replaceState`，配合 `popstate` 事件）。 |
| 能做什么 | Hash 模式不需要服务器配置，兼容性好，适合中后台应用；History 模式 URL 干净，对 SEO 友好，适合需要 SEO 的前台应用。 |
| 怎么用 | Hash：`createRouter({ history: createWebHashHistory(), routes })`；History：`createRouter({ history: createWebHistory(), routes })`；Nginx 配置 `try_files $uri $uri/ /index.html`。 |
| 原理和工作流程 | Hash 模式：`#` 后面的内容不发送给服务器，通过 `hashchange` 事件监听 URL 变化来切换路由；History 模式：`pushState` 修改 URL 不刷新页面，但手动调用不触发 `popstate`，只有浏览器前进后退触发；需要服务器配置 fallback，否则刷新页面会 404。 |
| 缺点 | Hash 模式 URL 不美观，部分搜索引擎不索引 `#` 后内容；History 模式需要服务器配置，增加了部署复杂度。 |

### 动态路由匹配

| 维度 | 内容 |
|------|------|
| 是什么 | 通过路由参数 `:id` 实现动态匹配，如 `/user/:id` 匹配 `/user/123`；当从 `/user/123` 导航到 `/user/456` 时组件被复用不会重新创建。 |
| 能做什么 | 实现基于参数的路由跳转和页面渲染；通过 `watch` 或 `onBeforeRouteUpdate` 守卫处理参数变化时的数据更新。 |
| 怎么用 | `const routes = [{ path: '/user/:id', component: UserDetail }]`；`const route = useRoute(); console.log(route.params.id)`；`watch(() => route.params.id, (newId) => fetchUser(newId))`。 |
| 原理和工作流程 | 路由匹配时从 URL 中提取动态参数，存入 `route.params`；相同路由不同参数时，组件实例被复用，不会触发 `onMounted`，需要通过 `watch` 或 `onBeforeRouteUpdate` 守卫响应参数变化。 |
| 缺点 | 组件复用可能造成数据残留，需要在守卫中做好数据重置。 |

### 嵌套路由

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 `children` 配置实现路由嵌套，父组件中使用 `<router-view>` 渲染子路由组件，支持多层嵌套。 |
| 能做什么 | 实现页面布局复用（如左侧导航 + 右侧内容区），子路由在父组件指定位置渲染。 |
| 怎么用 | `const routes = [{ path: '/user/:id', component: UserLayout, children: [{ path: 'profile', component: UserProfile }, { path: 'posts', component: UserPosts }] }]`；父组件中 `<router-view />` 渲染子路由。 |
| 原理和工作流程 | 路由匹配时逐层解析嵌套路径，每个 `<router-view>` 对应一层嵌套路由的渲染出口；子路由路径相对于父路由路径。 |
| 缺点 | 嵌套层级过深时路由配置复杂，调试困难。 |

### 路由守卫

| 维度 | 内容 |
|------|------|
| 是什么 | 三组路由守卫：全局守卫（beforeEach、beforeResolve、afterEach）、路由独享守卫（beforeEnter）、组件内守卫（beforeRouteEnter、beforeRouteUpdate、beforeRouteLeave），按固定顺序执行。 |
| 能做什么 | 控制导航访问权限（登录校验、角色校验）；在导航前后执行数据预加载、埋点统计等操作；阻止未保存数据的页面离开。 |
| 怎么用 | `router.beforeEach((to, from, next) => { if (to.meta.requiresAuth && !isLoggedIn()) next('/login'); else next(); })`；`onBeforeRouteLeave((to, from) => { if (!confirm('确定离开？')) return false })`。 |
| 原理和工作流程 | 完整导航解析流程：beforeRouteLeave → beforeEach → beforeRouteUpdate → beforeEnter → 解析异步组件 → beforeRouteEnter → beforeResolve → 确认导航 → afterEach → DOM 更新 → beforeRouteEnter 的 next 回调。 |
| 缺点 | 守卫中忘记调用 `next()` 会导致路由卡住；守卫中执行大量异步操作会阻塞导航。 |

### 路由懒加载

| 维度 | 内容 |
|------|------|
| 是什么 | 使用动态 import 语法实现路由级别的代码分割：`() => import('./Component.vue')`，构建工具将动态 import 的模块拆分为独立 chunk，仅在路由被访问时加载。 |
| 能做什么 | 减少首屏加载体积，提升页面加载速度；多个路由可共享同一 chunk（通过 webpackChunkName 命名）。 |
| 怎么用 | `const routes = [{ path: '/about', component: () => import(/* webpackChunkName: "about" */ './views/About.vue') }]`。 |
| 原理和工作流程 | 构建工具（Vite/Webpack）识别动态 import 语法，将对应模块拆分为独立 chunk；路由被访问时浏览器按需加载 chunk；`webpackChunkName` 注释给 chunk 命名，同名 chunk 合并打包。 |
| 缺点 | 每个路由一个 chunk 可能导致请求过多，需合理分组；网络较慢时首次访问路由会有加载延迟。 |

## Pinia 状态管理

### 为什么 Pinia 替代 Vuex

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 是 Vue 3 官方推荐的状态管理库，去掉了 Vuex 中冗余的 mutations 概念，提供原生 TypeScript 支持和扁平化的 store 管理。 |
| 能做什么 | 直接修改 state 无需 commit；完整的 TypeScript 类型推断；支持 Options API 和 Composition API 两种写法；代码量更少。 |
| 怎么用 | `export const useCounterStore = defineStore('counter', { state: () => ({ count: 0 }), getters: { doubleCount: (state) => state.count * 2 }, actions: { increment() { this.count++ } } })`。 |
| 原理和工作流程 | Pinia 内部使用 Vue 3 的 reactive 将 state 转换为响应式；getters 基于 computed 实现；actions 是普通函数，可以直接修改 state；每个 store 是独立的，通过 `useXxxStore()` 获取实例。 |
| 缺点 | 去掉了 mutations 可能让某些开发者不适应；state 修改的追踪不如 Vuex 的 mutations 明确。 |

### Pinia 核心概念

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 通过 `defineStore` 定义 store，支持 Options API 风格（state/getters/actions）和 Composition API 风格（setup 写法），提供 `$patch`、`$reset`、`$subscribe`、`$onAction` 等内置 API。 |
| 能做什么 | Options API 风格适合从 Vuex 迁移；Composition API 风格更灵活，支持任意组合；`$patch` 批量更新，`$subscribe` 监听变化，`$onAction` 拦截 action。 |
| 怎么用 | `const counter = useCounterStore(); counter.count++; counter.$patch({ count: 100 }); counter.$subscribe((mutation, state) => { ... })`。 |
| 原理和工作流程 | `$patch` 可接受对象或函数，批量更新 state 减少多次触发；`$subscribe` 与 Vue 的 `watch` 类似，监听 state 变化；`$reset` 将 state 重置为初始值（仅 Options API 风格支持）；`$onAction` 提供 action 执行前后的钩子。 |
| 缺点 | setup 风格不支持 `$reset`，需要手动实现；store 之间循环引用可能导致问题。 |

## 三、实战应用

### 权限路由控制

| 维度 | 内容 |
|------|------|
| 是什么 | 在 `beforeEach` 全局守卫中根据用户登录状态和角色权限控制路由访问，未登录跳转登录页，无权限跳转 403 页面。 |
| 能做什么 | 实现前端路由级别的权限控制，防止未授权用户访问受保护页面。 |
| 怎么用 | `router.beforeEach((to, from, next) => { if (to.meta.requiresAuth && !userStore.isLoggedIn) next('/login'); else if (to.meta.roles && !to.meta.roles.includes(userStore.role)) next('/403'); else next(); })`。 |
| 原理和工作流程 | 路由 `meta` 字段定义权限要求（`requiresAuth`、`roles`）；守卫中检查 Pinia store 中的用户状态和角色；根据检查结果决定放行、重定向或拒绝。 |
| 缺点 | 前端权限控制只能作为 UI 层面的拦截，后端仍需进行权限校验。 |

### 动态路由注册

| 维度 | 内容 |
|------|------|
| 是什么 | 登录成功后根据后端返回的权限路由列表，使用 `router.addRoute()` 动态添加路由，实现按权限加载的菜单和路由。 |
| 能做什么 | 实现不同角色看到不同的菜单和页面，避免前端硬编码所有路由。 |
| 怎么用 | `const permissionRoutes = await api.getPermissionRoutes(); permissionRoutes.forEach(route => router.addRoute(route))`。 |
| 原理和工作流程 | 后端返回用户有权访问的路由配置（含 path、component 映射）；前端动态注册路由，`router.addRoute` 支持嵌套路由和命名路由。 |
| 缺点 | 组件路径映射需要前端维护；动态路由增加路由初始化复杂度。 |

### Pinia 持久化

| 维度 | 内容 |
|------|------|
| 是什么 | 通过自定义 Pinia 插件实现状态持久化，将 store 状态保存到 localStorage，页面刷新后恢复状态。 |
| 能做什么 | 保持用户登录状态、偏好设置等跨会话数据，提升用户体验。 |
| 怎么用 | `function localStoragePlugin({ store }) { const saved = localStorage.getItem('pinia-' + store.$id); if (saved) store.$patch(JSON.parse(saved)); store.$subscribe((mutation, state) => localStorage.setItem('pinia-' + store.$id, JSON.stringify(state))) }`。 |
| 原理和工作流程 | 插件在 store 初始化时从 localStorage 恢复状态；通过 `$subscribe` 监听状态变化，自动保存到 localStorage。 |
| 缺点 | localStorage 有容量限制（约 5MB）；敏感数据不应存储在 localStorage 中。 |

## 四、常见面试题

### 1. hash 模式和 history 模式的区别

| 维度 | 内容 |
|------|------|
| 是什么 | Hash 模式 URL 带 `#`，`#` 后的内容不发送给服务器，通过 `hashchange` 监听；History 模式 URL 干净，通过 `pushState`/`popstate` 实现，需要服务器配置 fallback。 |
| 能做什么 | Hash 模式无需服务器配置，兼容性好；History 模式对 SEO 更友好，URL 更美观。 |
| 怎么用 | `createWebHashHistory()` 和 `createWebHistory()` 创建对应模式的路由实例。 |
| 原理和工作流程 | Hash 模式 `#` 后的内容仅用于前端路由，服务器只看到 `#` 前的部分；History 模式直接修改 URL 路径，刷新时浏览器向服务器请求该路径，无对应文件则 404。 |
| 缺点 | Hash 模式 URL 不美观，SEO 差；History 模式需要服务器配置。 |

### 2. 路由守卫有哪些？执行顺序是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 全局守卫（beforeEach、beforeResolve、afterEach）、路由独享守卫（beforeEnter）、组件内守卫（beforeRouteEnter、beforeRouteUpdate、beforeRouteLeave）。 |
| 能做什么 | 在导航的不同阶段执行权限检查、数据预加载、埋点统计等操作。 |
| 怎么用 | 守卫接收 `to`、`from`、`next` 参数，调用 `next()` 继续导航。 |
| 原理和工作流程 | 执行顺序：beforeRouteLeave → beforeEach → beforeRouteUpdate → beforeEnter → 解析组件 → beforeRouteEnter → beforeResolve → 确认导航 → afterEach → DOM 更新 → beforeRouteEnter 的 next 回调。 |
| 缺点 | 守卫链较长，忘记调用 `next()` 会导致导航卡住。 |

### 3. Pinia 和 Vuex 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 去掉了 mutations，可以直接修改 state；完整的 TypeScript 支持；多个独立 store 扁平化管理；支持 Options API 和 Composition API 两种写法。 |
| 能做什么 | 代码更简洁，模板代码更少；类型自动推断，开发体验更好。 |
| 怎么用 | `defineStore('counter', { state: () => ({ count: 0 }), actions: { increment() { this.count++ } } })`。 |
| 原理和工作流程 | Pinia 内部使用 reactive 实现响应式 state；actions 直接修改 state 无需 commit；store 之间可以互相引用。 |
| 缺点 | 去掉了 mutations 可能让某些团队失去状态变更的明确追踪。 |

### 4. 路由懒加载的原理

| 维度 | 内容 |
|------|------|
| 是什么 | 使用动态 import 语法 `() => import('./Component.vue')`，构建工具将模块拆分为独立 chunk，仅在路由被访问时加载。 |
| 能做什么 | 减少首屏加载体积，加快页面初始加载速度。 |
| 怎么用 | `const routes = [{ path: '/about', component: () => import('./views/About.vue') }]`。 |
| 原理和工作流程 | 构建工具识别动态 import，自动进行代码分割；路由被访问时浏览器按需加载对应的 chunk 文件。 |
| 缺点 | 每个路由一个 chunk 可能导致过多 HTTP 请求。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 聚合了路由与状态管理开发中七个常见错误：history 模式刷新 404、动态路由参数变化时组件不更新、Pinia 中直接替换整个 state、路由守卫中忘记调用 next、Pinia action 中返回 Promise 未处理、滥用路由守卫做大量异步操作、多个 store 中循环引用。 |
| 能做什么 | 快速对照排查：Nginx 配置 `try_files $uri /index.html`；使用 `watch` 或 `onBeforeRouteUpdate` 处理参数变化；使用 `$patch` 更新 state；检查每个守卫分支都调用了 `next()`；使用 `try/catch` 处理 action 错误；非必要异步操作放到 `afterEach` 中；在 action 内部按需引入避免顶层循环依赖。 |
| 怎么用 | Nginx：`location / { try_files $uri $uri/ /index.html; }`；`watch(() => route.params.id, fetchUser)`；`store.$patch({ count: 100 })`；`router.beforeEach((to, from, next) => { next() })`。 |
| 原理和工作流程 | History 模式刷新时浏览器向服务器请求对应路径，服务器无对应文件返回 404；动态路由参数变化时组件复用，不会触发 `onMounted`；Pinia state 通过 reactive 代理，直接替换引用会丢失 Proxy。 |
| 缺点 | 需要开发者对路由和状态管理有较深理解才能避免这些错误。 |

## 路由进阶

### 动态路由与权限路由

| 维度 | 内容 |
|------|------|
| 是什么 | 运行时通过 `router.addRoute()` 注册路由的能力，支持「顶级路由」与「指定父路由的嵌套路由」两种写法；`removeRoute()` / `hasRoute()` / `getRoutes()` 分别用于移除、判断存在、获取全部路由，`addRoute` 的返回值本身也是一个移除函数。 |
| 能做什么 | 按后端返回的权限列表动态生成路由表与菜单；退出登录时批量撤销动态路由；配合 `import.meta.glob` 把后端返回的组件字符串映射为真实组件。 |
| 怎么用 | `router.addRoute({ path: '/dashboard', name: 'dashboard', component: () => import('@/views/Dashboard.vue'), meta: { roles: ['admin'] } })`；嵌套：`router.addRoute('layout', childRoute)`；移除：`router.removeRoute('dashboard')`。 |
| 原理和工作流程 | 完整流程：静态路由先注册 → 守卫中判断登录态 → 未注入时 `await fetchPermissionRoutes()` 后逐条 `addRoute` → **通配路由 `/:pathMatch(.*)*` 必须最后添加** → `next({ ...to, replace: true })` 重新导航。刷新页面后动态路由会丢失，必须在守卫中重新注入，并用 `injected` 标志或 `hasRoute(name)` 保证幂等。 |
| 缺点 | `addRoute` 不会自动触发导航，已处于目标路径时页面不会刷新；重复添加会告警；通配路由先注册会把动态路由全部匹配到 404；权限路由只是 UI 层收敛，后端仍需鉴权。 |

### 路由懒加载与预加载策略

| 维度 | 内容 |
|------|------|
| 是什么 | 懒加载用动态 `import()` 让构建工具做代码分割，把路由组件拆成独立 chunk 按需加载；预加载则在空闲或用户即将访问时提前下载这些 chunk。 |
| 能做什么 | 懒加载降低首屏体积；预加载消除「切路由时等待 chunk 下载」的空白期。四种预加载策略：`webpackPrefetch` / `webpackPreload` 声明式、进入页面后预取、悬停预取、`afterEach` 全局兜底。 |
| 怎么用 | 懒加载：`component: () => import(/* webpackChunkName: "group-settings" */ '@/views/Settings.vue')`；预取：`router.getRoutes().find(r => r.name === name)?.components?.default?.()`，放在 `requestIdleCallback` 中执行；悬停：`@mouseenter="prefetch('report')" @focus="prefetch('report')"`。 |
| 原理和工作流程 | 构建工具识别动态 import 后拆出独立 chunk；懒加载路由的 `component` 是 `() => import(...)` 函数，**直接调用该函数即触发下载**，且 vue-router 会复用同一个 Promise 缓存，重复调用不会重复请求。`webpackPrefetch` 在浏览器空闲时以最低优先级下载，`webpackPreload` 与父 chunk 并行下载。 |
| 缺点 | `webpackPrefetch` / `webpackPreload` 是 Webpack 特有语法，**Vite 不支持**（Vite 需用 `build.modulePreload` 或手动策略）；预取清单需手工维护，配置错误会造成无谓下载；悬停预取在移动端无 hover，需补 `focus` 事件。 |

### 滚动行为（scrollBehavior）

| 维度 | 内容 |
|------|------|
| 是什么 | `createRouter` 的 `scrollBehavior(to, from, savedPosition)` 选项，用于控制路由切换后的滚动位置，返回 `false` 表示保持当前位置不滚动。 |
| 能做什么 | 前进后退时恢复历史位置；支持锚点跳转（可带固定头部偏移）；按 `meta` 声明保持列表页滚动位置；等异步组件渲染完成后再滚动。 |
| 怎么用 | `scrollBehavior(to, from, savedPosition) { if (savedPosition) return savedPosition; if (to.hash) return { el: to.hash, behavior: 'smooth', top: 80 }; if (to.meta.keepScroll) return false; return { top: 0 } }`。 |
| 原理和工作流程 | 返回值有五种形态：`{ left, top }` 坐标、`{ el, behavior, top }` 元素、`false` 不滚动、`savedPosition` 历史位置、`Promise`（异步返回上述任意值，Vue Router 会等待 resolve）。启用后 Vue Router 会把 `history.scrollRestoration` 置为 `'manual'`，避免与浏览器自身的滚动恢复冲突；`savedPosition` **仅在 `popstate` 导航（浏览器前进后退）时有值**，`router.push()` 拿不到。 |
| 缺点 | 目标元素由懒加载组件渲染时，同步滚动会找不到元素而失效，必须用 `Promise` + `requestAnimationFrame` 延迟一帧；`scrollBehavior` 无法感知页面内部的滚动容器，只能作用于 window 滚动。 |

### 路由元信息（meta）的类型扩展

| 维度 | 内容 |
|------|------|
| 是什么 | `meta` 是路由配置上唯一可自由扩展的字段；TypeScript 下需通过接口合并扩展 `vue-router` 的 `RouteMeta` 接口，才能让 `to.meta.xxx` 获得类型提示。 |
| 能做什么 | 承载 `title`、`requiresAuth`、`roles`、`keepAlive`、`keepScroll`、`prefetch`、`transition` 等约定字段，供守卫、过渡动画、缓存策略与 `afterEach` 统一消费。 |
| 怎么用 | `declare module 'vue-router' { interface RouteMeta { title?: string; roles?: string[]; keepAlive?: boolean } }`，文件必须含 `import` / `export`（如 `import 'vue-router'` + `export {}`）以保证是模块。 |
| 原理和工作流程 | 扩展后 `to.meta.roles` 自动推导为 `string[] \| undefined`，`to.meta.notExist` 直接报错。**必须用 `interface` 做声明合并**，写成 `export interface RouteMeta` 或 `type RouteMeta = ...` 会覆盖官方定义，导致 `path`、`fullPath` 等字段类型丢失；`.d.ts` 若不是模块，`declare module` 会被当作全局声明而失效。 |
| 缺点 | 字段全靠团队约定，缺少运行时校验，拼写错误只能靠类型系统兜底；`.d.ts` 忘记加 `import` / `export` 时会「静默不生效」，排查成本高。 |

### `<RouterView>` 的 `v-slot` 用法

| 维度 | 内容 |
|------|------|
| 是什么 | `<RouterView>` 提供作用域插槽，暴露 `Component`（当前匹配到的路由组件，未匹配时为 `undefined`）与 `route`（规范化路由对象，等价于 `useRoute()` 的返回值）两个 prop。 |
| 能做什么 | 在路由出口外层包裹 `<Transition>` 过渡、`<KeepAlive>` 缓存与条件渲染；按 `route.meta` 动态决定动画名称与缓存范围。 |
| 怎么用 | `<RouterView v-slot="{ Component, route }"><Transition :name="route.meta.transition \|\| 'fade'" mode="out-in"><KeepAlive :include="cachedViews"><component :is="Component" :key="route.path" /></KeepAlive></Transition></RouterView>`。 |
| 原理和工作流程 | `Component` 是渲染器解析出的路由组件 VNode 构造器，交给 `<component :is>` 动态渲染；`:key="route.path"` 决定同组件不同参数时是否重新创建（不写 `:key` 则复用组件、只触发 `onBeforeRouteUpdate`）。`KeepAlive` 的 `include` 匹配**组件名**，需页面用 `defineOptions({ name: 'UserList' })` 与路由名对齐。 |
| 缺点 | `v-slot` 与 `props` 不能混用，想透传参数应使用路由的 `props` 选项；`KeepAlive` 的 `include` 按组件名匹配，命名不一致时会「缓存不生效」且无报错。 |

## Pinia 进阶

### Pinia 插件机制

| 维度 | 内容 |
|------|------|
| 是什么 | 插件是签名为 `({ pinia, app, store, options }) => void \| Partial<store>` 的函数，通过 `pinia.use(plugin)` 注册，在**每个 store 被创建时**执行一次。 |
| 能做什么 | 统一做日志与埋点、action 耗时统计与错误上报、按 store 定制行为（读取 `defineStore` 第三个参数）、为所有 store 注入公共属性或方法。 |
| 怎么用 | `store.$onAction(({ name, args, after, onError }) => { const start = Date.now(); after(() => console.log(Date.now() - start)); onError(console.error) })`；注入响应式属性用 `store.requestCount = ref(0)`，注入非响应式实例（如 router）用 `store.router = markRaw(router)`；返回对象会被合并到 store 上。 |
| 原理和工作流程 | `pinia.use()` 把插件推进内部插件数组，store 实例化时依次调用；`$onAction` 的 `after` / `onError` 回调分别在 action resolve / reject 后执行。插件中可通过 `pinia.state.value` 拿到所有 store 的 state，适合做统一持久化或状态快照。 |
| 缺点 | 给 store 新增属性必须用 `ref()` / `reactive()` 包裹，直接 `store.foo = 1` 是普通属性，改动不触发视图更新；插件在每次创建 store 时执行，逻辑过重会拖慢首屏；插件内部报错会影响整个 store 的初始化。 |

### 持久化（pinia-plugin-persistedstate）

| 维度 | 内容 |
|------|------|
| 是什么 | 社区最主流的 Pinia 持久化插件，把「手写 `$subscribe` + `localStorage`」收敛为声明式配置，Options 风格写 `persist` 选项，Setup 风格作为 `defineStore` 的第三个参数。 |
| 能做什么 | 刷新页面后保留 token、主题、语言等跨会话状态；按 `pick` 白名单或 `omit` 黑名单选择字段；自定义 `key` / `storage` / `serializer`；通过 `createPersistedState({ auto: true })` 让未显式配置的 store 也自动持久化。 |
| 怎么用 | `persist: { key: 'app-user', storage: localStorage, pick: ['token', 'theme'] }`；Setup 风格：`defineStore('cart', () => {...}, { persist: true })`；全局：`pinia.use(createPersistedState({ auto: true }))`，`key` 可传函数统一加前缀，如 `(id) => 'app-' + id`。 |
| 原理和工作流程 | 插件在 store 初始化时读取存储并 `$patch` 回填，再通过 `$subscribe` 监听 state 变化写回存储。v4 用 `pick` / `omit`（v3 中对应 `paths`），只支持 JSON 可序列化的数据。 |
| 缺点 | `loading` / `error` 等瞬态字段被一起持久化会导致刷新后卡在 loading；函数、`Date`、`Map`、`Set` 无法正确序列化；`localStorage` 存 token 可被 XSS 直接读取，敏感凭证应优先放 `HttpOnly` Cookie；多标签页状态不一致，需监听 `storage` 事件或改用 `BroadcastChannel`；数据结构升级后旧数据会引发运行时错误，应在 `key` 中带版本号。 |

### storeToRefs 与响应式丢失

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 的 store 本身是 `reactive` 对象（state 为 `reactive`，getters 为 `computed`），直接解构会得到普通值而丢失响应性；`storeToRefs(store)` 把 state 与 getters 转成 ref 后返回。 |
| 能做什么 | 安全地解构 store 中的 state 与 getters 并保持响应式；明确区分「需要转 ref 的 state/getters」与「直接解构的 actions」。 |
| 怎么用 | `const { token, isLoggedIn } = storeToRefs(userStore)`；`const { logout } = userStore`（actions 直接解构）；模板中 ref 自动解包，JS 中需 `token.value`。 |
| 原理和工作流程 | `storeToRefs` 只处理 `isRef` / `isReactive` 的属性，因此会**跳过 actions**——actions 本就是普通函数，若也转成 ref，调用方式会变成 `logout.value()`，反直觉且易错；`toRefs` 不跳过 actions，这是两者的关键差异。 |
| 缺点 | 其它三种响应式丢失场景仍需注意：解构 `profile.value` 内部的属性、把 state 赋给普通变量（`let token = store.token`）、直接整体替换 `store.$state` 会丢失未声明字段。 |

### Pinia vs Vuex 的迁移要点

| 维度 | 内容 |
|------|------|
| 是什么 | 从 Vuex 4 迁移到 Pinia 的 API 映射与步骤：去掉 mutations、去掉 namespaced 与 rootState、state 统一为函数、辅助函数改为 `storeToRefs`、插件从 `store.subscribe` 改为 `pinia.use` + `$onAction`。 |
| 能做什么 | 逐个模块把 Vuex module 改写为独立的 `defineStore`；用 `commit` / `dispatch` → 直接方法调用、`mapState` / `mapGetters` / `mapActions` → `storeToRefs` + 直接调用完成调用点替换。 |
| 怎么用 | `createStore({...})` → `createPinia()` + `app.use(pinia)`；`defineStore(id, { state: () => ({...}), getters, actions })`；`store.commit('increment')` → `store.increment()`；`store.subscribe` → `store.$subscribe`；`store.subscribeAction` → `store.$onAction`。 |
| 原理和工作流程 | Pinia 内部用 `reactive` 承载 state、`computed` 承载 getters，actions 是普通函数可直接改 state，因此不再需要 mutation 这一层「变更入口」；模块扁平化后通过按需 `useXxxStore()` 互相引用，不再有根上下文。 |
| 缺点 | Options 风格的 `this` 指向 store 实例，但**箭头函数中的 `this` 不指向 store**，必须用普通方法简写；`state` 若直接写对象会在 SSR 下造成跨请求状态污染；`mapState` 等依赖 Options API 的 `this`，在 `<script setup>` 中不可用。 |

### 模块化 store 设计

| 维度 | 内容 |
|------|------|
| 是什么 | 大型项目中 store 的划分与协作约定：按业务域拆分文件、统一命名、状态就近、不持有实例、职责分层，并规定跨 store 的调用与修改方式。 |
| 能做什么 | 避免「一个巨型 store」和「按数据类型建 store」；让 state / getters / actions 各司其职；理清组件 → store action → service/api → 后端的调用链路。 |
| 怎么用 | 目录：`stores/{index,app,user,permission,cart,order}.js`；协作：在 getter / action 内部 `const userStore = useUserStore()`；修改他人状态走对方 action，如 `userStore.addOrderCount()`。 |
| 原理和工作流程 | 拆分原则：一个 store 对应一个业务域，文件 `user.js` ↔ store id `'user'` ↔ Hook `useUserStore`；`state` 存纯数据、`getters` 做纯派生、`actions` 是唯一允许修改 state 的地方。**只在 `getters` / `actions` / 组件 setup 内调用 `useXxxStore()`，不在模块顶层调用**，否则会触发循环依赖或「pinia 尚未安装」错误；跨域共享数据归属最基础的 store（如 `user`），其他 store 引用读取而非复制。 |
| 缺点 | 分层约定依赖团队自觉，缺少强制约束；跨 store 调用链过深时调试困难；`state` 一旦被多个 store 复制，就会出现「同一份数据两处真相」的同步问题。 |
