### 1. Vue 3 中创建响应式数据可以使用哪个 API

| 维度 | 内容 |
|------|------|
| 是什么 | Vue 3 通过 `ref()` 和 `reactive()` 创建响应式数据，`ref()` 用于基本类型和对象，`reactive()` 用于对象。 |
| 能做什么 | `ref` 返回包装对象，通过 `.value` 访问；`reactive` 返回 Proxy 代理对象，直接访问属性。 |
| 怎么用 | `const count = ref(0); count.value++`；`const user = reactive({ name: '张三' }); user.name = '李四'`。 |
| 原理和工作流程 | ref 内部通过 getter/setter 实现响应式，对对象自动调用 reactive；reactive 通过 Proxy 代理整个对象。 |
| 缺点 | ref 需要 `.value` 访问；reactive 不支持基本类型。 |

### 2. Vue 3 中 `<script setup>` 的优势不包括

| 维度 | 内容 |
|------|------|
| 是什么 | `<script setup>` 是 Composition API 的语法糖，优势包括代码更简洁、顶层变量自动暴露给模板、import 的组件直接可用不需要注册，但仍需要通过 `import` 导入组件。 |
| 能做什么 | 减少样板代码，提高开发效率。 |
| 怎么用 | `<script setup>import MyComponent from './MyComponent.vue'; const count = ref(0)</script>`。 |
| 原理和工作流程 | 编译时自动处理 `defineProps`、`defineEmits` 等宏，顶层变量自动暴露给模板。 |
| 缺点 | 语法糖隐藏了部分底层细节，初学者可能不理解 setup 函数的本质。 |

### 3. v-if 和 v-show 的区别是什么

| 维度 | 内容 |
|------|------|
| 是什么 | v-if 是条件渲染，控制 DOM 的创建和销毁，切换开销大；v-show 是 CSS 显示控制，始终渲染到 DOM，通过 `display` 切换，初始渲染开销大但切换开销小。 |
| 能做什么 | v-if 适合不频繁切换的场景（如权限控制）；v-show 适合频繁切换的场景（如 Tab 切换）。 |
| 怎么用 | `<div v-if="isVisible">内容</div>`；`<div v-show="isVisible">内容</div>`。 |
| 原理和工作流程 | v-if 在条件为 false 时 DOM 元素完全不存在，惰性渲染；v-show 元素始终存在，只是 `display: none`。 |
| 缺点 | v-if 频繁切换导致 DOM 频繁创建销毁；v-show 初始渲染所有元素。 |

### 4. 关于 ref 和 reactive 的区别，说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | ref 可以用于基本类型和对象，通过 `.value` 访问；reactive 只能用于对象，直接访问属性。 |
| 能做什么 | ref 更通用，支持基本类型和对象替换；reactive 访问更简洁。 |
| 怎么用 | `const count = ref(0); count.value++`；`const user = reactive({ count: 0 }); user.count++`。 |
| 原理和工作流程 | ref 内部对对象自动调用 reactive；两者解构时都需要 toRef/toRefs 保持响应性。 |
| 缺点 | ref 的 `.value` 在 JS 中需手动访问；reactive 不能用于基本类型。 |

### 5. Vue 3 的响应式原理使用的是什么技术

| 维度 | 内容 |
|------|------|
| 是什么 | Vue 3 使用 ES6 的 Proxy 实现响应式，代理整个对象，支持新增/删除属性检测和数组索引修改；Vue 2 使用 Object.defineProperty。（Vue 2 已于 2023-12-31 停止维护（EOL），新项目请使用 Vue 3） |
| 能做什么 | 解决 Vue 2 中无法检测新增/删除属性、数组索引修改和 length 修改的痛点。 |
| 怎么用 | `const state = reactive({}); state.newProp = 'value'` 自动响应式。 |
| 原理和工作流程 | Proxy 的 get/set/deleteProperty 陷阱拦截所有操作，配合 Reflect API 保证 this 指向正确。 |
| 缺点 | Proxy 不支持 IE11，无法被 polyfill。（历史兼容场景，2026 年新项目按现代浏览器基线） |

### 6. 关于 computed 和 watch 的区别，说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | computed 有缓存，依赖不变不重新计算，适合衍生值计算；watch 没有缓存，变化就执行回调，适合执行副作用。 |
| 能做什么 | computed 适合纯计算场景；watch 适合异步请求、DOM 操作等副作用。 |
| 怎么用 | `const doubled = computed(() => count.value * 2)`；`watch(count, (n) => fetchData(n))`。 |
| 原理和工作流程 | computed 内部有 dirty 标记控制缓存；watch 每次依赖变化都执行回调。 |
| 缺点 | computed 不应产生副作用；watch 没有缓存，多次访问需重复计算。 |

### 7. 关于 Vue Router 的 hash 模式和 history 模式，说法错误的是

| 维度 | 内容 |
|------|------|
| 是什么 | Hash 模式 URL 包含 `#`，通过 `hashchange` 监听；History 模式 URL 干净，通过 `popstate` 监听，需要服务器配置 fallback。History 模式对 SEO 更友好，而非 Hash 模式。 |
| 能做什么 | 识别两种路由模式的差异和适用场景。 |
| 怎么用 | `createWebHashHistory()` 和 `createWebHistory()`。 |
| 原理和工作流程 | Hash 模式 `#` 后的内容不发送给服务器；History 模式刷新时浏览器请求真实路径。 |
| 缺点 | Hash 模式 SEO 差；History 模式需要服务器配置。 |

### 8. 关于 Pinia 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 去掉了 Vuex 中冗余的 mutations 概念，可以直接修改 state，原生完整支持 TypeScript。 |
| 能做什么 | 简化状态管理，减少样板代码，更好的类型推断。 |
| 怎么用 | `const counter = useCounterStore(); counter.count++` 直接修改。 |
| 原理和工作流程 | Pinia 内部使用 reactive 实现响应式 state，actions 直接修改 state 无需 commit。 |
| 缺点 | 去掉了 mutations 可能让状态变更追踪不够明确。 |

### 9. 关于 Vue 3 中 watchEffect 和 watch 的区别，说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | watchEffect 自动追踪依赖并立即执行，不需要手动指定监听源；watch 需要显式指定监听源，默认惰性执行。 |
| 能做什么 | watchEffect 适合简单的副作用；watch 适合需要新旧值对比或精确控制执行时机的场景。 |
| 怎么用 | `watchEffect(() => { console.log(count.value) })`；`watch(count, (n, o) => { ... })`。 |
| 原理和工作流程 | watchEffect 首次执行时收集依赖，后续自动追踪；watch 根据指定源建立依赖。 |
| 缺点 | watchEffect 不能获取新旧值。 |

### 10. 关于 nextTick 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | nextTick 在下次 DOM 更新循环之后执行回调，确保在回调中能获取到更新后的 DOM。 |
| 能做什么 | 数据变化后获取更新后的 DOM 尺寸、位置等。 |
| 怎么用 | `await nextTick(); console.log(element.textContent)`。 |
| 原理和工作流程 | Vue 3 仅使用 `Promise.resolve().then()`（微任务）实现，无降级策略（Vue 2 曾使用降级链）。 |
| 缺点 | 过度使用增加代码复杂度。 |

### 11. Vue 3 Diff 算法的优化不包括以下哪项

| 维度 | 内容 |
|------|------|
| 是什么 | Vue 3 Diff 优化包括静态标记（PatchFlag）、静态提升（HoistStatic）、Block Tree 和事件缓存（cacheHandlers），不包括 Fiber 架构（Fiber 是 React 的特性）。 |
| 能做什么 | 区分 Vue 3 和 React 的架构差异，理解各自的核心优化方向。 |
| 怎么用 | 编译期自动优化，开发者无需手动配置。 |
| 原理和工作流程 | PatchFlag 标记动态内容类型；HoistStatic 提升静态节点；Block Tree 收集动态节点；cacheHandlers 缓存事件函数。 |
| 缺点 | 需要区分 Vue 和 React 的不同优化策略。 |

### 12. Vue 3 的静态提升（HoistStatic）是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 将静态节点提升到 render 函数外部，避免每次渲染重复创建 VNode，直接复用已有的 VNode。 |
| 能做什么 | 减少 VNode 创建开销，提升渲染性能。 |
| 怎么用 | 编译期自动优化，开发者无需手动操作。 |
| 原理和工作流程 | 编译器识别纯静态节点，将其 VNode 创建移到 render 函数外部，渲染时直接引用。 |
| 缺点 | 对于几乎全是动态内容的模板，优化效果有限。 |

### 13. 关于 provide/inject 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | provide/inject 用于跨层级组件通信，父组件（祖先组件）通过 provide 提供数据，任意后代组件通过 inject 获取数据。 |
| 能做什么 | 避免 props 逐层传递（prop drilling），实现跨层级数据共享。 |
| 怎么用 | `provide('theme', theme); const theme = inject('theme', 'light')`。 |
| 原理和工作流程 | 依赖注入机制，inject 的数据是否响应式取决于 provide 提供的数据是否是响应式数据。 |
| 缺点 | 数据流向不直观，追踪数据来源较困难。 |

### 14. Vue 3 生命周期中，setup 替代了 Vue 2 的哪些钩子

| 维度 | 内容 |
|------|------|
| 是什么 | setup 函数在 beforeCreate 和 created 之前执行，替代了这两个钩子；其他钩子仍有对应的 onXxx 形式。 |
| 能做什么 | 在 setup 中直接编写 Composition API 代码，不需要 beforeCreate 或 created。 |
| 怎么用 | `onMounted(() => { ... }); onUnmounted(() => { ... })`。 |
| 原理和工作流程 | setup 在组件初始化时最先执行，beforeCreate 和 created 中的逻辑可直接写在 setup 中。 |
| 缺点 | 从 Options API 迁移时需要适应新的生命周期钩子命名。 |

### 15. Vue 3 编译器优化的 Block Tree 是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 将动态节点收集到 `dynamicChildren` 数组中，Diff 时只对比动态节点，跳过所有静态节点。 |
| 能做什么 | 大幅减少 Diff 的时间复杂度，尤其对于大部分静态内容、少量动态内容的模板效果显著。 |
| 怎么用 | 编译期自动优化。 |
| 原理和工作流程 | `createBlock` 在创建 VNode 时收集动态子节点到 `dynamicChildren`；Diff 时直接从 `dynamicChildren` 获取需要对比的节点。 |
| 缺点 | 对于几乎全是动态内容的模板，优化效果有限。 |

## 三、场景设计题（5 题，附思路）

### 1. 设计一个权限管理系统

| 维度 | 内容 |
|------|------|
| 是什么 | 动态路由 + 按钮级权限控制：基础路由预定义，登录后根据后端返回的角色权限动态添加路由；按钮级权限通过自定义指令 `v-permission` 控制。 |
| 能做什么 | 实现按角色展示不同菜单和页面；控制按钮级别的操作权限（增删改查）。 |
| 怎么用 | `router.addRoute(route)` 动态添加路由；`app.directive('permission', { mounted(el, binding) { if (!hasPermission(binding.value)) el.parentNode?.removeChild(el) } })`。 |
| 原理和工作流程 | 动态路由表预先定义所有可能的路由，登录后根据权限筛选并动态注册；v-permission 指令在 mounted 时检查权限，无权限则移除 DOM 元素。 |
| 缺点 | 前端权限控制只是 UI 层拦截，后端仍需校验。 |

### 2. 设计一个通用表格组件

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 props 配置列（columns），支持排序、筛选、分页和自定义列渲染（插槽或 render 函数），通过 emit 通知父组件处理数据变化。 |
| 能做什么 | 实现一次开发、多处复用的表格组件，减少重复代码。 |
| 怎么用 | `const columns = [{ key: 'name', title: '姓名', sortable: true }, { key: 'action', title: '操作', render: (row) => h(Button, { onClick: () => edit(row) }, '编辑') }]`。 |
| 原理和工作流程 | 列配置驱动表格渲染；排序和筛选通过 emit 通知父组件处理；分页使用独立分页组件；自定义列通过插槽或 render 函数实现。 |
| 缺点 | 列配置过于复杂时维护成本高。 |

### 3. 设计一个低代码表单设计器

| 维度 | 内容 |
|------|------|
| 是什么 | 三栏布局（组件面板 + 画布 + 属性面板），JSON Schema 驱动表单定义，支持拖拽生成表单和属性配置。 |
| 能做什么 | 实现可视化表单搭建，通过 JSON Schema 存储和传输表单配置，渲染器根据 Schema 动态渲染。 |
| 怎么用 | `const formSchema = { fields: [{ id: 'f1', type: 'input', label: '用户名', key: 'username', required: true }], layout: 'vertical' }`。 |
| 原理和工作流程 | 拖拽组件到画布时生成新的字段配置；属性面板修改选中组件的配置；JSON Schema 序列化后存储或传输；渲染器遍历 fields 动态渲染对应组件。 |
| 缺点 | 拖拽交互实现复杂，需要考虑移动端适配和复杂校验规则。 |

### 4. 设计一个全局 Loading 和错误处理方案

| 维度 | 内容 |
|------|------|
| 是什么 | Pinia 管理 loading 状态，HTTP 请求拦截器自动显示/隐藏 loading；全局错误处理通过 `app.config.errorHandler` 和响应拦截器统一处理。 |
| 能做什么 | 统一管理应用中的加载状态和错误提示，避免每个组件单独处理。 |
| 怎么用 | `const loadingStore = useLoadingStore(); loadingStore.show('加载中...'); loadingStore.hide()`；`app.config.errorHandler = (err, instance, info) => { reportError(err); ElMessage.error('操作失败') }`。 |
| 原理和工作流程 | 请求拦截器中调用 show 增加计数器，响应拦截器中调用 hide 减少计数器，计数器为 0 时隐藏 loading；errorHandler 捕获未处理的组件错误并统一上报。 |
| 缺点 | 全局错误处理可能掩盖具体错误信息；Loading 计数器逻辑需要处理并发请求场景。 |

### 5. 设计一个前端微前端架构

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 qiankun 或 Module Federation 的微前端架构：主应用注册子应用，子应用独立开发部署，暴露生命周期钩子。 |
| 能做什么 | 实现多团队并行开发、独立部署；技术栈无关（子应用可用不同框架）；增量升级。 |
| 怎么用 | `registerMicroApps([{ name: 'app-vue', entry: '//localhost:8081', container: '#subapp', activeRule: '/app-vue' }]); start()`。 |
| 原理和工作流程 | qiankun 基于 single-spa，通过 fetch 获取子应用 HTML 并解析 JS/CSS，在沙箱中执行；CSS 隔离通过 Shadow DOM 或 CSS Scope；JS 沙箱通过 Proxy 实现。 |
| 缺点 | 子应用间通信、样式隔离、公共依赖共享和版本管理是主要挑战。 |
