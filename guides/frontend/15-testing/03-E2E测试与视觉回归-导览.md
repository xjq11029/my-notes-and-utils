# 03-E2E测试与视觉回归 - 导览

---

## 1.1 E2E 测试的定位（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | E2E 测试验证从用户视角出发的完整业务流程，位于测试金字塔顶层，占比 5-10%，用消防演习类比——不测试每个房间但确保逃生路线畅通 |
| 能做什么 | 验证关键用户路径不被破坏（如注册→登录→浏览→加购→下单→支付）；发现跨模块、跨页面的集成问题 |
| 怎么用 | 识别核心业务流程 → 定义 E2E 测试场景 → 使用 Playwright/Cypress 编写自动化脚本 → 集成到 CI/CD 流水线 |
| 原理和工作流程 | 真实浏览器启动 → 访问页面 → 模拟用户操作序列 → 断言页面状态和 URL → 验证业务流程完整性 |
| 缺点 | 执行速度慢（分钟级）；维护成本高；不稳定（flaky tests）；问题定位困难；不应该覆盖非关键路径和边界条件 |

---

## 1.2 Playwright vs Cypress 对比（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Playwright（Microsoft）和 Cypress（Cypress.io）是当前最主流的两大 E2E 测试框架，各有侧重 |
| 能做什么 | Playwright 适合跨浏览器测试、多标签页、高并发、视觉回归；Cypress 适合单浏览器测试、需要友好调试体验、Dashboard 服务 |
| 怎么用 | Playwright: pnpm create playwright 初始化 → 编写 spec 文件 → pnpm exec playwright test；Cypress: pnpm exec cypress open 启动 → 编写 spec 文件 → pnpm exec cypress run |
| 原理和工作流程 | Playwright 通过 CDP 协议控制浏览器，采用三层架构（Browser Server → Browser Context → Page）；Cypress 运行在浏览器内部，直接操作 DOM |
| 缺点 | Playwright 调试体验不如 Cypress（Time Travel）；Cypress 不支持多标签页和 Safari，串行执行速度较慢 |

---

## 1.3 视觉回归测试（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 视觉回归测试通过截图对比自动检测 UI 的意外变化，适用于设计系统组件库、多语言/多主题 UI 一致性验证、响应式布局断点验证 |
| 能做什么 | 自动发现重构后的样式回归；确保设计系统的组件在不同状态下外观一致；验证多语言版本的 UI 布局 |
| 怎么用 | 首次运行生成基准截图 → 后续运行生成新截图 → 使用 pixelmatch 逐像素对比 → 差异超过阈值则失败 |
| 原理和工作流程 | page.screenshot() 生成 PNG → 存储到 __screenshots__/ → 后续运行对比 → 差异区域红色高亮 → 人工确认或更新 |
| 缺点 | 对动态内容敏感（时间、随机推荐）；不同操作系统/浏览器版本可能导致像素级差异；需要维护基准截图文件 |

## 2.1 Playwright 架构（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Playwright 采用三层架构：Browser Server（浏览器进程）→ Browser Context（独立会话，类似无痕窗口）→ Page（标签页），层次分明 |
| 能做什么 | Browser Context 提供独立会话隔离（cookies、localStorage 互不影响）；多个 Context 可并行创建和销毁，比创建新浏览器进程快得多 |
| 怎么用 | chromium.launch() 创建 Browser Server → browser.newContext() 创建独立会话 → context.newPage() 创建标签页 |
| 原理和工作流程 | Browser Server 通过 CDP 协议与浏览器通信 → 每个 Context 是独立的浏览器会话 → 不同 Context 间完全隔离 → Page 是 Context 下的标签页 |
| 缺点 | 三层架构的概念对初学者有一定学习曲线；Context 之间的状态不共享需要用 storageState 手动传递 |

---

## 2.2 自动等待机制（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Playwright 在执行每个操作前自动执行"可操作性检查"（actionability checks），包括 5 个条件：DOM 存在、可见、稳定、可接收事件、已启用 |
| 能做什么 | 消除手动等待代码（如 waitForTimeout、sleep）；大幅减少 flaky tests；提升测试代码的可读性和可维护性 |
| 怎么用 | 无需额外配置，所有操作（click、fill、selectOption）自动等待；可通过 actionTimeout 配置超时时间 |
| 原理和工作流程 | 操作前自动轮询检查元素状态 → 满足所有 5 个条件后执行操作 → 超时未满足则抛出 TimeoutError |
| 缺点 | 自动等待不能解决所有等待问题（如等待网络请求完成仍需 waitForResponse）；轮询检查有性能开销 |

---

## 2.3 视觉回归原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 视觉回归测试使用 pixelmatch 库进行逐像素对比，通过阈值（maxDiffPixels/maxDiffPixelRatio/threshold）控制灵敏度 |
| 能做什么 | 像素级检测 UI 变化；生成差异高亮图（红色标记差异区域）；支持 mask 遮挡动态区域 |
| 怎么用 | toHaveScreenshot() 截图对比 → 配置 maxDiffPixelRatio 和 mask → 首次运行生成基准 → 后续运行对比 |
| 原理和工作流程 | 截图生成 PNG → pixelmatch 逐像素对比 RGB 值 → 统计差异像素数 → 与阈值对比 → 生成差异报告 |
| 缺点 | 对渲染环境敏感（操作系统字体、抗锯齿算法）；动态内容需要额外处理；PNG 基准文件占用存储空间 |

## 2.4 CI 集成（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 在 GitHub Actions 等 CI 平台中配置 Playwright 的自动化测试流水线，使用官方 Docker 镜像和多浏览器并行矩阵 |
| 能做什么 | 每次 PR 自动运行全浏览器 E2E 测试；失败时自动上传截图、视频、Trace；通过 retries 减少 flaky tests 的影响 |
| 怎么用 | 配置 GitHub Actions workflow → 使用 strategy.matrix 实现多浏览器并行 → 安装 Playwright 浏览器 → 运行测试 → 上传 artifact |
| 原理和工作流程 | CI 触发 → 启动 Docker 容器 → 安装依赖和浏览器 → 并行执行测试 → 收集结果 → 上传报告和截图 |
| 缺点 | CI 执行时间较长（E2E 测试本身慢）；Docker 镜像体积大；需要额外配置缓存和并行策略 |

## 3.1 Playwright 入门（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Playwright 入门示例：登录测试（getByLabel + getByRole + click + toHaveURL）、表单测试（fill + check + 校验断言）、页面导航测试（link + toHaveURL + 面包屑） |
| 能做什么 | 快速上手 Playwright 的基本 API；理解 page 对象的核心方法；掌握 E2E 测试的编写模式 |
| 怎么用 | test('用例名', async ({ page }) => { await page.goto('/'); ... }) → 使用 page.getByRole/getByLabel 定位 → 使用 page.click/fill 交互 → 使用 expect 断言 |
| 原理和工作流程 | 每个 test 块创建独立的 Browser Context 和 Page → 测试代码通过 Page 对象与浏览器交互 → 测试结束后自动清理 |
| 缺点 | 入门示例较简单，实际项目中需要处理登录态、测试数据管理和测试隔离 |

## 3.2 E2E 场景设计（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的电商购物 E2E 流程设计：注册 → 登录 → 浏览商品 → 搜索 → 加入购物车 → 修改数量 → 下单 → 支付 → 查看订单，6 个步骤串行执行 |
| 能做什么 | 验证电商核心业务流程的完整性；提供可复用的 E2E 场景模板；展示 test.describe.configure({ mode: 'serial' }) 串行依赖测试 |
| 怎么用 | 使用 serial 模式确保步骤依赖 → 每个步骤独立 test → 使用 storageState 保存登录态 → 逐步断言页面状态 |
| 原理和工作流程 | 步骤 1 注册 → 步骤 2 登录 → 步骤 3 浏览加购 → 步骤 4 修改购物车 → 步骤 5 下单 → 步骤 6 查看订单，形成完整链 |
| 缺点 | 串行测试执行时间长；一个步骤失败会导致后续步骤全部失败；需要维护测试数据的状态 |

## 3.3 视觉回归测试（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 Playwright 的 toHaveScreenshot 进行视觉回归测试：PC 端和移动端首页布局、商品详情页、按钮组件的各种状态、暗色主题 |
| 能做什么 | 自动检测重构后的样式回归；确保响应式设计在不同视口下的一致性；验证组件库的视觉一致性 |
| 怎么用 | page.setViewportSize 设置视口 → page.goto 访问页面 → page.waitForLoadState 等待渲染 → toHaveScreenshot 截图对比 |
| 原理和工作流程 | 截图 → 与基准对比 → 差异超过阈值失败 → 使用 --update-snapshots 更新基准 |
| 缺点 | 需要为不同主题、不同视口、不同状态分别维护截图基准；动态内容需要 mask 处理 |

## 3.4 测试报告（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Playwright 的 HTML Reporter（测试概览、步骤详情、截图、视频）和 Trace Viewer（DOM 快照、网络请求、时间线） |
| 能做什么 | 可视化分析测试结果；快速定位失败原因；通过 Trace 回放测试执行过程；自定义报告格式 |
| 怎么用 | 配置 reporter 选项 → 运行测试生成报告 → pnpm exec playwright show-report 查看 → 分析 Trace 定位问题 |
| 原理和工作流程 | 测试执行期间收集数据 → 生成 HTML/JSON/JUnit 报告 → Trace 记录每一步的 DOM 快照和网络请求 |
| 缺点 | Trace 文件体积大；HTML 报告在 CI 中需要额外配置才能查看；报告分析需要人工介入 |

## 补充：性能测试、CI 执行优化与契约测试

### 补1 性能测试（k6 与 Lighthouse CI）

| 维度 | 内容 |
|------|------|
| 是什么 | 性能测试分为负载/压力/冒烟/前端性能四类。k6 用 JavaScript 脚本对接口与服务端施压（运行在独立 JS 虚拟机中，无 DOM），Lighthouse CI 用 `@lhci/cli` 审计浏览器端页面质量并把性能变成 CI 门禁 |
| 能做什么 | k6 通过 `stages` / `scenarios` 描述负载模型，用 `thresholds` 断言 P95 延迟、失败率、check 通过率，阈值不满足时退出码非 0 可直接作为门禁；Lighthouse CI 用 `assertions` 断言性能分、LCP、CLS、TBT，`numberOfRuns` 取中位数降低波动 |
| 怎么用 | k6：`export const options = { stages, thresholds }` + `export default function(){ http.get(...); check(...); sleep(1) }`，用 `k6 run` 执行；Lighthouse：写 `lighthouserc.json`（`collect.url` + `assert.assertions` + `upload`），用 `lhci autorun` 一步完成采集、断言、上传 |
| 原理和工作流程 | k6 按执行器模型产生负载（VU 模型或到达率模型）→ 记录内置指标与自定义 Trend → 与阈值比对决定退出码；Lighthouse 在无头浏览器中加载页面并采集性能轨迹 → 多次运行取中位数 → 按断言配置输出 `error` / `warn`；性能回归通过与 main 分支基线对比指标变化率来判定 |
| 缺点 | k6 无法测浏览器渲染指标（LCP/CLS）；VU 模型下服务端变慢会导致 QPS 自动下降、掩盖问题；Lighthouse 单次波动可达 ±5 分，必须多次运行；基线对比要求两次运行环境完全一致，否则结论无效 |

### 补2 CI 中的测试执行优化

| 维度 | 内容 |
|------|------|
| 是什么 | 四类优化手段：测试分片并行（`--shard`）、增量测试选择（按变更文件决定跑哪些测试）、缓存与产物复用（依赖/浏览器/构建产物）、Flaky 测试的识别与治理 |
| 能做什么 | 用分片把 E2E 从串行的十几分钟压缩到几分钟；用增量选择把 PR 反馈时间降到秒级；用缓存与 artifact 省去重复安装与构建；用 flaky rate 度量并持续降低不稳定用例 |
| 怎么用 | `playwright test --shard=1/4` 配合 CI matrix + blob reporter + `merge-reports` 合并报告；`jest --findRelatedTests` / `vitest related` / `nx affected` / `turbo --filter='...[origin/main]'` 做增量；缓存 key 必须包含 lockfile 哈希；构建产物用 `upload-artifact` / `download-artifact` 在 job 间传递 |
| 原理和工作流程 | 分片按文件静态拆分，报告必须合并后再判定；增量选择基于模块依赖图反查受影响测试，因此对隐式依赖会漏判，只用于 PR 快速反馈，主干与合并队列跑全量；Flaky 治理流程为"检测（重试标记 + `--repeat-each` + 历史失败率）→ 隔离（打标移出阻断队列）→ 修复（按根因分类）→ 回归" |
| 缺点 | 分片数过大时调度与浏览器启动开销抵消收益；缓存 key 设计不当会命中过期依赖；增量测试存在漏测风险，配置/依赖变更时必须强制全量；重试会掩盖真实竞态并延长 CI 时间；Flaky 治理需要长期投入与度量机制 |

### 补3 契约测试（消费者驱动契约）

| 维度 | 内容 |
|------|------|
| 是什么 | 验证服务消费者与提供者之间"接口约定是否一致"的测试，核心是消费者驱动契约（CDC）：由消费者定义期望（请求 + 期望响应结构），生成契约文件，提供者拉取契约并真实发起请求验证 |
| 能做什么 | 在 CI 中发现"后端改了字段导致前端渲染失败"这类问题；替代高成本联调；支持多消费者（Web / iOS / Android）共享同一提供者时的变更保护；通过 `can-i-deploy` 在部署前阻断破坏性变更 |
| 怎么用 | 消费者侧用 `@pact-foundation/pact` 的 `PactV3` 声明交互（`given` / `uponReceiving` / `withRequest` / `willRespondWith`），用匹配器（`like` / `eachLike` / `integer`）约束结构；生成契约后用 `pact-broker publish` 发布；提供者侧用 `Verifier` + `stateHandlers` 验证并回传结果；部署前执行 `pact-broker can-i-deploy` |
| 原理和工作流程 | 消费者测试运行时 Pact 启动 mock server，真实走一遍消费者的请求逻辑并校验其能处理响应 → 生成契约 JSON → 发布到 Broker（附消费者版本号）→ 提供者按 `provider states` 准备数据、重放请求、比对响应 → 结果发布到 Broker → 门禁查询"消费者期望 + 提供者验证"是否都通过 |
| 缺点 | 契约只约束接口约定，不验证业务流程、多接口协作与 UI，不能替代 E2E；需要 `provider states` 能准备数据，否则验证退化为空数据路径；接口快速原型阶段契约变更频繁、维护成本高于收益；没有 Broker 与部署门禁时契约会退化成一份本地文档 |
