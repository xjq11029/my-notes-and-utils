### 单元测试（3 题）

**1. 测试金字塔模型中，各层测试的理想占比从高到低应该是？**

A. E2E > 集成测试 > 组件测试 > 单元测试
B. 单元测试 > 组件测试 > 集成测试 > E2E
C. 组件测试 > 单元测试 > 集成测试 > E2E
D. 单元测试 > 集成测试 > 组件测试 > E2E

**答案：B**

**解析**：测试金字塔中，底层单元测试占比最大（50-60%），中层组件测试（20-30%），上层集成测试（10-15%），顶层 E2E（5-10%）。越底层的测试执行速度越快、维护成本越低、问题定位越精确。A 选项是"冰淇淋甜筒"反模式；C 选项颠倒了组件测试和单元测试的占比；D 选项颠倒了组件测试和集成测试的占比。

**2. 以下关于 vi.mock 的描述，正确的是？**

A. vi.mock 可以在测试用例内部动态调用
B. vi.mock 会被 hoisting 提升到文件顶部，确保模块在导入前被替换
C. vi.mock 只能替换默认导出，不能替换命名导出
D. vi.mock 的 mock 工厂函数中可以使用外部变量

**答案：B**

**解析**：vi.mock 会被 Vitest 自动 hoisting 提升到文件顶部，确保在模块导入之前完成替换。A 错误：vi.mock 必须在文件顶部声明（虽然可以写在任意位置，但会被提升）；C 错误：vi.mock 可以替换命名导出和默认导出；D 错误：由于 hoisting 机制，mock 工厂函数中不能使用外部变量（会报错），需要使用 vi.hoisted() 来声明可提升的变量。

**3. 测试覆盖率 100% 意味着什么？**

A. 代码完全没有 bug
B. 每一行代码都至少被执行过一次
C. 所有边界条件都被充分测试
D. 测试用例质量很高

**答案：B**

**解析**：100% 覆盖率只能保证每一行代码都被执行过，不能保证测试用例的质量（如断言是否正确）、边界条件是否充分覆盖、业务逻辑是否正确。A 错误：覆盖率与 bug 数量没有直接关系；C 错误：覆盖率不能反映边界条件测试的充分性；D 错误：覆盖率是数量指标，不是质量指标。

### 组件测试（3 题）

**4. Testing Library 中查询优先级最高的是？**

A. getByTestId
B. getByText
C. getByRole
D. getByLabelText

**答案：C**

**解析**：Testing Library 的查询优先级从高到低为：getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId。getByRole 最接近辅助技术（读屏软件）的查询方式，因此优先级最高。getByTestId 是纯开发者视角（用户无法感知 data-testid），优先级最低。

**5. 以下关于 userEvent 和 fireEvent 的描述，错误的是？**

A. userEvent.click 会触发完整的点击事件链（pointerdown → mousedown → focus → mouseup → click）
B. fireEvent 可以触发单个 DOM 事件
C. 所有组件测试都应该使用 userEvent 而非 fireEvent
D. fireEvent.change 会触发完整的 focus → blur 事件链

**答案：D**

**解析**：fireEvent.change 只触发 change 事件，不会触发 focus 和 blur 事件链。这是 fireEvent 的核心缺陷——缺少中间事件可能导致某些校验逻辑（如 onBlur 校验）未执行。A、B 正确；C 正确：几乎所有的组件测试都应该使用 userEvent，只有测试特定 DOM 事件处理时才使用 fireEvent。

**6. MSW（Mock Service Worker）在集成测试中的主要作用是？**

A. 替代 Vitest 的测试运行器
B. 在浏览器中拦截网络请求，返回 mock 数据
C. 自动生成测试代码
D. 收集测试覆盖率数据

**答案：B**

**解析**：MSW 在测试环境中通过 Service Worker（浏览器）或 Node.js 拦截器（Node.js 环境）拦截网络请求，返回 mock 数据。A 错误：MSW 不替代测试运行器；C 错误：MSW 不自动生成测试代码；D 错误：MSW 不收集覆盖率数据（覆盖率由 Istanbul/V8 负责）。

### E2E 测试（4 题）

**7. Playwright 的三层架构从底层到上层依次是？**

A. Page → Browser Context → Browser Server
B. Browser Server → Browser Context → Page
C. Browser Context → Page → Browser Server
D. Browser Server → Page → Browser Context

**答案：B**

**解析**：Playwright 的三层架构为：Browser Server（浏览器进程）→ Browser Context（独立会话，类似无痕窗口）→ Page（标签页）。Browser Server 是最底层，一个 Browser Server 可以创建多个 Browser Context，每个 Browser Context 可以创建多个 Page。

**8. 以下哪种场景最适合使用 E2E 测试？**

A. 验证购物车价格计算函数的所有边界条件
B. 验证注册到下单的完整用户流程
C. 验证登录按钮的禁用状态
D. 验证日期格式化函数的输出

**答案：B**

**解析**：E2E 测试验证关键用户路径的完整流程，如注册 → 浏览 → 加购 → 下单 → 支付。A 适合单元测试；C 适合组件测试；D 适合单元测试。E2E 测试不应覆盖所有边界条件和简单 UI 状态。

**9. Playwright 中 toHaveScreenshot 用于什么类型的测试？**

A. 单元测试
B. 组件测试
C. 视觉回归测试
D. 性能测试

**答案：C**

**解析**：toHaveScreenshot 是 Playwright 内置的视觉回归测试 API，用于截图对比检测 UI 变化。它通过 pixelmatch 进行逐像素对比，差异超过阈值时测试失败。A/B 错误：toHaveScreenshot 是 E2E 层面的 API，不属于单元测试或组件测试；D 错误：toHaveScreenshot 不测试性能指标。

**10. 以下关于 Playwright 自动等待机制，描述错误的是？**

A. page.click 会自动等待元素可见、可交互
B. 自动等待可以完全替代手动等待代码
C. page.fill 会自动等待元素可见、可编辑
D. 自动等待的超时时间可通过 actionTimeout 配置

**答案：B**

**解析**：自动等待不能完全替代手动等待代码。某些场景仍需手动等待，如等待网络请求完成（page.waitForResponse）、等待特定条件满足（page.waitForFunction）、等待元素从 DOM 中移除（page.waitForSelector('.loading', { state: 'hidden' })）等。A、C、D 都是正确的描述。

## 第二部分：简答题（共 8 题）

**Q1：请解释测试金字塔模型，并说明为什么应该遵循这个模型。**

**答案**：

测试金字塔是 Mike Cohn 提出的测试策略模型，将测试分为四层（从底层到顶层）：

1. **单元测试（50-60%）**：测试单个函数或模块，执行速度最快（毫秒级），维护成本最低，问题定位最精确
2. **组件测试（20-30%）**：测试单个组件的 UI 交互，从用户视角验证组件行为
3. **集成测试（10-15%）**：测试多个组件/模块的协作流程，验证数据流转和状态同步
4. **E2E 测试（5-10%）**：验证完整用户路径，从真实浏览器角度测试业务流程

**遵循原因**：
- 底层测试执行快、维护成本低、问题定位精确，投入产出比最高
- 上层测试执行慢、维护成本高、不稳定，数量应严格控制
- 反模式"冰淇淋甜筒"（大量 E2E + 少量单元测试）会导致 CI 时间过长、测试不稳定、开发效率下降
- 金字塔模型确保"快速反馈"和"精确诊断"的平衡

> 📖 **参考链接**：
> - [测试金字塔 - Martin Fowler](https://martinfowler.com/articles/practical-test-pyramid.html)

**Q2：Vitest 相比 Jest 有哪些核心优势？在什么场景下应该选择 Vitest 而非 Jest？**

**答案**：

**核心优势**：
1. 与 Vite 共享配置（resolve.alias、插件、CSS 处理），无需维护两套构建配置
2. 原生 ESM 支持，无需额外配置 TypeScript（无需 ts-jest）
3. HMR 测试运行——watch 模式下只重跑受影响的测试文件
4. 浏览器模式——支持在真实浏览器中运行测试
5. 速度更快——基于 ESBuild 转译，比 Babel 更快
6. API 兼容 Jest——从 Jest 迁移成本低

**选择 Vitest 的场景**：
- 项目使用 Vite 作为构建工具
- 新项目启动，无历史包袱
- 需要 HMR 测试运行提升开发体验
- 需要浏览器模式进行布局/样式测试

**选择 Jest 的场景**：
- 项目使用 Webpack/CRA，且无迁移计划
- 大量现有 Jest 测试用例和自定义插件
- 团队对 Jest 生态更熟悉

> 📖 **参考链接**：
> - [Vitest 官方文档](https://cn.vitest.dev/guide/)
> - [从 Jest 迁移到 Vitest](https://cn.vitest.dev/guide/migration.html)

**Q3：请说明 Testing Library 查询优先级的设计原理，以及为什么 getByRole 优先级最高。**

**答案**：

**查询优先级（从高到低）**：
getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId

**设计原理**：查询优先级遵循"越接近用户交互方式，优先级越高"原则。用盲人使用读屏软件类比——读屏软件通过 ARIA Role 理解页面元素，getByRole 正是模拟这种交互方式。

**getByRole 优先级最高的原因**：
1. 最接近辅助技术（读屏软件）的查询方式
2. 强制开发者编写可访问性更好的组件（需要正确的 ARIA role）
3. 查询结果最稳定（不因文本内容或 DOM 结构调整而变化）
4. 符合 W3C WAI-ARIA 规范，是 Web 可访问性的最佳实践

**getByTestId 优先级最低的原因**：
- test-id 是纯开发者视角，用户无法感知
- 过度使用 test-id 会降低测试的可维护性
- 仅作为"最后手段"，当其他查询方式都无法使用时才使用

> 📖 **参考链接**：
> - [Testing Library 官方文档](https://testing-library.com/docs/)

**Q4：userEvent 和 fireEvent 的核心区别是什么？请举例说明为什么 userEvent 更推荐使用。**

**答案**：

**核心区别**：
- fireEvent：仅触发单个 DOM 事件，不模拟完整的用户操作序列
- userEvent：模拟真实用户的完整操作序列，触发完整的事件链

**userEvent 更推荐的原因（举例说明）**：

```typescript
// 场景：表单输入框有 onBlur 校验
// 用户输入后点击外部区域，触发 onBlur 校验

// fireEvent 方式——缺少 focus 和 blur 事件
fireEvent.change(input, { target: { value: 'test' } });
// onBlur 校验未触发，bug 被遗漏！

// userEvent 方式——完整的 focus → input → blur 事件链
await userEvent.click(input);        // 触发 focus
await userEvent.keyboard('test');    // 触发 keydown → input → keyup
await userEvent.click(outside);      // 触发 blur
// onBlur 校验正常触发，bug 可被发现
```

**事件链对比**：
- userEvent.click：pointerdown → mousedown → focus → mouseup → click
- userEvent.type：focus → keydown → input → keyup（每输入一个字符重复），change（失焦时触发一次）
- fireEvent.click：仅触发 click

**Q5：请描述 MSW 的工作原理，以及它在测试中的三种核心使用场景。**

**答案**：

**MSW 工作原理**：
- 浏览器环境：通过注册 Service Worker 拦截所有网络请求（fetch、XMLHttpRequest）
- Node.js 测试环境：通过拦截 globalThis.fetch 和 XMLHttpRequest 实现
- Handler 匹配：根据请求 URL 和方法匹配到对应的 handler，返回 mock 响应

**三种核心使用场景**：

1. **API 层单元测试**：使用 setupServer 拦截 fetch 请求，测试 API 函数在成功/失败/超时场景下的行为，不依赖真实后端
2. **组件集成测试**：组件渲染后自动发送请求，MSW 返回 mock 数据，组件按正常流程更新 UI，验证完整的数据加载 → 渲染 → 交互流程
3. **开发环境 Mock**：使用 setupWorker 在浏览器中启用 Service Worker，开发时使用 mock 数据替代未完成的后端 API，前后端并行开发

**优势**：同一套 handler 可用于开发、测试、Storybook 三种场景，无需修改任何业务代码。

**Q6：Playwright 的自动等待机制是如何工作的？列举 3 种自动等待无法覆盖的场景。**

**答案**：

**自动等待机制**：
Playwright 在执行每个操作前自动执行"可操作性检查"（actionability checks），包括：
1. 元素是否存在于 DOM 中
2. 元素是否可见（非 hidden、opacity > 0）
3. 元素是否稳定（动画完成、未在移动中）
4. 元素是否接收事件（未被其他元素遮挡）
5. 元素是否已启用（非 disabled）

**3 种自动等待无法覆盖的场景**：

1. **等待网络请求完成**：需要手动使用 page.waitForResponse 等待特定 API 请求返回
2. **等待特定业务状态**：如"等待商品列表加载完成"——需要 page.waitForFunction 检查 DOM 中的特定数据
3. **等待元素从 DOM 中移除**：如 loading 动画消失——需要 page.waitForSelector('.loading', { state: 'hidden' })

**Q7：视觉回归测试的原理是什么？如何处理包含动态内容的页面？**

**答案**：

**原理**：
1. 首次运行：为每个测试用例生成基准截图（baseline），存储为 PNG 文件
2. 后续运行：生成新截图，使用 pixelmatch 库进行逐像素对比
3. 差异检测：统计差异像素数量，与阈值（maxDiffPixels、maxDiffPixelRatio）对比
4. 失败处理：差异超过阈值时测试失败，生成差异高亮图（红色标记差异区域）

**处理动态内容的方法**：

1. **mask 遮挡**：使用 mask 参数遮挡动态区域（如 `mask: [page.locator('.timestamp')]`），被遮挡区域不参与像素对比
2. **注入 CSS 隐藏**：在截图前通过 page.addStyleTag 注入 CSS，隐藏动画和动态元素
3. **固定测试数据**：使用固定的时间戳、固定的用户数据、固定的随机种子
4. **合理设置阈值**：设置 maxDiffPixelRatio = 0.01（允许 1% 的像素差异），容忍微小的渲染差异
5. **使用稳定环境**：在 CI 中使用 Playwright Docker 镜像，确保字体和渲染环境一致

> 📖 **参考链接**：
> - [Playwright 视觉回归测试](https://playwright.dev/docs/test-snapshots)

**Q8：请描述一个完整的前端测试策略，涵盖从单元测试到 E2E 测试的各个层级，以及它们之间的分工。**

**答案**：

**测试策略设计**：

| 层级 | 测试对象 | 工具 | 覆盖内容 | 占比 |
|---|---|---|---|---|
| 单元测试 | 纯函数、工具函数、Store | Vitest | 业务逻辑、边界条件、异常处理 | 50-60% |
| 组件测试 | 单个 UI 组件 | Vitest + Testing Library | 渲染结果、用户交互、状态变化 | 20-30% |
| 集成测试 | 多组件协作流程 | Vitest + Testing Library + MSW | 数据流转、路由跳转、API 交互 | 10-15% |
| E2E 测试 | 关键用户路径 | Playwright | 完整业务流程、跨页面交互 | 5-10% |
| 视觉回归 | UI 组件、页面布局 | Playwright toHaveScreenshot | 样式回归、响应式设计 | 作为 E2E 补充 |

**分工原则**：
- 单元测试：覆盖所有业务逻辑的边界条件和异常处理，追求"快"和"全"
- 组件测试：覆盖组件的所有交互状态（正常、加载、错误、空、禁用），追求"用户视角"
- 集成测试：覆盖核心业务流程的数据流转，验证模块协作
- E2E 测试：只覆盖关键用户路径（2-5 条），追求"稳"和"精"
- 视觉回归：覆盖设计系统组件和关键页面布局，防止样式回归

**CI 执行策略**：
- 单元测试和组件测试在 pre-commit hook 中执行（< 30 秒）
- 集成测试在 PR 合并前执行（< 2 分钟）
- E2E 测试和视觉回归在 main 分支合并后执行（< 15 分钟，多浏览器并行）

**Q5：视觉回归方案——为设计系统组件库设计视觉回归测试方案**

**场景**：你的团队维护一个企业级设计系统组件库（包含 50+ 组件），需要保证每次发布前所有组件的视觉一致性。请设计视觉回归测试方案。

**答案要点**：

**方案设计**：

```typescript
// 1. 测试架构
// 为每个组件创建视觉回归测试页面（Storybook + Playwright）

// 组件测试页面（Storybook 或独立页面）
// /visual-tests/button.html
// 包含按钮的所有状态变体
// - 类型：primary / secondary / danger / ghost / link
// - 大小：small / medium / large
// - 状态：normal / hover / active / disabled / loading
// - 主题：light / dark

// 2. Playwright 测试脚本
test.describe('Button 组件视觉回归', () => {
  test('所有按钮变体', async ({ page }) => {
    await page.goto('/visual-tests/button');
    await page.waitForLoadState('networkidle');

    // 截图整个测试页面
    await expect(page).toHaveScreenshot('button-all-variants.png', {
      fullPage: true,
      maxDiffPixelRatio: 0.005,
    });
  });

  test('暗色主题下的按钮', async ({ page }) => {
    await page.goto('/visual-tests/button?theme=dark');
    await page.waitForSelector('[data-theme="dark"]');

    await expect(page).toHaveScreenshot('button-dark-theme.png', {
      fullPage: true,
    });
  });

  test('不同视口下的按钮', async ({ page }) => {
    await page.setViewportSize({ width: 320, height: 800 });
    await page.goto('/visual-tests/button');

    await expect(page).toHaveScreenshot('button-mobile.png', {
      fullPage: true,
    });
  });
});

// 3. CI 集成
// - 每次 PR 运行所有组件的视觉回归测试
// - 失败时在 PR 评论中自动贴出差异图
// - 使用 Playwright Sharding 将 50+ 组件分配给多个 CI worker 并行执行

// 4. 阈值策略
// - 组件级阈值：maxDiffPixelRatio = 0.005（严格）
// - 页面级阈值：maxDiffPixelRatio = 0.01（宽松）
// - 跨浏览器阈值：maxDiffPixelRatio = 0.02（最宽松，因字体渲染差异）

// 5. 动态内容处理
// - 使用固定时间戳替代动态时间
// - loading 组件使用 CSS animation: none 禁用动画
// - 使用 mask 遮挡不稳定的第三方组件（如地图、视频播放器）
```

**实施策略**：
1. 先为核心组件（Button、Input、Modal、Table）建立视觉回归
2. 逐步扩展到全部 50+ 组件
3. 在 CI 中使用 Sharding 并行执行，控制在 10 分钟内
4. 建立基准截图更新流程（需 Designer Review 确认）
5. 视觉回归测试只作为 E2E 测试的补充，不替代行为测试
