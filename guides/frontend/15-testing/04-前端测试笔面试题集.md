### 单元测试（3 题）

**1. ★ 测试金字塔模型中，各层测试的理想占比从高到低应该是？**

A. E2E > 集成测试 > 组件测试 > 单元测试
B. 单元测试 > 组件测试 > 集成测试 > E2E
C. 组件测试 > 单元测试 > 集成测试 > E2E
D. 单元测试 > 集成测试 > 组件测试 > E2E

**答案：B**

**解析**：测试金字塔中，底层单元测试占比最大（50-60%），中层组件测试（20-30%），上层集成测试（10-15%），顶层 E2E（5-10%）。越底层的测试执行速度越快、维护成本越低、问题定位越精确。A 选项是"冰淇淋甜筒"反模式；C 选项颠倒了组件测试和单元测试的占比；D 选项颠倒了组件测试和集成测试的占比。

**2. ★★ 以下关于 vi.mock 的描述，正确的是？**

A. vi.mock 可以在测试用例内部动态调用
B. vi.mock 会被 hoisting 提升到文件顶部，确保模块在导入前被替换
C. vi.mock 只能替换默认导出，不能替换命名导出
D. vi.mock 的 mock 工厂函数中可以使用外部变量

**答案：B**

**解析**：vi.mock 会被 Vitest 自动 hoisting 提升到文件顶部，确保在模块导入之前完成替换。A 错误：vi.mock 必须在文件顶部声明（虽然可以写在任意位置，但会被提升）；C 错误：vi.mock 可以替换命名导出和默认导出；D 错误：由于 hoisting 机制，mock 工厂函数中不能使用外部变量（会报错），需要使用 vi.hoisted() 来声明可提升的变量。

**3. ★ 测试覆盖率 100% 意味着什么？**

A. 代码完全没有 bug
B. 每一行代码都至少被执行过一次
C. 所有边界条件都被充分测试
D. 测试用例质量很高

**答案：B**

**解析**：100% 覆盖率只能保证每一行代码都被执行过，不能保证测试用例的质量（如断言是否正确）、边界条件是否充分覆盖、业务逻辑是否正确。A 错误：覆盖率与 bug 数量没有直接关系；C 错误：覆盖率不能反映边界条件测试的充分性；D 错误：覆盖率是数量指标，不是质量指标。

### 组件测试（3 题）

**4. ★★ Testing Library 中查询优先级最高的是？**

A. getByTestId
B. getByText
C. getByRole
D. getByLabelText

**答案：C**

**解析**：Testing Library 的查询优先级从高到低为：getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId。getByRole 最接近辅助技术（读屏软件）的查询方式，因此优先级最高。getByTestId 是纯开发者视角（用户无法感知 data-testid），优先级最低。

**5. ★★ 以下关于 userEvent 和 fireEvent 的描述，错误的是？**

A. userEvent.click 会触发完整的点击事件链（pointerdown → mousedown → focus → mouseup → click）
B. fireEvent 可以触发单个 DOM 事件
C. 所有组件测试都应该使用 userEvent 而非 fireEvent
D. fireEvent.change 会触发完整的 focus → blur 事件链

**答案：D**

**解析**：fireEvent.change 只触发 change 事件，不会触发 focus 和 blur 事件链。这是 fireEvent 的核心缺陷——缺少中间事件可能导致某些校验逻辑（如 onBlur 校验）未执行。A、B 正确；C 正确：几乎所有的组件测试都应该使用 userEvent，只有测试特定 DOM 事件处理时才使用 fireEvent。

**6. ★★ MSW（Mock Service Worker）在集成测试中的主要作用是？**

A. 替代 Vitest 的测试运行器
B. 在浏览器中拦截网络请求，返回 mock 数据
C. 自动生成测试代码
D. 收集测试覆盖率数据

**答案：B**

**解析**：MSW 在测试环境中通过 Service Worker（浏览器）或 Node.js 拦截器（Node.js 环境）拦截网络请求，返回 mock 数据。A 错误：MSW 不替代测试运行器；C 错误：MSW 不自动生成测试代码；D 错误：MSW 不收集覆盖率数据（覆盖率由 Istanbul/V8 负责）。

### E2E 测试（4 题）

**7. ★★ Playwright 的三层架构从底层到上层依次是？**

A. Page → Browser Context → Browser Server
B. Browser Server → Browser Context → Page
C. Browser Context → Page → Browser Server
D. Browser Server → Page → Browser Context

**答案：B**

**解析**：Playwright 的三层架构为：Browser Server（浏览器进程）→ Browser Context（独立会话，类似无痕窗口）→ Page（标签页）。Browser Server 是最底层，一个 Browser Server 可以创建多个 Browser Context，每个 Browser Context 可以创建多个 Page。

**8. ★ 以下哪种场景最适合使用 E2E 测试？**

A. 验证购物车价格计算函数的所有边界条件
B. 验证注册到下单的完整用户流程
C. 验证登录按钮的禁用状态
D. 验证日期格式化函数的输出

**答案：B**

**解析**：E2E 测试验证关键用户路径的完整流程，如注册 → 浏览 → 加购 → 下单 → 支付。A 适合单元测试；C 适合组件测试；D 适合单元测试。E2E 测试不应覆盖所有边界条件和简单 UI 状态。

**9. ★★ Playwright 中 toHaveScreenshot 用于什么类型的测试？**

A. 单元测试
B. 组件测试
C. 视觉回归测试
D. 性能测试

**答案：C**

**解析**：toHaveScreenshot 是 Playwright 内置的视觉回归测试 API，用于截图对比检测 UI 变化。它通过 pixelmatch 进行逐像素对比，差异超过阈值时测试失败。A/B 错误：toHaveScreenshot 是 E2E 层面的 API，不属于单元测试或组件测试；D 错误：toHaveScreenshot 不测试性能指标。

**10. ★★ 以下关于 Playwright 自动等待机制，描述错误的是？**

A. page.click 会自动等待元素可见、可交互
B. 自动等待可以完全替代手动等待代码
C. page.fill 会自动等待元素可见、可编辑
D. 自动等待的超时时间可通过 actionTimeout 配置

**答案：B**

**解析**：自动等待不能完全替代手动等待代码。某些场景仍需手动等待，如等待网络请求完成（page.waitForResponse）、等待特定条件满足（page.waitForFunction）、等待元素从 DOM 中移除（page.waitForSelector('.loading', { state: 'hidden' })）等。A、C、D 都是正确的描述。

### 补充：性能测试与 CI 执行优化（5 题）

**11. ★★ 关于 k6 与 Lighthouse CI 的分工，以下说法正确的是？**

A. k6 可以测 LCP、CLS 等浏览器渲染指标
B. k6 的脚本运行在独立的 JS 虚拟机中，没有 DOM，因此只能测服务端 / 接口性能
C. Lighthouse CI 用于压测接口吞吐量
D. 两者都能替代真实用户监控（RUM）

**答案：B**

**解析**：
- A 错误：k6 没有 DOM、没有 `window`、没有浏览器渲染引擎，无法测 LCP / CLS 这类浏览器指标
- B 正确：k6 测的是服务端 / 接口性能；浏览器性能必须用 Lighthouse CI 或 RUM
- C 错误：Lighthouse CI 是页面质量审计与性能预算门禁，不做接口压测
- D 错误：实验室环境（Lighthouse）与协议级压测（k6）都不能替代真实用户监控，RUM 才能反映真实分布

**12. ★★★ k6 的 VU 模型与到达率模型（arrival-rate）的区别是？性能门禁建议用哪个？**

A. 两者等价，只是配置写法不同
B. VU 模型下"实际 QPS = VU 数 / 单次迭代耗时"，服务端变慢时压力自动减小；到达率模型坚持发出固定 QPS，更容易压出问题
C. 到达率模型无法控制 QPS
D. VU 模型更适合模拟真实用户行为

**答案：B**

**解析**：
- A 错误：两者的压力模型不同
- B 正确：VU 模型下服务端变慢 → 迭代耗时变长 → QPS 自动下降，形成"服务变慢导致压测变轻"的假象；到达率模型坚持固定 QPS，服务端变慢时 VU 会被堆积，更接近真实用户行为。**性能门禁建议用到达率模型**
- C 错误：`constant-arrival-rate` / `ramping-arrival-rate` 正是用来精确控制 QPS
- D 错误：到达率模型更接近真实用户的到达行为
- 补充：k6 的 `thresholds` 不满足时退出码非 0，可直接作为 CI 门禁；`abortOnFail` 可在阈值确定失败时提前终止，`delayAbortEval` 跳过预热阶段的抖动

**13. ★★ 关于 Lighthouse CI 的配置，以下做法错误的是？**

A. 设置 `numberOfRuns: 3` 取中位数，降低单次运行波动的影响
B. 核心指标（性能分、LCP、CLS）用 `error` 级别阻断合并，次要项用 `warn`
C. 使用 `preset: lighthouse:recommended` 打开官方推荐的全部断言
D. 为了让门禁稳定，把所有断言都设为 `error`

**答案：D**

**解析**：
- D 错误：把全部断言设为 `error` 会被无关项（图片格式、第三方脚本等）频繁阻断，导致门禁不可用；应核心指标 `error`、次要项 `warn`、不相关项 `off`
- A 正确：Lighthouse 单次运行波动较大（±5 分常见），多次运行取中位数才能得到稳定结论
- B 正确：`error` 会使 `lhci assert` 退出码非 0（阻断合并）
- C 正确：也可以只写自定义 `assertions`，避免被无关项频繁阻断

**14. ★★ 关于测试分片（Sharding），以下说法错误的是？**

A. Playwright / Jest / Vitest 都支持 `--shard=1/3` 这类静态分片
B. 静态分片按测试文件分配，各分片耗时可能不均
C. 分片后每个机器只产出部分结果，直接看单份报告会误判"通过"，必须合并报告
D. 分片会让测试用例被重复执行，因此必须关闭并行

**答案：D**

**解析**：
- D 错误：分片是把用例拆分到多个机器 / 进程**并行执行**，不会重复执行；分片与并行都是提升速度的手段
- A、B、C 正确。Playwright 用 `blob` reporter 产出中间结果，再用 `merge-reports` 合并成一份 HTML 报告；JUnit XML 需按分片收集后由 CI 平台合并
- 更均衡的做法是按历史耗时动态分片，或把慢文件单独拆小

**15. ★★★ 关于增量测试选择（只跑受影响的测试），以下做法错误的是？**

A. 用 `jest --findRelatedTests <files>` 从模块依赖图反查受影响的测试文件
B. 用 `vitest related <files>` 基于 Vite 模块图找出相关测试
C. 主分支与合并队列（merge queue）也使用增量选择，以节省 CI 时间
D. `package.json` / 构建配置 / CI 配置变更时强制跑全量

**答案：C**

**解析**：
- C 错误：增量选择**只在 PR 快速反馈中使用**；合并队列与主分支必须跑全量，否则隐式依赖（全局样式、环境变量、快照、mock 数据）导致的漏测会进入主干
- A、B 正确。Nx 用 `nx affected -t test --base=origin/main`，Turborepo 用 `turbo run test --filter='...[origin/main]'`
- D 正确：必须有兜底触发条件，配置类文件变更时强制全量

### 契约测试（3 题）

**16. ★★★ 关于消费者驱动契约（Pact）的流程，以下顺序正确的是？**

A. 提供者写契约 → 消费者验证 → 部署
B. 消费者编写契约测试并生成契约文件 → 发布到 Pact Broker → 提供者拉取契约并真实验证 → `can-i-deploy` 门禁
C. 契约文件由 Broker 自动生成，无需消费者参与
D. 契约测试需要前端与后端同时启动联调

**答案：B**

**解析**：
- B 正确。四步：① 消费者声明"我发什么请求、期望收到什么响应"，测试运行时用 Mock Provider 拦截并生成 `pacts/*.json`；② 发布契约到 Pact Broker（附带消费者版本号）；③ 提供者拉取契约，按 `provider state` 准备数据并真实发起请求比对；④ `can-i-deploy` 判断某版本能否部署
- A 错误：契约由**消费者驱动**，不是提供者写
- C 错误：Broker 只负责存储与分发契约
- D 错误：契约测试不需要两者同时启动，只需提供者能启动即可 —— 这是它相对 E2E 的核心优势

**17. ★★ 契约测试中为什么使用匹配器（Matchers）而不是硬编码具体值？**

A. 匹配器性能更好
B. 契约应约束结构与类型而非具体值，否则提供者的正常数据变更会造成大量误报
C. 匹配器可以自动生成测试数据
D. 硬编码值会导致契约文件过大

**答案：B**

**解析**：B 正确。用 `integer(1)` / `string('张三')` / `eachLike(...)` / `like(...)` 让契约只约束"结构、类型、必填字段"；提供者可以自由变更数据内容（如用户名字），只要结构不变就不会破坏契约；而删除字段、改类型、改状态码会立即被验证捕获。
A、C、D 都不是原因。硬编码具体值会让契约退化成"数据快照测试"，提供者换数据就失败。

**18. ★★★ 关于契约测试与 Mock、E2E 的分工，以下说法错误的是？**

A. Mock（MSW / `page.route`）验证前端自身的逻辑，不连真实后端
B. 契约测试在提供者侧真实发起请求，能发现"后端改了字段"
C. 契约测试可以替代 E2E，因为它更快更稳定
D. E2E 是唯一能发现"业务流程断了"的手段

**答案：C**

**解析**：
- C 错误：契约测试**不能替代 E2E** —— 它只验证接口约定一致性，不验证业务规则、多接口协作与 UI 渲染
- A 正确：Mock 是前端自己写的假实现，只能验证前端逻辑
- B 正确：契约测试的提供者侧真实发起请求，因此能发现"后端改了字段"，而 Mock 不能
- D 正确：契约测试不能发现业务流程断裂，只有 E2E 可以

**19. ★★ 关于快照测试，以下说法错误的是？**

A. 快照测试适合检测"意外的输出变化"，而非验证输出是否正确
B. 内联快照（inline snapshot）把期望值写在测试文件里，便于 review

**20. ★★ Vitest Browser Mode 相比 jsdom 环境的核心优势是？**

A. 运行速度更快
B. 在真实浏览器中运行，能正确执行布局、样式、真实事件与浏览器 API
C. 不需要安装浏览器
D. 可以替代 E2E 测试

## 第二部分：简答题（共 15 题）

**Q1（★）：请解释测试金字塔模型，并说明为什么应该遵循这个模型。**

**答案**：

测试金字塔是 Mike Cohn 提出的测试策略模型，将测试分为四层（从底层到顶层）：

1. **单元测试（50-60%）**：测试单个函数或模块，执行速度最快（毫秒级），维护成本最低，问题定位最精确
2. **组件测试（20-30%）**：测试单个组件的 UI 交互，从用户视角验证组件行为
3. **集成测试（10-15%）**：测试多个组件/模块的协作流程，验证数据流转和状态同步
4. **E2E 测试（5-10%）**：验证完整用户路径，从真实浏览器角度测试业务流程

**遵循原因**：
- 底层测试执行快、维护成本低、问题定位精确，投入产出比最高
- 上层测试执行慢、维护成本高、不稳定，数量应严格控制
- 反模式"冰淇淋甜筒"（大量 E2E + 少量单元测试）会导致 CI 时间过长、测试不稳定、开发效率下降
- 金字塔模型确保"快速反馈"和"精确诊断"的平衡

> 📖 **参考链接**：
> - [测试金字塔 - Martin Fowler](https://martinfowler.com/articles/practical-test-pyramid.html)

---

**Q2（★★）：Vitest 相比 Jest 有哪些核心优势？在什么场景下应该选择 Vitest 而非 Jest？**

**答案**：

**核心优势**：
1. 与 Vite 共享配置（resolve.alias、插件、CSS 处理），无需维护两套构建配置
2. 原生 ESM 支持，无需额外配置 TypeScript（无需 ts-jest）
3. HMR 测试运行——watch 模式下只重跑受影响的测试文件
4. 浏览器模式——支持在真实浏览器中运行测试
5. 速度更快——基于 ESBuild 转译，比 Babel 更快
6. API 兼容 Jest——从 Jest 迁移成本低

**选择 Vitest 的场景**：
- 项目使用 Vite 作为构建工具
- 新项目启动，无历史包袱
- 需要 HMR 测试运行提升开发体验

**选择 Jest 的场景**：
- 项目使用 Webpack/CRA，且无迁移计划
- 大量现有 Jest 测试用例和自定义插件
- 团队对 Jest 生态更熟悉

**Q3（★★）：请说明 Testing Library 查询优先级的设计原理，以及为什么 getByRole 优先级最高。**

**答案**：

**查询优先级（从高到低）**：
getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId

**设计原理**：查询优先级遵循"越接近用户交互方式，优先级越高"原则。用盲人使用读屏软件类比——读屏软件通过 ARIA Role 理解页面元素，getByRole 正是模拟这种交互方式。

**getByRole 优先级最高的原因**：
1. 最接近辅助技术（读屏软件）的查询方式
2. 强制开发者编写可访问性更好的组件（需要正确的 ARIA role）
3. 查询结果最稳定（不因文本内容或 DOM 结构调整而变化）
4. 符合 W3C WAI-ARIA 规范，是 Web 可访问性的最佳实践

**getByTestId 优先级最低的原因**：
- test-id 是纯开发者视角，用户无法感知
- 过度使用 test-id 会降低测试的可维护性
- 仅作为"最后手段"，当其他查询方式都无法使用时才使用

> - [Testing Library 官方文档](https://testing-library.com/docs/)

**Q4（★★）：userEvent 和 fireEvent 的核心区别是什么？请举例说明为什么 userEvent 更推荐使用。**

**答案**：

**核心区别**：
- fireEvent：仅触发单个 DOM 事件，不模拟完整的用户操作序列
- userEvent：模拟真实用户的完整操作序列，触发完整的事件链

**userEvent 更推荐的原因（举例说明）**：

```typescript
// 场景：表单输入框有 onBlur 校验
// 用户输入后点击外部区域，触发 onBlur 校验

// fireEvent 方式——缺少 focus 和 blur 事件
fireEvent.change(input, { target: { value: 'test' } });
// onBlur 校验未触发，bug 被遗漏！

// userEvent 方式——完整的 focus → input → blur 事件链
await userEvent.click(input);        // 触发 focus
await userEvent.keyboard('test');    // 触发 keydown → input → keyup
await userEvent.click(outside);      // 触发 blur
// onBlur 校验正常触发，bug 可被发现
```

**事件链对比**：
- userEvent.click：pointerdown → mousedown → focus → mouseup → click
- userEvent.type：focus → keydown → input → keyup（每输入一个字符重复），change（失焦时触发一次）
- fireEvent.click：仅触发 click

**Q5（★★）：请描述 MSW 的工作原理，以及它在测试中的三种核心使用场景。**

**答案**：

**MSW 工作原理**：
- 浏览器环境：通过注册 Service Worker 拦截所有网络请求（fetch、XMLHttpRequest）
- Node.js 测试环境：通过拦截 globalThis.fetch 和 XMLHttpRequest 实现
- Handler 匹配：根据请求 URL 和方法匹配到对应的 handler，返回 mock 响应

**三种核心使用场景**：

1. **API 层单元测试**：使用 setupServer 拦截 fetch 请求，测试 API 函数在成功/失败/超时场景下的行为，不依赖真实后端
2. **组件集成测试**：组件渲染后自动发送请求，MSW 返回 mock 数据，组件按正常流程更新 UI，验证完整的数据加载 → 渲染 → 交互流程
3. **开发环境 Mock**：使用 setupWorker 在浏览器中启用 Service Worker，开发时使用 mock 数据替代未完成的后端 API，前后端并行开发

**优势**：同一套 handler 可用于开发、测试、Storybook 三种场景，无需修改任何业务代码。

**Q6（★★）：Playwright 的自动等待机制是如何工作的？列举 3 种自动等待无法覆盖的场景。**

**答案**：

**自动等待机制**：
Playwright 在执行每个操作前自动执行"可操作性检查"（actionability checks），包括：
1. 元素是否存在于 DOM 中
2. 元素是否可见（非 hidden、opacity > 0）
3. 元素是否稳定（动画完成、未在移动中）
4. 元素是否接收事件（未被其他元素遮挡）
5. 元素是否已启用（非 disabled）

**3 种自动等待无法覆盖的场景**：

1. **等待网络请求完成**：需要手动使用 page.waitForResponse 等待特定 API 请求返回
2. **等待特定业务状态**：如"等待商品列表加载完成"——需要 page.waitForFunction 检查 DOM 中的特定数据
3. **等待元素从 DOM 中移除**：如 loading 动画消失——需要 page.waitForSelector('.loading', { state: 'hidden' })

**Q7（★★）：视觉回归测试的原理是什么？如何处理包含动态内容的页面？**

**答案**：

**原理**：
1. 首次运行：为每个测试用例生成基准截图（baseline），存储为 PNG 文件
2. 后续运行：生成新截图，使用 pixelmatch 库进行逐像素对比
3. 差异检测：统计差异像素数量，与阈值（maxDiffPixels、maxDiffPixelRatio）对比
4. 失败处理：差异超过阈值时测试失败，生成差异高亮图（红色标记差异区域）

**处理动态内容的方法**：

1. **mask 遮挡**：使用 mask 参数遮挡动态区域（如 `mask: [page.locator('.timestamp')]`），被遮挡区域不参与像素对比
2. **注入 CSS 隐藏**：在截图前通过 page.addStyleTag 注入 CSS，隐藏动画和动态元素
3. **固定测试数据**：使用固定的时间戳、固定的用户数据、固定的随机种子
4. **合理设置阈值**：设置 maxDiffPixelRatio = 0.01（允许 1% 的像素差异），容忍微小的渲染差异
5. **使用稳定环境**：在 CI 中使用 Playwright Docker 镜像，确保字体和渲染环境一致

> 📖 **参考链接**：
> - [Playwright 视觉回归测试](https://playwright.dev/docs/test-snapshots)

**Q8（★★★）：请描述一个完整的前端测试策略，涵盖从单元测试到 E2E 测试的各个层级，以及它们之间的分工。**

**答案**：

**测试策略设计**：

| 层级 | 测试对象 | 工具 | 覆盖内容 | 占比 |
|---|---|---|---|---|
| 单元测试 | 纯函数、工具函数、Store | Vitest | 业务逻辑、边界条件、异常处理 | 50-60% |
| 组件测试 | 单个 UI 组件 | Vitest + Testing Library | 渲染结果、用户交互、状态变化 | 20-30% |
| 集成测试 | 多组件协作流程 | Vitest + Testing Library + MSW | 数据流转、路由跳转、API 交互 | 10-15% |
| E2E 测试 | 关键用户路径 | Playwright | 完整业务流程、跨页面交互 | 5-10% |
| 视觉回归 | UI 组件、页面布局 | Playwright toHaveScreenshot | 样式回归、响应式设计 | 作为 E2E 补充 |

**分工原则**：
- 单元测试：覆盖所有业务逻辑的边界条件和异常处理，追求"快"和"全"
- 组件测试：覆盖组件的所有交互状态（正常、加载、错误、空、禁用），追求"用户视角"
- 集成测试：覆盖核心业务流程的数据流转，验证模块协作
- E2E 测试：只覆盖关键用户路径（2-5 条），追求"稳"和"精"
- 视觉回归：覆盖设计系统组件和关键页面布局，防止样式回归

**CI 执行策略**：
- 单元测试和组件测试在 pre-commit hook 中执行（< 30 秒）
- 集成测试在 PR 合并前执行（< 2 分钟）
- E2E 测试和视觉回归在 main 分支合并后执行（< 15 分钟，多浏览器并行）

**Q9（★★）：k6 与 Lighthouse CI 分别测什么？为什么 k6 测不了 LCP / CLS？**

**答案**：

**k6：服务端 / 接口性能测试**
- 脚本运行在独立的 JS 虚拟机（Go 实现）中，**没有 DOM、没有 `window`、没有浏览器渲染引擎**，因此无法测 LCP / CLS 这类浏览器指标
- 四类测试：负载测试（预期流量下的表现）、压力测试（找崩溃拐点）、冒烟测试（极小流量验证脚本与链路正确）、前端性能测试（不属于 k6 范畴）
- 常用执行器：`constant-vus`、`ramping-vus`、`constant-arrival-rate`、`ramping-arrival-rate`、`shared-iterations`、`per-vu-iterations`
- 阈值即门禁：`thresholds: { http_req_duration: ['p(95)<500'], http_req_failed: ['rate<0.01'] }`，不满足时退出码非 0
- `sleep(1)` 模拟用户思考时间，否则单 VU 的请求速率取决于响应速度，压力模型失真

**Lighthouse CI：浏览器端页面质量审计与性能预算门禁**
- 采集 LCP、CLS、TBT、性能分、可访问性分等
- 关键配置：`numberOfRuns`（3 次取中位数降低波动）、断言级别（`error` 阻断 / `warn` 提示 / `off` 关闭）、`preset`
- 断言示例：`"categories:performance": ["error", { "minScore": 0.9 }]`、`"largest-contentful-paint": ["error", { "maxNumericValue": 2500 }]`

**为什么 k6 测不了浏览器指标**：LCP / INP / CLS 依赖渲染引擎、布局、绘制与真实用户交互，必须在浏览器环境中采集。k6 是协议级压测工具，只能观察 HTTP 层指标。真实用户分布需要 RUM。

**分工总结**：k6 守住接口层的吞吐与延迟，Lighthouse CI 守住页面层的性能预算，RUM 反映线上真实体验 —— 三者互补，不可互相替代。

**Q10（★★）：测试分片（Sharding）如何实现？为什么报告必须合并？**

**答案**：

**分片命令**：

```bash
npx playwright test --shard=1/3   # Playwright：按用例文件拆分
npx jest --shard=1/3              # Jest 28+
npx vitest --shard=1/3            # Vitest 1.0+
npx playwright test --workers=4   # 单机进程级并行
npx vitest run --maxWorkers=4
```

**CI 实现**：用矩阵策略起多个 job，每个 job 跑一个分片，`fail-fast: false` 让一个分片失败不影响其他分片继续跑，便于一次看到全部失败。

**两种分片方式**：

- **静态分片**（`--shard`）：按测试文件（或文件分组）预先分配，实现简单，但各分片耗时可能不均（取决于文件内的用例数量与耗时）
- **动态分片**：按历史耗时均衡调度（Playwright `blob` 报告 + 第三方调度器，或把慢文件单独拆小），或使用商业平台的自动均衡调度

**为什么必须合并报告**：分片后每个机器只产出部分结果，直接看单份报告会误判"通过"。做法：用 `blob` reporter 产出中间结果 → 上传为 artifact → `playwright merge-reports --reporter html` 合并成一份 HTML 报告；JUnit XML 需按分片收集后由 CI 平台合并。

**配套优化**：缓存浏览器二进制（`~/.cache/ms-playwright`）避免每个分片重复下载；把构建产物通过 artifact 在 job 间复用，避免重复构建。

**Q11（★★）：增量测试选择（`--findRelatedTests`）的三条纪律是什么？**

**答案**：

**工具与原理**：

| 工具 | 命令 | 原理 |
|---|---|---|
| Jest | `jest --findRelatedTests <files>` | 从模块依赖图反查受影响的测试文件 |
| Jest | `jest --changedSince=origin/main` | 找出自某提交以来变更文件相关的测试 |
| Jest | `jest --onlyChanged` | 基于当前 git 工作区的改动选择测试（本地开发常用） |
| Vitest | `vitest related <files>` | 基于 Vite 模块图找出相关测试 |
| Nx | `nx affected -t test --base=origin/main` | 基于项目依赖图 + 计算缓存，只跑受影响项目 |
| Turborepo | `turbo run test --filter='...[origin/main]'` | 基于包依赖图筛选受影响包 |

**三条纪律**：

1. **只在 PR 快速反馈中使用**：合并队列（merge queue）与主分支必须跑全量，否则隐式依赖（全局样式、环境变量、快照、mock 数据）导致的漏测会进入主干
2. **依赖图必须可信**：如果测试存在"跨包隐式依赖"（如 A 包测试读取 B 包的 fixture 文件），依赖图分析会漏判，需要把这些依赖显式声明，或用 `inputs` 兜底
3. **必须有兜底触发条件**：`package.json` / 构建配置 / CI 配置 / 共享工具目录变更时，强制跑全量测试

**收益**：PR 反馈时间显著下降，同时不牺牲主干的测试完整性。

**Q12（★★★）：Flaky 测试如何治理？**

**答案**：

**危害**：造成无效重跑、掩盖真实失败、让团队对 CI 失去信任，最终"重跑直到绿"成为常态。

**治理流程**：

1. **检测**：CI 中开启重试并记录重试次数（Playwright `retries`、Jest / Vitest `retry`），统计"重试后才通过"的用例清单；用报告平台标记 flaky 率
2. **定位**：查看 trace / video / 截图（Playwright 的 `--trace on`）；关注失败是否集中在特定时间、特定机器、特定浏览器
3. **修复根因**（按高频成因）：
   - 硬编码等待（`waitForTimeout`）→ 改为基于条件的等待（`waitForResponse`、`waitForSelector`、自动等待）
   - 测试间共享状态（数据库、localStorage、全局 store）→ 每个用例独立准备与清理
   - 测试数据冲突（并发写同一账号 / 同一订单）→ 用例内生成唯一数据
   - 依赖真实第三方服务 → 用 MSW / `page.route` 拦截
   - 动画与过渡未结束 → 关闭动画或等待元素稳定
   - 时间相关断言（`Date.now()`、时区）→ 固定时钟 / 固定时区
4. **止损**：确认无法立即修复的用例先隔离（quarantine / skip + 建 issue），并设置隔离时长上限，避免长期挂起
5. **预防**：新增用例必须通过 flaky 门禁（同一用例连续多次运行均通过）；把 flaky 率纳入 CI 健康度指标

**反面做法**：用 `waitForTimeout(1000)` "修复"不稳定用例 —— 把不确定性从"偶发失败"变成"稳定变慢"，在慢机器上依然失败。

**Q13（★★★）：什么是消费者驱动契约（Pact）？完整流程是怎样的？**

**答案**：

**定义**：契约测试验证"服务消费者与提供者之间对接口的约定是否一致"，不需要把两者真正连起来跑。核心思想是**消费者驱动契约（Consumer-Driven Contract，CDC）**：由消费者定义它依赖的接口形状，提供者验证自己是否满足这些期望。

**解决的问题**：前后端并行开发时接口约定漂移。三种现有手段都无法提前发现：

- 单元测试：Mock 返回的是前端自己写的假数据，永远"通过"
- Mock 服务：Mock 与真实接口是两套实现，Mock 通过 ≠ 真实接口可用
- E2E 测试：能发现问题，但需要真实环境、失败定位困难、成本高

**完整流程（四步）**：

```
① 消费者侧：编写消费者测试，声明"我发什么请求、期望收到什么响应"
   → 用 Mock Provider 拦截请求，校验前端对响应的处理
   → 生成契约文件 pacts/frontend-api.json
② 发布契约：pact-broker publish ./pacts --consumer-app-version=$GIT_SHA
③ 提供者侧：拉取契约 → 按 provider state 准备数据 → 真实发起请求
   → 比对真实响应是否符合契约 → 发布验证结果到 Broker
④ 部署门禁：pact-broker can-i-deploy --pacticipant frontend --version $GIT_SHA
```

**关键要素**：

- **匹配器**：用 `integer(1)` / `string(...)` / `eachLike(...)` / `like(...)` 只约束结构与类型，不约束具体值
- **provider states**：把契约里的 `given('用户 1 存在')` 转成真实的数据准备逻辑，否则验证要么失败要么只能验证空数据路径
- **Broker 与门禁**：契约文件必须发布到 Broker 并接入 `can-i-deploy`，否则契约退化成"一份本地文档"，无法在部署前阻断破坏性变更

**定位**：位于"单元 / 组件测试"与"E2E 测试"之间，验证的是**接口约定**这一层。

**Q14（★★★）：契约测试、Mock、E2E 三者的分工是什么？契约测试能替代 E2E 吗？**

**答案**：

**三者分工**：

| 维度 | Mock（MSW / `page.route`） | 契约测试（Pact） | E2E 测试 |
|---|---|---|---|
| 验证对象 | 前端自身的逻辑 | 接口约定的真实一致性 | 端到端业务流程 |
| 是否连真实后端 | 否 | 是（提供者侧真实发起请求） | 是 |
| 依赖环境 | 无 | 只需提供者能启动 | 完整环境（前端 + 后端 + 数据） |
| 执行速度 | 毫秒级 | 秒级 | 分钟级 |
| 失败定位 | 精确到前端逻辑 | 精确到接口交互 | 需要逐层排查 |
| 能否发现"后端改了字段" | 不能 | **能** | 能 |
| 能否发现"业务流程断了" | 不能 | 不能 | **能** |
| 理想占比 | 组件 / 集成测试内部使用 | 少量关键接口 | 极少关键路径 |

**契约测试能否替代 E2E**：**不能**。契约只验证接口约定（结构 / 类型 / 状态码），不验证业务规则、多接口协作与 UI 渲染，也不验证"用户能不能走完流程"。

**三者是互补关系**：Mock 让组件测试摆脱外部依赖；契约测试保证"前端以为的接口"与"后端真实的接口"一致；E2E 保证关键业务流程整体可用。

**适合使用契约测试的场景**：微服务之间接口调用频繁且独立部署；前端依赖的 BFF / API 由多个团队维护；同一提供者有多个消费者（Web / iOS / Android）；提供者启动成本远高于消费者（如需数据库、消息队列）。

**不适合的场景**：接口尚未稳定的快速原型阶段；提供者无法在 CI 中启动或无法准备测试数据；只有单一消费者且前后端同一人 / 同一仓库维护（直接写集成测试更简单）；需要验证业务流程与 UI 交互。

**Q15（★★）：快照测试的原理与适用场景是什么？什么场景不适合？**

**答案**：

**原理**：

1. 首次运行：把序列化后的输出写入快照文件（`.snap`），或用 `toMatchInlineSnapshot()` 内联到测试文件
2. 后续运行：重新序列化并与快照逐字符比较，不一致则测试失败
3. 更新：用 `--update` / `-u` 重新生成快照

**适用场景**：

- UI 组件结构（渲染树）—— 人眼难以逐项断言但变化需要被察觉
- 序列化输出（配置对象、生成的代码、AST）
- 数据结构的"形状"校验

**不适合的场景**：

- **验证正确性**：快照只能检测"是否变化"，不能判断"是否正确"。首次生成的快照若是错的，测试会一直通过 —— 核心业务逻辑必须用显式断言
- 包含随机值 / 时间戳 / UUID 的输出 → 需先规范化，或用属性匹配器（`expect.any(String)`）
- 大对象 / 整页快照 → 任何无关改动都会导致失败，维护成本高
- 频繁变更的 UI → 快照更新成为"习惯性 `-u`"，失去意义

**实践要点**：

- 快照文件必须纳入版本管理，变更需人工 review（否则 `-u` 会让它变成橡皮图章）
- 优先使用内联快照，把期望值放在测试文件里，review 时更直观
- 快照测试是补充而非替代：行为断言（用户视角）应占主体
- 与视觉回归的区别：快照测"结构与文本"，视觉回归测"渲染像素"

**Q6（★★★）：性能测试与性能门禁设计**

**场景**：某电商详情页需要把性能纳入 CI 门禁：接口层要求 P95 < 500ms、失败率 < 1%；前端页面要求 LCP < 2.5s、CLS < 0.1、性能分 ≥ 90。请设计性能测试与门禁方案。

**答案要点**：

**一、分层测试选型**

| 层次 | 工具 | 关注指标 | 执行时机 |
|---|---|---|---|
| 接口层 | k6 | 吞吐量、P95 / P99 延迟、错误率 | 每日定时 + 发版前 |
| 页面层 | Lighthouse CI | LCP、CLS、TBT、性能分、可访问性分 | 每个 PR |
| 线上真实用户 | RUM | Core Web Vitals 真实分布（P75） | 持续 |

**二、k6 脚本设计要点**
- 用 `ramping-arrival-rate`（到达率模型）作为门禁，避免"服务变慢导致压测变轻"的假象
- `stages` 分阶段：预热 → 加压 → 稳态 → 降压
- `thresholds` 作为门禁：`http_req_duration: ['p(95)<500', 'p(99)<1000']`、`http_req_failed: ['rate<0.01']`
- 用 `setup()` 登录拿 token 并在 `default` 中复用；用 `teardown()` 清理
- 用 `group()` 按业务分组统计；用自定义 `Trend` 记录关键链路的端到端耗时
- 必须加 `sleep(1)` 模拟用户思考时间
- `summaryTrendStats` 输出 `p(90) / p(95) / p(99)`，避免只看平均值

**三、Lighthouse CI 配置要点**
- `numberOfRuns: 3`（单次运行波动大，取中位数）
- 断言分级：性能分 / LCP / CLS 用 `error`，TBT、未使用 JS 用 `warn`，与业务无关项用 `off`
- 固定运行环境（Playwright / Lighthouse Docker 镜像 + headless），减少环境噪声
- 报告上传到公共存储或自建服务，PR 中贴出对比链接

**四、CI 集成策略**
- PR：只跑轻量检查（Lighthouse 单页 + k6 冒烟，低 VU 短时长）
- main：跑完整负载测试与多页面 Lighthouse
- 定时：每日凌晨跑压力测试，找容量拐点

**五、结果解读与避免假象**
- 实验室数据（Lighthouse）与现场数据（RUM）会有差异，门禁用实验室保证"可回归性"，用 RUM 校准阈值
- 压测结果必须结合服务端指标（CPU、连接数、GC）判断，避免只看客户端延迟

**六、性能回归的处置流程**
- 门禁失败 → 归因（本次变更 / 环境抖动 / 基线漂移）→ 修复或确认后更新基线
- 基线更新必须留痕并说明原因，禁止"顺手 `-u`"

**Q7（★★★）：大型测试套件的 CI 优化方案**

**场景**：某项目 E2E 测试从 200 个用例增长到 1200 个，CI 耗时从 8 分钟涨到 45 分钟，且约 3% 的用例偶发失败。请给出优化方案。

**答案要点**：

**一、优化目标与优先级**
- 第一优先：缩短 PR 反馈时长（目标 < 15 分钟）
- 第二优先：消除 flaky（目标 flaky 率 < 0.5%）
- 第三优先：降低 CI 成本（机器时长 / 并发数）

**二、分片并行**
- 用矩阵策略把 E2E 拆成 N 个分片（`--shard=i/N`），`fail-fast: false` 一次看全失败
- 分片报告用 `blob` reporter 产出、`merge-reports` 合并，避免"单份报告误判通过"
- 静态分片耗时不均时，改为按历史耗时动态分片

**三、增量选择**
- 用 `--findRelatedTests` / `vitest related` / `nx affected` 只跑受影响的用例
- 严守三条纪律：只在 PR 用；依赖图必须可信；配置类文件变更强制全量

**四、缓存与产物复用**
- 依赖缓存（`pnpm-lock.yaml` 哈希作为 key）
- 浏览器缓存（`~/.cache/ms-playwright`）
- 构建产物通过 artifact 在 job 间复用，避免每个分片重复构建
- Turborepo / Nx 的计算缓存（remote cache）跨机器复用测试结果

**五、Flaky 治理**
- 开启重试并记录重试次数，产出 flaky 用例清单
- 按高频成因修复：硬编码等待、共享状态、数据冲突、依赖真实第三方、动画未结束、时间相关断言
- 无法立即修复的先隔离并设时长上限；新增用例过 flaky 门禁

**六、测试分层再平衡**
- 把 E2E 中过细的断言下沉到组件 / 集成层（E2E 只保留 2-5 条关键路径）
- 用 MSW 拦截第三方依赖，减少 E2E 的不确定性来源

**七、效果度量**
- P50 / P95 反馈时长、flaky 率、CI 机器时长与成本、主干回归逃逸数
- 优化后用数据证明收益，避免"感觉变快了"

**Q8（★★★）：前后端接口契约测试落地**

**场景**：前端依赖 3 个后端团队的 API，接口变更常在联调或上线后才暴露。请设计契约测试落地方案。

**答案要点**：

**一、目标与边界**
- 目标：在 CI 中验证"提供者的真实响应"是否符合"消费者的真实期望"
- 边界：只验证接口约定一致性，**不替代** E2E（不验证业务规则、多接口协作、UI 渲染）

**二、角色与流程**

后端（提供者）→ 拉取契约 → 按 provider state 准备数据 → 真实发起请求验证 → 回传结果

- 用匹配器（`like` / `eachLike` / `integer` / `string`）约束结构与类型，不硬编码具体值
- 必须实现 `provider states`，否则只能验证空数据路径
- 只覆盖**关键接口**（登录、下单、支付等），不求全量
- 契约文件纳入版本管理，变更可 review

**四、CI 集成**
- 前端 PR：生成契约并发布（`--consumer-app-version=$GIT_SHA`）
- 后端 PR：拉取契约并验证，结果回传 Broker
- 部署前：`can-i-deploy --pacticipant frontend-web --version $GIT_SHA --to-environment production`
- 只有"消费者期望"与"提供者验证"都通过时才允许部署

**五、版本与兼容策略**
- 契约带消费者版本号，Broker 据此判断兼容性
- 破坏性变更（删字段、改类型、改状态码）必须在验证阶段被捕获并阻断
- 提供者需要变更接口时，先看 Broker 上有哪些消费者、哪些版本仍在使用

**六、推广节奏与适用性评估**
- 先选 1-2 个变更频繁、影响面大的接口试点，验证流程闭环后再推广
- 接口尚未稳定的原型阶段不上契约测试（维护成本高于收益）
- 提供者无法在 CI 中启动或无法准备测试数据时，不适合引入

## 第四部分：高频追问速答（共 12 题）

> 面试官常在主问题后沿同一条链路继续追问。以下 12 组速答覆盖测试模块最容易被追问的细节。

**追问 1（★★）：为什么 k6 不能测 LCP / CLS？**

因为 k6 的脚本运行在独立的 JS 虚拟机（Go 实现）中，没有 DOM、没有 `window`、没有渲染引擎。LCP / CLS 依赖布局、绘制与真实用户交互，必须在浏览器环境采集 —— 用 Lighthouse CI（实验室）或 RUM（线上真实用户）。

**追问 2（★★）：Lighthouse CI 为什么建议 `numberOfRuns: 3`？**

Lighthouse 单次运行波动较大（±5 分常见），单次结果不足以支撑门禁判断。取多次运行的中位数可以显著降低环境噪声；本地调试可设 1 次以加快反馈，CI 门禁建议 3 次。

**追问 3（★★★）：静态分片（`--shard`）有什么问题？**

按测试文件预先分配，各分片耗时可能严重不均（取决于文件内的用例数量与耗时），导致"一个分片跑 20 分钟、其他分片 3 分钟就跑完"，整体时长由最慢分片决定。改进方式是按历史耗时动态分片，或把慢文件单独拆小。

**追问 4（★★★）：增量选择为什么主分支不能用？**

因为增量选择依赖"依赖图分析"，而隐式依赖（全局样式、环境变量、快照文件、mock 数据、跨包 fixture）不会被依赖图捕获，会造成漏测。PR 阶段可以接受这种风险（有合并队列兜底），但主分支与合并队列必须跑全量，确保主干可信。

**追问 5（★★）：用 `waitForTimeout(1000)` 修 flaky 为什么不行？**

它把"偶发失败"变成了"稳定变慢"，并没有消除不确定性。在更慢的 CI 机器或网络抖动时依然会失败，同时还让整个套件变慢。正确做法是基于条件的等待（`waitForResponse`、`waitForSelector`、自动等待）与消除共享状态。

**追问 6（★★★）：契约里为什么不用硬编码值？**

契约应约束**结构与类型**而非具体值。硬编码 `name: '张三'` 会让提供者一换数据就验证失败，契约退化成"数据快照测试"，产生大量误报。用匹配器后，提供者可以自由变更数据内容，只要结构不变就不会破坏契约；而删字段、改类型、改状态码会立即被捕获。

**追问 7（★★★）：契约测试能替代 E2E 吗？**

不能。契约测试只验证"接口约定是否一致"，不验证业务规则、多接口协作与 UI 渲染，也不验证"用户能不能走完流程"。三者互补：Mock 让组件测试脱离外部依赖，契约测试保证接口约定一致，E2E 保证关键业务流程可用。

**追问 8（★★）：`provider states` 有什么用？**

契约里的 `given('用户 1 存在')` 只是声明前置条件，提供者侧必须把它转成真实的数据准备逻辑（建数据 / 删数据）。没有 `provider states`，提供者无法准备契约要求的数据，验证要么失败，要么只能验证空数据路径，契约失去意义。

**追问 9（★★）：快照测试为什么不能验证正确性？**

快照只做"与上次是否一致"的比较，不判断内容是否正确。若首次生成的快照本身就是错的，后续每次运行都会"通过"。因此核心业务逻辑必须用显式断言；快照只适合检测"意外的输出变化"。

**追问 10（★★）：Vitest Browser Mode 与 jsdom 的核心差别？**

jsdom 没有真实布局引擎：`getBoundingClientRect()` 返回全 0、CSS 计算值不可靠、部分浏览器 API 缺失。Browser Mode 在真实浏览器中运行测试，布局、样式、真实事件与浏览器 API 都正确，适合涉及布局 / 样式 / 真实事件的组件测试，代价是启动更慢、需要安装浏览器。

**追问 11（★）：测试金字塔的反模式是什么？**

"冰淇淋甜筒"（Ice Cream Cone）—— 大量 E2E + 少量单元测试。后果是 CI 时间过长、测试不稳定、问题定位困难、开发效率下降。正确做法是底层单元测试占 50-60%，越往上数量越少。

**追问 12（★）：测试覆盖率 100% 意味着什么？**

只意味着每一行代码都至少被执行过一次。它不能保证断言正确、边界条件充分、业务逻辑正确。覆盖率是**数量指标而非质量指标**，应关注关键路径的覆盖质量而非数字本身。
