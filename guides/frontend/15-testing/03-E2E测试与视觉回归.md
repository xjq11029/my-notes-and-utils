## 一、核心概念

### 1.1 E2E 测试的定位

E2E（End-to-End）测试验证从用户视角出发的完整业务流程，是测试金字塔的顶层，占比最少但价值独特。

**消防演习类比**：E2E 测试就像消防演习——你不会测试每个房间里每一件家具是否易燃，但你确保整栋楼的逃生路线是畅通的。E2E 测试不覆盖所有功能边界，但确保关键用户路径不被破坏。

```typescript
// E2E 测试的核心原则：只验证关键用户路径

// 关键路径：用户完成核心任务必须走的路径
// 例如电商系统：
// 1. 注册 → 登录 → 浏览商品 → 加入购物车 → 下单 → 支付
// 2. 登录 → 查看订单 → 申请退款
// 3. 搜索商品 → 筛选 → 查看详情 → 收藏

// 非关键路径（不应写入 E2E）：
// 1. 测试每个按钮的 hover 样式
// 2. 测试每个表单的边界条件校验
// 3. 测试各种错误提示文案
// 这些应该由组件测试和单元测试覆盖
```

**E2E 测试的定位矩阵**：

| 维度 | 单元测试 | 组件测试 | 集成测试 | E2E 测试 |
|---|---|---|---|---|
| 覆盖范围 | 单个函数 | 单个组件 | 多个组件协作 | 完整用户流程 |
| 测试目标 | 逻辑正确性 | UI 交互正确性 | 模块协作正确性 | 业务流程完整性 |
| 环境 | Node.js | jsdom | jsdom + MSW | 真实浏览器 |
| 维护成本 | 低 | 中 | 中高 | 高 |
| 运行时间 | 毫秒 | 秒 | 十秒 | 分钟 |
| 失败排查 | 精确到行 | 精确到组件 | 精确到模块 | 需要逐层排查 |
| 测试数量 | 大量 | 中等 | 少量 | 极少 |
| 典型占比 | 50-60% | 20-30% | 10-15% | 5-10% |

### 1.3 视觉回归测试

视觉回归测试（Visual Regression Testing）通过截图对比，自动检测 UI 的意外变化。

```typescript
// ========================
// 视觉回归测试的核心概念
// ========================

// 工作原理：
// 1. 首次运行：为每个测试用例生成基准截图（baseline）
// 2. 后续运行：为每个测试用例生成新截图
// 3. 像素级对比：将新截图与基准截图进行逐像素对比
// 4. 差异检测：如果差异超过阈值，测试失败
// 5. 人工确认：开发者确认差异是预期变更还是 bug

// 适用场景：
// - 设计系统组件库的样式回归
// - 多语言/多主题的 UI 一致性验证
// - 响应式布局的断点验证
// - 重构后的 UI 一致性保证

// 不适用场景：
// - 包含动态内容（时间、随机推荐）的页面
// - 动画过渡中的截图
// - 频繁变化的营销页面
```

## 二、底层原理

### 2.1 Playwright 架构

Playwright 采用三层架构模型，提供了清晰的关注点分离。

```typescript
// ========================
// Playwright 三层架构
// ========================

// 第一层：Browser Server
// - 一个 Browser Server 对应一个浏览器进程（Chromium/Firefox/WebKit）
// - 通过 CDP（Chrome DevTools Protocol）或类似协议与浏览器通信
// - 负责浏览器进程的生命周期管理

// 第二层：Browser Context
// - 一个 Browser Server 可以创建多个 Browser Context
// - 每个 Browser Context 是独立的浏览器会话（类似无痕窗口）
// - 不同 Context 之间完全隔离：cookies、localStorage、sessionStorage 互不影响
// - 创建和销毁 Context 极快（比创建新浏览器进程快得多）

// 第三层：Page
// - 一个 Browser Context 可以创建多个 Page（标签页）
// - 每个 Page 代表一个浏览器标签页
// - Page 提供页面交互 API（goto、click、fill、screenshot）

// 架构示意图：
// Browser Server (Chromium)
//   ├── Browser Context #1 (用户 A 的会话)
//   │   ├── Page: 首页
//   │   └── Page: 个人中心
//   └── Browser Context #2 (用户 B 的会话)
//       ├── Page: 首页
//       └── Page: 购物车

// 代码体现
import { chromium } from 'playwright';

const browser = await chromium.launch(); // Browser Server

const context1 = await browser.newContext({ // Browser Context #1
  storageState: 'userA.json',
});
const context2 = await browser.newContext({ // Browser Context #2
  storageState: 'userB.json',
});

const page1 = await context1.newPage(); // Context #1 的 Page
const page2 = await context1.newPage(); // Context #1 的另一个 Page
const page3 = await context2.newPage(); // Context #2 的 Page
```

### 2.2 自动等待机制

Playwright 在执行操作前会自动等待元素满足可交互条件，这是其最核心的设计特性之一。

```typescript
// ========================
// Playwright 自动等待机制
// ========================

// Playwright 在执行每个操作前，会自动执行一系列"可操作性检查"（actionability checks）：
// 1. 元素是否存在于 DOM 中
// 2. 元素是否可见（非 hidden、opacity > 0）
// 3. 元素是否稳定（动画完成、未在移动中）
// 4. 元素是否接收事件（未被其他元素遮挡）
// 5. 元素是否启用（非 disabled）

// 对比：Selenium 需要手动等待
// Selenium 写法：
// await driver.wait(until.elementIsVisible(element), 5000);
// await element.click();

// Playwright 写法：自动等待，无需手动
// await page.click('button'); // Playwright 自动等待按钮可点击

// 自动等待的具体场景
test('自动等待示例', async ({ page }) => {
  // 1. page.goto 自动等待页面加载完成（load 事件）
  await page.goto('https://example.com');

  // 2. page.click 自动等待元素可见、可交互
  await page.click('button#submit');

  // 3. page.fill 自动等待元素可见、可编辑
  await page.fill('input[name="username"]', 'admin');

  // 4. page.waitForSelector 等待元素出现在 DOM 中
  await page.waitForSelector('.loading-complete');

  // 5. 自定义等待条件
  await page.waitForFunction(() => document.querySelector('.progress')?.textContent === '100%');

  // 6. 等待网络请求完成
  await page.waitForResponse(resp => resp.url().includes('/api/products') && resp.status() === 200);
});

// 自动等待的超时配置
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  timeout: 30000,           // 全局测试超时
  expect: {
    timeout: 5000,          // expect 断言超时
  },
  use: {
    actionTimeout: 10000,   // 单个操作（click/fill）超时
    navigationTimeout: 30000, // 页面导航超时
  },
});
```

### 2.3 视觉回归原理

```typescript
// ========================
// 视觉回归测试原理
// ========================

// Playwright 的 toHaveScreenshot 工作流程：

// 1. 截图生成
//    - page.screenshot() 生成 PNG 截图
//    - 截图为当前 viewport 的完整渲染结果
//    - 支持全页面截图（fullPage: true）

// 2. 像素对比
//    - 使用 pixelmatch 库进行逐像素对比
//    - 计算差异像素数量
//    - 生成差异高亮图（红色标记差异区域）

// 3. 阈值判定
//    - maxDiffPixels: 允许的最大差异像素数
//    - maxDiffPixelRatio: 允许的最大差异像素比例
//    - threshold: 像素颜色差异阈值（0-1，默认 0.2）

// 4. 快照管理
//    - 基准截图存储在测试文件同目录的 __screenshots__/ 下
//    - 首次运行生成基准截图
//    - 后续运行与基准截图对比
//    - 使用 --update-snapshots 更新基准

// 视觉回归配置
test.describe('视觉回归测试', () => {
  test('首页布局', async ({ page }) => {
    await page.goto('/');

    // 全页截图对比
    await expect(page).toHaveScreenshot('homepage.png', {
      fullPage: true,
      maxDiffPixelRatio: 0.01, // 允许 1% 的像素差异
    });
  });

  test('按钮组件', async ({ page }) => {
    await page.goto('/components/button');

    // 元素截图对比
    const button = page.locator('.primary-button');
    await expect(button).toHaveScreenshot('button-primary.png');
  });
});

// 处理动态内容的策略
test('处理动态内容', async ({ page }) => {
  await page.goto('/dashboard');

  // 1. 使用 mask 遮挡动态区域
  await expect(page).toHaveScreenshot('dashboard.png', {
    mask: [
      page.locator('.current-time'),  // 遮挡时间显示
      page.locator('.user-avatar'),   // 遮挡用户头像
    ],
  });

  // 2. 使用 stylePath 注入自定义样式
  // 在截图前注入 CSS 隐藏动画和动态内容
  await page.addStyleTag({
    content: `
      .animated { animation: none !important; }
      .timestamp { visibility: hidden; }
    `,
  });
  await expect(page).toHaveScreenshot('dashboard.png');
});
```

### 2.4 CI 集成

```yaml
# ========================
# .github/workflows/playwright.yml
# Playwright CI 集成配置
# ========================

name: Playwright Tests
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    timeout-minutes: 30
    runs-on: ubuntu-latest

    strategy:
      matrix:
        # 在不同浏览器上并行执行
        browser: [chromium, firefox, webkit]

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: pnpm install

      # 推荐在 package.json 中配置脚本：
# "test:e2e": "playwright test"
# 然后在 CI 中直接使用 pnpm test:e2e

      - name: Install Playwright browsers
        run: pnpm playwright install --with-deps ${{ matrix.browser }}

      - name: Run Playwright tests
        run: pnpm playwright test --project=${{ matrix.browser }}

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report-${{ matrix.browser }}
          path: playwright-report/
          retention-days: 30

      - name: Upload screenshots (failed tests)
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: screenshots-${{ matrix.browser }}
          path: test-results/
          retention-days: 7
```

// ========================

// ========================

import { test, expect } from '@playwright/test';

test.describe('电商购物完整流程', () => {
  // 使用 test.describe.configure 设置串行执行
  // 因为这些步骤有依赖关系
  test.describe.configure({ mode: 'serial' });

  // 共享的测试状态
  let authToken: string;

  test('步骤 1：用户注册', async ({ page }) => {

    await page.getByLabel('密码').fill('Test@123456');

    await expect(page).toHaveURL('/login');

  test('步骤 2：用户登录', async ({ page }) => {
    await page.goto('/login');

    await expect(page).toHaveURL('/');

    await page.goto('/products');

    // 等待商品列表加载

    await page.getByText('AirPods Pro').click();

// 4. 测试结果分析脚本
// scripts/analyze-test-results.ts
import fs from 'fs';

interface TestResult {
  status: 'passed' | 'failed' | 'skipped';
  title: string;
  duration: number;
  retry: number;
}

function analyzeResults(resultsPath: string) {
  const results: { suites: Array<{ specs: Array<{ tests: TestResult[] }> }> } =
    JSON.parse(fs.readFileSync(resultsPath, 'utf-8'));

  const allTests = results.suites.flatMap(s =>
    s.specs.flatMap(sp => sp.tests)
  );

  const passed = allTests.filter(t => t.status === 'passed').length;
  const failed = allTests.filter(t => t.status === 'failed').length;
  const skipped = allTests.filter(t => t.status === 'skipped').length;
  const total = allTests.length;

  const avgDuration = allTests.reduce((sum, t) => sum + t.duration, 0) / total;
  const slowTests = allTests
    .filter(t => t.duration > 30000)
    .sort((a, b) => b.duration - a.duration)
    .slice(0, 10);

  console.log(`
    ========================
    测试结果分析
    ========================
    总计: ${total}
    通过: ${passed} (${((passed / total) * 100).toFixed(1)}%)
    失败: ${failed}
    跳过: ${skipped}
    平均耗时: ${(avgDuration / 1000).toFixed(1)}s
  `);

  if (slowTests.length > 0) {
    console.log('最慢的 10 个测试:');
    slowTests.forEach((t, i) => {
      console.log(`  ${i + 1}. ${t.title} - ${(t.duration / 1000).toFixed(1)}s`);
    });
  }
}

analyzeResults('./test-results/results.json');

## 四、常见面试题

**Q1：E2E 测试在测试金字塔中的定位是什么？为什么 E2E 测试不应该占最大比例？**

答案要点：E2E 测试位于测试金字塔顶层，理想占比 5-10%。E2E 测试验证关键用户路径（如消防演习——不测试每个房间但确保逃生路线畅通），不应该占最大比例因为：执行速度慢（分钟级）、维护成本高（UI 变化频繁导致测试失败）、不稳定（易受网络/环境干扰）、问题定位困难（失败后需要逐层排查）。E2E 测试应该只覆盖核心业务流程，非关键路径和边界条件由下层测试覆盖。

**Q2：Playwright 相比 Cypress 的核心优势有哪些？**

答案要点：多浏览器原生支持（Chromium + Firefox + WebKit vs Cypress 主要支持 Chromium）、多标签页原生支持、内置视觉回归测试（toHaveScreenshot）、多语言支持（JS/TS、Python、Java、.NET）、更快的执行速度（并行执行 + Browser Context 复用）、自动等待机制更完善、移动端原生模拟。Cypress 的优势在于更友好的调试体验（Time Travel、实时重载）和更成熟的 Dashboard 服务。

**Q3：Playwright 的自动等待机制是如何工作的？**

答案要点：Playwright 在执行每个操作前自动执行"可操作性检查"（actionability checks）：元素是否在 DOM 中、是否可见、是否稳定（动画完成）、是否接收事件（未被遮挡）、是否启用。这些检查是自动的，无需手动编写等待代码。例如 page.click('button') 会自动等待按钮出现、可见、稳定、可点击，然后才执行点击操作。

**Q4：视觉回归测试的原理是什么？如何处理动态内容？**

答案要点：视觉回归测试通过截图对比检测 UI 变化：首次运行生成基准截图 → 后续运行生成新截图 → 使用 pixelmatch 逐像素对比 → 差异超过阈值则测试失败。处理动态内容的方法：使用 mask 遮挡动态区域（如时间戳、用户头像）、注入 CSS 隐藏动画和动态元素、使用稳定的测试数据（固定时间、固定用户）、设置合理的差异阈值。

**Q5：如何在 CI/CD 中集成 Playwright 测试？**

答案要点：使用 Playwright 官方 Docker 镜像（mcr.microsoft.com/playwright）、GitHub Actions 中配置多浏览器并行矩阵、使用 storageState 保存登录态避免重复登录、配置失败重试（retries）、收集测试报告和 Trace、失败时上传截图和视频作为 artifact。关键配置：fullyParallel: true 开启全并行、forbidOnly: true 防止 CI 中提交 .only、workers 控制并行数。

## 五、避坑指南

| 错误现象 | 产生原因 | 正确做法 |
|---|---|---|
| E2E 测试频繁随机失败（flaky tests），开发团队不再信任测试结果 | 依赖不稳定的外部因素（网络延迟、动画时间、动态数据）；过度使用固定等待时间（sleep）而非条件等待 | 使用 Playwright 的自动等待机制和条件等待（waitForSelector、waitForResponse）；使用稳定测试数据（mock API 或固定数据集）；开启失败重试机制（retries）；避免使用 page.waitForTimeout 固定等待 |
| 视觉回归测试因 CI 环境与本地环境差异导致大量误报 | 不同操作系统、浏览器版本、字体渲染差异导致截图像素不完全一致 | 使用 Playwright Docker 镜像确保 CI 与本地环境一致；设置合理的 maxDiffPixelRatio（如 0.01）；使用模糊对比（threshold）而非精确像素对比；在 CI 中使用相同操作系统 |
| 将 E2E 测试当作"万能测试"，试图覆盖所有功能和边界条件 | 对 E2E 测试的定位理解偏差，认为 E2E 测试越多越安全 | 遵循测试金字塔，E2E 只覆盖关键用户路径；将边界条件测试下沉到单元测试和组件测试；定期评审 E2E 测试用例，删除冗余和非关键路径的测试 |

## 补充：性能测试、CI 执行优化与契约测试

> 本节补齐 E2E 之外的三个工程化主题：**性能测试**（k6 与 Lighthouse CI 把"性能"纳入 CI 门禁）、**CI 中的测试执行优化**（分片、增量选择、缓存、Flaky 治理）、**契约测试**（用消费者驱动契约解决前后端接口约定漂移）。三者共同回答一个问题：测试体系如何在高频交付下既快又可信。

### 1. 性能测试

#### 1.1 概念定义

性能测试按目标分为四类，前端项目通常组合使用：

| 类型 | 目标 | 典型工具 | 观察指标 |
|---|---|---|---|
| 负载测试（Load） | 验证预期流量下的表现 | k6、JMeter、wrk | 吞吐量、P95 延迟、错误率 |
| 压力测试（Stress） | 找到系统崩溃的拐点 | k6（ramping 场景） | 拐点 QPS、崩溃恢复时间 |
| 冒烟测试（Smoke） | 用极小流量验证脚本与链路正确 | k6（低 VU 短时长） | 是否全部通过 |
| 前端性能测试 | 量化页面加载与交互体验 | Lighthouse CI、Playwright + CDP | LCP、INP、CLS、TBT、性能分 |

关键区分：**k6 测的是服务端/接口性能，不是浏览器渲染性能**。k6 的脚本运行在独立的 JS 虚拟机（Go 实现）中，没有 DOM、没有 `window`、没有浏览器渲染引擎，因此它无法测 LCP/CLS 这类浏览器指标——浏览器性能必须用 Lighthouse CI 或真实用户监控（RUM）。

#### 1.2 k6：脚本编写与场景配置

k6 用 JavaScript 编写测试脚本，通过 `options` 声明负载模型与阈值：

```javascript
// ========================
// k6/load-test.js —— k6 负载测试脚本
// 运行：k6 run k6/load-test.js
// ========================

import http from 'k6/http';
import { check, group, sleep } from 'k6';
import { Trend } from 'k6/metrics';

// 自定义指标：k6 内置指标不够用时，用 Trend/Counter/Gauge/Rate 自定义
const loginDuration = new Trend('login_duration', true); // true = 以毫秒为时间单位

// ========== 负载模型与阈值 ==========
export const options = {
  // 方式一：stages 阶段式负载（最常用）
  // 每个阶段用 duration 描述时长、target 描述该阶段结束时的目标 VU 数
  stages: [
    { duration: '30s', target: 20 }, // 预热：30 秒内爬升到 20 个 VU
    { duration: '1m', target: 50 },  // 加压：1 分钟内爬升到 50 个 VU
    { duration: '2m', target: 50 },  // 稳态：维持 50 个 VU 跑 2 分钟
    { duration: '20s', target: 0 },  // 降压：20 秒内降到 0
  ],

  // 方式二：scenarios 显式场景（可组合多种执行器）
  // scenarios: {
  //   smoke: { executor: 'constant-vus', vus: 1, duration: '10s' },
  //   load: {
  //     executor: 'ramping-arrival-rate',   // 按"每秒请求数"而非 VU 数施压
  //     startRate: 10,
  //     timeUnit: '1s',
  //     preAllocatedVUs: 50,
  //     maxVUs: 200,
  //     stages: [
  //       { duration: '1m', target: 100 },
  //       { duration: '2m', target: 100 },
  //       { duration: '30s', target: 0 },
  //     ],
  //   },
  // },

  // ========== 阈值：不满足则 k6 退出码非 0，可直接作为 CI 门禁 ==========
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1000'], // 95% 请求 < 500ms
    http_req_failed: ['rate<0.01'],                  // 失败率 < 1%
    checks: ['rate>0.99'],                           // 断言通过率 > 99%
    login_duration: ['p(95)<800'],                   // 自定义指标的阈值
    // 阈值也可写成对象形式，控制"不满足时的行为"：
    // { threshold: 'http_req_duration: [p(95)<500]', abortOnFail: true, delayAbortEval: '10s' }
    // abortOnFail 在阈值确定失败时提前终止测试（CI 快速反馈）；
    // delayAbortEval 跳过预热阶段的抖动，避免刚启动就误判
  },

  // 汇总统计口径：自定义 summary 可用 handleSummary 钩子输出 HTML / JSON
  summaryTrendStats: ['avg', 'min', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
};

// ========== 前置准备（可选）：每个 VU 启动时执行一次 ==========
export function setup() {
  const res = http.post('https://api.example.com/login', JSON.stringify({
    username: 'perf_user',
    password: 'perf_pass',
  }), { headers: { 'Content-Type': 'application/json' } });

  // setup 的返回值会作为 data 参数传给 default 函数
  return { token: res.json('token') };
}

// ========== 主流程：每个 VU 反复执行 ==========
export default function (data) {
  const headers = {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${data.token}`,
  };

  // group 把多个请求归为一组，报告中按组统计耗时
  group('商品列表', () => {
    const res = http.get('https://api.example.com/api/products?page=1', { headers });

    // check 是断言，不影响流程，只统计通过率（与 threshold 的 checks 配合）
    check(res, {
      '状态码为 200': (r) => r.status === 200,
      '返回列表非空': (r) => r.json('items').length > 0,
      '响应时间 < 800ms': (r) => r.timings.duration < 800,
    });
  });

  group('商品详情', () => {
    const start = Date.now();
    const res = http.get('https://api.example.com/api/products/p1', { headers });
    loginDuration.add(Date.now() - start);

    check(res, { '详情返回 200': (r) => r.status === 200 });
  });

  // sleep 模拟用户思考时间，避免 VU 空转把压力测成"无脑压测"
  // 不加 sleep 时，单 VU 的请求速率取决于响应速度，压力模型会失真
  sleep(1);
}

// ========== 收尾（可选） ==========
export function teardown(data) {
  http.post('https://api.example.com/logout', null, {
    headers: { Authorization: `Bearer ${data.token}` },
  });
}
```

**k6 的四种常用执行器（executor）**：

| 执行器 | 负载模型 | 适用场景 |
|---|---|---|
| `constant-vus` | 固定 VU 数，持续指定时长 | 稳态负载测试 |
| `ramping-vus` | VU 数按 `stages` 变化 | 模拟流量爬坡（与 `options.stages` 等价） |
| `constant-arrival-rate` | 固定每秒请求数（与响应时间解耦） | 精确控制 QPS |
| `ramping-arrival-rate` | 每秒请求数按阶段变化 | 模拟真实流量的到达率变化 |
| `shared-iterations` | 所有 VU 共同完成固定迭代数 | 数据准备、脚本冒烟 |
| `per-vu-iterations` | 每个 VU 完成固定迭代数 | 可重复的基准测试 |

**选 VU 模型还是到达率模型**：VU 模型下"实际 QPS = VU 数 / 单次迭代耗时"，服务端变慢时 QPS 会自动下降（压力随之减小）；到达率模型则坚持发出固定 QPS，服务端变慢时 VU 会被"堆积"，更接近真实用户行为，也更容易压出问题。**性能门禁建议用到达率模型**，避免"服务变慢导致压测变轻"的假象。

```bash
# ========================
# k6 常用命令
# ========================
k6 run k6/load-test.js                              # 按脚本内 options 执行
k6 run --vus 10 --duration 30s k6/load-test.js      # 命令行覆盖负载模型
k6 run --out json=results.json k6/load-test.js      # 输出原始结果供后续分析
k6 run --http-debug k6/load-test.js                 # 打印请求/响应，排查脚本问题
```

#### 1.3 Lighthouse CI：性能预算门禁

Lighthouse 是浏览器端的页面质量审计工具，Lighthouse CI（`@lhci/cli`）把它接入 CI，使"性能回归"能像单元测试一样阻断合并：

```json
// ========================
// lighthouserc.json —— Lighthouse CI 配置
// 运行：lhci autorun
// ========================
{
  "ci": {
    "collect": {
      "url": ["http://localhost:4173/", "http://localhost:4173/products/p1"],
      "numberOfRuns": 3,
      "startServerCommand": "pnpm preview --port 4173",
      "startServerReadyPattern": "Local:",
      "settings": {
        "preset": "desktop",
        "chromeFlags": "--no-sandbox --headless=new"
      }
    },
    "assert": {
      "preset": "lighthouse:recommended",
      "assertions": {
        "categories:performance": ["error", { "minScore": 0.9 }],
        "categories:accessibility": ["error", { "minScore": 0.95 }],
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["warn", { "maxNumericValue": 300 }],
        "unused-javascript": ["warn", { "maxNumericValue": 102400 }],
        "uses-responsive-images": "off"
      }
    },
    "upload": {
      "target": "temporary-public-storage",
      "reportFilenamePattern": "%%PATHNAME%%-%%DATETIME%%.report.%%EXTENSION%%"
    }
  }
}
```

**三项关键配置**：

1. **`numberOfRuns`**：Lighthouse 单次运行有较大波动（±5 分常见），取多次运行的中位数才能得到稳定结论。CI 中建议 3 次，本地调试可设 1 次。
2. **断言级别**：`error` 会使 `lhci assert` 退出码非 0（阻断合并），`warn` 只提示，`off` 关闭。核心指标（性能分、LCP、CLS）用 `error`，次要项用 `warn`。
3. **`preset`**：`lighthouse:recommended` 打开官方推荐的全部断言；也可以只写自定义 `assertions`，避免被无关项（如"图片格式"）频繁阻断。

```bash
# ========================
# Lighthouse CI 常用命令
# ========================
npm i -D @lhci/cli
npx lhci autorun          # = collect + assert + upload 三步连跑
npx lhci collect          # 只采集，产物写入 .lighthouseci/
npx lhci assert           # 只断言（读取已有采集结果）
npx lhci upload           # 只上传报告
```

#### 1.4 性能回归的 CI 集成

性能测试的价值在于"与基线对比"，而不在于单次跑出一个分数：

```yaml
# ========================
# .github/workflows/perf.yml —— 性能门禁流水线
# ========================
name: Performance Gate

on:
  pull_request:
    branches: [main]

jobs:
  lighthouse:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: pnpm install
      - run: pnpm build

      # 1. 前端性能门禁：断言失败即 job 失败，PR 无法合并
      - name: Lighthouse CI
        run: npx lhci autorun

      # 2. 报告归档：即使失败也上传，便于对比
      - name: Upload Lighthouse report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: lighthouse-report
          path: .lighthouseci/

  k6:
    runs-on: ubuntu-latest
    # 性能测试通常不阻塞每次 PR，改为定时或手动触发
    if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
    steps:
      - uses: actions/checkout@v4
      - name: Run k6 load test
        run: |
          # k6 阈值不满足时退出码非 0，直接作为门禁
          docker run --rm -i grafana/k6 run - < k6/load-test.js
```

**性能回归的四种集成方式**：

| 方式 | 触发时机 | 优点 | 缺点 |
|---|---|---|---|
| Lighthouse CI 断言 | 每次 PR | 快速反馈、门禁明确 | 波动导致偶发失败，需要多次运行 |
| k6 阈值门禁 | 定时 / 手动 / 发布前 | 覆盖服务端容量与稳定性 | 环境要求高、耗时长，不适合每次 PR |
| 与 main 基线对比 | 每次 PR（跑两次） | 能发现"相对退化" | 环境差异会污染对比结果 |
| 真实用户监控（RUM） | 发布后持续 | 真实环境、真实设备 | 反馈滞后，无法阻断合并 |

**基线对比的实现要点**：在 main 分支定期跑一次性能测试并把结果（Lighthouse JSON / k6 summary）存为基线；PR 时跑同一套测试，比较关键指标的变化率，超过阈值（如 LCP 退化 > 10%）则告警。注意**两次运行必须在同一环境**（同镜像、同机器规格、同数据量），否则对比结论无效。

#### 1.5 面试常见问法

- "k6 能测浏览器性能吗？" → 不能，k6 脚本运行在独立 JS 虚拟机中，没有 DOM 与渲染引擎，只能测接口/服务端性能；浏览器性能用 Lighthouse CI 或 RUM。
- "为什么性能门禁要用到达率模型而不是固定 VU？" → VU 模型下服务端变慢会导致 QPS 自动下降，压力随之变小，掩盖问题；到达率模型坚持固定 QPS，更接近真实用户行为。
- "Lighthouse 分数每次都不一样，怎么在 CI 里用？" → 增加 `numberOfRuns` 取中位数；用绝对阈值（如 LCP < 2500ms）而非分数；对波动大的项降级为 `warn`。
- "性能回归怎么和基线对比？" → main 分支定期产出基线产物，PR 时在同环境重跑并比较关键指标变化率，超阈值则阻断或告警。

#### 1.6 易错点

- 用 k6 断言浏览器渲染指标（LCP/CLS）：工具能力不匹配，永远拿不到这些指标。
- k6 脚本里不加 `sleep`：VU 空转导致压测模型失真（实际施压远高于设计值）。
- Lighthouse 只跑 1 次就下结论：单次波动可达 ±5 分，容易误判回归。
- 在共享/异构 CI 机器上做基线对比：环境差异（CPU 型号、并发任务）比代码变更带来的差异更大。
- 把性能门禁设在"绝对分数"上（如性能分 ≥ 90）：分数受环境与审计项变更影响大，应优先用 LCP / CLS / TBT 等具体指标的绝对阈值。

### 2. CI 中的测试执行优化

#### 2.1 概念定义

测试套件变大后，CI 的瓶颈从"测试写得好不好"变成"跑得快不快"。四类优化手段：**分片并行**（把用例拆到多个机器/进程）、**增量选择**（只跑受影响的用例）、**缓存与产物复用**（避免重复安装与构建）、**Flaky 治理**（消除不稳定用例造成的无效重跑）。

#### 2.2 测试分片（Sharding）与并行执行

```yaml
# ========================
# .github/workflows/e2e-shard.yml —— 4 分片并行执行
# ========================
jobs:
  e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false        # 一个分片失败不影响其他分片继续跑，便于一次看到全部失败
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: pnpm install

      # 缓存浏览器，避免每个分片都下载（见 2.4）
      - uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: playwright-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}

      - run: pnpm exec playwright install --with-deps chromium

      # --shard=当前分片/总分片数
      - name: Run shard ${{ matrix.shard }}/4
        run: pnpm exec playwright test --shard=${{ matrix.shard }}/4

      # 每个分片上传自己的报告，最后再合并
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: blob-report-${{ matrix.shard }}
          path: blob-report/

  merge:
    needs: [e2e]
    runs-on: ubuntu-latest
    if: always()
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: pnpm install
      - uses: actions/download-artifact@v4
        with:
          path: all-blob-reports
          pattern: blob-report-*
          merge-multiple: true
      # 把多个分片的报告合并成一份 HTML 报告
      - run: pnpm exec playwright merge-reports --reporter html ./all-blob-reports
      - uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
```

```bash
# ========================
# 各框架的分片命令
# ========================
npx playwright test --shard=1/3        # Playwright：按用例文件拆分
npx jest --shard=1/3                   # Jest 28+
npx vitest --shard=1/3                 # Vitest 1.0+

# 进程级并行（单机多 worker）
npx playwright test --workers=4
npx vitest run --maxWorkers=4
```

**分片的两种实现**：Playwright / Jest / Vitest 的 `--shard` 是**静态分片**——按测试文件（或文件分组）预先分配，实现简单但各分片耗时可能不均（取决于文件内的用例数量与耗时）。更均衡的做法是按历史耗时动态分片（如 Playwright 的 `blob` 报告 + 第三方调度器，或把慢文件单独拆小），或使用商业平台的自动均衡调度。

**报告必须合并**：分片后每个机器只产出部分结果，直接看单份报告会误判"通过"。用 `blob` reporter 产出中间结果，再用 `merge-reports` 合并；JUnit XML 则需按分片收集后由 CI 平台合并。

#### 2.3 测试选择的增量策略

只跑"受本次变更影响"的测试，可以显著缩短 PR 反馈时间：

```yaml
# ========================
# 按变更文件决定跑哪些测试
# ========================
- name: Run affected tests
  run: |
    # 1) 基于 Git 差异：只跑与改动文件相关的测试
    #    Jest 内置 --findRelatedTests，会沿依赖图找出受影响的测试文件
    CHANGED=$(git diff --name-only origin/main...HEAD | grep -E '\.(ts|tsx)$' | tr '\n' ' ')
    if [ -n "$CHANGED" ]; then
      npx jest --findRelatedTests $CHANGED
    else
      echo "无 TS 变更，跳过单元测试"
    fi
```

| 工具 | 命令 | 原理 |
|---|---|---|
| Jest | `jest --findRelatedTests <files>` | 从模块依赖图反查受影响的测试文件 |
| Jest | `jest --changedSince=origin/main` | 找出自某提交以来变更文件相关的测试 |
| Jest | `jest --onlyChanged` | 基于当前 git 工作区的改动选择测试（本地开发常用） |
| Vitest | `vitest related <files>` | 基于 Vite 模块图找出相关测试 |
| Nx | `nx affected -t test --base=origin/main` | 基于项目依赖图 + 计算缓存，只跑受影响项目 |
| Turborepo | `turbo run test --filter='...[origin/main]'` | 基于包依赖图筛选受影响包 |

**增量选择的三条纪律**：

1. **只在 PR 快速反馈中用**：合并队列（merge queue）与主分支必须跑全量，否则隐式依赖（全局样式、环境变量、快照、mock 数据）导致的漏测会进入主干。
2. **依赖图必须可信**：如果测试存在"跨包隐式依赖"（如 A 包测试读取 B 包的 fixture 文件），依赖图分析会漏判，需要把这些依赖显式声明或用 `inputs` 兜底（如配置变更、lockfile 变更时强制全量）。
3. **必须有兜底触发条件**：`package.json` / 构建配置 / CI 配置 / 共享工具目录变更时，强制跑全量测试。

#### 2.4 缓存与产物复用

```yaml
# ========================
# 缓存策略：key 必须包含 lockfile 哈希
# ========================
- name: Cache pnpm store
  uses: actions/cache@v4
  with:
    path: ~/.pnpm-store
    key: pnpm-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: pnpm-${{ runner.os }}-

- name: Cache node_modules
  uses: actions/cache@v4
  with:
    path: node_modules
    key: nm-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}

- name: Cache Playwright browsers
  uses: actions/cache@v4
  with:
    path: ~/.cache/ms-playwright
    key: pw-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}

- name: Cache Vitest / Vite transform cache
  uses: actions/cache@v4
  with:
    path: node_modules/.vite
    key: vite-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml', 'vite.config.ts') }}
```

| 复用对象 | 缓存位置 | 收益 | 注意事项 |
|---|---|---|---|
| 依赖包 | `~/.pnpm-store` / `node_modules` | 省去 install 的下载与解压 | key 必须含 lockfile 哈希，否则用了过期依赖 |
| 浏览器二进制 | `~/.cache/ms-playwright` | 省去每次下载数百 MB | 与 Playwright 版本绑定，需含 lockfile 哈希 |
| 构建产物 | `dist/`、`.next/`、`turbo` 本地缓存 | 避免多 job 重复构建 | 用 artifact 在 job 间传递更可靠（缓存可能被清理） |
| 测试转换缓存 | `node_modules/.vite` | 加快 Vitest 启动 | 配置变更需使 key 失效 |
| 任务计算缓存 | Turbo / Nx 远程缓存 | 未变更的任务直接命中缓存 | 需保证任务输入（源码、环境变量）被完整声明 |

**产物复用的正确姿势**：构建 job 产出 `dist/` 并 `upload-artifact`，E2E job `download-artifact` 后直接起静态服务测试——避免每个 E2E 分片都重新构建一次。相比 cache（可能被淘汰、key 管理复杂），artifact 在**同一次流水线内**是确定性的传递方式。

#### 2.5 Flaky 测试的识别与治理

**Flaky 测试**指同一份代码多次运行结果不一致的测试。它是测试体系最大的信任杀手：团队会逐渐"看到红就重跑"，最终忽略真正的失败。

**第一步：识别**

```bash
# 方式一：失败重试 + 报告区分（Playwright 会把重试后通过的用例标记为 flaky）
npx playwright test --retries=2
# 报告中 status 为 'flaky' 的即不稳定用例

# 方式二：主动探测（同一用例重复执行 N 次，观察是否稳定）
npx playwright test --repeat-each=5

# 方式三：历史数据统计（把每次运行的用例结果入库，按用例名统计失败率）
# flaky_rate = 该用例"失败后重试通过"的次数 / 该用例总运行次数
# 目标：整体 flaky rate < 1%
```

**第二步：定位根因**（按出现频率排序）：

| 根因 | 典型现象 | 修复方式 |
|---|---|---|
| 固定等待（`sleep` / `waitForTimeout`） | 本地通过、CI 慢机器失败 | 改为条件等待（`waitForSelector` / `waitForResponse` / `expect.poll`） |
| 共享状态未隔离 | 单独跑通过、全量跑失败 | 每个测试独立数据（随机用户名）、独立上下文（`browser.newContext()`）、测试后清理 |
| 时间与时区依赖 | 跨天/跨时区失败 | 固定时间（`page.clock.setFixedTime`）与 `TZ` 环境变量；避免依赖"今天" |
| 随机数据不可复现 | 偶发失败且无法复现 | 固定随机种子；随机数据用可控生成器 |
| 执行顺序依赖 | 调换顺序即失败 | 用例必须自包含，禁止依赖前一个用例的副作用 |
| 并行资源冲突 | 并行失败、串行通过 | 每个 worker 独立端口/数据库 schema/测试账号；或用 `test.describe.serial` 显式串行 |
| 第三方依赖不稳定 | 随机超时 | 用 MSW / `page.route` 拦截外部接口，把不确定性挡在测试外 |
| 动画与过渡 | 断言时元素仍在移动 | 截图前禁用动画；用 `toBeVisible()` 等带自动重试的断言 |

**第三步：治理流程**

```
检测（重试标记 + 历史失败率统计）
  ↓
隔离（打上 @flaky 标记，从阻断合并的队列中移出，但仍每天运行）
  ↓
修复（按根因表逐项排查，优先修根因而不是加重试）
  ↓
回归（修复后连续运行 N 次稳定 → 移出隔离队列）
```

**三条纪律**：

1. **禁止用重试掩盖问题**：`retries` 只用于区分"环境抖动"与"真实失败"，不能作为长期方案。retries 会让 CI 变慢，并掩盖真实的竞态缺陷。
2. **禁止直接删除或永久跳过**：`test.skip` 会让覆盖静默丢失，必须走"隔离 + 修复 SLA（如 2 周）+ 回归"流程。
3. **Flaky 必须被度量**：把 flaky rate 作为 CI 健康度指标（如目标 < 1%），否则治理没有优先级。

#### 2.6 面试常见问法

- "E2E 太慢，怎么加速？" → 分片并行（`--shard`）+ 产物复用（artifact 传递构建产物）+ 缓存（依赖、浏览器）+ 增量选择（PR 只跑受影响）+ 减少不必要的全量重试。
- "测试分片后报告怎么看？" → 用 blob reporter 产出中间结果，再用 `merge-reports` 合并；单份分片报告不能作为结论。
- "增量测试有什么风险？" → 依赖图漏判隐式依赖导致漏测，因此只用于 PR 快速反馈，主干与合并队列跑全量，并对配置/依赖变更强制全量。
- "怎么发现和治理 Flaky 测试？" → 重试标记 + `--repeat-each` 主动探测 + 历史失败率统计；根因按固定等待、状态污染、时间依赖、并行冲突等分类修复；流程是检测 → 隔离 → 修复 → 回归，并用 flaky rate 度量。
- "缓存 key 怎么设计？" → 必须包含 lockfile 哈希（依赖与浏览器）与配置文件哈希（构建与转换缓存），否则会命中过期缓存导致"本地能过、CI 诡异失败"。

#### 2.7 易错点

- 分片数设得过大：分片调度与浏览器启动的固定开销会抵消并行收益，且报告合并更复杂。
- 缓存 `node_modules` 但 key 不含 lockfile 哈希：依赖更新后仍用旧依赖，出现难以解释的失败。
- 增量测试用在主分支上：漏测进入主干，问题被推迟到发布前才暴露。
- 把 `retries: 2` 当作 flaky 的解决方案：CI 时间翻倍，且真实的竞态缺陷被掩盖。
- 用 `waitForTimeout(1000)` "修复"不稳定用例：把不确定性从"偶发失败"变成"稳定变慢"，在慢机器上依然失败。

### 3. 契约测试

#### 3.1 概念定义

**契约测试（Contract Testing）** 验证"服务消费者与提供者之间对接口的约定是否一致"，而不需要把两者真正连起来跑。核心思想是**消费者驱动契约（Consumer-Driven Contract，CDC）**：由消费者定义它依赖的接口形状，提供者验证自己是否满足这些期望。

#### 3.2 契约测试解决的问题

前后端并行开发时，接口约定漂移是最常见的集成故障来源：

```
场景：前端（消费者）依赖 GET /api/users/{id}
  第 1 周：约定返回 { id, name, email }
  第 2 周：后端重构，把 name 拆成 firstName + lastName
  第 3 周：前端上线 → 页面显示 undefined

三种现有手段都无法提前发现：
  - 单元测试：Mock 返回的是前端自己写的假数据，永远"通过"
  - Mock 服务：Mock 与真实接口是两套实现，Mock 通过 ≠ 真实接口可用
  - E2E 测试：能发现问题，但需要真实环境、失败定位困难、成本高
契约测试补上这一环：在 CI 中验证"提供者的真实响应"是否符合"消费者的真实期望"
```

**契约测试的定位**：它位于"单元/组件测试"与"E2E 测试"之间，验证的是**接口约定**这一层，而不是业务流程，也不是业务逻辑。

#### 3.3 消费者驱动契约（Pact）的基本流程

```
① 消费者侧（前端 / 调用方）
   编写消费者测试：声明"我发什么请求、期望收到什么响应"
   → 测试运行时用 Mock Provider 拦截请求，校验前端对响应的处理
   → 生成契约文件 pacts/frontend-api.json

② 发布契约
   把契约文件发布到 Pact Broker（契约仓库），并附带消费者版本号
   → pact-broker publish ./pacts --consumer-app-version=$GIT_SHA

③ 提供者侧（后端 / 被调用方）
   拉取契约 → 对每个交互准备数据（provider state）→ 真实发起请求
   → 比对真实响应是否符合契约 → 发布验证结果到 Broker

④ 部署门禁
   pact-broker can-i-deploy --pacticipant frontend --version $GIT_SHA
   → 只有当"消费者期望"与"提供者验证"都通过时，才允许部署
```

```typescript
// ========================
// 消费者侧：pact/user.consumer.pact.spec.ts
// 依赖：@pact-foundation/pact
// ========================
import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import path from 'path';

const { like, eachLike, integer, string } = MatchersV3;

const provider = new PactV3({
  consumer: 'frontend-web',          // 消费者名
  provider: 'user-api',              // 提供者名
  dir: path.resolve(process.cwd(), 'pacts'), // 契约文件输出目录
  logLevel: 'warn',
});

describe('User API 契约', () => {
  it('GET /api/users/1 返回用户详情', async () => {
    // 1. 定义交互：请求 + 期望响应
    provider
      .given('用户 1 存在')            // provider state：提供者需要准备的数据状态
      .uponReceiving('获取用户详情的请求')
      .withRequest({
        method: 'GET',
        path: '/api/users/1',
        headers: { Accept: 'application/json' },
      })
      .willRespondWith({
        status: 200,
        headers: { 'Content-Type': 'application/json' },
        body: {
          // 用匹配器而不是硬编码值：契约只约束"类型与结构"，不约束具体值
          id: integer(1),
          name: string('张三'),
          email: string('zhangsan@example.com'),
          // eachLike 表示"数组，每个元素形状相同"
          roles: eachLike({ code: string('admin'), level: integer(1) }),
          // like 表示"类型相同即可"
          profile: like({ bio: string('简介') }),
        },
      });

    // 2. 执行消费者测试：Pact 会启动 mock server，
    //    真实走一遍前端的请求逻辑，并校验前端能正确处理响应
    await provider.executeTest(async (mockServer) => {
      const res = await fetch(`${mockServer.url}/api/users/1`, {
        headers: { Accept: 'application/json' },
      });
      const user = await res.json();

      expect(user.id).toBe(1);
      expect(user.name).toBeTruthy();
      expect(Array.isArray(user.roles)).toBe(true);
    });
    // 测试通过后，契约文件写入 pacts/frontend-web-user-api.json
  });
});
```

```typescript
// ========================
// 提供者侧：pact/user.provider.pact.spec.ts
// ========================
import { Verifier } from '@pact-foundation/pact';

describe('User API 提供者验证', () => {
  it('满足前端的契约期望', async () => {
    const verifier = new Verifier({
      providerBaseUrl: 'http://localhost:3000', // 真实运行中的服务
      pactBrokerUrl: process.env.PACT_BROKER_URL,
      pactBrokerToken: process.env.PACT_BROKER_TOKEN,
      provider: 'user-api',
      // 发布验证结果，供 can-i-deploy 查询
      publishVerificationResult: true,
      providerVersion: process.env.GIT_SHA,

      // provider state 处理器：把契约里的 given(...) 转成真实的数据准备
      stateHandlers: {
        '用户 1 存在': async () => {
          await db.users.create({ id: 1, name: '张三', email: 'zhangsan@example.com' });
        },
        '用户 1 不存在': async () => {
          await db.users.delete({ id: 1 });
        },
      },
    });

    await verifier.verifyProvider();
  });
});

pnpm vitest run pact/                     # 生成 pacts/*.json

  --version $GIT_SHA \
  --to-environment production
```

**契约的匹配器（Matchers）是关键**：契约只约束"结构、类型、必填字段"，不约束具体值。这样提供者可以自由变更数据内容（如用户名字），只要结构不变就不会破坏契约；而删除字段、改类型、改状态码则会立即被验证捕获。

#### 3.4 与 Mock / E2E 的分工

| 维度 | Mock（MSW / `page.route`） | 契约测试（Pact） | E2E 测试 |
|---|---|---|---|
| 验证对象 | 前端自身的逻辑 | 接口约定的真实一致性 | 端到端业务流程 |
| 是否连真实后端 | 否 | 是（提供者侧真实发起请求） | 是 |
| 依赖环境 | 无 | 只需提供者能启动 | 完整环境（前端 + 后端 + 数据） |
| 执行速度 | 毫秒级 | 秒级 | 分钟级 |
| 失败定位 | 精确到前端逻辑 | 精确到接口交互 | 需要逐层排查 |
| 能否发现"后端改了字段" | 不能（Mock 是前端自己写的） | **能** | 能 |
| 能否发现"业务流程断了" | 不能 | 不能 | **能** |
| 理想占比 | 组件/集成测试内部使用 | 少量关键接口 | 极少关键路径 |

**三者是互补关系**：Mock 让组件测试摆脱外部依赖；契约测试保证"前端以为的接口"与"后端真实的接口"一致；E2E 保证关键业务流程整体可用。契约测试**不替代** E2E——它不验证业务规则、不验证多接口协作、不验证 UI 渲染。

#### 3.5 在微服务与前端的适用场景

**适合使用契约测试的场景**：

- 微服务之间接口调用频繁、部署独立（契约测试能在不联调的情况下防止接口破坏）。
- 前端依赖的 BFF / API 由多个团队维护，接口变更缺乏沟通。
- 同一提供者有多个消费者（Web、iOS、Android），需要确保变更不破坏任一消费者。
- 提供者启动成本远高于消费者（如需要数据库、消息队列），无法在每次前端 PR 中启动。

**不适合使用的场景**：

- 接口尚未稳定、处于快速原型阶段（契约频繁变更的维护成本高于收益）。
- 提供者无法在 CI 中启动或无法准备测试数据（`provider states` 无法实现）。
- 只有单一消费者且前后端由同一人/同一仓库维护（直接写集成测试更简单）。
- 需要验证业务流程与 UI 交互（这是 E2E 的职责）。

#### 3.6 面试常见问法

- "契约测试解决了什么问题？" → 前后端接口约定漂移；Mock 通过 ≠ 真实接口可用，E2E 成本高且定位难，契约测试补上"接口约定一致性"这一层。
- "什么是消费者驱动契约？" → 由消费者定义期望（请求 + 响应结构），生成契约文件发布到 Broker，提供者拉取契约并真实验证是否满足。
- "契约测试和 Mock 有什么区别？" → Mock 是消费者自己写的假实现，只验证前端逻辑；契约测试用消费者的期望去验证提供者的真实行为。
- "契约测试能替代 E2E 吗？" → 不能。契约只验证接口约定，不验证业务流程、多接口协作与 UI。
- "为什么契约里用匹配器而不是固定值？" → 契约应约束结构与类型而非具体值，否则提供者的正常数据变更会造成大量误报。

#### 3.7 易错点

- 契约里硬编码具体值（如 `name: '张三'`）：提供者换数据就失败，契约变成"数据快照测试"。
- 契约只由提供者写：失去"消费者驱动"的意义，无法反映消费者的真实依赖。
- 没有 `provider states`：提供者无法准备契约要求的数据，验证要么失败要么只能验证空数据路径。
- 契约文件不发布到 Broker、没有 `can-i-deploy` 门禁：契约退化成"一份本地文档"，无法在部署前阻断破坏性变更。
- 把契约测试当 E2E 用（试图覆盖业务流程）：既跑不快，也覆盖不全，两头不讨好。
