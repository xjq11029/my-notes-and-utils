## 一、测试框架对比：Vitest vs Jest

| 维度 | Vitest | Jest |
|---|---|---|
| 出品方 | Vite 团队 | Meta（Facebook） |
| 构建工具 | Vite（ESBuild） | 自定义（babel-jest） |
| 配置复用 | 直接复用 vite.config.ts | 独立 jest.config.ts |
| ESM 支持 | 原生支持 | 需配置（experimental） |
| TypeScript | 开箱即用 | 需 ts-jest 或 @babel/preset-typescript |
| HMR 测试运行 | 支持 | 不支持 |
| 浏览器模式 | 支持（Playwright） | 不支持 |
| 转译速度 | 极快（ESBuild） | 较快（Babel） |
| API 兼容性 | 兼容 Jest API | 原生 API |
| 社区生态 | 快速增长 | 极其成熟 |
| 插件生态 | 兼容部分 Jest 插件 | 极其丰富 |
| 迁移成本 | 从 Jest 迁移成本低 | 从 Vitest 迁移成本低 |
| 适用场景 | Vite 项目、新项目 | Webpack/CRA 项目、老旧项目 |

**选择建议**：
- 使用 Vite 构建的项目 → **Vitest**
- 使用 Webpack/CRA 的项目且无迁移计划 → **Jest**
- 新项目启动 → **Vitest**
- 需要浏览器模式测试 → **Vitest**
- 大量现有 Jest 自定义插件 → **Jest**

## 二、E2E 工具对比：Playwright vs Cypress

| 维度 | Playwright | Cypress |
|---|---|---|
| 出品方 | Microsoft | Cypress.io |
| 开源协议 | Apache 2.0 | MIT |
| 支持浏览器 | Chromium、Firefox、WebKit | Chromium、Firefox、Edge（实验性） |
| 语言支持 | JS/TS、Python、Java、.NET | 仅 JS/TS |
| 多标签页 | 原生支持 | 不支持（需插件） |
| 多浏览器并行 | 原生支持 | 不支持 |
| 网络拦截 | 原生 route API | 原生 intercept API |
| 自动等待 | 内置（可操作性检查） | 内置 |
| 移动端模拟 | 原生支持 | 通过 viewport 配置 |
| 组件测试 | 支持（实验性） | 支持 |
| 视觉回归 | 内置 toHaveScreenshot | 需插件（cypress-plugin-snapshots） |
| 运行速度 | 快（并行 + Context 复用） | 较慢（单浏览器串行） |
| 调试体验 | Trace Viewer、VS Code 插件 | Time Travel、实时重载 |
| 社区生态 | 快速增长 | 成熟，文档丰富 |
| 执行架构 | 独立进程（CDP） | 与浏览器同进程 |
| CI 集成 | Docker 镜像 + GitHub Actions | Dashboard 服务 |

**选择建议**：
- 需要跨浏览器测试 → **Playwright**
- 需要多标签页交互 → **Playwright**
- 需要视觉回归测试 → **Playwright**
- 需要友好的调试体验 → **Cypress**
- 需要 Dashboard 服务 → **Cypress**
- 团队使用 Python/Java → **Playwright**

## 三、Mock 方案对比：vi.mock vs MSW vs 手动 Mock

| 维度 | vi.mock | MSW | 手动 Mock |
|---|---|---|---|
| 拦截层级 | 模块导入层 | 网络请求层 | 模块导入层 |
| 使用方式 | Vitest 内置 API | 独立库（msw） | 手写 mock 模块 |
| 开发复用 | 仅测试环境 | 开发 + 测试 + Storybook | 仅测试环境 |
| 真实度 | 低（完全替换模块） | 高（拦截网络请求，组件代码不变） | 低（替换模块） |
| 配置复杂度 | 低 | 中 | 低 |
| 请求验证 | 需手动验证调用参数 | 可验证请求 URL、method、headers、body | 需手动验证 |
| 错误场景模拟 | 需手动设置 | 原生支持（500、超时、网络断开） | 需手动设置 |
| 适用场景 | 纯函数测试、模块替换 | 组件集成测试、API 层测试 | 简单模块替换 |
| 学习成本 | 低 | 中 | 低 |
| 灵活性 | 中 | 高 | 高 |

**选择建议**：
- 单元测试中替换工具函数/Store → **vi.mock**
- 组件集成测试中模拟 API 调用 → **MSW**
- 简单模块替换（如 mock 图片/样式文件） → **手动 Mock**
- 同一套 handler 需要多环境复用 → **MSW**
- 需要验证网络请求的完整信息 → **MSW**

## 四、测试类型对比：单元 vs 组件 vs 集成 vs E2E vs 视觉回归

| 维度 | 单元测试 | 组件测试 | 集成测试 | E2E 测试 | 视觉回归测试 |
|---|---|---|---|---|---|
| 测试对象 | 单个函数/模块 | 单个 UI 组件 | 多个组件协作 | 完整用户流程 | UI 外观 |
| 核心工具 | Vitest | Vitest + Testing Library | Vitest + Testing Library + MSW | Playwright / Cypress | Playwright toHaveScreenshot |
| 运行环境 | Node.js | jsdom | jsdom + MSW | 真实浏览器 | 真实浏览器 |
| 执行速度 | 毫秒级 | 秒级 | 十秒级 | 分钟级 | 秒级 |
| 维护成本 | 低 | 中 | 中高 | 高 | 中 |
| 问题定位 | 精确到行 | 精确到组件 | 精确到模块 | 模糊（需逐层排查） | 精确到像素 |
| 稳定性 | 极高 | 高 | 中 | 低 | 中（受环境影响） |
| 编写成本 | 低 | 中 | 中高 | 高 | 中 |
| 测试数量 | 最多 | 较多 | 较少 | 最少 | 适量 |
| 理想占比 | 50-60% | 20-30% | 10-15% | 5-10% | 作为 E2E 补充 |
| 典型用例数 | 100+ | 50+ | 10-20 | 2-5 | 20-50 |
| 典型测试内容 | 函数输入输出、边界条件、异常 | 渲染结果、交互行为、状态变化 | 数据流转、API 交互、路由跳转 | 关键用户路径、业务流程 | 组件样式、页面布局、响应式设计 |

**选择建议**：
- 业务逻辑和工具函数 → **单元测试**
- UI 组件交互和状态变化 → **组件测试**
- 多模块协作流程 → **集成测试**
- 关键用户路径验证 → **E2E 测试**
- 设计系统和页面布局 → **视觉回归测试**

## 五、查询方式对比：Testing Library 查询优先级

| 查询方法 | 优先级 | 使用场景 | 示例 |
|---|---|---|---|
| getByRole | 最高（1） | 按钮、输入框、导航等有明确 ARIA role 的元素 | `screen.getByRole('button', { name: '提交' })` |
| getByLabelText | 高（2） | 表单元素（通过 label 关联） | `screen.getByLabelText('用户名')` |
| getByPlaceholderText | 中（3） | 有 placeholder 的输入框 | `screen.getByPlaceholderText('请输入邮箱')` |
| getByText | 中（4） | 可见文本内容 | `screen.getByText('欢迎回来')` |
| getByDisplayValue | 中（5） | 表单元素的当前值 | `screen.getByDisplayValue('zhangsan')` |
| getByAltText | 低（6） | 图片（通过 alt 属性） | `screen.getByAltText('用户头像')` |
| getByTitle | 低（7） | 有 title 属性的元素 | `screen.getByTitle('关闭')` |
| getByTestId | 最低（8） | 最后手段，当其他查询都无法使用时 | `screen.getByTestId('submit-btn')` |

**查询变体**：
- `getBy...` → 找不到抛错（同步）
- `queryBy...` → 找不到返回 null（用于断言不存在）
- `findBy...` → 返回 Promise（用于异步等待）
- `getAllBy...` / `queryAllBy...` / `findAllBy...` → 复数形式
