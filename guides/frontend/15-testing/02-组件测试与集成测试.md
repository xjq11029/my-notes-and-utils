## 一、核心概念

### 1.1 组件测试的"用户视角"原则

组件测试的核心原则是：**从用户的角度测试组件，而不是从实现细节的角度**。Testing Library 的设计哲学正是基于这一原则。

**盲人使用读屏软件类比**：

想象一个盲人用户使用读屏软件浏览你的网页。读屏软件通过"角色"（Role）来理解页面元素——按钮是"button"、输入框是"textbox"、导航栏是"navigation"。Testing Library 的 `getByRole` 查询就像读屏软件一样，通过元素的语义角色来定位元素。

```typescript
// 用户视角 vs 实现细节视角

// 坏：从实现细节角度测试（测试 CSS 类名、state 值）
it('点击按钮后 state 更新为 true', () => {
  const { container } = render(<LoginForm />);
  const button = container.querySelector('.submit-btn'); // 依赖 CSS 类名
  fireEvent.click(button);
  // 断言 state 值...（无法访问）
});

// 好：从用户视角测试（测试用户看到和操作的）
it('用户填写表单后点击提交按钮', async () => {
  render(<LoginForm />);

  // 用户通过标签找到输入框
  const usernameInput = screen.getByLabelText('用户名');
  const passwordInput = screen.getByLabelText('密码');

  // 用户输入
  await userEvent.type(usernameInput, 'zhangsan');
  await userEvent.type(passwordInput, 'password123');

  // 用户通过按钮文字找到提交按钮
  const submitButton = screen.getByRole('button', { name: '登录' });
  await userEvent.click(submitButton);

  // 用户看到加载状态
  expect(screen.getByText('登录中...')).toBeInTheDocument();
});
```

**Testing Library 的核心原则**：

```typescript
// 1. 查询方式应与用户交互方式一致
// 用户通过"看到的内容"定位元素，而非通过 CSS 类名或 DOM 结构
screen.getByText('欢迎回来');              // 用户看到文字
screen.getByRole('button', { name: '提交' }); // 用户看到按钮
screen.getByLabelText('邮箱地址');           // 用户看到标签

// 2. 断言应验证用户能看到的结果
expect(screen.getByText('操作成功')).toBeInTheDocument(); // 用户看到提示
expect(submitButton).toBeDisabled();                       // 用户看到按钮禁用

// 3. 避免测试实现细节
// 不要测试：state 值、props 传递、内部方法调用
// 应该测试：渲染结果、用户交互后的 UI 变化
```

### 1.2 getByRole/getByLabelText/getByText vs CSS 选择器

| 查询方法 | 优先级 | 原理 | 示例 |
|---|---|---|---|
| `getByRole` | 最高 | 通过 ARIA 角色（button、textbox、heading）查询 | `screen.getByRole('button', { name: '提交' })` |
| `getByLabelText` | 高 | 通过 label 的文本内容查询关联的表单元素 | `screen.getByLabelText('用户名')` |
| `getByPlaceholderText` | 中 | 通过 placeholder 属性查询 | `screen.getByPlaceholderText('请输入邮箱')` |
| `getByText` | 中 | 通过元素的文本内容查询 | `screen.getByText('欢迎')` |
| `getByDisplayValue` | 中 | 通过表单元素的当前值查询 | `screen.getByDisplayValue('zhangsan')` |
| `getByAltText` | 低 | 通过图片的 alt 属性查询 | `screen.getByAltText('用户头像')` |
| `getByTitle` | 低 | 通过 title 属性查询 | `screen.getByTitle('关闭')` |
| `getByTestId` | 最低 | 通过 data-testid 属性查询 | `screen.getByTestId('submit-btn')` |

```typescript
// 查询优先级示例
describe('查询方法对比', () => {
  it('优先使用 getByRole（语义化最强）', () => {
    render(<button>提交订单</button>);
    // 最佳：通过角色查询
    expect(screen.getByRole('button', { name: '提交订单' })).toBeInTheDocument();
  });

  it('getByLabelText 用于表单元素', () => {
    render(
      <>
        <label htmlFor="email">邮箱地址</label>
        <input id="email" type="email" />
      </>
    );
    // 通过 label 关联查询 input
    expect(screen.getByLabelText('邮箱地址')).toBeInTheDocument();
  });

  it('getByTestId 仅作为最后手段', () => {
    render(<div data-testid="complex-component">...</div>);
    // 最后手段：当其他查询方式都无法使用时
    expect(screen.getByTestId('complex-component')).toBeInTheDocument();
  });

  // 查询变体
  // getBy...    → 找不到元素时抛出错误
  // queryBy...  → 找不到元素时返回 null（用于断言元素不存在）
  // findBy...   → 返回 Promise，等待元素出现（用于异步渲染）
  it('queryByText 用于断言元素不存在', () => {
    render(<div>Hello</div>);
    expect(screen.queryByText('World')).toBeNull();
  });

  it('findByText 用于等待异步渲染', async () => {
    render(<AsyncComponent />);
    // 等待异步渲染完成后查找
    expect(await screen.findByText('加载完成')).toBeInTheDocument();
  });

  // getAllBy... / queryAllBy... / findAllBy... 用于多个匹配
  it('getAllByRole 获取多个匹配元素', () => {
    render(
      <ul>
        <li>项目 1</li>
        <li>项目 2</li>
        <li>项目 3</li>
      </ul>
    );
    const items = screen.getAllByRole('listitem');
    expect(items).toHaveLength(3);
  });
});
```

### 1.3 userEvent vs fireEvent

`userEvent` 模拟真实用户的完整操作序列，而 `fireEvent` 仅触发单个 DOM 事件。

```typescript
// ========================
// userEvent vs fireEvent 对比
// ========================

// fireEvent：仅触发 click 事件
// 缺点：不模拟用户在点击前的 hover、focus 等行为
fireEvent.click(button);

// userEvent：模拟完整的用户操作序列
// 优点：click 会触发 pointerdown → mousedown → focus → mouseup → click
//        type 会触发 focus → keydown → keyup → input → change
await userEvent.click(button);
await userEvent.type(input, 'hello');

// 实际场景对比
describe('userEvent vs fireEvent', () => {
  it('fireEvent 可能遗漏关键事件（如 focus）', () => {
    const handleFocus = vi.fn();
    render(<input onFocus={handleFocus} />);

    fireEvent.click(screen.getByRole('textbox'));

    // fireEvent.click 不会触发 focus 事件！
    expect(handleFocus).not.toHaveBeenCalled();
  });

  it('userEvent 模拟完整的用户操作链', async () => {
    const handleFocus = vi.fn();
    const handleChange = vi.fn();
    const handleKeyDown = vi.fn();

    render(
      <input
        onFocus={handleFocus}
        onChange={handleChange}
        onKeyDown={handleKeyDown}
      />
    );

    const input = screen.getByRole('textbox');
    await userEvent.type(input, 'a');

    // userEvent.type 会触发完整的键盘事件链
    expect(handleFocus).toHaveBeenCalled();  // 输入前先聚焦
    expect(handleKeyDown).toHaveBeenCalled(); // 键盘按下
    expect(handleChange).toHaveBeenCalled();  // 值变化
  });
});
```

## 二、底层原理

### 2.1 Testing Library 查询优先级

Testing Library 的查询优先级是经过深思熟虑的设计，遵循"越接近用户交互方式，优先级越高"的原则。

```typescript
// ========================
// 查询优先级的设计原理
// ========================

// 优先级从高到低：
// 1. getByRole - 最接近辅助技术（读屏软件）的查询方式
// 2. getByLabelText - 用户通过表单标签定位元素
// 3. getByPlaceholderText - 用户通过占位符文字定位
// 4. getByText - 用户通过可见文字定位
// 5. getByDisplayValue - 用户通过当前值定位
// 6. getByAltText - 用户通过图片替代文字定位
// 7. getByTitle - 用户通过悬停提示定位
// 8. getByTestId - 纯开发者视角，用户无法感知

// 底层实现原理：查询函数都基于 DOM Testing Library 的 queryHelpers
// 每种查询实际上是对 queryAllByAttribute 的封装

// getByRole 的简化实现原理
function getByRole(container: HTMLElement, role: string, options?: { name?: string }) {
  // 1. 获取所有匹配 ARIA role 的元素
  const elements = queryAllByRole(container, role);

  // 2. 如果指定了 name，通过 accessible name 进一步过滤
  if (options?.name) {
    return elements.filter(el => computeAccessibleName(el) === options.name);
  }

  return elements;
}

// computeAccessibleName 是 W3C AccName 规范的实现
// 它按优先级计算元素的可访问名称：
// 1. aria-labelledby 引用的元素文本
// 2. aria-label 属性值
// 3. 关联的 label 元素文本
// 4. 元素的文本内容
// 5. title 属性值
```

### 2.2 userEvent 的事件链

```typescript
// ========================
// userEvent 的事件链原理
// ========================

// userEvent.click 的事件序列（v14+）
// 1. pointerover   - 鼠标悬停
// 2. pointerenter  - 鼠标进入
// 3. pointerdown   - 鼠标按下
// 4. mousedown     - 鼠标按下（兼容事件）
// 5. focus         - 元素获得焦点
// 6. focusin       - 焦点进入（冒泡）
// 7. pointerup     - 鼠标释放
// 8. mouseup       - 鼠标释放（兼容事件）
// 9. click         - 点击事件

// userEvent.type 的事件序列（输入 'a'）
// 1. pointerover → pointerenter → pointerdown → mousedown
// 2. focus → focusin → pointerup → mouseup → click
// 3. keydown('a') → keypress('a') → input → keyup('a')

// 实际案例：为什么 userEvent 更可靠
describe('用户交互事件链', () => {
  it('click 事件链确保所有中间件正常触发', async () => {
    const events: string[] = [];
    const trackEvent = (name: string) => () => events.push(name);

    render(
      <button
        onPointerDown={trackEvent('pointerdown')}
        onMouseDown={trackEvent('mousedown')}
        onFocus={trackEvent('focus')}
        onMouseUp={trackEvent('mouseup')}
        onClick={trackEvent('click')}
      >
        点击我
      </button>
    );

    await userEvent.click(screen.getByRole('button'));

    // 验证完整的事件链
    expect(events).toEqual([
      'pointerdown',
      'mousedown',
      'focus',
      'mouseup',
      'click',
    ]);
  });

  it('type 事件链确保输入校验正常触发', async () => {
    const handleInput = vi.fn();
    render(<input onInput={handleInput} />);

    await userEvent.type(screen.getByRole('textbox'), 'hello');

    // type 触发 5 次 input 事件（每个字符一次）
    expect(handleInput).toHaveBeenCalledTimes(5);
  });
});
```

### 2.3 集成测试中的 MSW

MSW（Mock Service Worker）在集成测试中拦截网络请求，让组件在接近真实环境的条件下接受测试。

```typescript
// ========================
// MSW 在集成测试中的工作原理
// ========================

// MSW 架构：
// 浏览器环境：通过 Service Worker 拦截请求
// Node.js 环境：通过拦截 globalThis.fetch / XMLHttpRequest 实现

// 在测试环境中，MSW 使用 setupServer 创建服务端拦截器
// 流程：
// 1. setupServer 创建拦截器
// 2. server.listen() 激活拦截（在 beforeAll 中调用）
// 3. 组件发送请求时，MSW 匹配 handler 并返回 mock 数据
// 4. 组件状态更新，断言 UI 变化
// 5. server.close() 关闭拦截器（在 afterAll 中调用）

// 集成测试与单元测试中 MSW 的区别：
// 单元测试：测试 API 函数本身，验证函数返回值和错误处理
// 集成测试：测试组件 + API 交互，验证整个用户流程的 UI 表现

// 集成测试中 MSW 的典型用法
import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

const server = setupServer(
  // 正常场景
  http.get('/api/products', () => {
    return HttpResponse.json([
      { id: '1', name: 'iPhone', price: 6999 },
      { id: '2', name: 'MacBook', price: 14999 },
    ]);
  }),

  // 登录接口
  http.post('/api/login', async ({ request }) => {
    const body = await request.json() as { username: string; password: string };
    if (body.username === 'admin' && body.password === '123456') {
      return HttpResponse.json({ token: 'mock-token-xxx' });
    }
    return HttpResponse.json(
      { error: '用户名或密码错误' },
      { status: 401 }
    );
  })
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers()); // 重置 handler 确保测试隔离
afterAll(() => server.close());
```

### 2.4 Vitest Browser Mode 原理

Vitest Browser Mode 允许测试在真实浏览器环境中运行，而非 jsdom 模拟环境。

```typescript
// ========================
// Vitest Browser Mode 原理
// ========================

// 架构：
// Vitest → WebSocket → Playwright → 真实浏览器（Chromium/Firefox/WebKit）
// 测试代码在浏览器中执行，通过 WebSocket 将结果回传给 Vitest

// jsdom 与真实浏览器的关键差异：
// 1. jsdom 不支持布局计算（getBoundingClientRect 返回全 0）
// 2. jsdom 不支持 CSS 动画和过渡
// 3. jsdom 不支持 IntersectionObserver / ResizeObserver
// 4. jsdom 不支持 Canvas / WebGL
// 5. jsdom 不支持 localStorage 的存储配额检查

// 配置示例
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    // 启用浏览器模式
    browser: {
      enabled: true,
      // 浏览器名称
      name: 'chromium', // 'chromium' | 'firefox' | 'webkit'
      // 是否为无头模式
      headless: true,
      // 提供者
      provider: 'playwright',
    },
  },
});

// 浏览器模式测试示例
// 文件名需以 .browser.test.ts 结尾

// 在浏览器环境中可以测试：
// - 真实的布局和样式计算
// - IntersectionObserver 懒加载
// - Canvas 渲染
// - localStorage/sessionStorage
// - 真实的 CSS 动画

// 选择建议：
// - 纯逻辑测试 → Vitest + Node 环境（最快）
// - 组件交互测试 → Vitest + jsdom（够用）
// - 布局/样式/Canvas 测试 → Vitest Browser Mode（最接近真实环境）
```

```typescript
// ========================
// src/components/LoginForm.tsx —— 登录表单组件
// ========================

import React, { useState } from 'react';

interface LoginFormProps {
  onSubmit: (username: string, password: string) => Promise<void>;
}

export function LoginForm({ onSubmit }: LoginFormProps) {
  const [username, setUsername] = useState('');
  const [password, setPassword] = useState('');
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState('');

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    setError('');

    // 表单校验
    if (!username.trim()) {
      setError('请输入用户名');
      return;
    }
    if (password.length < 6) {
      setError('密码至少 6 位');
      return;
    }

    setLoading(true);
    try {
      await onSubmit(username, password);
    } catch (err: any) {
      setError(err.message || '登录失败');
    } finally {
      setLoading(false);
    }
  };

  return (
    <form onSubmit={handleSubmit} aria-label="登录表单">
      <div>
        <label htmlFor="username">用户名</label>
        <input
          id="username"
          type="text"
          value={username}
          onChange={e => setUsername(e.target.value)}
          placeholder="请输入用户名"
        />
      </div>

      <div>
        <label htmlFor="password">密码</label>
        <input
          id="password"
          type="password"
          value={password}
          onChange={e => setPassword(e.target.value)}
          placeholder="请输入密码"
        />
      </div>

      {error && <div role="alert">{error}</div>}

      <button type="submit" disabled={loading}>
        {loading ? '登录中...' : '登录'}
      </button>
    </form>
  );
}


// ========================

// ========================
```

### 3.2 Vue 组件测试

```typescript
// ========================
// src/components/Counter.vue —— Vue 计数器组件
// ========================

<template>
  <div class="counter">
    <h2>计数器：{{ count }}</h2>
    <p v-if="count >= 10" role="alert" class="warning">
      计数已达到上限！
    </p>
    <div class="actions">
      <button
        @click="decrement"
        :disabled="count <= 0"
        aria-label="减少"
      >
        -1
      </button>
      <button
        @click="increment"
        :disabled="count >= 10"
        aria-label="增加"
      >
        +1
      </button>
      <button @click="reset" aria-label="重置">
        重置
      </button>
    </div>
  </div>
</template>

<script setup lang="ts">
import { ref } from 'vue';

const props = withDefaults(defineProps<{
  initialCount?: number;
}>(), {
  initialCount: 0,
});

const emit = defineEmits<{
  change: [count: number];
}>();

const count = ref(props.initialCount);

function increment() {
  if (count.value < 10) {
    count.value++;
    emit('change', count.value);
  }
}

function decrement() {
  if (count.value > 0) {
    count.value--;
    emit('change', count.value);
  }
}

function reset() {
  count.value = 0;
  emit('change', 0);
}
</script>
```

```typescript
// ========================

import { describe, it, expect, beforeAll, afterAll, afterEach } from 'vitest';
import { render, screen, waitFor } from '@testing-library/react';

import { UserProfile } from '../components/UserProfile';

      email: 'zhangsan@example.com',
      avatar: 'https://cdn.example.com/avatar/001.png',
    });

    const body = await request.json();
    return HttpResponse.json({ id: '1', ...body });
  })
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

describe('UserProfile 组件（MSW 场景测试）', () => {
  // ========================
  // 场景 1：正常加载
  // ========================
  it('成功加载用户信息', async () => {
    render(<UserProfile />);

    // 初始状态：加载中
    expect(screen.getByText('加载中...')).toBeInTheDocument();

    // 等待加载完成
    await waitFor(() => {
      expect(screen.getByText('张三')).toBeInTheDocument();
    });

    expect(screen.getByText('zhangsan@example.com')).toBeInTheDocument();
  });

  // ========================
  // 场景 2：服务器错误（500）
  // ========================
  it('服务器返回 500 时显示错误信息', async () => {
    // 覆盖 handler 模拟服务器错误
    server.use(
      http.get('/api/user/profile', () => {
        return new HttpResponse(null, { status: 500 });
      })
    );

    render(<UserProfile />);

    await waitFor(() => {
      expect(screen.getByText('加载失败，请稍后重试')).toBeInTheDocument();
    });
  });

  // ========================
  // 场景 3：网络超时
  // ========================
  it('网络超时时显示超时提示', async () => {
    server.use(
      http.get('/api/user/profile', async () => {
        await delay(5000); // 模拟 5 秒延迟

      })

    render(<UserProfile timeout={100} />);

    await waitFor(() => {
      expect(screen.getByText('请求超时，请检查网络连接')).toBeInTheDocument();
    }, { timeout: 5000 });
  });

  // ========================
  // 场景 4：401 未授权
  // ========================
  it('未授权时跳转登录页', async () => {
    server.use(
      http.get('/api/user/profile', () => {
        return HttpResponse.json(
          { error: 'Unauthorized' },
          { status: 401 }
        );
      })
    );

  // ========================

      })
```

## 四、常见面试题

**Q1：Testing Library 的查询优先级是如何设计的？为什么？**

答案要点：优先级从高到低为 getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId。设计原则是"越接近用户交互方式，优先级越高"。getByRole 最接近辅助技术（读屏软件）的查询方式，因此优先级最高；getByTestId 是纯开发者视角（用户无法感知 data-testid），因此优先级最低。这种设计鼓励开发者编写可访问性更好的组件。

**Q2：userEvent 和 fireEvent 的核心区别是什么？什么时候应该使用 userEvent？**

答案要点：userEvent 模拟真实用户的完整操作序列（如 click 触发 pointerdown → mousedown → focus → mouseup → click 完整事件链），fireEvent 仅触发单个 DOM 事件。userEvent 更接近真实用户行为，能发现 fireEvent 遗漏的 bug（如缺少 focus 事件导致表单校验不触发）。几乎所有场景都应该使用 userEvent，只有在需要测试特定 DOM 事件处理时才使用 fireEvent。

**Q3：什么是 MSW？它在测试中相比传统 Mock 方案有什么优势？**

答案要点：MSW（Mock Service Worker）通过 Service Worker（浏览器）或 Node.js 拦截器（测试环境）拦截网络请求。优势包括：同一套 handler 可同时用于开发、测试和 Storybook 演示；请求拦截发生在网络层，组件代码无需修改；支持 REST 和 GraphQL；可以模拟各种网络异常场景（500、超时、网络断开）。相比传统 Mock 方案（如 vi.mock），MSW 让测试更接近真实环境。

**Q4：Vitest Browser Mode 相比 jsdom 的优势和适用场景是什么？**

答案要点：jsdom 是纯 JavaScript 实现的 DOM 模拟，不支持布局计算、CSS 动画、IntersectionObserver、Canvas 等。Vitest Browser Mode 在真实浏览器中运行测试，能测试这些场景。适用场景：需要测试布局和样式计算、IntersectionObserver 懒加载、Canvas 渲染、真实的 CSS 动画和过渡效果。缺点是运行速度比 jsdom 慢，配置更复杂。

**Q5：集成测试和组件测试的边界在哪里？如何判断一个测试应该写在哪个层级？**

答案要点：组件测试关注单个组件的独立行为（如登录表单的校验、按钮的禁用状态），不依赖外部 API 和路由。集成测试关注多个组件/模块的协作流程（如商品列表 → 加购 → 购物车 → 提交订单），通常涉及 API 调用和路由跳转。判断标准：如果测试需要多个组件协同工作且涉及真实的数据流转，就属于集成测试；如果测试只关注单个组件的 UI 交互，就属于组件测试。

## 五、避坑指南

| 错误现象 | 产生原因 | 正确做法 |
|---|---|---|
| 组件重构后测试大量失败，但用户功能正常 | 测试绑定了 DOM 结构（如 container.querySelector('.btn')）而非语义化查询 | 始终使用 getByRole/getByLabelText/getByText 等语义化查询；测试应该验证用户看到的结果，而非 DOM 结构 |
| 使用 fireEvent 测试表单，但实际用户操作时表单校验不触发 | fireEvent.change 只触发 change 事件，缺少 focus 和 blur 事件，导致某些校验逻辑（如 onBlur 校验）未执行 | 所有用户交互测试统一使用 userEvent；userEvent.type 会触发完整的 focus → keydown → input → change → blur 事件链 |
| 集成测试中未 resetHandlers，导致不同测试用例的 mock 相互干扰 | MSW 的 handler 在测试间共享，临时覆盖的 handler 会污染后续测试 | 在 afterEach 中调用 server.resetHandlers() 重置 handler；每个测试用例中需要特殊场景时使用 server.use() 临时覆盖 |
