# 02-组件测试与集成测试 - 导览

---

## 1.1 组件测试的"用户视角"原则（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 组件测试的核心原则是"从用户角度测试组件，而非从实现细节角度"，Testing Library 的语义化查询正是基于这一原则设计 |
| 能做什么 | 以盲人使用读屏软件类比——getByRole 就像读屏软件通过"角色"理解页面元素，让测试更贴近真实用户的使用方式 |
| 怎么用 | 使用 screen.getByRole('button') 替代 container.querySelector('.btn')；使用 screen.getByLabelText('用户名') 替代 screen.getByTestId('username-input') |
| 原理和工作流程 | 用户通过视觉（文字、标签、按钮）与页面交互 → Testing Library 通过语义化查询模拟这种交互 → 断言验证用户能看到的结果 |
| 缺点 | 对于复杂 UI 组件（如 Canvas、SVG 图表），语义化查询可能不够用，需要借助 getByTestId 作为补充 |

---

## 1.2 getByRole/getByLabelText/getByText vs CSS 选择器（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Testing Library 提供 8 种查询方法，按优先级从高到低排列：getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText → getByTitle → getByTestId |
| 能做什么 | 每种查询方法都有对应的 getBy/queryBy/findBy 变体和复数形式（getAllBy/queryAllBy/findAllBy），覆盖同步查找、不存在断言、异步等待等场景 |
| 怎么用 | getByRole 用于按钮/输入框等 → getByLabelText 用于表单元素 → getByText 用于文本内容 → getByTestId 作为最后手段 |
| 原理和工作流程 | 每种查询基于 DOM Testing Library 的 queryHelpers 封装，getByRole 底层通过 W3C AccName 规范计算元素的 accessible name |
| 缺点 | 需要组件具备良好的可访问性（ARIA role、label 关联），否则无法使用高优先级查询；getByText 对多语言应用不友好 |

## 1.3 userEvent vs fireEvent（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | userEvent 模拟真实用户的完整操作序列（事件链），fireEvent 仅触发单个 DOM 事件。userEvent 是 Testing Library 推荐的交互方式 |
| 能做什么 | userEvent.click 触发 pointerdown → mousedown → focus → mouseup → click 完整事件链；userEvent.type 触发 focus → keydown → keyup → input → change |
| 怎么用 | 所有组件测试中的用户交互统一使用 await userEvent.xxx()；fireEvent 仅在需要测试特定 DOM 事件处理时使用 |
| 原理和工作流程 | userEvent 内部维护事件调度器，按真实用户操作顺序依次触发事件，确保中间件（如 focus handler、blur handler）正常执行 |
| 缺点 | userEvent 是异步操作（需要 await），比 fireEvent 稍慢；部分底层 DOM 事件（如 compositionstart）可能需要额外配置 |

## 2.1 Testing Library 查询优先级（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 查询优先级的设计遵循"越接近用户交互方式，优先级越高"原则，getByRole 最接近辅助技术，getByTestId 最接近开发者视角 |
| 能做什么 | 引导开发者编写可访问性更好的组件；优先级高的查询方式更稳定（不易因 DOM 结构调整而破坏） |
| 怎么用 | 开发组件时确保正确的 ARIA role 和 label 关联 → 测试时优先使用 getByRole 和 getByLabelText → 仅在必要时使用 getByTestId |
| 原理和工作流程 | getByRole 底层通过 W3C AccName 规范计算元素的可访问名称（aria-labelledby → aria-label → label 文本 → 元素文本 → title） |
| 缺点 | 需要团队对可访问性有基本认知；部分 UI 库的组件可能缺少正确的 ARIA 属性 |

---

## 2.2 userEvent 的事件链（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | userEvent 的每个操作都对应一个完整的事件链，如 click 包含 9 个事件（pointerover → pointerenter → pointerdown → mousedown → focus → focusin → pointerup → mouseup → click） |
| 能做什么 | 确保测试能发现因缺少中间事件而导致的 bug（如缺少 focus 事件导致表单校验未触发） |
| 怎么用 | 使用 userEvent.click/type/tab/keyboard 等方法 → 在需要验证事件链的测试中捕获中间事件并断言 |
| 原理和工作流程 | userEvent 内部维护事件调度器（Event Scheduler），按 W3C 规范的事件触发顺序依次派发事件 |
| 缺点 | 事件链的长度和顺序可能因 userEvent 版本更新而变化；部分非标准事件需要额外处理 |

## 2.3 集成测试中的 MSW（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | MSW 在集成测试中通过 Service Worker（浏览器）或 Node.js 拦截器（测试环境）拦截网络请求，让组件在接近真实环境的条件下测试 |
| 能做什么 | 不依赖真实后端即可测试完整的用户流程（数据加载 → 交互 → 提交）；同一套 handler 用于开发、测试和 Storybook |
| 怎么用 | setupServer 创建服务端实例 → beforeAll 启动 → 定义 http.get/post 等 handler → 组件发送请求时被 MSW 拦截并返回 mock 数据 |
| 原理和工作流程 | MSW 在 Node.js 中拦截 globalThis.fetch 和 XMLHttpRequest → 匹配请求到 handler → 返回 mock 响应 → 组件按正常流程更新 UI |
| 缺点 | handler 需要手动维护与真实 API 的一致性；复杂场景下 handler 配置较繁琐；需要额外的学习成本 |

## 2.4 Vitest Browser Mode 原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Vitest Browser Mode 允许测试在真实浏览器（Chromium/Firefox/WebKit）中运行，而非 jsdom 模拟环境，通过 WebSocket 将结果回传给 Vitest |
| 能做什么 | 测试 jsdom 不支持的场景：布局计算、CSS 动画、IntersectionObserver、Canvas 渲染、localStorage 存储配额 |
| 怎么用 | 配置 vitest.config.ts 的 browser 选项 → 测试文件以 .browser.test.ts 结尾 → 运行 pnpm vitest |
| 原理和工作流程 | Vitest → WebSocket → Playwright → 真实浏览器 → 测试代码在浏览器中执行 → 结果通过 WebSocket 回传 Vitest |
| 缺点 | 运行速度比 jsdom 慢；配置更复杂；需要安装 Playwright 浏览器二进制文件 |

## 3.1 React 组件测试（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 @testing-library/react + userEvent 对 React 组件进行测试，覆盖表单交互、按钮点击、条件渲染、加载状态、错误处理等场景 |
| 能做什么 | 验证登录表单的校验逻辑、提交状态、成功/失败回调；确保组件在不同交互状态下的 UI 表现正确 |
| 怎么用 | render 渲染组件 → screen.getByRole/getByLabelText 定位元素 → await userEvent.xxx 模拟交互 → expect 断言 UI 变化 |
| 原理和工作流程 | 遵循 AAA 模式（Arrange → Act → Assert）；render 将组件渲染到 jsdom → 模拟用户操作 → 断言 DOM 变化 |
| 缺点 | 异步组件测试需要 waitFor 等待，增加代码复杂度；复杂组件状态管理测试需要 mock 外部依赖 |

## 3.2 Vue 组件测试（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 @testing-library/vue + userEvent 对 Vue 3 组件进行测试，覆盖模板渲染、事件触发、props 传递、emit 验证、条件渲染 |
| 能做什么 | 验证 Vue 计数器的增减逻辑、禁用状态、上限警告；测试组件的 props 和 emit 事件 |
| 怎么用 | render(Counter, { props: { initialCount: 5 } }) 渲染组件 → screen.getByRole 定位 → userEvent.click 交互 → emitted() 验证事件 |
| 原理和工作流程 | @testing-library/vue 封装了 Vue 3 的 createApp 和 mount，将组件渲染到 jsdom 并提供语义化查询 API |
| 缺点 | Vue 的响应式系统在 jsdom 中的行为与真实浏览器略有差异；emit 验证需要额外的 emitted() API |

## 3.3 集成测试：购物车流程（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 集成测试验证多组件协作的完整流程：浏览商品列表 → 加入购物车 → 查看购物车 → 修改数量 → 验证总价 → 提交订单 |
| 能做什么 | 发现组件间数据传递、状态同步、路由切换等方面的 bug；验证购物车价格计算和订单提交的完整业务逻辑 |
| 怎么用 | MSW 模拟后端 API → render 渲染整个 App → 按用户流程逐步操作 → 每步断言 UI 变化 → 最终验证订单确认 |
| 原理和工作流程 | 集成测试运行在 jsdom 中 → MSW 拦截网络请求 → 组件按真实流程渲染和交互 → 断言验证集成行为 |
| 缺点 | 集成测试运行时间较长；需要维护完整的 MSW handler 集合；测试失败时需要逐层排查问题 |

## 3.4 MSW 实战：多场景模拟（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 MSW 模拟成功、500 错误、网络超时、401 未授权、空数据、更新操作六种场景，全面测试组件的异常处理能力 |
| 能做什么 | 确保组件在各种网络条件下都有正确的 UI 反馈（加载中、错误提示、空状态、未授权提示） |
| 怎么用 | server.use() 临时覆盖 handler → 模拟特定错误场景 → render 组件 → 断言对应的错误提示 UI |
| 原理和工作流程 | 每个测试用例独立覆盖 handler → 组件发送请求被拦截 → MSW 返回模拟的错误响应 → 组件显示对应的错误 UI |
| 缺点 | 需要为每种异常场景编写独立的 handler；超时模拟需要使用 vi.useFakeTimers 避免真实等待 |
