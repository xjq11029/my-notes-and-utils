# 通用代码审查指令（CODE_REVIEW_GUIDE）

- **版本**：v1.1.1
- **版本规则**：语义化版本。新增审查维度、新增章节或新阶段 → 次版本号 +1；修订措辞、修正错误 → 修订号 +1。每次变更须在 `_GUIDE_CHANGELOG.md` 登记（见第五部分；审查指南与分析指南的版本演进已合并记录于该单一文件）。

> **用途**：本文件是一份供 Agent 智能体加载的**代码审查**指令规范。Agent 读取本文件后，须对**用户指定的变更集（diff）或文件清单**进行质量把关，产出带严重级别、可直接执行的审查意见与合入结论。
>
> **与 CODE_ANALYSIS_GUIDE 的分工**：
>
> | | CODE_ANALYSIS_GUIDE（理解） | CODE_REVIEW_GUIDE（本文件，把关） |
> |---|---|---|
> | 回答的问题 | 这段代码是什么、怎么运转？ | 这次改动有什么问题、能不能合入？ |
> | 分析对象 | 全量文件 | 变更集（diff）或指定文件 |
> | 产出 | 调用图 + 功能说明文档 | 分级审查意见 + 合入结论 |
> | 共享资产 | 生成 `_PROJECT_PROFILE.md` | 读取并复用该画像（见 2.0 节） |

## 第一部分：使用说明（面向人）

### 1.1 如何使用本文件

- **方式 A（推荐）**：将本文件放入目标项目根目录（可与 CODE_ANALYSIS_GUIDE.md 并存），对话中告知 Agent 审查范围。
- **方式 B**：全文粘贴到对话中，随后指定审查范围。

**最小可用提示词（可直接复制）**：

> 请阅读项目根目录下的 CODE_REVIEW_GUIDE.md，严格按规范审查当前分支相对 main 的全部变更，使用标准审查。先输出变更集摘要与影响面分析，经我确认后再出具审查意见。

### 1.2 如何指定审查范围（四选一）

1. **提交范围**：如 `HEAD~3..HEAD`、两个 commit 哈希之间；
2. **分支对比**：如"当前分支相对 `main`"；
3. **暂存区 / 工作区**："审查我未提交的改动"；
4. **文件清单**：直接给出文件列表（无 git 环境时用此方式）。

### 1.3 产出位置

```
<项目根目录>/docs/code-review/
├── _REVIEW_REPORT_<日期>_<范围标识>.md   # 审查报告（每次审查一份）
├── _ITERATION_PROPOSAL.md               # 指引迭代建议（见第五部分）
└── ...
```

> 范围标识须净化文件系统非法字符后再用于文件名（如 `HEAD~3..HEAD` → `HEAD3-HEAD`、`A..B` → `A-B`）。

### 1.4 审查严格度（三档，用户指令中指定，默认标准审查）

| 档位 | 适用场景 | 行为 |
|---|---|---|
| **快速审查** | 提交前自查、时间紧 | 只报告 Blocker 与 Critical 级问题 |
| **标准审查**（默认） | 常规 MR/PR 评审 | 全部维度，Major 及以上全报；Minor 聚合、Suggestion 摘要（与 2.5.4 噪音上限一致） |
| **严格审查** | 核心模块、上线前把关 | 标准审查 + 风格/命名细节 + 测试覆盖断言 + 逐条引用项目规范 |

## 第二部分：Agent 执行指令（核心）

> 以下内容是给 Agent 的**强制性执行规范**。

### 2.0 阶段零：加载共享上下文（每次审查前必做）

1. **共享画像**：若项目存在 `docs/code-analysis/_PROJECT_PROFILE.md`（由 CODE_ANALYSIS_GUIDE 生成），必须加载——技术栈、目录职责、项目特有调用模式直接复用，**禁止重复全量探测**。画像中没有而审查必需的信息（如 lint 配置），允许补充轻量探测。
2. **覆盖层**：存在 `CODE_ANALYSIS_GUIDE.local.md` 时一并加载，冲突时覆盖层优先。
3. **项目规范源**（审查依据，按优先级）：
   - 团队规范文档（`CONTRIBUTING.md`、`docs/` 中的编码规范）
   - Lint/格式化配置（`.eslintrc*`、`checkstyle.xml`、`.golangci.yml`、`pyproject.toml` 的 lint 段等）
   - 本指引的通用审查清单（2.3 节）
4. 画像不存在时：向用户说明"未检测到项目画像，审查依据将仅基于通用清单与 lint 配置；建议先用 CODE_ANALYSIS_GUIDE 生成画像以提高审查精度"，用户确认后继续。**确认合并规则**：变更集摘要（2.1.3）与影响面结论（2.2.4）可合并为一次确认输出；用户明确要求分步确认的除外。

### 2.1 阶段一：确定审查范围与基线

1. 按 1.2 节解析用户指定的范围，用 `git diff`（或等效手段）获取变更集；无 git 环境时以用户给定的文件清单为准，并在报告中注明"无 diff 基线，按全文件审查"。
2. **diff 命令速查**（按 1.2 节范围类型）：提交范围 → `git diff <A>..<B>`；分支对比 → `git diff <base>...<head>`（三点表示从分叉点起算）；暂存区 → `git diff --cached`；工作区 → `git diff`。范围解析失败或 diff 为空时，向用户报告并确认后再继续。
3. **防错处理**：跳过二进制文件与锁文件；检测到 `<<<<<<<` 合并冲突标记时，先提示用户解决冲突再审查，不将冲突内容当作有效代码分析。
4. **分批策略**：变更文件 >50 个或单文件 diff >1000 行时，按目录/文件分批审查并逐批汇报进度，全部完成后合并为总报告。
5. 对每个变更文件区分**新增行 / 修改行 / 删除行**；上下文理解可读全文件，但**审查意见必须锚定到变更行**（纯存量问题列入"顺带发现"，与本次变更意见分开）。
6. 输出**变更集摘要**：文件数、增删行数、变更性质分类（新功能/修复/重构/配置/文档），经用户确认后进入下一阶段。

### 2.2 阶段二：影响面分析

1. 列出变更涉及的**对外符号**（导出的函数/类/接口/组件/路由/配置项）。
2. 建立**反向引用清单**：每个变更符号被哪些文件/调用方使用——
   - 项目已有 `docs/code-analysis/` 分析文档时，直接查其"被引用情况"章节复用；
   - 否则对相关文件做局部检索（只读）。
3. 公共 API、接口签名、数据库 schema、配置键、消息协议的变更，**必须列出全部调用方**并逐一评估兼容性；无法确认兼容的列入"待确认"。
4. 输出影响面结论：本次变更的**影响半径**（仅本文件 / 模块内 / 跨模块 / 全项目）。

### 2.3 阶段三：维度检查（审查清单）

对每个变更点按下表逐维度检查（不适用的维度标"N/A"，不得省略思考过程）：

| 维度 | 检查信号（示例，非穷举） |
|---|---|
| **正确性** | 边界条件（空/null/0/负数/超界）、分支遗漏、错误返回值未处理、逻辑与变更意图不符 |
| **安全性** | 注入（SQL/命令/XSS）、越权与鉴权缺失、敏感信息硬编码或日志泄露、不安全的反序列化、依赖已知漏洞 |
| **性能** | 循环内 IO/查询（N+1）、不必要的全量加载、大对象拷贝、缺失索引的查询、正则灾难回溯 |
| **并发与资源** | 竞态条件、死锁风险、连接/句柄/流未释放、goroutine/线程泄漏、共享状态无保护 |
| **可维护性** | 函数过长/嵌套过深、重复代码、魔法数字、命名误导、注释与实现不符、破坏既有分层约定 |
| **规范一致性** | 违反 2.0 节加载的项目规范与 lint 规则、与周边代码风格明显不一致 |
| **测试与可观测性** | 关键路径无测试、测试断言缺失或过弱、关键失败路径无日志、指标/追踪缺失 |

### 2.4 阶段四：产出审查报告

1. **严重级别**（每条意见必须定级，定义见附录 A）：
   `Blocker`（必须修复，阻断合入）/ `Critical`（强烈建议修复）/ `Major`（应当修复）/ `Minor`（建议改进）/ `Suggestion`（可选优化）。
2. **意见格式**（每条意见六要素，缺一不可）：

   | 要素 | 说明 |
   |---|---|
   | 位置 | `文件路径:行号`（锚定变更行） |
   | 级别 | Blocker–Suggestion |
   | 维度 | 2.3 节七维度之一 |
   | 问题描述 | 一句话说清"什么问题" |
   | 依据 | 代码片段 + 规则/原理（为什么这是问题） |
   | 建议改法 | 具体可执行的修改方案（能给代码示例就给） |

3. **合入结论**（三选一，规则见附录 A）：
   - **打回**：存在任一 Blocker；
   - **有条件通过**：无 Blocker 但存在 Critical，须修复后复检；
   - **通过**：无 Blocker/Critical（Major/Minor 可建后续任务跟踪）。
   **复检闭环**："有条件通过"须约定复检执行者（原审查 Agent 或用户指定）、复检范围（仅原 Critical 意见对应的变更行）与时限（默认 7 个自然日，可配置）；复检结论追加到原报告"校对记录"之后。超时未复检的，结论降级为"打回"并重新走全量审查。
4. 报告按第三部分模板生成到 `docs/code-review/`，并向用户汇报结论与 Top 问题摘要。

### 2.5 误报控制（强制）

1. **证据原则**：只报告能给出"代码片段 + 规则/原理"双依据的问题；说不清依据的不许报。
2. **存疑单列**：不确定是否成立的问题放入报告"待确认"区，不混入正式意见。
3. **存量隔离**：非本次变更引入的问题进"顺带发现"区，不影响合入结论。
4. **噪音上限**：Minor/Suggestion 级意见只报最有代表性的，同类问题聚合为一条并注明出现次数；禁止逐行风格轰炸。
5. **误报反馈**：用户驳回的意见记入 `_ITERATION_PROPOSAL.md`（类型"修订"），用于校准后续审查尺度。

### 2.6 阶段五：审查意见校对（出具报告前执行）

> 复用 CODE_ANALYSIS_GUIDE 第六部分的校对思想，对**审查意见本身**做质检：

1. 每条 Blocker/Critical 意见必须**自证**：重新打开源文件核对位置、行号、代码片段三者一致；任一不符立即修正或撤下。
2. 抽查 ≥30% 的 Major/Minor 意见做同样自证。
3. 检查结论逻辑：级别判定是否符合附录 A、合入结论是否与意见列表一致。
4. 校对不通过的意见修正后复检；校对记录附在报告末尾（见模板第 6 节）。

## 第四部分：附录

### 附录 A：严重级别判定细则

| 级别 | 定义 | 示例 | 对结论的影响 |
|---|---|---|---|
| Blocker | 会导致数据丢失、安全漏洞、系统崩溃、功能不可用 | SQL 注入点；鉴权绕过；必现的空指针崩溃 | 任一存在 → **打回** |
| Critical | 高概率出错的逻辑缺陷、明显性能劣化、破坏公共契约 | 边界条件错误；N+1 查询进生产路径；接口签名不兼容变更 | 存在 → **有条件通过**（修复后复检） |
| Major | 明确的不良实践，中期会产生维护成本 | 重复大段代码；资源未释放；关键路径无日志 | 不影响结论，建议本次修复 |
| Minor | 局部可读性/一致性问题 | 命名误导；魔法数字；注释过期 | 聚合报告 |
| Suggestion | 可选的更优写法 | 更简洁的惯用法 | 聚合报告，仅供参考 |

> **判级口径（空引用/崩溃类）**：以"该路径是否为高频必现"为准——高频必现（如常规查询路径无结果即崩溃）判 **Blocker**；仅低概率边界条件触发判 **Critical**。与第三部分示例（意见 #1 判 Blocker）保持一致。

### 附录 B：无 diff 环境的全文件审查规则

- 将文件视为"全部新增"，但意见仍须锚定行号；
- 影响面分析改为"该文件的对外符号 + 被引用清单"；
- 报告"基线"栏注明"全文件审查"，合入结论措辞改为"准入评估结论"。

### 附录 C：与语言相关的审查提示（速查）

- **JS/TS/Node**：`==` 宽松相等、未处理的 Promise 拒绝、`await` 缺失、闭包捕获循环变量、原型污染；
- **Python**：可变默认参数、`except:` 裸捕获、循环引用导致的内存驻留、`eval/exec`；
- **Java**：`equals`/`hashCode` 不成对、资源未 try-with-resources、线程池无界队列、序列化版本号；
- **Go**：goroutine 泄漏、channel 关闭后发送、`defer` 在循环中堆积、错误未检查（`_` 丢弃 err）；
- **C**：`malloc`/`free` 不配对、缓冲区越界（`strcpy`/`sprintf`/`memcpy` 长度错）、指针悬垂与 use-after-free、整数溢出与符号混用、未检查返回值、文件句柄/锁泄漏、`sizeof(指针)` 误用、字符串不以 `\0` 结尾、宏参数副作用（`#define SQUARE(x) x*x`）；
- **C++**：C 全部要点 + `new`/`delete` 配对与异常安全（`new` 失败、析构抛异常）、智能指针误用（裸 `new` 配 `shared_ptr`、循环引用）、基类虚析构缺失、迭代器失效、`reinterpret_cast`/`const_cast` 滥用、移动语义误用（`std::move` 后继续使用）、模板特化歧义、`const` 正确性缺失；
- **Vue/React**：响应式丢失（解构 props）、`useEffect` 依赖数组缺漏、key 用 index、渲染内副作用。

### 附录 D：C/C++ 内存安全审查专项清单

> C/C++ 审查中内存安全类问题占比最高且后果严重（详见附录 C 速查），独立成清单便于逐项核对。命中项按附录 A 定级。

| 类别 | 检查项 | 典型信号 | 常见后果 |
|---|---|---|---|
| 内存生命周期 | 申请/释放配对 | `malloc` 无 `free`；`new[]` 配 `delete`；双重释放；异常路径跳过释放 | 泄漏 / 崩溃 |
| 指针安全 | 悬垂与空指针 | 释放后继续使用；`reinterpret_cast` 强转后解引用；未判空解引用 | use-after-free / 段错误 |
| 缓冲区 | 越界读写 | `strcpy`/`sprintf`/`memcpy` 无长度或长度错；数组下标未校验 | 栈/堆破坏、任意代码执行 |
| 整数与算术 | 溢出与符号混用 | 无符号下溢；`int` 溢出参与分配/索引；`size_t` 与 `int` 混用 | 越界、拒绝服务 |
| 资源管理 | 句柄与锁 | 文件描述符/互斥锁未释放；错误分支跳过清理 | 泄漏、死锁 |
| 字符串 | 终止符 | 非 `\0` 结尾拷贝；`strlen` 越过边界 | 越界读、信息泄露 |
| 并发 | 数据竞争 | 共享状态无锁/无原子；信号处理函数调用非异步信号安全函数 | 竞态、崩溃 |
| C++ 专属 | 对象生命周期 | 基类无虚析构；裸指针管理资源；`std::move` 后继续使用；迭代器失效后使用 | 未定义行为、崩溃 |
| C++ 专属 | 异常安全 | 析构函数抛异常；异常路径资源泄漏；`noexcept` 标注与实际不符 | 程序终止、泄漏 |
| C++ 专属 | 模板与转换 | 模板特化歧义；`reinterpret_cast`/`const_cast` 滥用 | 未定义行为 |

## 第五部分：协作接口与迭代机制

### 5.1 与 CODE_ANALYSIS_GUIDE 的协作

1. **画像共享**：`_PROJECT_PROFILE.md` 由分析指南生成并维护，本指南只读复用；审查中发现画像缺失/过时的，记入 `_ITERATION_PROPOSAL.md`，不直接修改画像。
2. **分析文档复用**：`docs/code-analysis/` 中已有分析文档的模块，影响面分析直接引用其"被引用情况"章节，不重复检索。注意分析文档已按源码目录层级嵌套存放（见分析指南 v1.5.1 的 1.3 节）：源文件 `src/services/user.ts` 的分析文档位于 `docs/code-analysis/src/services/user.ts.md`。定位时按"源文件相对项目根的路径"拼接，或统一经 `_INDEX.md` 的"分析文档链接"列检索；不要假设分析文档平铺在 `docs/code-analysis/` 根目录。
3. **交接触发**：审查中遇到无法理解的模块（画像与分析文档均无覆盖），停止臆测，向用户建议：
   > "模块 `<路径>` 缺乏分析文档，建议先用 CODE_ANALYSIS_GUIDE 对其生成分析（概览模式即可），再继续审查。"
4. **职责边界**：本指南**不生成**功能说明文档；分析指南**不出具**合入结论。两者产出互链，互不替代。

### 5.2 迭代闭环（每次审查完成后执行）

1. 记录：用户驳回的意见（误报）、漏报的问题（用户人工发现的）、本指引未覆盖的检查项；
2. 生成 `docs/code-review/_ITERATION_PROPOSAL.md`（格式同 CODE_ANALYSIS_GUIDE 5.2 节）；
3. 用户批准后：项目级条目写入 `CODE_ANALYSIS_GUIDE.local.md`（两指南共享同一覆盖层）；通用条目更新本文件，版本号递增，并在 `_GUIDE_CHANGELOG.md` 追加记录（版本号、日期、变更摘要、来源项目；审查指南条目记入该文件"审查指南"表）。
4. 未经用户批准，Agent 不得擅自修改本文件。
