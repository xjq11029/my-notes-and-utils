# 代码理解与审查指南体系 · 使用说明

本工作区包含两份供 Agent 智能体加载的指令规范，分别解决两个问题：

- **"这段代码是什么、怎么运转的？"** → 用 `CODE_ANALYSIS_GUIDE.md`（理解）
- **"这次改动有什么问题、能不能合入？"** → 用 `CODE_REVIEW_GUIDE.md`（把关）

两份指南**各自独立使用**，通过共享"项目画像"协作，互不替代。

---

## 一、文件清单

| 文件 | 版本 | 作用 |
|---|---|---|
| `CODE_ANALYSIS_GUIDE.md` | v1.3.1 | 代码理解指南：对指定文件夹逐文件生成调用图 + 功能说明文档 |
| `CODE_REVIEW_GUIDE.md` | v1.0.0 | 代码审查指南：对变更集（diff）出具分级审查意见 + 合入结论 |
| `_GUIDE_CHANGELOG.md` | — | 分析指南的版本变更记录 |
| `_REVIEW_GUIDE_CHANGELOG.md` | — | 审查指南的版本变更记录 |

**分工边界**：分析指南不出具合入结论；审查指南不生成分析文档。

## 二、快速上手

### 场景 A：接手陌生项目，想快速看懂代码

1. 将 `CODE_ANALYSIS_GUIDE.md` 复制到目标项目根目录；
2. 对 Agent 说（可直接复制）：

   > 请阅读项目根目录下的 CODE_ANALYSIS_GUIDE.md，严格按规范分析 `src/` 目录，使用标准模式。先输出项目画像摘要与待分析文件清单，经我确认后再生成。

3. 依次确认 Agent 输出的**项目画像摘要**和**待分析文件清单**；
4. 完成后查看产出（见下"产出物"），并审批 `_ITERATION_PROPOSAL.md`。

### 场景 B：提交代码前 / 评审 MR，想把关质量

1. 将 `CODE_REVIEW_GUIDE.md` 复制到目标项目根目录（若已跑过场景 A，画像会被自动复用）；
2. 对 Agent 说（可直接复制）：

   > 请阅读项目根目录下的 CODE_REVIEW_GUIDE.md，严格按规范审查当前分支相对 main 的全部变更，使用标准审查。先输出变更集摘要与影响面分析，经我确认后再出具审查意见。

   审查范围四种指定方式：提交范围（`HEAD~3..HEAD`）/ 分支对比 / 暂存区 / 文件清单（无 git 时）。
3. 确认变更集摘要与影响面分析后，Agent 出具分级意见与合入结论。

### 场景 C：精读某个核心文件

> …按 CODE_ANALYSIS_GUIDE 规范，仅分析 `core/engine.ts`，使用**逐行模式**。

（逐行模式对每一行生成行内注释，单文件 ≤500 行。）

## 三、模式与档位速查

### 分析指南 · 三档模式（默认标准）

| 模式 | 生成内容 | 适用 |
|---|---|---|
| 概览 | 文件概览/依赖/结构清单/调用图/被引用/注意事项（跳过逐块详解） | 快速摸清项目结构 |
| 标准 | 完整 8 节模板（含逐代码块图文解说） | 常规理解代码 |
| 逐行 | 完整模板 + 每行行内注释 | 精读核心文件 |

**增量更新**：项目已有分析产物时默认增量——只重生成变更过的文件及其关联方；你在文档"笔记区"写的人工内容不会被覆盖。

### 审查指南 · 三档严格度（默认标准）

| 档位 | 行为 | 适用 |
|---|---|---|
| 快速 | 只报 Blocker / Critical | 提交前自查 |
| 标准 | 全维度，Minor 以上全报 | 常规 MR/PR 评审 |
| 严格 | 标准 + 风格细节 + 测试断言 + 引用项目规范 | 核心模块、上线前 |

## 四、产出物与位置

### 分析指南产出 → `<项目>/docs/code-analysis/`

| 文件 | 内容 |
|---|---|
| `_PROJECT_PROFILE.md` | **项目画像**（技术栈/目录职责/特有调用模式），两个指南共享 |
| `_INDEX.md` | 总览索引：文件清单 + 模块依赖全景图 + 规模摘要 |
| `<源文件名>.md` | 每个代码文件一份分析文档（调用图 + 逐块图文解说） |
| `_AUDIT_REPORT.md` | 产物校对报告（10 维度合规审计 + 行号抽查记录） |
| `_ITERATION_PROPOSAL.md` | 指南迭代建议（需你审批） |

### 审查指南产出 → `<项目>/docs/code-review/`

| 文件 | 内容 |
|---|---|
| `_REVIEW_REPORT_<日期>_<范围>.md` | 审查报告：合入结论 + 分级意见（位置/级别/维度/问题/依据/建议改法） |
| `_ITERATION_PROPOSAL.md` | 指南迭代建议（误报校准、漏报补充） |

### 项目级覆盖层 → `<项目>/CODE_ANALYSIS_GUIDE.local.md`

随使用自动积累的项目专属规则（自研框架解析要点、豁免项、审查尺度校准）。两个指南共用，下次进入该项目自动加载、冲突时优先。**不要删除它。**

## 五、两份指南如何协作

```
首次进入项目
   │
   ▼
CODE_ANALYSIS_GUIDE ──生成──▶ _PROJECT_PROFILE.md（项目画像）
   │                                │
   │ 生成分析文档                    │ 只读复用
   ▼                                ▼
docs/code-analysis/      CODE_REVIEW_GUIDE（日常审查）
（逐文件理解文档）              │
                                │ 遇到未覆盖模块时
                                └──建议──▶ 回到分析指南补生成（概览模式即可）
```

**推荐组合**：
1. 接手项目 → 先跑分析（概览模式），生成画像与总览；
2. 日常开发 → 每次提交/MR 跑审查（标准审查）；
3. 需要深挖某文件 → 分析指南逐行模式单点精读；
4. 每次结束后 → 花 1 分钟审批 `_ITERATION_PROPOSAL.md`，指南会越用越贴合你的项目。

## 六、常见问题

**Q：不熟悉的语言，怎么确认生成内容是对的？**
看 `_AUDIT_REPORT.md` 的行号抽查记录（源文件原文 vs 文档描述的对照）；可要求提高抽查密度；也可用工具交叉验证（如 JS/TS 用 `madge`、Go 用 `callgraph` 生成基准调用图做 diff）。

**Q：分析产物会污染我的项目吗？**
所有产出只写入 `docs/code-analysis/` 与 `docs/code-review/` 两个目录，指南全程只读源码，不修改任何源文件。不想纳入版本控制可在 `.gitignore` 加这两行。

**Q：审查报告的意见可信吗？**
每条意见必须带"代码片段 + 规则/原理"双依据；Blocker/Critical 在出具前经逐条自证（位置、行号、片段三者一致）；拿不准的进"待确认"区而非正式意见。

**Q：指南本身如何更新？**
你不需手动改。每次使用后 Agent 会产出迭代建议，你审批后由 Agent 自动更新指南并登记版本日志。跨项目复用的改进进通用指南，项目专属的进覆盖层。
