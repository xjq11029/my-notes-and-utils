| 缺点 | 概念抽象易混淆；硬链接限制较多；软链接悬空后访问报错需排查 |

### 2. 软链接与硬链接 ★★

| 维度 | 内容 |
|------|------|
| 是什么 | 从存储原理、inode、跨文件系统、链接目录、删除原文件后行为多维度对比软硬链接 |
| 能做什么 | 软链接独立inode存路径可跨系统可链接目录；硬链接共享inode不可跨系统不可链接目录 |
| 怎么用 | `ln -s source target`；`ln source target` |

| 缺点 | 软链接原文件移动删除即失效；硬链接无法跨文件系统与链接目录限制使用场景；两者选择需权衡 |

### 3. 进程状态 ★★

| 维度 | 内容 |
|------|------|
| 是什么 | Linux进程R/S/D/Z/T等状态码的含义与典型场景 |
| 能做什么 | 解释各状态码含义；识别D状态指示IO瓶颈、Z状态指示父进程未回收 |
| 怎么用 | `ps aux`查看STAT列；`ps aux | grep ' D'`定位D状态 |

| 缺点 | D状态进程无法被kill杀死只能等待IO完成或重启；僵尸进程占用PID资源；状态附加标记多需结合理解 |

### 6. 网络排查 ★★★

| 维度 | 内容 |
|------|------|
| 是什么 | 服务监听8080但外部无法访问的分层排查思路 |
| 能做什么 | 检查监听地址、防火墙、本机连通性、网络路由、SELinux、应用绑定地址 |
| 怎么用 | `ss -tlnp | grep 8080`；`firewall-cmd --list-all`；`curl -v http://localhost:8080`；`getenforce` |
| 原理和工作流程 | 自底向上排查：先确认服务是否监听0.0.0.0而非仅127.0.0.1，再检查firewalld与云安全组是否放行端口，本机curl测试服务本身是否正常，从外部telnet/nc测试网络可达性，检查SELinux是否阻止，最后确认应用配置的绑定地址。最常见原因是绑定127.0.0.1与防火墙未放行 |
| 缺点 | 排查环节多需逐层排除耗时；云环境安全组与主机防火墙双层易遗漏；SELinux策略排查复杂 |

### 7. 服务部署 ★★★

| 维度 | 内容 |
|------|------|
| 是什么 | 编写systemd服务单元文件部署Node.js应用的实践 |
| 能做什么 | 配置启动命令与运行用户；设置环境变量；崩溃自动重启；安全加固 |
| 怎么用 | `ExecStart=/usr/bin/node /opt/app/server.js`；`User=appuser`；`Environment=NODE_ENV=production`；`Restart=always` |
| 原理和工作流程 | 单元文件分Unit、Service、Install三段。Unit段声明依赖关系，Service段定义启动停止命令、运行用户、环境变量、重启策略与安全加固选项，Install段声明启动目标。`daemon-reload`重新加载变更，`enable`建立启动目标目录的符号链接实现开机自启，日志通过journald收集 |
| 缺点 | 字段语法严格出错导致服务无法启动；`Restart=always`可能掩盖根本故障导致反复重启；安全加固选项可能影响服务功能 |

### 8. 性能排查 ★★★

| 维度 | 内容 |
|------|------|
| 是什么 | 负载高但CPU使用率不高时的原因分析与排查方法 |
| 能做什么 | 识别D状态进程过多导致负载高；用iostat/iotop/vmstat排查IO与内存瓶颈 |
| 怎么用 | `ps aux | awk '{print $8}' | sort | uniq -c`；`iostat -x 1`；`iotop -o`；`vmstat 1` |
| 原理和工作流程 | load average统计处于R与D状态的进程平均数，CPU使用率不高但负载高说明大量进程处于D状态等待IO。排查先用ps统计各状态进程数确认D状态数量，再用iostat查看磁盘`%util`与`await`判断IO瓶颈，用vmstat看si/so判断是否频繁换页，用iotop定位高IO进程，检查NFS与内核锁竞争 |
| 缺点 | D状态进程难直接定位等待的具体资源；多因素叠加排查复杂；性能工具自身需安装且需root |

### 场景题 1：线上服务 CPU 飙升 ★★★

| 维度 | 内容 |
|------|------|
| 是什么 | 线上服务CPU飙升至95%以上的紧急排查与应急处置方法论 |
| 能做什么 | 用top定位高CPU进程与线程；用strace/py-spy分析调用；保留现场后重启；cgroup限流止血 |
| 怎么用 | `top -H -p <PID>`；`strace -p <PID> -c -f`；`systemctl set-property myapp CPUQuota=200%`；`gcore <PID>` |
| 原理和工作流程 | 分四阶段：快速定位阶段用top找到高CPU进程与线程；深入分析阶段用top -H看线程、strace统计系统调用、lsof检查文件描述符泄漏、py-spy采样解释器栈；应急处理阶段可选重启恢复、cgroup限制CPU止血、或先dump现场再重启；事后复盘从死循环、正则回溯、慢查询、重试风暴、GC频繁等方向定位根因 |
| 缺点 | 紧急场景时间紧迫定位压力大；strace/gdb挂载有性能开销；重启可能丢失现场无法复现 |

### 场景题 2：磁盘空间不足 ★★★

| 维度 | 内容 |
|------|------|
| 是什么 | 根分区使用率100%导致写入失败的排查清理与预防方法论 |
| 能做什么 | 用df/du定位大文件目录；检查inode耗尽；清理已删除未释放文件与日志；配置logrotate预防 |
| 怎么用 | `df -h`；`du -h --max-depth=1 / | sort -rh`；`lsof | grep deleted`；`journalctl --vacuum-size=500M`；`docker system prune -a -f` |
| 原理和工作流程 | 分五阶段：确认问题范围同时检查磁盘空间与inode；逐层用du定位大目录、用find查找大文件；检查已删除但进程仍持有句柄的文件、日志、Docker占用、core dump；应急清理包缓存、旧内核、systemd日志、截断大日志、重启持有句柄进程；预防措施包括配置logrotate轮转、磁盘监控告警、分区规划、Docker清理 |
| 缺点 | 大文件定位在深层目录耗时；已删除未释放文件需重启进程影响服务；清理操作需谨慎避免误删 |
