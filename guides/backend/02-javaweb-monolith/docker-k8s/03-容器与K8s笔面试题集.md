## 一、选择题（15 题，每题附解析）

### 1. ★ Docker 中用于存储和分发容器镜像的组件是（ ）

A. Docker Engine
B. Docker Registry
C. Docker Compose
D. Docker Swarm

**答案：B**

**解析：** Docker Registry（如 Docker Hub、Harbor）用于存储和分发镜像。Engine 是运行时，Compose 是多容器编排，Swarm 是集群管理。

---

### 2. ★ Docker 容器的核心优势不包括（ ）

A. 轻量级，共享宿主机内核
B. 秒级启动
C. 环境一致性（一次构建，到处运行）
D. 完全替代虚拟机，隔离性更强

**答案：D**

**解析：** 容器共享宿主机内核，隔离性弱于虚拟机。虚拟机拥有独立 Guest OS，硬件级隔离，安全性更高。A、B、C 均为容器核心优势。

---

### 3. ★ Kubernetes 中最小的调度单位是（ ）

A. Container
B. Pod
C. Node
D. Service

**答案：B**

**解析：** Pod 是 K8s 最小调度单位，可以包含一个或多个容器。Container 运行在 Pod 内部，Node 是工作节点，Service 是服务抽象。

---

### 4. ★ Docker 镜像分层技术使用的文件系统是（ ）

A. NTFS
B. ext4
C. UnionFS / Overlay2
D. FAT32

**答案：C**

**解析：** Docker 使用 UnionFS（联合文件系统），如 Overlay2，实现镜像分层。每层只读，容器层可写，通过 Copy-on-Write 机制修改文件。

---

### 5. ★ Dockerfile 中，容器启动时的默认命令指令是（ ）

A. RUN
B. CMD
C. ENTRYPOINT
D. EXEC

**答案：B**

**解析：** CMD 提供容器启动时的默认命令，可被 `docker run` 参数覆盖。RUN 是构建时执行的命令，ENTRYPOINT 是不可被覆盖的入口点。

---

### 6. ★★ K8s 中，管理 Pod 副本数量和滚动更新的控制器是（ ）

A. Service
B. Deployment
C. ConfigMap
D. Ingress

**答案：B**

**解析：** Deployment 管理 Pod 副本数量、滚动更新和回滚。Service 负责服务发现和负载均衡，ConfigMap 管理配置，Ingress 管理外部访问。

### 7. ★★ 以下关于 Docker CMD 和 ENTRYPOINT 的描述，正确的是（ ）

## 二、简答题（8 题，每题附完整解析）

### 1. 简述 Docker 容器的核心优势。

**答案：** 1）轻量级：共享宿主机内核，无需 Guest OS，镜像小（MB 级 vs GB 级）；2）快速启动：秒级启动（vs 虚拟机分钟级）；3）环境一致性："一次构建，到处运行"，消除环境差异问题；4）资源利用率高：一台服务器可运行数百个容器；5）版本管理：镜像分层，支持版本控制和回滚。

> 📖 **延伸阅读**：[Docker 概述](https://docs.docker.com/get-started/overview/) -- Docker 官方概览，阐述容器架构与核心优势

---

### 2. 简述 Docker 镜像分层的原理和好处。

**答案：** 镜像分层原理：每个 Dockerfile 指令创建一个只读层，各层堆叠形成完整镜像。容器运行时在镜像层之上添加一个可写层（Container Layer），使用 Copy-on-Write 机制：读取时从上层向下查找，修改时先复制到容器层再修改。好处：1）共享基础层，节省磁盘空间；2）加速构建，未变化的层使用缓存；3）快速分发，只拉取本地没有的层。

> 📖 **延伸阅读**：[Docker 存储驱动](https://docs.docker.com/storage/storagedriver/) -- 官方镜像分层与 overlay2 存储驱动原理；[关于镜像、容器和存储驱动](https://docs.docker.com/storage/storagedriver/#images-and-layers) -- 镜像层、容器层与 Copy-on-Write 详解

---

### 3. 简述 CMD 和 ENTRYPOINT 的区别。

**答案：** CMD 提供容器启动时的默认命令，可以被 `docker run` 后面的参数覆盖。ENTRYPOINT 定义容器入口点，不可被覆盖，`docker run` 参数作为参数追加到 ENTRYPOINT 后面。最佳实践：ENTRYPOINT 定义可执行程序，CMD 提供默认参数。例如：`ENTRYPOINT ["java"]` + `CMD ["-jar", "app.jar"]`，这样 `docker run myimage -Xmx1g -jar app.jar` 会执行 `java -Xmx1g -jar app.jar`。

> 📖 **延伸阅读**：[Dockerfile ENTRYPOINT 指令](https://docs.docker.com/engine/reference/builder/#entrypoint) -- 官方 ENTRYPOINT 与 CMD 交互行为表（含 shell/exec 格式差异）

---

### 4. 简述 K8s 中 Pod 和 Container 的关系。

**答案：** Pod 是 K8s 最小调度单位，一个 Pod 可以包含一个或多个容器。同一 Pod 内的容器共享网络命名空间（同一 IP 和端口空间）和存储卷，可以通过 localhost 通信。Pod 内的容器作为一个整体被调度到同一 Node 上，共享生命周期。通常一个 Pod 运行一个主容器，必要时添加 Sidecar 容器（如日志收集、代理）。

> 📖 **延伸阅读**：[Kubernetes Pod 概念](https://kubernetes.io/zh-cn/docs/concepts/workloads/pods/) -- 官方 Pod 文档：Pod 内容器共享网络与存储、生命周期、Sidecar 模式

---

### 5. 简述 K8s Service 的作用和三种类型。

**答案：** Service 为一组 Pod 提供稳定的网络访问入口（固定 ClusterIP 和 DNS 名称），解决 Pod 动态创建/销毁导致 IP 变化的问题。三种类型：ClusterIP（默认）：分配集群内部 IP，只能集群内访问；NodePort：在每个 Node 上开放端口（30000-32767），通过 NodeIP:Port 从外部访问；LoadBalancer：云厂商提供的外部负载均衡器，分配公网 IP。

> 📖 **延伸阅读**：[Kubernetes Service](https://kubernetes.io/zh-cn/docs/concepts/services-networking/service/) -- 官方 Service 文档：ClusterIP/NodePort/LoadBalancer/ExternalName 四种类型与 kube-proxy 工作模式

---

### 6. 简述 K8s Deployment 滚动更新的原理。

**答案：** Deployment 通过 ReplicaSet 控制 Pod 副本数量。滚动更新时，逐步创建新版本 Pod 并删除旧版本 Pod，通过 maxSurge（允许超出期望副本数的最大值）和 maxUnavailable（允许不可用 Pod 的最大值）控制更新速度。流程：创建新版本 Pod -> 新 Pod 就绪 -> 删除旧版本 Pod -> 重复直到全部更新。更新失败时可自动回滚到上一个版本。

> 📖 **延伸阅读**：[Kubernetes Deployment](https://kubernetes.io/zh-cn/docs/concepts/workloads/controllers/deployment/) -- 官方 Deployment 文档：滚动更新策略、maxSurge/maxUnavailable、回滚机制

---

### 7. 简述 livenessProbe 和 readinessProbe 的区别。

**答案：** livenessProbe（存活探针）：检查容器是否存活，失败时 kubelet 会重启容器。应检查简单的存活状态，不要检查外部依赖。readinessProbe（就绪探针）：检查容器是否准备好接收流量，失败时 Pod 从 Service 端点移除，不接收流量。可以检查依赖服务是否可用。startupProbe（启动探针）：检查容器是否启动完成，在启动完成前 livenessProbe 和 readinessProbe 不生效，防止启动慢的应用被误杀。

> 📖 **延伸阅读**：[Kubernetes 容器探针](https://kubernetes.io/zh-cn/docs/concepts/workloads/pods/pod-lifecycle/#container-probes) -- 官方探针文档：liveness/readiness/startup 三种探针的配置与触发行为

---

### 8. 简述如何减小 Docker 镜像大小。

**答案：** 1）选择轻量级基础镜像，如 Alpine 版本（openjdk:17-alpine 替代 openjdk:17）；2）使用多阶段构建，构建阶段使用完整工具链，运行阶段只保留运行时文件；3）减少层数，合并 RUN 命令并使用 `&&` 连接，在同一层清理缓存（`rm -rf /var/lib/apt/lists/*`）；4）使用 .dockerignore 排除不需要的文件（target、.git、node_modules 等）；5）使用特定版本标签而非 latest，避免不可预期的体积变化；6）清理不再需要的包管理器缓存和临时文件。通过这些优化，Java 应用镜像可从 500MB+ 降至 100MB 左右。

> 📖 **延伸阅读**：[Docker 多阶段构建](https://docs.docker.com/build/building/multi-stage/) -- 官方多阶段构建指南；[Dockerfile 最佳实践](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/) -- 官方 Dockerfile 编写规范（层数优化、缓存利用、.dockerignore）

## 三、进阶面试题（K8s 调度 / Service 网络 / 存储卷）

> 本部分聚焦 K8s 三大高阶主题：**调度机制**（Pod 如何被分配到 Node）、**Service 网络**（流量如何路由到 Pod）、**存储卷**（数据如何持久化）。这些是中高级岗位面试的高频考点。

> **生活化类比：K8s 调度器 = "酒店前台分配房间"** —— 当一个 Pod（客人）来到 K8s 集群（酒店）要入住，调度器（前台）不会随便给个房间。它分两步走：**预选**（Filtering）像前台排除"不合适的房间"——这间房住不下这么多人（资源不足）、这间是 VIP 专属客人的（Taint 污点，客人没有 Toleration 容忍进不了）、这间房标签是"无烟房"但客人要抽烟（NodeSelector 不匹配）；**优选**（Scoring）像前台从剩下的房里挑"最合适的"——优先给空房间多的楼层（资源均衡）、优先给客人常住的楼层（镜像本地性，之前拉过镜像启动快）、优先让同团队住一起（Pod 亲和性）或分开住（反亲和性，避免单点）。最后把客人绑定到得分最高的房间（Node），交给该楼层的管家（kubelet）安排入住。理解这套机制能解释"为什么 Pod 卡在 Pending"（预选全被过滤）、"为什么 Pod 总调度到同一节点"（优选打分偏好）等问题。

> **生活化类比：K8s 存储卷体系 = "租房 vs 买房 vs 酒店储物柜"** —— K8s 的存储方案像不同居住方式：**emptyDir** 是"酒店储物柜"——Pod 在它就在，Pod 没了储物柜清空（同 Pod 容器间共享临时数据）；**hostPath** 是"住自己家"——直接用 Node 宿主机磁盘，快但 Pod 搬家后数据还在原 Node（危险，不推荐生产用）；**PersistentVolume (PV)** 是"整栋公寓楼"——集群管理员预先建好的存储资源池；**PersistentVolumeClaim (PVC)** 是"租客的租房合同"——Pod 提交申请"我要 10G 空间"，K8s 自动匹配一合适的 PV（静态供给）或调用 StorageClass 现建一个（动态供给）。**StorageClass** 是"房产开发商"——按需求自动建造不同档次的房子（SSD/HDD/NFS）。StatefulSet 配合 PVC 让每个 Pod 有"固定门牌的独立房"（有序、持久），这就是有状态应用（数据库）在 K8s 上的标准姿势。

### 9. ★★ 简述 K8s 调度器的预选（Filtering）和优选（Scoring）两个阶段。

**答案：**

- **预选阶段（Filtering）**：遍历所有 Node，过滤掉不满足 Pod 需求的节点，产出"可行节点列表"。常见过滤策略：
  - **资源检查**：Node 的可用 CPU/内存是否满足 Pod 的 requests
  - **NodeSelector / NodeAffinity**：节点标签是否匹配 Pod 指定的选择器
  - **Taints / Tolerations**：节点有污点但 Pod 无对应容忍，则过滤
  - **Volume 限制**：节点已挂载的 PV 数量、卷拓扑约束（如 EBS 可用区）

- **优选阶段（Scoring）**：对预选通过的 Node 打分（0-100），选得分最高的。常见打分策略：
  - **LeastRequestedPriority**：资源剩余越多分越高（均衡分布）
  - **ImageLocalityPriority**：Node 已有 Pod 需要的镜像，分高（启动快）
  - **PodAffinity / AntiAffinity**：与指定 Pod 同节点（亲和）或不同节点（反亲和）
  - **NodeAffinity（preferred）**：倾向调度到带特定标签的节点

> 📖 **延伸阅读**：[Kubernetes 调度器](https://kubernetes.io/zh-cn/docs/concepts/scheduling-eviction/kube-scheduler/) -- 官方调度器文档：预选优选两阶段、调度框架（Scheduling Framework）扩展点

### 10. ★★ 简述 Taint（污点）和 Toleration（容忍）的作用与区别。

**答案：**

- **Taint（污点）**：打在 **Node** 上，标记"这个节点有特殊情况，默认不接纳普通 Pod"。格式 `key=value:effect`，effect 有三种：
  - `NoSchedule`：不调度新 Pod（已运行的 Pod 不受影响）
  - `PreferNoSchedule`：尽量不调度（软约束，实在没节点也会调度）
  - `NoExecute`：不调度且驱逐已运行的不容忍 Pod

- **Toleration（容忍）**：配在 **Pod** 上，声明"我能忍受某类污点"。只有 Pod 的 Toleration 与 Node 的 Taint 匹配，Pod 才可能被调度到该 Node。

**典型场景**：Master 节点打 `node-role.kubernetes.io/master:NoSchedule` 污点，防止业务 Pod 跑到 Master 上抢占控制面资源；GPU 节点打 `nvidia.com/gpu:NoSchedule`，只有声明了 Toleration 的 AI 任务 Pod 才能调度上去。

```yaml
# Node 打污点
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule

# Pod 声明容忍
spec:
  tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

> 📖 **延伸阅读**：[Kubernetes 污点与容忍](https://kubernetes.io/zh-cn/docs/concepts/scheduling-eviction/taint-and-toleration/) -- 官方 Taint/Toleration 文档：三种 effect、operator（Equal/Exists）、污点驱逐行为

### 11. ★★★ 简述 kube-proxy 的 iptables 模式与 IPVS 模式的区别，生产环境如何选择。

**答案：**

| 维度 | iptables 模式 | IPVS 模式 |
|------|--------------|-----------|
| **底层** | Linux iptables 规则链 | Linux 内核 IPVS 模块（Netfilter hook） |
| **算法** | 随机（随机匹配规则） | 支持轮询/最少连接/源地址哈希等多种 |
| **规则规模** | 每个 Service+Pod 生成多条规则，O(n) | 哈希表查找，O(1) |
| **大规模性能** | 规则上万条后明显下降 | 性能稳定，支持万级 Service |
| **默认** | K8s 1.2+ 默认 | 需显式开启（`--proxy-mode=ipvs`） |

**生产环境选择**：集群规模小（<1000 Service）用 iptables 足够；大规模集群（>1000 Service）或对负载均衡算法有要求（如最少连接）推荐 IPVS。IPVS 需要内核加载 `ip_vs` 等模块。新版本 K8s 社区主推 IPVS。

```bash
# 查看当前 kube-proxy 模式
kubectl logs -n kube-system <kube-proxy-pod> | grep "Using.*Proxier"
# 开启 IPVS 模式（修改 kube-proxy ConfigMap）
kubectl edit configmap kube-proxy -n kube-system
# 设置 mode: "ipvs"，然后重启 kube-proxy DaemonSet
kubectl rollout restart daemonset kube-proxy -n kube-system
```

### 12. ★★ 简述 K8s 中 ClusterIP Service 的流量转发原理（从客户端到 Pod）。

**答案：**

1. **DNS 解析**：客户端 Pod 访问 `my-svc.default.svc.cluster.local`，CoreDNS 返回 Service 的 ClusterIP（如 `10.96.0.50`）
2. **流量命中规则**：数据包目标 IP 是 ClusterIP（虚拟 IP），kube-proxy 在每个 Node 上预先配置的 iptables/IPVS 规则将其拦截
3. **DNAT 转发**：iptables 规则将目标 IP 从 ClusterIP 改写为某个后端 Pod IP（DNAT），实现负载均衡（轮询/随机）
4. **路由到 Pod**：改写后的包按正常路由到达目标 Pod 所在 Node，由该 Node 的 kube-proxy 规则继续转发到容器
5. **响应回程**：Pod 响应包源 IP 是 Pod IP，经过反向 SNAT 还原为 ClusterIP，返回客户端

**Endpoints 的作用**：Service 通过 Label Selector 筛选匹配的 Pod，将其 IP:Port 列表写入 Endpoints（或 EndpointSlice）对象。kube-proxy 监听 Endpoints 变化，动态更新转发规则。Pod 扩缩容时 Endpoints 自动更新，流量自动切换。

> 📖 **延伸阅读**：[Kubernetes Service 网络原理](https://kubernetes.io/zh-cn/docs/concepts/services-networking/service/) -- 官方 Service 文档：ClusterIP 虚拟 IP、Endpoints、kube-proxy 转发机制

### 13. ★★ 简述 emptyDir、hostPath、configMap 三种 Volume 的区别与适用场景。

**答案：**

| Volume 类型 | 生命周期 | 存储位置 | 适用场景 | 风险 |
|-------------|----------|----------|----------|------|
| **emptyDir** | 随 Pod 创建/销毁 | Node 本地磁盘（或 tmpfs 内存） | 同 Pod 多容器共享临时数据（如主容器写日志、sidecar 读日志） | Pod 删除数据丢失 |
| **hostPath** | 持久（Node 级） | Node 宿主机指定路径 | DaemonSet 访问宿主机系统文件（如 /var/log、/sys） | 安全风险大，Pod 漂移后数据不可访问 |
| **configMap** | 随 ConfigMap 更新 | 内存（投射为文件/环境变量） | 注入配置文件（如 application.yml）、环境变量 | 适合非敏感配置 |

```yaml
volumes:
- name: shared-data          # emptyDir：容器间共享
  emptyDir: {}
- name: host-logs            # hostPath：访问宿主机日志
  hostPath:
    path: /var/log/myapp
    type: DirectoryOrCreate
- name: app-config           # configMap：注入配置
  configMap:
    name: myapp-config
```

> 📖 **延伸阅读**：[Kubernetes Volume](https://kubernetes.io/zh-cn/docs/concepts/storage/volumes/) -- 官方 Volume 文档：emptyDir/hostPath/configMap/secret/downwardAPI 等各类型说明

### 14. ★★★ 简述 PV、PVC、StorageClass 三者的关系与动态供给流程。

**答案：**

- **PersistentVolume (PV)**：集群级存储资源，由管理员预先创建（静态供给）或由 StorageClass 自动创建（动态供给）。类似"集群里的存储池"。
- **PersistentVolumeClaim (PVC)**：用户对存储的"申请单"，声明需要的容量和访问模式。K8s 自动匹配满足条件的 PV。类似"租客的租房合同"。
- **StorageClass**：存储"模板"，描述动态创建 PV 的参数（存储类型、性能 tier、provisioner）。类似"房产开发商的建房图纸"。

**动态供给流程（Dynamic Provisioning）：**

```
1. 用户创建 PVC（申请 10Gi，storageClassName=fast-ssd）
2. StorageClass 的 Provisioner（如 CSI 驱动）监听到 PVC
3. Provisioner 调用底层存储 API（如 AWS EBS / Ceph / NFS）创建实际存储卷
4. 自动生成对应的 PV 并与 PVC 绑定
5. Pod 通过 PVC 挂载该存储卷，Pod 消亡后数据按 reclaimPolicy 保留或回收
```

| reclaimPolicy | 说明 |
|---------------|------|
| `Retain` | PV 保留数据，需管理员手动回收（默认，安全） |
| `Delete` | PVC 删除时自动删除 PV 和底层存储（动态供给默认，省心但危险） |

> 📖 **延伸阅读**：[Kubernetes 持久化存储](https://kubernetes.io/zh-cn/docs/concepts/storage/persistent-volumes/) -- 官方 PV/PVC 文档；[StorageClass 动态供给](https://kubernetes.io/zh-cn/docs/concepts/storage/storage-classes/) -- 官方 StorageClass 文档：provisioner、reclaimPolicy、volumeBindingMode

### 15. ★★★ 简述 StatefulSet 与 Deployment 的区别，以及 StatefulSet 为何适合数据库类应用。

**答案：**

| 维度 | Deployment | StatefulSet |
|------|-----------|-------------|
| **Pod 名称** | 随机后缀（`app-7b9f-x4k2m`） | 有序固定（`db-0`、`db-1`、`db-2`） |
| **部署顺序** | 并行，无序 | 顺序（0→1→2），前一个 Ready 才创建下一个 |
| **扩缩容** | 随机 | 有序（扩容顺序加，缩容逆序减） |
| **网络标识** | Pod IP 随机 | 每个有固定 DNS：`db-0.mysql.default.svc.cluster.local` |
| **存储** | 所有副本共享 PVC 模板（或各自 emptyDir） | 每个副本独立 PVC，重建后绑定同一 PVC（数据不丢） |
| **滚动更新** | 随机替换 | 逆序（2→1→0）逐个更新 |
| **适用** | 无状态应用（Web/API） | 有状态应用（数据库、消息队列、分布式存储） |

**为何适合数据库**：数据库要求①固定网络标识（主从复制按主机名配置）、②稳定持久存储（Pod 重建数据不丢，每个实例独立卷）、③有序启停（先启主再启从，避免脑裂）。StatefulSet 完美满足这三点。Deployment 做不到——Pod 名随机、存储共享、无序启停会导致数据库集群混乱。

> 📖 **延伸阅读**：[Kubernetes StatefulSet](https://kubernetes.io/zh-cn/docs/concepts/workloads/controllers/statefulset/) -- 官方 StatefulSet 文档：有序部署、稳定网络标识、持久存储、并行/顺序策略
