### 1. Docker 中用于存储和分发容器镜像的组件是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Docker Registry 是存储和分发容器镜像的服务组件 |
| 能做什么 | 集中存储镜像；通过标签管理版本；支持推送和拉取镜像 |
| 怎么用 | `docker push registry.example.com/app:v1` / `docker pull nginx:1.25` |

### 2. Docker 容器的核心优势不包括（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 容器核心优势是轻量级、秒级启动、环境一致性，但隔离性弱于虚拟机 |
| 能做什么 | 提供轻量级运行环境；秒级启动；一次构建到处运行；高资源利用率 |
| 怎么用 | `docker run` 启动容器体验核心优势 |
| 原理和工作流程 | 容器共享宿主机内核无需 Guest OS，实现轻量级和秒级启动。但共享内核意味着隔离性弱于虚拟机，虚拟机拥有独立 Guest OS 实现硬件级隔离安全性更高。容器不能完全替代虚拟机，隔离性更强不是容器优势 |
| 缺点 | 隔离性弱于虚拟机；无法完全替代虚拟机；安全敏感场景仍需虚拟机 |

### 3. Kubernetes 中最小的调度单位是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Pod 是 K8s 最小的调度单位，可包含一个或多个容器 |
| 能做什么 | 承载容器；共享网络和存储；作为整体被调度到 Node |
| 怎么用 | `kubectl get pods` 查看 Pod |
| 原理和工作流程 | Pod 是 K8s 调度的原子单位，内容器共享 Network Namespace 和 Volume。Container 运行在 Pod 内部不是调度单位，Node 是工作节点，Service 是服务抽象。Pod 作为整体调度到同一 Node |
| 缺点 | Pod ephemeral 重启 IP 变化需 Service 配合；多容器 Pod 调试复杂 |

### 4. Docker 镜像分层技术使用的文件系统是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Docker 使用 UnionFS（如 Overlay2）实现镜像分层 |
| 能做什么 | 分层只读堆叠；Copy-on-Write 修改；共享基础层 |
| 怎么用 | Dockerfile 指令逐层构建镜像 |
| 原理和工作流程 | UnionFS 将多个只读层联合挂载为统一视图，每层对应一个 Dockerfile 指令。容器运行时在镜像层之上添加可写层，通过 Copy-on-Write 机制：读取时从上层向下查找，修改时先复制到容器层再修改。NTFS、ext4、FAT32 是常规文件系统不支持联合挂载 |
| 缺点 | 层数过多导致元数据膨胀；跨层查找增加 IO；写时复制有首次修改延迟 |

### 5. Dockerfile 中，容器启动时的默认命令指令是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | CMD 是 Dockerfile 中定义容器启动时默认命令的指令 |
| 能做什么 | 提供默认启动命令；可被 docker run 参数覆盖 |
| 怎么用 | `CMD ["java","-jar","app.jar"]` |

| 缺点 | shell 形式无法接收 SIGTERM 信号；被覆盖后默认参数丢失 |

### 8. K8s 中，用于解决 Pod 动态 IP 变化问题的资源是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Service 是为 Pod 提供稳定网络访问入口解决动态 IP 变化的资源 |
| 能做什么 | 提供固定 ClusterIP 和 DNS；负载均衡；屏蔽 Pod IP 变化 |
| 怎么用 | `kubectl expose deployment app --port=80` |
| 原理和工作流程 | Service 通过标签选择器关联后端 Pod，分配固定 ClusterIP 和 DNS 名称。Pod 动态创建销毁导致 IP 变化，Service 提供稳定入口，kube-proxy 通过 iptables/IPVS 将流量转发到后端 Pod。Deployment 管理 Pod 副本，ConfigMap 管理配置，Ingress 管理外部 HTTP 访问 |
| 缺点 | ClusterIP 仅集群内访问；iptables 模式规则多性能下降 |

### 9. 以下哪项不是 Docker 镜像分层的好处？（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 镜像分层的好处是共享基础层、加速构建、快速分发，不直接提高安全性 |
| 能做什么 | 节省磁盘空间；缓存加速构建；差异层快速分发 |
| 怎么用 | 多个镜像共享 `FROM ubuntu` 基础层 |
| 原理和工作流程 | 每个指令生成只读层，多个镜像引用相同基础层只存储一份节省空间，构建时未变化的层命中缓存，拉取时只下载缺失层。分层不直接提高运行时安全性，安全性取决于隔离机制而非分层 |
| 缺点 | 层数过多性能下降；共享层修改导致缓存失效 |

### 11. Docker 容器隔离使用的是 Linux 的（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Linux Namespace 是 Docker 实现容器隔离的核心机制 |
| 能做什么 | 隔离 PID、网络、挂载点、主机名、IPC、用户 ID 六类资源 |

### 12. K8s 中，livenessProbe 失败时会发生（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | livenessProbe 失败时 kubelet 重启容器的探针机制 |
| 能做什么 | 检测容器存活；失败时重启容器；区别于 readinessProbe 摘除流量 |
| 怎么用 | `livenessProbe.httpGet.path: /health` |
| 原理和工作流程 | livenessProbe 检查容器是否存活，失败时 kubelet 按重启策略重启容器。readinessProbe 失败时 Pod 从 Service 端点移除不接收流量。两者失败后果不同：livenessProbe 重启容器，readinessProbe 摘除流量。Pod 不会被删除或重新调度 |
| 缺点 | 检查外部依赖导致重启雪崩；配置敏感频繁重启 |

### 14. K8s 集群中，存储所有配置和状态数据的组件是（ ）

### 1. 简述 Docker 容器的核心优势

| 维度 | 内容 |
|------|------|
| 是什么 | Docker 容器相比虚拟机的五大核心优势 |
| 能做什么 | 轻量级；快速启动；环境一致性；高资源利用率；版本管理 |
| 怎么用 | `docker run` 体验秒级启动和高密度部署 |
| 原理和工作流程 | 轻量级因共享宿主机内核无需 Guest OS，镜像 MB 级 vs 虚拟机 GB 级；快速启动秒级 vs 分钟级因只需拉起进程；环境一致性因镜像打包所有依赖一次构建到处运行；高资源利用率因一台服务器可运行数百容器；版本管理因镜像分层支持版本控制和回滚 |
| 缺点 | 隔离性弱于虚拟机；共享内核存在安全风险；网络和存储管理复杂 |

### 2. 简述 Docker 镜像分层的原理和好处

| 维度 | 内容 |
|------|------|
| 是什么 | Docker 镜像分层是每指令创建只读层并通过 Copy-on-Write 修改的技术 |
| 能做什么 | 共享基础层；缓存加速构建；差异层快速分发 |
| 怎么用 | Dockerfile 指令逐层构建镜像 |
| 原理和工作流程 | 每个 Dockerfile 指令创建一个只读层，各层堆叠形成完整镜像。容器运行时在镜像层之上添加可写层（Container Layer），使用 Copy-on-Write：读取时从上层向下查找返回首个匹配，修改时先复制到容器层再修改。好处是共享基础层节省空间、缓存加速构建、差异层快速分发 |
| 缺点 | 层数过多元数据膨胀；跨层查找增加 IO；写时复制有首次修改延迟 |

### 3. 简述 CMD 和 ENTRYPOINT 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | CMD 提供可覆盖的默认命令，ENTRYPOINT 定义不可覆盖的入口点 |
| 能做什么 | CMD 可被覆盖；ENTRYPOINT 不可覆盖参数追加；两者组合使用 |
| 怎么用 | `ENTRYPOINT ["java"]` + `CMD ["-jar","app.jar"]` |
| 原理和工作流程 | CMD 提供容器启动默认命令，可被 docker run 参数覆盖。ENTRYPOINT 定义容器入口点不可被覆盖，docker run 参数作为参数追加。最佳实践 ENTRYPOINT 定义可执行程序，CMD 提供默认参数，如 `ENTRYPOINT ["java"]` + `CMD ["-jar","app.jar"]`，`docker run myimage -Xmx1g -jar app.jar` 会执行 `java -Xmx1g -jar app.jar` |
| 缺点 | shell 形式无法接收 SIGTERM；组合语义复杂；覆盖与追加易混淆 |

### 4. 简述 K8s 中 Pod 和 Container 的关系

| 维度 | 内容 |
|------|------|
| 是什么 | Pod 是 K8s 最小调度单位，包含一个或多个 Container |
| 能做什么 | 共享网络命名空间；共享存储卷；通过 localhost 通信；作为整体调度 |
| 怎么用 | Pod YAML 定义 containers 数组 |
| 原理和工作流程 | Pod 是 K8s 最小调度单位，一个 Pod 可包含一个或多个容器。同 Pod 内容器共享 Network Namespace（同一 IP 和端口空间）和 Volume，通过 localhost 通信。Pod 作为整体调度到同一 Node 共享生命周期。通常一个 Pod 一个主容器，必要时添加 Sidecar 容器如日志收集、代理 |
| 缺点 | 同 Pod 容器强耦合一崩全崩；多容器调试复杂；Pod ephemeral 需 Service 配合 |

### 5. 简述 K8s Service 的作用和三种类型

| 维度 | 内容 |
|------|------|
| 是什么 | Service 为一组 Pod 提供稳定网络入口，有 ClusterIP、NodePort、LoadBalancer 三种类型 |
| 能做什么 | 固定 ClusterIP 和 DNS；集群内/外访问；负载均衡 |
| 怎么用 | `type: ClusterIP` / `type: NodePort` / `type: LoadBalancer` |
| 原理和工作流程 | Service 为一组 Pod 提供稳定网络访问入口（固定 ClusterIP 和 DNS），解决 Pod 动态创建销毁导致 IP 变化。ClusterIP 默认类型分配集群内部 IP 仅集群内访问；NodePort 在每个 Node 开放 30000-32767 端口通过 NodeIP:Port 外部访问；LoadBalancer 云厂商提供外部负载均衡器分配公网 IP |
| 缺点 | ClusterIP 无法外部访问；NodePort 端口有限暴露所有 Node；LoadBalancer 依赖云厂商费用高 |

### 6. 简述 K8s Deployment 滚动更新的原理

| 维度 | 内容 |
|------|------|
| 是什么 | Deployment 通过 ReplicaSet 逐步替换 Pod 实现零停机更新的机制 |
| 能做什么 | 控制更新速度；保证可用性；支持自动回滚 |
| 怎么用 | `kubectl set image deployment/app app=app:v2` |
| 原理和工作流程 | Deployment 通过 ReplicaSet 控制 Pod 副本数量。滚动更新时逐步创建新版本 Pod 并删除旧版本 Pod，通过 maxSurge（允许超出期望副本数的最大值）和 maxUnavailable（允许不可用 Pod 的最大值）控制更新速度。流程：创建新 Pod 到新 Pod 就绪到删除旧 Pod 到重复直到全部更新。更新失败可自动回滚 |
| 缺点 | 新旧共存需 API 兼容；参数配置不当导致不可用；回滚依赖历史 ReplicaSet |

### 7. 简述 livenessProbe 和 readinessProbe 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | liveness 检查存活，readiness 检查就绪，startup 检查启动完成的探针机制 |
| 能做什么 | liveness 失败重启容器；readiness 失败摘除流量；startup 保护慢启动 |
| 怎么用 | `livenessProbe.httpGet.path: /liveness` / `readinessProbe.httpGet.path: /readiness` |
| 原理和工作流程 | livenessProbe 存活探针检查容器是否存活，失败时 kubelet 重启容器，应检查简单存活状态不检查外部依赖。readinessProbe 就绪探针检查是否准备好接收流量，失败时 Pod 从 Service 端点移除不接收流量，可检查依赖服务。startupProbe 启动探针检查是否启动完成，完成前 liveness 和 readiness 不生效防止慢启动应用被误杀 |
| 缺点 | liveness 检查外部依赖导致重启雪崩；未设 initialDelaySeconds 启动期误杀；配置敏感频繁重启 |

### 8. 简述如何减小 Docker 镜像大小

| 维度 | 内容 |
|------|------|
| 是什么 | 通过多种手段压缩 Docker 镜像最终体积的优化方法 |
| 能做什么 | 选 Alpine 镜像；多阶段构建；合并 RUN 清理缓存；.dockerignore；特定版本标签 |
| 怎么用 | `FROM openjdk:17-alpine` + 多阶段构建 + 合并 RUN + .dockerignore |
| 原理和工作流程 | 选择轻量级基础镜像如 Alpine（openjdk:17-alpine 替代 openjdk:17）；多阶段构建构建阶段用完整工具链运行阶段只保留运行时文件；减少层数合并 RUN 命令用 && 连接并在同层清理缓存（`rm -rf /var/lib/apt/lists/*`）；.dockerignore 排除 target、.git、node_modules；特定版本标签避免 latest 不可预期变化；清理包管理器缓存和临时文件。综合可将 Java 镜像从 500MB 降至 100MB |
| 缺点 | Alpine 的 musl libc 兼容性问题；过度合并降低缓存复用；瘦身镜像缺少调试工具 |
