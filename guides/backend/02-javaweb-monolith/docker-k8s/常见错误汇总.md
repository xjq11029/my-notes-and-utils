# Docker 与 Kubernetes - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

## 一、Docker 核心原理

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 在容器中存储数据，删除容器后数据丢失 | 容器是无状态的，删除后数据不可恢复 | 使用 Volume 挂载或 Bind Mount 将数据持久化到宿主机或外部存储 | [01-导览](./01-Docker核心原理-导览.md) |
| 以 root 用户运行容器，存在容器逃逸安全风险 | root 用户拥有最高权限 | 在 Dockerfile 中创建非 root 用户：`RUN addgroup -S appgroup && adduser -S appuser -G appgroup`，然后 `USER appuser` | [01-导览](./01-Docker核心原理-导览.md) |
| 使用 latest 标签，不同时间拉取得到不同镜像 | latest 标签指向最新版本，版本不确定导致环境不一致 | 使用明确的版本标签（如 `nginx:1.25.3`） | [01-导览](./01-Docker核心原理-导览.md) |
| 镜像层数过多，构建和拉取性能差 | 每个 RUN/COPY/ADD 指令创建一个新层 | 将相关命令合并到一个 RUN 指令中（使用 && 连接） | [01-导览](./01-Docker核心原理-导览.md) |
| 未设置资源限制，容器耗尽宿主机资源 | 未限制 CPU 和内存使用 | 设置 `--cpus`、`--memory` 等资源限制 | [01-导览](./01-Docker核心原理-导览.md) |
| 容器内时间比宿主机慢 8 小时 | 日志时间戳错位、定时任务在错误时点触发 | 精简基础镜像默认 UTC，既没装 tzdata 也没设 TZ | 安装 tzdata 并复制 `Asia/Shanghai` 到 `/etc/localtime`，同时加 `-Duser.timezone=Asia/Shanghai` | [01-导览](./01-Docker核心原理-导览.md) |
| 容器内中文日志或文件乱码 | 中文内容显示为问号或方块 | Alpine 等精简镜像未安装 locale，默认 POSIX 字符集 | 设置 `ENV LANG=C.UTF-8`（或安装对应 locale 包）并统一 UTF-8 | [01-导览](./01-Docker核心原理-导览.md) |
| CMD 与 ENTRYPOINT 混用导致启动命令被覆盖 | `docker run` 传参后应用没起来，或参数被整体替换 | 把启动命令写在 CMD 里，`docker run` 后的参数会整体覆盖 CMD | 用 ENTRYPOINT 固定入口、CMD 只提供默认参数，两者配合使用 | [01-导览](./01-Docker核心原理-导览.md) |
| 源码改了但构建出的镜像还是旧的 | 改动没进镜像，行为与代码不符 | 层缓存命中（COPY 顺序不当）或文件被 .dockerignore 排除 | 把变化频率低的指令放前面；必要时 `--no-cache` 重建；检查 .dockerignore 是否误排除了源文件 | [01-导览](./01-Docker核心原理-导览.md) |
| 构建上下文过大导致 build 极慢 | 构建时把大量无关文件传给 daemon | 未配置 .dockerignore，target/、.git、node_modules 全被打包进上下文 | 添加 .dockerignore 排除 target、.git、node_modules、日志等 | [01-导览](./01-Docker核心原理-导览.md) |
| docker-compose 中 depends_on 不保证依赖已就绪 | 应用启动时连不上 MySQL 直接退出 | depends_on 只保证启动顺序，不等待服务真正可用 | 给依赖服务加 healthcheck，并用 `depends_on: condition: service_healthy` | [01-导览](./01-Docker核心原理-导览.md) |
| `docker compose down` 后数据库数据全丢 | MySQL/Redis 数据消失，需要重新初始化 | 数据目录未用 named volume 持久化，只写在容器可写层 | 用 named volume 挂载 `/var/lib/mysql`、`/var/lib/redis` 等数据目录 | [01-导览](./01-Docker核心原理-导览.md) |
| 密码硬编码在 docker-compose.yml 中随代码泄露 | 仓库里能看到生产数据库密码 | 敏感信息直接写进 yml 文件 | 用 `.env` 文件（加入 .gitignore）或 Docker Secrets 管理，yml 中只引用变量名 | [01-导览](./01-Docker核心原理-导览.md) |
| 容器未处理 SIGTERM 导致发布时请求被中断 | 滚动重启时正在处理的请求失败 | 应用未注册关闭钩子，收到 SIGTERM 后进程直接退出 | 声明 `STOPSIGNAL SIGTERM`，应用实现优雅关闭并留足停止宽限期 | [01-导览](./01-Docker核心原理-导览.md) |
| 镜像未定义 HEALTHCHECK，编排无法判断就绪 | 依赖服务过早连接，启动即报错 | 只在应用层写了健康端点，镜像本身没有 HEALTHCHECK 指令 | 在 Dockerfile 中用 `HEALTHCHECK CMD curl -f http://localhost:8080/actuator/health` 声明 | [01-导览](./01-Docker核心原理-导览.md) |

## 二、Kubernetes 核心概念

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| Pod 中硬编码配置，镜像和环境绑定无法复用 | 配置写在镜像中 | 使用 ConfigMap 存储非敏感配置，Secret 存储敏感信息 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 未设置 resources 资源限制，Pod 被 OOM Killer 杀死 | 未设置 requests 和 limits | 设置 resources.requests（调度决策）和 resources.limits（运行时限制） | [02-导览](./02-Kubernetes核心概念-导览.md) |
| Pod 未优雅关闭，请求被中断、数据不一致 | Pod 删除时先 SIGTERM，超时后 SIGKILL 强制终止 | 应用正确处理 SIGTERM 信号，完成正在处理的请求后再退出 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 使用 latest 标签，镜像版本不确定、回滚困难 | latest 标签版本不确定 | 使用明确的版本号或 Git commit hash | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 健康检查配置不当，Pod 频繁重启或被错误摘除 | livenessProbe 检查外部依赖导致重启雪崩；未设置 initialDelaySeconds | livenessProbe 不检查外部依赖；readinessProbe 可检查依赖；设置合理的 initialDelaySeconds | [02-导览](./02-Kubernetes核心概念-导览.md) |
| Pod 一直处于 ImagePullBackOff | 事件显示 Failed to pull image | 镜像名或标签写错、私有仓库未配置 imagePullSecrets、仓库不可达 | 核对镜像地址；创建 docker-registry 类型的 Secret 并在 Pod 中通过 imagePullSecrets 引用 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| Pod 反复重启进入 CrashLoopBackOff | 重启间隔按指数退避拉长，服务始终不可用 | 应用启动即崩溃：配置错误、依赖连不上、内存不足 | `kubectl describe pod` 看 Events，`kubectl logs <pod> --previous` 看上次崩溃日志 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 容器被 OOMKilled，退出码 137 | Pod 反复被杀，重启计数持续上升 | 容器内存超过 limits，或未设 limits 被宿主机 OOM Killer 干掉 | 设置合理 resources.limits，并确保 JVM 堆（-Xmx）明显小于容器内存上限 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| Service 集群内访问超时，Endpoints 为空 | `kubectl get endpoints` 查不到后端地址 | Service 的 selector 与 Pod 标签不匹配，或 Pod 未 Ready | 保证 selector 与 Pod template 的 labels 完全一致；检查 readinessProbe 是否一直失败 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 修改 ConfigMap 后应用读到的仍是旧值 | 配置已更新但行为没变 | 以 envFrom/环境变量注入的配置在容器启动时就已固化，不会热更新 | 改为 Volume 挂载并让应用监听文件变化，或直接滚动更新 Deployment 重启 Pod | [02-导览](./02-Kubernetes核心概念-导览.md) |
| ConfigMap 用 subPath 挂载后不再随更新同步 | 其他方式挂载的会更新，只有 subPath 的那份不变 | subPath 挂载不会同步 ConfigMap 的后续变更 | 避免使用 subPath；或改为环境变量注入并配合重启生效 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 未设置 requests 导致 Pod 无法调度或被驱逐 | Pod 长时间 Pending，或频繁 Evicted | 未声明资源请求，调度器无法为其预留资源，节点压力大时优先被驱逐 | 设置 resources.requests（影响调度）与 limits（运行时上限） | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 探针 initialDelaySeconds 太小导致慢启动应用被反复误杀 | 应用还没启动完就被重启，永远起不来 | 应用启动耗时超过 initialDelaySeconds，livenessProbe 判定失败 | 用 startupProbe 保护慢启动应用，或加大 initialDelaySeconds 与 failureThreshold | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 所有副本被调度到同一节点导致单点故障 | 该节点宕机后服务整体不可用 | 未配置 Pod 反亲和性，调度器可能把副本集中到同一节点 | 用 podAntiAffinity 按 app 标签把副本分散到不同节点 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 滚动更新期间接口出现 502 | 更新过程中部分请求失败 | 新 Pod 未就绪就被接入流量，或 maxUnavailable 设置过大 | 配置 readinessProbe 把关；合理设置 maxSurge/maxUnavailable；必要时加 preStop 缓冲 | [02-导览](./02-Kubernetes核心概念-导览.md) |
| rollout undo 后仍是问题版本 | 回滚命令执行了但版本没变化 | 历史 ReplicaSet 被清理，或 `--to-revision` 指向了错误的 revision | `kubectl rollout history` 确认版本号后精确回滚；适当提高 revisionHistoryLimit | [02-导览](./02-Kubernetes核心概念-导览.md) |
| 容器退出码 143 | 容器被 SIGTERM 终止 | 属正常终止信号，但应用未在 terminationGracePeriodSeconds 内完成退出 | 实现优雅关闭；必要时调大 terminationGracePeriodSeconds | [02-导览](./02-Kubernetes核心概念-导览.md) |
