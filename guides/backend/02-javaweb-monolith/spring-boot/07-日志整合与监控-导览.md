## 一、核心概念

### 1.1 日志框架演进

| 维度 | 内容 |
|------|------|
| 是什么 | Java 日志框架从 JUL 到 Log4j 再到 Logback 与 Log4j2 的四个阶段演进路线 |
| 能做什么 | JUL 内置简单日志；Log4j 开源划时代；Logback 性能更优 Spring Boot 默认；Log4j2 异步性能极致 |
| 怎么用 | 演进路线：`JUL -> Log4j -> Logback / Log4j2`（Logback 与 Log4j2 同为现代主流） |
| 原理和工作流程 | JUL 是 JDK 内置日志框架功能简单仅用于小型项目。Log4j 是 Apache 开源划时代产品已停止维护。Logback 由 Log4j 作者开发性能更优，是 Spring Boot 默认日志实现。Log4j2 是重构版本异步性能极致，是高并发场景首选。演进路线为 JUL -> Log4j -> Logback -> Log4j2，其中 Logback 和 Log4j2 同为现代主流框架。演进的核心驱动力是性能提升（尤其异步日志）、功能完善（滚动策略、桥接器）和 API 设计优化 |
| 缺点 | 框架多样导致选型困惑；历史遗留项目混用多套日志框架；JUL 功能简陋不适用生产；Log4j 已停止维护存在已知漏洞风险 |

### 1.2 SLF4J 门面模式

| 维度 | 内容 |
|------|------|
| 是什么 | SLF4J（Simple Logging Facade for Java）只定义接口不提供实现的日志门面，底层可切换具体实现 |
| 能做什么 | 解耦应用代码与日志框架；底层灵活切换 Logback/Log4j2/JUL；通过桥接器转发其他框架调用 |
| 怎么用 | `应用代码 -> SLF4J（门面接口） -> 具体实现（Logback / Log4j2 / JUL）` |
| 原理和工作流程 | SLF4J 是日志门面只定义接口不提供实现，应用代码面向 SLF4J 接口编程，底层可切换 Logback、Log4j2 等具体实现而无需修改业务代码，这是门面模式（Facade Pattern）的典型应用。桥接器（Bridge）用于将项目依赖的其他日志框架调用转发到 SLF4J：jcl-over-slf4j 将 commons-logging 调用桥接到 SLF4J，log4j-over-slf4j 将 Log4j 调用桥接到 SLF4J，jul-to-slf4j 将 JUL 调用桥接到 SLF4J。桥接器和适配器方向相反，同时引入 xxx-over-slf4j 和 slf4j-xxx 会造成死循环 |
| 缺点 | 桥接器与适配器共存导致死循环；门面层增加一层间接调用有微小开销；运行时绑定实现若缺失依赖会告警；桥接配置错误难排查 |

### 1.3 Spring Boot 默认日志

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Boot 默认使用 Logback + SLF4J 的开箱即用日志方案，无需额外配置即可输出日志 |
| 能做什么 | 开箱即用输出日志；默认 INFO 级别输出控制台；内置桥接器统一其他框架日志；格式含时间级别 PID 线程类名 |
| 怎么用 | 引入 `spring-boot-starter` 即自带 logback-classic + slf4j-api + jul-to-slf4j + log4j-over-slf4j |
| 原理和工作流程 | Spring Boot 默认使用 Logback 作为日志实现、SLF4J 作为日志门面，开箱即用无需额外配置。spring-boot-starter 依赖自带 logback-classic、slf4j-api、jul-to-slf4j、log4j-over-slf4j 等依赖，自动将 JUL 和 Log4j 的调用桥接到 SLF4J+Logback。默认行为为日志级别 INFO、输出目标控制台、日志格式为"时间 级别 PID 线程 类名 消息"。开发者引入 starter 即可获得完整日志能力，无需手动管理日志依赖 |
| 缺点 | 默认仅输出控制台不写文件需额外配置；INFO 级别可能不足以排查问题；默认格式不含上下文追踪信息；生产环境需自定义滚动策略 |

## 二、底层原理

### 2.1 Logback 架构

| 维度 | 内容 |
|------|------|
| 是什么 | Logback 由 Logger、Appender、Layout/Encoder 三大核心组件构成的日志框架架构 |
| 能做什么 | Logger 决定日志是否输出；Appender 决定输出目的地；Layout/Encoder 决定日志格式；Logger 按包名形成树形层级 |
| 怎么用 | `<appender name="CONSOLE" class="...ConsoleAppender"><encoder><pattern>${LOG_PATTERN}</pattern></encoder></appender>` |
| 原理和工作流程 | Logback 三大核心组件协同工作。Logger 是日志记录器，按包名形成树形层级，子 Logger 继承父 Logger 的级别，根 Logger 名称为 ROOT。Appender 是日志输出目的地，如 ConsoleAppender 输出控制台、RollingFileAppender 滚动输出文件、AsyncAppender 异步输出。Layout/Encoder 负责日志格式化，将日志事件转换为字符串。Logger 层级关系示例：ROOT(DEBUG) -> com.example(INFO) -> com.example.service(未设置继承 INFO) -> com.example.service.UserService(未设置继承 INFO)。日志请求从当前 Logger 沿层级向上查找有效级别判断是否输出 |
| 缺点 | Logger 层级继承可能导致意外输出；Appender 配置繁琐易出错；格式化占位符学习成本；多 Appender 重复输出增加开销 |

### 2.2 日志级别

| 维度 | 内容 |
|------|------|
| 是什么 | 日志按重要程度从低到高分为 TRACE、DEBUG、INFO、WARN、ERROR、OFF 六个级别及过滤机制 |
| 能做什么 | TRACE 最详细跟踪；DEBUG 调试信息；INFO 重要业务；WARN 警告；ERROR 错误；设高级别过滤低级别日志 |
| 怎么用 | `logging.level.com.example=DEBUG`；设为 INFO 时 TRACE/DEBUG 不输出，INFO/WARN/ERROR 输出 |
| 原理和工作流程 | 日志级别从低到高为 TRACE < DEBUG < INFO < WARN < ERROR < OFF。设为某级别时，低于该级别的日志不输出，等于或高于该级别的日志输出。例如设为 INFO 级别时 TRACE 和 DEBUG 不输出，INFO、WARN、ERROR 输出。各级别用途：TRACE 用于最详细的跟踪信息（方法入参出参、SQL 参数），DEBUG 用于调试信息（关键变量值、流程分支），INFO 用于重要业务信息（用户登录、订单创建），WARN 用于警告信息（缓存命中率低、重试次数较多），ERROR 用于错误信息（异常捕获、接口调用失败）。生产环境通常用 INFO，开发环境用 DEBUG |
| 缺点 | 级别划分主观易因团队习惯不一致；生产开 DEBUG 日志量爆炸；ERROR 滥用导致告警疲劳；级别调整需理解层级继承 |

### 2.3 logback-spring.xml 配置详解

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Boot 专属的 logback-spring.xml 配置文件，支持 Profile 多环境，优先级高于 logback.xml |
| 能做什么 | 引入默认配置；定义属性与日志格式；配置控制台/滚动文件/异步输出；按 springProfile 区分多环境 |
| 怎么用 | `<springProfile name="prod"><root level="WARN"><appender-ref ref="ASYNC_FILE"/></root></springProfile>` |
| 原理和工作流程 | logback-spring.xml 是 Spring Boot 专属配置文件，支持 springProfile 标签按环境区分配置，优先级高于 logback.xml。配置结构：include 引入 Spring Boot 默认配置（defaults.xml），property 定义 LOG_PATH 和 LOG_PATTERN 属性。ConsoleAppender 配置控制台输出含 pattern 和 charset。RollingFileAppender 配置滚动文件输出，使用 SizeAndTimeBasedRollingPolicy 按大小和时间滚动，设 maxFileSize（100MB）、maxHistory（30 天）、totalSizeCap（3GB）。AsyncAppender 配置异步输出，设 queueSize、discardingThreshold、neverBlock。springProfile 标签按 dev/prod 区分 root 级度和 Appender。常用占位符：%d 时间、%thread 线程名、%-5level 级别、%logger{50} Logger 名、%msg 消息、%n 换行、%pid 进程 ID |
| 缺点 | XML 配置冗长易出错；占位符语法多学习成本；多环境配置分散难维护；滚动策略参数调优需经验 |

### 2.4 异步日志

| 维度 | 内容 |
|------|------|
| 是什么 | 通过队列将日志写入操作交给后台线程处理以提升应用吞吐的日志机制，含 Logback 与 Log4j2 两种实现 |
| 能做什么 | Logback AsyncAppender 基于阻塞队列；Log4j2 AsyncLogger 基于 Disruptor 无锁队列；降低日志 I/O 对业务线程影响 |
| 怎么用 | Logback：`<appender name="ASYNC_FILE" class="...AsyncAppender"><queueSize>1024</queueSize><appender-ref ref="FILE"/></appender>` |
| 原理和工作流程 | Logback AsyncAppender 基于 ArrayBlockingQueue（有锁队列）实现，应用线程将日志写入阻塞队列后立即返回，后台线程从队列取出写入文件，队列满时丢弃或阻塞。Log4j2 AsyncLogger 基于 Disruptor 无锁环形队列实现，性能远超 Logback 异步方案。三者对比：Logback AsyncAppender 队列类型 ArrayBlockingQueue 有锁、吞吐量中、延迟中；Log4j2 AsyncAppender 同样基于 ArrayBlockingQueue 性能相近；Log4j2 AsyncLogger 基于 Disruptor 无锁、吞吐量极高、延迟极低。高并发场景推荐 Log4j2 AsyncLogger |
| 缺点 | 队列满时日志丢失风险；异步导致日志时间戳与实际略有偏差；Disruptor 增加依赖；异常崩溃时队列内日志可能丢失 |

### 2.5 日志框架切换（Logback 切换为 Log4j2）

| 维度 | 内容 |
|------|------|
| 是什么 | 在 Spring Boot 中将默认 Logback 切换为 Log4j2 的依赖排除与引入操作 |
| 能做什么 | 排除 spring-boot-starter-logging；引入 spring-boot-starter-log4j2；使用 log4j2-spring.xml 配置 |
| 怎么用 | 排除 `spring-boot-starter-logging` 后引入 `spring-boot-starter-log4j2` |
| 原理和工作流程 | 切换日志框架需在 spring-boot-starter-web 中通过 exclusions 排除 spring-boot-starter-logging（内含 Logback 依赖），然后引入 spring-boot-starter-log4j2 依赖。切换后 Spring Boot 自动适配 Log4j2 作为日志实现，应用代码仍面向 SLF4J 接口无需修改。配置文件从 logback-spring.xml 替换为 log4j2-spring.xml，支持 Spring Boot 的 Profile 特性。切换的核心场景是高并发下利用 Log4j2 AsyncLogger 基于 Disruptor 的无锁队列获得更高吞吐和更低延迟 |
| 缺点 | 排除不彻底导致依赖冲突；配置文件需重新编写；切换后桥接器行为变化需验证；非高并发场景收益不明显增加复杂度 |

### 2.6 Actuator 监控

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Boot Actuator 提供的生产级监控端点，开箱即用暴露应用运行时状态 |
| 能做什么 | 健康检查；指标采集；环境信息查看；线程转储；日志级别动态调整；自定义端点 |
| 怎么用 | 引入 `spring-boot-starter-actuator`；访问 `/actuator/health`、`/actuator/metrics` 等端点 |
| 原理和工作流程 | Spring Boot Actuator 提供生产级监控端点开箱即用。引入 spring-boot-starter-actuator 依赖后暴露多个端点：health（/actuator/health 健康检查数据库磁盘 Redis 等）、info（应用基本信息）、metrics（指标数据内存线程 GC 等）、env（环境变量和配置属性）、beans（所有 Bean 列表）、loggers（日志级别动态调整）、threaddump（线程转储）、heapdump（堆转储下载 hprof 文件）。通过 management.endpoints.web.exposure.include 配置暴露的端点，生产环境按需开放。HealthIndicator 内置多种健康检查器自动检测组件状态。自定义端点用 @Endpoint 注解 + @ReadOperation 方法，访问 /actuator/{id} 获取信息 |
| 缺点 | 端点暴露过多有安全风险；heapdump 可能泄露内存敏感数据；端点调用有性能开销；需配合鉴权保护敏感端点 |

### 2.7 Prometheus + Grafana 集成

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Boot 通过 Micrometer 暴露 Prometheus 指标、Grafana 读取并可视化的监控集成方案 |
| 能做什么 | 应用通过 Micrometer 采集指标；Prometheus 抓取 /actuator/prometheus；Grafana 可视化展示与告警 |
| 怎么用 | `应用 (Micrometer) -> /actuator/prometheus -> Prometheus (抓取) -> Grafana (展示)` |
| 原理和工作流程 | Spring Boot 通过 Micrometer 暴露 Prometheus 指标，Grafana 读取并可视化。集成流程：应用引入 micrometer-registry-prometheus 依赖，配置 management.endpoints.web.exposure.include 含 prometheus，应用通过 Micrometer 采集指标并暴露在 /actuator/prometheus 端点。Prometheus 按配置的抓取间隔拉取该端点指标数据存储。Grafana 配置 Prometheus 数据源，通过仪表盘可视化指标并配置告警规则。可自定义业务指标，用 Counter 计数（如订单创建总数）、Timer 计时（如订单创建耗时），通过 MeterRegistry 注册 |
| 缺点 | 三组件部署运维成本高；Prometheus 拉取模式有延迟；指标存储长期占用磁盘；Grafana 仪表盘配置繁琐 |

## 三、实战应用

### 3.1 自定义 HealthIndicator

| 维度 | 内容 |
|------|------|
| 是什么 | 通过实现 HealthIndicator 接口自定义健康检查逻辑并接入 Actuator health 端点的实战示例 |
| 能做什么 | 检查第三方接口可用性；返回自定义健康状态和详情；区分 up/down 状态；集成到 /actuator/health |
| 怎么用 | `@Component public class CustomHealthIndicator implements HealthIndicator { public Health health() { return Health.up().withDetail("service","available").build(); } }` |
| 原理和工作流程 | CustomHealthIndicator 实现 HealthIndicator 接口标注 @Component 注册为 Spring Bean。health 方法执行自定义健康检查逻辑（如调用第三方接口检测可用性），检查通过返回 Health.up() 并附带 withDetail（如 service=available、latency=50ms），检查失败返回 Health.down() 并附带错误详情（如 service=unavailable、error=connection timeout）。Spring Boot 自动发现所有 HealthIndicator 实现并聚合到 /actuator/health 端点，任一 down 则整体状态为 down。配合 management.endpoint.health.show-details=always 可查看各健康检查器详情 |
| 缺点 | 健康检查逻辑执行慢拖累端点响应；检查失败导致整体健康状态 down 影响判断；外部依赖检查增加耦合；缺乏超时控制可能阻塞 |

### 3.2 Prometheus 指标暴露配置

| 维度 | 内容 |
|------|------|
| 是什么 | 配置 Spring Boot 暴露 Prometheus 指标端点并自定义业务指标的实战示例 |
| 能做什么 | 引入 Micrometer Prometheus 依赖；配置暴露 prometheus 端点；自定义 Counter 和 Timer 业务指标 |
| 怎么用 | `Counter.builder("order.created.total").tag("type","normal").register(meterRegistry); orderCounter.increment();` |
| 原理和工作流程 | 第一步引入 micrometer-registry-prometheus 依赖。第二步配置 management.endpoints.web.exposure.include 含 prometheus，配置 management.metrics.tags.application 标记应用名。第三步自定义业务指标，OrderService 通过构造器注入 MeterRegistry，用 Counter.builder 创建计数器（order.created.total 描述订单创建总数，带 type 标签），用 Timer.builder 创建计时器（order.create.duration 描述订单创建耗时），register 注册到 MeterRegistry。业务方法 createOrder 中用 orderTimer.record 包裹业务逻辑并在其中 orderCounter.increment 递增计数。Prometheus 抓取 /actuator/prometheus 端点获取这些指标 |
| 缺点 | 指标命名不规范导致查询困难；标签基数过高导致指标爆炸；Counter/Timer 误用导致数据失真；指标过多影响端点响应 |

### 3.3 日志最佳实践

| 维度 | 内容 |
|------|------|
| 是什么 | 日志开发中使用参数化日志、异常记录、级别守卫等最佳实践的实战示例 |
| 能做什么 | 参数化日志避免拼接开销；异常对象作为最后参数记录堆栈；DEBUG 复杂拼接用 isDebugEnabled 守卫 |
| 怎么用 | `log.info("用户 {} 登录成功", username);`；`log.error("读取文件失败，路径：{}", path, e);` |
| 原理和工作流程 | 最佳实践一使用参数化日志（占位符 {}），SLF4J 会先判断级别再拼接参数，避免字符串拼接在级别不匹配时浪费性能，错误写法 log.info("用户 " + username + " 登录成功") 会先执行拼接。最佳实践二记录异常时异常对象作为最后一个参数，SLF4J 自动识别并打印完整堆栈，如 log.error("读取文件失败，路径：{}", path, e)。最佳实践三 DEBUG 级别日志当日志拼接复杂时（如遍历集合）使用 isDebugEnabled 守卫，仅在级别开启时才执行拼接逻辑，避免不必要的对象构造和字符串拼接开销。这些实践兼顾日志可读性与运行性能 |
| 缺点 | 参数化日志占位符数量与参数不匹配时报错；isDebugEnabled 守卫增加代码冗余；异常记录位置错误导致堆栈丢失；过度日志影响性能 |

## 四、常见面试题

### 1. SLF4J 和 Logback 的关系是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | SLF4J 日志门面（接口）与 Logback 日志实现之间的解耦关系，门面模式的典型应用 |
| 能做什么 | SLF4J 定义接口不提供实现；Logback 提供具体实现；应用面向接口编程底层灵活切换 |
| 怎么用 | 应用代码：`Logger logger = LoggerFactory.getLogger(MyClass.class);` 底层绑定 Logback |
| 原理和工作流程 | SLF4J 是日志门面（接口），Logback 是日志实现。应用代码面向 SLF4J 接口编程，底层可灵活切换为 Logback、Log4j2 等实现而无需修改业务代码。这种设计是门面模式（Facade Pattern）的典型应用，SLF4J 屏蔽了不同日志实现 API 的差异，提供统一的调用接口。运行时 SLF4J 通过类路径查找绑定的实现（如 logback-classic），将日志调用委托给具体实现处理。切换实现只需替换依赖无需改代码 |
| 缺点 | 运行时绑定若实现缺失会告警或无输出；门面层增加一层间接调用有微小开销；桥接器配置错误导致日志丢失或死循环 |

### 2. 日志级别有哪些？如何选择？

| 维度 | 内容 |
|------|------|
| 是什么 | 日志六个级别 TRACE/DEBUG/INFO/WARN/ERROR/OFF 的划分及生产与开发环境的选择策略 |
| 能做什么 | TRACE 极详细跟踪；DEBUG 调试；INFO 业务；WARN 警告；ERROR 错误；按环境选择合适级别 |
| 怎么用 | 生产：`logging.level.root=INFO`；开发：`logging.level.root=DEBUG` |
| 原理和工作流程 | 从低到高为 TRACE、DEBUG、INFO、WARN、ERROR、OFF。设某级别时低于该级别不输出。生产环境通常使用 INFO，记录重要业务信息和警告错误，避免日志量过大。开发环境使用 DEBUG，输出调试信息便于排查。TRACE 用于极详细的跟踪信息（如 SQL 参数、方法入参出参），仅在深度排查时临时开启。ERROR 用于记录异常但不应输出过多，避免日志淹没关键信息。选择原则是生产够用、开发详尽、按需动态调整 |
| 缺点 | 级别划分主观因团队而异；生产开 DEBUG 日志量爆炸；ERROR 滥用导致告警疲劳；级别调整需重启或调端点 |

### 3. 如何动态调整日志级别？

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Actuator loggers 端点在不重启应用的情况下动态调整日志级别的机制 |
| 能做什么 | 运行时调整任意 Logger 级别；无需重启应用；按包名精细控制；通过配置文件静态设置 |
| 怎么用 | `POST /actuator/loggers/com.example.service` body `{"configuredLevel":"DEBUG"}` |
| 原理和工作流程 | 通过 Actuator 的 loggers 端点动态调整日志级别无需重启应用。发送 POST 请求到 /actuator/loggers/{loggerName}，请求体含 configuredLevel 字段指定目标级别，Actuator 调用 Logback 的 LoggerContext 修改对应 Logger 的级别立即生效。也可通过 logging.level.com.example=DEBUG 在配置文件中静态设置，但需重启。loggers 端点还支持 GET 查询当前所有 Logger 的有效级别和配置级别。这种方式在排查生产问题时临时开 DEBUG 收集信息后恢复，避免重启带来的服务中断 |
| 缺点 | 端点暴露有安全风险需鉴权；调整后重启会丢失需配合配置持久化；全局开 DEBUG 日志量爆炸；端点未暴露则无法使用 |

### 4. Logback 和 Log4j2 的异步日志有什么区别？

| 维度 | 内容 |
|------|------|
| 是什么 | Logback AsyncAppender 与 Log4j2 AsyncLogger 在队列实现和性能上的对比 |
| 能做什么 | Logback 基于 ArrayBlockingQueue 有锁；Log4j2 基于 Disruptor 无锁；高并发推荐 Log4j2 |
| 怎么用 | Logback：`AsyncAppender` + `queueSize`；Log4j2：`AsyncLogger` + Disruptor 依赖 |
| 原理和工作流程 | Logback 的 AsyncAppender 基于 ArrayBlockingQueue（有锁队列）实现，应用线程将日志写入阻塞队列后返回，后台线程从队列取出写入文件，高并发下存在锁竞争。Log4j2 的 AsyncLogger 基于 Disruptor 无锁环形队列实现，每个日志事件通过序列号机制写入 RingBuffer，消费者线程按序列号读取处理，无锁竞争吞吐量可达 Logback 的数倍，延迟更低。高并发场景推荐 Log4j2 AsyncLogger，普通场景 Logback 异步方案已足够 |
| 缺点 | Logback 有锁队列高并发性能瓶颈；Log4j2 Disruptor 增加依赖；异步队列满日志丢失；崩溃时队列日志可能丢失 |

### 5. Spring Boot Actuator 的作用是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Boot Actuator 提供的生产级监控能力，通过 HTTP 端点暴露应用运行时状态 |
| 能做什么 | 健康检查；指标采集；环境信息；线程转储；日志级别动态调整；结合 Prometheus+Grafana 监控告警 |
| 怎么用 | 引入 `spring-boot-starter-actuator`；访问 `/actuator/health`、`/actuator/metrics` 等 |
| 原理和工作流程 | Actuator 提供生产级监控能力，包括健康检查、指标采集、环境信息、线程转储等。通过 HTTP 端点暴露运行时状态便于运维监控和问题排查。核心端点有 health（健康检查数据库磁盘 Redis）、metrics（指标数据内存线程 GC）、env（环境变量和配置属性）、loggers（日志级别动态调整）、threaddump（线程转储）、heapdump（堆转储）。通过 management.endpoints.web.exposure.include 控制暴露端点。结合 Prometheus + Grafana 可实现完整的监控告警体系，Prometheus 抓取 /actuator/prometheus 指标，Grafana 可视化并配置告警 |
| 缺点 | 端点暴露过多有安全风险；heapdump 泄露内存敏感数据；端点调用有性能开销；需配合鉴权保护 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 日志与监控开发中日志拼接性能、桥接器冲突、队列满丢日志、文件无限增长等高频问题汇总 |
| 能做什么 | 用参数化日志避免拼接；排查桥接器与适配器共存；调大队列防丢失；配置滚动策略防磁盘写满；日志脱敏防泄露 |
| 怎么用 | `log.info("msg {}", arg)`；只保留桥接器排除适配器；`queueSize` 调大 + `neverBlock=true`；`maxHistory` + `totalSizeCap` |
| 原理和工作流程 | 日志字符串拼接性能下降因级别不匹配时仍执行字符串拼接，应用参数化日志 log.info("msg {}", arg) 由 SLF4J 先判断级别再拼接。桥接器与适配器共存导致应用启动死循环，因 log4j-over-slf4j 和 slf4j-log4j 同时存在形成循环调用，需只保留桥接器排除适配器。异步日志队列满导致日志丢失，AsyncAppender 默认队列满后丢弃，需调大 queueSize 并设 neverBlock=true 明确丢弃策略。日志文件无限增长导致磁盘写满，需用 RollingFileAppender 配置 maxHistory 和 totalSizeCap 限制保留数量和总大小。敏感信息泄露因直接打印完整请求响应，需日志脱敏并用 @ToString(exclude=...) 排除敏感字段。Actuator 端点暴露过多有安全风险，生产环境只暴露 health,info,prometheus 并配合 Spring Security 鉴权 |
| 缺点 | 参数化日志占位符不匹配报错；桥接器排查需理解依赖方向；队列调大增加内存占用；滚动策略参数调优需经验；脱敏规则维护成本高 |
