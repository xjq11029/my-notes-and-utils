## 一、核心概念

### 1.1 认证与授权的区别

| 维度 | 内容 |
|------|------|
| 是什么 | 认证是验证用户身份（你是谁），授权是验证用户权限（你能做什么）的两个安全概念 |
| 能做什么 | 认证通过用户名密码等凭证确认身份；授权基于角色或权限决定可访问资源 |
| 怎么用 | 认证：`authenticationManager.authenticate(token)`；授权：`http.authorizeHttpRequests(auth -> auth.requestMatchers("/admin/**").hasRole("ADMIN"))` |
| 原理和工作流程 | 认证发生在请求处理前，用户提交凭证（密码、Token 等），系统与存储中的记录比对验证身份，验证通过后生成身份凭证（Session、JWT）。授权发生在认证之后，系统根据已认证用户的角色或权限集合，判断其是否有权访问目标资源。认证回答"你是谁"，授权回答"你能做什么"，二者前后衔接，先认证后授权。Spring Security 中认证由 AuthenticationManager 负责，授权由 FilterSecurityInterceptor 或 AuthorizationManager 负责 |
| 缺点 | 二者常被混淆；授权策略复杂时维护成本高；认证失败和授权失败的响应区分不清 |

### 1.2 为什么需要认证

| 维度 | 内容 |
|------|------|
| 是什么 | HTTP 无状态协议下通过携带身份凭证让服务器识别用户身份的必要性说明 |
| 能做什么 | 在无状态 HTTP 上建立用户身份上下文；区分不同用户；保护受限资源 |
| 怎么用 | 每次请求携带身份凭证：`Authorization: Bearer <token>` 或 `Cookie: JSESSIONID=xxx` |
| 原理和工作流程 | HTTP 是无状态协议，每次请求独立，服务器默认不知道两次请求是否来自同一用户。认证机制通过在请求中携带身份凭证（SessionId 或 Token），让服务器能够将请求关联到特定用户。服务端验证凭证有效后，建立用户身份上下文，后续可据此做授权决策。无状态设计简化了 HTTP 协议但牺牲了用户追踪能力，认证机制通过凭证传递弥补这一缺口 |
| 缺点 | 无状态导致每次请求都需验证凭证增加开销；凭证传递有泄露风险；凭证管理增加系统复杂度 |

## 二、基于 Session 的认证

### 2.1 工作原理

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Session 的认证机制，服务端创建 Session 存储用户信息并通过 Cookie 传递 SessionId |
| 能做什么 | 服务端存储用户状态；通过 JSESSIONID 关联请求；支持主动失效和踢人 |
| 怎么用 | `HttpSession session = request.getSession(); session.setAttribute("user", user);` |
| 原理和工作流程 | 用户登录时服务端创建 HttpSession 对象存储用户信息，生成随机 SessionId，通过 Set-Cookie 响应头将 JSESSIONID 返回浏览器。浏览器后续请求自动携带 JSESSIONID Cookie，服务端根据 SessionId 在 Session 集合中查找对应 Session，获取用户信息处理请求。Session 默认存储在服务端内存中，有超时机制（默认 30 分钟），超时或主动 invalidate 后失效。SessionId 随机性强，难以伪造，安全性依赖服务端存储 |
| 缺点 | 服务端内存存储占用资源；分布式环境需 Session 共享；不适用于移动端和前后端分离；SessionId 劫持风险 |

### 2.2 Session 的优势与劣势

| 维度 | 内容 |
|------|------|
| 是什么 | Session 认证机制的优缺点对比分析 |
| 能做什么 | 服务端可控安全性高；SessionId 难伪造；可主动踢人；但占用内存且分布式难共享 |
| 怎么用 | `session.invalidate();` 主动销毁 Session 踢出用户 |
| 原理和工作流程 | Session 的优势在于服务端控制力强，用户状态存储在服务端，客户端只持有随机 SessionId，安全性高且可主动失效（删除 Session 即踢人）。劣势在于 Session 存储占用服务端内存，用户量增大时内存压力大；分布式环境下多台服务器需 Session 共享（粘滞、复制、集中存储），增加架构复杂度；Session 基于 Cookie 不适用于移动端和跨域前后端分离场景。这些劣势催生了 JWT 无状态认证方案 |
| 缺点 | 内存占用随用户量增长；分布式共享方案各有局限；不适用移动端和跨域场景；Cookie 限制影响可用性 |

### 2.3 分布式 Session 解决方案

| 维度 | 内容 |
|------|------|
| 是什么 | 多服务器集群环境下解决 Session 共享的三种方案：粘滞、复制、集中存储 |
| 能做什么 | Nginx ip_hash 粘滞；Tomcat 集群广播复制；Redis 集中存储（推荐） |
| 怎么用 | `spring.session.store-type=redis` 一行配置启用 Spring Session + Redis |
| 原理和工作流程 | 方案一 Session 粘滞，Nginx 配置 ip_hash 使同一 IP 请求始终路由到同一服务器，简单但服务器宕机 Session 丢失且负载不均。方案二 Session 复制，Tomcat 集群间广播 Session 数据实现共享，服务器间共享但网络开销大只适合小集群。方案三集中式存储（推荐），将 Session 存入 Redis 所有服务器共享，服务器无状态易扩展，但依赖 Redis 可用性。Spring Session + Redis 通过 filter 包装 request 替换原生 HttpSession 实现透明接入 |
| 缺点 | 粘滞方案宕机丢 Session 且负载不均；复制方案网络开销大；集中存储依赖 Redis 可用性增加故障点 |

## 三、基于 JWT 的认证

### 3.1 JWT 结构

| 维度 | 内容 |
|------|------|
| 是什么 | JWT 由 Header、Payload、Signature 三部分以点号分隔组成的紧凑令牌格式 |
| 能做什么 | Header 声明算法类型；Payload 携带用户数据；Signature 防篡改签名 |
| 怎么用 | `eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjF9.xxx签名xxx` |
| 原理和工作流程 | JWT 由三部分组成以 . 分隔。Header 是 JSON 对象声明签名算法（如 HS256）和类型（JWT），经 Base64URL 编码。Payload 是 JSON 对象存放声明（claims），如 userId、过期时间 exp，同样 Base64URL 编码，注意 Payload 仅编码不加密，不应存放敏感信息。Signature 用 Header 指定的算法（如 HMAC-SHA256）对 Base64 编码的 Header 加 . 加 Payload 用密钥计算签名。验证时服务端用相同密钥重新计算签名比对，任何篡改都会导致签名不匹配 |
| 缺点 | Payload 仅 Base64 编码非加密，不能存敏感信息；令牌体积大于 SessionId 每次请求都传；密钥泄露则所有令牌可伪造 |

### 3.2 JWT 认证流程

| 维度 | 内容 |
|------|------|
| 是什么 | 客户端登录获取 JWT 后，每次请求携带 JWT 由服务端验证身份的认证流程 |
| 能做什么 | 登录签发 JWT；请求携带 JWT；服务端验签提取用户；无状态认证 |
| 怎么用 | `Authorization: Bearer <token>` |
| 原理和工作流程 | 客户端提交用户名密码登录，服务端验证通过后生成 JWT（含用户 ID、过期时间），用密钥签名后返回客户端。客户端将 JWT 存储在本地（localStorage 或 Cookie），后续请求在 Authorization 头携带 Bearer Token。服务端拦截器取出 Token，用密钥验证签名有效性，检查过期时间，解析 Payload 提取用户信息，建立认证上下文处理请求。整个流程服务端不存储 Token 状态，是无状态认证，天然支持分布式 |
| 缺点 | 签发后无法主动失效（需黑名单）；过期前 Token 泄露即被冒用；每次请求传输完整 Token 增加带宽开销 |

### 3.3 JWT vs Session

| 维度 | 内容 |
|------|------|
| 是什么 | JWT 无状态认证与 Session 有状态认证两种方案的对比 |
| 能做什么 | JWT 状态存客户端天然分布式；Session 状态存服务端可主动失效；二者适用场景不同 |
| 怎么用 | JWT：`Authorization: Bearer <token>`；Session：`Cookie: JSESSIONID=xxx` |
| 原理和工作流程 | Session 状态存储在服务端（内存或 Redis），客户端只持 SessionId，服务端可控可主动失效，但分布式需共享存储。JWT 状态存储在客户端，服务端不存 Token，天然支持分布式无状态，但签发后无法主动失效（需黑名单配合）。Session 体积小只传 SessionId，JWT 携带用户信息每次请求都传体积大。Session 适用于传统 Web 应用（服务端渲染），JWT 适用于前后端分离、移动端、微服务架构。安全性上 Session 服务端控制更强，JWT 依赖短过期加 Refresh Token |
| 缺点 | JWT 无法主动失效需黑名单增加有状态成分；Session 分布式共享增加复杂度；JWT 体积大增加传输开销；Session 不适用移动端 |

### 3.4 JWT 的常见问题

| 维度 | 内容 |
|------|------|
| 是什么 | JWT 使用中 Token 泄露、主动失效、双 Token 机制三个常见问题的解决方案 |
| 能做什么 | 短过期加 Refresh Token 应对泄露；黑名单实现主动失效；双 Token 机制平衡安全与体验 |
| 怎么用 | Access Token 15 分钟 + Refresh Token 7 天 |
| 原理和工作流程 | Token 泄露应对方案是设置短过期时间（15 分钟）配合 Refresh Token，泄露后影响时间短，配合 HTTPS 防中间人攻击。主动失效方案是维护 Token 黑名单（Redis key 为 blacklist:token，过期时间为 Token 剩余有效时间），验证时检查黑名单，但这引入了状态破坏纯无状态。双 Token 机制中 Access Token 短期有效直接访问资源，Refresh Token 长期有效用于刷新 Access Token；Access Token 过期用 Refresh Token 换新，Refresh Token 过期则重新登录，Refresh Token 泄露可服务端标记失效 |
| 缺点 | 黑名单破坏无状态特性；短过期导致频繁刷新影响体验；双 Token 机制增加实现复杂度；Refresh Token 泄露仍需服务端撤销 |

## 四、Spring Security

### 4.1 核心架构

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Security 基于 Servlet 过滤器链的安全框架核心组件体系 |
| 能做什么 | 认证管理；密码加密；安全上下文存储；过滤器链处理请求；授权决策 |
| 怎么用 | `SecurityContextHolder.getContext().getAuthentication()` |
| 原理和工作流程 | Spring Security 核心基于 SecurityFilterChain 过滤器链，每个 HTTP 请求经过多个过滤器处理。SecurityContextHolder 用 ThreadLocal 存储当前用户安全上下文（Authentication 对象，含主体、凭证、权限）。UserDetailsService 从数据库加载用户信息封装为 UserDetails。AuthenticationManager 是认证管理器，委托给多个 AuthenticationProvider 完成认证。PasswordEncoder 负责密码加密验证（如 BCrypt）。请求经过滤器链完成认证后，授权过滤器根据 Authentication 的权限集合做访问控制决策 |
| 缺点 | 过滤器链长且复杂，学习曲线陡；配置繁琐易出错；默认行为对初学者不透明；与 Spring MVC 集成有细节陷阱 |

### 4.2 基本配置示例

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Security 基于 SecurityFilterChain 的链式配置示例，涵盖路径授权、CSRF、无状态会话等 |
| 能做什么 | 配置公开接口和受保护接口；禁用 CSRF；设置无状态会话；添加自定义过滤器 |
| 怎么用 | `@Bean public SecurityFilterChain filterChain(HttpSecurity http) throws Exception { http.csrf(c -> c.disable()).authorizeHttpRequests(a -> a.anyRequest().authenticated()); return http.build(); }` |
| 原理和工作流程 | 通过 HttpSecurity 构建器链式配置安全规则。authorizeHttpRequests 配置路径匹配与授权规则（permitAll、hasRole、authenticated）。csrf.disable 禁用 CSRF 保护（前后端分离场景 Token 在 Header 不在 Cookie，天然防 CSRF）。sessionManagement 设为 STATELESS 不创建 Session（配合 JWT）。addFilterBefore 在指定过滤器前插入自定义过滤器（如 JWT 认证过滤器插在 UsernamePasswordAuthenticationFilter 前）。build 后生成 SecurityFilterChain 注册到 servlet 容器，每个请求经此链处理 |
| 缺点 | 配置项繁多，初学者易遗漏关键配置；禁用 CSRF 需确认场景安全；过滤器顺序错误导致认证失效；版本升级配置方式变动大 |

### 4.3 BCrypt 密码加密

| 维度 | 内容 |
|------|------|
| 是什么 | BCrypt 一种自带盐值、不可逆、加密强度可调的密码哈希算法，适合密码存储 |
| 能做什么 | 每次加密生成不同盐值；强度参数可调（2^cost 次哈希）；抗 GPU 暴力破解和彩虹表 |
| 怎么用 | `BCryptPasswordEncoder encoder = new BCryptPasswordEncoder(); String hashed = encoder.encode("123456"); encoder.matches("123456", hashed);` |
| 原理和工作流程 | BCrypt 每次加密随机生成盐值并内嵌于哈希结果中（格式 $2a$10$盐值哈希值），无需额外存储盐值。加密强度由 cost 参数控制（如 10 表示 2^10=1024 次迭代哈希），cost 越大越安全越慢。验证时从哈希结果中提取盐值和 cost，用相同参数对输入密码哈希后比对。盐值随机使相同密码每次哈希结果不同，抵抗彩虹表攻击；慢哈希特性使 GPU 暴力破解成本极高。Spring Security 默认推荐 BCryptPasswordEncoder |
| 缺点 | 计算慢增加注册登录延迟；cost 参数过高影响性能；无法解密只能比对验证；旧系统迁移需重新哈希 |

## 五、OAuth2 授权码模式

### 5.1 四种授权模式

| 维度 | 内容 |
|------|------|
| 是什么 | OAuth2 定义的四种授权许可模式：授权码、隐式、密码、客户端凭证 |
| 能做什么 | 授权码模式适合有后端 Web 应用；密码模式适合自家应用；客户端模式适合服务间调用 |
| 怎么用 | 授权码模式：`GET /oauth/authorize?response_type=code&client_id=xxx&redirect_uri=xxx` |
| 原理和工作流程 | 授权码模式安全性最高，用户在授权服务器同意后返回授权码（code），后端用 code 换取 Access Token，Token 不经过浏览器，适合有后端的 Web 应用。隐式模式直接返回 Token 不经 code 交换，适用于纯前端应用但 Token 暴露在浏览器已不推荐。密码模式用户直接提供账号密码给客户端换取 Token，仅适用于自家应用。客户端模式客户端以自身身份获取 Token，适用于服务间调用无用户参与。四种模式安全性从高到低：授权码 > 密码 > 客户端 > 隐式 |
| 缺点 | 授权码流程步骤多实现复杂；隐式模式已不推荐；密码模式暴露密码给客户端有风险；模式选择需按场景权衡 |

### 5.2 授权码模式流程（最常用）

| 维度 | 内容 |
|------|------|
| 是什么 | OAuth2 授权码模式的完整流程，用户授权后通过授权码换取 Access Token |
| 能做什么 | 用户同意授权；返回授权码；后端换 Token；获取用户信息；创建本地 JWT |
| 怎么用 | 1.跳转授权页 2.用户同意返回 code 3.后端用 code 换 Token 4.用 Token 获取用户信息 |
| 原理和工作流程 | 1. 用户点击第三方登录（如微信登录），跳转到授权服务器授权页，携带 client_id 和 redirect_uri。2. 用户同意授权，授权服务器重定向到 redirect_uri 并携带授权码 code。3. 后端用授权码 code 加上 client_secret 向授权服务器换取 Access Token，此步骤在服务端完成 Token 不经浏览器。4. 后端用 Access Token 调用资源服务器 API 获取用户信息。5. 后端根据用户信息创建或关联本地用户，签发自己的 JWT 返回客户端。授权码作为中间凭证缩短了 Token 暴露窗口 |
| 缺点 | 流程步骤多，实现复杂；redirect_uri 校验不当可被劫持；client_secret 泄露风险；用户需理解授权含义 |

## 六、常见 Web 安全攻击与防御

### 6.1 CSRF（跨站请求伪造）

| 维度 | 内容 |
|------|------|
| 是什么 | 攻击者诱导已登录用户在不知情下向目标网站提交恶意请求的攻击方式 |
| 能做什么 | 利用浏览器自动携带 Cookie 特性伪造请求；防御用 CSRF Token 或 Token 存 Header |
| 怎么用 | 防御：`<input type="hidden" name="_csrf" value="${csrf.token}">` |
| 原理和工作流程 | CSRF 攻击原理是用户登录 A 网站后浏览器持有 A 的 Cookie，访问恶意 B 网站时，B 网站构造向 A 的请求（如转账），浏览器自动携带 A 的 Cookie 发送，A 服务器误以为是用户本人操作。利用条件是浏览器自动携带 Cookie 且请求含认证凭证。防御方式一是 CSRF Token，服务端生成随机 Token 放入表单隐藏字段和 Cookie，提交时验证两者一致，攻击者无法获取 Token。防御方式二是前后端分离将 Token 存 Header 而非 Cookie，浏览器不会自动携带自定义 Header，天然防 CSRF。Spring Security 默认开启 CSRF 保护 |
| 缺点 | CSRF Token 增加表单复杂度；Token 验证有性能开销；前后端分离禁用 CSRF 需确保 Token 不在 Cookie |

### 6.2 XSS（跨站脚本攻击）

| 维度 | 内容 |
|------|------|
| 是什么 | 攻击者向网页注入恶意脚本，用户访问时在浏览器执行的攻击方式 |
| 能做什么 | 存储型 XSS 存入数据库；反射型 XSS 经 URL 反射；DOM 型 XSS 纯前端漏洞 |
| 怎么用 | 防御：输出编码 `<` 转 `&lt;`；Cookie 设 HttpOnly |
| 原理和工作流程 | XSS 分三类。存储型 XSS 是攻击者将恶意脚本提交存入数据库，其他用户访问页面时脚本执行，危害最大。反射型 XSS 是恶意脚本在 URL 参数中，服务端将其反射回页面执行。DOM 型 XSS 是纯前端漏洞，JS 操作 DOM 时执行恶意代码。防御措施包括：对用户输入校验过滤；输出时 HTML 实体编码（< 转 &lt;）；设置 Content-Security-Policy 响应头限制脚本来源；Cookie 设置 HttpOnly 使 JS 无法读取防窃取。框架如 Thymeleaf、React 默认转义输出降低 XSS 风险 |
| 缺点 | 输出编码可能破坏正常内容显示；CSP 配置不当影响功能；富文本场景过滤规则复杂；HttpOnly 不能防 XSS 只能防 Cookie 窃取 |

### 6.3 SQL 注入

| 维度 | 内容 |
|------|------|
| 是什么 | 攻击者通过用户输入拼接 SQL 语句改变 SQL 语义，从而窃取或篡改数据的攻击方式 |
| 能做什么 | 拼接 SQL 改变查询逻辑；绕过认证；窃取数据；执行危险操作 |
| 怎么用 | 防御：`PreparedStatement` 参数化查询；MyBatis 用 `#{}` 而非 `${}` |
| 原理和工作流程 | SQL 注入原理是用户输入被直接拼接进 SQL 语句，如 SELECT * FROM users WHERE name='" + input + "'"，攻击者输入 ' OR '1'='1 使条件恒真绕过认证。防御核心是参数化查询（PreparedStatement），SQL 语句结构和参数分离，参数作为数据而非代码执行，数据库预编译 SQL 后只绑定参数值，不会改变 SQL 语义。MyBatis 中 #{} 使用 PreparedStatement 参数化安全，${} 是字符串拼接有注入风险，仅用于表名、列名等不能参数化的场景。ORM 框架默认参数化查询 |
| 缺点 | 动态表名、列名无法参数化需额外校验；复杂查询参数化写法繁琐；老项目遗留拼接 SQL 改造成本高 |

## 七、常见面试题

### 1. ★★ Session 和 JWT 的区别？分别适用于什么场景？

| 维度 | 内容 |
|------|------|
| 是什么 | Session 有状态认证与 JWT 无状态认证两种方案的对比与场景选择 |
| 能做什么 | Session 状态存服务端可主动失效；JWT 状态存客户端天然分布式；适用场景不同 |
| 怎么用 | Session：`Cookie: JSESSIONID=xxx`；JWT：`Authorization: Bearer <token>` |
| 原理和工作流程 | Session 状态存储在服务端（内存或 Redis），客户端只持 SessionId，服务端可控可主动失效，扩展需共享存储（Redis），适用于传统 Web 应用服务端渲染。JWT 状态存储在客户端，服务端不存 Token，天然支持分布式无状态，签发后无法主动失效需黑名单配合，适用于前后端分离、移动端、微服务架构。Session 扩展需 Redis 共享增加依赖，JWT 天然分布式但安全性依赖短过期加 Refresh Token。Session 可主动踢人，JWT 无法主动失效 |
| 缺点 | JWT 无法主动失效需黑名单引入状态；Session 分布式共享增加复杂度；JWT 体积大传输开销；Session 不适用移动端 |

### 2. ★★ JWT 的 Token 泄露了怎么办？

| 维度 | 内容 |
|------|------|
| 是什么 | JWT Token 泄露后的应急处理与预防方案 |
| 能做什么 | 短过期加 Refresh Token 缩小影响；HTTPS 防中间人；HttpOnly Cookie 防 XSS 窃取 |
| 怎么用 | Access Token 15 分钟过期 + Refresh Token 7 天 |
| 原理和工作流程 | JWT 签发后无法主动失效，Token 泄露的应对策略是多层次的。第一设置短过期时间（15 分钟），泄露后影响窗口小。第二配合 Refresh Token 机制，Access Token 过期后用 Refresh Token 换新，Refresh Token 可服务端标记失效。第三使用 HTTPS 传输防止中间人攻击窃取 Token。第四将 Token 存 HttpOnly Cookie 防止 XSS 脚本读取 Token。第五关键操作（如支付）要求二次验证（密码或短信验证码）。第六 Refresh Token 与设备绑定，泄露后可按设备撤销 |
| 缺点 | 短过期导致频繁刷新影响体验；Refresh Token 泄露仍需服务端撤销；黑名单破坏无状态；HttpOnly Cookie 跨域配置复杂 |

### 3. ★★ Spring Security 的过滤器链原理？

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Security 基于 Servlet Filter 实现的安全过滤器链机制 |
| 能做什么 | SecurityContext 管理；表单登录认证；JWT 认证；授权决策 |
| 怎么用 | `@EnableWebSecurity` 配合 `SecurityFilterChain` Bean 配置 |
| 原理和工作流程 | Spring Security 基于 Servlet Filter 实现，SecurityFilterChain 包含多个有序过滤器处理每个 HTTP 请求。核心过滤器包括 SecurityContextPersistenceFilter（用 SecurityContextRepository 加载或保存 SecurityContext 到 ThreadLocal）、UsernamePasswordAuthenticationFilter（处理表单登录认证）、FilterSecurityInterceptor 或 AuthorizationFilter（授权决策，根据 Authentication 权限判断是否放行）。每个过滤器处理后调用 FilterChain.doFilter 传递给下一个。自定义 JWT 过滤器通常插在 UsernamePasswordAuthenticationFilter 前，解析 Token 设置 SecurityContext。过滤器链由 FilterChainProxy 统一代理 |
| 缺点 | 过滤器链长且顺序敏感，配置错误难排查；学习曲线陡；版本间过滤器变动大；与 Servlet 容器集成细节复杂 |

### 4. ★★ 如何防止 CSRF 攻击？

| 维度 | 内容 |
|------|------|
| 是什么 | 跨站请求伪造攻击的防御方案，包括 CSRF Token 和 Header Token 两种方式 |
| 能做什么 | 服务端生成 CSRF Token；前后端分离用 Header Token；Spring Security 默认开启 |
| 怎么用 | 传统：表单隐藏字段 `_csrf`；前后端分离：`X-CSRF-TOKEN` 请求头 |
| 原理和工作流程 | CSRF 攻击利用浏览器自动携带 Cookie 特性伪造请求。传统方案是服务端生成随机 CSRF Token，放入表单隐藏字段和 Cookie，提交时服务端验证两者一致，攻击者无法获取表单中的 Token 故无法伪造。前后端分离方案是将 Token 存储在请求 Header 而非 Cookie，浏览器不会自动携带自定义 Header，攻击者构造的跨站请求无法携带 Token，天然防 CSRF。Spring Security 默认开启 CSRF 保护（CsrfFilter），前后端分离通常禁用（因 Token 在 Header 不在 Cookie 无需 CSRF 保护） |
| 缺点 | CSRF Token 增加表单和请求复杂度；Token 生成验证有性能开销；前后端分离禁用 CSRF 需确保 Token 不在 Cookie；移动端无 Cookie 不受 CSRF 威胁 |

### 5. ★★ BCrypt 为什么比 MD5/SHA 更适合密码存储？

| 维度 | 内容 |
|------|------|
| 是什么 | BCrypt 相比 MD5/SHA 在密码存储场景下的优势分析 |
| 能做什么 | 自带盐值无需额外存储；加密强度可调；慢哈希抗暴力破解；抗彩虹表 |
| 怎么用 | `new BCryptPasswordEncoder().encode("password")` |
| 原理和工作流程 | BCrypt 自带随机盐值内嵌于哈希结果中，每次加密结果不同，无需额外存储盐值，抵抗彩虹表攻击。加密强度通过 cost 参数可调（2^cost 次迭代），cost 越大越安全越慢，可随硬件升级提升。BCrypt 是慢哈希算法，计算耗时（1024 次以上迭代），使 GPU 暴力破解成本极高。MD5/SHA 是通用哈希算法设计目标是快速计算，无盐值时相同密码哈希结果相同易被彩虹表破解，即使加盐也因计算快可被 GPU 高速暴力破解。Argon2 是更新的密码哈希算法，抗 GPU 和 ASIC 破解能力更强 |
| 缺点 | 计算慢增加登录延迟；cost 参数过高影响性能；无法解密只能比对；硬件升级需提升 cost 但旧密码需重新哈希 |

## 八、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 登录认证与安全开发中 JWT 存敏感信息、Session 内存存储、MD5 存密码等高频错误汇总 |
| 能做什么 | JWT 只存用户 ID；Session 用 Redis 共享；密码用 BCrypt；Refresh Token 与设备绑定 |
| 怎么用 | `spring.session.store-type=redis`；`new BCryptPasswordEncoder()` |
| 原理和工作流程 | JWT 中存储敏感信息的风险在于 Payload 仅 Base64 编码非加密，任何人可解码，应只存用户 ID 敏感信息从数据库查。Session 默认内存存储重启后丢失，需配置 Spring Session + Redis 持久化。CSRF 不适用前后端分离是因为 Token 在 Header 不在 Cookie，浏览器不会自动携带自定义 Header，前后端分离应禁用 CSRF。密码用 MD5 存储易被彩虹表破解，因 MD5 计算快无盐值，应用 BCrypt 或 Argon2。Refresh Token 泄露长期被冒用，需与设备绑定并支持服务端撤销 |
| 缺点 | JWT 只存 ID 增加数据库查询；Redis Session 依赖 Redis 可用性；BCrypt 计算慢影响性能；设备绑定增加管理复杂度 |
