## 一、为什么 Agent 系统更需要异常与上下文管理

| 维度 | 内容 |
|------|------|
| 是什么 | 把 Agent 的失败分成输入错误、可重试错误、致命错误、超时取消等类型，并按作用域释放资源的方法论。 |
| 能做什么 | 让一次工具失败不拖垮整个会话；把错误转换成模型能理解的 observation；保证流、连接、会话在每条路径上都被关闭。 |
| 怎么用 | 在工具适配层分类异常；在 Agent 循环里根据 `retryable` 决定重试、反馈或终止；用 `with`、`async with`、`finally` 管理资源。 |
| 原理和工作流程 | 错误沿调用链向上传播，在边界被转换成领域异常；资源由上下文管理器在离开作用域时释放，异常路径也不例外。 |
| 缺点 | 分层过细会增加样板代码；分类错误会把可恢复问题当成致命错误，或把致命错误当成可重试问题。 |

**速记**：异常按层转换，资源按作用域释放。
**易错点**：把所有失败都包成同一种异常，Agent 就失去了重试和反馈的判断依据。

## 二、异常模型：BaseException 与 Exception

| 维度 | 内容 |
|------|------|
| 是什么 | Python 以 `BaseException` 为根的异常继承树，`Exception` 是常规错误分支，另有 `SystemExit`、`KeyboardInterrupt`、`GeneratorExit`。 |
| 能做什么 | 区分业务错误与进程退出/取消；用 `except` 精确捕获；用 `ExceptionGroup` 批量处理多个异常。 |
| 怎么用 | 业务代码捕获 `Exception` 或具体子类；异步取消捕获 `CancelledError` 后清理并重新抛出；3.11+ 用 `except*` 处理异常组。 |
| 原理和工作流程 | `except` 按类型匹配并沿异常类的 MRO 查找；裸 `except` 匹配 `BaseException`；`except*` 把异常组拆开，匹配的子异常被处理，其余继续传播。 |
| 缺点 | 捕获 `BaseException` 会吞掉取消和退出信号；`ExceptionGroup` 在 3.10 及以下不可用，跨版本代码需要兼容分支。 |

**速记**：业务捕获 `Exception`，不要碰 `BaseException`。
**易错点**：`CancelledError` 从 3.8 起继承 `BaseException`，`except Exception` 不会捕获它。

## 三、EAFP 与 LBYL

| 维度 | 内容 |
|------|------|
| 是什么 | EAFP 是"先操作、出错再捕获"，LBYL 是"先检查、再执行"两种错误处理风格。 |
| 能做什么 | 选择更适合外部资源的写法；避免检查与使用之间的竞态；为模型参数选择前置校验方式。 |
| 怎么用 | 文件、网络、字典键用 `try/except`；用户输入和工具参数用 schema 或 `if` 校验。 |
| 原理和工作流程 | EAFP 依赖操作本身原子地给出成功或失败；LBYL 先读取状态再执行，状态可能在两步之间变化，形成 TOCTOU。 |
| 缺点 | EAFP 把异常当控制流，滥用会降低可读性；LBYL 存在竞态，且检查逻辑可能与实际操作不一致。 |

**速记**：外部资源用 EAFP，用户输入用 LBYL。
**易错点**：`if path.exists(): path.read_text()` 不是原子操作，文件可能在中途被删除。

## 四、try/except/else/finally 的执行顺序

| 维度 | 内容 |
|------|------|
| 是什么 | `try` 保护可能出错的代码，`except` 处理匹配异常，`else` 处理无异常分支，`finally` 做必执行清理。 |
| 能做什么 | 精确控制异常捕获范围；把成功逻辑与可能出错的逻辑分开；保证清理一定执行。 |
| 怎么用 | 把可能抛异常的语句放 `try`；成功后的后续逻辑放 `else`；关闭资源放 `finally`。 |
| 原理和工作流程 | 先执行 `try`；无异常执行 `else`，有匹配异常执行 `except`；离开整个语句前执行 `finally`，包括 `return`、`break`、异常传播等路径。 |
| 缺点 | `finally` 中的 `return`、`break`、`continue` 会覆盖返回值并吞掉在途异常；`else` 的异常不会被同一个 `except` 捕获。 |

**速记**：`else` 是"没出错才走"，`finally` 是"怎么走都要走"。
**易错点**：在 `finally` 里 `return` 会让异常凭空消失，是隐蔽的 bug。

## 五、raise 与异常链

| 维度 | 内容 |
|------|------|
| 是什么 | `raise` 抛出异常，`raise ... from ...` 建立显式原因，`raise ... from None` 隐藏上下文展示。 |
| 能做什么 | 保留底层根因；把第三方异常转换成领域异常；在最终用户界面隐藏内部细节。 |
| 怎么用 | 包装时 `raise ToolError("...") from exc`；重新抛出用裸 `raise`；最终输出前记录日志再考虑 `from None`。 |
| 原理和工作流程 | 在 `except` 中抛新异常会自动设置 `__context__`；`from exc` 设置 `__cause__` 和 `__suppress_context__`；traceback 按原因链展示。 |
| 缺点 | `from None` 只是隐藏展示，不清理原因；只记录 `str(exc)` 会丢失类型和堆栈；多层重复包装会让异常链过长。 |

**速记**：包装用 `from exc`，重新抛出用裸 `raise`。
**易错点**：`from None` 不等于"没有异常"，排障信息仍然存在于 `__context__` 中。

## 六、自定义异常与业务错误分层

| 维度 | 内容 |
|------|------|
| 是什么 | 以 `AgentError` 为基类，按工具、模型、输入等维度分层，并用 `retryable`、`code` 等属性表达处理策略。 |
| 能做什么 | 让 Agent 循环只依赖领域异常；区分可重试与致命错误；为日志、指标和用户提示提供稳定错误码。 |
| 怎么用 | 继承 `Exception`，调用 `super().__init__(message)`，保存少量可序列化字段；工具适配层负责转换第三方异常。 |
| 原理和工作流程 | 业务层抛出领域异常，循环捕获后读取属性决定重试、反馈或终止；异常沿调用链传播，直到某个边界处理或记录。 |
| 缺点 | 层级过深难以维护和序列化；把编程错误也转换成业务异常会掩盖 bug；字段过多会让 `str(exc)` 变得不可读。 |

**速记**：浅层异常树 + `retryable`/`code` 属性，比深层继承更实用。
**易错点**：自定义 `__init__` 不调用 `super().__init__`，`str(exc)` 和 `args` 可能为空。

## 七、异常包装与转换的边界

| 维度 | 内容 |
|------|------|
| 是什么 | 在工具适配层、Agent 循环、API/CLI 入口等边界转换异常，而不是在每个函数里捕获。 |
| 能做什么 | 隔离第三方 SDK；统一错误码；保证日志只记录一次；对用户输出脱敏文案。 |
| 怎么用 | 适配层捕获传输异常并 `raise ToolError(...) from exc`；循环层根据领域异常决策；入口层 `logger.exception` 并返回错误码。 |
| 原理和工作流程 | 异常从底层向上传播，每经过一个边界可以选择转换、记录或放行；越靠近用户，信息越少、越结构化。 |
| 缺点 | 边界划分不清会导致重复记录或重复包装；过早转换会丢失底层类型；过度脱敏会增加排障成本。 |

**速记**：底层转换，循环决策，入口记录并脱敏。
**易错点**：每层都 `logger.exception` 再重新抛出，会在日志里制造多份相同堆栈。

## 八、上下文管理器协议

| 维度 | 内容 |
|------|------|
| 是什么 | 实现 `__enter__` 和 `__exit__` 的对象，用 `with` 保证进入初始化和退出清理成对执行。 |
| 能做什么 | 自动关闭文件、连接、会话；在退出时提交或回滚；在异常路径执行清理。 |
| 怎么用 | `with Resource() as r:`；`__enter__` 返回资源，`__exit__` 接收异常三参数并返回是否抑制。 |
| 原理和工作流程 | 进入 `with` 调用 `__enter__`；正常退出或异常退出都调用 `__exit__`；返回真值抑制异常，返回假值继续传播。 |
| 缺点 | `__enter__` 抛异常时 `__exit__` 不执行；`__exit__` 自身抛异常会替换原异常；错误地返回 True 会吞掉异常。 |

**速记**：`__enter__` 给资源，`__exit__` 收尾并决定是否放行异常。
**易错点**：清理代码里再抛异常，会覆盖真正需要排查的原始异常。

## 九、contextlib.contextmanager

| 维度 | 内容 |
|------|------|
| 是什么 | 用生成器函数写上下文管理器的装饰器：`yield` 前是进入逻辑，`yield` 后是退出逻辑。 |
| 能做什么 | 用更少的代码实现会话作用域、临时目录、计时器、事务回滚。 |
| 怎么用 | `@contextmanager` 装饰生成器；`yield` 一次并放在 `try/finally` 中；异常会在 `yield` 处抛出。 |
| 原理和工作流程 | 装饰器把生成器包装成上下文管理器；进入时运行到 `yield`，退出时继续执行；捕获异常后不重新抛出即抑制。 |
| 缺点 | 生成器只能使用一次；不能直接暴露多个方法；忘记 `try/finally` 会导致异常路径不清理。 |

**速记**：`yield` 前准备，`yield` 后清理，异常在 `yield` 处出现。
**易错点**：`except Exception: pass` 会把 `with` 块里的异常静默吞掉。

## 十、contextlib 常用工具

| 维度 | 内容 |
|------|------|
| 是什么 | 标准库提供的 `closing`、`suppress`、`nullcontext` 等小型上下文工具。 |
| 能做什么 | 关闭只有 `close()` 的对象；忽略明确的异常；在"可选资源"场景提供空上下文。 |
| 怎么用 | `with closing(obj) as c:`；`with suppress(FileNotFoundError):`；`nullcontext(value)`。 |
| 原理和工作流程 | `closing` 在退出时调用 `close`；`suppress` 在 `__exit__` 中匹配异常并返回 True；`nullcontext` 的进入和退出都是空操作。 |
| 缺点 | `suppress(Exception)` 范围过宽；`closing` 不抑制异常；`nullcontext` 只适合占位，不能替代真实资源管理。 |

**速记**：`closing` 关对象，`suppress` 忽略指定异常，`nullcontext` 占位。
**易错点**：`suppress` 不是"忽略所有错误"的快捷方式，列出的类型必须真的可以忽略。

## 十一、ExitStack 与动态资源管理

| 维度 | 内容 |
|------|------|
| 是什么 | 用栈动态注册多个上下文和清理回调，退出时按后进先出顺序统一关闭。 |
| 能做什么 | 打开数量不定的文件或连接；保证部分资源进入失败时已进入的资源仍被关闭；把资源所有权移交给调用方。 |
| 怎么用 | `with ExitStack() as stack:`；`stack.enter_context(cm)`；`stack.callback(fn, ...)`；`stack.pop_all()`。 |
| 原理和工作流程 | 每进入一个上下文就把退出函数压栈；退出时逆序弹出执行；某个 `__enter__` 失败时，之前压栈的清理仍会执行。 |
| 缺点 | 关闭顺序是隐式的，调试时不如嵌套 `with` 直观；回调抛异常会中断后续清理；异步资源需要 `AsyncExitStack`。 |

**速记**：`ExitStack` 管数量，后进先出关资源。
**易错点**：回调里抛异常会打断剩余清理，回调应自己捕获并记录。

## 十二、异步上下文管理器 async with

| 维度 | 内容 |
|------|------|
| 是什么 | 实现 `__aenter__`/`__aexit__` 的异步上下文管理器，用 `async with` 进入和退出。 |
| 能做什么 | 管理异步连接、流式响应、会话；在退出时 `await` 关闭或刷新；处理任务取消后的清理。 |
| 怎么用 | `async with session:`；`@asynccontextmanager` 装饰异步生成器；异步生成器用 `aclosing` 确保关闭。 |
| 原理和工作流程 | `async with` 会 `await __aenter__` 和 `__aexit__`；取消时 `CancelledError` 在 `await` 点抛出，`finally` 仍执行；`asyncio.timeout` 通过取消实现超时。 |
| 缺点 | 清理中的 `await` 可能再次被取消；同步与异步上下文管理器不能混用；超时和取消的异常类型随版本变化。 |

**速记**：异步资源用 `async with`，生成器退出用 `aclosing`。
**易错点**：`async for` 中 `break` 不保证关闭异步生成器，必须显式 `aclose` 或用 `aclosing`。

## 十三、重试、超时与资源清理模式

| 维度 | 内容 |
|------|------|
| 是什么 | 只对可重试错误做有限次退避重试，并为单次调用和整体流程设置超时与清理策略。 |
| 能做什么 | 吸收瞬时故障；避免雪崩式重试；防止请求无限等待；保证超时或取消后资源被释放。 |
| 怎么用 | 捕获明确的 `RetryableError`；指数退避加抖动；设置最大次数和总 deadline；用 `with`/`async with`/`finally` 清理。 |
| 原理和工作流程 | 每次失败后等待一段时间再试；达到上限后抛出最后一次异常；`asyncio.timeout` 取消协程，线程池超时只让等待方返回。 |
| 缺点 | 非幂等操作重试会产生重复副作用；线程超时不会杀死线程；总预算设计不当会让重试拖垮请求。 |

**速记**：只重试可重试的，退避有上限，总时长有 deadline。
**易错点**：`except Exception` 包住整个调用，会把参数错误和鉴权失败也重试。

## 十四、常见坑与根因分析

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总裸 `except`、吞异常、`finally` 中 `return`、异常链丢失、上下文管理器吞异常、重试过宽六类问题。 |
| 能做什么 | 根据现象快速定位根因；在代码评审中识别危险写法；把隐性失败变成可观测错误。 |
| 怎么用 | 对照"现象、根因、修复"表格排查；至少记录一次异常；清理逻辑不改控制流；重试只捕获明确类型。 |
| 原理和工作流程 | 六类问题分别来自 `BaseException` 捕获范围、静默处理、`finally` 控制流、异常链属性、`__exit__` 返回值、重试捕获范围。 |
| 缺点 | 表格只覆盖高频模式；真实故障可能同时涉及多个层次，需要结合日志和 traceback 分析。 |

**速记**：先看异常被谁捕获、被记录几次、清理有没有改控制流。
**易错点**：`except ... as exc` 的 `exc` 在块结束后会被删除，闭包不能跨块引用。

## 十六、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 六个工程陷阱：裸 `except`、吞异常、`finally` 中 `return`、丢失异常链、`contextmanager` 清理缺失、重试过宽。 |
| 能做什么 | 在上线前逐项检查异常处理代码；减少"失败但无日志"和"取消不生效"类事故。 |
| 怎么用 | 捕获具体异常；至少记录一次；清理逻辑不改控制流；包装保留 `from exc`；`yield` 放 `try/finally`；重试有上限和退避。 |
| 原理和工作流程 | 每个坑都对应一个语言机制：`BaseException`、静默处理、`finally` 控制流、异常链、生成器清理、重试捕获范围。 |
| 缺点 | 规则较多，容易变成机械检查；过度防御会增加样板代码，应按故障代价取舍。 |

**速记**：具体捕获、记录一次、清理不改流、保留原因、重试有界。
**易错点**：`finally` 里写 `return` 不仅吞异常，还会让静态检查工具发出警告。
