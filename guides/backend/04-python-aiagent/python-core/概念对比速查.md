# Python核心 - 概念对比速查

---

### Python vs Java 语言特性对比

| 对比维度 | Python | Java |
|---------|--------|------|
| 核心定位 | 解释型、动态类型、通用脚本语言，强调简洁和可读性 | 编译型、静态类型、面向对象企业级语言，强调健壮性和可维护性 |
| 适用场景 | 数据分析、AI/ML、自动化脚本、快速原型、Web后端 | 企业级后端、Android开发、大数据处理（Hadoop/Spark）、金融系统 |
| 性能特点 | 解释执行较慢，GIL限制多线程，CPU密集型任务需多进程 | JIT编译优化，JVM性能优秀，真正多线程，启动慢但运行快 |
| 类型系统 | 鸭子类型，运行时检查，灵活但缺乏编译期保障 | 静态强类型，编译期检查，泛型支持完善，类型安全高 |
| 代码块界定 | 靠缩进，缩进错误即语法错误 | 靠花括号，缩进仅为可读性约定 |
| 依赖与构建 | `pip install` + `requirements.txt`，无标准生命周期 | Maven/Gradle 解析依赖树并执行编译打包测试生命周期 |
| 行为增强机制 | 装饰器：定义时执行的高阶函数，直接包装替换原函数 | 注解：元数据标记，需反射或编译期处理器（APT）读取后由框架实现行为 |
| 抽象与多态 | 鸭子类型 + `abc`/`typing.Protocol` 结构化类型，无需显式声明 | 接口 `implements` 编译期强制，类型体系约束强 |
| 并发模型 | GIL 下多线程不适合 CPU 密集；多进程真并行；asyncio 协程处理海量 IO | JVM 原生多线程真并行；`CompletableFuture`/虚拟线程处理高并发 |
| 集合处理 | 生成器惰性求值 + `itertools`，可 `send`/`throw` 做协程 | Stream 惰性管道，支持 `parallelStream()` 并行 |
| 空值处理 | `None` 单例，判断用 `is None`，`Optional` 仅为类型提示 | `null` + `Optional<T>` 显式包装，编译期提示空指针风险 |
| 选择建议 | 适合快速开发、数据科学、AI领域；代码量少、迭代快 | 适合大型团队协作、高并发系统、长期维护的企业级项目 |

### 列表 vs 元组 vs 集合 vs 字典

| 对比维度 | 列表（list） | 元组（tuple） | 集合（set） | 字典（dict） |
|---------|-------------|--------------|------------|-------------|
| 核心定位 | 有序可变序列，通用容器 | 有序不可变序列，用于固定数据 | 无序不重复元素集合 | 键值对映射，键唯一 |
| 适用场景 | 需要频繁增删改的顺序数据 | 多返回值、字典键、不希望被修改的数据 | 去重、成员检测、集合运算 | 查找、映射、计数、缓存 |
| 性能特点 | 尾部追加O(1)，中间插入O(n)，查询O(n) | 访问O(1)，不可变无需额外内存 | 成员检测O(1)，无序，元素必须可哈希 | 键查找O(1)，键必须可哈希 |
| 内存开销 | 有一定预留空间 | 比列表更紧凑，无额外预留 | 有哈希表开销 | 有哈希表开销 |
| 是否可哈希 | 否，不能作字典键 | 是（元素全可哈希时） | 否（`frozenset` 可以） | 否 |
| 选择建议 | 需要动态增删改的顺序数据 | 固定不变的数据、需要哈希的场景 | 去重、集合运算、快速成员检测 | 键值映射、计数、缓存 |

### 深拷贝 vs 浅拷贝

| 对比维度 | 浅拷贝（shallow copy） | 深拷贝（deep copy） |
|---------|----------------------|---------------------|
| 核心定位 | 复制外层容器，内层元素仍共享引用 | 递归复制所有层级，完全独立的对象 |
| 适用场景 | 内层元素为不可变对象、只需修改外层结构 | 多层嵌套可变对象、需要完全独立的副本 |
| 性能特点 | 快，只复制一层引用 | 慢，递归复制所有层级，可能遇到循环引用 |
| 内存开销 | 小，内层元素共享 | 大，每层都创建新对象 |
| 常见产生方式 | `copy.copy()`、`list[:]`、`list.copy()`、`dict.copy()` | `copy.deepcopy()` |
| 选择建议 | `copy.copy()`：内层元素不可变或无需修改时 | `copy.deepcopy()`：嵌套可变对象且需要独立修改时 |

### 多线程 vs 多进程 vs 协程（适用场景对比）

| 对比维度 | 多线程（threading） | 多进程（multiprocessing） | 协程（asyncio） |
|---------|--------------------|--------------------------|----------------|
| 核心定位 | OS 调度的抢占式并发，共享同一进程内存 | 独立进程真并行，各自拥有解释器与 GIL | 单线程事件循环上的协作式并发 |
| 适用场景 | I/O 密集且依赖阻塞库、需要兼容旧代码 | CPU 密集计算、批量数据处理、需绕过 GIL | 海量 I/O 并发：爬虫、网关、长连接服务 |
| 是否受 GIL 限制 | 是，CPU 密集任务被串行化、性能不升反降 | 否，各进程独立 GIL 可真正并行 | 是，但本身单线程，靠协程切换而非线程切换 |
| 数据共享 | 共享内存，需 `Lock`/`Queue` 保证安全 | 需序列化传递（`Queue`/`Pipe`/共享内存） | 单线程内共享，无需加锁 |
| 资源开销 | 线程栈 + OS 调度切换，数百个即显吃力 | 进程创建 + 内存翻倍 + 序列化，较重 | 协程极轻，可支撑数千至数万并发 |
| 典型限制 | 竞态条件、死锁、调试困难 | 内存占用高、启动慢、跨进程调试难 | 需全链路异步，一处阻塞调用即卡死事件循环 |
| 选型口诀 | I/O 密集 + 阻塞库 → 多线程 | CPU 密集 → 多进程 | 海量 I/O 且可改造 → asyncio |

### 可迭代对象 vs 迭代器 vs 生成器

| 对比维度 | 可迭代对象（Iterable） | 迭代器（Iterator） | 生成器（Generator） |
|---------|----------------------|-------------------|-------------------|
| 核心定位 | 实现 `__iter__` 的容器，可重复遍历 | 同时实现 `__iter__` 与 `__next__`，一次性消费 | 含 `yield` 的函数或生成器表达式，本身即迭代器 |
| 典型代表 | `list`、`dict`、`str`、`set`、`range` | `iter(list)`、`itertools` 各工具、文件对象 | `def g(): yield 1`、`(x for x in it)` |
| 判定方式 | `hasattr(obj, "__iter__")` | `iter(obj) is obj` | `inspect.isgenerator(obj)` |
| 状态管理 | 每次 `iter()` 返回新迭代器，天然可重复 | 手动维护状态（如索引），耗尽即失效 | 解释器自动保存栈帧与指令指针 |
| 内存特征 | 已持有全部元素 | 惰性，按需产生 | 惰性，按需产生 |
| 双向交互 | 不支持 | 不支持 | 支持 `send()`/`throw()`，可做协程 |
| 常见陷阱 | 误认为所有可迭代对象都能 `next()` | 耗尽后再次遍历无输出，需重建 | 只能消费一次；无 `len()` 与索引 |
