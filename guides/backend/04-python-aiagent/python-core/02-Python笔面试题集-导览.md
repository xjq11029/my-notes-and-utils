### 1. 作用域与 LEGB

| 维度 | 内容 |
|------|------|
| 是什么 | Python 按 Local→Enclosing→Global→Built-in 顺序解析名字的规则。 |
| 能做什么 | 判断变量在何处被找到；理解闭包为何能访问外层变量；定位 UnboundLocalError。 |
| 怎么用 | 直接按名字引用即可；内层函数可读外层变量，写则需 `global`/`nonlocal`。 |
| 原理和工作流程 | 解释器沿命名空间链自内向外查找，命中即停；Enclosing 排在 Global 之前，故嵌套函数优先看到外层函数局部变量。 |
| 缺点 | 顺序反直觉易记错；函数内赋值即视为局部变量，导致"明明外面有却报未定义"。 |

### 2. global 与 nonlocal

| 维度 | 内容 |
|------|------|
| 是什么 | 在函数内部声明变量绑定到模块级（global）或外层函数级（nonlocal）作用域的关键字。 |
| 能做什么 | 修改模块级计数器/配置；在闭包中修改被捕获的外层局部变量。 |
| 怎么用 | `global total`；`nonlocal n`。 |
| 原理和工作流程 | 默认函数内赋值创建新的局部名字，加 `global`/`nonlocal` 后改为向外层命名空间写入；`nonlocal` 只向外找最近的外层函数作用域，找不到则 SyntaxError。 |
| 缺点 | 滥用 `global` 破坏封装、难以追踪状态来源；`nonlocal` 只能用于嵌套函数，模块级无效。 |

### 3. *args 与 **kwargs

| 维度 | 内容 |
|------|------|
| 是什么 | 收集多余位置参数为 tuple（*args）与多余关键字参数为 dict（**kwargs）的可变参数机制。 |
| 能做什么 | 接收任意数量参数；转发参数；解包调用 `f(*lst, **d)`。 |
| 怎么用 | `def f(*args, **kwargs)`；调用侧 `f(*lst, **d)`。 |
| 原理和工作流程 | 调用时解释器把多余位置参数打包为 tuple 绑定 args、多余关键字参数打包为 dict 绑定 kwargs；调用侧的 `*`/`**` 是反向解包。形参顺序必须是普通→默认→`*args`→仅关键字→`**kwargs`。 |
| 缺点 | 参数含义不直观、IDE 无法提示；滥用削弱类型安全；顺序写错直接语法错误。 |

---

### 4. 带参数的装饰器

| 维度 | 内容 |
|------|------|
| 是什么 | 需要先接收装饰器参数、再接收被装饰函数的三层嵌套装饰器结构。 |
| 能做什么 | 让装饰器可配置（重试次数、缓存大小、限流阈值）；等价于 `func = deco(arg)(func)`。 |
| 怎么用 | `@timer(repeat=3)`；实现为「外层收参数 → 中层收函数 → 内层 wrapper」。 |
| 原理和工作流程 | `@deco(arg)` 先执行 `deco(arg)` 得到真正的装饰器，再把它应用到函数；因此最外层返回的不是 wrapper 而是 decorator。 |
| 缺点 | 三层嵌套可读性下降；忘记最外层 return decorator 会直接报错；与 `functools.wraps` 配合不当会丢元信息。 |

### 5. functools.wraps 的作用

| 维度 | 内容 |
|------|------|
| 是什么 | 把被装饰函数的元信息复制到 wrapper 上的装饰器。 |
| 能做什么 | 保留 `__name__`/`__doc__`/`__module__`/`__qualname__`/`__dict__`；写入 `__wrapped__` 供 `inspect.unwrap()` 还原。 |
| 怎么用 | `@functools.wraps(func)` 加在 wrapper 定义上。 |
| 原理和工作流程 | 装饰器返回 wrapper 并替换原函数名，元信息随之变成 wrapper 的；wraps 显式复制原函数元信息并建立反向引用，使签名与文档查询仍指向原函数。 |
| 缺点 | 不写会导致日志、调试、文档、依赖签名的框架（FastAPI/Flask 路由、依赖注入）异常；复制 `__dict__` 也可能带来意外的属性覆盖。 |

### 6. MRO 与 C3 算法

| 维度 | 内容 |
|------|------|
| 是什么 | Python 用 C3 线性化算法计算出的方法解析顺序，存放于 `__mro__`。 |
| 能做什么 | 确定多继承下方法与属性的查找顺序；实现 Mixin 协作；让 `super()` 正确链式调用。 |
| 怎么用 | `Class.__mro__` 或 `Class.mro()` 查看顺序。 |
| 原理和工作流程 | C3 合并各父类 MRO 并满足三条约束：子类优先、保持基类声明顺序、保持单调性；`merge` 取"不在其他列表尾部出现"的表头元素。菱形继承 `D(B,C)` 得到 `D→B→C→A→object`。 |
| 缺点 | 顺序不直观、无法手算验证；约束冲突时抛 `TypeError: Cannot create a consistent MRO`；过度多继承使类层次混乱。 |

### 7. __slots__ 的作用

| 维度 | 内容 |
|------|------|
| 是什么 | 声明实例允许属性名、用固定槽位替代 `__dict__` 的类级声明。 |
| 能做什么 | 省内存（大量小对象省 40%~50%）；阻止动态添加属性；略提升属性访问速度。 |
| 怎么用 | `__slots__ = ("x", "y")`。 |
| 原理和工作流程 | 声明的名字被编译为类级描述符，实例按固定偏移存取，不再创建 `__dict__`；未声明属性赋值直接抛 AttributeError。 |
| 缺点 | 失去动态挂属性能力；子类不声明会重新获得 `__dict__` 使优化失效；默认不支持弱引用（需加 `__weakref__`）；与多继承、`@property` 同名字段易冲突。 |

### 8. 魔术方法 __call__

| 维度 | 内容 |
|------|------|
| 是什么 | 让实例可被当作函数调用的魔术方法。 |
| 能做什么 | 实现带状态的"函数"；写装饰器类、依赖注入容器、偏函数包装；用 `callable()` 判断。 |
| 怎么用 | `def __call__(self, *args, **kwargs)`；`obj()` 等价于 `type(obj).__call__(obj)`。 |
| 原理和工作流程 | 解释器在对象被调用时查找其类型的 `__call__`，因此实例与函数在调用协议上等价。 |
| 缺点 | 与 `__init__`（初始化）、`__new__`（创建）职责易混淆；隐式调用链降低可读性；过度使用让"对象即函数"语义模糊。 |

### 9. property 与描述符

| 维度 | 内容 |
|------|------|
| 是什么 | 用 `@property` 把方法包装成属性访问的机制，本质是数据描述符。 |
| 能做什么 | 以属性语法读写并加校验；定义只读属性；延迟计算；替代冗长 getter/setter。 |
| 怎么用 | `@property` + `@x.setter`（setter 函数名必须与 property 同名）。 |
| 原理和工作流程 | property 实现 `__get__`/`__set__`/`__delete__`，属性访问触发 `__get__`、赋值触发 `__set__`，从而以属性语法执行自定义逻辑。 |
| 缺点 | 不提供真正访问控制（`obj._x` 仍可读写）；继承时覆盖 setter 需重新声明 property；比直接属性访问略慢。 |

### 10. 元类 metaclass

| 维度 | 内容 |
|------|------|
| 是什么 | 类的类型，负责创建类对象的"类的工厂"，默认是 `type`。 |
| 能做什么 | 类定义时注入属性/方法；收集字段元数据；自动注册子类（插件系统）；强制编码规范。 |
| 怎么用 | `class Foo(metaclass=Meta)`；或 `type(name, bases, namespace)` 动态建类。 |
| 原理和工作流程 | 类体执行后收集 namespace，解释器确定元类（metaclass 参数或基类元类中最派生者），调用 `metaclass(name, bases, namespace)` 返回类对象，故元类在**类定义时**生效。 |
| 缺点 | 侵入性强、与多继承/`__slots__` 组合复杂、错误难调试；优先考虑 `__init_subclass__` 或类装饰器。 |

### 11. 可迭代对象与迭代器

| 维度 | 内容 |
|------|------|
| 是什么 | 实现 `__iter__` 的是可迭代对象，同时实现 `__iter__` 与 `__next__` 的是迭代器。 |
| 能做什么 | 支持 `for` 遍历；区分"可重复遍历的容器"与"一次性迭代器"；用 `iter(obj) is obj` 判定。 |
| 怎么用 | `it = iter(obj)`；`next(it)`；耗尽抛 `StopIteration`。 |
| 原理和工作流程 | `for` 循环先 `iter()` 取迭代器再反复 `next()`，捕获 `StopIteration` 结束；list/dict/str 只实现 `__iter__`，每次遍历返回新迭代器。 |
| 缺点 | 迭代器耗尽后不可复用；可迭代对象与迭代器概念易混；自定义迭代器需手动维护状态。 |

### 12. yield from

| 维度 | 内容 |
|------|------|
| 是什么 | 把子生成器委托给当前生成器的语法，建立双向通道。 |
| 能做什么 | 透传 `send()` 的值与 `throw()` 的异常；获取子生成器返回值；递归组合生成器。 |
| 怎么用 | `yield from sub_gen`。 |
| 原理和工作流程 | 委托期间调用方的 send/throw 直接作用于子生成器，子生成器结束时其返回值成为 `yield from` 表达式的值，从而实现协程式委托。 |
| 缺点 | 语义比普通循环复杂；对不熟悉协程的人可读性差；调试嵌套委托链不直观。 |

### 13. 生成器表达式与内存

| 维度 | 内容 |
|------|------|
| 是什么 | 用圆括号推导式构造的惰性序列，按需产生元素。 |
| 能做什么 | 以 O(1) 额外内存处理超大文件/流；配合 `sum`/`any`/`all` 做聚合。 |
| 怎么用 | `sum(1 for line in f if "ERROR" in line)`。 |
| 原理和工作流程 | 生成器表达式不预构建结果，每次迭代才计算下一个值，故内存与数据规模无关；列表推导式则一次性构造全部元素。 |
| 缺点 | 只能消费一次；无 `len()`/索引；调试时无法直接查看全部内容。 |

### 14. GIL 与并发选型

| 维度 | 内容 |
|------|------|
| 是什么 | CPython 保证同一时刻仅一个线程执行字节码的全局锁，及由此决定的并发方案选择。 |
| 能做什么 | 判断 CPU 密集/IO 密集该用多进程、多线程还是 asyncio；理解高并发 IO 场景的最优解。 |
| 怎么用 | CPU 密集 → `multiprocessing`；海量 IO → `asyncio` + `Semaphore`；IO 且依赖阻塞库 → `threading`。 |
| 原理和工作流程 | GIL 使 CPU 密集多线程串行化；IO 操作会释放 GIL 故多线程仍有效；多进程各有独立 GIL 可真并行；asyncio 单线程事件循环以协程切换替代线程切换，开销极低。 |
| 缺点 | GIL 释放时机影响公平性；多进程内存翻倍、启动慢；asyncio 需全链路异步，一处阻塞调用即卡死循环。 |

### 15. try/except/else/finally

| 维度 | 内容 |
|------|------|
| 是什么 | Python 异常处理的四段式结构及其执行顺序。 |
| 能做什么 | 捕获预期异常；用 else 放置"成功后逻辑"；用 finally 保证资源释放。 |
| 怎么用 | `try → except → else → finally`。 |
| 原理和工作流程 | try 正常结束走 else 再走 finally；try 抛异常被捕获则跳过 else 直接 finally；finally 无论是否异常都执行。 |
| 缺点 | finally 中 `return`/`break` 会覆盖返回值并吞掉异常；except 顺序写错会被宽泛类型抢先捕获；`except Exception` 掩盖编程错误。 |

### 16. 异常链 raise from

| 维度 | 内容 |
|------|------|
| 是什么 | 用 `raise X from e` 显式建立新异常与原始异常的因果链。 |
| 能做什么 | 对外统一异常类型同时保留根因；用 `from None` 切断上下文隐藏实现细节。 |
| 怎么用 | `raise ServiceError("...") from e`；`raise ... from None`。 |
| 原理和工作流程 | `from e` 设置新异常的 `__cause__`，Traceback 显示 "direct cause"（显式链）；except 块中隐式抛新异常时原异常记入 `__context__`（隐式链）。 |
| 缺点 | 不写 from 时链路易被忽略导致根因丢失；多层包装后 Traceback 冗长；`from None` 滥用会掩盖真实故障。 |

### 17. 上下文管理器

| 维度 | 内容 |
|------|------|
| 是什么 | 实现 `__enter__`/`__exit__` 协议、用于成对执行进入/退出逻辑的对象。 |
| 能做什么 | 自动释放文件/连接/锁；块内异常时执行清理；返回 True 可吞掉异常。 |
| 怎么用 | `with mgr as x:`；或 `@contextlib.contextmanager` 生成器写法。 |
| 原理和工作流程 | with 进入调用 `__enter__` 并绑定 as 变量，退出**必然**调用 `__exit__(exc_type, exc_val, exc_tb)`；无异常传 `(None, None, None)`，返回真值则异常不再外抛。 |
| 缺点 | `__exit__` 返回 True 会静默吞异常、掩盖故障；生成器写法必须用 try/finally 包住 yield，否则异常时清理被跳过。 |

### 18. 引用计数与弱引用

| 维度 | 内容 |
|------|------|
| 是什么 | CPython 以引用计数为主、标记-清除与分代回收为辅的内存回收机制，及打破循环引用的弱引用。 |
| 能做什么 | 理解对象何时释放；定位循环引用导致的内存泄漏；用 weakref 做缓存与观察者。 |
| 怎么用 | `weakref.ref(obj)`；`gc.collect()`；`WeakValueDictionary`。 |
| 原理和工作流程 | 计数归零即刻释放；循环引用使计数恒大于零，靠标记-清除与分代回收（默认阈值 700/10/10）周期性回收；弱引用不增加计数，对象销毁后返回 None。 |
| 缺点 | 循环引用需额外 GC 周期；`__del__` 在循环场景行为不确定；list/dict/str 等内置类型不支持弱引用。 |

### 4. __slots__ 的作用与限制

### 5. 元类与类创建流程

| 维度 | 内容 |
|------|------|
| 是什么 | 类的类型（默认 type），在类创建时介入的钩子。 |
| 能做什么 | 字段收集与表名注册（轻量 ORM）；自动注册子类；注入属性/方法；编码规范校验。 |
| 怎么用 | `class Foo(metaclass=Meta)`；`type(name, bases, namespace)`。 |
| 原理和工作流程 | 类体执行收集 namespace → 确定元类 → 调用 `metaclass(name, bases, namespace)` 返回类对象 → 绑定类名；元类在类定义时生效并沿继承链自动作用于子类。 |
| 缺点 | 侵入性强、错误难调试、与多继承/__slots__ 组合复杂；优先用 `__init_subclass__` 或类装饰器。 |

### 6. 迭代器与生成器

| 维度 | 内容 |
|------|------|
| 是什么 | 迭代器协议（`__iter__`+`__next__`）、含 yield 的生成器函数与生成器表达式。 |
| 能做什么 | 惰性按需生成元素省内存；处理大文件与无限序列；用 send/throw 做双向协程。 |
| 怎么用 | `def gen(): yield x`；`next(g)`/`g.send(v)`；`(expr for x in it)`。 |
| 原理和工作流程 | 生成器函数调用时不执行函数体，返回生成器对象；每次 next 执行到下一个 yield 暂停并保留局部变量与指令指针；yield 表达式值由 send 传入；结束抛 StopIteration(value)。 |
| 缺点 | 只能消费一次、耗尽后无输出；无 len 与索引；调试状态机复杂；生成器表达式仅支持单表达式。 |

### 7. GIL 与并发选型

| 维度 | 内容 |
|------|------|
| 是什么 | CPython 的全局解释器锁，及由此决定的三种并发方案取舍。 |
| 能做什么 | 按 CPU/IO 特征选型；理解多线程为何对 CPU 密集无效；掌握线程安全要点。 |
| 怎么用 | CPU 密集用 multiprocessing；海量 IO 用 asyncio；IO 且阻塞库用 threading。 |
| 原理和工作流程 | GIL 保证同一时刻仅一线程执行字节码；IO 时释放 GIL 故多线程仍有效；多进程各有独立 GIL 可真并行；asyncio 单线程事件循环以协程切换替代线程切换。 |
| 缺点 | GIL 释放时机影响公平性；多进程内存翻倍、序列化开销大；asyncio 需全链路异步；复合操作（如 `+=`）仍需加锁。 |

### 8. 异常处理与异常链

| 维度 | 内容 |
|------|------|
| 是什么 | try/except/else/finally 执行顺序、显式与隐式异常链、自定义异常体系。 |
| 能做什么 | 精确捕获预期异常；用 else 隔离成功逻辑；用异常链保留根因；用层次化自定义异常统一对外类型。 |
| 怎么用 | `raise ValidationError(...) from e`；`raise ... from None`；继承 Exception 定义业务异常。 |
| 原理和工作流程 | try 正常结束走 else 再走 finally，异常被捕获则跳过 else；from e 设置 `__cause__`（显式链），except 中隐式抛新异常写入 `__context__`（隐式链）。 |
| 缺点 | finally 中 return 覆盖返回值并吞异常；宽泛 except 掩盖编程错误；只打日志不重抛造成异常吞没。 |

### 9. 内存管理与垃圾回收

| 维度 | 内容 |
|------|------|
| 是什么 | 以引用计数为主、标记-清除与分代回收为辅的内存管理机制，及弱引用。 |
| 能做什么 | 理解对象释放时机；定位循环引用泄漏；用 gc 调优与 tracemalloc 排查；用 weakref 打破环。 |
| 怎么用 | `gc.collect()`；`weakref.ref(obj)`；`WeakValueDictionary`。 |
| 原理和工作流程 | 计数归零即释放；循环引用使计数恒正，由标记-清除与分代回收（0/1/2 三代，阈值 700/10/10）周期性回收；弱引用不计入计数，对象销毁后访问返回 None。 |
| 缺点 | 循环引用需额外 GC 周期与开销；`__del__` 在循环场景行为不确定；内置类型不支持弱引用；GC 停顿在大内存场景可见。 |

### 10. 上下文管理器与 contextlib

| 维度 | 内容 |
|------|------|
| 是什么 | 实现 `__enter__`/`__exit__` 协议的对象，用于成对管理资源。 |
| 能做什么 | 自动释放文件/连接/锁；异常时保证清理；suppress 忽略指定异常；ExitStack 管理不定数量资源。 |
| 怎么用 | `with mgr as x:`；类实现两方法；`@contextlib.contextmanager` 生成器写法。 |
| 原理和工作流程 | 进入调 `__enter__` 绑定 as 变量，退出必然调 `__exit__(exc_type, exc_val, exc_tb)`；无异常传三元组全 None，返回真值则异常被吞；contextmanager 把 yield 前后代码映射为 enter/exit。 |
| 缺点 | `__exit__` 返回 True 静默吞异常掩盖故障；生成器写法必须 try/finally 包 yield；嵌套 with 层级深时可读性下降。 |

### 11. 装饰器 vs Java 注解、鸭子类型、生成器 vs Stream

| 维度 | 内容 |
|------|------|
| 是什么 | 三组跨语言对照：装饰器 vs 注解、鸭子类型 vs 接口、生成器 vs Java Stream。 |
| 能做什么 | 用 Java 经验快速定位 Python 对应概念；理解行为增强与元数据标记的边界差异。 |
| 怎么用 | `@lru_cache` 对标 Guava Cache；`typing.Protocol` 做静态鸭子类型；生成器对标惰性 Stream 管道。 |
| 原理和工作流程 | 装饰器在定义时直接替换函数对象完成包装，注解只是元数据需反射/APT 读取；鸭子类型运行时按方法存在性判定，接口编译期按声明检查；生成器是语言级协程原语支持 send/throw，Stream 是库级管道且支持 parallelStream。 |
| 缺点 | 装饰器与注解同名"@"易误类比；鸭子类型把类型错误推迟到运行时；生成器无内建并行能力。 |

### 1. 大文件流式处理管道

| 维度 | 内容 |
|------|------|
| 是什么 | 用生成器链 + 上下文管理器处理 20GB 日志并单次遍历聚合统计的方案。 |
| 能做什么 | 内存恒定处理超大文件；Top-K 统计；状态码占比与按小时错误分布；坏行容错。 |
| 怎么用 | `open_log` 上下文管理器 → `read_lines` 生成器 → `parse_records` 生成器 → `analyze` 单次遍历聚合。 |
| 原理和工作流程 | 逐行生成器只维持 O(1) 内存；生成器链由 for 驱动形成天然背压；Counter/defaultdict 累积聚合状态；heapq.nlargest 避免全量排序；with 保证文件关闭。 |

### 2. 轻量 ORM 与重试框架

| 维度 | 内容 |
|------|------|
| 是什么 | 用元类收集字段/注册表、描述符做校验、带参装饰器做重试、`__getattr__` 做链式查询的轻量 ORM。 |
| 能做什么 | 类定义时自动注册表名与字段；字段类型校验与默认值；`filter_x(v)` 链式查询；失败自动重试并保留根因。 |
| 怎么用 | `class User(Model)` 声明 Field；`User.objects().filter_name("Alice").all()`；`@retry(times=3)` 装饰查询方法。 |
| 原理和工作流程 | 元类 `__new__` 在类创建时遍历 namespace 收集 Field 并写入 REGISTRY；描述符 `__set_name__` 自动获名、`__set__` 校验类型；装饰器三层嵌套 + wraps；`__getattr__` 动态生成 filter 方法返回自身实现链式。 |
| 缺点 | 元类侵入性强、调试困难；`__getattr__` 拼写错误不会立即报错；`@classmethod` 与装饰器叠加顺序易写错；仅为教学级实现，无 SQL 生成与连接池。 |

### 3. 异步并发限流抓取器

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 asyncio 的 1000 URL 抓取器：Semaphore 限流、超时、异步重试、结果统计。 |
| 能做什么 | 并发度上限控制；单请求超时；失败自动重试；成功/失败数与错误类型统计；总耗时度量。 |
| 怎么用 | `Fetcher(concurrency=20, timeout=5.0)`；`@async_retry(times=2)`；`asyncio.gather(..., return_exceptions=True)`。 |
| 原理和工作流程 | Semaphore 超出并发度即排队；asyncio.timeout 限制单请求；异步装饰器 wrapper 为 async 并 await 原函数；gather 汇总且异常不中断；dataclass 承载统计、Counter 汇总错误类型。 |
| 缺点 | 需全链路异步，一处阻塞调用即卡死事件循环；装饰器写成同步函数会返回协程对象而非结果；缺少连接池/重试抖动时对目标站点压力大。 |
