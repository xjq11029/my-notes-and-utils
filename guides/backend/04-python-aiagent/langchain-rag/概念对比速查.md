# LangChain与RAG - 概念对比速查

---

### LangChain vs LlamaIndex

| 对比维度 | LangChain | LlamaIndex |
|---------|-----------|------------|
| 核心定位 | 通用LLM应用开发框架，覆盖Chain、Agent、Tool、Memory全链路 | 专注于数据索引与检索的LLM框架，以RAG为核心 |
| 适用场景 | 复杂Agent、多步推理、工具调用、多模态应用、对话系统 | 文档问答、知识库搜索、数据摘要、结构化数据查询 |
| 性能特点 | 组件丰富但抽象层多，学习曲线陡峭，适合需要灵活编排的场景 | 索引结构优化好（支持多种索引类型），RAG场景上手快 |
| 生态集成 | 支持多种LLM、向量数据库、工具；LangSmith追踪；LangGraph状态图 | 内置多种数据连接器（PDF、SQL、API）；支持LangChain集成 |
| 选择建议 | 需要构建复杂Agent或多工具编排的应用 | 主要做文档问答或知识库检索，追求快速搭建RAG |

### RAG vs 微调

| 对比维度 | RAG（检索增强生成） | 微调（Fine-tuning） |
|---------|-------------------|---------------------|
| 核心定位 | 不修改模型参数，通过外部知识库检索增强生成 | 在预训练模型基础上用领域数据修改模型参数 |
| 适用场景 | 知识频繁更新、需要可溯源、多领域知识问答 | 学习特定风格/格式、注入领域知识、纠正模型行为 |
| 性能特点 | 知识更新即时（改库即可），可解释性强（可溯源），但检索延迟额外开销 | 推理时无额外延迟，但知识更新需重新训练 |
| 数据需求 | 需要构建和维护知识库文档，文档质量决定效果 | 需要高质量标注数据，数据量通常需数千条以上 |
| 选择建议 | 知识库内容频繁变化、需要引用来源、快速上线 | 需要改变模型行为风格、领域知识固定、追求推理速度 |

### Chroma vs Pinecone vs Milvus

| 对比维度 | Chroma | Pinecone | Milvus |
|---------|--------|----------|--------|
| 核心定位 | 轻量级开源向量数据库，适合原型开发和本地部署 | 全托管云原生向量数据库，零运维 | 高性能开源向量数据库，适合大规模生产环境 |
| 适用场景 | 原型验证、小规模项目、本地开发、嵌入应用 | 中小规模生产、快速上线、不想管理基础设施 | 大规模生产（亿级向量）、高性能检索、需自建或私有部署 |
| 性能特点 | 本地部署延迟低，但扩展性有限，不支持分布式 | 自动扩展，高可用，但成本随规模增长 | 支持多种索引（IVF/HNSW/DiskANN），GPU加速，分布式架构 |
| 部署方式 | pip安装，嵌入式运行，Python/JS双SDK | SaaS托管，无需运维 | Docker/K8s自建，支持云原生部署 |
| 选择建议 | 开发阶段快速验证RAG方案 | 快速上线无需运维，中小规模生产 | 大规模生产环境，需要高性能和私有化部署 |

### 向量检索 vs 关键词检索 vs 混合检索

| 对比维度 | 向量检索（语义） | 关键词检索（BM25） | 混合检索（Hybrid） |
|---------|----------------|------------------|------------------|
| 核心定位 | 把文本编码成向量，按语义相似度召回 | 基于词频与逆文档频率做词项匹配召回 | 两路召回结果融合，兼顾语义与字面匹配 |
| 匹配依据 | 语义相近（同义、近义、"说法不同但意思一样"） | 字面词项匹配（专有名词、型号、编号、错误码） | 两者结合，互补短板 |
| 优势 | 能召回同义表达、跨语言、口语化提问 | 术语、编号、代码类查询命中精准，可解释性强 | 召回率最高，兼顾"说得不一样"和"必须命中术语" |
| 劣势 | 对精确术语、罕见词、数字编号不敏感 | 无法理解同义表达，词不匹配就完全召回不到 | 实现更复杂，需要调融合权重 |
| 实现组件 | Embedding 模型 + 向量数据库（ANN 索引） | BM25（Lucene / ES 内置） | EnsembleRetriever 加权融合，或两路召回后合并去重 |
| 常见误区 | 只用向量检索，型号/编号类查询召回失败 | 只用关键词检索，口语化提问召回为空 | 融合权重不合理，反而引入噪声 |
| 选择建议 | 语义类问答为主时用向量检索 | 术语、编号密集的知识库用 BM25 | 生产环境推荐混合检索，再叠加 Cross-Encoder 重排序 |

### Chunk 切分策略对比

| 切分器 | 切分依据 | 优点 | 缺点 | 适用文档 |
|-------|---------|------|------|---------|
| CharacterTextSplitter | 固定字符数 + 指定分隔符 | 实现最简单、结果可预测 | 容易在句子中间切断，语义完整性差 | 结构简单的纯文本、日志 |
| RecursiveCharacterTextSplitter | 按段落→换行→空格逐级递归尝试分隔符 | 尽量落在段落/句子边界，通用性最好，官方推荐 | 仍以长度为准，不理解语义 | 绝大多数通用文档（默认首选） |
| TokenTextSplitter | 按 Token 数量切分 | 与模型上下文窗口直接对齐，token 预算可控 | 依赖具体模型的 tokenizer，跨模型不通用 | 对 token 成本敏感、需严格控制上下文长度 |
| MarkdownHeaderTextSplitter | 按 Markdown 标题层级切分 | 保留章节结构，块内主题单一 | 只适用于有标题结构的文档 | Markdown、技术文档、规范手册 |
| 语义切分（Semantic Chunking） | 按相邻句子 Embedding 相似度骤降处切分 | 块内语义完整，跨块割裂最少，检索精度高 | 需要额外 Embedding 计算，成本高、速度慢 | 长文、论文、高精度知识库 |

> 参数配套建议：`chunk_size` 按文档类型选（技术文档 512-1024、通用场景 256-512），`chunk_overlap` 取 chunk_size 的 10%-20%，避免边界语义被硬切断。

### Chain vs Agent vs Graph

| 对比维度 | Chain（链） | Agent（智能体） | Graph（LangGraph 状态图） |
|---------|-----------|----------------|------------------------|
| 核心定位 | 预定义的固定调用流水线 | 由 LLM 自主决定调用哪个工具、走几步 | 用状态图编排节点与条件边，流程可控可恢复 |
| 流程确定性 | 完全确定，步骤写死在代码里 | 不确定，执行路径由 LLM 运行时决策 | 结构确定，分支条件由代码与 LLM 共同决定 |
| 典型组件 | LCEL、SequentialChain、RouterChain | ReAct、AgentExecutor、Tool | StateGraph、conditional edge、Checkpointer |
| 循环能力 | 无，单向执行 | 有（思考-行动-观察循环） | 有，且循环次数与条件可显式控制 |
| 状态与中断恢复 | 无状态管理 | 状态在黑盒中，调试困难 | 支持 Checkpointer 持久化，支持人机协同与中断恢复 |
| 调试与可观测 | 环节清晰，但 LCEL 出错时错误信息不直观 | 中间步骤黑盒，依赖 verbose / LangSmith | 每步状态可见，可逐节点观测 |
| 成本与延迟 | 最低（调用次数固定） | 最高（每轮都调 LLM，无上限会死循环） | 中高（可显式限制步数） |
| 适用场景 | 简单线性流程、固定顺序调用、按类型路由 | 需要工具调用与动态决策的任务 | 复杂多步、多智能体协作、人机协同、需中断恢复 |
| 常见误区 | 用 Chain 硬编带循环或中断的复杂流程 | 不设 `max_iterations`，陷入死循环烧 token | 简单场景也上 Graph，过度设计 |
| 选择建议 | 简单线性/固定顺序用 Chain；需要自主决策与工具调用用 Agent；复杂分支、循环、多智能体、需持久化用 LangGraph | | |

### 相似度检索 vs MMR vs 重排序

| 对比维度 | 相似度检索（Similarity） | MMR（最大边际相关性） | 重排序（Cross-Encoder Rerank） |
|---------|-----------------------|---------------------|----------------------------|
| 核心定位 | 直接取与问题向量最相近的 top_k 个 chunk | 在"相关"与"多样"之间取平衡，抑制结果同质化 | 用交叉编码器对召回结果精细打分并重排 |
| 计算方式 | 查询向量与文档向量算余弦相似度 | 相似度减去与已选结果的相似度，贪心选择 | 查询与文档拼接后送入 Cross-Encoder 打分 |
| 解决的问题 | 快速拿到语义最相关的结果 | 返回的多个 chunk 内容高度重复、信息冗余 | Bi-Encoder 粗排精度不足，细粒度相关性判断不准 |
| 精度 | 中 | 中（多样性提升，相关性略降） | 高（精排效果最好） |
| 性能开销 | 最低 | 低（多一次相似度计算） | 高（每对"查询-文档"都要过一次模型） |
| 关键参数 | `top_k` | `top_k`、`lambda_mult`（偏 1 重相关性，偏 0 重多样性） | `top_n`（精排后保留的条数） |
| 在 RAG 中的位置 | 召回阶段 | 召回阶段（去冗余） | 精排阶段（在召回之后） |
| 适用场景 | 结果本身不重复的简单问答 | 长文档切块后内容重叠多、需要覆盖多个方面 | 对答案质量要求高的生产环境 |
| 选择建议 | 作为基线方案；chunk 冗余明显时加 MMR；追求最终质量时在召回后接 Cross-Encoder 重排序 | | |
