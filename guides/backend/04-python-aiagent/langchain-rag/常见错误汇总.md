# LangChain与RAG - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| Agent陷入无限循环反复调用同一工具 | ReAct模式中thought-action-observation的循环终止条件不明确，或工具返回格式不兼容 | 设置max_iterations上限；在工具描述中明确定义返回格式；使用LangGraph的conditional edge控制流程 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| Memory组件导致对话上下文无限增长超出token限制 | ConversationBufferMemory无限制追加历史消息，长对话后token数爆炸 | 根据场景选择BufferWindowMemory（限制最近N轮）或SummaryMemory（摘要压缩）；设置max_token_limit | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 文档分块大小不当导致检索质量差 | chunk_size过小丢失上下文语义，过大导致检索精度下降 | 根据文档类型选择chunk_size（代码200-500，文档500-1000，法律1000-2000），配合chunk_overlap=10%-20% | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 向量检索返回不相关文档导致LLM生成幻觉 | 检索策略单一（仅用相似度），embedding模型未适配领域数据 | 组合多种检索策略（关键词+语义混合）；使用领域数据微调embedding模型；引入reranker二次排序 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| RAG系统回答与检索内容不一致（忠实度低） | LLM忽略检索到的上下文，或检索结果与问题不匹配 | 用RAGAS评估Faithfulness指标；Prompt中强调"仅根据提供的上下文回答"；引入citation机制 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 向量数据库选型不当导致性能瓶颈 | 对数据规模、查询延迟、部署环境预估不足，选了不适合的向量数据库 | 原型验证用Chroma（轻量本地）；生产环境根据规模选Pinecone（托管）或Milvus（自建高性能）；评估QPS和召回率 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 直接用LangChain Expression Language（LCEL）而忽略调试 | LCEL链式调用出错时错误信息不直观，难以定位问题环节 | 使用`with_config`添加回调追踪；每个环节单独测试；用LangSmith追踪链执行 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| Tool调用时参数类型不匹配导致Agent执行失败 | Tool的args_schema定义与LLM生成的参数格式不一致，或缺少必填参数 | 使用Pydantic模型严格定义Tool输入schema；在Tool description中明确参数格式和示例 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 面试中混淆RAG与微调、Agent与Chain的概念 | 对核心概念边界理解不清，将不同技术范式混为一谈 | RAG是检索增强生成，微调是修改模型参数；Agent自主决策，Chain固定流程 | [面试题集导览](./04-Python与AI智能体笔面试题集-导览.md) |
| RAG检索延迟过高影响用户体验 | 未使用索引、向量维度过高、无缓存机制 | 建立向量索引（IVF/HNSW）；降低embedding维度；对高频查询结果做缓存 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 盲目认为 chunk_size 越大越好，检索和生成质量反而下降 | chunk 过大时包含大量与问题无关的内容，向量表示被噪声稀释，同时增加计算量和 token 消耗 | 按文档类型和任务选值（技术文档 512-1024，通用场景 256-512），通过小范围实验确定最优值，并非越大越好 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| chunk_overlap 设为 0，跨块的句子被硬切断，语义割裂 | 未设置重叠窗口，正好落在边界上的完整语义被拆到两个 chunk 里，两边都检索不全 | 设置 `chunk_overlap` 为 chunk_size 的 10%-20%，让边界内容在两个块中各保留一部分 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 直接用大模型的 token embedding 做向量检索，效果很差 | LLM 的 token embedding 是为生成任务优化的，向量空间分布不符合语义检索需求，相似度区分度差 | 使用专用 Embedding 模型（闭源 `text-embedding-3` 系列，开源 BGE-m3 等），不要复用 LLM 输出层 embedding | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 更换 Embedding 模型或调整 `dimensions` 后检索报错或结果错乱 | 新模型的向量维度与向量库中已有向量不一致，`dimensions` 参数变更后同样如此 | 更换 Embedding 模型或调整输出维度后，必须把全部文档重新向量化并重建向量库 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 知识库很大时检索结果不精准，无法按条件缩小范围 | 只对文档内容做了向量化，标题、日期、章节、来源等元数据被丢弃，检索时无法过滤 | 加载文档时保留关键 metadata，检索时结合元数据过滤（如"只检索最近一年的文档""只检索某产品手册章节"） | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 知识库文档量上来后检索越来越慢，CPU 占满 | 向量库用了精确（暴力）搜索，需计算查询向量与全库所有向量的相似度，复杂度 O(N) | 使用支持 ANN 近似最近邻搜索的向量库（Chroma、FAISS、Milvus），靠索引把检索降到 O(logN) 量级 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 程序重启后向量知识库"消失"，需要重新灌数据 | Chroma 未指定 `persist_directory`，默认走内存模式，进程结束数据即丢失 | 初始化时显式指定 `persist_directory` 持久化路径，后续用同一路径加载已有集合 | [RAG实战导览](./03-RAG检索增强生成实战-导览.md) |
| 照抄旧教程代码报导入错误，`LLMChain` 被标记为已废弃 | LangChain 0.2 做了重大重构，许多 API 迁移到 `langchain_core`、`langchain_community` 等子包，网上教程多为旧版 | 查官方文档用新版 API：用 LCEL（`prompt \| llm \| output_parser`）替代 `LLMChain`，导入路径以当前版本文档为准 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 调用 `chain.invoke()` 时抛 `KeyError`，提示缺少某个变量 | Prompt 模板里的变量名与 `invoke()` 传入字典的 key 不一致（模板写 `{question}`，传入 `{"query": ...}`） | 确保模板变量名与传入 key 完全一致，变量名建议用常量统一管理，避免手写拼错 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 多轮对话中 Agent 不记得上一轮说了什么，每次都像新会话 | LangGraph 默认不持久化状态，未配置 Checkpointer 时每次调用都是独立的 | 编译时配置 `checkpointer=MemorySaver()`，并用 `thread_id` 区分不同会话，同一 thread_id 共享状态 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| Memory 类型选错：长对话 token 爆炸，或需要细节时关键信息丢失 | 未按对话长度和精度需求选 Memory：Buffer 保留全部细节但 token 线性增长，Summary 稳定 token 但丢细节 | 短对话用 Buffer；长对话要全局上下文用 Summary；只需相关历史用 VectorStoreRetrieverMemory；只需最近几轮用 BufferWindow | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| Agent 频繁选错工具，或调用时参数填错 | 工具的描述（docstring）写得含糊，LLM 无法判断该工具的适用时机与参数含义 | 工具描述写清"用途、何时用、参数格式与示例、返回格式"，参数用 Pydantic 严格定义 schema，避免多个工具职责重叠 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| LLM 输出格式不符合预期时 Agent 直接报错中断 | 未设置 `handle_parsing_errors`，解析失败即抛出异常，整条链路中断 | 设置 `handle_parsing_errors=True` 让解析失败可重试；结构化输出用 Pydantic schema 明确定义，并在 Prompt 中给出格式示例 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 长耗时任务执行期间用户界面长时间无反馈 | 未使用流式输出，等整条链跑完才一次性返回 | 用 `graph.stream(input, stream_mode="messages")` 透传 token 流做打字机效果，异步场景用 `astream_events` 推送工具开始/结束等细粒度事件 | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
| 用 Chain 硬编排带条件分支、需要中断恢复的复杂流程，越写越乱 | Chain 是"流水线"，只适合固定顺序；条件分支、循环、人机协同、中断恢复是 LangGraph 的能力 | 按场景选型：简单线性流程用 Chain；条件分支用 RouterChain；需要"思考-行动-观察"循环、多智能体协作或中断恢复时用 LangGraph | [LangChain核心导览](./02-LangChain与AI智能体核心-导览.md) |
