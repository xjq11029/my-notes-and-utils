# ClickHouse - 概念对比速查

---

### ClickHouse vs MySQL

| 对比维度 | ClickHouse | MySQL |
|---------|-----------|-------|
| 核心定位 | 面向列的 OLAP 分析型数据库 | 面向行的 OLTP 关系型数据库 |
| 存储方式 | 列式存储，同一列数据连续存放 | 行式存储，同一行数据连续存放 |
| 查询特点 | 大批量行少量列的聚合扫描 | 少量行全列的精确查询和更新 |
| 写入方式 | 批量写入，不适合频繁单行更新 | 支持高频单行写入和更新 |
| 事务支持 | 不支持事务 | 完整支持 ACID 事务 |
| 并发能力 | 中低并发（数十连接） | 高并发（数千连接） |
| 索引结构 | 稀疏索引（每 8192 行一个 Mark） | B+Tree 稠密索引（每行一个索引项） |
| 数据压缩 | 列式同类型高压缩比 5-10 倍 | 行式压缩比低 |
| 向量化执行 | 支持 SIMD 指令批量处理 | 不支持 |
| UPDATE/DELETE | 异步 Mutation，重写整个 Part，性能差 | 原地更新，性能好 |
| 适用场景 | 实时报表、日志分析、用户行为分析、广告统计 | 业务数据存储、事务操作、高并发 OLTP |
| 选择建议 | 分析聚合场景选 ClickHouse；业务主库选 MySQL；两者配合使用 | |

### MergeTree vs InnoDB

| 对比维度 | MergeTree（ClickHouse） | InnoDB（MySQL） |
|---------|------------------------|-----------------|
| 核心定位 | ClickHouse 最核心的列式存储表引擎 | MySQL 默认的行式存储引擎 |
| 存储方式 | 列式存储，按列分块存放 | 行式存储，按页（16KB）存放 |
| 索引结构 | 稀疏索引（每 8192 行一个 Mark），按排序键生成 | B+Tree 稠密索引，按主键生成 |
| 索引大小 | 约为数据量的千分之一 | 约为数据量的 10%-30% |
| 数据写入 | 每次批量写入产生不可变 Part，后台合并线程合并 | 写入 Buffer Pool，后台线程刷脏页 |
| 数据更新 | 不支持原地更新，UPDATE 是异步 Mutation 重写 Part | 支持原地更新，通过 Undo Log 保证一致性 |
| 分区机制 | 按 PARTITION BY 表达式拆分到物理目录，支持分区裁剪 | 支持分区表，但裁剪效果较弱 |
| 压缩能力 | 列式同类型压缩比 5-10 倍（LZ4/ZSTD） | 支持页级压缩，但压缩比不如列式 |
| TTL 支持 | 原生支持 TTL，自动过期删除数据 | 不支持原生 TTL，需定时任务清理 |
| 衍生引擎 | ReplacingMergeTree（去重）、SummingMergeTree（汇总）、AggregatingMergeTree（聚合）等 | 无衍生引擎，通过 SQL 实现类似功能 |
| 适用场景 | 海量数据聚合分析、时序数据存储 | 事务处理、高并发 OLTP |
| 选择建议 | 分析场景选 MergeTree；事务场景选 InnoDB | |

### ClickHouse vs Elasticsearch

| 对比维度 | ClickHouse | Elasticsearch |
|---------|-----------|---------------|
| 核心定位 | 列式 OLAP 分析型数据库，面向海量数据聚合统计 | 分布式全文检索与分析引擎，面向搜索与日志检索 |
| 查询语言 | SQL | DSL（JSON） |
| 存储结构 | 列式存储 + 稀疏索引 + 向量化执行 | 倒排索引 + DocValues，按 Segment 组织 |
| 写入性能 | 极高（批量写入，写入即压缩落盘） | 较高（需建索引与刷新，写入成本更高） |
| 聚合性能 | 极快，亿级数据秒级聚合 | 较慢，跨分片聚合与深度分页开销大 |
| 全文搜索 | 不支持，只能做等值/范围/前缀匹配 | 核心能力，支持分词、模糊匹配、相关性评分 |
| 更新能力 | 异步 Mutation，重写 Part，更新代价高 | 支持按文档更新，但更新即重建该文档的索引 |
| 数据一致性 | 不保证强一致，副本为最终一致 | AP 系统，副本异步同步，最终一致 |
| 适用场景 | 实时报表、BI 分析、用户行为分析、广告统计 | 商品搜索、日志检索、全文搜索、模糊匹配 |
| 选择建议 | 统计聚合选 ClickHouse，搜索检索选 ES；两者常配合使用——ES 负责搜索，ClickHouse 负责统计 | |

### MergeTree 家族引擎对比

| 对比维度 | MergeTree | ReplacingMergeTree | SummingMergeTree | AggregatingMergeTree |
|---------|-----------|-------------------|------------------|---------------------|
| 核心定位 | 最基础的表引擎，所有高级引擎都基于它 | 在 MergeTree 基础上，合并时删除重复数据 | 在 MergeTree 基础上，合并时对数值列求和 | 在 MergeTree 基础上，合并时按聚合函数聚合 |
| 合并时的行为 | 只把小 Part 合并成大 Part | 按排序键去重，保留版本列最大的那一行 | 相同排序键的行，数值列自动相加 | 相同排序键的行，按 `-State` 聚合函数中间态聚合 |
| 是否需要额外列 | 无 | 需要版本列（如 `ver UInt32`） | 需要可求和的数值列 | 需要聚合函数状态列（`sumState`/`uniqState`） |
| 去重/汇总时机 | 不去重、不汇总 | 后台合并时，时机不确定 | 后台合并时，时机不确定 | 后台合并时，时机不确定 |
| 典型用途 | 通用明细表、宽表存储 | 数据去重、幂等写入、逻辑更新 | 预聚合统计（如按天按品类汇总金额） | 物化视图的底层存储，支持精确去重/中位数等 |
| 使用注意 | 通用首选 | 查询时可能仍有重复，需配合 FINAL 或最终一致语义 | 只对数值列求和，非数值列取任意值 | 查询时需用 `Merge` 系列函数读取状态列 |
| 选择建议 | 明细数据、宽表 | 需要按主键保留最新一条 | 只需求和类汇总 | 需要 uniq/quantile 等复杂聚合的物化视图 |

> 补充：`ReplicatedMergeTree` 在以上引擎基础上增加数据副本（生产环境高可用必选，依赖 ZooKeeper/Keeper）；`Distributed` 是分布式表引擎，本身不存数据，只把查询/写入扇出到各分片的本地表；`Buffer` 与 `Kafka` 是内存缓冲/消息队列引擎，用于把高频小批量写入攒成大批量再落盘。

### 主键 vs 排序键 vs 分区键

| 对比维度 | 主键（PRIMARY KEY） | 排序键（ORDER BY） | 分区键（PARTITION BY） |
|---------|-------------------|-------------------|----------------------|
| 作用对象 | 稀疏索引的生成依据 | 数据在 Part 内的物理排列顺序 | 数据落到的物理目录（分区） |
| 是否必须指定 | 可不指定，默认等于排序键 | MergeTree 必填 | 可不指定，默认不分区 |
| 两者关系 | 主键必须是排序键的前缀 | 排序键即为主键（可不唯一），不需要再显式指定 | 与主键/排序键相互独立 |
| 设计依据 | 需要索引加速的过滤字段 | 查询中最常用的过滤与聚合字段，按此顺序排在最前 | 低基数的日期/类型字段，控制分区数量 |
| 对查询的影响 | 决定稀疏索引能否快速定位数据区间 | 决定数据物理局部性，直接影响扫描效率 | 决定分区裁剪能否生效，减少扫描数据量 |
| 数量约束 | 无硬性限制 | 无硬性限制 | 分区总数建议控制在 1000 以内 |
| 常见误区 | 以为必须显式声明 PRIMARY KEY | 以为 ORDER BY 只是"排序"，与索引无关 | 用高基数字段（如 user_id）做分区键 |
| 选择建议 | 通常省略，直接由排序键承担 | 优先按"最常过滤 + 基数递减"设计 | 用日期/类型字段，按月或按天分区 |
