## 一、核心概念

### 1.1 ClickHouse 是什么

| 维度 | 内容 |
|------|------|
| 是什么 | Yandex 开源的面向列的 **OLAP** 数据库管理系统，为海量数据实时分析设计，秒级完成数十亿行聚合查询。 |
| 能做什么 | 列式存储减少 IO；数据压缩降低存储成本；向量化执行加速计算；分布式表水平扩展；支持标准 SQL；高吞吐批量写入。 |
| 怎么用 | `SELECT AVG(amount) FROM order_events WHERE event_time >= '2026-01-01'` |
| 原理和工作流程 | 同一列数据连续存储，查询只读取所需列；CPU SIMD 指令批量处理列数据；按排序键建立稀疏索引定位数据区间；后台合并线程将小 Part 合并为大 Part；列式数据同类型相似度高，LZ4/ZSTD 压缩比 5-10 倍。 |
| 缺点 | 不支持事务，UPDATE/DELETE 为异步 Mutation 性能差；不擅长点查询和高并发；JOIN 性能弱；不适合 OLTP 场景。 |

### 1.2 OLTP vs OLAP

| 维度 | 内容 |
|------|------|
| 是什么 | 两类数据库工作负载分类，OLTP 面向高频小事务，OLAP 面向大批量聚合分析。 |
| 能做什么 | 区分行式与列式存储适用场景；指导数据库选型；明确并发与数据量级差异；对应不同典型操作。 |
| 怎么用 | 业务主库选 MySQL（OLTP），分析引擎选 ClickHouse（OLAP）。 |
| 原理和工作流程 | OLTP 行式存储逐行写入适合事务，少量行全列查询，高并发数千连接；OLAP 列式存储按列读取适合聚合，大量行少量列查询，中低并发数十连接；二者在存储方式、查询特点、并发能力上形成互补，MySQL 记流水账，ClickHouse 算总账。 |
| 缺点 | 两者无法兼得，单一数据库难以同时满足事务和分析需求，通常需双库配合增加架构复杂度。 |

### 1.3 适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | ClickHouse 擅长的实时分析业务领域集合。 |
| 能做什么 | 海量日志分析；时序数据分析；用户行为分析；实时报表；广告分析。 |
| 怎么用 | 将日志、指标、点击流写入 ClickHouse，用 SQL 聚合查询出报表。 |
| 原理和工作流程 | 这些场景共同特征是写入批量大、查询为聚合统计、延迟要求亚秒到分钟级，契合列式存储与向量化执行的优势；日志和时序数据按时间分区便于裁剪；行为分析需去重统计，uniq 函数高效支持。 |
| 缺点 | 场景均要求低频更新、大批量写入，若涉及高频点查或事务则不适用；实时性受写入批次间隔限制。 |

## 二、底层原理

### 2.1 列式存储原理

| 维度 | 内容 |
|------|------|
| 是什么 | 将同一列数据连续存放的存储方式，与行式存储逐行存放相对。 |
| 能做什么 | 只读需要的列减少 IO；同列同类型高压缩比；向量化批量执行。 |
| 怎么用 | `SELECT AVG(age) FROM users` 只读取 age 列。 |
| 原理和工作流程 | 磁盘按列分块存储，id 列、name 列各自连续；查询 AVG(age) 时仅加载 age 列数据块；列内数据类型一致，LZ4/ZSTD 压缩比 5-10 倍；列数据内存连续，CPU SIMD 指令一次处理一批而非逐行。 |
| 缺点 | 整行写入需拆分到多列文件，写入开销高于行式；查询全列时优势丧失；不适合频繁单行更新。 |

### 2.2 MergeTree 引擎家族

| 维度 | 内容 |
|------|------|
| 是什么 | ClickHouse 最核心的表引擎家族，所有高级引擎均基于它构建。 |
| 能做什么 | 基础 MergeTree 支持分区排序 TTL；ReplacingMergeTree 去重；SummingMergeTree 汇总；AggregatingMergeTree 聚合；CollapsingMergeTree 折叠增删；ReplicatedMergeTree 提供副本。 |
| 怎么用 | `ENGINE = MergeTree() PARTITION BY toYYYYMM(event_time) ORDER BY (product_id, event_time) TTL event_time + INTERVAL 90 DAY` |
| 原理和工作流程 | 每次写入产生不可变 Part，后台 Merge 线程按排序键合并小 Part 为大 Part；合并时各引擎施加特定逻辑（去重、汇总、聚合、折叠）；分区按物理目录拆分，排序键决定数据物理顺序并生成稀疏索引。 |
| 缺点 | 合并时机不确定，查询时可能看到未合并的重复或未汇总数据；ReplacingMergeTree 不能保证查询时已去重。 |

### 2.3 分区策略（PARTITION BY）

| 维度 | 内容 |
|------|------|
| 是什么 | 按指定规则将数据拆分到不同物理目录的机制。 |
| 能做什么 | 按时间或自定义键分区；查询时分区裁剪减少扫描量；支持快速删除整个分区。 |
| 怎么用 | `PARTITION BY toYYYYMM(event_time)` |
| 原理和工作流程 | 建表时指定分区表达式，数据写入按表达式值落入对应分区目录；查询带分区键过滤条件时，ClickHouse 通过分区裁剪只扫描匹配分区，跳过无关分区的 Part 文件；按月分区最常用，按天适合日数据量大的场景。 |
| 缺点 | 分区数过多（超 1000）影响元数据管理性能；分区键建表后不可修改需重建表；粒度过大失去裁剪效果，过小则 Part 数膨胀。 |

### 2.4 排序键和稀疏索引

| 维度 | 内容 |
|------|------|
| 是什么 | 排序键决定数据物理顺序并作为主键，稀疏索引按固定行数间隔生成标记的索引结构。 |
| 能做什么 | 按排序键顺序存储加速范围查询；稀疏索引极小占用快速定位区间；支持跳数索引补充过滤。 |
| 怎么用 | `ORDER BY (product_id, event_time) SETTINGS index_granularity = 8192` |
| 原理和工作流程 | 数据按 ORDER BY 字段排序写入磁盘；默认每 8192 行生成一个 Mark，记录该区间排序键 min/max 与物理偏移；查询时用条件与 Mark 区间比较定位候选区间后扫描；跳数索引（minmax、set、bloom_filter）在 Mark 内进一步过滤。 |
| 缺点 | 稀疏索引只能定位区间不能精确定位单行，点查询需扫描整个 granule；排序键选择不当导致查询无法利用索引；跳数索引对高基数列效果有限。 |

### 2.5 数据压缩

| 维度 | 内容 |
|------|------|
| 是什么 | 对列数据块采用 LZ4 或 ZSTD 算法压缩存储的机制。 |
| 能做什么 | 减少磁盘 IO；降低网络传输量；压缩比 5-10 倍节省存储。 |
| 怎么用 | `SETTINGS min_compress_block_size = 65536, max_compress_block_size = 1048576` |
| 原理和工作流程 | 列式存储使同列数据类型相同、值域有限，排序后相邻行相似度高；写入时按压缩块大小聚合数据，用 LZ4（默认快）或 ZSTD（慢但比高）压缩；查询时按需解压对应块；100GB 原始数据压缩后只需 10-20GB。 |
| 缺点 | 压缩和解压消耗 CPU；ZSTD 速度低于 LZ4；随机读取需解压整个压缩块。 |

### 2.6 物化视图（Materialized View）

| 维度 | 内容 |
|------|------|
| 是什么 | 本质是触发器，源表有新数据写入时自动将聚合结果增量写入目标表。 |
| 能做什么 | 增量更新只算新数据；查询直接读预计算结果加速；支持聚合与过滤。 |
| 怎么用 | `CREATE MATERIALIZED VIEW mv TO target AS SELECT toStartOfHour(event_time) AS hour, count() FROM src GROUP BY hour` |
| 原理和工作流程 | 源表写入触发物化视图的 SELECT 聚合逻辑，结果 INSERT 到目标表；只处理新写入的 Block 不重算历史数据；目标表通常用 SummingMergeTree 或 AggregatingMergeTree 存储聚合结果。 |
| 缺点 | 占用额外存储；源表删除数据后物化视图不同步删除；聚合逻辑固定后修改需重建视图；写入有额外计算开销。 |

## 三、实战应用

### 3.1 建表最佳实践

| 维度 | 内容 |
|------|------|
| 是什么 | 建表时分区、排序键、TTL、数据类型等的一套推荐配置规范。 |
| 能做什么 | 按月分区平衡数量与效率；排序键选高频过滤字段高基数在前；TTL 自动过期；LowCardinality 优化低基数列；避免 Nullable。 |
| 怎么用 | `ENGINE = MergeTree() PARTITION BY toYYYYMM(event_time) ORDER BY (event_type, event_time, user_id) TTL event_time + INTERVAL 180 DAY` |
| 原理和工作流程 | 分区裁剪减少扫描；排序键决定物理顺序与稀疏索引；TTL 后台任务自动删除过期 Part；LowCardinality 用字典编码低基数字符串减少内存；Wide 格式按列存文件便于读取单列。 |
| 缺点 | 规范需根据实际查询模式调整，盲目套用可能适得其反；排序键一旦确定修改成本高；TTL 误配会删除需保留的数据。 |

### 3.2 数据类型选择

| 维度 | 内容 |
|------|------|
| 是什么 | ClickHouse 提供的数值、字符串、日期、数组等类型及选型建议。 |
| 能做什么 | 按值域选最小整数类型；金额用 Decimal；低基数用 LowCardinality；定长用 FixedString；多值用 Array。 |
| 怎么用 | `amount Decimal(10,2), event_type LowCardinality(String), tags Array(String)` |
| 原理和工作流程 | 整数类型按 bit 宽度存储；Decimal 定点数避免浮点误差；LowCardinality 对基数小于 1 万的字符串建立字典编码，值存为字典索引；Array 以紧凑结构存储多值。 |
| 缺点 | Nullable 每行额外 Null 标记字节开销大；Enum 修改需 ALTER TABLE 不如 LowCardinality 灵活；类型选过大会浪费存储和内存。 |

### 3.3 Spring Boot 集成 ClickHouse

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 JDBC 驱动将 ClickHouse 接入 Spring Boot 应用的集成方案。 |
| 能做什么 | 配置独立数据源；用 JdbcTemplate 执行查询；批量写入数据。 |
| 怎么用 | `spring.datasource.clickhouse.url=jdbc:clickhouse://localhost:8123/default`<br>`jdbcTemplate.batchUpdate(sql, events, 1000, (ps,e)->{...})` |
| 原理和工作流程 | 引入 clickhouse-jdbc 依赖，DataSourceBuilder 创建指向 8123 端口的 HTTP 数据源；JdbcTemplate 通过 HTTP 协议发送 SQL；批量写入用 batchUpdate 按批次提交减少 Part 产生。 |
| 缺点 | JDBC 逐行写入会产生大量 Part 不推荐；HTTP 协议有额外开销；连接池需单独配置；与 MySQL 数据源混用时需 @Qualifier 区分。 |

### 3.4 数据写入方式

| 维度 | 内容 |
|------|------|
| 是什么 | ClickHouse 支持的四种数据写入途径及适用场景。 |
| 能做什么 | 批量 INSERT 推荐；Buffer 引擎缓冲高频小量写入；Kafka 引擎流式接入；JDBC 逐行仅测试。 |
| 怎么用 | `CREATE TABLE t_buffer AS t ENGINE = Buffer(default, t, 16, 10, 100, 10000, 1000000, 10000000, 100000000)` |
| 原理和工作流程 | 批量 INSERT 一次产生一个 Part 后台合并；Buffer 引擎在内存缓冲，满足时间或行数阈值后 flush 到目标表；Kafka 引擎直接消费 Topic 写入实现流式接入。 |
| 缺点 | JDBC 逐行写入 Part 爆炸；Buffer 引擎数据在内存宕机丢失；Kafka 引擎消费位点管理复杂；所有方式都应避免小批量频繁写入。 |

### 3.5 典型场景：用户点击流日志分析

| 维度 | 内容 |
|------|------|
| 是什么 | 以点击流日志表为例展示 ClickHouse 在用户行为分析中的完整应用。 |
| 能做什么 | 存储点击流事件；按小时统计 PV/UV；漏斗分析转化。 |
| 怎么用 | `SELECT toStartOfHour(event_time) AS hour, count() AS pv, uniq(user_id) AS uv FROM click_stream WHERE event_date = '2026-06-29' GROUP BY hour` |
| 原理和工作流程 | 按天分区、event_type 与日期排序键加速查询；count() 统计 PV，uniq() 用 HyperLogLog 近似去重算 UV；漏斗分析用 uniqIf 按事件类型分别去重，multiIf 控制阶段顺序。 |
| 缺点 | 漏斗分析为各阶段独立去重非严格有序漏斗；uniq() 有约 2% 误差；高基数 user_id 去重内存占用大。 |

## 四、常见面试题

### 1. ClickHouse 为什么查询这么快

| 维度 | 内容 |
|------|------|
| 是什么 | 列式存储、向量化执行、稀疏索引、数据压缩四项技术协同带来的查询加速机制。 |
| 能做什么 | 减少磁盘 IO；CPU 批量处理；索引极小快速定位；压缩降低传输量。 |
| 怎么用 | 建表用 MergeTree 配排序键，查询只 select 所需列。 |
| 原理和工作流程 | 列式存储只读所需列减少 IO；向量化执行用 SIMD 指令一次处理一批数据；稀疏索引每 8192 行一个 Mark 极小占用快速定位区间；列式数据同类型高压缩比 5-10 倍，减少磁盘读取与分布式网络传输。 |
| 缺点 | 加速仅对聚合扫描类查询有效；点查询和高频更新场景优势不复存在；向量化对复杂字符串操作收益有限。 |

### 2. MergeTree 引擎的合并机制与为什么需要合并

| 维度 | 内容 |
|------|------|
| 是什么 | 后台 Merge 线程将多个小 Part 合并为大 Part 的机制及必要性。 |
| 能做什么 | 减少 Part 数量提升查询性能；触发去重汇总等引擎逻辑；删除旧 Part 释放空间。 |
| 怎么用 | 无需手动干预，ClickHouse 自动调度合并。 |
| 原理和工作流程 | 每次批量写入产生一个不可变 Part；随 Part 增多查询需合并多 Part 结果性能下降；后台 Merge 线程按排序键将小 Part 合并为大 Part，合并时 ReplacingMergeTree 去重、SummingMergeTree 汇总等逻辑生效；合并完成后删除旧 Part。 |
| 缺点 | 合并时机不确定，查询时可能看到未合并数据；合并消耗 CPU 和 IO；频繁小批量写入导致 Part 爆炸合并跟不上；不建议手动干预。 |

### 3. 行式存储和列式存储的区别与什么时候选列式存储

| 维度 | 内容 |
|------|------|
| 是什么 | 两种存储方式在数据排列、IO、压缩、聚合性能上的差异及选型准则。 |
| 能做什么 | 区分存储方式；判断写入与查询性能；指导选型。 |
| 怎么用 | 报表分析选列式，订单查询选行式。 |
| 原理和工作流程 | 行式存储同一行连续存放写入一次完成，查少量列需读整行；列式存储同一列连续存放查少量列只读所需列，同列同类型压缩比高 5-10 倍，聚合时向量化执行快；选型看查询模式是大量行少量列聚合还是少量行全列更新。 |
| 缺点 | 列式写入需拆分多列开销大；行式聚合慢压缩低；两者难以兼得。 |

### 4. ClickHouse 和 Elasticsearch 的核心区别与分别适合什么场景

| 维度 | 内容 |
|------|------|
| 是什么 | 两款分析型数据库在核心能力、存储、索引、查询语言上的对比。 |
| 能做什么 | ClickHouse 擅长聚合分析；ES 擅长全文检索；两者配合分工。 |
| 怎么用 | ES 负责搜索，ClickHouse 负责统计。 |
| 原理和工作流程 | ClickHouse 列式存储加稀疏索引，SQL 查询，批量写入极高，聚合极快但不支持全文搜索；ES 底层列式但对外行式，倒排索引支持全文检索，DSL 查询，聚合较慢；二者互补，搜索走 ES，统计走 ClickHouse。 |
| 缺点 | ClickHouse 无全文搜索能力；ES 聚合性能与资源消耗不如 ClickHouse；双库维护成本高、数据同步复杂。 |

### 5. ClickHouse 的物化视图和普通数据库视图有什么区别

| 维度 | 内容 |
|------|------|
| 是什么 | 物化视图是存储预计算结果的物理视图，普通视图是实时计算的逻辑视图。 |
| 能做什么 | 物化视图增量更新加速查询；普通视图简化查询不存数据。 |
| 怎么用 | `CREATE MATERIALIZED VIEW mv TO target AS SELECT ...` |
| 原理和工作流程 | ClickHouse 物化视图本质是触发器，源表写入时自动增量聚合写入目标表，查询读预计算结果；普通视图仅保存 SELECT 定义，查询时实时展开计算不存储数据；物化视图只算新写入数据不重算历史。 |
| 缺点 | 物化视图占用额外存储；源表删除不同步；逻辑修改需重建；普通视图无加速效果。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | ClickHouse 生产实践中常见错误、现象、原因与解决方案的汇总。 |
| 能做什么 | 避免频繁小批量写入；避免 UPDATE/DELETE；不用作业务主库；用 PREWHERE 优化；避免 SELECT *；控制分区数；避免大表 JOIN；用 uniq 替代 COUNT(DISTINCT)。 |
| 怎么用 | 批量写入每 1000-10000 条一批；用 ReplacingMergeTree 加版本号逻辑更新；`SELECT uniq(user_id) FROM t` |
| 原理和工作流程 | 小批量写入产生过多 Part 导致合并压力大；UPDATE/DELETE 是异步 Mutation 重写整个 Part；列式存储 SELECT * 丧失裁剪优势；WHERE 先读所有列再过滤，PREWHERE 先过滤再读其他列；JOIN 性能弱需写入时做宽表；COUNT(DISTINCT) 精确去重开销大，uniq 用 HyperLogLog 近似去重。 |
| 缺点 | 避坑措施增加架构复杂度；宽表导致数据冗余；近似去重有 2% 误差；Buffer 引擎有丢数据风险。 |
