# ClickHouse - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 频繁小批量写入导致 Part 数量爆炸、查询性能下降、CPU 和 IO 被合并线程占满 | MergeTree 每次写入产生新的 Part，后台合并有开销 | 批量写入（每 1000-10000 条或每 5-10 秒一批）；使用 Buffer 引擎或 Kafka 引擎缓冲写入 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 频繁 UPDATE/DELETE 导致磁盘 IO 飙升、Part 数量激增 | ClickHouse 的 UPDATE/DELETE 是异步 Mutation，会重写整个 Part | 避免需要 UPDATE/DELETE 的场景；使用 ReplacingMergeTree + 版本号实现逻辑更新；通过数据覆盖替代 UPDATE | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 用 ClickHouse 替代 MySQL 做业务主库导致事务缺失、点查询慢 | ClickHouse 不支持事务，不适合 OLTP 场景 | MySQL 做业务主库（OLTP），ClickHouse 做分析引擎（OLAP） | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 未使用 PREWHERE 优化导致全列读取后过滤、IO 浪费 | WHERE 先读取所有列再过滤 | 优先使用 PREWHERE（列裁剪，先过滤再读取其他列）；MergeTree 引擎会自动优化部分 WHERE 到 PREWHERE | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| SELECT * 查询导致列式存储优势丧失、IO 浪费 | 列式存储的优势在于只读需要的列 | 只查询需要的列 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 分区粒度过大或过小导致分区数过多（超过 1000）影响元数据管理 | 未合理规划分区粒度 | 分区数控制在 1000 以内，按月分区为常用粒度 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| JOIN 大表导致查询超时、性能差 | ClickHouse JOIN 性能不如分布式计算引擎 | 将 JOIN 逻辑放到数据写入时做宽表 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 使用 COUNT(DISTINCT) 导致性能差 | COUNT(DISTINCT) 精确去重开销大 | 使用 uniq() 近似去重（HyperLogLog 算法） | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 不监控 Part 数量导致查询性能下降 | Part 数量过多未及时发现 | 定期查询 system.parts 监控 Part 数量 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 把 `uniq()` 的近似去重结果当精确值使用 | `uniq()` 基于 HyperLogLog 近似算法，默认误差率约 2%，结果与真实值存在偏差 | 对精度敏感的场景改用 `uniqExact()`（精确但慢）或 `uniqCombined()`；报表中标注为近似值 | [ClickHouse笔面试题集导览](./02-ClickHouse笔面试题集-导览.md) |
| 排序键设计不合理导致查询无法裁剪数据 | 误以为 ORDER BY 只是"排序"，实际上排序键即主键（可不唯一），决定数据物理顺序与稀疏索引 | 把查询中最常用的过滤/聚合字段放在排序键最前面；基数过低的字段不宜做排序键首位 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 分区键选错导致分区数爆炸（超过 1000） | 用高基数字段（如 user_id）做分区键，元数据管理开销剧增 | 用低基数的日期/类型字段分区，分区数控制在 1000 以内，按月分区是常用粒度 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 滥用 `Nullable` 字段带来额外开销 | 每个 Nullable 字段在每行都有一个额外的 Null 标记字节，写入和查询都要额外处理 | 用默认值（空字符串、0）替代 Nullable；只有确实需要区分"空值"与"未填"时才使用 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 低基数字符串字段未用 `LowCardinality` | 状态、设备、类型等枚举值直接存 String，内存和存储占用偏高 | 低基数字符串字段使用 `LowCardinality(String)`；比 `Enum` 更灵活，改枚举值无需 ALTER TABLE | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 建表未配置 `TTL` 导致数据无限增长、磁盘被打满 | 建表时漏写 TTL，历史数据一直堆积 | 按数据保留周期设置 `TTL event_time + INTERVAL 90 DAY`，让过期数据自动清理 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 误以为物化视图会同步源表的删除操作 | 物化视图本质是触发器，只对源表新写入的数据增量计算，源表删数据不会同步删除目标表 | 给物化视图目标表单独配置 TTL；删除历史数据时同步清理目标表 | [ClickHouse笔面试题集导览](./02-ClickHouse笔面试题集-导览.md) |
| 物化视图建好后历史数据没有进预聚合表 | 物化视图只对创建之后新写入的数据生效，不会回溯已有历史数据 | 建好 MV 后手工执行 `INSERT INTO 目标表 SELECT ...` 回填历史数据 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 生产环境使用单副本 `MergeTree`，节点故障即丢数据 | 单副本表没有冗余，磁盘或节点故障后数据不可用 | 生产环境使用 `ReplicatedMergeTree`（依赖 ZooKeeper/Keeper 记录副本元数据）配置多副本 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 手动把所有过滤条件都塞进 `PREWHERE` 反而更慢 | PREWHERE 只适合高选择性、能快速裁剪数据的条件；MergeTree 已会自动把部分 WHERE 下推为 PREWHERE | 只把高选择性的过滤条件放 PREWHERE，其余交给 WHERE，由优化器自动处理 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 查询条件不带分区键导致分区裁剪失效 | 分区裁剪依赖查询条件命中 PARTITION BY 表达式，条件缺失时退化为全分区扫描 | 查询尽量带上分区键范围条件（如 `event_date BETWEEN ...`），只扫描相关分区 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 在查询中频繁使用 `FINAL` 做 ReplacingMergeTree 去重导致查询变慢 | 后台合并时机不确定，查询时可能仍有重复数据，`FINAL` 会强制合并，性能较差 | 不要在日常查询里频繁用 `FINAL`；接受"最终一致"语义，按业务周期用 `OPTIMIZE ... FINAL` 收敛 | [ClickHouse笔面试题集导览](./02-ClickHouse笔面试题集-导览.md) |
| 直接对分布式表做小批量写入，各分片 Part 同时膨胀 | 写 `Distributed` 表会扇出到所有分片，小批量写入让每个分片的 Part 数成倍增长 | 写本地表由业务侧决定分片，或用 `Buffer` / `Kafka` 引擎缓冲后批量写入 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
