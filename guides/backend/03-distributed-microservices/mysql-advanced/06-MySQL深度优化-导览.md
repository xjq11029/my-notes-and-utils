## 一、核心概念

### 1.1 InnoDB 存储引擎架构

| 维度 | 内容 |
|------|------|
| 是什么 | MySQL 默认的存储引擎，支持事务、行锁、外键，采用内存与磁盘结合的架构。 |
| 能做什么 | 支持事务 ACID；行级锁高并发；缓冲池加速；崩溃恢复；支持外键约束。 |
| 怎么用 | 建表时 `ENGINE=InnoDB` 默认即 InnoDB。 |
| 原理和工作流程 | InnoDB 架构分内存与磁盘两部分。内存含 Buffer Pool 缓存数据页与索引页、Change Buffer 缓存二级索引修改、Adaptive Hash Index 自适应哈希、Log Buffer 缓存 redo 日志。磁盘含系统表空间、独立表空间 ibd 文件、redo log 文件、undo log、binlog。查询先查 Buffer Pool 未命中则从磁盘加载页到内存。修改先更新 Buffer Pool 脏页，写 redo log 与 undo log，事务提交刷 redo log 保证持久性，后台线程异步刷脏页与合并 change buffer。 |
| 缺点 | Buffer Pool 内存占用大需调优；脏页刷盘时机影响性能；大事务产生大量 undo；系统表空间管理复杂；内存数据断电丢失依赖 redo 恢复。 |

### 1.2 行格式（Row Format）

| 维度 | 内容 |
|------|------|
| 是什么 | InnoDB 存储行数据的物理格式，包含 Compact、Dynamic、Compressed 等格式。 |
| 能做什么 | 高效存储行数据；处理变长字段溢出；压缩节省空间；支持 NULL 与变长字段。 |
| 怎么用 | `CREATE TABLE t (...) ROW_FORMAT=DYNAMIC;` |
| 原理和工作流程 | Compact 格式分记录额外信息与真实数据，额外信息含变长字段长度列表、NULL 标志位、记录头信息。变长字段实际长度较短存记录内，超长则溢出存到溢出页用指针指向。Dynamic 格式是 Compact 改进，溢出列只存 20 字节指针不存前 768 字节，溢出页全量存储，减少主页占用提升查询效率。Compressed 在 Dynamic 基础上压缩页节省空间但增加 CPU 开销。行格式影响存储空间与查询性能。 |
| 缺点 | 溢出页增加 IO 次数；Compressed 压缩解压耗 CPU；行格式升级需重建表；Compact 溢出列冗余存储；格式选择影响大字段性能。 |

## 二、底层原理

### 2.1 B+ 树索引

| 维度 | 内容 |
|------|------|
| 是什么 | InnoDB 默认的索引数据结构，所有数据按 B+ 树组织，主键为聚簇索引二级索引为辅助索引。 |
| 能做什么 | 加速等值与范围查询；聚簇索引存全行；二级索引存主键；支持排序；叶子节点链表遍历。 |
| 怎么用 | `CREATE INDEX idx_name ON t(name);` 主键自动建聚簇索引。 |
| 原理和工作流程 | InnoDB 数据按主键聚簇存储在 B+ 树叶子节点即聚簇索引，叶子节点存完整行数据。二级索引叶子节点存索引列值与主键值。B+ 树非叶子节点只存键值与指针不存数据，单页可存更多键降低树高通常 3 到 4 层。相比 B 树 B+ 树非叶节点不存数据查询更稳定，叶子节点有序链表支持高效范围查询。相比红黑树 B+ 树多路平衡树高远低于二叉树磁盘 IO 更少。回表指二级索引查到主键再到聚簇索引查全行。 |
| 缺点 | 索引占用磁盘空间；写入需维护 B+ 树降低性能；主键选择不当致页分裂；回表增加随机 IO；索引过多增加优化器选择成本。 |

#### 最左前缀原则

| 维度 | 内容 |
|------|------|
| 是什么 | 联合索引匹配查询条件时必须从最左列开始连续匹配的规则。 |
| 能做什么 | 判断联合索引是否生效；指导索引列顺序设计；优化查询条件编写。 |
| 怎么用 | 索引 (a,b,c) 可匹配 a、ab、abc，不能跳过 a 直接用 b。 |
| 原理和工作流程 | 联合索引按列顺序在 B+ 树中排序，先按 a 排序 a 相同按 b 排序 b 相同按 c 排序。查询条件必须从最左列 a 开始才能利用索引有序性。等于条件可乱序因优化器会调整，但范围查询会导致后续列无法用索引。如索引 (a,b,c) 查询 a=1 and c=3 则 c 无法用索引因 b 被跳过。最左前缀决定了哪些查询能走联合索引，是索引设计的核心依据。 |
| 缺点 | 范围查询后列失效；查询条件须含最左列；索引列顺序设计依赖经验；部分场景需建多索引；原则理解不深易失效。 |

#### 覆盖索引

| 维度 | 内容 |
|------|------|
| 是什么 | 查询所需字段全部被索引覆盖无需回表的技术。 |
| 能做什么 | 避免回表随机 IO；提升查询性能；减少磁盘访问；优化热点查询。 |
| 怎么用 | 建联合索引覆盖查询列 `CREATE INDEX idx_cover ON t(name, age);` 查询 `SELECT name, age FROM t WHERE name='zs';` |
| 原理和工作流程 | 二级索引叶子节点存索引列值与主键。当查询所需字段全部包含在索引列中时，二级索引即可返回完整结果无需再到聚簇索引回表查全行。EXPLAIN 中 Extra 显示 Using index 表示覆盖索引。覆盖索引避免了回表的随机 IO，对高频查询性能提升显著。设计索引时应尽量让索引覆盖常用查询字段，但需平衡索引大小与更新成本。 |
| 缺点 | 索引列增多增大索引体积；覆盖索引可能包含不必要的列；更新成本增加；无法覆盖大字段查询；索引设计复杂度上升。 |

#### 索引下推（ICP）

| 维度 | 内容 |
|------|------|
| 是什么 | MySQL 5.6 引入的优化，将部分 WHERE 条件下推到存储引擎层在索引遍历时过滤。 |
| 能做什么 | 减少回表次数；减少存储引擎到 Server 层的数据传输；提升查询性能。 |
| 怎么用 | 索引 (name, age) 查询 `WHERE name LIKE '张%' AND age > 18` 触发 ICP。 |
| 原理和工作流程 | 无 ICP 时存储引擎按 name LIKE '张%' 遍历索引取出所有匹配主键回表，再由 Server 层用 age 过滤。有 ICP 时存储引擎在索引遍历时同时用 age 条件过滤，只有同时满足 name LIKE 和 age 的记录才回表，大幅减少回表次数。EXPLAIN 中 Extra 显示 Using index condition 表示启用了 ICP。ICP 对联合索引中范围查询后的等值条件过滤效果显著。 |
| 缺点 | 仅对联合索引部分场景有效；条件下推有一定计算开销；子查询无法使用；需 MySQL 5.6 以上；部分条件不支持下推。 |

#### 索引失效场景

| 维度 | 内容 |
|------|------|
| 是什么 | 查询条件无法使用索引导致全表扫描的常见场景。 |
| 能做什么 | 识别索引失效原因；优化查询与索引；避免函数运算与隐式转换；规范 SQL 编写。 |
| 怎么用 | 避免 `WHERE YEAR(create_time)=2024`，改用范围查询 `WHERE create_time >= '2024-01-01'`。 |
| 原理和工作流程 | 索引失效常见场景：对索引列使用函数或运算如 YEAR(date) 或 age+1 破坏有序性；隐式类型转换如字符串列与数字比较致索引失效；LIKE 以通配符开头 '%张' 无法利用有序性；OR 连接非索引列致全表扫描；联合索引不满足最左前缀；NOT、!=、NOT IN 通常无法用索引范围扫描；ORDER BY 列与索引顺序不一致。这些场景使优化器放弃索引选择全表扫描。 |
| 缺点 | 失效场景多需逐一排查；部分场景难避免如 NOT IN；函数查询需改写 SQL；隐式转换隐蔽难发现；优化需重建索引。 |

### 2.2 索引优化

| 维度 | 内容 |
|------|------|
| 是什么 | 通过分析执行计划与慢查询识别低效 SQL 并优化索引的实践方法。 |
| 能做什么 | 解读 EXPLAIN 执行计划；分析慢查询日志；优化深分页；设计高效索引；消除全表扫描。 |
| 怎么用 | `EXPLAIN SELECT ...;` 查看执行计划关键字段。 |
| 原理和工作流程 | 索引优化以 EXPLAIN 为核心工具分析 SQL 执行计划，关注 type 访问类型、possible_keys 可能索引、key 实际索引、rows 扫描行数、Extra 额外信息。结合慢查询日志定位慢 SQL，分析是否全表扫描、回表过多、临时表或 filesort。针对问题添加合适索引、改写 SQL、利用覆盖索引与索引下推、优化深分页。优化后再次 EXPLAIN 验证效果，形成分析优化验证闭环。 |
| 缺点 | EXPLAIN 估算行数可能不准；优化需反复试错；索引过多影响写入；慢查询日志量大需筛选；部分场景优化器选择异常。 |

#### EXPLAIN 关键字段解读

| 维度 | 内容 |
|------|------|
| 是什么 | EXPLAIN 输出的执行计划关键字段及其含义。 |
| 能做什么 | 判断访问类型；查看使用索引；评估扫描行数；识别额外操作；诊断 SQL 性能。 |
| 怎么用 | `EXPLAIN SELECT * FROM t_user WHERE status=1;` |
| 原理和工作流程 | id 表示查询序号 id 越大越先执行。select_type 查询类型如 SIMPLE、PRIMARY、SUBQUERY。table 涉及表名。type 访问类型从优到差为 system、const、eq_ref、ref、range、index、ALL，ALL 为全表扫描需优化。possible_keys 可能使用的索引。key 实际使用的索引。key_len 索引使用长度判断联合索引用了几列。rows 估算扫描行数越小越好。filtered 过滤比例。Extra 额外信息如 Using index 覆盖索引、Using temporary 临时表、Using filesort 额外排序均需关注。 |
| 缺点 | rows 为估算值可能不准；统计信息过期致计划偏差；部分场景需 EXPLAIN ANALYZE；字段多需逐一分析；复杂查询计划难解读。 |

#### 慢查询日志分析

| 维度 | 内容 |
|------|------|
| 是什么 | 记录执行时间超过阈值的 SQL 语句用于定位性能问题的机制。 |
| 能做什么 | 记录慢 SQL；定位性能瓶颈；分析执行频率与耗时；为优化提供依据。 |
| 怎么用 | `SET GLOBAL slow_query_log=ON;` `SET GLOBAL long_query_time=1;` |
| 原理和工作流程 | 开启 slow_query_log 并设置 long_query_time 阈值，MySQL 将执行时间超过阈值的 SQL 记录到慢查询日志文件。日志包含 SQL 文本、执行时间、扫描行数、锁定时间等信息。通过 mysqldumpslow 或 pt-query-digest 工具聚合分析，按执行次数、总耗时、平均耗时排序找出高频慢 SQL。结合 EXPLAIN 分析原因并优化。生产环境建议设阈值 1 秒并定期分析。 |
| 缺点 | 日志文件持续增长需定期清理；阈值设置不当遗漏或过多；仅记录耗时不含执行计划；分析需工具辅助；高并发下日志影响性能。 |

#### 深分页优化

| 维度 | 内容 |
|------|------|
| 是什么 | 解决 LIMIT 深分页扫描丢弃大量行导致慢查询的优化技术。 |
| 能做什么 | 子查询覆盖索引定位；游标分页避免 OFFSET；减少回表；提升深分页性能。 |
| 怎么用 | `SELECT * FROM t_user WHERE id > (SELECT id FROM t_user ORDER BY id LIMIT 100000,1) LIMIT 10;` |
| 原理和工作流程 | 标准 LIMIT 100000,10 扫描 100010 行丢弃前 100000 行再返回 10 行，深分页扫描丢弃大量行极慢。优化方案一子查询覆盖索引：先 SELECT id 走覆盖索引定位第 100000 行的主键，再 WHERE id 大于该主键 LIMIT 10 回表，减少回表次数。方案二游标分页：记录上一页最大 id 用 WHERE id 大于 last_id LIMIT 10 直接定位避免 OFFSET 扫描。方案三覆盖索引 JOIN 回表。方案一二最常用。 |
| 缺点 | 游标分页不支持跳页；子查询仍需扫描定位；分页数据实时变化致重复或遗漏；方案选择依赖场景；复杂排序深分页难优化。 |

### 2.4 分库分表方案

| 维度 | 内容 |
|------|------|
| 是什么 | 应对单库单表数据量过大的水平与垂直拆分方案。 |
| 能做什么 | 垂直拆分按业务；水平拆分按数据；分片算法路由；分片键选择；解决单表瓶颈。 |
| 怎么用 | 借助 ShardingSphere 等中间件配置分片规则。 |
| 原理和工作流程 | 垂直分库按业务拆分数据库如用户库订单库降低单库压力，垂直分表将宽表拆为多张窄表分离热点字段。水平分表将单表数据按规则拆分到多表如 t_order_0 到 t_order_31，水平分库将数据分布到多个数据库实例。分片算法决定数据路由，分片键决定拆分维度。分库分表解决单表数据量大、单库连接与 IO 瓶颈问题，但引入分布式事务、跨库 JOIN、全局 ID、数据迁移等复杂度。通常单表超 1000 万或单库超 1TB 考虑拆分。 |
| 缺点 | 跨库 JOIN 困难；分布式事务复杂；全局 ID 需方案；数据迁移成本高；运维复杂度倍增；非必要不拆分。 |

#### 垂直拆分 vs 水平拆分

| 维度 | 内容 |
|------|------|
| 是什么 | 两种分库分表策略的对比，垂直按结构拆分水平按数据拆分。 |
| 能做什么 | 垂直拆分按业务或字段；水平拆分按行数据；降低单库单表压力；隔离热点。 |
| 怎么用 | 垂直分库按业务模块分库；水平分表按 hash 或范围分表。 |
| 原理和工作流程 | 垂直分库按业务将不同模块拆到不同数据库，如用户库、订单库、商品库，降低单库连接与 IO 压力实现业务隔离。垂直分表将宽表的冷热字段拆分，如商品基本信息表与详情表分离，减少单行大小提升 IO 效率。水平分表将同一表数据按分片键拆分到多张表，如按用户 ID 取模分到 t_order_0 到 t_order_15。水平分库在分表基础上分布到不同数据库实例。垂直拆分改变结构水平拆分改变数据分布。 |
| 缺点 | 垂直分库跨库 JOIN 困难；垂直分表增加查询复杂度；水平拆分路由规则设计难；两者组合运维复杂；拆分后难以回退。 |

#### 分片算法

| 维度 | 内容 |
|------|------|
| 是什么 | 决定数据如何路由到具体分片节点的算法。 |
| 能做什么 | 取模分片；范围分片；一致性哈希；按日期分片；自定义分片。 |
| 怎么用 | 配置分片规则如 `user_id % 16` 路由到 16 张表。 |
| 原理和工作流程 | 取模分片按分片键对分片数取模路由，数据分布均匀但扩容需重新分片。范围分片按分片键范围划分如 ID 1 到 100 万分片一，扩容方便但可能数据热点。一致性哈希将节点与数据映射到哈希环，扩容只迁移部分数据但实现复杂。按日期分片适合时间序列数据如按月分表便于清理历史。分片算法决定数据分布均匀性、扩容成本与查询效率，需根据业务特点选择。ShardingSphere 支持配置多种分片算法。 |
| 缺点 | 取模扩容需全量迁移；范围分片易热点；一致性哈希实现复杂；跨分片查询性能差；算法选择影响扩展性。 |

#### 分片键选择原则

| 维度 | 内容 |
|------|------|
| 是什么 | 选择分片键时需遵循的设计原则，决定查询路由效率。 |
| 能做什么 | 选择高频查询字段；保证数据均匀分布；避免跨分片查询；支持范围查询。 |
| 怎么用 | 选择 user_id 作为分片键因多数查询带用户维度。 |
| 原理和工作流程 | 分片键选择直接影响查询效率。原则一选择高频查询条件字段，使多数查询能定位到单分片避免广播查询。原则二高基数低重复保证数据均匀分布避免热点。原则三避免跨分片 JOIN 与聚合，分片键应覆盖主要查询维度。原则四考虑数据增长趋势避免未来热点。常见选择为用户 ID、订单 ID 等业务主键。若查询维度多无法单分片键覆盖，可考虑基因法或多维度冗余。分片键一旦确定难以更改需慎重。 |
| 缺点 | 分片键难以满足所有查询维度；跨分片查询不可避免；分片键变更成本极高；多维度查询需冗余；选择不当致数据倾斜。 |

## 三、实战应用

### 3.1 索引设计原则

| 维度 | 内容 |
|------|------|
| 是什么 | 设计高效索引时需遵循的核心原则集合。 |
| 能做什么 | 选择合适索引列；控制索引数量；利用覆盖索引；遵循最左前缀；避免冗余索引。 |
| 怎么用 | 高频查询字段建索引，联合索引按区分度排序。 |
| 原理和工作流程 | 索引设计原则：选择区分度高且查询频繁的列建索引；联合索引按区分度从高到低排序并遵循最左前缀；尽量设计覆盖索引避免回表；单表索引数量建议不超过 5 个避免影响写入；优先为 WHERE、ORDER BY、GROUP BY、JOIN ON 的列建索引；避免在低区分度列如性别单独建索引；避免冗余索引如已有 (a,b) 不需再建 (a)；使用前缀索引优化长字符串列。索引设计需结合业务查询模式与数据分布。 |
| 缺点 | 设计需平衡查询与写入性能；索引数量难精确控制；业务变化致索引失效；前缀索引不支持 ORDER BY；冗余索引难识别。 |

### 3.2 慢 SQL 优化案例

| 维度 | 内容 |
|------|------|
| 是什么 | 通过真实案例演示慢 SQL 定位分析与优化的完整流程。 |
| 能做什么 | 定位慢 SQL；分析执行计划；识别性能瓶颈；添加索引或改写 SQL；验证优化效果。 |
| 怎么用 | EXPLAIN 分析加添加覆盖索引加改写深分页。 |
| 原理和工作流程 | 案例流程：通过慢查询日志定位耗时 SQL，EXPLAIN 分析发现 type 为 ALL 全表扫描且 rows 估算巨大。原因分析：查询条件列无索引或索引失效、深分页扫描丢弃、LIKE 通配符开头、隐式类型转换。优化措施：为查询条件添加联合索引、深分页改用子查询或游标、LIKE 改为前缀匹配、确保类型一致、利用覆盖索引消除回表。优化后再次 EXPLAIN 验证 type 变为 ref 或 range、rows 大幅下降、Extra 显示 Using index。 |
| 缺点 | 优化需反复验证；部分 SQL 改写影响业务逻辑；索引添加影响写入；统计信息不准致计划偏差；复杂 SQL 优化难度大。 |

### 3.3 分表策略

| 维度 | 内容 |
|------|------|
| 是什么 | 针对不同业务场景的分表方案设计与落地实践。 |
| 能做什么 | 按用户分表；按时间分表；配置分片规则；处理跨表查询；数据迁移。 |
| 怎么用 | 借助 ShardingSphere 配置分表规则 `actual-data-nodes: ds.t_order_$->{0..15}`。 |
| 原理和工作流程 | 分表策略按业务场景选择。按用户 ID 取模分表适合用户维度查询为主的场景如订单表按 user_id 分 16 表。按时间范围分表适合时间序列数据如日志表按月分表便于清理历史。一致性哈希分表适合需要平滑扩容的场景。配置 ShardingSphere 分片规则定义分片键与分片算法，应用层透明访问逻辑表，中间件路由到物理表。跨表查询通过广播或绑定表优化。数据迁移采用双写或同步工具平滑过渡。 |
| 缺点 | 跨表聚合查询复杂；分表后事务一致性难保证；数据迁移风险高；分片规则变更困难；运维监控复杂。 |

## 四、常见面试题（附答案）

### 1. 为什么 MySQL 索引用 B+ 树而不是 B 树或红黑树？

| 维度 | 内容 |
|------|------|
| 是什么 | InnoDB 选择 B+ 树作为索引数据结构的原因分析。 |
| 能做什么 | 对比 B 树红黑树 B+ 树；分析磁盘 IO 效率；分析范围查询；分析树高与查询稳定性。 |
| 怎么用 | 主键自动建 B+ 树聚簇索引。 |
| 原理和工作流程 | 相比 B 树，B+ 树非叶子节点只存键值与指针不存数据，单页可容纳更多键值，树高更低通常 3 到 4 层即可存储千万级数据，磁盘 IO 次数更少。B+ 树叶子节点通过双向链表相连，范围查询只需遍历链表高效，而 B 树需中序遍历回溯效率低。B+ 树所有数据在叶子节点查询路径长度相同性能稳定，B 树数据分布在各节点查询不稳定。相比红黑树二叉结构树高远高于 B+ 树多路平衡，磁盘 IO 次数多不适合磁盘存储。 |
| 缺点 | B+ 树插入删除需维护平衡有分裂合并开销；树高虽低仍需多次 IO；范围查询依赖链表；非叶子节点不存数据需到叶子；相比哈希不支持等值快速查询。 |

### 2. 聚簇索引和非聚簇索引的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 两种索引组织方式的对比，数据存储位置不同。 |
| 能做什么 | 聚簇索引存全行；非聚簇索引存主键；回表查询；主键选择。 |
| 怎么用 | 主键自动建聚簇索引，`CREATE INDEX` 建非聚簇索引。 |
| 原理和工作流程 | 聚簇索引将数据行与索引一起存储，B+ 树叶子节点存完整行数据，InnoDB 主键即为聚簇索引，一张表只能有一个聚簇索引。非聚簇索引即二级索引，叶子节点存索引列值与主键值而非全行，查询需先查二级索引获取主键再回表到聚簇索引查全行。聚簇索引按主键有序存储利于主键范围查询，非聚簇索引需回表增加 IO。MyISAM 数据与索引分离均为非聚簇。聚簇索引选择推荐自增主键避免页分裂。 |
| 缺点 | 聚簇索引只能一个主键选择受限；非聚簇索引回表增加随机 IO；主键更新致聚簇索引重组；二级索引存主键增大体积；无主键时选唯一索引或隐式行号。 |

### 3. 什么是回表？如何避免？

| 维度 | 内容 |
|------|------|
| 是什么 | 二级索引查询主键后再到聚簇索引查全行数据的操作及避免方法。 |
| 能做什么 | 识别回表操作；设计覆盖索引避免回表；减少随机 IO；优化查询性能。 |
| 怎么用 | 建联合索引覆盖查询列 `CREATE INDEX idx_cover ON t(name, age);` |
| 原理和工作流程 | 回表指通过二级索引查到主键值后，再到聚簇索引 B+ 树查找完整行数据的过程，产生一次随机 IO。当查询所需字段全部包含在二级索引列中时即为覆盖索引，二级索引可直接返回结果无需回表。避免回表方法：设计联合索引覆盖常用查询字段；避免 SELECT * 只查必要字段；利用索引下推减少回表次数；将高频查询字段纳入索引。EXPLAIN 中 Extra 显示 Using index 表示覆盖索引未回表。 |
| 缺点 | 覆盖索引增大索引体积；索引列过多影响写入；无法覆盖大字段；SELECT * 无法覆盖；部分场景回表不可避免。 |

### 4. MySQL 什么情况下索引会失效？

| 维度 | 内容 |
|------|------|
| 是什么 | 查询条件无法使用索引导致全表扫描的常见场景汇总。 |
| 能做什么 | 识别索引失效；避免函数运算；避免隐式转换；规范 LIKE 与 OR；遵循最左前缀。 |
| 怎么用 | 避免 `WHERE YEAR(create_time)=2024`，改用 `WHERE create_time >= '2024-01-01'`。 |
| 原理和工作流程 | 索引失效场景：对索引列使用函数或运算如 YEAR(date) 或 age+1 破坏 B+ 树有序性；隐式类型转换如字符串列与数字比较 MySQL 将字符串转数字致索引失效；LIKE 以通配符开头 '%张' 无法利用有序性；OR 连接的条件中有非索引列致全表扫描；联合索引不满足最左前缀原则；NOT、!=、NOT IN 通常无法用范围扫描；ORDER BY 列与索引顺序不一致或方向不同。优化器评估全表扫描成本更低时也会放弃索引。 |
| 缺点 | 失效场景多需逐一排查；部分场景难避免如 NOT IN；函数查询需改写 SQL；隐式转换隐蔽难发现；优化器选择有时不可预期。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总 MySQL 深度优化中常见陷阱与最佳实践。 |
| 能做什么 | 避免索引失效；规范深分页；合理选主键；控制分表时机；优化大事务。 |
| 怎么用 | 自增主键；游标分页；单表超千万再分表；大事务拆分。 |
| 原理和工作流程 | 索引列函数运算致失效须改写 SQL 用范围查询替代函数。深分页 LIMIT 扫描丢弃大量行须用子查询或游标分页。主键选 UUID 致聚簇索引页分裂频繁与二级索引体积膨胀须用自增主键。过早分库分表引入不必要的分布式复杂度须单表超千万或单库超 1TB 再拆分。大事务产生大量 undo 日志占用空间与锁须拆分为小事务。SELECT * 致无法覆盖索引回表须只查必要字段。OR 查询致索引失效须用 UNION ALL 替代。 |
| 缺点 | 规则多需结合场景；自增主键暴露业务量；游标分页不支持跳页；分表时机难精确判断；大事务拆分影响一致性。 |
