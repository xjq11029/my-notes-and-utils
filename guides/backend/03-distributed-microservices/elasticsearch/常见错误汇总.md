# Elasticsearch - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 动态映射将日期格式字符串误识别为 Date 类型，后续写入报错 | ES 默认开启动态映射，自动推断字段类型 | 关闭动态映射（`dynamic: "strict"`）；或使用 dynamic_templates 精确控制 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 分片数设置不合理，无法动态修改 | Primary Shard 数量在索引创建时确定 | 创建索引前做好容量规划：分片数 = 预估数据量 / 单分片建议大小（10-50GB）；修改需通过 Reindex API 重建索引 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 用 ES 做事务型主存储导致数据不一致 | ES 是 AP 系统，牺牲了强一致性 | MySQL 做主存储，ES 做搜索引擎和只读副本，通过数据同步保持最终一致性 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 深度分页导致协调节点内存暴增、查询超时 | 协调节点需从每个分片收集 from+size 条数据，默认限制 10000 | 使用 search_after（实时翻页）；使用 scroll（全量导出）；修改 max_result_window（临时方案） | [ES核心原理导览](./01-ES核心原理-导览.md) |
| text 字段上做聚合导致结果无意义 | text 类型字段被分词，聚合无意义 | 聚合必须使用 keyword 类型字段 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 大量小 Segment 导致查询性能下降 | 频繁写入产生大量小 Segment | 低峰期手动调用 _forcemerge 合并；批量导入时设置 refresh_interval=-1 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 不监控集群健康状态导致部分分片不可用未及时发现 | 未监控集群状态 | 监控 green/yellow/red 状态，yellow 以上需及时处理 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| text 类型字段使用 term 查询查不到预期结果 | text 字段存储时已被分词，term 查询匹配的是分词后的词项 | 使用 match 查询；或对 name.keyword 子字段使用 term 查询 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| text 类型字段上做聚合导致堆内存消耗大 | text 字段默认不能聚合，需设置 fielddata=true（加载到堆内存） | 为 text 字段设置 fields 子字段（如 name.keyword），用 keyword 子字段做聚合 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| terms 聚合的 size 过大导致性能下降 | 指定过大的 size 会影响性能，默认只返回前 10 个桶 | 如需全部分组，使用 composite 聚合分页获取 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 高基数字段 terms 聚合导致内存和 CPU 消耗大 | 如 user_id 去重聚合，桶数量巨大 | 使用 cardinality 近似替代 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| date_histogram 时区未设置导致聚合结果按 UTC 时区计算 | 默认使用 UTC 时区 | 显式设置 `time_zone: "+08:00"` | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| filter 缓存失效导致频繁变化的 filter 条件命中率低 | 如"最近一小时"条件频繁变化，不适合缓存 | ES 会自动跳过不适合缓存的 filter；使用 Profile API 分析慢查询 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 把 `text` 类型当精确值字段用，导致排序、聚合、精确筛选都不可用 | 字段只定义了 `text`，没有 keyword 子字段；text 被分词后无法用于精确操作 | 显式定义 mapping，同时需要分词检索与精确操作的字段配置 `fields.keyword` 子字段，精确场景统一走 `字段名.keyword` | [ES核心原理导览](./01-ES核心原理-导览.md) |
| `search_after` 翻页出现重复或漏数据 | 排序字段不唯一，多条文档排序值相同时翻页边界不确定 | 排序字段必须包含唯一字段（如 `_id`）作为 tiebreaker | [ES笔面试题集导览](./03-ES笔面试题集-导览.md) |
| `search_after` 翻页期间数据被写入，结果前后不一致 | 两次查询之间索引数据发生变化，游标位置对应的排序值已改变 | 配合 `PIT`（Point In Time，ES 7.10+）固定查询视图，用完再关闭 PIT | [ES笔面试题集导览](./03-ES笔面试题集-导览.md) |
| 用 `scroll` 做用户实时翻页，新增数据看不到 | `scroll` 创建的是数据快照，快照期间写入的增量数据不可见 | 实时翻页 / 无限滚动用 `search_after`；`scroll` 只用于全量导出、批量处理等离线场景 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 简单调大 `max_result_window` 来绕过深分页限制 | 调大上限只是放开限制，协调节点仍要收集 `from+size` 条数据，内存压力没解决 | 治标不治本，仅作临时方案；正式方案用 `search_after`（实时）或 `scroll`（导出） | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 把 `cardinality` 的近似去重结果当精确 UV 使用 | `cardinality` 基于 HyperLogLog++，默认误差率在 5% 以内 | 用 `precision_threshold` 调高精度（最大 40000，误差约 1%，内存开销随之增大）；要求精确时在应用层或 `scripted_metric` 实现 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 只取聚合结果却仍返回大量文档，浪费带宽 | 查询里没设 `size: 0`，默认返回前 10 条命中文档 | 纯聚合查询设置 `"size": 0`，只返回聚合结果 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 高频聚合字段每次都重建全局序号，聚合开销大 | 未预加载 ordinals，每次聚合都要现场构建 | 对频繁参与聚合的字段设置 `eager_global_ordinals` 预加载全局序号 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 误以为文档写入后立刻可被搜索到 | ES 是近实时（NRT），默认 `refresh_interval=1s`，写入先进内存 Buffer，刷新为 Segment 后才可搜索 | 理解 1 秒的刷新延迟是性能与实时性的折中；确需立即可搜时手动 `_refresh`；批量导入时设 `refresh_interval=-1` 提升写入吞吐 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 混淆 `Refresh` 与 `Flush`，误以为 Flush 才是"数据可搜索"的时机 | `Refresh` 把内存 Buffer 刷成可搜索的 Segment；`Flush` 是把 Segment 持久化到磁盘并清空 Translog，两者目的不同 | 明确 Refresh 决定"能不能搜到"，Flush 决定"落没落盘"；调优写入时针对 Refresh 调 `refresh_interval` | [ES笔面试题集导览](./03-ES笔面试题集-导览.md) |
| 变更 mapping 或重建索引时直接删旧索引，导致服务中断 | 应用代码里写死了物理索引名，只能删了重建 | 用索引别名（Index Alias）解耦：应用始终读写别名 `products`，重建时建 `products_v2` 后原子切换别名，实现零停机 | [ES查询与聚合分析导览](./02-ES查询与聚合分析-导览.md) |
| 索引与搜索用同一个 IK 分词模式，召回率或准确率不理想 | 只配了一个 `analyzer`，没有区分写入和查询阶段 | 索引时用 `ik_max_word`（细粒度、提高召回），搜索时用 `ik_smart`（粗粒度、提高准确），分别配置 `analyzer` 与 `searchAnalyzer` | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 中文文档直接用默认 `standard` 分词器，检索效果差 | 未安装 IK 中文分词插件，中文被逐字切分，词项无意义 | 安装 `elasticsearch-analysis-ik` 插件并重启节点，索引 mapping 中显式指定 IK 分词器 | [ES核心原理导览](./01-ES核心原理-导览.md) |
| 集群健康状态为 `yellow` 被忽略，主分片故障时无副本可用 | 部分副本分片未分配，数据仍可读写，容易让人误以为"没问题" | 监控三种状态：`green` 正常、`yellow` 需告警（高可用受损）、`red` 需紧急处理（部分主分片不可用） | [ES笔面试题集导览](./03-ES笔面试题集-导览.md) |
| MySQL 与 ES 双写导致两边数据不一致 | 业务代码同时写两个存储，任一写入失败或顺序颠倒就产生脏数据 | 用 Canal 监听 MySQL binlog 经 Kafka 异步同步到 ES（零侵入、实时性高），或 Logstash 定时拉取（简单但有延迟） | [ES笔面试题集导览](./03-ES笔面试题集-导览.md) |
