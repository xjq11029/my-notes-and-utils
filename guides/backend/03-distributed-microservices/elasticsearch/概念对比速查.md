# Elasticsearch - 概念对比速查

---

### Elasticsearch vs MySQL

| 对比维度 | Elasticsearch | MySQL |
|---------|-------------|-------|
| 核心定位 | 分布式搜索和分析引擎 | 关系型数据库管理系统 |
| 数据模型 | 文档型（JSON），基于 Index/Document/Field | 关系型，基于 Database/Table/Row/Column |
| 存储引擎 | 基于 Apache Lucene 的倒排索引 | InnoDB（B+Tree）、MyISAM 等 |
| 查询语言 | DSL（JSON 格式），支持全文检索 | SQL，支持精确查询和 JOIN |
| 事务支持 | 不支持 ACID 事务 | 完整支持 ACID 事务 |
| CAP 定位 | AP 系统，牺牲强一致性 | CP 系统（默认），保证强一致性 |
| 水平扩展 | 原生支持分片和副本，水平扩展 | 需借助分库分表中间件 |
| 全文检索 | 核心能力，基于倒排索引和分词器 | 有限支持（LIKE、FULLTEXT），性能差 |
| 聚合分析 | 强大的聚合分析能力（Bucket/Metric/Pipeline） | GROUP BY + 聚合函数，大数据量下性能差 |
| 写入吞吐 | 批量写入高吞吐 | 单行写入，受事务和索引约束 |
| 适用场景 | 全文搜索、日志分析、实时监控 | 业务数据存储、事务操作、强一致性需求 |
| 选择建议 | 搜索和分析场景选 ES；事务型主存储选 MySQL；两者配合使用 | |

### Lucene vs Elasticsearch

| 对比维度 | Lucene | Elasticsearch |
|---------|-------|-------------|
| 核心定位 | Java 全文检索库，搜索引擎底层组件 | 基于 Lucene 构建的分布式搜索和分析引擎 |
| 使用方式 | 需要编写 Java 代码调用 API | 提供 RESTful API，语言无关 |
| 分布式能力 | 无，需自行实现 | 原生支持分片、副本、集群管理 |
| 运维管理 | 需自行管理索引、合并、优化 | 自动化分片分配、段合并、集群健康监控 |
| 高级功能 | 仅提供基础检索能力 | 聚合分析、高亮显示、索引别名、数据管道 |
| 学习成本 | 高，需理解底层 API | 中，RESTful API 易上手 |
| 适用场景 | 嵌入式搜索、对性能有极致要求的场景 | 分布式搜索、日志分析、业务搜索服务 |
| 选择建议 | 需要内嵌搜索能力或深度定制时选用；大多数场景直接使用 ES | |

### 倒排索引 vs B+树

| 对比维度 | 倒排索引 | B+树 |
|---------|---------|------|
| 核心定位 | 词项到文档 ID 列表的映射，用于全文检索 | 排序的平衡多路搜索树，用于精确查询和范围查询 |
| 数据结构 | Term Dictionary + Term Index（FST） + Posting List | 多层节点，叶子节点形成有序链表 |
| 检索方式 | 通过词项直接定位文档列表，O(1) 复杂度 | 从根节点逐层二分查找，O(log N) 复杂度 |
| 适用查询类型 | 全文检索、模糊匹配、相关性评分 | 精确等值查询、范围查询、排序 |
| 索引大小 | 较小，稀疏索引，每 8192 行一个 Mark | 较大，稠密索引，每行一个索引项 |
| 更新成本 | 高，需重建 Segment | 低，支持原地更新 |
| 存储引擎 | Elasticsearch 底层使用 | MySQL InnoDB 底层使用 |
| 选择建议 | 全文检索场景选倒排索引；OLTP 精确查询选 B+树 | |

### text vs keyword

| 对比维度 | text | keyword |
|---------|------|---------|
| 核心定位 | 面向全文检索的分词字段 | 面向精确匹配、排序、聚合的整值字段 |
| 是否分词 | 是，写入和查询时都经过分词器拆成词项 | 否，整个字段值作为一个词项存储 |
| 支持的查询 | `match`、`match_phrase`、`query_string` 等全文查询 | `term`、`terms`、`prefix`、`wildcard`、`range` 等精确查询 |
| 能否聚合/排序 | 默认不能（需开启 `fielddata`，会把词项加载到堆内存，代价高） | 可以，底层使用 DocValues，是聚合与排序的推荐字段类型 |
| 匹配行为 | 匹配的是分词后的词项，不是原始字符串 | 匹配的是字段完整值，大小写敏感 |
| 典型字段 | 商品标题、文章正文、日志 message | 商品 ID、分类、状态、标签、邮箱、枚举值 |
| 常见组合 | `text` + `fields.keyword` 子字段：同一份内容既能全文检索又能精确聚合 | 单独使用即可；不需要分词时不必再挂子字段 |
| 常见误区 | 在 `text` 上做 `term` 查询或聚合，结果不符合预期 | 用 `keyword` 做全文检索，必须输入完整值才匹配 |
| 选择建议 | 需要"按词搜索"的字段用 `text`；需要"精确比对/分组/排序"的字段用 `keyword`，两者都要时用 `fields` 子字段 | |

### query context vs filter context

| 对比维度 | query context（查询上下文） | filter context（过滤上下文） |
|---------|---------------------------|---------------------------|
| 核心定位 | 回答"有多相关"，为文档计算相关性评分 | 回答"符不符合"，只做是/否判断 |
| 是否计算 `_score` | 计算，结果按相关度排序 | 不计算，`_score` 恒为 0 |
| 结果缓存 | 不缓存 | 自动缓存（bitset），重复条件命中缓存后极快 |
| 性能 | 较慢，需遍历打分 | 较快，命中缓存时几乎零成本 |
| 对应 DSL 子句 | `must`、`should` | `filter`、`must_not` |
| 适用条件 | 全文检索、需要按相关度排序的条件 | 分类、状态、时间范围、价格区间等硬性筛选 |
| 缓存友好度 | 条件越固定越好 | 条件频繁变化（如"最近一小时"）时命中率低，ES 会自动跳过缓存 |
| 常见误区 | 把所有条件都写进 `must`，白白承担打分与不缓存的成本 | 需要相关度排序时误用 `filter`，结果顺序不符合预期 |
| 选择建议 | 遵循"能用 `filter` 就不用 `must`"：全文检索用 `must`，精确筛选用 `filter` | |

### from+size vs scroll vs search_after

| 对比维度 | `from + size` | `scroll` | `search_after` |
|---------|--------------|----------|----------------|
| 核心定位 | 最基础的分页方式，靠偏移量定位 | 创建数据快照，游标式迭代拉取 | 基于上一页最后一条的排序值继续查询 |
| 数据一致性 | 每次查询都是当前视图 | 快照视图，期间的增量数据不可见 | 默认非一致，配合 `PIT` 可保持一致 |
| 能否跳页 | 可以，能随机跳到任意页 | 不能，只能顺序迭代 | 不能，只能逐页向下翻 |
| 深度分页性能 | 差，协调节点要收集 `from+size` 条再排序，默认上限 `max_result_window=10000` | 好，一次初始化后按批拉取，不随页码退化 | 好，从指定排序值之后取数据，与页码无关 |
| 资源占用 | 页越深内存压力越大 | 快照期间占用分片上下文资源，需设置合理有效期 | 轻量，无额外服务端上下文 |
| 排序要求 | 无特殊要求 | 无特殊要求 | 必须指定排序字段，且需唯一字段作 tiebreaker |
| 适用场景 | 浅分页（前几页）、需要跳页的场景 | 全量导出、批量离线处理 | 实时翻页、无限滚动（推荐方案） |
| 常见误区 | 用它做深分页，或调大 `max_result_window` 硬扛 | 用它做用户实时翻页，看不到新写入的数据 | 排序字段不唯一，导致翻页重复或漏数据 |
| 选择建议 | 浅分页首选；深分页一律换 `search_after`，全量导出用 `scroll` | |

### Refresh vs Flush

| 对比维度 | Refresh | Flush |
|---------|---------|-------|
| 核心定位 | 把内存 Buffer 中的文档刷成可被搜索的 Segment | 把文件系统缓存中的 Segment 持久化到磁盘并清空 Translog |
| 解决的问题 | 文档"能不能被搜到"（近实时搜索） | 数据"会不会因断电丢失"（持久化） |
| 默认触发时机 | 每 1 秒（`refresh_interval=1s`） | 每 30 分钟，或 Translog 达到阈值时 |
| 是否产生新 Segment | 是，每次 Refresh 生成一个新 Segment | 否，只是把已有 Segment 落盘 |
| 对性能的影响 | 频繁 Refresh 产生大量小 Segment，影响查询性能 | 涉及磁盘 IO，开销较大但频率低 |
| 调优手段 | 批量导入时设 `refresh_interval=-1` 关闭自动刷新，导入完成后再恢复 | 一般无需手动干预；手动 `_flush` 用于运维排查 |
| 与 NRT 的关系 | ES 被称为"近实时搜索"正是因为默认 1 秒的 Refresh 延迟 | 与近实时无关，只关系数据安全 |
| 常见误区 | 误以为写入后立刻可搜；误以为 Flush 才是可搜索的时机 | 把 Flush 当成刷新搜索可见性的手段 |
| 选择建议 | 关注搜索实时性就调 `refresh_interval`；关注数据安全就看 Translog 与 Flush 策略 | |
