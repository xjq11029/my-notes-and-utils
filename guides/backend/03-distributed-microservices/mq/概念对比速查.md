# 消息队列 - 概念对比速查

---

### RabbitMQ vs Kafka vs RocketMQ

| 对比维度 | RabbitMQ | Kafka | RocketMQ |
|---------|---------|-------|----------|
| 核心定位 | 基于 AMQP 协议的企业级消息中间件 | 分布式流处理平台，日志管道 | 阿里巴巴开源的金融级分布式消息中间件 |
| 消息模型 | 队列模型，消费后删除 | 日志模型，消费后保留，支持回溯 | 类似 Kafka 的 Topic + Queue 模型，消费后保留 |
| 吞吐量 | 万级 TPS | 百万级 TPS | 十万级 TPS |
| 延迟 | 微秒级（us） | 毫秒级（ms） | 毫秒级（ms） |
| 路由能力 | 四种 Exchange（Direct/Topic/Fanout/Headers），复杂路由 | 仅 Topic 级别，路由能力弱 | Topic + Tag 二级分类，支持 SQL 表达式过滤 |
| 消息顺序 | 单队列内有序 | 单 Partition 内有序 | 支持全局顺序和分区顺序两种模式 |
| 事务消息 | 不支持原生事务消息 | 支持事务生产者（幂等 + 事务） | 原生支持事务消息（半消息、回查机制） |
| 延迟消息 | 通过 TTL + DLX 组合或插件实现 | 不支持原生延迟消息 | 原生支持 18 个预设延迟等级 |
| 消息回溯 | 不支持，消费后删除 | 支持按 offset 回溯 | 支持按时间或 offset 回溯 |
| 协议 | AMQP 标准协议 | 自定义二进制协议 | 自定义协议，兼容 HTTP |
| 集群架构 | 镜像队列 / Quorum Queue | Broker + ZooKeeper / KRaft | NameServer + Broker（Master/Slave）+ Dledger（Raft） |
| 运维复杂度 | 较低 | 较高（依赖 ZooKeeper 或 KRaft） | 中等 |
| 社区生态 | 成熟，插件丰富 | 极丰富，大数据生态核心 | 较 Kafka 小，国内生态活跃 |
| 适用场景 | 复杂路由、低延迟 RPC、业务消息 | 大数据管道、流处理、日志收集 | 金融电商、分布式事务、订单状态流转 |
| 选择建议 | 需要复杂路由和微秒级延迟时选用 | 需要百万级吞吐和流处理时选用 | 需要事务消息、延迟消息等金融级特性时选用 |

### 点对点 vs 发布订阅

| 对比维度 | 点对点 | 发布订阅 |
|---------|-------|---------|
| 核心定位 | 一条消息只能被一个消费者消费 | 一条消息可被多个订阅者同时消费 |
| 消息投递方式 | 生产者发送到队列，消费者从队列拉取，消费后删除 | 生产者发布到 Topic，所有订阅者各自接收消息副本 |
| 消费者关系 | 多个消费者竞争消费，负载均衡 | 每个订阅者独立消费全量消息，互不影响 |
| 消息保留 | 消费后从队列删除 | 消息保留，各订阅者独立维护消费进度 |
| Kafka 实现 | 同一消费者组内多个消费者分摊 Partition 消费 | 不同消费者组各自独立消费全量 Topic 消息 |
| RabbitMQ 实现 | 多个消费者绑定同一队列竞争消费 | 使用 Fanout Exchange 广播到多个队列 |
| 典型场景 | 订单处理、任务分发 | 配置变更通知、日志广播、缓存刷新 |

### 顺序消息 vs 并发消息

| 对比维度 | 顺序消息 | 并发消息 |
|---------|---------|---------|
| 核心定位 | 保证消息按发送顺序被消费 | 不保证消息顺序，追求最大吞吐量 |
| 实现方式 | 同一业务 Key 的消息发往同一队列，消费端单线程消费 | 消息分散到多个队列，多线程并行消费 |
| 吞吐量 | 较低，受单线程消费限制 | 高，多线程并行处理 |
| 消息乱序风险 | 低，分区内严格有序 | 高，跨分区消息到达顺序不确定 |
| 消费失败影响 | 阻塞当前队列后续所有消息 | 仅影响当前消息，其他消息正常消费 |
| 适用场景 | 订单状态流转、账户流水处理、Binlog 同步 | 日志收集、用户行为埋点、通知推送 |
| 选择建议 | 仅在业务严格依赖消息顺序时使用；优先设计为幂等处理，不依赖顺序 | 大多数场景默认选择，配合幂等设计保证最终一致性 |

### 消息确认与可靠性机制对比

| 对比维度 | Kafka | RabbitMQ | RocketMQ |
|---------|-------|----------|----------|
| 生产者确认 | acks=0 / 1 / all，配合 min.insync.replicas 控制最小同步副本数 | Publisher Confirm（ack/nack）+ Publisher Return（无法路由退回） | 同步发送返回 SendStatus + 重试；异步发送回调 |
| 生产者失败处理 | retries + 幂等生产者（PID + Sequence Number）去重 | Confirm 回调中未确认消息落库重发；CorrelationData 精确定位 | 同步发送失败重试；本地消息表定时补偿 |
| Broker 端保障 | 多副本 ISR 同步，acks=all 时所有 ISR 副本落盘才确认 | Exchange/Queue/消息三重持久化（durable + deliveryMode=2）+ Quorum Queue | 同步刷盘（SYNC_FLUSH）+ 同步复制（SYNC_MASTER）或 Dledger |
| 消费者确认 | 提交位移（自动 / commitSync / commitAsync），位移存于 `__consumer_offsets` | 手动 ack（basicAck）/ nack（basicNack）/ reject，支持 requeue | 返回 CONSUME_SUCCESS / RECONSUME_LATER，失败按延迟等级重试 |
| 重复消费来源 | 位移提交失败重试、消费端宕机、未开幂等时的重试 | 未 ack 就宕机导致消息重入队、ack 丢失、手动重试 | 消费重试、位点重置、广播模式本地进度丢失 |
| 幂等实现 | 幂等生产者（仅单分区单会话）+ 事务 + 消费端业务幂等 | 业务唯一 ID + 数据库唯一索引 / Redis 去重 | 业务唯一 ID 去重（Redis 或数据库唯一索引） |
| 消息不丢的完整链路 | acks=all + min.insync.replicas≥2 + unclean.leader.election.enable=false + 手动提交位移 | Confirm + Return + 三重持久化 + Quorum Queue + 手动 ack + 死信兜底 | 同步发送 + 同步刷盘 + 同步复制/Dledger + 手动确认 + 死信兜底 |
| 可靠性代价 | 吞吐下降、ISR 不足时不可写 | 吞吐下降、Quorum Queue 性能低于经典队列 | 同步刷盘 + 同步复制时 TPS 显著降低 |

### 延迟消息实现方式对比

| 对比维度 | Kafka | RabbitMQ | RocketMQ |
|---------|-------|----------|----------|
| 原生支持 | 不支持 | 不支持 | 原生支持 |
| 实现方式 | 定时任务扫描数据库 + 延迟 Topic 暂存，或外部调度组件 | TTL + DLX 组合；rabbitmq-delayed-message-exchange 插件 | 延迟等级（messageDelayLevel），写入 SCHEDULE_TOPIC_XXXX |
| 延迟精度 | 取决于扫描间隔（通常秒级） | 受队头阻塞与 Broker 扫描影响，近似延迟 | 约 100ms 偏差 |
| 延迟档位 | 任意（自行实现） | 任意（插件）或按队列档位（TTL+DLX） | 18 个固定等级（1s 到 2h），不可自定义 |
| 主要坑点 | 数据库压力大、扫描有延迟、需自行保证幂等 | 消息级 TTL 队头阻塞；插件延迟消息存于 Mnesia，节点故障风险较高 | 延迟等级固定；大量延迟消息时扫描压力增大 |
| 可靠性 | 消息存于 Kafka，可持久化 | TTL+DLX 消息在普通队列可持久化；插件方式可靠性较弱 | 延迟消息同样写入 CommitLog，可刷盘与复制 |
| 适用场景 | 对精度要求不高、可接受秒级延迟 | 固定几档延迟、延迟时间较短 | 订单超时取消、定时提醒等金融电商场景 |
