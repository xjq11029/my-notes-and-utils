# 消息队列 - 概念对比速查

---

### RabbitMQ vs Kafka vs RocketMQ

| 对比维度 | RabbitMQ | Kafka | RocketMQ |
|---------|---------|-------|----------|
| 核心定位 | 基于 AMQP 协议的企业级消息中间件 | 分布式流处理平台，日志管道 | 阿里巴巴开源的金融级分布式消息中间件 |
| 消息模型 | 队列模型，消费后删除 | 日志模型，消费后保留，支持回溯 | 类似 Kafka 的 Topic + Queue 模型，消费后保留 |
| 吞吐量 | 万级 TPS | 百万级 TPS | 十万级 TPS |
| 延迟 | 微秒级（us） | 毫秒级（ms） | 毫秒级（ms） |
| 路由能力 | 四种 Exchange（Direct/Topic/Fanout/Headers），复杂路由 | 仅 Topic 级别，路由能力弱 | Topic + Tag 二级分类，支持 SQL 表达式过滤 |
| 消息顺序 | 单队列内有序 | 单 Partition 内有序 | 支持全局顺序和分区顺序两种模式 |
| 事务消息 | 不支持原生事务消息 | 支持事务生产者（幂等 + 事务） | 原生支持事务消息（半消息、回查机制） |
| 延迟消息 | 通过 TTL + DLX 组合或插件实现 | 不支持原生延迟消息 | 原生支持 18 个预设延迟等级 |
| 消息回溯 | 不支持，消费后删除 | 支持按 offset 回溯 | 支持按时间或 offset 回溯 |
| 协议 | AMQP 标准协议 | 自定义二进制协议 | 自定义协议，兼容 HTTP |
| 集群架构 | 镜像队列 / Quorum Queue | Broker + ZooKeeper / KRaft | NameServer + Broker（Master/Slave）+ Dledger（Raft） |
| 运维复杂度 | 较低 | 较高（依赖 ZooKeeper 或 KRaft） | 中等 |
| 社区生态 | 成熟，插件丰富 | 极丰富，大数据生态核心 | 较 Kafka 小，国内生态活跃 |
| 适用场景 | 复杂路由、低延迟 RPC、业务消息 | 大数据管道、流处理、日志收集 | 金融电商、分布式事务、订单状态流转 |
| 选择建议 | 需要复杂路由和微秒级延迟时选用 | 需要百万级吞吐和流处理时选用 | 需要事务消息、延迟消息等金融级特性时选用 |

### 点对点 vs 发布订阅

| 对比维度 | 点对点 | 发布订阅 |
|---------|-------|---------|
| 核心定位 | 一条消息只能被一个消费者消费 | 一条消息可被多个订阅者同时消费 |
| 消息投递方式 | 生产者发送到队列，消费者从队列拉取，消费后删除 | 生产者发布到 Topic，所有订阅者各自接收消息副本 |
| 消费者关系 | 多个消费者竞争消费，负载均衡 | 每个订阅者独立消费全量消息，互不影响 |
| 消息保留 | 消费后从队列删除 | 消息保留，各订阅者独立维护消费进度 |
| Kafka 实现 | 同一消费者组内多个消费者分摊 Partition 消费 | 不同消费者组各自独立消费全量 Topic 消息 |
| RabbitMQ 实现 | 多个消费者绑定同一队列竞争消费 | 使用 Fanout Exchange 广播到多个队列 |
| 典型场景 | 订单处理、任务分发 | 配置变更通知、日志广播、缓存刷新 |

### 顺序消息 vs 并发消息

| 对比维度 | 顺序消息 | 并发消息 |
|---------|---------|---------|
| 核心定位 | 保证消息按发送顺序被消费 | 不保证消息顺序，追求最大吞吐量 |
| 实现方式 | 同一业务 Key 的消息发往同一队列，消费端单线程消费 | 消息分散到多个队列，多线程并行消费 |
| 吞吐量 | 较低，受单线程消费限制 | 高，多线程并行处理 |
| 消息乱序风险 | 低，分区内严格有序 | 高，跨分区消息到达顺序不确定 |
| 消费失败影响 | 阻塞当前队列后续所有消息 | 仅影响当前消息，其他消息正常消费 |
| 适用场景 | 订单状态流转、账户流水处理、Binlog 同步 | 日志收集、用户行为埋点、通知推送 |
| 选择建议 | 仅在业务严格依赖消息顺序时使用；优先设计为幂等处理，不依赖顺序 | 大多数场景默认选择，配合幂等设计保证最终一致性 |
