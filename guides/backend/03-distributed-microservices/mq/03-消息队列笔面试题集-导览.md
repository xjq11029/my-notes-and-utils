### 1. ★ 以下关于消息队列作用的描述，错误的是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 消息队列在分布式系统中实现异步通信、解耦、削峰、分发的能力及其与数据库事务的边界 |
| 能做什么 | 削峰填谷缓冲高并发；系统解耦；异步处理；数据分发 |
| 怎么用 | `producer.send(topic, msg)` 异步投递 |
| 原理和工作流程 | 消息队列提供最终一致性而非强一致性，不能替代数据库 ACID 事务。核心作用为削峰填谷、系统解耦、异步处理、数据分发。银行转账等强一致场景仍需数据库事务保证 |
| 缺点 | 不能保证强一致性；不适用于 ACID 事务场景；引入额外复杂度 |

### 2. ★ Kafka 中最小的并行处理单位是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Partition 作为 Kafka 并行处理和水平扩展基本单位的定位 |
| 能做什么 | 提供并行读写单元；决定消费并行度上限 |
| 怎么用 | `--partitions N` 创建分区 |
| 原理和工作流程 | 每个 Partition 是有序不可变的消息序列，独立读写。Broker 是服务节点，Topic 是逻辑分类，Consumer Group 是消费者组，均非最小并行单位 |
| 缺点 | 消费者数超过分区数时多余空闲；分区数调整后无法缩容 |

### 3. ★ Kafka 中 ISR 的全称和含义是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | In-Sync Replicas，与 Leader 保持同步的副本集合 |
| 能做什么 | 标记同步副本；为 Leader 选举提供候选；配合 acks 保证可靠 |
| 怎么用 | `replica.lag.time.max.ms=30000` |
| 原理和工作流程 | Follower 在 replica.lag.time.max.ms 默认 30s 内追上 Leader 则属于 ISR，只有 ISR 副本才有资格被选为新 Leader |
| 缺点 | 30s 窗口仍有丢失风险；ISR 为空时可用性受影响 |

### 4. ★ Kafka 中 acks=all 的含义是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 所有 ISR 副本写入成功后生产者才收到确认的最高可靠性级别 |
| 能做什么 | 保证消息不丢失；配合 min.insync.replicas 提升可靠 |
| 怎么用 | `acks=all` |
| 原理和工作流程 | acks=0 不等待确认，acks=1 仅 Leader 确认，acks=all 或 -1 要求所有 ISR 副本写入成功。注意是所有 ISR 而非所有 Broker |
| 缺点 | 性能最低；ISR 副本数少时可靠性下降；增加延迟 |

### 5. ★ 以下哪项不是 Kafka 高吞吐的原因？（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Kafka 高吞吐六大设计：顺序写、零拷贝、Page Cache、批量压缩、分区并行、批量发送 |
| 能做什么 | 顺序写达 600MB/s；零拷贝减少 CPU 参与；分区并行水平扩展 |
| 怎么用 | `compression.type=lz4`；`linger.ms=10` |
| 原理和工作流程 | Kafka 消息存储在磁盘而非内存数据库，依赖顺序写和 Page Cache 实现高吞吐。内存数据库存储不属于其设计 |
| 缺点 | 顺序写受磁盘限制；批量发送增加延迟；压缩消耗 CPU |

### 6. ★★ RabbitMQ 中，将消息广播到所有绑定队列的 Exchange 类型是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Fanout Exchange 忽略 Routing Key 将消息广播到所有绑定队列的交换机类型 |
| 能做什么 | 配置变更通知；全局广播；消息复制到所有绑定队列 |
| 怎么用 | `ExchangeBuilder.fanout("broadcast")` |
| 原理和工作流程 | Fanout 忽略 RoutingKey，将消息复制投递到所有绑定的队列。Direct 精确匹配，Topic 通配符匹配，Headers 按属性匹配 |
| 缺点 | 无法选择性投递；广播增加消息量；无差别分发浪费带宽 |

### 7. ★★ RabbitMQ 中消息成为死信的条件不包括（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 消息成为死信的三种情况：TTL 过期、队列满被拒、消费拒绝且 requeue=false |
| 能做什么 | 识别死信场景；配置死信队列接收；实现延迟和重试 |
| 怎么用 | `basicNack(tag, false, false)` requeue=false |
| 原理和工作流程 | 消息成功消费后从队列删除不会成为死信。死信仅来自 TTL 过期、队列达最大长度被拒、消费者 basic.nack 或 basic.reject 且 requeue=false |
| 缺点 | 死信堆积需监控；TTL 队头阻塞；配置错误丢消息 |

### 8. ★★ 以下关于 Kafka 消费者组的描述，正确的是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 消费者组内分摊消费 Partition、组间独立消费的消费规则 |
| 能做什么 | 组内负载均衡；组间独立广播；一个消费者属一个组 |
| 怎么用 | `--group order-group` |
| 原理和工作流程 | 一个 Partition 只能被组内一个消费者消费，消费者数超过分区数则多余空闲。不同消费者组各自独立消费互不影响。一个消费者可订阅多 Topic 但属一个组 |
| 缺点 | 消费者超分区数空闲；无法组内多消费者共享分区 |

### 9. ★★ Kafka 的 Rebalance 触发条件不包括（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Rebalance 三种触发条件：成员变更、分区数变更、心跳超时 |
| 能做什么 | 识别触发条件；区分直接与间接触发；优化超时配置 |
| 怎么用 | `session.timeout.ms=45000` |
| 原理和工作流程 | 触发条件为成员变更、Partition 数量变更、心跳超时。消息积压本身不直接触发 Rebalance，但可能导致处理超时间接触发心跳超时 |
| 缺点 | Rebalance 期间停止消费；频繁触发影响吞吐 |

### 10. ★★ RabbitMQ 中实现延迟队列的常用方式是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | RabbitMQ 通过 TTL 加死信队列组合实现延迟消费的机制 |
| 能做什么 | TTL 过期进死信队列；插件 x-delay 指定延迟；实现订单超时取消 |
| 怎么用 | `.ttl(10000).deadLetterExchange("dlx.exchange")` |
| 原理和工作流程 | RabbitMQ 不原生支持延迟队列。常用方案是 TTL 加 DLX 组合：消息设置 TTL 过期后进入死信队列，消费者监听死信队列实现延迟。也可用 rabbitmq-delayed-message-exchange 插件 |
| 缺点 | TTL 队头阻塞；插件需额外安装；延迟精度受限 |

### 11. ★★★ 以下关于 Kafka 幂等生产者的描述，正确的是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | Broker 为生产者分配 PID，按 PID 加 Sequence Number 去重防重复的机制 |
| 能做什么 | 单分区内消息去重；必须配合 acks=all；跨会话无效 |
| 怎么用 | `enable.idempotence=true`；`acks=all` |
| 原理和工作流程 | Broker 为每个 Producer 分配 PID，消息携带 PID 加 Sequence Number，Broker 据此去重。幂等仅保证单分区内不重复，不能跨分区；开启幂等必须 acks=all；Producer 重启 PID 变化，跨会话无效 |
| 缺点 | 仅单分区单会话有效；跨分区跨会话需事务；增加 Broker 开销 |

### 12. ★★★ RabbitMQ 中，消息持久化需要设置的属性是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 通过设置 deliveryMode=2 将消息体持久化到磁盘的机制 |
| 能做什么 | 消息体写磁盘；配合队列和 Exchange 持久化；Broker 重启不丢 |
| 怎么用 | `deliveryMode=2` |
| 原理和工作流程 | 消息持久化通过 deliveryMode=2 实现。仅消息持久化不够，还需队列持久化 durable=true 和 Exchange 持久化，三者缺一不可。deliveryMode=1 为非持久化 |
| 缺点 | 三层缺一不可；磁盘写入增加延迟；异步刷盘断电仍可能丢 |

### 13. ★★★ 以下关于 Kafka 零拷贝的描述，错误的是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 sendfile 系统调用，数据从 Page Cache 直接 DMA 拷贝到网卡的机制 |
| 能做什么 | 减少 CPU 参与拷贝；跳过用户态；拷贝次数从 4 降至 2 |
| 怎么用 | sendfile 系统调用由 Broker 自动调用 |
| 原理和工作流程 | 零拷贝核心是数据不经过用户态，从 Page Cache 直接 DMA 拷贝到网卡。传统 I/O 需 4 次拷贝含 2 次 CPU 拷贝到用户态。零拷贝仅 2 次 DMA 拷贝，CPU 不参与 |
| 缺点 | 无法在用户态加工数据；依赖操作系统支持；仅适用于文件到网络的传输 |

### 14. ★★★ RabbitMQ 镜像队列中，读写操作发生在（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 镜像队列中所有读写操作都经过 Master 节点处理的机制 |
| 能做什么 | Master 处理发布消费确认；Mirror 仅同步数据；Master 故障 Mirror 提升 |
| 怎么用 | `ha-mode=all` |
| 原理和工作流程 | 镜像队列所有操作经 Master 处理，Mirror 节点仅做数据同步，不提供负载均衡只提供高可用。Master 故障时资历最老的 Mirror 提升为新 Master |
| 缺点 | 无负载均衡所有读写经 Master；同步降低性能；切换期间可能丢消息 |

### 15. ★★★ Kafka 3.0+ 版本中，替代 ZooKeeper 的元数据管理方案是（ ）

### 1. 简述消息队列在分布式系统中的三大核心作用，并举例说明

| 维度 | 内容 |
|------|------|
| 是什么 | 削峰填谷、系统解耦、异步处理三大核心作用 |
| 能做什么 | 缓冲高并发；生产消费解耦；非关键路径异步化 |
| 怎么用 | 秒杀请求入队；订单发消息通知下游；注册后异步发邮件 |
| 原理和工作流程 | 削峰填谷将瞬时高并发暂存队列后端按速率消费，如秒杀。系统解耦使生产消费不直接依赖，如订单通知库存物流。异步处理将非关键路径异步化提升响应，如注册后发邮件短信 |
| 缺点 | 引入复杂度；最终一致性非强一致；消息丢失重复需处理 |

### 2. 解释 Kafka 的 ISR 机制，并说明 Leader 选举如何保证数据不丢失

| 维度 | 内容 |
|------|------|
| 是什么 | ISR 同步副本集合，配合 unclean 选举禁止和 acks=all 保证选举不丢数据的机制 |
| 能做什么 | 标记同步副本；禁止非 ISR 选举；配合 min.insync.replicas |
| 怎么用 | `unclean.leader.election.enable=false`；`acks=all`；`min.insync.replicas=2` |
| 原理和工作流程 | ISR 是与 Leader 同步的副本集合，Follower 在 replica.lag.time.max.ms 默认 30s 内追上则属于 ISR。Leader 宕机时 Controller 从 ISR 选举新 Leader。unclean.leader.election.enable=false 禁止非 ISR 选举，配合 acks=all 和 min.insync.replicas>=2，新 Leader 必然拥有所有已提交消息 |
| 缺点 | ISR 为空且禁非 ISR 时不可用；30s 窗口仍有风险；min.insync.replicas 高则可用性降 |

### 3. 对比 Kafka 和 RabbitMQ 的核心区别，分别适用于什么场景？

| 维度 | 内容 |
|------|------|
| 是什么 | Kafka 与 RabbitMQ 在消息模型、吞吐量、路由、回溯、协议等维度的差异 |
| 能做什么 | Kafka 日志模型百万 TPS 支持回溯；RabbitMQ 队列模型万级 TPS 强路由 |
| 怎么用 | 日志流处理选 Kafka；复杂路由低延迟选 RabbitMQ |
| 原理和工作流程 | Kafka 基于日志消费后保留支持 offset 回溯，吞吐百万级，路由弱仅 Topic 级，自定义协议。RabbitMQ 基于队列消费后删除，吞吐万级，路由强四种 Exchange，AMQP 标准协议。Kafka 适合日志收集流处理大数据管道，RabbitMQ 适合业务消息复杂路由低延迟 RPC |
| 缺点 | Kafka 路由弱运维复杂；RabbitMQ 吞吐低不支持回溯 |

### 4. 简述 RabbitMQ 中消息确认机制（Confirm 和 Ack）的作用

| 维度 | 内容 |
|------|------|
| 是什么 | 生产者 Confirm 确认消息到达 Broker，消费者 Ack 确认处理完成的两层机制 |
| 能做什么 | Confirm 感知发送结果；Return 处理无法路由；手动 Ack 保证处理成功 |
| 怎么用 | `setConfirmCallback(...)`；`acknowledge-mode=manual` |
| 原理和工作流程 | Producer Confirm 中 Broker 对成功路由到持久化队列返回 ack，无法路由返回 nack 或触发 Return。Consumer Ack 中手动确认处理成功后调用 basic.ack，失败调用 basic.nack；自动确认投递即确认可能丢消息。生产环境建议手动确认 |
| 缺点 | 手动确认增加复杂度；自动确认有丢消息风险；nack 重入队可能死循环 |

### 5. 什么是死信队列？列举三个常见使用场景

| 维度 | 内容 |
|------|------|
| 是什么 | 接收无法正常消费消息的队列，用于重试、延迟、异常分析、削峰 |
| 能做什么 | 消息重试；延迟队列；异常分析；流量削峰 |
| 怎么用 | `.deadLetterExchange("dlx.exchange")` |
| 原理和工作流程 | 死信三种情况：TTL 过期、队列满被拒、消费拒绝 requeue=false。场景一消费失败消息进死信队列定时重投；场景二 TTL 加 DLX 实现延迟如订单超时；场景三收集异常消息分析原因；场景四队列满多余消息进死信队列异步处理 |
| 缺点 | 死信堆积需监控；TTL 队头阻塞；增加拓扑复杂度 |

### 6. 简述 Kafka Rebalance 的触发条件和优化措施

| 维度 | 内容 |
|------|------|
| 是什么 | 成员变更、分区变更、心跳超时触发 Rebalance 及其优化措施 |
| 能做什么 | 识别触发条件；增大超时减少误判；Cooperative Sticky 不停消费 |
| 怎么用 | `session.timeout.ms=30000`；`cooperative-sticky` |
| 原理和工作流程 | 触发条件为消费者成员变更、Partition 数量变更、心跳超时默认 45s。优化措施：增大 session.timeout.ms 和 heartbeat.interval.ms 减少网络抖动误判；使用 Cooperative Sticky 分阶段 Rebalance 不停止消费；避免频繁启停；处理逻辑不阻塞超过 max.poll.interval.ms |
| 缺点 | Rebalance 期间停止消费；超时过大延迟故障发现；长任务仍可能触发 |

### 7. 解释 Kafka 的 Exactly-Once 语义是如何实现的

| 维度 | 内容 |
|------|------|
| 是什么 | 通过幂等生产者和事务生产者两层保障实现的精确一次语义 |
| 能做什么 | 幂等单分区去重；事务跨分区原子写入；消费者 read_committed 隔离 |
| 怎么用 | `enable.idempotence=true`；`initTransactions()` |
| 原理和工作流程 | 幂等层 Broker 为 Producer 分配 PID，消息携带 PID 加递增 Sequence Number，Broker 维护最近 5 个序列号去重。事务层通过 initTransactions 到 commitTransaction 将消费 offset 提交和生产消息发送放入同一事务，消费者用 read_committed 隔离级别只消费已提交事务消息 |
| 缺点 | 幂等仅单分区单会话；事务增加延迟和复杂度；消费者端仍需业务幂等 |

### 8. 简述 RabbitMQ 延迟队列的实现原理和典型应用场景

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 TTL 加 DLX 组合或延迟插件实现消息延迟消费的机制 |
| 能做什么 | TTL 过期进死信队列；插件 x-delay 指定延迟；订单超时取消 |
| 怎么用 | `.ttl(30000).deadLetterExchange("dlx")`；`setDelay(30*60*1000)` |
| 原理和工作流程 | 方案一 TTL 加 DLX，消息设 TTL 过期后自动转发死信队列，消费者监听死信队列实现延迟。方案二安装 rabbitmq-delayed-message-exchange 插件，用 x-delayed-type 类型 Exchange，消息携带 x-delay 头部指定延迟毫秒。典型场景：订单超时取消、定时提醒、重试退避 |
| 缺点 | TTL 队头阻塞首条未过期则后续阻塞；插件需额外维护；延迟精度受限 |

| 维度 | 内容 |
|------|------|
| 是什么 | 给定业务场景设计消息队列方案的综合题型，本题集共 3 道 |
| 能做什么 | 考查订单超时取消、跨服务数据同步、日志收集分析系统的方案设计 |
| 怎么用 | 分析场景需求，选型 Kafka 或 RabbitMQ，设计架构和可靠性保障 |
| 原理和工作流程 | 场景设计题要求结合业务需求选择消息中间件，设计架构、消息格式、可靠性保障、监控告警。覆盖延迟队列、多消费者组同步、Kafka 缓冲加 Flink 流处理等典型架构。每题附完整设计方案和关键配置 |
| 缺点 | 答案开放主观评分；需综合多知识点；难以机器批改 |

### 1. 设计一个"订单超时取消"系统

| 维度 | 内容 |
|------|------|
| 是什么 | 利用延迟队列实现下单后 30 分钟未支付自动取消订单并释放库存的方案 |
| 能做什么 | RabbitMQ 延迟队列精确触发；Kafka 定时任务扫描；幂等取消和分布式锁 |
| 怎么用 | `setDelay(30*60*1000)` 发送 30 分钟延迟消息 |
| 原理和工作流程 | 方案一基于 RabbitMQ 延迟队列，下单创建订单扣减库存后发送 30 分钟延迟消息，到期消费者查询订单状态，未支付则取消恢复库存。方案二基于 Kafka 加定时任务，每分钟扫描超时未支付订单批量取消。RabbitMQ 方案精确但需维护延迟队列，Kafka 方案简单但有扫描延迟和数据库压力。需保证取消操作幂等，多消费者加分布式锁 |
| 缺点 | 延迟消息积压需监控；取消需幂等；海量订单延迟队列压力大；Kafka 方案有扫描延迟 |

### 2. 设计一个"跨服务数据同步"方案

| 维度 | 内容 |
|------|------|
| 是什么 | 用户信息变更通过 Kafka 同步到订单、物流、营销多个下游服务的方案 |
| 能做什么 | Kafka Topic 多消费者组独立消费；版本号防乱序；幂等去重；死信兜底 |
| 怎么用 | `user-change-topic` 加 order-sync、logistics-sync、marketing-sync 三个消费者组 |
| 原理和工作流程 | 用户服务将变更消息发送到 Kafka Topic，订单、物流、营销服务各自作为独立消费者组消费全量消息。消息含 eventType、changedFields、version 等字段。可靠性用 acks=all 和手动提交 offset，消费者本地记录已处理 eventId 幂等。一致性用版本号防乱序，只处理 version 大于本地的消息，失败进死信队列。监控各消费者组 Lag 和同步延迟，定期对账 |
| 缺点 | 多消费者组增加资源；版本号需业务维护；死信需人工介入；最终一致性有延迟 |

### 3. 设计一个"日志收集与分析"系统

| 维度 | 内容 |
|------|------|
| 是什么 | 日均 10 亿条日志的实时收集存储分析系统，采用 Filebeat-Kafka-Flink-ES 架构 |
| 能做什么 | Filebeat 采集；Kafka 缓冲削峰；Flink 实时处理；ES HBase HDFS 分级存储 |
| 怎么用 | `partitions=50`；`compression.type=lz4`；`retention.ms=604800000` |
| 原理和工作流程 | 采集层 Filebeat 部署各服务器轻量采集，日志统一 JSON 按服务路由不同 Topic。缓冲层 Kafka 按日志类型建 Topic，分区 30-50，保留 7 天，LZ4 压缩。处理层 Flink 实时聚合、异常检测、数据清洗。存储层热数据 ES 全文检索、温数据 HBase 范围查询、冷数据 HDFS 归档。可视化 Grafana 大盘和 Kibana 检索，钉钉短信告警 |
| 缺点 | 架构复杂组件多；分级存储运维成本高；Flink 作业需调优；海量日志存储成本高 |
