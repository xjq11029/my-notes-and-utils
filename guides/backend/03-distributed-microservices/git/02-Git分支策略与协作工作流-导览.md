## 一、分支管理基础

### 1.1 什么是分支

| 维度 | 内容 |
|------|------|
| 是什么 | 指向某个提交对象的可变指针，Git 借此实现并行开发互不干扰的机制。 |
| 能做什么 | 隔离不同功能的开发；支持任意数量并行分支；创建删除几乎零成本。 |
| 怎么用 | `git branch feature`；`git switch feature` |
| 原理和工作流程 | 分支在 .git/refs/heads 目录下以文件形式存在，内容为 40 字节 SHA-1 哈希指向分支最新提交。创建分支仅写入该文件不复制项目内容，故极轻量。HEAD 指针指向当前分支，提交时当前分支指针自动前移，其他分支不动，实现多线并行演进。 |
| 缺点 | 分支过多时提交图复杂难读；长期分叉分支合并时冲突概率高。 |

### 1.2 HEAD 指针与分支切换

| 维度 | 内容 |
|------|------|
| 是什么 | 指向当前所在分支（或具体提交）的特殊指针，是所有分支操作的基础。 |
| 能做什么 | 标识当前工作分支；切换分支时更新指向；支持游离头指针状态直接指向提交。 |
| 怎么用 | `cat .git/HEAD` 查看指向；`git checkout <branch>` 切换 |
| 原理和工作流程 | HEAD 文件内容通常为 ref: refs/heads/<branch>，指向当前分支引用。切换分支时 Git 更新 HEAD 指向新分支，并将该分支指向的提交快照还原到工作区与暂存区。游离头指针（detached HEAD）状态下 HEAD 直接指向某个 commit 而非分支引用，此时提交不属于任何分支需手动创建分支保存。 |
| 缺点 | 游离头指针状态下提交若未及时建分支易被 gc 丢失；频繁切换分支需反复更新工作区有性能开销。 |

### 1.3 branch 命令详解

| 维度 | 内容 |
|------|------|
| 是什么 | 用于查看、创建、删除、重命名分支的多功能命令。 |
| 能做什么 | 列出本地/远程分支及合并状态；创建与强制删除分支；重命名分支。 |
| 怎么用 | `git branch -a`；`git branch feature`；`git branch -d feature`；`git branch -m new-name` |
| 原理和工作流程 | 无参数遍历 refs/heads 列出本地分支并用 * 标记当前分支。-r 遍历 refs/remotes，-a 合并两者。-v 附加最后提交信息。--merged/--no-merged 通过比对分支可达性过滤。-d 安全删除仅允许删已合并分支，-D 强制删除不论合并状态。重命名 -m 修改 refs 文件名并更新配置。 |
| 缺点 | -d 防误删但对未合并分支需改用 -D 增加风险；远程分支删除需另用 push --delete。 |

### 1.4 checkout 命令详解

| 维度 | 内容 |
|------|------|
| 是什么 | 承担切换分支、恢复文件、创建分支三项职责的多功能命令。 |
| 能做什么 | 切换到指定分支或提交；基于分支或远程分支创建新分支；丢弃工作区文件修改。 |
| 怎么用 | `git checkout main`；`git checkout -b feature`；`git checkout -- <file>` |
| 原理和工作流程 | 切换分支时更新 HEAD 指向并还原目标提交快照到工作区。-b 创建分支并立即切换。基于远程分支创建时建立本地分支与远程跟踪分支的关联。恢复文件用指定提交或暂存区版本覆盖工作区文件。Git 2.23 起将切换与恢复职责拆分为 switch 与 restore，语义更清晰。 |
| 缺点 | 单命令承担过多职责易误用（如 checkout -- 误删修改）；新项目建议改用 switch/restore 降低歧义。 |

### 1.5 merge 的三种模式

> 本节为模式分组，下列各子小节分别对应一张五维表格。

#### 模式一：Fast-Forward Merge（快进合并）

| 维度 | 内容 |
|------|------|
| 是什么 | 被合并分支是当前分支直接后继时，仅前移当前分支指针不产生合并提交的合并方式。 |
| 能做什么 | 快速合并线性历史；不引入额外提交节点；可通过 --no-ff 强制保留分支轨迹。 |
| 怎么用 | `git merge feature`；`git merge --no-ff feature` |
| 原理和工作流程 | 当目标分支的当前提交是当前分支的直接祖先时，Git 将当前分支指针直接前移到目标分支提交，无需创建新提交。--no-ff 即使可快进也强制生成合并提交节点，保留功能分支的历史边界便于追溯与回滚。快进合并不保留分支拓扑信息。 |
| 缺点 | 快进合并丢失分支存在痕迹，难以追溯哪些提交属于哪个功能分支；不适合需要分支隔离审计的场景。 |

#### 模式二：Three-Way Merge（三方合并）

| 维度 | 内容 |
|------|------|
| 是什么 | 两分支各有新提交时，基于共同祖先进行三方比对生成合并提交的合并方式。 |
| 能做什么 | 合并分叉分支；创建含两个父提交的合并提交；保留双方分支历史。 |
| 怎么用 | `git merge feature-branch`（分叉时自动触发） |
| 原理和工作流程 | Git 找到两分支的共同祖先提交（merge base），将当前分支、目标分支、共同祖先三方比对，对非冲突区域自动合并，对同一区域的不同修改标记冲突。合并成功后创建新的合并提交，该提交有两个父提交分别指向两分支的原顶端，历史图呈现分叉再汇合。 |
| 缺点 | 同一区域并行修改会产生冲突需手动解决；合并提交使历史图出现分叉节点增加阅读复杂度。 |

#### 模式三：Squash Merge（压缩合并）

| 维度 | 内容 |
|------|------|
| 是什么 | 将特性分支全部提交压缩为单个提交应用到当前分支的合并方式。 |
| 能做什么 | 整理杂乱提交历史；将多个小提交合并为有意义的一条记录；不保留原分支提交轨迹。 |
| 怎么用 | `git merge --squash feature`；`git commit -m "feat: ..."` |
| 原理和工作流程 | --squash 将目标分支相对当前分支的全部变更累加到暂存区，但不创建合并提交也不移动分支指针记录合并关系，需手动 git commit 生成单个提交。原分支的多个提交被压缩为一条，不保留原提交哈希与分支拓扑，历史更整洁但丢失细粒度修改轨迹。 |
| 缺点 | 丢失原始提交历史与分支轨迹，无法追溯每步修改；不创建合并提交导致后续合并可能重复引入变更。 |

## 二、分支高阶操作

### 2.1 rebase 黄金法则

> 本节为知识点分组，下列各子小节分别对应一张五维表格。

#### rebase 原理

| 维度 | 内容 |
|------|------|
| 是什么 | 将当前分支提交逐个重放到目标分支最新提交之上的历史重写操作。 |
| 能做什么 | 使提交历史线性化；将分支基点更新到目标分支最新；生成全新哈希的提交。 |
| 怎么用 | `git rebase main`（在 feature 分支执行） |
| 原理和工作流程 | rebase 找到当前分支与目标分支的共同祖先，将当前分支上自祖先以来的提交暂存，把当前分支指针指向目标分支最新提交，再将暂存提交逐个重新应用生成新哈希的提交（如 E'、F'、G'）。原提交 E、F、G 在 rebase 完成后被标记为不可达，最终由垃圾回收清除。 |
| 缺点 | 重写提交哈希破坏原历史；多个提交可能需逐个解决冲突；对已推送提交使用危害协作。 |

#### rebase vs merge

| 维度 | 内容 |
|------|------|
| 是什么 | rebase 与 merge 两种整合分支方式在历史记录、冲突处理、可追溯性上的对比。 |
| 能做什么 | rebase 产出线性历史；merge 保留分叉历史；两者各有适用场景。 |
| 怎么用 | 线性历史：`git rebase main`；保留历史：`git merge feature` |
| 原理和工作流程 | merge 创建合并提交保留完整分支分叉历史，冲突一次性解决，原提交 SHA 不变，可整体回滚。rebase 重写提交使历史线性整洁，但可能需逐个提交解决冲突，提交 SHA 全部改变，分支信息丢失，回滚需逐个处理。merge 重真实可追溯，rebase 重整洁。 |
| 缺点 | rebase 丢失分支轨迹且回滚难；merge 产生合并提交使历史图分叉杂乱。两者各有取舍无绝对优劣。 |

#### rebase 黄金法则

| 维度 | 内容 |
|------|------|
| 是什么 | 永远不对已推送到公共仓库的提交执行 rebase 的核心约束。 |
| 能做什么 | 防止历史重写破坏协作者工作基础；保障公共分支历史稳定；必要时用 --force-with-lease 替代 --force。 |
| 怎么用 | 仅对本地未推送提交 rebase；需强制推送时用 `git push --force-with-lease` |
| 原理和工作流程 | rebase 重写提交生成新 SHA-1，若他人已基于原提交开发，rebase 后其工作基础被破坏，推送时 Git 因历史分叉拒绝。强制推送覆盖远程历史会导致协作者本地仓库与远程严重冲突。正确做法是只对本地私有提交 rebase，公共分支改用 revert 或 merge。确需强制推送时用 --force-with-lease 检测远程是否有他人新提交。 |
| 缺点 | 约束依赖团队自觉，缺乏工具强制；--force-with-lease 在复杂多远程场景下仍有误判可能。 |

#### 交互式 rebase

| 维度 | 内容 |
|------|------|
| 是什么 | 提供逐提交编辑界面的 rebase 模式，可对提交执行保留、改写、合并、删除、重排等操作。 |
| 能做什么 | 合并多个小提交为有意义提交；修改历史提交信息；删除或重排提交顺序。 |
| 怎么用 | `git rebase -i HEAD~3`；编辑器中用 pick/squash/reword/edit/drop |
| 原理和工作流程 | -i 启动后打开编辑器列出指定范围内的提交，每行前缀命令决定操作：pick 保留、reword 改信息、edit 暂停修改内容、squash 合并到前一提交保留信息、fixup 合并并丢弃信息、drop 删除、调整行顺序重排。保存后 Git 按指令逐个处理生成新提交序列，实现历史整理。 |
| 缺点 | 同样受黄金法则约束不可用于公共提交；操作复杂误删提交需 reflog 恢复。 |

### 2.2 cherry-pick 操作

| 维度 | 内容 |
|------|------|
| 是什么 | 将指定提交的变更应用到当前分支而不合并整个分支的命令。 |
| 能做什么 | 跨分支移植单个或多个提交；选择性合并部分提交；误操作后转移提交到正确分支。 |
| 怎么用 | `git cherry-pick <hash>`；`git cherry-pick <start>..<end>`；`git cherry-pick --no-commit <hash>` |
| 原理和工作流程 | 读取目标提交相对于其父提交的 diff，将变更以新提交形式重新应用到当前分支顶端，生成新哈希。支持区间与多提交批量应用。--no-commit 仅将变更放入暂存区不自动提交。发生冲突时解决后 --continue 继续，--abort 放弃。典型场景包括跨分支移植 hotfix、选择性合并、补丁迁移。 |
| 缺点 | 生成新提交哈希不保留原分支关系；批量操作时相似冲突需反复解决（可配合 rerere）；过度使用导致历史碎片化。 |

## 三、冲突解决

### 3.1 冲突产生的原因

| 维度 | 内容 |
|------|------|
| 是什么 | Git 无法自动合并两分支对同一文件同一区域的不同修改时触发的状态。 |
| 能做什么 | 识别并行修改、文件删除、重命名、二进制修改等冲突类型；提示冲突文件供手动解决。 |
| 怎么用 | 合并后 `git status` 查看 both modified 文件 |
| 原理和工作流程 | Git 合并时对每文件区域做三方比对，当两分支对同一区域有不同修改且无法自动调和时标记冲突。常见场景：并行修改同一文件同一行、一分支修改另一分支删除同一文件、重命名与修改冲突、二进制文件无法行级合并、rebase 逐提交应用时多次遇冲突。冲突文件被插入冲突标记等待人工裁决。 |
| 缺点 | 冲突解决依赖人工判断易引入错误；二进制文件冲突无法自动合并只能二选一。 |

### 3.2 冲突标记解读

| 维度 | 内容 |
|------|------|
| 是什么 | Git 在冲突文件中插入的用于标识对立修改区域的特殊标记。 |
| 能做什么 | 划分当前分支与被合并分支的修改内容；指引手动编辑保留正确代码。 |
| 怎么用 | 查找 `<<<<<<< HEAD`、`=======`、`>>>>>>> branch` 标记 |
| 原理和工作流程 | 冲突区域以三组标记界定：<<<<<<< HEAD 到 ======= 之间为当前分支内容，======= 到 >>>>>>> feature-branch 之间为被合并分支内容。解决冲突即人工决定保留哪部分或组合两部分修改，随后删除全部冲突标记。标记保留在文件中直至手动编辑消除。 |
| 缺点 | 嵌套冲突或多区域冲突时标记密集难以辨识；标记残留会导致语法错误需仔细检查。 |

### 3.3 冲突解决流程

| 维度 | 内容 |
|------|------|
| 是什么 | 从合并触发冲突到完成合并提交的标准操作步骤。 |
| 能做什么 | 定位冲突文件；手动编辑消除冲突；标记已解决并完成合并；必要时放弃合并。 |
| 怎么用 | `git merge <branch>` → 编辑文件 → `git add <file>` → `git commit`；放弃：`git merge --abort` |
| 原理和工作流程 | 合并触发冲突后 Git 在冲突文件插入标记并将合并状态记录于 .git/MERGE_HEAD。git status 列出 both modified 文件，git diff 显示冲突详情。手动编辑删除标记保留正确代码后 git add 将文件标记为已解决。全部解决后 git commit 创建合并提交完成合并。--abort 清除合并状态恢复到合并前。 |
| 缺点 | 流程步骤多易遗漏 add 导致提交不完整；大型冲突集解决耗时且易引入新问题。 |

### 3.4 可视化冲突解决工具

| 维度 | 内容 |
|------|------|
| 是什么 | 辅助人工解决合并冲突的图形化或三栏对比工具集合。 |
| 能做什么 | 高亮冲突区域；提供保留当前/传入/双方的一键操作；三栏对比逐行裁决。 |
| 怎么用 | VS Code 内置按钮；IDEA 三栏视图；`git mergetool` 调用外部工具 |
| 原理和工作流程 | VS Code 解析冲突标记高亮区域并提供 Accept Current/Incoming/Both/Compare 四按钮。IntelliJ IDEA 提供左（本地）、中（合并结果）、右（远程）三栏视图支持逐行选择与语法高亮。git mergetool 读取配置调用 Beyond Compare、Meld 等外部工具。GitKraken 等 GUI 客户端内置冲突解决界面。 |
| 缺点 | 工具依赖图形环境，服务器端无界面时不可用；不同工具操作习惯差异增加切换成本。 |

### 3.5 git rerere：记录冲突解决方案

| 维度 | 内容 |
|------|------|
| 是什么 | 记录已解决的冲突方案并在相同冲突再现时自动应用的 Git 功能。 |
| 能做什么 | 自动复用历史冲突解决方案；减少重复手工解决；支持测试性合并预记录方案。 |
| 怎么用 | `git config --global rerere.enabled true`；`git rerere status`；`git rerere diff` |
| 原理和工作流程 | 启用后冲突发生时 rerere 记录冲突前文件状态，解决后记录方案。下次相同冲突再现时自动应用方案并标记为已解决（仍需 git add）。适用于长期特性分支频繁 rebase、批量 cherry-pick、测试性合并预记录等场景。测试性合并时解决冲突记录方案后 --abort 回退，正式合并时自动应用。 |
| 缺点 | 方案匹配基于冲突文本指纹，语义不同但文本相同的冲突可能误应用；记录累积需定期清理。 |

## 四、分支策略对比

### 4.1 GitFlow

| 维度 | 内容 |
|------|------|
| 是什么 | Vincent Driessen 于 2010 年提出的经典分支模型，定义 main、develop、feature、release、hotfix 五类分支。 |
| 能做什么 | 支持固定版本发布周期；多版本并行维护；严格的发布与热修复流程控制。 |
| 怎么用 | feature 从 develop 拉取合并回 develop；release 从 develop 拉取合并到 main+develop；hotfix 从 main 拉取合并到 main+develop |
| 原理和工作流程 | main 存放生产稳定代码每个提交对应发布版本；develop 是开发集成分支；feature 分支开发新功能完成后合并回 develop；release 分支做发布前测试与版本号更新完成后合并到 main 打 tag 与 develop；hotfix 从 main 拉取修复线上紧急问题后合并到 main 打 tag 与 develop。五类分支职责清晰流程严格。 |
| 缺点 | 分支模型复杂学习成本高；合并流程繁琐影响交付速度；develop 易成瓶颈；对持续部署项目过于重量级。 |

### 4.2 GitHub Flow

| 维度 | 内容 |
|------|------|
| 是什么 | GitHub 倡导的极简分支模型，仅 main 与功能分支两类，适合持续部署。 |
| 能做什么 | main 始终可部署；功能分支开发经 PR 审查后合并并立即部署。 |
| 怎么用 | 从 main 建分支 → 推送 → 发 PR → 审查通过合并 → 立即部署 |
| 原理和工作流程 | 核心原则是 main 始终保持可部署状态，任何新工作从 main 创建描述性分支，定期推送远程，通过 Pull Request 发起讨论与代码审查，审查通过合并到 main 后立即部署。流程极简无 release 缓冲阶段，依赖完善自动化测试与审查保障质量。 |
| 缺点 | 不支持多版本并行维护；缺少发布缓冲阶段；依赖完善质量保障体系；不适合固定发布周期项目。 |

### 4.3 Trunk-Based Development（主干开发）

| 维度 | 内容 |
|------|------|
| 是什么 | 所有开发者直接在主干上小批量高频提交的最激进分支模型。 |
| 能做什么 | 极致持续集成；分支生命周期极短（通常不超 1 天）；通过功能开关控制未完成功能可见性。 |
| 怎么用 | 拉取最新 → 直接在 main 小批量修改 → 全量测试 → 立即提交推送；未完成功能用 Feature Flag 隐藏 |
| 原理和工作流程 | 所有开发者直接在主干工作，分支生命周期极短或不存在。未完成功能通过 Feature Flag 隐藏而非分支隔离，配合 Branch by Abstraction 逐步替换实现、暗发布与金丝雀发布控制风险。要求极高的自动化测试覆盖率与持续代码审查，以小粒度高频提交避免大规模合并冲突。 |
| 缺点 | 对团队工程能力要求极高；需完善 CI/CD 与自动化测试基础设施；功能开关管理复杂；不适合大型团队与外包协作。 |

### 4.4 三种策略对比选型

| 维度 | 内容 |
|------|------|
| 是什么 | GitFlow、GitHub Flow、Trunk-Based 三种分支策略在复杂度、发布周期、团队规模等维度的对比与选型指引。 |
| 能做什么 | 依据项目特征匹配适用策略；评估分支数量、回滚能力、多版本维护需求。 |
| 怎么用 | 固定发布周期选 GitFlow；Web/SaaS 中等团队选 GitHub Flow；精英小团队 CI/CD 成熟选 Trunk-Based |
| 原理和工作流程 | GitFlow 复杂度高分支多适合固定周期企业软件与多版本维护；GitHub Flow 复杂度低仅两类分支适合持续部署 Web 应用；Trunk-Based 复杂度中分支极少适合追求极致交付速度且自动化测试覆盖率高的小团队。选型依据发布周期、团队规模、CI/CD 成熟度、多版本维护需求综合决策。 |
| 缺点 | 选型决策受多重因素影响边界模糊，混合实践中易产生流程冲突；无一种策略适用所有场景。 |

## 五、协作工作流

### 5.1 Pull Request / Merge Request 流程

| 维度 | 内容 |
|------|------|
| 是什么 | 代码托管平台提供的以分支合并为载体的代码审查与协作机制，非 Git 原生概念。 |
| 能做什么 | 发起合并讨论；触发 CI/CD 流水线；承载代码审查与知识共享；关联 Issue 追踪。 |
| 怎么用 | 建分支 → 推送 → 创建 PR → CI 通过 → 审查 → 合并 → 删分支 |
| 原理和工作流程 | 完整流程为 Fork/Clone 仓库、创建功能分支、开发提交推送、创建 Pull Request、触发 CI/CD 流水线、代码审查、依审查意见修改、审查通过合并到目标分支、删除功能分支。最佳实践包括单一职责、描述清晰、关联 Issue、Conventional Commits 规范提交信息、定期 rebase 目标分支、自测通过后请求审查。 |
| 缺点 | PR 堆积未及时审查形成瓶颈；大型 PR 审查质量下降；流程开销对小改动略显繁琐。 |

### 5.2 Code Review 规范

| 维度 | 内容 |
|------|------|
| 是什么 | 保障代码质量与促进团队知识共享的代码审查标准与评论规范。 |
| 能做什么 | 审查设计合理性、功能完整性、复杂度、测试覆盖、命名、安全与性能；规范评论三要素。 |
| 怎么用 | 审查关注设计/功能/复杂度/测试/命名/安全/性能；评论含问题+原因+建议 |
| 原理和工作流程 | 审查者从设计是否合理、功能是否考虑边界、复杂度是否可简化、测试是否充分、命名是否达意、注释是否解释为何、风格是否合规、是否存在安全漏洞与性能问题等维度检查。评论规范要求指出问题加说明原因加给出建议三要素。非紧急 PR 24 小时内反馈，单次审查不超 60 分钟不超 400 行以防疲劳降质。 |
| 缺点 | 审查质量依赖审查者水平与投入；主观维度（设计、命名）易引发争论；审查延迟阻塞交付。 |

### 5.3 git stash：暂存工作进度

| 维度 | 内容 |
|------|------|
| 是什么 | 将工作区与暂存区修改暂存起来使工作区恢复干净状态的命令。 |
| 能做什么 | 暂存已跟踪文件修改；含未跟踪文件暂存；查看恢复删除暂存；从暂存创建分支。 |
| 怎么用 | `git stash push -m "WIP"`；`git stash list`；`git stash pop`；`git stash apply stash@{1}` |
| 原理和工作流程 | stash 将工作区与暂存区当前修改保存为栈式暂存记录并恢复工作区到 HEAD 状态。默认仅暂存已跟踪文件，-u 含未跟踪文件。push -m 附加描述信息便于辨识。list 列出全部暂存，pop 恢复最近暂存并删除记录，apply 恢复不删除。drop 删除指定暂存，clear 清空全部。stash branch 从暂存创建新分支便于分离开发。 |
| 缺点 | stash 为本地记录不随推送同步；pop 遇冲突不自动删除需手动 drop；长时间 stash 易遗忘应改用临时分支。 |

### 5.4 git bisect：二分法定位问题提交

| 维度 | 内容 |
|------|------|
| 是什么 | 使用二分查找在大量提交中快速定位引入 bug 的具体提交的命令。 |
| 能做什么 | 手动标记 good/bad 逐步缩小范围；自动化运行测试脚本判断；以对数级测试次数定位问题提交。 |
| 怎么用 | `git bisect start`；`git bisect bad`；`git bisect good <hash>`；`git bisect run <test-cmd>` |
| 原理和工作流程 | 启动后标记一个坏版本与一个好版本，Git 自动切换到区间中间提交供测试，据测试结果标记 good 或 bad，Git 再取新区间中点，重复直至定位首个坏提交。二分法使 N 个提交仅需约 log2(N) 次测试。自动化模式通过 bisect run 执行脚本，退出码 0 为 good、1-127 为 bad、125 为 skip 跳过。结束后 reset 回原分支。 |
| 缺点 | 依赖明确的 good 与 bad 版本边界；中间提交若不可编译需 skip 增加测试次数；自动化需可重复的测试脚本。 |
