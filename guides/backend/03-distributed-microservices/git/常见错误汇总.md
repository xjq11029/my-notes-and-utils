# Git - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| `git reset --hard` 丢了代码，工作区修改找不到 | `--hard` 会覆盖工作区，未提交的修改直接丢掉 | 任何 reset --hard 之前先把修改 commit 或 stash 保存；错了立刻看 git reflog | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 把不该提交的大文件或敏感信息提交了（node_modules、密码、密钥） | 没写 `.gitignore`，或者一开始没注意 | 提前写好 `.gitignore`；已经提交了用 `git filter-branch` 或 `bfg` 从历史移除 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 直接在 `master` 分支开发并直接推送，影响他人 | 没有分支开发意识 | 功能开发新建 feature 分支，测试完再合并到 master | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 提交信息写得乱七八糟，git log 看不懂每次改了什么 | 不重视提交信息 | 提交信息第一行一句话说明做了什么，改动大的话空一行写详情；用祈使语气，现在时态 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| pull 不用 rebase，历史一堆合并提交，log 历史很乱 | 默认 pull 是 merge，每次拉都产生合并提交 | 配置 `git config --global pull.rebase true`，默认 pull --rebase 保持线性 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 推远程失败提示快进失败（error: failed to push some refs） | 远程有本地没有的提交，需要先 pull | 先 `git pull --rebase` 把远程更新拉下来，解决冲突再推 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 解决完 rebase 冲突不知道下一步，卡住了 | rebase 流程是一步步来的 | 解决完冲突后 `git add`，然后 `git rebase --continue`，要放弃就 `git rebase --abort` | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 本地分支推远程写错了远程分支名，远程多出来一个错的分支 | 不小心推错了 | 删除远程分支：`git push origin --delete wrong-branch` | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 误删了分支，分支上的代码也找不到了 | 以为删了就没了 | Git 不会立刻删除提交，只要没 gc，用 `git reflog` 找最后一次提交恢复 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| tag 打错了想改，已经把错误 tag 推远程了 | 打错了版本号 | 本地删：`git tag -d v1.0.0`，远程删：`git push origin --delete v1.0.0`，然后重新打正确的再推 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| `reset --soft/mixed/hard` 三种模式用错，暂存区或工作区内容意外丢失 | 不清楚三种模式的差异：`--soft` 只移动 HEAD（保留暂存区和工作区）；`--mixed`（默认）重置暂存区但保留工作区；`--hard` 三处全部重置 | 只想改提交信息/补文件用 `--soft`；想重新挑文件暂存用 `--mixed`；`--hard` 仅在确认工作区改动可丢弃时使用 | [Git核心概念与常用命令导览](./01-Git核心概念与常用命令-导览.md) |
| 对已经推送到公共仓库的提交执行 `rebase`，同事推送时被拒、历史分叉 | rebase 会重写历史，生成全新的 SHA-1，他人基于原提交的工作基础被破坏 | 遵守 rebase 黄金法则：只对本地尚未推送的提交做 rebase；拉取远程更新用 `git rebase origin/main` | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 用 `git push --force` 强推，把同事的提交直接覆盖掉 | `--force` 不做任何检查，无条件覆盖远程分支历史 | 改用 `git push --force-with-lease`，它会在远程被他人修改时拒绝推送，避免误覆盖 | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 用 `reset --hard` 撤销已经推送的公共提交，导致他人历史错乱 | reset 改写历史，已推送的提交被"抹掉"，协作者本地历史与远程分叉 | 公共提交用 `git revert` 生成一个反向提交来撤销，不改写历史；`reset --hard` 只限本地私有分支 | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
| 处于 `detached HEAD` 状态时提交，切换分支后提交"消失"了 | 游离头指针下提交不属于任何分支，切走后没有分支引用指向它，只能靠 reflog 找回 | 提交前先固定：`git switch -c 新分支名`，或提交后立刻 `git branch 新分支名 <commit>` | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| `git stash` 后新增的未跟踪文件仍留在工作区，或没被一起暂存 | `git stash` 默认只暂存已跟踪文件的修改，不含未跟踪文件 | 需要连未跟踪文件一起暂存时用 `git stash -u`；查看列表用 `git stash list` | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
| 以为 `git commit -a` 能提交所有改动，结果新增文件没进提交 | `git commit -a` 只对**已跟踪文件**生效，新建文件仍是未跟踪状态 | 新文件先 `git add` 再提交；`-a` 只用于跳过"已跟踪文件的暂存"这一步 | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
| 提交后才发现漏了文件，又提了一个 "fix" 提交，历史变脏 | 不知道可以修改最近一次提交 | `git add 遗漏文件` 后执行 `git commit --amend`（不想改提交信息可加 `--no-edit`），不产生新提交 | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
| 误用 `git revert HEAD~2` 想"恢复到两个提交前"，结果行为不符合预期 | revert 是创建反向提交来撤销指定提交，不是把代码回退到某个历史状态 | 撤销已推送的某个提交用 `revert`；要回到某个历史状态用 `reset`（本地）或 `checkout <commit>` 查看 | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
| 合并冲突解决完，代码里还残留 `<<<<<<<`、`=======`、`>>>>>>>` 标记 | 只删了冲突内容没删标记；或标记在文件中间不易发现 | 解决后全局搜索冲突标记确认清空，再 `git add <文件>` 标记已解决，最后 `git commit` 完成合并 | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 每次拉取和合并都产生合并提交，`git log` 历史一团乱 | 默认 `pull` 走 merge，`--no-ff` 又强制生成合并提交，主干被合并节点淹没 | 配置 `git config --global pull.rebase true` 让 pull 走 rebase；需要保留分支轨迹时才显式 `merge --no-ff` | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| hotfix 直接在 `main` 上改，修复后忘记同步回 `develop`，开发分支缺失修复 | 没有从 main 拉 hotfix 分支，也没做双线合并 | hotfix 必须从 main 拉取，修复后同时合并到 main（并打 tag）和 develop | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 用 `git branch -D` 强删分支，未合并的提交被"删掉" | `-D` 不做合并检查直接删除；`-d` 才在未合并时给出警告 | 删分支优先用 `git branch -d`；确需强删前先确认提交已合并，误删后用 `git reflog` 找回哈希 | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 定位"哪个提交引入了 bug"靠人工逐个 checkout，耗时且易漏 | 不知道 bisect 二分定位能力 | 用 `git bisect start` + `bad`/`good` 二分，或 `git bisect run <测试命令>` 全自动定位，最后 `git bisect reset` | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| `cherry-pick` 被当成"合并整个分支"用，重复应用同一提交导致冲突不断 | cherry-pick 只把指定提交的改动应用到当前分支，会产生新 SHA，与后续 merge 叠加时易冲突 | 只需要个别提交时用 cherry-pick；需要整个分支的改动时用 `merge` 或 `rebase` | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 同一个冲突反复出现，每次都要手工重新解决一遍 | 未启用 rerere（reuse recorded resolution）记录并复用冲突解决方案 | 执行 `git config --global rerere.enabled true` 开启记录，相同冲突再次出现时自动应用已记录的解法 | [Git分支策略与协作工作流导览](./02-Git分支策略与协作工作流-导览.md) |
| 有人直接 `push` 到 `main`/`master`，未走 PR 审查 | 没有在推送前设卡，本地也没有对应约束 | 配置 `pre-push` hook 检查当前分支名，命中 `main` 或 `master` 直接 `exit 1` 拦截；代码合并统一走 Pull Request | [Git笔面试题集导览](./03-Git笔面试题集-导览.md) |
