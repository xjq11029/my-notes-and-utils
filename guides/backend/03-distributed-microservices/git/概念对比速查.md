# Git - 概念对比速查

---

### Git vs SVN

| 对比维度 | Git | SVN |
|---------|-----|-----|
| 核心定位 | 分布式版本控制系统 | 集中式版本控制系统 |
| 仓库存储 | 每个节点持有完整仓库（含全部历史） | 仅中央服务器持有完整仓库，客户端仅工作副本 |
| 离线工作 | 支持，绝大多数操作在本地完成 | 不支持，提交和查看历史需联网 |
| 分支创建 | 极轻量，分支是指针文件（41 字节），创建为 O(1) | 较重，分支是目录复制 |
| 存储模型 | 快照存储，未修改文件仅保留引用 | 按文件差异增量存储 |
| 数据完整性 | SHA-1 哈希校验，内容被篡改则哈希变化 | 无内置校验 |
| 网络依赖 | 低，仅在 push/pull 时需要 | 高，大多数操作需与中央服务器通信 |
| 学习成本 | 较高，概念和命令繁多 | 较低，模型简单 |
| 适用场景 | 现代软件开发，尤其是分布式团队和开源协作 | 需要细粒度权限控制或大文件管理的场景 |
| 选择建议 | 绝大多数场景推荐 Git；SVN 仅在特定遗留项目或大文件管理需求时使用 | |

### fast-forward vs 合并提交 vs 变基

| 对比维度 | fast-forward 合并 | 合并提交（Three-Way Merge） | 变基（rebase） |
|---------|------------------|---------------------------|---------------|
| 核心定位 | 被合并分支是当前分支直接后继时，仅前移指针 | 两分支各有新提交时，基于共同祖先三方比对生成合并提交 | 将当前分支提交逐个重放到目标分支最新提交之上 |
| 历史记录 | 线性历史，不保留分支存在痕迹 | 保留分叉历史，合并提交有两个父提交 | 线性历史，但提交哈希全部改变 |
| 是否产生新提交 | 不产生新提交 | 产生合并提交 | 产生新哈希的提交（重写历史） |
| 分支轨迹 | 丢失，无法追溯哪些提交属于哪个功能分支 | 保留，可通过合并提交追溯 | 丢失，原分支提交被新提交替代 |
| 冲突解决 | 无冲突 | 一次性解决所有冲突 | 可能需逐个提交解决冲突 |
| 回滚方式 | 直接回退指针 | 可整体回滚合并提交 | 需逐个处理，回滚困难 |
| 适用场景 | 简单的线性更新 | 需要保留完整分支历史 | 需要保持历史整洁线性 |
| 选择建议 | 简单更新时可用；重要分支使用 --no-ff 强制保留分支轨迹 | 公共分支合并推荐，保留完整历史 | 仅用于本地私有分支，不对公共分支使用 |

### HEAD vs master

| 对比维度 | HEAD | master |
|---------|------|--------|
| 核心定位 | 指向当前所在分支（或具体提交）的特殊指针 | 默认的主分支名称，指向项目主线最新提交 |
| 存储位置 | .git/HEAD 文件，内容通常为 ref: refs/heads/<branch> | .git/refs/heads/master 文件，内容为 commit SHA-1 |
| 可变性 | 切换分支时改变指向 | 提交时自动前移 |
| 典型值 | ref: refs/heads/master 或 detached 状态下直接指向 commit | 一个 40 位 SHA-1 哈希值 |
| 关系 | HEAD 指向 master 时，master 指向最新提交，HEAD 间接指向该提交 | master 是 HEAD 可能指向的分支之一 |
| 特殊状态 | 游离头指针（detached HEAD）状态下直接指向 commit，提交不属于任何分支 | 不会处于游离状态 |
| 常见用法 | `HEAD^` 表示当前提交的父提交，`HEAD~N` 表示前 N 个提交 | `master` 作为分支名，用于合并、对比等操作 |
| 选择建议 | HEAD 用于表达相对于当前位置的操作；master 用于明确指定分支 | |
