### 1. Git 中，以下哪个命令用于查看当前工作区的状态？（★）

> 知识点：git status 命令

| 维度 | 内容 |
|------|------|
| 是什么 | 查看工作区与暂存区文件状态的命令，展示已修改、已暂存、未跟踪文件分类。 |
| 能做什么 | 列出文件状态分类；提示当前分支与上下游差异；支持简洁模式输出。 |
| 怎么用 | `git status`；`git status -s` |
| 原理和工作流程 | 读取 .git/index 暂存区快照与 HEAD 提交快照，扫描工作区实际文件，三者两两比对得出每文件状态。git log 查历史、git diff 比差异、git show 显示单提交详情，均非状态查看命令。 |
| 缺点 | 大型仓库扫描较慢；输出信息量对新手偏大。 |

### 2. 以下关于 Git 工作区的描述，错误的是？（★）

> 知识点：git commit 与暂存区关系

| 维度 | 内容 |
|------|------|
| 是什么 | git commit 默认仅提交暂存区内容不跳过暂存区的机制。 |
| 能做什么 | 区分工作区、暂存区、本地仓库职责；说明 commit 的默认数据来源。 |
| 怎么用 | `git commit` 提交暂存区；`git commit -a` 提交已跟踪文件修改（含自动 add） |
| 原理和工作流程 | commit 读取暂存区快照生成提交对象，不直接读取工作区。若需跳过暂存区提交已跟踪文件修改须用 -a（自动 add 已跟踪文件但不含未跟踪文件）。工作区是编辑目录、暂存区存待提交修改、本地库存全部版本，三者职责分离。 |
| 缺点 | -a 易让人误以为提交全部修改，未跟踪文件仍需手动 add；新手易混淆 commit 与 add 的边界。 |

### 3. 执行 git commit -m "fix: 修复登录bug" 后，发现遗漏了一个文件未提交，且不想新增一条 commit 记录，应该怎么做？（★★）

> 知识点：git commit --amend

| 维度 | 内容 |
|------|------|
| 是什么 | 将暂存区内容追加到上次提交而不产生新 commit 记录的命令。 |
| 能做什么 | 补充遗漏文件到上次提交；修改上次提交信息；保持提交历史无冗余记录。 |
| 怎么用 | `git add <遗漏文件>`；`git commit --amend` |
| 原理和工作流程 | --amend 读取当前暂存区内容替换上次提交的 tree，生成新提交对象替代原提交（新哈希），不追加独立 commit 记录。先 add 遗漏文件使其进入暂存区，再 amend 即可合并到上次提交。相较 reset HEAD~1 重提交更简洁且保留原提交信息。 |
| 缺点 | amend 改写提交哈希，对已推送提交使用需强制推送，危害公共分支协作安全。 |

### 4. 在 Git 中，HEAD 通常指向什么？（★）

> 知识点：HEAD 指针

| 维度 | 内容 |
|------|------|
| 是什么 | 指向当前所在分支最新提交的特殊指针，切换分支时随之改变。 |
| 能做什么 | 标识当前工作分支；切换时更新指向；游离状态下直接指向具体 commit。 |
| 怎么用 | `cat .git/HEAD`；切换分支自动更新 |
| 原理和工作流程 | HEAD 文件内容通常为 ref: refs/heads/<branch>，间接指向当前分支顶端提交。切换分支时 HEAD 更新为新分支引用。游离头指针（detached HEAD）状态下 HEAD 直接指向某 commit 而非分支，此时提交不属于任何分支。HEAD 不指向远程仓库、工作区根目录或暂存区索引。 |
| 缺点 | 游离头指针下提交若未建分支易被 gc 丢失；概念对新手抽象。 |

### 5. 以下哪个命令用于将本地分支 feature-a 推送到远程仓库，并建立追踪关系？（★★）

> 知识点：git push -u 建立追踪

| 维度 | 内容 |
|------|------|
| 是什么 | 推送本地分支到远程同时建立上游追踪关系的命令选项。 |
| 能做什么 | 推送分支并建立追踪；后续直接 git push/pull 无需指定远程与分支名。 |
| 怎么用 | `git push -u origin feature-a`；`git push --set-upstream origin feature-a` |
| 原理和工作流程 | -u 是 --set-upstream 的缩写，两者等价。执行后在本地分支配置中记录上游远程分支（branch.<name>.remote 与 branch.<name>.merge），后续 git push 与 git pull 默认使用该上游。无 -u 的普通 push 仅推送不建立追踪关系，每次需显式指定远程与分支名。 |
| 缺点 | 追踪关系配置后误删远程分支会导致本地 push/pull 失败需手动清理配置。 |

### 6. 执行 git merge feature 时发生冲突，以下处理流程正确的是？（★★）

> 知识点：合并冲突解决流程

| 维度 | 内容 |
|------|------|
| 是什么 | 从冲突发生到完成合并提交的标准操作步骤。 |
| 能做什么 | 定位冲突文件；手动编辑消除冲突标记；add 标记已解决后 commit 完成合并。 |
| 怎么用 | 编辑冲突文件 → `git add <file>` → `git commit`；放弃：`git merge --abort` |
| 原理和工作流程 | 合并触发冲突后文件插入 <<<<<<< ======= >>>>>>> 标记。正确流程为手动编辑保留正确代码删除标记，git add 标记已解决，git commit 创建合并提交完成合并。直接 commit 未解决冲突会失败；--abort 放弃合并恢复合并前；--hard 会丢失未提交修改风险极高。 |
| 缺点 | 流程步骤多易遗漏 add；大型冲突集解决耗时易引入新问题。 |

### 7. 以下关于 git rebase 和 git merge 的区别，描述正确的是？（★★）

> 知识点：rebase 与 merge 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | rebase 重写历史使线性化、merge 保留分叉合并记录的两种整合方式差异。 |
| 能做什么 | rebase 产出线性历史改写 SHA；merge 保留分支历史创建合并提交。 |
| 怎么用 | 线性：`git rebase main`；保留：`git merge feature` |
| 原理和工作流程 | rebase 将当前分支提交重放到目标分支最新提交之上，生成新哈希提交使历史线性，但改写历史。merge 创建合并提交保留分支分叉历史，原提交 SHA 不变。两者都可能产生冲突需手动解决，并非 rebase 不冲突。rebase 也可用于远程分支但需遵守黄金法则。 |
| 缺点 | rebase 改写历史危害公共分支；merge 产生合并提交使历史图分叉杂乱。 |

### 8. 执行 git reset --soft HEAD~1 后，会发生什么？（★★★）

> 知识点：reset --soft 模式

| 维度 | 内容 |
|------|------|
| 是什么 | 仅移动 HEAD 指针、不改变暂存区与工作区的 reset 模式。 |
| 能做什么 | 撤销上次提交；将修改保留在暂存区；便于重新编辑后提交。 |
| 怎么用 | `git reset --soft HEAD~1` |
| 原理和工作流程 | --soft 仅移动 HEAD 与分支指针回退一个提交，暂存区与工作区保持不变。原提交的修改退回暂存区，可重新编辑后提交。区别于 --mixed（重置暂存区保留工作区）与 --hard（重置暂存区与工作区修改丢失）。HEAD~1 表示往回移动一个提交。 |
| 缺点 | 对已推送提交使用需强制推送破坏协作历史；易与 --mixed/--hard 混淆误用。 |

### 9. 在协作开发中，git pull 实际上是哪两个命令的组合？（★）

> 知识点：git pull 的组成

| 维度 | 内容 |
|------|------|
| 是什么 | git pull 等价于 git fetch 加 git merge 的组合操作。 |
| 能做什么 | 下载远程更新并自动合并到当前分支；可通过 --rebase 改为 fetch 加 rebase。 |
| 怎么用 | `git pull`（= fetch + merge）；`git pull --rebase`（= fetch + rebase） |
| 原理和工作流程 | pull 先执行 fetch 将远程最新提交下载到本地远程跟踪分支，再执行 merge 将其合并到当前分支。--rebase 变体将 merge 替换为 rebase 使历史线性。推荐优先 fetch 加手动 merge/rebase 以便合并前检查变更。pull 非 clone 加 merge，clone 仅首次获取仓库用。 |
| 缺点 | 自动合并在分叉时产生意外合并提交；无法在合并前审查远程变更内容。 |

### 10. 不小心执行了 git reset --hard HEAD~2，想要恢复被删除的提交，应该怎么办？（★★★）

> 知识点：git reflog 恢复误删提交

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 reflog 查找被 reset 丢弃的提交哈希并恢复的方法。 |
| 能做什么 | 定位被 reset --hard 删除的提交；恢复误删分支；在 gc 前找回丢失对象。 |
| 怎么用 | `git reflog` 找哈希；`git reset --hard <hash>` 恢复 |
| 原理和工作流程 | reflog 记录 HEAD 全部移动历史含被 reset 丢弃的提交。只要未执行 git gc，被丢弃提交的对象仍存于数据库。通过 reflog 找到目标 commit 哈希后 reset --hard 即可恢复。revert 是创建反向提交非恢复删除；checkout 不恢复历史指针。 |
| 缺点 | 恢复有时效窗口，gc 后对象被清理无法找回；reflog 为本地记录不随推送同步。 |

### 11. 以下关于 git stash 的描述，错误的是？（★★）

> 知识点：git stash 默认行为

| 维度 | 内容 |
|------|------|
| 是什么 | git stash 默认仅暂存已跟踪文件修改、不暂存未跟踪文件的特性。 |
| 能做什么 | 暂存已跟踪文件修改；-u 含未跟踪文件；-a 含被忽略文件；list 查看 pop 恢复。 |
| 怎么用 | `git stash`（仅已跟踪）；`git stash -u`（含未跟踪）；`git stash -a`（含忽略） |
| 原理和工作流程 | 默认 stash 仅处理已跟踪文件的工作区与暂存区修改，未跟踪文件保持原样不暂存。需含未跟踪文件用 -u（--include-untracked），含被忽略文件用 -a（--all）。pop 恢复最近暂存并删除记录，list 列出全部暂存记录。 |
| 缺点 | 默认不含未跟踪文件易致新建文件遗漏；pop 遇冲突不自动删除需手动 drop。 |

### 12. 以下哪个工作流最适合开源项目的协作方式？（★★）

> 知识点：Fork + Pull Request 协作模式

| 维度 | 内容 |
|------|------|
| 是什么 | 开发者 Fork 仓库到自有账号开发后向原仓库提交 Pull Request 的开源协作模式。 |
| 能做什么 | 保障主仓库安全；经维护者审查后合并；支持外部贡献者无直接写入权限协作。 |
| 怎么用 | Fork 仓库 → 建分支开发 → 提交 PR → 维护者审查合并 |
| 原理和工作流程 | 开发者 Fork 原仓库到个人账号获得独立副本，在 Fork 中创建分支开发，完成后向原仓库提交 Pull Request。原仓库维护者 Review 代码后决定是否合并，避免未经审核代码直接进入主分支。该模式兼顾开放性与质量保障，是企业内部分支策略配合 PR 的基础。 |
| 缺点 | Fork 仓库需定期同步上游更新否则易分叉过大；维护者审查负担随贡献者增多而加重。 |

### 13. 执行 git cherry-pick 的作用是什么？（★★）

> 知识点：git cherry-pick 作用

| 维度 | 内容 |
|------|------|
| 是什么 | 将指定提交的变更应用到当前分支而不合并整个分支的命令。 |
| 能做什么 | 跨分支移植单个或多个提交；选择性合并部分提交；补丁迁移与误操作恢复。 |
| 怎么用 | `git cherry-pick <hash>`；`git cherry-pick <start>..<end>` |
| 原理和工作流程 | 读取目标提交相对其父提交的 diff，将变更以新提交形式重新应用到当前分支顶端，生成新哈希。典型场景为在 feature-a 修复的 bug 通过 cherry-pick 同步到 feature-b。过程中可能产生冲突需手动解决。非删除提交、非整分支合并、非丢弃修改。 |
| 缺点 | 生成新哈希不保留原分支关系；批量操作相似冲突需反复解决。 |

### 14. 关于 Git 分支策略 Git Flow，以下描述错误的是？（★★★）

> 知识点：GitFlow hotfix 分支来源

| 维度 | 内容 |
|------|------|
| 是什么 | GitFlow 中 hotfix 分支应从 main 而非 develop 拉取的规则。 |
| 能做什么 | 区分五类分支来源与合并去向；明确 hotfix 基于生产代码修复的定位。 |
| 怎么用 | hotfix 从 main 拉取 → 修复 → 合并到 main 打 tag 与 develop |
| 原理和工作流程 | hotfix 针对线上紧急问题，线上运行代码对应 main 分支，故修复须基于 main 拉取以保证修复基于生产版本。修复后同时合并到 main（打 tag 发布）与 develop（同步开发分支）。feature 从 develop 拉取合并回 develop，release 从 develop 拉取合并到 main 与 develop。 |
| 缺点 | hotfix 需合并到两分支易遗漏 develop 导致开发分支缺失修复；流程对新手复杂。 |

### 15. 以下哪个命令可以安全地撤销一个已经推送到远程的公共提交？（★★）

> 知识点：git revert 撤销公共提交

| 维度 | 内容 |
|------|------|
| 是什么 | 通过创建反向提交撤销指定提交变更且不改写历史的命令，适用于已推送公共分支。 |
| 能做什么 | 安全撤销公共提交；不改写历史不影响协作者；以新提交方式逆转变更。 |
| 怎么用 | `git revert HEAD` |
| 原理和工作流程 | revert 读取目标提交的 diff 生成一个反向变更的新提交，应用后抵消原提交的修改，历史中保留原提交与反向提交记录，不改写历史故不影响已基于原提交开发的协作者。reset --hard 加 push -f 会改写远程历史危害协作；--amend 也改写历史。核心原则：公共分支只用 revert 不用 reset/amend。 |
| 缺点 | 产生额外反向提交使历史冗余；对相互依赖的多个提交 revert 顺序不当会引发新冲突。 |

### 1. 请简述 Git 中工作区、暂存区、本地仓库和远程仓库四个区域之间的关系。（★）

> 知识点：四区域关系与数据流转

| 维度 | 内容 |
|------|------|
| 是什么 | Git 四个核心区域及其间数据流转方向的关系。 |
| 能做什么 | 区分四区域职责；说明区域间转换命令；阐述分层设计的精确控制价值。 |
| 怎么用 | `git add` 工作区→暂存区；`git commit` 暂存区→本地仓库；`git push` 本地→远程；`git fetch/pull` 远程→本地 |
| 原理和工作流程 | 工作区是编辑目录；暂存区 .git/index 存待提交修改；本地仓库 .git 存全部版本历史；远程仓库为服务器共享副本。数据正向沿工作区→暂存区→本地仓库→远程仓库流转，反向通过 checkout/restore 与 fetch/pull 回流。分层设计使每次提交内容可精确控制，支持灵活版本管理。 |
| 缺点 | 四层模型增加认知负担；暂存区概念在其他 VCS 中少见易被新手忽略。 |

### 2. 请解释 git fetch、git pull 和 git clone 三者的区别。（★★）

> 知识点：fetch、pull、clone 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | 三个获取远程代码命令在是否合并、是否首次获取上的区别。 |
| 能做什么 | clone 完整复制仓库；fetch 下载不合并；pull 下载并自动合并。 |
| 怎么用 | 首次：`git clone <url>`；查看更新：`git fetch`；快速同步：`git pull` |
| 原理和工作流程 | clone 将远程仓库完整复制到本地含全部分支与历史，自动创建本地 main 并关联，仅首次使用。fetch 下载远程最新提交到本地远程跟踪分支不合并到当前分支，允许先检查再决定。pull 下载并自动合并到当前分支等价 fetch 加 merge。fetch 安全可控，pull 快捷但可能产生意外冲突。 |
| 缺点 | pull 自动合并在分叉时产生合并提交；fetch 需额外手动合并步骤增加操作成本。 |

### 3. 请描述 Git 中合并冲突的典型场景及解决步骤。（★★）

> 知识点：合并冲突场景与解决步骤

| 维度 | 内容 |
|------|------|
| 是什么 | 合并冲突的典型触发场景与标准解决操作步骤。 |
| 能做什么 | 识别同文件同行修改、文件删除、同区域修改等冲突场景；按步骤解决冲突完成合并。 |
| 怎么用 | merge → status → 编辑删除标记 → add → commit；放弃：`git merge --abort` |
| 原理和工作流程 | 典型场景包括两分支修改同一文件同一行、一分支删除文件另一分支修改、两分支修改同一区域。解决步骤为执行合并后 git status 查冲突文件，打开文件找到 <<<<<<< ======= >>>>>>> 标记，手动编辑保留正确代码删除标记，git add 标记已解决，git commit 完成合并。可用 mergetool 辅助，--abort 放弃合并。预防靠频繁拉取、小粒度分支与及时沟通。 |
| 缺点 | 冲突解决依赖人工判断易出错；二进制文件冲突无法自动合并只能二选一。 |

### 4. 请简述 Git Flow 分支模型中的主要分支类型及其职责。（★★★）

> 知识点：GitFlow 分支类型与职责

| 维度 | 内容 |
|------|------|
| 是什么 | GitFlow 定义的 main、develop、feature、release、hotfix 五类分支的职责与生命周期。 |
| 能做什么 | 区分五类分支来源与合并去向；明确永久分支与临时分支边界；理解发布与热修复流程。 |
| 怎么用 | feature: develop→develop；release: develop→main+develop；hotfix: main→main+develop |
| 原理和工作流程 | main 永久存放生产稳定代码每提交对应发布版本；develop 永久为开发集成分支；feature 临时从 develop 拉取开发新功能完成后合并回 develop 删除；release 临时从 develop 拉取做发布前测试与版本号更新完成后合并到 main 打 tag 与 develop 删除；hotfix 临时从 main 拉取修复线上紧急问题后合并到 main 打 tag 与 develop 删除。 |
| 缺点 | 模型复杂分支多学习成本高；合并流程繁琐影响交付速度；对持续部署项目过重。 |

### 5. git reset 的三种模式（--soft、--mixed、--hard）有什么区别？请分别说明各自的使用场景。（★★★）

> 知识点：reset 三种模式区别与场景

| 维度 | 内容 |
|------|------|
| 是什么 | --soft、--mixed、--hard 三种模式对 HEAD、暂存区、工作区的不同处理策略及适用场景。 |
| 能做什么 | soft 撤销提交保留暂存；mixed 撤销提交与暂存保留工作区；hard 彻底回退三区。 |
| 怎么用 | `git reset --soft HEAD~1`；`git reset HEAD~1`；`git reset --hard HEAD~1` |
| 原理和工作流程 | 三模式均移动 HEAD。--soft 不动暂存区与工作区，修改退回暂存区，场景为重编辑提交信息或合并多提交。--mixed（默认）重置暂存区不动工作区，修改退回工作区，场景为撤销 add 与 commit 保留修改重新选择。--hard 重置暂存区与工作区修改丢失，场景为彻底放弃修改恢复干净状态，不可逆需谨慎。 |
| 缺点 | --hard 不可逆丢失修改；对已推送提交使用需强制推送破坏协作历史；三模式易混淆误用。 |

### 6. 请解释 git rebase 的工作原理，以及使用 rebase 时需要注意的黄金法则。（★★★）

> 知识点：rebase 原理与黄金法则

| 维度 | 内容 |
|------|------|
| 是什么 | rebase 将当前分支提交重放到目标分支最新提交之上的机制，及不对公共分支 rebase 的约束。 |
| 能做什么 | 使提交历史线性化；重写提交哈希；在本地私有分支保持历史整洁。 |
| 怎么用 | `git rebase main`（feature 分支）；推送前 `git pull --rebase` |
| 原理和工作流程 | rebase 找共同祖先，将当前分支自祖先以来的提交摘取，把当前分支指向目标分支最新提交，再逐个重放生成新哈希提交（如 D'、E'），原提交被 gc 清除。黄金法则为永远不对已推送公共分支 rebase，因其重写哈希破坏协作者工作基础，强制推送导致历史分叉冲突。正确用法限于本地私有分支与推送前 pull --rebase。 |
| 缺点 | 重写历史破坏可追溯性；多提交可能需逐个解决冲突；违反黄金法则危害团队协作。 |

| 是什么 | 以真实开发场景考查 Git 综合应用能力的题型，共 2 题，均★★★难度。 |

### 场景一：紧急修复与功能开发的冲突处理（★★★）

> 知识点：stash 暂存与 cherry-pick 跨分支移植

| 维度 | 内容 |
|------|------|
| 是什么 | 功能开发中途需切换分支处理紧急 bug 时，用 stash 暂存工作并用 cherry-pick 移植修复的综合操作。 |
| 能做什么 | 暂存未提交工作切换分支；创建 hotfix 修复推送；用 cherry-pick 将修复同步到功能分支。 |
| 怎么用 | `git stash -u` → `git checkout main` → 建 hotfix 修复推送 → `git checkout feature/payment` → `git stash pop` → `git cherry-pick <hotfix-hash>` |
| 原理和工作流程 | 未提交修改直接切换分支时，若修改文件在目标分支有不同版本 Git 拒绝切换提示覆盖风险。正确做法为先 git stash -u 暂存全部修改（含未跟踪），切到 main 拉取最新创建 hotfix 分支修复并推送，合并 hotfix 到 main 后切回 feature/payment 执行 stash pop 恢复工作。若功能分支也需该修复，用 cherry-pick 将 hotfix 提交移植到功能分支避免重复编码。 |
| 缺点 | stash pop 遇冲突需手动解决且 stash 不自动删除；cherry-pick 生成新哈希不保留分支关系。 |

### 场景二：误操作恢复综合演练（★★★）

> 知识点：reflog 恢复与协作流程改进

| 维度 | 内容 |
|------|------|
| 是什么 | 公共分支误用 reset --hard 与强制推送后，通过 reflog 恢复本地与远程提交并改进协作流程的综合处置。 |
| 能做什么 | 用 reflog 找回被 reset 丢弃的提交；恢复被强制推送覆盖的远程分支；识别不规范操作并提出改进措施。 |
| 怎么用 | `git reflog` 找哈希 → `git reset --hard <hash>` → `git push -f origin develop`；改进：分支保护 + revert + PR 审查 |
| 原理和工作流程 | reflog 记录 HEAD 全部移动历史含被 reset 丢弃的提交，未 gc 前对象仍存，找到目标哈希后 reset --hard 恢复本地，再 push -f 恢复远程。若他人已拉取错误版本需通知其 fetch 加 reset --hard origin/develop 同步。暴露的问题包括公共分支直接开发、随意 reset --hard、push -f 强制推送、提交信息不规范、缺乏审查。改进措施为启用分支保护禁止强制推送、用 revert 替代 reset 撤销公共提交、建立 Conventional Commits 规范、要求 PR 加 Code Review。 |
| 缺点 | 强制推送后若他人已拉取错误版本需逐一通知同步；恢复依赖 gc 前时效窗口，延迟过久对象被清理。 |
