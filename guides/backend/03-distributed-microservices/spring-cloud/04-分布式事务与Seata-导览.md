## 一、分布式事务概述

### 1.1 为什么需要分布式事务

| 维度 | 内容 |
|------|------|
| 是什么 | 微服务架构中跨服务跨数据库的业务操作需要保证数据一致性的需求 |
| 能做什么 | 跨服务操作统一提交或回滚；保证订单、账户、库存等多数据源一致；避免部分成功部分失败 |
| 怎么用 | `下单:订单服务(写订单) -> 账户服务(扣余额) -> 库存服务(减库存)` |
| 原理和工作流程 | 微服务架构下一个业务操作跨越多个服务和数据库，如下单流程需写订单表、扣余额、减库存。若库存服务扣减失败，订单和账户操作需回滚，否则数据不一致。本地事务无法覆盖多数据源，需分布式事务机制协调跨服务操作的全部提交或回滚 |
| 缺点 | 分布式事务引入额外协调组件增加系统复杂度；跨网络协调存在性能损耗；一致性保证与可用性存在权衡 |

### 1.2 分布式事务方案对比

| 维度 | 内容 |
|------|------|
| 是什么 | 主流分布式事务方案在一致性、性能、复杂度、适用场景上的对比 |
| 能做什么 | 对比 2PC 强一致低性能；对比 TCC 高性能高复杂；对比可靠消息异步最终一致；对比 Seata AT 通用低复杂；对比 Saga 长事务 |
| 怎么用 | `2PC | TCC | 可靠消息 | Seata AT | Saga` |
| 原理和工作流程 | 2PC 两阶段提交强一致但性能低，适用传统分布式事务；TCC 性能高但复杂度高，适用高性能场景；可靠消息最终一致性能高，适用异步场景；Seata AT 模式最终一致复杂度低，适用通用场景；Saga 模式最终一致性能高，适用长事务场景 |
| 缺点 | 强一致方案性能差，最终一致方案存在数据不一致窗口；TCC 业务侵入大；各方案均有适用边界，无通用银弹 |

## 二、Seata 核心架构

### 2.1 三大角色

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 定义的 TC、TM、RM 三个核心角色及其职责分工 |
| 能做什么 | TC 协调全局与分支事务状态；TM 定义全局事务范围；RM 管理分支事务资源 |
| 怎么用 | `TC=Seata Server | TM=@GlobalTransactional | RM=数据库操作Service` |
| 原理和工作流程 | TC（Transaction Coordinator）为事务协调者，独立部署的 Seata Server，维护全局事务和分支事务状态；TM（Transaction Manager）为事务管理器，@GlobalTransactional 注解标注的方法所在 Service，定义全局事务范围（开启/提交/回滚）；RM（Resource Manager）为资源管理器，每个参与分布式事务的数据库操作对应 Service，管理分支事务注册/报告状态/提交/回滚 |
| 缺点 | TC 需独立部署增加运维成本；TM 与 RM 角色边界依赖注解位置，理解成本高；TC 单点故障影响全局事务协调 |

### 2.2 角色交互流程

| 维度 | 内容 |
|------|------|
| 是什么 | TC、TM、RM 三角色在一次分布式事务中的交互时序 |
| 能做什么 | TM 开启全局事务；RM 执行并注册分支；TM 请求提交回滚；TC 驱动 RM 执行 |
| 怎么用 | `TM开启(XID) -> RM执行注册 -> TM请求 -> TC驱动提交/回滚` |
| 原理和工作流程 | TM 向 TC 开启全局事务获得 XID（全局事务 ID）；RM 携带 XID 执行分支事务；RM 向 TC 注册分支事务并报告状态；TM 向 TC 请求提交或回滚；TC 根据各分支状态驱动各 RM 提交或回滚分支事务 |
| 缺点 | 交互链路长增加延迟；任一角色故障影响事务完成；XID 传播依赖框架支持，跨非标准调用可能丢失 |

## 三、AT 模式深度解析

### 3.1 AT 模式原理

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 最常用的分布式事务模式，基于改进的两阶段提交协议，通过自动生成 undo_log 实现无侵入回滚 |
| 能做什么 | 自动记录回滚日志；业务代码零侵入；跨服务事务统一提交回滚；保证最终一致性 |
| 怎么用 | `@GlobalTransactional + undo_log表` |
| 原理和工作流程 | AT（Auto Transaction）模式基于改进的两阶段提交，通过自动生成回滚日志（undo_log）实现自动回滚，业务代码零侵入。第一阶段执行业务 SQL 同时记录 undo_log，第二阶段根据全局事务结果异步删除 undo_log（提交）或执行反向 SQL（回滚） |
| 缺点 | 全局锁限制并发性能；undo_log 增加存储与写入开销；仅支持关系型数据库依赖 ACID |

### 3.2 两阶段流程

| 维度 | 内容 |
|------|------|
| 是什么 | AT 模式第一阶段执行记录、第二阶段提交或回滚的详细步骤 |
| 能做什么 | 第一阶段执行 SQL 与记录 undo_log；第二阶段提交异步删除日志；第二阶段回滚执行反向 SQL |
| 怎么用 | `阶段1:执行SQL+undo_log | 阶段2提交:删undo_log | 阶段2回滚:反向SQL` |
| 原理和工作流程 | 第一阶段：TM 向 TC 开启全局事务获得 XID，RM 执行原始业务 SQL（INSERT/UPDATE/DELETE），RM 自动生成 undo_log 记录回滚 SQL，业务 SQL 与 undo_log 在同一本地事务提交，RM 向 TC 注册分支事务报告成功。第二阶段提交：TC 通知各 RM 提交，RM 异步删除 undo_log。第二阶段回滚：TC 通知各 RM 回滚，RM 读取 undo_log 执行反向 SQL（如 INSERT 对应 DELETE），删除 undo_log |
| 缺点 | 第一阶段本地事务包含 undo_log 写入增加事务时长；第二阶段回滚期间数据处于中间态；异步删除 undo_log 失败需补偿机制 |

### 3.3 undo_log 表结构

| 维度 | 内容 |
|------|------|
| 是什么 | AT 模式存储回滚信息的数据库表结构定义 |
| 能做什么 | 存储分支事务 ID 与全局事务 ID；记录回滚 SQL 信息；标记日志状态；支持唯一约束 |
| 怎么用 | `branch_id + xid + rollback_info(LONGBLOB) + log_status` |
| 原理和工作流程 | undo_log 表包含 id（自增主键）、branch_id（分支事务 ID）、xid（全局事务 ID）、context（上下文）、rollback_info（LONGBLOB 存储序列化的回滚日志含前镜像后镜像）、log_status（0 正常 1 已全局完成）、log_created/log_modified（时间戳）。唯一键 ux_undo_log（xid, branch_id）防止重复注册 |
| 缺点 | 每个参与事务的数据库都需建 undo_log 表，遗漏导致事务失败；rollback_info 为 LONGBLOB 占用存储；表数据需定期清理避免膨胀 |

### 3.4 AT 模式全局锁

| 维度 | 内容 |
|------|------|
| 是什么 | AT 模式在第二阶段提交前对涉及数据行加锁防止其他事务修改的机制 |
| 能做什么 | 行级粒度加锁；TC 内存维护；事务提交后释放；获取失败重试 |
| 怎么用 | `TC内存维护 + 行级锁(基于主键) + 重试30次/间隔10ms` |
| 原理和工作流程 | 全局锁在 TC 内存中维护，锁粒度为行级（基于主键）。事务提交前 TC 对涉及数据行加全局锁，防止其他分布式事务修改同一数据行。事务提交后释放全局锁。获取全局锁失败会重试，默认重试 30 次间隔 10ms |
| 缺点 | 全局锁限制并发性能，热点数据易产生锁竞争；锁存 TC 内存，TC 故障锁状态丢失；长事务持锁影响其他事务吞吐 |

## 四、TCC 模式

### 4.1 TCC 模式原理

| 维度 | 内容 |
|------|------|
| 是什么 | 需业务代码实现 Try、Confirm、Cancel 三个方法的分布式事务模式 |
| 能做什么 | Try 资源预留；Confirm 确认提交；Cancel 取消回滚；无锁高性能 |
| 怎么用 | `Try(预留) -> Confirm(提交) / Cancel(回滚)` |
| 原理和工作流程 | TCC（Try-Confirm-Cancel）模式需业务代码实现三个方法：Try 检查资源可用性并预留业务资源；Confirm 使用 Try 阶段预留资源完成业务操作；Cancel 释放 Try 阶段预留资源。无全局锁，性能优于 AT 模式，但业务侵入大 |
| 缺点 | 业务侵入大需实现三方法；需处理空回滚、悬挂、幂等等异常场景；开发与维护成本高 |

### 4.2 TCC 实现示例

| 维度 | 内容 |
|------|------|
| 是什么 | TCC 模式在账户扣款场景的三方法实现示例 |
| 能做什么 | Try 冻结资金；Confirm 扣减冻结资金；Cancel 解冻资金 |
| 怎么用 | `prepareMinus(冻结) -> commitMinus(扣减) / rollbackMinus(解冻)` |
| 原理和工作流程 | Try 阶段 prepareMinus 执行 UPDATE account SET frozen=frozen+?, available=available-? WHERE available>=? 冻结资金；Confirm 阶段 commitMinus 执行 UPDATE account SET frozen=frozen-? 扣减冻结资金；Cancel 阶段 rollbackMinus 执行 UPDATE account SET frozen=frozen-?, available=available+? 解冻资金。通过 frozen 字段实现资源预留 |
| 缺点 | 需在数据模型增加 frozen 冻结字段；三方法需保证幂等；Try 与 Cancel 失败处理逻辑复杂 |

### 4.3 AT 模式 vs TCC 模式

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 两种模式在侵入性、实现难度、性能、回滚方式上的对比 |
| 能做什么 | 对比侵入性；对比实现难度；对比性能；对比回滚方式与适用场景 |
| 怎么用 | `AT:无侵入+全局锁+自动回滚 | TCC:有侵入+无锁+手动回滚` |
| 原理和工作流程 | AT 模式无侵入自动生成 undo_log 回滚，有全局锁性能一般，实现简单只需引入依赖，适合大多数场景；TCC 模式有侵入需实现 Try/Confirm/Cancel，无锁性能好，实现复杂需自定义资源预留与回滚逻辑，适合高性能要求与自定义资源场景。两者均最终一致 |
| 缺点 | AT 模式全局锁限制并发且仅支持关系型数据库；TCC 模式业务侵入大开发成本高需处理异常场景；两者均无法保证强一致 |

## 五、实战集成

### 5.1 依赖配置

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Cloud 项目引入 Seata 的 Maven 依赖配置 |
| 能做什么 | 引入 Seata Starter；集成 Spring Cloud Alibaba 生态 |
| 怎么用 | `spring-cloud-starter-alibaba-seata` |
| 原理和工作流程 | 在 pom.xml 中引入 com.alibaba.cloud 的 spring-cloud-starter-alibaba-seata 依赖，Starter 自动装配 Seata 相关 Bean 与配置，集成 Spring Cloud Alibaba 生态 |
| 缺点 | 依赖版本需与 Spring Cloud Alibaba 版本对齐，版本不匹配导致冲突；Starter 自动装配掩盖细节，排查问题困难 |

### 5.2 配置

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 客户端连接 TC 与注册中心的核心配置 |
| 能做什么 | 配置事务分组；配置 TC 地址；配置注册中心；指定命名空间与分组 |
| 怎么用 | `tx-service-group + vgroup-mapping + grouplist + registry(nacos)` |
| 原理和工作流程 | 配置 tx-service-group 指定事务分组名；vgroup-mapping 将分组映射到集群；grouplist 指定 TC 集群地址（默认 127.0.0.1:8091）；registry 配置注册中心类型为 nacos，指定 server-addr、namespace 与 group。客户端通过注册中心发现 TC 并建立连接 |
| 缺点 | 配置项多易遗漏，分组映射错误导致事务不生效；TC 地址变更需同步修改配置；命名空间隔离不当导致跨环境事务冲突 |

### 5.3 使用示例

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 @GlobalTransactional 注解实现跨服务下单分布式事务的代码示例 |
| 能做什么 | 开启全局事务；协调订单账户库存三分支事务；任一失败全局回滚 |
| 怎么用 | `@GlobalTransactional(name="create-order", timeoutMills=300000)` |
| 原理和工作流程 | OrderService 的 createOrder 方法标注 @GlobalTransactional 开启全局事务（TM 角色），设置事务名与超时。方法内 orderMapper.insert 创建订单（分支事务 1），accountClient.debit 扣余额（分支事务 2），inventoryClient.reduce 减库存（分支事务 3）。任一分支事务失败，整个全局事务回滚，各 RM 读取 undo_log 执行反向 SQL |
| 缺点 | @GlobalTransactional 仅标注入口方法，分支事务失败需靠异常传播触发回滚；超时设置不当导致长事务持锁；Feign 调用需透传 XID 否则分支事务脱离全局事务 |

## 六、常见面试题

### 1. Seata 的三大角色分别是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Seata 中 TC、TM、RM 三角色的定义与职责 |
| 能做什么 | TC 维护全局与分支事务状态；TM 定义全局事务范围；RM 管理分支事务资源 |
| 怎么用 | `TC=Seata Server | TM=@GlobalTransactional | RM=数据库操作` |
| 原理和工作流程 | TC（Transaction Coordinator）为事务协调者，独立部署的 Seata Server，维护全局事务和分支事务状态；TM（Transaction Manager）为事务管理器，@GlobalTransactional 标注的方法定义全局事务范围；RM（Resource Manager）为资源管理器，管理分支事务资源，负责注册/报告状态/提交/回滚 |
| 缺点 | 三角色概念抽象理解成本高；TC 独立部署增加运维负担；角色边界依赖注解与配置易混淆 |

### 2. Seata AT 模式的两阶段流程是怎样的？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 AT 模式两阶段提交的执行步骤 |
| 能做什么 | 第一阶段执行 SQL 与记录 undo_log；第二阶段提交删除日志或回滚反向 SQL |
| 怎么用 | `阶段1:SQL+undo_log同事务 | 阶段2:提交删日志/回滚反向SQL` |
| 原理和工作流程 | 第一阶段：TM 开启全局事务获得 XID，RM 执行原始 SQL 并生成 undo_log 记录回滚 SQL，业务 SQL 与 undo_log 在同一本地事务提交，RM 向 TC 注册分支事务。第二阶段提交：TC 通知各 RM 提交，RM 异步删除 undo_log。第二阶段回滚：TC 通知各 RM 回滚，RM 读取 undo_log 执行反向 SQL 后删除 undo_log |
| 缺点 | 第一阶段 undo_log 写入增加事务时长；回滚期间数据中间态；异步删除失败需补偿 |

### 3. AT 模式和 TCC 模式的核心区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查两种模式在侵入性与性能上的差异 |
| 能做什么 | 对比侵入性；对比全局锁；对比回滚方式；对比适用场景 |
| 怎么用 | `AT:无侵入+全局锁 | TCC:有侵入+无锁` |
| 原理和工作流程 | AT 模式无侵入自动生成回滚日志，有全局锁性能一般，适合大多数场景；TCC 模式有侵入需实现 Try/Confirm/Cancel，无锁性能好，适合高性能要求场景。AT 回滚靠 undo_log 自动执行，TCC 回滚靠 Cancel 方法手动执行 |
| 缺点 | AT 全局锁限制并发且仅支持关系型数据库；TCC 业务侵入大需处理空回滚悬挂等异常；两者均最终一致无法强一致 |

### 4. Seata AT 模式的全局锁有什么作用？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 AT 模式全局锁的维护位置、粒度与作用 |
| 能做什么 | 防止提交前数据被修改；TC 内存维护；行级粒度；获取失败重试 |
| 怎么用 | `TC内存 + 行级锁(主键) + 重试30次/10ms` |
| 原理和工作流程 | 全局锁防止在分布式事务提交前其他事务修改同一数据行。全局锁在 TC（Seata Server）内存中维护，锁粒度为行级（基于主键），事务提交后释放。获取全局锁失败会重试，默认重试 30 次间隔 10ms |
| 缺点 | 全局锁限制并发性能；锁存 TC 内存，TC 故障锁状态丢失；热点数据锁竞争严重 |

## 七、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 使用中常见错误的现象、原因与解决方案汇总 |
| 能做什么 | 创建 undo_log 表；独立部署 Seata Server；非关系库用 TCC；避免长事务；配置集群 |
| 怎么用 | `每库建undo_log | Server独立部署 | 非关系库用TCC | 避免长事务 | 集群部署` |
| 原理和工作流程 | 未创建 undo_log 表导致 AT 模式失败，每个参与事务的数据库都需建 undo_log 表；Seata Server 嵌入业务应用导致部署耦合，必须独立部署；非关系型数据库用 AT 模式回滚失败，因 AT 依赖 ACID 事务应改用 TCC 或 Saga；全局事务时间过长持锁影响并发，应避免长事务；Server 单节点部署单点故障，生产环境配置集群 |
| 缺点 | 避坑要点需逐库逐场景检查；独立部署与集群增加运维成本；长事务识别缺乏自动预警 |
