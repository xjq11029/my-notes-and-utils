## 一、核心概念

### 1.1 可观测性三大支柱

| 维度 | 内容 |
|------|------|
| 是什么 | 通过外部输出推断系统内部状态的能力，由 Metrics、Tracing、Logging 三大支柱构成 |
| 能做什么 | Metrics 量化系统状态适合告警；Tracing 还原请求完整路径；Logging 记录离散事件细节 |
| 怎么用 | `Metrics(出没出问题) + Tracing(问题在哪段) + Logging(具体什么错)` |
| 原理和工作流程 | 三大支柱互补：Metrics（指标）为聚合数据低存储成本适合告警，回答系统出没出问题；Tracing（链路追踪）跨服务关联因果链路，回答问题在哪一段；Logging（日志）上下文丰富存储成本高，回答具体出了什么错。三者通常结合使用：Metrics 触发告警，Tracing 定位服务，Logging 查看详情 |
| 缺点 | 三支柱数据分散在不同系统需关联查询；Logging 存储成本高全量采集不可行；三者集成需统一 TraceId 关联增加复杂度 |

### 1.2 为什么需要链路追踪

| 维度 | 内容 |
|------|------|
| 是什么 | 微服务架构下通过唯一 TraceId 串联跨服务调用形成完整调用树的能力 |
| 能做什么 | 串联跨服务调用；还原完整调用树；定位慢调用与错误环节；从猜测变看图 |
| 怎么用 | `TraceId串联 Gateway -> Order -> User/Product/Payment` |
| 原理和工作流程 | 单体架构一次请求在一个进程内完成，通过日志即可定位问题。微服务架构下一次请求可能经过 Gateway、Order Service、User Service、Product Service、Payment Service 等多个服务及第三方网关。请求变慢或报错时没有链路追踪几乎无法判断哪个环节出问题。链路追踪通过唯一 TraceId 将跨服务调用串联形成完整调用树，让问题定位从猜测变成看图 |
| 缺点 | 链路追踪引入额外采集与存储开销；全量采样性能损耗大需采样策略；调用树层级深时分析耗时 |

### 1.3 主流方案对比

| 维度 | 内容 |
|------|------|
| 是什么 | SkyWalking、Zipkin、Jaeger、Pinpoint 四种链路追踪方案的对比 |
| 能做什么 | 对比侵入性；对比协议标准；对比存储与 APM 能力；对比社区活跃度 |
| 怎么用 | `SkyWalking(无侵入Agent,强APM) | Zipkin(中侵入Brave,弱APM) | Jaeger(低侵入OTel) | Pinpoint(无侵入)` |
| 原理和工作流程 | SkyWalking 为 Apache 顶级项目，无侵入（Java Agent），支持 OpenTelemetry，存储 ES/H2/MySQL，APM 能力强（指标加链路加拓扑图），社区活跃度高；Zipkin 为 Twitter 出品，中等侵入（需引入 Brave 库），协议 B3/W3C，仅链路追踪 APM 弱；Jaeger 为 CNCF 毕业项目，低侵入（OpenTelemetry SDK）；Pinpoint 为 Naver 出品，无侵入（Java Agent），自有协议，社区活跃度低 |
| 缺点 | 各方案存储与协议不统一增加迁移成本；无侵入方案 Agent 版本与 OAP 需对齐；轻量方案 APM 能力不足 |

## 二、底层原理

### 2.1 Trace/Span 模型

| 维度 | 内容 |
|------|------|
| 是什么 | 链路追踪由 Trace 和 Span 两层结构构成的数据模型 |
| 能做什么 | Trace 标识完整调用链；Span 记录单次操作；ParentSpan 构成父子树；SpanContext 跨进程传播 |
| 怎么用 | `Trace(全局唯一TraceId) > Span(operationName+时间+tags) > 父子关系(parentSpanId)` |
| 原理和工作流程 | Trace 为一次完整请求的调用链由全局唯一 TraceId 标识；Span 为一次操作（RPC 调用、数据库查询等）包含操作名、起止时间、标签、日志。Span 核心属性：operationName 操作名、startTime/endTime 起止时间、tags 键值对标签、logs 事件日志、spanType 类型。Span 类型区分 Entry（接收请求）、Local（内部操作）、Exit（发起外部调用）。Span 间通过 parentSpanId 构成有向无环树（DAG），根 Span 对应入口请求 |
| 缺点 | Span 数量随调用深度增长存储开销大；tags 与 logs 语义无强约束；复杂调用树可视化困难 |

### 2.2 上下文传播

| 维度 | 内容 |
|------|------|
| 是什么 | TraceId 在跨服务调用时通过 HTTP Header 注入与提取的传播机制 |
| 能做什么 | W3C traceparent 标准传播；B3 Header 传播；跨服务上下文传递；保证链路连续 |
| 怎么用 | `traceparent: 00-<traceId>-<spanId>-<traceFlags> | X-B3-TraceId/SpanId/ParentSpanId/Sampled` |
| 原理和工作流程 | W3C TraceContext 标准用 traceparent Header 传播，格式为版本号-TraceId（32 位十六进制）-SpanId（16 位十六进制）-采样标志。B3 Header（Zipkin 原生）用 X-B3-TraceId、X-B3-SpanId、X-B3-ParentSpanId、X-B3-Sampled 系列。传播流程：服务 A 调用服务 B 时 A 的 Tracer 将 SpanContext 注入 HTTP Header，服务 B 收到请求后 Tracer 从 Header 提取上下文创建子 Span 继续向下游传播。Header 丢失导致链路断裂 |
| 缺点 | Header 丢失导致链路断裂；W3C 与 B3 协议不兼容需适配；跨非 HTTP 协议（如 MQ）传播需额外处理 |

### 2.3 采样策略

| 维度 | 内容 |
|------|------|
| 是什么 | 控制记录多少比例链路以平衡数据量与性能开销的策略 |
| 能做什么 | 全量采样；概率采样；限流采样；自适应采样；采样决策随上下文传播 |
| 怎么用 | `全量(100%) | 概率(默认0.1) | 限流(每秒N) | 自适应` |
| 原理和工作流程 | 全量采样 100% 记录所有请求适用开发测试；概率采样按比例随机采样适用生产通用场景（Sleuth 默认 0.1 即 10%）；限流采样限制每秒采样数保护后端存储；自适应采样根据错误率延迟动态调整。采样决策在链路入口（根 Span）做出后通过 Sampled 标志位随 SpanContext 向下游传播，下游收到已采样请求继续创建 Span 上报，未采样则跳过，保证同一条链路要么完整记录要么不记录 |
| 缺点 | 采样率过低遗漏偶发问题；过高导致存储成本与性能开销；概率采样可能漏掉关键异常请求 |

### 2.4 SkyWalking 原理

| 维度 | 内容 |
|------|------|
| 是什么 | SkyWalking 采用 Java Agent 字节码增强实现零侵入链路采集的原理 |
| 能做什么 | JVM 启动加载 Agent；拦截关键类插入埋点；gRPC 上报 OAP；分析聚合存储；UI 展示 |
| 怎么用 | `-javaagent:skywalking-agent.jar -> premain拦截 -> gRPC上报OAP -> ES存储 -> UI展示` |
| 原理和工作流程 | JVM 启动通过 -javaagent 参数加载 skywalking-agent.jar，premain 方法拦截关键类（Tomcat、SpringMVC、MySQL Driver、Feign 等）；Java Agent 在类加载阶段用 ByteBuddy 修改字节码，在目标方法前后插入探针逻辑（创建 Span、记录耗时）；业务代码完全无感知无需引入依赖或修改代码；通过 gRPC 上报到 OAP Server，OAP 分析聚合（构建服务拓扑、计算指标），存储到 Elasticsearch/H2/MySQL，UI 展示拓扑图、链路详情、慢调用分析 |
| 缺点 | Agent 版本需与 OAP Server 版本一致否则协议不兼容；字节码增强增加启动耗时；Agent 与应用同进程故障相互影响 |

### 2.5 Zipkin 原理

| 维度 | 内容 |
|------|------|
| 是什么 | Zipkin 通过应用内嵌 Brave 库采集链路数据的原理 |
| 能做什么 | Tracer 创建 Span；拦截器自动埋点；异步批量上报；存储与查询展示 |
| 怎么用 | `应用内嵌Brave -> Tracer创建Span -> 异步批量上报Zipkin Server -> 存储 -> UI查询` |
| 原理和工作流程 | Zipkin 数据采集依赖应用内嵌的 Tracer 库（Java 中为 Brave）。Brave 通过 Tracing 类管理 Span 生命周期，通过 Tracing.currentTracer() 获取当前 Tracer。自动埋点依赖各组件拦截器（HttpTracing 包装 Servlet Filter、HttpClientHandler 包装 HTTP 客户端），在请求进出时自动创建和关闭 Span。Span 数据先在内存异步累积批量上报到 Zipkin Server，避免每次请求同步网络开销。Zipkin Server 存储到 ES/MySQL/Cassandra，UI 查询展示链路树与依赖图 |
| 缺点 | 需在应用引入 Brave 依赖侵入性中等；Spring Cloud 2022.0.0 起 Sleuth 废弃需迁移 Micrometer Tracing；批量上报失败可能丢数据 |

## 三、实战应用

### 3.1 Spring Cloud 集成 SkyWalking（Agent 挂载方式）

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 JVM 启动参数挂载 SkyWalking Agent 实现零代码侵入链路采集的方式 |
| 能做什么 | 无需改业务代码；指定服务名与实例名；配置 OAP 地址；Docker 环境挂载 |
| 怎么用 | `java -javaagent:/path/to/skywalking-agent.jar -Dskywalking.agent.service_name=order-service -Dskywalking.collector.backend_service=127.0.0.1:11800 -jar app.jar` |
| 原理和工作流程 | 仅通过 JVM 启动参数挂载 Agent：-javaagent 指定 Agent jar 路径 JVM 启动时加载，service_name 标识链路归属，backend_service 指定 OAP Server 地址（gRPC 端口默认 11800），instance_name 区分同服务多实例。Docker/K8s 环境通过 sidecar 或 init-container 将 Agent jar 挂载到容器实现与应用镜像解耦。Agent 版本与 OAP Server 需一致。完整链路：Agent -> OAP Server -> Elasticsearch -> UI |
| 缺点 | -javaagent 必须在 -jar 之前否则不生效；Agent 版本与 OAP 不兼容导致无数据；Docker 挂载增加构建复杂度 |

### 3.2 Spring Cloud Sleuth + Zipkin 集成

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Spring Cloud Sleuth 封装 Brave 集成 Zipkin 的方式 |
| 能做什么 | 引入 Sleuth 与 Zipkin 依赖；配置 Zipkin Server 地址；配置采样率与传播协议；自动注入埋点 |
| 怎么用 | `spring-cloud-starter-sleuth + spring-cloud-sleuth-zipkin + base-url + sampler.probability` |
| 原理和工作流程 | 引入 spring-cloud-starter-sleuth 与 spring-cloud-sleuth-zipkin 依赖。配置 spring.zipkin.base-url 指定 Zipkin Server 地址，sender.type 指定上报方式（web/rabbit/kafka），spring.sleuth.sampler.probability 配置采样率（生产建议 0.1），propagation.type 配置上下文传播协议（B3 或 W3C）。Sleuth 自动为 Spring MVC 请求入口、OpenFeign 调用、RestTemplate、数据库访问、消息队列收发注入链路追踪无需手动埋点。注意 Spring Cloud 2022.0.0 起 Sleuth 废弃迁移至 Micrometer Tracing |
| 缺点 | Sleuth 已废弃新项目需迁移 Micrometer Tracing；采样率配置不当影响排障或性能；需额外部署 Zipkin Server |

### 3.3 日志关联 TraceId

| 维度 | 内容 |
|------|------|
| 是什么 | 将 TraceId 与 SpanId 注入 MDC 实现日志与链路关联的机制 |
| 能做什么 | TraceId 注入 MDC；logback pattern 引用；日志按 TraceId 检索；还原完整日志链 |
| 怎么用 | `logback pattern: [%X{traceId},%X{spanId}]` |
| 原理和工作流程 | Sleuth 将 TraceId 和 SpanId 注入 MDC（Mapped Diagnostic Context），日志框架可直接引用。在 logback-spring.xml 的 pattern 中添加 [%X{traceId},%X{spanId}]，日志输出效果为每行日志包含 traceId 与 spanId。发现请求异常时从 Zipkin UI 拿到 TraceId，再到 ELK 中用该 TraceId 检索即可还原完整日志链 |
| 缺点 | 未在 pattern 配置 %X{traceId} 导致日志中 traceId 为空；异步线程中 MDC 不自动传播需手动处理；日志量大全量存储成本高 |

### 3.4 慢调用分析实战

| 维度 | 内容 |
|------|------|
| 是什么 | 通过链路追踪调用树瀑布图定位性能瓶颈的分析方法 |
| 能做什么 | 按时间筛选 Trace；查看瀑布图；定位耗时最长 Span；查看 SQL 与调用参数；结合日志确认根因 |
| 怎么用 | `告警/反馈 -> 按时间筛选Trace -> 选最长Trace -> 找耗时Span -> 查tags -> 结合日志` |
| 原理和工作流程 | 从告警或用户反馈获知接口响应慢，记录请求时间与耗时；在追踪 UI 按时间范围和接口名筛选 Trace 列表；选择总耗时最长的 Trace 进入详情查看瀑布图；找到耗时最长的 Span 查看 operationName 和 tags；数据库 Span 查看 db.statement 确认 SQL，RPC Span 查看下游服务名与调用参数；结合日志（用 TraceId 检索 ELK）查看详细日志确认根因。例：Product Service 的 MySQL 查询耗时 2.18s 占总耗时 95% 为根因 |
| 缺点 | 采样可能漏掉慢调用 Trace；调用树层级深定位耗时；需结合多系统（追踪加日志）综合分析 |

### 3.5 SkyWalking 与 Zipkin 选型建议

| 维度 | 内容 |
|------|------|
| 是什么 | 根据代码侵入、APM 需求、运维复杂度、团队规模选择链路追踪方案的指导 |
| 能做什么 | 不改代码选 SkyWalking；需完整 APM 选 SkyWalking；轻量方案选 Zipkin；小团队选 Zipkin |
| 怎么用 | `无侵入/完整APM/中大型团队 -> SkyWalking | 可引入依赖/轻量/小团队 -> Zipkin` |
| 原理和工作流程 | 考量维度：代码侵入方面不想改业务代码选 SkyWalking，可接受引入依赖选 Zipkin；APM 需求方面需指标加拓扑加链路选 SkyWalking，只需链路选 Zipkin；运维复杂度方面 SkyWalking 需维护 OAP Server 加存储，Zipkin 只需 Server 加存储；云原生兼容方面 SkyWalking 已支持 OpenTelemetry，Zipkin 生态成熟 Sleuth 集成简单；团队规模方面中大型选 SkyWalking，小型选 Zipkin。两者均支持 OpenTelemetry 可平滑切换 |
| 缺点 | SkyWalking 运维复杂度高需维护 OAP；Zipkin APM 能力弱仅链路；两者迁移存在数据与配置转换成本 |

## 四、常见面试题

### 1. 可观测性三大支柱是什么，它们之间有什么关系？

| 维度 | 内容 |
|------|------|
| 是什么 | 可观测性的 Metrics、Tracing、Logging 三大支柱及其互补关系 |
| 能做什么 | Metrics 触发告警；Tracing 定位服务；Logging 查看详情；三者结合使用 |
| 怎么用 | `Metrics(出没出问题) + Tracing(问题在哪段) + Logging(具体什么错)` |
| 原理和工作流程 | Metrics（指标）为聚合数据低存储成本适合告警，回答系统出没出问题；Tracing（链路追踪）跨服务关联完整调用链，回答问题出在哪一段；Logging（日志）上下文最丰富存储成本高，回答具体出了什么错。三者互补通常结合使用：Metrics 触发告警，Tracing 定位服务，Logging 查看详情 |
| 缺点 | 三支柱数据分散需关联查询；Logging 全量采集成本高；三者需统一 TraceId 关联增加集成复杂度 |

### 2. Trace 和 Span 的关系是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 链路追踪中 Trace 与 Span 的层级构成关系 |
| 能做什么 | Trace 标识完整调用链；Span 记录单次操作；父子关系构成 DAG；一个 Trace 含多个 Span |
| 怎么用 | `Trace(TraceId) > Span(parentSpanId构成父子树) > 根Span(入口请求)` |
| 原理和工作流程 | Trace 是一次完整请求的调用链由全局唯一 TraceId 标识。Span 是一次具体操作（如 RPC 调用、数据库查询）包含操作名、起止时间、标签等。多个 Span 通过 parentSpanId 构成父子关系形成有向无环树（DAG），根 Span 对应入口请求。一个 Trace 包含多个 Span |
| 缺点 | Span 数量随调用深度增长存储开销大；复杂调用树可视化困难；父子关系依赖上下文传播正确性 |

### 3. SkyWalking 和 Zipkin 的核心区别？

| 维度 | 内容 |
|------|------|
| 是什么 | SkyWalking 与 Zipkin 在采集方式与 APM 能力上的差异 |
| 能做什么 | 对比采集方式（Agent vs Brave）；对比 APM 能力；对比数据分析方式；对比适用场景 |
| 怎么用 | `SkyWalking:Agent无侵入+完整APM | Zipkin:Brave中侵入+仅链路` |
| 原理和工作流程 | SkyWalking 采用 Java Agent 字节码增强业务代码零侵入无需引入依赖或改代码；Zipkin 需在应用中嵌入 Brave 库侵入性中等。SkyWalking 提供完整 APM 能力（指标加链路加服务拓扑图）；Zipkin 专注链路追踪 APM 弱。SkyWalking 通过 OAP Server 分析聚合数据；Zipkin 直接存储原始 Span。SkyWalking 适合不想改业务代码的团队，Zipkin 更轻量 |
| 缺点 | SkyWalking 运维复杂需维护 OAP；Zipkin APM 能力不足；两者协议与存储不同迁移有成本 |

### 4. 链路追踪的上下文是如何在服务间传播的？

| 维度 | 内容 |
|------|------|
| 是什么 | TraceId 等 SpanContext 通过 HTTP Header 在服务间传播的机制 |
| 能做什么 | 上游注入 Header；下游提取 Header；创建子 Span 继续传播；保证链路连续 |
| 怎么用 | `W3C:traceparent(00-traceId-spanId-flags) | B3:X-B3-TraceId/SpanId/ParentSpanId/Sampled` |
| 原理和工作流程 | 通过 HTTP Header 注入和提取 SpanContext。上游服务调用下游时 Tracer 将 traceId、spanId、采样标志注入请求 Header（W3C 标准用 traceparent，Zipkin 用 X-B3-* 系列）。下游服务收到请求后 Tracer 从 Header 提取上下文创建子 Span 并继续向下游传播。上下文传播是链路串联的基础，Header 丢失会导致链路断裂 |
| 缺点 | Header 丢失导致链路断裂；W3C 与 B3 协议不兼容需适配；跨非 HTTP 协议传播需额外处理 |

### 5. 采样策略有哪些，如何选择？

| 维度 | 内容 |
|------|------|
| 是什么 | 链路追踪控制记录比例的采样策略类型与选择方法 |
| 能做什么 | 全量采样；概率采样；限流采样；自适应采样；按场景选择采样率 |
| 怎么用 | `全量(开发测试) | 概率0.1-0.5(生产) | 限流(保护存储) | 排障期调高1.0` |
| 原理和工作流程 | 全量采样（100%）适合开发和测试环境；概率采样（默认 10%）适合生产环境通用场景；限流采样按每秒采样数控制保护后端存储。生产环境通常设为 0.1 到 0.5，排障期临时调高到 1.0。采样率过低会遗漏偶发问题，过高导致存储成本和性能开销增大 |
| 缺点 | 概率采样可能漏掉关键异常请求；采样率调优依赖经验；排障期调高采样率增加存储压力 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 链路追踪使用中常见错误的现象、原因与解决方案汇总 |
| 能做什么 | 控制采样率；正确挂载 Agent；日志输出 TraceId；跨线程传播上下文；Feign 链路连续；第三方调用追踪 |
| 怎么用 | `采样0.1-0.5 | -javaagent在-jar前 | logback配%X{traceId} | TraceableExecutorService | 引入Sleuth | Sleuth包装RestTemplate` |
| 原理和工作流程 | 采样率过高导致存储暴增性能下降，生产设 0.1-0.5 仅排障期调高；Agent 未正确挂载导致 UI 无数据，-javaagent 必须在 -jar 之前确认路径正确查看 agent.log；TraceId 未在日志输出因未在 logback pattern 配置 %X{traceId}，需添加 [%X{traceId},%X{spanId}]；跨线程丢失上下文因 Sleuth 默认只对 @Async 和线程池自动传播，需用 TraceableExecutorService 包装；Feign 调用链路断裂因未集成 Sleuth 或 Header 未透传，需引入 spring-cloud-starter-sleuth 自动传播；第三方调用未追踪因 RestTemplate 未被 Sleuth 包装，Sleuth 自动包装 RestTemplate 和 WebClient 需正确创建 Bean |
| 缺点 | 避坑要点多分散；Agent 挂载与日志配置排查依赖经验；跨线程与第三方调用上下文传播需额外处理 |
