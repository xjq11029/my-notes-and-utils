### 1. ★ 以下关于 CAP 定理的描述，正确的是（ ）

A. 分布式系统可以同时满足 C、A、P 三个属性
B. CAP 中的 C 指的是最终一致性
C. 当网络分区发生时，必须在 C 和 A 之间做取舍
D. P（分区容错性）是可选项，可以不选

**答案：C**

**解析：** CAP 定理指出，当网络分区（P）发生时，必须在一致性（C）和可用性（A）之间做取舍。A 错误，数学证明最多只能同时满足两个；B 错误，C 特指线性一致性；D 错误，P 是网络分区的客观存在，不是可选项。

> **生活化类比：CAP 定理 = 银行 ATM 机取款** —— CAP 定理可以用银行 ATM 机来理解。假设某银行有"总行账本"和"分行 ATM 机"两个节点（分布式系统）。**正常情况下**（网络畅通无分区）：你取钱时，ATM 机先向总行查询余额（一致性 C），余额充足就扣款返回现金（可用性 A），网络本身没故障（分区容错 P），三个属性都满足。**网络分区发生时**（分行 ATM 与总行断网，P 必然发生）：此时银行只能二选一：① 选 C：ATM 机拒绝服务，显示"网络故障，请稍后再试"，保证不会超支取款，但牺牲可用性 A；② 选 A：ATM 机基于本地缓存余额让你取钱，保证可用但可能与总行账本不一致（最终一致性），牺牲强一致 C。**P 是客观存在的网络分区，不可选**（除非你假设网络永不故障，但分布式系统做不到）。Zookeeper 选 CP（断网时拒绝服务保一致），Nacos 服务发现选 AP（断网时仍能服务但最终一致）。

**断路器状态流转图：**

```mermaid
%%{init: {'themeVariables': {'fontSize': '16px'}}}%%
stateDiagram-v2
    [*] --> "CLOSED（关闭）"
    "CLOSED（关闭）" --> "OPEN（打开）": 错误率超过阈值
    "OPEN（打开）" --> "HALF_OPEN（半开）": 熔断时间窗口结束
    "HALF_OPEN（半开）" --> "CLOSED（关闭）": 探测请求成功
    "HALF_OPEN（半开）" --> "OPEN（打开）": 探测请求失败
```

> 断路器（Circuit Breaker）有三种状态：CLOSED 正常放行请求并统计指标，当错误率达到阈值时切换为 OPEN 拒绝所有请求，经过熔断时间窗口后进入 HALF_OPEN 放行少量探测请求，根据探测结果决定恢复关闭还是重新打开。

### 9. ★★ Sentinel 熔断器的三种状态不包括（ ）

A. CLOSED
B. OPEN
C. HALF_OPEN
D. DEGRADED

**答案：D**

**解析：** 熔断器三种状态：CLOSED（正常）、OPEN（熔断打开）、HALF_OPEN（半开）。DEGRADED 不是状态名。

> **生活化类比：服务熔断 = 家用保险丝** —— Sentinel 的熔断器就像家中的保险丝（空气开关）。正常用电时（CLOSED 状态），电流平稳通过保险丝，保险丝同时统计用电量。当某个大功率电器短路（后端服务异常率高），电流瞬间飙升超过保险丝额定值（错误率超阈值），保险丝自动跳闸断电（OPEN 状态），切断故障电路，避免火灾蔓延到全屋其他电器（防止故障扩散到其他服务）。断电一段时间后（熔断时间窗口），保险丝尝试半合闸（HALF_OPEN 状态），让你按一下测试按钮（探测请求）：如果电路正常就完全合闸恢复正常供电（CLOSED）；如果还短路就立即再次跳闸（OPEN）。三种状态自动切换，无需人工干预，是微服务"自愈"能力的核心。

## 二、简答题（10 题，每题附完整解析）

### 1. 简述 CAP 定理的含义，并说明 Nacos 如何体现 CAP 选择。

**答案：** CAP 定理指出，分布式系统最多只能同时满足一致性（C）、可用性（A）、分区容错性（P）中的两个。Nacos 通过实例类型区分：临时实例走 AP 模式（Distro 协议，保证可用性，最终一致性），永久实例走 CP 模式（Raft 协议，保证强一致性，牺牲部分可用性）。配置中心使用 CP 模式，服务发现使用 AP 模式。

> 📖 **参考链接**：[Nacos 架构与一致性协议](https://nacos.io/zh-cn/docs/v2/architecture.html) -- Nacos 同时支持 AP（Distro）和 CP（Raft）两种模式的设计原理

---

### 2. 简述 Nacos 作为注册中心的核心流程。

**答案：** 服务提供者启动时向 Nacos 注册（IP + Port + 元数据）。客户端每 5s 发送心跳维持注册。Nacos 服务端每 5s 检查：15s 未收到心跳标记不健康，30s 未收到心跳剔除实例。服务消费者订阅服务后，Nacos 推送实例变更通知，消费者从健康实例列表中负载均衡选择调用。

> 📖 **参考链接**：[Nacos 服务发现快速开始](https://nacos.io/zh-cn/docs/v2/quickstart.html) -- Nacos 服务注册、心跳、订阅、推送的完整流程

---

### 3. 简述 Sentinel 的熔断降级机制。

**答案：** Sentinel 熔断器有三种状态：CLOSED（正常通过，统计指标）、OPEN（拒绝所有请求，抛出 DegradeException）、HALF_OPEN（放行少量探测请求，试探服务是否恢复）。三种熔断策略：慢调用比例（响应时间超过阈值的请求比例）、异常比例、异常数。熔断时间窗口结束后自动进入 HALF_OPEN。

> 📖 **参考链接**：[Sentinel 熔断降级 Wiki](https://github.com/alibaba/Sentinel/wiki/%E7%86%94%E6%96%AD%E9%99%8D%E7%BA%A7) -- 三种熔断策略与状态机详解

---

### 4. 简述 Spring Cloud Gateway 的请求处理流程。

**答案：** 客户端请求 -> Netty Server 接收 -> RouteLocator 匹配路由（按 Predicate 条件匹配）-> 匹配成功进入 Filter Chain -> Pre Filter 执行（鉴权、限流、添加请求头）-> 转发到后端服务 -> 后端返回响应 -> Post Filter 执行（添加响应头、记录日志）-> 返回客户端。

> 📖 **参考链接**：[Spring Cloud Gateway 工作原理](https://docs.spring.io/spring-cloud/docs/current/reference/html/) -- Gateway Route / Predicate / Filter 工作流程官方说明

---

### 5. 简述 Seata AT 模式的两阶段提交流程。

**答案：** 第一阶段：TM 开启全局事务获得 XID，RM 执行原始 SQL 并生成 undo_log（记录回滚 SQL），在同一本地事务提交，RM 向 TC 注册分支事务。第二阶段提交：TC 通知各 RM 提交，RM 异步删除 undo_log。第二阶段回滚：TC 通知各 RM 回滚，RM 读取 undo_log 执行反向 SQL，删除 undo_log。

> 📖 **参考链接**：[Seata AT 模式原理](https://seata.io/zh-cn/docs/dev/mode/at-mode) -- AT 模式两阶段提交、undo_log、全局锁机制详解

### 6. 简述 Nacos 2.x 相比 1.x 的核心变化。

**答案：** 通信层从 HTTP 短连接升级为 gRPC 长连接。心跳从 HTTP 定时请求改为 gRPC 双向流。服务发现从客户端轮询 + UDP 推送改为 gRPC 双向流实时推送。配置监听从 HTTP 长轮询改为 gRPC 双向流。新增 gRPC 端口 9848（主端口 + 1000）。性能提升 2-3 倍，连接复用减少开销。

> 📖 **参考链接**：[Nacos 2.0 升级文档](https://nacos.io/zh-cn/docs/v2/upgrading/2.0.0-upgrading.html) -- Nacos 2.x 架构变化与 gRPC 通信升级

### 7. 简述 Sentinel 的 8 个 Slot 责任链及其顺序。

**答案：** NodeSelectorSlot（构建调用树）-> ClusterBuilderSlot（构建集群统计）-> LogSlot（记录异常日志）-> StatisticSlot（核心统计：QPS、RT、异常）-> AuthoritySlot（黑白名单）-> SystemSlot（系统保护）-> FlowSlot（流量控制）-> DegradeSlot（熔断降级）。StatisticSlot 是统计核心，FlowSlot 和 DegradeSlot 分别负责限流和熔断。

> 📖 **参考链接**：[Sentinel 工作主流程 Wiki](https://github.com/alibaba/Sentinel/wiki/Sentinel%E5%B7%A5%E4%BD%9C%E4%B8%BB%E6%B5%81%E7%A8%8B%E4%BB%8B%E7%BB%8D) -- Sentinel 8 个 Slot 责任链与 ProcessorSlotChain 详解

### 8. 简述微服务架构的优缺点。

**答案：** 优点：独立部署（每个服务独立构建、测试、部署）、技术栈灵活（不同服务可用不同技术）、高可扩展（热点服务单独扩容）、故障隔离（一个服务故障不影响其他）、团队自治。缺点：分布式复杂性（网络通信、数据一致性、分布式事务）、运维成本高（需要基础设施）、调试困难（跨服务调用链长）、数据一致性挑战。

> 📖 **参考链接**：[Spring Cloud 微服务架构](https://docs.spring.io/spring-cloud/docs/) -- Spring Cloud 微服务设计原则与组件总览

---

### 9. 简述 Nacos 配置中心的三层隔离机制。

**答案：** Namespace（命名空间）：租户级隔离，用于环境隔离（dev/test/prod），不同 Namespace 配置完全隔离。Group（分组）：应用级隔离，按业务模块或应用分组（ORDER_GROUP/USER_GROUP）。Data ID（配置集）：配置级隔离，对应具体配置文件。命名规则：`${application.name}-${profiles.active}.${file-extension}`。

> 📖 **参考链接**：[Nacos 配置管理](https://nacos.io/zh-cn/docs/v2/quickstart-spring-cloud.html) -- Nacos Namespace / Group / Data ID 三层隔离设计

### 10. 简述 Sentinel 和 Hystrix 的核心区别。

**答案：** 隔离策略：Sentinel 使用信号量隔离，Hystrix 使用线程池/信号量隔离。熔断策略：Sentinel 支持慢调用比例/异常比例/异常数三种，Hystrix 仅支持异常比例。流量控制：Sentinel 支持丰富的流控策略（QPS/线程数/热点），Hystrix 不支持。规则配置：Sentinel 支持控制台实时下发，Hystrix 需代码硬编码。维护状态：Sentinel 持续维护，Hystrix 已停更。

> 📖 **参考链接**：[Sentinel vs Hystrix 对比](https://github.com/alibaba/Sentinel/wiki/How-to-use#相关概念) -- Sentinel 与 Hystrix 在隔离、熔断、流控、维护状态上的全面对比

### 1. 设计一个"微服务网关统一鉴权"方案

**场景描述：** 某电商平台有 10+ 个微服务，需要在网关层统一鉴权，支持 JWT Token 校验、白名单路径、用户信息透传。

**设计方案：**

```
1. 客户端请求 -> Gateway
2. GlobalFilter 拦截所有请求
3. 判断路径是否在白名单（登录、注册、公开接口）
   - 白名单 -> 直接转发
   - 非白名单 -> 提取 Authorization Header
4. 校验 JWT Token
   - 无效/过期 -> 返回 401
   - 有效 -> 解析用户信息，添加到请求头（X-User-Id、X-User-Name）
5. 透传到下游服务
```

**关键设计点：**
- 使用 GlobalFilter 实现，Order 设置 -100 保证最先执行
- 白名单配置在 Nacos 配置中心，支持动态更新
- Token 使用 RSA 非对称加密，网关只持有公钥
- 下游服务通过请求头获取用户信息，无需再次解析 Token

> 📖 **参考链接**：
> - [Spring Cloud Gateway GlobalFilter](https://docs.spring.io/spring-cloud/docs/current/reference/html/) -- 自定义 GlobalFilter 实现统一鉴权
> - [Nacos 配置动态刷新](https://nacos.io/zh-cn/docs/v2/quickstart-spring-cloud.html) -- 白名单动态更新方案

### 2. 设计一个"秒杀系统的流量控制"方案

**场景描述：** 秒杀活动开始时，瞬间有 10w+ 并发请求涌入，需要在网关层和服务层分别限流。

**设计方案：**

**网关层限流：**
```
- 使用 Gateway + Sentinel 网关限流
- 配置：QPS 限制 1000，超出直接返回"活动太火爆，请稍后再试"
- 按 IP 限流：每个 IP 每秒最多 10 次请求
```

**服务层限流：**
```
- 秒杀接口使用 @SentinelResource 配置流控规则
- QPS 限制 100（扣减库存是瓶颈）
- 超出 QPS 的请求快速失败，返回"已售罄"
```

**热点参数限流：**
```
- 针对热门商品 ID 单独限流
- 如商品 ID=100 限制 QPS=50，其他商品限制 QPS=100
```

**熔断降级：**
```
- 当库存服务 RT 超过 200ms 或异常比例超过 30%，触发熔断
- 熔断期间返回"系统繁忙，请稍后再试"
- 30s 后半开探测，服务恢复后自动关闭熔断
```

> **生活化类比：服务降级 = 超市高峰期关闭部分收银台外的服务** —— 服务降级就像超市在客流高峰期的运营策略。**平时正常运营**：超市开放所有服务——自助结账、人工收银、礼品包装、退换货、会员办卡、试吃试用、广播点歌。**客流高峰期（系统高负载）**：超市主动关闭非核心服务，把人力集中到核心环节：① 停止礼品包装（关闭推荐功能，只返回基础数据）；② 暂停退换货（关闭日志写入，只读不写）；③ 停止试吃试用（关闭非必要业务接口）；④ 停止广播点歌（关闭实时推送）；⑤ 把所有收银员调到结账（核心下单/支付服务保留全部资源）。**核心特征**：降级是"主动放弃非核心服务，保住核心链路"，与限流（拒绝部分请求）、熔断（被动切断故障）不同。秒杀场景中"商品详情显示默认评价而非实时评价"、"下单页隐藏推荐列表"都是典型的服务降级策略。

> 📖 **第 2 题参考链接**：
> - [Sentinel 流量控制文档](https://github.com/alibaba/Sentinel/wiki/%E6%B5%81%E9%87%8F%E6%8E%A7%E5%88%B6) -- Sentinel QPS 限流、热点参数限流详解
> - [Spring Cloud Gateway 限流](https://docs.spring.io/spring-cloud/docs/current/reference/html/) -- Gateway RequestRateLimiter + Redis 令牌桶实现
> - [Seata 高并发场景](https://seata.io/zh-cn/docs/user/quickstart/) -- 秒杀场景下的分布式事务处理思路

### 3. 设计一个"跨服务下单"的分布式事务方案

**场景描述：** 用户下单需要同时操作订单服务（创建订单）、账户服务（扣余额）、库存服务（减库存），需要保证数据一致性。

**设计方案（Seata AT 模式）：**

```
1. 订单服务使用 @GlobalTransactional 注解
2. 全局事务流程：
   - 订单服务：INSERT INTO orders（分支事务 1）
   - 账户服务：UPDATE account SET balance = balance - ?（分支事务 2）
   - 库存服务：UPDATE inventory SET stock = stock - ?（分支事务 3）
3. 每个分支事务在同一本地事务中生成 undo_log
4. 任一分支失败 -> TC 触发全局回滚 -> 各 RM 读取 undo_log 执行反向 SQL
5. 全部成功 -> TC 触发全局提交 -> 各 RM 异步删除 undo_log
```

**补偿设计：**
```
- 库存不足时，直接抛出异常，Seata 自动回滚
- 账户余额不足时，抛出异常，Seata 自动回滚
- 网络超时等异常，TC 的重试机制保证最终一致性
```

> 📖 **参考链接**：
> - [Seata AT 模式原理](https://seata.io/zh-cn/docs/dev/mode/at-mode) -- AT 模式 undo_log 生成与全局锁机制
> - [Seata 快速开始](https://seata.io/zh-cn/docs/user/quickstart/) -- @GlobalTransactional 注解使用与 TC/RM/TM 三角色协作

### 4. 设计一个"配置中心灰度发布"方案

**场景描述：** 某功能开关需要先在 10% 的实例上生效，验证通过后再全量发布。

**设计方案：**

```
1. 在 Nacos 中创建配置：
   - Data ID: feature-switch.yaml
   - Group: FEATURE_GROUP
   - 内容：feature.new.enabled: false

2. 按标签灰度：
   - 10% 的实例打上标签 version=v2
   - 创建灰度配置：Data ID: feature-switch.yaml，Group: FEATURE_GROUP，标签: v2
   - 灰度配置内容：feature.new.enabled: true

3. 验证通过后：
   - 全量发布：修改默认配置 feature.new.enabled: true
   - 删除灰度配置
```

**关键设计点：**
- 使用 `@ConfigurationProperties` 绑定配置，天然支持动态刷新
- 配置变更后，通过 `@EventListener` 监听 RefreshScopeRefreshedEvent 打印日志
- 灰度期间监控错误率和业务指标，异常时一键回滚

> 📖 **参考链接**：
> - [Nacos 灰度发布](https://nacos.io/zh-cn/docs/v2/quickstart-spring-cloud.html) -- Nacos Beta 发布与标签灰度策略
> - [Spring Cloud @RefreshScope](https://docs.spring.io/spring-cloud/docs/current/reference/html/) -- 配置动态刷新原理与 @ConfigurationProperties 联动

### 5. 设计一个"微服务监控告警"方案

**场景描述：** 某交通系统有 20+ 个微服务，需要监控服务健康状态、接口响应时间、错误率，异常时自动告警。

**设计方案：**

**监控体系：**
```
1. 健康检查：Spring Boot Actuator + Nacos 健康检查
2. 指标采集：Micrometer + Prometheus 拉取指标
3. 链路追踪：SkyWalking 采集调用链
4. 日志收集：ELK（Elasticsearch + Logstash + Kibana）
5. 告警通知：Prometheus AlertManager -> 钉钉/短信
```

**核心指标：**
```
- 服务可用性：Nacos 健康实例数 / 总实例数
- 接口 QPS：Sentinel Dashboard 实时监控
- 接口 RT：P99 响应时间
- 错误率：5xx 错误占比
- 熔断状态：Sentinel 熔断器状态
```

**告警规则：**
```
- 服务不可用：健康实例数 < 1，持续 30s -> 紧急告警
- 错误率 > 5%：持续 1 分钟 -> 警告
- P99 RT > 1000ms：持续 5 分钟 -> 警告
- 熔断器 OPEN：立即告警
- 消费 Lag > 10000：持续 5 分钟 -> 警告
```

> - [Spring Boot Actuator](https://docs.spring.io/spring-boot/docs/current/reference/html/) -- 健康检查、Metrics 指标采集
> - [SkyWalking 官方文档](https://skywalking.apache.org/docs/) -- 链路追踪与告警规则配置
> - [Prometheus AlertManager](https://prometheus.io/docs/alerting/latest/alertmanager/) -- 告警规则与通知渠道
