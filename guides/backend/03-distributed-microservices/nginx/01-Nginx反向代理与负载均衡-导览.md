## 一、Nginx概述：高性能Web服务器与反向代理服务器

### Master-Worker架构设计

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx采用一个Master进程管理多个Worker进程的多进程架构，Master不处理业务，Worker实际承接请求。 |
| 能做什么 | 管理Worker生命周期；承接用户请求并发处理；支持热升级与平滑重启；进程崩溃互不影响。 |
| 怎么用 | `worker_processes auto;` 配置Worker数量等于CPU核心数。 |
| 原理和工作流程 | Master进程读取并验证配置文件，fork出多个Worker子进程，每个Worker单线程运行，采用异步非阻塞事件驱动模型（如epoll）处理成百上千连接。Worker数量通常等于CPU核心数，绑定核心减少切换开销。进程间相互独立，单个Worker崩溃由Master重新拉起，不影响其他Worker。 |
| 缺点 | 单Worker单线程，CPU密集型任务会阻塞该Worker上的所有连接；进程间共享数据需通过共享内存，编程模型相对复杂。 |

### 与Apache、Tomcat的对比

| 维度 | 内容 |
|------|------|
| 是什么 | 三款主流Web服务软件在定位、处理模型、并发能力等维度的横向对照。 |
| 能做什么 | 区分静态服务器、动态容器、反向代理的适用边界；指导生产环境选型与组合部署。 |
| 怎么用 | 生产常用Nginx作为前置反向代理与静态服务，Tomcat作为Java应用后端。 |
| 原理和工作流程 | Nginx基于异步非阻塞事件驱动，多进程单线程，内存轻量，擅长静态资源与反向代理；Apache采用同步多进程/多线程，每连接一进程/线程，内存较重，适合嵌入式动态处理；Tomcat是Java Servlet容器，多线程模型，专为Java Web应用服务。三者处理模型差异决定并发能力与适用场景不同。 |
| 缺点 | 对比维度较粗，未覆盖具体版本差异与扩展模块能力；实际选型还需结合业务特征、运维成本与团队技术栈综合判断。 |

## 二、nginx.conf配置结构：http、server、location层级关系

### 全局块

| 维度 | 内容 |
|------|------|
| 是什么 | nginx.conf最外层配置区，定义影响整个Nginx进程的指令。 |
| 能做什么 | 设置运行用户；配置Worker进程数；指定错误日志与PID路径；定义events块连接参数。 |
| 怎么用 | `user nginx; worker_processes 4; error_log /var/log/nginx/error.log; pid /var/run/nginx.pid;` |
| 原理和工作流程 | 全局块指令在Master进程启动时读取并生效，作用于整个Nginx实例。events块中的worker_connections限定每个Worker最大连接数，use epoll选择Linux下高效事件模型。这些参数决定Nginx进程的基础运行环境与并发上限。 |
| 缺点 | 参数调整需重启或重载Nginx才生效；部分参数（如worker_processes）设置不当会造成CPU浪费或进程切换开销过大。 |

### http块：配置HTTP服务器全局参数

| 维度 | 内容 |
|------|------|
| 是什么 | nginx.conf中定义HTTP服务器全局参数的配置块，是server与location的父容器。 |
| 能做什么 | 导入MIME类型映射；定义日志格式与访问日志；开启sendfile、gzip、keepalive等全局优化；包含多个server虚拟主机。 |
| 怎么用 | `http { include mime.types; default_type application/octet-stream; sendfile on; keepalive_timeout 65; gzip on; }` |
| 原理和工作流程 | http块指令在Nginx启动时解析，作用于所有HTTP请求。log_format定义日志字段变量，access_log按格式写入访问日志。sendfile开启零拷贝传输，keepalive_timeout控制长连接保持时间，gzip开启响应压缩。http块内可嵌套多个server块，每个server代表一个虚拟主机。 |
| 缺点 | 全局参数对全部虚拟主机生效，精细化控制需在server或location层级覆盖；指令层级较深，配置错误难以快速定位。 |

### server块：定义一个虚拟主机

| 维度 | 内容 |
|------|------|
| 是什么 | http块内定义一个虚拟主机的配置单元，通过监听端口与域名区分服务。 |
| 能做什么 | 监听指定端口；绑定一个或多个域名；包含多个location处理规则；实现基于端口或域名的虚拟主机隔离。 |
| 怎么用 | `server { listen 80; server_name example.com; location / { ... } }` |
| 原理和工作流程 | Nginx接收请求后，根据listen监听端口与server_name匹配Host头，定位到对应server块。匹配优先级为精确域名、前缀通配域名、正则域名。server块内的指令作用于该虚拟主机的所有请求，location块进一步细分URI处理逻辑。 |
| 缺点 | 域名匹配规则较复杂，配置不当易导致请求落到错误虚拟主机；大量虚拟主机时配置文件臃肿，维护成本上升。 |

### location块：匹配特定URI并进行配置

| 维度 | 内容 |
|------|------|
| 是什么 | server块内基于URI匹配规则进行请求分发与配置的最小逻辑单元。 |
| 能做什么 | 精确匹配首页；前缀匹配静态资源目录；正则匹配图片等文件后缀；通用匹配兜底转发后端。 |
| 怎么用 | `location = / { ... }` `location ^~ /static/ { ... }` `location ~* \.(gif|jpg)$ { ... }` `location / { proxy_pass http://backend; }` |
| 原理和工作流程 | Nginx按优先级顺序匹配location：精确匹配(=)最高，其次前缀匹配(^~)，再是正则匹配(~/~*)，最后最长前缀匹配与通用匹配(/)。命中精确匹配或^~后不再检查正则。正则之间按配置顺序匹配，命中即停止。匹配成功后执行location内指令。 |
| 缺点 | 匹配优先级规则繁琐，正则与前缀混用时易出错；嵌套location支持有限，复杂路由逻辑可读性差。 |

## 三、反向代理核心配置：proxy_pass、proxy_set_header与WebSocket代理

### 什么是反向代理

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx位于客户端与后端服务器之间，接收请求并转发给后端，再将响应返回客户端的代理模式。 |
| 能做什么 | 隐藏后端真实地址；实现负载均衡；统一鉴权与日志；承接SSL卸载与静态资源处理。 |
| 怎么用 | `location / { proxy_pass http://backend; }` |
| 原理和工作流程 | 客户端请求到达Nginx，Nginx解析请求头与URL，依据location匹配反向代理配置，构建发往后端的新请求（可修改请求头），建立与后端连接并转发请求，接收后端响应后回传客户端，处理连接复用或释放。整个过程对客户端透明，客户端感知不到后端存在。 |
| 缺点 | 增加一跳网络延迟；Nginx自身成为单点，需配合高可用方案；连接与缓冲管理不当可能放大后端压力。 |

### proxy_pass指令

| 维度 | 内容 |
|------|------|
| 是什么 | 反向代理核心指令，指定后端服务器地址与可选路径。 |
| 能做什么 | 转发请求到单机后端；转发到upstream服务器组；控制URI是否被替换。 |
| 怎么用 | `proxy_pass http://127.0.0.1:8080;`（保留原URI） `proxy_pass http://127.0.0.1:8080/;`（替换location匹配部分） |
| 原理和工作流程 | 当proxy_pass不带URI路径时，Nginx将原始请求URI完整透传给后端；当带URI路径（含结尾斜杠）时，Nginx会用proxy_pass的路径替换location匹配的部分。区别源于Nginx对location与proxy_pass的字符串拼接逻辑。 |
| 缺点 | 带路径与不带路径的行为差异易混淆，配置错误会导致后端收到错误URI；变量形式的proxy_pass（如含$host）会触发DNS解析，需配置resolver。 |

### proxy_set_header指令

| 维度 | 内容 |
|------|------|
| 是什么 | 反向代理时设置转发给后端服务器请求头的指令，用于传递客户端真实信息。 |
| 能做什么 | 传递原始Host；传递客户端真实IP；传递代理链路IP；传递请求协议。 |
| 怎么用 | `proxy_set_header Host $host;` `proxy_set_header X-Real-IP $remote_addr;` `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` |
| 原理和工作流程 | Nginx转发请求时会重置部分请求头，proxy_set_header在转发前注入指定头。$host为原始Host头，$remote_addr为直连客户端IP，$proxy_add_x_forwarded_for在原有X-Forwarded-For基础上追加当前直连IP，形成完整代理链路。后端据此还原客户端真实地址与协议。 |
| 缺点 | 需后端配合解析并信任这些头，否则可被伪造；多层代理时X-Forwarded-For链路需谨慎校验，防止IP伪造攻击。 |

### 常用超时配置

| 维度 | 内容 |
|------|------|
| 是什么 | 反向代理场景下控制Nginx与后端交互各阶段超时时间的指令集合。 |
| 能做什么 | 限制连接后端超时；限制读取后端响应超时；限制发送请求超时；控制响应缓冲行为。 |
| 怎么用 | `proxy_connect_timeout 60s;` `proxy_read_timeout 60s;` `proxy_send_timeout 60s;` `proxy_buffering on;` |
| 原理和工作流程 | proxy_connect_timeout限制TCP连接建立阶段超时，proxy_read_timeout限制两次读操作间隔超时，proxy_send_timeout限制两次写操作间隔超时。proxy_buffering开启时Nginx缓存后端响应再返回客户端，减轻后端压力。超时触发后Nginx返回502或504错误。 |
| 缺点 | 超时值设置过短会误杀慢请求，过长会导致连接资源占用过久；buffering开启会延迟响应首字节到达客户端，影响TTFB体验。 |

### WebSocket代理配置

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx代理WebSocket长连接协议所需的特殊配置。 |
| 能做什么 | 升级HTTP连接为WebSocket；保持长连接不断开；适配心跳与持久通信。 |
| 怎么用 | `proxy_http_version 1.1;` `proxy_set_header Upgrade $http_upgrade;` `proxy_set_header Connection "upgrade";` `proxy_read_timeout 3600s;` |
| 原理和工作流程 | WebSocket依赖HTTP/1.1的Upgrade机制完成协议升级。proxy_http_version设为1.1启用升级协商，Upgrade头与Connection头告知后端将连接升级为WebSocket。升级成功后连接变为全双工长连接，proxy_read_timeout需调大以避免空闲断开，默认60s会中断WebSocket会话。 |
| 缺点 | 长连接占用Worker连接数资源，高并发下需评估连接数上限；超时设置不当易导致空闲会话被断开或连接资源泄漏。 |

## 四、负载均衡六种算法对比：轮询、加权、ip_hash、least_conn、url_hash、fair

### 1. 轮询（默认）

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx upstream默认调度算法，按时间顺序逐一将请求分配到各后端服务器。 |
| 能做什么 | 均等分配请求；无需额外参数；适配性能相近的无状态集群。 |
| 怎么用 | `upstream backend { server 192.168.1.10:8080; server 192.168.1.11:8080; }` |
| 原理和工作流程 | Nginx维护后端服务器列表，每个请求按列表顺序轮流分发到下一台服务器，循环往复。无需显式声明算法，upstream块不指定调度指令时即生效。请求分配完全均等，不考虑服务器当前负载与性能差异。 |
| 缺点 | 不考虑服务器性能差异，弱机会成为瓶颈；无会话保持，同一用户请求可能落到不同节点。 |

### 2. 加权轮询（weight）

| 维度 | 内容 |
|------|------|
| 是什么 | 按权重比例分配请求的轮询算法，权重越高分配请求越多。 |
| 能做什么 | 根据服务器性能差异化分配负载；适配硬件配置不均的集群。 |
| 怎么用 | `server 192.168.1.10:8080 weight=5;` `server 192.168.1.11:8080 weight=3;` |
| 原理和工作流程 | 每台后端服务器配置weight值，Nginx按权重比例构建调度序列。如权重5:3:2，则每10个请求中5个分给第一台、3个分给第二台、2个分给第三台，循环执行。分配比例与权重成正比，性能强的机器承担更多请求。 |
| 缺点 | 权重静态配置，无法根据运行时负载动态调整；权重设置依赖人工经验，配置不当会导致负载不均。 |

### 3. ip_hash

| 维度 | 内容 |
|------|------|
| 是什么 | 基于客户端IP哈希结果分配后端服务器的调度算法，实现会话保持。 |
| 能做什么 | 同一IP固定访问同一节点；解决后端Session共享问题；适配有状态应用。 |
| 怎么用 | `upstream backend { ip_hash; server 192.168.1.10:8080; server 192.168.1.11:8080; }` |
| 原理和工作流程 | Nginx对客户端IP（前三个八位组）做哈希计算，根据哈希值与后端服务器数量取模，将请求固定分配到某台服务器。同一客户端IP始终落到同一节点，节点变更时重新计算哈希。当某节点故障时，该IP的请求会被重新分配到其他节点。 |
| 缺点 | 后端节点增减会导致大量IP重新分配，会话失效；NAT环境下大量用户共享同一出口IP会导致负载严重不均。 |

### 4. least_conn（最少连接）

| 维度 | 内容 |
|------|------|
| 是什么 | 将请求分配给当前活动连接数最少的后端服务器的调度算法。 |
| 能做什么 | 动态感知后端连接负载；避免繁忙服务器更忙；适配请求处理时间差异大的场景。 |
| 怎么用 | `upstream backend { least_conn; server 192.168.1.10:8080; server 192.168.1.11:8080; }` |
| 原理和工作流程 | Nginx实时维护各后端服务器的活动连接计数，每次收到请求时遍历服务器列表，选择当前活动连接数最少的节点分发。若多个节点连接数相同，则对这些节点执行加权轮询。连接建立时计数加一，连接释放时计数减一。 |
| 缺点 | 每次调度需遍历并比较连接数，增加少量计算开销；连接数少不代表服务器性能空闲，可能误判慢节点的处理能力。 |

### 5. url_hash（URL哈希）

| 维度 | 内容 |
|------|------|
| 是什么 | 基于请求URL哈希结果分配后端服务器的调度算法，同一URL固定访问同一节点。 |
| 能做什么 | 提高后端缓存命中率；适配缓存服务器与内容分发场景；减少重复回源。 |
| 怎么用 | `upstream backend { hash $request_uri; server 192.168.1.10:8080; server 192.168.1.11:8080; }` |
| 原理和工作流程 | Nginx对请求URI做哈希计算，根据哈希值与后端服务器数量取模，将同一URL的请求固定分发到同一节点。后端节点若部署本地缓存，相同URL请求命中同一缓存，提升命中率。需要Nginx 1.7.2+版本支持。 |
| 缺点 | URL变化会导致请求落到不同节点，缓存失效；后端节点增减会引发哈希重分布，缓存大面积失效。 |

### 6. fair（第三方）

| 维度 | 内容 |
|------|------|
| 是什么 | 根据后端服务器响应时间分配请求的第三方调度算法，响应时间短的优先分配。 |
| 能做什么 | 智能感知后端处理能力；优先分给处理快的服务器；追求最佳整体响应。 |
| 怎么用 | `upstream backend { server 192.168.1.10:8080; server 192.168.1.11:8080; fair; }` |
| 原理和工作流程 | nginx-upstream-fair模块记录每个后端服务器的响应时间，调度时优先将请求分给平均响应时间最短的节点。响应时间通过实际请求采样统计，动态更新。响应快的节点承担更多请求，实现基于实际能力的智能均衡。 |
| 缺点 | 依赖第三方模块，需编译安装，运维复杂度增加；响应时间统计存在滞后，瞬时波动可能导致调度抖动。 |

## 五、Rewrite重定向与URL重写

### 5.1 rewrite指令语法

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx用于URL重定向与重写的指令，通过正则匹配替换URI。 |
| 能做什么 | 正则匹配URI；引用捕获组重写路径；通过flag控制后续行为；实现域名迁移与协议跳转。 |
| 怎么用 | `rewrite regex replacement [flag];` 如 `rewrite ^/old/(.*)$ /new/$1 last;` |
| 原理和工作流程 | rewrite指令在请求处理阶段执行，regex对当前URI做正则匹配，匹配成功后用replacement替换URI。replacement中可用$1、$2引用正则分组。flag参数决定替换后是否重新匹配location、是否返回重定向。rewrite可在server或location块中配置，按配置顺序执行。 |
| 缺点 | 正则匹配存在性能开销，复杂正则在高压场景下影响吞吐；配置顺序敏感，多条rewrite规则叠加时调试困难。 |

### 5.2 flag参数详解

| 维度 | 内容 |
|------|------|
| 是什么 | rewrite指令的第四个参数，控制重写后是否重新匹配location及重定向行为。 |
| 能做什么 | last重新匹配location；break留在当前location；redirect返回302临时重定向；permanent返回301永久重定向。 |
| 怎么用 | `rewrite ^/old/(.*)$ /new/$1 last;` `rewrite ^/api/(.*)$ /v2/$1 break;` `return 301 https://$host$request_uri;` |
| 原理和工作流程 | last停止当前rewrite规则集，用新URI重新发起location匹配，相当于换地方继续处理；break停止当前rewrite规则集，不再重新匹配location，继续在当前location执行后续指令；redirect返回302，浏览器地址栏变化但不缓存；permanent返回301，浏览器永久缓存新地址。 |
| 缺点 | last使用不当可能造成循环重写（rewrite循环上限10次后返回500）；redirect与permanent区别仅在于缓存语义，误用会导致SEO或用户体验问题。 |

### 5.3 if条件判断

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx配置中基于变量值进行条件分支的指令。 |
| 能做什么 | 判断请求方法；匹配User-Agent；检测文件或目录是否存在；实现设备重定向等逻辑。 |
| 怎么用 | `if ($request_method = POST) { ... }` `if ($http_user_agent ~* "mobile") { ... }` `if (-f $request_filename) { ... }` |
| 原理和工作流程 | if在请求处理阶段求值condition，支持=、!=、~、~*、!~等运算符及-f、-d、-e文件检测。条件为真时执行块内指令。if可在server或location块中使用，求值结果影响后续rewrite、return、set等指令。 |
| 缺点 | if在location块内的行为可能不符合预期，嵌套与组合易产生副作用，被称为Nginx的邪恶之物；复杂逻辑应优先使用try_files或map指令。 |

### 5.4 常见重定向场景

| 维度 | 内容 |
|------|------|
| 是什么 | rewrite与return指令在生产环境中的典型应用模式。 |
| 能做什么 | HTTP跳HTTPS；旧域名跳新域名；去除URL后缀；基于UA的设备重定向。 |
| 怎么用 | `return 301 https://$host$request_uri;` `rewrite ^/(.*)$ https://new-domain.com/$1 permanent;` `rewrite ^/(.*)\.php$ /$1 last;` |
| 原理和工作流程 | HTTP跳HTTPS通过return 301将80端口请求永久重定向到HTTPS；旧域名跳转用rewrite配合permanent捕获路径并拼接到新域名；去后缀用rewrite重写URI后以last重新匹配；设备重定向通过set变量记录UA判断结果，再以rewrite跳转到移动站点。 |
| 缺点 | 301重定向会被浏览器长期缓存，回滚困难；基于UA的重定向规则需持续维护设备特征列表，覆盖不全易误判。 |

## 六、健康检查与upstream完整配置示例

### 后端服务器状态参数

| 维度 | 内容 |
|------|------|
| 是什么 | upstream块中为每台后端服务器配置的状态控制参数。 |
| 能做什么 | 设置权重；标记备用服务器；标记永久下线；配置失败次数与隔离时间。 |
| 怎么用 | `server 192.168.1.10:8080 weight=5 max_fails=3 fail_timeout=30s;` `server 192.168.1.12:8080 backup;` `server 192.168.1.13:8080 down;` |
| 原理和工作流程 | weight控制加权轮询分配比例；backup标记的节点仅在所有非备份节点故障时启用；down标记节点不参与调度，用于维护；max_fails设定允许失败次数，达到阈值后在fail_timeout时间内将节点标记为不可用，超时后重新尝试。 |
| 缺点 | max_fails基于被动检查，无法提前发现故障；backup节点长期闲置，资源利用率低；fail_timeout过短会导致故障节点被频繁试探。 |

### 被动健康检查

| 维度 | 内容 |
|------|------|
| 是什么 | Nginx默认提供的健康检查机制，在请求处理过程中被动发现后端故障。 |
| 能做什么 | 基于请求失败次数标记节点不可用；超时后自动恢复探测；无需额外模块。 |
| 怎么用 | `server 192.168.1.10:8080 max_fails=2 fail_timeout=30s;` |
| 原理和工作流程 | Nginx转发请求到后端时，若连接失败或响应异常，对该节点的失败计数加一。失败次数达到max_fails后，在fail_timeout时间内将该节点标记为不可用，不再分发请求。fail_timeout过后重新尝试分发请求，成功则恢复节点，失败继续隔离。整个过程依赖实际请求触发，无主动探测。 |
| 缺点 | 无法提前发现故障，首个请求仍会落到故障节点导致用户感知错误；低流量场景下故障发现滞后。 |

### 主动健康检查（第三方模块）

| 维度 | 内容 |
|------|------|
| 是什么 | 通过第三方模块定期主动向后端发送探测请求的健康检查机制。 |
| 能做什么 | 定时探测后端健康状态；基于连续成功/失败次数判定可用性；提前隔离故障节点。 |
| 怎么用 | `check interval=5000 rise=2 fall=3 timeout=2000;` |
| 原理和工作流程 | nginx-upstream-healthcheck模块按interval间隔向后端发送健康检查请求，timeout限定探测超时。连续rise次成功则标记节点可用，连续fall次失败则标记不可用。探测独立于业务请求，Nginx主动维护节点健康状态表，调度时跳过不可用节点。 |
| 缺点 | 依赖第三方模块编译安装，增加部署复杂度；探测请求增加后端额外负载；探测接口与真实业务接口行为可能不一致，存在误判。 |
