# Nginx - 概念对比速查

---

### 正向代理 vs 反向代理

| 对比维度 | 正向代理 | 反向代理 |
|---------|---------|---------|
| 核心定位 | 代理客户端，帮助客户端访问外部网络资源 | 代理服务端，接收客户端请求并转发到后端服务器 |
| 代理方向 | 客户端 -> 代理 -> 目标服务器 | 客户端 -> 反向代理 -> 后端服务器 |
| 客户端感知 | 客户端需要配置代理地址，知道代理的存在 | 客户端无感知，以为直接访问目标服务器 |
| 服务端感知 | 目标服务器不知道真实客户端，只知道代理 | 后端服务器不知道真实客户端，只知道反向代理 |
| 典型用途 | VPN 科学上网、内网穿透、访问控制 | 负载均衡、SSL 卸载、缓存加速、安全防护 |
| 配置位置 | 在客户端侧配置（浏览器、系统代理设置） | 在服务端侧配置（Nginx 服务器） |
| 安全性 | 隐藏客户端真实 IP | 隐藏后端服务器真实 IP，统一入口防护 |
| 选择建议 | 客户端需要突破网络限制时使用 | 服务端需要统一入口管理和负载分发时使用 |

### 负载均衡算法对比：轮询 vs 权重 vs ip_hash

| 对比维度 | 轮询（round-robin） | 加权轮询（weight） | ip_hash |
|---------|-------------------|-------------------|---------|
| 核心定位 | 依次将请求分发到每个后端服务器 | 根据服务器权重比例分配请求 | 根据客户端 IP 的哈希值固定路由到同一服务器 |
| 分发策略 | 循环顺序分发，每个服务器平均分配 | 权重越高的服务器分配越多请求 | 同一客户端 IP 始终路由到同一后端服务器 |
| 适用场景 | 后端服务器性能一致的无状态服务 | 后端服务器性能不一致（如不同配置的机器） | 需要 Session 保持的场景（如登录状态） |
| Session 保持 | 不保证，请求可能分发到不同服务器 | 不保证，请求可能分发到不同服务器 | 保证同一客户端 IP 请求到同一服务器 |
| 服务器增减影响 | 平均分配，无影响 | 权重调整后重新按比例分配 | 哈希值变化，部分客户端路由可能改变 |
| 配置示例 | 默认值，无需额外配置 | `server backend1 weight=3;` | `ip_hash;` 放在 upstream 块第一行 |
| 选择建议 | 后端同构的首选方案 | 后端异构（不同性能）时的首选 | 需要 Session 粘性且无共享存储时使用 |

### keepalive 长连接 vs 短连接

| 对比维度 | keepalive 长连接 | 短连接 |
|---------|-----------------|-------|
| 核心定位 | TCP 连接建立后保持不关闭，复用已建立的连接 | 每次请求新建 TCP 连接，请求完成后立即关闭 |
| 连接建立过程 | 首次请求建立连接，后续请求复用同一连接 | 每次请求都需要三次握手建立连接 |
| TCP 握手开销 | 仅首次握手，后续请求零开销 | 每次请求都需要完整的三次握手 + 四次挥手 |
| 资源占用 | 持续占用连接和内存资源 | 请求结束后释放连接资源 |
| 并发能力 | 连接数有限，高并发时可能耗尽连接 | 可支持更多并发请求（但效率低） |
| 适用场景 | 客户端与 Nginx 之间（HTTP/1.1 默认 keepalive） | Nginx 与后端服务器之间（默认短连接） |
| 配置方式 | `keepalive_timeout 65;` 客户端保持连接；`keepalive 32;` upstream 保持连接池 | 默认行为，无需额外配置 |
| 选择建议 | 客户端侧始终开启 keepalive 减少握手开销；后端侧根据实际负载选择性开启 upstream keepalive | 后端服务器性能敏感或连接数充足时可用短连接 |

### root vs alias

| 对比维度 | root | alias |
|---------|------|-------|
| 核心定位 | 指定站点根目录，请求 URI 会拼接在根目录之后 | 把 location 匹配到的路径替换为指定目录 |
| 路径拼接规则 | 最终路径 = `root` + 完整 URI（含 location 部分） | 最终路径 = `alias` 指定的目录 + URI 中**去掉 location 部分**的剩余内容 |
| 示例配置 | `location /static/ { root /var/www; }` | `location /static/ { alias /var/www/assets/; }` |
| 示例请求映射 | 请求 `/static/a.png` → `/var/www/static/a.png` | 请求 `/static/a.png` → `/var/www/assets/a.png` |
| 末尾斜杠要求 | 无特殊要求 | 目录类 location 的 `alias` 末尾必须带 `/`，否则拼接出错 |
| 常见用途 | 站点整体根目录、按目录结构存放的静态资源 | 把某个 URL 前缀映射到磁盘上完全不同的目录 |
| 常见误区 | 以为 root 会替换 location 前缀，导致多出一层目录而 404 | 忘记在 `alias` 末尾加斜杠，路径拼接错乱导致 404 |
| 选择建议 | 磁盘目录结构与 URL 结构一致时用 `root`；URL 前缀与磁盘目录不一致时用 `alias` | |

### proxy_pass 带斜杠 vs 不带斜杠

| 对比维度 | `proxy_pass http://backend;`（不带 URI） | `proxy_pass http://backend/;`（带 URI，以 `/` 结尾） |
|---------|----------------------------------------|---------------------------------------------------|
| 核心定位 | 只指定后端地址，不做路径替换 | 指定后端地址同时声明替换路径 |
| URI 处理方式 | 保留客户端原始 URI，原样转发 | 用 `proxy_pass` 中的 URI **替换掉 location 匹配到的部分** |
| 示例配置 | `location /api { proxy_pass http://127.0.0.1:8080; }` | `location /api/ { proxy_pass http://127.0.0.1:8080/; }` |
| 示例请求映射 | `/api/user` → `http://127.0.0.1:8080/api/user` | `/api/user` → `http://127.0.0.1:8080/user` |
| 后端看到的路径 | 与前端请求路径一致 | 去掉了 location 前缀 |
| 适用场景 | 后端路由与前端路径完全一致（最常见） | 前端有统一前缀、后端接口没有该前缀 |
| 常见误区 | 本想剥掉前缀却漏写斜杠，导致后端 404 | 本想保留前缀却多写了斜杠，导致路径被截断 |
| 选择建议 | 不确定时优先用不带 URI 的写法，让前后端路径保持一致；确需剥前缀时，`location` 与 `proxy_pass` 的斜杠要成对出现 | |

### 负载均衡六种算法对比

| 算法 | 实现方式 | 会话保持 | 负载感知 | 优点 | 缺点 | 适用场景 |
|------|---------|---------|---------|------|------|---------|
| 轮询（round-robin） | 按顺序轮流分发 | 否 | 否 | 简单高效，默认即用 | 不考虑后端性能差异 | 后端性能相近的无状态服务 |
| 加权轮询（weight） | 按权重比例分配 | 否 | 部分 | 可控制分配比例 | 权重是静态的，不随实际负载变化 | 后端配置差异明显的异构集群 |
| ip_hash | 按客户端 IP 哈希固定路由 | 是 | 否 | 会话保持，无需共享存储 | 可能负载不均（IP 集中时） | 需要 Session 粘性且无 Redis 共享存储 |
| least_conn | 选当前连接数最少的后端 | 否 | 是 | 动态均衡，避免忙闲不均 | 有少量计算开销 | 请求处理时间差异大的场景 |
| url_hash | 按请求 URI 哈希固定路由 | 否（按 URL 维度固定） | 否 | 提高后端缓存命中率 | 配置复杂 | 缓存场景（同一 URL 命中同一后端） |
| fair | 按后端响应时间动态调度 | 否 | 是 | 最智能，优先给响应快的后端 | 属第三方模块，已多年未维护，兼容性差 | 追求最佳响应（生产建议改用 Nginx Plus 的 `least_time`） |

> 选型顺序建议：无状态服务先用轮询；后端异构加 `weight`；需要会话保持优先把 Session 外置到 Redis，其次才考虑 `ip_hash`；请求耗时差异大用 `least_conn`。

### rewrite 四种 flag 对比

| 对比维度 | `last` | `break` | `redirect` | `permanent` |
|---------|--------|---------|-----------|------------|
| 核心定位 | 停止当前 rewrite 规则，用新 URI 重新匹配 location | 停止当前 rewrite 规则，留在当前 location 继续执行 | 返回 302 临时重定向 | 返回 301 永久重定向 |
| 是否重新匹配 location | 是 | 否 | 否（客户端重新发起请求） | 否（客户端重新发起请求） |
| 浏览器地址栏 | 不变 | 不变 | 变化 | 变化 |
| 浏览器是否缓存 | 不涉及 | 不涉及 | 不缓存（临时） | 会长期缓存（永久） |
| 是否产生额外请求 | 否，服务端内部处理 | 否，服务端内部处理 | 是，客户端再发一次请求 | 是，客户端再发一次请求 |
| 典型用途 | URL 重写后需要交给另一个 location 处理 | 在当前 location 内改写 URI 后直接交给后端 | 临时 URL 跳转、灰度切换 | 域名迁移、URL 永久变更 |
| 常见误区 | 想留在当前 location 却用了 `last`，造成重复匹配甚至循环 | 想切换 location 却用了 `break`，新 URI 未被正确处理 | 临时跳转误用 `permanent`，改回配置后用户仍访问旧地址 | 永久变更误用 `redirect`，旧地址长期可访问、权重无法传递 |
| 选择建议 | 需要跨 location 处理用 `last`；只改 URI 用 `break`；涉及客户端地址变化时，临时用 `redirect`、永久用 `permanent` | | | |
