# project - 概念对比速查

> 快速对比本模块涉及的核心概念，帮助理解技术选型与架构决策依据。

---

## 实时计算 vs 离线计算

| 对比维度 | 实时计算（流处理） | 离线计算（批处理） |
|---------|------------------|------------------|
| 数据处理方式 | 逐条或微批次处理，数据到达即处理 | 批量处理，按固定时间窗口（小时/天）调度 |
| 延迟 | 毫秒到秒级 | 分钟到小时级 |
| 数据范围 | 当前窗口或增量数据 | 全量历史数据 |
| 典型引擎 | Flink、Spark Streaming、Kafka Streams | Spark、Hive、MapReduce |
| 数据存储 | 内存 + 状态后端（RocksDB） | 磁盘（HDFS） |
| 吞吐量 | 单条低延迟，总体中等 | 单次高吞吐，延迟高 |
| 适用场景 | 实时大屏、异常检测、实时推荐、风控 | 日报、周报、年度汇总、数据仓库 ETL |
| 容错机制 | Checkpoint + Savepoint 状态恢复 | 任务重跑（幂等写入） |
| 结果精度 | 近似计算（基于窗口），99.9% 精度 | 精确计算，100% 精度 |
| 资源消耗 | 长期占用计算资源 | 任务执行时占用，完成后释放 |
| 开发复杂度 | 需要考虑窗口、水位线、状态管理 | 逻辑相对简单，SQL 即可 |
| 本项目使用 | stats-service 消费 Kafka 写入 ClickHouse 后物化视图聚合，属于近实时 | ClickHouse 预聚合表的日趋势查询，属于轻度离线 |

**选择原则**：延迟敏感用实时计算，精度优先或全量分析用离线计算。大多数场景采用 Lambda 架构（实时 + 离线互补）。

## Flink vs Spark Streaming

| 对比维度 | Flink | Spark Streaming |
|---------|-------|-----------------|
| 处理模型 | 真正的流处理（逐条处理），批处理是流的特例 | 微批次处理（将流切分为小批次），底层是批处理引擎 |
| 延迟 | 毫秒级（亚秒级） | 秒级（微批次间隔通常 500ms-几秒） |
| 状态管理 | 内置状态后端（RocksDB/内存），支持大状态 | 基于 DStream 的 updateStateByKey 或 Structured Streaming 的状态存储 |
| 窗口机制 | 滚动窗口、滑动窗口、会话窗口、全局窗口，原生支持 | 滚动窗口、滑动窗口，会话窗口需自定义 |
| 时间语义 | 事件时间、处理时间、摄入时间，Watermark 机制成熟 | 事件时间（Structured Streaming），Watermark 支持较晚加入 |
| 容错 | Checkpoint/Savepoint，Exactly-Once 语义 | Checkpoint/WAL，Exactly-Once（需幂等 Sink） |
| 背压 | 天然支持，基于 TCP 流量控制 | 微批次模式下具备天然背压能力 |
| 吞吐量 | 高（百万条/秒） | 微批次模式高吞吐，延迟略高 |
| 生态集成 | 独立项目，与 Kafka/ES/ClickHouse 原生集成 | Spark 生态（MLlib、GraphX、Spark SQL）统一 |
| SQL 支持 | Flink SQL 成熟，支持流批一体 | Spark SQL 成熟，Structured Streaming 支持流式 SQL |
| 部署模式 | Standalone、YARN、K8s | Standalone、YARN、K8s、Mesos |
| 本项目关联 | 可用于替代 stats-service 的 Kafka 消费逻辑，实现更复杂的流式聚合 | 可用于离线 T+1 报表，补充 ClickHouse 覆盖不到的复杂分析 |

**选择原则**：纯实时低延迟场景选 Flink；已有 Spark 技术栈且延迟要求不苛刻选 Spark Streaming；需要统一流批一体选 Flink。

## Kafka vs Pulsar

| 对比维度 | Kafka | Pulsar |
|---------|-------|--------|
| 架构 | Broker 耦合存储与计算 | 计算层（Broker）与存储层（BookKeeper）分离 |
| 消息模型 | 发布-订阅，基于 Topic-Partition | 发布-订阅 + 队列（Shared/Exclusive/Failover 订阅模式） |
| 分区扩展 | 分区数创建后不可减少，需整体规划 | 分区数可动态调整，无需停止服务 |
| 多租户 | 通过 ACL 和 Topic 前缀模拟 | 原生支持 Tenant/Namespace 多租户隔离 |
| 消息确认 | 基于 Offset 顺序确认 | 支持单条消息确认（Ack），适合队列场景 |
| 延迟消息 | 不支持原生延迟队列 | 支持原生延迟消息投递 |
| 死信队列 | 需自行实现 | 原生支持死信队列（DLQ） |
| 跨地域复制 | MirrorMaker 异步复制 | 原生 Geo-Replication 内置支持 |
| 存储分层 | 需借助外部存储（S3 connector） | 原生 Tiered Storage，冷数据自动卸载到廉价存储 |
| 吞吐量 | 极高（百万 TPS），顺序写磁盘 | 高（百万 TPS），但多层架构有额外开销 |
| 延迟 | 低（毫秒级） | 低（毫秒级），但略高于 Kafka（因 BookKeeper 层） |
| 运维复杂度 | 依赖 Zookeeper（KRaft 模式可移除），组件少 | 需维护 Broker + BookKeeper + Zookeeper 三层，运维复杂 |
| 生态成熟度 | 极高，大数据生态事实标准 | 增长中，生态不如 Kafka 丰富 |
| 本项目使用 | 选定 Kafka 3.x，生态成熟、高吞吐匹配订单事件流需求 | 若需要队列模式消费 + 原生延迟消息，可考虑替换 |

**选择原则**：生态成熟优先选 Kafka；需要原生多租户、队列消费、延迟消息、存储分层选 Pulsar；已有 Kafka 运维经验且满足需求无需迁移。
