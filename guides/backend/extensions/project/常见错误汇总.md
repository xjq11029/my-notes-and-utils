# project - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 订单创建成功但 Kafka 消息丢失 | 未使用 Kafka 事务消息，先写 MySQL 再发消息，发消息失败时 MySQL 已提交无法回滚 | 使用 `@Transactional` 绑定本地事务，通过 `kafkaTemplate.executeInTransaction()` 发送事务消息，消息发送失败则 MySQL 回滚 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 通知重复发送给用户 | 消费端未做幂等去重，Kafka 重试机制导致同一消息被多次消费 | 基于 `orderId + eventType` 拼接唯一键，调用 `setIfAbsent` 写入 Redis 去重，业务失败时删除标记允许重试 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ClickHouse 进程崩溃后数据丢失 | 内存 buffer 批量写入，未 flush 的数据在进程崩溃时丢失 | 配合 Kafka 手动提交 offset：仅 flush 成功后才提交 offset，崩溃后从上次 offset 重新消费 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ES 分片数设置后无法扩容 | 索引创建后分片数不可修改，规划不当导致后期只能 reindex 重建 | 建索引前预估数据量，单分片控制在 10-50GB，预留增长空间；3 主分片 + 1 副本为常见起点 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ES 搜索查不到刚下单的商品 | ES 默认 refresh_interval 为 1s，刚写入的文档在 refresh 前不可搜索 | 设置 `refresh_interval=5s` 平衡性能与实时性；对实时性要求极高的查询，先查 MySQL 兜底再查 ES | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Docker Compose 密码明文泄露 | 数据库密码、中间件密码直接写在 yml 文件中 | 使用环境变量文件（`.env`）或 Docker Secrets 管理敏感信息，yml 中仅引用变量名 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 网关限流粒度太粗导致误伤 | 使用全局 Redis 令牌桶限流，无法区分不同用户或 IP | 自定义 KeyResolver 按用户 IP 或用户 ID 维度限流，避免单用户高频请求影响其他用户 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Feign 同步调用拖垮线程池 | 同步 HTTP 调用阻塞线程，高并发下线程池耗尽导致服务不可用 | 非关键链路使用异步消息解耦（Kafka）；关键同步调用配置合理的线程池大小与超时时间 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 物化视图无法满足临时多维分析 | 物化视图按固定维度预聚合，临时新增分析维度需扫源表 | 物化视图覆盖热点查询维度（80% 场景），临时分析走源表加分区裁剪，时效性低的分析可异步生成报表 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Nacos 单节点故障导致服务发现瘫痪 | 开发环境仅部署单节点 Nacos | 生产环境部署 Nacos 集群（3 节点），配置数据持久化到 MySQL，保证高可用 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| HPA 基于 CPU/内存扩缩不精准 | 业务高峰期 CPU 不一定与 QPS 线性相关，基于 CPU 的 HPA 可能滞后或误扩 | 接入 Prometheus Adapter，基于自定义指标（如 QPS、消息积压量）配置 HPA | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Kafka linger.ms 过高导致消息延迟 | 为了提高批量发送效率设置过大的 linger.ms（如 100ms），延迟敏感场景不可接受 | 根据业务容忍度设置 linger.ms（通常 5-10ms），配合 batch.size 在延迟与吞吐间权衡 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Redis 缓存与数据库数据不一致 | 缓存更新与数据库写入非原子操作，存在短暂不一致窗口 | 设置合理过期时间（如 5 分钟），关键数据采用 Cache Aside 模式：先更新 DB 再删除缓存 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ES painless 脚本并发累加冲突 | 多消费者同时执行 `ctx._source.salesCount += quantity` 可能导致版本冲突 | 使用 `retry_on_conflict` 参数（如设为 3），或改用 bulk API 中 `doc_as_upsert` 加版本号控制 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ClickHouse 小批量写入触发 merge 风暴 | 频繁的少量 INSERT 产生大量小 Part，后台 merge 消耗大量 IO 和 CPU | 每 1000 条或每 5 秒批量 flush，控制写入频率，减少 Part 数量 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 库存扣减未加锁导致超卖 | 同一商品实际卖出数量超过库存，出现负库存 | "查询库存—判断是否充足—扣减"三步非原子，并发下相互覆盖 | 用带条件的行锁更新（`UPDATE ... SET stock = stock - n WHERE id = ? AND stock >= n` 判断影响行数）；跨服务的关键扣减用 Seata 分布式事务 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 用户连点或网络重试产生重复订单 | 同一笔业务生成多张订单，后续重复发货 | 下单接口未做幂等控制，请求被重复处理 | 用去重令牌/唯一订单号做接口幂等（Redis `setIfAbsent`），数据库对 order_no 加唯一索引兜底 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 消息顺序错乱导致订单状态回退 | 先消费到"取消"再消费到"创建"，状态从已取消变回已创建 | 同一订单的事件被发到不同分区，消费者并行处理时乱序 | 用 orderId 作为 Kafka key，保证同一订单的事件落到同一分区；消费端按事件时间/版本号丢弃过期事件 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| Kafka 分区数与消费并行度不匹配 | 部分消费线程空闲，吞吐上不去，消息持续积压 | 分区数少于并发线程数，多出的线程拿不到分区 | 分区数 ≥ 消费并发度（如 6 分区配 concurrency=3），扩分区后同步调整并发度 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| ClickHouse 分区键选择不当导致查询无法分区裁剪 | 统计接口全表扫描，聚合明显变慢 | 分区键与查询常用的时间过滤条件不一致 | 按 `toYYYYMMDD` 等与查询条件对齐的粒度分区，让时间过滤能直接裁剪分区 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
| 监控缺失导致故障不可见 | 接口已大面积超时，团队却毫无感知，靠用户反馈才发现 | 只打了日志，没有指标采集、没有告警规则 | 接入 Actuator + Prometheus + Grafana，对错误率、慢查询、消费积压配置告警，逐步补齐全链路监控 | [01-电商订单实时统计分析平台-导览](./01-电商订单实时统计分析平台-导览.md) |
