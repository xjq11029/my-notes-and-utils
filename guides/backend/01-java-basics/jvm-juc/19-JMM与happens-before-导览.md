## 一、核心概念

### 1.1 什么是 JMM

| 维度 | 内容 |
|------|------|
| 是什么 | Java 虚拟机规范定义的并发编程抽象规范，描述多线程下共享变量的读写行为与可见性条件 |
| 能做什么 | 屏蔽硬件与操作系统差异；划定编译器与处理器重排序边界；为 volatile、synchronized、final、Atomic、AQS 提供统一语义底座 |
| 怎么用 | 判断可见性时按规范推导不依赖硬件时序；规范层用 happens-before 实现层用内存屏障 |
| 原理和工作流程 | JMM 是规范非实现，由 JLS 第 17 章定义经 JSR 133 修订，HotSpot 只是实现之一。规范只规定必须保证什么不规定如何实现，x86 与 ARM 实现方式不同但语义一致。核心是主内存与工作内存两层抽象加 happens-before 规则集，最终目的是解决原子性可见性有序性三类问题 |
| 缺点 | 抽象难懂易与 JVM 运行时数据区混淆；规范与实现的差异导致 x86 正常 ARM 出 Bug；规范本身不含调试手段需借助工具 |

### 1.2 JMM 要解决的三个问题

| 维度 | 内容 |
|------|------|
| 是什么 | 并发编程中原子性、可见性、有序性三类问题及 JMM 对应的保证手段 |
| 能做什么 | 原子性由 synchronized、Lock、Atomic 保证；可见性由 volatile、synchronized、final 保证；有序性由内存屏障与临界区串行保证 |
| 怎么用 | 状态标志位用 volatile；复合操作与多变量一致性用 synchronized 或 Lock；单变量计数用 Atomic 或 LongAdder |
| 原理和工作流程 | 原子性指操作要么全做要么不做，JMM 保证 8 种内存交互操作本身原子，代码块整体原子靠锁。可见性指一个线程修改后其他线程立即可见，靠 volatile 写刷主存读重取与 synchronized 的 lock 清空 unlock 刷新。有序性指执行顺序符合预期，靠内存屏障禁止重排序与临界区串行。三者相互独立，volatile 只解决可见性与有序性不解决原子性 |
| 缺点 | volatile 不保证原子性最易踩坑；synchronized 有互斥开销与死锁风险；单变量原子与复合操作原子常被混淆 |

### 1.3 主内存与工作内存

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 的两层内存抽象，主内存存全部变量，每条线程有独立工作内存存变量副本 |
| 能做什么 | 解释可见性问题的根源；说明线程间传值必须经主内存中转；为 lock 与 unlock 语义提供依据 |
| 怎么用 | 属概念模型无需编码；排查时关注线程是否读到了工作内存中的过期副本 |
| 原理和工作流程 | 所有变量存主内存，线程工作内存保存该线程使用变量的主内存副本拷贝，线程对变量的所有操作都必须在工作内存进行不能直接读写主内存，线程间无法直接访问对方工作内存传值必须经主内存中转。注意与 JVM 运行时数据区不是一回事，主内存与工作内存是并发语义层抽象对应硬件主存与寄存器高速缓存，堆栈方法区是内存布局层真实区域，二者层次不同 |
| 缺点 | 与堆栈方法区概念极易混淆；抽象模型无法直接观测；不同教材表述不一致增加理解成本 |

### 1.4 JMM 与硬件内存架构的区别

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 抽象与真实多核 CPU 内存层次及缓存一致性协议的对比 |
| 能做什么 | 说明重排序的硬件来源；解释 x86 与 ARM 的行为差异；指导跨平台并发代码编写 |
| 怎么用 | x86 上只需关注 volatile 写的 lock 前缀开销；迁 ARM 必须严格按规范补齐 volatile |
| 原理和工作流程 | 硬件层次为寄存器、L1/L2/L3 缓存、主内存加 Store Buffer 写缓冲与 Invalidate Queue 失效队列，一致性由 MESI 等协议保证。JMM 用主内存与工作内存两层抽象屏蔽平台差异。重排序来源为编译器重排序、指令级并行重排序、内存系统重排序三类。x86 采用 TSO 全存储顺序只允许写读重排序其余三种被硬件禁止故 volatile 只需 lock 前缀指令，ARM 为弱内存模型四种重排序都可能发生需显式 dmb 与 isb 指令 |
| 缺点 | 跨平台行为差异导致本地正常线上偶发；x86 掩盖代码缺陷增加迁移风险；硬件细节理解成本高 |

## 二、底层原理

### 2.1 内存间交互的 8 种原子操作

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 定义的描述主内存与工作内存之间交互协议的八种原子操作 |
| 能做什么 | lock 与 unlock 锁定释放；read 与 load 读取载入；use 与 assign 使用赋值；store 与 write 存储写入；解释 synchronized 可见性来源 |
| 怎么用 | 属概念模型不直接编码；用规则 6 与规则 8 解释 synchronized 的可见性 |
| 原理和工作流程 | 读链路为主内存 read 到工作内存 load 入变量副本 use 给执行引擎，写链路为执行引擎 assign 给变量副本 store 到工作内存 write 入主内存。八条规则核心：read 与 load、store 与 write 必须成对出现；不允许丢弃最近的 assign；新变量只能在主内存诞生；同一时刻只允许一条线程 lock 但同一线程可重入；lock 会清空工作内存中该变量的值需重新 load 或 assign；unlock 前必须先 store 与 write 刷回主内存。规则 6 与规则 8 共同构成 synchronized 的可见性。JSR 133 之后做正确性推导应以 happens-before 为主要依据 |
| 缺点 | 属旧版 JMM 描述粒度偏实现指导；八条规则记忆负担重；做正确性推导不如 happens-before 直观易错 |

### 2.2 重排序

| 维度 | 内容 |
|------|------|
| 是什么 | 编译器与处理器为优化性能，在不改变单线程执行结果前提下调整指令执行顺序的行为 |
| 能做什么 | 说明三类重排序来源；界定 as-if-serial 语义边界；区分数据依赖与控制依赖；定位 DCL 半初始化的根因 |
| 怎么用 | 用 volatile 或 synchronized 禁止关键重排序；不要依赖代码书写顺序传递可见性 |
| 原理和工作流程 | 三类重排序为编译器重排序由 javac 与 JIT 指令调度产生，指令级并行重排序由处理器乱序发射超标量流水线产生，内存系统重排序由 Store Buffer 延迟提交与 Invalidate Queue 延迟失效产生。as-if-serial 语义保证单线程执行结果不变，故编译器和处理器不会重排序存在数据依赖的操作，但该语义只管单线程不保证多线程正确性。数据依赖分写后读、写后写、读后写三种均禁止重排序，控制依赖则允许重排序处理器用分支预测与投机执行提前执行。DCL 中 new 的引用赋值与构造器初始化无数据依赖故可被重排导致半初始化对象逸出 |
| 缺点 | 单线程结果不变这一前提在多线程下失效最易被忽视；控制依赖可重排序最反直觉；问题偶发难复现且加日志后往往消失 |

### 2.3 happens-before 规则

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 判断数据是否存在竞争、线程是否安全的核心依据，八条规则构成可见性推导基础 |
| 能做什么 | 程序顺序规则；监视器锁规则；volatile 变量规则；线程启动规则；线程终止规则；线程中断规则；对象终结规则；传递性 |
| 怎么用 | 三步法找共享变量找同步点连 hb 链；连不上即存在可见性 Bug |
| 原理和工作流程 | 定义是若 A happens-before B 则 A 的结果对 B 可见且 A 在 B 之前。八条规则为：程序顺序规则单线程内书写在前 hb 书写在后；监视器锁规则 unlock hb 后续对同一锁的 lock；volatile 变量规则 volatile 写 hb 后续对该变量的读；线程启动规则 start 方法 hb 该线程的所有动作；线程终止规则 线程内所有操作 hb 终止检测如 join 与 isAlive；线程中断规则 interrupt 调用 hb 被中断线程检测到中断；对象终结规则 构造器结束 hb finalize 开始；传递性 A hb B 且 B hb C 则 A hb C。关键辨析是 happens-before 不等于时间上先发生，它是可见性契约而非时间戳比较，hb 成立时物理执行顺序仍可不同，物理时间上晚执行但无 hb 关系时可见性无任何保证 |
| 缺点 | 最易与时间先后混淆；八条规则需结合传递性才能推导跨线程可见性；无 hb 关系时读到值未定义难定位 |

### 2.4 内存屏障

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 禁止特定类型重排序、强制刷新与失效缓存的指令级手段，是 happens-before 在实现层的落地方式 |
| 能做什么 | LoadLoad 禁后续装载提前；StoreStore 禁后续存储提前；LoadStore 禁装载与后续存储重排；StoreLoad 开销最大兼具三者效果 |
| 怎么用 | volatile 写前插 StoreStore 写后插 StoreLoad；volatile 读后插 LoadLoad 与 LoadStore |
| 原理和工作流程 | 四种屏障为 LoadLoad 确保 Load1 装载先于 Load2 及后续装载；StoreStore 确保 Store1 先刷到内存可见先于 Store2 及后续存储；LoadStore 确保 Load1 装载先于 Store2 及后续存储；StoreLoad 确保 Store1 先可见先于 Load2 及后续装载且开销最大。volatile 写采用前 StoreStore 后 StoreLoad 组合，volatile 读采用后 LoadLoad 加 LoadStore 组合，这是保守策略以保证任何处理器平台语义正确。x86 上只有 StoreLoad 需要真实指令即 lock 前缀的空操作 lock addl，其余三种为空操作 |
| 缺点 | 保守策略带来额外开销；StoreLoad 需清空写缓冲开销最大；屏障概念抽象难与源码对应；不同平台指令差异增加理解成本 |

### 2.5 volatile 的内存语义

| 维度 | 内容 |
|------|------|
| 是什么 | 保证可见性与禁止重排序但不保证原子性的轻量级同步机制 |
| 能做什么 | 可见性写后刷主存读后重取；有序性内存屏障禁止重排；状态标志位通信；DCL 防半初始化；一次性发布不可变对象 |
| 怎么用 | `private volatile boolean flag;` 或 volatile 引用一次性发布不可变配置 |
| 原理和工作流程 | 可见性由 volatile 写后 StoreLoad 屏障强制刷新主内存与 volatile 读后 LoadLoad 与 LoadStore 屏障强制重读实现。有序性由写前 StoreStore 写后 StoreLoad 读后 LoadLoad 与 LoadStore 实现。不保证原子性因 i++ 编译为读加载使用加计算赋存储写入多条指令中间可被其他线程插入导致丢失更新。适用边界看操作是否依赖变量当前值，不依赖适合做标志位，依赖当前值如计数必须用锁或原子类 |
| 缺点 | 不保证原子性最易误用；性能低于普通变量；过度使用无收益；仅适合状态标志与一次性发布；循环中反复读 volatile 会导致快照不一致 |

### 2.6 synchronized 的内存语义

| 维度 | 内容 |
|------|------|
| 是什么 | 同时提供原子性、可见性、有序性的内置互斥同步机制 |
| 能做什么 | 原子性由 Monitor 互斥保证；可见性由 lock 清空副本与 unlock 前刷新保证；有序性由临界区串行与内存屏障保证 |
| 怎么用 | `synchronized(obj){ }` 或 synchronized 修饰方法；复合操作与多变量一致性必须用它或 Lock |
| 原理和工作流程 | 可见性依据 JMM 八种操作的规则 6 与规则 8，加锁 lock 时清空工作内存中该变量的值故必须重新 read 与 load 拿到最新值，解锁 unlock 前必须 store 与 write 把修改刷回主内存。有序性来自临界区内代码相对临界区外串行，块内块外操作存在 hb 关系。JIT 在 monitorenter 与 monitorexit 处插入内存屏障，x86 上体现为 lock 前缀指令，并通过对象头 Mark Word 与 Monitor 提供互斥能力从而额外获得原子性 |
| 缺点 | 有锁开销与阻塞唤醒成本；可能死锁；粒度不当致性能下降；不可中断不可超时；可见性来源易与 volatile 的屏障路径混淆 |

### 2.7 final 域的内存语义

| 维度 | 内容 |
|------|------|
| 是什么 | JMM 为不可变对象安全发布提供的规范级保证，含两条重排序规则与一条编程约束 |
| 能做什么 | 写 final 域禁重排到构造器外；读 final 域禁重排到读引用之前；保证不可变对象无需同步即可安全共享 |
| 怎么用 | 字段声明为 final；构造器内不让 this 逸出；构造完成后再发布对象 |
| 原理和工作流程 | 写 final 域规则为 JSR 133 禁止把 final 域的写重排序到构造器之外，编译器在 final 域写入之后构造器 return 之前插 StoreStore 屏障，保证对象发布时 final 域已初始化完成。读 final 域规则为初次读对象引用与初次读该对象 final 域禁止重排序，编译器在读 final 域前插 LoadLoad 屏障，避免读到引用有效但 final 域仍为默认值的对象。第三条约束是 final 引用不能从构造器内逸出否则前两条规则前提被破坏，逸出场景包括构造器内赋值静态字段、注册监听器、启动线程、调用可重写方法 |
| 缺点 | 需所有字段 final 且构造期不逸出才生效；逸出场景隐蔽难发现；finalize 已废弃对象终结规则实际价值有限；理解成本高 |

## 三、实战应用

### 3.1 DCL 为什么必须加 volatile

| 维度 | 内容 |
|------|------|
| 是什么 | 双重检查锁定单例必须用 volatile 修饰实例的原因，JMM 最经典的应用场景 |
| 能做什么 | 解释 new 的三步操作与重排序；给出 volatile 生效的完整推导；提供不依赖 volatile 的替代方案 |
| 怎么用 | `private static volatile Singleton instance;` 或改用静态内部类与枚举单例 |
| 原理和工作流程 | new Singleton 实际分三步分配内存、调用构造器初始化、引用指向内存，步骤二与三无数据依赖故可被重排为分配、引用指向、初始化。线程 B 在引用赋值后通过第一次检查返回构造器尚未执行的对象，访问字段读到默认值导致偶发 NPE 或数据错乱。加 volatile 后推导为 volatile 写前 StoreStore 屏障禁止构造器初始化被重排到 volatile 写之后，写后 StoreLoad 屏障强制刷新主内存，线程 B 的 volatile 读强制从主内存读取，再由 volatile 变量规则与传递性得出构造器内所有写对读者可见。替代方案为静态内部类与枚举单例均依赖 JVM 保证的类初始化线程安全 |
| 缺点 | 漏加 volatile 时 Bug 概率极低极难复现；反射与反序列化仍可破坏单例；DCL 代码可读性差易写错 |

### 3.2 用 happens-before 推导可见性

| 维度 | 内容 |
|------|------|
| 是什么 | 三个正确案例与三个错误写法的 hb 链推导 |
| 能做什么 | volatile 一次性发布不可变配置；join 汇总子任务结果；synchronized 保护复合操作；识别三个典型错误写法 |
| 怎么用 | 读一次 volatile 到局部变量避免循环内快照不一致；子线程写普通变量后主线程 join 再读 |
| 原理和工作流程 | 案例一用 volatile 发布不可变配置，构建完成后一次性赋值给 volatile 引用，由程序顺序规则、volatile 变量规则与传递性保证配置内容全部可见，技巧是读一次 volatile 到局部变量避免多次读导致快照不一致。案例二用 join 汇总，子线程写普通变量后主线程 join，由线程终止规则保证读到结果，去掉 join 则结果不确定。案例三用 synchronized 保护 count++ 复合操作，由监视器锁规则保证原子与可见。三个错误写法为普通变量当标志位导致死循环、用 volatile 做计数导致丢失更新、多个 volatile 变量无法保证同时可见 |
| 缺点 | hb 链推导需熟练掌握八条规则；实际代码中同步点分散难以完整枚举；遗漏一个同步点即推导失效 |

### 3.3 排查可见性问题的实战套路

| 维度 | 内容 |
|------|------|
| 是什么 | 线上偶发难复现并发问题的五步排查流程与 jcstress 验证手段 |
| 能做什么 | 判断是否为可见性有序性问题；列出共享状态；检查同步手段；用 jcstress 复现竞态；修复并回归 |
| 怎么用 | 编写 @JCStressTest 用例并以 @Outcome(expect = Expect.FORBIDDEN) 断言非法结果不出现 |
| 原理和工作流程 | 步骤一确认是否为可见性有序性问题，判据为现象偶发且重试就好、换机器换 JDK 换负载后表现不同、加日志后 Bug 消失。步骤二列出所有跨线程共享的可变状态，特别关注配置缓存、状态标志、懒加载对象、单例。步骤三逐个检查同步手段，是否漏 volatile、复合操作是否只加 volatile 未加锁、对象是否构造器内逸出、不可变对象字段是否全 final。步骤四用 OpenJDK 的 jcstress 框架编写用例跑大量迭代复现 JMM 层面竞态。步骤五修复优先选不可变对象加 volatile 一次性发布，其次用 synchronized 包裹复合操作 |
| 缺点 | jcstress 需额外搭建测试环境；线上问题难以本地复现；加日志本身改变时序会掩盖竞态；定位高度依赖经验 |

## 四、常见面试题（附答案）

### 1. 什么是 JMM？为什么需要 JMM？

| 维度 | 内容 |
|------|------|

| 能做什么 | 说明伪共享的定义与成因；给出手动填充与注解两种避免方式；说明 LongAdder 的设计思路 |
| 怎么用 | 手动填充 long 字段；用 @Contended 注解配合 -XX:-RestrictContended；用 LongAdder 做线程本地聚合 |
| 原理和工作流程 | 伪共享指多个线程分别修改位于同一缓存行通常 64 字节的不同变量时，由于缓存一致性协议 MESI 以缓存行为单位失效，导致彼此的缓存行反复失效频繁从主内存重载性能急剧下降。避免方式一为手动填充，在变量前后插入无用的 long 字段让变量独占缓存行；方式二为使用 @Contended 注解由 JVM 自动填充需开启 -XX:-RestrictContended；方式三为线程本地聚合，如 LongAdder 把计数分散到多个带 @Contended 的 Cell 最后汇总，从设计上规避竞争 |
| 缺点 | 属性能问题非正确性问题不会导致数据错误只导致性能抖动；需 perf 观察 cache-misses 才能定位；填充浪费内存 |

### 17. 一个线程写普通变量 A 再写 volatile B，另一线程读 volatile B 再读 A，A 一定可见吗？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 volatile 发布订阅用法的 hb 推导与前提条件 |
| 能做什么 | 给出肯定结论；给出完整 hb 推导；说明两个必须满足的前提；指出常见错误写法 |
| 怎么用 | 写者先写普通数据后写 volatile 标志，读者先读 volatile 标志再读数据 |
| 原理和工作流程 | 结论是一定可见，这正是 volatile 最典型的发布订阅用法。推导为写 A 是 P，写 volatile B 是 Q，读 volatile B 是 R，读 A 是 S，P hb Q 由程序顺序规则且 volatile 写前的 StoreStore 屏障禁止 P 被重排到 Q 之后，Q hb R 由 volatile 变量规则，R hb S 由程序顺序规则，由传递性 P hb S 故 T2 在读到 B 的新值后一定能读到 A 的新值。前提条件有两点必须同时满足：T2 必须真的读到了 T1 写入的 B 的新值否则 Q hb R 不成立；A 的写入必须在 volatile 写之前由程序顺序保证。常见错误是把 A 的赋值写在 volatile 写之后，此时 A 与 volatile 写之间没有 hb 链可见性无保证 |
| 缺点 | 前提条件易被忽略；顺序写反即失效；读者读到旧值时整个推导不成立 |

### 18. volatile 和 synchronized 在内存语义上的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查两种同步手段在三大特性上的覆盖差异 |
| 能做什么 | 对比原子性；对比可见性；对比有序性；对比互斥与阻塞；给出选择原则 |
| 怎么用 | 能用 volatile 解决就不用 synchronized；涉及复合操作或多变量一致性必须用 synchronized 或 Lock |
| 原理和工作流程 | 原子性上 volatile 不保证 i++ 不安全，synchronized 保证临界区整体原子。可见性上二者都保证，volatile 靠写刷主存读重取，synchronized 靠 unlock 刷新与 lock 重取即 JMM 规则 6 与规则 8。有序性上 volatile 靠内存屏障禁止特定重排序，synchronized 靠临界区串行加内存屏障。互斥上 volatile 无 synchronized 有。阻塞上 volatile 不阻塞 synchronized 竞争时阻塞。开销上 volatile 极小 x86 仅 volatile 写有 lock 前缀开销，synchronized 有锁开销但 JDK 6 加锁升级后已优化。选择原则是能用 volatile 解决就不用 synchronized，涉及复合操作或多变量一致性必须用 synchronized 或 Lock |
| 缺点 | volatile 边界易误用；synchronized 粒度不当致性能下降；二者可见性来源路径不同易混淆 |
