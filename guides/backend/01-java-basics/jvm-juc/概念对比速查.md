# jvm-juc - 概念对比速查

> 本模块易混淆概念的对比速查，帮助快速区分关键差异。

---

### synchronized vs ReentrantLock

| 对比维度 | synchronized | ReentrantLock |
|---------|-------------|---------------|
| 核心定位 | JVM 层面内置关键字，基于 Monitor 实现 | API 层面显式锁，基于 AQS 框架实现 |
| 适用场景 | 简单同步需求，代码块/方法加锁 | 需要高级特性：可中断、超时、公平锁、多条件 |
| 性能特点 | JDK 6+ 锁升级优化后接近 ReentrantLock | 略高开销但差距不大 |
| 线程安全 | 自动释放（代码块退出或异常），不可中断 | 需手动 unlock() 在 finally 中，支持 lockInterruptibly() |
| 选择建议 | 优先使用 synchronized，需要高级特性时改用 ReentrantLock |

---

### volatile vs synchronized

| 对比维度 | volatile | synchronized |
|---------|----------|-------------|
| 核心定位 | 轻量级可见性保证，禁止指令重排序 | 重量级互斥锁，保证原子性、可见性、有序性 |
| 适用场景 | 状态标志位、DCL 单例中的 instance 变量 | 多线程竞争共享资源的读写操作 |
| 性能特点 | 开销极小，接近普通变量读写 | 有锁竞争开销，JDK 6+ 经锁升级优化 |
| 线程安全 | 仅保证可见性和禁止重排，不保证原子性 | 保证原子性、可见性、有序性，完整线程安全 |
| 选择建议 | 仅用于简单状态标记或 DCL 防重排；复合操作仍需 synchronized |

### JVM 堆 vs 栈 vs 方法区

| 对比维度 | 堆（Heap） | 栈（VM Stack） | 方法区（Metaspace） |
|---------|-----------|---------------|-------------------|
| 核心定位 | 存储对象实例和数组，GC 主战场 | 存储方法调用的栈帧（局部变量表、操作数栈等） | 存储类元数据、静态变量、运行时常量池 |
| 适用场景 | 所有 new 创建的对象 | 方法调用与返回、局部变量 | 类加载后的元信息存储 |
| 性能特点 | 分配快但 GC 有停顿 | 存取极快，线程私有无需同步 | 类信息常驻，JDK 8+ 使用本地内存 |
| 线程安全 | 线程共享，需并发控制 | 线程私有，天然线程安全 | 线程共享，类加载时安全 |
| 选择建议 | 调整 -Xms/-Xmx，关注 GC 频率和对象生命周期管理 | 调整 -Xss，关注递归深度和方法调用链长度 | 调整 -XX:MaxMetaspaceSize，关注类加载器泄漏问题 |

### AQS vs CAS

| 对比维度 | AQS（AbstractQueuedSynchronizer） | CAS（Compare And Swap） |
|---------|--------------------------------|------------------------|
| 核心定位 | JUC 同步器模板框架，用 state + CLH 队列实现阻塞式同步 | 无锁原子操作原语，由 CPU 的 CMPXCHG 指令保证原子性 |
| 适用场景 | 需要排队等待、可重入、公平性控制的场景（ReentrantLock、Semaphore、CountDownLatch） | 单变量无竞争或少竞争下的原子更新（AtomicInteger、LongAdder） |
| 性能特点 | 竞争激烈时线程 park 阻塞，不空耗 CPU，但有阻塞唤醒开销 | 无锁自旋，低竞争下极快；高竞争下自旋空耗 CPU |
| 线程安全 | 独占/共享两种模式，state 为 volatile，保证原子性、可见性、有序性 | 只保证单个变量的原子性，多变量需锁或 AtomicReference |
| 阻塞行为 | 获取失败会进入 CLH 队列并 park，可被唤醒 | 不阻塞，失败即自旋重试，无排队语义 |
| 依赖关系 | 底层依赖 CAS 修改 state，是 CAS 的上层封装 | 是 AQS 的底层实现基础，二者是「框架」与「原语」的关系 |
| 典型缺陷 | 实现复杂、CLH 队列调试困难、公平与非公平选择影响性能 | ABA 问题（用 AtomicStampedReference 解决）、自旋开销、只能单变量 |
| 选择建议 | 需要阻塞、排队、可重入或条件变量时用 AQS 系列（ReentrantLock 等） | 单变量计数与状态更新优先用 CAS 系列原子类，高并发计数改用 LongAdder |

### G1 vs CMS vs ZGC

| 对比维度 | G1 | CMS | ZGC |
|---------|----|-----|-----|
| 核心定位 | 全堆分 Region 收集器，平衡延迟与吞吐量，JDK 9+ 默认 | 老年代并发收集器，低延迟优先，JDK 9 废弃、JDK 14 移除 | 染色指针 + 并发整理的超低延迟收集器 |
| 适用场景 | 大堆（>4G）且要求停顿可预测，JDK 9+ 通用场景 | 中小堆（<4G）低延迟场景，仅存于 JDK 8 老系统 | 超大堆（几十 G 到 TB 级）且停顿要求 <10ms |
| 算法与结构 | 标记-整理 + 复制，堆划分为约 2048 个 Region（1~32MB） | 标记-清除，连续分代结构 | 标记-整理（染色指针 + 读屏障），支持分代（JDK 21+） |
| 停顿表现 | 可预测，通过 `-XX:MaxGCPauseMillis` 设定软目标；Young GC 短停、Mixed GC 中等停顿 | 不可预测，初始标记与重新标记 STW，可能出现 Concurrent Mode Failure | 极短（通常 <1ms），主体工作在并发阶段完成 |
| 内存碎片 | 可控，Region 复制天然压缩 | 有碎片，标记-清除不移动对象 | 无碎片，并发整理 |
| 关键参数 | `-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`、`-XX:InitiatingHeapOccupancyPercent` | `-XX:+UseConcMarkSweepGC`、`-XX:CMSInitiatingOccupancyFraction` | `-XX:+UseZGC`、`-XX:+ZGenerational`（JDK 21+） |
| 典型缺陷 | 实现复杂、内存与 CPU 开销较大、Humongous 对象处理有额外成本 | 浮动垃圾、内存碎片、对 CPU 敏感、并发失败会退化为单线程 Full GC | 内存开销大（染色指针与读屏障）、吞吐量略低于 G1 |
| 选择建议 | JDK 9+ 大堆通用首选，停顿目标 100~300ms | 仅在 JDK 8 老系统维护时使用，新项目不再选型 | 停顿敏感型服务（交易、行情）且机器内存充足时选用 |

### JMM happens-before 规则速查表

| 编号 | 规则名称 | 内容 | 关键要点 | 典型应用 |
|------|---------|------|---------|---------|
| 1 | 程序顺序规则 | 单线程内，代码书写在前 hb 书写在后 | hb 成立不等于物理执行顺序相同，无数据依赖时仍可重排 | 所有单线程代码的基础 |
| 2 | 监视器锁规则 | unlock hb 后续对同一锁的 lock | 加锁时清空工作内存副本，解锁前必须刷回主内存 | `synchronized` 保证可见性 |
| 3 | volatile 变量规则 | volatile 写 hb 后续对该变量的读 | 写前 StoreStore、写后 StoreLoad；读后 LoadLoad 与 LoadStore | 状态标志位、DCL、一次性发布 |
| 4 | 线程启动规则 | `Thread.start()` hb 该线程的所有动作 | start 之前的写对子线程可见，start 之后的写无保证 | 主线程准备数据后启动子线程 |
| 5 | 线程终止规则 | 线程内所有操作 hb 终止检测（`join()` / `isAlive()`） | 不调用 join 直接读子线程结果，值不确定 | 子线程计算结果后主线程汇总 |
| 6 | 线程中断规则 | `interrupt()` hb 被中断线程检测到中断 | 中断前写入的状态对中断处理器可见 | 中断前写状态、中断后清理 |
| 7 | 对象终结规则 | 构造器结束 hb `finalize()` 开始 | finalize 已废弃（JDK 9），生产用 Cleaner 或 try-with-resources | 对象终结时读取构造期字段 |
| 8 | 传递性 | A hb B，B hb C ⇒ A hb C | 把前七条规则串联，是推导跨线程可见性的关键 | 推导 volatile 发布、join 汇总等场景 |

> **易错辨析**：happens-before 是「可见性契约」，不是「时间戳比较」。hb 成立时物理执行顺序仍可不同；物理时间上晚执行但无 hb 关系时，可见性无任何保证（可能读到旧值）。判断可见性用三步法：找共享变量 → 找同步点 → 连 hb 链，连不上即存在 Bug。
