# jvm-juc - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 使用 Executors 创建线程池高并发时 OOM | newFixedThreadPool 使用无界 LinkedBlockingQueue；newCachedThreadPool 的 maximumPoolSize 为 Integer.MAX_VALUE | 使用 ThreadPoolExecutor 构造器 + 有界队列（如 ArrayBlockingQueue）+ 合理拒绝策略 | [13-多线程与并发编程-导览](./13-多线程与并发编程-导览.md) |
| 静态共享 SimpleDateFormat 日期解析结果错乱 | SimpleDateFormat 非线程安全，多线程共享会出错 | 使用 ThreadLocal 包装；使用 DateTimeFormatter（Java 8+，线程安全）；每次创建新实例 | [13-多线程与并发编程-导览](./13-多线程与并发编程-导览.md) |
| submit() 不处理 Future 任务异常被静默吞没 | submit() 的异常封装在 Future 中，不调用 get() 则异常无法感知 | 调用 future.get() 并捕获 ExecutionException；在任务内部 try-catch 并记录日志 | [13-多线程与并发编程-导览](./13-多线程与并发编程-导览.md) |
| 线程池未优雅关闭任务丢失或线程泄漏 | 直接 shutdownNow() 可能中断正在执行的任务 | 先 shutdown() 不再接受新任务，awaitTermination 等待完成，超时后再 shutdownNow() 强制关闭 | [13-多线程与并发编程-导览](./13-多线程与并发编程-导览.md) |
| finally 块中 return 导致返回值或异常被吞没 | finally 块中的 return 会覆盖 try 中的 return 或异常 | 避免在 finally 块中使用 return，finally 仅用于资源释放 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 依赖 System.gc() 立即回收内存未释放 | System.gc() 只是建议 JVM 进行 GC，不保证立即执行 | 生产环境使用 `-XX:+DisableExplicitGC` 禁用；依赖 JVM 自动 GC 策略 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 未理解逃逸分析条件优化未生效 | 逃逸分析是 JIT 优化，仅在对象不逃逸出方法时生效（需 HotSpot Server 模式） | 确保相关参数开启（`-XX:+DoEscapeAnalysis`、`-XX:+EliminateAllocations`，默认开启） | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 高并发下大量调用 String.intern() 性能下降 | intern() 需操作字符串常量池，频繁调用涉及锁竞争和哈希表操作 | 避免在高并发场景大量调用 intern()；使用自定义缓存替代 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| Stream 重复消费抛 IllegalStateException | Stream 只能被消费一次，终止操作后不能再使用 | 每次需要操作时重新获取 Stream，或将结果收集到集合后再处理 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| 并行流中使用非线程安全集合数据丢失 | `ArrayList.add()` 非线程安全，并行流中并发写入导致数据损坏 | 使用 `Collectors.toList()` 等线程安全的收集器，或使用 `ConcurrentHashMap` 等并发集合 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| Lambda 中修改外部变量编译错误 | Lambda 只能引用 effectively final 的局部变量 | 使用 `AtomicInteger` 等原子类包装变量，或将变量声明为实例变量 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| Optional 用作字段/方法参数序列化失败 | Optional 未实现 `Serializable`，且设计初衷是返回值类型 | 仅将 Optional 用作方法返回值；字段保持原始类型，参数直接接收原始类型 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| `orElse` 中传入方法调用不必要的性能开销 | `orElse(expensiveOp())` 即使 Optional 有值也会执行 `expensiveOp()` | 使用 `orElseGet(() -> expensiveOp())` 实现惰性求值 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| 文本块缩进不一致生成多余空格 | 文本块以内容行最小缩进为基准去除公共空白，混合缩进会导致结果不符合预期 | 确保文本块内容使用一致的缩进，推荐使用 4 空格缩进 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| Record 与 JPA/Hibernate 混用持久化异常 | Record 要求字段 final，无无参构造器，不符合 JPA 实体规范 | Record 适合用作 DTO/VO/数据传输对象，实体类仍使用传统 POJO | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| 密封类 permits 遗漏编译错误 | 声明了 `sealed` 但未用 `permits` 列出子类，或子类不在同一包/模块中 | 确保 `permits` 子句中列出所有允许的子类，且子类位于同一包或模块 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| 模式匹配变量作用域混淆编译错误 | `if (obj instanceof String s \|\| s.length() > 5)` 中 `s` 的作用域受短路运算影响 | 理解模式匹配变量作用域：`&&` 之后可见，`\|\|` 之后不可见；确保变量在使用前已绑定 | [15-JDK8-17新特性-导览](./15-JDK8-17新特性-导览.md) |
| 单例用懒汉式+synchronized 高并发时性能差 | synchronized 锁整个方法 | 改用 DCL 或静态内部类 | [16-设计模式-导览](./16-设计模式-导览.md) |
| 工厂模式滥用类爆炸调试困难 | 不区分场景滥用工厂 | 仅当创建逻辑复杂或需要解耦时使用 | [16-设计模式-导览](./16-设计模式-导览.md) |
| AOP 代理失效 @Transactional 不生效 | 同类方法调用不走代理 | 将方法拆分到不同类，或注入自身代理 | [16-设计模式-导览](./16-设计模式-导览.md) |
| 策略模式定义过多类维护成本高 | 策略数量过多 | 可用枚举或函数式接口简化 | [16-设计模式-导览](./16-设计模式-导览.md) |
| 用普通变量做线程间状态标志导致线程死循环 | 无 happens-before 关系，工作内存副本一直未刷新，读不到新值 | 标志位声明为 `volatile`，或使用 `AtomicBoolean` | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| DCL 单例漏加 volatile 偶发 NPE 或字段读到默认值 | `new` 的引用赋值与构造器初始化无数据依赖，可能被重排序导致半初始化对象逸出 | `instance` 加 `volatile`；或改用静态内部类、枚举单例 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 用 volatile 做计数器高并发下计数偏小 | volatile 不保证原子性，`i++` 是读-改-写复合操作，中间可被其他线程插入 | 用 `AtomicInteger` / `LongAdder`，或加锁保护复合操作 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 构造函数中让 this 逸出导致其他线程读到未初始化字段 | 对象引用在构造完成前被发布，final 域内存语义的前提被破坏 | 构造器内不赋值静态字段、不注册监听器、不启动线程、不调用可重写方法 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 误以为代码书写顺序就是执行顺序导致逻辑偶发失败 | 只有存在数据依赖才禁止重排序，无依赖时编译器和处理器可自由重排 | 用 volatile / synchronized 建立明确的 happens-before 关系，不依赖书写顺序 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 误以为时间上后执行就能看到先执行的结果 | happens-before 不等于时间先后，无同步手段时可见性无任何保证 | 显式建立 hb 关系（volatile、锁、`join()`、`start()`） | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 用 volatile 保证多个变量的一致性读到中间态 | 多个 volatile 变量各自独立可见，不构成原子快照，可能一半新一半旧 | 合并为一个不可变对象用 volatile 一次性发布，或用锁保护 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 循环中反复读 volatile 变量导致快照不一致 | 每次读 volatile 可能拿到不同值，循环内多次读不构成一致快照 | 先读到局部变量再在循环中使用：`Map m = this.config;` | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 非 volatile 的 long / double 共享字段读到撕裂值 | JLS 允许把 64 位读写拆成两次 32 位操作，可能高 32 位新、低 32 位旧 | 加 `volatile`（规范要求保证原子性）或使用 `AtomicLong` | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 依赖 x86 的额外内存约束写并发代码迁移后偶发 Bug | x86 的 TSO 模型禁止了三种重排序，掩盖了代码缺陷；ARM 是弱内存模型 | 严格按 JMM 规范补齐 volatile，并在 ARM 环境做回归测试 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 只加日志不分析就修并发 Bug 上线后复现 | 日志的 IO 与同步改变了时序，掩盖了竞态，问题并未消失 | 按「找共享变量 → 找同步点 → 连 hb 链」三步法定向分析；用 jcstress 复现 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| 期望 finalize() 保证资源清理时机导致资源迟迟不释放 | finalize() 由 GC 触发，不保证执行时机与是否执行；JDK 9 起已废弃 | 用 `try-with-resources` 或 `Cleaner`，显式 `close()` 释放资源 | [19-JMM与happens-before-导览](./19-JMM与happens-before-导览.md) |
| AQS 自定义同步器未正确实现 tryRelease 导致锁无法释放 | 只重写 tryAcquire 未配套实现 tryRelease，或未处理重入与 state 边界 | 成对重写 tryAcquire 与 tryRelease，保证 state 加减对称，并在 finally 中释放 | [13-多线程与并发编程-导览](./13-多线程与并发编程-导览.md) |
| ThreadLocal 未 remove 在线程池场景累积内存泄漏 | ThreadLocalMap 的 value 是强引用，线程池线程长期存活导致 value 无法回收 | 每次使用完在 finally 中调用 `remove()` 清理 Entry | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| GC 日志未开启或未滚动导致线上 GC 问题无现场可查 | 未配置 `-Xlog`，或未设置 filecount 与 filesize 导致日志被覆盖 | 提前配置 `-Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=50m` | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| Xms 与 Xmx 不相等导致堆动态扩缩引发 GC 抖动 | 堆容量动态调整带来额外开销与不可预测的停顿波动 | 生产环境设置 `-Xms` 与 `-Xmx` 相等，避免运行时扩缩 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 误判「Full GC 后老年代不回落」就是内存泄漏 | 可能只是长生命周期对象较多形成的稳态，看单点值会误判 | 看趋势：连续多次 Full GC 后 OU 仍单调上涨才是泄漏特征，再用 MAT 确认 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 把 GC overhead limit exceeded 当独立类型只调参数 | 本质仍是堆不足或泄漏，GC 占用超 98% 时间却回收不足 2% 堆 | 按堆溢出路径 dump 分析定位泄漏根因，而非只调 GCTimeLimit 与 GCHeapFreeLimit | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 未限制直接内存导致堆外 OOM | 报 `OutOfMemoryError: Direct buffer memory`，NIO DirectByteBuffer 未释放 | 设置 `-XX:MaxDirectMemorySize`；检查 Netty ByteBuf 是否 release | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 动态代理与热部署过多导致元空间泄漏 | 报 `OutOfMemoryError: Metaspace`，类加载器无法回收，动态类持续累积 | 排查 CGLIB、动态代理与热部署；设置 `MaxMetaspaceSize` 并观察 MC 与 MU 趋势 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 线上直接 jmap -dump 未评估停顿导致业务抖动 | dump 会触发 STW，大堆耗时可达数十秒，引发接口超时 | 优先用 `-XX:+HeapDumpOnOutOfMemoryError` 自动 dump，或选择低峰期执行 | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
| 在高 QPS 接口上直接 trace / watch 未限次导致接口更慢 | Arthas 的 trace 需对每个子调用埋点，watch 每次调用都输出，开销较大 | 配合 `-n` 限制次数，条件过滤缩小范围，诊断完执行 `stop` | [14-JVM原理与调优-导览](./14-JVM原理与调优-导览.md) |
