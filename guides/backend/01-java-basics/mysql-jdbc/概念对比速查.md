# mysql-jdbc - 概念对比速查

> 选取本模块易混淆概念进行对比，帮助快速区分与选型。

---

## Statement vs PreparedStatement vs CallableStatement

| 对比维度 | Statement | PreparedStatement | CallableStatement |
|---------|-----------|-------------------|-------------------|
| 核心定位 | 执行静态 SQL 字符串 | 预编译 SQL，参数化执行 | 调用数据库存储过程 |
| 适用场景 | 极少使用，仅执行无参数的固定 SQL | 绝大多数 CRUD 操作，带参数查询 | 需要调用数据库存储过程或函数 |
| 性能特点 | 每次执行都需解析编译 SQL，性能差 | 可复用执行计划，批量场景更快 | 依赖存储过程，性能取决于过程实现 |
| SQL 注入防御 | 无防御，直接拼接字符串 | 参数作为字面量处理，有效防御 | 参数化传递，可防御注入 |
| 类型安全 | 无 | setInt/setString 等显式设值 | 支持 OUT/INOUT 参数注册 |
| 继承关系 | 基类 | 继承 Statement | 继承 PreparedStatement |
| 选择建议 | 不推荐使用 | 首选，日常开发标准选择 | 仅在调用存储过程时使用 |

## WHERE vs HAVING

| 对比维度 | WHERE | HAVING |
|---------|-------|--------|
| 核心定位 | 行级过滤，在分组前对原始数据行进行筛选 | 组级过滤，在分组后对聚合结果进行筛选 |
| 适用场景 | 过滤基础数据行，如 `WHERE age > 18` | 过滤分组聚合结果，如 `HAVING COUNT(*) > 5` |
| 执行时机 | 在 GROUP BY 之前执行 | 在 GROUP BY 之后执行 |
| 聚合函数 | 不能使用聚合函数 | 可以使用聚合函数 |
| 性能特点 | 提前过滤减少分组数据量，性能好 | 在分组后过滤，无法减少分组开销 |
| 与 GROUP BY 关系 | 不依赖 GROUP BY，可单独使用 | 通常配合 GROUP BY 使用 |
| 选择建议 | 能用 WHERE 过滤的条件不要放到 HAVING；优先用 WHERE 缩小数据集 | 仅当条件涉及聚合结果时才使用 HAVING |

## INNER JOIN vs LEFT JOIN vs RIGHT JOIN

| 对比维度 | INNER JOIN | LEFT JOIN | RIGHT JOIN |
|---------|------------|-----------|------------|
| 核心定位 | 取两表交集，仅返回匹配行 | 以左表为基准，左表全保留 | 以右表为基准，右表全保留 |
| 适用场景 | 查询两表都有匹配的数据，如"有订单的用户" | 查询主表所有数据及关联数据，如"所有用户及其订单" | 与 LEFT JOIN 对称，较少使用 |
| 结果特征 | 不匹配的行被丢弃 | 右表无匹配时右表字段补 NULL | 左表无匹配时左表字段补 NULL |
| 驱动表灵活性 | 优化器可自由选择驱动表 | 驱动表固定为左表，优化空间受限 | 驱动表固定为右表，优化空间受限 |
| 特殊用法 | 无 | 配合 `IS NULL` 查询差集，如"未下单用户" | 配合 `IS NULL` 查询差集 |
| 选择建议 | 仅需匹配数据时使用，表意明确 | 需要保留主表全部数据时使用，是最常用的外连接 | 可用 LEFT JOIN 交换表顺序替代，不推荐主动使用 |
