# mysql-jdbc - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

## 来自 01-MySQL基础与SQL核心

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| UPDATE/DELETE 不带 WHERE 导致全表数据被修改/删除 | 忘记加条件或先执行了语句 | 执行前用 SELECT 验证条件；开启安全模式 `SET sql_safe_updates=1` | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| VARCHAR 长度设置过大导致创建表失败或行数据超限 | MySQL 单行最大 65535 字节，多个 VARCHAR 累加超限 | 评估实际需求；超长文本用 TEXT 类型 | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 金额使用 FLOAT/DOUBLE 导致计算结果出现精度误差 | 浮点数采用二进制存储，无法精确表示十进制小数 | 金额使用 `DECIMAL(10,2)`，应用层使用 BigDecimal | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| DATETIME 与 TIMESTAMP 混用导致跨时区显示异常或 2038 年溢出 | TIMESTAMP 自动转时区且范围仅到 2038 | 业务时间用 DATETIME；自动记录时间可用 TIMESTAMP | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 分页深翻页慢，`LIMIT 1000000,10` 查询耗时数秒 | 扫描并丢弃前 100 万行后才取 10 行 | 子查询先定位主键再 JOIN；或用游标分页（记录上一页最大 id） | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| GROUP BY 后直接 SELECT 非聚合列导致结果不确定或报错 | SQL 模式 `ONLY_FULL_GROUP_BY` 禁止非聚合列随意出现 | SELECT 只包含分组列或聚合列；或调整业务逻辑 | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 隐式类型转换导致索引失效，字符串列与数字比较时全表扫描 | MySQL 对列做类型转换使索引失效 | 比较值与列类型一致：`WHERE phone = '13800000001'` | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 索引列上使用函数导致索引失效 | 函数破坏索引有序性 | 把函数移到值一侧：`WHERE created_at >= '2025-01-01'` | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 用 TRUNCATE 代替 DELETE 后数据无法恢复 | 误删数据不可回滚，且执行后无法撤销 | TRUNCATE 属于 DDL，会隐式提交且不可回滚 | 需要可回滚的删除用 DELETE + WHERE；TRUNCATE 只用于清空整表 | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| 把本可在 WHERE 过滤的条件写进 HAVING | 先完成全部分组再过滤，性能明显下降 | 混淆 WHERE（分组前过滤行）与 HAVING（分组后过滤组）的执行时机 | 非聚合条件一律放 WHERE，只有对聚合结果过滤才用 HAVING | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |
| LEFT JOIN 后把右表条件写进 WHERE，结果退化成 INNER JOIN | 左表中未匹配的行被意外过滤掉 | WHERE 对右表列做过滤会排除右表为 NULL 的行 | 右表的过滤条件下移到 ON 子句，保留左表全部行 | [01-MySQL基础与SQL核心-导览](./01-MySQL基础与SQL核心-导览.md) |

## 来自 02-JDBC核心原理

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 资源未关闭导致连接泄漏，连接池耗尽 | ResultSet/Statement/Connection 未在 finally 关闭 | 使用 try-with-resources 自动关闭；按 rs -> ps -> conn 逆序关闭 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| Statement 拼接 SQL 导致 SQL 注入漏洞 | 用户输入直接拼入 SQL 字符串 | 全部使用 PreparedStatement + `?` 占位 + setXxx 设值 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 事务未提交/回滚导致数据不一致或脏数据残留 | 异常时未 rollback，或 autoCommit 仍为 true | try-catch-finally 模式，异常时 rollback，finally 中恢复 autoCommit 并关闭 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 连接池 maxLifetime 过大导致连接被数据库单方面断开 | maxLifetime 大于数据库 `wait_timeout`，连接失效仍在用 | maxLifetime 设置为 `wait_timeout` 的 60%~80%，如 30min | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 获取连接超时导致请求堆积、接口超时 | 最大连接数过小或慢 SQL 长期占用连接 | 调大 maximumPoolSize；排查慢 SQL；设置合理 connectionTimeout | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 批量插入逐条执行导致插入万条数据耗时数分钟 | 每次 executeUpdate 都一次网络往返 | 使用 `addBatch` + `executeBatch`；开启 `rewriteBatchedStatements=true` | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| ResultSet 使用后关闭报错 `Operation not allowed after ResultSet closed` | 同一 Statement 执行新查询后旧 ResultSet 自动关闭 | 先读取完旧 ResultSet 数据再执行新查询；使用不同 Statement | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 日期类型精度丢失，时间字段时分秒为 00:00:00 | 用 `rs.getDate()` 只取日期部分 | 使用 `rs.getTimestamp()` 获取完整时间 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 拼接好 SQL 再交给 prepareStatement，依然被注入 | 以为用了 PreparedStatement 就安全，漏洞仍存在 | SQL 用字符串拼接生成后整体传给 prepareStatement，`?` 根本没参与参数传递 | 参数必须用 `?` 占位 + `setXxx` 传入，绝不把参数拼进 SQL 模板 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 连接池最大连接数与数据库上限不匹配 | 数据库报 Too many connections，应用获取连接失败 | 多实例部署时各实例 maximumPoolSize 之和超过数据库 max_connections | 保证 实例数 × maximumPoolSize 明显小于 max_connections，并留出余量 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| setAutoCommit(false) 后未恢复，连接被复用时仍处于事务中 | 后续借到该连接的请求事务行为异常、数据未提交 | 归还连接前没有把 autoCommit 恢复为 true | finally 中恢复 autoCommit=true 再归还；连接池虽会重置，显式恢复更稳妥 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 用 executeQuery 执行 UPDATE 抛异常 | `executeQuery` 只接受返回结果集的语句 | 增删改误用了 executeQuery | 查询用 executeQuery，增删改用 executeUpdate，通用场景用 execute | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 可滚动/可更新 ResultSet 在部分驱动上报不支持 | 抛异常或行为与预期不一致 | 驱动未完整实现 TYPE_SCROLL_SENSITIVE + CONCUR_UPDATABLE | 分页用 LIMIT、更新用 UPDATE 语句；生产环境慎用可滚动/可更新 ResultSet | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 批量操作未配 rewriteBatchedStatements，addBatch 没有效果 | 用了 addBatch 但性能与逐条执行几乎一样 | 驱动默认把批量拆成逐条发送，未重写为多 VALUES 的 INSERT | JDBC URL 加 `rewriteBatchedStatements=true`，并配合 autoCommit=false 使用 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 自增主键获取方式错误，插入后拿不到新 ID | 插入成功但实体主键为 null 或 0 | 未用 `RETURN_GENERATED_KEYS`，或误用 executeQuery 取主键 | `prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` + `ps.getGeneratedKeys()` | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 时区配置缺失导致时间相差 8 小时 | 入库时间与业务时间对不上 | JDBC URL 未指定 serverTimezone，JVM 与数据库时区不一致 | URL 显式加 `serverTimezone=Asia/Shanghai`，并统一 JVM 与数据库时区 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| 字符集未指定导致中文写入变问号 | 中文内容入库后乱码或丢失 | URL 未指定 characterEncoding，库表字符集也不是 utf8mb4 | URL 加 `characterEncoding=utf8`，库表统一使用 utf8mb4 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
| DDL 语句写在业务事务中导致前面操作被隐式提交 | 事务未走到 commit，前面的写入却已落库 | MySQL 执行 DDL 会隐式提交当前事务 | DDL 不要在业务事务中执行，单独用独立连接或提前执行 | [02-JDBC核心原理-导览](./02-JDBC核心原理-导览.md) |
