## 一、核心概念

### 1.1 异常是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 程序运行中发生的意外情况，会中断正常指令流，由异常处理机制捕获处理 |
| 能做什么 | 分离业务与错误逻辑；沿调用栈传播异常；分类差异化处理；保证资源释放 |
| 怎么用 | try-catch-finally 捕获处理或 throws 声明抛出 |
| 原理和工作流程 | 异常以对象形式抛出，沿调用栈向上传播直到匹配的 catch 处理器。异常处理将正常业务逻辑与错误处理分离提升可读性与健壮性。未捕获异常最终致线程终止并打印栈信息。异常类层次结构支持按类型差异化处理 |
| 缺点 | 异常处理有性能开销；过度捕获掩盖编程错误；异常流控制降低可读性 |

### 1.2 异常体系：Throwable / Error / Exception

| 维度 | 内容 |
|------|------|
| 是什么 | 以 Throwable 为根、分 Error 与 Exception 两大分支的异常类层次体系 |
| 能做什么 | 区分不可处理 Error；区分受检与非受检异常；按类型捕获处理 |
| 怎么用 | Error 不捕获，受检异常必须处理，非受检异常可选处理 |
| 原理和工作流程 | Throwable 下分 Error 与 Exception。Error 是 JVM 级严重错误如 OOM、StackOverflow 不可处理不应捕获。Exception 分 RuntimeException 及其子类（非受检异常，编译器不强制处理如 NPE、数组越界）与其他 Exception（受检异常，编译器强制 try-catch 或 throws 如 IOException、SQLException） |
| 缺点 | 三层分类初学者易混；受检异常滥用致代码冗长；Error 与 Exception 边界有时模糊 |

### 1.3 常见异常类型速查表

| 维度 | 内容 |
|------|------|
| 是什么 | Java 常见异常类型及其触发条件与示例的速查集合 |
| 能做什么 | 识别 NPE、越界、类型转换、算术、格式、参数、IO、SQL 等异常触发场景 |
| 怎么用 | `Integer.parseInt("abc")` 抛 NumberFormatException |
| 原理和工作流程 | 常见运行时异常含 NullPointerException（null 调方法）、ArrayIndexOutOfBoundsException（越界访问）、ClassCastException（不兼容强转）、ArithmeticException（整数除零）、NumberFormatException（非数字解析）、IllegalArgumentException（非法参数）。受检异常含 IOException、SQLException、ClassNotFoundException。Error 含 OutOfMemoryError、StackOverflowError |
| 缺点 | 异常类型多难全记；同类异常触发场景多；需结合栈信息定位 |

### 1.4 try-catch-finally 基本语法

| 维度 | 内容 |
|------|------|
| 是什么 | 捕获并处理异常的三段式语法结构，含 try、catch、finally |
| 能做什么 | try 监控异常；catch 按类型捕获；finally 保证释放资源；多重 catch |
| 怎么用 | `try { } catch (Exception e) { } finally { }` |
| 原理和工作流程 | try 块抛出异常后后续代码不执行，JVM 从上到下匹配 catch 块，子类异常须在父类之前否则编译错误不可达。JDK7+ 支持多异常捕获 `catch (IOException | SQLException e)`。finally 无论是否异常都执行用于资源释放。异常对象常用 getMessage、toString、printStackTrace 获取信息 |
| 缺点 | 多重 catch 顺序敏感；空 catch 吞异常；finally 写 return 吞异常 |

### 1.5 throws 关键字：声明抛出异常

| 维度 | 内容 |
|------|------|
| 是什么 | 用在方法签名上声明该方法可能抛出的异常，将处理责任推给调用者 |
| 能做什么 | 声明单个或多个异常；向上传递处理责任；约束子类重写异常范围 |
| 怎么用 | `void readFile() throws IOException, SQLException {}` |
| 原理和工作流程 | throws 声明受检异常告知调用者须处理或继续声明。子类重写方法抛出异常不能比父类更宽泛，可不抛或抛父类异常的子类。throws 是声明非动作，将异常沿调用栈向上传播直到有 catch 处理或线程终止 |
| 缺点 | 滥用 throws 致方法签名冗长；异常层层声明污染代码；调用者被迫处理无关异常 |

### 1.6 throw 关键字：手动抛出异常

| 维度 | 内容 |
|------|------|
| 是什么 | 用在方法体内手动创建并抛出一个异常对象的关键字 |
| 能做什么 | 参数校验抛异常；抛业务异常；触发错误处理流程 |
| 怎么用 | `throw new IllegalArgumentException("年龄不合法");` |
| 原理和工作流程 | throw 创建异常对象并抛出，中断当前方法执行沿调用栈传播。一次只能抛一个异常对象。与 throws 区别：throw 是动作在方法体内抛出对象，throws 是声明在方法签名上告知可能抛出类型。常用于参数校验与业务逻辑异常 |
| 缺点 | 滥用异常控制流程有性能开销；异常信息不具体难排查；抛受检异常强制调用者处理 |

### 1.7 自定义异常

| 维度 | 内容 |
|------|------|
| 是什么 | 继承 Exception 或 RuntimeException 定义的业务专用异常类 |
| 能做什么 | 表达业务错误语义；携带业务数据；构建异常链保留原始异常 |
| 怎么用 | `class UserNotFoundException extends Exception {}` |
| 原理和工作流程 | 继承 Exception 为受检异常强制调用者处理，继承 RuntimeException 为非受检异常不强制。应提供无参、带 message、带 message 与 cause 的构造器以支持异常链。类名以 Exception 结尾见名知意。选择依据：调用者必须处理用 Exception，无法恢复用 RuntimeException |
| 缺点 | 自定义异常类增多；受检自定义异常污染代码；命名不当失去语义 |

### 1.8 try-with-resources（自动资源管理）

| 维度 | 内容 |
|------|------|
| 是什么 | JDK7 引入的自动关闭 AutoCloseable 资源的语法糖 |
| 能做什么 | 自动关闭资源；管理多个资源；JDK9 支持已声明 effectively final 变量 |
| 怎么用 | `try (BufferedReader br = new BufferedReader(...)) { }` |
| 原理和工作流程 | 资源须实现 AutoCloseable 接口。try 块结束时无论是否异常自动调用 close。多个资源用分号分隔按声明逆序关闭。编译后展开为 try-catch-finally 结构，close 异常作为被压制异常附加到主异常通过 getSuppressed 获取。JDK9 允许使用已声明的 effectively final 变量 |
| 缺点 | 资源须实现 AutoCloseable；JDK7 才支持；多资源关闭顺序固定不可控 |

## 二、底层原理

### 2.1 异常处理机制底层原理

| 维度 | 内容 |
|------|------|
| 是什么 | 编译器为方法生成异常处理表、JVM 运行时按表匹配处理器的机制 |
| 能做什么 | 生成异常处理表；按偏移量匹配 catch；沿调用栈传播异常 |
| 怎么用 | 异常表存 from、to、target、type 四字段 |
| 原理和工作流程 | 编译器为每个可能抛异常的方法在 Code 属性生成异常处理表，记录 try 块字节码偏移范围 from-to、catch 入口 target、捕获类型 type。抛异常时 JVM 在当前方法异常表查找匹配条目，用 instanceof 判断类型，匹配则压入异常对象跳转 target 执行 catch。无一匹配则弹出栈帧在调用者继续查找直至线程终止 |
| 缺点 | 异常表对开发者透明难调试；异常传播有栈帧弹出开销；未捕获异常致线程终止 |

### 2.2 finally 的执行原理与 return 陷阱

| 维度 | 内容 |
|------|------|
| 是什么 | finally 执行机制及其中 return 覆盖 try/catch 返回值与吞异常的陷阱 |
| 能做什么 | 说明 finally 几乎必执行；说明 return 覆盖与吞异常；区分基本与引用类型修改 |
| 怎么用 | finally 中不写 return 只做资源释放 |
| 原理和工作流程 | finally 在 try 或 catch 的 return 计算返回值并暂存后执行，若 finally 有 return 则覆盖暂存值且吞掉异常。基本类型在 return 时值已压栈，finally 修改局部变量不影响暂存值。引用类型 return 暂存的是地址，finally 修改对象内容对外可见。System.exit、JVM 崩溃、守护线程结束、无限循环时 finally 不执行 |
| 缺点 | finally return 吞异常是高频陷阱；基本类型假修改违反直觉；finally 抛异常覆盖原异常 |

### 2.3 try-with-resources 的字节码原理

| 维度 | 内容 |
|------|------|
| 是什么 | try-with-resources 编译后展开为 try-catch-finally 并用压制异常保留 close 异常的机制 |
| 能做什么 | 自动展开为传统结构；压制 close 异常附加到主异常；保证资源关闭顺序 |
| 怎么用 | 编译器生成 addSuppressed 调用 |
| 原理和工作流程 | 编译器将 try-with-resources 展开为声明资源、try 块、catch 捕获主异常、finally 关闭资源的结构。当 try 块与 close 都抛异常时，close 异常不丢弃而通过 addSuppressed 附加到主异常，调用 getSuppressed 获取。资源按声明逆序关闭确保依赖顺序正确 |
| 缺点 | 生成的字节码复杂；压制异常易被忽略；需调用 getSuppressed 才能看到 close 异常 |

## 三、实战应用

### 3.1 try-catch 与 throws 使用场景对比

| 维度 | 内容 |
|------|------|
| 是什么 | 实际开发中在 try-catch 就地处理与 throws 向上声明间的权衡决策 |
| 能做什么 | 可恢复用 try-catch 降级；无法处理用 throws 上抛；底层异常转业务异常 |
| 怎么用 | 谁能处理谁 catch，处理不了就 throws |
| 原理和工作流程 | try-catch 适用于可自行恢复提供降级、与用户交互给友好提示、底层异常转业务异常、循环批量个别失败不影响整体。throws 适用于调用者更清楚如何处理、框架约定须抛特定异常、工具类底层库不应吞异常。核心原则谁能处理谁 catch，不能处理就 throws 不要吞异常 |
| 缺点 | 决策不当致异常吞没或层层声明；try-catch 包裹过大致循环终止；滥用 throws 污染签名 |

### 3.2 finally 中 return 陷阱详解

| 维度 | 内容 |
|------|------|
| 是什么 | finally 中 return 吞异常、基本类型假修改、引用类型真修改三类陷阱详解 |
| 能做什么 | 识别 return 吞异常；识别基本类型值不变；识别引用类型内容被改 |
| 怎么用 | finally 只做资源释放不写 return |
| 原理和工作流程 | 陷阱一 finally return 吞掉 try 异常调用者无感知。陷阱二基本类型 return 时值已压操作数栈，finally 修改局部变量表不影响暂存值故返回原值。陷阱三引用类型 return 暂存地址，finally 修改对象内容因同一对象故对外可见。正确做法 finally 只释放资源或用 try-with-resources |
| 缺点 | 陷阱违反直觉难排查；基本与引用行为不一致；finally return 破坏异常传播 |

## 四、常见面试题（附答案）

### 1. Java 异常体系是怎样的？Error 和 Exception 有什么区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Throwable 体系结构及 Error 与 Exception 的区别 |
| 能做什么 | 画出体系结构；区分严重程度与可恢复性；区分处理要求 |
| 怎么用 | Error 不捕获，Exception 可捕获处理 |
| 原理和工作流程 | Throwable 是根类，下分 Error 与 Exception。Error 是 JVM 级严重错误如 OOM、StackOverflow 无法恢复不应捕获。Exception 是程序级问题可捕获处理，又分受检异常（编译器强制处理如 IOException）与非受检异常（RuntimeException 子类编译器不强制如 NPE） |
| 缺点 | 体系层次多易混；Error 与 Exception 边界有时模糊；受检非受检选择有争议 |

### 2. 受检异常（Checked）和非受检异常（Unchecked）有什么区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查两类异常在编译检查与设计理念上的差异 |
| 能做什么 | 区分父类与编译检查；区分设计理念；说明 Spring 事务回滚差异 |
| 怎么用 | 可恢复预期用受检，编程错误用非受检 |
| 原理和工作流程 | 受检异常是 Exception 非 RuntimeException 子类，编译器强制 try-catch 或 throws，表示调用者可预期并恢复如文件不存在。非受检异常是 RuntimeException 子类编译器不检查，通常表示编程错误应修复代码如 NPE。Spring 事务默认仅对非受检异常回滚 |
| 缺点 | 受检异常滥用致代码冗长；非受检异常易被忽略；选型有争议 |

### 3. throw 和 throws 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 throw 抛出动作与 throws 声明的位置与本质差异 |
| 能做什么 | 区分位置；区分作用；区分数量与本质 |
| 怎么用 | throw 在方法体内抛对象，throws 在签名上声明类型 |
| 原理和工作流程 | throw 用在方法体内部手动创建并抛出一个异常对象是动作，一次只能抛一个。throws 用在方法签名上声明可能抛出的异常类型是声明，可声明多个逗号分隔，将处理责任交给调用者。throw 主动触发异常，throws 告知调用者须处理 |
| 缺点 | 两者拼写相似易混；throw 滥用控制流程有开销；throws 滥用污染签名 |

### 4. finally 一定会执行吗？finally 中的 return 会怎样？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 finally 执行条件及其中 return 覆盖与吞异常行为 |
| 能做什么 | 列举 finally 不执行情况；说明 return 覆盖返回值；说明吞异常 |
| 怎么用 | 强烈不建议在 finally 写 return |
| 原理和工作流程 | finally 绝大多数情况执行，不执行的情况有 System.exit、JVM 崩溃、守护线程中所有非守护线程结束、try/catch 无限循环。finally 中的 return 会覆盖 try 或 catch 的返回值并吞掉异常使调用者无法感知错误，故不应在 finally 写 return |
| 缺点 | finally return 吞异常是隐蔽 bug；不执行条件易被忽略；return 覆盖难排查 |

### 5. try-with-resources 的原理是什么？和传统 try-finally 相比有什么优势？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 try-with-resources 编译展开原理及相对传统方式的优势 |
| 能做什么 | 说明语法糖展开；说明压制异常机制；列举优势 |
| 怎么用 | 资源须实现 AutoCloseable |
| 原理和工作流程 | try-with-resources 是编译器语法糖，编译后展开为传统 try-catch-finally，资源须实现 AutoCloseable。try 与 close 都抛异常时 close 异常作为被压制异常附加到主异常通过 getSuppressed 获取不丢弃。优势：代码简洁、自动正确关闭、正确处理 close 异常、资源按声明逆序关闭 |
| 缺点 | 资源须实现 AutoCloseable；JDK7 才支持；生成的字节码复杂 |

### 6. 自定义异常应该继承 Exception 还是 RuntimeException？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查自定义异常父类选择依据 |
| 能做什么 | 说明继承 Exception 强制处理；说明继承 RuntimeException 不强制；结合 Spring 事务 |
| 怎么用 | 多数项目继承 RuntimeException |
| 原理和工作流程 | 继承 Exception 为受检异常希望调用者必须显式处理。继承 RuntimeException 为非受检异常调用者无需强制处理表示不可恢复编程错误。实际项目多数继承 RuntimeException，因 Spring 事务默认仅对非受检异常回滚，且现代框架倾向非受检避免代码污染 |
| 缺点 | 受检异常污染代码；非受检异常易被忽略；Spring 事务回滚策略需配合 |
