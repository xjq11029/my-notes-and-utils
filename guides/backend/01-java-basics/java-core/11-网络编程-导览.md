## 一、核心概念

### 1.1 网络编程三要素

| 维度 | 内容 |
|------|------|
| 是什么 | 网络通信的三个基本要素：IP 地址、端口号、通信协议 |
| 能做什么 | IP 定位主机；端口定位进程；协议约定通信规则 |
| 怎么用 | `Socket("127.0.0.1", 8080)` 指定 IP 与端口 |
| 原理和工作流程 | IP 地址标识网络中的主机，IPv4 为 32 位四段十进制，IPv6 为 128 位。端口号标识主机内进程，范围 0 到 65535，0 到 1023 为系统端口。协议约定数据格式与传输规则，传输层协议为 TCP 与 UDP。三者共同确定通信端点：IP 加端口即 Socket 地址 |
| 缺点 | IPv4 资源枯竭；端口冲突；协议选择影响可靠性；需理解网络分层 |

### 1.2 InetAddress 类

| 维度 | 内容 |
|------|------|
| 是什么 | java.net.InetAddress 表示 IP 地址的类，封装主机名与 IP |
| 能做什么 | 获取本机地址；按主机名解析 IP；获取主机名；判断可达性 |
| 怎么用 | `InetAddress addr = InetAddress.getByName("www.baidu.com");` |
| 原理和工作流程 | InetAddress 无构造器通过静态方法 getLocalHost、getByName、getAllByName 获取实例。getByName 通过 DNS 解析主机名为 IP 地址。getHostName 反向解析 IP 为主机名。isReachable 通过 ICMP 或 TCP 探测可达性。Inet4Address 与 Inet6Address 为其子类分别表示 IPv4 与 IPv6 |
| 缺点 | DNS 解析阻塞可能超时；isReachable 受防火墙限制；反向解析可能失败；不支持端口 |

### 1.3 TCP 编程（Socket / ServerSocket）

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 TCP 协议的面向连接可靠通信编程，客户端用 Socket 服务端用 ServerSocket |
| 能做什么 | 建立连接；流式读写；服务端监听多客户端；三次握手建连 |
| 怎么用 | 服务端 `ServerSocket ss = new ServerSocket(8080); Socket s = ss.accept();` |
| 原理和工作流程 | 服务端 ServerSocket 绑定端口 listen，accept 阻塞等待客户端连接返回 Socket。客户端 Socket 指定服务端 IP 端口发起连接经三次握手建立。连接后双方通过 Socket 的 getInputStream 与 getOutputStream 流式读写。TCP 面向连接可靠有序但需建连开销。一客户端一线程模型处理并发 |
| 缺点 | accept 阻塞致单线程无法多客户端；连接建立有开销；资源未释放致连接耗尽；C10K 问题 |

### 1.4 UDP 编程（DatagramSocket）

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 UDP 协议的无连接不可靠数据报通信编程，用 DatagramSocket 与 DatagramPacket |
| 能做什么 | 发送接收数据报；无需建连；支持广播多播；低延迟 |
| 怎么用 | `ds.send(new DatagramPacket(data, len, addr, port));` |
| 原理和工作流程 | UDP 无连接，发送方将数据封装为 DatagramPacket 指定目标地址端口用 DatagramSocket.send 发送，接收方 DatagramSocket 绑定端口 receive 阻塞接收 DatagramPacket。UDP 不保证可靠有序不保证到达但低延迟无建连开销。适合直播、DNS、视频会议等容忍丢包场景。MulticastSocket 支持多播 |
| 缺点 | 不可靠可能丢包乱序；不保证到达；数据报大小受限；需应用层处理可靠性 |

### 1.5 URL 编程

| 维度 | 内容 |
|------|------|
| 是什么 | java.net.URL 表示统一资源定位符，用于访问网络资源 |
| 能做什么 | 解析 URL 各部分；打开连接读取；下载文件；URLConnection 交互 |
| 怎么用 | `URL url = new URL("https://a.com/f.txt"); InputStream is = url.openStream();` |
| 原理和工作流程 | URL 封装协议、主机、端口、路径、查询参数等。openConnection 返回 URLConnection 可设置请求头与超时，openStream 直接返回输入流。HttpURLConnection 是 HTTP 子类支持 GET POST 与状态码。JDK11+ HttpClient 提供更现代的 HTTP/2 客户端替代 URLConnection |
| 缺点 | URLConnection API 老旧；不支持 HTTP/2；超时需手动设置；编码处理繁琐 |

## 二、底层原理

### 2.1 TCP 三次握手与四次挥手

| 维度 | 内容 |
|------|------|
| 是什么 | TCP 建立连接的三次握手与断开连接的四次挥手过程 |
| 能做什么 | 描述握手建连；描述挥手断连；说明状态变迁；解释为何三次四次 |
| 怎么用 | 握手 SYN/SYN+ACK/ACK，挥手 FIN/ACK/FIN/ACK |
| 原理和工作流程 | 三次握手：客户端发 SYN 进入 SYN_SENT，服务端回 SYN+ACK 进入 SYN_RCVD，客户端再发 ACK 进入 ESTABLISHED 建立连接。三次因需确认双方收发能力。四次挥手：主动方发 FIN 进入 FIN_WAIT_1，被动方回 ACK 进入 CLOSE_WAIT，被动方发 FIN 进入 LAST_ACK，主动方回 ACK 进入 TIME_WAIT 等待 2MSL 后关闭。四次因 TCP 全双工需各自关闭 |
| 缺点 | 过程复杂状态多；TIME_WAIT 占用端口资源；握手有延迟；挥手需等 2MSL |

### 2.2 TCP vs UDP 底层对比

| 维度 | 内容 |
|------|------|
| 是什么 | TCP 与 UDP 两种传输层协议的特性对比 |
| 能做什么 | 对比连接性；对比可靠性；对比有序性；对比速度与开销 |
| 怎么用 | 可靠传输用 TCP，实时低延迟用 UDP |
| 原理和工作流程 | TCP 面向连接需三次握手，可靠传输有确认重传流量控制拥塞控制，有序全双工字节流，头部 20 字节开销大。UDP 无连接，不可靠无确认无序，数据报文，头部 8 字节开销小，支持广播多播。TCP 适合文件传输 HTTP 邮件，UDP 适合 DNS 直播视频会议 |
| 缺点 | TCP 开销大延迟高；UDP 不可靠；选型需权衡可靠性与延迟；各有适用场景 |

### 2.3 Socket 本质

| 维度 | 内容 |
|------|------|
| 是什么 | Socket 是应用层与传输层之间的编程接口 API，封装 TCP/IP 通信细节 |
| 能做什么 | 封装网络通信；提供流式读写；屏蔽协议细节；标识通信端点 |
| 怎么用 | Socket 即 IP 加端口构成的通信端点抽象 |
| 原理和工作流程 | Socket 不是协议而是通信端点的抽象，由 IP 地址与端口号标识，是操作系统提供的网络编程接口。应用通过 Socket API 调用操作系统内核的 TCP/IP 协议栈完成通信，无需关心底层封包解包。Socket 屏蔽了网络分层细节，应用层只需读写流。一个 Socket 五元组为协议、本地 IP、本地端口、远端 IP、远端端口 |
| 缺点 | 抽象层增加理解难度；不同平台实现有差异；阻塞模型限制并发；需理解底层才能调优 |

### 2.4 BIO 模型（阻塞 IO）

| 维度 | 内容 |
|------|------|
| 是什么 | 传统阻塞 IO 模型，每个连接独占一个线程，IO 操作阻塞线程 |
| 能做什么 | 一连接一线程；accept 阻塞等待；read 阻塞读取；简单直观 |
| 怎么用 | 主线程 accept 循环，每连接 new Thread 处理 |
| 原理和工作流程 | BIO 服务端主线程在 accept 阻塞等待连接，每来一个连接新建线程处理该线程在 read 时阻塞直至数据到达。连接空闲时线程也阻塞占用资源。一连接一线程模型在连接数少时简单有效，但连接数多时线程开销大且空闲线程浪费资源，无法支撑高并发即 C10K 问题。需 NIO 多路复用解决 |
| 缺点 | 一连接一线程资源浪费；无法支撑高并发；线程切换开销大；连接空闲占用线程 |

## 三、实战应用

### 3.1 简单的 Echo 程序（TCP）

| 维度 | 内容 |
|------|------|
| 是什么 | 服务端回显客户端消息的 TCP 通信入门程序 |
| 能做什么 | 服务端 accept 等待；客户端连接发送；服务端读取回写；验证通信流程 |
| 怎么用 | 服务端 accept 后 read 再 write，客户端 write 后 read |
| 原理和工作流程 | 服务端 ServerSocket 绑定端口 accept 阻塞等待，客户端 Socket 连接经三次握手建立。客户端通过输出流发送消息，服务端通过输入流读取并原样通过输出流回写，客户端通过输入流读取回显。演示 TCP 流式通信完整流程。需用字符流包装并指定编码 |
| 缺点 | 单线程无法多客户端；阻塞模型限制并发；忘记关闭致资源泄漏；无异常处理 |

### 3.2 UDP 广播发送

| 维度 | 内容 |
|------|------|
| 是什么 | 用 UDP DatagramSocket 发送广播数据报的应用 |
| 能做什么 | 设置广播地址；发送数据报；接收端监听；无连接通信 |
| 怎么用 | `ds.send(new DatagramPacket(data, len, broadcastAddr, port));` |
| 原理和工作流程 | 发送方 DatagramSocket 设置 SO_BROADCAST 启用广播，将数据报发往广播地址如 255.255.255.255 或子网广播地址，子网内所有监听该端口的接收方均收到。接收方 DatagramSocket 绑定端口 receive 阻塞接收。UDP 广播无连接一次性发给所有主机，适合服务发现、局域网通知等场景 |
| 缺点 | 广播范围受限局域网；不可靠可能丢包；广播流量大；不跨网段 |

### 3.3 项目：多人聊天室

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 TCP 与多线程实现的多客户端实时聊天室项目 |
| 能做什么 | 多客户端连接；服务端转发消息；客户端收发；群聊广播 |
| 怎么用 | 服务端线程池处理连接，维护在线客户端集合转发消息 |
| 原理和工作流程 | 服务端主线程 accept 循环接收连接，每连接交由线程池处理，维护在线客户端 Socket 集合。客户端发送消息后服务端读取并遍历集合转发给所有其他客户端实现群聊。客户端需独立读线程接收消息。涉及多线程并发集合同步、连接管理、消息协议设计。是 BIO 多线程模型的典型应用 |
| 缺点 | 一连接一线程难扩展；消息广播遍历开销；并发集合需同步；无消息边界处理粘包 |

### 3.4 使用 URL 下载网络文件

| 维度 | 内容 |
|------|------|
| 是什么 | 用 URL 与 URLConnection 下载网络文件的应用 |
| 能做什么 | 打开 URL 连接；读取输入流；写入本地文件；显示进度 |
| 怎么用 | `InputStream is = url.openStream(); Files.copy(is, path)` |
| 原理和工作流程 | 用 URL 封装文件地址，openStream 或 openConnection 获取输入流，循环读取字节写入本地 FileOutputStream 或用 Files.copy 一行完成。可设置连接超时与读取超时避免卡死。大文件应分块读取显示进度。JDK11+ HttpClient 提供更现代的下载方式支持异步与 HTTP/2 |
| 缺点 | 需设置超时避免卡死；大文件占内存；网络异常需处理；编码与重定向问题 |

## 四、常见面试题（附答案）

### 1. TCP 和 UDP 的区别是什么？分别适用什么场景？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 TCP 与 UDP 两种传输层协议的差异与场景 |
| 能做什么 | 对比连接可靠性有序性；对比开销速度；给出适用场景 |
| 怎么用 | 可靠用 TCP，实时用 UDP |
| 原理和工作流程 | TCP 面向连接需三次握手，可靠有确认重传流量拥塞控制，有序全双工字节流，头部 20 字节。UDP 无连接不可靠无序，数据报文头部 8 字节，支持广播多播。TCP 适合文件传输 HTTP 邮件等需可靠场景，UDP 适合 DNS 直播视频会议等容忍丢包求低延迟场景 |
| 缺点 | TCP 开销大延迟高；UDP 不可靠；需按场景权衡；各有局限 |

### 2. 为什么 TCP 建立连接需要三次握手，而断开连接需要四次挥手？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查三次握手与四次挥手的原因 |
| 能做什么 | 解释三次握手确认双方收发；解释四次挥手全双工各自关闭；说明 TIME_WAIT |
| 怎么用 | 握手 SYN/ACK，挥手 FIN/ACK |
| 原理和工作流程 | 三次握手因需确认双方收发能力：客户端 SYN 表明可发，服务端 SYN+ACK 表明可收可发，客户端 ACK 表明可收，三次后双方确认收发能力。四次挥手因 TCP 全双工各自独立关闭：主动方 FIN 表示不再发数据，被动方 ACK 后可能还有数据要发，故被动方 FIN 与主动方 ACK 分开，需四次。TIME_WAIT 等 2MSL 确保最后 ACK 到达并使旧报文失效 |
| 缺点 | 过程复杂；TIME_WAIT 占资源；状态多易混；挥手不对称难理解 |

### 3. 什么是 Socket？Socket 中 BIO、NIO、AIO 有什么区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Socket 概念与三种 IO 模型区别 |
| 能做什么 | 解释 Socket 端点抽象；对比 BIO 阻塞 NIO 多路复用 AIO 异步；说明适用场景 |
| 怎么用 | 简单用 BIO，高并发用 NIO，Linux AIO 受限 |
| 原理和工作流程 | Socket 是 IP 加端口构成的通信端点抽象，是应用层与传输层间的编程接口。BIO 同步阻塞一连接一线程 accept 与 read 阻塞适合连接少。NIO 同步非阻塞 Selector 多路复用一个线程管理多连接，Channel 就绪才处理适合高并发如 Netty。AIO 异步非阻塞由操作系统回调完成适合连接多且操作重，但 Linux 支持不完善实际多用 NIO |
| 缺点 | BIO 无法高并发；NIO 编程复杂；AIO 平台支持差；选型需权衡 |

### 4. URI 和 URL 的区别是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 URI 与 URL 的概念区别 |
| 能做什么 | 区分标识与定位；说明 URL 是 URI 子集；举例 |
| 怎么用 | URL urn 都是 URI 子集 |
| 原理和工作流程 | URI 统一资源标识符用于标识资源，是抽象概念。URL 统一资源定位符是 URI 子集，通过位置定位资源含协议主机路径如 https://a.com/f。URN 统一资源名是 URI 另一子集通过名称标识如 urn:isbn:123。URL 是 URI 最常见形式，URL 一定是 URI 但 URI 不一定是 URL |
| 缺点 | 概念抽象易混；URN 使用少；区分意义在实际开发中有限 |

### 5. TCP 粘包拆包问题是什么？怎么解决？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 TCP 流式传输的粘包拆包现象及解决方案 |
| 能做什么 | 解释粘包拆包成因；列举解决方案；说明应用层定界 |
| 怎么用 | 消息定长、分隔符、长度字段 |
| 原理和工作流程 | TCP 是字节流无边界，应用层多次发送可能被合并为一次接收即粘包，或一次发送被拆为多次接收即拆包。因 TCP 只保证字节流顺序不保证消息边界。解决方案：一消息定长不足补齐；二用分隔符如换行符；三用长度字段前缀标明消息长度最常用；四自定义协议头含长度。Netty 提供多种解码器处理 |
| 缺点 | 需应用层处理增加复杂度；定长浪费空间；分隔符需转义；长度字段需解析 |

### 6. UDP 一定不可靠吗？为什么很多直播用 UDP？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 UDP 可靠性边界与直播场景选型 |
| 能做什么 | 解释 UDP 不可靠原因；解释直播用 UDP 优势；说明应用层可补可靠 |
| 怎么用 | 直播用 UDP 加应用层 FEC |
| 原理和工作流程 | UDP 本身不可靠不保证到达有序，但可在应用层补充可靠性如 QUIC 协议基于 UDP 实现可靠传输。直播用 UDP 因实时性要求高容忍丢包：TCP 重传致延迟累积不适合实时，UDP 丢包直接跳过保持实时。直播常结合 FEC 前向纠错与应用层重传策略平衡实时与可靠。WebRTC 即基于 UDP |
| 缺点 | UDP 需应用层补可靠增加开发量；网络拥塞控制需自己实现；与 TCP 混用可能不公平 |
