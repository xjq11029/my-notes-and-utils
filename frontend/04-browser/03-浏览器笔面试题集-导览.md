### 1. 浏览器渲染流程中，以下哪个步骤最先执行

| 维度 | 内容 |
|------|------|
| 是什么 | 浏览器渲染流程的第一步是解析 HTML 构建 DOM 树，然后解析 CSS 构建 CSSOM 树，再合并为 Render 树，最后 Layout 和 Paint。 |
| 能做什么 | 理解渲染流程的先后顺序，有助于优化关键渲染路径：优先加载 HTML、尽早解析和渲染。 |

### 2. 以下哪个操作一定会触发回流（Reflow）

| 维度 | 内容 |
|------|------|
| 是什么 | 修改元素的 `width` 属性改变了几何属性，会影响布局，一定会触发回流；修改 `color`、`background-color`、`visibility` 只触发重绘。 |
| 能做什么 | 区分触发重排和重绘的 CSS 属性，在动画和交互中选择只触发重绘的属性以降低性能开销。 |
| 怎么用 | 修改 `element.style.width = '100px'` 触发重排；修改 `element.style.color = 'red'` 只触发重绘。 |
| 原理和工作流程 | 回流（重排）需要浏览器重新计算布局，从 Layout 阶段开始；重绘仅需要重新绘制像素，跳过 Layout 阶段。 |
| 缺点 | 开发者不容易记住所有 CSS 属性的触发类型，需要参考 CSS Triggers 文档。 |

### 3. 关于重排和重绘的说法，正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | 重排一定会触发重绘，因为布局变了必须重新绘制；重绘不一定触发重排，只修改颜色不影响布局；`display: none` 同时触发重排和重绘。 |
| 能做什么 | 理解重排和重绘的因果关系，帮助在开发中做出正确的性能优化决策。 |
| 怎么用 | 避免频繁修改触发重排的属性；使用 `visibility: hidden` 代替 `display: none` 可避免重排（仅触发重绘）。 |
| 原理和工作流程 | 重排从 Layout 阶段开始，之后必然进入 Paint 阶段；重绘跳过 Layout 直接从 Paint 阶段开始；`display: none` 将元素从渲染树移除，恢复时触发重排+重绘。 |
| 缺点 | 区分重排和重绘是理论层面，实际开发中浏览器优化可能模糊两者边界。 |

### 4. V8 引擎中，Ignition 的作用是

| 维度 | 内容 |
|------|------|
| 是什么 | Ignition 是 V8 的解释器，负责将 JavaScript 代码解析为字节码并解释执行，是 V8 执行流水线的第二阶段。 |
| 能做什么 | 将 AST（由 Parser 生成）转换为字节码；解释执行字节码；收集热点代码信息供 TurboFan 优化编译使用。 |
| 怎么用 | 开发者无需直接操作 Ignition，但理解其角色有助于理解 V8 的 JIT 编译流程。 |
| 原理和工作流程 | Parser 将 JavaScript 源码解析为 AST；Ignition 将 AST 转换为字节码并逐条解释执行；TurboFan 识别热点代码（频繁执行的代码），将其编译为优化机器码；如果优化假设失效，TurboFan 会反优化回退到 Ignition 解释执行。 |
| 缺点 | 解释执行比编译执行慢，冷启动时性能不如预编译方案。 |

### 5. 关于 Event Loop 的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | 微任务优先级高于宏任务，每个宏任务执行完后立即清空微任务队列，然后才执行下一个宏任务。 |
| 能做什么 | 正确预测异步代码的执行顺序，理解为什么 `Promise.then` 回调比 `setTimeout` 回调先执行。 |
| 怎么用 | `console.log('1'); setTimeout(() => console.log('2'), 0); Promise.resolve().then(() => console.log('3')); console.log('4');` 输出 1、4、3、2。 |
| 原理和工作流程 | 同步代码（script 宏任务）执行完后，清空微任务队列；然后取出下一个宏任务（setTimeout）执行，再清空微任务队列；微任务产生的微任务也在当前轮次执行。 |
| 缺点 | 微任务无限递归会导致页面卡死。 |

### 6. 以下哪个不属于宏任务（MacroTask）

| 维度 | 内容 |
|------|------|
| 是什么 | `Promise.then` 属于微任务（MicroTask），不属于宏任务；宏任务包括 `setTimeout`、`setInterval`、`I/O`、`script` 整体代码段。 |
| 能做什么 | 区分宏任务和微任务的类型，在编码时选择合适的异步 API。 |
| 怎么用 | 需要延迟到下一个宏任务执行时使用 `setTimeout`；需要尽快执行（在下一个宏任务前）使用 `Promise.then` 或 `queueMicrotask`。 |
| 原理和工作流程 | 宏任务由浏览器的事件循环依次取出执行；微任务在当前宏任务执行完后统一清空。 |
| 缺点 | 不同环境（浏览器/Node.js）的宏任务类型略有差异，增加了理解复杂度。 |

### 7. 以下哪个不属于微任务（MicroTask）

| 维度 | 内容 |
|------|------|
| 是什么 | `setTimeout` 属于宏任务，不属于微任务；微任务包括 `Promise.then/catch/finally`、`MutationObserver`、`queueMicrotask`。 |
| 能做什么 | 区分微任务和宏任务，在需要立即执行（在下一个宏任务之前）的异步操作中使用微任务。 |
| 怎么用 | 使用 `queueMicrotask(() => { ... })` 显式添加微任务；使用 `Promise.resolve().then(() => { ... })` 在微任务队列中执行回调。 |
| 原理和工作流程 | 微任务在当前宏任务执行完后同步清空，比下一个宏任务先执行；在 Node.js 中 `process.nextTick` 优先级高于其他微任务。 |
| 缺点 | 微任务中执行耗时操作会阻塞宏任务和 UI 渲染。 |

### 8. Cookie 的 SameSite 属性设置为 Strict 的作用是

| 维度 | 内容 |
|------|------|
| 是什么 | `SameSite=Strict` 完全禁止第三方请求携带 Cookie，包括从第三方网站点击链接跳转时也不会携带 Cookie。 |
| 能做什么 | 提供最强的 CSRF 防御，确保 Cookie 仅在用户直接从同站访问时发送。 |
| 怎么用 | `Set-Cookie: token=abc; SameSite=Strict`。 |
| 原理和工作流程 | 浏览器判断请求是否为同站请求（同站判断基于 eTLD+1，即有效顶级域名加一级域名）；第三方请求（如从其他网站链接跳转、iframe 嵌入、img 标签引用等）不会附带 Strict Cookie。 |
| 缺点 | 过于严格，从外部链接跳转时用户需要重新登录，用户体验受影响。 |

### 9. 以下哪个不是跨域解决方案

| 维度 | 内容 |
|------|------|
| 是什么 | `localStorage` 受同源策略限制，不同源之间无法共享数据，因此不是跨域解决方案；CORS、JSONP、代理服务器都是跨域解决方案。 |
| 能做什么 | 识别哪些方案可以解决跨域问题，避免错误使用 localStorage 实现跨域通信。 |
| 怎么用 | 跨域通信使用 `postMessage` 或 CORS，而非尝试共享 localStorage。 |
| 原理和工作流程 | 同源策略限制不同源之间的资源访问和存储共享；localStorage 以源为隔离单位，不同源无法访问彼此的 localStorage。 |
| 缺点 | 部分开发者可能误以为 localStorage 可以跨域共享。 |

### 10. 关于 localStorage 和 sessionStorage 的说法，正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | sessionStorage 在关闭标签页后数据清除，localStorage 永久保存（除非手动清除），这是两者最主要的区别；两者容量都约 5MB，都只能存储字符串，都不会随 HTTP 请求发送。 |
| 能做什么 | 根据数据生命周期选择合适的存储方式：临时数据用 sessionStorage，长期缓存用 localStorage。 |
| 怎么用 | `sessionStorage.setItem('formData', JSON.stringify(data))` 临时存储；`localStorage.setItem('theme', 'dark')` 长期存储。 |
| 原理和工作流程 | sessionStorage 与标签页会话绑定，关闭标签页即清除；localStorage 数据持久化到磁盘，跨会话保留；两者都受同源策略限制，都不能跨域访问。 |
| 缺点 | 两者都只能存储字符串，存储对象需要 JSON 序列化/反序列化，有性能开销。 |

### 11. 关于 XSS 攻击的防御措施，不正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | HTTPS 加密传输数据，可以防止中间人攻击，但不能防御 XSS 攻击；XSS 发生在浏览器端，攻击者将恶意脚本注入页面中执行。 |
| 能做什么 | 区分不同安全措施的防护范围：HTTPS 防传输层攻击，XSS 防御需要输入校验、输出编码、CSP 和 HttpOnly Cookie。 |
| 怎么用 | 防御 XSS：`element.textContent = userInput` + `Content-Security-Policy: script-src 'self'` + `Set-Cookie: token=abc; HttpOnly`。 |
| 原理和工作流程 | HTTPS 确保数据在传输过程中不被窃听和篡改，但无法阻止恶意脚本在页面中执行；XSS 攻击的脚本可以是合法的 HTTPS 来源，HTTPS 无法区分。 |
| 缺点 | 开发者容易混淆不同安全措施的作用范围，误以为 HTTPS 能防御所有攻击。 |

### 12. 关于 CSP（内容安全策略）的说法，正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | CSP 可以通过 HTTP 响应头或 `<meta>` 标签设置，限制页面可以加载的资源来源（脚本、样式、图片、字体、连接等），是防御 XSS 的强力手段。 |
| 能做什么 | 禁止内联脚本和 `eval()`；限制脚本只能从可信来源加载；配置违规报告端点监控 CSP 违规情况。 |
| 怎么用 | `Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com`；`<meta http-equiv="Content-Security-Policy" content="default-src 'self'">`。 |
| 原理和工作流程 | 浏览器解析 CSP 策略后建立白名单机制；任何不符合白名单的资源请求被阻止并触发违规报告；`'self'` 表示同源，`'none'` 表示禁止。 |
| 缺点 | CSP 配置不当可能导致正常功能被误拦截；`<meta>` 标签方式不支持所有指令（如 `frame-ancestors`、`report-uri`）。 |

### 13. V8 垃圾回收中，新生代使用什么算法

| 维度 | 内容 |
|------|------|
| 是什么 | V8 新生代使用 Scavenge 算法（Cheney 复制算法），将空间分为 From 和 To 两块，复制存活对象到 To 空间后清空 From 空间并交换角色。 |
| 能做什么 | 快速回收生命周期短的新生对象，适合高频创建和销毁的场景。 |
| 怎么用 | 理解新对象先进入新生代，经历两次 Scavenge 回收后仍存活则晋升到老生代；标记清除和标记整理用于老生代；增量标记用于减少全停顿时间。 |
| 原理和工作流程 | 新生代空间较小，分为 From 和 To 两块；每次回收时，标记 From 中的活对象，复制到 To 空间，清空 From 空间，交换 From 和 To 的角色；复制过程中内存连续，无碎片。 |
| 缺点 | 空间利用率只有一半（From/To 双空间）；晋升策略可能导致短命对象进入老生代。 |

### 14. 关于 requestAnimationFrame 的说法，正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | `requestAnimationFrame` 在浏览器下次重绘之前执行回调，频率与屏幕刷新率同步（通常 60fps），页面不可见时自动暂停。 |
| 能做什么 | 实现流畅动画，保证不掉帧；自动适配不同刷新率设备；节省后台标签页的 CPU 和电量。 |
| 怎么用 | `function animate() { element.style.transform = 'translateX(' + x++ + 'px)'; requestAnimationFrame(animate); } requestAnimationFrame(animate);`。 |
| 原理和工作流程 | rAF 在每帧渲染前执行回调，不会在浏览器空闲时执行；页面切换到后台标签页时自动暂停，恢复后继续；浏览器会将多个 rAF 回调合并到同一帧执行。 |
| 缺点 | 执行频率受屏幕刷新率限制，不适合需要高精确定时的场景。 |

### 15. 关于浏览器进程架构的说法，正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | Chrome 采用多进程架构，默认每个标签页一个独立的渲染进程，渲染进程崩溃只影响对应标签页，不会导致整个浏览器退出。 |
| 能做什么 | 提供稳定性（标签页崩溃隔离）和安全性（沙箱隔离），一个页面的恶意代码难以窃取其他页面数据。 |
| 怎么用 | 开发者无需配置，Chrome 自动管理；通过 Chrome 任务管理器（Shift+Esc）查看各进程。 |
| 原理和工作流程 | 浏览器主进程管理窗口和协调各进程；渲染进程负责页面渲染，默认每个标签页一个；GPU 进程负责硬件加速；网络进程负责网络请求；插件进程运行第三方插件。 |
| 缺点 | 多进程内存占用高，每个进程需要独立的内存空间。 |

### 1. 浏览器从输入 URL 到页面显示的完整渲染流程

| 维度 | 内容 |
|------|------|
| 是什么 | 浏览器渲染的六步流水线：构建 DOM 树、构建 CSSOM 树、生成 Render 树、Layout 布局、Paint 绘制、Composite 合成。 |
| 能做什么 | 系统掌握渲染流程有助于优化关键渲染路径：减少 DOM 深度、优化 CSS 选择器、避免阻塞渲染的脚本。 |
| 怎么用 | 关键步骤：HTML 解析为 DOM 树，遇 `<script>` 阻塞解析；CSS 解析为 CSSOM 树，不阻塞 DOM 解析但阻塞渲染树构建；DOM 和 CSSOM 合并为 Render 树（只含可见节点）；Layout 计算位置；Paint 绘制像素；Composite 合成图层。 |

### 2. 重排和重绘的区别及关系

| 维度 | 内容 |
|------|------|
| 是什么 | 重排是元素几何属性变化时浏览器重新计算布局的过程，代价大；重绘是元素外观变化时重新绘制像素的过程，代价相对较小；重排一定触发重绘，重绘不一定触发重排。 |
| 能做什么 | 区分触发重排和重绘的操作，在编码时优先选择只触发重绘的方案。 |
| 怎么用 | 触发重排：修改 width/height、增删 DOM、改变 display、读取 offsetWidth 等；只触发重绘：修改 color、background-color、visibility。 |
| 原理和工作流程 | 重排从 Layout 阶段重新计算，完成后进入 Paint 阶段；重绘跳过 Layout 直接 Paint。 |
| 缺点 | 浏览器优化（如批量处理）可能模糊重排/重绘的边界，但强制同步回流仍会触发。 |

### 3. 如何减少重排重绘

| 维度 | 内容 |
|------|------|
| 是什么 | 七种减少重排重绘的实践方法：批量修改 DOM（DocumentFragment）、使用 className 批量修改样式、离线 DOM 操作（display: none）、使用 transform 代替 top/left、使用 requestAnimationFrame、提升为独立图层、避免循环中读取布局属性。 |
| 能做什么 | 将多次重排合并为一次；将动画从 Layout 层降到 Composite 层；避免强制同步回流。 |
| 怎么用 | `const fragment = document.createDocumentFragment()` 批量插入；`box.className = 'active'` 批量修改样式；`box.style.display = 'none'` 先隐藏再修改；`transform: translate(0, 100px)` 代替 `top: 100px`；`will-change: transform` 提升为独立图层。 |
| 原理和工作流程 | DocumentFragment 在内存中操作不触发重排；离线 DOM 操作从渲染树中移除元素，修改期间不触发重排；transform 在合成线程执行，跳过 Layout 和 Paint；读取 offsetWidth 等属性会强制浏览器同步回流。 |
| 缺点 | 部分优化手段需要重构现有代码；`will-change` 过度使用会消耗 GPU 内存。 |

### 4. V8 垃圾回收机制

| 维度 | 内容 |
|------|------|
| 是什么 | V8 分代垃圾回收机制：新生代使用 Scavenge 复制算法快速回收短命对象，老生代使用 Mark-Sweep（标记清除）+ Mark-Compact（标记整理）回收长命对象，配合增量标记减少全停顿。 |
| 能做什么 | 理解垃圾回收机制有助于避免内存泄漏：及时清理定时器和事件监听、解除 DOM 引用。 |
| 怎么用 | 新对象进入新生代，经历两次回收仍存活晋升到老生代；标记清除平时使用，碎片多时使用标记整理；增量标记将标记过程拆分为小步骤。 |
| 原理和工作流程 | 详细参见原文。 |
| 缺点 | 全停顿仍可能造成卡顿；内存泄漏排查需要 DevTools 经验。 |

### 5. 浏览器事件循环机制

| 维度 | 内容 |
|------|------|
| 是什么 | JavaScript 单线程下通过宏任务队列和微任务队列实现异步调度的机制：每个宏任务执行完后清空所有微任务，再执行下一个宏任务，循环往复。 |
| 能做什么 | 预测异步代码输出顺序；理解 `Promise.then` 和 `setTimeout` 的执行优先级。 |
| 怎么用 | 宏任务：`setTimeout`、`setInterval`、`I/O`；微任务：`Promise.then/catch/finally`、`MutationObserver`、`queueMicrotask`。 |
| 原理和工作流程 | 详细参见原文。 |
| 缺点 | 微任务无限递归会导致页面卡死。 |

### 6. 跨域的解决方案

| 维度 | 内容 |
|------|------|
| 是什么 | 六种跨域解决方案：CORS（标准方案，服务器设置响应头）、JSONP（利用 script 标签，仅 GET）、代理服务器（转发请求绕过浏览器限制）、postMessage（跨窗口通信）、WebSocket（不受同源限制）、document.domain + iframe（同主域，已废弃）。 |
| 能做什么 | 根据不同场景选择合适方案：生产环境优先 CORS，开发环境用代理，跨窗口通信用 postMessage。 |
| 怎么用 | CORS：服务端设置 `Access-Control-Allow-Origin`；JSONP：动态创建 `<script src="url?callback=fn">`；代理：Vite proxy 配置或 Nginx 反向代理。 |
| 原理和工作流程 | 同源策略限制不同源之间的资源访问；CORS 通过响应头声明允许跨域；JSONP 利用 `<script>` 标签不受同源限制的特性。 |
| 缺点 | CORS 预检请求增加延迟；JSONP 只支持 GET 且不安全；代理增加运维成本。 |

### 7. Cookie、localStorage、sessionStorage、IndexedDB 的区别

| 维度 | 内容 |
|------|------|
| 是什么 | 四种浏览器存储方案的对比：Cookie（约 4KB，每次 HTTP 请求携带）、localStorage（约 5MB，永久）、sessionStorage（约 5MB，标签页关闭清除）、IndexedDB（无上限，结构化数据，异步）。 |
| 能做什么 | Cookie 用于认证和会话管理；localStorage 用于长期缓存；sessionStorage 用于临时数据；IndexedDB 用于大量结构化数据和离线应用。 |
| 怎么用 | `document.cookie = 'token=abc; max-age=3600; secure; samesite=lax'`；`localStorage.setItem('key', 'value')`；`sessionStorage.setItem('key', 'value')`；`indexedDB.open('db', 1)`。 |
| 原理和工作流程 | 详细参见原文。 |
| 缺点 | Cookie 容量小且每次请求携带；localStorage/sessionStorage 仅存储字符串；IndexedDB API 较复杂。 |

### 8. XSS 攻击的原理和防御措施

| 维度 | 内容 |
|------|------|
| 是什么 | XSS 是攻击者将恶意脚本注入页面在用户浏览器中执行的攻击，分为存储型、反射型和 DOM 型三种。 |
| 能做什么 | 防御：输入校验+输出编码、使用 `textContent` 代替 `innerHTML`、CSP 限制脚本来源、HttpOnly Cookie、DOMPurify 清理 HTML。 |
| 怎么用 | `element.textContent = userInput` + `Content-Security-Policy: script-src 'self'` + `Set-Cookie: token=abc; HttpOnly`。 |
| 原理和工作流程 | 存储型：恶意脚本存储在服务器；反射型：恶意脚本通过 URL 参数传递；DOM 型：纯客户端，前端代码不当插入用户输入。 |
| 缺点 | 需要多层防护；富文本编辑器场景完全防御 XSS 难度大。 |

### 9. CSRF 攻击的原理和防御措施

| 维度 | 内容 |
|------|------|
| 是什么 | CSRF 是攻击者利用用户已登录状态，诱导用户访问恶意页面，以用户身份发起非预期请求的攻击。 |
| 能做什么 | 防御：CSRF Token（服务器生成随机 Token）、SameSite Cookie（Strict/Lax）、Referer/Origin 校验、双重 Cookie 验证。 |
| 怎么用 | `Set-Cookie: token=abc; SameSite=Strict`；`fetch('/api', { headers: { 'X-CSRF-Token': getCsrfToken() } })`。 |
| 原理和工作流程 | 用户登录 A 网站后浏览器保存 Cookie；访问恶意网站 B 时 B 向 A 发送请求，浏览器自动携带 Cookie；A 服务端以为是用户自己发起的请求。 |
| 缺点 | CSRF Token 需要前后端配合；SameSite=Strict 过于严格影响用户体验。 |

### 10. CSP（内容安全策略）的作用和常用配置

| 维度 | 内容 |
|------|------|
| 是什么 | CSP 通过 HTTP 响应头或 `<meta>` 标签，告诉浏览器哪些资源可以加载和执行，是防御 XSS 和点击劫持的强力手段。 |
| 能做什么 | 限制脚本、样式、图片、字体、连接等资源的来源；禁止内联脚本和 `eval()`；防御点击劫持（`frame-ancestors`）。 |
| 怎么用 | `Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; object-src 'none'; frame-ancestors 'self'`。 |
| 原理和工作流程 | 浏览器解析 CSP 策略建立白名单；不符合白名单的资源被阻止；`report-uri` 可配置违规报告端点。 |
| 缺点 | 配置复杂，需要测试确保不误拦截正常功能。 |

| 是什么 | 三道场景设计题：前端错误监控系统、跨域资源共享方案、前端性能监控 SDK，考查综合设计能力和工程实践能力。 |

### 1. 设计一个前端错误监控系统

| 维度 | 内容 |
|------|------|
| 是什么 | 一个完整的前端错误监控 SDK，能捕获 JS 运行时错误、Promise 未捕获错误、资源加载错误和接口请求错误，并将错误信息上报到服务器。 |
| 能做什么 | 实时监控线上应用的错误情况；通过 `sendBeacon` 保证页面关闭时也能上报；区分错误类型便于分类统计。 |
| 怎么用 | `window.addEventListener('error', handler, true)` 捕获 JS 错误和资源错误；`window.addEventListener('unhandledrejection', handler)` 捕获 Promise 错误；包装 `fetch` 和 `XMLHttpRequest` 捕获接口错误；`navigator.sendBeacon(url, payload)` 上报。 |
| 原理和工作流程 | `window.error` 事件区分 JS 错误（`event.target instanceof Window`）和资源加载错误（`event.target` 为具体元素）；`unhandledrejection` 事件捕获未处理的 Promise 拒绝；通过包装原生 `fetch` 和 `XMLHttpRequest` 拦截请求，记录状态码和耗时；使用 `sendBeacon` 在页面卸载时也能发送数据。 |
| 缺点 | 包装 `fetch` 和 `XHR` 可能影响第三方库的请求拦截；错误上报本身可能产生额外的错误。 |

### 2. 设计一个跨域资源共享方案

| 维度 | 内容 |
|------|------|
| 是什么 | 一个完整的跨域解决方案，包括 CORS 服务端配置（白名单校验、credentials 支持、预检缓存）、JSONP 降级方案和开发环境代理配置。 |
| 能做什么 | 生产环境使用 CORS 白名单安全控制跨域访问；开发环境使用代理避免跨域问题；JSONP 作为 GET 请求的降级方案。 |
| 怎么用 | CORS：`cors({ origin: ['https://frontend.com'], credentials: true, maxAge: 86400 })`；JSONP：动态创建 `<script>` 标签，服务端返回 `callback(data)`；代理：Vite `proxy: { '/api': { target: 'https://api.com', changeOrigin: true } }`。 |
| 原理和工作流程 | CORS 中间件根据白名单校验 Origin 请求头，设置对应的响应头；带 Cookie 时 `Access-Control-Allow-Origin` 不能为 `*`，必须指定具体域名；OPTIONS 预检请求返回 `Access-Control-Max-Age` 缓存预检结果；Nginx 反向代理将跨域请求转为同源请求。 |
| 缺点 | CORS 白名单需要维护；JSONP 不支持 POST 且安全性差；Nginx 配置需要运维参与。 |

### 3. 设计一个前端性能监控 SDK

| 维度 | 内容 |
|------|------|
| 是什么 | 一个能采集 Core Web Vitals 核心指标（FP、FCP、LCP、CLS、FID/INP）的前端性能监控 SDK，支持自定义指标上报、批量上报和采样率控制。 |
| 能做什么 | 实时监控页面性能；采集导航时序指标（DNS、TCP、TTFB）、资源加载指标和 Web Vitals 指标；支持批量上报和定时上报减少请求次数。 |
| 怎么用 | `new PerformanceObserver(callback).observe({ type: 'largest-contentful-paint', buffered: true })` 采集 LCP；`performance.getEntriesByType('navigation')` 获取导航时序；`performance.getEntriesByType('paint')` 获取 FP/FCP。 |
| 原理和工作流程 | PerformanceObserver 异步监听性能指标，不阻塞主线程；`buffered: true` 可获取观察器注册前已产生的指标；`sendBeacon` 在页面卸载时发送数据；采样率控制通过 `Math.random() > sampleRate` 实现；定时上报 + 缓冲区满上报 + 页面隐藏上报。 |
| 缺点 | PerformanceObserver 兼容性需要检查；CLS 指标需要持续累积，计算方式较复杂；采样率过高时数据量过大。 |
