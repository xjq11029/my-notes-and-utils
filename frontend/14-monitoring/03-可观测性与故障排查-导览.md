# 03-可观测性与故障排查 - 导览

---

## 1.1 可观测性三支柱（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 可观测性三支柱：Logs（日志，记录离散事件）、Metrics（指标，量化系统状态）、Traces（链路追踪，追踪请求路径），类比医院体检：日志是病历、指标是体检数据、链路是诊断流程 |
| 能做什么 | Logs 用于问题定位和上下文分析；Metrics 用于趋势分析、告警触发；Traces 用于分布式系统瓶颈定位和端到端可视化 |
| 怎么用 | Logs 通过 console 劫持 + Breadcrumbs 收集；Metrics 通过 PerformanceObserver + Prometheus 采集；Traces 通过 W3C Trace Context 标准在前后端传播 |
| 原理和工作流程 | 日志收集：劫持原生 API → 记录事件 → 附加时间戳和上下文 → 定期上报；指标采集：观察者模式收集性能数据 → 聚合为时序数据 → 对接 Prometheus/Grafana；链路追踪：生成 traceId → 注入 HTTP 头 → 后端传递 → 收集 Span 数据 |
| 缺点 | 三支柱数据量大，存储成本高；需要多种工具配合（Sentry + Prometheus + Jaeger）；不同工具数据格式不统一，关联分析困难 |

## 1.2 前端故障排查流程（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端故障排查遵循六步法：发现（Detect）→ 定位（Locate）→ 复现（Reproduce）→ 修复（Fix）→ 验证（Verify）→ 复盘（Review），形成闭环 |
| 能做什么 | 系统化地处理线上故障，避免遗漏关键步骤；确保每次故障有完整的记录和改进措施 |
| 怎么用 | 发现：监控告警 + 用户反馈；定位：Sentry 错误堆栈 + Sourcemap 还原；复现：本地模拟条件；修复：改代码 + 写测试；验证：灰度发布 + 监控确认；复盘：写文档 + 改进措施 |
| 原理和工作流程 | 监控报警 → 确认影响范围 → 查找根因 → 本地复现 → 修复代码 → Code Review → 灰度验证 → 全量上线 → 监控确认 → 复盘文档 |
| 缺点 | 流程依赖完善的监控体系；复现可能需要特定条件（设备、网络、数据）；紧急故障可能跳过部分步骤 |

## 1.3 Session Replay（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Session Replay 是用户行为录制回放技术，记录 DOM 快照、用户交互（点击、滚动、输入）、网络请求、控制台日志、性能数据 |
| 能做什么 | 还原用户遇到的问题现场；理解用户操作路径；发现 UI/UX 问题；辅助错误排查 |
| 怎么用 | 接入 Sentry Replay 或 LogRocket 等工具，配置采样率和脱敏规则，错误发生时自动关联录制 |
| 原理和工作流程 | 页面加载时开始录制 → 记录 DOM 快照 + 增量变化 → 记录用户交互事件 → 记录网络请求 → 错误发生时关联录制时间线 → 开发者回放查看 |
| 缺点 | 录制数据量大，增加带宽消耗；隐私合规风险（需严格脱敏）；可能影响页面性能 |

## 2.1 日志收集（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 前端日志收集通过劫持原生 console 方法（log/warn/error）实现，同时收集 Breadcrumbs（用户操作轨迹）作为错误上下文 |
| 能做什么 | 收集前端所有日志输出；记录用户操作轨迹还原错误现场；支持数据脱敏保护用户隐私 |
| 怎么用 | 劫持 console.log/warn/error → 保留原始行为 → 收集日志内容 → 附加时间戳和 Breadcrumbs → 数据脱敏 → 定期上报 |
| 原理和工作流程 | 替换原生 console 方法 → 调用原始方法保持控制台输出 → 提取参数并序列化 → 脱敏处理（password、token 等）→ 存入日志缓冲区 → 达到阈值或定时上报 |
| 缺点 | 劫持原生方法可能与其他库冲突；大量日志需要截断处理；脱敏可能遗漏新的敏感字段 |

## 2.2 性能指标采集（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 通过 PerformanceObserver 采集 Core Web Vitals（LCP/INP/CLS/FCP/TTFB）和自定义指标，支持长任务监控和自定义计时 |
| 能做什么 | 量化用户体验；建立性能基线；识别性能瓶颈；触发性能告警 |
| 怎么用 | 创建 PerformanceObserver 实例 → observe 指定 type → 在回调中提取指标值 → 与阈值对比 → 上报 |
| 原理和工作流程 | 浏览器异步收集性能数据 → 放入 Observer 缓冲区 → 回调触发 → 提取指标 → 计算分级（好/需改进/差）→ 上报到监控平台 |
| 缺点 | 部分指标需要浏览器支持（PerformanceObserver 需要 Chrome 52+）；INP 需在页面卸载时计算；自定义指标需手动编码 |

## 2.3 链路追踪（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于 W3C Trace Context 标准，通过 traceparent HTTP 头在前后端之间传播 traceId 和 spanId，实现分布式链路追踪 |
| 能做什么 | 追踪一个用户请求从前端到后端的完整调用链；定位分布式系统中的性能瓶颈；关联前后端日志和错误 |
| 怎么用 | 前端生成 traceId/spanId → 注入到 fetch/XHR 请求的 traceparent 头 → 后端接收并继续传播 → 各服务上报 Span 数据到追踪系统（Jaeger/Zipkin） |
| 原理和工作流程 | 请求入口生成 TraceContext（traceId 32 位十六进制 + spanId 16 位）→ 每次下游调用创建子 Span → 通过 traceparent 头传播 → 所有 Span 上报到 Collector → 通过 traceId 关联展示调用链 |
| 缺点 | 需要前后端统一支持 W3C 标准；追踪系统需要额外部署和维护；采样率需要平衡数据量和存储成本 |

## 2.4 告警策略设计（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 告警策略设计包括五种规则类型：阈值告警（错误率>1%）、趋势告警（环比增长>100%）、新错误告警、异常告警，以及冷却时间、分级告警、影响用户数优先等原则 |
| 能做什么 | 及时发现线上问题；避免告警风暴和告警疲劳；确保告警的可信度和可操作性 |
| 怎么用 | 定义告警规则（条件 + 冷却时间 + 严重级别）→ 接收实时指标数据 → 评估规则 → 触发告警 → 通过钉钉/飞书/邮件/短信通知 |
| 原理和工作流程 | 指标数据流入 → 告警引擎评估每条规则 → 检查冷却时间 → 检查条件 → 满足条件则触发告警 → 记录告警历史 → 发送通知 → 进入冷却期 |
| 缺点 | 阈值设置需要历史数据支持，初始配置可能不合理；告警策略需要持续调整优化；多渠道通知配置复杂 |

## 3.1 接入 Sentry Performance Monitoring（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 Sentry Performance Monitoring 接入，包括 BrowserTracing 配置、自定义 Transaction 和 Span、API 调用耗时追踪 |
| 能做什么 | 自动追踪页面加载和导航性能；手动创建自定义 Transaction 追踪业务流程；测量 API 调用耗时 |
| 怎么用 | 配置 tracesSampleRate → 启用 BrowserTracing → 使用 startTransaction 创建自定义 Transaction → 使用 startChild 创建 Span → 调用 finish 结束 |
| 原理和工作流程 | 页面加载时自动创建 Transaction → 监听路由变化创建新 Transaction → 自动为 fetch/XHR 创建 Span → 手动创建自定义 Span → 结束 Transaction 时上报所有 Span 数据 |
| 缺点 | 需要额外配置 tracePropagationTargets；API 调用追踪需要手动集成；性能数据可能影响免费版事件配额 |

## 3.2 搭建 Grafana 前端监控大盘（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 Prometheus 作为数据源，搭建 Grafana 前端监控大盘，展示错误率、P99 响应时间、Core Web Vitals、PV/UV、可用性等核心指标 |
| 能做什么 | 实时可视化前端监控数据；支持自定义面板和告警；支持多数据源聚合 |
| 怎么用 | 前端 SDK 上报指标到 Prometheus Pushgateway → Prometheus 拉取数据 → Grafana 配置 Prometheus 数据源 → 创建 Dashboard 面板 |
| 原理和工作流程 | 前端采集指标 → 通过 Pushgateway 推送到 Prometheus → Prometheus 定时拉取（scrape）→ 存储时序数据 → Grafana 查询 PromQL → 渲染面板 |
| 缺点 | 需要部署 Prometheus + Grafana 基础设施；PromQL 查询语法有学习曲线；Pushgateway 不适合高频数据 |
