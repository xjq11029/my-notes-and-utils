# 04-测试集成与质量门禁 - 导览

---

## 1.1 质量门禁定义（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 质量门禁（Quality Gate）是代码合并前必须通过的自动化检查关卡。用机场安检类比：Lint 是行李检查（X 光机），类型检查是身份验证（身份证），测试是安检扫描（金属探测），构建是登机确认（登机牌），安全扫描是危险品排查 |
| 能做什么 | 将"人肉审查"转变为"自动化检查"，确保每次代码合并都经过标准化的质量验证，避免人为疏忽导致的线上问题 |
| 怎么用 | 通过 Husky（Git Hooks）+ lint-staged（暂存文件检查）+ CI 流水线（GitHub Actions）组合实现 |
| 原理和工作流程 | 开发者提交代码 → 本地 Git Hooks 检查（pre-commit: lint-staged, commit-msg: commitlint）→ 推送 → CI 流水线执行五阶段检查 → 全部通过后允许合并 |
| 缺点 | 配置复杂度高，初期需要投入时间；过于严格的规则可能降低开发效率；需要团队共识和持续维护 |

---

## 1.2 门禁体系（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 五层级门禁体系：Lint 检查（代码风格、潜在错误）→ 类型检查（TypeScript 类型正确性）→ 单元测试（逻辑正确性、边界条件）→ 构建验证（项目可构建性）→ 依赖安全扫描（已知漏洞检测） |
| 能做什么 | 从快到慢、从浅到深逐层递进检查，快速失败让开发者尽早获得反馈，阻断优先避免问题进入后续阶段 |
| 怎么用 | 本地：Husky pre-commit（lint-staged）+ pre-push（type-check + test）；CI：GitHub Actions 五阶段 job 设计 |
| 原理和工作流程 | 设计原则：快速失败（越快的检查越靠前）、阻断优先（失败立即阻断后续）、并行执行（同一层级可并行）、结果可见（汇总到统一报告） |
| 缺点 | 五层检查全部通过需要较长时间（5-15 分钟）；门禁失败可能阻塞紧急修复 |

---

## 1.3 CI/CD 流水线中的质量门禁（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 在 GitHub Actions / GitLab CI 中，质量门禁通过 stage/job 设计实现，每个 stage 包含一组并行 job，stage 之间串行依赖 |
| 能做什么 | 实现自动化质量验证流水线，确保 PR 合并前通过所有检查，主干分支始终保持可部署状态 |
| 怎么用 | GitHub Actions workflow 配置：`needs` 字段控制 job 依赖关系，`strategy.matrix` 实现并行测试 |
| 原理和工作流程 | Stage 1（Lint + TypeCheck 并行）→ Stage 2（Test 依赖 Stage 1）→ Stage 3（Build 依赖 Stage 2）→ Stage 4（Security Audit 依赖 Stage 3） |
| 缺点 | GitHub Actions 免费额度有限；矩阵构建可能产生大量 job 消耗额度；中国区访问 GitHub Actions 速度较慢 |

## 2.1 Husky + lint-staged 原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Husky 利用 Git Hooks 机制在 Git 操作时执行自定义脚本；lint-staged 只检查 `git add` 暂存区文件，避免全量检查 |
| 能做什么 | 在提交前自动检查代码质量，拦截不合规的提交，确保仓库中的代码始终符合规范 |
| 怎么用 | `pnpm add -D husky lint-staged` → `pnpm exec husky init` → 配置 `.husky/pre-commit` 和 `lint-staged.config.js` |
| 原理和工作流程 | `git commit` → Git 触发 pre-commit hook → Husky 拦截 → lint-staged 读取暂存文件列表 → 对匹配文件执行 ESLint/Prettier → 通过则继续，失败则中断 |
| 缺点 | 需要所有团队成员安装 Husky；`--no-verify` 可以绕过检查；lint-staged 配置错误可能导致部分文件被跳过 |

---

## 2.2 CI 中的并行执行策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 三种核心优化策略：依赖缓存（actions/cache 缓存 node_modules 和 pnpm store）、并行 job（同一 stage 的 job 互不依赖）、矩阵构建（不同 Node.js 版本/操作系统并行测试） |
| 能做什么 | 缩短 CI 执行时间，从 15 分钟优化到 5 分钟以内，提升开发反馈速度 |
| 怎么用 | 缓存：`actions/cache@v4` 配置 path 和 key；并行：多个 job 无 `needs` 依赖；矩阵：`strategy.matrix` 定义多维度组合 |
| 原理和工作流程 | 依赖缓存：首次运行缓存依赖 → 后续运行命中缓存跳过下载 → 并行 job：多个检查同时运行等待最慢的完成 → 矩阵构建：`os × node-version` 笛卡尔积生成多个并行 job |
| 缺点 | 缓存 key 设计不当可能导致命中率低；矩阵构建数量过多可能超出 GitHub Actions 免费额度（20 个并行 job） |

---

## 2.3 覆盖率报告与质量门禁（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 测试覆盖率通过 lines/functions/branches/statements 四个指标衡量测试覆盖程度；Vitest 通过 `coverage.thresholds` 配置最低阈值，低于阈值则 CI 失败 |
| 能做什么 | 确保测试覆盖核心逻辑，防止提交未经充分测试的代码，量化测试质量 |
| 怎么用 | `vitest.config.ts` 中配置 `coverage.thresholds: { lines: 80, functions: 80, branches: 75, statements: 80 }`；按目录设置不同阈值 |
| 原理和工作流程 | V8 原生覆盖率（provider: 'v8'）在代码执行时记录覆盖情况 → 生成 JSON/HTML/LCov 报告 → 对比阈值 → 低于阈值返回非零退出码 |
| 缺点 | 覆盖率不等于质量，100% 覆盖率不代表没有 Bug；阈值设置过高导致开发效率下降；UI 组件测试覆盖率通常较低 |

---

## 2.4 构建产物验证（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 通过 @next/bundle-analyzer 可视化分析构建产物，通过体积预算脚本监控 chunk 大小，防止未经审查的打包体积膨胀 |
| 能做什么 | 监控每次构建的产物大小变化，识别意外引入的大型依赖，优化 chunk 拆分策略 |
| 怎么用 | `ANALYZE=true pnpm build` 生成可视化报告；`scripts/check-bundle-size.js` 脚本检查体积预算 |
| 原理和工作流程 | webpack 构建时记录每个 chunk 的组成和大小 → Bundle Analyzer 生成交互式树状图 → 体积预算脚本对比预设阈值 → 超出阈值则 CI 失败 |
| 缺点 | 体积预算阈值需要根据项目实际情况调整；第三方库更新可能导致体积变化但无法避免；tree-shaking 效果受导入方式影响 |

## 3.1 完整质量门禁配置（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 Husky + lint-staged + commitlint 从零搭建完整的本地质量门禁，包括 pre-commit（lint-staged）、commit-msg（commitlint）、pre-push（type-check + test）三个钩子 |
| 能做什么 | 在代码提交前自动检查代码质量和提交信息格式，拦截不合规的提交 |
| 怎么用 | 安装依赖 → `husky init` 初始化 → 配置 `.husky/pre-commit`、`.husky/commit-msg`、`.husky/pre-push` → 配置 `lint-staged.config.js` 和 `commitlint.config.js` |
| 原理和工作流程 | pre-commit：lint-staged 只检查暂存文件（ESLint + Prettier + Stylelint）→ commit-msg：commitlint 验证提交信息格式（Conventional Commits）→ pre-push：运行类型检查和测试 |
| 缺点 | 多个钩子会增加提交等待时间；commitlint 的严格规则可能影响开发体验；pre-push 钩子失败后需要重新推送 |

## 3.2 CI 流水线设计（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 完整的 GitHub Actions 五阶段质量门禁流水线，包括 lint → type-check → test（带覆盖率）→ build（带体积检查）→ security-audit |
| 能做什么 | 自动化质量验证，确保 PR 合并前通过所有检查，主干分支始终保持可部署状态 |
| 怎么用 | 创建 `.github/workflows/quality-gate.yml`，配置五个 job 的依赖关系和并行策略 |
| 原理和工作流程 | PR 触发 workflow → Stage 1（lint + type-check 并行）→ Stage 2（test 分片并行，需要 Stage 1）→ Stage 3（coverage-report 汇总覆盖率）→ Stage 4（build 需要 Stage 2）→ Stage 5（security-audit 需要 Stage 4） |
| 缺点 | 完整流水线执行时间较长（5-15 分钟）；GitHub Actions 免费额度有限；中国区访问速度较慢 |

## 3.3 覆盖率门禁（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | Vitest 覆盖率阈值配置 + CI 阻断，按目录设置不同阈值（utils 95%、hooks 85%、components 70%），使用 watermarks 区分警告和错误 |
| 能做什么 | 确保核心逻辑（utils/hooks）有充分的测试覆盖，UI 组件有基本的测试覆盖，量化测试质量 |
| 怎么用 | `vitest.config.ts` 中配置 `coverage.thresholds` 设置全局和按目录阈值；`coverage.watermarks` 设置警告和错误水印；CI 中 `--coverage` 运行测试 |
| 原理和工作流程 | 测试运行 → V8 收集覆盖率数据 → 生成覆盖报告 → 对比阈值和水印 → 低于水印下限则警告 → 低于阈值则 CI 失败 |
| 缺点 | 覆盖率阈值需要根据项目实际情况调整；新增目录时需要更新阈值配置；watermarks 在 CI 中可能被忽略 |

## 3.4 Bundle 体积监控（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 配置 @next/bundle-analyzer 可视化分析、webpack splitChunks 优化分包策略、体积预算脚本检查 chunk 大小 |
| 能做什么 | 监控每次构建的产物大小变化，识别意外引入的大型依赖，优化 chunk 拆分策略 |
| 怎么用 | `ANALYZE=true pnpm build` 生成可视化报告；`next.config.ts` 中配置 `splitChunks.cacheGroups` 手动拆分；`scripts/check-bundle-size.js` 检查体积预算 |
| 原理和工作流程 | webpack 构建时记录每个 chunk 的组成和大小 → Bundle Analyzer 生成交互式树状图 → 体积预算脚本对比预设阈值 → 超出阈值则 CI 失败 |
| 缺点 | 体积预算阈值需要根据项目实际情况调整；第三方库更新可能导致体积变化但无法避免；tree-shaking 效果受导入方式影响 |
