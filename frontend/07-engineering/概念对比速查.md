# 前端工程化 - 概念对比速查

---

### Webpack vs Vite

| 对比维度 | Webpack | Vite |
|---------|---------|------|
| 核心定位 | 基于模块打包的传统构建工具，一切资源视为模块 | 基于浏览器原生 ESM 的下一代构建工具，开发时零打包 |
| 开发启动速度 | 几十秒到几分钟（大型项目），需先打包整个应用 | 秒级启动，利用原生 ESM 按需编译 |
| HMR 速度 | 秒级，随项目增大而变慢 | 毫秒级，只更新变更模块 |
| 底层依赖 | 自建打包引擎，JS 实现 | 开发用 esbuild（Go 语言）预构建，生产用 Rollup 打包 |
| 配置复杂度 | 较复杂，需配置 entry/output/loader/plugin | 简洁，开箱即用，内置 TypeScript 和 CSS 预处理器支持 |
| 生态成熟度 | 极其成熟，Loader 和 Plugin 生态丰富 | 快速成长，基本覆盖主流场景，但不如 Webpack 丰富 |
| 浏览器兼容性 | 支持所有浏览器，包括 IE11（需配置） | 开发环境需支持 ESM 的现代浏览器，老浏览器需 @vitejs/plugin-legacy |
| 学习曲线 | 陡峭，需理解 Loader/Plugin/Chunk 等概念 | 平缓，配置 API 直观 |
| 选择建议 | 大型企业项目、需兼容老浏览器、生态插件依赖多 | 新项目默认选择，开发体验优先，浏览器兼容性要求不苛刻 |

### ESLint vs Prettier

| 对比维度 | ESLint | Prettier |
|---------|--------|----------|
| 核心定位 | 代码质量检查工具，发现潜在错误和不符合最佳实践的代码 | 代码格式化工具，按统一规则重新格式化 |
| 关注点 | 逻辑错误、潜在 bug、最佳实践（未使用变量、可能的空指针等） | 纯格式问题（缩进、引号、分号、换行、尾逗号等） |
| 工作方式 | 将源码解析为 AST，遍历节点匹配规则，报告不符合的代码 | 将源码解析为自有 AST，按固定规则重新输出，完全忽略原有格式 |
| 可自动修复 | 部分支持（--fix 可修复部分规则） | 完全支持（--write 可修复所有格式问题） |
| 配置灵活性 | 高，可自定义规则、 extends 共享配置、按文件覆盖 | 低，设计为"有主见的"，只提供少量选项 |
| 典型配置 | `eslint.config.mjs`（Flat Config，ESLint 9+）/ `.eslintrc.js`（已废弃） | `.prettierrc.js` 中 printWidth/tabWidth/semi 等选项 |
| 配合方式 | 通过 eslint-config-prettier 关闭与 Prettier 冲突的规则，让 ESLint 只管质量，Prettier 只管格式 |  |

### Git Flow vs GitHub Flow vs Trunk-based

| 对比维度 | Git Flow | GitHub Flow | Trunk-based |
|---------|----------|-------------|-------------|
| 核心定位 | 多分支模型，适合有明确版本发布周期的项目 | 单分支模型，适合持续部署的项目 | 极简模型，所有开发者直接提交到主干或短生命周期分支 |
| 长期分支 | master + develop（两个） | main（一个） | main/trunk（一个） |
| 临时分支 | feature、release、hotfix | feature | 短生命周期 feature 分支（通常 < 1 天） |
| 发布流程 | 从 develop 拉 release 分支，冻结后修 bug 打 tag，合并到 master 和 develop | feature 分支通过 PR 合并到 main 后立即部署 | 直接提交到主干，通过 feature flag 控制功能开关 |
| 分支复杂度 | 高，需维护多个分支类型和合并策略 | 低，只需管理 feature 分支和 PR | 最低，几乎无分支管理 |
| 适用场景 | 有固定发版周期的产品（如移动 App、企业软件） | Web 应用、SaaS 产品、持续部署的项目 | 成熟团队、完善的 CI/CD 和 feature flag 基础设施 |
| 团队要求 | 中，需理解分支模型和合并策略 | 低，流程简单，上手快 | 高，需严格的代码审查、自动化测试和 feature flag 能力 |
| 选择建议 | 版本发布周期明确（如每月发版） | 持续部署、快速迭代的 Web 项目 | 团队成熟度高、基础设施完善 |

### Husky vs lint-staged

| 对比维度 | Husky | lint-staged |
|---------|-------|-------------|
| 核心定位 | Git Hooks 管理工具，在 Git 操作时自动触发脚本 | Git 暂存区文件检查工具，只对暂存文件执行检查 |
| 职责 | 管理 Git 钩子（pre-commit、commit-msg、pre-push 等） | 限定检查范围，避免全量文件检查 |
| 工作方式 | 在 .git/hooks 目录创建钩子脚本，拦截 Git 操作 | 读取 Git 暂存区文件列表，只对匹配的文件执行命令 |
| 解决的问题 | 自动化触发检查脚本，无需手动执行 | 全量检查耗时过长，只检查变更文件大幅提升速度 |
| 使用方式 | `pnpm exec husky init` 初始化，`.husky/pre-commit` 写入 `pnpm lint-staged` | package.json 中配置 lint-staged 匹配规则，如 `"*.js": ["eslint --fix"]` |
| 独立使用 | 可以独立使用，但通常配合 lint-staged 限定检查范围 | 必须配合 Husky 等 Git Hook 工具触发 |
| 选择建议 | 两者配合使用：Husky 管理钩子触发时机，lint-staged 限定检查范围，实现提交前自动检查暂存文件 |  |

### npm vs yarn vs pnpm

| 对比维度 | npm | yarn | pnpm |
|---------|-----|------|------|
| 核心定位 | Node.js 官方包管理器 | Meta 推出的替代方案，强调速度和确定性 | 高性能、节省磁盘空间的包管理器 |
| node_modules 结构 | 扁平化（hoist），所有依赖提升到顶层 | 扁平化（hoist），与 npm 类似 | 非扁平化，使用硬链接和符号链接，严格依赖访问 |
| 磁盘空间 | 每个项目独立复制依赖，占用大 | 每个项目独立复制依赖，占用大 | 全局 store 存储依赖，项目通过硬链接共享，节省大量空间 |
| 安装速度 | 较慢 | 快（并行下载） | 快（并行下载 + 硬链接跳过复制） |
| lock 文件 | package-lock.json | yarn.lock | pnpm-lock.yaml |
| Monorepo 支持 | 支持 workspaces | 支持 workspaces | 原生支持 workspaces，且通过 --filter 精确控制 |
| 幽灵依赖 | 存在（可访问未声明依赖） | 存在（可访问未声明依赖） | 不存在（严格模式，只能访问声明过的依赖） |
| 选择建议 | 无需额外安装，适合小型项目 | 社区仍有大量使用，但优势已被 pnpm 超越 | 默认推荐，磁盘空间友好，Monorepo 支持最佳 |
