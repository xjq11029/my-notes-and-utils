### 1. ★ Webpack 中 Loader 的作用是什么？

A. 在打包过程中执行自定义任务，如生成 HTML 文件
B. 将非 JavaScript 文件转换为 Webpack 能够处理的模块
C. 压缩打包后的 JavaScript 代码
D. 分析打包后的文件体积

**答案：B**

**解析**：Loader 是 Webpack 中的文件转换器，核心作用是将非 JavaScript 文件（如 CSS、图片、TypeScript、Sass 等）转换为 Webpack 能够处理的模块。A 描述的是 Plugin 的作用，C 是 TerserWebpackPlugin 的功能，D 是 BundleAnalyzerPlugin 的功能。

### 2. ★ Webpack 中 Plugin 的作用是什么？

A. 转换 TypeScript 为 JavaScript
B. 处理 CSS 文件中的 `@import` 语句
C. 在 Webpack 打包生命周期的各个阶段执行自定义任务
D. 将 ES6+ 代码转换为 ES5

**答案：C**

**解析**：Plugin 是 Webpack 的功能扩展器，通过 hooks 机制在打包生命周期的各个阶段执行自定义任务，如生成 HTML、提取 CSS、压缩代码、定义环境变量等。A、B、D 都是 Loader 的职责。

### 3. ★ Vite 开发环境启动快的主要原因是什么？

A. 使用了更快的 JavaScript 引擎
B. 基于浏览器原生 ES Module，按需编译，不需要打包整个应用
C. 使用了 WebAssembly 加速编译
D. 去掉了所有编译步骤，直接运行源码

**答案：B**

**解析**：Vite 开发环境启动快是因为它利用浏览器原生 ES Module 能力，不需要像 Webpack 那样先打包整个应用，而是按需编译，浏览器请求哪个模块就编译哪个模块。同时使用 esbuild 预构建依赖，速度极快。A 不准确，Vite 仍使用 Node.js 的 V8 引擎；C 不准确，esbuild 使用 Go 语言而非 WebAssembly；D 错误，Vite 仍然有编译步骤，只是按需执行。

> 📖 **参考链接**：
> - [Vite官方文档](https://cn.vitejs.dev/guide/)
> - [esbuild官方文档](https://esbuild.github.io/)

### 4. ★★ 以下关于 Tree Shaking 的说法正确的是？

A. Tree Shaking 通过分析 CommonJS 的 `require` 语法来移除未使用的代码
B. Tree Shaking 基于 ES Module 的静态导入（`import`）特性实现
C. Tree Shaking 是 Webpack 独有的功能，其他打包工具不支持
D. Tree Shaking 在生产模式和开发模式下都会自动启用

**答案：B**

**解析**：Tree Shaking 基于 ES Module 的静态导入/导出特性实现。ES Module 的 `import` 和 `export` 是静态的，在编译时就能确定依赖关系，因此可以分析出哪些导出被实际使用，哪些未被使用（dead code）。A 错误，CommonJS 的 `require` 是动态的，无法在编译时做静态分析；C 错误，Rollup、Vite 等工具也支持 Tree Shaking；D 错误，Tree Shaking 通常在 `production` 模式下启用，`development` 模式下为了调试方便通常不启用。

> 📖 **参考链接**：
> - [Webpack官方文档 - Tree Shaking](https://webpack.docschina.org/guides/tree-shaking/)

### 5. ★★ Webpack 的 HMR（热模块替换）原理是什么？

A. 每次修改文件后自动刷新整个页面
B. 通过 WebSocket 连接，只推送变更的模块到浏览器进行热替换
C. 使用 Service Worker 缓存所有模块，修改后替换缓存
D. 通过轮询方式定期检查文件变化，然后全量替换

**答案：B**

**解析**：Webpack 的 HMR 通过 WebSocket 在 Dev Server 和浏览器之间建立长连接。文件变更时，Webpack 重新编译变更的模块，通过 WebSocket 推送 hash 和更新清单到浏览器，浏览器 HMR Runtime 请求变更模块的增量更新，然后执行 `module.hot.accept()` 完成热替换。A 是 Live Reload（全量刷新），不是 HMR；C 和 D 都不是 HMR 的实现方式。

### 6. ★★ 以下哪个不是 Webpack 的内置性能优化手段？

A. Tree Shaking（摇树优化）
B. Code Splitting（代码分割）
C. Scope Hoisting（作用域提升）
D. Lazy Compilation（惰性编译）

**答案：D**

**解析**：Webpack 内置的性能优化手段包括 Tree Shaking、Code Splitting 和 Scope Hoisting。Lazy Compilation（惰性编译/按需编译）是 Vite 的核心特性，不是 Webpack 的内置优化。Webpack 5 实验性支持 lazy compilation（`experiments.lazyCompilation`），但 Vite 的按需编译是其核心设计理念，默认行为更成熟。

### 7. ★★ ESLint 和 Prettier 的区别是什么？

A. ESLint 格式化代码，Prettier 检查代码质量
B. ESLint 检查代码质量和潜在错误，Prettier 格式化代码风格
C. 两者功能完全相同，只是配置方式不同
D. ESLint 只能用于 JavaScript，Prettier 可以用于所有语言

**答案：B**

**解析**：ESLint 主要关注代码质量和潜在错误（如未使用的变量、可能的空指针、不符合最佳实践的写法），Prettier 专注于代码格式化（如缩进、引号、分号、换行等纯格式问题）。配合使用时通过 `eslint-config-prettier` 关闭 ESLint 中与 Prettier 冲突的格式规则。

### 8. ★★ 以下关于 pnpm 的说法正确的是？

A. pnpm 使用 npm 的扁平化 node_modules 结构
B. pnpm 使用硬链接和符号链接来管理依赖，节省磁盘空间
C. pnpm 的安装速度比 npm 慢
D. pnpm 不支持 Monorepo

**答案：B**

**解析**：pnpm 的核心优势是使用硬链接（hard link）和符号链接（symlink）来管理依赖，所有项目共享同一份依赖文件，大幅节省磁盘空间，安装速度也更快。A 错误，npm 使用扁平化结构，pnpm 使用非扁平化的内容寻址存储；C 错误，pnpm 通常比 npm 更快；D 错误，pnpm 原生支持 workspaces 和 Monorepo。

### 9. ★★★ Vite 生产环境使用什么工具进行打包？

A. esbuild
B. Webpack
C. Rollup
D. SWC

**答案：C**

**解析**：Vite 在生产环境使用 Rollup 进行打包（Vite 7 及以下版本）。Vite 8（2025 年 12 月 Beta）起切换为 Rolldown——一个用 Rust 编写的高性能打包器，兼容 Rollup 插件 API。Rollup/Rolldown 在打包 ES Module 代码方面有天然优势，输出的代码更干净、体积更小，天然支持 Tree Shaking。esbuild 在 Vite 中主要用于开发环境的预构建依赖和生产环境的代码压缩（minify），而不是打包。Webpack 和 SWC 都不是 Vite 生产打包的默认工具。

### 10. ★★★ Webpack 中 chunk 和 bundle 的区别是什么？

A. chunk 和 bundle 完全相同，没有区别
B. chunk 是 Webpack 内部处理时的代码块，bundle 是最终输出的文件
C. chunk 是最终输出的文件，bundle 是内部处理的代码块
D. chunk 只能从入口文件生成，bundle 只能从代码分割生成

**答案：B**

**解析**：chunk 是 Webpack 打包过程中的中间产物，由多个 module 组成，是 Webpack 内部的概念。bundle 是最终输出到文件系统的文件，是 chunk 经过处理和优化（压缩、合并等）后的产物。一个 chunk 可能对应一个 bundle，也可能多个 chunk 合并为一个 bundle（通过 SplitChunksPlugin）。Module 是源码中的每个文件，是最小单位。

## 二、简答题（8 题）

### 1. ★★ Webpack 的打包流程是什么？

**参考答案**：

Webpack 的打包流程分为以下几个阶段：

1. **初始化参数**：从 `webpack.config.js` 和命令行参数中读取配置，合并为最终配置
2. **创建 Compiler 对象**：用合并后的配置初始化 Compiler，它是 Webpack 的核心引擎
3. **加载 Plugin**：依次调用所有 Plugin 的 `apply` 方法，将 Compiler 传入，Plugin 注册到生命周期钩子
4. **run 开始编译**：调用 Compiler 的 `run` 方法，正式启动编译
5. **从 Entry 开始递归构建依赖图**：从入口文件开始，解析 `import`/`require` 依赖，递归处理所有依赖模块，形成依赖图
6. **Loader 转换模块**：对每个 Module 按照配置的 rules 匹配 Loader 链，从右向左执行转换
7. **生成 Chunk**：将 Module 按照入口和代码分割策略组合成 Chunk
8. **输出文件**：将 Chunk 写入文件系统，生成最终 Bundle

> 📖 **参考链接**：
> - [Webpack官方文档 - 核心概念](https://webpack.docschina.org/concepts/)

### 2. ★★ Loader 和 Plugin 的区别

**参考答案**：

| 维度 | Loader | Plugin |
|------|--------|--------|
| 作用 | 文件转换器，将非 JS 文件转为 Webpack 能处理的模块 | 扩展 Webpack 功能，在生命周期中执行任务 |
| 处理对象 | 单个文件（模块） | 整个打包流程 |
| 执行时机 | 模块加载时，对源码进行转换 | 在 Webpack 生命周期的各个钩子中 |
| 调用方式 | 链式调用，从右向左（从下向上） | 通过 hooks 注册，按 tap 顺序执行 |
| 编写方式 | 导出一个函数，接收 source 返回转换后内容 | 导出一个类，包含 `apply(compiler)` 方法 |

简而言之：Loader 做的是"翻译"工作，Plugin 做的是"扩展"工作。Loader 让 Webpack 能处理非 JS 文件，Plugin 让 Webpack 能做更多事情（生成 HTML、提取 CSS、压缩代码等）。

### 3. ★★ Vite 的原理和优势

**参考答案**：

**开发环境原理**：
- 利用浏览器原生 ES Module 能力，不需要打包整个应用
- 使用 esbuild（Go 语言）预构建 node_modules 中的依赖，速度极快
- 按需编译：只编译浏览器当前请求的模块
- HMR 基于 ES Module，只更新变更的模块，毫秒级响应

**生产环境**：使用 Rollup 打包（Vite 7-）/ Rolldown 打包（Vite 8+），esbuild 做代码压缩

**优势**：
- 极速冷启动：秒级启动，大型项目也很快
- 极速 HMR：毫秒级热更新，不受项目规模影响
- 开箱即用：内置 TypeScript、CSS 预处理器、JSX 支持
- 配置简洁：API 设计清晰，相比 Webpack 大幅简化

> - [Vite官方文档 - 为什么选Vite](https://cn.vitejs.dev/guide/why)

### 4. ★★ Tree Shaking 的原理和实现条件

**参考答案**：

**原理**：Tree Shaking 基于 ES Module 的静态导入特性（`import` 和 `export`），在编译时分析模块间的依赖关系，将未被引用（import）的导出代码标记为 dead code，在打包时移除。

**实现条件**：
1. 必须使用 ES Module 语法（`import`/`export`），不能使用 CommonJS（`require`/`module.exports`），因为后者是动态的
2. 在 `package.json` 中设置 `"sideEffects": false` 或指定副作用文件列表，告诉打包工具哪些文件没有副作用（即导入后即使不引用也不会影响全局）
3. 生产模式（`mode: 'production'`）下 Webpack 会自动启用 Tree Shaking
4. 确保 Babel 等转译工具不会将 ES Module 转换为 CommonJS

> 📖 **参考链接**：
> - [Webpack官方文档 - Tree Shaking](https://webpack.docschina.org/guides/tree-shaking/)

### 6. ★★ CI/CD 流程是什么？

**参考答案**：

**CI（持续集成）**：开发者频繁将代码合并到主干，每次合并自动触发构建、测试和代码检查，及早发现集成问题。

**CD（持续部署/持续交付）**：通过自动化流程将构建产物部署到测试环境或生产环境。

**标准流程**：
```
代码提交 → 依赖安装 → 代码检查（lint）→ 单元测试 → 构建 → 部署测试环境 → 自动化测试 → 部署生产环境
```

**核心价值**：
- 减少手动操作，避免人为失误
- 快速发现和修复问题
- 提高发布频率和质量
- 统一构建环境，消除"在我机器上能跑"的问题

**常用工具**：GitHub Actions、GitLab CI/CD、Jenkins、Vercel、Netlify。

> 📖 **参考链接**：
> - [GitHub Actions官方文档](https://docs.github.com/zh/actions)
> - [GitHub Actions - 理解GitHub Actions](https://docs.github.com/zh/actions/learn-github-actions/understanding-github-actions)

### 7. ★★★ Monorepo 的优缺点和 pnpm workspaces 配置

**参考答案**：

**优点**：
- 统一配置：一份 ESLint、Prettier、TypeScript 配置，所有包共享
- 代码共享：公共代码放在 `packages/shared` 中，所有应用直接引用
- 原子提交：一次提交可以同时修改多个包，确保一致性
- 统一依赖管理：避免版本冲突，使用 pnpm 节省磁盘空间

**缺点**：
- 仓库体积大，克隆速度慢
- 构建时间可能较长（需要工具如 Turborepo 优化）
- 权限管理困难（所有开发者能看到所有代码）
- 对工具链要求较高

**pnpm workspaces 配置**：

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

```json
// 根 package.json 中的脚本
{
  "scripts": {
    "dev:web": "pnpm --filter @my-app/web dev",
    "build:all": "pnpm -r build",
    "lint": "pnpm -r lint"
  }
}
```

### 8. ★★ 前端部署方案有哪些？SPA 的 Nginx 配置要点是什么？

**参考答案**：

**部署方案**：

| 方案 | 适用场景 | 特点 |
|------|----------|------|
| 静态托管（Vercel/Netlify） | 个人项目、小型项目 | 零配置、自动 HTTPS、免费 |
| Nginx 自建服务器 | 中大型项目、需要定制化 | 灵活、高性能、支持反向代理 |
| Docker 容器化部署 | 微服务、需要环境一致性 | 可移植、隔离性好 |
| CDN + OSS | 纯静态资源、大流量 | 全球加速、高可用 |

**SPA 的 Nginx 配置要点**：
1. **路由 fallback**：`try_files $uri $uri/ /index.html` 确保前端路由刷新不 404
2. **gzip 压缩**：开启 gzip 压缩，减少传输体积
3. **静态资源缓存**：对带 hash 的静态资源设置长期缓存（`expires 1y`）
4. **反向代理**：将 `/api/` 请求转发到后端服务，解决跨域
5. **HTTPS 配置**：强制 HTTP 跳转 HTTPS

### 2. ★★ 设计一个前端 CI/CD 流水线（GitHub Actions）

**题目**：设计一个完整的 CI/CD 流水线，包含 lint 检查、单元测试、构建和自动部署到服务器。

**参考答案**：

```yaml
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  # 阶段 1：代码质量检查
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with:
          version: 10
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint

  # 阶段 2：单元测试
  test:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with:
          version: 10
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm test

  # 阶段 3：构建 + 部署
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v5
        with:
          version: 10
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - name: Deploy to Server
        uses: easingthemes/ssh-deploy@v4
        with:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          REMOTE_HOST: ${{ secrets.REMOTE_HOST }}
          REMOTE_USER: ${{ secrets.REMOTE_USER }}
          TARGET: /var/www/app
          SOURCE: 'dist/'
```

**流水线设计要点**：
- `lint` 和 `test` 是并行还是串行？根据实际情况，这里设计为串行（lint 通过后再 test），也可以并行执行节省时间
- 使用 `--frozen-lockfile` 确保依赖版本一致
- 部署仅限 `main` 分支
- 敏感信息（SSH 密钥、服务器地址）通过 GitHub Secrets 管理

### 4. ★★ 设计一个前端错误监控和日志上报方案

**题目**：设计一套前端错误监控方案，包括错误捕获、日志上报、Source Map 还原。

**参考答案**：

**整体架构**：

```
前端错误捕获 → 日志格式化 → 批量上报 → 后端接收 → 存储分析 → 告警通知
```

**前端错误捕获层**：

```javascript
// error-monitor.js
class ErrorMonitor {
  constructor(options) {
    this.options = {
      reportUrl: '/api/error/report',
      maxBatchSize: 10,       // 批量上报最大条数
      flushInterval: 5000,    // 定时上报间隔（毫秒）
      ...options
    }
    this.queue = []
    this.init()
  }

  init() {
    // 1. 捕获 JS 运行时错误
    window.addEventListener('error', (event) => {
      this.report({
        type: 'js-error',
        message: event.message,
        filename: event.filename,
        lineno: event.lineno,
        colno: event.colno,
        stack: event.error?.stack
      })
    })

    // 2. 捕获 Promise 未处理的 rejection
    window.addEventListener('unhandledrejection', (event) => {
      this.report({
        type: 'promise-error',
        message: event.reason?.message || String(event.reason),
        stack: event.reason?.stack
      })
    })

    // 3. 捕获资源加载错误
    window.addEventListener('error', (event) => {
      if (event.target !== window) {
        this.report({
          type: 'resource-error',
          tagName: event.target.tagName,
          src: event.target.src || event.target.href
        })
      }
    }, true)

    // 4. 捕获 Vue/React 组件错误
    // Vue: app.config.errorHandler
    // React: ErrorBoundary 组件

    // 5. 定时批量上报
    setInterval(() => this.flush(), this.options.flushInterval)
  }

  report(data) {
    this.queue.push({
      ...data,
      timestamp: Date.now(),
      url: location.href,
      userAgent: navigator.userAgent
    })

    // 达到阈值立即上报
    if (this.queue.length >= this.options.maxBatchSize) {
      this.flush()
    }
  }

  flush() {
    if (this.queue.length === 0) return
    const logs = this.queue.splice(0)
    // 使用 sendBeacon 确保页面关闭时也能上报
    if (navigator.sendBeacon) {
      navigator.sendBeacon(
        this.options.reportUrl,
        JSON.stringify(logs)
      )
    } else {
      fetch(this.options.reportUrl, {
        method: 'POST',
        body: JSON.stringify(logs),
        headers: { 'Content-Type': 'application/json' },
        keepalive: true
      })
    }
  }
}

// 使用
new ErrorMonitor({ reportUrl: '/api/error/report' })
```

**Source Map 还原**：
- 构建时上传 Source Map 到错误监控平台（如 Sentry）
- 或使用 `hidden-source-map`，只在服务端保留 Source Map
- 使用 `source-map` 库解析错误堆栈，还原到源代码位置

**关键设计要点**：
- 使用 `sendBeacon` 确保页面关闭时也能上报
- 批量上报减少请求次数
- 区分错误类型（JS 错误、Promise 错误、资源错误、接口错误）
- 生产环境使用 `hidden-source-map`，不暴露源码

### 5. ★★★ 设计一个前端灰度发布方案

**题目**：设计一套前端灰度发布方案，支持按用户比例、白名单、地域等维度进行灰度。

**参考答案**：

**整体架构**：

```
用户请求 → CDN/LB → 灰度策略判断 → 灰度版本 / 稳定版本
                      ↑
                 配置中心（动态下发灰度规则）
```

**方案一：Nginx 层灰度**

```nginx
# 基于 Cookie 的灰度分流
map $cookie_gray_version $backend {
    "v2"    gray_server;
    default stable_server;
}

upstream stable_server {
    server 192.168.1.10:3000;
}

upstream gray_server {
    server 192.168.1.11:3000;
}

server {
    location / {
        proxy_pass http://$backend;
    }
}
```

**方案二：前端代码层灰度**

```javascript
// gray-release.js
class GrayRelease {
  constructor(config) {
    this.config = config
    this.userId = this.getUserId()
  }

  getUserId() {
    // 从 Cookie、localStorage 或登录态获取
    return localStorage.getItem('uid') || 'anonymous'
  }

  // 基于用户 ID 哈希的灰度判断
  isInGrayByHash(percentage = 10) {
    const hash = this.hashCode(this.userId)
    return (hash % 100) < percentage
  }

  // 基于白名单的灰度判断
  isInWhiteList(whiteList = []) {
    return whiteList.includes(this.userId)
  }

  // 综合判断
  shouldUseGray() {
    const { percentage, whiteList, forcedVersion } = this.config

    // 强制版本（用于调试）
    if (forcedVersion) return forcedVersion === 'gray'

    // 白名单优先
    if (whiteList && this.isInWhiteList(whiteList)) return true

    // 比例灰度
    return this.isInGrayByHash(percentage || 10)
  }

  hashCode(str) {
    let hash = 0
    for (let i = 0; i < str.length; i++) {
      const char = str.charCodeAt(i)
      hash = ((hash << 5) - hash) + char
      hash = hash | 0 // Convert to 32bit integer
    }
    return Math.abs(hash)
  }

  // 获取灰度配置（从远程配置中心）
  async fetchConfig() {
    try {
      const res = await fetch('/api/gray-config')
      const config = await res.json()
      this.config = { ...this.config, ...config }
    } catch (e) {
      console.warn('获取灰度配置失败，使用默认配置')
    }
  }
}

// 使用示例
const grayRelease = new GrayRelease({
  percentage: 10,                // 10% 用户进入灰度
  whiteList: ['admin', 'test1'], // 白名单用户
  forcedVersion: null            // 强制版本（调试用）
})

async function init() {
  await grayRelease.fetchConfig()

  if (grayRelease.shouldUseGray()) {
    // 加载灰度版本资源
    console.log('进入灰度版本')
    import('./app-gray.js')
  } else {
    // 加载稳定版本资源
    console.log('使用稳定版本')
    import('./app-stable.js')
  }
}

init()
```

**灰度发布完整流程**：

```
1. 功能开发 → 2. 代码合并到灰度分支 → 3. 构建灰度版本
4. 部署灰度环境 → 5. 配置灰度策略（比例/白名单）
6. 小流量验证 → 7. 监控指标（错误率、性能、业务指标）
8. 无异常 → 逐步放量（10% → 30% → 50% → 100%）
9. 全量发布 → 10. 清理灰度环境
```

**关键设计要点**：
- 使用**用户 ID 哈希**确保同一用户始终进入同一版本（一致性）
- 支持**多维度灰度**：用户比例、白名单、地域、设备类型
- **灰度配置动态下发**：不需要重新部署即可调整灰度策略
- **快速回滚**：一旦发现异常，通过配置中心立即切回稳定版本
- **监控和告警**：对比灰度版本和稳定版本的错误率、性能指标
