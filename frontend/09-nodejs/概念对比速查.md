# Node.js - 概念对比速查

---

### Express vs Koa vs Nest.js

| 对比维度 | Express | Koa | Nest.js |
|---------|---------|-----|---------|
| 核心定位 | 功能完备、开箱即用的 Web 框架（v4.x 主流，v5.0 已于 2024.9 发布） | 极简内核、洋葱模型 Web 框架 | 企业级、模块化、装饰器驱动框架 |
| 内核大小 | 较大，内置路由、静态文件、模板引擎等 | 极小，核心约 2000 行代码 | 中等，基于 Express/Fastify 的上层架构 |
| 中间件模型 | 线性执行，通过 next() 串联回调 | 洋葱模型，基于 async/await | 基于 Express/Koa 中间件 + 守卫/拦截器/管道 |
| 错误处理 | 需要专门的 4 参数错误处理中间件 | 使用 try/catch 统一捕获 | 内置异常过滤器，分层错误处理 |
| 请求/响应 | 独立的 req 和 res 对象 | 统一的 ctx 上下文对象 | 装饰器注入 @Req()/@Res() 及专用 DTO |
| 异步支持 | 基于回调，需手动处理 Promise | 原生支持 async/await | 原生支持 async/await + RxJS |
| TypeScript | 需要额外配置 @types/express | 需要额外配置 @types/koa | 内置 TypeScript 优先，装饰器元数据 |
| 依赖注入 | 不支持 | 不支持 | 内置 IoC 容器，模块化依赖注入 |
| 生态丰富度 | 最丰富，中间件最多 | 较丰富，但需第三方插件 | 快速成长，官方模块体系完善 |
| 适用场景 | 快速开发、传统项目 | 需要精细控制、现代项目 | 大型企业级应用、微服务架构 |
| 选择建议 | 小型项目或快速原型 | 中等项目需自定义中间件栈 | 大型团队、需要模块化架构的项目 |

### CommonJS vs ESM

| 对比维度 | CommonJS | ES Module |
|---------|----------|-----------|
| 语法 | require() / module.exports | import / export |
| 加载方式 | 同步加载，运行时解析 | 异步加载，编译时静态分析 |
| 导出方式 | 值拷贝，模块内部变化不影响外部 | 值引用（live binding），模块内部变化反映到外部 |
| Tree Shaking | 不支持 | 支持 |
| 顶层 await | 不支持 | 支持 |
| this 指向 | 指向当前模块 | undefined |
| 缓存机制 | 首次加载后缓存到 require.cache | 由引擎管理，规范层面无缓存要求 |
| 文件扩展名 | .js / .cjs | .mjs 或 package.json 中 "type": "module" |
| 动态导入 | require() 本身是动态的 | import() 函数返回 Promise |
| 循环引用 | 可能拿到不完整对象 | 通过 live binding 处理，更安全 |
| 使用环境 | Node.js 默认 | 现代浏览器 + Node.js 12+ |
| 选择建议 | 维护旧 Node.js 项目 | 新项目默认使用 ESM |

### process.nextTick vs setImmediate vs setTimeout

| 对比维度 | process.nextTick | setImmediate | setTimeout(fn, 0) |
|---------|-----------------|-------------|-------------------|
| 任务类型 | 微任务 | 宏任务 | 宏任务 |
| 执行阶段 | 当前阶段结束后立即执行 | check 阶段（poll 之后） | timers 阶段 |
| 优先级 | 最高 | 中 | 低（在 I/O 回调中低于 setImmediate） |
| 典型用途 | 在当前操作完成后立即执行回调 | 将回调推迟到 poll 阶段之后 | 延迟到下一轮事件循环执行 |
| 递归风险 | 递归调用会饿死事件循环 | 安全，每次只执行一个 | 安全，但最小延迟约 1ms |
| 在 I/O 回调中 | 最先执行 | 先于 setTimeout(fn, 0) | 后于 setImmediate |
| 取消方式 | 无法取消 | clearImmediate() | clearTimeout() |
| 选择建议 | 需要最高优先级立即执行时 | 需要 poll 阶段之后执行回调 | 需要最小延迟时（不推荐用于精确时机） |

### Stream vs Buffer

| 对比维度 | Stream | Buffer |
|---------|--------|--------|
| 核心定位 | 流式数据处理的抽象接口，分块处理数据 | 二进制数据缓冲区，一次性持有完整数据 |
| 数据处理方式 | 逐块（chunk）读取/写入 | 整块数据一次性加载到内存 |
| 内存占用 | 恒定，不随数据量增长 | 与数据大小成正比 |
| 典型场景 | 大文件读写、HTTP 请求响应、压缩解压 | 编码转换、二进制协议解析、加密解密 |
| 类型 | Readable / Writable / Duplex / Transform | 单一类型，Uint8Array 子类 |
| 背压机制 | 内置（pipe 自动处理） | 不适用 |
| 事件驱动 | 支持（data/end/error 等事件） | 不支持事件 |
| 适用数据量 | 适用于任意大小数据，尤其大文件 | 适用于小数据量（KB 级别） |
| 选择建议 | 处理 GB 级大文件或实时流数据 | 处理小数据块、编码转换、协议解析 |

### JWT vs Session

| 对比维度 | JWT | Session |
|---------|-----|---------|
| 存储位置 | 客户端存储完整 Token | 服务端存储会话数据，客户端仅存 Session ID |
| 服务端状态 | 无状态，服务端不需要存储 | 有状态，服务端需要存储会话 |
| 分布式支持 | 天然支持，无需共享存储 | 需要 Redis 等共享存储 |
| 主动失效 | 无法主动失效（除非用黑名单） | 服务端可直接销毁 Session |
| 安全性 | Payload 仅 Base64 编码，不加密 | 敏感数据仅存服务端，不暴露给客户端 |
| 传输方式 | 通常放在 Authorization 头中 | 通常通过 Cookie 自动携带 |
| CSRF 风险 | 低（不在 Cookie 中） | 高（需要 SameSite 或 CSRF Token 防护） |
| XSS 风险 | 高（Token 可被 JS 读取） | 低（httpOnly Cookie 防 JS 读取） |
| 体积 | 较大，包含完整用户信息 | 小，仅 Session ID |
| 适用场景 | 分布式微服务、移动端 API | 传统服务端渲染、单体应用 |
| 选择建议 | 前后端分离、微服务架构 | 需要服务端主动控制会话的场景 |

### BFF vs 传统 API 网关

| 对比维度 | BFF | 传统 API 网关 |
|---------|-----|-------------|
| 核心定位 | 为特定前端定制的后端服务层 | 统一的 API 入口，通用路由转发 |
| 服务粒度 | 每个前端类型一个 BFF（Web/iOS/Android） | 所有客户端共享同一个网关 |
| 数据聚合 | 主动聚合多个微服务数据并裁剪 | 通常只做路由转发，不聚合数据 |
| 数据裁剪 | 按前端需求裁剪字段，减少传输量 | 透传原始数据，不做裁剪 |
| 协议转换 | 可转换 gRPC/SOAP 为 REST/GraphQL | 通常只做 HTTP 协议层面的转换 |
| 认证鉴权 | 可集成前端专属的认证逻辑 | 通用认证，不区分客户端 |
| 开发维护 | 由前端团队自主开发和维护 | 由网关团队或基础设施团队维护 |
| 灵活性 | 高，前端可自主决定接口形态 | 低，变更需协调网关团队 |
| 适用场景 | 微服务 + 多端（Web/移动端/小程序） | 大规模微服务治理、多协议统一入口 |
| 选择建议 | 前端团队有 Node.js 能力，需定制化接口 | 统一网关治理、多协议兼容 |
