## 一、核心概念

### 1.1 uni-app 框架概述

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Vue.js 的跨端开发框架，由 DCloud 推出，一套代码可编译到 iOS、Android、Web（H5）、以及各大主流小程序平台（微信、支付宝、百度、字节跳动、QQ、快手、京东等）。 |
| 能做什么 | 使用 Vue 语法编写一次代码，通过编译器生成多端可运行的应用；覆盖移动端 App、H5 网页、各类小程序，极大降低多端维护成本，统一开发体验。 |
| 怎么用 | 通过 HBuilderX IDE 或 CLI 创建项目：`pnpm dlx @dcloudio/uvm` 或直接在 HBuilderX 中新建 uni-app 项目；使用 `.vue` 单文件组件，配合 `pages.json` 配置路由和页面。 |
| 原理和工作流程 | uni-app 在编译阶段将 Vue 模板编译为各端原生代码：H5 端编译为标准 Vue 项目运行在浏览器；小程序端将 Vue 模板编译为小程序的 WXML/WXSS/JS；App 端通过内置的 WebView 渲染引擎或原生渲染引擎（nvue）运行。核心是编译器 + 运行时桥接层的组合。 |
| 缺点 | 各端平台能力差异导致部分特性无法完全统一，需通过条件编译处理平台差异；复杂交互场景下小程序端性能可能受限；原生功能调用需要编写原生插件。 |

### 1.2 跨端开发原理

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 通过"编译时转换 + 运行时适配"的双重机制，将同一份 Vue 源码转换为各平台可执行代码的技术方案。 |
| 能做什么 | 实现一套代码同时发布到 iOS、Android、H5、微信小程序、支付宝小程序、百度小程序等多个平台，减少重复开发工作量。 |
| 怎么用 | 开发者无需关心底层转换细节，只需按 uni-app 规范编写 Vue 组件，使用 `uni.xxx` API 替代平台专用 API，编译器自动处理跨端适配。 |
| 原理和工作流程 | 编译时：Vue 单文件组件的 `<template>` 被转换为各平台的模板语法（H5 保留 Vue 模板、小程序转为 WXML 等）；`<script>` 中的框架 API 被替换为平台对应的底层实现；`<style>` 通过 PostCSS 和条件编译处理各平台样式差异。运行时：uni-app 在各平台提供统一的 JS 运行时桥接层，封装了平台原生 API，对外暴露一致的 `uni.xxx` 接口。 |
| 缺点 | 编译转换并非 100% 完美，某些复杂的 Vue 特性（如自定义指令的部分用法）在小程序端可能受限；平台特有的 UI 组件（如小程序原生组件）需要通过条件编译单独处理。 |

### 1.3 条件编译

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 提供的一种特殊注释语法，在编译阶段根据目标平台选择性保留或删除代码块，实现不同平台使用不同代码。 |
| 能做什么 | 在同一个文件中为不同平台编写差异化代码，编译时自动裁剪，最终产物只包含目标平台的代码，不会增加其他平台的冗余代码。 |
| 怎么用 | 使用 `<!-- #ifdef H5 -->` / `<!-- #endif -->` 在模板中条件编译；使用 `// #ifdef MP-WEIXIN` / `// #endif` 在脚本中条件编译；使用 `/* #ifdef APP-PLUS */` / `/* #endif */` 在样式中条件编译。 |
| 原理和工作流程 | 在编译阶段，uni-app 编译器扫描源码中的条件编译注释，根据 `process.env.UNI_PLATFORM` 的值判断当前目标平台，匹配 `#ifdef` 的代码保留，不匹配的代码删除。`#ifndef` 为反向条件（除指定平台外保留）。支持平台值包括：H5、MP-WEIXIN、MP-ALIPAY、MP-BAIDU、MP-TOUTIAO、MP-QQ、APP-PLUS、APP-PLUS-NVUE 等。 |
| 缺点 | 条件编译注释过多会降低代码可读性，增加维护难度；条件编译只在编译时生效，无法在运行时动态切换平台行为；嵌套条件编译可能引发逻辑混乱。 |

### 1.4 页面生命周期与组件生命周期

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 中页面和组件各自拥有独立的生命周期钩子函数，页面生命周期兼容小程序页面生命周期，组件生命周期基于 Vue 组件生命周期扩展。 |
| 能做什么 | 页面生命周期（onLoad、onShow、onReady、onHide、onUnload、onPullDownRefresh、onReachBottom、onPageScroll 等）用于页面级的初始化、数据加载、状态管理；组件生命周期（beforeCreate、created、beforeMount、mounted、beforeUpdate、updated、beforeUnmount、unmounted）（Vue 3 命名，Vue 2 为 beforeDestroy/destroyed）用于组件内部逻辑处理。 |
| 怎么用 | 页面中直接在 `export default` 中定义：`onLoad(options) { }`、`onShow() { }`；组件中使用 Vue 标准生命周期：`created() { }`、`mounted() { }`。页面也支持 Vue 生命周期，但小程序端 onLoad 等页面生命周期更可靠。 |
| 原理和工作流程 | 页面生命周期由 uni-app 运行时桥接层统一管理，在小程序端映射到小程序原生页面生命周期（onLoad → Page.onLoad），在 H5 端通过 Vue Router 的路由守卫模拟。组件生命周期完全遵循 Vue 的响应式系统和虚拟 DOM 更新机制。数据请求推荐在 onLoad 中发起（页面加载时只调用一次），而非 mounted（组件每次显示都会触发）。 |
| 缺点 | 小程序端页面生命周期的触发时机与 Vue 生命周期不同步，例如 `created` 可能在 `onLoad` 之前或之后执行，取决于平台实现；App 端页面栈深度有限制（通常 5-10 层），超出后 `navigateTo` 会失败。 |

## 二、底层原理

### 2.1 uni-app 编译流程

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 将开发者编写的 Vue 源码通过编译器转换为各平台可执行代码的完整流水线。 |
| 能做什么 | 理解编译流程有助于排查跨端兼容性问题，优化编译配置，以及编写更高效的跨端代码。 |
| 怎么用 | 流程：`Vue 源码 → 模板解析 → AST 转换 → 平台代码生成 → 平台 SDK 打包 → 各平台产物` |
| 原理和工作流程 | 1. 模板解析：将 `.vue` 文件的 `<template>` 解析为 AST（抽象语法树）；2. 条件编译裁剪：扫描并处理条件编译注释，移除不匹配平台的代码块；3. 平台转换：将 Vue AST 转换为目标平台的 AST（H5 保留、小程序转 WXML AST、App 转原生渲染树）；4. 样式处理：通过 PostCSS 转换单位（rpx 转 px 或 rem），处理平台特有的样式前缀；5. 代码生成：根据目标平台生成对应的 JS/CSS/模板文件；6. 打包：H5 端使用 Webpack/Vite 打包，小程序端生成小程序工程，App 端通过离线打包或云打包生成 APK/IPA。 |
| 缺点 | 编译过程较复杂，大型项目编译时间可能较长；自定义 webpack 配置需要理解 uni-app 的编译链，有一定学习成本。 |

### 2.2 各端渲染机制总览

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 在不同平台上采用不同的渲染引擎：H5 端使用浏览器 WebView 渲染，小程序端使用各平台小程序框架的渲染引擎，App 端支持 WebView 渲染（vue 页面）和原生渲染（nvue 页面）两种模式。 |
| 能做什么 | 理解各端渲染机制有助于合理选择 nvue/webview 页面类型，优化渲染性能，避免平台差异导致的 UI 异常。 |
| 怎么用 | vue 页面（默认）：跨平台兼容性最好，使用 WebView 渲染，适用于大多数场景；nvue 页面：使用原生渲染引擎，性能更好，但 CSS 支持受限，适用于高性能列表、复杂动画等场景。 |
| 原理和工作流程 | H5 端：uni-app 编译为标准的 Vue 单页应用，运行在浏览器 WebView 中，通过虚拟 DOM 更新视图。小程序端：编译为小程序原生代码，运行在小程序的双线程架构中（渲染层 WebView + 逻辑层 JSCore），数据通过 setData 传递。App 端 vue 页面：运行在系统 WebView 中，类似 H5 但可调用原生能力。App 端 nvue 页面：使用 Weex 原生渲染引擎，将 Vue 组件映射为原生 UI 控件（Android 的 View、iOS 的 UIView），直接在原生渲染线程上绘制。 |
| 缺点 | nvue 页面 CSS 支持有限（仅支持 flexbox 布局子集，不支持 css 动画、百分比等），开发体验不如 vue 页面；小程序端 setData 数据量限制（单次不超过 256KB），频繁大量数据更新会卡顿。 |

### 2.3 rpx 响应式单位原理

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 内置的响应式像素单位，以屏幕宽度 750rpx 为基准，自动适配不同屏幕尺寸。 |
| 能做什么 | 实现一套样式在不同屏幕宽度的设备上等比缩放，无需手动计算 rem 或使用媒体查询。 |
| 怎么用 | 直接在 CSS 中使用 rpx 单位：`width: 375rpx;`（即屏幕宽度的一半）；uni-app 编译时自动转换为各端对应的单位。 |
| 原理和工作流程 | uni-app 以 750rpx 为基准宽度（对应 iPhone 6/7/8 的 375px 物理像素 @2x）。编译器在构建时将 rpx 按比例转换：H5 端转为 rem（基准 `font-size: (屏幕宽度 / 750 * 设备像素比)px`）；小程序端转为 rpx（小程序原生支持）；App 端转为 px（根据屏幕宽度和密度自动计算）。开发者无需关心转换细节。 |
| 缺点 | 在需要精确像素控制（如 1px 边框）的场景，rpx 换算可能导致非整数像素值，产生模糊；横屏模式下 750rpx 基准与竖屏一致，可能导致比例失调。 |

## 三、实战应用

### 3.1 项目初始化与配置

| 维度 | 内容 |
|------|------|
| 是什么 | 创建 uni-app 项目并配置 pages.json、manifest.json、uni.scss 等核心配置文件的过程。 |
| 能做什么 | 快速搭建跨端项目骨架，配置页面路由、导航栏样式、全局样式变量、各平台权限和能力声明。 |
| 怎么用 | HBuilderX：新建项目 → 选择 uni-app 模板；CLI：`pnpm dlx degit dcloudio/uni-preset-vue#vite-ts my-project`；核心配置：`pages.json` 定义页面路由和窗口样式，`manifest.json` 配置各平台应用信息，`uni.scss` 定义全局样式变量。 |
| 原理和工作流程 | `pages.json` 是 uni-app 的路由和窗口配置文件，编译器根据此文件生成各平台的路由配置（H5 生成 vue-router 配置、小程序生成 app.json 的 pages 数组）。`manifest.json` 定义应用级别的配置，编译时映射到各平台的 manifest 文件（AndroidManifest.xml、Info.plist、project.config.json 等）。`uni.scss` 中的变量在编译时注入到所有页面的样式文件中。 |
| 缺点 | `pages.json` 不支持动态路由，所有页面必须在编译前静态声明；配置项较多，各平台差异配置分散，容易遗漏。 |

### 3.2 页面路由与导航

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 提供的页面跳转和导航 API，封装了各平台的路由能力，支持路由跳转、页面栈管理、参数传递。 |
| 能做什么 | 实现页面间的跳转（navigateTo、redirectTo、switchTab、reLaunch、navigateBack），页面间参数传递，以及页面栈的控制。 |
| 怎么用 | `uni.navigateTo({ url: '/pages/detail/detail?id=1' })` 保留当前页跳转；`uni.redirectTo({ url: '/pages/login/login' })` 关闭当前页跳转；`uni.switchTab({ url: '/pages/index/index' })` 跳转 tabBar 页面；`uni.navigateBack({ delta: 1 })` 返回上一页；目标页面通过 `onLoad(options)` 接收参数。 |
| 原理和工作流程 | 在 H5 端，uni-app 使用 Vue Router 实现路由管理，navigateTo 对应 `router.push`，redirectTo 对应 `router.replace`。在小程序端，直接调用小程序原生导航 API（`wx.navigateTo` 等）。在 App 端，维护一个原生页面栈，每个页面对应一个 WebView 实例。页面栈深度在各平台有不同限制（小程序 10 层、App 端约 5-10 层）。 |
| 缺点 | 页面栈深度有限制，超出后 navigateTo 静默失败，需要改用 redirectTo 或 reLaunch；URL 参数长度有限制（小程序端约 2KB），大数据量传递需使用全局变量或 Vuex。 |

### 3.3 API 统一调用

| 维度 | 内容 |
|------|------|
| 是什么 | uni-app 提供的一套跨平台 API，通过 `uni.xxx` 命名空间统一调用各平台的原生能力，包括网络请求、存储、媒体、设备、界面等。 |
| 能做什么 | 一套 API 代码调用所有平台的原生功能：网络请求（uni.request）、本地存储（uni.setStorageSync）、地理位置（uni.getLocation）、相机（uni.chooseImage）、支付（uni.requestPayment）、推送（uni.getPushClientId）等。 |
| 怎么用 | Promise 风格：`uni.request({ url: '/api/data', method: 'GET' }).then(res => {})`；也支持 async/await：`const res = await uni.request({ url: '/api/data' })`；回调风格（兼容旧版）：`uni.request({ url: '/api/data', success: (res) => {} })` |
| 原理和工作流程 | uni-app 运行时在初始化阶段注入 `uni` 全局对象，该对象在不同平台指向不同的底层实现。H5 端封装浏览器 API（如 fetch 封装为 uni.request）；小程序端映射到 wx/qq/my 等原生 API；App 端通过 JS Bridge 调用原生模块。开发者在代码中统一使用 `uni.xxx`，运行时根据当前平台自动路由到正确的底层实现。 |
| 缺点 | 部分平台特有 API 不在 uni-app 统一封装范围内（如微信小程序的订阅消息、支付宝小程序的特定 API），需要使用条件编译直接调用平台原生 API；各平台 API 能力不完全一致，需查阅文档确认兼容性。 |

## 四、常见面试题

### 1. uni-app 如何实现一套代码多端运行？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查候选人对 uni-app 跨端原理的理解，包括编译时转换和运行时适配两个核心机制。 |
| 能做什么 | 检验候选人是否深入理解跨端框架的工作原理，而非仅停留在"会用"的层面。 |
| 怎么用 | 核心回答点：编译时 Vue 模板转各平台代码、条件编译处理平台差异、运行时 uni API 桥接层封装原生能力。 |
| 原理和工作流程 | 编译时：Vue 模板 → 各平台模板（H5 保留、小程序转 WXML、App 转原生渲染树），条件编译裁剪平台特定代码，rpx 单位转换。运行时：注入 uni 全局对象，封装各平台原生 API 为统一接口；页面生命周期通过桥接层映射到各平台生命周期。 |
| 缺点 | 回答时注意区分"编译时"和"运行时"两个阶段，以及各平台的具体差异，避免笼统回答。 |

### 2. 条件编译的作用和使用方式？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查候选人对条件编译语法的掌握程度，以及在实际项目中处理平台差异的能力。 |
| 能做什么 | 检验候选人是否理解条件编译的编译时特性，以及能否合理运用条件编译避免代码冗余。 |
| 怎么用 | 模板：`<!-- #ifdef H5 --><view>H5内容</view><!-- #endif -->`；脚本：`// #ifdef MP-WEIXIN` / `// #endif`；样式：`/* #ifdef APP-PLUS */` / `/* #endif */`；还支持 `#ifndef` 反向条件。 |
| 原理和工作流程 | 条件编译在编译阶段处理，编译器扫描所有条件编译注释，根据目标平台变量决定保留或删除代码块。最终产物中只包含目标平台的代码，不会增加包体积。条件编译支持嵌套使用，但不能跨文件。 |
| 缺点 | 回答时需说明条件编译的局限性：只在编译时处理，无法运行时动态切换；过度使用降低代码可读性。 |

### 3. uni-app 页面生命周期及其与 Vue 生命周期的关系？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查候选人对 uni-app 页面生命周期（onLoad、onShow、onReady、onHide、onUnload 等）的理解，以及它们与 Vue 组件生命周期（created、mounted 等）的执行顺序和适用场景。 |
| 能做什么 | 检验候选人是否能在实际项目中正确选择生命周期钩子进行数据请求和状态管理。 |
| 怎么用 | 页面加载时请求数据用 `onLoad`（只调用一次）；页面显示时刷新数据用 `onShow`（每次显示都调用）；组件初始化用 `created`/`mounted`。执行顺序：onLoad → onShow → created → beforeMount → onReady → mounted。 |
| 原理和工作流程 | 页面生命周期由 uni-app 运行时管理，在小程序端直接映射到小程序页面生命周期，在 H5 端通过路由守卫模拟。Vue 生命周期由 Vue 框架管理。两者的执行顺序在不同平台可能略有差异，但数据请求放在 onLoad 中是最可靠的跨端方案。 |
| 缺点 | 需注意 `onShow` 可能在页面首次加载和从后台切回时都触发，避免重复请求；`onHide` 和 `onUnload` 的触发时机在小程序和 H5 端有差异。 |

### 4. uni-app 中如何调用各端原生能力？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查候选人对 uni-app 原生能力调用方案的理解，包括 uni API、原生插件、条件编译调用原生 API 三种方式。 |
| 能做什么 | 检验候选人是否能在项目中处理平台特定的原生功能需求（如指纹识别、蓝牙、NFC 等）。 |
| 怎么用 | 通用方案：使用 `uni.xxx` API（如 `uni.getLocation`）；条件编译方案：`// #ifdef MP-WEIXIN` 中直接调用 `wx.xxx` API；App 端方案：编写原生插件（Android/iOS 原生模块），通过 `uni.requireNativePlugin` 调用。 |
| 原理和工作流程 | uni API 封装了各平台最常用的原生能力，运行时自动路由到对应平台实现。对于 uni API 未覆盖的功能，在小程序端通过条件编译直接调用平台原生 API；在 App 端通过原生插件扩展——原生插件编译为 .aar（Android）或 .framework（iOS），通过 JS Bridge 与 JS 层通信。 |
| 缺点 | 回答时需说明原生插件开发成本较高，需要 Android（Java/Kotlin）和 iOS（Objective-C/Swift）原生开发能力；且原生插件需在 manifest.json 中配置，打包时需勾选。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总 uni-app 跨端开发基础中四个高频错误及其解决方案，涵盖生命周期、条件编译、rpx 单位、页面栈四个方面。 |
| 能做什么 | 帮助开发者避免数据请求时机错误、平台差异代码未裁剪、样式适配异常、页面栈溢出等常见问题。 |
| 怎么用 | 数据请求放在 `onLoad` 中而非 `mounted`；条件编译注释必须写正确且完整闭合；使用 rpx 单位替代 px 实现多端适配；注意页面栈深度限制，合理使用 redirectTo 替代 navigateTo。 |
| 原理和工作流程 | 小程序端 `mounted` 触发时机不稳定，`onLoad` 由框架保证在页面加载时调用；条件编译注释写错（如 `#ifdef` 写成 `#ifdef`）不会报错，但代码不会按预期裁剪；rpx 换算基于 750 基准宽度，不同屏幕自动等比缩放；页面栈深度限制由各平台框架实现，超出后 navigateTo 静默失败。 |
| 缺点 | 这些避坑方案是基础规范，实际项目中还需结合各平台特性进行调试和测试。 |
