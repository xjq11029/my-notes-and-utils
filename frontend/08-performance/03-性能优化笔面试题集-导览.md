### 1. Core Web Vitals 不包括以下哪个指标

| 维度 | 内容 |
|------|------|
| 是什么 | Core Web Vitals 包含三大核心指标：LCP（加载性能）、FID/INP（交互性）、CLS（视觉稳定性），TTI 是 Lighthouse 指标但不属于 Core Web Vitals |
| 能做什么 | 考查对 Google 官方 Web 体验标准的准确认知，区分核心指标和辅助指标 |
| 怎么用 | 使用 web-vitals 库采集 LCP、INP、CLS 并通过 sendBeacon 上报 |
| 原理和工作流程 | LCP 衡量视口最大内容绘制时间，INP（2024 年 3 月替代 FID）衡量所有交互响应延迟的第 98 百分位值，CLS 衡量布局偏移累积分数。TTI（可交互时间）是 Lighthouse 性能评分的辅助指标，不属于 Core Web Vitals 三大核心指标 |
| 缺点 | FID 和 INP 的过渡期可能造成混淆 |

### 2. LCP 的良好标准是

| 维度 | 内容 |
|------|------|
| 是什么 | LCP（最大内容绘制）的良好标准为 < 2.5s，2.5-4.0s 需改进，>= 4.0s 差 |
| 能做什么 | 考查对 Google Web Vitals 评分标准的记忆 |
| 怎么用 | 通过 Lighthouse 或 web-vitals 库测量 LCP，优化目标为 < 2.5s |
| 原理和工作流程 | LCP 追踪视口内最大可见元素（img/video 封面/背景图元素/文本块）完成渲染的时间点。优化策略包括预加载 LCP 资源、压缩图片、使用 CDN、避免懒加载 LCP 元素 |
| 缺点 | LCP 受网络环境和设备性能影响大，移动端达标难度较高 |

### 3. 以下哪种缓存策略属于强缓存

| 维度 | 内容 |
|------|------|
| 是什么 | Cache-Control: max-age=86400 是强缓存策略，浏览器在有效期内直接使用缓存不发送请求；ETag/If-None-Match/If-Modified-Since 属于协商缓存 |
| 能做什么 | 考查对强缓存（不发送请求）和协商缓存（发送请求验证）的准确区分 |
| 怎么用 | 强缓存：`Cache-Control: max-age=31536000`；协商缓存：`ETag` + `If-None-Match` |
| 原理和工作流程 | 强缓存由 Cache-Control: max-age 和 Expires 控制，有效期内浏览器直接返回 200 from disk/memory cache，完全不发送请求。协商缓存由 ETag/If-None-Match 和 Last-Modified/If-Modified-Since 控制，浏览器发送请求验证，服务器返回 304 Not Modified 或 200 新内容 |
| 缺点 | 强缓存期间用户无法获取更新，需配合文件名哈希实现版本控制 |

### 4. Tree Shaking 依赖 JavaScript 的什么特性

| 维度 | 内容 |
|------|------|
| 是什么 | Tree Shaking 依赖 ES Module 的静态导入/导出（import/export）特性，因为编译时即可确定引用关系 |
| 能做什么 | 考查对 Tree Shaking 底层原理的理解——为什么 CommonJS 不支持 |
| 怎么用 | 使用 ES Module 语法；package.json 设置 `"sideEffects": false`；production 模式构建 |
| 原理和工作流程 | ES Module 的 import/export 在编译时即可确定模块间的引用关系（静态分析），构建工具标记未被引用的导出为 dead code 并在打包阶段移除。CommonJS 的 require 是动态的（运行时确定），可以在条件语句中使用，路径可以是变量，无法在编译时进行静态分析 |
| 缺点 | 部分老旧库仍使用 CommonJS，无法享受 Tree Shaking |

### 5. 以下关于代码分割的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | 动态 import() 可以实现按需加载，是代码分割最灵活的方式；入口分割和 SplitChunksPlugin 也是常用策略 |
| 能做什么 | 考查对代码分割三种方式的全面理解，纠正"代码分割增加总体积""只能在 Webpack 中使用"等错误认知 |
| 怎么用 | 动态导入：`const AboutPage = () => import('./pages/About.vue')`；入口分割：多 entry 配置；SplitChunksPlugin：自动提取公共依赖 |
| 原理和工作流程 | 代码分割不增加总体积，而是将大包拆分为多个小包，提升首屏加载速度。三种方式：入口分割（多 entry 手动拆分）、动态导入（import() 返回 Promise，Webpack/Vite 自动拆分）、SplitChunksPlugin（提取公共模块）。Vite（基于 Rollup）、esbuild 等构建工具都支持代码分割 |
| 缺点 | 过度分割可能导致 HTTP 请求数量增加；动态导入的 chunk 加载失败需处理错误 |

### 6. 虚拟列表的核心原理是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 只渲染可视区域内的 DOM 节点，根据 scrollTop 动态计算 startIndex/endIndex，通过 padding 或 transform 模拟完整滚动高度 |
| 能做什么 | 考查对虚拟列表核心原理的理解，区分虚拟列表与分页、Web Worker 的本质区别 |
| 怎么用 | React：react-window 的 FixedSizeList；Vue：vue-virtual-scroller 的 RecycleScroller |
| 原理和工作流程 | 监听滚动事件获取 scrollTop → 计算 startIndex = Math.floor(scrollTop / itemHeight) 和 endIndex = startIndex + visibleCount + bufferSize → 只渲染该范围内的数据 → 设置容器总高度保证滚动条正确。核心优势是 DOM 节点数量恒定（约 20-30 个），与数据总量无关。Web Worker 无法访问 DOM，不能用于渲染 |
| 缺点 | 动态高度场景实现复杂；快速滚动时可能短暂白屏 |

### 7. 以下关于 SSR 的描述正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | SSR 在服务端将组件渲染为完整 HTML 字符串返回，SEO 友好，首屏速度快，需要 Node.js 服务器支持 |
| 能做什么 | 考查对 SSR 基本概念和特性的理解，纠正常见错误认知 |
| 怎么用 | Next.js：`getServerSideProps` 实现每次请求渲染；Nuxt.js：内置 SSR 支持 |
| 原理和工作流程 | SSR 在服务端执行组件代码生成完整 HTML，客户端接收后直接展示（首屏快），随后进行 hydration（注入交互逻辑）。与 CSR 的区别在于 CSR 返回空 HTML 壳，由客户端 JS 渲染内容。主流框架（React 的 Next.js、Vue 的 Nuxt.js）都支持 SSR |
| 缺点 | 服务器压力大需缓存策略；开发复杂度高于 CSR |

### 8. 以下哪种方式可以减少回流

| 维度 | 内容 |
|------|------|
| 是什么 | CSS transform 只触发合成（Composite），不触发回流（Reflow）和重绘（Repaint），是性能最优的动画实现方式 |
| 能做什么 | 考查对回流触发条件和优化策略的理解 |
| 怎么用 | `transform: translateY(100px)` 替代 `top: 100px`；`transform: scale(1.2)` 替代 `width/height` 变化 |
| 原理和工作流程 | 浏览器渲染管线：JS → Style → Layout → Paint → Composite。回流在 Layout 阶段重新计算几何属性，开销最大。transform 和 opacity 在 Composite 阶段处理（合成线程），不经过 Layout 和 Paint，因此不触发回流。逐条修改 style、使用 top/left、频繁读取 offsetHeight 都会触发回流或 Layout Thrashing |
| 缺点 | transform 不能替代所有需要改变布局的动画场景 |

### 9. 以下关于 HTTP 缓存的说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | ETag/If-None-Match 和 Last-Modified/If-Modified-Since 属于协商缓存，浏览器需要发送请求验证；强缓存和协商缓存可同时使用，浏览器优先使用强缓存 |
| 能做什么 | 考查对缓存策略组合和优先级规则的理解 |
| 怎么用 | 同时设置强缓存和协商缓存：浏览器先检查强缓存，过期后用协商缓存验证 |
| 原理和工作流程 | 两级缓存策略：浏览器先检查强缓存（Cache-Control: max-age），有效期内直接使用不发送请求。强缓存过期后，发送协商缓存请求（携带 If-None-Match 或 If-Modified-Since），服务器判断资源是否变化，未变化返回 304 Not Modified，变化返回 200 新内容。ETag 优先级高于 Last-Modified |
| 缺点 | 缓存策略配置不当会导致更新延迟或缓存失效 |

### 10. 关于 preload 和 prefetch 的区别以下说法正确的是

| 维度 | 内容 |
|------|------|
| 是什么 | preload 是当前页面需要的资源，优先级高，立即加载；prefetch 是未来页面可能需要的资源，优先级低，空闲时加载 |
| 能做什么 | 考查对两种预加载策略的核心区别和使用场景的准确理解 |
| 怎么用 | preload：`<link rel="preload" href="/hero.webp" as="image">`；prefetch：`<link rel="prefetch" href="/page2.js">` |
| 原理和工作流程 | preload 强制浏览器立即以高优先级加载，用于当前页面必需资源（首屏 CSS、字体、LCP 图片），3 秒内未使用触发警告。prefetch 浏览器空闲时以低优先级加载，用于未来页面可能需要的资源。preload 支持多种 as 类型（script、style、font、image、fetch 等），不仅限于 CSS |
| 缺点 | preload 滥用会与关键资源竞争带宽；prefetch 在移动网络下可能浪费流量 |

### 1. Core Web Vitals 三大指标是什么如何优化

| 维度 | 内容 |
|------|------|
| 是什么 | LCP（加载性能 < 2.5s）、INP（交互响应 < 200ms）、CLS（视觉稳定性 < 0.1），三大指标共同构成 Google 搜索排名影响因素 |
| 能做什么 | 以统一标准指导性能优化方向，确保加载速度、交互流畅度和视觉稳定性 |
| 怎么用 | LCP 优化：预加载关键资源、CDN、压缩图片；INP 优化：减少长任务、代码分割、Web Worker；CLS 优化：设置图片宽高、预留动态内容空间、font-display: swap |
| 原理和工作流程 | LCP 追踪视口最大元素渲染时间，优化关键渲染路径。INP 取所有交互延迟的第 98 百分位值，减少主线程阻塞。CLS = 影响比例 x 距离比例，避免已有内容上方插入新内容 |
| 缺点 | 三个指标可能相互制约（如字体 swap 优化 CLS 但可能影响 LCP） |

### 2. 强缓存和协商缓存的区别

| 维度 | 内容 |
|------|------|
| 是什么 | 强缓存不发送请求直接使用缓存（200 from cache），协商缓存发送请求验证后返回 304 |
| 能做什么 | 实现 HTML 协商缓存及时更新 + 静态资源强缓存永久缓存的最佳实践 |
| 怎么用 | 关键策略：HTML 用 `Cache-Control: no-cache`，JS/CSS 用文件名哈希 + `Cache-Control: max-age=31536000, immutable` |
| 原理和工作流程 | 浏览器先判断强缓存（Cache-Control/Expires），有效期内直接使用。过期后发送协商缓存请求（If-None-Match/If-Modified-Since），服务器返回 304 或 200。ETag 优先级高于 Last-Modified。immutable 指令告诉浏览器资源不会变化，跳过验证请求 |
| 缺点 | 缓存策略配置不当会导致更新延迟或缓存失效 |

### 3. 如何实现图片懒加载

| 维度 | 内容 |
|------|------|
| 是什么 | 三种方案：原生 loading="lazy"（推荐）、Intersection Observer API、第三方库（lazysizes 等） |
| 能做什么 | 延迟加载非首屏图片，减少首屏资源加载量，节省带宽 |
| 怎么用 | 原生：`<img src="image.jpg" loading="lazy">`；Intersection Observer：`observer.observe(img)` 在进入视口时替换 data-src |
| 原理和工作流程 | 原生懒加载：浏览器自动判断图片是否接近视口，兼容性好（Chrome 77+）。Intersection Observer：监听元素进入视口，通过 rootMargin 提前触发加载。第三方库提供更丰富的功能（如模糊占位图、加载动画） |
| 缺点 | 原生懒加载对 LCP 元素不适用（应优先加载）；Intersection Observer 需要 polyfill 支持老浏览器 |

### 4. Tree Shaking 的原理和实现条件

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 ES Module 静态分析，标记未使用导出，压缩阶段移除 dead code |
| 能做什么 | 减少打包体积，对大型第三方库效果显著 |
| 怎么用 | 使用 ES Module 语法；package.json 设置 sideEffects；production 模式构建；确保 Babel 不将 ES Module 转为 CommonJS |
| 原理和工作流程 | 构建工具在编译时分析模块依赖图，标记所有未被引用的导出（usedExports），Terser 在压缩阶段删除标记代码。实现条件：必须使用 ES Module（import/export）、正确声明 sideEffects、生产模式构建、模块无隐式副作用（修改全局变量、原型链） |
| 缺点 | 仅支持 ES Module；sideEffects 误用会移除全局 CSS |

### 5. 代码分割的策略有哪些

| 维度 | 内容 |
|------|------|
| 是什么 | 五种策略：入口分割、动态导入、SplitChunksPlugin、路由级分割、组件级分割 |
| 能做什么 | 将大包拆分为多个小包，按需加载或并行加载，提升首屏速度 |
| 怎么用 | 动态导入：`() => import('./page')`；路由级：`const routes = [{ component: () => import('./views/Dashboard.vue') }]`；组件级：`React.lazy(() => import('./Heavy'))` |
| 原理和工作流程 | 入口分割配置多 entry 手动拆分；动态导入 import() 返回 Promise，构建工具自动将动态导入模块拆分为独立 chunk；SplitChunksPlugin 自动提取公共依赖到 vendor/common chunk；路由级和组件级基于动态导入实现按需加载 |
| 缺点 | 过度分割可能导致 HTTP 请求数量增加 |

### 6. 虚拟列表的原理和实现

| 维度 | 内容 |
|------|------|
| 是什么 | 只渲染可视区域 DOM 节点，根据 scrollTop 计算 startIndex/endIndex，通过 padding 或 transform 模拟滚动位置 |
| 能做什么 | 解决大数据量列表渲染卡顿问题，DOM 节点数量恒定与数据总量无关 |
| 怎么用 | startIndex = Math.floor(scrollTop / itemHeight)；endIndex = startIndex + visibleCount + bufferSize；offsetY 通过 paddingTop 模拟 |
| 原理和工作流程 | 监听滚动事件 → 计算可视范围 → 只渲染范围内的数据 → 设置容器总高度保证滚动条正确 → 设置 overscan 缓冲区避免快速滚动白屏。动态高度场景需维护每项高度缓存并动态计算偏移量 |
| 缺点 | 动态高度实现复杂；快速滚动可能短暂白屏；不支持锚点定位 |

### 7. SSR SSG ISR 的区别和适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | SSR 每次请求渲染（实时），SSG 构建时渲染（最快），ISR 首次请求渲染后复用（可配置 revalidate） |
| 能做什么 | 根据数据新鲜度和服务器成本选择合适渲染模式 |
| 怎么用 | Next.js：SSR 用 getServerSideProps；SSG 用 getStaticProps；ISR 用 getStaticProps + revalidate |
| 原理和工作流程 | SSR 适合个性化内容、实时数据，服务器压力大。SSG 适合文档、博客、营销页，性能最优。ISR 适合商品详情、新闻列表，结合实时性和性能。Nuxt.js 支持 SSR/SSG，Gatsby 专注 SSG |
| 缺点 | 选择不当会导致服务器成本过高或内容更新不及时 |

### 8. 如何排查前端内存泄漏

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Chrome DevTools 的 Performance 面板录制 + Memory 面板堆快照对比，排查 JS Heap 持续增长和分离 DOM 节点 |
| 能做什么 | 识别和修复内存泄漏，避免页面长时间运行后卡顿或崩溃 |
| 怎么用 | Performance 面板勾选 Memory 录制 → 观察 JS Heap 是否持续上升 → 手动 GC 后是否回落 → Memory 面板堆快照对比 Delta → 搜索 "Detached" |
| 原理和工作流程 | 排查步骤：录制页面操作 → 手动 GC → 内存未回落则存在泄漏 → 拍摄两次堆快照对比 → 搜索 "Detached" 查找分离 DOM 节点。常见泄漏：全局变量、未清除定时器、未解绑事件监听、闭包引用、DOM 引用、WebSocket 未关闭 |
| 缺点 | 堆快照分析需要经验；大型应用快照体积大难以分析 |

| 是什么 | 场景分析题覆盖首屏加载优化、大数据列表优化、SPA SEO 解决、缓存策略设计、性能监控体系搭建 |

| 怎么用 | 先独立设计方案，再对照参考答案补充遗漏部分 |
| 原理和工作流程 | 题目按难度分布：中档题（1-2、4 题）考查具体优化方案，拔高题（3、5 题）考查架构设计和监控体系 |
| 缺点 | 场景分析题需要综合能力，对新手有一定难度 |

### 1. 首屏加载时间过长如何分析和优化

| 维度 | 内容 |
|------|------|
| 是什么 | 四步法：性能分析（Lighthouse + Performance）→ 瓶颈定位（网络/渲染/代码）→ 优化方案（资源/加载/缓存/CDN/预加载/SSR）→ 验证效果 |
| 能做什么 | 提供系统化的首屏优化流程，从诊断到实施到验证的完整闭环 |
| 怎么用 | 分析工具：Lighthouse、Performance 面板、Coverage 面板、webpack-bundle-analyzer；优化：图片转 WebP/AVIF、Gzip/Brotli、关键 CSS 内联、代码分割、HTML 协商缓存 + JS/CSS 强缓存、CDN、preload、SSR/SSG |
| 原理和工作流程 | 分析阶段：Lighthouse 审计获取 FCP/LCP/TBT/CLS，Performance 瀑布图分析资源加载时序，Coverage 面板找出未使用代码，Bundle 分析找出大体积模块。优化阶段：资源优化（压缩/格式转换）、加载策略（关键 CSS 内联、JS defer/async）、代码分割、缓存策略、CDN、预加载、SSR/SSG。验证阶段：再次 Lighthouse 对比优化前后数据，建立性能监控持续追踪 |
| 缺点 | 优化需要根据具体瓶颈制定方案，没有万能药方 |

### 2. 列表页有 10000 条数据渲染卡顿如何优化

| 维度 | 内容 |
|------|------|
| 是什么 | 推荐方案：虚拟列表 + 后端分页接口，虚拟列表保证渲染性能，后端分页减少数据传输量 |
| 能做什么 | 解决大数据量列表的性能问题，提供多种优化方案对比 |
| 怎么用 | 虚拟列表：react-window 或 vue-virtual-scroller；分页：后端分页接口 + 前端分页组件；懒加载：Intersection Observer 滚动加载更多 |
| 原理和工作流程 | 虚拟列表只渲染可视区域约 20-30 个 DOM 节点，与数据总量 10000 无关。后端分页每次只返回一页数据（如 50 条），减少传输量和前端内存占用。综合推荐虚拟列表 + 后端分页，辅以 React.memo 避免不必要重渲染、图片懒加载、数据缓存 |
| 缺点 | 虚拟列表需要处理动态高度和搜索定位等交互场景 |

### 3. SPA 应用 SEO 问题如何解决

| 维度 | 内容 |
|------|------|
| 是什么 | SPA 的 HTML 是空壳，内容由 JS 动态渲染，搜索引擎爬虫抓取效果差，解决方案包括 SSR、SSG、预渲染、动态渲染 |
| 能做什么 | 对比四种方案（SSR/SSG/预渲染/动态渲染）的优缺点，推荐 Next.js 或 Nuxt.js 进行 SSR/SSG 改造 |
| 怎么用 | 内容型页面用 SSG（getStaticProps），个性化页面用 SSR（getServerSideProps），配合 next-seo 等 SEO 插件完善 meta 标签 |
| 原理和工作流程 | 问题原因：Google 虽可执行 JS 但效率低，百度等搜索引擎基本不支持 JS 渲染。SSR 方案 SEO 最佳但服务器压力大；SSG 方案性能最优适合内容不常变页面；预渲染方案对现有 SPA 改动小但动态路由多时构建慢；动态渲染方案兼容性好但需额外服务 |
| 缺点 | SSR/SSG 改造需要迁移到 Next.js/Nuxt.js，对现有项目改动较大 |

### 4. 如何设计一个前端资源缓存策略

| 维度 | 内容 |
|------|------|
| 是什么 | 核心原则：HTML 协商缓存确保及时更新，JS/CSS 文件名哈希 + 强缓存实现永久缓存，图片/字体强缓存，API 协商缓存或无缓存 |
| 能做什么 | 提供完整的资源缓存策略设计，覆盖 HTML、JS、CSS、图片、字体、API 数据 |
| 怎么用 | HTML：`Cache-Control: no-cache`；JS/CSS 带哈希：`Cache-Control: max-age=31536000, immutable`；Nginx：`location ~* \.(js|css|png|jpg)$ { expires 1y; add_header Cache-Control "public, immutable"; }` |
| 原理和工作流程 | HTML 入口文件使用协商缓存确保每次请求验证是否有新版本。JS/CSS 文件名包含内容哈希，内容变化时哈希变化 URL 也变化，旧 URL 的缓存不会影响新版本。immutable 指令告诉浏览器缓存期间资源不会变化，跳过 304 验证请求。图片和字体内容相对稳定使用强缓存 |
| 缺点 | 需要构建工具支持文件名哈希；HTML 协商缓存仍有请求开销 |

### 5. 如何设计一个前端性能监控体系

| 维度 | 内容 |
|------|------|
| 是什么 | 四层架构：指标采集（Core Web Vitals + 自定义指标 + 错误监控）→ 数据上报（sendBeacon + 采样率）→ 监控平台（性能大盘 + 分布分析 + 告警）→ 优化闭环 |
| 能做什么 | 建立完整的性能监控、分析和优化闭环，持续追踪线上用户体验 |
| 怎么用 | 指标采集：web-vitals 库采集 LCP/INP/CLS；自定义指标：PerformanceObserver 监听 resource、performance.mark/measure 打点；错误监控：window.onerror + unhandledrejection + Axios 拦截器。上报：sendBeacon 非阻塞上报，错误 100% 上报，性能数据可配置采样率 |
| 原理和工作流程 | 指标采集层：Core Web Vitals 通过 web-vitals 库封装 PerformanceObserver API；自定义指标通过 performance.mark/measure 打点；错误监控覆盖 JS 运行时错误、Promise 未捕获、资源加载错误、接口异常。数据上报层：sendBeacon 确保页面关闭时也能上报，批量上报减少请求。监控平台层：性能大盘展示 P75 值趋势、页面级分析、按地区/设备/浏览器/网络分布分析、指标劣化告警。优化闭环：发现问题 → 定位瓶颈 → 实施优化 → 验证效果 → 持续监控，建立性能预算自动告警 |
| 缺点 | 需要前后端配合建立完整基础设施；监控本身消耗资源需要控制采样率 |
