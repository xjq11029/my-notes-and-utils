# 01-测试金字塔与单元测试 - 导览

---

## 1.1 测试金字塔（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 测试金字塔是 Mike Cohn 提出的测试策略模型，将测试分为四层：单元测试（50-60%）、组件测试（20-30%）、集成测试（10-15%）、E2E 测试（5-10%），越底层占比越大 |
| 能做什么 | 指导团队合理分配测试资源，确保投入产出比最大化；以建筑类比理解：地基（单元）→ 墙体（组件）→ 房间（集成）→ 整栋楼验收（E2E） |
| 怎么用 | 在项目初期建立测试策略文档，明确各层级的测试范围和比例；CI/CD 流水线中按层级并行执行测试 |
| 原理和工作流程 | 底层测试快速反馈（毫秒级）→ 中层测试验证组件交互（秒级）→ 上层测试验证模块协作（十秒级）→ 顶层测试验证关键路径（分钟级），形成渐进式质量保障体系 |
| 缺点 | 过度追求金字塔比例可能导致实际场景覆盖不足；小项目不需要严格按照金字塔比例（投入产出比不划算） |

## 1.2 测试 ROI 分析（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 测试 ROI（投入产出比）分析：对比不同测试类型的编写速度、运行速度、维护成本、问题定位精度和稳定性 |
| 能做什么 | 帮助团队做出理性的测试策略决策；识别并避免"冰淇淋甜筒"反模式（大量手工 E2E、少量单元测试） |
| 怎么用 | 编写速度：单元测试分钟级，E2E 天级；运行速度：单元测试毫秒级，E2E 分钟级；维护成本：单元测试低，E2E 高 |
| 原理和工作流程 | 每一层测试的 ROI 由执行速度、维护成本、定位精度、稳定性四个维度加权计算；底层测试 ROI 最高，上层越低 |
| 缺点 | ROI 分析是定性分析，不同项目需要根据实际情况调整权重；过度追求 ROI 可能忽视 E2E 测试对关键路径的保障价值 |

## 1.3 Vitest 核心概念（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | Vitest 是 Vite 团队开发的下一代测试框架，与 Vite 生态深度集成，支持 HMR 测试运行、浏览器模式、原生 ESM 和 TypeScript |
| 能做什么 | 替代 Jest 成为 Vite 项目的首选测试框架；共享 Vite 配置（resolve.alias、插件等），减少配置维护成本 |
| 怎么用 | 安装 vitest 依赖 → 配置 vitest.config.ts（复用 vite.config.ts）→ 编写 Vitest 风格的测试用例 → 运行 pnpm vitest |
| 原理和工作流程 | 基于 ESBuild 进行代码转译（比 Babel 更快）→ 在 watch 模式下利用 Vite 的 HMR 机制只重跑受影响的测试 → 支持 jsdom 和浏览器两种运行环境 |
| 缺点 | 生态不如 Jest 成熟（部分 Jest 插件未迁移）；非 Vite 项目迁移成本较高；部分老旧项目不兼容 |

## 2.1 Vitest 测试运行机制（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Vitest 的测试运行机制基于三个核心 API：describe（组织测试套件）、it/test（定义测试用例）、expect（断言），内部通过 Suite 树和 TestCase 列表管理 |
| 能做什么 | 理解测试框架的内部工作原理，有助于编写更高效的测试代码、调试测试失败问题、甚至自定义测试工具 |
| 怎么用 | describe 嵌套创建测试套件树 → it 注册测试用例到当前 suite → beforeEach/afterEach 管理测试生命周期 → 运行器按深度优先遍历执行 |
| 原理和工作流程 | 全局 describe 函数将 fn 回调中的 it 收集到 Suite 树中 → 运行器按深度优先遍历 Suite 树 → 执行 beforeAll → 遍历 it 用例（beforeEach → fn → afterEach）→ 递归子 Suite → afterAll |
| 缺点 | 理解内部实现需要一定的抽象思维能力；实际使用中不需要关心内部实现，只需掌握 API 用法 |

---

## 2.2 Mock 策略（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | Vitest 提供三种 Mock 策略：vi.mock（模块级替换）、vi.fn（创建独立 mock 函数）、vi.spyOn（监听已有方法），覆盖不同场景的模拟需求 |
| 能做什么 | vi.mock 替换整个模块用于隔离外部依赖；vi.fn 创建可配置的 mock 函数用于回调验证；vi.spyOn 监听已有方法可选择保留或替换原始实现 |
| 怎么用 | vi.mock 在文件顶部声明（hoisting 机制）→ vi.fn 创建独立 mock 函数并配置返回值 → vi.spyOn 监听对象方法后调用 mockRestore 恢复 |
| 原理和工作流程 | vi.mock 通过模块系统的 hoisting 机制在导入前替换模块；vi.fn 创建带有 mock 属性（calls、results）的函数对象；vi.spyOn 包装原方法并记录调用信息 |
| 缺点 | vi.mock 的 hoisting 导致无法在 mock 工厂中使用外部变量；Mock 过度会使测试失去意义（只验证 mock 行为不验证真实行为） |

## 2.3 测试覆盖率原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 测试覆盖率通过 Istanbul 或 V8 的代码插桩技术，统计测试执行过程中代码被覆盖的程度，包括行覆盖率、分支覆盖率、函数覆盖率、语句覆盖率四种类型 |
| 能做什么 | 量化测试质量，发现未被测试覆盖的代码区域；在 CI 中设置覆盖率阈值阻止低质量代码合并 |
| 怎么用 | 配置 vitest.config.ts 的 coverage 选项 → 运行 pnpm vitest --coverage → 查看生成的 HTML 报告和终端输出 |
| 原理和工作流程 | Istanbul 将原始代码进行插桩（在每行/每个分支/每个函数前插入计数器）→ 运行测试时计数器记录执行次数 → 计算覆盖率 = 已执行数 / 总数 |
| 缺点 | 100% 覆盖率不等于高质量测试（可能缺少边界条件和断言验证）；覆盖率指标容易被"刷"（写无意义的测试覆盖 getter/setter） |

## 2.4 快照测试原理（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 快照测试将测试输出序列化后存储为快照文件，后续运行测试时对比输出是否与快照一致，用于检测 UI 或数据结构的意外变化 |
| 能做什么 | 简化 UI 组件的回归测试；快速检测意外的 DOM 结构变化；验证复杂数据结构的输出格式 |
| 怎么用 | 首次运行 toMatchSnapshot() 生成快照文件 → 代码变更后运行测试对比差异 → 确认变更后使用 --update 更新快照 |
| 原理和工作流程 | pretty-format 序列化输出 → 写入 __snapshots__/ 目录 → 后续运行对比 → 不匹配时输出 diff → 手动确认或更新 |
| 缺点 | 快照文件过大时难以 review 变更；动态值（时间戳、ID）导致快照不稳定；过度使用快照测试替代行为测试 |

## 3.1 纯函数测试示例（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 纯函数测试是对无副作用、输入确定则输出确定的函数进行单元测试，包括工具函数（日期格式化、货币格式化）、数据转换函数（扁平转树形）、业务计算函数（折扣计算） |
| 能做什么 | 用最少的代码覆盖最核心的业务逻辑；参数化测试减少重复代码；边界条件测试保证代码健壮性 |
| 怎么用 | describe 组织测试套件 → it.each 参数化测试 → 覆盖正常输入、边界条件、异常输入 |
| 原理和工作流程 | 给定输入（Arrange）→ 调用被测函数（Act）→ 验证输出（Assert），即 AAA 模式 |
| 缺点 | 纯函数测试只能覆盖无副作用逻辑，不适用于有外部依赖的代码 |

## 3.2 状态管理测试（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 Vitest 对 Zustand Store 进行单元测试，验证 store 的 actions（增删改查）是否正确更新状态 |
| 能做什么 | 验证购物车、用户信息、全局配置等状态管理的正确性；在组件渲染前发现有状态管理 bug |
| 怎么用 | beforeEach 重置 store 状态 → 调用 store action → 断言 state 变化 → 验证 totalPrice 和 totalCount 等派生状态 |
| 原理和工作流程 | Zustand 的 create 返回一个 hook → 通过 getState() 获取当前状态 → 通过 setState() 重置状态 → 在测试中调用 action 并断言状态变化 |
| 缺点 | Zustand store 测试需要重置状态确保测试隔离；复杂异步 action 需要额外处理 |

## 3.3 API 层测试（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 使用 MSW（Mock Service Worker）在 Node.js 环境中拦截网络请求，对 API 层进行单元测试，模拟成功、失败、超时等场景 |
| 能做什么 | 不依赖真实后端即可测试 API 调用逻辑；模拟各种网络异常场景（500、超时、网络断开）；验证请求参数和响应处理 |
| 怎么用 | setupServer 创建 MSW 服务端 → beforeAll 启动 → 定义 http.get/post 等 handler → 调用 API 函数并断言结果 |
| 原理和工作流程 | MSW 在 Node.js 中拦截 globalThis.fetch → 匹配请求 URL 和方法到对应 handler → 返回 mock 响应 → 测试代码验证 API 函数的行为 |
| 缺点 | MSW handler 需要手动维护与真实 API 的一致性；复杂场景下 handler 配置较繁琐 |

## 3.4 测试覆盖率配置（实战应用）

| 维度 | 内容 |
|---|---|
| 是什么 | 在 vitest.config.ts 中配置 coverage 选项，包括覆盖率引擎（v8/istanbul）、报告格式（text/json/html/lcov）、阈值（thresholds）、排除规则（exclude）、水印（watermarks） |
| 能做什么 | 在 CI 中强制执行覆盖率标准；通过 HTML 报告可视化查看未覆盖的代码行；针对不同目录设置不同阈值 |
| 怎么用 | 配置 coverage.provider → 设置 thresholds → 添加 exclude 排除测试文件 → 运行 pnpm vitest --coverage |
| 原理和工作流程 | 覆盖率引擎在测试运行时插桩代码 → 收集执行数据 → 与阈值对比 → 不满足阈值时测试失败 |
| 缺点 | 阈值设置过高会导致开发效率下降；不同项目需要不同的阈值策略 |
