# 03-前端分层架构与技术管理 - 导览

---

## 1.1 前端分层架构（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 将前端应用按职责划分为数据层（Data Layer）、业务逻辑层（Service Layer）、视图层（View Layer）三层，每层只依赖其下层 |
| 能做什么 | 提升代码可测试性、可替换性、可维护性、可复用性；业务逻辑层可在多端共享 |
| 怎么用 | 数据层封装 API/存储 → 业务逻辑层编写 Service 类 → 视图层通过 Composable/Hook 调用 Service |
| 原理和工作流程 | 依赖方向：View → Service → Repository；通过依赖注入解耦；接口定义抽象 → 具体实现可替换 |
| 缺点 | 小型项目显得过度设计；需要团队严格遵守分层规范；初期开发效率略低于直接写在组件中 |

---

## 1.2 架构决策记录 ADR（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 一种轻量级的架构决策文档化方法，用五要素（标题、状态、上下文、决策、后果）结构化记录"为什么这样设计" |
| 能做什么 | 保留架构决策的上下文和理由；帮助新成员理解历史决策；避免重复讨论已决定的问题 |
| 怎么用 | 创建 ADR 模板 → 重大技术决策时填写 → 提交到项目仓库的 docs/adr 目录 → 状态变更时更新 |
| 原理和工作流程 | 遇到架构决策 → 填写 ADR 五要素 → 团队评审 → 标记为"已接受" → 定期回顾 |
| 缺点 | 需要团队养成习惯；小型决策写 ADR 成本过高；ADR 过多时难以索引 |

## 1.3 技术债管理（核心概念）

| 维度 | 内容 |
|---|---|
| 是什么 | 对项目中因快速交付而产生的次优技术决策进行识别、分级、登记和偿还的系统化管理方法 |
| 能做什么 | 控制技术债总量；将隐性成本显性化；为技术优化争取资源提供数据支撑 |
| 怎么用 | 识别技术债 → 分级（L1-L4）→ 登记到技术债表 → 制定偿还计划 → 每个迭代偿还 20% |
| 原理和工作流程 | 定期扫描代码中的技术债信号 → 评估影响范围和紧急程度 → 分配优先级 → 纳入迭代计划 → 偿还后更新状态 |
| 缺点 | 技术债的识别和分级较主观；偿还通常需要与业务需求竞争资源；过度追求零技术债可能影响交付速度 |

## 2.1 依赖倒置在前端分层中的应用（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 将依赖倒置原则（DIP）应用于前端分层架构：高层模块（业务逻辑层）不应依赖低层模块（数据层），两者都应依赖抽象（接口） |
| 能做什么 | 解耦业务逻辑与数据源；支持 Mock 数据源进行单元测试；方便切换数据源（REST → GraphQL） |
| 怎么用 | 定义 Repository 接口 → Service 依赖接口 → 通过 provide/inject 或 Context 注入具体实现 |
| 原理和工作流程 | 接口定义契约 → 数据层实现接口 → 业务逻辑层通过构造函数注入 → 视图层通过 DI 容器获取 Service |
| 缺点 | 增加了抽象层数量；接口定义和实现分离增加了初期工作量；需要团队理解 DI 概念 |

## 2.2 数据流模式对比（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 单向数据流（Redux/Zustand `Action → Store → View`）与响应式数据流（Vue Reactivity/MobX 自动追踪依赖）的对比分析 |
| 能做什么 | 单向数据流适合复杂状态管理（可预测、可调试）；响应式适合快速开发（少写模板代码） |
| 怎么用 | 单向：dispatch action → reducer 更新 store → 组件订阅；响应式：直接修改响应式对象 → 自动触发更新 |
| 原理和工作流程 | 单向：基于不可变数据 + 发布订阅；响应式：基于 Proxy / Object.defineProperty 的依赖追踪 |
| 缺点 | 单向：模板代码多（Redux）、学习曲线陡；响应式：状态变更不够透明、调试困难、不可变数据场景需额外处理 |

## 2.3 技术选型框架（底层原理）

| 维度 | 内容 |
|---|---|
| 是什么 | 基于五维度（学习成本、性能、TS 支持、生态社区、团队熟悉度）加权评估的技术选型方法论 |
| 能做什么 | 将主观的技术选型决策量化，提供可追溯、可论证的决策依据 |
| 怎么用 | 确定评估维度 → 分配权重 → 候选方案打分 → 加权计算 → 选择最高分方案 → 编写 ADR |
| 原理和工作流程 | 多属性决策（MADM）：各维度独立评分 → 加权求和 → 排序 → 结合风险分析做最终决策 |
| 缺点 | 权重设定有一定主观性；评分依赖评分者的经验；部分维度（如"开发体验"）难以量化 |

## 6.1 Island Architecture（岛屿架构）

| 维度 | 内容 |
|---|---|
| 是什么 | 由 Astro 框架推广的前端架构模式，将页面分为静态 HTML 内容（零 JS）和独立的交互岛屿（Islands of Interactivity），各岛屿独立加载和水合，互不依赖。 |
| 能做什么 | 大幅减少首屏 JS 体积（仅交互组件加载 JS）；支持多框架混合（React/Vue/Svelte 组件共存于同一页面）；通过五类水合策略（`client:load`/`idle`/`visible`/`media`/`only`）精细控制交互时机。 |
| 怎么用 | 在 Astro 组件中通过 `client:*` 指令标记交互组件：`<Cart client:load />` 立即水合，`<Chart client:visible />` 进入视口时水合，`<Widget client:only="react" />` 跳过 SSR 仅客户端渲染；静态内容组件不加任何 `client:` 指令，直接输出为 HTML。 |
| 原理和工作流程 | 服务端渲染完整 HTML → 仅交互岛屿组件的 JS 被发送到客户端 → 客户端根据 `client:*` 指令在对应时机水合岛屿组件 → 其余静态内容保持 HTML 零 JS。与整页水合相比，岛屿架构避免了"重放"所有组件代码，TBT（Total Blocking Time）显著降低。 |
| 缺点 | 不适合高度交互的 SaaS 应用（几乎所有组件都需要交互）；岛屿之间共享状态需要额外机制（如 Custom Events 或 Nano Stores）；Astro 默认 MPA 模式，页面切换时岛屿状态会丢失。 |

### 6.2 Partial Hydration / Resumability（Qwik）

| 维度 | 内容 |
|---|---|
| 是什么 | Qwik 框架提出的 Resumability（可恢复性）概念，将组件的状态和执行上下文序列化到 HTML 中，客户端无需"重放"组件代码，直接从序列化状态恢复执行，实现接近零 JS 的启动。 |
| 能做什么 | 消除传统 SSR 的水合过程（不需要重新执行组件代码）；按交互事件粒度拆分 JS chunk（`$()` 标记的函数各自独立打包）；通过 Service Worker 预加载机制，用户悬停时即开始下载 JS，点击时几乎零延迟。 |
| 怎么用 | `component$()` 定义可序列化组件；`useSignal()` 创建状态（自动序列化到 HTML）；`$()` 包装事件处理函数（自动拆分为独立 chunk）；`onClick$={handler}` 绑定懒加载事件；`routeLoader$()` 定义按路由加载的数据获取函数。 |
| 原理和工作流程 | SSR 阶段：渲染组件 → 序列化组件状态为 JSON → 嵌入 HTML → 事件处理函数映射为独立 JS chunk 的 URL；客户端阶段：解析 HTML → 从 JSON 恢复状态 → 用户交互时按需下载对应 JS chunk → 执行事件处理函数。全过程无需"重放"组件代码。 |
| 缺点 | 仅支持 Qwik 框架，无法与 React/Vue 等混用；`$()` 语法和序列化约束学习曲线高；生态较新，第三方库和社区资源远不如 React/Vue 丰富。 |

### 6.3 与 SSR/CSR/SSG 的对比

| 维度 | 内容 |
|---|---|
| 是什么 | 五种前端渲染策略（CSR、SSR、SSG、Island Architecture、Resumability）的全面对比，涵盖首屏速度、SEO、TTI、JS 体积、服务端负载、构建复杂度、框架限制等十个维度。 |
| 能做什么 | 帮助架构师根据项目需求选择最合适的渲染策略：内容型网站选 Island Architecture，高交互 SaaS 选 CSR/SSR，对性能极致追求选 Resumability，静态内容选 SSG。 |
| 怎么用 | 根据项目需求参照对比表：首屏速度优先 → SSG/Island；SEO 优先 → SSG/SSR；交互速度优先 → Resumability；开发效率优先 → CSR/SSR；多框架协作 → Island Architecture。 |
| 原理和工作流程 | CSR 在客户端完成所有渲染；SSR 在服务端渲染 HTML 后客户端水合；SSG 构建时生成静态 HTML；Island Architecture 生成静态 HTML + 选择性水合交互组件；Resumability 在 SSR 中序列化状态，客户端直接恢复。 |
| 缺点 | 没有一种策略是万能的，需要根据项目规模、团队能力、性能目标综合权衡；混合使用多种策略会增加架构复杂度。 |
