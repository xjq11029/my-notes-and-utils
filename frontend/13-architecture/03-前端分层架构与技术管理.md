# 03-前端分层架构与技术管理

## 一、核心概念

### 1.1 前端分层架构

**前端分层架构**是将前端应用按照职责划分为**数据层（Data Layer）**、**业务逻辑层（Service Layer）**、**视图层（View Layer）**三层，每层只依赖其下层，形成清晰的依赖方向。

```
┌─────────────────────────────────────────────┐
│          视图层（View Layer）                 │
│  Vue/React 组件、页面、UI 交互逻辑            │
│  只负责渲染和用户交互，不包含业务逻辑          │
├─────────────────────────────────────────────┤
│        业务逻辑层（Service Layer）             │
│  业务规则、数据校验、状态管理、API 编排         │
│  纯函数/类，不依赖任何 UI 框架                │
├─────────────────────────────────────────────┤
│          数据层（Data Layer）                 │
│  HTTP 请求、WebSocket、本地存储、缓存          │
│  只负责数据的获取和持久化，不包含业务逻辑       │
└─────────────────────────────────────────────┘
```

**MVC 类比**：

| 分层架构 | MVC 对应 | 职责 |
|---|---|---|
| 视图层 | View | 渲染 UI、响应用户交互、绑定事件 |
| 业务逻辑层 | Controller + Model | 业务流程编排、数据校验、状态管理 |
| 数据层 | Model（数据访问部分） | API 请求、本地存储、缓存管理 |

**分层的好处**：
- **可测试性**：业务逻辑层不依赖 UI 框架，可以纯 Vitest 单元测试
- **可替换性**：切换 UI 框架（Vue → React）只需重写视图层
- **可维护性**：每层职责清晰，修改一处不影响其他层
- **可复用性**：业务逻辑层可在 Web、小程序、桌面端之间共享

### 1.2 架构决策记录 ADR

**ADR（Architecture Decision Record）** 是一种轻量级的架构决策文档化方法，用结构化的方式记录"为什么这样设计"。

**ADR 五要素**：

| 要素 | 说明 | 示例 |
|---|---|---|
| 标题（Title） | 决策的简短描述 | "ADR-001: 选择 Zustand 而非 Redux Toolkit 作为状态管理方案" |
| 状态（Status） | 提议 / 已接受 / 已废弃 / 已替代 | 已接受 |
| 上下文（Context） | 当前面临的问题和约束 | 项目需要轻量级状态管理，团队对 Redux 经验不足，不需要中间件生态 |
| 决策（Decision） | 做出了什么选择 | 选择 Zustand，因为它 API 简洁、体积小、TypeScript 支持好 |
| 后果（Consequences） | 决策带来的正面和负面影响 | 正面：开发效率高、bundle 小；负面：生态不如 Redux 丰富 |

### 1.3 技术债管理

**技术债（Technical Debt）** 是指为了快速交付而做出的次优技术决策，需要在未来偿还的"利息"。

**技术债分级标准**：

| 级别 | 名称 | 描述 | 偿还策略 | 示例 |
|---|---|---|---|---|
| L1 | 关键债 | 影响系统稳定性、安全性，存在线上故障风险 | 立即偿还，可暂停当前迭代 | 核心依赖有已知安全漏洞 |
| L2 | 高优债 | 影响开发效率，每次迭代都产生额外成本 | 本迭代内偿还 | 公共组件缺乏单元测试 |
| L3 | 中优债 | 影响代码可读性，但不影响功能 | 下个迭代偿还 | 部分代码缺少 TypeScript 类型 |
| L4 | 低优债 | 代码风格不一致，有优化空间但不紧急 | 纳入技术债 backlog，逐步偿还 | 部分文件使用 options API 而非 composition API |

**技术债识别信号**：
- "这段代码先这样，后面再优化"（口头禅检测）
- 相同逻辑在多处重复出现（拷贝粘贴式开发）
- 组件文件超过 500 行（职责过重）
- 修改一个功能需要改动 5 个以上文件（耦合度过高）
- 新人入职需要 2 周以上才能提交第一个 PR（上手成本高）

## 二、底层原理

### 2.1 依赖倒置在前端分层中的应用

**依赖倒置原则（Dependency Inversion Principle, DIP）**：高层模块不应依赖低层模块，两者都应依赖抽象。

```typescript
// ❌ 违反依赖倒置：视图层直接依赖具体的数据层实现
// components/UserProfile.vue
import { fetchUser } from '@/api/user'; // 直接依赖具体实现

// ✅ 遵循依赖倒置：通过接口/抽象层解耦

// types/user.ts - 定义抽象接口
export interface IUserRepository {
  getUser(id: string): Promise<User>;
  updateUser(user: User): Promise<void>;
}

// services/UserService.ts - 业务逻辑层依赖抽象
export class UserService {
  constructor(private userRepo: IUserRepository) {}

  async getProfile(userId: string): Promise<UserProfile> {
    const user = await this.userRepo.getUser(userId);
    // 业务逻辑：格式化用户数据
    return {
      ...user,
      displayName: user.nickname || user.name || '匿名用户',
      avatarUrl: user.avatar || '/default-avatar.png',
    };
  }
}

// repositories/HttpUserRepository.ts - 数据层实现抽象
export class HttpUserRepository implements IUserRepository {
  async getUser(id: string): Promise<User> {
    return http.get(`/api/users/${id}`);
  }
  async updateUser(user: User): Promise<void> {
    return http.put(`/api/users/${user.id}`, user);
  }
}

// repositories/MockUserRepository.ts - 测试用实现
export class MockUserRepository implements IUserRepository {
  async getUser(id: string): Promise<User> {
    return { id, name: 'Test User', email: 'test@example.com' };
  }
  async updateUser(user: User): Promise<void> {
    console.log('Mock update:', user);
  }
}

// Composition API 中使用依赖注入
// composables/useUser.ts
import { inject, provide } from 'vue';

const USER_SERVICE_KEY = Symbol('UserService');

export function provideUserService() {
  const repo = new HttpUserRepository(); // 或 MockUserRepository
  const service = new UserService(repo);
  provide(USER_SERVICE_KEY, service);
  return service;
}

export function useUserService() {
  const service = inject<UserService>(USER_SERVICE_KEY);
  if (!service) throw new Error('UserService not provided');
  return service;
}
```

### 2.2 数据流模式对比

**单向数据流（Redux / Zustand） vs 响应式（Vue / MobX）**

| 维度 | 单向数据流（Redux/Zustand） | 响应式（Vue Reactivity/MobX） |
|---|---|---|
| 数据流向 | `Action → Store → View` 单向 | 自动追踪依赖，双向绑定 |
| 状态变更 | 显式 dispatch action / 调用 setState | 直接修改状态，自动触发更新 |
| 调试 | 时间旅行调试（Redux DevTools） | 依赖 Vue DevTools / MobX DevTools |
| 模板代码 | Redux 较多，Zustand 较少 | 较少 |
| 适用场景 | 复杂状态管理、需要可预测的状态变更 | 中小型应用、快速开发 |
| 学习曲线 | 中等（需理解 action/reducer/middleware） | 低（Vue 响应式开箱即用） |

```typescript
// Zustand（单向数据流）示例
import { create } from 'zustand';

interface CounterStore {
  count: number;
  increment: () => void;
  decrement: () => void;
}

const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
}));

// 使用
function Counter() {
  const { count, increment } = useCounterStore();
  return <button onClick={increment}>Count: {count}</button>;
}
```

```typescript
// Vue 3 响应式示例
import { reactive } from 'vue';

const state = reactive({
  count: 0,
});

function increment() {
  state.count++; // 直接修改，自动触发视图更新
}

// 使用
// <template>
//   <button @click="increment">Count: {{ state.count }}</button>
// </template>
```

### 3.1 完整前端分层架构示例（Vue 3）

```typescript
// ========================
// 数据层（Data Layer）
// ========================

// repositories/types.ts
export interface IProductRepository {
  getProducts(params: ProductQueryParams): Promise<PaginatedResult<Product>>;
  getProductById(id: string): Promise<Product>;
  createProduct(data: CreateProductDTO): Promise<Product>;
}

// repositories/HttpProductRepository.ts
export class HttpProductRepository implements IProductRepository {
  async getProducts(params: ProductQueryParams): Promise<PaginatedResult<Product>> {
    return http.get('/api/products', { params });
  }
  async getProductById(id: string): Promise<Product> {
    return http.get(`/api/products/${id}`);
  }
  async createProduct(data: CreateProductDTO): Promise<Product> {
    return http.post('/api/products', data);
  }
}

// ========================
// 业务逻辑层（Service Layer）
// ========================

// services/ProductService.ts
export class ProductService {
  constructor(private productRepo: IProductRepository) {}

  async getProductList(params: ProductQueryParams): Promise<PaginatedResult<Product>> {
    // 业务规则：默认分页参数
    const defaultParams = {
      page: 1,
      pageSize: 20,
      sortBy: 'createdAt',
      sortOrder: 'desc' as const,
      ...params,
    };
    return this.productRepo.getProducts(defaultParams);
  }

  async getProductDetail(id: string): Promise<ProductDetail> {
    const product = await this.productRepo.getProductById(id);
    // 业务逻辑：数据转换和格式化
    return {
      ...product,
      priceDisplay: `¥${(product.price / 100).toFixed(2)}`,
      statusLabel: this.getStatusLabel(product.status),
      isDiscount: product.originalPrice > product.price,
    };
  }

  async createProduct(data: CreateProductFormData): Promise<Product> {
    // 业务校验
    this.validateProduct(data);
    // 数据转换
    const dto: CreateProductDTO = {
      ...data,
      price: Math.round(data.price * 100), // 元转分
    };
    return this.productRepo.createProduct(dto);
  }

  private validateProduct(data: CreateProductFormData): void {
    if (!data.name || data.name.length < 2) {
      throw new ValidationError('商品名称至少 2 个字符');
    }
    if (data.price <= 0) {
      throw new ValidationError('商品价格必须大于 0');
    }
  }

  private getStatusLabel(status: ProductStatus): string {
    const labels: Record<ProductStatus, string> = {
      draft: '草稿',
      published: '已上架',
      archived: '已下架',
    };
    return labels[status];
  }
}

// ========================
// 视图层（View Layer）
// ========================

// composables/useProductList.ts
export function useProductList() {
  const productService = useProductService();
  const products = ref<Product[]>([]);
  const loading = ref(false);
  const error = ref<string | null>(null);
  const pagination = ref({ page: 1, pageSize: 20, total: 0 });

  async function loadProducts(params?: ProductQueryParams) {
    loading.value = true;
    error.value = null;
    try {
      const result = await productService.getProductList(params);
      products.value = result.items;
      pagination.value = {
        page: result.page,
        pageSize: result.pageSize,
        total: result.total,
      };
    } catch (e) {
      error.value = e instanceof Error ? e.message : '加载失败';
    } finally {
      loading.value = false;
    }
  }

  return { products, loading, error, pagination, loadProducts };
}

// components/ProductList.vue
<template>
  <div class="product-list">
    <div v-if="loading" class="loading">加载中...</div>
    <div v-else-if="error" class="error">{{ error }}</div>
    <template v-else>
      <ProductCard
        v-for="product in products"
        :key="product.id"
        :product="product"
      />
      <Pagination v-bind="pagination" @change="loadProducts" />
    </template>
  </div>
</template>

<script setup lang="ts">
import { onMounted } from 'vue';
import { useProductList } from '@/composables/useProductList';

const { products, loading, error, pagination, loadProducts } = useProductList();

onMounted(() => {
  loadProducts();
});
</script>
```

### 3.2 ADR 模板与实战示例

```markdown
# ADR-003: 选择 Zustand 而非 Redux Toolkit 作为状态管理方案

## 状态
已接受

## 上下文
- 项目为中型 React 电商后台管理系统，预计 50+ 页面
- 团队共 5 名前端，其中 3 人对 Redux 有经验但认为其模板代码过多
- 需要的状态管理功能：全局用户信息、购物车、主题设置
- 不需要 Redux 中间件生态（如 redux-saga），因为已有 React Query 处理服务端状态
- 技术栈：React 18 + TypeScript + Rspack

## 决策
选择 **Zustand** 作为全局状态管理方案，理由如下：
1. API 极简：一个 `create` 函数即可创建 store，无需 Provider、Reducer、Action Creator
2. 体积小：gzip 后约 1KB，Redux Toolkit 约 11KB
3. TypeScript 原生支持：类型推导完善，无需额外类型声明
4. 与 React Query 互补：Zustand 管理客户端状态，React Query 管理服务端状态
5. 支持订阅切片：`useStore(state => state.count)` 精准订阅，避免不必要的重渲染

## 后果
### 正面影响
- 开发效率提升约 30%（减少模板代码）
- Bundle 体积减少约 10KB
- 新成员上手时间从 2 天缩短到半天

### 负面影响
- 社区生态不如 Redux 丰富（中间件、DevTools 集成）
- 团队需要学习新的 API（但学习成本低）
- 如果未来需要复杂的状态管理（如 undo/redo），可能需要引入额外工具

### 缓解措施
- 编写 Zustand 使用规范和最佳实践文档
- 对复杂场景（如 undo/redo）预留扩展方案（immer + zundo）
```

// 技术选型决策工具
interface TechnologyOption {
  name: string;
  scores: Record<string, number>; // 维度名 → 分数（1-10）
}

interface Dimension {
  name: string;
  weight: number; // 权重（0-1，总和为 1）
}

function evaluateTechnology(
  options: TechnologyOption[],
  dimensions: Dimension[]
) {
  return options.map((option) => {
    const details = dimensions.map((dim) => {
      const score = option.scores[dim.name] || 0;
      return {
        dimension: dim.name,
        weight: dim.weight,
        score,
        weightedScore: score * dim.weight,
      };
    });

    const totalScore = details.reduce((sum, d) => sum + d.weightedScore, 0);

    return {
      name: option.name,
      details,
      totalScore: Math.round(totalScore * 100) / 100,
    };
  }).sort((a, b) => b.totalScore - a.totalScore);
}

## 四、常见面试题

**Q1：请解释前端分层架构的设计思想，以及各层的职责。**

**答案要点**：
- 分层架构将前端应用分为数据层、业务逻辑层、视图层三层
- 数据层：负责 HTTP 请求、本地存储、缓存，只做数据获取和持久化
- 业务逻辑层：业务规则、数据校验、状态管理，不依赖 UI 框架
- 视图层：UI 渲染、用户交互，只负责展示和事件绑定
- 核心原则：依赖方向自上而下，每层只依赖其下层
- 好处：可测试、可替换、可维护、可复用

**Q2：什么是 ADR（架构决策记录）？它包含哪些要素？**

**答案要点**：
- ADR 是一种轻量级的架构决策文档化方法
- 五要素：标题（Title）、状态（Status）、上下文（Context）、决策（Decision）、后果（Consequences）
- 状态包括：提议、已接受、已废弃、已替代
- 上下文描述当前面临的问题和约束条件
- 决策描述具体选择了什么方案
- 后果描述正面和负面影响，以及缓解措施

**Q3：如何识别和管理技术债？**

**答案要点**：
- 识别信号：口头禅"后面再优化"、重复代码、超大组件文件、高耦合、新人上手慢
- 分级标准：L1 关键债（影响安全/稳定性）、L2 高优债（影响开发效率）、L3 中优债（影响可读性）、L4 低优债（风格问题）
- 管理方法：建立技术债登记表，明确级别、影响范围、预估工时、偿还计划
- 偿还策略：童子军规则、每个迭代预留 20% 时间、L1 立即偿还、L2 本迭代偿还

**Q4：依赖倒置原则在前端分层架构中如何应用？**

**答案要点**：
- 定义抽象接口（如 IUserRepository），业务逻辑层依赖接口而非具体实现
- 数据层实现接口（如 HttpUserRepository、MockUserRepository）
- 通过依赖注入（DI）将具体实现注入业务逻辑层
- 好处：业务逻辑层不依赖具体的数据源，方便切换和测试
- 在前端中，可以通过 provide/inject（Vue）或 Context（React）实现简单的 DI

**Q5：请描述一个完整的技术选型流程，包含评估维度、权重设定和决策方法。**

**答案要点**：
- 明确需求：列出当前项目的核心需求和非功能性需求
- 确定评估维度：学习成本、性能、TypeScript 支持、生态社区、团队熟悉度等
- 设定权重：根据项目实际情况为每个维度分配权重（总和为 1）
- 候选方案打分：每个候选方案在每个维度上打分（1-10 分）
- 加权计算：每个维度的分数乘以权重，求和得到总分
- 做出决策：选择总分最高的方案，同时考虑风险因素
- 编写 ADR：记录决策过程和理由

## 五、避坑指南

| 坑点 | 现象 | 原因 | 解决方案 |
|---|---|---|---|
| 分层过细导致过度抽象 | 一个简单的 CRUD 页面需要经过 5 层调用，开发效率极低 | 教条式地套用分层架构，不考虑项目实际规模 | 小项目可以简化分层（如只分 View + Hook）；分层架构适用于中大型项目 |
| 业务逻辑泄漏到视图层 | 组件中直接调用 API、处理业务校验、格式化数据 | 开发者为了快速完成功能，将所有逻辑写在组件中 | 严格遵守分层规范；Code Review 时重点检查视图层是否包含业务逻辑 |
| 技术选型追求"最新最好" | 引入不成熟的新技术，导致项目不稳定、团队成员学习成本高 | 技术选型时过于关注技术本身，忽略了团队能力和项目风险 | 使用五维度评估矩阵；优先选择团队熟悉的成熟技术；新技术先在小型项目中试点 |

## 六、现代前端渲染架构模式补充

> 传统的 SSR（服务端渲染）、CSR（客户端渲染）和 SSG（静态站点生成）各有优劣，但都面临一个共同挑战：**如何在交互性和性能之间取得平衡**。Island Architecture 和 Partial Hydration / Resumability 是两种更细粒度的解决方案，它们通过"选择性水合"策略，让页面既保持接近静态内容的首屏性能，又具备交互组件的动态能力。

### 6.1 Island Architecture（Astro）

**Island Architecture**（岛屿架构）由 Astro 框架推广，其核心思想是：将页面视为由**静态内容**（Non-interactive）和**交互岛屿**（Islands of Interactivity）组成。静态内容在服务端渲染后直接输出 HTML，不包含任何 JavaScript；交互岛屿是页面中需要交互的独立组件，各自独立加载和水合。

```
┌─────────────────────────────────────────────────┐
│              静态 HTML 内容（无 JS）               │
│  ┌──────────────────────┐                       │
│  │  交互岛屿 A（React）   │  ← 独立水合，不依赖其他岛屿  │
│  │  <Cart client:load /> │                       │
│  └──────────────────────┘                       │
│              静态 HTML 内容（无 JS）               │
│  ┌──────────────┐  ┌──────────────────┐         │
│  │ 岛屿 B (Vue)  │  │ 岛屿 C (Svelte)   │        │
│  │ client:idle  │  │ client:visible   │        │
│  └──────────────┘  └──────────────────┘         │
│              静态 HTML 内容（无 JS）               │
└─────────────────────────────────────────────────┘
```

#### Astro 岛屿架构示例

```astro
---
// 页面逻辑在服务端执行，零 JS 输出到客户端
import Header from '../components/Header.astro';
import StaticContent from '../components/StaticContent.astro';
import SearchBar from '../components/SearchBar.jsx';
import ShoppingCart from '../components/ShoppingCart.vue';
import AnalyticsChart from '../components/AnalyticsChart.svelte';
---

<!-- 静态组件：不输出任何 JS，直接渲染为 HTML -->
<Header />
<StaticContent />

<!-- 交互岛屿：根据 client:* 指令控制水合时机 -->
<!-- client:load：页面加载后立即水合（最高优先级） -->
<SearchBar client:load />

<!-- client:idle：浏览器空闲时水合（低优先级） -->
<ShoppingCart client:idle />

<!-- client:visible：组件进入视口时才水合（按需加载） -->
<AnalyticsChart client:visible />

<!-- client:media：匹配媒体查询时才水合 -->
<MobileMenu client:media="(max-width: 768px)" />

<!-- client:only：跳过 SSR，仅在客户端渲染 -->
<ThirdPartyWidget client:only="react" />
```

#### 岛屿架构的核心原理

```typescript
// 岛屿架构的核心概念：部分水合（Partial Hydration）
// 与传统的整页水合对比：

// ========== 传统 SSR 水合（整页水合）==========
// 服务端渲染完整 HTML
// → 客户端加载整个应用的 JS bundle
// → 对整棵 DOM 树执行水合（hydrate）
// → 所有组件变为可交互
// 问题：即使只有 10% 的组件需要交互，也要加载 100% 的 JS 并水合所有节点

// ========== 岛屿架构水合（部分水合）==========
// 服务端渲染完整 HTML
// → 仅加载交互岛屿组件的 JS
// → 仅对岛屿组件执行水合
// → 其余 90% 的静态内容保持 HTML 零 JS
// 优势：JS 体积大幅减少，TBT（Total Blocking Time）显著降低

// 岛屿架构的水合策略
type HydrationStrategy =
  | 'load'      // 立即水合
  | 'idle'      // requestIdleCallback 时水合
  | 'visible'   // IntersectionObserver 进入视口时水合
  | 'media'     // matchMedia 匹配时水合
  | 'only';     // 仅在客户端渲染
```

#### 岛屿架构的适用场景

| 场景 | 适合岛屿架构 | 原因 |
|---|---|---|
| 内容型网站（博客、文档站） | 非常适合 | 90%+ 内容是静态的，仅少量交互组件 |
| 电商网站（商品列表、详情页） | 非常适合 | 列表静态渲染，购物车、搜索为交互岛屿 |
| 企业官网（Landing Page） | 非常适合 | 大部分内容静态，联系方式表单为交互岛屿 |
| 复杂 SaaS 后台管理系统 | 不太适合 | 几乎每个组件都需要交互，岛屿架构优势不明显 |
| 实时协作应用（在线文档） | 不适合 | 全页面高度交互，部分水合没有意义 |

### 6.2 Partial Hydration / Resumability（Qwik）

**Qwik** 提出了一个比岛屿架构更激进的概念：**Resumability（可恢复性）**。与传统的 Hydration（水合）不同，Qwik 不在客户端重新执行组件代码来重建状态，而是将应用的**状态和执行上下文序列化到 HTML 中**，客户端只需要"恢复"执行，无需"重放"。

#### Hydration vs Resumability

```
传统 Hydration（React、Vue SSR）：
  SSR 生成 HTML → 客户端下载 JS Bundle → 重新执行组件代码 → 绑定事件监听器 → 重建组件状态 → 页面可交互
  问题：下载的 JS 包含所有组件代码，即使大部分不需要交互；"重放"过程消耗 CPU 时间

Resumability（Qwik）：
  SSR 生成 HTML + 序列化状态 → 客户端仅下载交互需要的 JS → 从序列化状态恢复 → 直接可交互
  优势：不需要"重放"；JS 按需加载（仅加载用户交互触发的代码）；接近零 JS 启动
```

#### Qwik 核心概念

```tsx
// ========== Qwik 组件示例 ==========
import { component$, useSignal, $ } from '@builder.io/qwik';

// component$ 中的 $ 后缀表示这是一个可序列化的组件边界
// Qwik 编译器会将组件拆分为多个可延迟加载的 chunk
export const Counter = component$(() => {
  // useSignal 创建响应式状态，状态会被序列化到 HTML
  const count = useSignal(0);

  // $() 创建可序列化的事件处理函数
  // 这个函数会被提取为独立的 JS chunk，仅在用户点击时加载
  const increment = $(() => {
    count.value++;
  });

  return (
    <div>
      <p>计数: {count.value}</p>
      <button onClick$={increment}>+1</button>
      {/* onClick$ 中的 $ 表示事件处理函数是懒加载的 */}
    </div>
  );
});

// ========== Qwik 序列化输出示例 ==========
// 服务端渲染的 HTML 片段：
// <div q:container="...">
//   <p>计数: <!--qv q:id=0-->0<!--/qv--></p>
//   <button on:click="./chunk-abc.js#increment">+1</button>
// </div>
// <script type="qwik/json">
//   {"state": {"count": 0}}
// </script>
//
// 关键点：
// 1. 组件状态序列化为 JSON 嵌入 HTML
// 2. 事件处理函数映射到独立的 JS chunk URL
// 3. 用户点击按钮时，浏览器才下载 ./chunk-abc.js
// 4. 无需重新执行组件代码，直接从 JSON 恢复状态
```

#### Qwik 的延迟加载策略

```typescript
// ========== Qwik 的细粒度代码拆分 ==========
// Qwik 通过 $ 后缀自动将代码拆分为多个小块：

// 1. 组件级拆分
export const Header = component$(/* 独立 chunk */);
export const Footer = component$(/* 独立 chunk */);

// 2. 事件处理函数拆分
const handleClick = $(/* 独立 chunk，仅在点击时加载 */);

// 3. 任务拆分
import { useVisibleTask$ } from '@builder.io/qwik';
useVisibleTask$((/* 独立 chunk，仅在组件可见时加载 */) => {
  // 仅在组件进入视口时执行
});

// 4. 数据加载拆分
import { routeLoader$ } from '@builder.io/qwik-city';
export const useProductData = routeLoader$((/* 独立 chunk */) => {
  // 仅在此路由被访问时加载和执行
});

// ========== 预加载策略 ==========
// Qwik 提供了 Service Worker 级别的预加载：
// 当用户鼠标悬停按钮时，Qwik 的预加载机制会提前下载对应的 JS chunk
// 用户点击时，JS 已经在缓存中，实现了几乎零延迟的交互响应
```

#### Qwik 与 Island Architecture 的对比

| 维度 | Island Architecture（Astro） | Resumability（Qwik） |
|---|---|---|
| 核心理念 | 页面由静态内容 + 交互岛屿组成 | 序列化组件状态，客户端恢复执行 |
| 静态内容 | 零 JS，纯 HTML | 零 JS，纯 HTML（但包含序列化状态） |
| 交互组件 | 独立水合，框架无关（React/Vue/Svelte） | Qwik 专属组件，状态已序列化 |
| JS 加载 | 按岛屿加载完整组件代码 | 按交互事件加载最小 JS chunk |
| 水合过程 | 需要水合（重建事件监听） | 无需水合（状态已序列化，直接恢复） |
| 框架支持 | 多框架（React/Vue/Svelte/Solid） | 仅 Qwik |
| 学习曲线 | 低（接近传统 SSR 开发） | 高（$ 后缀、序列化约束等新概念） |
| 适用场景 | 内容型网站、电商、企业官网 | 对性能极致追求的场景、电商、移动端 |

### 6.3 与 SSR/CSR/SSG 的对比

```typescript
// ========== 五种渲染策略对比 ==========

// 1. CSR（客户端渲染）
// 特点：空白 HTML → 下载 JS → 渲染页面
// 首屏：慢（白屏时间长）
// SEO：差（搜索引擎难以抓取）
// 交互：快（客户端路由，无刷新）
// 适用：后台管理系统、需要登录的应用

// 2. SSR（服务端渲染）
// 特点：服务端生成 HTML → 客户端下载 → 水合
// 首屏：快（直接返回 HTML）
// SEO：好（搜索引擎可直接解析）
// 交互：中等（需等待水合完成）
// 适用：电商、内容平台、需要 SEO 的应用

// 3. SSG（静态站点生成）
// 特点：构建时生成 HTML → 部署为静态文件
// 首屏：最快（CDN 直接返回静态文件）
// SEO：最好
// 交互：中等（同 SSR 需要水合）
// 适用：博客、文档站、企业官网

// 4. Island Architecture（岛屿架构）
// 特点：SSG/SSR 生成静态 HTML + 独立交互岛屿
// 首屏：接近 SSG（大部分内容零 JS）
// SEO：好
// 交互：好（仅交互岛屿加载 JS，其余零开销）
// 适用：内容型网站、电商、企业官网

// 5. Resumability（可恢复性）
// 特点：SSR 生成 HTML + 序列化状态 → 客户端恢复
// 首屏：接近 SSG（启动时几乎不加载 JS）
// SEO：好
// 交互：最快（无需水合，直接从序列化状态恢复）
// 适用：对性能极致追求的场景、电商、移动端
```

#### 五者对比总表

| 维度 | CSR | SSR | SSG | Island Architecture | Resumability |
|---|---|---|---|---|---|
| **首屏速度** | 慢 | 快 | 最快 | 接近 SSG | 接近 SSG |
| **SEO 友好** | 差 | 好 | 最好 | 好 | 好 |
| **TTI（可交互时间）** | 较慢 | 中等 | 中等 | 快 | 最快 |
| **JS 体积** | 全部 | 全部 | 全部 | 仅交互岛屿 | 按需最小化 |
| **服务端负载** | 无 | 高（每次请求） | 无（构建时） | 中等 | 中等 |
| **构建复杂度** | 低 | 中等 | 中等 | 中等 | 高 |
| **动态内容** | 支持 | 支持 | 需重新构建或 ISR | 支持 | 支持 |
| **框架限制** | 任意 | 任意 | 任意 | 多框架 | 仅 Qwik |
| **学习曲线** | 低 | 中等 | 中等 | 低 | 高 |
| **典型框架** | CRA、Vite | Next.js、Nuxt | Next.js、Gatsby | Astro | Qwik |

### 6.4 避坑指南

| 常见错误 | 现象 | 原因 | 解决方案 |
|---------|------|------|---------|
| 用岛屿架构构建高度交互的 SaaS 应用 | 页面交互响应慢，组件间通信困难 | 岛屿之间共享状态需要额外机制，大部分组件都需要交互 | SaaS 应用使用 SSR/CSR 混合（如 Next.js App Router），岛屿架构适合内容型网站 |
| 在 Astro 中导入含副作用的第三方库 | 构建失败或运行时错误 | Astro 岛屿组件在服务端和客户端执行环境不同 | 使用 `client:only` 指令跳过 SSR，或使用条件判断 `import.meta.env.SSR` |
| Qwik 中忘记使用 `$()` 包装函数 | 闭包序列化错误或 JS 体积膨胀 | Qwik 通过 `$()` 标记函数边界，未标记的函数无法被正确拆分 | 所有事件处理函数、异步任务必须使用 `$()` 包装 |
| 混淆 Islands 和传统 SPA 路由 | 页面切换时岛屿状态丢失 | Astro 默认是 MPA 模式，每次导航会重新加载页面 | 使用 Astro 的 View Transitions 或 SPA 模式（`transition:persist`）保持岛屿状态 |
| 过度使用 `client:load` 指令 | 首屏 JS 体积过大，加载变慢 | 所有岛屿都立即水合，失去了岛屿架构的优势 | 根据交互优先级选择合适的水合策略：`idle`、`visible` 或 `media` |
