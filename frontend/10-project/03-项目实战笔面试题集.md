### 1. ★ 企业后台管理系统中，RBAC 权限模型的核心思想是什么？

A. 用户直接关联权限，通过权限列表控制访问
B. 用户通过角色间接关联权限，用户-角色-权限三层模型
C. 用户通过部门关联权限，同一部门拥有相同权限
D. 用户通过菜单关联权限，有菜单就有权限

**答案：B**

**解析**：RBAC（Role-Based Access Control）的核心思想是用户不直接关联权限，而是通过角色间接关联。用户属于某个角色，角色拥有若干权限，用户最终权限 = 所有角色权限的并集。A 选项描述的是 ACL（访问控制列表），C 选项描述的是基于部门的权限控制，D 选项混淆了菜单和权限的概念。

### 2. ★ 在电商平台中，商品 SKU 和商品的关系是什么？

A. 一对一关系，一个商品只有一个 SKU
B. 一对多关系，一个商品可以有多个 SKU（如不同颜色/尺寸）
C. 多对多关系，一个 SKU 可以属于多个商品
D. 无关系，SKU 和商品是独立的两个实体

**答案：B**

**解析**：商品和 SKU 是一对多关系。一个商品（如 iPhone 15）可以有多个 SKU（如 128G 黑色、256G 白色、512G 蓝色），每个 SKU 有独立的库存、价格和规格描述。SKU（Stock Keeping Unit）是库存管理的最小粒度。

### 3. ★★ 关于 Vue 3 中动态路由的实现，以下说法正确的是？

A. 动态路由只能在 `router/index.ts` 中预先定义所有路由
B. 使用 `router.addRoute()` 可以在运行时动态注册路由
C. 动态路由注册后，刷新页面会自动保留
D. 动态路由不需要权限过滤，所有用户看到的都一样

**答案：B**

**解析**：`router.addRoute()` 是 Vue Router 4 提供的动态注册路由的方法。在企业后台管理系统中，登录后根据用户权限列表，通过 `filterAsyncRoutes` 过滤动态路由表，再调用 `router.addRoute()` 注册。刷新页面后需要重新获取用户信息和权限，重新注册路由。选项 C 错误，因为刷新后路由状态会丢失，需要重新注册。

### 4. ★★ 在电商平台中，为了防止超卖，以下哪种方案最适合高并发场景？

A. 在应用层使用 `synchronized` 关键字锁定库存扣减方法
B. 使用 Redis Lua 脚本原子扣减库存 + 数据库乐观锁
C. 直接在数据库中使用 `SELECT ... FOR UPDATE` 行锁
D. 增加库存数量，多备一些货避免超卖

**答案：B**

**解析**：Redis Lua 脚本保证 Redis 层面的原子性，数据库乐观锁（`WHERE stock >= quantity`）保证数据最终一致性，两者结合是电商高并发场景的最佳实践。A 选项的 `synchronized` 是 Java 单机锁，分布式环境下无效；C 选项的行锁在高并发下性能很差；D 选项是业务层面的妥协，不是技术方案。

### 5. ★★ 企业后台管理系统中，Token 刷新时多个请求同时返回 401，正确的处理方式是？

A. 每个请求独立刷新 Token，互不影响
B. 使用 `isRefreshing` 标记 + `pendingRequests` 队列，只刷新一次
C. 直接跳转登录页，让用户重新登录
D. 忽略 401 错误，继续使用旧的 Token

**答案：B**

**解析**：多个请求同时 401 时，如果每个都独立刷新 Token，会导致多次刷新请求，可能造成 Token 混乱（后面的刷新使前面的 Token 失效）。正确做法是使用 `isRefreshing` 标记判断是否正在刷新，将后续请求放入 `pendingRequests` 队列，刷新完成后统一重试。A 会导致多次刷新，C 用户体验差，D 会导致请求失败。

### 6. ★★ 关于电商平台 BFF 层的作用，以下说法错误的是？

A. BFF 层可以聚合多个后端接口，减少前端请求次数
B. BFF 层可以针对不同客户端（PC/Mobile）返回不同粒度的数据
C. BFF 层替代了数据库，直接存储业务数据
D. BFF 层可以统一处理鉴权、限流和缓存

**答案：C**

**解析**：BFF（Backend For Frontend）层是位于前端和后端之间的中间层，不替代数据库。它负责接口聚合、数据裁剪、鉴权统一、缓存加速等，但业务数据仍然存储在 MySQL/Redis 等数据库中。BFF 层通常是无状态的，不存储持久化业务数据。

### 7. ★★★ 在电商平台中，关于支付回调的幂等性处理，以下方案最佳的是？

A. 在回调处理函数中不做任何幂等检查，直接更新订单状态
B. 使用 `synchronized` 关键字锁定回调处理方法

## 二、简答题（8 题）

### 1. ★★ 企业后台管理系统中，RBAC 权限控制的三级体系是什么？请分别说明。

**答案要点**：

**三级权限控制体系**：

1. **菜单权限（路由级）**：控制用户能看到哪些菜单和页面。通过前端维护完整路由表，登录后根据后端返回的权限码过滤路由，使用 `router.addRoute()` 动态注册。路由守卫 `beforeEach` 在每次导航时检查权限。

2. **按钮权限（元素级）**：控制页面内按钮的可见性。通过自定义指令 `v-permission` 实现，在 `mounted` 阶段检查用户权限码，无权限则从 DOM 中移除元素。权限码命名规范：`模块:操作`（如 `user:add`、`role:delete`）。

3. **接口权限（请求级）**：后端中间件/拦截器校验 API 权限。前端只做 UI 层面的展示控制，真正的安全校验必须在后端完成。前端代码运行在浏览器中，可以被用户修改，因此后端接口权限是安全的最后一道防线。

> 📖 **参考链接**：
> - [OWASP - Access Control](https://owasp.org/www-community/Access_Control)
> - [MDN - Web 安全](https://developer.mozilla.org/zh-CN/docs/Web/Security)

### 2. ★★ 电商平台中，购物车在未登录和登录状态下分别如何处理？登录后如何合并？

**答案要点**：

**未登录状态**：购物车数据存储在浏览器的 `localStorage` 中（key 如 `guest_cart`），包含 SKU ID、数量、选中状态等信息。每次操作购物车时直接读写 `localStorage`。

**登录状态**：购物车数据存储在服务端（MySQL），通过 API 进行增删改查。用户在任何设备登录都能看到相同的购物车数据。

**登录后合并**：
1. 登录成功后，首先读取 `localStorage` 中的本地购物车数据
2. 将本地购物车数据通过 API 批量同步到服务端
3. 合并规则：相同 SKU 的商品，数量取最大值（或累加，取决于业务规则）
4. 合并完成后，清除 `localStorage` 中的 `guest_cart`
5. 从服务端重新加载完整的购物车数据

**注意**：合并时需要考虑并发问题，如果用户在多个设备同时操作，可能出现数据覆盖。

> 📖 **参考链接**：
> - [MDN - Web Storage API](https://developer.mozilla.org/zh-CN/docs/Web/API/Web_Storage_API)
> - [MDN - Window.localStorage](https://developer.mozilla.org/zh-CN/docs/Web/API/Window/localStorage)

### 3. ★★★ 电商平台中，如何通过 Redis 和数据库的配合实现防超卖？请描述完整流程。

**答案要点**：

**多层防护架构**：

1. **Redis 预减库存（第一层）**：
   - 商品上架时，将库存同步到 Redis：`SET stock:sku:{id} {stock}`
   - 下单时使用 Lua 脚本原子扣减：先 GET 检查库存，再 DECRBY 扣减
   - 扣减失败直接返回"库存不足"，不进入后续流程

2. **数据库乐观锁（第二层）**：
   - 创建订单时，使用 `UPDATE product_skus SET stock = stock - ? WHERE id = ? AND stock >= ?`
   - 如果 `affected rows = 0`，说明库存不足或已被其他事务修改，回滚 Redis 库存

3. **消息队列削峰（第三层）**：
   - 秒杀等高并发场景，将下单请求放入消息队列
   - 后端消费者异步处理，避免数据库压力过大

4. **定时对账**：
   - 定时任务对比 Redis 和数据库的库存数据
   - 发现不一致时以数据库为准进行修复

**关键代码逻辑**：
```
下单流程：Redis 预减 → 创建订单（事务 + 乐观锁）→ 失败回滚 Redis
取消流程：Redis 恢复 → 更新订单状态 → 数据库恢复库存
```

> - [Redis 官方文档](https://redis.io/docs/)
> - [MySQL 官方文档 - InnoDB 事务模型](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-model.html)

### 4. ★★ 企业后台管理系统中，Axios 拦截器如何实现 Token 刷新？请描述核心逻辑。

**答案要点**：

**核心机制**：双 Token 模式（accessToken 短期有效 + refreshToken 长期有效）+ 并发请求队列。

**实现步骤**：

1. **请求拦截器**：每次请求前从 `localStorage` 读取 `accessToken`，添加到请求头 `Authorization: Bearer {token}`。

2. **响应拦截器**：捕获 401 状态码，触发 Token 刷新流程。

3. **Token 刷新流程**：
   - 检查是否有 `refreshToken`，没有则直接跳转登录页
   - 使用 `isRefreshing` 标记防止并发刷新
   - 正在刷新时，将后续失败的请求放入 `pendingRequests` 队列
   - 刷新成功后，更新 `localStorage` 中的 `accessToken`，遍历队列重试所有请求
   - 刷新失败，清除所有 Token 和用户状态，跳转登录页

4. **并发处理**：`isRefreshing` + `pendingRequests` 队列确保多个 401 请求只触发一次 Token 刷新，刷新完成后统一重试。

> 📖 **参考链接**：
> - [MDN - Fetch API](https://developer.mozilla.org/zh-CN/docs/Web/API/Fetch_API)
> - [MDN - HTTP 状态码 401 Unauthorized](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Status/401)

### 5. ★★★ 电商平台的订单状态机包含哪些状态？请描述完整的状态转移流程。

**答案要点**：

**7 种订单状态**：

| 状态 | 值 | 说明 |
|------|---|------|
| 待支付 | 0 | 订单已创建，等待用户支付 |
| 已支付 | 1 | 支付成功，等待商家发货 |
| 已发货 | 2 | 商家已发货，等待用户确认收货 |
| 已完成 | 3 | 用户确认收货，订单完成 |
| 已取消 | 4 | 订单已取消（超时或用户取消） |
| 退款中 | 5 | 用户申请退款/售后，等待审核 |
| 已退款 | 6 | 退款审核通过，已退款 |

**状态转移规则**：
- 待支付 → 已支付（用户支付成功）
- 待支付 → 已取消（超时未支付 / 用户主动取消）
- 已支付 → 已发货（商家发货）
- 已支付 → 已取消（商家取消订单）
- 已发货 → 已完成（用户确认收货）
- 已发货 → 退款中（用户申请退款）
- 已完成 → 退款中（用户申请售后）
- 退款中 → 已退款（退款审核通过）
- 退款中 → 已完成（退款审核拒绝）

**实现要点**：使用 `transitions` 映射表定义合法转移，乐观锁 `WHERE status = oldStatus` 防止并发，状态变更副作用在事务中处理。

### 6. ★★ 请对比 Vue 3 中 Pinia 和 Vuex 的区别，并说明 Pinia 的优势。

**答案要点**：

| 对比维度 | Vuex 4 | Pinia |
|---------|--------|-------|
| mutations | 必须通过 commit mutations 修改 state | 去掉 mutations，直接修改 state |

| 模块化 | 嵌套模块，需要 namespace | 独立 store，扁平化管理 |

| 代码量 | 模板代码较多 | 代码更简洁 |
| 体积 | 较大 | 更轻量 |
| DevTools | 支持 | 支持，且更好 |

**Pinia 核心优势**：
- 去掉了冗余的 mutations 概念
- 完整的 TypeScript 类型推断
- 扁平化的 store 管理，无需嵌套模块和命名空间
- 同时支持 Options API 和 Setup Store 两种写法

### 8. ★★★ 电商平台中，BFF 层如何进行缓存策略设计？请描述缓存穿透、击穿、雪崩的防护方案。

**答案要点**：

**缓存策略**：

| 场景 | Key 设计 | TTL | 更新策略 |
|------|---------|-----|---------|
| 商品详情 | `product:detail:{id}` | 10min | 更新时删除缓存 |
| 商品列表 | `product:list:{hash}` | 5min | 定时刷新 |
| 用户购物车 | `cart:user:{id}` | 7天 | 实时更新 |

**三大问题防护**：

1. **缓存穿透**（查询不存在的数据）：
   - 布隆过滤器：在查询前判断 key 是否存在
   - 空值缓存：对不存在的 key 也缓存空值（TTL 较短，如 60s）

2. **缓存击穿**（热点 key 过期，大量请求打到数据库）：
   - 互斥锁：使用 Redis `SET key NX EX` 获取锁，只有获取锁的线程查询数据库
   - 逻辑过期：缓存值中存储逻辑过期时间，物理不过期，后台异步刷新

3. **缓存雪崩**（大量 key 同时过期）：
   - TTL 加随机值：`TTL = base + random(0, 60)`
   - 多级缓存：本地缓存 + Redis + 数据库
   - 限流降级：Nginx 或 BFF 层限流，保护数据库

> 📖 **参考链接**：
> - [Redis 官方文档](https://redis.io/docs/)
> - [Redis 官方命令参考](https://redis.io/commands/)

## 三、场景设计题（5 题）

### 1. ★★★ 设计一个支持高并发的秒杀系统

**设计思路**：

**全链路架构**：

```
客户端 → CDN（静态页面） → Nginx（限流 + 验证码）
  → BFF（Redis 预减库存） → 消息队列（削峰）
  → 消费者（创建订单 + 数据库扣减） → 返回结果
```

**各层设计**：

1. **前端层**：
   - 秒杀按钮置灰 + 倒计时，防止用户重复点击
   - 静态页面 CDN 缓存，减少服务器压力
   - 提交时携带验证码或 token，防止脚本攻击

2. **网关层（Nginx）**：
   - `limit_req` 限制单 IP 请求频率
   - 验证码校验，过滤机器人
   - 动态扩容，根据流量自动增加实例

3. **BFF 层**：
   - Redis Lua 脚本预减库存（原子操作）
   - 库存不足直接返回，不进入后续流程
   - 分布式锁控制单用户只能抢一次

4. **消息队列层**：
   - 扣减成功的请求发送到消息队列
   - 消费者异步创建订单、扣减数据库库存
   - 前端轮询或 WebSocket 推送秒杀结果

5. **数据层**：
   - 数据库读写分离
   - 订单表按用户 ID 分片
   - 热点数据全部在 Redis 中

**关键指标**：预估 QPS = 总库存 / 秒杀时长，根据预估设计各层容量。

### 2. ★★ 设计一个通用表单组件，支持动态字段、联动校验和草稿保存

**设计思路**：

**组件 Props**：
- `formItems`：字段配置数组（type、label、key、required、rules、options、placeholder）
- `model`：表单数据对象
- `rules`：校验规则
- `mode`：模式（create / edit / view）

**联动校验**：
- 使用 `watch` 监听字段变化，动态修改其他字段的 `rules`、`disabled`、`options`
- 支持声明式联动规则（如 `effects: { individual: { hide: ['invoiceGroup'] } }`）
- 复杂场景使用联动规则引擎，通过 `addRule` 注册，`evaluate` 计算

**草稿保存**：
- 使用 `useDebounceFn` 防抖自动保存（2 秒）
- 保存到 `localStorage`，包含数据和保存时间戳
- 7 天过期自动清理
- 组件挂载时提示用户是否恢复草稿

**性能优化**：
- 超大规模表单（200+ 字段）使用分步/分页渲染
- 使用 `shallowRef` 减少深层响应式开销
- 非当前步骤组件使用 `KeepAlive` 缓存

### 3. ★★★ 设计一个电商平台的微服务拆分方案

**设计思路**：

**服务拆分**：

| 微服务 | 职责 | 数据库 |
|--------|------|--------|
| 用户服务 | 注册登录、用户信息、收货地址 | user_db |
| 商品服务 | 商品管理、分类、SKU、搜索 | product_db |
| 订单服务 | 订单创建、状态管理、退款 | order_db |
| 购物车服务 | 购物车增删改查、合并 | cart_db（也可合并到订单服务） |
| 支付服务 | 支付对接、回调处理、对账 | payment_db |
| 营销服务 | 优惠券、满减、秒杀 | marketing_db |

**服务间通信**：
- 同步调用：HTTP REST 或 gRPC
- 异步消息：消息队列（Kafka/RabbitMQ）用于订单状态变更通知、库存同步等
- 分布式事务：使用 Saga 模式或 TCC 模式处理跨服务事务

**BFF 层**：
- 每个前端端（PC/Mobile）对应一个 BFF 实例
- BFF 负责聚合多个微服务的数据
- 服务发现使用 Consul 或 Nacos

**关键挑战**：
- 数据一致性：订单创建需要扣库存，跨服务事务用 Saga 补偿
- 服务降级：某个服务故障时，BFF 返回降级数据
- 链路追踪：使用 Jaeger/Zipkin 追踪跨服务调用

### 4. ★★ 设计一个企业后台管理系统的权限管理方案

**设计思路**：

**RBAC 模型**：
```
用户（User） --N:M--> 角色（Role） --N:M--> 权限（Permission）
```

**三级权限控制**：

1. **路由级权限**：
   - 前端维护完整路由表，`meta.permission` 标注权限码
   - 登录后根据后端返回的权限列表过滤路由
   - `router.addRoute()` 动态注册

2. **按钮级权限**：
   - 自定义 `v-permission` 指令
   - `mounted` 阶段检查权限，无权限移除 DOM

3. **接口级权限**：
   - 后端中间件校验 JWT + 权限码
   - 前端只做 UI 控制，后端做安全校验

**数据表设计**：
- `users`（用户表）、`roles`（角色表）、`permissions`（权限表）
- `user_roles`（用户-角色关联表）、`role_permissions`（角色-权限关联表）

**权限码命名规范**：`模块:操作`，如 `user:add`、`order:export`、`system:setting`

**前端实现**：
- 路由守卫 `beforeEach` 检查权限
- `v-permission` 指令控制按钮显隐
- `usePermission` composable 提供权限检查方法

> 📖 **参考链接**：
> - [OWASP - Access Control](https://owasp.org/www-community/Access_Control)
> - [Vue Router - 动态路由匹配](https://router.vuejs.org/guide/essentials/dynamic-matching.html)

### 5. ★★★ 设计一个支持多端（PC、Mobile、小程序）的电商 BFF 架构

**设计思路**：

**BFF 分层架构**：

```
客户端层：
  PC Web BFF ─── Mobile H5 BFF ─── 小程序 BFF
      │               │               │
      └───────────────┼───────────────┘
                      │
              服务聚合层（Service Aggregator）
                      │
      ┌───────────────┼───────────────┐
      │               │               │
   商品服务        订单服务        用户服务
```

**核心设计**：

1. **按端拆分 BFF**：
   - 每个客户端（PC/Mobile/小程序）对应独立的 BFF 实例
   - 各 BFF 根据客户端特点做数据裁剪和格式转换
   - PC BFF 返回完整字段，Mobile BFF 只返回必要字段

2. **接口聚合**：
   - 商品详情页 = 商品服务（商品信息）+ 评价服务（评价列表）+ 推荐服务（推荐商品）
   - BFF 层并行请求多个微服务，聚合结果后返回

3. **数据裁剪**：
   - PC 端返回高清图片、完整描述
   - Mobile 端返回压缩图片、精简描述
   - 小程序端返回适配格式

4. **公共能力**：
   - 统一鉴权中间件（JWT）
   - 统一限流（令牌桶）
   - 统一缓存（Redis）
   - 统一日志和监控

5. **降级策略**：
   - 推荐服务故障时，返回热门商品兜底
   - 评价服务故障时，只返回商品基本信息
   - 缓存命中时，直接返回缓存数据

**技术选型**：
- BFF 框架：Express/Koa（Node.js）
- 服务发现：Consul
- API 网关：Nginx/Kong
- 监控：Prometheus + Grafana

> 📖 **参考链接**：
> - [Node.js 官方介绍 - 关于 Node.js](https://nodejs.org/zh-cn/about/)
> - [Express 官方网站](https://expressjs.com/)
