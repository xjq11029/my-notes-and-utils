### 1. RBAC 权限模型的核心思想

| 维度 | 内容 |
|------|------|
| 是什么 | RBAC（Role-Based Access Control）核心思想是用户不直接关联权限，而是通过角色间接关联，用户最终权限等于所有角色权限的并集。 |
| 能做什么 | 区分 RBAC 与 ACL、基于部门权限控制等不同模型。 |
| 怎么用 | 数据库设计：users → user_roles（关联表）→ roles → role_permissions（关联表）→ permissions。 |
| 原理和工作流程 | 用户属于某个角色，角色拥有若干权限。前端通过权限码过滤路由和按钮，后端通过中间件校验接口权限。 |
| 缺点 | 角色层级复杂时，权限继承关系需要仔细设计。 |

### 2. 商品 SKU 和商品的关系

| 维度 | 内容 |
|------|------|
| 是什么 | 商品和 SKU 是一对多关系，一个商品可以有多个 SKU（不同颜色/尺寸/规格），每个 SKU 有独立的库存和价格。 |
| 能做什么 | 区分商品展示层和库存管理层，SKU 是库存管理的最小粒度。 |
| 怎么用 | 数据库设计：`products` 表（商品基本信息）1:N `product_skus` 表（规格 + 库存 + 价格）。 |
| 原理和工作流程 | 商品列表展示商品维度的最低价格和总库存，商品详情展示各 SKU 的独立价格和库存，下单时按 SKU 扣减库存。 |
| 缺点 | 规格组合过多时 SKU 数量膨胀，需要合理控制规格维度。 |

### 3. Vue 3 中动态路由的实现

| 维度 | 内容 |
|------|------|
| 是什么 | `router.addRoute()` 是 Vue Router 4 提供的动态注册路由方法，结合权限过滤实现按角色展示不同菜单。 |
| 能做什么 | 实现不同角色看到不同的菜单和页面，用户无法通过 URL 访问无权限的页面。 |
| 怎么用 | `const accessedRoutes = filterAsyncRoutes(asyncRoutes, permissions); accessedRoutes.forEach(route => router.addRoute(route))`。 |
| 原理和工作流程 | 前端维护完整路由表，登录后根据权限码过滤，动态注册。刷新后需重新获取权限并注册路由。 |
| 缺点 | 刷新后路由状态丢失，需要重新注册；权限变更需要重新登录或刷新页面。 |

### 4. 防止超卖的最佳方案

| 维度 | 内容 |
|------|------|
| 是什么 | 多层防护：Redis Lua 脚本原子扣减库存 + 数据库乐观锁 + 消息队列异步下单，是电商高并发场景的最佳实践。 |
| 能做什么 | 确保高并发下库存扣减的原子性和一致性，防止超卖。 |
| 怎么用 | Redis：`eval` 执行 Lua 脚本 `GET + DECRBY`；数据库：`UPDATE ... WHERE stock >= quantity` 乐观锁。 |
| 原理和工作流程 | 下单时先在 Redis 原子扣减库存，扣减成功才进入下单流程；数据库最终扣减用乐观锁保证一致性。 |
| 缺点 | Redis 和数据库库存可能短暂不一致，需要定时对账。 |

### 5. Token 刷新时多个请求同时 401 的处理

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 `isRefreshing` 标记 + `pendingRequests` 队列，多个 401 请求只触发一次 Token 刷新，完成后统一重试。 |
| 能做什么 | 防止并发刷新导致 Token 混乱，提升用户体验。 |
| 怎么用 | 响应拦截器中检查 `isRefreshing`：为 true 时将请求放入队列；为 false 时执行刷新，完成后遍历队列重试。 |
| 原理和工作流程 | 第一个 401 请求触发刷新，后续 401 请求进入等待队列。刷新成功：更新 Token + 重试队列；刷新失败：清除状态 + 跳转登录。 |
| 缺点 | 队列中的请求如果刷新失败，需要统一处理错误。 |

### 6. BFF 层的作用

| 维度 | 内容 |
|------|------|
| 是什么 | BFF（Backend For Frontend）是位于前端和后端之间的中间层，负责接口聚合、数据裁剪、鉴权统一和缓存加速，不替代数据库。 |
| 能做什么 | 减少前端请求次数，降低前后端耦合，针对不同客户端返回不同粒度的数据。 |
| 怎么用 | Express/Koa 路由定义 API，中间件处理鉴权和缓存，Service 层封装业务逻辑。 |
| 原理和工作流程 | 前端请求 BFF，BFF 聚合多个后端服务数据，按需裁剪后返回。BFF 层通常是无状态的。 |
| 缺点 | 增加了系统复杂度，需要额外维护 BFF 层代码。 |

### 7. 支付回调的幂等性处理

| 维度 | 内容 |
|------|------|
| 是什么 | 根据第三方交易流水号 `trade_no` 判断是否已处理，配合 Redis 分布式锁防止并发重复处理。 |
| 能做什么 | 防止同一支付回调被多次处理导致重复发货或重复扣款。 |
| 怎么用 | 回调处理：验签 → 查 `trade_no` 是否已处理 → Redis 分布式锁（`SET key NX EX`）→ 事务更新订单和支付记录。 |
| 原理和工作流程 | 幂等 key 为 `trade_no`，首次处理时写入支付记录；后续相同回调直接返回成功。分布式锁防止并发写入。 |
| 缺点 | 需要处理回调丢失的情况，需要主动查询接口兜底。 |

### 8. 暗黑模式的实现方式

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 CSS 变量定义两套主题色，通过切换 `html` 元素的 class 实现暗黑模式切换，Pinia 管理状态，localStorage 持久化。 |
| 能做什么 | 提供亮色/暗色主题切换，适配用户偏好和系统设置。 |
| 怎么用 | `:root { --bg-color: #fff; }`；`html.dark { --bg-color: #1a1a2e; }`；`document.documentElement.classList.toggle('dark')`。 |
| 原理和工作流程 | 全局 CSS 变量在 `:root` 和 `html.dark` 中定义不同值，切换 class 时变量自动更新。Element Plus 通过 CSS 变量覆盖适配。 |
| 缺点 | 第三方组件可能需要额外适配；需要同时考虑系统偏好（prefers-color-scheme）。 |

### 9. 订单状态机的设计约束

| 维度 | 内容 |
|------|------|
| 是什么 | 状态机必须定义合法状态转移规则，不允许任意跳跃。例如订单不能从"待支付"直接跳到"已发货"。 |
| 能做什么 | 保证订单状态流转的合法性和一致性，防止状态错乱。 |
| 怎么用 | `transitions` 映射表定义合法转移，乐观锁 `WHERE status = oldStatus` 防并发，转移副作用在事务中处理。 |
| 原理和工作流程 | 每次状态变更先检查转移规则是否合法，再用乐观锁更新，最后处理副作用（扣库存、发通知等）。 |
| 缺点 | 状态机复杂度随业务增长；新增状态需要更新转移规则表。 |

### 10. Prisma ORM 的特点

| 维度 | 内容 |
|------|------|
| 是什么 | Prisma 使用专用 DSL（Schema 语言）定义数据模型，通过 `prisma generate` 自动生成类型安全的 TypeScript Client，支持事务操作。 |
| 能做什么 | 类型安全的数据库操作，Schema 即文档，自动生成迁移脚本。 |
| 怎么用 | `schema.prisma` 定义模型 → `prisma migrate dev` 生成迁移 → `prisma generate` 生成 Client → `prisma.user.findMany()` 操作数据库。 |
| 原理和工作流程 | Prisma Client 使用 Rust 引擎，查询性能好；Schema DSL 直观易读；自动生成完整 TypeScript 类型。 |
| 缺点 | 复杂查询（如多表联查）需要手动编写 SQL；学习成本比简单的 ORM 高。 |

### 1. RBAC 权限控制的三级体系

### 3. Redis 和数据库配合防超卖

| 维度 | 内容 |
|------|------|
| 是什么 | 多层防护：Redis Lua 脚本原子预减库存 → 数据库乐观锁真实扣减 → 消息队列削峰 → 定时对账。 |
| 能做什么 | 确保高并发下库存扣减原子性和最终一致性。 |
| 怎么用 | Redis：`eval` Lua 脚本 `GET + DECRBY`；数据库：`UPDATE ... WHERE stock >= quantity`；失败回滚 Redis。 |
| 原理和工作流程 | 下单：Redis 预减 → 创建订单 + 数据库扣减（事务）→ 失败回滚 Redis。取消：Redis 恢复 + 数据库恢复。 |
| 缺点 | Redis 和数据库可能短暂不一致，需定时对账。 |

### 4. Axios 拦截器 Token 刷新机制

| 维度 | 内容 |
|------|------|
| 是什么 | 双 Token 模式（accessToken 短期 + refreshToken 长期）+ `isRefreshing` 标记 + `pendingRequests` 队列。 |
| 能做什么 | 无感刷新 Token，避免用户频繁登录，处理并发 401 请求。 |
| 怎么用 | 请求拦截器添加 Token 头；响应拦截器捕获 401 → 检查 refreshToken → 刷新 → 更新 Token → 重试。 |
| 原理和工作流程 | 第一个 401 触发刷新（`isRefreshing = true`），后续 401 进入队列等待。刷新成功：重试队列；刷新失败：跳转登录。 |

### 8. BFF 缓存策略和三大问题防护

| 维度 | 内容 |
|------|------|
| 是什么 | 缓存穿透（布隆过滤器 + 空值缓存）、缓存击穿（互斥锁 + 逻辑过期）、缓存雪崩（TTL 加随机值 + 多级缓存）。 |
| 能做什么 | 保护数据库不被高并发请求击垮，提升接口响应速度。 |
| 怎么用 | 穿透：布隆过滤器 `BF.EXISTS`；击穿：`SET lock NX EX` 互斥锁；雪崩：`TTL = base + random(0, 60)`。 |
| 原理和工作流程 | 请求 → 布隆过滤器判断是否存在 → Redis 缓存查询 → 未命中加互斥锁查询数据库 → 回写缓存。 |
| 缺点 | 缓存策略增加了系统复杂度；缓存一致性需要额外处理。 |

### 1. 设计支持高并发的秒杀系统

| 维度 | 内容 |
|------|------|
| 是什么 | 全链路架构：CDN 静态页面 → Nginx 限流 + 验证码 → BFF Redis 预减库存 → 消息队列削峰 → 消费者异步下单。 |
| 能做什么 | 支撑秒杀场景下的高并发流量，保证库存不超卖。 |
| 怎么用 | 前端：按钮置灰 + 倒计时；网关：`limit_req` 限流；BFF：Lua 脚本原子扣减；MQ：异步下单；DB：读写分离 + 分片。 |
| 原理和工作流程 | 层层过滤无效请求，只有 Redis 扣减成功的请求才进入 MQ，最终只有极少数请求到达数据库。 |
| 缺点 | 系统复杂度高，需要仔细设计降级方案和监控告警。 |

### 2. 设计通用表单组件

| 维度 | 内容 |
|------|------|
| 是什么 | 支持动态字段渲染、联动校验和草稿保存的通用表单组件，通过 JSON Schema 或 formItems 配置驱动。 |
| 能做什么 | 减少重复表单开发，支持复杂联动逻辑和草稿恢复。 |
| 怎么用 | `formItems` 配置字段类型和校验规则；`watch` 实现联动；`useFormDraft` 草稿自动保存（防抖 2s + 7天过期）。 |
| 原理和工作流程 | 分步表单：每步独立渲染，KeepAlive 缓存；联动：watch 监听变化 + 声明式规则引擎；草稿：localStorage 自动保存 + 挂载时提示恢复。 |
| 缺点 | 超大规模表单需要分步/分页优化；联动规则复杂时维护成本高。 |

### 3. 设计电商平台微服务拆分方案

| 维度 | 内容 |
|------|------|
| 是什么 | 按业务域拆分为用户服务、商品服务、订单服务、购物车服务、支付服务、营销服务，各自独立数据库。 |
| 能做什么 | 实现多团队并行开发、独立部署、技术栈无关、增量升级。 |
| 怎么用 | 同步通信：HTTP REST/gRPC；异步消息：Kafka 用于订单状态通知和库存同步；分布式事务：Saga 补偿模式。 |
| 原理和工作流程 | 每个微服务独立数据库，服务间通过 API 和消息队列通信。BFF 层聚合多个微服务数据。服务发现通过 Consul/Nacos。 |
| 缺点 | 数据一致性、服务降级、链路追踪是主要挑战。 |

### 4. 设计企业后台权限管理方案

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 RBAC 模型的完整权限管理方案：用户-角色-权限三层模型 + 路由级/按钮级/接口级三级控制。 |
| 能做什么 | 实现不同角色看到不同菜单和操作按钮，保护敏感操作。 |
| 怎么用 | 路由：`router.addRoute()` 动态注册；按钮：`v-permission` 指令；接口：后端中间件校验。 |
| 原理和工作流程 | 登录后获取权限码 → 过滤路由表 → 动态注册 → 路由守卫检查 → 按钮指令检查 → 后端接口独立校验。 |
| 缺点 | 前端权限只是 UI 控制，后端校验才是安全底线；权限标识需前后端统一约定。 |

### 5. 设计多端 BFF 架构

| 维度 | 内容 |
|------|------|
| 是什么 | 按客户端（PC/Mobile/小程序）拆分 BFF 实例，各 BFF 负责接口聚合、数据裁剪和格式转换。 |
| 能做什么 | 实现多端数据适配，减少前端请求次数，降低前后端耦合。 |
| 怎么用 | PC BFF 返回完整字段；Mobile BFF 返回压缩图片和精简描述；小程序 BFF 返回适配格式。公共能力：统一鉴权、限流、缓存、日志。 |
| 原理和工作流程 | 前端请求对应端 BFF → BFF 并行请求多个微服务 → 聚合数据 → 按端裁剪格式 → 返回。降级策略：某服务故障时返回兜底数据。 |
| 缺点 | 多套 BFF 增加维护成本；各端 BFF 可能存在重复逻辑。 |
