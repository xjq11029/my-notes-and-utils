## 一、核心概念

### 1.1 Git 概述：分布式版本控制

| 维度 | 内容 |
|------|------|
| 是什么 | Linus Torvalds 于 2005 年创建的分布式版本控制系统，用于记录文件内容变化并管理多版本修订。 |
| 能做什么 | 追踪文件修改历史；回退到任意历史版本；支持多人并行开发与分支合并；查看每处修改的责任人。 |
| 怎么用 | `git init` 初始化仓库；`git add .` 暂存修改；`git commit -m "msg"` 提交 |
| 原理和工作流程 | 采用内容寻址的对象数据库存储模型，每次提交生成项目快照并以 SHA-1 哈希标识。工作区修改经暂存区进入本地仓库，再按需推送到远程仓库。本地拥有完整历史，绝大多数操作在本地磁盘完成，无需联网。 |
| 缺点 | 学习曲线陡峭，概念与命令繁多；二进制大文件存储效率低；对非文本内容差异比对能力弱。 |

### 1.2 分布式 vs 集中式（Git vs SVN）

| 维度 | 内容 |
|------|------|
| 是什么 | 两种版本控制架构的对比：Git 每个节点持有完整仓库，SVN 仅中央服务器持有完整仓库。 |
| 能做什么 | Git 支持离线提交、轻量分支、快照存储、SHA-1 完整性校验；SVN 依赖中央服务器在线协作。 |
| 怎么用 | Git: `git clone` 即获完整仓库；SVN: `svn checkout` 仅获工作副本 |
| 原理和工作流程 | Git 以快照方式存储全部文件状态，分支仅是指向提交的指针文件（41 字节），创建切换为 O(1)。SVN 按文件差异增量存储，分支是目录复制。Git 本地仓库自带全部历史，服务器宕机可从任意节点恢复；SVN 中央服务器宕机则全员受阻。 |
| 缺点 | Git 概念抽象度高于 SVN，初次上手难；SVN 对大文件和权限细粒度控制更友好，Git 在这两方面较弱。 |

### 1.3 Git 四层模型：工作区 / 暂存区 / 本地仓库 / 远程仓库

| 维度 | 内容 |
|------|------|
| 是什么 | Git 管理文件流转的四个区域：工作区、暂存区（Stage/Index）、本地仓库（.git 目录）、远程仓库。 |
| 能做什么 | 分层隔离已编辑、待提交、已提交、已共享四种状态；精确控制每次提交的内容范围。 |
| 怎么用 | `git add` 工作区→暂存区；`git commit` 暂存区→本地仓库；`git push` 本地→远程 |
| 原理和工作流程 | 工作区是实际可见的目录；暂存区存于 .git/index 文件，记录下次提交的文件列表与快照引用；本地仓库 .git 目录存储全部对象与引用；远程仓库是服务器端的共享副本。文件状态沿 未跟踪→已暂存→已提交→已推送 生命周期单向流转，每层只承接上一层的输出。 |
| 缺点 | 四层模型增加认知负担，新手易混淆暂存区与本地仓库的边界；暂存区在大型变更集下操作繁琐。 |

### 1.4 SHA-1 快照机制

| 维度 | 内容 |
|------|------|
| 是什么 | 以 SHA-1 哈希值标识所有对象、以快照而非差异存储版本内容的核心机制。 |
| 能做什么 | 保证数据完整性；相同内容去重存储；通过哈希值内容寻址快速定位任意对象。 |
| 怎么用 | 提交后 `git log --oneline` 查看哈希；`git show a108590` 检视对象 |
| 原理和工作流程 | 每次提交生成项目快照，未修改文件仅保留指向已有内容的引用以节省空间。对象分三类：blob 存文件内容、tree 存目录结构、commit 指向 tree 并含父提交引用。哈希基于内容计算，40 位十六进制，前 6-7 位即可唯一标识。内容被篡改则哈希变化，据此检测完整性。 |
| 缺点 | SHA-1 已被发现碰撞漏洞，高安全场景需迁移至 SHA-256（Git 新版本已支持）；哈希值对人类不可读。 |

## 二、底层原理

### 2.1 Git 对象存储模型

| 维度 | 内容 |
|------|------|
| 是什么 | .git 目录下以对象数据库为核心的存储结构，包含 HEAD、index、objects、refs 等组件。 |
| 能做什么 | 持久化全部提交、目录树、文件内容；管理分支引用、标签引用与远程引用；存储项目配置。 |
| 怎么用 | `ls .git/` 查看结构；`git cat-file -p <hash>` 检视对象内容 |
| 原理和工作流程 | objects 目录按哈希前两位分目录存放松散对象，pack 目录存放打包压缩后的对象。refs/heads 存分支指针（每分支一个文件记录 commit 的 SHA-1），refs/tags 存标签，refs/remotes 存远程分支引用。HEAD 文件记录当前分支指向（如 ref: refs/heads/master）。index 文件维护暂存区快照。 |
| 缺点 | 松散对象数量多时占用 inode 与磁盘空间，需定期 git gc 打包；内部结构对用户不透明，误删 .git 即丢全部历史。 |

### 2.2 分支实现原理

| 维度 | 内容 |
|------|------|
| 是什么 | 指向某个提交对象的可变指针，存储于 .git/refs/heads/ 下的小文件中。 |
| 能做什么 | 支持并行开发；快速创建、切换、删除分支；通过 HEAD 指针标识当前所处分支。 |
| 怎么用 | `git branch feature` 创建；`git checkout feature` 切换；`git branch -d feature` 删除 |
| 原理和工作流程 | 创建分支仅新建一个 41 字节文件（40 位 SHA-1 加换行），不复制项目内容，故为 O(1) 操作。HEAD 指针指向当前分支引用，切换分支时改变 HEAD 指向并将目标提交快照还原到工作区。新提交自动让当前分支指针前移，其他分支指针不动。 |
| 缺点 | 分支过多时历史图难以阅读；长期不合并的分支易产生难以解决的冲突。 |

### 2.3 为什么说 Git 是分布式？

| 维度 | 内容 |
|------|------|
| 是什么 | 架构中每个节点都持有完整仓库，没有哪个中央仓库是不可替代的核心依赖。 |
| 能做什么 | 离线提交与分支操作；任意节点可作为恢复源；远程仓库仅是约定好的共享位置而非必需。 |
| 怎么用 | `git clone` 获取完整仓库；离线 `git commit`；联网后 `git push` 同步 |
| 原理和工作流程 | 集中式（SVN）中所有人必须经中央服务器中转，服务器故障则全员无法提交。Git 中每个开发者本地具备全部历史与对象数据库，本地提交不依赖网络，推送时才与远程同步。即使远程丢失，从任意开发者的本地仓库克隆即可恢复全部历史。 |
| 缺点 | 完整历史本地存储占用磁盘较大；多节点并行修改需额外的合并与冲突解决成本。 |

## 三、实战应用

### 3.1 基本操作速查

> 本节为命令分组，下列各子小节分别对应一张五维表格。

#### 初始化与克隆

| 维度 | 内容 |
|------|------|
| 是什么 | 创建新仓库或获取远程仓库完整副本的起始操作。 |
| 能做什么 | 在空目录初始化 Git 仓库；从远程 URL 克隆包含全部历史的项目副本。 |
| 怎么用 | `git init`；`git clone <url>`；`git clone git@host:repo`（SSH） |
| 原理和工作流程 | init 在当前目录生成 .git 目录并初始化空对象数据库与 HEAD 引用。clone 向远程发起请求，下载全部对象与引用，自动创建本地分支并关联远程跟踪分支，默认检出默认分支。SSH 方式免密适合内部仓库，HTTPS 适合公开仓库。 |
| 缺点 | 克隆大型仓库耗时且占用带宽；浅克隆（--depth）虽快但缺失完整历史影响后续操作。 |

#### 查看状态

| 维度 | 内容 |
|------|------|
| 是什么 | 显示工作区与暂存区文件当前状态的命令。 |
| 能做什么 | 列出已修改、已暂存、未跟踪的文件；提示当前分支与上下游差异。 |
| 怎么用 | `git status`；`git status -s` 简洁输出 |
| 原理和工作流程 | 读取 .git/index 中的暂存区快照与 HEAD 指向的提交快照，再扫描工作区实际文件，三者两两比对得出每文件的状态分类。简洁模式以单字母前缀（如 M、A、??）标识状态，适合脚本解析。 |
| 缺点 | 超大型仓库扫描工作区较慢；输出对新手可能信息量偏大不易聚焦。 |

#### 添加到暂存区

| 维度 | 内容 |
|------|------|
| 是什么 | 将工作区修改登记到暂存区以待提交的操作。 |
| 能做什么 | 添加指定文件、全部修改或按模式匹配的文件；区分新增、修改、删除三种变更。 |
| 怎么用 | `git add <file>`；`git add .`；`git add *.java` |
| 原理和工作流程 | 读取工作区文件内容，为每个被添加文件创建 blob 对象写入对象数据库，并更新 .git/index 中对应条目使其指向新 blob。暂存区实质是文件路径到 blob 哈希的映射表，可多次 add 累积，最终一次 commit 将 index 快照固化为 tree 与 commit 对象。 |
| 缺点 | 容易误将大文件或敏感信息加入暂存区；暂存区与工作区分离后需额外命令查看差异。 |

#### 提交

| 维度 | 内容 |
|------|------|
| 是什么 | 将暂存区快照固化为本地仓库中一个提交对象的操作。 |
| 能做什么 | 记录项目快照与提交信息；可跳过暂存区提交已跟踪文件修改；支持追加修改到上次提交。 |
| 怎么用 | `git commit -m "msg"`；`git commit -a -m "msg"`；`git commit --amend` |
| 原理和工作流程 | 读取暂存区快照生成 tree 对象，创建 commit 对象含 tree 哈希、父提交引用、作者信息与提交信息，更新当前分支指针指向新 commit。-a 模式自动将已跟踪文件的修改加入暂存区再提交但不包含未跟踪文件。提交信息建议首行不超 50 字，空行后写详情，用祈使语气现在时态。 |
| 缺点 | 提交信息质量全靠自觉，缺乏约束易产生无意义记录；--amend 会改写历史，对已推送提交使用有风险。 |

#### 对比差异

| 维度 | 内容 |
|------|------|
| 是什么 | 比较不同区域或提交之间文件内容差异的命令。 |
| 能做什么 | 比较工作区与暂存区、暂存区与上次提交、工作区与任意提交的差异。 |
| 怎么用 | `git diff`；`git diff --cached`；`git diff HEAD`；`git diff -- <file>` |
| 原理和工作流程 | 无参数时比对工作区与暂存区快照，输出未暂存的修改。--cached 比对暂存区与 HEAD 提交，显示已暂存待提交的修改。HEAD 比对工作区与最新提交，显示全部未提交修改。可指定文件路径限定范围，底层基于两份快照的行级差异算法生成 unified diff 输出。 |
| 缺点 | 仅支持文本差异，二进制文件只能报告是否变化无法显示具体差异；大型仓库全量 diff 输出冗长。 |

#### 查看提交历史

| 维度 | 内容 |
|------|------|
| 是什么 | 按时间倒序列出提交记录或追溯单文件修改责任人的命令族。 |
| 能做什么 | 列出提交历史；以拓扑图显示分支结构；按数量或关键词过滤；逐行追溯文件修改者。 |
| 怎么用 | `git log --oneline --graph`；`git log -n 10`；`git log --grep="关键词"`；`git blame <file>` |
| 原理和工作流程 | log 从 HEAD 出发沿父提交引用遍历提交图，按提交时间排序输出。--graph 在遍历时记录分支合并拓扑绘制 ASCII 图。--grep 对提交信息做正则匹配。blame 逐行解析文件每行最后修改的提交，输出提交哈希、作者、时间与行内容。 |
| 缺点 | 历史极长时 log 输出庞大需分页；blame 对频繁重排的文件追溯结果可能误导。 |

#### 恢复历史操作：reflog

| 维度 | 内容 |
|------|------|
| 是什么 | 记录 HEAD 与分支指针所有移动历史的命令，是误操作恢复的关键工具。 |
| 能做什么 | 查找被 reset 丢弃的提交；恢复误删分支；追溯强制推送前的提交位置。 |
| 怎么用 | `git reflog`；恢复：`git reset --hard <reflog-hash>` |
| 原理和工作流程 | Git 在 .git/logs 下维护引用更新日志，每次 HEAD 或分支指针变动（commit、reset、checkout 等）均追加一条记录，含新旧哈希与操作描述。即使提交被 reset 丢弃，只要未执行 git gc 垃圾回收，对象仍存在于数据库，可通过 reflog 定位哈希后 reset 恢复。 |
| 缺点 | reflog 是本地记录不随推送同步；过期记录会被 gc 清理，恢复有时效窗口。 |

### 3.2 reset 三种模式详解

| 维度 | 内容 |
|------|------|
| 是什么 | git reset 移动当前分支指针到指定位置，并按模式决定是否连带重置暂存区与工作区的三种策略。 |
| 能做什么 | --soft 撤销提交保留暂存区；--mixed 撤销提交与暂存保留工作区；--hard 彻底回退三区。 |
| 怎么用 | `git reset --soft HEAD^`；`git reset HEAD -- <file>`；`git reset --hard <commit>` |
| 原理和工作流程 | 三种模式均移动分支指针到目标提交。--soft 仅改 HEAD，暂存区与工作区不变，原提交修改退回暂存区可重新提交。--mixed（默认）改 HEAD 并用目标提交覆盖暂存区，修改退回工作区需重新 add。--hard 改 HEAD 并同时覆盖暂存区与工作区，未提交修改彻底丢失。口诀：soft 只动头，mixed 动头与暂存，hard 三区全动。 |
| 缺点 | --hard 不可逆地丢弃工作区修改，误操作风险高；对已推送提交 reset 后需强制推送，破坏协作历史。 |

### 3.3 远程协作

> 本节为命令分组，下列各子小节分别对应一张五维表格。

#### 远程仓库管理

| 维度 | 内容 |
|------|------|
| 是什么 | 管理本地仓库关联的远程仓库地址的命令组。 |
| 能做什么 | 查看、添加、修改、删除、重命名远程仓库配置。 |
| 怎么用 | `git remote -v`；`git remote add origin <url>`；`git remote set-url origin <new>` |
| 原理和工作流程 | 远程仓库配置存储于 .git/config 文件的 [remote] 段，每条记录含名称与 URL。-v 显示名称与对应 URL（含读写方向）。add 写入新配置段，set-url 修改已有 URL，remove 删除整段。fetch 与 push 默认使用名为 origin 的远程。 |
| 缺点 | 多远程场景下命名易混淆；修改 URL 不校验可达性，错误地址到推送时才暴露。 |

#### 推送、拉取、抓取的区别

| 维度 | 内容 |
|------|------|
| 是什么 | fetch、pull、push 三个远程同步命令的职能区分。 |
| 能做什么 | fetch 下载远程更新不合并；pull 下载并自动合并；push 上传本地提交到远程。 |
| 怎么用 | `git fetch origin`；`git pull`；`git push origin <branch>` |
| 原理和工作流程 | fetch 将远程分支最新提交下载到本地远程跟踪分支（如 origin/master）并更新其指针，不触碰当前工作分支。pull 等价于 fetch 加 merge，下载后立即合并到当前分支。push 将本地分支提交上传到远程对应分支，远程分支指针前移，若远程有本地不具备的提交则拒绝并要求先拉取。 |
| 缺点 | pull 自动合并在远程有分叉时易产生意外冲突与合并提交；fetch 需额外手动合并步骤增加操作成本。 |

#### pull --rebase 是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 拉取远程更新时以变基替代合并的拉取方式，使本地提交重放到远程最新提交之后。 |
| 能做什么 | 保持提交历史线性无合并提交；避免无意义的 merge commit 噪声。 |
| 怎么用 | `git pull --rebase origin master`；`git config --global pull.rebase true` |
| 原理和工作流程 | 普通 pull 在本地与远程均有新提交时产生合并提交，历史出现分叉。pull --rebase 先 fetch 远程更新，再将本地新增提交逐个重放到远程最新提交之上，生成新哈希的提交，历史保持一条直线。可全局配置 pull.rebase true 使其成为默认行为。 |
| 缺点 | 变基重写本地提交哈希，若本地提交已共享则引发冲突；rebase 过程中遇冲突需逐个提交解决。 |

#### 推送到远程

| 维度 | 内容 |
|------|------|
| 是什么 | 将本地分支提交上传到远程仓库对应分支的操作。 |
| 能做什么 | 推送当前分支；推送全部本地分支；建立上游追踪关系；删除远程分支。 |
| 怎么用 | `git push origin <branch>`；`git push --all origin`；`git push origin --delete <branch>` |
| 原理和工作流程 | push 将本地分支的提交对象上传远程，更新远程分支指针。若远程分支是本地的直接祖先则快进更新，否则拒绝推送防止覆盖。首次推送加 -u（--set-upstream）会在本地分支与远程分支间建立追踪关系，后续直接 git push 即可。--delete 向远程发送删除引用请求移除远程分支。 |
| 缺点 | 远程有本地不具备的提交时推送被拒需先拉取；强制推送覆盖远程历史危害协作安全。 |

### 3.4 标签与版本

> 本节为命令分组，下列各子小节分别对应一张五维表格。

#### 创建标签

| 维度 | 内容 |
|------|------|
| 是什么 | 给特定提交打上不可变标记的操作，分轻量标签与附注标签两种。 |
| 能做什么 | 标记版本发布点；附注标签携带标签信息与签名；可对历史提交补打标签。 |
| 怎么用 | `git tag v1.0.0`；`git tag -a v1.0.0 -m "发布说明"`；`git tag -a v0.9.0 <hash>` |
| 原理和工作流程 | 轻量标签仅在 refs/tags 下创建一个文件指向目标提交，不含额外信息。附注标签创建独立的 tag 对象（含目标提交、标签信息、签名、时间），refs/tags 文件指向该 tag 对象而非直接指向 commit，适合正式发布。补打标签通过指定 commit 哈希将标签指向历史提交。 |
| 缺点 | 轻量标签不携带信息难以追溯发布上下文；标签默认不随 push 推送到远程需显式推送。 |

#### 列标签与查看

| 维度 | 内容 |
|------|------|
| 是什么 | 枚举与检索已有标签及查看标签详细信息的操作。 |
| 能做什么 | 列出全部标签；按模式搜索标签；查看标签指向的提交与附注信息。 |
| 怎么用 | `git tag`；`git tag -l "v1.*"`；`git show v1.0.0` |
| 原理和工作流程 | git tag 不带参数遍历 refs/tags 目录列出所有标签名按版本排序。-l 接受通配符模式过滤标签名。git show 读取标签引用的目标对象，附注标签展示 tag 对象信息与指向提交的差异摘要，轻量标签直接展示提交详情。 |
| 缺点 | 标签数量多时列表冗长需配合搜索；标签排序按字符串而非语义版本，可能顺序不符合预期。 |

#### 推送标签

| 维度 | 内容 |
|------|------|
| 是什么 | 将本地标签同步到远程仓库的操作。 |
| 能做什么 | 推送单个标签；一次性推送全部本地标签。 |
| 怎么用 | `git push origin v1.0.0`；`git push origin --tags` |
| 原理和工作流程 | 普通 git push 不会推送标签引用，需显式指定。推送单个标签时将 refs/tags/<name> 引用及关联对象上传远程。--tags 遍历全部本地标签引用批量上传，包括轻量与附注标签。远程标签与本地标签独立，删除本地标签不影响远程。 |
| 缺点 | --tags 推送全部标签可能包含不再需要的临时标签；标签推送后误删需额外操作清理远程。 |

#### 删除标签

| 维度 | 内容 |
|------|------|
| 是什么 | 移除本地或远程标签引用的操作。 |
| 能做什么 | 删除本地标签；删除远程标签。 |
| 怎么用 | `git tag -d v1.0.0`；`git push origin --delete v1.0.0` |
| 原理和工作流程 | -d 删除本地 refs/tags 下对应文件，标签指向的提交对象不受影响（仍由其他引用或 reflog 保留）。删除远程标签通过 push --delete 向远程发送引用删除请求。打错标签时需先删本地再删远程，再重新创建推送。 |
| 缺点 | 本地与远程标签需分别删除，遗漏一方导致不一致；已删除标签若他人本地仍存在会在推送时复活。 |

#### 语义化版本号

| 维度 | 内容 |
|------|------|
| 是什么 | SemVer 规范定义的 MAJOR.MINOR.PATCH 三段式版本号规则。 |
| 能做什么 | 通过版本号传达变更幅度；区分不兼容修改、向下兼容新增、向下兼容修复。 |
| 怎么用 | 格式：`MAJOR.MINOR.PATCH`；先行版：`v2.0.0-alpha.1`、`v2.0.0-rc.1` |
| 原理和工作流程 | 主版本号在不兼容 API 修改时递增，打破向后兼容；次版本号在向下兼容新增功能时递增；修订号在向下兼容 bug 修复时递增。先行版本号追加于修订号后用连字符分隔（alpha、beta、rc），标识预发布阶段。使用方可据版本号变化判断升级风险与影响范围。 |
| 缺点 | 依赖团队自觉遵守，缺乏工具强制；向后兼容性判断主观，边界场景易产生分歧。 |

## 四、常见面试题

> 本节为题集，下列各题以所考知识点生成五维表格。

### 1. Git 和 SVN 的主要区别是什么？Git 优势在哪里？

> 知识点：Git 与 SVN 架构差异

| 维度 | 内容 |
|------|------|
| 是什么 | 分布式 Git 与集中式 SVN 在仓库存储、网络依赖、分支管理等方面的系统性差异。 |
| 能做什么 | 区分离线与在线工作模式；对比分支轻量度；说明存储模型与完整性校验差异。 |
| 怎么用 | Git: `git clone` 获完整仓库；SVN: `svn checkout` 获工作副本 |
| 原理和工作流程 | Git 每节点持有完整仓库，多数操作本地完成支持离线；分支是指针文件创建为 O(1)。SVN 仅中央服务器持完整仓库，操作需联网；分支是目录复制较重。Git 按快照存储并用 SHA-1 校验完整性，SVN 按差异存储无内置校验。Git 优势在于离线工作、灵活分支、高性能与分布式安全。 |
| 缺点 | Git 学习成本高于 SVN；SVN 在大文件与细粒度权限控制上仍有适用场景，Git 非全场景替代。 |

### 2. Git 工作区、暂存区、本地仓库、远程仓库的区别？

> 知识点：四层区域模型

| 维度 | 内容 |
|------|------|
| 是什么 | Git 文件流转的四个区域及其职责边界。 |
| 能做什么 | 区分编辑、待提交、已提交、已共享四种状态；说明各区域间的转换命令。 |
| 怎么用 | `git add`→暂存区；`git commit`→本地仓库；`git push`→远程仓库 |
| 原理和工作流程 | 工作区是可见目录；暂存区存于 .git/index 记录待提交文件列表；本地仓库 .git 目录存储全部版本历史；远程仓库是服务器端共享副本。数据沿工作区→暂存区→本地仓库→远程仓库单向流转，反向通过 checkout/restore 与 fetch/pull 回流。分层设计使提交内容可精确控制。 |
| 缺点 | 四层模型对新手认知负担重；暂存区概念在其他 VCS 中不常见易被忽略。 |

### 3. git fetch 和 git pull 的区别？

> 知识点：fetch 与 pull 的差异

| 维度 | 内容 |
|------|------|
| 是什么 | 两个远程同步命令在是否自动合并上的区别。 |
| 能做什么 | fetch 仅下载不合并便于审查；pull 下载并自动合并快捷同步。 |
| 怎么用 | `git fetch origin` 后 `git merge`；`git pull`（= fetch + merge） |
| 原理和工作流程 | fetch 将远程最新提交下载到本地远程跟踪分支（origin/master）并更新其指针，不触碰当前工作分支，合并需手动执行。pull 等价于 fetch 加 merge，下载后立即合并到当前分支。推荐先 fetch 查看差异再决定合并方式，更可控。 |
| 缺点 | pull 自动合并在分叉时产生合并提交使历史杂乱；fetch 需额外合并步骤。 |

### 4. reset 的三种模式（soft/mixed/hard）区别是什么？各自使用场景？

> 知识点：reset 三种模式

| 维度 | 内容 |
|------|------|
| 是什么 | git reset 移动分支指针时对暂存区与工作区的三种处理策略。 |
| 能做什么 | soft 撤销提交保留暂存；mixed 撤销提交与暂存；hard 彻底回退三区。 |
| 怎么用 | `git reset --soft HEAD^`；`git reset HEAD <file>`；`git reset --hard <hash>` |
| 原理和工作流程 | 三模式均移动 HEAD 与分支指针。--soft 不动暂存区与工作区，修改退回暂存区。--mixed 覆盖暂存区不动工作区，修改退回工作区。--hard 同时覆盖暂存区与工作区，修改丢失。口诀：soft 只动头，mixed 动头与暂存，hard 三区全动。 |
| 缺点 | --hard 不可逆丢失工作区修改；对已推送提交 reset 需强制推送破坏协作历史。 |

### 5. 什么是 SHA-1 快照？Git 为什么用 SHA-1？

> 知识点：SHA-1 快照机制

| 维度 | 内容 |
|------|------|
| 是什么 | 以快照存储版本内容、以 SHA-1 哈希标识对象的机制。 |
| 能做什么 | 保证数据完整性；去重存储节省空间；内容寻址定位对象。 |
| 怎么用 | 提交生成 40 位哈希；`git log --oneline` 查看短哈希 |
| 原理和工作流程 | 每次提交保存项目全部文件快照，未修改文件仅保留引用。每个对象计算 40 位 SHA-1 哈希，内容相同则哈希相同。采用原因：完整性保证（篡改致哈希变化可检测）、去重存储（相同内容只存一份）、内容寻址（哈希即地址快速定位）。 |
| 缺点 | SHA-1 存在碰撞漏洞，高安全场景需迁移 SHA-256；哈希值对人类不可读。 |

### 6. Git 分支是什么？为什么 Git 创建分支这么快？

> 知识点：分支实现原理

| 维度 | 内容 |
|------|------|
| 是什么 | 指向提交对象的可变指针，创建操作为 O(1)。 |
| 能做什么 | 支持并行开发；快速创建切换删除；HEAD 标识当前分支。 |
| 怎么用 | `git branch <name>` 创建；`git checkout <name>` 切换 |
| 原理和工作流程 | 创建分支仅需在 .git/refs/heads 下新建 41 字节文件（40 位 SHA-1 加换行），不复制项目内容，故 O(1) 极快。HEAD 指针指向当前分支引用，切换分支改变 HEAD 指向并还原目标提交快照到工作区。新提交让当前分支指针自动前移。 |
| 缺点 | 分支过多历史图难读；长期未合并分支易积累冲突。 |

### 7. 什么是语义化版本号？规则是什么？

> 知识点：语义化版本号

| 维度 | 内容 |
|------|------|
| 是什么 | MAJOR.MINOR.PATCH 三段式版本号规范。 |
| 能做什么 | 传达变更幅度；区分不兼容修改、兼容新增、兼容修复。 |
| 怎么用 | `MAJOR.MINOR.PATCH`；先行版：`v2.0.0-alpha.1` |
| 原理和工作流程 | 主版本号不兼容 API 修改时递增，次版本号兼容新增功能时递增，修订号兼容 bug 修复时递增。先行版本号追加于修订号后标识预发布阶段。使用方据版本号变化判断升级影响。 |
| 缺点 | 依赖团队自觉遵守；兼容性判断主观边界场景易分歧。 |

### 8. git reflog 有什么用？什么时候用？

> 知识点：reflog 误操作恢复

| 维度 | 内容 |
|------|------|
| 是什么 | 记录 HEAD 与分支指针全部移动历史的命令，用于误操作恢复。 |
| 能做什么 | 找回被 reset 丢弃的提交；恢复误删分支；追溯强制推送前位置。 |
| 怎么用 | `git reflog`；`git reset --hard <reflog-hash>` |
| 原理和工作流程 | .git/logs 下维护引用更新日志，每次 HEAD 或分支变动均追加记录含新旧哈希与操作描述。即使提交被 reset 丢弃，未执行 gc 前对象仍存于数据库，可通过 reflog 定位哈希后 reset 恢复。适用于 reset --hard 误操作、误删分支等场景。 |
| 缺点 | 本地记录不随推送同步；过期记录被 gc 清理有恢复时效限制。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总 Git 日常使用中高频踩坑场景、现象、原因与正确应对方式的实践清单。 |
| 能做什么 | 预防 reset --hard 丢码；避免大文件敏感信息入库；规范分支开发与提交信息；正确处理 rebase 冲突与误删恢复。 |
| 怎么用 | 提交前写 .gitignore；reset --hard 前 commit 或 stash；冲突后 `git add` 再 `git rebase --continue` |
| 原理和工作流程 | 各坑点均源于对 Git 区域模型或指针机制理解不足。如 --hard 覆盖工作区致未提交修改丢失，可通过 reflog 在 gc 前恢复；大文件入库因无 .gitignore 需 filter-branch 或 bfg 清理历史；rebase 冲突需逐个 add 后 continue 而非直接 commit；pull 默认 merge 产生合并提交可配置 pull.rebase true 改善。 |
| 缺点 | 清单无法穷举所有场景；部分恢复操作（filter-branch）改写公共历史有协作风险。 |
