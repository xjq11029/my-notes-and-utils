### 1. ★ Redis 的默认端口是？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 服务监听的默认端口号 6379。 |
| 能做什么 | 区分 Redis 与 MySQL(3306)、MongoDB(27017)、Web(8080) 端口；指导连接配置。 |
| 怎么用 | `redis-cli -p 6379` 连接；`port 6379` 配置。 |
| 原理和工作流程 | 6379 来源于手机键盘 MERZ 对应数字，MERZ 是 Redis 作者 Antirez 与朋友玩笑用的意大利广告女郎名字，遂定为默认端口。Redis 服务启动后监听该端口接受客户端连接。 |
| 缺点 | 默认端口易被扫描攻击；生产环境建议修改并配合防火墙与 AUTH 认证；端口冲突时需调整。 |

### 2. ★ Redis 的数据存储在？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 作为内存数据库将数据主要存储在内存中。 |
| 能做什么 | 实现极高读写速度；单机达 10 万 QPS；通过持久化将内存数据落盘备份。 |
| 怎么用 | 数据读写始终在内存；RDB/AOF 仅做持久化备份不参与读写路径。 |
| 原理和工作流程 | 所有键值常驻内存，读写直接操作内存数据结构，内存带宽成主要瓶颈而非磁盘 IO，故速度极快。RDB 与 AOF 将内存数据异步写入磁盘用于重启恢复，但运行时读写不经过磁盘。 |
| 缺点 | 内存容量受物理内存限制成本高；断电未持久化数据丢失；大数据集启动加载耗时长。 |

### 3. ★★ Redis 的 String 类型底层数据结构是？

| 维度 | 内容 |
|------|------|
| 是什么 | String 类型底层使用 SDS（Simple Dynamic String）而非 C 原生字符串。 |
| 能做什么 | O(1) 取长度；杜绝缓冲区溢出；二进制安全；预分配与惰性释放减少 malloc。 |
| 怎么用 | int/embstr(<=44 字节)/raw 三种编码按内容自动切换。 |
| 原理和工作流程 | SDS 含 len、free、buf[]，len 使取长 O(1)；修改前检查 free 自动扩容避免溢出；以 len 判断结束可存含 \0 的二进制数据；扩容 len<1MB 加倍、>=1MB 加 1MB，缩短惰性释放。整数用 int 直接存不分配 SDS，短字符串 embstr 连续分配，长字符串 raw 两次 malloc。 |
| 缺点 | 预分配占额外内存；embstr 修改转 raw；大字符串占连续内存。 |

### 4. ★★ Redis 哈希表扩容采用什么方式？

| 维度 | 内容 |
|------|------|
| 是什么 | 字典扩容采用渐进式 rehash 分摊迁移而非一次性完成。 |
| 能做什么 | 避免一次性扩容阻塞主线程；扩缩容平滑过渡；期间保持读写可用。 |
| 怎么用 | 负载因子>=1 扩容；<0.1 缩容；serverCron 每 1ms 迁移 100 桶。 |
| 原理和工作流程 | 字典维护 ht[0]、ht[1]，触发时为 ht[1] 分配空间置 rehashidx=0。每次增删改查顺带迁移 rehashidx 对应桶到 ht[1] 并自增，serverCron 每 1ms 迁移 100 桶。期间查找先 ht[0] 后 ht[1]，新增直接入 ht[1]。rehashidx==ht[0].size 时完成释放 ht[0] 替换。 |
| 缺点 | rehash 期间双表内存翻倍；查找需访问两表增加开销；BGSAVE 期间提高阈值仍有内存压力。 |

### 5. ★★ Redis 有序集合（ZSet）的底层实现是？

| 维度 | 内容 |
|------|------|
| 是什么 | ZSet 底层使用跳跃表（skiplist）与字典（dict）组合实现。 |
| 能做什么 | 按 score 排序；O(logN) 范围与排名查询；O(1) 单点 score 查询。 |
| 怎么用 | 元素少用 ziplist，超阈值转 skiplist+dict；`ZADD`/`ZRANGE` 操作。 |
| 原理和工作流程 | skiplist 多层索引链表按 score 排序支持 O(logN) 范围查询，dict 提供 member→score 的 O(1) 查找，二者指针共享 member 与 score 不翻倍。元素<=128 且成员<=64 字节用 ziplist 紧凑存储。选 skiplist 而非红黑树因实现简单、范围查询友好、易维护。 |
| 缺点 | skiplist 额外指针内存开销；ziplist 大集合连锁更新；全量 ZRANGE 阻塞主线程。 |

### 6. ★★ 以下哪个命令会阻塞 Redis 主线程？

| 维度 | 内容 |
|------|------|
| 是什么 | KEYS 命令一次性遍历所有 key 为 O(N) 会阻塞主线程。 |
| 能做什么 | 模式匹配查询 key；识别危险命令；以 SCAN 替代安全遍历。 |
| 怎么用 | 生产禁用 `KEYS *`；改用 `SCAN 0 MATCH pattern COUNT 100`。 |
| 原理和工作流程 | KEYS 遍历整个键空间逐个模式匹配，时间复杂度 O(N)，数百万 key 时主线程长时间阻塞无法处理其他请求。SCAN 基于游标分批返回，每次只处理少量 key，不阻塞主线程，且通过 rehashidx 兼容 rehash 期间遍历。 |
| 缺点 | KEYS 生产阻塞致服务不可用；SCAN 结果可能重复且不保证完整；SCAN 多次往返增加客户端复杂度。 |

### 7. ★★ Redis 的 AOF 默认写入策略是？

| 维度 | 内容 |
|------|------|
| 是什么 | AOF 默认写入策略为 everysec（每秒刷盘一次）。 |
| 能做什么 | 平衡性能与数据安全；最多丢失 1 秒数据；按需切换 always 或 no。 |
| 怎么用 | `appendfsync everysec` 配置默认策略。 |
| 原理和工作流程 | AOF 写入分 write() 入内核缓冲区与 fsync() 刷盘两步。always 每命令 fsync 最安全但性能差；everysec 每秒 fsync 一次平衡性能与安全最多丢 1 秒；no 由 OS 决定性能最好但不可控可能丢 30 秒。everysec 为默认推荐。 |
| 缺点 | everysec 仍可能丢 1 秒数据；always 性能差；no 不可控丢数据风险大；fsync 有磁盘 IO 开销。 |

### 8. ★★ 哨兵模式下，判断主节点客观下线（ODOWN）的条件是？

| 维度 | 内容 |
|------|------|
| 是什么 | 超过 quorum 个 Sentinel 都认为主节点主观下线时标记为客观下线 ODOWN。 |
| 能做什么 | 区分主观/客观下线；触发故障转移；防止单点误判。 |
| 怎么用 | `sentinel monitor mymaster ip 6379 2` 中 quorum=2。 |
| 原理和工作流程 | 单 Sentinel 在 down-after-milliseconds 内未收 PONG 判主观下线 SDOWN。当超过 quorum 个 Sentinel 都判 SDOWN 时，主节点被标记客观下线 ODOWN，方才触发故障转移流程。quorum 在 sentinel monitor 配置中指定，通常设为 Sentinel 总数的一半加一。 |
| 缺点 | quorum 设置过高致故障转移延迟；过低易误判；需多数 Sentinel 存活；网络分区可能影响判定。 |

### 9. ★★ Redis Cluster 有多少个哈希槽？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis Cluster 将键空间划分为 16384 个哈希槽。 |
| 能做什么 | CRC16 定位槽；每主节点负责一部分槽；Hash Tag 聚合同槽批量操作。 |
| 怎么用 | `HASH_SLOT = CRC16(key) % 16384`。 |
| 原理和工作流程 | 选 16384 因心跳包约 2KB（16384/8/1024），65536 槽会使心跳包膨胀到 8KB 增网络开销；Redis 作者认为集群节点数不超 1000，16384 足够均匀分布；16384 为 2 的幂位运算高效。每主节点负责一部分槽，客户端通过 CRC16 定位 key 所属槽与节点。 |
| 缺点 | 不支持跨槽事务与批量；最小 3 主部署成本高；Gossip 心跳有开销；客户端需智能重定向。 |

### 10. ★★ 缓存穿透的解决方案不包括？

| 维度 | 内容 |
|------|------|
| 是什么 | 缓存穿透指查询不存在的数据每次直达数据库，解决方案不包括增加缓存过期时间。 |
| 能做什么 | 布隆过滤器前置拦截；缓存空值短过期；参数校验过滤非法请求。 |
| 怎么用 | `RBloomFilter.contains` 判断；`redis.setex(key,300,"null")` 缓存空值。 |
| 原理和工作流程 | 缓存穿透核心是查不存在的数据缓存与数据库都查不到。布隆过滤器用位数组与多哈希函数判定元素是否可能存在，不存在一定不存在前置拦截。缓存空值将 null 结果以短 TTL 缓存避免重复查库。参数校验过滤非法请求。增加缓存过期时间解决的是缓存雪崩（大量 key 同时过期）与穿透无关。 |
| 缺点 | 布隆过滤器误判且不支持删除；缓存空值堆积占内存；攻击者变换 key 仍可绕过；参数校验需维护规则。 |

### 11. ★★ Redis 的默认内存淘汰策略是？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 默认内存淘汰策略为 noeviction（不淘汰）。 |
| 能做什么 | 内存满时拒绝写入返回错误；保护数据不丢失；生产建议改 allkeys-lru。 |
| 怎么用 | `maxmemory-policy noeviction` 默认；生产设 `allkeys-lru`。 |
| 原理和工作流程 | noeviction 为默认策略，内存达 maxmemory 限制时不淘汰任何 key，写入操作返回错误。生产环境通常配置 allkeys-lru 从所有 key 淘汰最近最少使用的保证缓存可用性。其他策略包括 volatile-lru、allkeys-lfu、volatile-lfu、allkeys-random、volatile-random、volatile-ttl。 |
| 缺点 | noeviction 致写入失败影响服务；未配 maxmemory 致 OOM Killer；需根据场景选策略；淘汰增加 CPU 开销。 |

### 12. ★★ 以下关于 Redis 分布式锁，说法错误的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 分布式锁解锁不能直接用 DEL 命令，错误说法即认为可直接 DEL。 |
| 能做什么 | 加锁用 SET NX EX；解锁用 Lua 脚本保证原子性；value 设唯一标识防误删。 |
| 怎么用 | `SET k uuid NX EX 30` 加锁；Lua 脚本 GET 判断再 DEL 解锁。 |
| 原理和工作流程 | 加锁用 SET NX EX 原子操作，value 为 UUID 标识持有者。直接 DEL 错误因锁可能已过期被他线程获取，直接 DEL 会误删别人的锁。正确做法用 Lua 脚本先 GET 判断 value 是否为自己再 DEL，保证判断与删除原子性。锁续期由 Redisson Watchdog 处理。 |
| 缺点 | 直接 DEL 致并发安全问题；Lua 脚本调试困难；锁过期与业务超时竞态；单点故障致锁失效。 |

### 13. ★★ Redis 主从复制的全量复制使用什么机制？

| 维度 | 内容 |
|------|------|
| 是什么 | 主从全量复制使用 RDB 快照作为全量数据载体。 |
| 能做什么 | 主节点 BGSAVE 生成 RDB；发送给从节点加载；补充积压缓冲区增量命令。 |
| 怎么用 | 从节点 `PSYNC ? -1` 请求全量；主节点 `BGSAVE` 生成 RDB。 |
| 原理和工作流程 | 从节点首次连接或断开过久发 PSYNC ? -1 请求全量同步。主节点执行 BGSAVE 生成 RDB 快照发送给从节点，期间新写命令入复制积压缓冲区。从节点加载 RDB 后，主节点发送积压缓冲区增量命令，从节点执行完成同步。RDB 二进制紧凑可高效传输全量数据。 |
| 缺点 | 全量复制耗带宽与 CPU；大数据集 BGSAVE fork 耗时；积压缓冲区不足退化为全量；复制风暴压垮主节点。 |

### 14. ★★★ Redis 的 HyperLogLog 统计 UV 的误差率约为？

| 维度 | 内容 |
|------|------|
| 是什么 | HyperLogLog 标准误差率约为 0.81%。 |
| 能做什么 | 用 12KB 内存统计 2^64 基数；亿级 UV 去重计数；多 key 合并统计。 |
| 怎么用 | `PFADD k uid`；`PFCOUNT k`；`PFMERGE d s1 s2`。 |
| 原理和工作流程 | 基于伯努利试验，对元素哈希值记录连续前导零最大长度 k，估算基数约 2^k。通过分桶与调和平均降低方差，固定 12KB 内存估算 2^64 基数，标准误差 0.81%。亿级 UV 场景该误差通常可接受，内存优势巨大。 |
| 缺点 | 存在 0.81% 误差不精确；无法取出具体元素；少量元素估算偏差大；不适用于需精确计数的场景。 |

### 15. ★★★ 以下关于 Redis Cluster，说法正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis Cluster 使用哈希槽而非一致性哈希，为去中心化架构，支持在线扩缩容。 |
| 能做什么 | 16384 槽分片；Gossip 去中心化；reshard 在线迁移槽；MOVED/ASK 重定向。 |
| 怎么用 | `CRC16(key) % 16384` 定位槽；`redis-cli --cluster reshard` 扩缩容。 |
| 原理和工作流程 | Cluster 使用哈希槽，节点变化时迁移整个槽数据；一致性哈希节点变化只迁移少量数据。Cluster 为去中心化架构通过 Gossip 协议交换状态无中心节点。支持在线扩缩容通过 reshard 迁移槽实现，迁移中 ASK 重定向，完成后 MOVED 更新缓存。 |
| 缺点 | 不支持跨槽事务与批量；最小 3 主部署成本高；迁移期间槽部分不可用；客户端需智能重定向。 |

### 16. ★★ Redis 的 Pipeline 的作用是？

| 维度 | 内容 |
|------|------|
| 是什么 | Pipeline 将多个命令打包一次性发送以减少网络往返时间 RTT。 |
| 能做什么 | 批量执行降低 RTT；提升高延迟网络吞吐；客户端异步发送。 |
| 怎么用 | `redisTemplate.executePipelined(RedisCallback)` 循环发送多条命令。 |
| 原理和工作流程 | 客户端将多条命令写入发送缓冲区一次性发出，服务端依次执行按序返回结果，省去每条命令的往返等待，网络往返由 N 次降为 1 次。Pipeline 仅减少网络开销，不保证原子性（事务才保证），中间命令失败不影响其他。 |
| 缺点 | 不保证原子性；命令过多占内存与网络；需 Lua 或事务保证原子性；结果需按序处理。 |

### 17. ★★ 以下哪个不是 Redis 的持久化方式？

| 维度 | 内容 |
|------|------|
| 是什么 | WAL（预写日志）不是 Redis 的持久化方式，Redis 用 RDB、AOF、混合持久化。 |
| 能做什么 | 区分 Redis 与关系型数据库持久化机制；识别 RDB/AOF/混合三种方式。 |
| 怎么用 | Redis 用 `RDB` 快照、`AOF` 日志、`aof-use-rdb-preamble` 混合持久化。 |
| 原理和工作流程 | WAL（Write-Ahead Logging）是关系型数据库（如 PostgreSQL）与部分 NoSQL（如 RocksDB）的持久化机制，写前先记日志。Redis 持久化包括 RDB 全量快照、AOF 追加写命令日志、混合持久化（4.0+，AOF 前半 RDB 后半 AOF 增量），不含 WAL。 |
| 缺点 | 混淆不同数据库持久化机制易选错；Redis 持久化均有数据丢失或性能取舍；需根据场景选型。 |

### 18. ★★★ Redis 6.0 引入多线程主要用于？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 6.0 引入的多线程仅用于网络 IO 读写，命令执行仍单线程。 |
| 能做什么 | 多线程处理网络读写与协议解析；提升网络吞吐；保持命令执行原子性。 |
| 怎么用 | `io-threads 4` 配置开启，建议 4-8。 |
| 原理和工作流程 | Redis 性能瓶颈主要在网络 IO 而非 CPU 计算。6.0 引入多线程处理网络数据读写与协议解析，命令执行仍保持单线程避免锁竞争与上下文切换，保证原子性。默认关闭需通过 io-threads 配置开启。这样既提升网络吞吐又保持命令执行无锁。 |
| 缺点 | 仅缓解网络 IO 瓶颈；CPU 密集命令无改善；多线程增加配置复杂度；命令执行仍单线程无法利用多核计算。 |

### 19. ★★ Redis 的过期键删除策略是？

| 维度 | 内容 |
|------|------|
| 是什么 | 采用惰性删除与定期删除的组合策略删除过期键。 |
| 能做什么 | 惰性删除访问时检查；定期删除抽样清理；平衡 CPU 与内存开销。 |

| 缺点 | 惰性删除致过期 key 滞留占内存；定期删除有延迟；大量同时过期仍可能集中处理阻塞；无法及时释放内存。 |

| 怎么用 | `SET stock:pid <total>`；Lua 脚本 GET 判断 DECR；扣减成功写 MQ 异步下单。 |
| 原理和工作流程 | 秒杀前将库存加载到 Redis。请求来时 Lua 脚本原子执行 GET 判断库存>0 则 DECR 扣减，保证不超卖。扣减成功将下单请求写入 Kafka/RabbitMQ 异步处理订单创建与支付。网关层对单用户 QPS 限流防刷单。前端按钮防重复、验证码、CDN 加速。Redis 故障降级为数据库扣减保证可用。 |
| 缺点 | Redis 故障降级数据库性能差；异步下单有延迟；限流可能误杀正常用户；库存与订单最终一致需保障。 |

### 5. ★★ 设计一个亿级 UV 统计系统

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 HyperLogLog 实现的亿级 UV 统计系统设计。 |
| 能做什么 | 按日期统计 UV；多天合并；自动去重；12KB 统计亿级基数。 |
| 怎么用 | `PFADD uv:20250101 uid`；`PFCOUNT uv:20250101`；`PFMERGE uv:202501 uv:20250101 ...`。 |
| 原理和工作流程 | HyperLogLog 每个用户 ID 只存一次自动去重。按日期 PFADD 添加用户 ID，PFCOUNT 获取当日 UV。多天用 PFMERGE 合并为月 UV 再 PFCOUNT。12KB 内存可统计 2^64 元素，亿级 UV 完全可行，标准误差 0.81%。需精确 UV 或取用户列表则用 Bitmap 或 Set（内存占用大）。 |
| 缺点 | 存在 0.81% 误差不精确；无法获取具体用户 ID 列表；少量数据估算偏差大；精确方案内存占用大。 |
