## 一、持久化

### 1.1 RDB（快照持久化）

| 维度 | 内容 |
|------|------|
| 是什么 | 将某时刻内存全量数据以二进制快照写入磁盘 dump.rdb 的持久化方式。 |
| 能做什么 | 手动 SAVE/BGSAVE 触发；配置自动触发；支撑冷备份与灾难恢复；作为主从全量同步载体。 |
| 怎么用 | `BGSAVE`；`save 900 1`；`save 60 10000` 自动配置。 |
| 原理和工作流程 | BGSAVE 调用 fork() 创建子进程，利用 Copy-On-Write 父子共享物理内存，仅修改页才复制，子进程遍历内存生成压缩二进制 RDB。SAVE 在主线程同步生成会阻塞严禁使用。自动触发按 save 规则（N 秒内 M 次修改）触发 BGSAVE。SHUTDOWN/FLUSHALL 前及主从全量同步也会触发。 |
| 缺点 | 可能丢失最后一次快照后数据；fork 时 COW 触发内存翻倍风险；大数据量 fork 耗时阻塞主线程。 |

### 1.2 AOF（追加文件持久化）

| 维度 | 内容 |
|------|------|
| 是什么 | 以日志形式记录每个写命令、重启回放恢复数据的持久化方式。 |
| 能做什么 | 三种写入策略；BGREWRITEAOF 重写精简；混合持久化兼顾速度与安全；损坏文件修复。 |
| 怎么用 | `appendfsync everysec`；`BGREWRITEAOF`；`aof-use-rdb-preamble yes`；`redis-check-aof --fix`。 |
| 原理和工作流程 | 写命令先 write() 入内核缓冲区再 fsync() 刷盘。always 每命令刷盘最安全但性能差，everysec 每秒刷盘最多丢 1 秒，no 由 OS 决定。重写时 fork 子进程遍历内存生成最小命令集新 AOF，期间主进程增量写重写缓冲区，完成后追加并原子替换。混合持久化前半 RDB 后半 AOF 增量。 |
| 缺点 | 文件大恢复慢；always 性能差；重写期间 fork 内存翻倍；everysec 仍可能丢 1 秒数据。 |

### 1.3 RDB vs AOF 对比选型

| 维度 | 内容 |
|------|------|
| 是什么 | RDB 与 AOF 在文件大小、恢复速度、安全性等维度的对比与选型决策。 |
| 能做什么 | 依据数据丢失容忍度选择；评估恢复速度；权衡性能影响；指导生产配置。 |
| 怎么用 | 生产开启 `aof-use-rdb-preamble yes` 混合持久化；容忍高丢失只用 RDB；不能丢用 AOF everysec。 |
| 原理和工作流程 | RDB 二进制压缩文件小、加载快但可能丢快照后数据；AOF 文本命令可读、安全性高但文件大恢复慢需逐条回放。混合持久化（4.0+）AOF 文件前半 RDB 全量后半 AOF 增量，RDB 部分快速恢复、AOF 部分保证完整，兼顾速度与安全。 |
| 缺点 | RDB 数据丢失风险；AOF 恢复慢与文件膨胀；混合持久化增加配置复杂度；选型需在速度与安全间取舍。 |

## 二、主从复制与哨兵

### 2.1 主从复制

| 维度 | 内容 |
|------|------|
| 是什么 | 将主节点数据同步到从节点实现读写分离与数据冗余的机制。 |
| 能做什么 | 全量复制初始化从节点；部分复制断线重连补数据；树状结构分散复制压力；无盘复制降低磁盘 IO。 |
| 怎么用 | `replicaof <master-ip> <master-port>`；`repl-diskless-sync yes`。 |
| 原理和工作流程 | 全量复制：从节点发 PSYNC ? -1，主节点 BGSAVE 生成 RDB 发送，期间新写命令入复制积压缓冲区，从节点加载 RDB 后主节点发增量命令。部分复制（2.8+）：从节点带 run_id 与 offset 重连，主节点校验后从 offset 发送积压缓冲区增量。复制风暴因多从同时全量复制致 fork 飙高，用树状复制与无盘复制缓解。 |
| 缺点 | 全量复制耗带宽与 CPU；积压缓冲区不足退化为全量；复制风暴压垮主节点；主从存在同步延迟。 |

### 2.2 哨兵（Sentinel）

| 维度 | 内容 |
|------|------|
| 是什么 | 由多个 Sentinel 节点组成的高可用方案，负责监控、通知与自动故障转移。 |
| 能做什么 | 心跳监控节点存活；主观/客观下线判定；Raft 选举 Leader；自动选新主并通知客户端。 |
| 怎么用 | `sentinel monitor mymaster ip 6379 2`；`sentinel down-after-milliseconds mymaster 30000`。 |
| 原理和工作流程 | Sentinel 定期 PING 节点，down-after-milliseconds 内未收 PONG 判主观下线 SDOWN；超 quorum 个 Sentinel 同意则客观下线 ODOWN 触发故障转移。Sentinel 间 Raft 选举 Leader（先到先得，半数以上），Leader 按优先级最高、复制偏移最大、run_id 最小选新主，发 REPLICAOF NO ONE 升级，其余从节点指向新主，Pub/Sub 通知客户端。 |
| 缺点 | 故障转移有秒级不可用窗口；脑裂风险；选举需半数以上节点存活；客户端需感知主切换。 |

## 三、集群（Cluster）

### 3.1 集群架构

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 分布式解决方案，支持数据分片、自动故障转移与水平扩展的去中心化架构。 |
| 能做什么 | 16384 槽分片存储；Gossip 协议交换状态；MOVED/ASK 客户端重定向；Hash Tag 聚合同槽。 |
| 怎么用 | `HASH_SLOT = CRC16(key) % 16384`；`user:{1001}:name` 用 Hash Tag 同槽。 |
| 原理和工作流程 | 键空间分 16384 槽，每主节点负责一部分，CRC16(key)%16384 定位槽。16384 槽使心跳包约 2KB（65536 会 8KB）且节点数不超 1000 足够均匀。去中心化 Gossip 协议通过 MEET/PING/PONG/FAIL 传播状态。槽永久迁移返回 MOVED 更新缓存，迁移中返回 ASK 仅本次转发。最少 3 主节点满足故障检测半数以上。 |
| 缺点 | 不支持跨槽事务与批量操作；集群最小 3 主部署成本高；Gossip 心跳有网络开销；客户端需智能重定向。 |

### 3.2 集群扩缩容

| 维度 | 内容 |
|------|------|
| 是什么 | 通过迁移哈希槽实现 Redis Cluster 在线水平扩容与缩容的操作流程。 |
| 能做什么 | 新增节点加入集群；迁移槽到新节点；迁出槽后下线节点；原子迁移单个 key。 |
| 怎么用 | `redis-cli --cluster add-node`；`--cluster reshard`；`--cluster del-node`；`MIGRATE`。 |
| 原理和工作流程 | 新增节点通过 CLUSTER MEET 经 Gossip 传播加入，再 reshard 交互式迁移槽。下线先 reshard 迁出所有槽再 CLUSTER FORGET 移除。单 key 迁移用 MIGRATE 原子操作：源节点删除同时在目标节点创建。迁移中对应槽读写通过 ASK 重定向到目标节点。 |
| 缺点 | 迁移期间槽部分不可用；大批量迁移耗时长影响业务；MIGRATE 大 Key 阻塞；需人工或脚本介入。 |

## 四、缓存策略（重点）

### 4.1 缓存穿透

| 维度 | 内容 |
|------|------|
| 是什么 | 查询数据库与缓存均不存在的数据，每次请求穿透缓存直达数据库的现象。 |
| 能做什么 | 布隆过滤器前置拦截；缓存空值短过期；参数校验过滤非法请求。 |
| 怎么用 | `RBloomFilter.tryInit(100000L,0.01)` 配合 `add`/`contains`；`redis.setex(key,300,"null")`。 |
| 原理和工作流程 | 布隆过滤器用位数组与多哈希函数判定元素是否可能存在，不存在一定不存在，存在可能误判（假阳性），查询前先过滤。缓存空值将数据库返回 null 的 key 以短 TTL（如 5 分钟）缓存，下次命中直接返回。二者配合参数校验拦截恶意构造的大量不存在 key。 |
| 缺点 | 布隆过滤器存在误判且不支持删除；缓存空值堆积大量 key 占内存；攻击者变换 key 仍可绕过空值缓存。 |

### 4.2 缓存击穿

| 维度 | 内容 |
|------|------|
| 是什么 | 热点 key 过期瞬间大量并发请求同时查缓存失效直达数据库压垮数据库的现象。 |
| 能做什么 | 互斥锁串行重建缓存；逻辑过期返回旧值异步更新；双重检查防重复构建。 |
| 怎么用 | `SETNX lock:key 1 EX 10` 互斥；value 内嵌 expireAt 逻辑过期。 |
| 原理和工作流程 | 互斥锁：首请求 SETNX 获锁查库重建缓存，其余请求休眠重试读缓存，双重检查防重复构建。逻辑过期：key 不设 TTL，value 存逻辑过期时间，读取时判断过期则先返回旧值再异步获锁更新缓存，未获锁直接返回旧值兜底。 |
| 缺点 | 互斥锁增加等待延迟可能死锁；逻辑过期存在短暂数据不一致；异步更新失败需兜底重试。 |

### 4.3 缓存雪崩

| 维度 | 内容 |
|------|------|
| 是什么 | 大量 key 同时过期或 Redis 集群宕机致请求全部打到数据库压垮数据库的现象。 |
| 能做什么 | 过期时间加随机值打散；集群高可用避免单点；服务限流降级保护数据库。 |
| 怎么用 | `redis.setex(key, 3600 + random(600), v)`；主从+哨兵/Cluster；`rateLimiter.tryAcquire()`。 |
| 原理和工作流程 | 过期时间加随机偏移（如基础 1 小时加 0-10 分钟）避免大量 key 同时过期集中删除。Redis 集群主从复制+哨兵或 Cluster 提供故障自动切换避免单点宕机。缓存不可用时对数据库请求限流并返回默认值或友好提示，保护数据库不被压垮。 |
| 缺点 | 随机过期降低缓存命中率；集群高可用增加部署成本；限流降级牺牲用户体验；无法完全消除雪崩风险。 |

### 4.4 缓存一致性

| 维度 | 内容 |
|------|------|
| 是什么 | 数据库与缓存双写时保持数据一致的策略与方案。 |
| 能做什么 | Cache Aside 先更新库再删缓存；延迟双删清脏数据；订阅 binlog 最终一致。 |
| 怎么用 | 写：`db.update` → `redis.del`；延迟双删：删→更新→延迟→再删；Canal 订阅 binlog。 |
| 原理和工作流程 | Cache Aside 读先查缓存 miss 查库写缓存，写先更新库再删缓存（非更新，避免并发写 ABA 问题与聚合成本）。延迟双删在更新库前后各删一次，清除更新期间他线程读旧值写入的脏数据。Canal 订阅 MySQL binlog 解析变更事件异步更新/删除缓存，业务无侵入实现最终一致性。强一致需分布式事务但牺牲性能。 |
| 缺点 | 删除缓存瞬间存在读旧值窗口；延迟双删延迟时间难定；binlog 方案有延迟属最终一致；强一致方案性能差。 |

## 五、内存淘汰策略

### 八种淘汰策略详解

| 维度 | 内容 |
|------|------|
| 是什么 | 内存达 maxmemory 时按策略淘汰 key 以容纳新写入的八种机制。 |
| 能做什么 | noeviction 拒绝写入；allkeys/volatile-lru 淘汰最久未用；allkeys/volatile-lfu 淘汰最低频；random 随机；volatile-ttl 淘汰最近过期。 |
| 怎么用 | `maxmemory-policy allkeys-lru`；`maxmemory 4gb`。 |
| 原理和工作流程 | noeviction 不淘汰写入报错；allkeys-* 从全部 key 选，volatile-* 仅从设过期 key 选。LRU 淘汰最近最少使用，LFU（4.0+）淘汰访问频率最低解决偶发访问干扰。volatile-ttl 优先淘汰最接近过期的 key。策略在写入且内存超限时触发，扫描候选 key 决定淘汰对象。 |
| 缺点 | noeviction 致写入失败；LRU 偶发访问干扰；LFU 计数器衰减需调参；淘汰过程增加 CPU 开销。 |

### LRU（Least Recently Used）

| 维度 | 内容 |
|------|------|
| 是什么 | 近似 LRU 淘汰策略，以最后访问时间为依据淘汰最久未用的 key。 |
| 能做什么 | 随机抽样淘汰；调节抽样数量逼近精确 LRU；通用缓存场景首选。 |
| 怎么用 | `maxmemory-policy allkeys-lru`；`maxmemory-samples 5`。 |
| 原理和工作流程 | 非精确 LRU（维护链表内存开销大），改为随机抽样 N 个 key（默认 5），淘汰其中最后访问时间最久远的。samples 越大越接近精确 LRU 但 CPU 开销越高。Redis 对象头记录最后访问时间供抽样比较。 |
| 缺点 | 随机抽样非精确可能误淘汰热点；偶发性访问干扰（昨天高频今天不用仍被保留）；samples 增大增加 CPU 开销。 |

### LFU（Least Frequently Used，Redis 4.0+）

| 维度 | 内容 |
|------|------|
| 是什么 | 以访问频率为依据淘汰最低频 key 的策略，解决 LRU 偶发访问问题。 |
| 能做什么 | 按访问频率淘汰；对数计数器随时间衰减；区分热点与偶发访问。 |
| 怎么用 | `maxmemory-policy allkeys-lfu`；`lfu-log-factor 10`；`lfu-decay-time 1`。 |
| 原理和工作流程 | 使用 Redis 对象头 24 位记录频率：高 16 位为上次访问时间（分钟级），低 8 位为对数计数器。访问时计数器按对数增长（lfu-log-factor 控制增长速度），随时间按 lfu-decay-time 周期衰减。淘汰时抽样选计数器最小的 key。解决 LRU 中昨天访问 1000 次今天未访问仍被保留的问题。 |
| 缺点 | 对数计数器非精确频率；衰减参数需调优；新 key 初始计数低易被误淘汰；8 位计数器范围有限。 |

## 六、分布式锁

### 6.1 单机 Redis 分布式锁

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 SET NX EX 与 Lua 脚本在单 Redis 实例上实现的分布式锁。 |
| 能做什么 | 原子加锁防死锁；Lua 原子解锁防误删；Watchdog 自动续期；Hash 结构可重入。 |
| 怎么用 | `SET lock:k <uuid> NX EX 30`；Lua 脚本 GET 判断再 DEL；`redisson.getLock(k).lock()`。 |
| 原理和工作流程 | 加锁用 SET NX EX 原子操作，NX 保证互斥、EX 防死锁、value 用 UUID 标识持有者。解锁用 Lua 脚本先 GET 判断 value 为自己再 DEL，保证判断与删除原子性，避免误删已过期被他线程获取的锁。Redisson Watchdog 默认 30 秒过期，每 10 秒（1/3）检查续期到 30 秒，业务完成显式解锁取消续期。可重入基于 Hash，field 为线程 ID，value 为重入次数，HINCRBY 递增递减，归零删 key。 |
| 缺点 | 单点故障致锁失效；锁过期与业务超时竞态；Watchdog 依赖客户端存活；主从切换期间锁可能丢失。 |

### 6.2 Redlock 算法（多节点分布式锁）

| 维度 | 内容 |
|------|------|
| 是什么 | 在 N 个独立 Redis 节点上获取锁、半数以上成功且总耗时小于有效期才算成功的多节点锁算法。 |
| 能做什么 | 跨多节点容错；降低单点故障风险；提供更强安全性保证。 |
| 怎么用 | 依次向 N 节点 `SET NX EX`，成功数>=N/2+1 且耗时<有效期即获锁。 |
| 原理和工作流程 | 获取时间戳，依次向 N 个独立节点 SET NX EX 加锁（每节点超时远小于锁有效期），计算总耗时。成功节点数>=N/2+1 且总耗时<锁有效期则获锁成功，实际有效期为原有效期减耗时；否则向所有节点发解锁请求。失败时需清理全部节点避免残留锁。 |
| 缺点 | 时钟跳跃致锁提前过期；GC 停顿超有效期致锁失效不知情；部署复杂成本高；实践中单机+哨兵通常已够。 |

## 七、常见面试题

### 1. RDB 和 AOF 的区别？如何选择持久化策略？

| 维度 | 内容 |
|------|------|
| 是什么 | RDB 快照与 AOF 日志两种持久化方式的差异与选型决策。 |
| 能做什么 | 评估文件大小、恢复速度、数据安全性；按丢失容忍度选择；混合持久化兼顾两者。 |
| 怎么用 | 生产 `aof-use-rdb-preamble yes` 混合；容忍高丢失用 RDB；不能丢用 AOF everysec。 |
| 原理和工作流程 | RDB 定时二进制快照文件小恢复快但可能丢快照后数据、大数据 fork 耗时；AOF 追加写命令日志支持 always/everysec/no 三策略，安全性高但文件大恢复慢。混合持久化（4.0+）AOF 前半 RDB 全量后半 AOF 增量，兼顾恢复速度与数据完整。 |
| 缺点 | RDB 丢失风险；AOF 恢复慢与文件膨胀；混合持久化配置复杂；选型需在速度与安全间取舍。 |

### 2. 哨兵模式的故障转移流程是怎样的？

| 维度 | 内容 |
|------|------|
| 是什么 | Sentinel 从判定主节点下线到选出新主并通知客户端的完整流程。 |
| 能做什么 | 主观/客观下线判定；Raft 选举 Leader；按优先级选新主；通知从节点与客户端。 |
| 怎么用 | `sentinel monitor mymaster ip 6379 2`；`sentinel down-after-milliseconds` 配置。 |
| 原理和工作流程 | SDOWN：单 Sentinel 在 down-after-milliseconds 未收 PONG 判主观下线。ODOWN：超 quorum 个 Sentinel 同意判客观下线。Leader 选举：Raft 协议先到先得半数以上。选新主：优先级最高（replica-priority 最小）、复制偏移最大、run_id 最小。新主 REPLICAOF NO ONE 升级，其余从节点指向新主，Pub/Sub 通知客户端。 |
| 缺点 | 故障转移秒级不可用窗口；选举需半数以上 Sentinel 存活；脑裂风险；客户端需感知主切换。 |

### 3. 缓存穿透、缓存击穿、缓存雪崩分别是什么？如何解决？

| 维度 | 内容 |
|------|------|
| 是什么 | 三种典型缓存失效问题的定义与核心解决方案对照。 |
| 能做什么 | 区分穿透/击穿/雪崩；分别用布隆过滤器、互斥锁、随机过期应对；提供综合防护。 |
| 怎么用 | 穿透：布隆过滤器+缓存空值；击穿：SETNX 互斥锁；雪崩：过期加随机值+限流。 |
| 原理和工作流程 | 穿透指查不存在的数据每次直达数据库，用布隆过滤器前置拦截与缓存空值短过期。击穿指热点 key 过期瞬间并发打库，用互斥锁串行重建或逻辑过期返回旧值异步更新。雪崩指大量 key 同时过期或集群宕机，用过期时间加随机值打散、集群高可用与限流降级保护数据库。 |
| 缺点 | 布隆过滤器误判且不支持删除；互斥锁增加延迟；随机过期降低命中率；限流降级牺牲体验；无法完全消除风险。 |

### 4. Redis 分布式锁如何实现？Redisson 的看门狗机制是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | SET NX EX 加锁、Lua 解锁、Watchdog 续期、Hash 可重入的分布式锁实现。 |
| 能做什么 | 原子加锁防死锁；Lua 解锁防误删；看门狗自动续期；可重入支持同线程多次加锁。 |
| 怎么用 | `SET k uuid NX EX 30`；Lua 脚本解锁；`redisson.getLock(k).lock()` 自动续期。 |
| 原理和工作流程 | 加锁 SET NX EX 原子操作，value 为 UUID 标识持有者。解锁 Lua 脚本先 GET 判断 value 再 DEL 保证原子性，避免误删。Watchdog 默认 30 秒过期每 10 秒（1/3）检查续期到 30 秒，业务完成显式解锁取消续期。可重入基于 Hash，field 为线程 ID，value 为重入次数，HINCRBY 递增递减归零删 key。 |
| 缺点 | 单点故障致锁失效；锁过期与业务超时竞态；Watchdog 依赖客户端存活；主从切换锁可能丢失。 |

### 5. Redis 集群的哈希槽是什么？为什么是 16384 个？

| 维度 | 内容 |
|------|------|
| 是什么 | Redis Cluster 将键空间分 16384 槽、每主节点负责一部分的分片机制及数量选择原因。 |
| 能做什么 | CRC16 定位槽；Hash Tag 聚合同槽；Gossip 去中心化；MOVED/ASK 重定向。 |
| 怎么用 | `HASH_SLOT = CRC16(key) % 16384`；`user:{1001}:name` 用 Hash Tag。 |
| 原理和工作流程 | 键空间分 16384 槽，每主节点负责一部分，CRC16(key)%16384 定位槽。选 16384 因心跳包约 2KB（65536 会 8KB 增网络开销）、集群节点数不超 1000 足够均匀、2 的幂位运算高效。去中心化 Gossip 协议交换状态，槽永久迁移 MOVED 更新缓存、迁移中 ASK 仅本次转发。 |
| 缺点 | 不支持跨槽事务与批量；最小 3 主部署成本高；Gossip 心跳有开销；客户端需智能重定向。 |

## 八、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | Redis 高级特性在生产实践中的高频踩坑点与解决方案汇总。 |
| 能做什么 | 识别消息队列误用、危险命令、复制风暴、跨槽操作、事务回滚误区、大热 Key、OOM 等问题。 |
| 怎么用 | Stream 替代 List 做队列；`rename-command` 禁用 KEYS；树状复制；Hash Tag 同槽；设 maxmemory。 |
| 原理和工作流程 | Redis 做队列缺 ACK 致消息丢失故用 Stream 或 Kafka；KEYS/FLUSHALL 阻塞或不可逆故禁用并改 SCAN；多从挂一主致复制风暴故树状复制；MGET 跨槽报 CROSSSLOT 故用 Hash Tag；事务不支持回滚运行时错误继续执行故充分测试；大热 Key 阻塞与单点过载故拆分与本地缓存；未配 maxmemory 致 OOM 故设上限与淘汰策略。 |
| 缺点 | Stream 复杂度高于 List；禁用命令影响运维便利；树状复制增加层级延迟；Hash Tag 限制 key 设计；本地缓存有一致性延迟。 |
