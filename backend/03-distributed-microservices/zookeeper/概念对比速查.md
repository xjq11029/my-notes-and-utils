# ZooKeeper - 概念对比速查

---

### ZNode四种类型

| 对比维度 | 持久节点（PERSISTENT） | 持久有序节点（PERSISTENT_SEQUENTIAL） | 临时节点（EPHEMERAL） | 临时有序节点（EPHEMERAL_SEQUENTIAL） |
|---------|----------------------|-------------------------------------|---------------------|-------------------------------------|
| 核心定位 | 存储配置信息和元数据 | 分布式ID生成和任务队列 | 服务注册和存活检测 | 分布式锁和Leader选举 |
| 生命周期 | 显式删除前一直存在 | 显式删除前一直存在 | 会话结束自动删除 | 会话结束自动删除 |
| 序号特性 | 无 | 名称带10位递增序号 | 无 | 名称带10位递增序号 |
| 可拥有子节点 | 是 | 是 | 否 | 否 |
| 创建命令 | create /path data | create -s /path data | create -e /path data | create -s -e /path data |
| 典型场景 | 数据库连接配置、服务元数据 | 任务队列、分布式ID | 服务注册发现、分布式锁（非公平） | 公平锁、Leader选举 |
| 选择建议 | 配置存储首选 | 需要有序标识时使用 | 与客户端生命周期绑定的场景 | 需要公平排队时使用 |

### CAP vs BASE

| 对比维度 | CAP理论 | BASE理论 |
|---------|--------|---------|
| 核心定位 | 分布式系统设计的上限约束，指出最多同时满足C/A/P中的两个 | 分布式系统实现的实践指导，在CAP约束下追求高可用 |
| 核心主张 | 网络分区（P）发生时必须在一致性（C）和可用性（A）之间取舍 | 基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent） |
| 一致性要求 | 强一致性（线性一致性），所有节点同时看到相同数据 | 最终一致性，允许短暂数据不一致，最终达到一致 |
| 可用性要求 | 每个请求都获得非错误响应 | 基本可用，允许降级或延迟响应 |
| 代表系统 | ZooKeeper（CP）、Nacos（AP/CP）、Eureka（AP） | 大多数互联网系统采用BASE |
| 选择建议 | 协调服务选CP，服务发现选AP | 对一致性要求不极严格的业务场景优先采用BASE |

### ZAB vs Raft

| 对比维度 | ZAB协议 | Raft协议 |
|---------|---------|---------|
| 核心定位 | ZooKeeper专用原子广播协议，保证分布式数据一致性 | 通用分布式一致性算法，易于理解和实现 |
| 设计目标 | 为ZooKeeper量身定制，优化协调服务场景 | 通用可理解性，降低工程实现复杂度 |
| Leader选举 | Fast Leader Election，基于epoch+counter+myid优先级 | 随机超时触发选举，Term+LogIndex比较 |
| 日志复制 | 两阶段（Proposal+ACK、Commit），支持流水线化 | 两阶段（AppendEntries确认、Commit），强Leader |
| 成员变更 | 需重启集群或手动配置 | 支持Joint Consensus安全的动态成员变更 |
| 崩溃恢复 | TRUNC/DIFF/SNAP三种同步策略 | 通过Term和LogIndex匹配自动同步 |
| 使用系统 | ZooKeeper | Nacos（CP模式）、etcd、Consul、TiKV |
| 选择建议 | 使用ZooKeeper时自动使用ZAB | 自研分布式系统建议基于Raft实现 |
