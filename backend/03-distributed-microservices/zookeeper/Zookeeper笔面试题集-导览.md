### 1. ZooKeeper 的数据模型类似于？（★）

| 维度 | 内容 |
|------|------|
| 是什么 | ZooKeeper 采用类似 Unix 文件系统的层级树形命名空间，节点以 `/` 分隔路径。 |
| 能做什么 | 区分 ZK 与关系型数据库、KV 存储、图数据库的数据模型差异。 |
| 怎么用 | 与关系型表、键值对、图结构对比辨识。 |
| 原理和工作流程 | ZNode 以 `/` 分隔组织为层级树，类似文件系统目录结构，可存储数据并拥有子节点；关系型为二维表结构，KV 为扁平键值对，图数据库为节点与边。 |
| 缺点 | 树形结构不适合表达复杂关系；路径层次不宜过深（建议不超过 10 层）。 |

### 2. 以下哪种 ZNode 类型在客户端会话结束后会自动删除？（★）

| 维度 | 内容 |
|------|------|
| 是什么 | 临时节点（EPHEMERAL）与会话绑定，会话结束自动删除。 |
| 能做什么 | 区分持久节点、持久有序节点、临时节点、容器节点的生命周期管理。 |
| 怎么用 | `create -e /path data` 创建临时节点。 |
| 原理和工作流程 | 临时节点在客户端建立 Session 时创建，会话超时或主动关闭后自动删除；持久节点显式删除前一直存在；容器节点在最后一个子节点删除后自动删除自身。 |
| 缺点 | 临时节点不能拥有子节点；会话超时时间较长时故障检测延迟大。 |

### 3. ZooKeeper 在 CAP 理论中选择了？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | ZooKeeper 选择 CP 架构，基于 Zab 协议保证强一致性，通过过半机制保证分区容错性。 |
| 能做什么 | 区分 CP 与 AP 的选择差异；了解 ZooKeeper 牺牲可用性换取一致性的代价。 |
| 怎么用 | 与 Nacos（AP/CP 可切换）对比理解。 |
| 原理和工作流程 | 所有写操作由 Leader 执行保证一致性；过半机制保证分区容错；选举期间（约 200ms）集群不可用；过半节点故障时集群拒绝服务。 |
| 缺点 | 选举期间不可用；不适合对可用性要求极高的场景。 |

### 4. ZooKeeper 的 Watcher 机制中，以下哪项描述是正确的？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | Watcher 机制的一次性触发、轻量级通知、串行执行特性。 |
| 能做什么 | 区分一次性触发与持续监听；区分通知含数据与不含数据；理解串行执行保证顺序。 |
| 怎么用 | 一次性触发需在回调中重新注册；通知不含数据需主动 getData 拉取。 |
| 原理和工作流程 | 每个 Watcher 仅触发一次，收到通知后自动失效；通知只含事件类型和路径不含数据；同一客户端 Watcher 事件串行处理保证顺序；Watcher 存储在服务端内存中客户端重启后需重新注册。 |
| 缺点 | 一次性触发增加客户端复杂度；通知不含数据需额外拉取增加延迟。 |

### 5. ZAB 协议中，zxid 的高 32 位表示什么？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | zxid 高 32 位为 epoch（纪元号），每次 Leader 选举递增。 |
| 能做什么 | 区分 epoch（纪元号）与 counter（事务计数器）；理解 epoch 防止旧 Leader 脑裂。 |
| 怎么用 | 低 32 位 counter 同一 epoch 内事务递增，高 32 位 epoch 区分 Leader 任期。 |
| 原理和工作流程 | zxid 为 64 位整数，高 32 位 epoch 每次 Leader 选举递增，低 32 位 counter 同一 epoch 内每次事务递增；epoch 用于区分不同 Leader 任期，旧 Leader 发现 epoch 落后自动降级。 |
| 缺点 | 32 位 counter 在极端高频事务下可能溢出（需近 43 亿次事务）。 |

### 6. 关于 ZooKeeper 集群的过半机制，以下说法错误的是？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | 过半机制下奇数节点更经济，偶数节点容忍度与 N-1 奇数节点相同。 |
| 能做什么 | 5 节点容忍 2 个故障；事务提交需过半 ACK；Leader 选举需过半投票；偶数节点不提升容错。 |
| 怎么用 | 生产环境推荐 5 节点（1 Leader + 4 Follower）。 |
| 原理和工作流程 | 4 节点（过半 3）容忍 1 个故障，与 3 节点（过半 2）容忍度相同但多部署 1 个节点；6 节点（过半 4）容忍 2 个故障，与 5 节点（过半 3）容忍度相同；奇数节点以更少资源达到相同容错。 |
| 缺点 | 偶数节点浪费资源；节点数固定后扩展需重新配置。 |

### 7. 以下哪种场景不适合使用 ZooKeeper 实现？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | ZooKeeper 设计用于存储协调元数据，不适合海量数据存储（TB 级）。 |
| 能做什么 | 分布式配置管理、分布式锁、Leader 选举为典型场景；海量数据存储应选 HDFS、ClickHouse 等。 |
| 怎么用 | 协调元数据存 ZK，业务数据存外部存储。 |
| 原理和工作流程 | ZK 单个 ZNode 数据上限 1MB，所有数据存储在内存中，总数据量受内存限制；设计目标为协调服务而非数据存储；海量数据存储需用分布式文件系统或列式数据库。 |
| 缺点 | 内存限制数据总量；不适合大文件存储；不适合高频大数据量读写。 |

### 8. ZooKeeper 集群中 Observer 角色的特点是？（★★）

| 维度 | 内容 |
|------|------|
| 是什么 | Observer 同步 Leader 数据处理读请求，但不参与 Leader 选举和事务过半确认。 |
| 能做什么 | 扩展读能力不影响写性能；跨数据中心部署降低延迟；减少选举通信开销。 |
| 怎么用 | 配置 `peerType=observer` 和 `server.{myid}=host:2888:3888:observer`。 |
| 原理和工作流程 | Observer 与 Follower 类似同步数据并响应读请求，但不参与投票；参与投票节点增多会导致事务提交延迟增大，Observer 不投票可在不影响写性能前提下水平扩展读能力；Follower 参与选举和投票，Leader 处理写请求。 |
| 缺点 | 不提升容错能力；Observer 故障不影响集群但自身读请求中断。 |

### 9. 关于 ZooKeeper 分布式锁，以下说法正确的是？（★★★）

| 维度 | 内容 |
|------|------|
| 是什么 | 基于临时有序节点的锁是公平锁，序号最小者获锁，保证先到先得。 |
| 能做什么 | 区分排他锁（同名临时节点）与公平锁（临时有序节点）；理解 ZooKeeper 锁与 Redis 锁的性能差异；理解临时节点自动释放。 |
| 怎么用 | 公平锁：`InterProcessSemaphoreMutex`；排他锁：`InterProcessMutex`。 |
| 原理和工作流程 | 公平锁所有客户端创建临时有序节点，序号最小者获锁，其他客户端监听前一个节点，释放时只有下一个被唤醒（先到先得）；排他锁所有客户端竞争同一节点唤醒所有等待者（惊群效应）；ZooKeeper 锁一致性高但性能低于 Redis；临时节点会话超时自动删除释放锁。 |
| 缺点 | 排他锁存在惊群效应；ZooKeeper 锁性能低于 Redis 锁；公平锁节点数多时排序开销大。 |

### 10. ZooKeeper 崩溃恢复时，以下哪种数据同步策略用于全量同步？（★★★）

| 维度 | 内容 |
|------|------|
| 是什么 | SNAP 策略用于 Follower zxid 远小于 Leader 时的全量快照同步。 |
| 能做什么 | 区分 TRUNC（回退截断）、DIFF（差异同步）、SNAP（全量同步）三种策略。 |
| 怎么用 | 新 Leader 根据 zxid 差距自动选择同步策略，无需手动干预。 |
| 原理和工作流程 | TRUNC：Follower zxid 大于 Leader，回退截断多余事务；DIFF：Follower zxid 略小于 Leader，逐条发送差异事务日志；SNAP：Follower zxid 远小于 Leader，发送完整快照全量同步。 |
| 缺点 | SNAP 全量同步耗时长；大量节点同时 SNAP 同步增加 Leader 压力。 |

### 1. 简述 ZooKeeper 的 Watcher 机制及其一次性特性。

| 维度 | 内容 |
|------|------|
| 是什么 | Watcher 是事件监听机制，一次性特性指每个 Watcher 只触发一次，收到通知后自动失效。 |
| 能做什么 | 监听节点数据变更、创建、删除、子节点变化；Curator 的 NodeCache 等自动处理反复注册。 |
| 怎么用 | `zk.getData(path, watcher)` 注册后在回调中重新注册；Curator 的 NodeCache/PathChildrenCache/TreeCache 自动处理。 |
| 原理和工作流程 | 客户端注册 Watcher 存入服务端 WatchManager；数据变更触发事件通知后删除 Watcher；一次性设计简化服务端状态管理；Curator 的三种缓存封装了反复注册逻辑。 |
| 缺点 | 一次性触发增加客户端复杂度；通知不含数据需额外拉取；大量 Watcher 导致通知风暴。 |

### 2. 简述 ZooKeeper 中临时节点和持久节点的区别及各自适用场景。

| 维度 | 内容 |
|------|------|
| 是什么 | 临时节点与会话绑定会话结束自动删除，持久节点显式删除前一直存在。 |
| 能做什么 | 临时节点用于服务注册、分布式锁、存活检测；持久节点用于配置信息、服务元数据。 |
| 怎么用 | 临时：`create -e /path data`；持久：`create /path data`。 |
| 原理和工作流程 | 临时节点不能拥有子节点，会话超时或主动关闭后自动删除；持久节点可拥有子节点，显式删除前一直存在；临时节点适合与客户端生命周期绑定的场景，持久节点适合存储不随客户端变化的元数据。 |
| 缺点 | 临时节点不能有子节点；会话超时时间较长时故障检测延迟大；持久节点需手动清理避免残留。 |

### 3. 简述 ZooKeeper 的 ZAB 协议中消息广播的两阶段提交流程。

| 维度 | 内容 |
|------|------|
| 是什么 | 消息广播是 ZAB 协议正常模式，Leader 通过两阶段提交（Proposal + ACK、Commit）广播事务。 |
| 能做什么 | 阶段一 Leader 广播 Proposal，Follower 写入日志返回 ACK；阶段二过半 ACK 后 Leader 发送 Commit 所有节点应用事务。 |
| 怎么用 | 集群自动运行，无需手动干预；支持流水线化连续发送多个 Proposal。 |
| 原理和工作流程 | 阶段一：Leader 生成 Proposal 广播给 Follower，Follower 写入本地事务日志返回 ACK；阶段二：Leader 收到过半 ACK 后发送 Commit，所有节点应用事务到内存；与经典 2PC 相比支持流水线化、自动选举、过半机制容忍少数节点故障。 |
| 缺点 | 需等待过半 ACK 增加延迟；Follower 同步写入事务日志增加开销；Leader 为写操作单点瓶颈。 |

### 4. 简述 ZooKeeper 集群的三种角色及其职责。

| 维度 | 内容 |
|------|------|
| 是什么 | Leader、Follower、Observer 三种角色分别承担写处理、投票参与、读扩展等不同职责。 |
| 能做什么 | Leader 唯一写处理器广播 Proposal；Follower 参与选举和投票同步数据处理读请求；Observer 同步数据处理读请求不参与投票。 |
| 怎么用 | 配置 `server.{myid}` 指定节点，Observer 额外配置 `peerType=observer`。 |
| 原理和工作流程 | Leader 处理所有写请求并广播；Follower 转发写请求给 Leader 参与过半确认和选举；Observer 引入原因：扩展读能力不影响写性能、跨数据中心部署降低延迟、减少选举通信开销。 |
| 缺点 | Leader 为单点瓶颈；Follower 增多增加事务延迟；Observer 不提升容错。 |

### 5. 简述 ZooKeeper 如何避免脑裂问题。

| 维度 | 内容 |
|------|------|
| 是什么 | 通过过半机制、epoch 机制、Quorum 检查三重防护避免网络分区后出现多个 Leader。 |
| 能做什么 | 过半机制使少数派无法凑够票数自动退位；epoch 机制使旧 Leader 发现 epoch 落后自动降级；Quorum 检查使 Follower 超时后发起重新选举。 |
| 怎么用 | 集群自动防范脑裂，确保网络稳定降低分区风险。 |
| 原理和工作流程 | 过半机制确保任何决策需超过半数同意，网络分区后少数派自动退位拒绝服务；epoch 每次选举递增，旧 Leader 发现 epoch 落后自动降级并同步数据；Follower 定期检查 Leader 连接超时则发起重新选举。 |
| 缺点 | 网络分区期间少数派无法服务；网络抖动可能导致频繁选举；跨机房延迟可能被误判为分区。 |

### 6. 简述 ZooKeeper 的本地文件存储架构及重启恢复流程。

| 维度 | 内容 |
|------|------|
| 是什么 | 内存数据树加事务日志加快照的三层存储架构，重启时加载快照再回放日志恢复完整状态。 |
| 能做什么 | 内存数据树加速读写；WAL 事务日志保证不丢失；快照加速重启恢复。 |
| 怎么用 | 配置 `dataDir` 和 `dataLogDir`；`snapCount=100000` 控制快照频率；`autopurge` 开启自动清理。 |
| 原理和工作流程 | 内存 DataTree 存储所有 ZNode 数据提供快速读写；事务日志预写 WAL 先落盘再改内存；快照事务累积超 snapCount 时异步生成；重启时先加载最近快照恢复基础状态，再按序回放快照之后的事务日志恢复完整状态。 |
| 缺点 | 内存数据树受内存容量限制；fsync 为写操作瓶颈；未开启自动清理磁盘耗尽。 |

### 7. 简述 ZooKeeper 分布式锁与 Redis 分布式锁的优缺点对比。

| 维度 | 内容 |
|------|------|
| 是什么 | 两种分布式锁方案在一致性、性能、公平性、自动释放、惊群效应上的差异。 |
| 能做什么 | ZooKeeper 强一致原生公平锁；Redis 高性能弱一致；根据场景选型。 |
| 怎么用 | 强一致性场景选 ZooKeeper；高并发可容忍短暂不一致选 Redis。 |
| 原理和工作流程 | ZooKeeper：临时节点加 Watcher 实现，CP 架构保证一致性，公平锁基于临时有序节点，会话超时自动释放；Redis：SETNX 加 Lua 脚本实现，AP 架构主从切换可能丢锁，看门狗续期加 TTL 过期，Redisson 已封装。 |
| 缺点 | ZooKeeper 性能低；Redis 一致性弱可能丢锁；两者各有适用边界。 |

### 8. 简述 ZooKeeper 中 Stat 结构体的版本号机制及其乐观锁实现。

| 维度 | 内容 |
|------|------|
| 是什么 | 每个 ZNode 维护 version、cversion、aversion 三个版本号，通过 CAS 比较实现乐观锁。 |
| 能做什么 | version 控制数据更新并发；cversion 控制子节点增删并发；aversion 控制 ACL 修改并发；避免丢失更新。 |
| 怎么用 | `Stat stat = new Stat(); zk.getData("/path", false, stat); zk.setData("/path", newData, stat.getVersion());` |
| 原理和工作流程 | 读取时获取当前 version；更新时传入期望 version；服务端比较期望与当前版本号，匹配则成功并递增，不匹配抛出 BadVersionException；客户端捕获异常后重新读取版本号并重试。 |
| 缺点 | 并发冲突频繁时重试增加；不适用于跨节点原子操作；客户端需自行实现重试。 |

### 1. 分布式锁系统设计

| 维度 | 内容 |
|------|------|
| 是什么 | 基于临时有序节点和 Curator InterProcessSemaphoreMutex 的公平锁方案，实现库存扣减互斥访问。 |
| 能做什么 | 公平锁先到先得；会话超时自动释放避免死锁；ZK 5 节点集群高可用；锁路径按 productId 隔离。 |
| 怎么用 | `InterProcessSemaphoreMutex(client, "/locks/inventory/" + productId)` 获取锁，`acquire(5, TimeUnit.SECONDS)` 超时等待，`release()` 释放锁。 |
| 原理和工作流程 | 所有客户端在 `/locks/inventory/{productId}/` 下创建临时有序节点，序号最小者获锁；其他客户端监听前一个节点删除事件；客户端宕机会话超时临时节点自动删除，下一个客户端自动获锁；ZK 5 节点集群过半机制容忍 2 节点故障。 |
| 缺点 | 性能低于 Redis 锁；锁竞争激烈时频繁创建删除节点增加 ZK 压力；需合理设置 acquire 超时避免线程长时间阻塞。 |

### 2. 配置中心系统设计

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 ZooKeeper TreeCache 的配置中心方案，实现配置集中管理、实时推送、历史回滚、审计日志。 |
| 能做什么 | 配置按服务隔离（/config/{serviceName}/）；TreeCache 监听整个子树实时推送；持久有序节点保存历史版本支持回滚；审计日志记录操作人和时间。 |
| 怎么用 | 注入 ConfigCenter，`getConfig(path)` 读配置，`addListener(path, listener)` 注册变更回调，`publishConfig(path, value, operator)` 发布配置，`rollback(path, version)` 回滚。 |
| 原理和工作流程 | 配置存储结构：/config/common/ 公共配置、/config/{serviceName}/ 服务专属配置覆盖公共、/config/history/ 历史版本持久有序节点、/config/audit/ 审计日志带时间戳；TreeCache 监听 /config 子树所有变更，变更时更新本地缓存并通知监听器；发布时同时记录历史版本和审计日志；回滚时读取指定版本数据重新发布。 |
| 缺点 | 无内置 Web 管理界面需自行开发；灰度发布需自行实现；TreeCache 监听大量节点内存占用高；配置数量大时 ZK 集群压力增大。 |
