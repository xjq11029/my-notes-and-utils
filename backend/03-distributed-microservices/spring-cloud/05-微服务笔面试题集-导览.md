### 1. 以下关于 CAP 定理的描述，正确的是（ ）

| 维度 | 内容 |
|------|------|
| 是什么 | 分布式系统在网络分区时需在一致性与可用性间取舍的定理 |
| 能做什么 | 阐明 C/A/P 三者最多同时满足两个；指出 P 为客观存在非可选项；区分线性一致性与最终一致性 |
| 怎么用 | `网络分区(P)发生 -> 在 C 与 A 间取舍` |
| 原理和工作流程 | CAP 定理指出分布式系统最多同时满足一致性（C，特指线性一致性）、可用性（A）、分区容错性（P）中的两个。当网络分区（P）发生时，必须在 C 和 A 之间做取舍。P 是网络分区的客观存在不是可选项，数学证明最多同时满足两个属性 |
| 缺点 | CAP 为粗粒度理论，实际系统多为混合模式（如 Nacos AP/CP 可切换）；过于简化忽略延迟与分区恢复细节；强一致定义严格，工程中常放宽 |

| 维度 | 内容 |

| 缺点 | 心跳间隔固定，网络抖动易误剔除；高频心跳增加网络与服务端开销；永久实例不适用此机制 |

### 9. Sentinel 熔断器的三种状态不包括（ ）

| 怎么用 | `CLOSED -> OPEN -> HALF_OPEN -> CLOSED/OPEN` |
| 原理和工作流程 | 熔断器三种状态：CLOSED（正常通过，统计指标）、OPEN（拒绝所有请求，抛出 DegradeException）、HALF_OPEN（放行少量探测请求，试探服务是否恢复）。DEGRADED 不是熔断器状态名 |
| 缺点 | 状态转换依赖阈值配置，配置不当误熔断；HALF_OPEN 探测期间仍有请求受影响；状态机缺乏手动控制 |

### 1. 简述 CAP 定理的含义，并说明 Nacos 如何体现 CAP 选择

| 维度 | 内容 |
|------|------|
| 是什么 | CAP 定理含义及 Nacos 通过实例类型体现 AP/CP 选择的机制 |
| 能做什么 | 阐述 C/A/P 三者关系；说明 Nacos 临时实例走 AP；说明永久实例走 CP；区分服务发现与配置中心模式 |
| 怎么用 | `CAP最多满足两个 | 临时实例AP(Distro) | 永久实例CP(Raft)` |
| 原理和工作流程 | CAP 定理指出分布式系统最多同时满足一致性（C）、可用性（A）、分区容错性（P）中的两个。Nacos 通过实例类型区分：临时实例走 AP 模式（Distro 协议，保证可用性，最终一致性），永久实例走 CP 模式（Raft 协议，保证强一致性，牺牲部分可用性）。配置中心使用 CP 模式，服务发现使用 AP 模式 |
| 缺点 | CAP 为粗粒度理论，Nacos 混合模式增加理解复杂度；AP 最终一致存在数据不一致窗口；CP 牺牲可用性 |

### 2. 简述 Nacos 作为注册中心的核心流程

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 注册中心从服务注册到被消费者调用的完整流程 |
| 能做什么 | 提供者注册与心跳；服务端健康检查与剔除；消费者订阅与变更通知；负载均衡调用 |
| 怎么用 | `注册 -> 心跳5s -> 检查15s不健康/30s剔除 -> 订阅推送 -> 负载均衡` |
| 原理和工作流程 | 服务提供者启动时向 Nacos 注册（IP + Port + 元数据）；客户端每 5s 发送心跳维持注册；Nacos 服务端每 5s 检查，15s 未收到心跳标记不健康，30s 未收到剔除实例；服务消费者订阅服务后 Nacos 推送实例变更通知，消费者从健康实例列表负载均衡选择调用 |
| 缺点 | 注册与剔除存在时间窗口延迟；心跳异常导致误剔除；推送依赖网络质量 |

### 3. 简述 Sentinel 的熔断降级机制

| 维度 | 内容 |
|------|------|
| 是什么 | Sentinel 熔断器三态转换与三种熔断策略的机制 |
| 能做什么 | CLOSED 正常统计；OPEN 拒绝请求；HALF_OPEN 探测恢复；慢调用/异常比例/异常数三种策略 |
| 怎么用 | `CLOSED -> OPEN(触发) -> HALF_OPEN(时间窗结束) -> CLOSED/OPEN` |
| 原理和工作流程 | 熔断器三态：CLOSED（正常通过，统计指标）、OPEN（拒绝所有请求，抛出 DegradeException）、HALF_OPEN（放行少量探测请求，试探服务是否恢复）。三种熔断策略：慢调用比例（响应时间超阈值的请求比例）、异常比例、异常数。熔断时间窗口结束后自动进入 HALF_OPEN |
| 缺点 | 阈值配置不当误熔断或保护失效；HALF_OPEN 探测期间请求受影响；规则默认存内存重启丢失 |

### 4. 简述 Spring Cloud Gateway 的请求处理流程

| 维度 | 内容 |
|------|------|
| 是什么 | Gateway 从接收请求到返回响应的完整处理链路 |
| 能做什么 | Netty 接收；路由匹配；Pre 过滤；转发后端；Post 过滤；响应返回 |
| 怎么用 | `客户端 -> Netty -> RouteLocator -> Predicate -> PreFilter -> 后端 -> PostFilter -> 客户端` |
| 原理和工作流程 | 客户端请求到达 Netty Server 接收，RouteLocator 按 Predicate 条件匹配路由，匹配成功进入 Filter Chain；Pre Filter 执行鉴权限流添加请求头，转发到后端服务；后端返回响应后 Post Filter 执行添加响应头记录日志，最终返回客户端 |
| 缺点 | 过滤器链过长增加延迟；路由匹配随路由数增长效率下降；异步链路异常堆栈难追踪 |

### 5. 简述 Seata AT 模式的两阶段提交流程

| 维度 | 内容 |
|------|------|
| 是什么 | Seata AT 模式两阶段提交的详细执行步骤 |
| 能做什么 | 第一阶段执行 SQL 与记录 undo_log；第二阶段提交删除日志或回滚反向 SQL |
| 怎么用 | `阶段1:SQL+undo_log同事务 | 阶段2:提交删日志/回滚反向SQL` |
| 原理和工作流程 | 第一阶段：TM 开启全局事务获得 XID，RM 执行原始 SQL 并生成 undo_log（记录回滚 SQL），在同一本地事务提交，RM 向 TC 注册分支事务。第二阶段提交：TC 通知各 RM 提交，RM 异步删除 undo_log。第二阶段回滚：TC 通知各 RM 回滚，RM 读取 undo_log 执行反向 SQL，删除 undo_log |
| 缺点 | 第一阶段 undo_log 写入增加事务时长；回滚期间数据中间态；异步删除失败需补偿 |

### 6. 简述 Nacos 2.x 相比 1.x 的核心变化

### 7. 简述 Sentinel 的 8 个 Slot 责任链及其顺序

| 维度 | 内容 |
|------|------|
| 是什么 | Sentinel 责任链中 8 个 Slot 的执行顺序与职责 |
| 能做什么 | 构建调用树；集群统计；日志记录；核心统计；黑白名单；系统保护；流量控制；熔断降级 |
| 怎么用 | `NodeSelector -> ClusterBuilder -> Log -> Statistic -> Authority -> System -> Flow -> Degrade` |
| 原理和工作流程 | 8 个 Slot 顺序：NodeSelectorSlot（构建调用树）-> ClusterBuilderSlot（构建集群统计）-> LogSlot（记录异常日志）-> StatisticSlot（核心统计 QPS、RT、异常）-> AuthoritySlot（黑白名单）-> SystemSlot（系统保护）-> FlowSlot（流量控制）-> DegradeSlot（熔断降级）。StatisticSlot 是统计核心，FlowSlot 和 DegradeSlot 分别负责限流和熔断 |
| 缺点 | Slot 链固定缺乏灵活扩展；8 个 Slot 顺序需记忆；自定义 Slot 集成复杂度高 |

### 8. 简述微服务架构的优缺点

| 怎么用 | `优点:独立部署/技术灵活/可扩展/故障隔离/团队自治 | 缺点:分布式复杂/运维高/调试难/一致性挑战` |

### 10. 简述 Sentinel 和 Hystrix 的核心区别

| 维度 | 内容 |
|------|------|
| 是什么 | Sentinel 与 Hystrix 在隔离策略、熔断策略、流控能力上的区别 |
| 能做什么 | 对比隔离策略；对比熔断策略；对比流控能力；对比规则配置；对比维护状态 |
| 怎么用 | `Sentinel:信号量+三种熔断+流控+控制台+活跃 | Hystrix:线程池+异常比例+无流控+硬编码+停更` |
| 原理和工作流程 | 隔离策略：Sentinel 信号量隔离，Hystrix 线程池/信号量隔离；熔断策略：Sentinel 支持慢调用比例/异常比例/异常数三种，Hystrix 仅异常比例；流控：Sentinel 支持丰富流控（QPS/线程数/热点），Hystrix 不支持；规则配置：Sentinel 控制台实时下发，Hystrix 代码硬编码；维护：Sentinel 持续维护，Hystrix 已停更 |
| 缺点 | Sentinel 信号量隔离无法线程级隔离；Hystrix 已停更无社区支持；两者均有学习配置成本 |

### 1. 设计一个微服务网关统一鉴权方案

| 维度 | 内容 |
|------|------|
| 是什么 | 在网关层通过 GlobalFilter 统一校验 JWT Token 并透传用户信息的鉴权方案设计 |
| 能做什么 | 白名单放行；JWT 校验；用户信息透传；Token 非对称加密；动态白名单 |
| 怎么用 | `GlobalFilter(Order=-100) + 白名单(Nacos) + RSA公钥校验 + X-User-Id透传` |
| 原理和工作流程 | 客户端请求到达 Gateway，GlobalFilter 拦截所有请求；判断路径是否在白名单（登录、注册、公开接口），白名单直接转发，非白名单提取 Authorization Header；校验 JWT Token，无效过期返回 401，有效解析用户信息添加到请求头（X-User-Id、X-User-Name）；透传下游服务。关键设计点：Order 设 -100 最先执行，白名单配置在 Nacos 支持动态更新，Token 用 RSA 非对称加密网关只持公钥，下游通过请求头获取用户信息无需解析 Token |
| 缺点 | 网关承担鉴权增加单点压力；白名单变更依赖配置中心可用性；Token 泄露网关层无法识别需配合过期刷新 |

### 2. 设计一个秒杀系统的流量控制方案

| 维度 | 内容 |
|------|------|
| 是什么 | 秒杀场景下网关层与服务层多级限流熔断的综合流量控制方案 |
| 能做什么 | 网关层 QPS 限流与 IP 限流；服务层接口限流；热点参数限流；熔断降级 |
| 怎么用 | `网关Sentinel(QPS1000/IP10) + 服务@SentinelResource(QPS100) + 热点商品限流 + 熔断(RT200ms/异常30%)` |
| 原理和工作流程 | 网关层限流：Gateway + Sentinel 网关限流，QPS 限制 1000 超出返回提示，按 IP 限流每秒最多 10 次。服务层限流：秒杀接口用 @SentinelResource 配置流控规则，QPS 限制 100（扣减库存瓶颈），超出快速失败返回已售罄。热点参数限流：针对热门商品 ID 单独限流，商品 ID=100 限 QPS=50。熔断降级：库存服务 RT 超 200ms 或异常比例超 30% 触发熔断，30s 后半开探测恢复 |
| 缺点 | 多级限流参数调优复杂；热点参数限流需预设热门商品；熔断阈值不当导致误熔断或保护失效 |

### 3. 设计一个跨服务下单的分布式事务方案

| 维度 | 内容 |
|------|------|
| 是什么 | 跨订单、账户、库存三服务的分布式事务一致性方案设计 |
| 能做什么 | 全局事务协调；分支事务 undo_log；任一失败全局回滚；TC 重试保证最终一致 |
| 怎么用 | `@GlobalTransactional + 订单INSERT + 账户UPDATE + 库存UPDATE + undo_log回滚` |
| 原理和工作流程 | 订单服务使用 @GlobalTransactional 注解开启全局事务。全局事务流程：订单服务 INSERT INTO orders（分支事务 1），账户服务 UPDATE account 扣余额（分支事务 2），库存服务 UPDATE inventory 减库存（分支事务 3）。每个分支事务在同一本地事务生成 undo_log。任一分支失败 TC 触发全局回滚，各 RM 读取 undo_log 执行反向 SQL；全部成功 TC 触发全局提交，各 RM 异步删除 undo_log。补偿设计：库存不足抛异常自动回滚，余额不足抛异常自动回滚，网络超时靠 TC 重试保证最终一致 |
| 缺点 | 全局锁限制并发性能；长事务持锁影响吞吐；非关系型数据库不适用 AT 模式 |

### 4. 设计一个配置中心灰度发布方案

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Nacos 标签实现配置灰度发布的功能开关方案设计 |
| 能做什么 | 按实例标签灰度；部分实例先生效；验证后全量发布；异常一键回滚 |
| 怎么用 | `Nacos配置(Feature开关) + 实例标签(version=v2) + 灰度配置(标签v2) + @ConfigurationProperties刷新` |
| 原理和工作流程 | 在 Nacos 创建配置 Data ID 为 feature-switch.yaml，Group 为 FEATURE_GROUP，内容 feature.new.enabled: false。按标签灰度：10% 实例打标签 version=v2，创建灰度配置 Data ID 相同 Group 相同标签 v2，内容 feature.new.enabled: true。验证通过后全量发布：修改默认配置为 true，删除灰度配置。关键设计点：用 @ConfigurationProperties 绑定配置天然支持动态刷新，通过 @EventListener 监听 RefreshScopeRefreshedEvent 打印日志，灰度期间监控错误率异常时一键回滚 |

### 5. 设计一个微服务监控告警方案

| 维度 | 内容 |
|------|------|
| 是什么 | 覆盖健康检查、指标采集、链路追踪、日志收集、告警通知的综合监控方案设计 |
| 能做什么 | 健康检查；指标采集；链路追踪；日志收集；多级告警规则 |
| 怎么用 | `Actuator+Prometheus+SkyWalking+ELK+AlertManager` |
| 原理和工作流程 | 监控体系：健康检查用 Spring Boot Actuator 加 Nacos 健康检查；指标采集用 Micrometer 加 Prometheus 拉取；链路追踪用 SkyWalking 采集调用链；日志收集用 ELK；告警通知用 Prometheus AlertManager 推送钉钉短信。核心指标：服务可用性（健康实例数/总实例数）、接口 QPS（Sentinel Dashboard）、接口 RT（P99）、错误率（5xx 占比）、熔断状态。告警规则：服务不可用（健康实例数<1 持续 30s 紧急）、错误率>5% 持续 1 分钟警告、P99 RT>1000ms 持续 5 分钟警告、熔断器 OPEN 立即告警、消费 Lag>10000 持续 5 分钟警告 |
| 缺点 | 监控体系组件多运维成本高；告警规则阈值需持续调优避免告警风暴；全链路采集性能开销大 |
