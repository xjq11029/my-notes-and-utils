## 一、核心概念

### 1.1 单体架构到微服务架构演进

| 维度 | 内容 |
|------|------|
| 是什么 | 软件架构从所有功能打包单包部署，演进到按业务领域拆分独立部署的分布式形态，经历单体、SOA、微服务三个阶段 |
| 能做什么 | 按业务边界拆分服务；每个服务独立部署与技术选型；实现故障隔离与按需扩缩容；支撑团队自治开发 |
| 怎么用 | `单体 -> SOA(ESB集成) -> 微服务(独立部署+轻量通信)` |
| 原理和工作流程 | 单体架构所有模块编译为一个包部署，耦合高、扩展难；SOA 通过 ESB 总线集成服务，复用性提升但 ESB 成为瓶颈；微服务按业务领域拆分，每个服务拥有独立数据存储，通过 REST/gRPC 轻量通信，独立部署与扩展。核心原则为单一职责、自治性、去中心化、容错设计（熔断降级限流） |
| 缺点 | 分布式复杂性高，网络通信、数据一致性、分布式事务处理困难；运维成本激增，需服务发现、配置中心、监控、链路追踪等基础设施；跨服务调试排查困难 |

### 1.2 Spring Cloud Alibaba vs Spring Cloud Netflix

| 维度 | 内容 |
|------|------|
| 是什么 | 阿里巴巴开源的微服务组件套件，替代已停更的 Spring Cloud Netflix，成为当前主流选型 |
| 能做什么 | 提供注册配置中心 Nacos；流量治理 Sentinel；分布式事务 Seata；网关 Gateway；消息队列 RocketMQ；RPC 框架 Dubbo |
| 怎么用 | `注册:Nacos | 限流:Sentinel | 事务:Seata | 网关:Gateway` |
| 原理和工作流程 | Netflix 套件核心组件 Eureka、Ribbon、Hystrix、Zuul 已全部停更；Alibaba 套件对应组件持续维护，注册中心由 Eureka 换为 Nacos，限流熔断由 Hystrix 换为 Sentinel，负载均衡由 Ribbon 换为 Spring Cloud LoadBalancer，网关由 Zuul 换为 Gateway，并新增分布式事务 Seata |
| 缺点 | 组件强绑定阿里生态，部分组件文档以中文为主，国际化支持弱于 Netflix；版本与 Spring Cloud 升级节奏需手动对齐，存在兼容性风险 |

### 1.3 核心组件全景

| 维度 | 内容 |
|------|------|
| 是什么 | Spring Cloud Alibaba 生态六大核心组件的功能定位与替代方案总览 |
| 能做什么 | Nacos 服务发现与配置管理；Sentinel 流量控制与熔断降级；Seata 分布式事务；Gateway 路由转发鉴权限流；RocketMQ 消息中间件；Dubbo 高性能 RPC |
| 怎么用 | `Nacos(注册+配置) | Sentinel(流控) | Seata(事务) | Gateway(网关)` |
| 原理和工作流程 | 六大组件分工协作：Nacos 同时承担注册中心与配置中心，替代 Eureka+Apollo；Sentinel 通过滑动窗口统计与规则引擎实现流控熔断；Seata 基于 AT/TCC/Saga 模式解决分布式事务；Gateway 基于 WebFlux 非阻塞模型实现 API 网关；RocketMQ 提供事务顺序延迟消息；Dubbo 提供高性能 RPC 与服务治理 |
| 缺点 | 组件间存在功能重叠（如 Dubbo 与 OpenFeign 都可做服务调用），选型需权衡；全量引入组件增加学习与运维成本 |

## 二、底层原理

### 2.1 服务注册发现原理

| 维度 | 内容 |
|------|------|
| 是什么 | 服务提供者将自身地址注册到注册中心，消费者订阅并获取实例列表以发起调用的机制 |
| 能做什么 | 动态注册服务实例；健康检查与自动剔除；变更通知推送；消费者负载均衡选实例 |
| 怎么用 | `provider注册(IP+Port+元数据) -> consumer订阅拉取 -> 负载均衡调用` |
| 原理和工作流程 | 提供者启动时向注册中心注册 IP、Port 与元数据；注册中心存储实例信息；消费者订阅服务并拉取实例列表；实例上下线时注册中心推送变更通知；消费者通过负载均衡策略选择实例发起调用。Nacos 临时实例客户端每 5s 发心跳，15s 未收到标记不健康，30s 剔除。注册中心对比：Nacos 支持 AP/CP 切换，Eureka 为 AP，Consul/ZooKeeper 为 CP |
| 缺点 | 依赖注册中心可用性，注册中心宕机影响服务发现；实例列表存在短暂不一致窗口；心跳机制带来额外网络开销 |

### 2.2 Nacos AP vs CP 模式

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 通过实例类型区分使用 Distro（AP）或 Raft（CP）一致性协议的两种工作模式 |
| 能做什么 | 临时实例走 AP 保证高可用；永久实例走 CP 保证强一致；同一集群可混合使用两种模式 |
| 怎么用 | `ephemeral=true(AP/Distro) | ephemeral=false(CP/Raft)` |
| 原理和工作流程 | AP 模式采用阿里自研 Distro 协议，对等节点设计，每个节点平等处理读写，数据分片后先写本地再异步同步，保证最终一致性与高可用；CP 模式采用 Raft 算法，写入必须经过 Leader，通过 Leader 同步半数以上节点，保证强一致性但 Leader 选举期间短暂不可用。临时实例默认 AP，永久实例与配置变更走 CP |
| 缺点 | AP 模式仅最终一致，存在短暂数据不一致窗口；CP 模式 Leader 故障期间集群短暂不可用；模式切换需理解实例类型语义 |

### 2.3 Sentinel 滑动窗口限流算法

| 维度 | 内容 |
|------|------|
| 是什么 | Sentinel 默认采用 LeapArray 滑动窗口算法统计单位时间内的请求量以实现流量控制 |
| 能做什么 | 统计 QPS 与线程数；控制突发流量；支持预热与匀速排队；驱动熔断器三态转换 |
| 怎么用 | `LeapArray(滑动窗口) | WarmUpController(令牌桶预热) | RateLimiterController(漏桶匀速)` |
| 原理和工作流程 | 滑动窗口将时间区间切分为多个小窗口（默认 1s 分 2 个 500ms 窗口），滑动时丢弃过期窗口数据，统计当前窗口内请求数。令牌桶以固定速率放令牌允许突发；漏桶以固定速率流出严格限速。熔断器三态：CLOSED 正常统计，触发条件后转 OPEN 拒绝所有请求，熔断时间窗结束后转 HALF_OPEN 放行探测请求，探测成功回 CLOSED、失败回 OPEN |
| 缺点 | 滑动窗口存在窗口边界精度问题，临界突发可能被放过；窗口统计占用内存，窗口数过多增加开销；熔断探测期间仍有少量请求受影响 |

### 2.4 Seata AT 模式两阶段提交

| 维度 | 内容 |
|------|------|
| 是什么 | Seata 最常用的分布式事务模式，基于改进的两阶段提交协议，通过自动生成 undo_log 实现无侵入回滚 |
| 能做什么 | 自动记录回滚日志；跨服务事务统一提交或回滚；业务代码零侵入；保证最终一致性 |
| 怎么用 | `@GlobalTransactional + undo_log表` |
| 原理和工作流程 | 第一阶段 TM 向 TC 开启全局事务获得 XID，RM 执行原始业务 SQL 并生成 undo_log（记录回滚 SQL），业务 SQL 与 undo_log 在同一本地事务提交，RM 向 TC 注册分支事务报告成功。第二阶段提交时 TC 通知各 RM 异步删除 undo_log；回滚时 RM 读取 undo_log 执行反向 SQL 后删除 undo_log。undo_log 表存储 branch_id、xid、rollback_info 等字段 |
| 缺点 | 第二阶段提交前需持有全局锁，并发性能受限；undo_log 增加存储与写入开销；仅支持关系型数据库，依赖 ACID 事务；长事务持锁影响吞吐 |

## 三、实战应用

### 3.1 微服务拆分原则

| 维度 | 内容 |
|------|------|
| 是什么 | 将单体应用按业务领域拆分为多个独立部署服务的指导准则 |
| 能做什么 | 按业务边界划分服务；控制服务粒度；保证数据独立；定义清晰 API 契约；逐步拆分 |
| 怎么用 | `用户服务 | 商品服务 | 订单服务 | 支付服务 | 物流服务` |
| 原理和工作流程 | 拆分以业务领域为边界而非技术层面；服务粒度适中，太细增加运维成本太粗失去优势；每个服务拥有独立数据库不共享；定义清晰 API 契约通过 API 通信；从单体逐步拆分，优先拆分变化频繁模块。电商系统典型拆分为用户、商品、订单、支付、物流等服务 |
| 缺点 | 拆分粒度难以把握，过度拆分导致运维复杂度激增与跨服务调用延迟；数据独立后跨服务查询与事务处理复杂；逐步拆分过程中存在过渡期双重维护 |

### 3.2 Nacos 配置中心动态刷新

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 配置变更后无需重启即可让应用感知新配置并生效的机制 |
| 能做什么 | 配置集中管理；变更实时推送；Bean 动态重建；多环境隔离 |
| 怎么用 | `@RefreshScope+@Value | @ConfigurationProperties(天然刷新)` |
| 原理和工作流程 | 两种方式：@RefreshScope + @Value 通过代理模式，配置变更后清除 refresh 作用域缓存，下次访问重新创建 Bean；@ConfigurationProperties 天然支持动态刷新。刷新流程：Nacos 长轮询检测到配置变更，触发 RefreshEvent 事件，ContextRefresher.refresh() 清除缓存，下次访问时重新创建 Bean 使用新配置 |
| 缺点 | @RefreshScope 重建 Bean 有短暂延迟且仅对该 Bean 生效；长轮询存在最长 30s 感知延迟；大规模配置变更触发大量重建影响性能 |

### 3.3 Gateway 统一鉴权

| 维度 | 内容 |
|------|------|
| 是什么 | 在网关层通过 GlobalFilter 拦截所有请求统一校验 JWT Token 并透传用户信息的方案 |
| 能做什么 | 统一身份校验；白名单放行；Token 解析与用户信息透传；高优先级先执行 |
| 怎么用 | `GlobalFilter+Ordered(getOrder=-100)` |
| 原理和工作流程 | 实现 GlobalFilter 与 Ordered 接口，getOrder 返回 -100 保证最先执行。流程：获取请求路径，白名单路径直接放行；提取 Authorization Header 中的 Token，缺失则返回未授权；JwtUtil 解析 Token，校验失败返回未授权；解析成功后将 userId、userName 通过 mutate 写入请求头透传下游服务，chain.filter 放行 |
| 缺点 | 网关承担鉴权逻辑增加单点压力，Token 解析消耗 CPU；白名单配置变更需重启或依赖配置中心；Token 泄露后网关层无法识别，需配合过期与刷新机制 |

### 3.4 Sentinel 降级规则配置

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 DegradeRule 配置熔断策略，在服务异常或响应变慢时自动切断请求的保护机制 |
| 能做什么 | 慢调用比例熔断；异常比例熔断；异常数熔断；熔断时长与统计窗口可配 |
| 怎么用 | `DegradeRule.setGrade(SLOW_REQUEST_RATIO).setCount(200)` |
| 原理和工作流程 | 通过 @PostConstruct 初始化 DegradeRule，设置资源名、熔断策略、阈值、最小请求数、统计窗口与熔断时长，DegradeRuleManager.loadRules 加载。三种策略：慢调用比例（响应时间超阈值的请求比例超阈值触发）、异常比例（异常调用比例超阈值）、异常数（分钟级异常数超阈值）。熔断时长结束进入半开探测 |
| 缺点 | 规则默认存内存，重启丢失需持久化到 Nacos；阈值设置不当导致误熔断或保护失效；统计窗口内的最小请求数过小易被偶发异常触发 |

## 四、常见面试题

### 1. 微服务架构的优缺点？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查微服务架构相比单体架构的优势与代价的对比认知 |
| 能做什么 | 阐述独立部署、技术栈灵活、高可扩展、故障隔离、团队自治等优势；指出分布式复杂性、运维成本、调试困难等代价 |
| 怎么用 | `优点:独立部署/技术灵活/可扩展/故障隔离 | 缺点:分布式复杂/运维高/调试难` |
| 原理和工作流程 | 优势源于服务独立部署与技术去中心化，每个服务可独立构建测试部署，热点服务单独扩容，故障隔离互不影响；代价源于分布式引入的网络通信、数据一致性、分布式事务复杂性，以及服务发现、配置中心、监控、链路追踪等基础设施的运维成本，跨服务调用链路长导致调试排查困难 |
| 缺点 | 微服务并非银弹，小团队或简单业务引入微服务得不偿失；服务间网络调用增加延迟；分布式事务与数据一致性处理复杂；运维与基础设施门槛高 |

### 2. Nacos 和 Eureka 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Nacos 与 Eureka 两个注册中心在 CAP 模型、健康检查、配置能力等方面的差异 |
| 能做什么 | 对比一致性协议；对比健康检查方式；对比配置中心能力；对比维护状态 |
| 怎么用 | `Nacos:AP/CP可切换+内置配置 | Eureka:AP+无配置+已停更` |
| 原理和工作流程 | Nacos 支持 AP/CP 可切换（Distro/Raft），健康检查为客户端心跳加服务端主动探测，内置配置中心，服务下线主动通知加自动剔除，持续维护；Eureka 为 AP 模型无 Leader 设计，仅客户端心跳，无配置中心，多级缓存更新慢，已停更 |
| 缺点 | Nacos 功能丰富但部署运维比 Eureka 复杂；Eureka 虽简单但已停更无社区支持，新项目不推荐；两者在超大集群下均面临性能瓶颈 |

### 3. Sentinel 和 Hystrix 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Sentinel 与 Hystrix 两个熔断限流组件在隔离策略、流控能力、配置方式上的差异 |
| 能做什么 | 对比隔离策略；对比熔断策略；对比流控能力；对比规则配置与维护状态 |
| 怎么用 | `Sentinel:信号量隔离+流控+控制台下发 | Hystrix:线程池隔离+已停更` |
| 原理和工作流程 | Sentinel 使用信号量隔离，熔断支持慢调用比例/异常比例/异常数三种策略，提供丰富流控（QPS/线程数/热点），控制台实时下发规则，持续维护；Hystrix 支持线程池/信号量隔离，仅异常比例熔断，不支持流控，规则代码硬编码，已停更 |
| 缺点 | Sentinel 信号量隔离无法实现线程级隔离，依赖方故障仍占用调用线程；Hystrix 已停更无社区维护；两者均有学习配置成本 |

### 4. Seata AT 模式和 TCC 模式的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Seata 两种分布式事务模式在侵入性、性能、回滚方式上的差异 |
| 能做什么 | 对比侵入性；对比实现难度；对比性能；对比回滚方式与适用场景 |
| 怎么用 | `AT:无侵入+全局锁+undo_log | TCC:有侵入+无锁+Try/Confirm/Cancel` |
| 原理和工作流程 | AT 模式无侵入，自动生成 undo_log 回滚，有全局锁性能一般，适合大多数场景；TCC 模式有侵入需实现 Try/Confirm/Cancel 三方法，Try 预留资源、Confirm 确认提交、Cancel 取消回滚，无锁性能好，适合高性能要求与自定义资源场景。两者均最终一致 |
| 缺点 | AT 模式全局锁限制并发且仅支持关系型数据库；TCC 模式业务侵入大、开发成本高，需处理空回滚与悬挂等异常场景；两者均无法保证强一致 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 微服务实践中常见错误的现象、原因与解决方案汇总 |
| 能做什么 | 识别过度拆分；防止敏感信息明文存储；避免集群节点不足；规则持久化；网关职责边界控制 |
| 怎么用 | `5-8人维护一服务 | Jasypt加密 | 集群>=3节点 | 规则持久化Nacos` |
| 原理和工作流程 | 过度拆分导致运维复杂度激增，应控制服务数量 10-20 个、5-8 人维护一服务；配置中心明文存敏感信息会泄露，用 Jasypt 加密；Nacos 集群少于 3 节点不满足 Raft 半数存活要求导致不可用；Sentinel 规则默认存内存重启丢失需持久化到 Nacos；Gateway 做复杂业务逻辑会成瓶颈，应专注横切关注点 |
| 缺点 | 避坑经验依赖踩坑积累，缺乏系统化预警机制；部分方案（如加密、集群部署）增加配置与运维成本；规则持久化引入外部依赖增加故障点 |
