## 一、Nacos 整体架构

### 1.1 定位与角色

| 维度 | 内容 |
|------|------|
| 是什么 | 阿里巴巴开源的动态服务发现、配置管理与服务管理平台，在 Spring Cloud Alibaba 中扮演注册中心与配置中心双重角色 |
| 能做什么 | 服务注册与发现；配置集中管理与动态刷新；健康检查与自动剔除；多环境隔离；支持集群部署 |
| 怎么用 | `Server(核心服务端) + Client(SDK) + OpenAPI(REST/gRPC)` |
| 原理和工作流程 | 三层架构：Server 层提供注册中心与配置中心能力并支持集群部署；Client 层为嵌入业务应用的 SDK，负责服务注册、心跳上报、配置拉取与监听；OpenAPI 层通过 HTTP REST 或 gRPC 对外暴露标准 API，非 Java 语言可经 OpenAPI 接入。服务端与客户端通过协议交互完成注册、心跳、配置推送 |
| 缺点 | Server 端需独立部署与运维，集群依赖外部 MySQL 做持久化；Client SDK 与应用耦合，升级需重启应用；双角色合一增加单组件故障影响面 |

### 1.2 Nacos 1.x vs 2.x

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 两个大版本的架构对比，2.x 将通信层从 HTTP 升级为 gRPC 长连接 |
| 能做什么 | 对比通信协议；对比心跳与服务发现机制；对比配置监听方式；对比性能与端口 |
| 怎么用 | `1.x:HTTP短连接+8848 | 2.x:gRPC长连接+8848+9848` |
| 原理和工作流程 | 1.x 通信采用 HTTP 短连接加定时心跳（5s），服务发现靠客户端轮询加 UDP 推送，配置监听用 HTTP 长轮询（30s 超时）；2.x 通信升级为 gRPC 长连接（基于 HTTP/2），实现双向流推送，服务端可主动推送，新增 gRPC 端口 9848（主端口 +1000）。性能提升：注册性能 2 倍，配置查询 3 倍 |
| 缺点 | 2.x 引入 gRPC 端口增加网络配置复杂度，防火墙需放行多端口；长连接占用服务端文件句柄，超大规模连接需调优；1.x 到 2.x 升级存在兼容过渡成本 |

## 二、服务注册与发现

### 2.1 两种实例类型

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 按生命周期管理方式将服务实例分为临时实例与永久实例两类 |
| 能做什么 | 临时实例支持客户端心跳与自动剔除；永久实例支持服务端主动探测与持久保留；按场景选择实例类型 |
| 怎么用 | `ephemeral=true(临时,默认) | ephemeral=false(永久)` |
| 原理和工作流程 | 临时实例（ephemeral=true）由客户端主动上报心跳，间隔 5s，服务端 15s 未收到心跳标记不健康，30s 剔除实例，适用于大部分业务场景；永久实例（ephemeral=false）无心跳，服务端定期主动调用健康检查接口探测，实例下线不自动剔除，适用于数据库、缓存等基础设施服务 |
| 缺点 | 临时实例心跳异常或网络抖动易被误剔除导致调用失败；永久实例不自动剔除，故障实例残留在列表中需人工清理；两种类型混用时一致性协议不同，增加理解成本 |

### 2.2 服务注册流程

| 维度 | 内容 |
|------|------|
| 是什么 | 服务从启动注册到被发现调用的完整交互过程 |
| 能做什么 | 客户端注册与心跳上报；服务端健康检查与状态标记；消费者订阅与变更通知 |
| 怎么用 | `注册 -> 心跳(5s) -> 健康检查(15s不健康/30s剔除) -> 发现推送` |
| 原理和工作流程 | Client 启动时向 Nacos Server 发送注册请求；Client 内部 BeatReactor 线程池每隔 5s 发送心跳；Server 端 ClientBeatCheckTask 每 5s 检查一次，15s 未收到心跳标记不健康，30s 未收到剔除实例；Consumer 订阅服务后 Server 推送实例变更通知，Consumer 从健康实例列表负载均衡选择调用 |
| 缺点 | 注册与剔除存在时间窗口，实例刚下线到消费者感知有延迟；心跳线程池异常会导致实例被误剔除；推送依赖网络质量，丢消息可能造成列表不一致 |

### 2.3 AP 模式 vs CP 模式

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 通过实例注册时的 ephemeral 属性区分使用 Distro（AP）或 Raft（CP）一致性协议 |
| 能做什么 | AP 模式保证高可用与最终一致；CP 模式保证强一致；同一集群混合支持两种模式 |
| 怎么用 | `ephemeral=true -> AP(Distro) | ephemeral=false -> CP(Raft)` |
| 原理和工作流程 | AP 模式采用 Distro 协议，对等节点设计，每个节点平等处理读写，数据分片后先写本地再异步同步，保证最终一致与高可用；CP 模式采用 Raft 算法，写入经 Leader 同步半数以上节点，保证强一致但 Leader 选举期间短暂不可用。普通微服务实例默认 AP，数据库实例与配置变更走 CP |
| 缺点 | AP 模式存在短暂数据不一致窗口，多节点列表可能不一致；CP 模式 Leader 故障期间集群短暂不可用降低可用性；模式选择依赖对实例类型语义的正确理解 |

## 三、配置中心

### 3.1 三层配置隔离

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 通过 Namespace、Group、Data ID 三个层级实现配置的逻辑隔离 |
| 能做什么 | 租户级环境隔离；应用级分组隔离；配置级文件隔离；支持共享配置 |
| 怎么用 | `Namespace(dev/test/prod) > Group(ORDER_GROUP) > Data ID(order-service-dev.yaml)` |
| 原理和工作流程 | Namespace 为租户级隔离，用于环境隔离（dev/test/prod），不同 Namespace 配置完全隔离，配置项填写命名空间 ID（UUID）而非名称；Group 为应用级隔离，按业务模块分组；Data ID 为配置级隔离，对应具体配置文件，命名规则为 `${application.name}-${profiles.active}.${file-extension}` |
| 缺点 | Namespace 使用 UUID 易混淆，填名称而非 ID 是常见错误；层级过多增加配置管理复杂度；跨 Namespace 引用配置需显式声明共享配置 |

### 3.2 长轮询机制

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 1.x 实现配置变更实时推送的机制，客户端发起请求后服务端挂起直到有变更或超时 |
| 能做什么 | 配置变更实时感知；减少无效请求；降低资源消耗；默认 30s 超时 |
| 怎么用 | `Client携带MD5查询 -> Server比较 -> 一致挂起30s/不一致立即返回` |
| 原理和工作流程 | Client 发起配置查询并携带当前配置 MD5 值；Server 比较 MD5，一致（未变更）则挂起请求等待 30s，不一致（已变更）则立即返回新配置；30s 超时返回 304 Not Modified；Client 收到响应后立即发起下一轮长轮询。相比短轮询实时性高且挂起期间不占额外资源 |
| 缺点 | 长轮询存在最长 30s 感知延迟；服务端挂起请求占用连接资源，客户端多配置监听时连接数增长；2.x 已改用 gRPC 双向流，1.x 长轮询机制逐步淘汰 |

### 3.3 配置动态刷新

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 配置变更后应用无需重启即可让新配置生效的机制 |
| 能做什么 | 配置集中管理；变更实时推送；Bean 动态重建；支持 @RefreshScope 与 @ConfigurationProperties 两种方式 |
| 怎么用 | `@RefreshScope+@Value | @ConfigurationProperties(天然刷新)` |
| 原理和工作流程 | @RefreshScope 底层为代理模式，配置变更后清除 refresh 作用域缓存，下次访问时重新创建 Bean；@ConfigurationProperties 天然支持动态刷新。刷新流程：Nacos 配置变更触发 RefreshEvent 事件，ContextRefresher.refresh() 清除缓存，下次访问重建 Bean 使用新配置 |
| 缺点 | @RefreshScope 重建 Bean 有短暂延迟且仅对标注 Bean 生效；@Value 不配合 @RefreshScope 不会刷新是常见陷阱；大规模配置变更触发大量 Bean 重建影响性能 |

## 四、集群部署

### 4.1 生产环境要求

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 生产环境集群部署的必要条件与规范 |
| 能做什么 | 满足 Raft 半数存活要求；保证数据持久化；前端负载均衡；高可用部署 |
| 怎么用 | `>=3节点 + 外部MySQL + Nginx/SLB + cluster.conf` |
| 原理和工作流程 | 至少 3 个节点以满足 Raft 协议半数以上存活要求，避免 2 节点无法选举；使用外部 MySQL 做持久化存储，不能用嵌入式 Derby（仅适用单机开发）；前端通过 Nginx 或 SLB 做负载均衡分发请求；cluster.conf 中配置所有节点 IP 与端口供集群互相发现 |
| 缺点 | 集群部署增加服务器与运维成本；外部 MySQL 成为新的单点需额外保障；节点数与网络分区场景需权衡，少于 3 节点集群不可用 |

### 4.2 接入配置

| 维度 | 内容 |
|------|------|
| 是什么 | 业务应用接入 Nacos 集群的配置方式 |
| 能做什么 | 指定注册中心与配置中心地址；配置命名空间；指定配置格式与分组；引用共享配置 |
| 怎么用 | `server-addr指向VIP + namespace + file-extension + shared-configs` |
| 原理和工作流程 | discovery 与 config 分别配置 server-addr 指向 Nginx VIP，namespace 指定命名空间 ID，file-extension 指定配置文件格式（yaml），group 指定分组；shared-configs 引用公共配置并支持 refresh 动态刷新。客户端通过 VIP 接入集群，长连接维持注册与配置监听 |
| 缺点 | 配置项较多易遗漏，namespace 填名称而非 ID 是常见错误；shared-configs 引用过多增加配置加载耗时；VIP 故障会导致全部客户端断连 |

## 五、常见面试题

### 1. Nacos 如何同时支持 AP 和 CP 两种模式？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Nacos 通过实例类型区分一致性协议的机制 |
| 能做什么 | 临时实例走 AP；永久实例走 CP；配置管理与服务发现可在同一集群分别使用不同模式 |
| 怎么用 | `ephemeral=true(AP/Distro) | ephemeral=false(CP/Raft)` |
| 原理和工作流程 | 通过实例注册时指定 ephemeral 属性区分：临时实例（ephemeral=true）走 AP 模式采用 Distro 协议，保证可用性与最终一致；永久实例（ephemeral=false）走 CP 模式采用 Raft 协议，保证强一致牺牲部分可用性。配置中心使用 CP 模式，服务发现使用 AP 模式，两者在同一集群共存 |
| 缺点 | 混合模式增加理解与运维复杂度；AP 与 CP 切换依赖实例类型语义，配置错误会导致一致性与可用性预期不符 |

### 2. Nacos 心跳机制是怎样的？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Nacos 临时实例心跳上报与健康检查的阈值参数 |
| 能做什么 | 客户端定时上报心跳；服务端按时标记不健康与剔除；支持动态调整心跳间隔 |
| 怎么用 | `心跳5s -> 15s不健康 -> 30s剔除` |
| 原理和工作流程 | 临时实例客户端每隔 5s 发送心跳；服务端 15s 未收到心跳标记为不健康，30s 未收到心跳剔除实例。服务端可通过 clientBeatInterval 动态调整客户端心跳间隔。永久实例无心跳，由服务端主动探测健康状态 |
| 缺点 | 心跳间隔与剔除阈值固定，网络抖动易误剔除；动态调整心跳间隔需服务端配合；永久实例主动探测占用服务端资源 |

### 3. Nacos 配置中心长轮询超时时间是多少？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Nacos 1.x 配置监听长轮询的超时时间与工作流程 |
| 能做什么 | 配置变更实时感知；挂起请求减少无效轮询；MD5 比对判断变更 |
| 怎么用 | `默认30s超时 + MD5比对` |
| 原理和工作流程 | 默认 30 秒。客户端携带当前配置 MD5 值发起请求，服务端比较 MD5，未变更则挂起请求等待 30s。30s 内配置变更则立即返回新配置，超时则返回 304 Not Modified。客户端收到响应后立即发起下一轮长轮询 |
| 缺点 | 存在最长 30s 感知延迟；多配置监听连接数增长；2.x 已改 gRPC 双向流，长轮询为 1.x 机制 |

### 4. Nacos 2.x 相比 1.x 的核心变化是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Nacos 2.x 通信层升级的核心改动 |
| 能做什么 | 通信层升级 gRPC；心跳改为双向流；服务发现实时推送；性能提升 2-3 倍 |
| 怎么用 | `HTTP短连接 -> gRPC长连接 + 新增端口9848` |
| 原理和工作流程 | 通信层从 HTTP 短连接升级为 gRPC 长连接，实现双向流推送；心跳从 HTTP 定时请求改为 gRPC 双向流，服务端可主动推送；服务发现从客户端轮询加 UDP 推送改为 gRPC 双向流实时推送；配置监听从 HTTP 长轮询改为 gRPC 双向流；新增 gRPC 端口 9848（主端口 +1000），性能提升 2-3 倍 |
| 缺点 | 新增 gRPC 端口增加网络与防火墙配置复杂度；长连接占用服务端句柄需调优；1.x 升级 2.x 存在兼容过渡成本 |

## 六、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | Nacos 使用中常见错误的现象、原因与解决方案汇总 |
| 能做什么 | 避免使用嵌入式 Derby 生产部署；正确填写 namespace ID；保证集群节点数；正确配置动态刷新；控制配置文件大小 |
| 怎么用 | `外部MySQL | namespace填UUID | 集群>=3 | @RefreshScope | 单配置<100KB` |
| 原理和工作流程 | 生产环境用嵌入式 Derby 无法支持集群且有数据丢失风险，必须用外部 MySQL；namespace 填名称而非 ID 会导致配置不生效，应从控制台复制 UUID；集群少于 3 节点不满足 Raft 半数存活要求导致不可用；@Value 未配合 @RefreshScope 配置不刷新；配置中心存超大文件导致加载慢与网络传输大，单配置建议不超过 100KB |
| 缺点 | 避坑要点分散，缺乏统一校验机制；部分方案增加部署与配置成本；超大文件限制需人工约束，无强制拦截 |
