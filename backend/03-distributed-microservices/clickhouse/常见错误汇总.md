# ClickHouse - 常见错误汇总

> 汇总本模块所有知识点的常见错误，从各源文件避坑指南章节提取。

---

| 错误现象 | 产生原因 | 正确做法 | 关联导览 |
|---------|---------|---------|---------|
| 频繁小批量写入导致 Part 数量爆炸、查询性能下降、CPU 和 IO 被合并线程占满 | MergeTree 每次写入产生新的 Part，后台合并有开销 | 批量写入（每 1000-10000 条或每 5-10 秒一批）；使用 Buffer 引擎或 Kafka 引擎缓冲写入 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 频繁 UPDATE/DELETE 导致磁盘 IO 飙升、Part 数量激增 | ClickHouse 的 UPDATE/DELETE 是异步 Mutation，会重写整个 Part | 避免需要 UPDATE/DELETE 的场景；使用 ReplacingMergeTree + 版本号实现逻辑更新；通过数据覆盖替代 UPDATE | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 用 ClickHouse 替代 MySQL 做业务主库导致事务缺失、点查询慢 | ClickHouse 不支持事务，不适合 OLTP 场景 | MySQL 做业务主库（OLTP），ClickHouse 做分析引擎（OLAP） | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 未使用 PREWHERE 优化导致全列读取后过滤、IO 浪费 | WHERE 先读取所有列再过滤 | 优先使用 PREWHERE（列裁剪，先过滤再读取其他列）；MergeTree 引擎会自动优化部分 WHERE 到 PREWHERE | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| SELECT * 查询导致列式存储优势丧失、IO 浪费 | 列式存储的优势在于只读需要的列 | 只查询需要的列 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 分区粒度过大或过小导致分区数过多（超过 1000）影响元数据管理 | 未合理规划分区粒度 | 分区数控制在 1000 以内，按月分区为常用粒度 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| JOIN 大表导致查询超时、性能差 | ClickHouse JOIN 性能不如分布式计算引擎 | 将 JOIN 逻辑放到数据写入时做宽表 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 使用 COUNT(DISTINCT) 导致性能差 | COUNT(DISTINCT) 精确去重开销大 | 使用 uniq() 近似去重（HyperLogLog 算法） | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
| 不监控 Part 数量导致查询性能下降 | Part 数量过多未及时发现 | 定期查询 system.parts 监控 Part 数量 | [ClickHouse核心原理导览](./01-ClickHouse核心原理-导览.md) |
