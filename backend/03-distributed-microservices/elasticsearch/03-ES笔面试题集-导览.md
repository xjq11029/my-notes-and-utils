### 1. 以下关于 Elasticsearch 的描述，错误的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 的系统定位（AP 还是 CP）及核心特性描述。 |
| 能做什么 | 区分 AP 与 CP 系统；识别 ES 分布式、RESTful、Type 废弃等特性。 |
| 怎么用 | 答案 C：ES 是 AP 系统非 CP，牺牲强一致性换取高可用和分区容错。 |
| 原理和工作流程 | ES 基于 Apache Lucene 是分布式搜索分析引擎，Type 在 7.x 废弃 8.x 移除，支持 RESTful API 基于 HTTP 交互。ES 是 AP 系统（CAP 理论），写入时主分片和副本分片都写入成功后返回，但读取时可能读到旧数据（主从之间短暂不一致），牺牲强一致性换取高可用和分区容错。C 选项错误说 ES 是 CP 系统。 |
| 缺点 | AP 系统不保证强一致性；读取可能读到旧数据；不适合事务型主存储。 |

### 2. ES 中倒排索引存储的是哪种映射关系？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查倒排索引的映射方向：词项到文档 ID 列表。 |
| 能做什么 | 区分倒排索引与正向索引；识别映射关系；理解全文检索基础。 |
| 怎么用 | 答案 B：词项 → 文档 ID 列表，正向索引才是文档 ID → 词项列表。 |
| 原理和工作流程 | 倒排索引（Inverted Index）将"词项（Term）→ 包含该词项的文档 ID 列表"作为映射关系，是全文检索的核心数据结构。正向索引是"文档 ID → 词项列表"（选项 A）。倒排索引通过词项直接定位文档列表，时间复杂度 O(1)。 |
| 缺点 | 倒排索引占用额外存储；更新成本高需重建 Segment；不适合精确等值查询。 |

### 3. ES 中 refresh_interval 的默认值是多少？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 近实时搜索的 Refresh 默认周期参数值。 |
| 能做什么 | 记忆 refresh_interval 默认 1s；理解 NRT 1 秒延迟来源。 |
| 怎么用 | 答案 C：默认 refresh_interval=1s，每秒将 Buffer 刷新为 Segment 使数据可搜索。 |
| 原理和工作流程 | ES 默认 refresh_interval=1s，即每秒将内存 Buffer 刷新为 Segment 并打开，使数据变为可搜索。这是 ES 被称为"近实时搜索（NRT）"的原因。1 秒延迟是性能与实时性的折中，若每次写入立即刷新会产生大量小 Segment 严重影响性能。 |
| 缺点 | 1 秒延迟非实时；频繁刷新影响写入性能；关闭刷新期间数据不可搜索。 |

### 5. ES 中的 Primary Shard 数量设置后，以下说法正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Primary Shard 数量创建后不可修改的特性。 |
| 能做什么 | 识别主分片数不可动态修改；理解路由算法依赖分片数；知晓 Reindex 重建。 |
| 怎么用 | 答案 C：设置后不可修改，只能通过 Reindex 重建索引。 |
| 原理和工作流程 | Primary Shard 数量在索引创建时确定，文档路由算法 `shard = hash(_routing) % num_primary_shards` 依赖此数量，因此不可动态修改。如果分片数不合理，必须通过 Reindex API 重建索引。 |
| 缺点 | 主分片数不可改需提前规划；Reindex 重建耗时长；分片规划不当难以调整。 |

### 6. 以下关于 ES 写入流程的描述，正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 写入流程中 Translog 与 Buffer 的写入顺序及可搜索时机。 |
| 能做什么 | 识别先写 Translog 再写 Buffer；区分可搜索时机；理解副本写入确认。 |
| 怎么用 | 答案 B：文档先写入 Translog，再写入内存 Buffer。 |
| 原理和工作流程 | 写入流程：文档先写入 Translog（保证数据不丢失），再写入内存 Buffer。此时数据不可搜索，需等待 Refresh 将 Buffer 刷新为 Segment 后才可搜索。写入必须等待所有副本分片也写入成功后才返回。因此 B 正确。 |
| 缺点 | 等待所有副本写入才返回延迟受最慢副本影响；写入后需等 Refresh 才可搜索；写放大严重。 |

### 8. ES 中 Flush 和 Refresh 的区别，以下描述正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Refresh 与 Flush 在操作内容、效果、触发频率上的区别。 |
| 能做什么 | 区分 Refresh 刷新为 Segment 可搜索；区分 Flush 持久化到磁盘清空 Translog。 |
| 怎么用 | 答案 B：Refresh 将 Buffer 刷新为 Segment 使其可搜索，Flush 将 Segment 持久化到磁盘。 |
| 原理和工作流程 | Refresh（默认 1s）将内存 Buffer 中的数据刷新为新的 Segment，使数据变为可搜索（但仍在内存/文件系统缓存中）。Flush（默认 30min 或 Translog 512MB）将 Segment 持久化到磁盘并清空 Translog。 |

### 1. 简述 ES 的倒排索引结构及其优势

### 4. 简述 ES 的写入流程

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 数据写入从客户端到副本分片的完整链路和路由算法。 |
| 能做什么 | 描述七步写入流程；说明路由算法；解释 Translog 和 Buffer 写入顺序；指出可搜索时机。 |
| 怎么用 | 路由 `shard = hash(_routing) % num_primary_shards`；主分片写 Translog 和 Buffer 后转发副本。 |
| 原理和工作流程 | 客户端发送写入请求到协调节点，协调节点计算路由转发到主分片所在节点。主分片写入 Translog 和内存 Buffer，然后转发到所有副本分片。所有副本分片写入成功后，主分片返回成功给协调节点，协调节点返回客户端。等待下一个 Refresh 周期（默认 1s）数据变为可搜索。 |
| 缺点 | 等待所有副本写入才返回延迟受最慢副本影响；写入后需等 Refresh 才可搜索；写放大严重。 |

### 5. ES 如何实现数据同步？列举三种方案并比较优缺点

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 MySQL 到 ES 的三种数据同步方案（Logstash、Canal、MQ）及推荐组合。 |
| 能做什么 | 比较三种方案优缺点；给出推荐方案；说明 Canal+Kafka 解耦可靠实时。 |
| 怎么用 | 推荐 `MySQL binlog → Canal Server → Kafka → ES 消费者` 组合方案。 |
| 原理和工作流程 | Logstash 简单配置即可但定时拉取有延迟影响 MySQL；Canal 实时性高零侵入但运维复杂需维护 Canal Server；MQ 异步同步灵活可控解耦但需业务代码配合处理一致性。推荐 Canal+Kafka 组合：Canal 监听 MySQL binlog 解析后发到 Kafka，ES 消费者消费 Kafka 写入 ES，解耦可靠实时。 |
| 缺点 | Logstash 有延迟影响 MySQL；Canal 运维复杂；MQ 需业务配合；双写一致性差。 |

### 6. 什么是 ES 的段合并？为什么需要它？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查段合并机制的定义、必要性和 TieredMergePolicy 分层合并策略。 |
| 能做什么 | 解释 Segment 不可变导致数量增长；说明合并提升性能释放空间；描述分层合并策略。 |
| 怎么用 | 后台自动合并；`POST /products/_forcemerge?max_num_segments=1` 手动合并。 |
| 原理和工作流程 | 段合并是 ES 后台自动将多个小 Segment 合并为大 Segment 的过程。每次 Refresh 创建新的不可变 Segment，随时间推移 Segment 数量增长导致查询遍历更多 Segment、文件句柄增加、内存占用增大。段合并减少 Segment 数量提升查询性能释放磁盘空间。合并策略为 TieredMergePolicy 分层合并，优先合并大小相近的 Segment。 |
| 缺点 | 合并消耗 CPU 和 IO 资源；大 Segment 合并耗时长；高峰期合并影响在线查询。 |

### 7. ES 集群的三种健康状态及其含义

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 集群 green/yellow/red 三种健康状态的含义和影响。 |
| 能做什么 | 识别 green 完全健康；识别 yellow 副本未分配；识别 red 主分片不可用需紧急处理。 |
| 怎么用 | 监控集群状态；yellow 以上需及时处理；red 需紧急修复主分片。 |
| 原理和工作流程 | green 表示所有主分片和副本分片都正常分配，集群完全健康。yellow 表示所有主分片正常但部分副本分片未分配，数据可读写但可能丢失高可用性。red 表示部分主分片未分配（不可用），部分数据不可读写，需紧急处理。 |
| 缺点 | yellow 长期未处理可能丢失高可用；red 部分数据不可用；监控不到位隐患大。 |

### 8. 简述 ES 中 search_after 的实现原理和使用注意事项

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 search_after 基于游标实时翻页的实现原理和四项注意事项。 |
| 能做什么 | 说明游标原理；指出必须含唯一排序字段；说明不支持跳页；建议配合 PIT。 |
| 怎么用 | `search_after:[2999,"p_10050"]` 配合唯一排序字段（如 _id）作为 tiebreaker。 |
| 原理和工作流程 | search_after 通过上一页最后一条数据的排序值作为游标查询下一页。排序字段值确定，ES 从指定值之后返回数据，避免 from+size 需协调节点在内存收集排序所有分片数据的问题。注意事项：必须指定排序字段且含唯一字段（如 _id）作为 tiebreaker；不支持跳页只能逐页向下翻；排序字段值变化导致数据重复遗漏；需配合 pit 保持查询一致性。 |
| 缺点 | 不支持跳页；排序字段值变化导致重复遗漏；需配合 PIT 增加复杂度。 |

### 3. 数据同步一致性方案设计

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 MySQL 到 ES 数据同步的 Canal+Kafka 架构设计及一致性保障（不丢失、低延迟、断点续传）。 |
| 能做什么 | 设计 Canal+Kafka+ES 消费者架构；实现幂等写入；保障数据不丢失；实现断点续传和数据对账。 |
| 怎么用 | `MySQL binlog → Canal Server → Kafka(order_id 为 key) → ES 消费者(bulk 批量写入)`。 |
| 原理和工作流程 | 架构：MySQL binlog → Canal Server → Kafka → ES 同步消费者，ZooKeeper 记录同步位点。Canal 配置过滤规则只同步订单表，解析 binlog 事件发送 Kafka。Kafka Topic 分区 6，消息 key 为 order_id 保证同订单变更有序。ES 消费者手动提交 offset，每 500 条或 5 秒 bulk 批量写入，基于 order_id 幂等写入，消费失败不提交 offset 重启续传。一致性保障：Kafka 持久化加手动 offset 不丢失，Canal 秒级解析加 Kafka 低延迟控制 5 秒内，Kafka 消费者组自动 offset 断点续传，定时对账校验。 |
| 缺点 | 架构复杂组件多运维成本高；Canal 解析 binlog 故障需处理；数据对账有窗口期差异；消费延迟需监控告警。 |
