## 一、核心概念

### 1.1 查询上下文 vs 过滤上下文

| 维度 | 内容 |
|------|------|
| 是什么 | ES 查询的两种上下文，Query Context 计算 _score 相关性评分，Filter Context 只判断是否匹配。 |
| 能做什么 | Query 回答"有多匹配"；Filter 回答"是否匹配"；Filter 自动缓存结果提升性能。 |
| 怎么用 | 全文搜索用 `must`/`should`；精确筛选用 `filter`/`must_not`；能用 filter 不用 must。 |
| 原理和工作流程 | Query Context 对匹配文档计算相关性评分 _score 用于排序，较慢。Filter Context 只判断命中与否不计算评分，ES 自动缓存过滤结果，后续相同条件直接命中缓存，较快。核心原则：能用 filter 就不用 must，因为 filter 不计算评分且结果会被缓存。 |
| 缺点 | Query 计算评分开销大；Filter 不适合需要相关性排序的场景；缓存占用内存。 |

### 1.2 全文搜索 vs 精确搜索

| 维度 | 内容 |
|------|------|
| 是什么 | 全文搜索对查询词分词后匹配适用于 text 字段，精确搜索不分词直接匹配适用于 keyword 等字段。 |
| 能做什么 | 全文搜索支持 match/match_phrase/multi_match；精确搜索支持 term/terms/range/exists。 |
| 怎么用 | `match` 分词匹配 text；`term` 精确匹配 keyword/数值/日期。 |
| 原理和工作流程 | 全文搜索（Full Text）对查询词进行分词后匹配，适用于 text 类型字段，如搜索"苹果手机"会匹配到"苹果"和"手机"相关文档。精确搜索（Term）不对查询词分词，直接精确匹配，适用于 keyword、数值、日期、布尔类型，如查询 category="手机" 只匹配分类为手机的文档。 |
| 缺点 | 全文搜索分词可能导致召回过多无关结果；精确搜索不适用于 text 字段（已分词）；选择不当查询不到预期结果。 |

### 1.3 聚合

| 维度 | 内容 |
|------|------|
| 是什么 | ES 的分析能力，类似 SQL 的 GROUP BY 加聚合函数，分 Bucket、Metric、Pipeline 三类。 |
| 能做什么 | Bucket 分桶分组；Metric 统计计算；Pipeline 二次计算聚合结果。 |
| 怎么用 | `aggs` 下定义聚合；`size:0` 只返回聚合结果不返回文档。 |
| 原理和工作流程 | Bucket Aggregation 按条件将文档分组类似 GROUP BY；Metric Aggregation 对文档统计计算类似 COUNT/SUM/AVG；Pipeline Aggregation 对其他聚合结果二次计算类似窗口函数和 HAVING。聚合可与查询组合，先过滤文档再聚合分析。 |
| 缺点 | 聚合消耗内存和 CPU；高基数字段聚合性能差；text 字段聚合需 fielddata 开销大。 |

## 二、DSL 查询详解

### 2.1 基本查询

| 维度 | 内容 |
|------|------|
| 是什么 | ES DSL 的基础查询语句集合，包括 match、match_phrase、multi_match、term、terms、range、exists。 |
| 能做什么 | 分词匹配；短语匹配；多字段匹配；精确匹配；多值匹配；范围查询；字段存在性查询。 |
| 怎么用 | `match` 分词匹配；`term` 精确匹配；`range` 范围 `gte/lte`；`multi_match` 多字段带权重 `name^3`。 |
| 原理和工作流程 | match 对查询词分词后匹配适用于 text 字段；match_phrase 要求分词后词项按顺序连续出现；multi_match 在多字段搜索可设置权重；term 不分词直接精确匹配适用于 keyword；terms 类似 SQL IN 多值匹配；range 按 gte/lte 范围查询可 boost 提升权重；exists 查询存在某字段的文档。 |
| 缺点 | match 分词可能召回不准；term 查 text 字段结果异常；range 范围过大性能下降。 |

### 2.2 bool 组合查询

| 维度 | 内容 |
|------|------|
| 是什么 | ES 最强大的组合查询，通过 must、should、must_not、filter 四个子句组合多个查询条件。 |
| 能做什么 | AND 逻辑 must；OR 逻辑 should；NOT 逻辑 must_not；精确筛选 filter 缓存；设置 minimum_should_match。 |
| 怎么用 | `bool` 内组合 must/should/must_not/filter 数组；`minimum_should_match:1` 控制 should 最少匹配数。 |
| 原理和工作流程 | must 必须匹配计算评分（AND）；should 应该匹配计算评分（OR）；must_not 必须不匹配不计算评分（NOT）；filter 必须匹配不计算评分且结果自动缓存。must 和 should 参与 _score 计算，filter 和 must_not 不参与。minimum_should_match 控制 should 至少匹配数。 |
| 缺点 | must 计算评分较慢；条件过多 DSL 复杂；should 与 minimum_should_match 配合易出错。 |

### 2.3 高亮显示

| 维度 | 内容 |
|------|------|
| 是什么 | ES 在查询结果中对匹配关键词包裹高亮标签的显示功能。 |
| 能做什么 | 自定义高亮前后缀标签；控制片段长度；控制返回片段数；前端直接渲染高亮。 |
| 怎么用 | `highlight` 配置 `pre_tags:["<em>"]`、`post_tags:["</em>"]`、`fragment_size:150`、`number_of_fragments:3`。 |
| 原理和工作流程 | 在查询中配置 highlight 字段，pre_tags 和 post_tags 定义高亮前后缀标签（默认 <em>）。fragment_size 控制每个高亮片段长度，number_of_fragments 控制返回片段数。返回结果中匹配关键词被标签包裹，前端直接渲染高亮效果。高亮基于倒排索引中的 Offset 信息定位关键词位置。 |
| 缺点 | 大文本高亮消耗内存；片段切割可能截断关键词；多字段高亮性能下降。 |

### 2.4 排序和分页

| 维度 | 内容 |
|------|------|
| 是什么 | ES 查询结果的排序规则和分页机制，包括 from/size、search_after 两种分页方案。 |
| 能做什么 | 多字段排序；按价格/时间/评分排序；from/size 基础分页；search_after 深度分页。 |
| 怎么用 | `sort:[{"price":{"order":"asc"}}]` 排序；`from:0,size:20` 分页；`search_after:[2999,"p_10050"]` 深度分页。 |
| 原理和工作流程 | sort 支持多字段排序，默认按 _score 相关性降序。from/size 分页 from+size 不能超过 10000（max_result_window），因为协调节点需从每个分片收集 from+size 条数据排序。search_after 基于上一页最后一条数据的排序值实时查询下一页，必须包含唯一排序字段（如 _id）作为 tiebreaker，避免协调节点内存排序，性能最优。 |
| 缺点 | from/size 深度分页内存暴增；search_after 不支持跳页；排序字段值变化导致数据重复遗漏。 |

### 2.5 别名

| 维度 | 内容 |
|------|------|
| 是什么 | 索引别名的机制，应用程序始终读写别名，底层索引切换无需修改代码，实现零停机运维。 |
| 能做什么 | 一个别名指向多个索引；多个索引指向一个别名；零停机索引切换；配合 Reindex 重建索引。 |
| 怎么用 | `POST /_aliases` 添加 `add` 或移除 `remove` 别名指向，原子操作同时 remove 旧索引 add 新索引。 |
| 原理和工作流程 | 通过 _aliases API 为索引创建别名，应用程序始终读写别名而非实际索引名。零停机切换时，在一个原子操作中 remove 旧索引（products_v1）的别名并 add 新索引（products_v2）的别名，应用程序无感知。结合 Reindex 可实现零停机索引重建和字段类型修改。 |
| 缺点 | 写别名指向多索引时需指定 is_write_index；别名管理增加运维复杂度；误删别名影响应用。 |

## 三、聚合分析

### 3.1 分桶聚合

| 维度 | 内容 |
|------|------|
| 是什么 | 按条件将文档分组的聚合类型，类似 SQL GROUP BY，包括 terms、date_histogram、range、filter 聚合。 |
| 能做什么 | 按字段值分组；按时间间隔分组；按数值范围分组；先过滤再分组。 |
| 怎么用 | `terms` 按字段值 `size:10`；`date_histogram` 按 day；`range` 自定义区间；`filter` 聚合嵌套子聚合。 |
| 原理和工作流程 | terms 聚合按字段值分组返回前 N 个桶，类似 GROUP BY category，可 order 按 _count 排序。date_histogram 按时间间隔（day/hour/week/month）分组，min_doc_count=0 包含无文档日期。range 聚合按数值范围分组指定 from/to。filter 聚合先过滤文档再嵌套子聚合，如只统计上架商品的分类分布。 |
| 缺点 | terms 高基数字段桶数巨大性能差；date_histogram 时区未设置结果偏差；range 区间过多开销大。 |

### 3.2 指标聚合

| 维度 | 内容 |
|------|------|
| 是什么 | 对文档进行统计计算的聚合类型，类似 SQL 聚合函数，包括 avg/max/min/sum/stats/cardinality。 |
| 能做什么 | 计算平均值；最大最小值；求和；综合统计；近似去重计数。 |
| 怎么用 | `avg`/`max`/`min`/`sum` 单指标；`stats` 综合统计；`cardinality` 近似去重。 |
| 原理和工作流程 | avg 计算平均值，max/min 求最大最小值，sum 求和。stats 一次返回 count/avg/min/max/sum 综合统计。cardinality 基于 HyperLogLog++ 算法近似去重计数，默认误差率 5% 以内，可通过 precision_threshold 调整精度，最大 40000（误差率约 1%），精度越高内存消耗越大。 |
| 缺点 | cardinality 近似不精确；高精度内存消耗大；scripted_metric 性能差。 |

### 3.3 嵌套聚合

| 维度 | 内容 |
|------|------|
| 是什么 | 分桶聚合内嵌套指标聚合，实现类似 SQL 的 GROUP BY 加聚合函数的复合分析。 |
| 能做什么 | 按分类分组后计算平均值；分组后求最大值；分组后求总销量；多级嵌套聚合。 |
| 怎么用 | `terms` 聚合下嵌套 `aggs` 定义 avg/max/sum 子聚合。 |
| 原理和工作流程 | 在分桶聚合（如 by_category 的 terms）内部定义 aggs 子聚合（avg_price、max_price、total_sales），ES 先按 category 分桶，再对每个桶内的文档计算指标。等价 SQL：SELECT category, COUNT(*), AVG(price), MAX(price), SUM(sales) FROM products GROUP BY category ORDER BY COUNT(*) DESC LIMIT 10。 |
| 缺点 | 嵌套层级过多性能下降；高基数分桶加指标计算内存压力大；跨分片聚合结果需二次归并。 |

### 3.4 实战案例：电商商品搜索

| 维度 | 内容 |
|------|------|
| 是什么 | 综合运用全文搜索、bool 过滤、聚合、排序、高亮、分页的完整电商商品搜索查询示例。 |
| 能做什么 | 关键词搜索；分类价格品牌筛选；品牌分布聚合；价格区间聚合；销量相关性排序；关键词高亮。 |
| 怎么用 | bool 组合 multi_match + filter；aggs 统计 brand_distribution 和 price_range；sort 按 sales 和 _score。 |
| 原理和工作流程 | bool 查询中 must 用 multi_match 搜索"蓝牙耳机"在 name^3 和 description 字段，filter 用 term 筛选 category 和 status，range 筛选 price 区间。aggs 同时计算 brand_distribution（terms 品牌）、price_range（range 价格区间）、avg_price（avg 平均价格）。sort 按销量降序和相关性评分。highlight 高亮 name 字段。from/size 分页。 |
| 缺点 | 单次查询包含搜索加聚合开销大；DSL 复杂易出错；聚合结果受分片影响可能不精确。 |

## 四、常见面试题

### 1. match 和 term 查询的区别？什么场景用哪个？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 match 与 term 查询在分词行为和适用字段上的区别。 |
| 能做什么 | 区分分词与不分词；说明适用字段类型；指出 term 查 text 字段的陷阱。 |
| 怎么用 | 全文搜索"苹果手机"用 match；筛选 category="手机"用 term。 |
| 原理和工作流程 | match 对搜索词分词后匹配分词后的词项，适用于 text 类型字段全文检索。term 不对搜索词分词直接精确匹配，适用于 keyword、数值、日期等精确值字段。注意 text 字段存储时已被分词，用 term 查询 text 字段实际匹配分词后的词项而非原始字符串，可能导致预期外结果。 |
| 缺点 | match 分词可能召回不准；term 查 text 字段结果异常；场景选错查询不到数据。 |

### 2. bool 查询中 must 和 filter 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 bool 查询中 must 与 filter 在评分、缓存、性能上的差异。 |
| 能做什么 | 区分评分参与与否；说明缓存机制；给出最佳实践搭配。 |
| 怎么用 | 全文搜索用 must；精确筛选（分类/状态/价格区间）用 filter。 |
| 原理和工作流程 | must 参与相关性评分 _score 计算，查询结果不缓存，较慢。filter 不参与评分只判断文档是否匹配是/否，结果会被自动缓存，较快。最佳实践：全文搜索需要评分的场景用 must，精确筛选（分类、状态、价格区间）用 filter。例如搜索"手机"用 must，筛选"上架状态+价格区间"用 filter。 |
| 缺点 | must 计算评分开销大；filter 缓存占用内存；频繁变化条件缓存命中率低。 |

### 3. ES 深度分页有哪些解决方案？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 深度分页的三种方案：search_after、scroll、修改 max_result_window。 |
| 能做什么 | search_after 实时翻页；scroll 全量导出；max_result_window 临时调大。 |
| 怎么用 | `search_after:[2999,"p_10050"]` 配合唯一排序字段；`scroll` 创建快照；`max_result_window` 调大限制。 |
| 原理和工作流程 | search_after 基于上一页最后一条数据排序值实时查询下一页，适合实时翻页和无限滚动，性能最优但无法跳页。scroll 创建数据快照遍历所有数据，适合全量导出和批量处理，但快照期间增量数据不可见。修改 max_result_window 调大参数简单但治标不治本，深度分页时协调节点内存压力大。推荐 search_after 首选。 |
| 缺点 | search_after 不支持跳页；scroll 快照期间数据不一致；max_result_window 治标不治本内存风险。 |

### 4. 聚合分析中 cardinality 的精度问题？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 cardinality 聚合基于 HyperLogLog++ 算法的近似去重精度问题。 |
| 能做什么 | 说明近似特性；调整 precision_threshold 精度；对比精确去重方案。 |
| 怎么用 | `cardinality` 默认误差 5%；`precision_threshold:40000` 误差约 1%。 |
| 原理和工作流程 | cardinality 聚合用于近似去重计数，基于 HyperLogLog++ 算法实现。精度是近似的，默认误差率在 5% 以内。通过 precision_threshold 参数调整精度，最大值 40000（此时误差率约 1%），精度越高内存消耗越大。若对精度要求极高需精确去重，建议应用层实现或使用 scripted_metric 聚合（性能较差）。 |
| 缺点 | 近似不精确不适合精确计数；高精度内存消耗大；scripted_metric 性能差。 |

### 5. 如何优化 ES 的聚合查询性能？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 聚合查询性能优化的六大策略。 |
| 能做什么 | 用 keyword 聚合；设 size:0；filter 聚合缩小范围；合理分片数；eager_global_ordinals；execution_hint map。 |
| 怎么用 | 聚合字段用 keyword；`size:0` 不返回文档；`eager_global_ordinals:true` 预加载；`execution_hint:map` 优化低基数。 |
| 原理和工作流程 | 使用 keyword 类型字段聚合避免 text 开启 fielddata；设置 size:0 不返回文档只返回聚合结果；使用 filter 聚合先缩小数据范围；合理设置分片数减少跨分片协调开销；对频繁聚合字段设置 eager_global_ordinals 预加载全局序号减少聚合时计算；使用 execution_hint:map 优化低基数 terms 聚合。 |
| 缺点 | eager_global_ordinals 增加刷新开销；map 模式不适合高基数；优化需根据场景权衡。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | ES 查询与聚合实战中常见错误的现象、原因和解决方案汇总。 |
| 能做什么 | 规避 text 用 term 查询；避免 text 字段聚合；处理 terms size 过大；解决高基数字段聚合；设置时区。 |
| 怎么用 | text 用 match 或 name.keyword；聚合用 keyword 子字段；高基数用 cardinality；date_histogram 设 time_zone。 |
| 原理和工作流程 | text 字段用 term 查询不到结果因存储已分词，应用 match 或 name.keyword 子字段。text 字段聚合无意义且堆内存消耗大，需为 text 设置 fields.keyword 子字段做聚合。terms 聚合 size 过大影响性能，全部分组用 composite 聚合分页。高基数字段（如 user_id）terms 聚合内存 CPU 消耗大，用 cardinality 近似替代。date_histogram 默认 UTC 时区需显式设 time_zone:"+08:00"。filter 缓存对频繁变化条件命中率低，用 Profile API 分析。 |
| 缺点 | 避坑依赖经验；text 聚合 fielddata 易 OOM；高基数聚合性能差需妥协精度。 |
