## 一、核心概念

### 1.1 ES 是什么

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Apache Lucene 构建的分布式搜索和分析引擎，能近实时存储、搜索和分析海量数据。 |
| 能做什么 | 全文检索；聚合分析；日志分析；业务监控；水平扩展；RESTful API 交互。 |
| 怎么用 | `PUT /products` 创建索引；`POST /products/_doc` 写入文档；`GET /products/_search` 检索。 |
| 原理和工作流程 | 底层依赖 Lucene 的倒排索引实现全文检索，通过分片与副本实现分布式存储和并行计算。数据写入内存 Buffer 后经 Refresh 生成 Segment 实现近实时搜索，Translog 保障数据可靠性。集群采用主从架构，Master 管理元数据，Data 节点存储执行 CRUD，Coordinating 节点路由汇总。 |
| 缺点 | 近实时而非实时，默认 1 秒延迟；不支持事务，不适合做主存储；内存和磁盘消耗较大。 |

### 1.2 核心概念与术语

| 维度 | 内容 |
|------|------|
| 是什么 | ES 中 Index、Document、Field、Mapping、Shard、Replica 等核心术语的统称，可与 MySQL 概念类比。 |
| 能做什么 | 定义数据组织方式；区分索引、文档、字段层级；配置字段类型与分词器；实现分片与副本存储。 |
| 怎么用 | `Index` 类比表；`Document` 类比行；`Field` 类比列；`Mapping` 类比 Schema；`Shard` 类比分表。 |
| 原理和工作流程 | Index 是文档的集合，物理上拆分为多个 Primary Shard，每个主分片可拥有多个 Replica Shard。Mapping 定义字段类型和分词器约束。Type 在 7.x 废弃、8.x 移除，实际开发中 Index 直接类比 Table。文档以 JSON 格式存储，通过路由算法归属到唯一主分片。 |
| 缺点 | Type 移除导致历史多 Type 索引需迁移；概念较多学习曲线陡；与 MySQL 类比有偏差易误解。 |

### 1.3 ES 集群架构

| 维度 | 内容 |
|------|------|
| 是什么 | ES 采用主从架构，集群节点按角色分为 Master、Data、Coordinating、Ingest 四类。 |
| 能做什么 | Master 管理元数据；Data 存储 CRUD；Coordinating 路由汇总；Ingest 数据预处理。 |
| 怎么用 | `node.roles: [master, data]` 配置节点角色；客户端请求先到 Coordinating Node。 |
| 原理和工作流程 | Master 维护集群状态和分片分配，不处理读写；Data 节点存储数据并执行搜索聚合；每个节点默认可作为 Coordinating 接收请求并路由到正确分片，汇总各分片结果返回客户端；Ingest 节点在索引前对文档做字段转换富化。写请求经协调节点路由到主分片，再复制到副本分片。 |
| 缺点 | Master 单点风险（靠选举缓解）；节点角色混部时资源争抢；集群规模过大时元数据管理开销增加。 |

## 二、底层原理

### 2.1 倒排索引

| 维度 | 内容 |
|------|------|
| 是什么 | 从词项到文档 ID 列表的映射数据结构，是 ES 全文检索的核心，与正向索引相反。 |
| 能做什么 | 通过词项快速定位文档；存储词频用于评分；存储位置用于短语匹配和高亮。 |
| 怎么用 | 写入时 Analyzer 分词生成倒排表；查询时 `match` 分词后查 Term Dictionary 定位文档。 |
| 原理和工作流程 | 倒排索引由 Term Dictionary（排序词项字典，支持二分查找）、Term Index（基于 FST 的压缩前缀树，加速定位）、Posting List（文档 ID 列表，含 TF、Position、Offset）三部分组成。检索时通过 Term Index 快速定位到 Term Dictionary，再获取 Posting List，时间复杂度近 O(1)。正向索引需遍历所有文档匹配，倒排索引直接由词项定位文档。 |
| 缺点 | 占用额外存储空间；不适合精确等值查询（不如 B+Tree）；更新成本高需重建 Segment。 |

### 2.2 分词器

| 维度 | 内容 |
|------|------|
| 是什么 | 将文本拆分为独立词项的组件，由 Character Filter、Tokenizer、Token Filter 三部分组成。 |
| 能做什么 | 文本预处理；HTML 标签剥离；中文分词；大小写转换；停用词过滤；同义词扩展。 |
| 怎么用 | `POST /_analyze {"analyzer":"ik_max_word","text":"苹果手机"}` 测试分词效果。 |
| 原理和工作流程 | Character Filter 在分词前对原始文本预处理（如 html_strip 去标签）；Tokenizer 将文本切分为 Token（如 standard、ik_smart、ik_max_word）；Token Filter 对 Token 过滤处理（如 lowercase、stop、synonym）。IK 分词器是中文标配，ik_smart 粗粒度切分最少词适合搜索，ik_max_word 细粒度穷尽切分适合索引。 |
| 缺点 | 中文分词依赖词典，新词识别能力有限；分词不当导致召回率下降；自定义词典维护成本高。 |

### 2.3 分片机制

| 维度 | 内容 |
|------|------|
| 是什么 | ES 实现分布式存储和并行计算的核心机制，分 Primary Shard（主分片）和 Replica Shard（副本分片）。 |
| 能做什么 | 水平扩展存储容量；并行提升写入吞吐；副本提供高可用；读负载均衡。 |
| 怎么用 | `number_of_shards:3` 设置主分片数；`number_of_replicas:1` 设置副本数；创建后主分片不可改。 |
| 原理和工作流程 | Primary Shard 在索引创建时确定数量且不可修改，文档通过 `shard = hash(_routing) % num_primary_shards` 路由到唯一主分片，负责写操作。Replica Shard 是主分片拷贝，数量可动态调整，主分片故障时提升为新主分片。主分片与其副本不会分配到同一节点。单分片建议 10-50GB。 |
| 缺点 | 主分片数创建后不可改，需 Reindex 重建；分片过多增加协调开销；分片过小浪费资源。 |

### 2.4 写入流程

| 维度 | 内容 |
|------|------|
| 是什么 | ES 数据写入的完整链路，从客户端到主分片再到副本分片的多阶段过程。 |
| 能做什么 | 路由文档到正确分片；Translog 保障不丢失；复制到副本保证高可用；返回写入确认。 |
| 怎么用 | `POST /products/_doc {"name":"手机"}` 触发完整写入链路。 |
| 原理和工作流程 | 客户端请求到 Coordinating Node，计算路由 `shard = hash(_routing) % num_primary_shards`，转发到主分片所在节点。主分片写入内存 Buffer 同时写 Translog，再转发到 Replica Shard。副本写入 Buffer 和 Translog 后返回成功给主分片。所有副本成功后主分片返回协调节点，协调节点返回客户端。 |
| 缺点 | 等待所有副本写入才返回，延迟受最慢副本影响；写入后需等 Refresh 才可搜索；写放大严重。 |

### 2.5 Refresh 机制与近实时搜索

| 维度 | 内容 |
|------|------|
| 是什么 | ES 默认每秒将内存 Buffer 刷新为 Segment 使数据可搜索的机制，实现近实时（NRT）搜索。 |
| 能做什么 | 控制 NRT 延迟；批量导入时关闭刷新提升性能；权衡实时性与写入吞吐。 |
| 怎么用 | `refresh_interval:1s` 默认；批量导入设 `refresh_interval:-1`；导入后恢复。 |
| 原理和工作流程 | 文档写入内存 Buffer 时不可搜索，默认每秒（refresh_interval=1s）将 Buffer 刷新为新的 Segment 并打开，数据变为可搜索，Buffer 清空等待新写入。若每次写入都立即刷新会创建大量小 Segment 严重影响性能，1 秒延迟折中实时性与性能。 |
| 缺点 | 默认 1 秒延迟非实时；频繁刷新产生小 Segment 影响性能；关闭刷新期间数据不可搜索。 |

### 2.6 段合并

| 维度 | 内容 |
|------|------|
| 是什么 | ES 后台自动将多个小 Segment 合并为大 Segment 的机制，因为每次 Refresh 都会创建不可变 Segment。 |
| 能做什么 | 减少 Segment 数量提升查询性能；释放磁盘空间；控制单 Segment 最大大小。 |
| 怎么用 | 后台自动合并；`POST /products/_forcemerge?max_num_segments=1` 手动合并。 |
| 原理和工作流程 | 每次 Refresh 创建新的不可变 Segment，随时间推移 Segment 数量增长降低查询性能。后台合并线程按 TieredMergePolicy 分层策略优先合并大小相近的 Segment，合并后删除旧 Segment 释放磁盘。通过 `max_merged_segment`（默认 5GB）控制单 Segment 最大大小，`segments_per_tier` 控制每层 Segment 数量。 |
| 缺点 | 合并过程消耗 CPU 和 IO 资源；大 Segment 合并耗时长；高峰期合并影响在线查询。 |

### 2.7 数据可靠性保证

| 维度 | 内容 |
|------|------|
| 是什么 | ES 通过 Translog 事务日志和定期 Flush 机制保证数据不丢失的可靠性体系。 |
| 能做什么 | Translog 重放恢复未持久化数据；Flush 持久化 Segment 到磁盘；清空 Translog。 |
| 怎么用 | Translog 自动写入；`POST /products/_flush` 手动触发 Flush。 |
| 原理和工作流程 | 每个分片维护一个 Translog，每次写入先写 Translog 再写内存 Buffer，节点宕机重启时从 Translog 重放未持久化操作。Flush 默认每 30 分钟或 Translog 达 512MB 触发，将内存 Segment 提交到磁盘并清空 Translog。数据层级：写入 Buffer（不可搜索）→ Refresh → Segment（可搜索未持久化）→ Flush → 磁盘持久化。 |
| 缺点 | Translog 达 512MB 前 Flush 之间宕机仍依赖 Translog 恢复；ES 是 AP 系统不保证强一致性；读取可能读到旧数据。 |

## 三、实战应用

### 3.1 Spring Boot 集成 ES

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Spring Data Elasticsearch 将 ES 接入 Spring Boot 应用的集成方案。 |
| 能做什么 | 提供两种操作方式；实体类映射索引；自动建索引；RESTful 客户端连接。 |
| 怎么用 | `ElasticsearchRestTemplate` 适合复杂 DSL；`ElasticsearchRepository` 适合简单 CRUD。 |
| 原理和工作流程 | 引入 `spring-boot-starter-data-elasticsearch` 依赖，application.yml 配置 `spring.elasticsearch.uris` 连接信息。实体类用 `@Document(indexName)` 标注索引，`@Id` 标注主键，`@Field(type, analyzer, searchAnalyzer)` 标注字段类型和分词器。ElasticsearchRestTemplate 底层封装 RestClient 执行 DSL，ElasticsearchRepository 类似 JPA 自动实现 CRUD。 |
| 缺点 | 版本与 ES 服务端需严格匹配；高级 DSL 支持有限需手写；Repository 灵活性不足。 |

### 3.2 索引设计最佳实践

| 维度 | 内容 |
|------|------|
| 是什么 | 创建 ES 索引时 Settings 和 Mappings 的配置规范，涵盖分片、副本、分词器、字段类型选择。 |
| 能做什么 | 合理设置分片副本数；配置自定义分词器；选择 text/keyword 等字段类型；优化索引结构。 |
| 怎么用 | `PUT /products` 请求体含 `settings` 和 `mappings` 两部分配置。 |
| 原理和工作流程 | Settings 定义索引级参数（number_of_shards、number_of_replicas、refresh_interval、analysis 自定义分词器）。Mappings 定义字段类型：text 全文搜索会分词，keyword 精确匹配排序聚合不分词，long/integer/double 数值，date 日期，boolean 布尔，geo_point 地理位置。text 字段常配 fields.keyword 子字段兼顾搜索与聚合。 |
| 缺点 | 字段类型创建后不可改需 Reindex；动态映射可能误识别类型；分片数规划不当难以调整。 |

### 3.3 索引模板

| 维度 | 内容 |
|------|------|
| 是什么 | 用于统一管理按时间滚动创建索引（如日志索引）的配置模板，匹配 index_patterns 自动应用。 |
| 能做什么 | 统一索引 Settings 和 Mappings；自动应用到匹配的新索引；简化运维管理。 |
| 怎么用 | `PUT /_index_template/logs_template` 配置 `index_patterns:["logs-*"]` 和 template 内容。 |
| 原理和工作流程 | 创建索引模板时指定 index_patterns 匹配模式、priority 优先级、template（含 settings 和 mappings）。当新建索引名匹配 pattern 时，ES 自动应用优先级最高的模板配置。创建 `logs-2026-06-01` 索引会自动继承 `logs-*` 模板的分片数、副本数、refresh_interval 和字段映射。 |
| 缺点 | 多模板匹配时优先级冲突需谨慎配置；模板修改不影响已创建索引；组件模板组合复杂。 |

### 3.4 数据同步方案

| 维度 | 内容 |
|------|------|
| 是什么 | 将 MySQL 等关系库数据同步到 ES 的四种方案：Logstash、Canal、MQ 异步同步、双写。 |
| 能做什么 | 全量同步；增量实时同步；解耦异步同步；业务代码双写。 |
| 怎么用 | 推荐 Canal + Kafka 组合：`MySQL binlog → Canal Server → Kafka → ES 消费者`。 |
| 原理和工作流程 | Logstash 定时从 MySQL 拉取写入 ES，简单但有延迟；Canal 监听 MySQL binlog 解析变更事件写入 ES，实时零侵入但运维复杂；MQ 异步同步业务代码写 MySQL 后发 MQ，消费端写 ES，灵活但需业务配合；双写同时写 MySQL 和 ES，简单但一致性难保证。推荐 Canal + Kafka 解耦可靠实时。 |
| 缺点 | Logstash 有延迟影响 MySQL；Canal 运维复杂；MQ 需业务配合处理一致性；双写一致性差。 |

## 四、常见面试题

### 1. 什么是倒排索引？为什么比正向索引快？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查倒排索引的数据结构定义及其相比正向索引的性能优势。 |
| 能做什么 | 区分正排与倒排；说明时间复杂度差异；解释词频位置存储用途。 |
| 怎么用 | 检索时通过 Term Dictionary 二分查找或 FST 前缀树定位词项。 |
| 原理和工作流程 | 倒排索引是词项到文档 ID 列表的映射。正向索引是文档到词项映射，检索需遍历所有文档匹配关键词；倒排索引直接通过词项查找包含该词的文档列表，时间复杂度 O(1)。倒排索引还存储词频 TF 和位置信息，用于计算相关性评分排序搜索结果。 |
| 缺点 | 正向索引遍历慢不适合全文检索；倒排索引占用额外存储且更新成本高。 |

### 2. ES 的写入流程是怎样的？为什么是近实时（NRT）？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 写入链路和近实时搜索（NRT）机制的原因。 |
| 能做什么 | 描述写入流程；解释 NRT 1 秒延迟来源；说明 Refresh 折中设计。 |
| 怎么用 | `refresh_interval=1s` 控制刷新周期，可调整以平衡实时性与性能。 |
| 原理和工作流程 | 写入流程：客户端请求 → 协调节点路由 → 主分片写内存 Buffer 和 Translog → 转发副本分片 → 副本成功返回。近实时原因：文档写入后先入内存 Buffer 不可搜索，默认每 1 秒 Refresh 将 Buffer 刷新为 Segment 并打开才可搜索。1 秒延迟是性能与实时性折中，若每次写入立即刷新会产生大量小 Segment 严重影响性能。 |
| 缺点 | 1 秒延迟对强实时场景不满足；频繁刷新影响写入性能；调整参数需权衡。 |

### 3. ES 的分片策略？Primary Shard 和 Replica Shard 的作用？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Primary Shard 与 Replica Shard 的职责分工和分片分配策略。 |
| 能做什么 | 说明主分片水平扩展作用；说明副本高可用和读负载均衡作用；解释分配规则。 |
| 怎么用 | 主分片数创建时确定不可改；副本数 `number_of_replicas` 可动态调整。 |
| 原理和工作流程 | Primary Shard 是数据主要存储单元，创建索引时确定数量且不可修改，负责处理写请求，实现水平扩展容量和写入吞吐。Replica Shard 是主分片拷贝，数量可动态调整，主分片故障时提升为新主分片提供高可用，读请求可分发到副本实现负载均衡。主分片和其副本不会分配到同一节点。 |
| 缺点 | 主分片数不可改需 Reindex；副本增加写入开销；分配不均需手动调整。 |

### 4. ES 如何保证数据一致性？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ES 通过 Translog 和 Flush 保障数据不丢失，以及 AP 系统的一致性特征。 |
| 能做什么 | 说明 Translog 重放恢复；说明 Flush 持久化机制；指出 ES 是 AP 系统。 |
| 怎么用 | Translog 自动写入；Flush 默认 30 分钟或 512MB 触发。 |
| 原理和工作流程 | ES 通过 Translog + 定期 Flush 保证数据不丢失。每次写入先写 Translog 再写内存 Buffer，节点宕机重启从 Translog 重放未持久化操作。Flush 定期将 Segment 持久化到磁盘并清空 Translog。ES 是 AP 系统，牺牲强一致性换取高可用和分区容错，写入成功返回表示所有副本已写入，但读取时可能读到旧数据。 |
| 缺点 | AP 系统不保证强一致性；读取可能读到旧数据；不适合事务型主存储。 |

### 5. IK 分词器的 ik_smart 和 ik_max_word 区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 IK 分词器两种模式的特点和最佳实践搭配。 |
| 能做什么 | 区分粗粒度与细粒度；说明适用场景；给出索引与搜索的搭配建议。 |
| 怎么用 | 索引时 `analyzer: ik_max_word`；搜索时 `search_analyzer: ik_smart`。 |
| 原理和工作流程 | ik_smart 是粗粒度分词模式，尽量切分出最少的词，适合搜索时使用提高准确率。ik_max_word 是细粒度分词模式，穷尽所有可能的词组合，适合索引时使用提高召回率。最佳实践：索引时用 ik_max_word 尽可能多切分词提高召回率，搜索时用 ik_smart 精确匹配提高准确率。 |
| 缺点 | ik_smart 召回率低可能漏匹配；ik_max_word 切分过多索引膨胀；词典维护成本。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | ES 实战开发中常见错误的现象、原因和解决方案汇总。 |
| 能做什么 | 识别动态映射误识别；规避分片数设置问题；避免用 ES 做主存储；解决深度分页。 |
| 怎么用 | 关闭动态映射 `dynamic:"strict"`；聚合用 keyword；深度分页用 search_after。 |
| 原理和工作流程 | 动态映射默认开启会自动推断字段类型导致日期误识别，需关闭或用 dynamic_templates 控制。分片数创建后不可修改需提前规划。ES 是 AP 系统不支持事务，MySQL 做主存储 ES 做只读副本。深度分页协调节点需收集 from+size 条数据默认限 10000，用 search_after 或 scroll 解决。text 字段聚合无意义需用 keyword。频繁写入产生小 Segment 需低峰 _forcemerge。 |
| 缺点 | 避坑依赖经验积累；动态映射和分片数问题一旦发生难以挽回；监控不到位隐患大。 |
