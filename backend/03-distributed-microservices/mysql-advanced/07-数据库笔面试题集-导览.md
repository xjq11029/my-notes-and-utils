### 1. ★ MySQL 默认存储引擎是？

| 维度 | 内容 |
|------|------|
| 是什么 | MySQL 5.5.5 之后默认使用的存储引擎，支持事务、行锁、外键和崩溃恢复 |
| 能做什么 | 提供事务 ACID 保障；行级锁支持高并发；外键约束保证参照完整性；崩溃后通过 redo log 恢复数据 |
| 怎么用 | 建表时省略 ENGINE 子句默认即为 InnoDB，或显式指定 `ENGINE=InnoDB` |
| 原理和工作流程 | MySQL 5.5.5 起 default_storage_engine 设为 InnoDB，替代早期默认的 MyISAM。InnoDB 采用聚簇索引组织数据，内存层 Buffer Pool 缓存数据页与索引页，磁盘层通过 redo log 保证持久性、undo log 支持回滚与 MVCC |
| 缺点 | 内存与磁盘占用大于 MyISAM；写性能不及 MyISAM；旧版本全文索引支持弱于 MyISAM |

### 2. ★★ InnoDB 中数据和索引的存储关系是？

| 维度 | 内容 |
|------|------|
| 是什么 | InnoDB 中数据与索引合一存储的聚簇索引结构，主键索引叶子节点存完整行数据 |
| 能做什么 | 主键查询直接定位行数据；二级索引存储主键值作为指针；通过回表获取完整行 |
| 怎么用 | 定义主键即建立聚簇索引，二级索引自动存储主键值 |
| 原理和工作流程 | InnoDB 聚簇索引的叶子节点存储完整行数据，二级索引叶子节点存储索引列值与主键值。查询二级索引时先获取主键，再到聚簇索引回表查全行。MyISAM 数据与索引分离属于非聚簇 |
| 缺点 | 聚簇索引只能有一个；主键过长导致所有二级索引体积膨胀；非顺序主键插入引发页分裂 |

### 3. ★★ B+ 树中，数据存储在？

| 维度 | 内容 |
|------|------|
| 是什么 | B+ 树数据存储位置的判定，数据只存于叶子节点 |
| 能做什么 | 区分 B+ 树与 B 树的数据分布；理解 InnoDB 索引底层结构；判断范围查询效率 |
| 怎么用 | 理解索引数据结构特性，为查询优化提供依据 |
| 原理和工作流程 | B+ 树非叶子节点只存储索引键与指针不存数据，单页可容纳更多键降低树高；叶子节点存储全部数据并通过双向链表相连，支持高效范围扫描。B 树在所有节点都存储数据 |
| 缺点 | 等值查询必须遍历到叶子节点路径略长；链表维护有额外开销 |

### 4. ★ 以下哪个 SQL 子句可能导致索引失效？

| 维度 | 内容 |
|------|------|
| 是什么 | LIKE 前导通配符查询导致索引失效的场景 |
| 能做什么 | 识别 LIKE 语句能否走索引；指导模糊查询编写规范 |

### 5. ★★ EXPLAIN 输出中，以下哪个 type 表示全表扫描？

| 维度 | 内容 |
|------|------|
| 是什么 | EXPLAIN 输出中 type 列表示的访问类型，ALL 表示全表扫描 |
| 能做什么 | 判断查询是否走索引；评估访问类型优劣；定位必须优化的全表扫描 SQL |
| 怎么用 | 执行 `EXPLAIN SELECT ...`，查看 type 列的值 |
| 原理和工作流程 | type 从优到劣为 system > const > eq_ref > ref > range > index > ALL。const 为主键或唯一索引等值查询，ref 为非唯一索引等值查询，range 为范围扫描，index 为扫描整个索引树，ALL 为扫描整表数据。出现 ALL 必须优化 |
| 缺点 | type 仅反映访问类型不展示索引选择是否最优；需结合 rows、filtered 综合判断 |

### 6. ★★ EXPLAIN 输出中 Extra 显示 "Using filesort" 表示？

| 维度 | 内容 |
|------|------|
| 是什么 | EXPLAIN 中 Extra 列出现 Using filesort 表示需要额外排序操作 |
| 能做什么 | 发现无法利用索引排序的 SQL；提示排序环节需优化 |
| 怎么用 | 执行 EXPLAIN 后检查 Extra 是否出现 Using filesort |
| 原理和工作流程 | 当 ORDER BY 字段无法利用索引有序性时，MySQL 在内存或磁盘执行额外排序。数据量小在内存 sort buffer 完成，数据量大落盘产生临时文件排序，性能急剧下降 |
| 缺点 | filesort 消耗 CPU 与内存；大数据量落盘排序导致 IO 飙升；需为排序字段建索引消除 |

### 7. ★★ 联合索引 (a, b, c) 中，以下哪个查询可以使用索引？

| 维度 | 内容 |
|------|------|
| 是什么 | 联合索引 (a,b,c) 的最左前缀匹配原则 |
| 能做什么 | 判断 WHERE 条件能否命中联合索引；指导联合索引列顺序设计 |
| 怎么用 | 查询条件须从最左列开始连续使用，`WHERE a=1 AND b=1` 可用索引 |
| 原理和工作流程 | 联合索引按字段顺序在 B+ 树中排序，先按 a 排序、a 相同按 b、b 相同按 c。跳过最左列 a 无法利用有序性。`WHERE a=1 AND c=1` 中 a 可用索引但 c 跳过 b 无法使用；等值条件顺序可由优化器调整但范围查询后列失效 |
| 缺点 | 范围查询后列失效；业务多变时索引列顺序设计成本高；调整顺序需重建索引 |

### 8. ★★ COUNT(*) 和 COUNT(列名) 的区别是？

| 维度 | 内容 |
|------|------|
| 是什么 | COUNT(*) 与 COUNT(列名) 在统计 NULL 行时的语义差异 |
| 能做什么 | 正确统计行数；区分是否包含 NULL 行；避免统计偏差 |
| 怎么用 | COUNT(*) 统计所有行包含 NULL 行，COUNT(列名) 不统计该列为 NULL 的行 |
| 原理和工作流程 | COUNT(*) 不关心列值直接统计所有行；COUNT(列名) 逐行判断该列是否为 NULL，NULL 行不计入。MySQL 对 COUNT(*) 做了优化通常使用最小索引扫描，性能等于或优于 COUNT(列名) |
| 缺点 | COUNT(列名) 语义易被误用导致统计遗漏；NULL 语义在不同数据库可能不同 |

### 9. ★★ 以下关于乐观锁和悲观锁说法正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 乐观锁与悲观锁两种并发控制策略的对比 |
| 能做什么 | 根据冲突频率选择锁机制；乐观锁通过版本号实现不阻塞；悲观锁通过数据库锁阻塞保证一致 |
| 怎么用 | 乐观锁用版本号或 CAS 校验，悲观锁用 `SELECT ... FOR UPDATE` 加锁 |
| 原理和工作流程 | 乐观锁假设并发冲突少，读取时记录版本号，提交时校验版本号是否变化，冲突则重试。悲观锁假设冲突多，操作前先加排他锁阻塞其他事务，保证串行执行 |
| 缺点 | 乐观锁高并发下重试频繁甚至活锁；悲观锁阻塞降低吞吐量易死锁 |

### 10. ★★ 分库分表中，以下哪个不是常用的分片算法？

| 维度 | 内容 |
|------|------|
| 是什么 | 分库分表常用分片算法的识别，随机分片不属于常用算法 |
| 能做什么 | 为数据分布选择合适分片策略；保证数据均匀分布与可路由 |
| 怎么用 | 哈希取模、一致性哈希、范围分片、日期分片 |

| 缺点 | 哈希取模扩容迁移成本高；范围分片易热点；一致性哈希实现复杂；跨分片查询性能差 |

### 12. ★★ MyBatis 中 #{} 和 ${} 的区别是？

| 维度 | 内容 |
|------|------|
| 是什么 | MyBatis 中 #{} 与 ${} 两种参数传递方式的区别 |
| 能做什么 | 选择安全的参数绑定方式；防止 SQL 注入；支持动态表名与排序字段 |
| 怎么用 | #{} 使用预编译占位符防注入，${} 字符串直接替换用于动态表名、排序字段等 |
| 原理和工作流程 | #{} 编译为 JDBC PreparedStatement 的 ? 占位符，参数以预编译方式绑定安全防注入。${} 在 SQL 解析阶段将参数原样字符串替换拼接到 SQL 中，存在 SQL 注入风险，仅用于无法预编译的场景如表名、列名、ORDER BY 字段 |
| 缺点 | ${} 存在 SQL 注入风险必须确保参数来源可信；误用 ${} 替代 #{} 带来安全隐患 |

### 13. ★★ JPA 中 @OneToMany 和 @ManyToOne 的默认 fetch 策略分别是？

| 维度 | 内容 |
|------|------|
| 是什么 | JPA 关联注解 @OneToMany 与 @ManyToOne 的默认 fetch 策略 |
| 能做什么 | 控制关联对象是否懒加载；避免不必要的关联查询 |
| 怎么用 | @OneToMany 与 @ManyToMany 默认 LAZY，@OneToOne 与 @ManyToOne 默认 EAGER |
| 原理和工作流程 | LAZY 延迟加载，首次访问关联属性时才发送查询；EAGER 立即加载，主查询时同步关联查询。JPA 规范将多对一与一对一设为 EAGER 因关联对象通常单值需即时可用，一对多与多对多设为 LAZY 避免一次加载大量关联数据 |
| 缺点 | EAGER 导致 N+1 问题和多余查询；LAZY 在事务外访问关联抛 LazyInitializationException |

### 14. ★★ MyBatis-Plus 默认的主键生成策略是？

| 维度 | 内容 |
|------|------|
| 是什么 | MyBatis-Plus 3.3.0+ 默认的主键生成策略 ASSIGN_ID |
| 能做什么 | 为实体生成分布式唯一 Long 型 ID；基于雪花算法保证趋势递增 |
| 怎么用 | 实体主键标注 `@TableId(type = IdType.ASSIGN_ID)` 或使用默认策略 |
| 原理和工作流程 | MyBatis-Plus 3.3.0 起默认 ASSIGN_ID，基于雪花算法生成 Long 型 ID。雪花算法由时间戳、机器位、序列位组合，时间戳保证趋势递增，机器位区分节点，序列位支持单节点毫秒内多 ID。3.3.0 之前默认 ID_WORKER |
| 缺点 | 依赖机器时钟，时钟回拨会导致重复 ID；Long 型 ID 超过 JS 安全整数范围前端精度丢失需转字符串 |

### 15. ★★ 以下哪个不是事务的 ACID 特性？

| 维度 | 内容 |
|------|------|
| 是什么 | 事务 ACID 四大特性与 CAP 可用性的区分 |
| 能做什么 | 正确识别事务特性；区分数据库事务理论与分布式 CAP 理论 |
| 怎么用 | ACID 为原子性、一致性、隔离性、持久性 |
| 原理和工作流程 | 原子性保证事务全部成功或全部回滚由 undo log 实现；一致性保证事务前后数据满足约束；隔离性控制并发事务间可见性由锁与 MVCC 实现；持久性保证提交结果永久存储由 redo log 实现。可用性是 CAP 理论中分布式系统的特性不属于事务 ACID |
| 缺点 | 强隔离级别降低并发性能；分布式场景下 ACID 难以保证需 BASE 与最终一致性折中 |

### 16. ★★★ 以下关于 JPA N+1 问题说法正确的是？

| 维度 | 内容 |
|------|------|
| 是什么 | JPA N+1 问题的成因与解决方案 |
| 能做什么 | 识别关联查询产生的多次额外 SQL；通过 JOIN FETCH、@EntityGraph、@BatchSize 消除 |
| 怎么用 | `@EntityGraph` 预定义关联抓取；`JOIN FETCH` 显式关联查询；`@BatchSize` 批量加载 |
| 原理和工作流程 | N+1 问题指查询 N 条主记录后，访问延迟加载关联时逐条触发额外查询共 N+1 次 SQL。LAZY 关联被访问时即时查询且无批量优化。JOIN FETCH 在主查询用 JOIN 一次性加载关联；@EntityGraph 通过查询提示指定抓取关联；@BatchSize 将逐条查询改为按批次 IN 查询 |
| 缺点 | JOIN FETCH 对多条关联产生笛卡尔积膨胀；@BatchSize 需调优批次大小；@EntityGraph 配置复杂 |

### 18. ★★ MySQL 中，以下哪个索引类型是最常用的？

| 维度 | 内容 |
|------|------|
| 是什么 | MySQL InnoDB 默认使用的 B+ 树索引类型 |
| 能做什么 | 支持等值查询、范围查询、排序、前缀匹配等多种查询模式 |

### 19. ★★ @Transactional 注解的默认传播行为是？

| 维度 | 内容 |
|------|------|
| 是什么 | @Transactional 注解的默认事务传播行为 REQUIRED |
| 能做什么 | 控制事务在方法调用链间的传播方式；决定是否复用当前事务 |
| 怎么用 | `@Transactional` 不指定 propagation 时默认 REQUIRED |
| 原理和工作流程 | Spring 通过 AOP 代理拦截 @Transactional 方法。REQUIRED 语义为当前存在事务则加入，不存在则新建。REQUIRES_NEW 总是挂起当前事务新建独立事务；SUPPORTS 有事务则加入无则非事务运行；NESTED 创建嵌套子事务依赖父事务 |
| 缺点 | REQUIRED 嵌套调用内层异常会标记外层事务回滚；需隔离时配置 REQUIRES_NEW 增加事务开销 |

### 20. ★★ 以下关于索引的说法错误的是？

| 维度 | 内容 |
|------|------|
| 是什么 | 索引数量与性能关系的正确认识，索引并非越多越好 |
| 能做什么 | 合理控制单表索引数量；权衡查询加速与写入开销 |
| 怎么用 | 每张表索引建议不超过 5 到 6 个，根据查询模式精简冗余索引 |
| 原理和工作流程 | 索引通过 B+ 树加速查询但占用磁盘空间。INSERT、UPDATE、DELETE 时需同步维护所有索引的 B+ 树结构，索引越多写入性能越低。优化器选择索引时需评估更多候选增加成本，索引过多还可能导致优化器选择非最优索引 |

| 是什么 | 查询每个部门工资排名前 2 员工的分组 Top-N 排名查询 |
| 能做什么 | 实现每组取前 N 名；处理并列排名 |
| 怎么用 | `DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC)` 后过滤 `rk <= 2` |
| 原理和工作流程 | DENSE_RANK 按部门分区按工资降序排名，同薪并列同名且不跳号（如两个第 1 名后下一个为第 2 名）。外层过滤 rk <= 2 取前 2 名。ROW_NUMBER 同薪也会分配不同序号不保留并列。需 MySQL 8.0+ |
| 缺点 | 需 MySQL 8.0+；DENSE_RANK 并列多时返回行数超过 N；若需严格 N 行用 ROW_NUMBER 但丢失并列语义 |
