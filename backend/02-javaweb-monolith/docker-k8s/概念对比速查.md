# Docker 与 Kubernetes - 概念对比速查

---

### Docker vs 虚拟机

| 对比维度 | Docker 容器 | 虚拟机 |
|---------|-------|-------|
| 核心定位 | 进程级隔离，共享宿主机内核 | 硬件级虚拟化，每个 VM 运行独立操作系统 |
| 适用场景 | 微服务部署、CI/CD、快速扩缩容 | 运行不同操作系统、强隔离需求、传统应用迁移 |
| 资源占用 | 轻量级，MB 级别，共享宿主机内核 | 重量级，GB 级别，每个 VM 有完整 OS |
| 启动速度 | 秒级 | 分钟级 |
| 隔离级别 | 进程级（Namespace + Cgroups） | 完全隔离（Hypervisor） |
| 性能损耗 | 接近原生性能 | 有 Hypervisor 层开销 |
| 镜像大小 | 通常几十 MB 到几百 MB | 通常几 GB |
| 可移植性 | 镜像可在任何支持 Docker 的环境中运行 | 跨 Hypervisor 迁移较复杂 |
| 选择建议 | 应用容器化部署、微服务架构、快速迭代场景用 Docker | 需要完全隔离、运行不同内核或不同操作系统时用虚拟机 |

### Dockerfile CMD vs ENTRYPOINT

| 对比维度 | CMD | ENTRYPOINT |
|---------|-----|------------|
| 核心定位 | 为容器提供默认的执行命令和参数 | 定义容器的主进程，作为固定入口点 |
| 适用场景 | 提供可被 `docker run` 命令行覆盖的默认行为 | 固定容器启动行为，将容器当作可执行程序 |
| 可覆盖性 | `docker run` 后的命令行参数会完全替换 CMD | `docker run` 后的参数作为追加参数传给 ENTRYPOINT |
| 组合使用 | 单独使用提供默认命令 | 与 CMD 组合：ENTRYPOINT 定义固定命令，CMD 提供默认参数 |
| Shell 形式 | `CMD command param1 param2`（通过 /bin/sh -c 执行） | `ENTRYPOINT command param1 param2`（通过 /bin/sh -c 执行） |
| Exec 形式 | `CMD ["executable","param1","param2"]`（推荐） | `ENTRYPOINT ["executable","param1","param2"]`（推荐） |
| 信号转发 | Shell 形式不转发信号 | Exec 形式正确转发信号 |
| 选择建议 | 需要灵活的默认命令时用 CMD | 需要将容器当作固定工具使用时用 ENTRYPOINT |

### Docker Compose vs Kubernetes

| 对比维度 | Docker Compose | Kubernetes |
|---------|----------------|------------|
| 核心定位 | 单机多容器编排工具 | 分布式容器编排平台 |
| 适用场景 | 本地开发环境、单机部署、CI 测试 | 生产环境、多节点集群、大规模服务编排 |
| 集群规模 | 单机 | 多节点集群，支持数千节点 |
| 服务发现 | 内置 DNS（通过服务名访问） | 内置 DNS + Service + Ingress |
| 负载均衡 | 无内置 | Service（ClusterIP/NodePort/LoadBalancer）+ Ingress |
| 自动扩缩 | 不支持 | HPA（水平自动扩缩） |
| 滚动更新 | 不支持 | 内置 RollingUpdate 策略 |
| 自愈能力 | 基础 restart 策略 | 自动重启、重新调度、健康检查 |
| 配置管理 | 环境变量、.env 文件 | ConfigMap、Secret |
| 存储编排 | Volume 挂载 | PV/PVC/StorageClass 动态供给 |
| 配置文件 | docker-compose.yml（YAML） | 多种资源 YAML（Deployment、Service、ConfigMap 等） |
| 选择建议 | 本地开发、单机部署、简单编排用 Docker Compose | 生产级多节点部署、需要高可用和自动运维用 Kubernetes |

### Deployment vs StatefulSet vs DaemonSet

| 对比维度 | Deployment | StatefulSet | DaemonSet |
|---------|------------|-------------|-----------|
| 核心定位 | 管理无状态应用的副本集 | 管理有状态应用，保证 Pod 唯一性和有序性 | 确保每个节点运行一个 Pod 副本 |
| 适用场景 | Web 服务、API 网关、微服务 | 数据库（MySQL、MongoDB）、消息队列（Kafka）、分布式存储 | 日志收集（Fluentd）、监控（Prometheus Node Exporter）、网络插件 |
| Pod 标识 | 随机名称（如 app-5d8f9c7b6-abcde） | 固定序号名称（如 app-0、app-1、app-2） | 以节点名称为后缀 |
| Pod 启停顺序 | 无序并行 | 有序启动（0,1,2...）和逆序停止（...,2,1,0） | 节点加入时自动创建，节点移除时自动删除 |
| 存储 | 共享 PVC，所有 Pod 使用相同存储 | 每个 Pod 独立 PVC（volumeClaimTemplates） | 通常使用 hostPath 或 local PV |
| 网络标识 | 无固定网络标识 | 固定 DNS 名称（pod-name.service-name） | 使用 hostNetwork 或 hostPort |
| 扩缩容 | 水平扩缩，修改 replicas 即可 | 有序扩缩容 | 跟随节点数自动变化 |
| 滚动更新 | 支持，可配置 maxSurge/maxUnavailable | 支持，但按逆序逐个更新 | 支持，逐个节点更新 |
| 选择建议 | 无状态应用（Web 服务、API）用 Deployment | 有状态应用（数据库、消息队列）用 StatefulSet | 每个节点都需要运行的系统级服务用 DaemonSet |
