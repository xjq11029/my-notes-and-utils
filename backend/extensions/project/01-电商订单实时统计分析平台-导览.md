## 一、项目架构

### 1.1 整体架构

| 维度 | 内容 |
|------|------|
| 是什么 | 由 Gateway、order-service、Kafka 及 search/stats/notification 三消费者组成的订单实时处理链路，订单事件异步分发到 ES、ClickHouse、通知渠道。 |
| 能做什么 | 订单创建与 MySQL 持久化；事件驱动异构存储同步；商品全文检索；海量订单聚合统计；订单通知下发。 |
| 怎么用 | `POST /api/orders → order-service 写 MySQL + 发 Kafka`<br>`→ search-service 消费写 ES / stats-service 写 ClickHouse / notification-service 发通知` |
| 原理和工作流程 | 用户下单请求经 Spring Cloud Gateway 鉴权路由到 order-service，order-service 在本地事务中写 MySQL 并通过 `kafkaTemplate.executeInTransaction()` 发送事务消息到 order-events topic。三个消费者以独立 consumer group 订阅：search-service 用 painless 脚本 upsert 更新 ES 商品销量索引；stats-service 按 1000 条或 5 秒批量缓冲写 ClickHouse；notification-service 发邮件短信。Kafka 解耦生产消费，各存储各司其职，MySQL 为业务主存储。 |
| 缺点 | 链路节点多（MySQL→Kafka→ES/ClickHouse），任一环节故障影响数据到达；最终一致性而非强一致，实时性要求高的查询需 MySQL 兜底；同时维护多种中间件，运维与排障成本高。 |

### 1.2 技术选型与理由

| 维度 | 内容 |
|------|------|
| 是什么 | 针对订单实时统计各环节选定的技术栈及选用依据，覆盖框架、ORM、消息队列、搜索引擎、分析库、注册中心、网关、熔断、容器。 |
| 能做什么 | Spring Boot+JPA 快速开发订单服务；Kafka 承载高吞吐订单事件流；ES 支撑全文检索；ClickHouse 秒级聚合十亿行；Nacos 统一注册与配置；Sentinel 限流熔断；Docker+K8s 标准化部署。 |
| 怎么用 | `Spring Boot 2.7 + JPA`<br>`Kafka 3.x` / `ES 7.17` / `ClickHouse 23.x` / `MySQL 8.0`<br>`Nacos 2.x` / `Gateway 3.1` / `Sentinel 1.8` / `Docker+K8s` |
| 原理和工作流程 | 选型依据各组件特性匹配业务需求：Kafka 分区机制支撑百万 TPS 订单写入与并行消费；ES 倒排索引加 IK 分词实现商品关键词搜索与高亮；ClickHouse 列式存储加 MergeTree 引擎加物化视图预聚合实现秒级聚合；MySQL InnoDB 事务保证订单强一致主存储；Nacos 同时提供服务发现与配置中心减少组件数；Gateway 响应式非阻塞优于 Zuul；Sentinel 滑动窗口统计实现流量控制与熔断降级；Docker 镜像加 K8s 编排实现弹性伸缩与滚动发布。 |
| 缺点 | 技术栈过重，小规模场景过度设计；多组件版本兼容性需持续维护（如 ES 7.x 与 Spring Data ES 版本对齐）；部分选型存在替代争议（Nacos vs Eureka、Sentinel vs Hystrix），团队学习曲线陡。 |

## 二、模块设计

### 2.1 order-service（订单服务）

| 维度 | 内容 |
|------|------|
| 是什么 | 系统中唯一写 MySQL 并生产 Kafka 事件的订单核心业务服务，负责订单创建、查询、取消及事件生产。 |
| 能做什么 | 创建订单并生成唯一 order_no；分页查询用户订单；取消订单；在本地事务中同时写 MySQL 与发送 ORDER_CREATED 事件；保证 DB 与消息一致性。 |
| 怎么用 | `@Transactional(rollbackFor = Exception.class)`<br>`order = orderRepository.save(order);`<br>`kafkaTemplate.executeInTransaction(ops -> ops.send("order-events", id, event));` |
| 原理和工作流程 | Controller 接收 CreateOrderDTO 校验后调用 Service。Service 标注 `@Transactional` 开启本地事务，先构建 Order 实体（含唯一 order_no、CREATED 状态）调用 JPA save 写入 MySQL InnoDB，再构建 OrderEvent 通过 `kafkaTemplate.executeInTransaction()` 发送事务消息到 order-events topic。Kafka 事务与 DB 事务绑定：消息发送失败则 DB 回滚，避免 DB 有记录而消息丢失。事件含 orderId、userId、productId、amount、quantity 等完整字段供下游消费。 |
| 缺点 | 本地事务加 Kafka 事务仅保证“都成功或都失败”，无法解决“消息发出但下游消费失败”的跨服务一致性，需消费者幂等加重试兜底；事务期间持有 DB 连接与 Kafka Producer 资源，高并发下吞吐受限；order_no 生成与库存校验未展开，生产需补充。 |

### 2.2 search-service（搜索服务）

| 维度 | 内容 |
|------|------|
| 是什么 | 消费 Kafka 订单事件维护 ES 商品搜索索引，并提供关键词检索、过滤、排序、高亮、聚合的搜索服务。 |
| 能做什么 | 消费订单事件更新 ES 商品销量；关键词全文检索（IK 分词）；分类与价格区间过滤；销量评分排序；关键词高亮；分类与价格区间聚合统计。 |
| 怎么用 | `@KafkaListener(topics = "order-events", groupId = "search-service-group")`<br>`UpdateRequest u = new UpdateRequest("products", pid);`<br>`u.script(new Script(INLINE, "painless", "ctx._source.salesCount += params.qty", map)).upsert(doc);` |
| 原理和工作流程 | 消费者以 search-service-group 订阅 order-events，收到事件构建 UpdateRequest，用 painless 脚本 `ctx._source.salesCount += params.quantity` 原子累加商品销量，配合 upsert 保证文档不存在时自动创建。搜索 API 用 NativeSearchQueryBuilder 组装 bool 查询：multiMatch 对 productName 加权 3 倍、must 过滤 ON_SALE 状态、term 过滤分类、range 过滤价格、addAggregation 做分类 terms 与价格区间 range 聚合，HighlightBuilder 对 productName 加 `<em>` 标签，PageRequest 分页。 |
| 缺点 | ES 写入有 1-2 秒 refresh 延迟，刚下单商品即时搜索可能查不到；painless 脚本累加并发下可能冲突，需 retry 或 version 控制；高亮与聚合增加查询开销，大结果集 size 需控制；索引 mapping 变更需重建索引。 |

### 2.3 stats-service（统计服务）

| 维度 | 内容 |
|------|------|
| 是什么 | 消费 Kafka 订单事件批量写入 ClickHouse，并通过物化视图预聚合提供小时、分类、趋势统计分析 API 的服务。 |
| 能做什么 | 批量缓冲订单事件写 ClickHouse；按月分区与 TTL 自动过期；物化视图预聚合小时销售额与订单数；小时统计、分类汇总、日趋势查询接口；毫秒级聚合响应。 |
| 怎么用 | `@KafkaListener(topics = "order-events", groupId = "stats-service-group")`<br>`buffer.add(e); if (buffer.size() >= 1000) flush();`<br>`@Scheduled(fixedDelay = 5000) scheduledFlush(); // batchUpdate INSERT` |
| 原理和工作流程 | 消费者以 stats-service-group 订阅，事件先入内存 buffer，达 BATCH_SIZE=1000 或 `@Scheduled` 每 5 秒触发 flush。flush 用 JdbcTemplate.batchUpdate 批量 INSERT 到 order_events 表（MergeTree 引擎，PARTITION BY toYYYYMM 按月分区，ORDER BY event_date,category,event_time 排序键，TTL 180 天自动清理）。物化视图 mv_order_hourly 以 toStartOfHour 分组、SummingMergeTree 预聚合到 order_hourly_stats，统计 API 直接查预聚合表实现毫秒级响应。 |
| 缺点 | 内存 buffer 进程崩溃丢失未 flush 数据，需配合 Kafka 手动 offset 提交与重消费；批量 INSERT 产生多个 Part，频繁小批量触发 merge 压力；物化视图仅支持特定聚合维度，临时多维分析仍需扫源表；ClickHouse 不擅长高频单条更新，状态变更场景受限。 |

### 2.4 notification-service（通知服务）

| 维度 | 内容 |
|------|------|
| 是什么 | 消费 Kafka 订单事件发送邮件短信通知，并基于 Redis 实现幂等去重的服务。 |
| 能做什么 | 消费订单事件触发通知；发送订单确认邮件；基于 orderId 的 Redis 幂等去重；发送失败删除去重标记允许重试；24 小时去重窗口。 |
| 怎么用 | `@KafkaListener(topics = "order-events", groupId = "notification-service-group")`<br>`String key = "notification:order:" + event.getOrderId();`<br>`if (!redis.setIfAbsent(key, "1", Duration.ofHours(24))) return;` |
| 原理和工作流程 | 消费者以 notification-service-group 订阅，收到事件先以 `notification:order:{orderId}` 为键调用 `setIfAbsent` 写入 Redis（24 小时过期）。返回 true 表示首次消费，调用 EmailService 发送订单确认邮件；返回 false 表示重复消费直接跳过。若发送抛异常，catch 块删除 Redis 去重标记，使 Kafka 重试时能重新处理，避免因临时故障导致通知永久丢失。抛出 RuntimeException 触发 Kafka 消费者重试机制。 |
| 缺点 | Redis 宕机期间去重失效，可能重复发送通知；邮件短信第三方服务自身可能重复投递，去重仅覆盖本服务侧；24 小时窗口外的迟到事件会被视为新事件重复处理；通知与订单状态强耦合，扩展多渠道通知需改造。 |

## 三、微服务架构

### 3.1 服务注册与发现

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Nacos 实现微服务注册发现与配置管理的机制，各服务启动注册到 Nacos 并拉取共享配置。 |
| 能做什么 | 服务自动注册与心跳保活；服务名解析负载均衡；命名空间隔离 dev/prod；配置中心动态刷新；共享 common-config.yaml。 |
| 怎么用 | `spring.cloud.nacos.discovery.server-addr: localhost:8848`<br>`spring.cloud.nacos.discovery.namespace: dev`<br>`spring.cloud.nacos.config.shared-configs: [{data-id: common-config.yaml, refresh: true}]` |
| 原理和工作流程 | 各服务在 bootstrap.yml 配置 Nacos 地址与 namespace，启动时向 Nacos 注册实例信息（IP、端口、服务名）并维持心跳。服务间调用时通过服务名从 Nacos 拉取实例列表，客户端负载均衡（Ribbon/LoadBalancer）选择实例。配置中心部分 Nacos 存储 yaml 配置，shared-configs 引用公共配置 common-config.yaml 并开启 refresh，配置变更时 Nacos 推送至 `@RefreshScope` 标注的 Bean 实现热更新，namespace 实现多环境隔离。 |
| 缺点 | Nacos 单节点故障导致服务发现瘫痪，生产需集群部署；服务列表拉取有延迟，实例上下线瞬间可能调用失败实例；配置热更新仅对 RefreshScope Bean 生效，静态字段不刷新；namespace 与 group 设计不当易导致配置混乱。 |

### 3.2 服务间调用

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 OpenFeign 声明式调用实现微服务间 HTTP 通信，并集成 Sentinel 实现熔断降级的机制。 |
| 能做什么 | 声明式接口调用远程服务；服务名寻址自动负载均衡；FallbackFactory 熔断降级；异常隔离与日志记录；失败返回兜底结果。 |
| 怎么用 | `@FeignClient(name = "search-service", path = "/internal",`<br>`    fallbackFactory = SearchFeignFallbackFactory.class)`<br>`Result<Void> updateSales(@PathVariable Long pid, @RequestBody UpdateSalesDTO dto);` |
| 原理和工作流程 | `@FeignClient` 声明接口，Spring 动态代理生成 HTTP 客户端，调用时根据 name 从 Nacos 解析实例列表，负载均衡选择实例发起请求。集成 Sentinel 后请求先经 Sentinel 插槽：统计 QPS 与异常比例，超阈值触发熔断，转而调用 FallbackFactory.create() 返回的兜底实现。FallbackFactory 接收 Throwable cause 可记录失败原因，返回 Result.fail("搜索服务暂时不可用")，避免级联故障扩散，熔断恢复期后自动半开探测。 |
| 缺点 | 同步 HTTP 调用增加链路延迟与线程占用，高并发下线程池易耗尽；Fallback 掩盖异常，业务方可能误以为成功；熔断阈值需精细调参，过低误熔断过高失去保护；声明式接口隐藏网络细节，调试排障困难。 |

### 3.3 网关路由

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Spring Cloud Gateway 实现的统一入口网关，承担路由转发、JWT 鉴权与 Redis 令牌桶限流。 |
| 能做什么 | 按 Path 谓词路由到各服务；StripPrefix 去前缀；Redis 令牌桶限流；全局 JWT 鉴权过滤器；lb 前缀负载均衡。 |
| 怎么用 | `routes: [{id: order-service, uri: lb://order-service,`<br>`  predicates: [Path=/api/orders/**], filters: [StripPrefix=1,`<br>`  {name: RequestRateLimiter, args: {replenishRate: 100, burstCapacity: 200}}]}]`<br>`default-filters: [{name: JwtAuthFilter}]` |
| 原理和工作流程 | Gateway 基于 WebFlux 响应式非阻塞模型，请求进入后按 routes 配置顺序匹配 Path 谓词，命中后 filters 链式处理：StripPrefix=1 去掉 /api 前缀，RequestRateLimiter 基于 Redis Lua 脚本实现令牌桶（replenishRate=100 每秒补充 100 令牌，burstCapacity=200 桶容量），超限返回 429。default-filters 的 JwtAuthFilter 全局校验 JWT。最终 uri 为 lb://service-name 时，Gateway 从注册中心解析实例负载均衡转发。 |
| 缺点 | 限流维度单一（全局限流），无法按用户 IP 精细化控制，需自定义 KeyResolver；JWT 全局过滤对所有路由生效，公开接口需单独排除配置；网关单点故障影响全局，需多实例加负载均衡；响应式编程模型对同步业务逻辑不友好。 |

## 四、容器化部署

### 4.1 Docker Compose 编排

| 维度 | 内容 |
|------|------|
| 是什么 | 用 docker-compose.yml 单文件编排 MySQL、Kafka、ES、ClickHouse、Nacos、Redis 及五个微服务的本地开发环境。 |
| 能做什么 | 一键启动全部依赖中间件与服务；声明服务依赖启动顺序；healthcheck 健康检查；端口映射；构建各服务镜像。 |
| 怎么用 | `version: '3.8'`<br>`mysql: {image: mysql:8.0, healthcheck: [CMD, mysqladmin, ping]}`<br>`order-service: {build: ./order-service, depends_on: {mysql: {condition: service_healthy}}}` |
| 原理和工作流程 | Compose 解析 yml 构建服务依赖图，按依赖顺序启动：先启动 zookeeper 再 kafka，mysql 带 healthcheck（mysqladmin ping）healthy 后才启动 order-service。各服务通过 build 指向 Dockerfile 构建镜像，ports 映射主机端口到容器。中间件用官方镜像加环境变量配置（如 KAFKA_ZOOKEEPER_CONNECT、ES_JAVA_OPTS 内存、Nacos MODE=standalone）。服务间通过服务名（如 kafka:9092）在 Compose 网络内 DNS 解析通信。 |
| 缺点 | 单机部署无法生产可用，无高可用与弹性伸缩；depends_on 仅控制启动顺序不保证就绪，需配合 healthcheck；密码明文写在 yml 有安全风险；网络与存储卷配置简化，重启数据可能丢失（中间件未挂持久卷）。 |

### 4.2 K8s 部署

| 维度 | 内容 |
|------|------|
| 是什么 | 用 Kubernetes Deployment、Service、ConfigMap、HPA 实现的容器化生产部署方案，含探针与水平自动扩缩。 |
| 能做什么 | 副本数控制与滚动更新；liveness/readiness 探针自愈；ConfigMap 注入环境配置；HPA 按 CPU 内存自动扩缩；ClusterIP 服务发现。 |
| 怎么用 | `kind: Deployment, spec.replicas: 2`<br>`livenessProbe: {httpGet: {path: /actuator/health/liveness}}`<br>`kind: HorizontalPodAutoscaler, minReplicas: 2, maxReplicas: 10, metrics: cpu averageUtilization: 70` |
| 原理和工作流程 | Deployment 声明期望副本数 2，Controller Manager 持续调谐使实际 Pod 数趋近期望，滚动更新时新建 Pod 就绪才删旧 Pod。livenessProbe 探测 /actuator/health/liveness 失败重启容器，readinessProbe 探测 /actuator/health/readiness 失败将 Pod 移出 Service 端点。ConfigMap 以 envFrom 注入数据库、Kafka、Nacos 地址等环境变量。HPA 每周期从 Metrics Server 拉取 CPU 内存利用率，超 70%/80% 阈值计算目标副本数在 2-10 间扩缩。 |
| 缺点 | HPA 基于 CPU 内存无法反映业务 QPS，需自定义指标（Prometheus Adapter）才精准；滚动更新期间新老版本共存，需接口版本兼容；ConfigMap 明文存储敏感信息不安全，Secret 更合适；探针阈值不当导致频繁重启或假健康。 |

## 五、性能优化

### 5.1 Kafka 优化

| 维度 | 内容 |
|------|------|
| 是什么 | 针对订单事件流场景的 Kafka 生产消费调优配置，通过分区、批量、压缩、并行提升吞吐。 |
| 能做什么 | 6 分区提高并行消费；Producer 批量发送加 linger 延迟聚合；snappy 压缩减网络量；Consumer 批量拉取 500 条；concurrency=3 匹配分区。 |
| 怎么用 | `分区数: 6 (3 Broker × 2)`<br>`batch.size=16KB, linger.ms=10, compression.type=snappy`<br>`max.poll.records=500, concurrency=3` |
| 原理和工作流程 | 分区数 6 使 3 个 Broker 各 2 分区，消费者 concurrency=3 与分区数匹配避免空闲线程。Producer 端 batch.size=16KB 与 linger.ms=10 让消息在缓冲区聚合，满 16KB 或等 10ms 批量发送减少网络请求；snappy 压缩在发送前压缩批次降低网络带宽。Consumer 端 max.poll.records=500 单次拉取 500 条减少 RPC 次数，配合批量处理提升消费吞吐。分区是并行单元，分区数决定消费并行度上限。 |
| 缺点 | 分区数调整不可降（只能增），规划不当造成资源浪费；linger.ms 增加消息延迟，实时性敏感场景受限；snappy 压缩消耗 CPU，CPU 瓶颈时适得其反；批量拉取增大内存占用与单次处理失败的重试成本。 |

### 5.2 ES 优化

| 维度 | 内容 |
|------|------|
| 是什么 | 针对商品搜索场景的 ES 索引与查询调优，通过分片、字段索引、bulk、filter 缓存、聚合优化提升性能。 |
| 能做什么 | 3 主 1 副分片控制单分片规模；关闭不必要字段索引；bulk 批量 500 条写入；filter 替代 must 利用缓存；聚合 size:0 只返回聚合结果。 |
| 怎么用 | `number_of_shards: 3, number_of_replicas: 1`<br>`bulk API, 每批 500 条`<br>`boolQuery().filter(termQuery(...))  // 替代 must；aggregation size: 0` |
| 原理和工作流程 | 分片数 3 使单分片保持 10-50GB 健康规模，1 副本提供高可用。不需要检索的字段设 `index: false` 减少倒排索引体积。写入用 bulk API 每批 500 条合并请求降低网络开销。查询时 filter 子句不参与评分且结果可缓存（bitset 复用），替代 must 提升过滤性能。聚合查询设 size:0 跳过文档返回仅返回聚合桶，减少数据传输。refresh_interval=5s 降低 segment 生成频率。 |
| 缺点 | 分片数建索引后不可改，扩容只能 reindex；filter 不参与相关性评分，需排序的场景仍需 must；bulk 失败需重试机制处理部分失败；聚合 size:0 无法同时获取文档，需二次查询；副本增加写入开销与磁盘占用。 |

### 5.3 ClickHouse 优化

| 维度 | 内容 |
|------|------|
| 是什么 | 针对订单统计分析的 ClickHouse 表结构与写入调优，通过分区、批量、物化视图、数据类型、压缩提升性能。 |
| 能做什么 | 按月分区查询裁剪；1000 条或 5 秒批量 flush 减 Part；物化视图预聚合毫秒响应；LowCardinality 与 UInt 减内存；ZSTD 高压缩比。 |
| 怎么用 | `PARTITION BY toYYYYMM(event_time)`<br>`批量: 每 1000 条或每 5 秒 flush`<br>`CREATE MATERIALIZED VIEW mv_order_hourly TO order_hourly_stats AS ...` |
| 原理和工作流程 | 按月分区使查询通过分区键裁剪只扫描目标月份 Part。批量写入（1000 条或 5 秒）减少 Part 数量，避免过多 Part 触发 merge 风暴。物化视图在 INSERT 时自动触发聚合写入预聚合表，热点查询命中预聚合表实现毫秒响应。LowCardinality 对低基数字符串用字典编码减少内存，UInt 比 Int 省空间。ZSTD 压缩比高于 LZ4，牺牲少量 CPU 换存储空间。ORDER BY 排序键使范围查询利用稀疏索引跳过 granule。 |
| 缺点 | 按月分区粒度粗，跨月查询仍扫多分区；物化视图增加写入开销与存储，聚合维度变更需重建；LowCardinality 对高基数列反降性能；ZSTD 解压 CPU 开销高于 LZ4，查询密集场景需权衡；ClickHouse 不擅长高频单条 UPDATE/DELETE。 |

### 5.4 微服务优化

| 维度 | 内容 |
|------|------|
| 是什么 | 针对各微服务的通用性能优化手段，覆盖连接池、线程池、缓存、异步、限流五个维度。 |
| 能做什么 | HikariCP 连接池控 DB 连接；自定义线程池隔离 Kafka 消费；Redis 缓存热点数据；非核心逻辑异步化；Sentinel 网关加服务双重限流。 |
| 怎么用 | `HikariCP: minimumIdle=5, maximumPoolSize=20`<br>`线程池隔离 Kafka 消费线程`<br>`Redis 缓存商品信息、分类列表；Sentinel 网关层 + 服务层双重限流` |
| 原理和工作流程 | HikariCP 连接池复用 DB 连接避免频繁建连，min5/max20 控制并发与资源。Kafka 消费线程与业务线程池隔离，防止慢消费阻塞消息拉取。Redis 缓存热点商品信息与分类列表，未命中回源 DB 减轻主库压力。非核心逻辑（日志、审计）通过 `@Async` 或消息队列异步化，释放主链路线程。Sentinel 在网关层限总流量、服务层限单服务流量，双层防护避免单服务过载拖垮全局。 |
| 缺点 | 连接池与线程池参数需压测调优，过小限流过大耗资源；Redis 缓存存在一致性窗口，需过期或 binlog 刷新策略；异步化增加排查难度，链路追踪必备；双重限流规则叠加可能过度限制正常流量；缓存击穿穿透需额外防护（互斥锁、空值缓存）。 |

## 六、常见面试问题（基于项目）

| 维度 | 内容 |
|------|------|
| 考查范围 | 订单与 Kafka 一致性、ES 同步延迟、ClickHouse 与 ES 职责分工、微服务数据一致性、系统扩展、消息重复消费、MQ 选型七类项目实战问题。 |
| 题型特点 | 基于项目架构与代码的开放性问题，要求阐述技术选型理由、一致性保证机制、性能优化原理及局限性权衡。 |
| 答题要点 | 先点明核心机制，再结合数据流向与组件职责展开，最后补充局限与兜底方案。 |

### 1. 如何保证订单创建和 Kafka 消息发送的一致性

| 维度 | 内容 |
|------|------|
| 是什么 | 通过本地事务绑定 MySQL 写入与 Kafka 事务消息发送，保证订单持久化与事件生产原子性的机制。 |
| 能做什么 | DB 与消息同事务提交或回滚；消息发送失败触发 DB 回滚；消费者手动提交 offset 保证消费端最终一致；重试机制兜底。 |
| 怎么用 | `@Transactional(rollbackFor = Exception.class)`<br>`orderRepository.save(order);`<br>`kafkaTemplate.executeInTransaction(ops -> ops.send("order-events", id, event));` |
| 原理和工作流程 | `@Transactional` 开启本地事务，先 save 写 MySQL，再 `executeInTransaction` 发送 Kafka 事务消息，二者绑定在同一事务边界。消息发送失败抛异常触发 DB 回滚，避免 DB 有记录而消息丢失。消费端手动提交 offset，处理成功才提交，失败不提交触发重试。生产端保证“都成功或都失败”，消费端靠幂等加重试保证最终一致。 |
| 缺点 | 仅解决生产端原子性，消费端失败仍需幂等去重兜底；事务期间占用 Producer 与 DB 连接，高并发吞吐受限；Kafka 事务有额外开销且需 transactional.id 配置；跨服务无法强一致。 |

### 2. ES 数据同步延迟如何处理

| 维度 | 内容 |
|------|------|
| 是什么 | 订单数据经 MySQL→Kafka→ES 消费者链路同步到 ES 的延迟来源分析与兜底查询策略。 |
| 能做什么 | 量化各环节延迟（binlog 秒级、Kafka 毫秒、ES 1-2 秒）；总体 3-5 秒可控；实时性高查询先查 MySQL 兜底；搜索场景容忍最终一致。 |
| 怎么用 | `MySQL binlog(秒级) → Kafka(毫秒) → ES 写入+refresh(1-2s)`<br>`实时查询兜底: 先查 MySQL 再查 ES` |
| 原理和工作流程 | 同步链路为 MySQL→Kafka→ES 消费者。Canal 解析 binlog 近实时秒级，Kafka 传输毫秒级，ES 写入含 refresh_interval 约 1-2 秒，总体延迟 3-5 秒。搜索场景容忍该延迟。对实时性要求极高的查询（如确认订单是否已同步），先查 MySQL 主存储获取最新状态作为兜底，再查 ES 获取检索能力，避免读到未同步数据。 |
| 缺点 | 兜底查询增加 DB 压力与代码复杂度；延迟窗口内 ES 与 MySQL 数据不一致；Canal 解析 binlog 有自身延迟与故障风险；refresh_interval 调小增加 segment 数量与开销。 |

### 3. ClickHouse 和 ES 在这个项目中各司什么职

| 维度 | 内容 |
|------|------|
| 是什么 | ES 负责商品全文检索、ClickHouse 负责订单聚合统计的职责划分，二者通过 Kafka 异步同步各司其职。 |
| 能做什么 | ES 倒排索引实现关键词搜索分词高亮相关性排序；ClickHouse 列式存储实现 PV/UV 销售额趋势聚合；Kafka 异步同步互不影响。 |
| 怎么用 | `ES: 商品搜索 (倒排索引, IK 分词, 高亮)`<br>`ClickHouse: 统计分析 (列式存储, 物化视图预聚合)`<br>`Kafka: 异步同步, 互不影响` |
| 原理和工作流程 | ES 基于倒排索引加 IK 分词器实现商品 productName 全文检索，支持 multiMatch 加权、高亮、相关性评分排序，擅长关键词匹配场景。ClickHouse 基于列式存储加 MergeTree 引擎，物化视图预聚合实现海量订单的 sum/count/uniq 聚合，秒级十亿行，擅长统计分析场景。两者通过 Kafka 异步接收同一订单事件，数据冗余存储但查询路径独立，搜索走 ES、统计走 ClickHouse 互不影响。 |
| 缺点 | 数据双写冗余存储成本高；两套系统需分别维护与调优；数据一致性靠 Kafka 最终一致，存在窗口期不一致；ES 聚合能力弱、ClickHouse 全文检索弱，跨界查询受限。 |

### 4. 微服务之间如何保证数据一致性

| 维度 | 内容 |
|------|------|
| 是什么 | 通过 Kafka 异步事件解耦微服务，各消费者保证幂等性，靠重试机制实现跨服务最终一致性的方案。 |
| 能做什么 | order-service 发 Kafka 事件解耦；各服务独立消费；基于 orderId 幂等去重；Kafka 重试保证不丢；关键业务用 Seata 强一致。 |
| 怎么用 | `order-service → Kafka 事件 → search/stats/notification 各自消费`<br>`幂等: setIfAbsent("notification:order:" + orderId)`<br>`关键业务: Seata 分布式事务` |
| 原理和工作流程 | order-service 创建订单后发送 Kafka 事件，search-service、stats-service、notification-service 各自以独立 consumer group 消费，独立处理互不阻塞。每个消费者基于 orderId+eventType 做幂等去重（Redis setIfAbsent），重复消费跳过。消费者处理失败不提交 offset，Kafka 重试机制保证消息不丢。非关键业务靠最终一致，关键业务（如库存扣减）用 Seata AT 模式分布式事务强一致。 |
| 缺点 | 最终一致性有延迟，强一致场景需 Seata 增加复杂度；幂等去重依赖 Redis，Redis 故障期间去重失效；重试可能造成消息积压；Seata 性能开销大且需数据库支持。 |

### 5. 如何扩展系统支持更大流量

| 维度 | 内容 |
|------|------|
| 是什么 | 从 Kafka、ES、ClickHouse、微服务、网关、数据库多维度水平扩展以支撑更大流量的方案。 |
| 能做什么 | Kafka 增分区提并行；ES 增 Data Node；ClickHouse 分布式表分片；K8s HPA 自动扩缩；网关多实例 Nginx 负载；MySQL 读写分离分库分表。 |
| 怎么用 | `Kafka: 增分区(配合 Broker)`<br>`ES: 增 Data Node；ClickHouse: 分布式表+分片`<br>`微服务: K8s HPA(CPU/内存/QPS)；MySQL: 读写分离+分库分表` |
| 原理和工作流程 | Kafka 增加分区数（配合 Broker）提高并行消费能力，分区是并行单元。ES 增加 Data Node 分散分片提升搜索与写入吞吐。ClickHouse 用分布式表加分片水平扩展，查询并行分发到各分片。微服务通过 K8s HPA 根据 CPU 内存 QPS 自动增减实例。网关增加 Gateway 实例前置 Nginx 负载均衡。数据库读写分离（主写从读）加分库分表（按用户 ID 哈希）突破单库瓶颈。 |
| 缺点 | 各维度扩展有上限与副作用，Kafka 分区不可降、ES 分片不可改；分布式表查询需聚合各分片增加延迟；分库分表破坏跨库 JOIN 与事务；HPA 扩容有冷启动延迟；扩容成本线性增长。 |

### 6. 项目中如何处理消息重复消费

| 维度 | 内容 |
|------|------|
| 是什么 | 利用 Redis setIfAbsent 以业务唯一键实现消费幂等，重复消费跳过、失败删除标记允许重试的机制。 |
| 能做什么 | 以 orderId+eventType 为唯一键；setIfAbsent 首次消费成功；已存在跳过；失败删标记允许重试；设置过期时间防堆积。 |
| 怎么用 | `String key = "notification:order:" + event.getOrderId();`<br>`if (!redis.setIfAbsent(key, "1", Duration.ofHours(24))) return;`<br>`// 业务处理; 失败则 redis.delete(key) 允许重试` |
| 原理和工作流程 | 消费消息时以 `orderId+eventType` 拼接唯一键，调用 `setIfAbsent` 写入 Redis（设过期时间如 24 小时）。返回 true 表示首次消费，执行业务逻辑；返回 false 表示键已存在即重复消费，直接跳过。业务处理成功后正常返回，标记保留防止重复。若业务抛异常，catch 块删除 Redis 去重标记，使 Kafka 重试时能重新处理，避免因临时故障导致消息永久跳过。 |
| 缺点 | Redis 宕机期间去重失效可能重复消费；过期时间窗口外的迟到事件被视为新事件重复处理；去重键设计不当（如未含 eventType）会导致同订单不同事件互相误判；业务成功但删标记前进程崩溃会重复消费。 |

### 7. 为什么选择 Kafka 而不是 RocketMQ 或 RabbitMQ

| 维度 | 内容 |
|------|------|
| 是什么 | 基于高吞吐、持久化、分区并行、生态成熟四个优势选择 Kafka 作为订单事件流 MQ 的选型依据。 |
| 能做什么 | 百万 TPS 高吞吐；磁盘持久化支持回溯；分区天然并行水平扩展；与 Spark/Flink/ClickHouse 生态集成；事务消息满足订单场景。 |
| 怎么用 | `选型: Kafka 3.x`<br>`理由: 高吞吐(百万 TPS) + 持久化(磁盘) + 分区并行 + 生态成熟`<br>`对比: RocketMQ 事务消息更优但本项目 Kafka 事务已满足` |
| 原理和工作流程 | Kafka 核心优势匹配订单事件流需求：高吞吐达百万 TPS，顺序写磁盘加零拷贝支撑高频订单写入；消息持久化到磁盘支持回溯与重复消费，适合事件溯源；分区机制使消费者并行消费水平扩展；生态成熟与 Spark、Flink、ClickHouse 无缝集成便于后续大数据分析。RocketMQ 在事务消息方面更完善，但本项目 Kafka 事务消息已能满足订单一致性需求，且吞吐与生态更优，故选 Kafka。 |
| 缺点 | Kafka 事务消息不如 RocketMQ 完善，强事务场景 RocketMQ 更优；无延迟队列与死信队列原生支持（RabbitMQ 更优）；运维复杂度高，需维护 Broker 与 Zookeeper/KRaft；topic 数过多时性能下降，不适合海量小 topic 场景。 |
