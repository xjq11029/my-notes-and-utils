## 一、核心概念

### 1.1 MySQL 安装配置

| 维度 | 内容 |
|------|------|
| 是什么 | 在不同操作系统上部署 MySQL 数据库服务并完成初始化配置的过程，涵盖 Windows、Linux、Docker 三种方式。 |
| 能做什么 | 安装数据库服务；配置 root 密码与认证方式；设置开机自启；选择字符集与存储引擎；初始化开发或生产环境。 |
| 怎么用 | `docker run -d --name mysql8 -p 3306:3306 -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0` |
| 原理和工作流程 | Windows 通过 MSI 安装包图形化引导配置；Linux 借助 yum 仓库安装 RPM 包后由 systemd 管理服务，首次启动生成临时密码写入 mysqld.log；Docker 通过镜像启动容器并挂载数据卷，环境变量初始化 root 密码与默认库。三种方式最终都启动 mysqld 守护进程，监听 3306 端口，加载配置文件与数据目录。 |
| 缺点 | 图形安装步骤繁琐且不可自动化；yum 依赖官方仓库网络；Docker 性能略低于宿主机直装，数据卷管理不当易丢数据；生产环境需额外配置防火墙、参数调优与高可用方案。 |

### 1.2 客户端工具对比

| 维度 | 内容 |
|------|------|
| 是什么 | 用于连接和操作 MySQL 数据库的图形或命令行工具集合，包含官方与第三方产品。 |
| 能做什么 | 执行 SQL 语句；可视化浏览表结构与数据；数据建模与迁移；SQL 补全与格式化；性能监控与导出。 |
| 怎么用 | `mysql -h 127.0.0.1 -P 3306 -u root -p` 命令行连接；DataGrip 或 Navicat 配置连接信息。 |
| 原理和工作流程 | 客户端通过 MySQL 协议与服务器建立 TCP 连接，完成握手认证后发送 SQL 文本，服务器解析执行返回结果集。图形工具在此基础上提供对象树、语法高亮、结果网格渲染；命令行工具轻量直接输出文本。DataGrip 依赖 JDBC 驱动连接，支持跨数据库方言。 |
| 缺点 | 图形工具多收费且内存占用高；命令行无补全不利于复杂 SQL 编写；Workbench 启动慢；DBeaver 大数据量查询卡顿；各工具对部分语法高亮支持不全。 |

### 1.3 数据库/表/记录基本概念

| 维度 | 内容 |
|------|------|
| 是什么 | 关系型数据库组织数据的层级结构，从数据库到表再到记录与字段的概念体系。 |
| 能做什么 | 定义数据容器；按表组织实体；用行表示实例；用列描述属性；通过主键唯一标识记录；用外键建立关联；用索引加速查询。 |
| 怎么用 | `SHOW DATABASES; USE shop; SHOW TABLES; DESC t_user;` |
| 原理和工作流程 | MySQL 实例管理多个 Schema，每个 Schema 下存放表、视图等对象。表是逻辑结构，InnoDB 中数据按主键聚簇存储在 B+ 树叶子节点。主键唯一标识一行，外键维护参照完整性，索引以独立 B+ 树结构存储列值与主键映射以加速检索。 |
| 缺点 | 概念抽象需结合实例理解；外键带来额外检查开销并影响写入性能；主键选择不当导致页分裂；索引过多占用空间并拖慢写入。 |

### 1.4 数据类型

| 维度 | 内容 |
|------|------|
| 是什么 | MySQL 为字段定义的存储类型，涵盖整型、浮点定点、字符串、日期时间、JSON 等类别。 |
| 能做什么 | 精确控制存储空间；保证数值精度；支持定长与变长字符串；记录日期时间；存储半结构化 JSON 数据。 |
| 怎么用 | `balance DECIMAL(10,2)`、`username VARCHAR(50)`、`created_at DATETIME DEFAULT CURRENT_TIMESTAMP` |
| 原理和工作流程 | 整型按字节分配固定空间并支持有符号无符号；DECIMAL 以二进制字符串精确存储十进制数避免浮点误差；VARCHAR 额外存 1 到 2 字节长度按实际占用；DATETIME 占 8 字节与时区无关，TIMESTAMP 占 4 字节自动转时区但存在 2038 问题；JSON 类型以二进制存储支持路径查询函数。 |
| 缺点 | 类型选择不当导致空间浪费或精度丢失；FLOAT/DOUBLE 存精度误差不适合金额；TIMESTAMP 范围仅到 2038 年；CHAR 定长浪费空间；JSON 查询性能不如规范字段。 |

## 二、底层原理

### 2.1 SQL 分类

| 维度 | 内容 |
|------|------|
| 是什么 | 按 SQL 语句功能划分的四大类别 DDL、DML、DQL、DCL。 |
| 能做什么 | DDL 定义库表结构；DML 操作数据；DQL 查询数据；DCL 控制权限与事务。 |
| 怎么用 | `CREATE/ALTER/DROP`、`INSERT/UPDATE/DELETE`、`SELECT`、`GRANT/COMMIT` |
| 原理和工作流程 | DDL 修改数据库元数据，InnoDB 中 DDL 通常自动提交不可回滚；DML 操作行数据，可纳入事务批量提交或回滚；DQL 经过解析器生成执行计划由存储引擎返回结果集；DCL 修改权限表或控制事务状态。四类语句共享同一 SQL 接口但作用对象和提交行为不同。 |
| 缺点 | DDL 自动提交无法回滚，误操作 DROP 不可恢复；DML 不带 WHERE 危险；DQL 复杂查询性能难控；TRUNCATE 等语句分类边界存在争议。 |

### 2.2 DDL 语法

| 维度 | 内容 |
|------|------|
| 是什么 | 用于创建和修改数据库对象结构的 SQL 语句，包括建库建表、修改列、删除表、清空表。 |
| 能做什么 | 创建数据库与表并指定字符集引擎；添加修改删除列；重命名表；清空数据重置自增；删除表结构。 |
| 怎么用 | `CREATE TABLE t_user (id BIGINT PRIMARY KEY AUTO_INCREMENT, ...) ENGINE=InnoDB;` |
| 原理和工作流程 | CREATE 解析列定义与约束生成表元数据并分配存储；ALTER 通过拷贝或 INPLACE 算法修改表结构，大表加列可能锁表；TRUNCATE 直接释放数据页并重置自增，DDL 自动提交；DROP 删除元数据与数据文件。修改列类型需重建表数据。 |
| 缺点 | ALTER 大表耗时并可能阻塞业务；TRUNCATE 不可回滚误删无法恢复；DROP 连表结构一起删除风险高；列修改可能丢失数据；不支持事务回滚保护。 |

### 2.3 DML 语法

| 维度 | 内容 |
|------|------|
| 是什么 | 用于操作表中数据的 SQL 语句，包括 INSERT、UPDATE、DELETE 及批量与 upsert 操作。 |
| 能做什么 | 插入单条或批量数据；更新满足条件的行；删除数据；实现存在则更新不存在则插入。 |
| 怎么用 | `INSERT INTO t_user (username) VALUES ('zs');` `UPDATE t_user SET age=21 WHERE id=1;` |
| 原理和工作流程 | INSERT 将行写入聚簇索引并更新二级索引，批量插入减少网络往返；UPDATE 先定位行再加锁修改，记录 undo 与 redo 日志；DELETE 标记删除并记录日志；ON DUPLICATE KEY UPDATE 依赖唯一键冲突触发更新。所有 DML 受事务控制可回滚。 |
| 缺点 | UPDATE/DELETE 不带 WHERE 会全表操作酿成事故；批量插入过大超 max_allowed_packet；upsert 高并发下可能死锁；大量更新产生大量 undo 日志拖慢性能。 |

### 2.4 DQL 语法（SELECT）

| 维度 | 内容 |
|------|------|
| 是什么 | 用于查询数据的 SELECT 语句及其子句体系，包含过滤、分组、聚合、排序、分页等。 |
| 能做什么 | 按条件过滤行；分组聚合统计；多表关联；去重；排序；分页；使用聚合函数计算。 |
| 怎么用 | `SELECT status, COUNT(*) FROM t_user GROUP BY status HAVING COUNT(*)>10 ORDER BY user_count DESC LIMIT 10;` |
| 原理和工作流程 | SQL 书写顺序与执行顺序不同，实际按 FROM、JOIN、ON、WHERE、GROUP BY、HAVING、SELECT、DISTINCT、ORDER BY、LIMIT 执行。优化器先生成执行计划，存储引擎按索引扫描或全表扫描返回行，Server 层完成过滤、分组、聚合、排序与分页。聚合函数在分组后对每组计算。 |
| 缺点 | 子句顺序固定书写易错；深分页 LIMIT 性能差；GROUP BY 受 ONLY_FULL_GROUP_BY 限制；复杂查询难优化；聚合无法使用索引下推。 |

### 2.5 多表 JOIN

| 维度 | 内容 |
|------|------|
| 是什么 | 将多张表按关联条件连接查询的 SQL 语法，包括 INNER、LEFT、RIGHT、CROSS 四种连接类型。 |
| 能做什么 | 取两表交集；保留左表全部；保留右表全部；生成笛卡尔积；支持三表及以上关联。 |
| 怎么用 | `SELECT u.username, o.amount FROM t_user u LEFT JOIN t_order o ON u.id=o.user_id;` |
| 原理和工作流程 | 优化器选择驱动表与被驱动表，驱动表每行到被驱动表查找匹配。INNER JOIN 仅保留匹配行；LEFT JOIN 左表全保留右表无匹配补 NULL；RIGHT JOIN 反之；CROSS JOIN 生成 M 乘 N 行。嵌套循环或 Hash Join 执行关联，关联列有索引时走索引查找。 |
| 缺点 | 多表关联性能随表数量下降；无索引时全表扫描笛卡尔积爆炸；LEFT JOIN 产生 NULL 处理麻烦；超过三表难维护；CROSS JOIN 易产生海量结果。 |

### 2.6 子查询

| 维度 | 内容 |
|------|------|
| 是什么 | 嵌套在另一条 SQL 语句中的查询，按返回结果分为标量、列、行、表及 EXISTS 子查询。 |
| 能做什么 | 用子查询结果做比较条件；配合 IN/ANY/ALL；作为临时表；判断关联数据是否存在。 |
| 怎么用 | `SELECT * FROM t_user WHERE age > (SELECT AVG(age) FROM t_user);` |
| 原理和工作流程 | 标量子查询返回单值用于比较；列子查询返回一列配合 IN；表子查询结果作为 FROM 临时表；EXISTS 对外层每行执行子查询判断是否返回行。优化器可能将子查询改写为半连接或物化为临时表。小表驱动大表时 IN 较优，主查询小时 EXISTS 较优。 |
| 缺点 | 相关子查询每行执行一次性能差；多层嵌套可读性低；子查询可能被优化器改写导致行为不确定；NOT IN 遇 NULL 返回空结果；临时表子查询无法用索引。 |

### 2.7 视图

| 维度 | 内容 |
|------|------|
| 是什么 | 基于查询语句定义的虚拟表，只存储 SQL 定义不存储实际数据。 |
| 能做什么 | 封装复杂查询；简化访问；控制列级权限；提供一致的数据访问接口。 |
| 怎么用 | `CREATE VIEW v_user_order_stats AS SELECT ... ;` `SELECT * FROM v_user_order_stats;` |
| 原理和工作流程 | 视图本质是保存在数据字典中的 SELECT 语句定义。查询视图时优化器将视图定义展开合并到外部查询，等价于执行合并后的 SQL。简单视图可做 INPLACE 更新直接映射到底表，含聚合、JOIN、DISTINCT 的复杂视图不可更新。视图本身不占用数据存储空间。 |
| 缺点 | 复杂视图查询性能差且难优化；不可更新的视图限制多；视图嵌套层次深难维护；视图变更影响依赖对象；无法建索引加速。 |

### 2.8 索引基础

| 维度 | 内容 |
|------|------|
| 是什么 | 用于加速查询的独立数据结构，InnoDB 中默认为 B+ 树，包括主键、唯一、普通、联合、全文索引。 |
| 能做什么 | 加速等值与范围查询；保证唯一性；加速排序与分组；支持全文检索；遵循最左前缀。 |
| 怎么用 | `CREATE INDEX idx_email ON t_user(email);` `ALTER TABLE t_user ADD INDEX idx_status_age (status, age);` |
| 原理和工作流程 | InnoDB 索引为 B+ 树，主键索引叶子节点存完整行数据即聚簇索引，二级索引叶子节点存索引列与主键值。查询时按 B+ 树从根到叶定位，等值查询 O(log n)，范围查询遍历叶子链表。联合索引按列顺序排序遵循最左前缀。索引页与数据页统一以 16KB 页管理。 |
| 缺点 | 占用额外磁盘空间；写入需同步维护索引降低性能；索引过多增加优化器选择成本；选择不当索引无效甚至负优化;维护索引页分裂产生碎片。 |

## 三、实战应用

### 3.1 完整建库建表演练

| 维度 | 内容 |
|------|------|
| 是什么 | 以电商系统用户、商品、订单三表为例的完整数据库设计与建表实践。 |
| 能做什么 | 设计表结构与字段类型；定义主键唯一键与普通索引；设置默认值与时间自动填充；插入测试数据。 |
| 怎么用 | `CREATE DATABASE shop;` `CREATE TABLE t_user (...);` `CREATE TABLE t_order (...);` |
| 原理和工作流程 | 先创建数据库指定 utf8mb4 字符集，再按业务实体建表。每表定义自增主键聚簇存储，唯一键保证业务字段唯一，普通索引加速常用查询条件。金额用 DECIMAL 避免精度损失，状态用 TINYINT 节省空间，时间字段用 DATETIME 默认当前时间并随更新自动刷新。外键关联通过 user_id 字段在应用层维护。 |
| 缺点 | 仅演示单机建表未考虑分库分表；索引设计依赖经验易遗漏；无外键约束靠应用保证一致性；测试数据量小无法暴露性能问题；字符集排序规则需统一。 |

### 3.2 分页查询（LIMIT）

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 LIMIT 子句限制返回行数实现分页的查询技术，含标准分页与深分页优化。 |
| 能做什么 | 实现按页大小返回数据；计算分页偏移量；优化百万级深分页性能。 |
| 怎么用 | `SELECT id, username FROM t_user ORDER BY id ASC LIMIT 10 OFFSET 10;` |
| 原理和工作流程 | LIMIT offset, size 让优化器扫描并跳过前 offset 行后返回 size 行。深分页时 offset 很大需扫描并丢弃大量行导致慢查询。优化方案一是子查询先走覆盖索引定位主键再 JOIN 回表减少回表次数；方案二是游标分页记录上一页最大 id 用 WHERE id 大于 last_id LIMIT size 直接定位避免扫描丢弃。 |
| 缺点 | 标准 LIMIT 深分页性能急剧下降；OFFSET 越大越慢；游标分页不支持跳页；子查询方案仍需扫描；分页数据实时变化可能导致重复或遗漏。 |

### 3.3 分组统计

| 维度 | 内容 |
|------|------|
| 是什么 | 使用 GROUP BY 与聚合函数对数据分组统计的查询技术。 |
| 能做什么 | 按维度分组计数；计算分组均值与总和；统计每日数据量；按条件聚合。 |
| 怎么用 | `SELECT status, COUNT(*), AVG(balance) FROM t_user GROUP BY status;` |
| 原理和工作流程 | WHERE 先过滤基础行，再按 GROUP BY 列值分组，每组应用聚合函数计算。HAVING 在分组后按聚合结果过滤组。聚合函数忽略 NULL 值。优化器可能利用索引有序性避免临时表排序，若 GROUP BY 列有索引则可直接顺序扫描。LEFT JOIN 配合分组可统计含零值的全量维度。 |
| 缺点 | GROUP BY 受 ONLY_FULL_GROUP_BY 限制需包含分组列；无索引时产生临时表与 filesort；大数据量分组内存消耗大；多字段分组维度爆炸；聚合无法下推到索引。 |

### 3.4 多表关联查询

| 维度 | 内容 |
|------|------|
| 是什么 | 结合 JOIN、子查询、排序分页实现复杂业务统计的实战查询技术。 |
| 能做什么 | 查询用户与订单关联；统计消费排名；查找未下单用户；按条件过滤关联数据。 |
| 怎么用 | `SELECT u.username, SUM(o.amount) FROM t_user u JOIN t_order o ON u.id=o.user_id GROUP BY u.id ORDER BY total_spent DESC LIMIT 3;` |
| 原理和工作流程 | LEFT JOIN 保留左表全部并按关联条件匹配右表，关联列有索引时走索引查找。子查询先聚合各用户消费再 JOIN 主表排序分页。未下单用户用 LEFT JOIN 加 IS NULL 过滤。优化器选择小表作驱动表，被驱动表关联列走索引，WHERE 提前过滤减少参与 JOIN 的行数。 |
| 缺点 | 关联列无索引时性能差；多表 JOIN 临时表内存大；子查询可能无法下推；统计排序需 filesort；复杂 SQL 难维护与调优。 |

## 四、常见面试题（附答案）

### 1. CHAR 和 VARCHAR 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 两种字符串存储类型的对比，前者定长后者变长，是字段选型的核心考点。 |
| 能做什么 | CHAR 固定长度补空格存储；VARCHAR 按实际长度存储加长度字节；权衡空间与读取效率。 |
| 怎么用 | `CHAR(10)`、`VARCHAR(50)` |
| 原理和工作流程 | CHAR(N) 无论实际存多少字符都占 N 个字符空间不足补空格，读取时去尾部空格，无需计算长度读取略快。VARCHAR(N) 按实际字符数存储并额外用 1 到 2 字节记录长度节省空间。InnoDB 中两者溢出页处理也有差异。CHAR 适合 MD5、性别等定长编码，VARCHAR 适合用户名、邮箱等长度不固定字段。 |
| 缺点 | CHAR 浪费存储空间；VARCHAR 有长度计算开销；CHAR(10) 存 abc 占 10 字节；VARCHAR 超长行可能触发溢出；选型不当影响空间与性能。 |

### 2. DROP、TRUNCATE、DELETE 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 三种删除数据的 SQL 操作，分属 DDL 与 DML，删除范围与可回滚性不同。 |
| 能做什么 | DELETE 按条件删行；TRUNCATE 清空整表重置自增；DROP 删除表结构与数据。 |
| 怎么用 | `DELETE FROM t WHERE id=1;` `TRUNCATE TABLE t;` `DROP TABLE t;` |
| 原理和工作流程 | DELETE 是 DML 逐行删除并记录 undo 日志，可回滚不重置自增速度慢。TRUNCATE 是 DDL 直接释放数据页重置自增，自动提交不可回滚速度快。DROP 是 DDL 删除表元数据与数据文件不可回滚速度最快。三者按删除粒度递增危险程度递增。 |
| 缺点 | DELETE 慢且产生大量日志；TRUNCATE 不可回滚误删难恢复；DROP 连结构一起删风险最高；TRUNCATE 与 DROP 自动提交无法事务保护；DELETE 不重置自增导致空洞。 |

### 3. WHERE 和 HAVING 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 两种过滤子句的对比，WHERE 在分组前过滤行，HAVING 在分组后过滤组。 |
| 能做什么 | WHERE 过滤基础数据行；HAVING 过滤聚合后的分组；两者可共存先后执行。 |
| 怎么用 | `WHERE age>18 GROUP BY status HAVING COUNT(*)>5` |
| 原理和工作流程 | SQL 执行顺序中 WHERE 在 GROUP BY 之前对原始行过滤，不能使用聚合函数。GROUP BY 完成分组后 HAVING 对分组结果按聚合值过滤，可使用聚合函数。两者共存时 WHERE 先缩小数据集再分组，HAVING 再筛掉不满足聚合条件的组。优化器优先用 WHERE 减少分组数据量。 |
| 缺点 | WHERE 不能用聚合函数易混淆；HAVING 在分组后执行性能差；误用 HAVING 替代 WHERE 增加分组数据量；两者顺序固定不可调换；新手易将过滤条件写错位置。 |

### 4. INNER JOIN 和 LEFT JOIN 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 两种表连接方式的对比，INNER 取交集，LEFT 保留左表全部。 |
| 能做什么 | INNER JOIN 仅返回匹配行；LEFT JOIN 保留左表并补 NULL；结合 IS NULL 查找未关联数据。 |
| 怎么用 | `INNER JOIN o ON u.id=o.user_id` 或 `LEFT JOIN o ON u.id=o.user_id WHERE o.id IS NULL` |
| 原理和工作流程 | INNER JOIN 遍历驱动表每行到被驱动表找匹配，仅保留两表都匹配的行不匹配行丢弃。LEFT JOIN 左表每行都保留，被驱动表无匹配时右表字段补 NULL。优化器对 INNER JOIN 可自由选择驱动表，LEFT JOIN 受限于左表必须全保留。LEFT JOIN 加 IS NULL 等价于反连接查找差集。 |
| 缺点 | LEFT JOIN 产生 NULL 增加处理复杂度；INNER JOIN 丢失未关联数据；LEFT JOIN 驱动表固定优化空间小；无索引时性能差；NULL 参与聚合需 IFNULL 处理。 |

### 5. COUNT(*)、COUNT(1)、COUNT(列) 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | COUNT 函数三种写法的对比，统计行数时的行为与性能差异。 |
| 能做什么 | COUNT(*) 统计所有行；COUNT(1) 统计所有行；COUNT(列) 统计非 NULL 行。 |
| 怎么用 | `SELECT COUNT(*), COUNT(email) FROM t_user;` |
| 原理和工作流程 | InnoDB 中 COUNT(*) 和 COUNT(1) 都统计所有行含 NULL，优化器选择最小索引扫描，MySQL 8.0 已优化两者性能基本相同。COUNT(列) 只统计该列非 NULL 的行需读取列值判断。COUNT(*) 是 SQL 标准推荐写法。若列有覆盖索引 COUNT(列) 可能略快，无索引时三者差异极小。 |
| 缺点 | COUNT(列) 忽略 NULL 行结果可能与预期不符；大表 COUNT 全表扫描慢；COUNT(1) 非标准写法；InnoDB 无精确行数缓存需扫描；并发下 COUNT 结果是近似值。 |

## 五、避坑指南

| 维度 | 内容 |
|------|------|
| 是什么 | 汇总 MySQL 常见误用场景与对应解决方案的实践清单。 |
| 能做什么 | 避免无 WHERE 全表操作；防止金额精度误差；规避深分页慢查询；识别索引失效；处理类型转换。 |
| 怎么用 | `SET sql_safe_updates=1;` 金额用 `DECIMAL(10,2)`；比较值与列类型一致。 |
| 原理和工作流程 | UPDATE/DELETE 无 WHERE 全表修改，安全模式可拦截。VARCHAR 过长超单行 65535 字节限制。FLOAT/DOUBLE 二进制存储无法精确表示十进制小数。深分页 LIMIT 扫描丢弃大量行。隐式类型转换使索引列加函数导致失效。GROUP BY 非聚合列违反 ONLY_FULL_GROUP_BY 模式。索引列函数破坏有序性。 |
| 缺点 | 避坑规则多需记忆；安全模式影响合法批量操作；DECIMAL 计算慢于浮点；游标分页不支持跳页；类型转换问题隐蔽难排查。 |
