## 一、核心概念

### 1.1 线程创建方式

| 维度 | 内容 |
|------|------|
| 是什么 | Java 创建线程的四种方式 |
| 能做什么 | 继承 Thread；实现 Runnable；实现 Callable 配 FutureTask；线程池 |
| 怎么用 | `new Thread(() -> {}).start()` 或 `executor.submit(task)` |
| 原理和工作流程 | 四种方式：一继承 Thread 重写 run 无返回值单继承局限；二实现 Runnable 传给 Thread 无返回值可复用推荐；三实现 Callable 配 FutureTask 有返回值可抛异常；四线程池 Executor 提交任务复用线程生产推荐。start 启动线程触发 run 执行，直接调 run 是普通方法调用非新线程 |
| 缺点 | 继承 Thread 单继承局限；手动创建线程开销大；无返回值限制；生产应用线程池 |

### 1.2 线程状态（6 种）

| 维度 | 内容 |
|------|------|
| 是什么 | Thread 类定义的线程六种生命周期状态 |
| 能做什么 | NEW 新建；RUNNABLE 可运行；BLOCKED 阻塞；WAITING 等待；TIMED_WAITING 限时等待；TERMINATED 终止 |
| 怎么用 | `thread.getState()` 获取状态 |
| 原理和工作流程 | NEW 已创建未 start。RUNNABLE 已 start 等待 CPU 或运行含就绪与运行。BLOCKED 等待 synchronized 监视器锁。WAITING 调 wait、join、LockSupport.park 无限期等待需被唤醒。TIMED_WAITING 调 sleep(time)、wait(time)、join(time) 限时等待自动唤醒。TERMINATED run 执行结束。start 触发 NEW 到 RUNNABLE，锁竞争致 BLOCKED |
| 缺点 | BLOCKED 仅限 synchronized 不含 Lock 等待；RUNNABLE 含就绪与运行混淆；状态转换复杂 |

### 1.3 与 Node.js 对比

| 维度 | 内容 |
|------|------|
| 是什么 | Java 多线程与 Node.js 单线程事件循环的并发模型对比 |
| 能做什么 | 对比线程模型；对比并发实现；对比适用场景 |
| 怎么用 | CPU 密集用 Java 多线程，IO 密集可两者 |
| 原理和工作流程 | Java 多线程模型一个进程多线程，每请求一线程或线程池，多核并行适合 CPU 密集与阻塞 IO，需处理线程安全与锁。Node.js 单线程事件循环，异步非阻塞 IO 回调与 Promise，单线程避免锁但 CPU 密集任务阻塞事件循环，适合 IO 密集高并发。Java 通过线程池与 NIO 也能高并发 IO |
| 缺点 | Java 线程开销大需池化；Node 单线程不能利用多核 CPU；各有适用场景 |

## 二、底层原理

### 2.1 synchronized 原理

| 维度 | 内容 |
|------|------|
| 是什么 | 基于 Monitor 与对象头实现的内置锁，JDK6+ 引入锁升级优化 |
| 能做什么 | 代码块用 monitorenter 与 monitorexit；方法用 ACC_SYNCHRONIZED 标志；锁升级提性能 |
| 怎么用 | `synchronized(obj){ }` 或 `synchronized void m(){}` |
| 原理和工作流程 | 每个 Java 对象有 Monitor 存于对象头 Mark Word。代码块编译为 monitorenter 与 monitorexit 指令，方法用 ACC_SYNCHRONIZED 标志。JDK6+ 锁升级：无锁→偏向锁（单线程 CAS 设线程 ID）→轻量级锁（多线程交替 CAS 自旋）→重量级锁（激烈竞争操作系统互斥量）。升级不可逆但偏向锁可批量撤销 |
| 缺点 | 不可中断不可超时；锁升级不可逆；重量级锁开销大；不保证公平 |

### 2.2 AQS（AbstractQueuedSynchronizer）原理

| 维度 | 内容 |
|------|------|
| 是什么 | JUC 包的基石，用 state 与 CLH 队列实现同步器的模板框架 |
| 能做什么 | 支撑 ReentrantLock、Semaphore、CountDownLatch、读写锁；独占与共享两种模式 |
| 怎么用 | 继承 AQS 重写 tryAcquire 与 tryRelease |
| 原理和工作流程 | 三核心：一 volatile int state 表示同步状态，ReentrantLock 用 0 未锁大于 0 重入次数，Semaphore 用许可数，CountDownLatch 用剩余计数。二 CLH 双向链表队列存等待线程，队首运行后续等待。三独占模式同时一线程获取如 ReentrantLock，共享模式多线程同时获取如 Semaphore。子类重写 tryAcquire 与 tryRelease 控制获取释放逻辑 |
| 缺点 | 实现复杂；自定义同步器需理解模板方法；CLH 队列调试难；公平与非公平选择影响性能 |

### 2.3 volatile 原理

| 维度 | 内容 |
|------|------|
| 是什么 | 保证可见性与禁止指令重排但不保证原子性的轻量级同步机制 |
| 能做什么 | 可见性修改立即可见；内存屏障禁止重排；DCL 防半初始化；不保证 i++ 原子 |
| 怎么用 | `private volatile boolean flag;` |
| 原理和工作流程 | 三特性：可见性修改后强制刷主存其他线程读主存；禁止指令重排序通过四类内存屏障 StoreStore、StoreLoad、LoadLoad、LoadStore；不保证原子性因 i++ 是读改写复合操作。DCL 单例用 volatile 因 new 对象分分配内存、初始化、赋引用三步，无 volatile 步骤二三可能重排致其他线程获未初始化对象 |
| 缺点 | 不保证原子性；性能低于普通变量；过度使用无收益；仅适合状态标志与 DCL |

### 2.4 CAS 原理

| 维度 | 内容 |
|------|------|
| 是什么 | 比较并交换的无锁原子操作，JUC 原子类与 AQS 的底层 |
| 能做什么 | 三操作数 V/A/B 原子更新；CPU CMPXCHG 指令保证；Atomic 类基础 |
| 怎么用 | `AtomicInteger ai = new AtomicInteger(0); ai.incrementAndGet();` |
| 原理和工作流程 | CAS 三操作数内存位置 V、预期值 A、新值 B，若 V 等于 A 则更新为 B 否则不变，CPU 的 CMPXCHG 指令保证原子性。Unsafe 类提供 native CAS 方法。自旋 CAS 失败重试。ABA 问题：值从 A 变 B 再变 A，CAS 检测不到中间变化，用 AtomicStampedReference 加版本号或 AtomicMarkableReference 加布尔标记解决 |
| 缺点 | 自旋开销大竞争激烈时；ABA 问题；仅保证单变量原子；多变量需锁或 AtomicReference |

### 2.5 ThreadLocal 原理

| 维度 | 内容 |
|------|------|
| 是什么 | 为每个线程提供独立变量副本的隔离机制 |
| 能做什么 | 线程隔离；数据库连接与 Session 管理；TraceId 传递；避免 SimpleDateFormat 线程安全 |
| 怎么用 | `ThreadLocal<DateFormat> tl = new ThreadLocal<>(); tl.set(x); tl.get();` |
| 原理和工作流程 | 每个 Thread 内有 ThreadLocalMap，key 是 ThreadLocal 的弱引用 value 是强引用。set 与 get 操作当前线程的 ThreadLocalMap。内存泄漏风险：ThreadLocal 被 GC 后 key 变 null 但 value 强引用无法回收，线程存活则 value 常驻泄漏，线程池场景严重。解决方案用完在 finally 调 remove 清理 |
| 缺点 | 内存泄漏需手动 remove；线程池复用致脏数据；InheritableThreadLocal 才能父子传递；性能不如局部变量 |

## 三、实战应用

### 3.1 线程池参数配置

| 维度 | 内容 |
|------|------|
| 是什么 | ThreadPoolExecutor 的七个核心参数配置 |
| 能做什么 | corePoolSize 核心线程；maximumPoolSize 最大线程；keepAliveTime 空闲存活；unit 单位；workQueue 队列；threadFactory 工厂；handler 拒绝策略 |
| 怎么用 | `new ThreadPoolExecutor(8,16,60,SECONDS,new LinkedBlockingQueue<>(),handler)` |
| 原理和工作流程 | 七参数：corePoolSize 核心线程数，maximumPoolSize 最大线程数，keepAliveTime 非核心线程空闲存活时间，unit 时间单位，workQueue 任务队列，threadFactory 线程工厂，handler 拒绝策略。提交流程：核心线程未满创建核心线程，满则入队列，队列满则创建非核心线程至最大，仍满触发拒绝策略。CPU 密集核心数加 1，IO 密集按 N×(1+等待/计算) |
| 缺点 | 参数配置不当致 OOM 或吞吐低；队列无界致 OOM；核心数设置错误；拒绝策略选择不当 |

### 3.2 4 种线程池及适用场景

| 维度 | 内容 |
|------|------|
| 是什么 | Executors 提供的四种预置线程池 |
| 能做什么 | newFixedThreadPool 定长；newCachedThreadPool 可缓存；newSingleThreadExecutor 单线程；newScheduledThreadPool 定时 |
| 怎么用 | 生产避免 Executors 用 ThreadPoolExecutor |
| 原理和工作流程 | newFixedThreadPool 固定线程数无界队列适合负载较重。newCachedThreadPool 核心线程 0 最大 Integer.MAX_VALUE 同步队列适合大量短任务。newSingleThreadExecutor 单线程串行适合顺序执行。newScheduledThreadPool 定时周期任务。但 Executors 的队列与最大线程配置有 OOM 风险，阿里规范要求用 ThreadPoolExecutor 手动配置 |
| 缺点 | Fixed 与 Single 无界队列致 OOM；Cached 最大线程 Integer.MAX_VALUE 致 OOM；生产禁用 Executors；需手动配置 |

### 3.3 CompletableFuture 异步编程

| 维度 | 内容 |
|------|------|
| 是什么 | JDK8 引入的异步编排与组合编程工具 |
| 能做什么 | supplyAsync 异步执行；thenApply 转换；thenCombine 合并；allOf 等待全部；exceptionally 异常处理 |
| 怎么用 | `CompletableFuture.supplyAsync(()->fetch()).thenApply(d->transform(d)).join();` |
| 原理和工作流程 | CompletableFuture 实现 Future 与 CompletionStage，supplyAsync 提交任务到 ForkJoinPool 异步执行返回 Future。thenApply、thenAccept、thenRun 链式编排依赖任务。thenCombine 合并两个独立任务结果。allOf 等待全部完成 anyOf 任一完成。exceptionally 与 handle 处理异常。相比 Future 支持回调与组合避免阻塞轮询 |
| 缺点 | 默认 ForkJoinPool 共用致资源竞争；异常处理链复杂；调试难；回调地狱风险 |

## 四、常见面试题（附答案）

### 1. synchronized 和 Lock 的区别？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查内置锁与显式锁的区别 |
| 能做什么 | 对比实现机制；对比可中断与超时；对比公平性；对比释放方式 |
| 怎么用 | 简单同步用 synchronized，高级特性用 Lock |
| 原理和工作流程 | synchronized 是 JVM 关键字基于 Monitor 自动释放不可中断不可超时非公平。Lock 是 juc 接口基于 AQS 手动 lock 与 unlock 需 finally 释放，支持可中断 lockInterruptibly、超时 tryLock、公平锁、多 Condition。synchronized JDK6+ 锁升级后性能接近 Lock。优先 synchronized 复杂场景用 ReentrantLock |
| 缺点 | synchronized 不可中断不可超时；Lock 需手动释放易忘；各有适用场景 |

### 2. volatile 能保证原子性吗？DCL 为什么需要 volatile？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 volatile 可见性与原子性边界及 DCL 应用 |
| 能做什么 | 说明不保证原子性；说明禁止重排；解释 DCL 半初始化问题 |
| 怎么用 | DCL 单例用 volatile 修饰实例 |
| 原理和工作流程 | volatile 保证可见性与禁止指令重排但不保证原子性，因 i++ 是读改写复合操作。DCL 双重检查锁定需 volatile 因 new 对象分分配内存、初始化、赋引用三步，无 volatile 编译器可能重排步骤二三，其他线程可能获未初始化对象。volatile 内存屏障禁止重排保证对象完整构造后才可见 |
| 缺点 | volatile 不保证原子性易误用；DCL 理解需懂指令重排；过度依赖 volatile |

### 3. 线程池的 7 个参数？拒绝策略有哪些？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ThreadPoolExecutor 七参数与四种拒绝策略 |
| 能做什么 | 列举七参数；列举四拒绝策略；说明触发条件 |
| 怎么用 | corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler |
| 原理和工作流程 | 七参数为核心线程数、最大线程数、空闲存活时间、时间单位、任务队列、线程工厂、拒绝策略。四拒绝策略：AbortPolicy 抛 RejectedExecutionException 默认；CallerRunsPolicy 由提交线程执行；DiscardPolicy 直接丢弃；DiscardOldestPolicy 丢弃队列最老任务再提交。线程超核心数满队列满最大数后触发拒绝 |
| 缺点 | 参数配置复杂；拒绝策略选择需结合业务；Abort 默认致任务丢失；队列无界致 OOM |

### 4. ThreadLocal 内存泄漏的原因和解决方案？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 ThreadLocal 内存泄漏机制与解决 |
| 能做什么 | 解释 key 弱引用 value 强引用；解释线程池场景；说明 remove 解决 |
| 怎么用 | 用完 finally 调 remove |
| 原理和工作流程 | ThreadLocalMap 的 key 是 ThreadLocal 弱引用 value 是强引用。ThreadLocal 被 GC 后 key 变 null 但 value 强引用无法回收，只要 Thread 存活 value 常驻，线程池复用线程致泄漏累积。解决方案每次用完在 finally 调 remove 清理 Entry。根本原因 value 强引用且线程长存活 |
| 缺点 | 需手动 remove 易忘；线程池场景严重；脏数据问题；remove 需配合 try-finally |
