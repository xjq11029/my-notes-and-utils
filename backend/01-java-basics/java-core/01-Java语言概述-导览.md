## 一、核心概念

### 1.1 Java 发展历史

| 维度 | 内容 |
|------|------|
| 是什么 | 由 Sun Microsystems 于 1995 年发布、James Gosling 主导设计的通用面向对象编程语言，前身名为 Oak |
| 能做什么 | 编写跨平台桌面/服务端/移动端应用；支撑 Hadoop、Spring 等企业生态；按 LTS 版本提供长期支持 |
| 怎么用 | 学习选 **JDK 17 LTS**，新项目可用 **JDK 21 LTS** |
| 原理和工作流程 | 版本演进按特性划分：1.2 划分三大平台，5.0 引入泛型注解，8 加 Lambda 与 Stream，9 模块化，17/21 为当前 LTS。Oracle 于 2009 年收购 Sun，OpenJDK 为参考实现，Temurin、Corretto、Zulu、Dragonwell 等发行版均基于 OpenJDK 构建 |
| 缺点 | 版本迭代快导致 LTS 与非 LTS 并存，老项目升级成本高；Oracle JDK 商用收费促使企业迁移到 OpenJDK 发行版 |

### 1.2 JDK 版本选择与安装

| 维度 | 内容 |
|------|------|
| 是什么 | Java 开发工具包，包含 JRE 与编译调试工具，是编写 Java 程序的必备环境 |
| 能做什么 | 提供 javac/java/javadoc/jar 等工具；区分 JDK/JRE/JVM 三层结构；支持多发行版选择 |
| 怎么用 | `brew install openjdk@17` 或下载 Temurin 安装包 |
| 原理和工作流程 | 包含关系为 JDK > JRE > JVM：JVM 执行字节码，JRE 加核心类库，JDK 再加开发工具。主流发行版差异在维护方与支持策略，OpenJDK 是参考实现，Oracle JDK 商用收费，Adoptium、Corretto、Zulu、Dragonwell 均免费 |
| 缺点 | 多发行版并存增加选型成本；Oracle JDK 商业许可复杂；安装路径含空格在某些工具中需转义处理 |

### 1.3 Path 环境变量配置

| 维度 | 内容 |
|------|------|
| 是什么 | 操作系统查找可执行程序的目录列表，配置后命令行可全局调用 javac 与 java |
| 能做什么 | 通过 JAVA_HOME 统一引用 JDK 路径；支持多版本切换；让 Maven、Gradle、IDE 定位 JDK |
| 怎么用 | `set JAVA_HOME=...` 后 `set Path=%JAVA_HOME%\bin;%Path%` |
| 原理和工作流程 | 系统执行命令时按 Path 顺序在各目录查找同名可执行文件。JAVA_HOME 是约定变量，Path 中引用 `%JAVA_HOME%\bin` 避免硬编码。配置后需重开命令行窗口才生效，多 JDK 共存时靠 Path 顺序决定优先级 |
| 缺点 | 配置错误导致命令找不到；多版本冲突需手动调整 Path 顺序；GUI 配置步骤繁琐易遗漏 |

### 1.4 HelloWorld 编写与执行

| 维度 | 内容 |
|------|------|
| 是什么 | Java 入门程序，演示从源码编写到编译运行的完整流程，固定包含 main 方法入口 |
| 能做什么 | 验证环境配置；理解编译与运行两阶段；展示类声明、main 签名、标准输出三要素 |
| 怎么用 | `javac HelloWorld.java` 后 `java HelloWorld` |
| 原理和工作流程 | 源文件经 javac 词法、语法、语义分析生成字节码 .class；java 命令启动 JVM，类加载后通过 main 方法签名定位入口，解释执行字节码并输出。文件名须与 public 类名一致，运行时不加 .class 后缀 |
| 缺点 | 文件名与类名不一致即编译报错；中文注释默认 GBK 编码需加 `-encoding UTF-8`；初学者易混淆 java 与 javac 用途 |

### 1.5 注释（Comment）

| 维度 | 内容 |
|------|------|
| 是什么 | 源码中不被编译器执行的说明性文本，分单行、多行、文档注释三种 |
| 能做什么 | 解释设计意图；通过 javadoc 生成 API 文档；标记 TODO 与 FIXME |
| 怎么用 | `// 单行`、`/* 多行 */`、`/** 文档 @param */` |
| 原理和工作流程 | 编译器在词法分析阶段识别注释起始符并跳过对应内容。文档注释以 `/**` 开头，可携带 @author、@param、@return 标签，javadoc 工具解析这些标签生成 HTML API 文档。多行注释不支持嵌套，遇到首个 `*/` 即结束 |
| 缺点 | 过时注释比无注释更危险；多行注释不能嵌套；滥用注释掩盖烂代码，应优先重构 |

### 1.6 Java 语言特点

| 维度 | 内容 |
|------|------|
| 是什么 | 以简单、面向对象、健壮、安全、跨平台为核心设计哲学的静态强类型语言 |
| 能做什么 | 实现封装继承多态；一次编译到处运行；自动垃圾回收；原生支持多线程与反射 |
| 怎么用 | 编译为字节码交 JVM 执行，`javac` + `java` |
| 原理和工作流程 | 跨平台依赖统一字节码格式与平台相关 JVM 实现；健壮性来自强类型、异常机制、GC 与无指针；安全性靠沙箱模型、字节码校验、安全管理器；动态性来自反射与按需类加载 |
| 缺点 | 跨平台的是字节码而非 JVM，各平台需单独安装 JVM；启动慢于原生语言；GC 带来不可控停顿 |

## 二、底层原理

### 2.1 JVM 虚拟机概述

| 维度 | 内容 |
|------|------|
| 是什么 | 执行 Java 字节码的抽象计算机，规范定义类文件格式、运行时数据区与指令集 |
| 能做什么 | 加载并校验字节码；管理运行时数据区；通过解释器与 JIT 执行指令；回收内存 |
| 怎么用 | `java -version` 查看 JVM，`jstat -gc <pid>` 监控 |
| 原理和工作流程 | 类加载器子系统按加载、验证、准备、解析、初始化处理类；运行时数据区分堆、方法区（共享）与程序计数器、虚拟机栈、本地方法栈（私有）；执行引擎含解释器、JIT、GC。热点代码由 JIT 编译为机器码，C1 快速编译、C2 深度优化，JDK7+ 默认分层编译 |
| 缺点 | 启动需加载类与预热 JIT，冷启动慢；内存占用高于原生程序；GC 停顿影响延迟敏感场景 |

### 2.2 类加载机制（双亲委派模型）

| 维度 | 内容 |
|------|------|
| 是什么 | 类加载器收到请求后先委派父加载器加载，父加载失败才自行加载的层级机制 |
| 能做什么 | 避免类重复加载；保护核心 API 不被篡改；支持自定义加载器扩展加载逻辑 |
| 怎么用 | 自定义 ClassLoader 继承 ClassLoader 重写 findClass |
| 原理和工作流程 | 层级为 Bootstrap（加载 rt.jar、java.base）→ Extension/Platform（ext、jdk.*）→ Application（classpath）→ 自定义。收到请求逐层向上委派，Bootstrap 先尝试加载，失败再逐层向下回退，保证核心类由顶层加载器加载 |
| 缺点 | 严格层级限制灵活性，SPI 场景需线程上下文类加载器打破委派；Tomcat 等容器需自定义层级实现应用隔离 |

### 2.3 Java 程序为什么能跨平台

| 维度 | 内容 |
|------|------|
| 是什么 | 同一份字节码可在不同操作系统 JVM 上运行的特性，口诀"编译一次到处运行" |
| 能做什么 | 屏蔽操作系统差异；统一标准类库 API；降低多平台部署成本 |
| 怎么用 | javac 编译出 .class，各平台装对应 JVM 运行 |
| 原理和工作流程 | 机制有三：javac 将源码编译为平台无关字节码；各操作系统有对应 JVM 实现负责翻译为本地机器码；标准类库提供统一 API 屏蔽底层差异。跨平台的是字节码，JVM 本身平台相关 |
| 缺点 | JVM 本身不跨平台，需为每类系统单独安装；GUI 等少数 API 仍有平台差异；间接执行带来性能损耗 |

## 三、实战应用

### 3.1 完整的环境搭建与 HelloWorld 演练

| 维度 | 内容 |
|------|------|
| 是什么 | 从零完成 JDK 下载、环境配置、编写运行第一个程序的全流程实操 |
| 能做什么 | 验证开发环境可用；练习命令行编译运行；掌握命令行参数传递 |
| 怎么用 | 下载安装→配 JAVA_HOME 与 Path→javac 编译→java 运行 |
| 原理和工作流程 | 下载 Temurin JDK17 安装包并记录路径；配置 JAVA_HOME 指向根目录，Path 追加 `%JAVA_HOME%\bin`；编写含 main 方法的 HelloWorld.java，用 `javac -encoding UTF-8` 编译，`java HelloWorld 张三 李四` 运行，args 数组接收命令行参数 |
| 缺点 | 步骤多易出错；编码问题需手动指定参数；命令行参数无类型校验 |

### 3.2 常用 JDK 命令行工具速查

| 维度 | 内容 |
|------|------|
| 是什么 | JDK 自带的一组命令行可执行工具，覆盖编译运行打包监控等场景 |
| 能做什么 | javac 编译、java 运行、javadoc 生成文档、jar 打包、javap 反编译、jps 与 jstat 监控 JVM |
| 怎么用 | `javac X.java`、`jps -l`、`jstat -gc <pid>` |
| 原理和工作流程 | 这些工具位于 JDK 的 bin 目录，多数通过包装 native 库或调用 JDK API 实现。javac 是用 Java 写的编译器，java 启动 JVM 实例，jps 通过 HotSpot 内部协议枚举本机 Java 进程，jstat 读取 HotSpot 性能计数器输出 GC 统计 |
| 缺点 | 命令参数繁多需记忆；部分工具仅对 HotSpot 有效；交互体验不如图形化工具 |

### 3.3 JShell 快速实验（JDK 9+）

| 维度 | 内容 |
|------|------|
| 是什么 | JDK9 引入的 Java 交互式 REPL 工具，无需写完整类即可执行代码片段 |
| 能做什么 | 即时求值表达式；快速验证 API；逐行试验逻辑；保存加载片段 |
| 怎么用 | 命令行输入 `jshell` 进入，`/exit` 退出 |
| 原理和工作流程 | JShell 内部维护一个片段状态机，将用户输入包装为内部类实例，借助编译器 API 编译并加载到内部类加载器，再通过反射调用执行。变量与方法片段保留在会话中可相互引用，/exit 结束会话释放资源 |
| 缺点 | 仅 JDK9+ 可用；不支持完整包结构；片段间状态隐式耦合，复杂逻辑难以管理 |

## 四、常见面试题

### 1. Java 语言的跨平台原理是什么？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查字节码与 JVM 分工的跨平台机制理解 |
| 能做什么 | 解释为何同份 .class 多平台运行；区分编译期与运行期；辨析 JVM 平台相关性 |
| 怎么用 | 口述"字节码跨平台，JVM 平台相关" |
| 原理和工作流程 | 源码经 javac 编译为平台无关字节码；各操作系统对应不同 JVM 实现负责把字节码解释或 JIT 编译为本地机器码；标准类库统一 API 屏蔽系统差异。同份字节码可在任何装了对应 JVM 的平台运行 |
| 缺点 | 仅靠口诀易忽略 JVM 本身不跨平台；初学者常误以为 JVM 也跨平台 |

### 2. JDK、JRE、JVM 的区别和联系？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 Java 运行环境三层包含关系的概念辨析 |
| 能做什么 | 区分开发与运行需求；说明安装选型依据；解释工具来源 |
| 怎么用 | 记忆 JDK > JRE > JVM |
| 原理和工作流程 | JVM 是字节码执行引擎；JRE = JVM + 核心类库，面向只需运行的用户；JDK = JRE + javac、javadoc、jar 等开发工具，面向开发者。三者层层包含，开发装 JDK 即可 |
| 缺点 | 概念易混淆；现代 JDK 安装已不再单独提供 JRE，JDK11+ 用 jlink 裁剪运行时 |

### 3. 为什么配置 JAVA_HOME 环境变量？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查环境变量约定与工具依赖的理解 |
| 能做什么 | 统一引用 JDK 路径；便于切换版本；满足 Maven、Gradle、Tomcat 依赖 |
| 怎么用 | Path 中写 `%JAVA_HOME%\bin` 而非硬编码 |
| 原理和工作流程 | JAVA_HOME 是业界约定变量，指向 JDK 根目录。Path 通过引用它拼接 bin 路径，更换 JDK 版本只改 JAVA_HOME 一处即可生效。众多 Java 工具启动脚本读取该变量定位 JDK |
| 缺点 | 变量名拼写错误静默失效；多 JDK 切换仍需手动改值 |

### 4. Java 程序从编写到运行经历了哪些步骤？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查从源码到输出的全链路执行流程 |
| 能做什么 | 描述编译阶段；描述类加载阶段；描述执行阶段 |
| 怎么用 | 编写→javac 编译→类加载→执行 |
| 原理和工作流程 | 编写 .java 源码；javac 词法、语法、语义分析生成 .class 字节码；类加载经历加载、验证、准备、解析、初始化；执行引擎解释执行字节码并对热点代码 JIT 编译为本地机器码；最后输出结果 |
| 缺点 | 流程长易遗漏阶段；JIT 预热阶段常被忽略 |

### 5. Java 是编译型语言还是解释型语言？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查对 Java 半编译半解释执行模型的理解 |
| 能做什么 | 辨析编译与解释；说明 JIT 角色；定位 Java 在两类语言间位置 |
| 怎么用 | 回答"半编译半解释" |
| 原理和工作流程 | 先编译：javac 把源码编译为字节码 .class；后解释：JVM 解释执行字节码，并对热点代码用 JIT 编译为本地机器码提升性能。因此兼具编译型与解释型特征 |
| 缺点 | 二元分类过于简化；JIT 细节常被忽略 |

### 6. main 方法的签名为什么是固定的？

| 维度 | 内容 |
|------|------|
| 是什么 | 考查 main 方法各修饰符与参数的设计原因 |
| 能做什么 | 解释 public、static、void、main、args 各自必要性；说明 JVM 入口约定 |
| 怎么用 | 固定写 `public static void main(String[] args)` |
| 原理和工作流程 | public 使 JVM 可从外部调用；static 使 JVM 无需创建对象即可调用；void 因退出码由 System.exit 返回；main 是 JVM 规范约定的入口名不可改；String[] args 接收命令行参数由 JVM 自动传入 |
| 缺点 | 签名僵化不可自定义；args 参数现代项目很少使用 |
