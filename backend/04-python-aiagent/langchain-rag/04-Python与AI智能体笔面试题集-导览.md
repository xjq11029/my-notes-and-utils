### 1. 可变数据类型判断

| 维度 | 内容 |
|------|------|
| 是什么 | Python数据类型按是否可原地修改分为可变与不可变两类。 |
| 能做什么 | 区分list/dict/set可变与int/str/tuple不可变；判断修改时是否创建新对象。 |
| 怎么用 | `list`可变 `x.append(1)`；`tuple`不可变 `t[0]=1` 报错。 |
| 原理和工作流程 | 可变类型修改在原对象上操作不改变id，不可变类型修改会创建新对象并重新绑定；list/dict/set内部结构支持原地变更，int/str/tuple修改即新建对象。 |
| 缺点 | 可变类型作默认参数或共享引用易产生跨调用副作用；不可变类型频繁修改产生大量临时对象。 |

### 2. 装饰器特性

| 维度 | 内容 |
|------|------|
| 是什么 | Python装饰器是不修改原函数代码而增强其功能的高阶函数机制。 |
| 能做什么 | 包装原函数；保留元信息用@wraps；多装饰器从内向外叠加。 |
| 怎么用 | `@decorator1\n@decorator2\ndef f(): pass`。 |
| 原理和工作流程 | 装饰器本质是接收函数返回函数的高阶函数，@语法在定义时将原函数传入装饰器并用返回值替换原名字；多装饰器按从下到上（从内到外）顺序逐层包装。 |
| 缺点 | 多层装饰器调用栈深调试困难；不使用@wraps丢失原函数元信息；误用闭包变量产生状态污染。 |

### 3. 默认参数可变对象陷阱

| 维度 | 内容 |
|------|------|
| 是什么 | Python默认参数在函数定义时求值并跨调用共享的机制导致的常见陷阱。 |
| 能做什么 | 识别可变默认值累积bug；用None作默认值规避；理解求值时机。 |
| 怎么用 | `def f(x=None):\n    if x is None: x=[]`。 |
| 原理和工作流程 | 默认参数在def执行时求值一次存于__defaults__，每次调用未传参复用同一对象，可变默认值被修改后累积到下次调用，故可变默认值会跨调用共享状态。 |
| 缺点 | 可变默认值致隐蔽累积bug；需用None哨兵模式规避；新手难定位该类问题。 |

### 4. __new__与__init__

| 维度 | 内容 |
|------|------|
| 是什么 | Python对象创建过程中__new__负责分配实例、__init__负责初始化实例的两个魔术方法。 |
| 能做什么 | __new__创建并返回实例；__init__初始化实例属性；__new__先于__init__调用。 |
| 怎么用 | `def __new__(cls,...): return super().__new__(cls)`。 |
| 原理和工作流程 | 创建对象先调用__new__（静态方法）分配内存返回类实例，再调用__init__（实例方法）对该实例初始化属性；单例模式等需重写__new__控制实例创建。 |
| 缺点 | 重写__new__易出错如忘记返回实例；两者职责划分新手易混淆；不可变类型需在__new__设置属性。 |

### 5. GIL全局解释器锁

| 维度 | 内容 |
|------|------|
| 是什么 | CPython中保证同一时刻仅一个线程执行字节码的全局解释器锁。 |
| 能做什么 | 解释多线程无法利用多核原因；指导CPU密集任务用多进程；理解GIL仍存在。 |
| 怎么用 | CPU密集任务用 `multiprocessing`；IO密集可用 `threading`。 |
| 原理和工作流程 | CPython内存管理非线程安全，GIL使同一时刻仅一个线程执行字节码，CPU密集多线程被串行化无法利用多核；IO操作会释放GIL故IO密集多线程仍有效；多进程各自独立GIL可并行。 |
| 缺点 | CPU密集多线程无法并行性能差；GIL释放时机影响并发公平性；移除GIL改动巨大至今未完成。 |

### 12. RAG分块原因

### 1. 浅拷贝与深拷贝

| 维度 | 内容 |
|------|------|
| 是什么 | Python中浅拷贝只拷贝外层引用、深拷贝递归拷贝整个对象树的两种拷贝方式。 |
| 能做什么 | 浅拷贝复制外层不复制子对象；深拷贝完全独立；按对象层次选择。 |
| 怎么用 | `copy.copy(obj)` 浅拷贝；`copy.deepcopy(obj)` 深拷贝。 |
| 原理和工作流程 | 浅拷贝创建新对象但内部仍引用原子对象，修改内部可变对象影响原对象；深拷贝递归复制整个对象及所有子对象完全独立，修改互不影响；全不可变对象可用浅拷贝。 |
| 缺点 | 浅拷贝致嵌套可变对象意外共享；深拷贝对循环引用与大对象耗内存性能；需按场景选择。 |

### 2. 闭包

| 维度 | 内容 |
|------|------|
| 是什么 | 内部函数引用外部函数变量且外部函数返回内部函数形成的闭包结构。 |
| 能做什么 | 捕获并保留外层变量；实现数据封装；延迟计算；构建装饰器。 |
| 怎么用 | `def make_adder(n):\n    def adder(x): return x+n\n    return adder`。 |
| 原理和工作流程 | 内部函数引用外部函数的局部变量，外部函数返回内部函数后，被捕获变量作为闭包环境保留不被垃圾回收，每次调用闭包仍访问该变量，实现数据封装与延迟计算。 |
| 缺点 | 闭包变量长期驻留内存；调试调用链不直观；过度使用降低可读性。 |

### 3. 生成器

| 维度 | 内容 |
|------|------|
| 是什么 | 使用yield关键字返回数据、按需生成元素的特殊迭代器。 |
| 能做什么 | 内存高效处理大文件与无限序列；延迟计算；简化迭代逻辑。 |
| 怎么用 | `def gen():\n    yield 1`；`next(gen())`。 |
| 原理和工作流程 | 生成器函数遇yield暂停并返回值保留执行状态，下次next从暂停处继续执行到下一个yield，按需生成元素不一次性构建全部数据，相较普通列表节省内存与计算资源。 |
| 缺点 | 只能迭代一次不可随机访问；调试状态机复杂；无len与索引。 |

### 5. Agent特点

### 6. Plan-and-Execute Agent

| 维度 | 内容 |
|------|------|
| 是什么 | 分规划与执行两阶段的Agent架构。 |
| 能做什么 | 先整体规划分解子任务；按计划逐步执行；汇总结果；减少重复思考。 |
| 怎么用 | 规划阶段生成计划 → 执行阶段逐步调用工具 → 汇总答案。 |

| 缺点 | 规划失误致整体执行偏差；计划僵化难应对动态变化；中间步骤失败需重新规划。 |

### 8. RAG优化方法

| 是什么 | RAG实践中提升检索与生成质量的一系列优化方法。 |
| 能做什么 | 优化分块；选择嵌入模型；多路召回重排序；上下文压缩；多层RAG；结果融合；LLM提炼。 |
| 怎么用 | 语义分块 + 混合检索 + Reranker + 上下文压缩组合。 |
| 原理和工作流程 | 通过语义分块保留语义、选择领域适配嵌入模型、多路召回加重排序提升准确率、上下文压缩去冗余、多层RAG粗召精排、结果融合提高召回、LLM提炼压缩检索内容等手段系统优化RAG效果。 |
| 缺点 | 优化手段多组合复杂；各方法增加延迟与成本；需按场景调参验证。 |

---

### 9. Zero/One/Few-Shot

| 维度 | 内容 |
|------|------|
| 是什么 | Prompt中提供零个、一个、少量示例的三种提示方式。 |
| 能做什么 | Zero-Shot不给示例；One-Shot给一个示例；Few-Shot给少量示例；按任务复杂度选择。 |
| 怎么用 | Zero-Shot直接提问；Few-Shot在Prompt列2-5个示例。 |
| 原理和工作流程 | Zero-Shot不提供示例直接让模型完成任务省token适用简单任务；One-Shot给一个示例展示格式；Few-Shot给少量示例帮助模型理解任务要求与输出格式不需微调即获效果，示例越多效果越好但消耗更多token。 |
| 缺点 | 示例增多消耗token与上下文；示例选择不当误导模型；复杂任务Few-Shot仍可能不足。 |

### 10. Self-Consistency

| 维度 | 内容 |
|------|------|
| 是什么 | 对同一问题生成多个推理路径再投票选择最一致答案的后处理提示技巧。 |
| 能做什么 | 生成多条推理路径；投票选多数答案；提升推理任务准确率。 |
| 怎么用 | 同一问题多次采样生成 → 对答案投票取多数。 |
| 原理和工作流程 | 对同一问题让LLM生成多个不同推理路径，由于模型偶尔在推理中出错，通过投票选择最一致的多数答案能有效滤除偶发错误，显著提升数学等推理任务的准确率。 |
| 缺点 | 多次采样增加token与延迟；答案聚合对开放性问题困难；成本成倍上升。 |
